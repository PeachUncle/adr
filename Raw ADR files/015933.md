# ADR-002: Use Filesystem for File Storage

## Status

Accepted

## Context

RustDrop needs to store uploaded files durably and retrieve them efficiently. The primary options for file storage are:

1. **Filesystem storage**: Store files directly on the local disk
2. **Database storage**: Store files as BLOBs in a database (PostgreSQL, SQLite)
3. **Object storage**: Use S3-compatible storage (AWS S3, MinIO, etc.)
4. **Distributed filesystem**: Use systems like HDFS or GlusterFS

Key requirements:
- Support files up to hundreds of megabytes
- Handle concurrent uploads and downloads
- Stream files without loading entirely into memory
- Simple deployment with minimal dependencies
- Easy backup and recovery
- Cost-effective for self-hosted deployments

## Decision

We chose **filesystem storage** with UUID-based file naming.

### Implementation Details

```rust
// Files are stored with UUID names to prevent collisions
let stored_name = Uuid::new_v4().to_string();
let file_path = upload_dir.join(&stored_name);

// Streaming write - never loads entire file into memory
let mut file = tokio::fs::File::create(&file_path).await?;
while let Some(chunk) = field.chunk().await? {
    file.write_all(&chunk).await?;
}
```

Files are stored in a configurable upload directory (default: `uploads/`) with their original names preserved only in metadata.

## Consequences

### Positive

1. **Simplicity**: No additional infrastructure required beyond a filesystem
2. **Streaming I/O**: Tokio's async file I/O enables efficient streaming without buffering
3. **Performance**: Direct filesystem access is faster than database BLOB operations for large files
4. **Transparency**: Files can be inspected, backed up, or migrated using standard tools
5. **No Size Limits**: Unlike database BLOBs, no artificial size constraints
6. **Cost**: No additional storage service costs for self-hosted deployments
7. **Single Binary**: Contributes to the goal of a self-contained deployment

### Negative

1. **Horizontal Scaling**: Multiple instances would require shared storage (NFS, etc.)
2. **No Built-in Replication**: Must rely on filesystem-level solutions for redundancy
3. **Backup Complexity**: Need to coordinate file and metadata backups
4. **Cloud Deployment**: Less cloud-native than object storage solutions

### Neutral

1. **Security**: Files are protected by OS-level permissions; additional encryption could be added if needed

## Alternatives Considered

### Database BLOB Storage (PostgreSQL/SQLite)

**Pros:**
- Single backup for data and metadata
- Transactional consistency
- Built-in replication options (for PostgreSQL)

**Cons:**
- Poor performance for large files (100MB+ can cause issues)
- Streaming is complex; often buffers entire file
- Increases database size significantly
- SQLite has practical size limits for BLOBs

**Why not chosen:** The performance characteristics for large files are poor, and it adds unnecessary database complexity for a file-sharing service where the primary payload is binary files.

### Object Storage (S3/MinIO)

**Pros:**
- Excellent scalability
- Built-in replication and durability
- Industry standard API
- Ideal for cloud deployments

**Cons:**
- Requires additional infrastructure (MinIO for self-hosted)
- Added latency for local deployments
- More complex deployment
- Additional cost for cloud S3

**Why not chosen:** For the primary use case of self-hosted, single-instance deployment, the added infrastructure complexity isn't justified. However, this could be reconsidered for a future cloud-native version.

### Distributed Filesystem (HDFS, GlusterFS)

**Pros:**
- Built-in replication
- Handles very large files
- Scales horizontally

**Cons:**
- Significant operational complexity
- Overkill for typical deployment sizes
- Requires cluster management

**Why not chosen:** The operational overhead far exceeds the needs of a simple file-sharing service.

## Design Decisions

### UUID-Based File Naming

Files are stored with UUID v4 names rather than original filenames:

```
uploads/
├── 87b77d35-8042-4b68-a035-69141febffc1
├── a3d9f2e1-7c45-4b89-9012-345678901234
└── ...
```

**Rationale:**
1. **No filename collisions**: Two users uploading "report.pdf" get unique storage names
2. **Security**: Original filenames aren't exposed in the filesystem
3. **Path traversal prevention**: UUIDs can't contain `../` or other malicious paths
4. **Consistent naming**: No encoding issues with special characters

### Streaming Writes

Files are streamed directly to disk as chunks arrive:

```rust
while let Some(chunk) = field.chunk().await? {
    file.write_all(&chunk).await?;
}
```

**Rationale:**
- Handles files larger than available memory
- Provides backpressure through async I/O
- Reduces latency (writing starts immediately)

## Future Considerations

1. **Optional S3 Backend**: Could add a storage abstraction layer to support S3 for cloud deployments
2. **Encryption at Rest**: Could encrypt files before writing to disk
3. **Deduplication**: Could hash files and deduplicate identical uploads
4. **Cleanup Job**: Already implemented for expired files; could be enhanced with orphan detection
