# Secure options for (pypi) package supply to build solutions in Azure ML

## Context and Problem Statement

Customers need a secure way to supply (pypi) packages/libraries for developers. The CAIRA implementation aims to be secure by default but offer flexibility to conform with a customer's chosen approach to securely supply packages for the developer.

We need to determine which settings to use for security and networking from Azure ML Compute.

## Decision Drivers

* Secure but flexible approach
* Able to limit the access from dev environment to only the certain ip ranges/custom dns domains, etc. in order to be able to fetch packages from only white-listed and pre-approved endpoints (locations like approved dns domains, etc.)
* Able to limit deployment of packages that have known security vulnerabilities, etc.
* A known issue in AML is that if all outbound and inbound access is disabled, it is not possible to create a compute instance within a VNET and subnet, only a compute cluster

## Considered Options

* Restricted outbound access from AML/AI Studio (allow only whitelisted outbound access)
* Containerize all packages
* Pre-download the packages for solutions
* Use an artefact management solution

## Decision Outcome

By default, restrict inbound and outbound access from AML/AI studio to only allow whitelisted IPs or domains and necessary service tags.

## Pros and Cons of the Options

### Restricted outbound access from AML/AI Studio (allow only whitelisted outbound access)

By default, disable internet outbound access from AML/AI studio. Allow only approved/whitelisted outbound access from AML/AI Studio.
For any test environments, developers can choose to accept the risk and allow internet outbound access when deploying the aml solution. The guidance will be documented on the manual steps needed to override network restrictions based on environment needs. This is intentionally kept as a manual step so as to ensure that the engineer understands and accepts the risk when overriding CAIRA's security recommendations.

* Good, simplifies the internal development process and can contain the risk exposure to un-managed endpoints
* Good, provides flexibility to customers to introduce their solution to secure package management
* *Bad*, could be too restrictive for quick and easy testing environments.
* *Bad*, requires explicit whitelisting of Azure services via Service Tags/FQDNs

### Containerize all solutions

Containerize all solutions built on CAIRA. Container image scanning will be required and customers may already have a solution in place.

* Good, all solutions can be pre-built; provides ability to consistently scan and validate solutions/packages in a container image.
* *Bad*, introduces additional components to the solution that would likely be replaced by a customer with their own solution and would introduce complexity and cost to the solution now that would reduce development velocity.
* *Bad*, does not conform to the first principles of the CAIRA project - "do not add anything that is not mandatory"
* *Bad*, reduces flexibility for brownfield deployments.

### Pre-download the packages for solutions

Pre-download the packages for solutions and then mount them in the solution storage for build.

* Good, all packages can be pre-downloaded and consistently scanned and validated.
* *Bad*, does not conform to the first principles of the CAIRA project - "do not add anything that is not mandatory"
* *Bad*, reduces flexibility for brownfield deployments.

### Use an artefact management solution

Use an artefact management solution such as [Azure Artifacts](https://learn.microsoft.com/en-us/azure/devops/artifacts/start-using-azure-artifacts?view=azure-devops&tabs=nuget%2Cnugetserver).

* Good, allows for central build and deployment of solutions.
* Good, ease of maintenance of CI/CD pipelines
* *Bad*, Not all customers use Azure Artifacts. Not common and most customers have bespoke artifact/package management solution
* *Bad*, hosting and maintaining custom artifact management solution is not focus of CAIRA
