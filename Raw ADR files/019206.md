# ADR-009: Elasticsearch for Full-Text Search

## Status

Accepted

## Context

The Trama platform requires robust search capabilities beyond simple proximity-based queries. Users need to:

1. **Search by Text**: Find artists by name, bio, style descriptions, and artwork titles
2. **Fuzzy Matching**: Handle typos and partial matches in search queries
3. **Relevance Ranking**: Return most relevant results first, not just exact matches
4. **Fast Performance**: Sub-second search response times even with thousands of artists
5. **Faceted Search**: Filter by multiple criteria (style, location, availability, rating)

PostgreSQL offers full-text search capabilities via `tsvector` and `tsquery`, but has limitations:

- **Limited Relevance Tuning**: Basic ranking, hard to customize
- **No Fuzzy Matching**: Exact word matching only, poor typo tolerance
- **Performance at Scale**: Full-text search can be slow on large datasets
- **Complex Queries**: Difficult to combine text search with other filters efficiently
- **No Analytics**: Limited search analytics and query insights
- **Language Support**: Basic stemming, limited multi-language support

The key tension is between using PostgreSQL's built-in full-text search (simpler, fewer dependencies) versus adding Elasticsearch (more powerful, additional infrastructure).

## Decision

We will use **Elasticsearch 9.2.2** for full-text search with the following approach:

**Architecture:**
- PostgreSQL remains the source of truth for all data
- Elasticsearch is a read-only search index, rebuilt from PostgreSQL
- MassTransit events keep Elasticsearch synchronized with PostgreSQL changes
- Search queries go to Elasticsearch, detail queries go to PostgreSQL

**Implementation:**
```
User Search Request
    ↓
API Search Endpoint
    ↓
Elasticsearch (get artist IDs)
    ↓
PostgreSQL (get full artist details)
    ↓
Return Results
```

**Synchronization:**
```
Artist Created/Updated in PostgreSQL
    ↓
MassTransit Event Published
    ↓
Search Module Consumer
    ↓
Update Elasticsearch Index
```

**Why Elasticsearch:**
- Industry-standard search engine with proven scalability
- Excellent full-text search with relevance tuning
- Built-in fuzzy matching and typo tolerance
- Fast aggregations for faceted search
- Geospatial support (can combine with PostGIS results)
- Rich query DSL for complex searches
- Search analytics and query insights

## Consequences

### Positive

- **Better Search Experience**: Fuzzy matching, typo tolerance, relevance ranking
- **Fast Performance**: Sub-second search even with large datasets
- **Flexible Queries**: Easy to combine text, filters, and sorting
- **Faceted Search**: Fast aggregations for filter counts
- **Search Analytics**: Track popular searches, zero-result queries
- **Scalability**: Elasticsearch scales horizontally as data grows
- **Multi-Language**: Better support for Portuguese, Spanish, English
- **Learning Value**: Gain experience with industry-standard search technology

### Negative

- **Additional Infrastructure**: Another service to run, monitor, and maintain
- **Operational Complexity**: Need to manage Elasticsearch cluster, backups, upgrades
- **Data Synchronization**: Must keep Elasticsearch in sync with PostgreSQL
- **Eventual Consistency**: Search results may be slightly stale (seconds)
- **Storage Overhead**: Data duplicated in Elasticsearch
- **Memory Requirements**: Elasticsearch requires significant RAM (1GB+ for MVP)
- **Reindexing Complexity**: Full reindex required for schema changes
- **Learning Curve**: Team must learn Elasticsearch query DSL

### Neutral

- **Single-Node Cluster**: MVP uses single Elasticsearch node (no clustering)
- **No Persistence Guarantee**: Can rebuild index from PostgreSQL if lost
- **Search-Only**: Elasticsearch not used for analytics or logging (separate tools)
- **Version 9.2.2**: Latest stable version at time of implementation

**Performance Considerations:**
- Elasticsearch returns only IDs, full data fetched from PostgreSQL
- Results cached in Redis (future) to reduce database load
- Pagination using `from` and `size` (search after for deep pagination)

## Alternatives Considered

**PostgreSQL Full-Text Search:**
- Pros: No additional infrastructure, simpler deployment, data consistency
- Cons: Limited relevance tuning, no fuzzy matching, slower at scale
- Rejected: Insufficient for good search UX, especially with typos

**Algolia (SaaS Search):**
- Pros: Managed service, excellent search UX, no infrastructure
- Cons: Cost ($1/month per 1K records), vendor lock-in, data privacy concerns
- Rejected: Want to learn Elasticsearch, avoid vendor lock-in

**Apache Solr:**
- Pros: Similar features to Elasticsearch, mature, open-source
- Cons: More complex configuration, smaller community, less modern
- Rejected: Elasticsearch has better .NET support and larger community

**Meilisearch:**
- Pros: Lightweight, fast, easy to use, good for small datasets
- Cons: Less mature, fewer features, limited scalability
- Rejected: Want to learn industry-standard tool (Elasticsearch)

**Typesense:**
- Pros: Fast, typo-tolerant, easy to use, good for small datasets
- Cons: Newer, smaller community, less proven at scale
- Rejected: Elasticsearch more widely used in industry

**Keep PostgreSQL Full-Text + Add Fuzzy Matching:**
- Pros: No new infrastructure, use pg_trgm for fuzzy matching
- Cons: Still limited relevance tuning, performance concerns
- Rejected: Elasticsearch provides better overall search experience

## Migration Path

**Phase 1 (MVP):**
- Use PostgreSQL full-text search
- Simple text matching on artist names and bios
- Good enough for initial users

**Phase 2 (Current):**
- Add Elasticsearch for better search
- Migrate existing search queries to Elasticsearch
- Keep PostgreSQL as fallback

**Phase 3 (Future):**
- Add search analytics
- Implement personalized search ranking
- Add ML-powered recommendations
