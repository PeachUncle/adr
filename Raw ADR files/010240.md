# ADR 003: SQLite for Local Storage

**Status:** Accepted

**Date:** 2025-10-13

**Deciders:** Development Team

## Context

Latera needs to store user data locally on the desktop:
- Saved articles/links with metadata (title, URL, description, image)
- User preferences and settings
- Tags and categories for organization
- Read/unread status, favorites, archive
- Full-text search capabilities
- Potentially hundreds to thousands of articles per user
- Fast query performance for UI rendering
- Data export/backup functionality
- No server dependency for core functionality (local-first)

Requirements:
- Offline-first: Works without internet connection
- Fast queries: <50ms for list views, <10ms for searches
- Simple backup: Easy to export user data
- Cross-platform: Works on Windows and macOS
- Relational data: Articles have tags, categories, metadata
- Future sync: Potential cloud sync later (not MVP)

## Decision

We will use **SQLite** via **better-sqlite3** as the local database solution.

### Schema Overview:

```sql
-- Articles table
CREATE TABLE articles (
  id TEXT PRIMARY KEY,
  url TEXT UNIQUE NOT NULL,
  title TEXT,
  description TEXT,
  image_url TEXT,
  domain TEXT,
  reading_time INTEGER,
  is_read BOOLEAN DEFAULT 0,
  is_favorite BOOLEAN DEFAULT 0,
  is_archived BOOLEAN DEFAULT 0,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  read_at INTEGER,
  archived_at INTEGER
);

-- Tags table
CREATE TABLE tags (
  id TEXT PRIMARY KEY,
  name TEXT UNIQUE NOT NULL,
  color TEXT,
  created_at INTEGER NOT NULL
);

-- Article tags junction
CREATE TABLE article_tags (
  article_id TEXT REFERENCES articles(id) ON DELETE CASCADE,
  tag_id TEXT REFERENCES tags(id) ON DELETE CASCADE,
  PRIMARY KEY (article_id, tag_id)
);

-- Full-text search index
CREATE VIRTUAL TABLE articles_fts USING fts5(
  title, description, content='articles', content_rowid='rowid'
);

-- Settings table
CREATE TABLE settings (
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL,
  updated_at INTEGER NOT NULL
);
```

## Consequences

### Positive

- **Zero Configuration**: No server setup, no connection management
- **Excellent Performance**: Embedded database, no network latency, <10ms queries
- **ACID Transactions**: Data integrity guarantees
- **Full-Text Search**: Built-in FTS5 for fast article search
- **Single File**: Easy backup (copy .db file), simple data export
- **Cross-Platform**: Works identically on Windows and macOS
- **SQL Power**: Complex queries, joins, aggregations with familiar syntax
- **Small Footprint**: ~2MB library, minimal memory overhead
- **Battle-Tested**: Used by browsers, mobile apps, embedded systems
- **Node Integration**: `better-sqlite3` is synchronous, simplifying main process code
- **Migration Support**: Easy schema evolution with migration scripts
- **No Dependencies**: No external database server required

### Negative

- **Single Writer**: No concurrent writes from multiple processes (not an issue for desktop app)
- **File Locking**: Potential issues if file accessed from multiple apps
- **Large Data Limits**: Performance degrades with >100k+ records (unlikely for reading list)
- **Binary Format**: Not human-readable like JSON (mitigated by export feature)
- **Native Module**: `better-sqlite3` requires compilation, adds build complexity
- **No Built-in Encryption**: Need to implement encryption separately if required
- **Manual Backups**: User responsible for backing up .db file (can automate)

### Mitigation Strategies

- Use Write-Ahead Logging (WAL) mode for better concurrency
- Implement automatic backups to user's cloud storage
- Add JSON export functionality for data portability
- Use prepared statements to prevent SQL injection
- Implement migration system (e.g., `node-migrate`) for schema changes
- Keep indexes optimized for fast queries
- Monitor database size and implement archive/cleanup features
- Use `better-sqlite3` for better performance than `sqlite3` package

## Alternatives Considered

### JSON Files
- **Pros**: Human-readable, simple, no dependencies, easy backup
- **Cons**: No indexing, slow search, no transactions, manual querying, data corruption risk, poor performance with >100 items

### IndexedDB (in Renderer)
- **Pros**: Browser-native, asynchronous, good for large data
- **Cons**: Async complexity, limited query capabilities, no SQL, browser-only (not main process), harder to backup, quota limits

### LevelDB/RocksDB
- **Pros**: Fast writes, embedded, key-value simplicity
- **Cons**: No SQL, manual indexing, no relations, complex query logic, less familiar to developers

### Realm Database
- **Pros**: Object-oriented, reactive queries, mobile-friendly
- **Cons**: Larger library, commercial licensing for large apps, less familiar syntax, heavier than SQLite

### MongoDB (Embedded)
- **Pros**: Schema-less, JSON documents, flexible
- **Cons**: Requires server process, larger footprint, overkill for desktop app, more complex setup

### PostgreSQL (Embedded)
- **Pros**: Full SQL features, excellent for complex queries
- **Cons**: Requires server process, heavier resource usage, complex setup for embedded use

## Implementation Details

### Library Choice: better-sqlite3

We choose `better-sqlite3` over `sqlite3` because:
- **Synchronous API**: Simpler code in main process, no callback hell
- **4-6x Faster**: Better performance for typical queries
- **Better TypeScript Support**: Excellent type definitions
- **Active Maintenance**: Well-maintained, modern API
- **Simpler Error Handling**: Throws exceptions vs callbacks

### Database Location

```typescript
// Store in user data directory
import { app } from 'electron';
import path from 'path';

const dbPath = path.join(app.getPath('userData'), 'latera.db');
```

Locations:
- **Windows**: `C:\Users\{username}\AppData\Roaming\Latera\latera.db`
- **macOS**: `~/Library/Application Support/Latera/latera.db`

### Performance Optimizations

```sql
-- Enable WAL mode for better concurrency
PRAGMA journal_mode = WAL;

-- Optimize for performance
PRAGMA synchronous = NORMAL;
PRAGMA cache_size = -64000;  -- 64MB cache
PRAGMA temp_store = MEMORY;

-- Create indexes
CREATE INDEX idx_articles_created_at ON articles(created_at DESC);
CREATE INDEX idx_articles_is_read ON articles(is_read);
CREATE INDEX idx_articles_is_favorite ON articles(is_favorite);
CREATE INDEX idx_articles_domain ON articles(domain);
```

### Migration System

Use custom migration runner:

```typescript
interface Migration {
  version: number;
  up: (db: Database) => void;
}

const migrations: Migration[] = [
  {
    version: 1,
    up: (db) => {
      db.exec(`CREATE TABLE articles (...)`);
    }
  }
];
```

### Backup Strategy

- **Automatic Daily Backups**: Copy .db file to user-selected location
- **Export to JSON**: Allow full data export in JSON format
- **Import from JSON**: Allow restoration from JSON export
- **Cloud Sync** (Future): Sync to user's cloud storage (Dropbox, iCloud)

## Query Performance Targets

- **List all articles**: <50ms for 1000 items
- **Search articles**: <100ms for FTS query
- **Insert article**: <10ms
- **Update article**: <5ms
- **Delete article**: <5ms
- **Tag filtering**: <30ms

## Notes

- Start with simple schema, add complexity as needed
- Use transactions for batch operations
- Implement soft deletes (archived) before hard deletes
- Consider adding `content` field for full article text (future)
- Monitor database size and implement cleanup for archived items
- Add database vacuum on app quit to optimize file size
- Use prepared statements for all queries to prevent injection

## Future Considerations

- **Encryption**: Implement SQLCipher if sensitive data storage needed
- **Cloud Sync**: Design sync layer on top of SQLite (operational transform or CRDTs)
- **Multi-Device**: Consider sync protocol for shared reading list
- **Analytics**: Track usage patterns (reading time, popular domains)
