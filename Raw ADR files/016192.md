# ADR-001: Vulnerability Service Consolidation

**Status**: Proposed  
**Date**: 2025-09-18  
**Author**: Refactoring Analysis  

## Context

The vulnerability domain has evolved three different service implementations:

1. **PostgreSqlVulnerabilityService** (service.rs) - Original stub implementation
2. **EnhancedVulnerabilityService** (enhanced_service.rs) - Currently used in production
3. **ImprovedEnhancedVulnerabilityService** (improved_enhanced_service.rs) - Most advanced with false positive reduction

This proliferation happened due to incremental feature development without proper refactoring.

## Decision

We will consolidate all three services into a single `VulnerabilityService` implementation with the following design:

### Core Service Structure
```rust
pub struct VulnerabilityService {
    repository: VulnerabilityRepository,
    confirmation_repository: VulnerabilityConfirmationRepository,
    false_positive_reducer: FalsePositiveReducer,
    config: VulnerabilityServiceConfig,
}
```

### Configuration-Driven Behavior
```rust
pub struct VulnerabilityServiceConfig {
    pub enable_false_positive_reduction: bool,
    pub confidence_threshold: f64,
    pub enable_confirmation_system: bool,
    pub max_cpe_matches_per_software: usize,
}
```

### Extension Points
1. **Pluggable False Positive Reduction**: Interface for different reduction strategies
2. **Configurable Confidence Thresholds**: Runtime behavior modification
3. **Strategy Pattern for CPE Matching**: Different matching algorithms
4. **Observable Pipeline**: Hooks for monitoring and debugging

## Implementation Plan

### Phase 1: Create Unified Service
1. Create new consolidated service based on ImprovedEnhancedVulnerabilityService
2. Add configuration layer for backward compatibility
3. Implement feature flags for gradual migration

### Phase 2: Migrate Production Usage
1. Update lib.rs to use new service with enhanced_service config
2. Add integration tests comparing old vs new behavior
3. Deploy with feature flags to ensure identical behavior

### Phase 3: Enable Advanced Features
1. Enable false positive reduction in production
2. Add confirmation system integration
3. Remove legacy services

### Phase 4: Cleanup
1. Delete old service files
2. Update all imports and tests
3. Update documentation

## Consequences

### Positive
- Single source of truth for vulnerability logic
- False positive reduction becomes available in production
- Clear extension points for future enhancements
- Reduced maintenance burden
- Better test organization

### Negative
- Temporary complexity during migration
- Risk of regression during consolidation
- Need to maintain backward compatibility during transition

## Implementation Notes

### Preserved Features
- All current production behavior from EnhancedVulnerabilityService
- All advanced features from ImprovedEnhancedVulnerabilityService
- All test coverage from existing implementations

### Migration Strategy
- Feature flags to control behavior
- Side-by-side comparison testing
- Gradual rollout with monitoring

### Extension Architecture
- Plugin interfaces for new reduction strategies
- Configuration-driven feature enablement
- Observable pipeline for debugging and monitoring
