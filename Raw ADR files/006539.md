# Decision: Pipeline Architecture - Human-Equivalent Approach with On-Demand Metrics

Date: 2025-10-31

## Context

The video editing pipeline needed to balance several competing concerns:
- Processing speed and user experience (fast initial feedback)
- CPU cost per video (expensive audio analysis upfront vs on-demand)
- Edit quality (word-accurate cuts vs segment-level granularity)
- Scalability (works for both freemium and premium tiers)

Multiple approaches were evaluated for when and how to compute audio metrics (energy, F0, pitch variance, voiced ratio) for word-level editing.

## Options Considered

- **Option A: Transcript-Only (Naive)**
  - Use transcript to drive everything; minimal audio analysis
  - Pros: Fastest, lowest CPU cost, good for language-heavy content
  - Cons: Misses audio cues (energy, breaths, filler), risk of awkward cuts, relies on transcript accuracy

- **Option B: Original Segment-First**
  - Segment-level analysis only; each segment gets single scores
  - Pros: Simple, fast, deterministic
  - Cons: Coarse cuts, no mid-sentence trims, poor pacing

- **Option C: Full Word-Level Analysis Upfront (Modification 1)**
  - Compute per-word metrics for entire file at ingest
  - Store complete word-level feature set
  - Pros: Highest deterministic quality, word-accurate trims, prosody-aware
  - Cons: High upfront CPU, longer ingest, wasted work on files never refined

- **Option D: Transcript-First with On-Demand Metrics (Human-Equivalent)**
  - Transcript-first storyboard and candidate selection
  - Compute cheap audio metrics at ingest (RMS, VAD)
  - Compute per-word energy/F0 only for shortlisted candidates or on demand
  - Deterministic validator enforces snap/filler/tail/crossfade rules
  - Pros: Matches human editor workflow, fast initial UX, lower average compute, high final quality
  - Cons: More engineering complexity (MetricStore, cache, audio random access), potential recompute unless candidates locked

- **Option E: Hybrid Strategy**
  - Default: Transcript-first + on-demand metrics
  - Optional background worker for full per-word precompute for finalized/premium files
  - Pros: Fast UX and low average cost, deterministic high-quality exports when required
  - Cons: More components (worker, cache invalidation)

## Decision

Chose **Option D (Human-Equivalent)** for MVP, with **Option E (Hybrid)** as production evolution path.

**Rationale:**
- Matches how human video editors actually work (review transcript first, then refine audio cuts)
- Fast initial user experience (low latency)
- Lower average compute cost (only process what gets used)
- High quality when needed (full audio analysis on selected ranges)
- Suitable for interactive editor and freemium model

**Implementation approach:**
1. Always produce `words[{text, start, end, confidence}]` at ingest
2. Compute cheap metrics (frame RMS, VAD, silence ranges) and cache them
3. Compute heavy features (F0, pitch) on-demand; cache results keyed by file+range
4. Use deterministic validator as final arbiter for cuts
5. Lock candidate IDs between storyboard and refine passes to avoid churn

## Consequences

**Positive:**
- Fast initial UX (users see results quickly)
- Lower average cost per video (only ~20-30% of content gets full analysis)
- Scales to freemium model (free tier = basic cuts, paid = full analysis)
- Can offer optional "premium export" with full precompute for finalized projects

**Negative:**
- Engineering complexity: requires MetricStore, caching layer, audio random access
- Potential recompute if user changes structure after analysis
- Must carefully manage cache invalidation
- More complex debugging (need to track which metrics computed when)

**Affected Areas:**
- Audio processing pipeline (ingest.py, word_metrics.py)
- Storyboard generation (must work with partial metrics)
- Assembly (must request metrics on-demand for selected ranges)
- Caching layer (new MetricStore component needed)
- API design (endpoints for progressive refinement)
