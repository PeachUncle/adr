# ADR-003: SQLite Test Configuration for Concurrency Management

## Status

Accepted

## Context

After migrating from ETS to SQLite (ADR-001), we encountered concurrency issues during test execution:

1. **Database Busy Errors**: Multiple tests accessing SQLite simultaneously caused "Database busy" errors
2. **SQLite Write Lock**: SQLite only allows one writer at a time, causing conflicts in parallel tests
3. **Async Test Issues**: ExUnit's async tests don't work well with SQLite's single-writer limitation
4. **Pool Size Conflicts**: Multiple database connections competing for write access

## Decision

We will configure the test environment to work within SQLite's concurrency constraints:

1. Set pool_size to 1 to prevent connection conflicts
2. Disable async tests globally
3. Increase queue timeouts to handle wait times
4. Use Ecto.Adapters.SQL.Sandbox in manual mode

## Implementation

### Test Configuration (config/test.exs)

```elixir
config :shared_ledger, SharedLedger.Repo,
  database: Path.expand("../shared_ledger_test.db", __DIR__),
  pool_size: 1,  # Single connection to avoid conflicts
  pool: Ecto.Adapters.SQL.Sandbox,
  queue_target: 5000,  # Increased timeout
  queue_interval: 5000  # Increased check interval
```

### Test Helper (test/test_helper.exs)

```elixir
ExUnit.start()
Ecto.Adapters.SQL.Sandbox.mode(SharedLedger.Repo, :manual)

# Disable async tests due to SQLite concurrency limitations
Application.put_env(:ex_unit, :async, false)
```

## Consequences

### Positive

- **Test Stability**: Eliminates "Database busy" errors
- **Predictable Execution**: Tests run sequentially without conflicts
- **Simpler Debugging**: No race conditions between tests
- **Consistent Results**: Removes intermittent failures from concurrency

### Negative

- **Slower Test Suite**: Tests run sequentially instead of in parallel
- **Longer CI Times**: Build times increase due to sequential execution
- **Resource Underutilization**: Can't leverage multiple CPU cores for tests
- **Scalability Limit**: Test suite becomes slower as more tests are added

### Neutral

- **Different from Production**: Test configuration differs significantly from production setup
- **Migration Path**: When moving to PostgreSQL, these restrictions can be removed

## Future Improvements

When migrating to PostgreSQL for production:

1. Re-enable async tests by removing the Application.put_env call
2. Increase pool_size back to 5 or more
3. Remove queue timeout configurations
4. Update test tags to mark tests as async: true where appropriate

## Trade-offs

We accept slower test execution in exchange for:

- Stability during development
- Ability to use SQLite for MVP
- Simpler test debugging
- Consistent CI builds
