# ADR-003: Domain Service Standardization

## Status
Accepted

## Date
2025-09-19

## Context

As the Scopeon Server codebase has grown, we've identified inconsistencies in how domain services are structured, how errors are handled, and how business logic is organized. Different domains follow different patterns, making the codebase harder to understand, maintain, and extend.

### Problems Identified

1. **Inconsistent Error Handling**: Different domains use different error types and patterns
2. **Mixed Service Patterns**: Some services use traits, others don't; some have repository abstractions, others access databases directly
3. **Unclear Module Boundaries**: Public interfaces vary between domains
4. **Testing Inconsistencies**: Different testing patterns and coverage across domains
5. **Documentation Gaps**: Service responsibilities and interfaces not clearly documented

### Requirements

We need to establish consistent patterns across all domain services while improving error handling, testability, and maintainability. The solution should maintain clean architecture principles and provide a clear migration path for existing services.

## Decision

We will standardize all domain services to follow a consistent pattern with four core components:

### 1. Standardized Error Types (`error.rs`)

All domains must define their own error type using `thiserror::Error` with standard variants:

```rust
#[derive(Debug, Error)]
pub enum DomainError {
    #[error("Database operation failed: {0}")]
    DatabaseError(String),
    
    #[error("Validation failed: {0}")]
    ValidationError(String),
    
    #[error("Resource not found: {message}")]
    NotFound { message: String },
    
    #[error("Operation not authorized: {operation}")]
    Unauthorized { operation: String },
    
    #[error("Access forbidden: {reason}")]
    Forbidden { reason: String },
    
    #[error("Resource conflict: {reason}")]
    Conflict { reason: String },
    
    #[error("Business rule violation: {rule}")]
    BusinessRuleViolation { rule: String },
    
    // Domain-specific variants as needed
}
```

**Error Helper Methods**: Each error type should provide helper methods for common error creation patterns to reduce boilerplate.

### 2. Domain Models (`models.rs`)

All domain entities and DTOs should be organized in a single models file with:

- **Main Entity**: Core business entity with all fields
- **Creation DTOs**: `NewEntity` structs for creation operations
- **Update DTOs**: Update request structures
- **Status Enums**: Business-relevant status types
- **Business Logic**: Entity methods for validation and business rules
- **Builder Patterns**: For complex creation scenarios

### 3. Service Layer (`service.rs`)

All domains should define a service trait and implementation:

```rust
#[async_trait]
pub trait DomainService: Send + Sync {
    async fn operation(&self, params: Params) -> Result<ReturnType, DomainError>;
}

pub struct PostgreSqlDomainService {
    repository: Arc<dyn DomainRepository>,
}
```

**Service Responsibilities**:
- Input validation
- Business rule enforcement
- Orchestration of repository calls
- Error handling and conversion

### 4. Repository Pattern

Services should use repository abstractions for data access:

```rust
#[async_trait]
pub trait DomainRepository: Send + Sync {
    async fn create(&self, entity: NewEntity) -> Result<Entity, DomainError>;
    async fn get_by_uuid(&self, uuid: Uuid) -> Result<Option<Entity>, DomainError>;
    // ... other CRUD operations
}
```

### 5. Module Organization (`mod.rs`)

Consistent module structure with:
- Clean public interface
- Selective exports
- Comprehensive module documentation
- Basic module tests

## Implementation Strategy

### Phase 1: Template and Documentation
- ✅ Create comprehensive template in `src/domain/template/`
- ✅ Document patterns in standardization guide
- ✅ Validate with health domain refactoring

### Phase 2: Core Domain Refactoring
- Refactor auth domain (critical security component)
- Refactor user domain (simpler, good practice)
- Refactor analytics domain (high usage)

### Phase 3: Remaining Domains
- Host domain standardization
- Software domain standardization
- Vulnerability domain final cleanup

### Migration Guidelines

1. **Analyze Current Service**: Document existing operations and business rules
2. **Create New Structure**: Start with error types and models
3. **Define Service Interface**: Extract service trait from existing implementation
4. **Implement Repository**: Create abstraction for data access
5. **Migrate Business Logic**: Move validation and rules to service layer
6. **Update Tests**: Convert to standardized testing patterns
7. **Update Dependencies**: Refactor calling code

## Benefits

### 1. Consistency
- Predictable code structure across all domains
- Consistent error handling patterns
- Uniform testing approaches

### 2. Maintainability
- Clear separation of concerns
- Easier to understand and modify
- Reduced cognitive overhead

### 3. Testability
- Repository abstractions enable easy mocking
- Standardized test patterns
- Better coverage consistency

### 4. Extensibility
- Clear extension points through traits
- Easier to add new implementations
- Better support for dependency injection

### 5. Documentation
- Self-documenting through consistent patterns
- Clear service responsibilities
- Comprehensive error documentation

## Trade-offs

### Costs
- **Migration Effort**: Refactoring existing services requires significant work
- **Initial Complexity**: More abstraction layers may seem complex initially
- **Learning Curve**: Developers need to learn new patterns

### Benefits
- **Long-term Maintainability**: Consistent patterns reduce long-term maintenance cost
- **Team Productivity**: Predictable structure improves developer velocity
- **Quality**: Better error handling and testing lead to fewer bugs

## Validation

The standardization patterns have been successfully validated through:

1. **Template Implementation**: Complete reference implementation in `src/domain/template/`
2. **Health Domain Refactoring**: Real-world validation with existing service
3. **Test Coverage**: All patterns thoroughly tested
4. **Documentation**: Comprehensive guides and examples
