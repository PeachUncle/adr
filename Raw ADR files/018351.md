# ADR-003: Penerapan Keamanan dan Akses Kontrol

**Status:** Accepted

## Context

Adanya keperluan untuk memastikan bahwa hanya pengguna yang sah yang dapat melakukan tindakan sesuai dengan hak aksesnya. Hal ini penting untuk melindungi data sensitif dan melindungi sistem dari penyalahgunaan akses (baik yang disengaja maupun tidak disengaja).

## Decision

Kami akan menerapkan pendekatan keamanan berlapis (*defense-in-depth*) yang mencakup autentikasi, otorisasi, manajemen *secret key*, dan perlindungan *endpoint*.

1.  **Autentikasi & Otorisasi (JWT + RBAC):**
    * Semua *endpoint* yang diamankan akan mewajibkan **JSON Web Token (JWT)** yang valid di *header* `Authorization`.
    * JWT akan berisi *claim* `roles` (misal: `operator`, `supervisor`) yang menentukan peran pengguna.
    * Akses ke *endpoint* spesifik akan diatur menggunakan **Role-Based Access Control (RBAC)**.
    * *Contoh:* `operator` hanya bisa `POST /transfers` (membuat request), tetapi hanya `supervisor` yang bisa `PUT /transfers/{id}/approve` (menyetujui).

2.  **Keamanan Aplikasi:**
    * **Validasi Input:** Validasi skema yang ketat akan diterapkan pada semua *payload* request (*body*, *param*, *query*) untuk mencegah serangan *injection* dan memastikan integritas data.
    * **Manajemen Secret Key:** Kredensial (seperti *password* DB, API *key*) tidak boleh disimpan dalam kode (*hardcoded*).
        * Untuk *environment staging/production*, *secret key* akan dikelola melalui **Secret Manager** (misal: GCP Secret Manager atau HashiCorp Vault).
        * Untuk *environment* lokal, file `.env` dapat digunakan.

3.  **Perlindungan Infrastruktur (Gateway):**
    * **Rate Limiting:** *Rate limit* dasar (berdasarkan IP atau token JWT) akan diterapkan di level API Gateway untuk melindungi sistem dari serangan *brute-force* atau *Denial of Service (DoS)* volume rendah.

## Consequences

### Positif

* Memberikan pengamanan yang kuat terhadap akses tidak sah (autentikasi JWT).
* Menerapkan prinsip *least privilege* (hak akses minimum) secara efektif melalui RBAC di level *endpoint*.
* Mengurangi risiko kebocoran kredensial dengan memisahkan *secret key* dari basis kode.
* Mengurangi permukaan serangan (attack surface) melalui validasi input yang ketat dan *rate limiting*.

### Negatif

* Memerlukan infrastruktur pendukung untuk *Identity Provider* (yang menerbitkan JWT) dan *Secret Manager*.
* Menambah kompleksitas pada logika *handler* API atau *middleware* untuk melakukan pemeriksaan *role* (RBAC).
* Konfigurasi *rate limit* harus dipantau dengan cermat agar tidak salah memblokir *traffic* yang asli (legitimate) saat terjadi lonjakan penggunaan.
