# ADR-030: Infrastructure Architecture

**Status**: Accepted  
**Date**: 2025-10-16  
**Decision Makers**: Architecture Team, DevOps Team, Security Team  
**Related ADRs**: ADR-011 (Docker), ADR-016 (Cloud Run), ADR-019 (Terraform), ADR-026 (GCP), ADR-027 (IAM), ADR-015 (Pub/Sub)

## Context

The multi-agent options trading system requires robust, scalable, and secure infrastructure to support production trading operations with real capital at risk. The infrastructure must meet stringent requirements for reliability (99.5% uptime), security (financial system compliance), performance (sub-second latency for critical paths), and cost efficiency (monthly budget $4,500).

### Business Requirements

1. **Production Readiness**: Infrastructure must support live trading with zero tolerance for data loss or corruption
2. **Scalability**: Handle market hours load (20+ agents, 100+ requests/minute) with <30s p95 latency
3. **Security**: Financial system compliance (SOC 2 Type II equivalent controls)
4. **Cost Management**: Stay within $4,500/month budget while maintaining performance SLOs
5. **Operational Excellence**: Infrastructure as Code (IaC) for reproducibility and disaster recovery

### Technical Challenges

1. **Multi-Agent Coordination**: 11+ agents communicating asynchronously via message queues
2. **Stateful Operations**: Trading session state, portfolio positions, risk limits
3. **External Dependencies**: Alpha Vantage, Polygon.io, broker APIs with rate limits
4. **Data Persistence**: Operational database (Cloud SQL), analytics warehouse (BigQuery)
5. **Secret Management**: API keys, database credentials, service account keys

## Decision

We adopt a **serverless-first infrastructure architecture** on Google Cloud Platform with the following core principles:

1. **Compute**: Cloud Run for stateless agent deployment with auto-scaling
2. **Messaging**: Cloud Pub/Sub for asynchronous inter-agent communication
3. **Data**: Cloud SQL (PostgreSQL) for operational data, BigQuery for analytics
4. **Storage**: Cloud Storage for ML models, backtest results, and logs
5. **Security**: IAM service accounts, Secret Manager, VPC Service Controls
6. **Networking**: Private VPC with VPC peering for Cloud SQL, NAT gateway for egress
7. **Infrastructure as Code**: Terraform for all resource provisioning and management

## Architecture

### 1. Container Architecture

#### 1.1 Base Image Standardization

All agent containers use standardized base images:

```dockerfile
FROM python:3.11-slim AS builder

# Build stage: Install dependencies
WORKDIR /build
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

FROM python:3.11-slim

# Runtime stage: Copy dependencies and application
WORKDIR /app
COPY --from=builder /root/.local /root/.local
COPY . .

# Non-root user execution
RUN useradd -m -u 1000 agent
USER agent

# Health check endpoint
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD curl -f http://localhost:8080/health || exit 1

CMD ["python", "main.py"]
```

**Security Controls**:
- Multi-stage build reduces final image size by 60-70%
- Non-root user execution (UID 1000) prevents privilege escalation
- Read-only root filesystem with writable /tmp volume
- No privilege escalation allowed (`allowPrivilegeEscalation: false`)
- Vulnerability scanning with Artifact Registry analysis
- Image signing with Binary Authorization

#### 1.2 Resource Limits by Agent Type

| Agent Type | CPU Limit | Memory Limit | CPU Request | Memory Request |
|------------|-----------|--------------|-------------|----------------|
| Portfolio Orchestrator (L1) | 2 vCPU | 4Gi | 1 vCPU | 2Gi |
| Stock Selection (L2) | 2 vCPU | 4Gi | 1 vCPU | 2Gi |
| Strategy Agents (L2) | 1 vCPU | 2Gi | 0.5 vCPU | 1Gi |
| Level 3 Strategy Agents | 1 vCPU | 2Gi | 0.5 vCPU | 1Gi |
| Portfolio Hedging Agent | 2 vCPU | 4Gi | 1 vCPU | 2Gi |
| Greeks Calculation Service | 2 vCPU | 4Gi | 1 vCPU | 2Gi |
| Risk Management Service | 1 vCPU | 2Gi | 0.5 vCPU | 1Gi |

**Rationale**: Resource limits prevent single agent from consuming excessive resources, ensure predictable costs, and enable efficient instance packing.

#### 1.3 Health Check Configuration

All agents implement standardized health checks:

```python
@app.get("/health")
async def health_check():
    """Liveness probe: Is the agent running?"""
    return {"status": "healthy", "timestamp": datetime.utcnow().isoformat()}

@app.get("/ready")
async def readiness_check():
    """Readiness probe: Can the agent handle requests?"""
    checks = {
        "database": await check_database_connection(),
        "pubsub": await check_pubsub_connectivity(),
        "external_apis": await check_api_availability()
    }
    
    if all(checks.values()):
        return {"status": "ready", "checks": checks}
    else:
        raise HTTPException(status_code=503, detail=checks)
```

**Cloud Run Configuration**:
- Liveness probe: `/health` every 30s, timeout 5s, 3 retries
- Readiness probe: `/ready` every 10s, timeout 5s, 3 retries
- Startup probe: `/ready` every 5s, timeout 10s, failure threshold 12

### 2. Cloud Run Architecture

#### 2.1 Service Configuration

**Orchestrator Agent** (critical path):
```hcl
resource "google_cloud_run_service" "portfolio_orchestrator" {
  name     = "portfolio-orchestrator"
  location = var.region

  template {
    metadata {
      annotations = {
        "autoscaling.knative.dev/minScale"         = "1"  # Always warm
        "autoscaling.knative.dev/maxScale"         = "5"
        "run.googleapis.com/cpu-throttling"        = "false"  # Always-on CPU
        "run.googleapis.com/execution-environment" = "gen2"
      }
    }

    spec {
      service_account_name = google_service_account.orchestrator.email
      timeout_seconds      = 300  # 5 minutes

      containers {
        image = "gcr.io/${var.project_id}/portfolio-orchestrator:${var.version}"

        resources {
          limits = {
            cpu    = "2"
            memory = "4Gi"
          }
        }

        env {
          name  = "ENVIRONMENT"
          value = var.environment
        }

        env {
          name = "DATABASE_CONNECTION_STRING"
          value_from {
            secret_key_ref {
              name = google_secret_manager_secret.db_connection.secret_id
              key  = "latest"
            }
          }
        }
      }
    }
  }

  traffic {
    percent         = 100
    latest_revision = true
  }
}
```

**Standard Agents** (on-demand scaling):
- **Min Instances**: 0 (scale to zero during off-hours)
- **Max Instances**: 3-5 per agent type
- **CPU Allocation**: CPU-throttling enabled (cost optimization)
- **Timeout**: 60-120 seconds based on agent complexity
- **Concurrency**: 1-10 concurrent requests per instance

#### 2.2 Service-to-Service Authentication

All Cloud Run services use IAM-based authentication:

```hcl
resource "google_cloud_run_service_iam_member" "orchestrator_invoker" {
  service  = google_cloud_run_service.orchestrator.name
  location = google_cloud_run_service.orchestrator.location
  role     = "roles/run.invoker"
  member   = "serviceAccount:${google_service_account.api_gateway.email}"
}
```

**Invocation Flow**:
1. Caller obtains ID token for target service using Workload Identity
2. ID token included in `Authorization: Bearer <token>` header
3. Cloud Run validates token signature and audience
4. Request forwarded to container if authorized

```hcl
resource "google_compute_network" "trading_vpc" {
  name                    = "trading-vpc"

```

**VPC Connector** for Cloud Run private networking:
- CIDR: 10.8.0.0/28 (16 IPs, reserved for serverless VPC access)
- Throughput: 300 Mbps (scales to 1 Gbps if needed)
- Machine type: e2-micro (cost-optimized)

#### 3.2 Cloud SQL Private Connectivity

**VPC Peering** for private Cloud SQL access:

```hcl
resource "google_sql_database_instance" "trading_db" {
  name             = "trading-db-prod"
  database_version = "POSTGRES_15"
  region           = var.region

  settings {
    tier              = "db-custom-2-7680"  # 2 vCPU, 7.5GB RAM
    availability_type = "REGIONAL"          # Multi-zone HA
    disk_size         = 100                 # 100GB SSD
    disk_autoresize   = true

    ip_configuration {
      ipv4_enabled    = false  # No public IP
      private_network = google_compute_network.trading_vpc.id

      enabled                        = true
      start_time                     = "03:00"  # 3 AM UTC
      point_in_time_recovery_enabled = true
      transaction_log_retention_days = 7
      backup_retention_settings {
        retained_backups = 30
      }
    }
  }
}
```

**Connection Pooling**:
- Use Cloud SQL Proxy for secure connections
- Connection pool size: 10-20 per agent
- Connection lifetime: 30 minutes
- Idle timeout: 5 minutes

### 4. Messaging Architecture

#### 4.1 Pub/Sub Topic Configuration

**Standard Topics** (agent communication):

```hcl
resource "google_pubsub_topic" "stock_analysis_tasks" {
  name = "stock-analysis-tasks"

  message_retention_duration = "86400s"  # 24 hours

  message_storage_policy {
    allowed_persistence_regions = [var.region]
  }
}

resource "google_pubsub_subscription" "stock_selection_sub" {
  name  = "stock-selection-agent-sub"
  topic = google_pubsub_topic.stock_analysis_tasks.name

  ack_deadline_seconds = 60

  retry_policy {
    minimum_backoff = "10s"
    maximum_backoff = "600s"  # 10 minutes
  }

  dead_letter_policy {
    dead_letter_topic     = google_pubsub_topic.dlq.id
    max_delivery_attempts = 5
  }

  expiration_policy {
    ttl = ""  # Never expire
  }

  push_config {
    push_endpoint = google_cloud_run_service.stock_selection.status[0].url
    
    oidc_token {
      service_account_email = google_service_account.pubsub_invoker.email
    }
  }
}
```

**Dead Letter Queue**:
- Topic: `trading-dlq`
- Subscription: Manual processing required
- Retention: 7 days
- Alerting: Critical alert on any DLQ message

#### 4.2 Message Ordering

For stateful operations requiring order:

```hcl
resource "google_pubsub_topic" "trading_session_events" {
  name = "trading-session-events"

  name  = "session-orchestrator-sub"
  topic = google_pubsub_topic.trading_session_events.name

```

**Ordering Key Strategy**:
- Portfolio operations: `portfolio:{portfolio_id}`
- Symbol operations: `symbol:{symbol}`
- Session operations: `session:{session_id}`

### 5. Data Architecture

#### 5.1 Cloud SQL (Operational Database)

**Schema Design**:
- `trading_sessions`: Active session state, status, metadata
- `portfolio_positions`: Current positions with Greeks
- `orders`: Order history, status, fills
- `risk_limits`: Portfolio-level risk parameters
- `agent_state`: Persistent agent state for recovery

**High Availability**:
- Configuration: Regional (multi-zone HA)
- Automatic failover: <60 seconds
- Read replicas: 1 read replica in same region for reporting queries
- Backup: Automated daily backups with 30-day retention
- PITR: Point-in-time recovery for last 7 days

**Performance Optimization**:
- Connection pooling via Cloud SQL Proxy
- Index optimization for frequent queries
- Query result caching for market data
- Partitioning for orders table (by month)

#### 5.2 BigQuery (Analytics Warehouse)

**Dataset Organization**:
- `market_data`: Historical price data, option chains, Greeks
- `trading_analytics`: Backtests, performance metrics, attribution
- `agent_telemetry`: Agent logs, metrics, traces for analysis
- `ml_features`: Feature engineering tables for ML models

**Cost Optimization**:
- Partitioning: By date for all time-series tables
- Clustering: By symbol, strategy for better query performance
- Expiration: 2-year retention for raw data, 7-year for aggregates
- Flat-rate pricing: Evaluate when query volume increases

#### 5.3 Cloud Storage (Object Storage)

**Bucket Organization**:

```hcl
resource "google_storage_bucket" "ml_models" {
  name          = "${var.project_id}-ml-models"
  location      = var.region
  storage_class = "STANDARD"

  versioning {
    enabled = true
  }

  lifecycle_rule {

      num_newer_versions = 4  # Keep 4 quarterly versions
    }

      type = "Delete"
    }
  }
}

resource "google_storage_bucket" "backtest_results" {
  name          = "${var.project_id}-backtest-results"
  location      = var.region
  storage_class = "NEARLINE"  # Cost-optimized for infrequent access

  lifecycle_rule {
    condition {
      age = 365  # 1 year
    }
    action {
      type          = "SetStorageClass"
      storage_class = "COLDLINE"
    }

```

**Buckets**:
- `{project}-ml-models`: Trained model artifacts (versioned)
- `{project}-backtest-results`: Historical backtest results
- `{project}-compliance-logs`: Long-term log retention (7 years)
- `{project}-terraform-state`: Terraform state files (locked)

### 8. Disaster Recovery

#### 8.1 Backup Strategy

| Component | Backup Frequency | Retention | RTO | RPO |
|-----------|-----------------|-----------|-----|-----|
| Cloud SQL | Daily + PITR | 30 days / 7 days | 1 hour | 5 minutes |
| Cloud Storage | Versioned | N/A (immutable) | 0 | 0 |
| BigQuery | Snapshots | 7 days | 4 hours | 24 hours |
| Terraform State | Versioned | 10 versions | 15 minutes | N/A |

#### 8.2 Recovery Procedures

**Cloud SQL Recovery**:
1. Identify recovery point (timestamp or backup ID)
2. Create new instance from backup or PITR
3. Update DNS or connection strings
4. Verify data integrity
5. Resume operations

**Infrastructure Recovery**:
1. Clone infrastructure repository
2. Authenticate Terraform service account
3. Run `terraform init` and `terraform plan`
4. Review plan for accuracy
5. Apply with `terraform apply`
6. Verify service health

## Consequences

### Positive

1. **Serverless Benefits**: Auto-scaling, pay-per-use pricing, zero infrastructure management
2. **High Availability**: Regional HA for Cloud SQL, multi-zone Cloud Run, automatic failover
3. **Security**: Defense in depth with VPC, IAM, Secret Manager, VPC Service Controls
4. **Cost Efficiency**: Scale-to-zero during off-hours, optimized resource allocation
5. **Operational Excellence**: IaC enables reproducible deployments, disaster recovery
6. **Compliance Ready**: Audit logging, data residency, encryption meet financial system requirements

### Negative

1. **Vendor Lock-in**: Deep integration with GCP-specific services (Cloud Run, Pub/Sub)
2. **Cold Start Latency**: Initial requests may experience 5-10s delay (mitigated with min instances)
3. **Debugging Complexity**: Distributed tracing required across multiple serverless functions
4. **Cost Predictability**: Serverless pricing varies with usage patterns
5. **Migration Effort**: Moving to different cloud provider requires significant refactoring

### Risks

1. **Regional Outage**: Single-region architecture vulnerable to regional GCP failures
2. **Cloud SQL Bottleneck**: Database could become performance bottleneck at high scale
3. **Pub/Sub Ordering**: Message ordering guarantees add latency overhead
4. **Terraform State Corruption**: State file corruption could block deployments

### Mitigation Strategies

1. **Multi-Region Planning**: Design Phase 2 includes multi-region active-active architecture
2. **Database Optimization**: Monitor slow queries, add indexes, consider read replicas
3. **Pub/Sub Testing**: Validate ordering behavior under failure scenarios
4. **State Backup**: Automated Terraform state backups every 4 hours
5. **Disaster Recovery Drills**: Quarterly DR exercises to validate recovery procedures
