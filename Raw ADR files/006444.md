# Architecture Decision Record: Hexagonal Architecture (Ports & Adapters)

## Status

**Accepted** - 2025-11-01

## Context

We need to design a system that is:

1. **Testable** - Unit tests without databases or external dependencies
2. **Maintainable** - Easy to understand and modify over time
3. **Flexible** - Ability to swap infrastructure (e.g., Prisma → TypeORM)
4. **Compliant** - Clear separation between business logic and technical concerns
   Traditional layered architecture often leads to tight coupling between business logic and frameworks (e.g., database ORMs, HTTP libraries).

## Decision

We will implement **Hexagonal Architecture** (also called Ports & Adapters) with the following structure:

```
packages/
├── domain/           # Entities & value objects (pure TypeScript)
├── application/      # Use cases + Ports (interfaces)
├── infra-prisma/     # Adapters (Prisma implementations)
apps/
├── api/              # NestJS controllers (HTTP adapters)
├── worker/           # BullMQ processors (queue adapters)
```

### Core Principles

1. **Domain Layer** (`packages/domain/`)
   - Pure TypeScript classes (no dependencies)
   - Entities: `User`, `AuditTrail`
   - Domain events: `UserRegisteredEvent`, etc.
   - Business rules enforced here
2. **Application Layer** (`packages/application/`)
   - Use case services: `UserService.registerUser()`
   - **Ports** (interfaces): `UserRepository`, `PasswordHasher`, `UnitOfWork`
   - No concrete implementations - only contracts
   - Framework-agnostic
3. **Infrastructure Layer** (`packages/infra-prisma/`)
   - **Adapters** (implementations of ports)
   - `PrismaUserRepository implements UserRepository`
   - `Argon2PasswordHasher implements PasswordHasher`
   - `PrismaUnitOfWork implements UnitOfWork`
4. **Presentation Layer** (`apps/api/`, `apps/worker/`)
   - NestJS controllers call application services
   - Dependency injection wires adapters to ports
   - No business logic in controllers

### Dependency Flow

```
API → Application ← Infra
       ↓
     Domain
```

- **Inward dependencies only**: Outer layers depend on inner layers, never the reverse
- Domain has zero dependencies
- Application depends only on Domain
- Infrastructure depends on Application (to implement ports)
- API depends on Application (to call services)

## Example Code

### Port (Interface)

```typescript
// packages/application/src/ports/user.repository.ts
export interface UserRepository {
  save(user: User): Promise<Result<User, Error>>;
  findById(id: string): Promise<Result<User | null, Error>>;
}
```

### Adapter (Implementation)

```typescript
// packages/infra-prisma/src/user.repository.prisma.ts
export class PrismaUserRepository implements UserRepository {
  constructor(private prisma: PrismaClient) {}

  async save(user: User): Promise<Result<User, Error>> {
    // Prisma-specific implementation
  }
}
```

### Service (Use Case)

```typescript
// packages/application/src/services/user.service.ts
export class UserService {
  constructor(
    private userRepository: UserRepository, // Port (interface)
    private passwordHasher: PasswordHasher // Port (interface)
    // ...
  ) {}

  async registerUser(input: RegisterUserInput): Promise<Result<User, Error>> {
    // Business logic here
    const hashedPassword = await this.passwordHasher.hash(input.password);
    const user = User.create({ ...input, passwordHash: hashedPassword });
    return this.userRepository.save(user);
  }
}
```

### Dependency Injection (NestJS)

```typescript
// apps/api/src/infra/infra.module.ts
@Module({
  providers: [
    {
      provide: 'UserRepository',
      useFactory: (prisma: PrismaClient) => new PrismaUserRepository(prisma),
      inject: [PrismaClient],
    },
    {
      provide: UserService,
      useFactory: (userRepo: UserRepository, ...) =>
        new UserService(userRepo, ...),
      inject: ['UserRepository', ...],
    },
  ],
})
export class InfraModule {}
```

## Consequences

### Positive

✅ **Testability**: Mock ports in unit tests without real database

```typescript
const mockUserRepo: UserRepository = {
  save: vi.fn().mockResolvedValue(ok(user)),
  // ...
};
const service = new UserService(mockUserRepo, ...);
```

✅ **Flexibility**: Swap Prisma for another ORM by creating new adapter

```typescript
class TypeORMUserRepository implements UserRepository {
  // Different implementation, same interface
}
```

✅ **Compliance**: Clear audit trail - business logic isolated from infrastructure
✅ **Maintainability**: Changes to database schema don't affect business logic
✅ **Framework Independence**: Application layer has no NestJS imports
✅ **Scalability**: Clear package boundaries enable multi-team ownership (see ADR-006)

### Negative

❌ **Boilerplate**: More files and interfaces than simple layered architecture
❌ **Learning Curve**: Developers must understand DI and ports/adapters pattern
❌ **Initial Setup Time**: More upfront design work

### Mitigations

- Provide clear documentation and examples
- Use TypeScript strict mode to catch interface mismatches
- Automate boilerplate with code generators (if needed)
- See ADR-006 for scaling patterns to 3+ teams

## Scalability Notes

### Package Organization for Teams

As the team grows, organize packages by **domain + responsibility**:

```
packages/domain/src/
  ├── user/              # Team A
  ├── audit/             # Team B
  └── shared/            # All teams

packages/application/src/
  ├── user/services/     # Team A
  ├── audit/services/    # Team B
  └── shared/ports/      # All teams

packages/infra-prisma/src/
  ├── user/              # Team A
  ├── audit/             # Team B
```

**Key principle:** Each team owns vertical slice (domain → application → infra) for their aggregate root.

### Module Size Guidelines

| Package Size | Files | LOC   | Action                     |
| ------------ | ----- | ----- | -------------------------- |
| Small        | <30   | <3K   | Keep together ✅           |
| Medium       | 30-80 | 3K-8K | Monitor, plan split ⚠️     |
| Large        | >80   | >8K   | Split into sub-packages 🔀 |

### When to Split Infrastructure Packages

**Create new `packages/infra-*` when:**

1. **Independently deployable** (release cycle >2 weeks apart)
2. **Different team ownership** (infrastructure team vs. feature team)
3. **Reusable adapters** (e.g., `infra-cache` used by multiple domains)
4. **Large implementation** (>50 files or >5K LOC)

**Examples:**

- ✅ `packages/infra-cache` - Shared Redis adapters (Team C)
- ✅ `packages/infra-aws` - AWS-specific adapters (when scaling)
- ❌ Single repository method - Keep in `infra-prisma`

### Dependency Flow with Multiple Teams

```
Team A (Users)      Team B (Audit)      Team C (Infrastructure)
   |                    |                         |
   ├── domain/user      ├── domain/audit         ├── infra-cache/
   ├── app/user         ├── app/audit            ├── infra-aws/
   └── infra/user       └── infra/audit         └── monitoring/
           \                    /                      |
            \                  /                       |
             └─── domain/shared ◄──────────────────────┘
                  app/shared
```

**Shared layers enable code reuse while maintaining team independence.**

### Observability per Layer

Each layer should expose clear signals:

- **Domain:** Entity creation rates, business rule violations (Counter, no DB queries)
- **Application:** Use case execution time, success/failure rates (Histogram, Gauge)
- **Infrastructure:** Query latency, connection pool, slow queries (Histogram)
- **API:** HTTP request/response times, error codes (Histogram)

See [ADR-006: Monorepo Scalability and Team Ownership](ADR-006-monorepo-scalability-and-team-ownership.md) for detailed observability patterns.

### Team Ownership Model

Use `.github/CODEOWNERS` to enforce review requirements:

```
# .github/CODEOWNERS
packages/domain/src/user/     @team-a
packages/domain/src/audit/    @team-b
packages/shared/              @team-a @team-b @team-c
```

This ensures:

- ✅ Team A reviews user domain changes
- ✅ Team B reviews audit domain changes
- ✅ All teams approve shared code

**See ADR-006 for complete team ownership strategy.**

## Alternatives Considered

### 1. Traditional Layered Architecture

```
Controller → Service → Repository → Database
```

**Rejected because:**

- Tight coupling to frameworks
- Hard to test without database
- Business logic leaks into controllers

### 2. Clean Architecture (Uncle Bob)

Similar to Hexagonal, but more complex with additional layers (Use Cases, Entities, Gateways, etc.)
**Rejected because:**

- Overkill for this project size
- Hexagonal is simpler while achieving same goals

### 3. Vertical Slice Architecture

Organize by feature, not by layer.
**Rejected because:**

- Less code reuse across features
- Harder to enforce consistency in monorepo
