## Context

The project's cloud infrastructure, which includes multiple services across Google Cloud Platform (Cloud Run, Pub/Sub, BigQuery, Cloud SQL, etc.), needs to be managed in a reliable, repeatable, and version-controlled manner. Manually managing these resources through a web console is error-prone, not scalable, and makes it difficult to track changes or replicate the environment for testing or disaster recovery.

## Decision

We will use **Terraform** as the exclusive tool for defining and managing all cloud infrastructure resources. All infrastructure will be declared as code in `.tf` files and stored in the project's GitHub repository.

## Rationale

1.  **Cost-Effectiveness**: Terraform is a free and open-source tool. There are no licensing costs associated with its use; we only pay for the cloud resources that it provisions.
2.  **Industry Standard**: Terraform is the de facto industry standard for Infrastructure as Code. This provides a large community for support, extensive documentation, and a vast ecosystem of pre-built modules that can accelerate development.
3.  **Declarative and Repeatable**: Terraform uses a declarative language (HCL) to define the *desired state* of the infrastructure. This makes the configuration easy to understand and ensures that the same configuration will produce the exact same infrastructure every time it's applied, which is critical for consistency between development, staging, and production environments.
4.  **CI/CD Integration**: Terraform integrates seamlessly into a CI/CD pipeline. Our GitHub Actions workflow (ADR-018) will include steps to automatically `plan` and `apply` infrastructure changes, enabling a fully automated "GitOps" approach to infrastructure management.
5.  **Cloud-Agnostic**: While the project is currently standardized on GCP, Terraform is cloud-agnostic. The skills and patterns used are directly transferable to other cloud providers (like AWS or Azure) if the project's needs change in the future.

## Consequences

-   **Learning Curve**: The development team will need to be proficient in Terraform's declarative language, HCL (HashiCorp Configuration Language).
-   **State Management**: Terraform relies on a "state file" to keep track of the resources it manages. This state file must be stored in a secure, remote, and shared location. We will use a **Google Cloud Storage (GCS) bucket** as the remote backend for the Terraform state, which is the standard practice for GCP-based projects.
-   **Implementation**:
    -   A new directory (e.g., `/terraform`) will be created in the repository to hold all `.tf` configuration files.
    -   The CI/CD pipeline in GitHub Actions will be configured with `terraform plan` and `terraform apply` steps to automate the deployment of infrastructure changes.
    -   Sensitive variables (e.g., project IDs, API keys) will not be hardcoded in the Terraform files but will be passed in securely via GitHub Actions secrets.

## Alternatives Considered

-   **Pulumi**: Pulumi allows for defining infrastructure using general-purpose programming languages like Python or TypeScript. While this can be more intuitive for developers, Terraform is a more mature and widely-adopted tool with a larger community, making it a safer and better-supported choice.
-   **Cloud-Specific IaC (e.g., Google Cloud Deployment Manager)**: Using a provider-specific tool would lock us into the GCP ecosystem more deeply. Terraform's cloud-agnostic nature provides better long-term flexibility.
-   **Manual Configuration (ClickOps)**: Managing resources via the GCP web console. This was rejected as it is not scalable, repeatable, or version-controlled, and is highly prone to human error.

## Implementation Strategy

### Phase 1: Foundation and State Management (Week 1)
**Deliverables**:
- Create `/terraform` directory structure with environment-specific subdirectories (dev, staging, prod)
- Configure GCS bucket for remote state storage with versioning and encryption enabled
- Define Terraform backend configuration for state locking
- Create base `provider.tf` and `versions.tf` files with required provider constraints

**Dependencies**: GCP project and service accounts with appropriate IAM permissions

### Phase 2: Core Infrastructure (Week 2-3)
**Deliverables**:
- Define Cloud Run service configurations as Terraform modules
- Create Pub/Sub topics and subscriptions infrastructure
- Configure Cloud SQL instances (PostgreSQL) with read replicas
- Define Redis (Memorystore) instance configurations
- Implement VPC and networking resources

**Dependencies**: Phase 1 completion, existing service specifications from architecture docs

### Phase 3: Data and ML Infrastructure (Week 3-4)
**Deliverables**:
- Define BigQuery datasets, tables, and scheduled queries
- Configure Vertex AI workbench and training job templates
- Create GCS buckets for data storage with lifecycle policies
- Implement IAM roles and service accounts for all services

**Dependencies**: Phase 2 completion, ADR-020 (Vertex AI MLOps)

### Phase 4: CI/CD Integration (Week 4-5)
**Deliverables**:
- Integrate Terraform into GitHub Actions workflow with `terraform plan` on PR
- Implement `terraform apply` automation for merged changes to main branch
- Configure GitHub Actions secrets for GCP authentication
- Create Terraform workspace strategy for environment promotion
- Implement drift detection scheduled job

**Dependencies**: Phase 1-3 completion, ADR-018 (GitHub Actions CI/CD)

## Cost Analysis

### Monthly Operational Costs

| Component | Cost |
|-----------|------|
| Terraform Cloud (Free Tier) | $0/month |
| GCS State Storage (< 1GB) | $0.02/month |
| State Lock Operations (Minimal) | $0.01/month |
| **Total Infrastructure Cost** | **$0.03/month** |

**Note**: Costs for provisioned infrastructure (Cloud Run, Cloud SQL, etc.) are separate and managed by those respective services.

### Cost Optimization Strategies

1. **Use Free Tier for State Management**: Terraform state files are small (< 100MB). GCS Standard Storage free tier (5GB) covers all project needs.

2. **Self-Hosted vs Cloud**: Self-hosting Terraform in CI/CD (GitHub Actions) eliminates need for Terraform Cloud paid tiers. Free tier provides state storage UI and limited collaboration features.

3. **Modular Design**: Reusable Terraform modules reduce code duplication and maintenance overhead. Initial investment in module development reduces long-term operational costs.

4. **Automated Drift Detection**: Scheduled GitHub Actions job to detect infrastructure drift prevents costly manual audits and reduces mean-time-to-resolution for configuration issues.

5. **Environment Tagging**: Consistent resource labeling enables cost attribution per environment, allowing identification of cost optimization opportunities.

### ROI Comparison vs Alternatives

| Approach | Setup Cost | Monthly Cost | Operational Overhead | Drift Detection | Audit Trail |
|----------|------------|--------------|----------------------|-----------------|-------------|
| Terraform (IaC) | 40 hours | $0.03 | Low | Automated | Git history |
| Manual (ClickOps) | 0 hours | $0 | High | Manual | None |
| Pulumi | 50 hours | $0.05 | Medium | Automated | Git history |
| GCP Deployment Manager | 60 hours | $0 | Medium | Manual | Limited |

**Verdict**: Terraform provides best balance of cost, automation, and industry-standard tooling.

## Risk Assessment

| Risk | Severity | Likelihood | Impact | Mitigation |
|------|----------|------------|--------|------------|
| State file corruption or loss | High | Low | Critical service outage, complete infrastructure recreation required | GCS bucket versioning enabled, automated state backups to secondary bucket, state locking prevents concurrent modifications |
| Terraform version incompatibility | Medium | Medium | Deployment failures, resource drift | Pin Terraform and provider versions in `versions.tf`, test upgrades in dev environment first, maintain changelog of version updates |
| Unauthorized state access | High | Low | Credential theft, infrastructure tampering | GCS bucket access restricted via IAM to CI/CD service account only, audit logging enabled, state encryption at rest |
| Accidental resource deletion | High | Medium | Service disruption, data loss | Enable deletion protection on critical resources (databases), require manual approval for destroy operations, implement resource tagging for protection levels |
| Terraform drift (manual changes) | Medium | Medium | Configuration inconsistencies, deployment failures | Scheduled drift detection jobs, enforcement of "no manual changes" policy, alerting on detected drift |
| Provider API rate limits | Low | Low | Deployment delays during large infrastructure changes | Implement parallelism limits in Terraform configuration, schedule large deployments during off-peak hours |
| GitHub Actions secrets exposure | High | Low | Credential compromise, unauthorized infrastructure changes | Use OIDC workload identity federation instead of long-lived service account keys, rotate credentials quarterly, audit GitHub Actions logs |

## Monitoring and Success Criteria

### Key Metrics

| Metric | Target | Measurement Method |
|--------|--------|-------------------|
| Deployment Success Rate | >95% | GitHub Actions workflow success rate for terraform apply jobs |
| Mean Time to Deploy (MTTD) | <10 minutes | Average duration of terraform apply in CI/CD pipeline |
| Infrastructure Drift Detection Latency | <24 hours | Time between manual change and automated drift alert |
| State File Size Growth | <10% per quarter | GCS bucket monitoring of state file size over time |

### Alerting Thresholds

**Critical**:
- Terraform apply failure in production environment
- State file corruption detected
- Unauthorized access to state file bucket
- Drift detected on production databases or networking resources

**Warning**:
- Terraform plan shows >50 resource changes (potential misconfiguration)
- State file size increased >50% month-over-month
- Provider version outdated >3 minor versions
- Drift detected on non-critical resources

**Info**:
- Successful deployment completion
- New Terraform module created
- Terraform version upgrade completed

### Success Criteria

**Functional Requirements**:
- All GCP infrastructure resources defined in Terraform
- Zero manual infrastructure changes in production
- Terraform state stored in GCS with versioning enabled
- CI/CD pipeline successfully runs terraform plan on all PRs
- All environments (dev, staging, prod) deployed via Terraform

**Performance Requirements**:
- Infrastructure deployment completes within 15 minutes
- Terraform plan execution completes within 3 minutes
- State file operations complete within 5 seconds

**Cost Requirements**:
- State management costs remain below $1/month
- No Terraform Cloud paid tier required

**Operational Requirements**:
- Drift detection runs daily and alerts on discrepancies
- Terraform documentation maintained for all modules
- At least 2 team members trained in Terraform operations
- Disaster recovery procedure documented and tested quarterly

### Risk Factors

1. **Team Learning Curve**: Moderate - HCL syntax is declarative and easier than imperative programming languages. Risk mitigated by extensive Terraform documentation and community resources.

2. **State Management Complexity**: Low - Remote state in GCS is standard practice with minimal operational overhead. State locking prevents concurrency issues.

3. **Environment Parity**: Low - Terraform ensures identical configuration across environments. Risk limited to variable differences (instance sizes, region selection).

4. **Provider Breaking Changes**: Low - Google Cloud provider is mature and maintains backward compatibility. Version pinning prevents unexpected updates.

5. **Rollback Complexity**: Medium - Terraform does not natively support rollback. Mitigation: maintain Git history, test changes in dev/staging first, implement blue-green deployment for critical infrastructure.
