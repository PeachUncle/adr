# ADR-006: YARP Reverse Proxy Gateway

## Status

Accepted

## Context

The Trama platform uses a modular monolith architecture where multiple modules (Auth, Artists, Users, Search) expose HTTP endpoints through a single API host. As the application grows, we need a solution for:

- **Layered Security**: Validate authentication at multiple layers for defense in depth
- **Routing**: Direct requests to appropriate modules based on URL patterns
- **Cross-Cutting Concerns**: Logging, rate limiting, CORS, request/response transformation
- **Future Flexibility**: Potential extraction of modules to separate services
- **Development Experience**: Single entry point for frontend developers

Traditional API Gateway solutions (Kong, Nginx, Traefik) are powerful but add operational complexity and require learning new configuration languages. We need a .NET-native solution that integrates naturally with our stack and provides flexibility for future evolution.

## Decision

We will use **YARP (Yet Another Reverse Proxy)** as our API Gateway:

**Architecture:**
```
Client (React)
    ↓ HTTPS
Gateway (YARP) - Port 5001
    ↓ HTTP (internal)
API (Modular Monolith) - Port 7135
    ↓
PostgreSQL
```

**Gateway Responsibilities:**
- JWT token validation for route-level authorization
- Request routing to API based on URL patterns
- CORS policy enforcement
- Rate limiting (per IP, per user)
- Request/response logging
- Health check aggregation
- Request ID generation for correlation

**API Responsibilities:**
- JWT token validation for resource-level authorization
- Business logic execution
- Database access
- Event publishing
- Response generation

**Routing Configuration:**
```json
{
  "ReverseProxy": {
    "Routes": {
      "auth-route": {
        "ClusterId": "api-cluster",
        "Match": { "Path": "/api/auth/{**catch-all}" }
      },
      "artists-route": {
        "ClusterId": "api-cluster",
        "Match": { "Path": "/api/artists/{**catch-all}" },
        "AuthorizationPolicy": "authenticated"
      }
    },
    "Clusters": {
      "api-cluster": {
        "Destinations": {
          "api": { "Address": "https://localhost:7135" }
        }
      }
    }
  }
}
```

**Authentication Flow:**
1. Client sends request with JWT in Authorization header
2. Gateway validates JWT signature and expiration
3. Gateway forwards request to API with original JWT token
4. API independently validates JWT signature and expiration
5. Both Gateway and API extract user claims from validated token

**Why YARP:**
- Native .NET library (Microsoft-maintained)
- Configuration-based routing (JSON or code)
- Built-in authentication/authorization integration
- High performance (built on Kestrel)
- Extensible via middleware pipeline
- Supports dynamic configuration updates
- Well-documented and actively maintained

## Consequences

### Positive

- **Defense in Depth**: Both Gateway and API validate JWT tokens independently, providing layered security
- **Consistent Security**: All requests go through same authentication/authorization logic at both layers
- **Flexible Authorization**: Gateway handles route-level authorization, API handles resource-level authorization
- **Future-Proof**: Easy to extract modules to separate services (just update routing)
- **Native .NET Integration**: Uses familiar ASP.NET Core middleware and configuration
- **Performance**: YARP is highly optimized for .NET workloads
- **Observability**: Centralized logging and metrics collection point
- **Rate Limiting**: Single place to enforce rate limits across all modules
- **CORS Management**: Centralized CORS policy for frontend

### Negative

- **Additional Hop**: Every request goes through gateway, adding latency (~5-10ms)
- **Double Validation**: JWT validated twice (Gateway and API), adding processing overhead
- **Single Point of Failure**: Gateway downtime affects entire application
- **Complexity**: Additional component to deploy, monitor, and maintain
- **Configuration Management**: Routing rules must be kept in sync with API endpoints
- **Debugging Overhead**: Request flow is less direct, requires correlation IDs
- **Memory Overhead**: Gateway process consumes additional resources
- **Learning Curve**: Team must learn YARP configuration and patterns

### Neutral

- **Two Processes**: Gateway and API run as separate processes (manageable with Docker Compose)
- **Port Management**: Gateway on 5001, API on 7135 (internal only)
- **JWT Forwarding**: Gateway forwards original JWT token to API for independent validation
- **Health Checks**: Gateway aggregates health from API and dependencies
- **Development Workflow**: Developers must run both gateway and API locally

## Implementation Notes

**Gateway Project Structure:**
```
src/Gateway/
├── Program.cs                    # YARP configuration
├── Middleware/
│   ├── RequestLoggingMiddleware.cs
│   └── RateLimitingMiddleware.cs
├── appsettings.json             # Routing configuration
└── Gateway.csproj
```

**Key Configuration:**
- JWT validation configured in both Gateway and API
- Rate limiting per IP and per user at Gateway
- CORS policy for React frontend at Gateway
- Request timeout: 30 seconds
- Connection timeout: 10 seconds
- Correlation ID generation for request tracing

**Security Model:**
- Gateway validates JWT for route-level authorization
- API validates JWT independently for resource-level authorization
- Defense in depth: compromised gateway doesn't bypass API security
- Both layers use same JWT secret and validation parameters
- No trust relationship: each layer validates tokens independently

## Alternatives Considered

**No Gateway (Direct API Access):**
- Pros: Simpler architecture, no additional hop, easier debugging, no double JWT validation
- Cons: No centralized rate limiting, CORS, or logging; harder to extract modules later
- Rejected: Need centralized cross-cutting concerns and future flexibility for microservices

**Nginx Reverse Proxy:**
- Pros: Battle-tested, high performance, widely known
- Cons: Requires learning Nginx config, not .NET-native, harder to integrate with JWT validation
- Rejected: Prefer .NET-native solution for team consistency

**Ocelot API Gateway:**
- Pros: .NET-native, similar to YARP, good documentation
- Cons: Less actively maintained, smaller community, fewer features than YARP
- Rejected: YARP is Microsoft-maintained and more actively developed

**Kong API Gateway:**
- Pros: Feature-rich, plugin ecosystem, enterprise support
- Cons: Requires Lua for plugins, operational complexity, overkill for MVP
- Rejected: Too complex for MVP

**Authentication in Each Module:**
- Pros: No gateway needed, simpler deployment, single JWT validation
- Cons: No centralized rate limiting or CORS, harder to maintain consistency
- Rejected: Need centralized cross-cutting concerns for better security and observability
