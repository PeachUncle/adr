# ADR-002: Low-Confidence Handling, Conservative Fallback, and Image Retention

## Status
Accepted

## Context
The classifier sometimes receives ambiguous or low-quality images. We need to:
- Avoid confidently wrong recommendations
- Improve the model using difficult cases
- Protect user privacy by limiting image retention
- Provide a safe user experience when confidence is low

Options considered:
1. Store all images indefinitely for future retraining  
2. Store no images at all (privacy-maximal)  
3. Store only low-confidence images  
4. Automatically adjust the confidence threshold over time  

## Decision

We use a fixed confidence threshold of 0.6 at inference time (driven by the
`CONFIDENCE_THRESHOLD` environment variable, defaulting to `0.6`).

For *requests where `no_store` is not set or is `false`*:

- Lambda decodes the uploaded image, converts it to a normalized RGB
  representation, and **re-encodes it without EXIF/embedded metadata**.
- The EXIF-stripped bytes are saved to a region-local S3 bucket governed by a
  30-day lifecycle rule.

For *requests where `no_store = true`*:

- The image is **not** written to S3.
- The prediction metadata is still logged in DynamoDB (including `no_store=true`
  and a `null` `s3_key`).

For low-confidence predictions (`confidence < 0.6`):

- Lambda flags the prediction (`flagged_low_conf = true`).
- API returns a conservative fallback to the user.
- DynamoDB logs `flagged_low_conf = true` for offline analysis.

The production system **does not** auto-tune the threshold; offline review and
retraining occur manually.

## Rationale
- Fixed threshold ensures auditability and avoids unstable behavior  
- 30-day retention is long enough for debugging, but bounded for privacy  
- Region-scoped storage protects residency expectations  
- Keeping all images allows accurate debugging when issues arise  
- Low-confidence fallback prevents confidently wrong guidance  

## Consequences
**Positive**
- Clear, predictable behavior for users
- Strong privacy rule enforced by a lifecycle guardrail
- Works with downstream monitoring (low-confidence spike alerts)
- Supports manual offline retraining and error analysis

**Negative**
- Requires manual review to improve the model
- 30-day window may not be long enough for some error investigations
- Borderline items may trigger fallback more often

### Notes on De-Identifications
- Lambda strips EXIF and other embedded metadata by re-encoding the image
  before hashing and writing it to S3 for requests where `no_store` is `false`.
- DynamoDB logs prediction metadata only (no user identifiers, no raw image
  bytes).
