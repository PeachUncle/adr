# ADR-0005: API Style (REST vs GraphQL vs tRPC)

**Status**: Accepted
**Date**: 2025-11-21
**Deciders**: Principal Architect, Tech Lead, Frontend Lead
**Related ADRs**: None (foundational decision)

---

## Context

PrintXpress requires a consistent API design for communication between:
- **Frontend (Next.js)** ↔ **Backend (Lambda functions)**
- **Backend** ↔ **External Services** (Printify, Stripe)
- **Mobile Apps** (Phase 3) ↔ **Backend**

**API Style Options**:
1. **REST**: Resource-oriented, HTTP verbs (GET, POST, PUT, DELETE)
2. **GraphQL**: Query language, client specifies exact data needed
3. **tRPC**: TypeScript RPC, end-to-end type safety (no schema)

---

## Decision

**Use RESTful API (JSON over HTTP) with OpenAPI 3.0 specification for all API endpoints.**

**Supplement with tRPC for Next.js internal API routes** (frontend ↔ backend within same codebase).

**Hybrid Approach**:
- **Public API** (external integrations, mobile apps): REST + OpenAPI spec
- **Internal API** (Next.js frontend ↔ backend): tRPC (type-safe, faster development)

---

## Rationale

### Why REST for Public API?

**1. Universal Compatibility**

REST is industry standard for public APIs:
- **Stripe API**: REST (webhooks, checkout)
- **Printify API**: REST (products, orders)
- **Mobile apps** (Phase 3): React Native works seamlessly with REST

**Alternative (GraphQL)**:
- **Pros**: Flexible queries, single endpoint
- **Cons**: Overkill for simple CRUD, requires GraphQL client (Apollo, Relay), no native webhook support

**Decision**: REST aligns with external services we integrate with (Stripe, Printify)

**2. Simplicity for MVP**

REST is simpler to implement and test:
- **No Schema Definition Language** (unlike GraphQL): Just TypeScript types
- **Familiar HTTP Verbs**: GET, POST, PUT, DELETE (team already knows)
- **Standard HTTP Status Codes**: 200 OK, 404 Not Found, 403 Forbidden

**3. Caching & CDN Compatibility**

REST GET requests are cacheable by default:
- **CloudFront**: Can cache GET `/api/products` responses (reduce Lambda invocations)
- **Browser Cache**: `Cache-Control` headers supported natively

**GraphQL**: Typically POST-only (not cacheable without custom logic)

**4. OpenAPI Spec for Documentation**

OpenAPI 3.0 auto-generates API documentation:
- **Swagger UI**: Interactive API explorer (test endpoints in browser)
- **SDK Generation**: Auto-generate TypeScript SDK for frontend (via `openapi-generator`)
- **Contract Testing**: Validate API responses match OpenAPI spec (Pact.js)

**Example OpenAPI Spec**:
```yaml
openapi: 3.0.0
paths:
  /api/shops/{slug}/cart:
    get:
      summary: Get cart for shop
      parameters:
        - name: slug
          in: path
          required: true
          schema:
            type: string
      responses:
        '200':
          description: Cart retrieved successfully
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Cart'
```

---

### Why tRPC for Internal API (Next.js)?

**1. End-to-End Type Safety**

tRPC provides **zero-latency type safety** between frontend and backend:
- **Backend defines procedure**: `createProduct(input: CreateProductInput)`
- **Frontend auto-imports types**: `trpc.product.create.useMutation()` (TypeScript knows input/output types)
- **No manual sync**: Change backend type → frontend sees TypeScript error immediately

**Example**:
```typescript
// Backend: app/api/trpc/[trpc].ts
const appRouter = router({
  product: {
    create: protectedProcedure
      .input(z.object({ title: z.string(), price: z.number() }))
      .mutation(async ({ input, ctx }) => {
        const product = await createProduct(input, ctx.userId);
        return product;
      }),
  },
});

// Frontend: components/CreateProductForm.tsx
const mutation = trpc.product.create.useMutation();
mutation.mutate({ title: 'Cool Shirt', price: 29.99 }); // ✅ Type-safe
mutation.mutate({ title: 'Cool Shirt' }); // ❌ TypeScript error: missing price
```

**2. Faster Development**

tRPC eliminates boilerplate:
- **No REST route definitions**: No need to write `app/api/products/route.ts`
- **No manual validation**: Zod schemas validate input automatically
- **No fetch() calls**: tRPC client handles HTTP requests

**Time Savings**: ~30% faster than REST for internal APIs (no manual type sync)

**3. Perfect for Monorepo (Next.js)**

Next.js is a monorepo (frontend + backend in same codebase):
- tRPC leverages this: Shared types between client and server
- No API versioning needed (internal only, always in sync)

**When NOT to Use tRPC**:
- ❌ External API clients (mobile apps, third-party integrations) — Use REST
- ❌ Webhooks (Stripe, Printify) — Use REST (standard HTTP POST)

### tRPC Internal API Structure

**Router Definition**: `app/api/trpc/[trpc].ts`

```typescript
import { router, protectedProcedure, publicProcedure } from './trpc';
import { z } from 'zod';

export const appRouter = router({
  // Shop procedures
  shop: {
    create: protectedProcedure
      .input(z.object({ name: z.string(), description: z.string() }))
      .mutation(async ({ input, ctx }) => createShop(input, ctx.userId)),

    update: protectedProcedure
      .input(z.object({ shopId: z.string(), name: z.string() }))
      .mutation(async ({ input, ctx }) => updateShop(input, ctx.userId)),

    list: protectedProcedure.query(async ({ ctx }) => getShopsByUser(ctx.userId)),
  },

  // Product procedures
  product: {
    create: protectedProcedure
      .input(z.object({ shopId: z.string(), title: z.string(), price: z.number() }))
      .mutation(async ({ input, ctx }) => createProduct(input, ctx.userId)),

    list: publicProcedure
      .input(z.object({ shopId: z.string() }))
      .query(async ({ input }) => getProductsByShop(input.shopId)),
  },

  // Cart procedures
  cart: {
    get: publicProcedure
      .input(z.object({ shopId: z.string() }))
      .query(async ({ input, ctx }) => getCart(ctx.userId, input.shopId)),

    addItem: publicProcedure
      .input(z.object({ shopId: z.string(), productId: z.string(), quantity: z.number() }))
      .mutation(async ({ input, ctx }) => addToCart(input, ctx.userId)),
  },
});

export type AppRouter = typeof appRouter;
```

**Frontend Usage**:
```typescript
// components/ProductCard.tsx
import { trpc } from '@/lib/trpc';

export function ProductCard({ productId, shopId }) {
  const addToCart = trpc.cart.addItem.useMutation();

  const handleAddToCart = () => {
    addToCart.mutate({ shopId, productId, quantity: 1 });
  };

  return <button onClick={handleAddToCart}>Add to Cart</button>;
}
```

### REST API Response Format (Standard Envelope)

**Success Response**:
```json
{
  "success": true,
  "data": {
    "id": "cart-123",
    "items": [
      { "productId": "prod-456", "quantity": 2, "price": 29.99 }
    ],
    "subtotal": 59.98
  },
  "meta": {
    "timestamp": "2025-11-21T10:30:00Z",
    "requestId": "req-789"
  }
}
```

**Error Response**:
```json
{
  "success": false,
  "error": {
    "code": "FORBIDDEN",
    "message": "Product does not belong to this shop",
    "details": {
      "productId": "prod-456",
      "shopId": "shop-123"
    }
  },
  "meta": {
    "timestamp": "2025-11-21T10:30:00Z",
    "requestId": "req-790"
  }
}
```

**HTTP Status Codes**:
- `200 OK`: Successful GET request
- `201 Created`: Successful POST (resource created)
- `400 Bad Request`: Invalid input (Zod validation failed)
- `401 Unauthorized`: Missing or invalid JWT token
- `403 Forbidden`: User not authorized for this resource
- `404 Not Found`: Resource does not exist
- `500 Internal Server Error`: Unhandled exception

### Pagination (Cursor-Based)

**Why Cursor Over Offset**:
- **Offset** (`?page=2&limit=20`): Inefficient for large datasets (skips rows)
- **Cursor** (`?cursor=prod-456&limit=20`): Uses last item ID, faster queries

**Example**:
```http
GET /api/v1/shops/acme/products?cursor=prod-456&limit=20
```

**Response**:
```json
{
  "success": true,
  "data": [
    { "id": "prod-457", "title": "Product 1" },
    { "id": "prod-458", "title": "Product 2" }
  ],
  "meta": {
    "nextCursor": "prod-458",
    "hasMore": true
  }
}
```

**DynamoDB Implementation**:
```javascript
const result = await dynamoDB.query({
  TableName: 'PrintXpressMain',
  KeyConditionExpression: 'PK = :pk AND SK > :cursor',
  ExpressionAttributeValues: {
    ':pk': `SHOP#${shopId}`,
    ':cursor': cursor || 'PRD#', // Start from beginning if no cursor
  },
  Limit: 20,
});

return {
  data: result.Items,
  meta: {
    nextCursor: result.LastEvaluatedKey?.SK,
    hasMore: !!result.LastEvaluatedKey,
  },
};
```

## Authentication & Authorization

### JWT Token (Lambda Authorizer)

**Flow**:
1. User logs in → NextAuth.js issues JWT token
2. Frontend includes token in `Authorization: Bearer <token>` header
3. API Gateway triggers Lambda authorizer
4. Authorizer validates token, extracts `userId`, returns policy
5. Lambda function receives `userId` in `event.requestContext.authorizer`

**JWT Payload**:
```json
{
  "sub": "user-123", // userId
  "role": "VENDOR",
  "iat": 1700000000,
  "exp": 1700003600 // 1 hour expiry
}
```

**Lambda Authorizer**:
```typescript
export async function handler(event: APIGatewayAuthorizerEvent) {
  const token = event.headers.Authorization?.replace('Bearer ', '');
  if (!token) return { isAuthorized: false };

  try {
    const decoded = jwt.verify(token, process.env.JWT_SECRET);
    return {
      isAuthorized: true,
      context: { userId: decoded.sub, role: decoded.role },
    };
  } catch {
    return { isAuthorized: false };
  }
}
```

## Rate Limiting

**API Gateway Throttling**:
- **Default**: 10,000 requests/second per account
- **Per-Endpoint**: 100 requests/second per endpoint (configurable)

**DDoS Protection**:
- **AWS Shield Standard**: Free, protects against common attacks
- **WAF Rules** (Phase 2): Block suspicious IPs, SQL injection patterns

**Application-Level Rate Limiting** (Phase 2):
- **Redis** (ElastiCache): Track requests per user per minute
- **Limit**: 100 requests/minute per user

## Comparison Matrix

| Feature | REST | GraphQL | tRPC |
|---------|------|---------|------|
| **Type Safety** | Manual (OpenAPI → codegen) | Manual (GraphQL schema) | Automatic (TypeScript) |
| **Learning Curve** | Low (industry standard) | Medium (new syntax) | Low (just TypeScript) |
| **External Clients** | ✅ Native support | ✅ Works (GraphQL clients) | ❌ TypeScript-only |
| **Webhooks** | ✅ Standard HTTP POST | ❌ No native support | ❌ No native support |
| **Caching** | ✅ GET requests cacheable | ⚠️ POST-only (custom cache) | ⚠️ Custom cache needed |
| **Over-fetching** | ⚠️ Returns all fields | ✅ Client specifies fields | ⚠️ Returns all fields |
| **Development Speed** | Medium (manual types) | Medium (schema-first) | Fast (auto-types) |
| **Mobile Apps** | ✅ Works with any HTTP client | ✅ Apollo Client, Relay | ❌ TypeScript-only |
| **Tooling** | ✅ Swagger, Postman | ✅ GraphiQL, Apollo Studio | ✅ tRPC Panel |

## Migration Path (If Needed)

### Scenario: Need GraphQL for Complex Queries

**Trigger**: Mobile app (Phase 3) requires flexible queries (reduce over-fetching)

**Implementation**:
1. Add GraphQL endpoint: `/api/graphql` (Apollo Server on Lambda)
2. GraphQL resolvers query DynamoDB (same data layer)
3. REST API remains for webhooks, simple CRUD
4. Mobile app uses GraphQL, web app uses tRPC

**Effort**: 5-8 story points (GraphQL schema, resolvers)

**Cost**: No additional infrastructure cost (same Lambda functions)

**Probability**: 20% (only if mobile app becomes core product)

## Consequences

### Positive

✅ **REST**: Universal compatibility (Stripe, Printify, mobile apps)

✅ **tRPC**: 30% faster internal development (auto-types, no boilerplate)

✅ **Hybrid**: Best of both worlds (REST for external, tRPC for internal)

✅ **OpenAPI Spec**: Auto-generated docs, SDK generation, contract tests

✅ **Simplicity**: No GraphQL complexity for MVP (YAGNI principle)

### Negative

⚠️ **Over-fetching**: REST returns all fields (cannot select specific fields)

**Impact**: Minor for MVP (bandwidth cost <$1/month, all fields typically needed)

**Mitigation**: Phase 3 can add GraphQL if mobile app needs field selection

⚠️ **Two API Styles**: Developers must learn both REST and tRPC

**Impact**: Minimal (tRPC syntax is trivial, just TypeScript functions)

**Mitigation**: Documentation clarifies when to use each (external = REST, internal = tRPC)
