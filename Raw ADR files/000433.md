# ADR-003: Rapid Response Infrastructure for Adversarial Threats

**Status**: Accepted
**Date**: December 2024
**Author**: Vincent
**Implementation**: [Hyperion](https://github.com/BugVanquisher/Hyperion) + [Sentinel](https://github.com/BugVanquisher/Sentinel)

---

## Context

When operating safety-critical AI systems, threats evolve constantly. From Gmail Shield experience:
- New spam patterns emerge daily
- Attackers adapt within hours of detection
- Traditional ML deployment cycles (days/weeks) are too slow

### The Problem

Standard ML deployment:
1. Detect new attack pattern
2. Collect training data
3. Retrain model
4. Validate in staging
5. Deploy to production
6. **Total: 1-2 weeks**

During this window, attackers have free reign.

### Requirements

- **Time-to-mitigation**: Minutes, not weeks
- **Safety**: Can't break production with rushed changes
- **Rollback**: Instant revert if something goes wrong
- **Observability**: Know impact immediately

---

## Decision

**Implement a multi-layer rapid response system:**

```
┌─────────────────────────────────────────────────────────────┐
│              RAPID RESPONSE LAYERS                          │
├─────────────────────────────────────────────────────────────┤
│  LAYER 1: Pattern Updates (Minutes)                         │
│  ├── Add regex patterns without redeploy                    │
│  ├── Update block lists in Redis                            │
│  └── Adjust thresholds via config                           │
├─────────────────────────────────────────────────────────────┤
│  LAYER 2: Shadow Mode Deployment (Hours)                    │
│  ├── New models run in parallel (no user impact)            │
│  ├── Compare decisions with production                      │
│  └── Validate before promoting                              │
├─────────────────────────────────────────────────────────────┤
│  LAYER 3: Canary Rollout (Hours)                            │
│  ├── 1% → 10% → 50% → 100% traffic                         │
│  ├── Automatic rollback on safety degradation               │
│  └── Real-time metrics comparison                           │
└─────────────────────────────────────────────────────────────┘
```

## Implementation in Sentinel

### Dynamic Pattern Updates

```python
# sentinel/engine/dynamic_patterns.py

class DynamicPatternStore:
    """
    Runtime-updateable pattern store backed by Redis.

    Design Decision: Patterns in Redis, not code
    - Can update without redeploy
    - Can rollback instantly
    - Can A/B test patterns

    Trade-off: Redis dependency, slight latency
    Mitigation: Local cache with 60s TTL
    """

    def __init__(self, redis_client):
        self.redis = redis_client
        self.local_cache = {}
        self.cache_ttl = 60

    async def get_patterns(self, category: str) -> List[Pattern]:
        """
        Get patterns from Redis with local caching.
        """
        cache_key = f"patterns:{category}"

        # Check local cache
        if cache_key in self.local_cache:
            cached = self.local_cache[cache_key]
            if time.time() - cached["timestamp"] < self.cache_ttl:
                return cached["patterns"]

        # Fetch from Redis
        raw_patterns = await self.redis.smembers(f"sentinel:patterns:{category}")
        patterns = [Pattern.from_json(p) for p in raw_patterns]

        # Update local cache
        self.local_cache[cache_key] = {
            "patterns": patterns,
            "timestamp": time.time()
        }

        return patterns

    async def add_pattern(
        self,
        category: str,
        pattern: str,
        metadata: dict = None
    ) -> AddResult:
        """
        Add new pattern with immediate effect.

        Called when:
        - New attack detected in logs
        - Security team identifies threat
        - Automated anomaly detection

        Time to effect: <60 seconds (cache TTL)
        """
        pattern_obj = Pattern(
            regex=pattern,
            category=category,
            added_at=datetime.utcnow(),
            added_by=metadata.get("author", "system"),
            confidence=metadata.get("confidence", 0.9),
            source=metadata.get("source", "manual")
        )

        await self.redis.sadd(
            f"sentinel:patterns:{category}",
            pattern_obj.to_json()
        )

        # Invalidate local cache across all instances
        await self.redis.publish("sentinel:cache:invalidate", category)

        return AddResult(
            success=True,
            pattern_id=pattern_obj.id,
            effective_in_seconds=self.cache_ttl
        )

    async def remove_pattern(self, pattern_id: str) -> RemoveResult:
        """
        Remove pattern (instant rollback capability).
        """
        # Patterns are never deleted, just deactivated
        await self.redis.hset(
            f"sentinel:pattern:{pattern_id}",
            "active", "false"
        )

        await self.redis.publish("sentinel:cache:invalidate", "all")

        return RemoveResult(success=True)
```

### Threshold Tuning API

```python
# sentinel/api/admin.py

@router.post("/admin/thresholds")
async def update_thresholds(
    update: ThresholdUpdate,
    auth: AdminAuth = Depends(verify_admin)
):
    """
    Update detection thresholds without redeploy.

    Example: Lower toxicity threshold during attack
    - Normal: block if toxicity > 0.9
    - During attack: block if toxicity > 0.7

    Rollback: Set back to original value
    """
    old_value = await threshold_store.get(update.detector, update.threshold_name)

    await threshold_store.set(
        detector=update.detector,
        threshold_name=update.threshold_name,
        value=update.value,
        reason=update.reason,
        author=auth.user_id
    )

    # Emit event for observability
    await event_bus.emit(ThresholdChangedEvent(
        detector=update.detector,
        threshold=update.threshold_name,
        old_value=old_value,
        new_value=update.value,
        author=auth.user_id,
        timestamp=datetime.utcnow()
    ))

    return {"success": True, "previous_value": old_value}
```

## Implementation in Hyperion

### Shadow Mode Deployment

```python
# hyperion/deployment/shadow.py

class ShadowDeployment:
    """
    Run new models in shadow mode alongside production.

    Design Decision: Shadow before promote
    - New model sees real traffic
    - No user impact (production model serves)
    - Compare decisions for validation

    Use cases:
    - New safety classifier
    - Updated model weights
    - New detection rules
    """

    def __init__(self, production_model, shadow_model):
        self.production = production_model
        self.shadow = shadow_model
        self.metrics = ShadowMetrics()

    async def inference(self, request: InferenceRequest) -> InferenceResponse:
        # Production model serves the user
        production_response = await self.production.inference(request)

        # Shadow model runs async (non-blocking)
        asyncio.create_task(self._run_shadow(request, production_response))

        return production_response

    async def _run_shadow(self, request, production_response):
        """
        Run shadow model and compare results.
        """
        try:
            shadow_response = await self.shadow.inference(request)

            # Compare decisions
            comparison = self._compare_responses(
                production_response,
                shadow_response
            )

            # Record metrics
            self.metrics.record(
                agreement=comparison.agreed,
                production_decision=production_response.decision,
                shadow_decision=shadow_response.decision,
                latency_diff=shadow_response.latency - production_response.latency
            )

            # Alert on significant disagreement
            if comparison.disagreement_rate > 0.1:
                await alert_service.send(
                    level="warning",
                    message=f"Shadow model disagreement: {comparison.disagreement_rate:.1%}",
                    details=comparison.to_dict()
                )

        except Exception as e:
            logger.error(f"Shadow inference failed: {e}")
            # Shadow failures don't affect production
```

### Canary Rollout

```python
# hyperion/deployment/canary.py

class CanaryDeployment:
    """
    Gradual rollout with automatic rollback.

    Stages: 1% → 10% → 50% → 100%
    Each stage must pass safety metrics before promotion.

    Automatic rollback if:
    - Error rate > 2x baseline
    - Latency P95 > 1.5x baseline
    - Safety block rate changes > 20%
    """

    def __init__(self, current_model, canary_model):
        self.current = current_model
        self.canary = canary_model
        self.canary_percentage = 0
        self.stage_metrics = {}

    async def set_canary_percentage(self, percentage: int):
        """
        Set traffic percentage for canary.
        """
        self.canary_percentage = percentage
        await self._start_stage_monitoring(percentage)

    async def inference(self, request: InferenceRequest) -> InferenceResponse:
        # Hash-based routing for consistency
        request_hash = hash(request.request_id) % 100

        if request_hash < self.canary_percentage:
            model = self.canary
            is_canary = True
        else:
            model = self.current
            is_canary = False

        response = await model.inference(request)
        response.metadata["canary"] = is_canary

        return response

    async def check_promotion_criteria(self) -> PromotionResult:
        """
        Check if canary can be promoted to next stage.
        """
        canary_metrics = await self._get_canary_metrics()
        baseline_metrics = await self._get_baseline_metrics()

        checks = {
            "error_rate": canary_metrics.error_rate < baseline_metrics.error_rate * 2,
            "latency_p95": canary_metrics.latency_p95 < baseline_metrics.latency_p95 * 1.5,
            "safety_block_rate": abs(
                canary_metrics.safety_block_rate - baseline_metrics.safety_block_rate
            ) < 0.2 * baseline_metrics.safety_block_rate,
        }

        passed = all(checks.values())

        return PromotionResult(
            can_promote=passed,
            checks=checks,
            recommendation="promote" if passed else "rollback"
        )

    async def auto_rollback(self, reason: str):
        """
        Instant rollback to current model.
        """
        self.canary_percentage = 0

        await alert_service.send(
            level="critical",
            message=f"Canary auto-rollback triggered: {reason}",
            details={
                "canary_model": self.canary.version,
                "rolled_back_to": self.current.version
            }
        )
```

## Operational Workflow

### New Attack Response (15-minute playbook)

```
Minute 0-2: Detection
├── MonitorX alert: unusual block pattern
├── Review sample requests in logs
└── Identify attack signature

Minute 2-5: Pattern Addition
├── Extract regex pattern from examples
├── Add pattern via Admin API
├── Pattern effective in <60 seconds
└── Verify blocks in MonitorX

Minute 5-10: Validation
├── Check false positive rate
├── Review legitimate traffic impact
└── Adjust pattern if needed

Minute 10-15: Documentation
├── Log pattern addition
├── Update threat intelligence
└── Share with team
```

### Model Update Response (2-hour playbook)

```
Hour 0-0.5: Preparation
├── Build new model artifact
├── Deploy to shadow environment
└── Start shadow comparison

Hour 0.5-1: Shadow Validation
├── Collect 1000+ shadow comparisons
├── Review disagreement cases
├── Check latency impact
└── Approve for canary

Hour 1-2: Canary Rollout
├── Stage 1 (1%): 15 minutes
├── Stage 2 (10%): 15 minutes
├── Stage 3 (50%): 15 minutes
├── Stage 4 (100%): Promote
└── Monitor for 15 minutes post-promote
```

## Consequences

### Benefits

1. **Response Time**: Pattern updates in <2 minutes
2. **Safety**: Shadow mode validates before production impact
3. **Confidence**: Canary catches issues before full rollout
4. **Rollback**: Instant revert capability at any point

### Trade-offs

1. **Complexity**: Three deployment modes to manage
   - Mitigation: Clear playbooks, automation
   - Benefit: Right tool for right urgency

2. **Resource Cost**: Shadow runs double inference
   - Mitigation: Shadow only during deployments
   - Benefit: Catches issues before users see them

3. **Redis Dependency**: Patterns require Redis
   - Mitigation: Fallback to compiled patterns
   - Benefit: Dynamic updates without redeploy

### Metrics from Production

| Metric | Value |
|--------|-------|
| Pattern update time | 47 seconds average |
| Shadow deployment duration | 2-4 hours |
| Canary rollout duration | 1-2 hours |
| Auto-rollback triggers | 3 (in 6 months) |
| Mean time to mitigation | 8 minutes |

## Alternatives Considered

### 1. Traditional CI/CD Only

**Rejected because**:
- Deploy cycles too slow (hours minimum)
- Can't respond to attacks in real-time
- No gradual rollout

### 2. Blue/Green Only

**Rejected because**:
- All-or-nothing (no gradual validation)
- Requires double infrastructure
- No shadow comparison

### 3. Manual Threshold Changes

**Rejected because**:
- Requires code change and deploy
- No audit trail
- Higher friction = slower response
