Abstract:: There is currently no way to test Reference Implementations of EPs, and no way  described in the Production Spec to use the Repo in Obsidian! A LibLoader that provides branches of the Repo in Obsidian is proposed.

## Motivation
> Description of the goals achieved by this Enhancement Proposal and argument that this is the minimal alteration of the Production Spec that would achieve those goals. From PEP 1: "It should clearly explain why the existing language specification is inadequate to address the problem that the PEP solves."

The Repo is the central object that makes the Production Spec part of a working ecosystem (you certainly can't remember the whole Production Spec) by making certain standardized operations, searches, and visualizations available in Obsidian. Code exists for loading the Repo into obsidian using the CustomJS plugin, but is not integrated into the Production Spec and is therefore not sustainable to extensible. The current PS does not describe any access to the Repo.
Enhancement Protocols also require developing new branches of the Repo as Reference Implementations. It is essential to be able to test these branches in Obsidian, and for sustainability it is essential that the any behavior of the Repo accessed by Obsidian reverts to the mater branch easily and by default.

## Rationale
> Explanation of major design decisions, including comparison to alternative designs and related work, e.g. how the problem is solved in other software or systems.

A CustomJS LibLoader script is a solution adopted by previous vaults, but
1. The modes of access to the custom library were verbose, and error prone. A global `Lib` object was used and `await Lib.ensureLib()` was meant to be called before each use case. The new pattern adopted by CustomJS of an asynchronous getter function is preferable.
2. Quite a bit of boilerplate structure for loading and unloading the custom library was required, and these methods were poorly documented.
3. The loader consisted of a single method run once to establish the `ensureLib` function that was relied on for reloading, which was poorly abstracted and hence not very extensible.
4. No functionality was available for switching between branches of a codebase.

A new LibLoader is proposed that loads `Internals/lib/<BRANCH>/customlib.<VERSION>.js`, and allows access to the loaded library through an asynchronous "entry point" function `CL()`. The loader checks on an interval for a `<VERSION>` that is newer than the last-loaded one, and if it succeeds it refreshes the loaded version returned by future calls to `CL()`.
A default branch name (`master`) can be overridden, after which the next refresh will load the version. Overriding is possible through the Developer Tools console as
```js
(await cJS()).CustomLibLoader.branchName = '<branch name>'
```
Note that older `<VERSION>`'s can need to be loaded if `branchName` has switched since the previous refresh.

The LibLoader operates by pasting the file contents into a `<script/>` block in Obsidian's head, dropping any previous `<script/>` tag when a new branch or version is loaded. Other implementation details can be ignored, but it is worth noting that this does not actually clear objects from the global namespace, just overwrites them with new ones if they have the same name.

This requires a Builder that outputs code to the `Internals/lib` directory, named the current git branch and version. Again, previous vaults have done this, but the Production Spec does not require this at the moment. Details of the Builder are outside the scope of this EP, but are described in [[EP 3]].

A number of choices to limit scope were made that could be addressed in future EPs.
- No CSS loading.
- Only one compiled JS file can be loaded at once.
- Smoother branch switching or warnings while using code from a non-default branch.


## Contracts at Risk
> Description of how Contracts of any involved Spec Objects were maintained.

- *SOC 1*. The docs overview page currently does not describe any relationship between the Repo and Obsidian, which will be inaccurate. See Reference Implementation for planned updates to the DOP.
- *SOC 2*. The Master Branch previously did not contain any code and so lacked any properties and SOC 2 did not actually bind the Master Branch to do anything. The LibLoader will be added to the Master Branch section of the PS and SOC 2 will be updated to reference the proposed contract of the LibLoader.
- *SOC 3* is not impacted.

## Reference Implementation
> A branch of the Repo that implements what the Production Spec would be once the Spec Changes were applied.

A root-level file `libloader.js` in branch `branch-build` adds a LibLoader Implementation to the Repo.
The Docs Overview Page will be updated to say "The Repo code is made available in obsidian through a LibLoader that refreshes when new code is compiled and allows switching between branches."
