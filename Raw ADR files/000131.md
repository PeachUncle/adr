# ADR-0010: Script Composition Architecture for CI/CD

**Date**: 2024-10-12
**Status**: Accepted

## Context

CI/CD pipelines for iOS projects require various automated tasks: building, testing, coverage reporting, and validation. Multiple consumers need these capabilities:

1. **Local Development**: Developers running commands manually
2. **Pre-commit Hooks**: Automated checks before git operations
3. **Makefile Targets**: Convenient command shortcuts
4. **GitHub Actions**: CI/CD pipeline automation
5. **Manual Testing**: Ad-hoc validation and debugging

The traditional approach often leads to:

- **Code Duplication**: Same xcodebuild commands in multiple places
- **Inconsistency**: Different behavior in different environments
- **Maintenance Burden**: Changes require updates in multiple locations
- **Testing Gaps**: CI behavior differs from local behavior

The challenge is balancing:

- DRY principle (Don't Repeat Yourself)
- Composability (reusable components)
- Clarity (easy to understand and modify)
- Consistency (same behavior everywhere)

## Decision

**We will implement a script composition architecture where atomic, single-purpose scripts are reused across all automation contexts.**

### Architecture Pattern

```
Atomic Scripts (Single Responsibility):
├── build-release.sh        # Builds release configuration
├── run-tests.sh            # Runs tests with coverage
└── [future scripts]        # Additional focused scripts

Composition Layer (Orchestration):
├── run-ci-locally.sh       # Combines build + test
├── Makefile                # Exposes scripts as targets
├── .pre-commit-config.yaml # Uses scripts in hooks
└── .github/workflows/      # Uses scripts in CI

Consumers:
├── Developer: make test
├── Git Hook: run-tests.sh
├── Makefile: calls run-tests.sh
└── CI: run-ci-locally.sh → build-release.sh + run-tests.sh
```

### Script Principles

1. **Atomic**: Each script does one thing well
2. **Composable**: Scripts can be called from other scripts
3. **Idempotent**: Safe to run multiple times
4. **Self-Contained**: No external state dependencies
5. **Clear Output**: Human-readable progress messages
6. **Exit Codes**: 0 for success, non-zero for failure

## Alternatives Considered

### 1. Monolithic Scripts

Single large script (e.g., `ci.sh`) that does everything.

**Why not chosen**:

- Hard to reuse parts (can't run just tests)
- Difficult to compose (all-or-nothing)
- Hard to maintain (large, complex)
- Violates Single Responsibility Principle
- Can't optimize individual steps

### 2. Inline Commands Everywhere

Repeating xcodebuild commands in each location (Makefile, CI, hooks).

**Why not chosen**:

- Massive code duplication
- Inconsistent parameters across contexts
- Changes require updates in multiple files
- High risk of drift and inconsistency
- Violates DRY principle

### 3. Complex Build System (CMake, Bazel, etc.)

Using sophisticated build systems with dependency graphs.

**Why not chosen**:

- Overkill for straightforward iOS project
- Not idiomatic for iOS development
- Steep learning curve
- iOS uses Xcode/xcodebuild by convention
- Adds unnecessary complexity

### 4. GitHub Actions Reusable Workflows

Using GitHub's workflow composition features exclusively.

**Why not chosen**:

- Locks logic into GitHub (vendor lock-in)
- Can't test CI locally without third-party tools (act)
- Not reusable in Makefile or hooks
- Limits portability
- Still need scripts for actual commands

### 5. Shell Functions in Shared Library

Central `lib.sh` with shared functions sourced by other scripts.

**Why not chosen**:

- Tight coupling between scripts
- Can't run functions standalone
- Sourcing creates implicit dependencies
- Harder to test individual functions
- Less clear than explicit script calls

## Consequences

### Positive

1. **DRY Compliance**: Build/test logic exists once
2. **Consistency**: Identical behavior across all contexts
3. **Testability**: Can test scripts individually
4. **Composability**: Easy to create new combinations
5. **Clarity**: Each script has clear purpose
6. **Maintainability**: Changes in one place
7. **Local CI**: Can run exact CI steps locally
8. **Independence**: Scripts don't depend on each other
9. **Debugging**: Easy to run individual steps
10. **Documentation**: Scripts self-document via clear names

### Negative

1. **Multiple Files**: More files to track than monolithic approach
2. **Indirection**: Need to look in scripts to see actual commands
3. **Discovery**: Need documentation to know which scripts exist
4. **Coordination**: Changes may affect multiple consumers

### Mitigation Strategies

- **Clear Naming**: Use descriptive script names (`run-tests.sh`, not `test.sh`)
- **Documentation**: Maintain `scripts/README.md` with script inventory
- **Makefile**: Provide convenient aliases for common scripts
- **Comments**: Each script has header explaining purpose and usage

## Rationale

The decision prioritizes **maintainability, consistency, and DRY principles** over minimizing file count.

Key factors:

1. **Proven Pattern**: Widely used in professional projects (Docker, Kubernetes, etc.)
2. **iOS Examples**: Jon Reid's Mastermind and other modern iOS projects use this pattern
3. **Scalability**: Easy to add new scripts as project grows
4. **Testing**: Can verify CI behavior locally before pushing
5. **Debugging**: Can run individual steps in isolation
6. **Onboarding**: New contributors understand focused scripts faster

The pattern follows Unix philosophy: small, composable tools that do one thing well.

## Implementation Details

### Script Organization

```
scripts/
├── README.md              # Script documentation
├── verify-setup.sh        # Environment validation
├── build-release.sh       # Atomic: Build release
├── run-tests.sh           # Atomic: Run tests + coverage
└── run-ci-locally.sh      # Composition: Full CI pipeline
```

### Atomic Script: `build-release.sh`

**Purpose**: Build release configuration only
**Lines of Code**: ~30
**Reused by**: run-ci-locally.sh, Makefile

```bash
#!/bin/bash
set -euo pipefail

echo "Building Release configuration..."
xcodebuild -project ... -configuration Release clean build ...
echo "✓ Build successful"
```

### Atomic Script: `run-tests.sh`

**Purpose**: Run tests with coverage reporting
**Lines of Code**: ~60
**Reused by**: run-ci-locally.sh, Makefile, pre-commit hooks

```bash
#!/bin/bash
set -euo pipefail

echo "Running tests with coverage..."
xcodebuild test -enableCodeCoverage YES ...
echo "Generating coverage reports..."
xcrun xccov view --report ...
echo "✓ Tests passed, coverage reports generated"
```

### Composition Script: `run-ci-locally.sh`

**Purpose**: Orchestrate full CI pipeline
**Lines of Code**: ~30
**Reused by**: GitHub Actions, Makefile

```bash
#!/bin/bash
set -euo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"

echo "==== Running CI Pipeline Locally ===="
"${SCRIPT_DIR}/build-release.sh"
"${SCRIPT_DIR}/run-tests.sh"
echo "==== ✓ CI Pipeline Complete ===="
```

### Makefile Integration

```makefile
test:
 @./scripts/run-tests.sh

build-release:
 @./scripts/build-release.sh

ci:
 @./scripts/run-ci-locally.sh
```

### Pre-commit Integration

```yaml
- repo: local
  hooks:
    - id: swift-tests
      entry: ./scripts/run-tests.sh
      language: system
      stages: [push]
```

### GitHub Actions Integration

```yaml
- name: Run CI pipeline
  run: ./scripts/run-ci-locally.sh
```

## Script Standards

### Required Elements

All scripts must include:

1. **Shebang**: `#!/bin/bash`
2. **Error Handling**: `set -euo pipefail`
3. **Header Comment**: Purpose and usage
4. **Progress Messages**: Echo major steps
5. **Success Indicator**: Final "✓" message
6. **Exit Codes**: 0 for success, non-zero for failure

### Example Template

```bash
#!/bin/bash
# Purpose: [What this script does]
# Usage: ./script-name.sh [args]
# Exit: 0 on success, non-zero on failure

set -euo pipefail  # Exit on error, undefined variables, pipe failures

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"

echo "Starting [task]..."

# Main logic here

echo "✓ [Task] complete"
exit 0
```

### Naming Conventions

- Use lowercase with hyphens: `run-tests.sh`
- Descriptive verbs: `build`, `run`, `verify`, `generate`
- Avoid abbreviations: `run-tests.sh` not `test.sh`
- Indicate scope: `run-ci-locally.sh` vs. `run-tests.sh`

## Composition Examples

### Example 1: Current CI Pipeline

```
Developer runs: make ci
   ↓
Makefile calls: ./scripts/run-ci-locally.sh
   ↓
   ├─→ ./scripts/build-release.sh (builds once)
   └─→ ./scripts/run-tests.sh (tests once)
```

**Benefit**: Same scripts work in all contexts

### Example 2: Pre-push Hook

```
Developer runs: git push
   ↓
Pre-commit framework
   ↓
   └─→ ./scripts/run-tests.sh (tests only, no build)
```

**Benefit**: Reuse atomic script, skip unnecessary build

### Example 3: Debugging Failed Test

```
Developer runs: ./scripts/run-tests.sh
   ↓
Direct script execution
   ↓
Same behavior as CI
```

**Benefit**: Reproduce exact CI behavior locally

## Future Extensions

### Easy to Add New Scripts

```bash
# New atomic script
scripts/lint-swift.sh       # Just linting

# Compose into existing workflow
run-ci-locally.sh:
  lint-swift.sh    # Add before build
  build-release.sh
  run-tests.sh
```

### Potential Future Scripts

- `generate-docs.sh`: API documentation generation
- `analyze-code.sh`: Static analysis
- `verify-signing.sh`: Code signing validation
- `archive-build.sh`: Create archive for distribution
- `upload-symbols.sh`: Upload dSYMs to crash reporting
