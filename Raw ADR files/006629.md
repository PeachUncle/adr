# ADR 2.1: Log-First Memory Stack

- Status: Accepted (2025-10-29)
- Owners: Platform Architecture Guild
- Tags: memory, persistence, provenance, milvus, neo4j

## Context
- V3 must unify structured (PostgreSQL), vector (Milvus), and object (MinIO) storage while keeping evidence provenance for every agent action.
- Previous iterations allowed tools to write directly to storage, creating race conditions, missing lineage, and inconsistent replay results.
- GraphRAG and Agentic RAG layers now depend on deterministic inputs so replay jobs and regulatory audits can reproduce knowledge flows byte-for-byte.

## Decision
- All agent outputs, tool responses, and user uploads SHALL be persisted first to an append-only execution log with monotonic sequence IDs.
- A log dispatcher service SHALL perform deterministic serialization into canonical storage targets (PostgreSQL, Milvus, MinIO) before downstream indexing or graph mutation begins.
- Agentic RAG indexers SHALL derive embeddings exclusively from serialized artifacts produced by the dispatcher, never from transient in-memory buffers.
- GraphRAG workers SHALL emit versioned deltas that reference the originating log sequence ID, enabling graph rollback and replay.
- Log retention SHALL follow a tiered policy: hot storage (7 days) in PostgreSQL + S3-compatible archive (90 days+) with checksum validation for compliance.

## Consequences
- Pros: deterministic provenance, simplified replay, auditable ingestion pipeline, clear blast radius for data corruption.
- Cons: higher write latency (log + dispatch), additional storage cost, dispatcher becomes a critical path component requiring HA.
- Mitigation: deploy dispatcher as a replicated FastAPI service with idempotent consumers; introduce circuit breakers that pause downstream indexers if log lag exceeds defined thresholds.

## Implementation Notes
- Execution log schema: `execution_log(id BIGSERIAL, tenant_id UUID, source ENUM(tool|agent|user), payload JSONB, checksum BYTEA, created_at TIMESTAMPTZ)`.
- Dispatcher jobs SHALL stamp `content_hash` on every MinIO object and store cross-references (`storage_pointer`) in PostgreSQL for join-free lookup.
- Milvus insertion pipeline SHALL batch events by tenant and payload modality to maintain vector index performance and support replay via `SELECT * FROM execution_log WHERE id BETWEEN x AND y`.
- Backfill strategy: migrate legacy records by replaying historical tool outputs through the dispatcher; mark migrated batches with `migrated_from` metadata for traceability.
