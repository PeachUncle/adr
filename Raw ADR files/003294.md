# ADR-0002: DynamoDB as Primary Data Store

**Status**: Accepted
**Date**: 2025-11-21
**Deciders**: Principal Architect, CTO
**Related ADRs**: ADR-0003 (Postgres Replica)

---

## Context

PrintXpress requires a primary database that can:
- **Scale horizontally** from 1K to 10K+ orders/month without manual intervention
- **Provide consistent low latency** (<10ms reads/writes) at any scale
- **Support event-driven architecture** via change data capture (CDC)
- **Minimize operational overhead** (no patching, index rebuilding, capacity planning)
- **Meet AWS-native requirement** (>85% AWS services)

### Alternatives Considered

| Option | Pros | Cons | Cost (1K orders/mo) |
|--------|------|------|---------------------|
| **DynamoDB** | Infinite scale, <10ms latency, zero ops | No joins, learning curve | $25/mo |
| **Aurora Serverless v2 (Postgres)** | SQL, joins, familiar | Connection limits, ~50ms latency, cost | $43/mo |
| **Neon Postgres** | Low cost, serverless | Limited scale, external dependency | $15/mo |
| **RDS Postgres (Managed)** | Full Postgres features | Manual scaling, $85/mo minimum | $85/mo |

---

## Decision

**Use DynamoDB as the primary (source of truth) data store** for all writes and transactional reads.

**Single-Table Design**: One DynamoDB table (`PrintXpressMain`) with composite PK/SK keys.

**On-Demand Capacity Mode**: Pay-per-request pricing (auto-scales without throttling).

**Replication**: DynamoDB Streams → Transform Lambda → Postgres replica (for analytics/joins).

---

## Rationale

### Why DynamoDB Over Aurora/RDS Postgres?

**1. Infinite Horizontal Scale (Future-Proof)**
- DynamoDB auto-scales to any traffic level (millions of requests/second)
- Aurora hits connection limits (~100 per ACU) at moderate scale
- RDS requires manual vertical scaling (upgrade instance types)

**2. Consistent Sub-10ms Latency**
- DynamoDB: p99 latency <10ms at any scale
- Aurora: p99 latency 20-50ms (network + query execution)
- **Impact**: 5x faster reads/writes for cart operations, checkout

**3. Zero Operational Overhead**
- DynamoDB: No patching, no index rebuilds, no VACUUM
- Aurora: Occasional maintenance windows, index fragmentation
- **Savings**: ~10 hours/month of DBA work (at scale)

**4. Event-Driven Architecture**
- DynamoDB Streams: Native change data capture (CDC) for replication
- Aurora: Requires custom triggers or CDC tools (Debezium, AWS DMS)
- **Use Case**: Real-time replication to Postgres replica

**5. Cost at MVP Scale**
- DynamoDB: $25/month (500K writes, 2M reads at 1K orders/month)
- Aurora Serverless v2: $43/month (0.5 ACU minimum)
- **Savings**: $18/month (40% cheaper)

### Trade-offs Accepted

**❌ No SQL Joins**
- **Impact**: Cannot run complex analytics queries directly on DynamoDB
- **Mitigation**: Replicate to Postgres replica (Neon) for joins/aggregations
- **Acceptable**: 99% of application queries are simple key-value lookups

**❌ Learning Curve (Single-Table Design)**
- **Impact**: Team must learn composite keys (PK/SK patterns), GSIs
- **Mitigation**: Comprehensive documentation in `data-stores.md`, team training (1 week)
- **Acceptable**: One-time learning investment

**❌ Vendor Lock-In (AWS-Specific)**
- **Impact**: Cannot migrate to GCP/Azure without significant re-architecture
- **Mitigation**: AWS-native is project requirement (stakeholder mandate)
- **Acceptable**: AWS commitment is explicit project constraint

---

## Consequences

### Positive

✅ **Infinite Scale**: Platform can grow to 100K+ orders/month without database changes

✅ **Low Latency**: Sub-10ms reads/writes improve user experience (faster cart, checkout)

✅ **Zero Ops**: No DBA required, no maintenance windows, auto-scaling

✅ **Cost-Effective**: $25/month MVP, scales linearly ($200/month at 10K orders/month)

✅ **Event-Driven**: DynamoDB Streams enable real-time data pipelines

### Negative

⚠️ **No Native Joins**: Complex queries require Postgres replica

**Impact**: Admin dashboard, seller analytics rely on Postgres replica (eventual consistency)

**Mitigation**: Documented in ADR-0003 (Postgres Replica Purpose)

⚠️ **Data Modeling Complexity**: Single-table design requires careful PK/SK planning

**Impact**: Changes to access patterns may require new GSIs (downtime-free, but deployment step)

**Mitigation**: Up-front design (see `data-stores.md`), validate access patterns before implementation

⚠️ **Read-After-Write Consistency (GSI Queries)**
- DynamoDB table queries are strongly consistent
- GSI queries are eventually consistent (~100ms lag)
- **Impact**: Rarely an issue (most queries use table, not GSI)
- **Mitigation**: Use table queries for critical reads (checkout, cart validation)

## Implementation Details

### Table Configuration

```yaml
TableName: PrintXpressMain
BillingMode: PAY_PER_REQUEST
PointInTimeRecovery: ENABLED (35-day retention)
Encryption: AWS_MANAGED (KMS default key)
StreamSpecification: NEW_AND_OLD_IMAGES (for replication)
```

### Access Patterns (Validated)

| Access Pattern | Index | Complexity |
|----------------|-------|------------|
| Get merchant profile | Table (PK/SK) | O(1) |
| Get shop by ID | GSI1 (PK=SHOP#{shopId}) | O(1) |
| List merchant's shops | Table (PK, SK begins_with) | O(n) shops |
| Get product by ID | GSI1 (PK=PRD#{productId}) | O(1) |
| List shop's products | GSI1 (PK=SHOP#{shopId}, SK begins_with PRD#) | O(n) products |
| Get user's cart for shop | Table (PK=U#{userId}, SK=CART#{shopId}) | O(1) |
| List orders by status | GSI3 (PK=STATUS#{status}, SK=TS#...) | O(n) orders (paginated) |

**Validation**: All critical MVP access patterns achievable with 3 GSIs.

### Cost Projection

| Orders/Month | Writes/Month | Reads/Month | Cost |
|--------------|--------------|-------------|------|
| 1,000 | 500K | 2M | $25 |
| 5,000 | 2.5M | 10M | $100 |
| 10,000 | 5M | 20M | $200 |

**Formula**: (Writes × $1.25/million) + (Reads × $0.25/million)

### Hot Partition Mitigation

**Risk**: Popular product (10K+ orders) creates hot partition (PK=PRD#{productId} overwhelmed)

**Mitigation** (if needed at scale):
1. Write sharding: Append random suffix to PK (`PRD#{productId}#0` through `PRD#{productId}#9`)
2. Scatter-gather: Query all shards in parallel, merge results
3. Cost: 10x queries, but still <50ms total latency

**When**: Only if single product exceeds 1,000 requests/second (unlikely at MVP scale)

## Migration Path (If Needed)

### Scenario: DynamoDB Costs Exceed Budget

**Trigger**: DynamoDB costs >$500/month (e.g., 50K orders/month with high read traffic)

**Alternative**: Migrate to Aurora Serverless v2 or managed RDS

**Migration Effort**: 6-8 weeks

**Steps**:
1. Run dual-write (DynamoDB + Aurora) for 1 week (validate data consistency)
2. Switch reads to Aurora (gradual rollout, monitor latency)
3. Switch writes to Aurora (blue-green deployment)
4. Decommission DynamoDB (archive data to S3 for backup)

**Cost Impact**: Aurora $400-600/month (4-8 ACU at 50K orders/month)

**Probability**: Low (10%) — DynamoDB pricing is predictable, scales linearly
