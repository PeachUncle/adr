# Helper Module Implementation Workflow

## Context

When implementing new helper modules for the M4300 API, we need a consistent workflow that ensures quality, reliability, and maintainability. This ADR codifies the workflow used for implementing the device helpers as a template for future helper module implementations.

## Decision

We will follow a structured workflow for implementing new helper modules:

### 1. API Validation Phase

```bash
# 1. Test endpoint with curl to verify actual behavior
curl -k -i -X GET https://$M4300_HOST:$M4300_PORT/api/v1/endpoint \
  -H "Authorization: Bearer $TOKEN"

# 2. Document response in m4300_live_api.yaml
openapi: 3.0.0
paths:
  /endpoint:
    get:
      responses:
        '200':
          content:
            application/json:
              schema: # Document actual response
```

### 2. Implementation Phase

1. Create helper module structure:
```python
"""Module docstring explaining purpose."""

from dataclasses import dataclass
from typing import Dict, List, Optional
from ..exceptions import M4300Error

@dataclass
class ResponseType:
    """Response data structure."""
    field1: str
    field2: int

class NewHelper:
    """Helper class docstring."""
    
    def __init__(self, client):
        self._client = client

    async def method_name(self) -> ResponseType:
        """Method docstring with Args/Returns/Raises."""
        try:
            response = await self._client.get("endpoint")
            data = response.get("key", {})
            return ResponseType(
                field1=data["field1"],
                field2=data["field2"]
            )
        except KeyError as e:
            raise M4300Error(f"Invalid response format: {e}")
        except Exception as e:
            raise M4300Error(f"Operation failed: {e}")
```

2. Implement unit tests:
```python
@pytest.mark.asyncio
async def test_method_success(helper, mock_client):
    """Test successful operation."""
    mock_client.get.return_value = {"key": {
        "field1": "value1",
        "field2": 123
    }}
    
    result = await helper.method_name()
    
    assert isinstance(result, ResponseType)
    assert result.field1 == "value1"
    assert result.field2 == 123

@pytest.mark.asyncio
async def test_method_error(helper, mock_client):
    """Test error handling."""
    mock_client.get.side_effect = Exception("API Error")
    
    with pytest.raises(M4300Error) as exc_info:
        await helper.method_name()
    assert "Operation failed" in str(exc_info.value)
```

3. Implement integration tests:
```python
@pytest.mark.integration
@pytest.mark.live_switch
@pytest.mark.asyncio
async def test_method_live(m4300_client):
    """Test with live switch."""
    client = await m4300_client
    async with client:
        helper = NewHelper(client)
        result = await helper.method_name()
        
        assert isinstance(result, ResponseType)
        assert isinstance(result.field1, str)
        assert isinstance(result.field2, int)
```

### 3. MCP Integration Phase

1. Add tool to MCP server:
```typescript
case 'new_tool':
  return {
    content: [{ type: 'text', text: JSON.stringify({
      field1: "value1",
      field2: 123
    })}]
  };
```

2. Add tool tests:
```typescript
it('should handle new_tool', async () => {
  const response = await server.handleCallTool('new_tool') as CallToolResponse;
  expect(response.content[0].text).to.include('value1');
});
```

### 4. Documentation Phase

1. Update API documentation with any discrepancies found
2. Add helper module documentation
3. Add configuration examples
4. Document error cases

## Validation Checklist

Before considering a helper module complete, verify:

- [ ] API behavior validated with curl
- [ ] Live API responses documented
- [ ] Helper module implemented with:
  - [ ] Type hints
  - [ ] Docstrings
  - [ ] Error handling
  - [ ] Input validation
- [ ] Tests implemented:
  - [ ] Unit tests
  - [ ] Integration tests
  - [ ] Error cases
  - [ ] Input validation
- [ ] MCP integration:
  - [ ] Tool exposed
  - [ ] Tests passing
  - [ ] Error handling
- [ ] Documentation:
  - [ ] API discrepancies noted
  - [ ] Helper docs complete
  - [ ] Examples provided
  - [ ] Error cases documented

## Consequences

### Positive

- Consistent quality across helper modules
- Comprehensive testing coverage
- Reliable API documentation
- Clear implementation pattern
- Maintainable code structure

### Negative

- More upfront work required
- Longer implementation time
- More files to maintain

## Status

Accepted
