# ADR-0001: 3MF Strategy (Manual XML vs Library)

Date: 2025-09-13
Status: Draft

## Context

We need to export (and minimally import) 3MF files containing:

- Multiple mesh objects (parts) with build items
- Vertex colors (palette + per-triangle / per-vertex mapping simplified to per-vertex color extension)
- Embedded palette / AMS metadata JSON (future: filament mapping)
- Deterministic hashing for reproducibility (topology + palette influencing cache / IDs)

Existing Python ecosystem options:

1. `py3mf` / `python-3mf`: Provide higher-level object model, but:
   - Less control over raw XML ordering (determinism risk without auditing)
   - Additional dependency footprint; some packages unmaintained / slower release cadence
   - Harder to embed custom metadata file names or experimental extensions without upstream changes
2. Manual construction: build XML parts (model.model, resources, build) and zip them with required `[Content_Types].xml`.
   - Complete control over ordering, IDs, and stable formatting
   - Easy to embed additional files (JSON metadata) deterministically
   - Lower dependency surface
   - Slightly more maintenance burden (must ensure spec compliance for extended features later)

Constraints & Goals (Milestone 1 / near-term):

- Only need a constrained subset of 3MF (triangular meshes, vertex colors, basic build section)
- Deterministic output is critical for hashing + caching
- Performance acceptable with pure Python for small-medium meshes
- Simplicity & auditability favored over abstraction

Future Needs (Milestone 2+):

- Material / multi-color slot mapping aligned with AMS spool allocation
- Potential support structure hints (orientation, support volume metrics)
- Texture / UV maps (optional) and segmentation-derived color indexes
- Optional compression tuning and large mesh scaling

## Decision

Adopt manual XML + ZIP assembly for 3MF export/import in early milestones.

Rationale:

- Deterministic control: stable ordering of vertices, triangles, and metadata
- Easier to embed custom JSON (palette, AMS plan) without upstream library constraints
- Reduced dependency risk; no waiting for upstream fixes
- Current feature scope small enough that manual code remains concise

## Alternatives Considered

- Using `py3mf` directly: Higher abstraction but harder to guarantee deterministic ordering; less transparent for contributors unfamiliar with library internals.
- Using a hybrid approach (manual read, library write): Adds complexity and mental overhead; inconsistent conventions.
- Deferring 3MF entirely in favor of OBJ + sidecar: Would block color/material pipeline and multi-part build planning.

## Consequences

Positive:

- Predictable, hash-stable outputs facilitate caching & reproducibility
- Lean runtime dependency list
- Rapid iteration for experimental metadata (support metrics, segmentation maps)

Negative / Risks:

- Must self-maintain correctness as we add: multiple color groups, textures, potential lattice/hollow features
- Potentially duplicating work solved in libraries (validation, advanced materials, slicing hints)

## Mitigations / Follow-ups

- Add validation tests comparing against a reference library or known-good slicer load (CI smoke test opening/export round trip)
- Document supported 3MF subset explicitly (README section)
- Modularize XML assembly to ease swap to library later if needed
- Revisit this ADR once: (a) advanced material/texture needs emerge, or (b) maintenance burden rises

## Reference Implementation Points

- `core/export/three_mf.py`: writer constructs XML strings and zips
- `core/export/three_mf_reader.py`: minimal tolerant XML parsing for tests
- Vertex ordering sorted; palette / metadata embedded as extra file `metadata/palette.json` (future additional files)

## Status Review Criteria

Revisit when ANY of:

- Texture maps required (image relationship parts)
- Need for complex materials (composite, multi-property) arises
- Performance concerns; serialization cost >5% of end-to-end pipeline time on typical models

## Appendix: Determinism Practices

- Sort faces by (min_index, max_index, third_index) for stability
- Explicit numeric formatting for floats (fixed precision) if/when needed
- Stable UUID/hash derived names for objects (not random)
