# ADR-0002: ODS Parsing and Container Strategy

- Status: Accepted
- Date: 2025-12-08

## Context

`odsview-cli-python` needs to load `.ods` (LibreOffice Calc) workbooks in
order to render them as terminal tables. The long-term vision includes:

- Handling **plain** (unencrypted) `.ods` files reliably.
- Eventually supporting **encrypted** `.ods` files where the encryption
  metadata is described in `META-INF/manifest.xml`.
- Keeping the tool **minimal and portable**, suitable for SSH and
  constrained environments.
- Preserving a clear separation of concerns between:
  - Opening the ZIP container and handling encryption.
  - Interpreting ODF XML into sheets/rows/cells.

Several options exist for working with `.ods` in Python:

1. Use a higher-level `.ods` convenience library such as `ezodf`.
2. Use a general ODF library such as `odfpy`.
3. Use `pandas.read_excel(..., engine="odf")` with `odfpy`.
4. Use the `pyexcel-ods*` family.
5. Implement our own `.ods` reader on top of `zipfile` and XML.

This ADR selects a strategy that balances **minimal dependencies**,
**future encrypted support**, and **maintainability**.

## Decision

We adopt the following strategy:

1. **Use `odfpy` as the primary ODF/ODS document model library.**
2. Introduce an explicit separation between:
   - `odsview.container`: responsible for ZIP-level access,
     `META-INF/manifest.xml` parsing, and (future) encryption/decryption.
   - `odsview.workbook`: responsible for building a logical workbook
     abstraction (sheets, rows, cells) on top of `odfpy`.
3. Treat encryption/decryption as an explicit concern of the container
   layer, which may in the future depend on a separate crypto library
   (e.g. `cryptography`), not on `odfpy` itself.

At this stage we will only implement **plain (unencrypted) `.ods`**
loading, but the interfaces are designed to accommodate encrypted
workbooks in later milestones.

## Rationale

### Why `odfpy`?

- **Standards-oriented**: `odfpy` works directly with the ODF XML
  elements, including those used in `META-INF/manifest.xml`. This makes
  it well-suited for introspecting and manipulating metadata related to
  encryption algorithms, salts, iteration counts, etc., when we get
  there.
- **Long-term compatibility**: Being close to the ODF spec reduces the
  risk that future `.ods` producers (LibreOffice, other tools) generate
  structures the library cannot represent. We avoid depending on a
  thinner convenience layer that might not evolve with the spec.
- **Clear responsibility split**: By keeping `odfpy` focused on the
  document model while our own `odsview.container` handles the ZIP and
  encryption aspects, we maintain a clean architecture that is easier to
  reason about and test.

### Why not `ezodf`?

- `ezodf` provides a convenient, higher-level spreadsheet API but is
  less focused on exposing the full ODF structure, especially
  `META-INF/manifest.xml` and encryption metadata.
- It is more tightly coupled to an already-decrypted `.ods` view; for
  encrypted support we would still need a separate container/encryption
  layer, at which point `ezodf` adds an extra abstraction without
  strongly helping with the core encrypted use case.
- Maintenance activity for `ezodf` appears lower, making it a slightly
  riskier dependency for a long-lived tool whose primary job is reading
  `.ods` files.

### Why not `pandas` + `odf` engine?

- `pandas` (and its dependencies such as `numpy`) are significantly
  heavier than we want for a **minimal, SSH-friendly CLI**.
- While convenient for data analysis, a DataFrame-centric API is not
  necessary for a read-only viewer whose first concern is streaming rows
  to a terminal.
- Encryption handling would still require a lower-level layer; `pandas`
  does not help with reading manifests or encryption metadata.

### Why not `pyexcel-ods*`?

- The `pyexcel` ecosystem provides convenient abstractions for spreadsheet
  data but introduces additional indirection and plugin mechanisms.
- For this single-purpose CLI, that additional complexity is not
  justified compared to using `odfpy` directly.
- As with the other high-level options, encryption would still require a
  separate container/encryption layer beneath `pyexcel`.

### Why not implement our own `.ods` reader?

- The ODF/ODS formats are non-trivial. Implementing a correct and robust
  reader on top of `zipfile` and XML would be a substantial undertaking,
  especially when considering:
  - Cell addressing, repeated rows/columns, merged cells.
  - Data types (strings, numbers, dates, booleans).
  - Real-world corner cases from diverse generators.
  - Encryption algorithms and key derivation as described in the
    manifest.
- We would own all correctness and security risks, with limited
  opportunity to leverage community knowledge.
- The testing surface would grow very large; we would need a curated
  corpus of `.ods` files (plain and encrypted) to reach reliability
  comparable to existing libraries.

Using `odfpy` allows us to stand on the shoulders of an existing
standards-focused implementation while keeping tighter control over the
container and encryption logic.

## Consequences

- **Dependencies**:
  - We will add `odfpy` as a runtime dependency in `pyproject.toml`.
  - Future encrypted support will likely introduce a crypto dependency
    (e.g. `cryptography`), but this will be justified in a separate ADR
    when implemented.
- **Architecture**:
  - `odsview.container` will own ZIP and manifest handling and will be
    responsible for deciding whether a file is encrypted, and if so,
    whether we can decrypt it.
  - `odsview.workbook` will provide a stable interface over `odfpy`
    objects, making it possible to change internal details (or even
    substitute another ODF library in the future) behind that boundary.
- **Testing**:
  - Early tests will focus on plain `.ods` workbooks: listing sheets and
    reading basic cell values.
  - Later tests will cover detection of encrypted files and clear
    diagnostic messages when decryption is not yet supported or fails.
- **Future changes**:
  - If `odfpy` were to become unsuitable, a future ADR could introduce a
    different ODF library behind the same `odsview.workbook` interface
    without affecting the CLI or container/encryption logic.

As of the initial implementation of this ADR:

- `odsview.container.open_ods_container(path)` validates the container
  and provides access to `content.xml`.
- `odsview.workbook.load_workbook(path)` uses `odfpy` to load the ODS
  document and exposes a lightweight `Workbook` abstraction.
- `Workbook.sheets` returns an ordered list of sheet names.
- `tests/test_workbook.py` and the fixture `tests/fixtures/simple.ods`
  exercise the plain, unencrypted `.ods` path end to end.
- Encryption detection and decryption remain future work under this ADR
  and will be specified and implemented in follow-on changes once we
  select concrete mechanisms and dependencies.
