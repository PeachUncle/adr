# 📘 ADR-001 — Manifest Resolver Placement & Phase Boundaries

**Architecture Decision Record (ADR)**
**ADR ID:** ADR-001-MANIFEST-RESOLVER
**Status:** ✅ ACCEPTED & VERIFIED
**Date:** 2025-12-31
**Verified:** 2026-01-01
**Deciders:** Kernel / Platform Architecture (NexusCanon)

---

## 1. Context

The AI-BOS architecture defines a strict separation of concerns:

- **Kernel (L0)**: semantic constitution, immutable, infrastructure-agnostic
- **Manifest Layer**: auditable usage contract derived from Kernel
- **Runtime (Apps / APIs)**: execution, caching, tenancy, performance

The original plan proposed implementing a **Manifest Resolver** inside the Kernel SDK (`@aibos/kernel`) using dependency injection for data access. During Phase 1 execution, the resolver was instead implemented inside the **Portal App runtime** with direct Supabase integration and caching.

---

## 2. Decision

**The Manifest Resolver SHALL live in the application runtime (apps/portal) for Phase 1**, while the Kernel remains restricted to:

- manifest schema (Zod)
- validation helpers
- semantic constants

The resolver implementation includes:

- direct Supabase access
- LRU caching (TTL-based)
- tenant-aware resolution

---

## 3. Rationale

### 3.1 Kernel Constitutional Law

The Kernel is constitutionally forbidden from importing:

- database clients
- caching libraries
- runtime infrastructure

Placing the resolver inside the Kernel would violate this law or require complex runtime injection.

### 3.2 Performance Requirements

The PRD defines p95 latency targets (<50ms) for manifest resolution. Achieving this requires:

- in-process caching
- locality to the runtime

These requirements are best satisfied at the application layer.

### 3.3 Phase-Appropriate Pragmatism

Phase 1 prioritizes:

- system connectivity
- enforceable governance
- real runtime behavior

Portability and SDK purity are deferred to Phase 2 once behavior is proven.

## 5. Consequences

### Positive

- ✅ Immediate Supabase connectivity
- ✅ Deterministic runtime behavior
- ✅ Cache-enabled performance
- ✅ Kernel purity preserved

### Negative / Trade-offs

- ⚠️ Resolver is coupled to Supabase
- ⚠️ Logic is not yet reusable across apps

These trade-offs are **explicit, intentional, and reversible**.

---

## 6. Future Direction (Phase 2)

In Phase 2, the architecture will converge toward:

```
@aibos/kernel
 └─ mergeManifests(base, overrides)   // pure, stateless

apps/*
 ├─ fetchManifestChain()
 └─ ManifestResolver (glue + cache)
```

This refactor will be mechanical and low-risk because merge logic is already clean and isolated.

---

## 7. Phase Boundaries

### Phase 1 (P1) — Executable Governance ✅ CURRENT

**Goal:** Enforce Kernel semantics at runtime with deterministic behavior.

#### In Scope (P1)

| Component                      | Status | Location                               |
| ------------------------------ | ------ | -------------------------------------- |
| Kernel semantic constants      | ✅     | `packages/kernel/src/concepts.ts`      |
| Kernel manifest Zod schema     | ✅     | `packages/kernel/src/manifest.ts`      |
| Manifest registry tables       | ✅     | Supabase: `sys_manifests`, etc.        |
| Manifest Resolver (runtime)    | ✅     | `apps/portal/lib/manifest-resolver.ts` |
| L1→L2→L3 restrict-only merge   | ✅     | Resolver `mergeManifests()`            |
| CRUD-S (soft delete semantics) | ✅     | Schema + policies                      |
| API-level enforcement          | 🔲     | Next: middleware                       |
| Audit linkage                  | ✅     | `sys_manifest_audit`                   |

#### Out of Scope (P1)

- ❌ Kernel-level resolver
- ❌ Multi-app reuse of resolver
- ❌ Cross-runtime portability
- ❌ OpenMetadata integration
- ❌ UI-based manifest editors

---

### Phase 2 (P2) — SDK Consolidation & Portability

**Goal:** Extract pure logic into Kernel SDK for reuse and formalization.

#### Planned Additions (P2)

- Kernel-level `mergeManifests()` API
- Abstract `ManifestFetcher` interface
- App-level adapters (Supabase, future providers)
- Shared resolver package (optional)
- Formal ADR-driven refactor

#### Explicit Non-Goals (P2)

- ❌ Changing manifest semantics
- ❌ Weakening restriction laws
- ❌ Allowing downstream redefinition

---

## 8. Canonical Phase Statement

> **Phase 1 proves governance works.
> Phase 2 makes governance portable.**
