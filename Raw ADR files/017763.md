# ADR-001: Saga Pattern - Orchestration vs Choreography for Visit Creation

**Status:** Accepted  
**Date:** 2025-10-07  
**Decision Makers:** Architecture Team  
**Context:** Distributed transaction management across microservices for visit creation

## Context and Problem Statement

The Spring PetClinic microservices application requires distributed transaction management for visit creation, which involves coordination between three microservices:

1. **Customers Service** - Validates customer and pet existence
2. **Vets Service** - Manages vet availability and reservations  
3. **Visits Service** - Creates and manages visit records

The challenge is ensuring data consistency across these services while maintaining system resilience, performance, and maintainability. Two primary saga pattern approaches were considered: **Orchestration** and **Choreography**.

## Decision Drivers

### Functional Requirements
- Atomic visit creation across multiple services
- Compensation for partial failures
- Idempotent operations to handle message redelivery
- Support for timeout and retry mechanisms
- Audit trail for transaction states

### Non-Functional Requirements
- **Reliability:** Handle network partitions and service failures gracefully
- **Performance:** Minimize latency for visit creation operations
- **Scalability:** Support increasing transaction volumes
- **Maintainability:** Clear understanding of transaction flows
- **Observability:** Monitor saga execution and identify bottlenecks
- **Complexity:** Balance between functionality and implementation complexity

## Considered Options

### Option A: Saga Orchestration Pattern

**Description:** A centralized saga orchestrator service manages the entire transaction flow, explicitly calling each microservice and handling compensations.

**Architecture:**
```
API Gateway → Saga Service → [Customers, Vets, Visits] Services
                ↓
        Message Queue (Events)
```

**Pros:**
- ✅ **Centralized Control:** Single point of coordination makes flow explicit and easier to understand
- ✅ **Clear Transaction Boundaries:** Well-defined saga states and transitions  
- ✅ **Simplified Debugging:** All coordination logic in one place
- ✅ **Better Error Handling:** Centralized error management and compensation logic
- ✅ **Timeout Management:** Easy to implement global timeouts and retries
- ✅ **Audit Trail:** Complete transaction history in saga store
- ✅ **Testability:** Easier to unit test coordination logic
- ✅ **Backwards Compatibility:** Existing services don't need saga-specific modifications

**Cons:**
- ❌ **Additional Service:** Introduces another service to maintain
- ❌ **Single Point of Failure:** Orchestrator failure affects all sagas
- ❌ **Service Coupling:** Orchestrator must know about all participating services
- ❌ **Scalability Bottleneck:** All coordination goes through orchestrator

### Option B: Saga Choreography Pattern

**Description:** Each microservice publishes domain events and reacts to events from other services, with no central coordinator.

**Architecture:**
```
API Gateway → Customers Service → Events → Vets Service → Events → Visits Service
                    ↑                                                    ↓
                    ←——————————— Compensation Events ←——————————————————
```

**Pros:**
- ✅ **Loose Coupling:** Services only depend on events, not specific services
- ✅ **High Availability:** No single point of failure
- ✅ **Scalability:** Distributed processing, no central bottleneck
- ✅ **Service Autonomy:** Each service manages its own saga steps
- ✅ **Event-Driven Architecture:** Natural fit for microservices

**Cons:**
- ❌ **Complex Flow Understanding:** Transaction flow scattered across services
- ❌ **Difficult Debugging:** Hard to trace complete saga execution
- ❌ **Cyclic Dependencies:** Risk of circular event chains
- ❌ **Error Handling Complexity:** Distributed error management
- ❌ **Testing Complexity:** Integration testing requires all services
- ❌ **Service Modifications:** Each service needs saga-aware implementation

## Decision Outcome

**Chosen Option: Saga Orchestration Pattern (Option A)**

### Rationale

The **Orchestration pattern** was selected based on the following key factors:

1. **Current Team Expertise:** The development team has more experience with centralized coordination patterns
2. **System Complexity:** The PetClinic domain is relatively simple with clear business workflows
3. **Service Maturity:** Existing services can be used as-is without saga-specific modifications
4. **Operational Requirements:** Strong need for observability and debugging capabilities
5. **Transaction Complexity:** Visit creation has clear sequential dependencies that map well to orchestration

### Implementation Details

#### Saga Orchestrator Service
- **Technology Stack:** Spring Boot with JPA for state persistence
- **State Machine:** Explicit saga states with defined transitions
- **Message Queue:** RabbitMQ for event publishing and asynchronous processing
- **Persistence:** PostgreSQL/MySQL for saga transaction storage

#### Saga States
```java
STARTED → CUSTOMER_VALIDATED → VET_RESERVED → VISIT_CREATED → COMPLETED
    ↓              ↓                ↓              ↓
CUSTOMER_     VET_RESERVATION_  VISIT_CREATION_   ↓
VALIDATION_        FAILED         FAILED          ↓
FAILED             ↓              ↓              ↓
    ↓              ↓              ↓              ↓
COMPENSATING_CUSTOMER_VALIDATION ← ← ← ← ← ← ← ← ←
    ↓
  FAILED
```

#### Compensation Strategy
- **Reverse Order:** Compensations executed in reverse order of successful operations
- **Idempotent Operations:** All operations designed to be safely retryable
- **Graceful Degradation:** Compensation failures logged but don't block saga completion

#### Resilience Patterns
- **Circuit Breaker:** Protect against cascading failures (Resilience4j)
- **Retry Logic:** Exponential backoff for transient failures
- **Timeout Handling:** Global saga timeouts with automatic cleanup
- **Dead Letter Queues:** Handle permanently failed messages

### Trade-offs Accepted

1. **Additional Service Overhead:** Accepted the cost of maintaining an additional service for better control and observability
2. **Orchestrator Dependency:** Accepted potential single point of failure, mitigated by high availability deployment
3. **Service Coupling:** Accepted orchestrator knowledge of all services for explicit transaction control

## Consequences

### Positive Consequences
- **Improved Reliability:** Clear compensation logic ensures data consistency
- **Better Observability:** Complete saga execution visibility through centralized logging
- **Easier Maintenance:** Business logic changes isolated to orchestrator service
- **Faster Development:** Existing services require minimal changes

### Negative Consequences
- **Service Proliferation:** Additional service to deploy and monitor
- **Potential Bottleneck:** Orchestrator could become performance bottleneck under high load
- **Operational Complexity:** Need to ensure orchestrator high availability

### Mitigation Strategies
1. **High Availability Deployment:** Deploy orchestrator in clustered mode
2. **Performance Monitoring:** Implement comprehensive metrics and alerting
3. **Graceful Degradation:** Design fallback mechanisms for orchestrator failures
4. **Load Testing:** Regular performance testing to identify bottlenecks

## Compliance

This decision ensures compliance with:
- **ACID Properties:** Through saga compensation mechanisms
- **Microservices Principles:** While maintaining service autonomy where possible
- **Event-Driven Architecture:** Through RabbitMQ event publishing
- **Observability Standards:** Through structured logging and metrics
