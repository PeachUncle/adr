# ADR-002: Discretization Strategy

**Status**: DECIDED  
**Date**: 2025-12-18  
**Context**: Foundational architecture

## Decision

**Discretization is mathematics, not I/O.**

All discretization — from continuous math to pixel grid — happens in Lean 4 with proofs. The pixel buffer `Fin w × Fin h × Color` is an algebraic structure, not a rendering artifact.

## The Insight

Pixels are not "just display." They are the **fundamental quanta of our simulated space**.

```
Continuous Space (ℝ³)
        │
        │  Mathematical discretization (resolution = algebraic parameter)
        ▼
Discrete Space (Fin w × Fin h × Fin d)  ← This IS algebra
        │
        │  Projection, rasterization (proven algorithms)
        ▼
Pixel Buffer (Fin w × Fin h × Color)    ← This IS algebra
        │
        │  .toByteArray (trivial conversion)
        ▼
Raw Bytes → Rust → Display              ← This is I/O
```

## Rationale

### Why Discretization Must Be Proven

1. **Rasterization algorithms have correctness properties**
   - Bresenham's line: exactly the pixels closest to the ideal line
   - Triangle rasterization: every pixel inside the triangle, none outside
   - These properties can (and should) be proven in Lean 4

2. **Resolution is a type parameter, not a runtime value**
   - `Frame (w : ℕ) (h : ℕ) := Fin w → Fin h → Color`
   - Type system guarantees no out-of-bounds access
   - Proofs are parameterized by resolution

3. **Discretization errors are mathematical**
   - Aliasing, sampling artifacts are analyzable
   - Anti-aliasing is a proven filtering operation
   - Error bounds can be formally stated

4. **Lean 4's Fin type is perfect**
   - `Fin n` is the type of natural numbers less than n
   - Bounds checking is eliminated by the type system
   - Mathlib has extensive support

### Why Rust Does Zero Computation

1. **Proof boundary**: If Lean proves the buffer correct, and Rust only copies, display is correct
2. **Minimal attack surface**: Less Rust = less to go wrong outside proofs
3. **Trivial verification**: ~100 lines of buffer copy is inspectable by humans

## Mathlib Types We Use

| Type | Definition | Our Usage |
|------|------------|-----------|
| `Fin n` | `{ val : ℕ // val < n }` | Pixel coordinates (x : Fin w, y : Fin h) |
| `ZMod n` | Integers mod n | Wraparound coordinates (if needed) |
| `Fin n → α` | Function from finite domain | Row of pixels |
| `Fin m → Fin n → α` | 2D grid | Pixel buffer |

## Resolution as Type Parameter

Resolution is NOT a runtime value — it's part of the type:

```lean
-- Resolution is at the type level
def Frame (w h : ℕ) := Fin w → Fin h → Color

-- Operations are proven for ANY resolution
theorem bresenham_correct (w h : ℕ) (p1 p2 : Fin w × Fin h) :
  ∀ p ∈ bresenham_line p1 p2, closest_to_ideal_line p1 p2 p := ...
```

This means:
- Proofs hold for all resolutions
- No runtime bounds checking needed (type-guaranteed)
- Resolution changes require recompilation (intentional — it's a fundamental parameter)

## Consequences

### Positive
- Rasterization algorithms are proven correct
- Pixel buffer is type-safe (no out-of-bounds possible)
- Entire rendering pipeline is mathematical
- Rust layer is trivially simple (~100 lines)

### Negative  
- Resolution is compile-time, not runtime (acceptable for our use case)
- More work in Lean 4 (but that's where rigor belongs)
- Learning curve for dependent types

### Mitigations
- Use Mathlib's existing Fin infrastructure
- Start with simple algorithms (points, lines) before complex rasterization
- Document all proofs clearly

## Implementation Plan

### Layer 0: Discrete Foundation
```lean
-- Use Mathlib's Fin
import Mathlib.Data.Fin.Basic

-- Define our pixel coordinate type
abbrev PixelX (w : ℕ) := Fin w
abbrev PixelY (h : ℕ) := Fin h

```
