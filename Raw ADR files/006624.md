# ADR-001: Use Qdrant for Vector Storage

## Status
**Accepted** - January 2, 2026

## Context

Axiom Intelligence Studio requires a vector database for semantic search capabilities. The system needs to:
- Store document embeddings for similarity search
- Scale to millions of vectors
- Support metadata filtering for RBAC
- Provide fast retrieval (sub-100ms)
- Be cost-effective for a portfolio project

### Options Considered

| Option | Type | Pros | Cons |
|--------|------|------|------|
| **Qdrant** | Dedicated Vector DB | Purpose-built, filtering, open source, cloud + self-hosted | Additional service to manage |
| **pgvector** | PostgreSQL Extension | Single database, familiar SQL | Limited filtering, slower at scale |
| **Pinecone** | Managed Service | Fully managed, fast | Expensive, vendor lock-in |
| **Weaviate** | Dedicated Vector DB | GraphQL API, modules | More complex setup |
| **Chroma** | Embedded | Simple, local-first | Not production-ready at scale |

## Decision

Use **Qdrant** as the primary vector database.

### Rationale

1. **Purpose-Built Performance**: Qdrant is optimized for vector search with HNSW indexing, providing consistent sub-100ms queries.

2. **Rich Filtering**: Supports metadata filtering at query time, essential for RBAC:
   ```python
   # Filter by access_level during search
   results = client.search(
       collection_name="documents",
       query_vector=embedding,
       query_filter=Filter(
           must=[
               FieldCondition(key="access_level", match=MatchValue(value="public"))
           ]
       )
   )
   ```

3. **Deployment Flexibility**:
   - Docker for local development
   - Railway template for staging/production
   - Qdrant Cloud available if needed

4. **Portfolio Visibility**: Using a dedicated vector DB demonstrates understanding of modern AI infrastructure, more impressive than "just using pgvector."

5. **Open Source**: No vendor lock-in, full control over data.

6. **Active Community**: Well-maintained with LangChain, LlamaIndex integrations.

## Consequences

### Positive
- Fast, scalable vector search out of the box
- Native support for payload filtering (RBAC)
- Clear separation of concerns (SQL DB vs Vector DB)
- Impressive tech choice for portfolio

### Negative
- Additional service to deploy and monitor
- Need to manage Qdrant separately from PostgreSQL
- Learning curve for Qdrant-specific APIs

### Mitigations
- Docker Compose handles local complexity
- Railway template simplifies cloud deployment
- Use LlamaIndex/LangChain abstractions to minimize direct Qdrant code

## Implementation Notes

### Local Development
```yaml
# docker-compose.yml
qdrant:
  image: qdrant/qdrant:latest
  ports:
    - "6333:6333"
  volumes:
    - qdrant_data:/qdrant/storage
```

### Production (Railway)
Deploy via Railway's Qdrant template or Docker image.

### Collection Schema
```python
from qdrant_client.models import Distance, VectorParams

client.create_collection(
    collection_name="document_chunks",
    vectors_config=VectorParams(
        size=1536,  # OpenAI embedding dimension
        distance=Distance.COSINE,
    ),
)
```
