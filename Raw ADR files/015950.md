# ADR-0003: Decision to Implement Native PTY

**Status**: Accepted  
**Date**: 2025-01-XX  
**Deciders**: Architecture Team  
**Tags**: pty, i/o, async, platform-abstraction, decision

## Context

We've been struggling with `portable_pty` API limitations:
- Cannot extract writer from boxed trait object
- Resorting to unsafe code to access file descriptors
- Writer lifecycle management is complex
- Limited async support
- API doesn't expose what we need

## Decision

**We will drop `portable_pty` and implement native PTY using:**
- `nix` crate for Unix/macOS PTY operations
- Windows ConPTY API for Windows (future)
- `tokio::io::unix::AsyncFd` for async I/O
- Enum-based platform abstraction

## Rationale

### Why Native?

1. **Full Control**: No API limitations - we own the implementation
2. **Proper Async**: Direct `tokio::io` integration, not workarounds
3. **Type Safety**: Enum-based, no trait object issues
4. **Performance**: Direct syscalls, zero unnecessary abstractions
5. **Maintainability**: Clear, atomic, modular code structure
6. **Production Ready**: Alacritty uses native, proving it works

### Why Not portable_pty?

1. **API Limitations**: Can't get writer from trait object
2. **Unsafe Workarounds**: We're using unsafe code to extract FDs
3. **Lifecycle Issues**: Writer management is complex
4. **Async Gaps**: Limited async support, requires workarounds
5. **Not Our Code**: We can't fix the API issues

## Implementation Plan

### Phase 1: macOS/Unix (Immediate)
- Use `nix::pty::openpty` for PTY creation
- Use `tokio::io::unix::AsyncFd` for async I/O
- Implement proper read/write with full async support
- Follow existing `native_example.rs` pattern

### Phase 2: Linux (Same as macOS)
- Unix implementation works on Linux
- Test and verify platform differences

### Phase 3: Windows (Future)
- Implement ConPTY API
- Use `windows-rs` or similar
- Enum-based abstraction handles this cleanly

## Architecture

```rust
pub enum Pty {
    Unix(UnixPty),      // nix + tokio::io::unix::AsyncFd
    Windows(WindowsPty), // ConPTY + tokio (future)
}

pub struct UnixPty {
    master: AsyncFd<RawFd>,
    slave_path: PathBuf,
    child: Option<tokio::process::Child>,
}
```

## Consequences

### Positive
- Full control over PTY lifecycle
- Proper async/await throughout
- No API limitations
- Better performance
- Type safety
- Fits our atomic, modular architecture

### Negative
- ⚠️ More code to maintain (~500-1000 lines)
- ⚠️ Platform-specific implementations
- ⚠️ Need to test on all platforms
- ⚠️ Windows implementation deferred

### Mitigations
- Use `#[cfg]` for platform code
- Comprehensive tests
- Clear documentation
- Follow existing atomic file structure
- Reuse `native_example.rs` as starting point

## Migration Path

1. **Keep portable_pty temporarily** - Don't break existing code
2. **Implement native alongside** - New `native` module
3. **Switch over** - Update `Pty::new()` to use native
4. **Remove portable_pty** - Clean up dependencies

## Success Criteria

- [ ] PTY creation works on macOS
- [ ] Reading from PTY works (async)
- [ ] Writing to PTY works (async)
- [ ] Shell spawning works
- [ ] Resize works
- [ ] No unsafe code (except where necessary for syscalls)
- [ ] All tests pass
- [ ] Performance matches or exceeds portable_pty
