# DEC-0010: Determinism Enforcement vs. Semantic Versioning Lifecycle

**Date Created:** 2025-12-20  
**Status:** 📋 **EVALUATION NEEDED**  
**Priority:** Medium (Post-M9 Phase 2, Pre-v1.0.0)

---

## ✅ REVISED DECISION (Paradigm Shift!)

**NEW APPROACH:** **User-Controlled Determinism (Not Author-Controlled)**

### Key Insight (From User Feedback)

> "Determinism is important for the USER of a rulebook, not the author. The user says: render 100 prompts with 'midjourney.v8:fancy_prompts' for latest, or 'midjourney.v8:fancy_prompts@1.0.3' for deterministic."

**This changes everything!**

### The New Model

**Authors:** Use semver naturally (^1.0.0, ~2.3.0)
- No forced exact versions
- Flexible during development
- Marketplace locks on publish

**Users:** Control determinism via command
- `rpg render package:rulebook` → Latest (flexible)
- `rpg render package:rulebook@1.0.3 --seed 42` → Deterministic (locked)

**Marketplace:** Enforces at publish time
- Resolves flexible dependencies to exact
- Creates locked manifest
- Cryptographic signing
- Namespace ownership validation

### Implementation Path

**M9 (Immediate - 2-3 hours):**
- Remove exact-only validation
- Accept semver ranges (^, ~, etc.)
- Add warnings for major version ranges
- Update UI/docs

**M10-M11 (No changes):**
- Continue with flexible dependencies
- Works for development/testing

**M12 (Marketplace - Full solution):**
- Publish locks dependencies
- Cryptographic signatures
- User commands control determinism
- Namespace ownership enforcement

### Benefits

1. **Zero author burden:** Use semver naturally
2. **User control:** Choose determinism when needed
3. **Simple tooling:** No modes, no complexity
4. **Marketplace safety:** Locks + signatures
5. **Industry standard:** Like npm/cargo/etc.

**Next Steps:**
1. Implement semver acceptance in M9 ✅
2. Plan marketplace locking for M12
3. Design cryptographic signing
4. Document user-controlled model

## Problem Statement

We currently enforce **strict determinism at all times** via exact version matching for dependencies (see DESIGN_DECISION_EXACT_VERSION_MATCHING.md). This ensures that the same package with the same seed always produces identical output, which is critical for our design tenets.

**Question:** Are we enforcing determinism **too strictly**? Could we improve developer experience by relaxing determinism during development/draft phases while maintaining strict guarantees for finalized releases?

---

## Current State (Strict Determinism)

### What We Have Now
```yaml
dependencies:
  - package: prompt-gen.common
    version: "1.0.0"  # Exact version required - ALWAYS
```

**Guarantees:**
- ✅ Same package + same seed = same output (always)
- ✅ Deterministic rendering across all engine implementations
- ✅ Reproducible results for users

**Pain Points:**
- ⚠️ Authors must manually update versions for every bug fix
- ⚠️ Can't benefit from non-breaking improvements automatically
- ⚠️ Iterative development requires frequent version updates
- ⚠️ Testing package changes requires updating all dependent packages

---

## Proposed Alternative: Lifecycle-Based Determinism

### Concept: Tie Validation Strictness to Package State

Allow **flexible versioning** during development, enforce **strict determinism** for releases:

```yaml
# Option 1: Package-level mode flag
metadata:
  id: my.package
  version: "0.5.0-draft"  # -draft, -dev, -alpha suffix indicates mode
  
dependencies:
  - package: prompt-gen.common
    version: "^1.0.0"  # Allowed in draft mode
    # Enforced as "1.0.0" in release mode

---

# Option 2: Explicit mode declaration
metadata:
  id: my.package
  version: "0.5.0"
  mode: draft  # draft | release (default: release)

dependencies:
  - package: prompt-gen.common
    version: "^1.0.0"  # Flexible in draft
    # Must be exact in release

---

# Option 3: Semver-based lifecycle
metadata:
  id: my.package
  version: "0.5.0"  # 0.x.x = development, 1.0.0+ = release
  
dependencies:
  - package: prompt-gen.common
    version: "^1.0.0"  # Flexible constraints allowed
    # Engine determines strictness based on dependent version
```

### Semantic Versioning Constraints

Tie determinism requirements to **semantic versioning meaning**:

| Version Type | Breaking Changes | Determinism Requirement | Rationale |
|--------------|------------------|-------------------------|-----------|
| **Major (X.0.0)** | ✅ Allowed | ⚠️ Flexible during X.0.0-alpha/beta | New features, API changes expected |
| **Major (X.0.0 release)** | ✅ Allowed | ✅ **Strict** | Published release must be stable |
| **Minor (X.Y.0)** | ⚠️ Should avoid | ✅ **Strict** | Backward compatible additions only |
| **Patch (X.Y.Z)** | ❌ Not allowed | ✅ **STRICT** | Bug fixes must not break determinism |

**Key Insight:** Patch versions **must** preserve deterministic rendering. Users expect `1.0.0` → `1.0.1` to fix bugs without changing any outputs.

## Use Cases Analysis

### Use Case 1: Package Author Iterating
**Current (Strict):**
```yaml
# my-package v0.1.0
dependencies:
  - package: base
    version: "1.0.0"

# base package gets bug fix → 1.0.1
# Author must:
# 1. Manually change dependency version to "1.0.1"
# 2. Test everything
# 3. Increment my-package to v0.1.1
# 4. Save and reload
```

**Proposed (Flexible in Draft):**
```yaml
# my-package v0.1.0-draft
dependencies:
  - package: base
    version: "^1.0.0"  # Auto-resolves to 1.0.1

# base package gets bug fix → 1.0.1
# Engine automatically uses 1.0.1 on next reload
# Author can test immediately
# Determinism not critical during development
```

### Use Case 2: Published Package Stability
**Current (Strict):**
```yaml
# my-package v1.0.0
dependencies:
  - package: base
    version: "1.0.0"

# User A renders with seed 42 → "red dragon"
# User B renders with seed 42 → "red dragon"
# ✅ Guaranteed identical (deterministic)
```

**Proposed (Strict in Release):**
```yaml
# my-package v1.0.0 (release mode)
dependencies:
  - package: base
    version: "1.0.0"  # Must be exact in release mode

# Even if author wrote "^1.0.0", engine validates:
# - ERROR: Release packages require exact versions
# - Suggestion: Change to version: "1.0.0"

# ✅ Same strict guarantee for releases
```

### Use Case 3: Bug Fix in Dependency
**Current (Strict - Forces Version Bump):**
```yaml
# Scenario: base v1.0.0 has typo in datatype value
# base v1.0.1 fixes typo

# my-package v1.0.0 depends on base "1.0.0"
# Problem: Can't get bug fix without:
#   1. Changing dependency to "1.0.1"
#   2. Bumping my-package to v1.0.1
#   3. Users must update my-package
# Result: Cascade of version updates
```

**Question:** Should patch version bug fixes break determinism?
- **Yes (current):** Even typo fixes change output → need exact version
- **No (proposed):** Allow `^1.0.0` to auto-resolve patches for bug fixes
  - But: This breaks determinism for users who already rendered with 1.0.0
  - Trade-off: Better DX vs. determinism guarantee

## Semantic Versioning Implications

### Strict Interpretation (Current)
```yaml
# Package A v1.0.0 depends on B "1.0.0"
# B releases v1.0.1 (bug fix - typo in value)
# Result: A still uses B v1.0.0
# Impact: Bug remains in A until author explicitly updates
```

**Pros:**
- ✅ Perfect determinism
- ✅ No surprises for users
- ✅ Explicit control

**Cons:**
- ❌ Bug fixes don't propagate
- ❌ Author must manually track dependency updates
- ❌ Version cascade (B v1.0.1 → A v1.0.1 → C v1.0.1)

### Flexible Patch Versions (Proposed Option)
```yaml
# Package A v1.0.0 depends on B "^1.0.0"
# B releases v1.0.1 (bug fix)
# Result: A automatically uses B v1.0.1
# Impact: Bug fixed, but determinism broken for seed 42
```

**Pros:**
- ✅ Bug fixes propagate automatically
- ✅ Less version management burden
- ✅ Better developer experience

**Cons:**
- ❌ Breaks determinism across different resolution times
- ❌ User A (today) and User B (tomorrow) get different outputs
- ❌ Violates core design tenet

## Evaluation Framework

### Questions to Answer

#### 1. **Determinism Scope**
- Q: Must determinism be guaranteed **forever** or just **at a point in time**?
- Current: Forever (same package + seed = same output across years)
- Alternative: Point-in-time (same package + seed = same output **today**)
- Consideration: Lock files could solve this (npm/yarn style)

#### 2. **Development Workflow**
- Q: How much friction is acceptable during package authoring?
- Current: High friction (manual version management)
- Alternative: Low friction (auto-resolution in draft mode)
- Consideration: Most packages are consumed, not authored - optimize for whom?

#### 3. **Semantic Versioning Guarantees**
- Q: Should **patch versions** preserve deterministic output?
  - Yes: Patch = bug fix, should not change any outputs (strict)
  - No: Patch = bug fix, outputs **should** change if they were wrong (flexible)
  - Middle: Depends on type of fix (typo vs. weight adjustment)

#### 4. **Release vs. Draft Distinction**
- Q: Is a mode flag (`draft` vs. `release`) a good UX?
  - Pros: Clear intent, explicit control
  - Cons: Authors might forget to switch, adds complexity
  - Alternative: Infer from version suffix (`-draft`, `-alpha`, `-beta`)

#### 5. **Lock File Solution**
- Q: Would lock files solve this better than lifecycle modes?
```yaml
# package.yaml
dependencies:
  - package: base
    version: "^1.0.0"

# package-lock.yaml (generated, not hand-edited)
resolved:
  base: "1.0.1"
  base.dependencies: {}
```
- Pros: Proven pattern (npm, yarn, cargo)
- Cons: Additional file complexity, resolution algorithm needed

#### 6. **Cross-Engine Consistency**
- Q: If we allow flexible versioning, how do we ensure cross-engine consistency?
- Example: Engine A resolves `^1.0.0` → `1.0.1`, Engine B resolves → `1.0.2`
- Solution: Lock files? Registry with resolution API?

## Proposed Design Options

### Option A: Status Quo (Strict Always)
**Keep exact version matching for all packages, all the time.**

```yaml
dependencies:
  - package: base
    version: "1.0.0"  # Always exact
```

**Verdict:**
- ✅ Simple, predictable, deterministic
- ❌ Poor DX for iterative development
- ✅ Aligns with core design tenet

---

### Option B: Draft Mode (Relaxed During Development)
**Allow flexible constraints in draft mode, enforce exact in release mode.**

```yaml
# Draft phase
metadata:
  version: "0.5.0-draft"  # Suffix indicates mode
  
dependencies:
  - package: base
    version: "^1.0.0"  # Allowed

---

# Release phase (author removes -draft suffix)
metadata:
  version: "0.5.0"  # No suffix = release mode
  
dependencies:
  - package: base
    version: "^1.0.0"  # ERROR: Must be exact in release
```

**Engine Behavior:**
- Draft mode: Resolve `^1.0.0` to latest compatible (1.0.x)
- Release mode: Reject flexible constraints, require exact

**Verdict:**
- ✅ Best of both worlds (flexible dev, strict release)
- ⚠️ Complexity: Two validation modes
- ⚠️ Author must remember to finalize before publishing

---

### Option C: Semver-Based Lifecycle (Inferred Mode)
**Use semantic version to infer mode: 0.x.x = draft, 1.0.0+ = release.**

```yaml
# v0.x.x = Draft (flexible allowed)
metadata:
  version: "0.5.0"
dependencies:
  - package: base
    version: "^1.0.0"  # OK

---

# v1.0.0+ = Release (strict required)
metadata:
  version: "1.0.0"
dependencies:
  - package: base
    version: "^1.0.0"  # ERROR: Must be exact in v1.0.0+
```

**Verdict:**
- ✅ No explicit mode flag needed
- ✅ Follows semver convention (0.x.x = unstable)
- ⚠️ Might surprise authors who use 0.x.x for "stable but early"

---

### Option D: Lock Files (Resolution Snapshot)
**Allow flexible constraints, but pin actual resolutions in lock file.**

```yaml
# package.yaml
dependencies:
  - package: base
    version: "^1.0.0"

# package-lock.yaml (auto-generated)
resolved:
  base:
    version: "1.0.1"
    hash: "sha256:..."
    path: "./packages/base.yaml"
```

**Engine Behavior:**
- If lock file exists: Use pinned versions (deterministic)
- If no lock file: Resolve constraints, generate lock file
- On publish: Lock file must exist

**Verdict:**
- ✅ Industry-standard pattern
- ✅ Determinism via lock file
- ✅ Flexibility via constraints
- ⚠️ Requires resolution algorithm implementation
- ⚠️ Lock file management adds complexity

---

### Option E: Patch-Version Flexibility (Middle Ground)
**Allow patch version auto-resolution, but require exact major.minor.**

```yaml
dependencies:
  - package: base
    version: "1.0.x"  # Auto-resolves to latest 1.0.z
    # Or: "~1.0.0" (tilde = patch-level changes)
```

**Semantic Meaning:**
- Major: Breaking changes allowed
- Minor: New features, backward compatible
- Patch: Bug fixes only (should preserve semantics)

**Question:** Do bug fixes in our domain break determinism?
- Typo fix: "colour" → "color" → ✅ Changes output (intentional fix)
- Weight fix: `weight: 10` → `weight: 1` → ✅ Changes output (intentional fix)
- Logic fix: Rule condition → ✅ Changes output (intentional fix)

**Answer:** Yes, even patch-level fixes change output in our domain.

**Verdict:**
- ❌ Doesn't work for our use case
- Patch versions **do** change outputs (by design, when fixing bugs)
