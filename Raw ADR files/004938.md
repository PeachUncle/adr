# ADR-001: Monorepo Workspace Structure with pnpm

## Status

Accepted

## Date

July 25, 2025

## Context

The Advisory Platform M&A brokerage project requires a scalable architecture to support 7 distinct packages with shared dependencies and coordinated development. We need to choose between:

1. **Monorepo with workspaces** (pnpm/yarn/npm workspaces)
2. **Multi-repo with individual packages** (separate repositories)
3. **Monorepo with build tools** (Nx, Lerna, Rush)

### Requirements

- Support for 7 packages: @advisory/core, @advisory/matching-engine, @advisory/compliance, @advisory/documents, @advisory/api, @advisory/web, @advisory/data-pipeline
- Shared TypeScript configuration and tooling
- Efficient dependency management
- Fast build and test cycles
- Clear package boundaries while enabling code sharing
- Regulatory compliance considerations (audit trails, security isolation)

### Package Architecture

Based on the implementation plan, packages have clear responsibilities:

- `@advisory/core`: Business logic and domain models
- `@advisory/matching-engine`: AI matching algorithms
- `@advisory/compliance`: Regulatory compliance engine
- `@advisory/documents`: Document generation system
- `@advisory/api`: GraphQL/REST API layer
- `@advisory/web`: Next.js frontend
- `@advisory/data-pipeline`: ETL and data processing

## Decision

We will use **pnpm workspaces** for monorepo management.

## Rationale

### Why Monorepo?

1. **Shared Code**: Common business logic, types, and utilities across packages
2. **Coordinated Releases**: Ensure compatibility across all platform components
3. **Developer Experience**: Single repository for easier development and testing
4. **Tooling Consistency**: Shared ESLint, TypeScript, and build configurations
5. **Regulatory Benefits**: Centralized audit trail and dependency management

### Why pnpm over alternatives?

**vs. npm/yarn workspaces:**

- **Performance**: pnpm's hard-link approach reduces disk usage by ~50%
- **Dependency Management**: Strict handling prevents phantom dependencies
- **Speed**: Faster installation and resolution
- **Workspace Protocol**: Better support for workspace: dependencies

**vs. Nx/Lerna/Rush:**

- **Simplicity**: Lighter tooling overhead for initial development
- **Learning Curve**: Team familiarity with package.json-based workflows
- **Flexibility**: Can migrate to advanced build tools later if needed
- **Performance**: pnpm's native workspace support is sufficient for current scale

### Technical Benefits

1. **Dependency Deduplication**: Shared dependencies hoisted to root
2. **Type Safety**: Cross-package TypeScript references
3. **Build Optimization**: Parallel builds with proper dependency ordering
4. **Testing**: Comprehensive cross-package integration testing

## Consequences

### Positive

- Unified development environment and tooling
- Efficient dependency management and reduced disk usage
- Clear package boundaries with shared infrastructure
- Simplified CI/CD pipeline with coordinated testing
- Better audit trail for regulatory compliance

### Negative

- All developers need pnpm installed (vs. npm/yarn)
- Potential for tight coupling between packages if not managed carefully
- Single repository means all code lives in one place (security consideration)
- Build complexity increases with more packages

### Neutral

- Can migrate to more sophisticated build tools (Nx, Rush) later if needed
- Package boundaries require discipline to maintain
- Workspace configuration needs careful management

## Implementation Plan

### Phase 1: Basic Workspace Setup

1. Create `pnpm-workspace.yaml` defining package locations
2. Initialize all 7 packages with basic `package.json` files
3. Set up shared TypeScript configuration in root
4. Configure shared tooling (ESLint, Prettier, Jest)

### Phase 2: Advanced Configuration

1. Implement cross-package TypeScript references
2. Set up build orchestration with proper dependency ordering
3. Configure CI/CD pipeline for workspace
4. Add workspace-specific scripts and tooling

## Security Considerations

- Individual packages can maintain security boundaries through proper imports
- Compliance package will be isolated with minimal external dependencies
- Dependency scanning covers entire workspace from single configuration
- Audit trails maintained at workspace level for regulatory requirements

## Migration Path

If workspace becomes too complex:

1. Can split into separate repositories while maintaining shared tooling
2. Can migrate to Nx or Rush for advanced build orchestration
3. Can use git subtree/submodule for gradual migration
