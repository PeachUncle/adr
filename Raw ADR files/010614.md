# ADR-004: Parallel Execution in workflows4s

**Status**: Proposed

## Question

Can workflows4s handle parallel execution of workflow steps?

## Context

Tripper demonstrates parallel execution in two key areas:
1. **POI Research**: 12 concurrent LLM calls for researching points of interest
2. **Accommodation Search**: Parallel searches across multiple locations

Parallel execution is critical for:
- Performance optimization (reducing total execution time)
- Cost efficiency (faster overall workflow = lower costs)
- Resource utilization (maximizing API throughput)

We need to determine if workflows4s supports parallel step execution and how to implement it.

## Decision

workflows4s **supports parallel execution** through **two complementary approaches**:

1. **`WIO.parallel`** - Parallel workflow steps (logical parallelism)
2. **`WIO.forEach`** - Map over collections with parallel processing
3. **Cats Effect `Parallel[F]`** - Inside steps for concurrent IO operations

**Recommended approach**: Use **`WIO.forEach` + Cats Effect `Parallel[F]`** for POI research pattern.

### Approach 1: WIO.parallel (Parallel Workflow Steps)

Execute multiple independent workflow steps in parallel:

```scala
import TripperWorkflowCtx._

case class POIResearchResult(poi: PointOfInterest, research: ResearchedPOI) extends Event

// Define individual research tasks as workflows
def researchOnePOI(poi: PointOfInterest): WIO[State, Nothing, ResearchedPOI] = WIO
  .runIO[State] { _ =>
    callLLMForResearch(poi).map(result => POIResearchResult(poi, result))
  }
  .handleEvent { (_, event) => event.research }
  .named(s"Research ${poi.name}")

// Parallel execution of multiple tasks
val researchPOIsParallel: WIO[State, Nothing, State] = WIO
  .parallel[State, Nothing, State]
  .apply {
    // Create workflow for each POI
    state.pointsOfInterest.map(poi => researchOnePOI(poi))
  }
  .collectResults { results: Seq[ResearchedPOI] =>
    state.copy(researchedPOIs = results.toList)
  }
  .named("Research All POIs (Parallel)")
```

**Characteristics**:
- ✅ Logical parallelism (clear in BPMN diagrams)
- ⚠️ Physical concurrency depends on runtime (InMemorySyncRuntime = sequential!)
- ✅ Each task is a separate workflow step with events
- ⚠️ Must create workflows dynamically based on state

### Approach 2: WIO.forEach (Map Over Collection)

**Recommended for POI research pattern** - process collection elements:

```scala
case class POIResearched(poi: PointOfInterest, research: ResearchedPOI) extends Event

val researchPOIsForEach: WIO[State, Nothing, State] = WIO
  .forEach { (state: State) => state.pointsOfInterest.toSet }
  .apply { (poi: PointOfInterest) =>
    // Workflow for single POI
    WIO.runIO[PointOfInterest] { poi =>
      callLLMForResearch(poi).map(research => POIResearched(poi, research))
    }
    .handleEvent { (poi, event) => event.research }
    .named(s"Research ${poi.name}")
  }
  .buildOutput { (state: State, results: Map[PointOfInterest, ResearchedPOI]) =>
    state.copy(researchedPOIs = results.values.toList)
  }
  .named("Research All POIs")
```

**Characteristics**:
- ✅ Clean collection processing pattern
- ✅ Results aggregated automatically
- ✅ Built-in support for partial failures
- ⚠️ Still depends on runtime for physical concurrency

### Approach 3: Cats Effect Parallel Inside Steps

**For true concurrent execution** - use Cats Effect `Parallel[F]` inside `runIO`:

```scala
import cats.effect.IO
import cats.syntax.parallel._
import cats.Parallel

case class AllPOIsResearched(researched: List[ResearchedPOI]) extends Event

val researchPOIsConcurrent: WIO[State, Nothing, State] = WIO
  .runIO[State] { state =>
    // Use Cats Effect parTraverse for true concurrency
    state.pointsOfInterest
      .parTraverse { poi =>
        callLLMForResearch(poi)  // IO[ResearchedPOI]
      }
      .map(researched => AllPOIsResearched(researched))
  }
  .handleEvent { (state, event) =>
    state.copy(researchedPOIs = event.researched)
  }
  .named("Research POIs (Concurrent)")
```

**With concurrency limit** (like Tripper's max 12):

```scala
import cats.effect.std.Semaphore

val researchWithConcurrencyLimit: WIO[State, Nothing, State] = WIO
  .runIO[State] { state =>
    for {
      // Limit to 12 concurrent LLM calls
      semaphore <- Semaphore[IO](12)
      
      researched <- state.pointsOfInterest.parTraverse { poi =>
        semaphore.permit.use { _ =>
          callLLMForResearch(poi)
        }
      }
    } yield AllPOIsResearched(researched)
  }
  .handleEvent { (state, event) =>
    state.copy(researchedPOIs = event.researched)
  }
  .named("Research POIs (Limited Concurrency)")
```

### Approach 4: Hybrid - forEach + Cats Effect (Best of Both Worlds)

**Recommended for production** - combines workflows4s structure with true concurrency:

```scala
val researchPOIsHybrid: WIO[State, Nothing, State] = WIO
  .runIO[State] { state =>
    // Batch POIs for controlled concurrency
    val batches: List[List[PointOfInterest]] = 
      state.pointsOfInterest.grouped(12).toList
    
    for {
      // Process batches sequentially, POIs within batch in parallel
      allResults <- batches.traverse { batch =>
        batch.parTraverse { poi =>
          callLLMForResearch(poi)
        }
      }
    } yield AllPOIsResearched(allResults.flatten)
  }
  .handleEvent { (state, event) =>
    state.copy(researchedPOIs = event.researched)
  }
  .named("Research POIs (Batched)")
```

### Comparison Table

| Approach | Logical Parallelism | Physical Concurrency | Event Granularity | Complexity |
|----------|---------------------|---------------------|-------------------|------------|
| **WIO.parallel** | ✅ Yes (BPMN visible) | ⚠️ Runtime-dependent | Fine (per POI) | Medium |
| **WIO.forEach** | ✅ Yes (collection) | ⚠️ Runtime-dependent | Fine (per POI) | Low |
| **Cats Effect Parallel** | ❌ No (inside step) | ✅ True concurrency | Coarse (all POIs) | Low |
| **Hybrid (forEach + Cats)** | ✅ Yes | ✅ True concurrency | Fine (per POI) | Medium |

## Consequences

### Positive

1. **Multiple strategies**: Can choose based on requirements
2. **True concurrency**: Cats Effect `Parallel[F]` provides real concurrent execution
3. **Concurrency control**: Semaphore allows limiting concurrent operations
4. **Event sourcing preserved**: All approaches maintain event-sourced state
5. **Type-safe**: Compiler ensures correct parallel composition
6. **Flexible**: Can mix approaches in same workflow

### Negative

1. **Runtime dependency**: `WIO.parallel` and `WIO.forEach` depend on runtime for physical concurrency
2. **Complexity**: Multiple approaches can be confusing
3. **Testing**: InMemorySyncRuntime executes sequentially (not representative)
4. **Event granularity**: Cats Effect approach has single event for all results
5. **No built-in rate limiting**: Must manually implement with Semaphore

### Trade-offs

**For POI Research (12 concurrent calls)**:
- ✅ **Use**: Cats Effect `Parallel[F]` with `Semaphore(12)` inside `runIO`
- **Why**: True concurrency, simple code, controlled limit
- **Event**: Single event for all results (simpler state management)

**For Independent Workflow Steps**:
- ✅ **Use**: `WIO.parallel` or `WIO.forEach`
- **Why**: Logical parallelism visible in BPMN diagrams
- **Event**: Fine-grained events per step

## Implementation Examples

### Example 1: POI Research (Recommended Pattern)

```scala
package io.github.llm4s.tripper.workflow

import cats.effect.IO
import cats.effect.std.Semaphore
import cats.syntax.parallel._
import io.github.llm4s.tripper.domain._
import workflows4s.wio.WIO

object POIResearchWorkflow {
  
  case class AllPOIsResearched(researched: List[ResearchedPointOfInterest]) extends Event
  
  def researchPOIs(
    llmClient: LLMClient,
    maxConcurrency: Int = 12
  ): WIO[State, Nothing, State] = WIO
    .runIO[State] { state =>
      for {
        // Create semaphore for concurrency control
        semaphore <- Semaphore[IO](maxConcurrency)
        
        // Research all POIs in parallel with limit
        researched <- state.pointsOfInterest.parTraverse { poi =>
          semaphore.permit.use { _ =>
            researchSinglePOI(llmClient, poi, state.travelBrief, state.travelers)
          }
        }
      } yield AllPOIsResearched(researched)
    }
    .handleEvent { (state, event) =>
      state.copy(researchedPOIs = event.researched)
    }
    .named("Research Points of Interest")
  
  private def researchSinglePOI(
    client: LLMClient,
    poi: PointOfInterest,
    brief: TravelBrief,
    travelers: Travelers
  ): IO[ResearchedPointOfInterest] = {
    val conversation: Conversation = buildResearchConversation(poi, brief, travelers)
    
    IO.delay(client.complete(conversation)).map {
      case Right(completion) => 
        ResearchedPointOfInterest(
          poi = poi,
          researchFindings = completion.message.content,
          llmModel = completion.model
        )
      case Left(error) =>
        ResearchedPointOfInterest(
          poi = poi,
          researchFindings = s"Error: ${error.message}",
          llmModel = "unknown"
        )
    }
  }
}
```

### Example 4: Rate Limiting with Retry

```scala
import scala.concurrent.duration._

val researchWithRateLimit: WIO[State, Nothing, State] = WIO
  .runIO[State] { state =>
    for {
      semaphore <- Semaphore[IO](12)
      
      researched <- state.pointsOfInterest.parTraverse { poi =>
        semaphore.permit.use { _ =>
          // Retry with exponential backoff
          researchSinglePOI(client, poi, brief, travelers)
            .handleErrorWith { error =>
              IO.sleep(1.second) >> 
              researchSinglePOI(client, poi, brief, travelers)
            }
        }
      }
    } yield AllPOIsResearched(researched)
  }
  .handleEvent { (state, event) =>
    state.copy(researchedPOIs = event.researched)
  }
  .named("Research POIs with Retry")
```

## Performance Considerations

### Concurrency Tuning

```scala
// Configuration
case class WorkflowConfig(
  poiResearchConcurrency: Int = 12,
  accommodationSearchConcurrency: Int = 5,
  llmTimeoutSeconds: Int = 30
)

// Usage
def researchWithConfig(config: WorkflowConfig): WIO[State, Nothing, State] = WIO
  .runIO[State] { state =>
    for {
      semaphore <- Semaphore[IO](config.poiResearchConcurrency)
      
      researched <- state.pointsOfInterest.parTraverse { poi =>

    state.copy(researchedPOIs = event.researched)
```

```scala
val researchWithMetrics: WIO[State, Nothing, State] = WIO
  .runIO[State] { state =>
    val startTime: Long = System.currentTimeMillis()
    
    for {
      semaphore <- Semaphore[IO](12)

    state.copy(researchedPOIs = event.researched)
  }
  .named("Research POIs")
```

### Integration Test (Concurrent)

```scala
"POI research" should "execute concurrently" in {
  val test: IO[Assertion] = for {
    runtime <- InMemoryRuntime.default(workflow, initialState, engine)
    instance <- runtime.createInstance("concurrent-test")
    
    startTime <- IO.realTime
    _ <- instance.wakeup()
    endTime <- IO.realTime
    
    state <- instance.queryState()
  } yield {
    val duration: FiniteDuration = endTime - startTime
    // With 12 POIs and concurrency=12, should take ~1 LLM call duration
    // Without concurrency, would take 12x duration
    assert(duration.toSeconds < 5)  // Reasonable for concurrent execution
    assert(state.researchedPOIs.size == 12)
  }
  
  test.unsafeRunSync()
}
```

## Recommendation for llm4s-tripper

✅ **Use Cats Effect `Parallel[F]` with `Semaphore` inside `WIO.runIO`**

**Rationale**:
1. True concurrent execution (not runtime-dependent)
2. Simple concurrency control with Semaphore
3. Single event per batch (simpler state management)
4. Easy to test and monitor
5. Matches Tripper's parallelMap pattern

**Pattern**:
```scala
WIO.runIO[State] { state =>
  Semaphore[IO](12).flatMap { semaphore =>
    state.items.parTraverse { item =>
      semaphore.permit.use(_ => processItem(item))
    }
  }.map(results => AllProcessed(results))
}.handleEvent { (state, event) =>
  state.copy(processedItems = event.results)
}
```
