# 13. Context-Specific Domain Models (DTO)

Date: 2024-10-19

## Status

Accepted

## Context

In microservice architectures like PITAS, services must remain loosely coupled to ensure flexibility and scalability. During the development of the PITAS system, we initially attempted to use a shared library where the `pitas-scheduler` would depend on the `pitas-jobs` service's domain model to parse job data retrieved from the API. 
However, this introduced strong coupling between services, which led to startup conflicts as both services attempted to initialize each other’s Spring Boot environments.

## Decision

Rather than tightly coupling services by sharing a common domain model (Shared Libary), we opted to implement context-specific domain models (also known as Data Transfer Objects (DTOs) or Boundary Models). 
For example, `pitas-scheduler` introduced its own `JobInformation` model, which contains only the necessary fields for job parsing and JSON annotations required for deserialization.

### Why Context-Specific Domain Models?
- **Why:** By creating a lightweight model tailored to the needs of the `pitas-scheduler`, we avoid unnecessary dependencies and maintain the autonomy of each microservice. This model acts as a boundary between services, allowing the `pitas-scheduler` to remain independent from the internal domain logic of `pitas-jobs`.
- **How:** The `JobInformation` model is an independent class in the `pitas-scheduler` service, containing only the required data structures and annotations. This avoids the need for direct dependencies on `pitas-jobs` and ensures the scheduler can handle job parsing in its own context.

## Consequences
- **Loose Coupling:** Each service maintains its own domain model, reducing the risk of tight coupling and initialization issues.
- **Simplified Models:** Each service handles only the information it needs, which reduces the complexity of shared domain logic and keeps each service focused on its specific responsibilities.
- **Maintenance:** If changes are required for example in the pitas-jobs domain, they don’t automatically affect other services like the pitas-scheduler, thus reducing potential bugs and simplifying updates.

## Comparison to Code Replication

Unlike code replication, where entire components are duplicated across services, this approach reuses only what is necessary by defining independent models. These models do not require frequent updates across services, and they maintain service boundaries, adhering to the principles of loose coupling and service autonomy. Also called Anti-Corruption Layer.
