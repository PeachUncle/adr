# ADR-028: Machine Learning Models Architecture

**Date**: 2025-10-16  
**Status**: Accepted  
**Decision Makers**: System Architect, ML Engineer, DevOps Lead  
**Consulted**: Data Science Team, Risk Management  
**Informed**: Development Team, QA Team

---

## Context

The multi-agent trading system requires sophisticated machine learning models to enhance decision-making capabilities. These models must provide real-time predictions while maintaining high accuracy, reliability, and operational efficiency. The system needs to support three core ML models: Market Regime Classifier, Volatility Predictor, and Assignment Risk Model.

### Business Drivers

- **Enhanced Decision Quality**: ML models provide data-driven insights for strategy selection and risk management
- **Real-Time Performance**: Models must deliver predictions in <100ms to support trading decisions
- **Continuous Improvement**: Automated retraining ensures models adapt to changing market conditions
- **Operational Reliability**: Models must degrade gracefully and provide fallback mechanisms
- **Compliance & Auditability**: All predictions must be traceable and explainable

### Technical Constraints

- **Google Cloud Platform**: Vertex AI for training, Cloud Run for inference
- **Python Ecosystem**: Scikit-learn, XGBoost, TensorFlow for model development
- **Latency Requirements**: <100ms inference, <200ms end-to-end including API
- **Training Budget**: <3 hours per model on n1-standard-4 instances
- **Storage Efficiency**: Models must be <500MB for fast deployment

---

## Decision

We will implement a **unified ML architecture** based on Vertex AI for training and Cloud Run for inference, with the following core principles:

### 1. **Model Development & Training Architecture**

- **Algorithm Selection**:
  - Market Regime Classifier: Gradient Boosting Machine (GBM) via XGBoost
  - Volatility Predictor: LSTM neural network via TensorFlow
  - Assignment Risk Model: Random Forest via Scikit-learn
  
- **Training Infrastructure**:
  - Vertex AI Custom Training Jobs for scalable, reproducible training
  - Docker containers for training code (ensures reproducibility)
  - Quarterly scheduled retraining + event-driven retraining
  - Walk-forward validation for temporal data integrity

- **Data Pipeline**:
  - Minimum 5 years (1,260 trading days) of historical data
  - Feature engineering in BigQuery for scalability
  - SMOTE for class imbalance handling
  - 70% train / 15% validation / 15% test split

### 2. **Model Deployment & Inference Architecture**

- **Deployment Platform**:
  - Cloud Run for serverless, auto-scaling inference
  - FastAPI for REST API endpoints
  - Vertex AI Model Registry for versioning and metadata

- **API Design**:
  - `/predict` - Single prediction endpoint
  - `/batch-predict` - Batch predictions (up to 100 samples)
  - `/health` - Health check and model metadata
  - `/explain` - SHAP-based prediction explanations

- **Performance Optimization**:
  - Model caching in memory (warm starts)
  - Batch inference for non-real-time requests
  - Async prediction queue for high-volume scenarios

### 3. **Model Versioning & Registry**

- **Version Strategy**:
  - Semantic versioning (MAJOR.MINOR.PATCH)
  - MAJOR: Algorithm change or breaking API change
  - MINOR: Retraining with new data
  - PATCH: Hyperparameter tuning only

- **Registry Metadata**:
  - Model artifact location (GCS bucket)
  - Training metrics (accuracy, precision, recall, F1)
  - Feature importance rankings
  - Training dataset version and date range
  - Hyperparameters and configuration

- **Retention Policy**:
  - Keep last 4 quarterly versions (1 year)
  - Archive champion models indefinitely
  - Delete underperforming candidates after 30 days

### 4. **Model Monitoring & Retraining**

- **Scheduled Retraining**:
  - Quarterly retraining (first week of Jan/Apr/Jul/Oct)
  - Validation on subsequent quarter's data
  - Automatic deployment if performance improves

- **Event-Driven Retraining**:
  - Market regime shift detected (20+ consecutive days in new regime)
  - Prediction accuracy drops >2% below baseline
  - Major market event (VIX spike >50% in single day)

- **Model Validation**:
  - Minimum accuracy thresholds (Regime: 75%, Volatility: 70%, Assignment: 80%)
  - Feature importance validation (top 3 features must match expectations)
  - Reject deployment if test accuracy <2% below production model

### 5. **Fallback & Resilience**

- **Three-Tier Fallback Hierarchy**:
  1. **Primary**: Latest deployed model (Cloud Run)
  2. **Secondary**: Previous model version (Cloud Run)
  3. **Tertiary**: Rule-based heuristics (no ML)

- **Graceful Degradation**:
  - Low confidence predictions (confidence <0.20) trigger warnings
  - Model unavailability falls back to rule-based logic
  - All fallback events logged to Cloud Logging

- **Circuit Breaker**:
  - Opens after 5 consecutive failures
  - Routes all requests to fallback for 5 minutes
  - Attempts recovery with exponential backoff

## Rationale

### Why Vertex AI for Training?

- **Managed Infrastructure**: No infrastructure management overhead
- **Experiment Tracking**: Built-in MLflow-compatible experiment tracking
- **Scalability**: Easy to scale from single instance to distributed training
- **Integration**: Seamless integration with BigQuery, GCS, Model Registry
- **Reproducibility**: Containerized training ensures consistent results

### Why Cloud Run for Inference?

- **Serverless**: Auto-scaling from zero to handle variable load
- **Cost-Effective**: Pay only for actual inference time
- **Fast Cold Starts**: <1 second for model loading
- **HTTP-Based**: Easy integration with existing microservices
- **Monitoring**: Built-in metrics and logging integration

### Why Multiple Model Types?

- **Market Regime Classifier (GBM)**: Tree-based models excel at tabular data with mixed feature types
- **Volatility Predictor (LSTM)**: Sequential nature of volatility requires time-series model
- **Assignment Risk (Random Forest)**: Robust to outliers, provides feature importance

### Why Quarterly Retraining?

- **Balance**: Captures market evolution without overfitting to recent noise
- **Cost-Effective**: Training costs manageable at quarterly frequency
- **Operational Stability**: Minimizes deployment overhead and validation burden
- **Regulatory**: Aligns with quarterly compliance reporting cycles

## Consequences

### Positive

✅ **Unified Architecture**: Consistent patterns across all three models simplifies development and operations  
✅ **Scalability**: Vertex AI and Cloud Run provide infinite scalability without infrastructure management  
✅ **Fast Inference**: Cloud Run's serverless architecture enables <100ms predictions  
✅ **Continuous Improvement**: Automated quarterly retraining ensures models stay current  
✅ **Operational Resilience**: Three-tier fallback prevents system degradation during model failures  
✅ **Cost-Effective**: Serverless inference minimizes costs during low-traffic periods  
✅ **Auditability**: Comprehensive logging and versioning support regulatory compliance  
✅ **Developer Productivity**: Managed services reduce infrastructure overhead, focus on model quality

### Negative

⚠️ **Vendor Lock-in**: Heavy dependence on Google Cloud Platform (Vertex AI, Cloud Run)  
⚠️ **Cold Start Latency**: First request after idle may take 1-2 seconds  
⚠️ **Training Costs**: Quarterly retraining for 3 models costs ~$150-200/quarter  
⚠️ **Complexity**: Managing 3 separate models increases operational complexity  
⚠️ **Data Requirements**: 5-year historical data requirement may delay initial deployment

### Mitigation Strategies

- **Vendor Lock-in**: Containerize all training code for portability to AWS SageMaker or Azure ML
- **Cold Starts**: Implement periodic keep-alive pings to maintain warm instances
- **Training Costs**: Implement automatic instance shutdown and spot instance usage
- **Complexity**: Use Infrastructure as Code (Terraform) for consistent deployments
- **Data Requirements**: Start with 3-year minimum, scale to 5 years over time
