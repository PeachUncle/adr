# DEC-0010 REVISION: User Insight on Public v1.0.0

**Date:** 2025-12-20  
**Status:** 🔄 **DECISION REVISED** - Reconsidering based on user feedback

---

## 🎯 The Issue

### What I Initially Decided
**Decided:** Keep strict exact version matching for v1.0.0
- Simple, stable
- Ship what we have
- Iterate based on feedback

### What The User Correctly Pointed Out
> "I don't want to have to explain: 'oh yeah ... this is called v1.0.0 ... but actually there are tons of limitations and we consider fixes only if people complain'. I'd like external v1.0.0 to be a well rounded release with close to zero known issues."

**User is absolutely RIGHT!** ✅

---

## 💡 The Critical Insight I Missed

### Internal vs. External Versioning

From VERSIONING_FINAL_STRATEGY.md:

```
Internal v1.0.0  →  M9 complete (testing baseline, NOT PUBLIC)
Internal v1.1.0  →  Full feature set for public
Public v1.0.0    →  M10 extraction (FIRST PUBLIC RELEASE)
```

**Key Realization:**
- **Internal v1.0.0** = Testing baseline, internal only
- **Public v1.0.0** = First impression to users!
- They're **NOT the same thing**!

### Why This Changes Everything

**Public v1.0.0 is the first impression:**
- Can't have obvious limitations
- Can't say "we'll fix it if you complain"
- Must feel complete, polished, well-thought-out
- Sets the tone for the entire project

**If Public v1.0.0 has strict-only:**
- Users: "Why can't I use `^1.0.0` like in npm?"
- Us: "Well, we decided to keep it simple first..."
- Users: "But this is v1.0.0! It should be feature-complete!"
- Us: "We'll add it in v1.1.0 if people want it..."
- **Result:** Bad first impression! ❌

## 🤔 Revised Analysis

### What Should Public v1.0.0 Include?

**Option A: Strict Only**
- ✅ Simple
- ✅ Already implemented
- ❌ **Known limitation we're aware of**
- ❌ **"We'll fix it if you complain" attitude**
- ❌ **Bad first impression**

**Option B: Draft Mode**
- ✅ **Polished, complete experience**
- ✅ **Addresses known DX friction proactively**
- ✅ **"v1.0.0" feels like v1.0.0**
- ✅ **Good first impression**
- ⚠️ +1-2 days implementation

**Option D: Lock Files**
- ✅ Industry standard
- ✅ Best long-term solution
- ❌ +1-2 weeks implementation
- ❌ Too much for M9/M10 timeline

## 📊 Decision Framework

### Question 1: What's the goal of Public v1.0.0?

**A:** Ship stable foundation, iterate based on feedback
- This was my assumption
- Works for Internal v1.0.0
- **Not appropriate for Public v1.0.0**

**B:** Ship polished, complete experience
- **This is what users expect**
- **This is what "v1.0.0" means publicly**
- User's insight ✅

**Answer:** **B** - Public v1.0.0 must feel complete!

### Question 2: Is strict-only a known limitation?

**Yes!** We spent hours analyzing it:
- Created 6000+ word evaluation
- Identified DX friction
- Know draft mode would help
- Other tools (npm, cargo) have flexible workflows

**If we KNOW it's a limitation, why ship it in Public v1.0.0?**

### Question 3: Can we afford 1-2 days?

**Timeline Check:**
- M9 currently at 85%
- Phase 3 (UI) = 4-6 hours
- Draft mode = 8-12 hours (1-2 days)
- **Total to M9 complete: 2-3 days**
- M10 is weeks 3-4 (plenty of time)

**Answer:** Yes! 1-2 extra days is worth better Public v1.0.0

## ✅ Revised Recommendation

### For Public v1.0.0: Implement Draft Mode (Option B)

**Why:**
1. **First impressions matter** 
   - Public v1.0.0 is our debut
   - Must feel complete, not "basic but works"

2. **Known pain point**
   - We're aware of the limitation
   - Why not fix it before launch?
   - Proactive beats reactive

3. **User expectation**
   - "v1.0.0" means polished release
   - Not "we'll add features if you ask"
   - Sets quality bar for project

4. **Competitive**
   - npm has flexible dev workflows
   - cargo has flexible dev workflows
   - Users will expect similar

5. **Timeline acceptable**
   - +1-2 days to M9 completion
   - Still plenty of time before M10
   - Worth the polish

#### Task 3.7: Draft Mode Backend (4-6 hours)

**Files to modify:**

- `src/parser/dependency_resolver.rs` - Mode-aware resolution

**Changes:**
```rust
// In Package metadata
pub struct PackageMetadata {
    pub id: String,
    pub version: String,
    pub mode: Option<PackageMode>,  // NEW
    pub dependencies: Vec<Dependency>,
    // ...
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum PackageMode {
    #[serde(rename = "draft")]
    Draft,
    #[serde(rename = "release")]
    Release,
}

impl Default for PackageMode {
    fn default() -> Self {
        PackageMode::Release  // Safe default
    }
}
```

**Validation Changes:**
```rust
// In validator
if package.metadata.mode == PackageMode::Release {
    // Enforce exact version matching
    for dep in &package.metadata.dependencies {
        if !is_exact_version(&dep.version) {
            return Err(ValidationError::FlexibleVersionInRelease {
                package: dep.package.clone(),
                version: dep.version.clone(),
            });
        }
    }
}
// In draft mode, flexible constraints allowed
```

**YAML Format:**
```yaml
metadata:
  id: my.package
  version: "0.5.0"
  mode: draft  # or "release", defaults to "release"

dependencies:
  - package: prompt-gen.common
    version: "^1.0.0"  # OK in draft, ERROR in release
```
