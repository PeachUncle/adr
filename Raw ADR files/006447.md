# ADR-006: Monorepo Scalability and Team Ownership Model

**Status:** ✅ Accepted  
**Date:** 2025-11-02  
**Tags:** architecture, scalability, team-ownership, observability, ci-cd

---

## Context

As ATEKBase grows from a single-team prototype to a **3+ feature team organization**, the hexagonal architecture (ADR-001) must scale across multiple ownership boundaries while maintaining:

- 🔒 **Clear ownership** - Each team owns specific packages/features
- 🚀 **Independent deployments** - Teams can release without global coordination
- 📊 **Operational observability** - Each layer produces predictable telemetry
- 🏗️ **Modular boundaries** - Domain logic stays shareable; infrastructure layers split by domain
- ⚡ **CI/CD efficiency** - Parallel testing/building of independently-owned modules

### Example Growth Timeline

```
Month 1: Single team (you)
  ├── Apps (API, Web, Admin)
  └── Packages (Domain, Application, Infra-Prisma, Shared)

Month 6: 3 teams emerge
  ├── Team A: User Management (auth, RBAC)
  ├── Team B: Audit & Compliance (audit trail, reporting)
  └── Team C: Infrastructure & DevOps (database, deployment)

Year 1: 6+ teams with parallel development
  ├── Data team
  ├── Security team
  ├── Reporting team
  └── ...
```

**Challenge:** How to structure packages and CI so teams can iterate without stepping on each other?

## Decision

### 1. Package Ownership Model

Organize packages by **team + responsibility**, keeping hexagonal layers intact:

```
packages/
├── domain/
│   ├── src/
│   │   ├── user/                 # Team A (Users)
│   │   │   ├── user.entity.ts
│   │   │   └── user.errors.ts
│   │   ├── audit/                # Team B (Audit)
│   │   │   ├── audit-trail.entity.ts
│   │   │   └── hash-chain.ts
│   │   └── shared/               # Cross-team
│   │       ├── value-objects.ts
│   │       └── events.ts
│   └── package.json
│
├── application/
│   ├── src/
│   │   ├── user/                 # Team A ports
│   │   │   └── ports/
│   │   │       └── user.repository.ts
│   │   ├── audit/                # Team B ports
│   │   │   └── ports/
│   │   │       └── audit.repository.ts
│   │   └── services/
│   │       ├── user.service.ts   # Team A
│   │       └── audit.service.ts  # Team B
│   └── package.json
│
├── infra-prisma/
│   ├── src/
│   │   ├── user/                 # Team A (User DB layer)
│   │   │   └── user.repository.prisma.ts
│   │   ├── audit/                # Team B (Audit DB layer)
│   │   │   └── audit.repository.prisma.ts
│   │   └── unit-of-work.ts
│   └── package.json
│
├── [NEW] infra-cache/            # Team C (Shared infrastructure)
│   ├── src/
│   │   ├── redis-cache.ts
│   │   ├── session-store.ts
│   │   └── event-bus.ts
│   └── package.json
│
├── [NEW] monitoring/             # Team C + all teams
│   ├── src/
│   │   ├── metrics.ts            # Metrics collection
│   │   ├── tracing.ts            # Distributed tracing
│   │   └── health-checks.ts
│   └── package.json
│
└── shared/
    ├── src/
    │   ├── result.ts              # All teams
    │   ├── logger.ts              # All teams
    │   └── errors.ts              # All teams
    └── package.json

apps/
├── api/                           # Presentation layer (managed by all teams)
│   ├── src/
│   │   ├── auth/                  # Team A
│   │   ├── users/                 # Team A
│   │   ├── audit/                 # Team B
│   │   └── infra/                 # DI wiring (all teams)
│   └── package.json
│
├── admin/                         # Admin UI (Team A + B)
│   └── ...
│
└── web/                           # Web UI (Team A)
    └── ...
```

**Key Principle:** **Vertical slicing at domain level, horizontal layers organization.**

Each team owns:

- 🟦 **Domain entities** (their aggregate root)
- 🟩 **Application services** (use cases)
- 🟨 **Infrastructure adapters** (repositories, external services)
- 🟪 **API endpoints** (controllers in apps/api)

### 3. Package Split Decision Tree

**When to split a package:**

```
├─ Size check
│  └─ > 100 files OR > 10,000 LOC?
│     ├─ YES  → Consider splitting
│     └─ NO   → Keep together
│
├─ Team ownership check
│  └─ Owned by >1 team?
│     ├─ YES  → Split by team boundary
│     └─ NO   → Keep together
│
├─ Deployment frequency check
│  └─ Released independently?
│     ├─ YES  → Split into separate package
│     └─ NO   → Keep together
│
└─ Dependency complexity check
   └─ Creates circular deps or tight coupling?
      ├─ YES  → Split
      └─ NO   → Keep together
```

**Example: When to create `packages/infra-cache`**

```
Size: 2,000 LOC
Team: Team C (Infrastructure)
Frequency: Every 2 weeks (cache strategy updates)
Deps: Zero circular dependencies, used by all teams

Result: ✅ SPLIT - Create packages/infra-cache
```

### 4. CI/CD Partitioning Strategy

**Parallel test execution by package ownership:**

```yaml
# .github/workflows/ci.yml
jobs:
  # Team A: Tests
  test-team-a:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pnpm install
      - run: |
          pnpm --filter "@pkg/domain" test
          pnpm --filter "@pkg/application" test
          pnpm --filter "@pkg/infra-prisma" test
          pnpm --filter "@apps/api" test:user
          pnpm --filter "@apps/web" test
      - run: pnpm arch:check

  # Team B: Tests
  test-team-b:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pnpm install
      - run: |
          pnpm --filter "@pkg/application" test
          pnpm --filter "@pkg/infra-prisma" test
          pnpm --filter "@apps/api" test:audit
          pnpm --filter "@apps/admin" test
      - run: pnpm arch:check

  # Team C: Infrastructure tests
  test-team-c:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:15
        env:
          POSTGRES_PASSWORD: postgres
      redis:
        image: redis:7
    steps:
      - uses: actions/checkout@v4
      - run: pnpm install
      - run: |
          pnpm --filter "@pkg/infra-cache" test
          pnpm --filter "@pkg/monitoring" test
          pnpm --filter "@pkg/infra-prisma" test:integration
      - run: pnpm arch:check

  # Shared: Always runs
  test-shared:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pnpm install
      - run: pnpm --filter "@pkg/shared" test
      - run: pnpm arch:check

  # Merge all results
  ci-status:
    needs: [test-team-a, test-team-b, test-team-c, test-shared]
    runs-on: ubuntu-latest
    steps:
      - run: echo "All tests passed!"
```

**Benefits:**

- ⚡ Tests run in parallel (40 sec → 15 sec)
- 🚀 Teams don't block each other
- 📊 Clear visibility into which team broke CI

### 5. Observability by Layer

Each layer must emit predictable telemetry:

#### **Domain Layer** (Business Logic)

```typescript
// packages/domain/src/user/user.entity.ts
export class User {
  static create(input: CreateUserInput): Result<User, UserCreationError> {
    // Metrics: domain_user_creation_attempt
    // Tags: status=success|failure, reason=invalid_email|...
    return ok(new User(...));
  }
}
```

**Expected signals:**

- ✅ Entity creation/mutation success/failure rates
- ✅ Business rule violations (metrics)
- ❌ NOT: database execution time

#### **Application Layer** (Use Cases)

```typescript
// packages/application/src/services/user.service.ts
export class UserService {
  constructor(
    private userRepository: UserRepository,
    private logger: Logger,
    private metrics: Metrics
  ) {}

  async registerUser(input: RegisterUserInput): Promise<Result<User, Error>> {
    // Start trace
    const span = this.metrics.startSpan('user.registerUser');

    try {
      this.logger.info('User registration started', { email: input.email });
      // ... business logic ...

      span.setAttributes({
        'user.status': 'registered',
        'user.roles': user.roles,
      });
      return ok(user);
    } catch (error) {
      span.setAttributes({ 'error.type': error.name });
      this.logger.error('User registration failed', {
        error,
        email: input.email,
      });
      return err(error);
    } finally {
      span.end();
    }
  }
}
```

**Expected signals:**

- ✅ Use case execution duration (histogram)
- ✅ Success/failure rates by use case
- ✅ Business context (user email, roles)
- ❌ NOT: database connection pool stats

#### **Infrastructure Layer** (Adapters)

```typescript
// packages/infra-prisma/src/user/user.repository.prisma.ts
export class PrismaUserRepository implements UserRepository {
  constructor(
    private prisma: PrismaClient,
    private metrics: Metrics,
  ) {}

  async save(user: User): Promise<Result<User, Error>> {
    const span = this.metrics.startSpan('repository.user.save');

    try {
      const start = Date.now();
      const result = await this.prisma.user.upsert({...});
      const duration = Date.now() - start;

      span.setAttributes({
        'db.operation': 'upsert',
        'db.duration_ms': duration,
        'db.rows_affected': 1,
      });

      return ok(result);
    } catch (error) {
      span.setAttributes({
        'error.type': error.name,
        'db.error': true,
      });
      return err(error);
    } finally {
      span.end();
    }
  }
}
```

**Expected signals:**

- ✅ Query execution time (duration)
- ✅ Rows affected / database operations
- ✅ Connection pool utilization
- ✅ Slow query alerts (>100ms)

#### **API Layer** (HTTP Endpoints)

```typescript
// apps/api/src/users/users.controller.ts
@Controller('users')
export class UsersController {
  constructor(
    private userService: UserService,
    private metrics: Metrics
  ) {}

  @Post('register')
  async register(@Body() input: RegisterUserDto) {
    const span = this.metrics.startSpan('http.users.register');

    try {
      const result = await this.userService.registerUser(input);

      span.setAttributes({
        'http.status_code': 201,
        'http.request.size': JSON.stringify(input).length,
      });

      return { data: result };
    } catch (error) {
      span.setAttributes({
        'http.status_code': 500,
        'error.type': error.name,
      });
      throw error;
    } finally {
      span.end();
    }
  }
}
```

**Expected signals:**

- ✅ HTTP request/response times
- ✅ Status code distribution
- ✅ Request size / response size
- ✅ Endpoint-level error rates

## Performance & Tradeoffs

### Scalability Tradeoffs

| Decision                      | Pro                    | Con                    | Resolution                     |
| ----------------------------- | ---------------------- | ---------------------- | ------------------------------ |
| **Split by team**             | Clear ownership ✅     | More packages ⚠️       | Reduces boilerplate with tools |
| **Shared domain**             | Code reuse ✅          | Harder coordination ⚠️ | CODEOWNERS + PR reviews        |
| **Parallel CI**               | Faster feedback ✅     | More infrastructure ⚠️ | GitHub Actions cost is low     |
| **Cross-layer observability** | Complete visibility ✅ | Telemetry overhead ⚠️  | Sampling in production         |

### Module Size Guidelines

**Recommended boundaries:**

| Package Size | Files | LOC   | Action                  |
| ------------ | ----- | ----- | ----------------------- |
| **Small**    | <30   | <3K   | Keep together           |
| **Medium**   | 30-80 | 3K-8K | Monitor, plan split     |
| **Large**    | >80   | >8K   | Split into sub-packages |

**Current State:**

```
packages/domain:         18 files,  2,100 LOC  ✅ Small
packages/application:    15 files,  1,800 LOC  ✅ Small
packages/infra-prisma:   22 files,  3,200 LOC  ✅ Medium (monitor)
packages/shared:         12 files,  1,500 LOC  ✅ Small
```

### Runtime Performance Impact

**Hexagonal layers have minimal overhead:**

```
API Request → Controller → Service → Port → Adapter → Database
   |             1ms          2ms      <1ms    5ms      40ms

Total: ~48ms overhead (all layers are fast)
```

**Recommendation:** Layer separation **does not** impact performance.

## Operational Concerns

### Health Checks & Observability

**Each layer provides health signals:**

```typescript
// apps/api/src/health.controller.ts
@Controller('health')
export class HealthController {
  constructor(
    private userService: UserService,
    private auditService: AuditService,
    private cacheHealth: CacheHealth,
    private dbHealth: DatabaseHealth
  ) {}

  @Get()
  async check(): Promise<HealthResponse> {
    const [db, cache, services] = await Promise.allSettled([
      this.dbHealth.check(),
      this.cacheHealth.check(),
      this.servicesHealth.check(),
    ]);

    return {
      status: 'healthy',
      layers: {
        application: services.status,
        infrastructure: { db: db.status, cache: cache.status },
      },
      timestamp: new Date(),
    };
  }
}
```

**Monitoring dashboards should show:**

- 📊 **Domain:** Entity creation rates, business rule violations
- 📊 **Application:** Use case execution time, success rates
- 📊 **Infrastructure:** DB query time, cache hit ratio, connection pool
- 📊 **API:** HTTP request time, error rates, throughput

## Recommendations for Technical Director

### ✅ DO:

1. **Use this structure from day 1** - Even with one team, organize code for multi-team growth
2. **Create CODEOWNERS file** - Enables automated code review assignment
3. **Implement observability** - Make layer boundaries visible through metrics
4. **Test infrastructure partitioning** - Run CI jobs in parallel even with one team
5. **Document ownership** - Keep README architecture section updated

### ❌ DON'T:

1. **Wait to split packages** - Waiting until "team 2 arrives" means painful refactoring
2. **Share infrastructure without clear ports** - This breaks hexagonal architecture
3. **Optimize for the current team** - Design for the team you'll have next year
4. **Skip health check endpoints** - Make layer integration visible
5. **Put tests in one place** - Each team owns tests for their code
