# 6. Adopt Micro-Commits Practice

**Status:** Accepted

## Context

We have implemented Kent Beck's TDD + Tidy First workflow (ADR-0005), which includes commit discipline separating structural from behavioral changes. However, we still face challenges:

- **Progress loss risk**: Developers may lose significant work between commits if something breaks
- **Commit hesitation**: Fear of "breaking things" leads to infrequent, large commits
- **Slow feedback**: Large commits make it harder to identify which specific change introduced a bug
- **Cognitive overhead**: Developers must remember multiple changes before committing
- **Difficult rollbacks**: Large commits make "graceful retreat" (git reset --hard) costly

Tim Ottinger's **micro-commits** practice addresses these issues by treating commits like "saving a game" in video games—frequent, small saves that provide safe rollback points.

### What are Micro-Commits?

**Micro-commits** are extremely small, frequent commits (5-20 per hour) that capture **one complete intent**.

**Intent** is the key concept: each commit represents a single, atomic purpose that can be stated in one sentence:
- "Format UserService.ts"
- "Rename getUserById to findUser"
- "Extract validateEmail function"
- "Add test for user login success"
- "Implement calculateTotal function"
- "Update TypeScript config"

Each micro-commit represents a "save point" when the code is in a working state (all tests pass).

**Size is a consequence, not the goal**: While micro-commits typically involve 1-10 lines changed, the size depends on the intent. An IDE refactoring that renames a widely-used function across 80 lines is still one intent ("Rename X to Y"). Hand-coding 80 lines likely represents multiple intents that should be separate commits.

### Key Principles

1. **One intent per commit**: Each commit expresses exactly one purpose
2. **Commit when intent is complete**: After every small change when tests are green
3. **Always working**: Codebase is stable between commits
4. **Graceful retreat**: Can safely `git reset --hard` to last commit without significant loss
5. **Reduces stress**: No fear of losing hours of work

### Relationship to TDD

Micro-commits align perfectly with our existing workflow:
- **Red-Green-Refactor**: Commit after reaching Green, commit again after each Refactor step
- **Test additions**: Each new test can be its own micro-commit
- **Implementation**: Each small implementation increment is its own micro-commit
- **Refactoring**: Each refactoring step is its own micro-commit

## Decision

We will adopt Tim Ottinger's micro-commits practice as an extension of our TDD + Tidy First workflow.

### Intent-Based Commit Guidelines

A micro-commit should express **one complete intent**:
- **Single purpose**: Can be stated in one sentence (the commit message)
- **Atomic**: Represents the smallest complete change for that intent
- **Always green**: All tests pass, no linter/type errors
- **Quick to review**: Intent is immediately clear (< 30 seconds to understand)

**Size follows intent**:
- Most intents involve 1-10 lines changed
- IDE refactorings may involve more lines but still represent one intent
- Hand-coded changes exceeding ~50 lines likely contain multiple intents

### Examples of Micro-Commits

- `Format UserService.ts`
- `Rename getUserById to findUser`
- `Extract validateEmail function`
- `Add JSDoc to calculateTotal`
- `Update TypeScript config`
- `Add test for user login success`
- `Add email validation to User model`
- `Handle null case in getUserById`
- `Implement calculateTotal function`

### Workflow Integration

```
User says "go"
  → /go command triggered
  → Read plan.md, find first unchecked test
  → Write ONE failing test
  → MICRO-COMMIT: Add test for X
  → Run tests (verify failure)
  → Write MINIMAL code
  → Run tests (verify pass)
  → MICRO-COMMIT: Implement X
  → Mark test complete in plan.md
  → Ask about refactoring
  → If refactoring needed:
      → Make structural change 1
      → MICRO-COMMIT: Extract Y
      → Make structural change 2
      → MICRO-COMMIT: Rename Z
  → Wait for next "go"
```

### Enforcement via Hook

We will create a `.claude/hooks/micro-commits.sh` hook that:
1. **Checks test status**: Blocks commits when tests are failing
2. **Uses Claude to evaluate intent**: Analyzes the git diff to determine if it represents ONE complete intent or MULTIPLE intents
   - Considers context: IDE refactorings touching many lines may still be one intent
   - Identifies when hand-coded changes likely contain multiple intents
   - Asks user for confirmation when multiple intents detected
3. **Fallback heuristic**: If Claude response is unclear, uses line count (> 100 lines triggers warning)
4. **No hard line limits**: Size is evaluated based on intent, not arbitrary thresholds

Update the following files:

- **.claude/agents/tdd-driver.md**: Update to make micro-commits after each step
- **AGENTS.md**: Document micro-commits practice for users

## Consequences

### Positive

- **Eliminates progress loss fear**: Can always retreat to last commit (< 5 minutes of work)
- **Faster debugging**: Know exactly which change broke tests
- **Cleaner git history**: Every commit is understandable and reviewable
- **Reduces cognitive load**: Don't need to remember many changes before committing
- **Improves code review**: Reviewers can understand each small step
- **Supports trunk-based development**: Small commits merge easily, reduce conflicts
- **Natural TDD fit**: Aligns with Red-Green-Refactor cycle cadence
- **Psychological safety**: "Saving frequently" reduces development stress

### Negative

- **Git history verbosity**: More commits means longer git log output
- **Commit message overhead**: Writing 5-20 commit messages per hour takes time
- **Possible noise**: Very small commits might seem unnecessary to some developers
- **Rebase complexity**: Interactive rebasing becomes more work with many commits
- **CI/CD pressure**: If CI runs on every commit, micro-commits increase load

### Mitigations

- **Commit notation**: Consider using a commit notation system to organize and filter verbose git logs (see next ADR)
- **Skip CI option**: Use `[skip ci]` for intermediate micro-commits if needed
- **Tooling support**: `/go` command automates commit creation
- **Clear guidelines**: Document when to micro-commit vs. when to batch

### Open Questions

- Should `/go` command auto-commit after each step, or wait for confirmation?
