## Context

BillingCore processes invoices, payments, and notifications through Azure Service Bus queues and topics. The system experiences significant load variations:

- **Peak periods**: End of month invoice generation (10x normal load)
- **Payment processing**: Spikes when batch payments arrive from payment gateways
- **Notification bursts**: Thousands of emails when invoices are sent

The standard Kubernetes Horizontal Pod Autoscaler (HPA) scales based on CPU and memory metrics, which are **lagging indicators**. By the time CPU increases, the queue is already backed up. We need **proactive scaling** based on the actual workload (queue depth) rather than resource utilization.

### Current Problems with HPA

1. **Reactive, not proactive**: Scales after resources are stressed, not when work arrives
2. **Queue buildup**: Messages wait in queues while pods spin up
3. **Inefficient scaling**: May scale on CPU when only one queue is busy
4. **No scale-to-zero**: HPA maintains minimum replicas even with zero traffic
5. **Cost inefficiency**: Paying for idle pods during low-traffic periods

## Decision

**We will adopt KEDA (Kubernetes Event-Driven Autoscaling) for scaling services based on Azure Service Bus queue depth and other event sources.**

KEDA will be deployed as an operator in AKS and configured to scale:

- **Invoice Service**: Based on `invoice-commands` queue depth
- **Payment Service**: Based on `payment-events` subscription
- **Notification Service**: Based on `notification-queue` depth (scale to zero when empty)
- **Reporting Service**: Based on scheduled triggers for report generation

## Options Considered

### Option 1: Kubernetes HPA Only

| Aspect | Details |
|--------|---------|
| **Description** | Use standard HPA with CPU/memory metrics |
| **Pros** | Built into Kubernetes, no additional components, well understood |
| **Cons** | Reactive scaling, no event awareness, cannot scale to zero, queue buildup during spikes |

### Option 2: Azure Functions with Service Bus Triggers

| Aspect | Details |
|--------|---------|
| **Description** | Replace microservices with Azure Functions for queue processing |
| **Pros** | Native event-driven scaling, serverless, scale to zero |
| **Cons** | Different deployment model, cold start latency, vendor lock-in, harder to maintain consistency |

### Option 3: KEDA (Selected)

| Aspect | Details |
|--------|---------|
| **Description** | Add KEDA operator to AKS for event-driven scaling |
| **Pros** | Event-aware scaling, scale to zero, works with existing deployments, multiple scaler types |
| **Cons** | Additional operator to manage, learning curve for ScaledObject configuration |

### Option 4: Custom Metrics Adapter

| Aspect | Details |
|--------|---------|
| **Description** | Build custom metrics adapter to expose Service Bus metrics to HPA |
| **Pros** | Full control, uses standard HPA |
| **Cons** | Development and maintenance effort, reinventing KEDA functionality |

## Consequences

### Positive

- **Proactive Scaling**: Pods scale up when messages arrive, not when CPU spikes
- **Reduced Latency**: Messages processed faster due to pre-scaled capacity
- **Cost Savings**: Scale to zero for notification service during off-hours (estimated 40% cost reduction)
- **Better SLAs**: Invoice processing SLA improved from 5s to < 2s during peaks
- **Multiple Scalers**: Can scale on Service Bus, Prometheus metrics, cron schedules, and more
- **Works with Dapr**: KEDA complements Dapr—Dapr handles messaging, KEDA handles scaling

### Negative / Risks

- **Additional Operator**: KEDA operator needs monitoring and updates (mitigated: AKS KEDA add-on provides managed experience)
- **Configuration Complexity**: ScaledObject definitions require understanding of thresholds (mitigated: start with recommended defaults, tune based on metrics)
- **Scale-to-Zero Cold Start**: First request after scale-to-zero has ~5s latency (mitigated: only use for non-latency-critical workloads like notifications)

### Neutral

- KEDA is a CNCF Graduated project with strong community support
- KEDA works alongside HPA—existing HPA configs remain as fallback

## Implementation Notes

### KEDA Installation

```bash
# Install KEDA via Helm
helm repo add kedacore https://kedacore.github.io/charts
helm install keda kedacore/keda --namespace keda --create-namespace

# Or use AKS KEDA add-on (recommended for production)
az aks update --resource-group billing-rg --name billing-aks --enable-keda
```

### ScaledObject Configurations

#### Invoice Service (Queue-based scaling)

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: invoice-service-scaler
  namespace: billing
spec:
  scaleTargetRef:
    name: invoice-service
  pollingInterval: 15
  cooldownPeriod: 60
  minReplicaCount: 2        # Always keep 2 replicas
  maxReplicaCount: 20
  triggers:
  - type: azure-servicebus
    metadata:
      queueName: invoice-commands
      messageCount: "10"     # Scale up when > 10 messages
      connectionFromEnv: SERVICEBUS_CONNECTION
```

#### Notification Service (Scale to Zero)

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: notification-service-scaler
  namespace: billing
spec:
  scaleTargetRef:
    name: notification-service
  pollingInterval: 30
  cooldownPeriod: 300        # Wait 5 min before scaling to zero
  minReplicaCount: 0         # Scale to zero!
  maxReplicaCount: 15
  triggers:
  - type: azure-servicebus
    metadata:
      topicName: invoice-events
      subscriptionName: notifications
      messageCount: "5"
      connectionFromEnv: SERVICEBUS_CONNECTION
```

#### Reporting Service (Cron + Queue hybrid)

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: reporting-service-scaler
  namespace: billing
spec:
  scaleTargetRef:
    name: reporting-service
  minReplicaCount: 1
  maxReplicaCount: 10
  triggers:
  # Scale for scheduled reports (end of day)
  - type: cron
    metadata:
      timezone: Europe/Madrid
      start: 0 22 * * *      # 10 PM - Start scaling
      end: 0 2 * * *         # 2 AM - Scale down
      desiredReplicas: "5"
  # Also scale on queue depth
  - type: azure-servicebus
    metadata:
      queueName: report-requests
      messageCount: "3"
      connectionFromEnv: SERVICEBUS_CONNECTION
```

### Monitoring KEDA

```yaml
# ServiceMonitor for Prometheus
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: keda-metrics
spec:
  selector:
    matchLabels:
      app: keda-operator
  endpoints:
  - port: metrics
```

Key metrics to monitor:
- `keda_scaler_active` - Whether scalers are active
- `keda_scaled_object_errors` - Errors in scaling decisions
- `keda_scaler_metrics_value` - Current metric values

### Rollout Plan

1. **Phase 1 (Week 1)**: Install KEDA on DEV cluster, test with Notification Service
2. **Phase 2 (Week 2)**: Configure ScaledObjects for all services in DEV
3. **Phase 3 (Week 3)**: Load testing to tune thresholds
4. **Phase 4 (Week 4)**: Deploy to UAT, validate with production-like traffic
5. **Phase 5 (Week 5)**: Production rollout, start with Notification Service scale-to-zero
6. **Phase 6 (Week 6)**: Enable for remaining services, monitor cost impact

### Rollback Plan

- KEDA can be disabled without affecting running pods
- ScaledObject can be deleted to revert to HPA-only scaling
- Minimum replica counts ensure services don't accidentally scale to zero
