# ADR 0003: Java read API (Spring Boot 4), OpenAPI docs, and DB-backed integration testing

## Status
Accepted

## Context
Phase 2 introduces a new service boundary: a Java API that reads from the same SQLite database as the Go ingest service and exposes clean, queryable endpoints for portfolio-ready demonstration (service boundaries, API design, error handling, docs, testing, CI).

Constraints and goals:
- No Docker for local development.
- Use the shared SQLite DB file (`data/telemetry.db`) already established in Phase 1.
- Keep the API “I can explain every line”: prefer simple JDBC + explicit SQL over heavier abstractions.
- Provide API documentation similar to ingest-go’s Swagger UI.
- Maintain consistent error envelopes across services.
- Add tests that exercise real DB behavior (not mocked repositories) and fit CI.

## Decision
1. Create a dedicated Java module (`api-java/`) as a read-only service.
2. Use Spring Boot **4.0.1** with Java **21** for local development and CI.
3. Use **JdbcTemplate** with parameterized SQL (no ORM) for data access.
4. Configure the DB using a single env var:
   - `DB_PATH=../data/telemetry.db`
   - Spring builds `jdbc:sqlite:${DB_PATH}` (shared DB across services).
5. Implement endpoints:
   - `GET /healthz` (DB ping)
   - `GET /events`, `GET /events/{id}`
   - `GET /findings`, `GET /findings/{id}` (Phase 2 adds table + read API; analytics writes arrive later)
6. Standardize API error responses to match ingest-go:

   ```json
   {"error":{"code":"...","message":"..."}}
   ```

   using `@RestControllerAdvice`.
7. Add interactive API docs using **springdoc OpenAPI** (Swagger UI):
   - `/v3/api-docs`
   - `/swagger-ui/index.html`
   - Optional friendly entry path `/docs` (redirects to swagger UI index).
8. Write integration tests using **MockMvc** + a temporary SQLite DB file:
   - `DynamicPropertySource` points `app.dbPath` to a temp file
   - Tests create required tables and seed rows via `JdbcTemplate`
   - Validate both success responses and error envelopes (e.g., invalid `since` returns 400 + envelope).

## Alternatives Considered
- Keep API in Go instead of adding Java  
  Rejected: portfolio goal includes Java/Spring reps and multi-service CI.
- Use Spring Data JPA / Hibernate  
  Rejected: unnecessary complexity for read-only MVP; explicit SQL is easier to explain and control.
- Use a separate DB per service  
  Rejected: conflicts with Phase 1 “shared SQLite file” decision; adds setup overhead.
- Use TestRestTemplate for integration tests  
  Rejected: in Boot 4 this introduced autowiring/config friction; MockMvc was simpler and stable.
- Maintain OpenAPI as a static YAML file (like ingest-go)  
  Rejected for Phase 2: springdoc provides faster iteration and accurate docs from routes.

## Consequences
- The Java API remains intentionally thin and readable: controllers + JDBC repositories + DTOs.
- Schema changes must remain idempotent and shared (Go schema bootstrap is the source of truth).
- SQLite’s concurrency limits still apply; Phase 2 is read-heavy so this is acceptable.
- MockMvc + temp SQLite integration tests provide strong confidence and mirror real behavior in CI.
- Swagger UI is available by default and improves demo/portfolio usability.
- Future Phase 3 (Python analytics) can begin writing findings immediately without changing the Java API shape.

## Notes / Implementation
- DB config:
  - `application.yml` reads `DB_PATH` and sets `spring.datasource.url=jdbc:sqlite:${app.dbPath}`
- Findings table added to shared schema (Phase 2):
  - `findings(id, created_at, type, severity, source, summary, details_json)`
  - Indexes on common filters (`created_at`, `source`, `severity`)
- Added performance index:
  - `idx_events_received_at` to support `/events?since=...` and ordering by `received_at`
- Swagger UI:
  - `/docs` may redirect to `/swagger-ui/index.html` (expected behavior)
