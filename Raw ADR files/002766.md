# ADR-0008: Stripe + StoreKit Entitlement Unification Strategy

## Status
Accepted (2025-12-26)

## Context
Payments differ by platform:
- Web payments: **Stripe** (Checkout, subscriptions, webhooks).
- iOS/iPadOS: App Store rules may require **StoreKit/IAP** for subscriptions/digital content.

The product must enforce access (playback + gated posts) via one consistent, auditable **Entitlements** system, independent of payment provider.

## Decision
Implement a **provider-agnostic entitlements engine**:
- Define internal `ProductPlan` objects (stable IDs) that map to:
  - Stripe `priceId`/`productId`
  - App Store `productId`
- Normalize provider updates into append-only `EntitlementGrant` records:
  - `{userId, productPlanId, sourceProvider, sourceTransactionId, status, startsAt, endsAt}`
- Compute and cache an `EntitlementSnapshot` for fast checks in playback/community.

Stripe is V1; StoreKit ingestion/receipt validation is V2, but the model is designed now so it plugs in cleanly.

## Options Considered
1) Provider-specific entitlement checks (Stripe logic in playback/community)
2) Unified entitlements engine (chosen)
3) Separate “iOS-only” product with separate gating logic

## Pros / Cons
### 1) Provider-specific checks
Pros:
- Fastest initial implementation.
Cons:
- Access logic becomes duplicated and inconsistent; hard to support iOS later.

### 2) Unified entitlements engine
Pros:
- Single source of truth for gating and playback decisions.
- Easier reconciliation/audit (money/access-related bugs are costly).
- StoreKit/other providers can be added without touching all callers.
Cons:
- Requires a bit more upfront modeling (plans, grants, snapshots).

### 3) Separate iOS-only gating
Pros:
- Avoids designing unification early.
Cons:
- Creates platform fragmentation and user confusion; hard to maintain.

## Consequences
- Payments module becomes a producer of entitlement-grant events.
- Playback/community consume entitlements only (no direct Stripe/StoreKit knowledge).
- Reconciliation jobs are required (e.g., reprocess Stripe events, revalidate StoreKit receipts in V2).

## Rollback
If unification complexity blocks V1:
- Implement Stripe-only grants and keep the entitlement engine minimal,
- defer StoreKit ingestion to V2 but preserve the plan/grant/snapshot model to avoid refactors later.
