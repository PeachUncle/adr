# ADR 0001: CloudFormation Over CDK as Default

## Status

Accepted

## Context

AWS provides multiple Infrastructure as Code (IaC) options:
- **CloudFormation**: Native AWS IaC, declarative YAML/JSON templates
- **CDK (Cloud Development Kit)**: Programmatic IaC using TypeScript, Python, etc.
- **Terraform**: Multi-cloud IaC (out of scope for this decision)

We need to establish a default recommendation for new services while remaining flexible for specific use cases.

## Decision

**CloudFormation is the recommended default** for new Service Catalog products.

CDK is supported but requires additional maintenance documentation.

## Rationale

### CloudFormation Advantages

1. **Lower Maintenance Overhead**
   - No runtime dependencies to update (Node.js, Python versions)
   - No CDK library version management
   - No construct library compatibility issues

2. **Direct Service Catalog Integration**
   - Service Catalog natively consumes CloudFormation templates
   - No synthesis step required
   - Simpler CI/CD pipeline

3. **Operational Simplicity**
   - Templates are self-contained
   - Easier to review in pull requests
   - Debugging is straightforward (what you see is what deploys)

4. **Long-term Stability**
   - CloudFormation syntax rarely has breaking changes
   - AWS maintains backwards compatibility

### CDK Considerations

CDK may be preferred when:
- Complex logic is needed (loops, conditionals beyond CFn capabilities)
- Team has strong TypeScript/Python expertise
- Reusable constructs across many services justify the overhead
- Testing infrastructure code is a priority

### CDK Maintenance Requirements

If using CDK, you MUST:
1. Document CDK version and update schedule in `docs/maintenance/infrastructure/cdk.md`
2. Include CDK dependency updates in regular maintenance cycles
3. Test CDK synthesis in CI before deployment
4. Pin construct library versions explicitly

## Consequences

### Positive
- Reduced maintenance burden for most services
- Simpler onboarding for new team members
- Fewer moving parts in deployment pipeline

### Negative
- Some advanced patterns require verbose CloudFormation
- Less code reuse across services
- No compile-time type checking
