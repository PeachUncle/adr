# ADR-007: Seed Data Strategy for Development

## Date

2025-09-14

## Status

Accepted

## Context

During the development of RBAC features and UI testing, we discovered that testing new features was cumbersome without pre-existing sample data. Each time we wanted to test:

- RBAC permissions across different user roles
- Multi-currency transactions
- Account sharing functionality
- Real-world usage scenarios

We had to manually create users, accounts, and transactions through the UI or IEx console, which was time-consuming and error-prone.

## Decision

We will maintain comprehensive seed data in `priv/repo/seeds.exs` that creates:

1. **Sample Users** with different roles:
   - `bangal@example.com` - Account owner (Korean living in Berlin)
   - `maria@example.com` - Co-owner/Partner (German)
   - `john@example.com` - Member (friend for shared expenses)
   - `viewer@example.com` - Viewer (tax advisor with read-only access)

2. **Sample Accounts** with realistic scenarios:
   - **Household Expenses** - Shared household account with EUR/KRW
     - Owners: Bangal, Maria
     - Represents daily shared expenses for an international couple

   - **Greece Vacation 2025** - Vacation expense tracking
     - Owner: Maria
     - Members: Bangal, John
     - Viewer: Sarah (tax advisor)
     - Represents temporary shared expense tracking

3. **Sample Transactions** covering various categories:
   - Rent, groceries, utilities (household expenses)
   - Travel, accommodation, entertainment (vacation expenses)
   - Multiple currencies (EUR, KRW, USD)
   - Both income and expense types

## Consequences

### Positive

- **Faster Development**: Developers can immediately test features without manual data creation
- **Consistent Testing**: All developers work with the same baseline data
- **RBAC Testing**: Pre-configured users with different roles enable immediate permission testing
- **Realistic Scenarios**: Sample data represents real-world usage patterns
- **UI/UX Testing**: Designers and developers can see how the app looks with real data
- **Demo Ready**: The application is always ready for demonstrations
- **Onboarding**: New developers can quickly understand the domain model

### Negative

- **Maintenance**: Seed data needs to be updated when schema changes
- **Data Conflicts**: Need to handle cases where seed data already exists
- **Security**: Must ensure seed data is never used in production
- **Test Isolation**: Tests should not depend on seed data

## Implementation Details

### Usage

```bash
# Reset database and seed
mix ecto.reset

# Just run seeds
mix run priv/repo/seeds.exs
```

### Key Features

- **Idempotent**: Running seeds multiple times won't create duplicates
- **Self-Documenting**: Prints summary of created data with login credentials
- **Comprehensive**: Covers all major features and edge cases
- **Confirmed Users**: All users are pre-confirmed for immediate login

### Security Considerations

- Use only in development and test environments
- Never deploy seed data to production
- All sample users use the same password for convenience
- Join codes are predictable (not cryptographically secure)
