## Context

The multi-agent trading system is a distributed application composed of multiple containerized services (agents) running on Google Cloud Run, communicating via Google Cloud Pub/Sub, and interacting with various databases (BigQuery, Cloud SQL, Redis). To operate this system reliably, we need a comprehensive strategy for observability, which includes logging, monitoring, and alerting. Without this, debugging failures, diagnosing performance issues, and ensuring operational health would be extremely difficult.

## Decision

We will adopt the **Google Cloud Operations Suite** (formerly Stackdriver) as the unified platform for all observability needs.

1.  **Logging**: **Google Cloud Logging** will be the central repository for all logs. All agents and services running on Cloud Run will be configured to write structured logs (JSON) to `stdout`. Cloud Logging automatically ingests these logs, making them searchable, analyzable, and available for alerting.

2.  **Monitoring**: **Google Cloud Monitoring** will be used to collect and visualize metrics on the health and performance of our infrastructure. This includes both standard metrics provided automatically by GCP services (e.g., Cloud Run latency, Pub/Sub message count) and custom application-level metrics (e.g., trade execution success rate, portfolio P&L).

3.  **Alerting**: **Google Cloud Alerting** will be used to create automated alerts based on the logs and metrics collected. Alerting policies will be defined in Terraform to notify operators of critical system events.

## Rationale

1.  **Seamless GCP Integration**: The Cloud Operations Suite is the native observability solution for GCP. It requires zero configuration to start collecting logs and metrics from Cloud Run, Pub/Sub, BigQuery, and other services we are using. This drastically simplifies setup and reduces operational overhead.
2.  **Cost-Effectiveness**: The suite includes a generous free tier for log and metric ingestion. For a system of this scale, the costs will be minimal and significantly lower than integrating and managing a third-party observability platform (e.g., Datadog, New Relic).
3.  **Unified Platform**: It provides a single pane of glass for logs, metrics, and alerts. This allows for powerful correlation, such as viewing the specific logs that occurred during a spike in metric latency, which is invaluable for debugging.
4.  **Infrastructure as Code (IaC) Compatibility**: Dashboards and alerting policies in Cloud Monitoring can be defined declaratively using Terraform, which aligns with our decision in ADR-019 to manage all infrastructure as code.

## Consequences

-   **Implementation**:
    -   **Structured Logging**: All agents **must** be implemented with a logging library configured to output structured JSON to standard output. This allows for easy filtering and analysis in Cloud Logging (e.g., searching for all logs with a specific `trade_id`).
    -   **Custom Metrics**: The `PerformanceAnalyticsAgent` will be responsible for calculating key business metrics (e.g., win rate, profit factor) and exporting them to Cloud Monitoring using the appropriate client library.
    -   **Dashboards & Alerts**: A set of standard monitoring dashboards and critical alerting policies (e.g., for API errors, high latency, or critical agent failures) will be defined in our Terraform configuration.
-   **Dependencies**: The project will require the `google-cloud-logging` and `google-cloud-monitoring` Python libraries.

## Alternatives Considered

-   **Third-Party Observability Platforms (e.g., Datadog, New Relic, Grafana)**: These are extremely powerful platforms. However, they introduce additional cost and complexity. They would require installing agents, managing API keys, and learning a separate system. For our GCP-native architecture, the benefits of the native Cloud Operations Suite outweigh the advanced features of these platforms for our current needs.
-   **Self-Hosted Open Source Stack (e.g., Prometheus, Grafana, Loki)**: This approach offers maximum control and no licensing fees but comes with a massive operational burden. We would be responsible for provisioning, scaling, securing, and maintaining the entire observability infrastructure, which directly contradicts our serverless, managed-first architectural principles.

## Implementation Strategy

### Phase 1: Structured Logging Implementation (Week 1)
**Deliverables**:
- Define standard JSON logging schema (timestamp, severity, message, trace_id, agent_name, trade_id, symbol)
- Implement Python logging library configuration for all agents (using python-json-logger)
- Configure stdout/stderr output for automatic Cloud Logging ingestion
- Create log correlation strategy using trace_id for request tracing across agents

**Dependencies**: Agent codebase structure, Cloud Run services deployed

### Phase 2: Cloud Monitoring Metrics Setup (Week 2)
**Deliverables**:
- Configure automatic metric collection for Cloud Run (request count, latency, error rate)
- Configure automatic metric collection for Pub/Sub (message count, publish latency, subscription backlog)
- Configure automatic metric collection for Cloud SQL (connections, query latency)
- Implement custom metrics exporter for business-level metrics (trades executed, P&L, win rate)
- Create PerformanceAnalyticsAgent to calculate and export business metrics hourly

**Dependencies**: Phase 1 completion, google-cloud-monitoring Python library integrated

### Phase 3: Dashboards and Visualization (Week 3)
**Deliverables**:
- Create Cloud Monitoring dashboard for infrastructure health (Cloud Run, Pub/Sub, databases)
- Create dashboard for agent-specific metrics (StockSelectionAgent scan rate, execution success rate)
- Create dashboard for business metrics (daily P&L, open positions, portfolio Greeks)
- Create dashboard for error tracking (error rate by agent, error types, failed trades)
- Define all dashboards as Terraform configuration for version control

**Dependencies**: Phase 2 completion, ADR-019 (Terraform for IaC)

### Phase 4: Alerting Policies (Week 4)
**Deliverables**:
- Create critical alerts (agent crash, database down, Pub/Sub delivery failure)
- Create warning alerts (high error rate, elevated latency, approaching risk limits)
- Create business alerts (daily loss exceeds threshold, position count exceeds max)
- Configure notification channels (email, Pub/Sub for integration with incident management)
- Define all alerting policies in Terraform

**Dependencies**: Phase 3 completion, metric baselines established

## Cost Analysis

### Monthly Operational Costs

| Component | Usage Pattern | Cost |
|-----------|---------------|------|
| Cloud Logging (50GB ingestion/month) | Continuous logging from all services | $25/month |
| Log Storage (200GB, 30-day retention) | Retained logs for debugging | $4/month |
| Cloud Monitoring (50 custom metrics) | Business and application metrics | $10/month |
| Metric API Calls (1M reads/month) | Dashboard and alerting queries | $0.10/month |
| Alert Notifications (1000/month) | Email and Pub/Sub notifications | $0.02/month |
| **Total Monthly Cost** | | **$39-40/month** |

**Free Tier Coverage**:
- First 50GB log ingestion: Free
- First 200 metric time series: Free
- Standard metrics (Cloud Run, Pub/Sub, Cloud SQL): Free
- First 1000 alerting checks: Free

**Cost Sensitivity**:
- Actual costs may be $10-15/month due to free tier coverage
- Verbose logging at DEBUG level can increase log ingestion costs by 3-5x
- Custom metrics beyond 200 time series: $0.10/metric/month

### Cost Optimization Strategies

1. **Log Level Management**: Use INFO level for production, DEBUG only for specific debugging sessions. Reduces log volume by 60-80%.

2. **Log Sampling**: For high-frequency events (Greeks calculations, price updates), sample 10% of logs. Reduces ingestion costs while maintaining visibility.

3. **Log Retention Policies**: Retain detailed logs for 30 days, aggregate logs for 90 days, delete after 90 days. Reduces storage costs by 50%.

4. **Metric Aggregation**: Export business metrics hourly instead of per-trade. Reduces custom metric count from 500 to 50.

5. **Alert Deduplication**: Configure alert grouping to prevent notification storms. Reduces notification costs and alert fatigue.

### ROI Comparison vs Alternatives

| Approach | Setup Cost | Monthly Cost | Feature Completeness | GCP Integration |
|----------|------------|--------------|----------------------|-----------------|
| Cloud Operations Suite | Low | $10-40 | High | Native |
| Datadog | Medium | $100-300 | Very High | Third-party agent |
| New Relic | Medium | $80-250 | Very High | Third-party agent |
| Self-Hosted (Prometheus/Grafana) | Very High | $30-60 (infrastructure) | Medium | Custom integration |

**Verdict**: Cloud Operations Suite provides best cost-to-value ratio for GCP-native applications.

## Risk Assessment

| Risk | Severity | Likelihood | Impact | Mitigation |
|------|----------|------------|--------|------------|
| Log ingestion quota exceeded | Medium | Low | New logs dropped, loss of visibility during incident | Configure log exclusion filters for noisy logs, implement log sampling, set up quota monitoring alerts |
| Custom metric quota exceeded | Medium | Low | New business metrics not recorded | Design metric schema to minimize time series count, use metric labels efficiently, monitor quota usage |
| Alert fatigue from false positives | Medium | Medium | Important alerts ignored, delayed incident response | Tune alert thresholds based on historical data, implement alert grouping, establish on-call rotation |
| Sensitive data in logs | High | Medium | Credential exposure, PII leakage, compliance violations | Implement log scrubbing for API keys, passwords, account numbers, regular audit of log content |
| Dashboard performance degradation | Low | Low | Slow dashboard loading impacts debugging | Use pre-aggregated metrics, limit dashboard time range, implement dashboard caching |
| Missing critical logs during incident | High | Low | Unable to debug root cause, extended outage | Implement structured logging standard, require critical path logging, regular log coverage audits |
| Cloud Operations service outage | Medium | Very Low | Loss of observability during incident | Export critical metrics to secondary monitoring system, implement local log buffering |

## Monitoring and Success Criteria

### Key Metrics

| Metric | Target | Measurement Method |
|--------|--------|-------------------|
| Log Ingestion Success Rate | >99.9% | Cloud Logging ingestion errors |
| Dashboard Load Time (p95) | <3 seconds | Cloud Monitoring dashboard performance |
| Alert Delivery Latency (p95) | <2 minutes | Time from condition trigger to notification |
| Mean Time to Detect (MTTD) | <5 minutes | Time from incident start to alert |
| False Positive Alert Rate | <10% | Alerts triggered without actionable incident |

### Alerting Thresholds

**Critical**:
- Cloud Run agent container crashed (exit code non-zero)
- Cloud SQL database connection pool exhausted
- Pub/Sub message delivery failures >5% for 5 minutes
- Error rate >10% for any agent for 5 minutes
- Daily loss exceeds 2% of account value (circuit breaker)
- Log ingestion quota at 95% capacity

**Warning**:
- Cloud Run request latency p95 >5 seconds for 10 minutes
- Pub/Sub subscription backlog >1000 messages for 15 minutes
- Custom metric not updated for 2 hours (indicates agent failure)
- Error rate >5% for any agent for 10 minutes
- Portfolio heat exceeds 80% of max_portfolio_heat
- Log storage approaching 90% of retention quota

**Info**:
- New agent deployment completed
- Scheduled maintenance window started
- Daily performance report generated
- Backup completed successfully

### Success Criteria

**Functional Requirements**:
- All agents emit structured JSON logs to Cloud Logging
- Standard metrics automatically collected for Cloud Run, Pub/Sub, Cloud SQL
- Custom business metrics (P&L, win rate, positions) exported to Cloud Monitoring
- Dashboards created for infrastructure, agents, and business metrics
- Critical and warning alerting policies configured and tested

**Performance Requirements**:
- Logs appear in Cloud Logging within 30 seconds of emission
- Metrics updated in Cloud Monitoring within 1 minute
- Dashboards load within 3 seconds (p95)
- Alerts delivered within 2 minutes of condition trigger

**Cost Requirements**:
- Total observability costs remain below $50/month
- Log ingestion costs <$30/month
- Custom metrics costs <$15/month

**Operational Requirements**:
- All dashboards and alerts defined in Terraform (infrastructure as code)
- On-call runbook references specific dashboards and log queries for common incidents
- Quarterly review of log volume and metric usage to optimize costs
- Documentation maintained for logging standards and custom metric definitions

### Risk Factors

1. **Log Volume Management**: Low complexity - Log volume can grow rapidly with verbose logging. Risk: Cost overruns, quota exhaustion. Mitigation: Use log sampling, INFO-level production logging, regular log volume audits.

2. **Alert Threshold Tuning**: Medium complexity - Setting appropriate alert thresholds requires historical baseline data. Risk: False positives (alert fatigue) or false negatives (missed incidents). Mitigation: Start with conservative thresholds, iterate based on historical data, implement alert grouping.

3. **Sensitive Data Exposure**: Medium complexity - Logs may inadvertently contain API keys, passwords, or account numbers. Risk: Security vulnerability, compliance violations. Mitigation: Implement log scrubbing, regular log content audits, developer training on secure logging practices.

4. **Dashboard Complexity**: Low complexity - Overly complex dashboards with many metrics can be slow to load. Risk: Poor user experience during incident response. Mitigation: Design focused dashboards for specific use cases, limit time ranges, use pre-aggregated metrics.

5. **Dependency on GCP Service**: Low complexity - Observability platform is tightly coupled to GCP. Risk: Vendor lock-in, observability outage during GCP incidents. Mitigation: Acceptable trade-off for cost and integration benefits, implement local log buffering as backup.
