# ADR-004: Use Row Level Security for Data Isolation

**Status**: Accepted

**Date**: 2024-09-20

**Deciders**: Development Team

**Tags**: security, database, multi-tenancy, rls

## Context

ParentLog is a multi-family platform where each family must only see their own messages and data. We need a robust mechanism to ensure data isolation between families while keeping the application code simple.

Options for data isolation:
1. **Application-level filtering**: Add `WHERE family_account_id = ?` to every query
2. **Database views**: Create per-family database views
3. **Row Level Security (RLS)**: PostgreSQL built-in feature
4. **Separate databases**: One database per family

Critical requirements:
- **Security**: Impossible for one family to see another family's data
- **Developer ergonomics**: Easy to write queries without security bugs
- **Performance**: Minimal overhead for data filtering
- **Scalability**: Support hundreds of families on shared database

## Decision

We will use **PostgreSQL Row Level Security (RLS)** enforced at the database level for all multi-tenant tables.

## Alternatives Considered

### Option 1: Application-Level Filtering
**Pros:**
- Familiar pattern for developers
- Works with any database
- No special database features needed

**Cons:**
- **Critical security risk**: Easy to forget `WHERE` clause
- Code duplication across queries
- Difficult to audit for missing filters
- Junior developers could introduce data leaks
- No enforcement mechanism

### Option 2: Database Views
**Pros:**
- Enforced at database level
- Familiar SQL concept

**Cons:**
- Complex view management (one per family)
- Doesn't scale to many families
- Hard to maintain schema changes
- Limited flexibility for queries

### Option 3: Row Level Security (Chosen)
**Pros:**
- **Database-enforced**: Impossible to bypass from application code
- **Automatic filtering**: Applied to every query automatically
- **Audit trail**: Policies visible in database schema
- **PostgreSQL native**: Well-tested and performant
- **Supabase integration**: Works seamlessly with PostgREST API
- **JWT-based**: Uses Supabase auth.uid() for current user

**Cons:**
- **Learning curve**: RLS concepts unfamiliar to many developers
- **Debugging complexity**: Harder to understand why queries return empty
- **Service role needed**: Admin operations require bypassing RLS
- **Policy maintenance**: Must update policies when schema changes

### Option 4: Separate Databases
**Pros:**
- Complete isolation (one DB per family)
- Simple application code

**Cons:**
- Expensive (database instances cost money)
- Ops nightmare (managing hundreds of databases)
- Cross-family analytics impossible
- Connection pool exhaustion
- Migration complexity

## Consequences

### Positive
- **Security by default**: Data leaks nearly impossible
- **Simple queries**: No need to add family filtering to every query
- **Auditable**: Policies documented in SQL schema
- **Performance**: RLS implemented efficiently in PostgreSQL query planner
- **JWT integration**: Seamless with Supabase Auth (auth.uid())
- **PostgREST compatibility**: Auto-generated API respects RLS

### Negative
- **Learning curve**: Team must understand RLS concepts
- **Debugging difficulty**: Empty results can be confusing
- **Service role complexity**: Admin operations need special client
- **Policy maintenance**: Must remember to add RLS to new tables

### Neutral
- **Testing**: Need to test with multiple users to verify RLS
- **Documentation**: Must document when to use service role client

## Implementation Details

### Example RLS Policy

```sql
-- Enable RLS on messages table
ALTER TABLE messages ENABLE ROW LEVEL SECURITY;

-- Users can only see messages from their family
CREATE POLICY "Family members can view family messages"
  ON messages FOR SELECT
  USING (
    family_account_id IN (
      SELECT family_account_id
      FROM family_members
      WHERE user_id = auth.uid()
    )
  );

-- Users can insert messages to their family
CREATE POLICY "Family members can insert family messages"
  ON messages FOR INSERT
  WITH CHECK (
    family_account_id IN (
      SELECT family_account_id
      FROM family_members
      WHERE user_id = auth.uid()
    )
  );
```

### Service Role Pattern

For admin operations (invitations, cross-family queries), we use the service role client:

```typescript
// apps/web/lib/supabase/server.ts

import { createClient } from '@supabase/supabase-js'

// ✅ Bypasses RLS for admin operations
export function createServiceRoleClient() {
  return createClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.SUPABASE_SERVICE_ROLE_KEY!,
    {
      auth: {
        autoRefreshToken: false,
        persistSession: false
      }
    }
  )
}
```

### Common RLS Pitfalls

1. **Empty results despite data existing**
   - **Symptom**: Query returns `[]` but SQL shows data exists
   - **Cause**: Using user client when service role needed
   - **Fix**: Use `createServiceRoleClient()` for admin queries

2. **Invitations not showing**
   - **Symptom**: Created invitations don't appear
   - **Cause**: RLS blocking access to invitation records
   - **Fix**: Service role for invitation APIs

3. **Policy on wrong column**
   - **Symptom**: Data leaks between families
   - **Cause**: Policy checking wrong foreign key
   - **Fix**: Verify policy uses correct `family_account_id`

## Testing Strategy

**RLS Verification Checklist:**

1. ✅ Create two test families with different users
2. ✅ Verify User A cannot see User B's messages
3. ✅ Verify admin can see all family members
4. ✅ Verify contributor sees only their own messages
5. ✅ Test invitation creation with service role
6. ✅ Verify direct SQL queries respect RLS

**Test Database:**

```sql
-- Test with different users
SET request.jwt.claims.sub = 'user-a-id';
SELECT * FROM messages; -- Should only see User A's family

SET request.jwt.claims.sub = 'user-b-id';
SELECT * FROM messages; -- Should only see User B's family
```

## Notes

**When to Use Service Role Client:**
- ✅ Creating/managing family invitations
- ✅ Admin viewing all family members
- ✅ System-level operations (cleanup, migrations)
- ✅ Cross-family aggregations or reports
- ❌ User viewing their own data (use regular client)
- ❌ User-initiated CRUD on their own records

**Debugging RLS Issues:**

1. Check which client is being used (service role vs user)
2. Query table directly via SQL to confirm data exists
3. Review RLS policies in Supabase dashboard
4. Add logging to see query results vs database contents
5. Verify `SUPABASE_SERVICE_ROLE_KEY` is set correctly
