# ADR-005: Public REST API with Facade Pattern and Versioning Strategy

## Status
Accepted (October 7, 2025)

## Context

### Business Drivers
BahariWatch requires a stable, well-documented public API to serve multiple client types with varying lifespans and update frequencies:

1. **Mobile Application**: Installed on 10,000+ coastal users' devices (3-6 month update cycles due to app store approval lag, offline usage constraints)
2. **Web Dashboard**: Browser-based enforcement portal (instant updates via CDN, modern browser requirements)
3. **Government Integrations**: Kenya Wildlife Service, Kenya Coast Guard (12-24 month procurement/integration cycles, legacy systems)
4. **Research Partners**: University analytics tools (variable update cycles, academic calendars)
5. **Third-Party Developers**: Future NGO/enforcement tool integrations (unpredictable update adoption)

### Stakeholder Concerns
1. **Mobile Users**: Breaking changes force app store resubmission (Apple: 2-7 days, Google: hours-days review), disrupting critical reporting during enforcement operations
2. **Enforcement Officers**: API downtime during version migrations prevents real-time alert delivery (15-30 minute vessel escape window)
3. **Development Team**: Managing multiple API versions strains 6-month pilot timeline (May-October 2025) and limited budget (KSh 59,500)
4. **Research Compliance**: Protocol changes require ethics board re-approval (2-4 week process per ADR-008 GDPR requirements)

### Technical Constraints
1. **Client Diversity**: iOS/Android/Web/Server clients have different update mechanisms and backward compatibility needs
2. **Offline-First**: Mobile app caches API responses for 72 hours (ADR-002 choreography), requiring backward-compatible response schemas
3. **Event-Driven Architecture**: API Gateway publishes events to RabbitMQ (ADR-015), versioning must extend to event schemas
4. **Microservices Facade**: API Gateway routes to 6 internal services (ADR-001), each with independent deployment schedules
5. **Budget Constraint**: Can't afford multiple load-balanced gateways ($15/month DigitalOcean per ADR-012), single instance must handle version negotiation

### Integration with Other ADRs
- **ADR-001 (Microservices)**: API Gateway acts as facade for 6 backend services, isolating clients from internal architecture changes
- **ADR-002 (Event Choreography)**: API version changes must cascade to RabbitMQ event schemas (ADR-015 JSON Schema validation)
- **ADR-006 (Performance SLO)**: API versioning overhead must not exceed <500ms p95 response time budget
- **ADR-008 (Security)**: JWT tokens include API version scope, version migrations must preserve anonymity guarantees
- **ADR-010 (Fitness Functions)**: Automated tests validate backward compatibility before deployment
- **ADR-012 (Deployment)**: Single API Gateway instance on DigitalOcean App Platform, zero-downtime version migrations
- **ADR-015 (RabbitMQ)**: Event schemas versioned in parallel with API endpoints (e.g., `report.submitted.v1`, `report.submitted.v2`)

## Decision

**We will use URL path versioning (e.g., `/v1/reports`, `/v2/reports`) with a comprehensive deprecation lifecycle to manage API evolution while maintaining client stability.**

### Specific Configuration

#### **1. Versioning Strategy: URL Path Versioning**
```
https://api.bahariwatch.ke/v1/reports
https://api.bahariwatch.ke/v2/reports
```

**Rationale:** URL path versioning chosen over header versioning because:
- **Discoverability**: Version visible in browser address bar, logs, monitoring dashboards (simplifies debugging)
- **Client Simplicity**: No custom header management in mobile SDKs (React Native, Flutter clients)
- **Caching Compatibility**: CDN/proxy caching works without inspecting headers (DigitalOcean CDN per ADR-012)
- **OpenAPI Support**: OpenAPI 3.0 spec naturally describes path-based versions as separate servers

#### **2. Versioning Scope: Major Versions Only**
- **v1, v2, v3**: Major versions for breaking changes (remove fields, change types, alter semantics)
- **No minor versions**: Additive changes (new fields, endpoints) deployed to existing major version
- **Example Breaking Change**: Removing `Report.userId` field (privacy enhancement) → requires v2
- **Example Non-Breaking Change**: Adding `Report.verificationStatus` field → deploy to v1

#### **3. API Lifecycle Stages**

```plaintext
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│   Active    │ →  │ Deprecated  │ →  │  Sunset     │ →  │  Retired    │
│   (v1)      │    │   (v1)      │    │   (v1)      │    │   (v1)      │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
      │                   │                   │                   │
      │                   │                   │                   │
 No warnings       Deprecation header   Returns 410 Gone     404 Not Found
                   Sunset header         "Use /v2/..."        (route removed)
```

**Stage Definitions:**
1. **Active** (6+ months): Fully supported, no warnings, documented in primary API docs
2. **Deprecated** (6 months): Sunset header indicates retirement date, migration guide published, dashboard shows deprecation warnings
3. **Sunset** (3 months): Returns `410 Gone` with location header pointing to replacement, breaking change deployed to old version (forces migration)
4. **Retired** (permanent): Route removed from gateway, returns `404 Not Found`

**Total Lifecycle:** 15 months minimum (6 active + 6 deprecated + 3 sunset)

#### **4. Backward Compatibility Rules**

**Non-Breaking Changes (Deploy to Existing Version):**
- ✅ Add new optional request fields
- ✅ Add new response fields (clients ignore unknown fields per JSON best practices)
- ✅ Add new endpoints (e.g., `/v1/reports/bulk-verify`)
- ✅ Add new query parameters (optional)
- ✅ Add new enum values (if clients use open enums)
- ✅ Relax validation constraints (e.g., increase `notes` field max length from 500 → 1000 chars)

**Breaking Changes (Require New Major Version):**
- ❌ Remove request/response fields
- ❌ Rename fields
- ❌ Change field types (e.g., `latitude: string` → `latitude: number`)
- ❌ Change endpoint URLs
- ❌ Remove endpoints
- ❌ Change HTTP verbs (e.g., POST `/reports` → PUT `/reports`)
- ❌ Change authentication schemes
- ❌ Tighten validation (e.g., make optional field required)
- ❌ Change response status codes for existing scenarios

#### **5. Deprecation Communication Strategy**

**Phase 1: Announcement (T-0)**
- **API Changelog**: Publish deprecation notice with migration guide
- **HTTP Headers**: Add `Deprecation: true` and `Sunset: Sat, 31 May 2025 23:59:59 GMT` headers to deprecated endpoints
- **Link Header**: Include successor version link `Link: </v2/reports>; rel="successor-version"`
- **Dashboard Notice**: Red banner in API documentation portal
- **Email Campaign**: Notify all registered API key holders (BMU officers, enforcement, researchers)

**Phase 2: Client Monitoring (T+1 month)**
- **Usage Analytics**: Track deprecated endpoint calls per client (API key, device ID)
- **Proactive Outreach**: Email clients still using deprecated endpoints with 5-month deadline
- **Migration Support**: Offer 1-on-1 video calls for government integrations with complex migrations

**Phase 3: Breaking Change Deployment (T+6 months - Sunset Period)**
- **410 Gone Response**: Replace deprecated endpoint with permanent redirect
```json
{
  "type": "https://api.bahariwatch.ke/errors/endpoint-retired",
  "title": "Endpoint Retired",
  "status": 410,
  "detail": "This endpoint was retired on 2025-05-31. Please migrate to v2.",
  "instance": "/v1/reports",
  "migrationGuide": "https://docs.bahariwatch.ke/migration/v1-to-v2",
  "successorEndpoint": "/v2/reports"
}
```
- **Location Header**: `Location: /v2/reports` for automatic client redirect support
- **Monitoring**: Track 410 response rate, escalate if >1% of traffic (indicates unmigrated critical clients)

**Phase 4: Route Removal (T+9 months)**
- **Complete Removal**: Delete route from API Gateway configuration
- **404 Response**: Standard not found error
- **Archive Documentation**: Move v1 docs to `/docs/archive/v1/` for historical reference

#### **6. Rate Limiting Per Version**

```yaml
# API Gateway rate limiting configuration (Kong/Nginx)
rate_limiting:
  v1:
    authenticated_users: 1000 requests/hour
    anonymous_users: 100 requests/hour
```

**Rationale:** Higher rate limits for newer versions incentivize migration, reduce load on legacy infrastructure.

#### **8. Event Schema Versioning (RabbitMQ)**

API versions cascade to event schemas (ADR-015 RabbitMQ):

```json
// report.submitted.v1 event
{
  "event_id": "evt-123",
  "event_type": "report.submitted.v1",
  "timestamp": "2025-05-15T14:30:00Z",
  "payload": {
    "report_id": "rpt-001",
    "user_id": "anon-abc123",  // ← Breaking: removed in v2 for privacy
    "latitude": -4.0435,
    "longitude": 39.6682
  }
}

// report.submitted.v2 event (v2 API migration)
{
  "event_id": "evt-456",
  "event_type": "report.submitted.v2",
  "timestamp": "2025-06-01T10:00:00Z",
  "payload": {
    "report_id": "rpt-002",
    // user_id removed (privacy enhancement per ADR-008)
    "latitude": -4.0435,
    "longitude": 39.6682,
    "verification_status": "pending"  // ← New field
  }
}
```

**Consumer Migration:**
```python
# Matching Service consumer handles both v1 and v2 events
def handle_report_event(event: dict):
    if event['event_type'] == 'report.submitted.v1':
        # Legacy event handling (during deprecation period)
        payload = event['payload']
        report_id = payload['report_id']
        # user_id ignored (deprecated field)
        
    elif event['event_type'] == 'report.submitted.v2':
        # New event handling
        payload = event['payload']
        report_id = payload['report_id']
        verification_status = payload.get('verification_status', 'pending')
```

#### **9. JWT Token Versioning**

JWT tokens include API version scope to enforce version-specific rate limits and permissions:

```json
{
  "sub": "usr-123",
  "iat": 1684156800,
  "exp": 1684243200,
  "scopes": ["report:write", "vessel:read"],
  "api_version": "v1",  // ← Token tied to API version
  "rate_limit_tier": "authenticated_user"
}
```

**Version Migration:** Users must re-authenticate when switching API versions (forces acceptance of new terms of service per ADR-008 GDPR).

## Rationale

### Alternatives Considered

#### **Alternative 1: Header-Based Versioning (`Accept-Version: v1`)**

**Advantages:**
- **Clean URLs**: Single endpoint URL (e.g., `/reports`) serves all versions
- **RESTful Purists**: Aligns with HTTP content negotiation principles
- **No URL Clutter**: Documentation shows single canonical URL

**Disadvantages:**
- **Discoverability**: Version hidden in headers (not visible in browser, logs, monitoring dashboards)
- **Client Complexity**: Mobile SDKs (React Native, Flutter) require custom header management
- **Caching Issues**: CDN/proxy must inspect headers to cache different versions (complex Vary header configuration)
- **OpenAPI Limitations**: OpenAPI 3.0 spec doesn't naturally express header-based versioning (requires custom extensions)
- **Default Version Ambiguity**: Must define behavior when `Accept-Version` header missing (breaking change for existing clients)
- **Testing Complexity**: Integration tests must explicitly set headers for every request

**Why Rejected:**
Header-based versioning **optimizes for API aesthetics over client usability**. BahariWatch prioritizes community reporter experience (non-technical mobile users) over architectural purity. Hidden version headers create debugging friction ("Why does this work in Postman but not the mobile app?"), violating ADR-006 operational simplicity goal. Additionally, DigitalOcean CDN (ADR-012) doesn't support advanced Vary header caching without upgrade to expensive Business plan ($200/month vs $15/month), breaking budget constraint.

---

#### **Alternative 2: Query Parameter Versioning (`/reports?api_version=v1`)**

**Advantages:**
- **Explicit Versioning**: Version visible in URL like path versioning
- **Single Endpoint**: Base URL remains stable (`/reports`)
- **Easy Testing**: Version switchable via query parameter in browser/Postman

**Disadvantages:**
- **Not RESTful**: Query parameters traditionally used for filtering/pagination, not resource identification
- **Caching Fragmentation**: Every version creates separate cache entry (CDN cache hit rate drops)
- **URL Ugliness**: `?api_version=v1` suffix on every endpoint (documentation verbosity)
- **Parameter Pollution**: Conflicts with resource-specific query parameters (e.g., `/reports?status=verified&api_version=v1`)
- **Default Version Confusion**: Ambiguous behavior when parameter omitted
- **Security Risk**: Version parameter in URL logs creates version enumeration attack surface

**Why Rejected:**
Query parameter versioning **violates REST principles** (resource identity changes based on filtering parameter) and creates **cache fragmentation** that degrades DigitalOcean CDN effectiveness (ADR-012 performance optimization). Additionally, mixing version parameters with resource filters (`?status=verified&api_version=v2&$orderby=createdAt`) creates confusing URL soup that violates Microsoft REST API Guidelines (ADR-005 current standard). Finally, version in query string appears in server logs, creating privacy concern (audit log bloat per ADR-008 compliance).

---

#### **Alternative 3: Subdomain Versioning (`v1.api.bahariwatch.ke/reports`)**

**Advantages:**
- **Complete Isolation**: Each version on separate subdomain (independent deployments, DNS routing)
- **Version-Specific Infrastructure**: Can allocate different resources per version (e.g., v1 on cheap server, v2 on fast server)
- **CORS Simplicity**: Each version has own CORS configuration
- **Blue-Green Deployment**: DNS switch enables instant version cutover

**Disadvantages:**
- **SSL Certificate Management**: Separate wildcard certificate for each subdomain ($50/year per cert) or complex Let's Encrypt automation
- **DNS Propagation Delay**: Version switches require DNS TTL wait (5 minutes minimum), breaks instant rollback
- **CORS Configuration**: Browsers treat `v1.api.bahariwatch.ke` and `v2.api.bahariwatch.ke` as different origins (complex CORS preflight handling)
- **Mobile App Configuration**: Hard-coded base URL in mobile app (v1.api.bahariwatch.ke) prevents dynamic version switching
- **Cost**: Multiple DigitalOcean App Platform instances ($15/month each) vs single instance with path-based routing ($15/month total)

**Why Rejected:**
Subdomain versioning **multiplies infrastructure costs** (3 versions × $15/month = $45/month) that exceed total budget allocation for API Gateway ($15/month per ADR-012). Additionally, separate subdomains create **CORS complexity** for web dashboard (must whitelist `v1.api.bahariwatch.ke`, `v2.api.bahariwatch.ke`, `v3.api.bahariwatch.ke`), violating ADR-008 security simplicity principle. Finally, DNS-based routing introduces **5-minute propagation delay** that breaks <5 second alert delivery SLO (ADR-006) during emergency version rollbacks.

---

#### **Alternative 4: No Versioning (Breaking Changes Allowed)**

**Advantages:**
- **Simplicity**: No version management overhead
- **Agility**: Deploy breaking changes immediately without migration planning
- **Single Codebase**: No parallel version support in API Gateway

**Disadvantages:**
- **Client Breakage**: Every breaking change breaks all mobile app installations (10,000+ users)
- **Forced Updates**: Users must update app immediately or lose reporting capability (violates ADR-008 accessibility)
- **App Store Delays**: Apple app review takes 2-7 days (breaking changes create multi-day outage window)
- **Government Integration Failures**: 12-month integration cycles mean breaking changes strand government systems
- **No Rollback**: Can't rollback breaking change without breaking clients that adopted new API

**Why Rejected:**
No versioning strategy **violates proposal's core requirement** for offline-first community reporting (page 51: "mobile application enables small-scale fishers to capture, geotag, and anonymously submit evidence"). Breaking changes that force app updates create **enforcement gaps** (users can't report IUU fishing during 2-7 day app store review), costing KSh 2.9B annual economic loss (proposal page 189). Additionally, unversioned API prevents **gradual rollout** of privacy enhancements (ADR-008 GDPR compliance), creating legal risk for pilot study.

### Trade-Off Analysis

| Dimension | URL Path Versioning | Header Versioning | Query Parameter | Subdomain | No Versioning |
|-----------|---------------------|-------------------|-----------------|-----------|---------------|
| **Discoverability** (higher is better) | ⭐⭐⭐⭐⭐ Visible in URL | ⭐⭐ Hidden in headers | ⭐⭐⭐⭐ Visible in URL | ⭐⭐⭐⭐ Visible in domain | ⭐ Version unknown |
| **Client Simplicity** (lower complexity is better) | ⭐⭐⭐⭐⭐ Base URL change | ⭐⭐⭐ Custom headers | ⭐⭐⭐⭐ Query param | ⭐⭐ Subdomain config | ⭐⭐⭐⭐⭐ No changes needed |
| **Caching Compatibility** (higher is better) | ⭐⭐⭐⭐⭐ URL-based | ⭐⭐ Vary header | ⭐⭐⭐ URL-based | ⭐⭐⭐⭐⭐ DNS-based | ⭐⭐⭐⭐⭐ Single cache |
| **Cost** (monthly) | ⭐⭐⭐⭐⭐ $15/month | ⭐⭐⭐⭐⭐ $15/month | ⭐⭐⭐⭐⭐ $15/month | ⭐ $45/month (3 versions) | ⭐⭐⭐⭐⭐ $15/month |
| **Rollback Speed** (faster is better) | ⭐⭐⭐⭐⭐ Instant routing | ⭐⭐⭐⭐⭐ Instant routing | ⭐⭐⭐⭐⭐ Instant routing | ⭐⭐ DNS propagation (5min) | ⭐ Can't rollback |

| **Client Breakage Risk** (lower is better) | ⭐⭐⭐⭐⭐ Isolated versions | ⭐⭐⭐⭐ Header default risk | ⭐⭐⭐⭐ Param default risk | ⭐⭐⭐⭐⭐ Complete isolation | ❌ All clients break |

**Justification:**
URL path versioning provides the **optimal balance** for BahariWatch's constraints:
1. **Discoverability**: Version visible in API logs, monitoring dashboards, browser address bar (simplifies debugging for non-technical BMU officers)
2. **Client Simplicity**: Mobile app changes base URL from `/v1/` to `/v2/` (single line code change), no custom header management
3. **Caching**: DigitalOcean CDN caches `/v1/reports` and `/v2/reports` separately (no Vary header complexity)
4. **Cost**: Single API Gateway instance handles both versions via path routing ($15/month vs $45/month for subdomains)
5. **Rollback**: Instant routing change in Kong/Nginx (no DNS propagation delay)
6. **OpenAPI**: Versions expressed as separate `servers` blocks (standard spec, generates clean docs)

URL path versioning sacrifices RESTful purity (version embedded in resource URL), but **prioritizes operational pragmatism over architectural idealism**, aligning with ADR-012 DigitalOcean deployment simplicity and ADR-006 sub-5-second performance SLO.

## Consequences

### Positive

1. **Client Stability**: 15-month deprecation lifecycle gives mobile apps 6+ months to migrate before breaking changes (app store review delays accommodated)
2. **Zero-Downtime Migrations**: URL path routing enables instant version cutover without DNS propagation delays (<5 second SLO maintained per ADR-006)
3. **Gradual Privacy Enhancements**: Can deploy GDPR improvements (ADR-008) to v2 while v1 remains stable (compliance without disruption)
4. **Government Integration Compatibility**: 12-24 month lifecycle matches procurement cycles (Kenya Coast Guard integration survives version changes)
5. **Cost Efficiency**: Single API Gateway instance handles all versions via path routing ($15/month vs $45/month subdomain approach)
6. **Debugging Simplicity**: Version visible in logs, monitoring dashboards, browser address bar (non-technical BMU officers can report "I'm using v1")
7. **Cache Optimization**: CDN caches `/v1/reports` and `/v2/reports` separately (no Vary header complexity, 80%+ cache hit rate)
8. **Automated Governance**: Fitness functions (ADR-010) validate backward compatibility before deployment (prevents accidental breaking changes)
9. **Migration Incentives**: Higher rate limits for v2 (1500 vs 1000 req/hr) incentivize adoption (carrot approach vs stick)
10. **Event Schema Alignment**: RabbitMQ events versioned in parallel (ADR-015), maintains consistency across API and messaging layers
11. **Rollback Safety**: Can instantly revert v2 to v1 via routing rule change (no DNS propagation, no client redeployment)
12. **Documentation Clarity**: OpenAPI spec generates separate docs for v1 and v2 (reduces migration confusion, side-by-side comparison)

### Negative

1. **Operational Overhead**: 15-month deprecation lifecycle requires client tracking, email campaigns, usage monitoring (strains 6-month pilot timeline)
2. **Parallel Maintenance**: Must maintain v1 and v2 codepaths simultaneously (2× regression testing, security patches for both versions)
3. **URL Verbosity**: `/v1/reports` instead of `/reports` (extra 3 characters per URL, documentation clutter)
4. **Version Sprawl Risk**: Without strict governance, could accumulate v1, v2, v3, v4 simultaneously (increase surface area for vulnerabilities)
5. **Client Migration Friction**: Users must explicitly change base URL from `/v1/` to `/v2/` (requires app update, not automatic)
6. **Event Consumer Complexity**: Matching Service must handle both `report.submitted.v1` and `report.submitted.v2` events (duplicate consumer logic)
7. **Storage Growth**: Archived OpenAPI specs for v1, v2, v3 accumulate over time (documentation repository bloat)
8. **Testing Multiplication**: Every API change requires validation against current version AND deprecated versions (2-3× test suite execution time)
9. **Rate Limit Enforcement**: Must track rate limits per version per client (API Gateway rule complexity increases)
10. **Version Enumeration**: Attackers can probe `/v1/`, `/v2/`, `/v3/` to discover supported versions (security disclosure, but low risk)

### Neutral

1. **RESTful Purity Violation**: URL path versioning embeds version in resource identifier (violates REST principles, but pragmatic trade-off)
2. **Client Update Requirement**: Mobile apps must update base URL to adopt new version (explicit migration vs automatic, transparency benefit)
3. **Documentation Duplication**: Must maintain separate docs for v1 and v2 (extra work, but clarifies migration path)
4. **Version Negotiation Absence**: No automatic version selection based on client capabilities (client must explicitly request version, simpler but less intelligent)

### Fitness Functions

#### **Build-Time: Backward Compatibility Validation**
```python
# tests/api/test_backward_compatibility.py
import json
import jsonschema
import pytest
from deepdiff import DeepDiff

def test_v1_schema_not_broken():
    """Validate v1 OpenAPI schema hasn't changed (breaking compatibility)"""
    # Load archived v1 schema (baseline)
    with open('docs/api/v1/openapi.yml') as f:
        v1_baseline = yaml.safe_load(f)
    
    # Load current v1 schema (potentially modified)
    with open('docs/api/openapi.yml') as f:
        v1_current = yaml.safe_load(f)
    
    # Compare schemas (only v1 paths)
    v1_baseline_paths = {k: v for k, v in v1_baseline['paths'].items() if k.startswith('/v1/')}
    v1_current_paths = {k: v for k, v in v1_current['paths'].items() if k.startswith('/v1/')}
    
    diff = DeepDiff(v1_baseline_paths, v1_current_paths, ignore_order=True)
    
    # Assert no fields removed, no types changed
    assert 'dictionary_item_removed' not in diff, f"Breaking change: Fields removed from v1: {diff}"
    assert 'type_changes' not in diff, f"Breaking change: Types changed in v1: {diff}"
    
def test_v1_response_compatible_with_v2():
    """Validate v2 responses can be safely consumed by v1 clients (additive only)"""
    # Load v1 and v2 Report response schemas
    v1_report_schema = load_schema('v1', 'Report')
    v2_report_schema = load_schema('v2', 'Report')
    
    # Generate sample v2 response
    v2_response = {
        "id": "rpt-001",
        "latitude": -4.0435,
        "longitude": 39.6682,
        "photoUrl": "/media/reports/rpt-001.jpg",
        "status": "pending",
        "verificationStatus": "pending",  # ← New field in v2
        "createdAt": "2025-05-15T14:30:00Z"
        # Note: userId removed in v2 (breaking change, requires new major version)
    }
    
    # Validate v2 response against v1 schema (should pass if only additive changes)
    # v1 clients ignore unknown fields per JSON best practices
    try:
        # Remove v2-specific fields before validating against v1 schema
        v1_compatible = {k: v for k, v in v2_response.items() if k in v1_report_schema['required'] + v1_report_schema['properties'].keys()}
        jsonschema.validate(instance=v1_compatible, schema=v1_report_schema)
    except jsonschema.ValidationError as e:
        pytest.fail(f"v2 response breaks v1 compatibility: {e}")
```

### Security Implications

1. **Version Enumeration**: Attackers can probe `/v1/`, `/v2/`, `/v3/` to discover supported versions
   - **Mitigation**: Rate limit version enumeration attempts (10 probes/minute from same IP)
   - **Monitoring**: Alert if single IP probes >5 versions in 60 seconds

2. **Token Version Binding**: JWT tokens scoped to specific API version (prevents v1 token from accessing v2)
   - **Implementation**: `api_version: "v1"` claim in JWT payload
   - **Validation**: API Gateway validates token `api_version` matches request path `/v1/...` or `/v2/...`

3. **Deprecation Information Disclosure**: Sunset headers reveal API lifecycle stages
   - **Risk**: Low (version lifecycle is public information, documented in API portal)
   - **Benefit**: Transparency helps legitimate clients plan migrations

4. **Parallel Version Attack Surface**: Must patch security vulnerabilities in v1 AND v2 simultaneously
   - **Mitigation**: Automated security scanning runs against all active versions (Snyk, Dependabot)
   - **Policy**: Security patches deployed to deprecated versions within 48 hours (same SLA as active versions)

### Data Privacy Implications

1. **Version-Specific Privacy Enhancements**: v2 removes `userId` field from responses (ADR-008 GDPR compliance)
   - **v1 Clients**: Continue receiving `userId` during deprecation period (backward compatibility)
   - **v2 Clients**: Never receive `userId` (stricter privacy by default)
   - **Migration Incentive**: Privacy-conscious users encouraged to upgrade to v2 (GDPR compliance marketing)

2. **Deprecation Emails**: Client outreach emails contain minimal PII (API key holder email only)
   - **Compliance**: Emails include unsubscribe link per GDPR Article 21 (Right to Object)
   - **Retention**: Deprecation email logs deleted after version retirement (minimize data exposure)

3. **Version Usage Analytics**: Track API version adoption per client without identifying individual users
   - **Aggregation**: Metrics grouped by client type (mobile, web, government) not individual devices
   - **Purpose**: Measure migration success rate, not user surveillance

```bash
#!/bin/bash
# rollback-v2-deployment.sh

# Emergency rollback if v2 breaking changes detected

# 1. Check error rate spike
V2_ERROR_RATE=$(curl -s 'http://prometheus:9090/api/v1/query?query=sum(rate(http_requests_total{path=~"/v2/.*",status=~"4.."}[5m]))/sum(rate(http_requests_total{path=~"/v2/.*"}[5m]))' | jq -r '.data.result[0].value[1]')

    kubectl patch service api-gateway \
      --patch '{"spec":{"selector":{"version":"v1"}}}'
    
    # 3. Update v2 routes to return 503 Service Unavailable

      -d "plugins.response-transformer.config.replace.body={\"error\":\"v2 temporarily unavailable, use v1\"}"

        }
```
