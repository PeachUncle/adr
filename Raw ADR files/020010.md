# ADR-007: Real-Time Subscription Strategy - Supabase Postgres Changes

## Status

Accepted

## Context

The chat application requires real-time updates for messages, channels, and user changes. Multiple approaches exist for implementing real-time functionality, including WebSockets, Server-Sent Events (SSE), polling, and database change streams. The application needs to handle concurrent users seeing updates instantly while maintaining data consistency.

## Decision

We will use Supabase's real-time subscriptions via `postgres_changes` events to listen for database changes and update the UI automatically.

## Rationale

### Chosen: Supabase Real-Time Subscriptions

- **Built-in Infrastructure**: Leverages Supabase's managed real-time engine
- **Database-Driven**: Changes originate from database, ensuring consistency
- **Automatic Scaling**: Supabase handles connection management and scaling
- **Type Safety**: Payload matches database schema exactly
- **Row Level Security**: Subscriptions respect RLS policies automatically
- **Multi-Table Support**: Single connection can listen to multiple tables

### Rejected Alternatives

**Custom WebSocket Server**

- ❌ **Infrastructure Overhead**: Need to manage WebSocket server, scaling, reconnection logic
- ❌ **Complexity**: Manual message broadcasting, user session management
- ❌ **Maintenance**: Additional service to deploy and monitor
- ❌ **Security**: Need to implement authentication and authorization separately

**Server-Sent Events (SSE)**

- ❌ **Unidirectional**: Only server-to-client, need separate API for client actions
- ❌ **Browser Limits**: Connection limits per domain (6 in most browsers)
- ❌ **Complexity**: Need custom event routing and user targeting

**Polling (HTTP Requests)**

- ❌ **Performance**: Constant unnecessary requests when no changes
- ❌ **Latency**: Updates delayed by polling interval
- ❌ **Resource Usage**: High server load and bandwidth consumption
- ❌ **Battery Impact**: Continuous requests drain mobile device batteries

**GraphQL Subscriptions**

- ❌ **Overhead**: Additional GraphQL layer over existing REST API
- ❌ **Complexity**: Need to set up GraphQL server and subscription resolvers
- ❌ **Learning Curve**: Team already familiar with Supabase patterns

## Implementation Details

### Subscription Setup

```javascript
// Listen for message changes
const messageListener = supabase
  .channel("public:messages")
  .on(
    "postgres_changes",
    {
      event: "INSERT",
      schema: "public",
      table: "messages",
    },
    payload => handleNewMessage(payload.new)
  )
  .on(
    "postgres_changes",
    {
      event: "DELETE",
      schema: "public",
      table: "messages",
    },
    payload => handleDeletedMessage(payload.old)
  )
  .subscribe();
```

### Event Types Handled

- **INSERT**: New messages, channels, users
- **DELETE**: Removed messages, channels
- **UPDATE**: User profile changes (handled via wildcard '\*' event)

### Connection Management

- **Single Hook**: `useStore` manages all subscriptions in one place
- **Cleanup**: Subscriptions removed on component unmount
- **Reconnection**: Supabase handles automatic reconnection
- **Error Handling**: Failed subscriptions logged, app continues functioning

### Data Flow

```
User Action (addMessage)
→ Supabase API Call
→ Database Insert
→ Postgres Change Event
→ Supabase Real-time Engine
→ Client Subscription Handler
→ React State Update
→ UI Re-render
```

## Consequences

### Positive

- **Zero Configuration**: No additional infrastructure setup required
- **Automatic Scaling**: Supabase handles connection limits and load balancing
- **Consistent State**: All clients receive identical updates from single source of truth
- **Security**: RLS policies automatically filter subscription events
- **Performance**: Efficient binary protocol, minimal bandwidth usage
- **Reliability**: Built-in reconnection and error handling
- **Development Speed**: Simple API, no custom server code needed

### Negative

- **Vendor Lock-in**: Tightly coupled to Supabase real-time infrastructure
- **Limited Customization**: Cannot modify subscription behavior or add custom routing
- **Network Dependency**: Poor connections affect real-time experience
- **Debugging**: Less visibility into subscription internals compared to custom solution

### Performance Characteristics

- **Latency**: ~100-200ms from database change to UI update
- **Throughput**: Handles hundreds of concurrent connections per project
- **Bandwidth**: ~1KB per message event (including metadata)
- **Memory**: Minimal client-side overhead, subscriptions are lightweight

## Security Considerations

### Row Level Security Integration

```sql
-- Messages are filtered by channel access automatically
CREATE POLICY "Users can view messages in accessible channels" ON messages
  FOR SELECT USING (
    channel_id IN (
      SELECT id FROM channels
      WHERE /* user has access */
    )
  );
```

### Authentication

- Subscriptions use same JWT token as API calls
- Unauthenticated users receive no events
- Token expiration automatically closes subscriptions

## Alternative Patterns Considered

### Optimistic Updates + Real-time Sync

- Considered showing immediate updates, then syncing with real-time events
- Rejected due to complexity of deduplication and conflict resolution
- Documented in [ADR-003: No Optimistic Updates](./adr-003-no-optimistic-updates.md)

### Channel-Specific Subscriptions

- Considered subscribing only to current channel's messages
- Rejected because users need notifications from all accessible channels
- Current approach filters events in React, not at subscription level
