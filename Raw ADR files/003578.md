# ADR-006: Use bcrypt for Password Hashing

## Status
**Status:** Approved

## Context and Problem Statement
One of our non-functional requirements is security. Therefore, our application will require secure storage of user passwords to protect user accounts and sensitive data in line with regulations. It is essential to use a hashing algorithm for password security that provides robustness against modern attacks like brute force, rainbow tables, and dictionary attacks. We must decide on a specific approach to password hashing and ensure its impact on system performance remains within acceptable limits.

### Problem being solved:
- Securing user passwords in storage and preventing unauthorized access.
- Ensuring the application meets security best practices for handling sensitive user data.
- Maintaining application performance, with hashing operations contributing minimal overhead. 

### Driving Forces and Decision Drivers
The key factors influencing this decision include:

- **Security**: Protecting user credentials from being compromised in case of a data breach by choosing a secure hashing algorithm designed for password storage.  
- **Compliance**: Adhering to industry standards and regulations like GDPR, DPA, and PCI DSS that require secure password handling and proper handling of user data.  
- **Performance**: Ensuring password hashing does not significantly impact overall application performance, targeting less than 150–200ms overhead per request and adhering to a maximum 2-second load time benchmark.  
- **Resilience**: Employing a hashing mechanism that provides resistance against brute force, rainbow table, and dictionary attacks.  
- **Ease of adoption and implementation**: Selecting a solution that is easy to integrate into the current system, maintain within the existing codebase, and avoids excessive complexity.  
- **Industry acceptance**: Favouring algorithms with broad adoption and validation by the security community.  

## Options Considered
- **Option 1: Use plaintext passwords (no hashing)**  
  - Storing plaintext passwords is inherently insecure and exposes user credentials directly if the database is compromised. This option is unacceptable.
  
- **Option 2: Use general-purpose hashing algorithms (e.g., SHA-256)**  
  - Hashing passwords with a general-purpose cryptographic hash function like SHA-256 provides some security but lacks features such as salting and work factor adjustment. This approach is not ideal for password storage.
  
- **Option 3: Use bcrypt**  
  - bcrypt is a password-specific hashing algorithm that includes features like salting, adaptive complexity, and built-in resistance to brute force attacks. It is widely used and recommended for password storage. 

## Decision Outcome
We have decided to use **bcrypt** for hashing and storing passwords.

### Why is this the best option?
- **Security**: bcrypt is specifically designed for password storage, incorporating features like salting and computational expense to thwart attacks.
- **Performance**: In testing (e.g., Postman API requests), bcrypt demonstrated an acceptable 150–200ms additional time per request, remaining well below the 2-second load time benchmark.
- **Adaptive Work Factor**: bcrypt's cost factor allows the algorithm to remain effective as computing power increases, making it future-proof against technological advancements.
- **Broad Adoption**: bcrypt is a well-tested and widely accepted solution in the security community, providing confidence in its robustness.
- **Ease of Implementation**: bcrypt is easy to integrate with most modern programming frameworks and libraries, requiring minimal effort to adopt.

## Consequences
### Positive Outcomes:
- Strong password protection, reducing the risk of compromised accounts in case of data breaches.
- Compliance with industry security standards and best practices.
- Future-proofing password storage by adjusting bcrypt's cost factor over time.

### Negative Outcomes:
- Slightly higher computational cost compared to general-purpose hash functions, which may impact performance on systems with extremely high authentication traffic.
- Initial development effort to integrate bcrypt into the application.

### What will be affected:
- **Codebase**: The authentication system will be updated to hash passwords using bcrypt during user registration and login.
- **Performance**: A minor increase in computational time for hashing passwords, which is an acceptable tradeoff for enhanced security.
- **Performance**: Testing shows bcrypt's impact remains within acceptable bounds, contributing less than 200ms per request to overall response time.

### How does this decision affect future systems:
- Future systems will inherit a secure and scalable password storage mechanism, reducing the need for retrofitting security measures later.
- The ability to adjust bcrypt's cost factor ensures continued security as computational power grows.

### Mitigation Strategy:
- Conduct performance testing to ensure the chosen bcrypt cost factor does not significantly impact authentication times, or exceed the 200ms benchmark. Use JMeter with concurrent users.
- Monitor advancements in password hashing algorithms to ensure continued adherence to best practices.

## Confirmation
We will validate this decision by:
1. Testing the bcrypt implementation for correctness and performance.
2. Performing security reviews to ensure proper password handling.
3. Conducting penetration testing to identify and address vulnerabilities.

## Pros and Cons

### Pros:
- **Enhanced Security**: Designed to resist brute force attacks and equipped with salting to defend against rainbow tables.
- **Future-proof**: Adjustable cost factor ensures the algorithm remains secure against advancements in computational power.
- **Broad Adoption**: Trusted and tested by the security community, ensuring reliability.
- **Ease of Use**: Supported by most modern frameworks, making it simple to integrate.
- **Minimal Performance Impact**: Testing confirms bcrypt adds only 150–200ms per request, maintaining a total load time well below the 2-second benchmark.

### Cons:
- **Performance Overhead**: Higher computational cost than general-purpose hash functions, though this is a tradeoff for security.
- **Learning Curve**: Some initial effort may be required to understand and configure bcrypt effectively.
