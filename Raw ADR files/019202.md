# ADR-005: JWT Authentication Strategy

## Status

Accepted

## Context

The Trama platform requires a stateless authentication mechanism that can scale horizontally without requiring session storage or sticky sessions. As a project focused on modern web development practices, we need an authentication approach that:

- Works seamlessly with a React SPA frontend
- Supports stateless API authentication
- Enables horizontal scaling without shared session state
- Provides reasonable security
- Is widely adopted and well-documented
- Allows for future mobile app integration

Traditional session-based authentication would require server-side session storage (Redis, database) and sticky sessions for load balancing, adding complexity and infrastructure dependencies. We need a solution that balances security, simplicity, and scalability.

## Decision

We will use **JWT (JSON Web Tokens) with refresh token rotation** for authentication:

**Access Tokens:**
- Short-lived JWT tokens (15 minutes expiration)
- Contain user ID, email, and roles
- Signed with HS256 algorithm
- Stored in memory on the client (not localStorage)
- Sent in Authorization header: `Bearer <token>`

**Refresh Tokens:**
- Long-lived tokens (7 days expiration)
- Stored in HTTP-only, secure cookies
- Used to obtain new access tokens
- Rotated on each use (one-time use)
- Stored in database with user association
- Can be revoked for logout/security

**Token Flow:**
1. User logs in → Receive access token + refresh token
2. Client stores access token in memory
3. Client stores refresh token in HTTP-only cookie
4. API requests use access token in Authorization header
5. When access token expires → Use refresh token to get new pair
6. Refresh token is rotated (old one invalidated, new one issued)

**Security Measures:**
- HTTPS only in production
- HTTP-only cookies for refresh tokens (prevents XSS)
- Refresh token rotation (prevents replay attacks)
- Refresh token family tracking (detects token theft)
- Configurable token expiration times
- Password hashing with bcrypt (cost factor 12)

## Consequences

### Positive

- **Stateless Authentication**: No server-side session storage required, enabling horizontal scaling
- **SPA-Friendly**: Works naturally with React and future mobile apps
- **Scalability**: API instances don't need to share session state
- **Standard Approach**: JWT is widely adopted with extensive tooling and libraries
- **Flexible Claims**: Can include user roles and metadata in token payload
- **Cross-Domain Support**: Enables future microservices architecture
- **Offline Validation**: API can validate tokens without database lookup (for access tokens)
- **Learning Value**: Industry-standard authentication pattern

### Negative

- **Token Management Complexity**: Client must handle token refresh logic
- **Token Size**: JWTs are larger than session IDs (sent with every request)
- **Revocation Challenges**: Cannot immediately revoke access tokens (must wait for expiration)
- **Refresh Token Storage**: Requires database table for refresh token management
- **XSS Vulnerability**: Access tokens in memory are vulnerable if XSS occurs
- **Implementation Complexity**: More complex than simple session-based auth
- **Token Theft Risk**: Stolen tokens are valid until expiration

### Neutral

- **15-Minute Access Token Expiration**: Balances security (short-lived) with UX (not too frequent refresh)
- **7-Day Refresh Token Expiration**: Balances security with user convenience (weekly re-login)
- **Database Dependency for Refresh**: Refresh tokens require database lookup, but this is infrequent
- **No Automatic Logout**: Users remain logged in until refresh token expires (unless manually logged out)

## Implementation Notes

**Libraries:**
- `System.IdentityModel.Tokens.Jwt` for token generation/validation
- `Microsoft.AspNetCore.Authentication.JwtBearer` for middleware
- `BCrypt.Net-Next` for password hashing

**Configuration:**
- JWT secret stored in environment variables (not in code)
- Different secrets for development and production
- Token expiration times configurable via appsettings.json

**Database Schema:**
```sql
CREATE TABLE RefreshTokens (
    Id UUID PRIMARY KEY,
    UserId UUID NOT NULL REFERENCES Users(Id),
    Token VARCHAR(500) NOT NULL,
    ExpiresAt TIMESTAMP NOT NULL,
    CreatedAt TIMESTAMP NOT NULL,
    RevokedAt TIMESTAMP NULL,
    ReplacedByToken VARCHAR(500) NULL
);
```

**Client Implementation:**
- Automatic token refresh
- Axios interceptors for adding Authorization header
- Automatic retry on 401 with token refresh

## Alternatives Considered

**Session-Based Authentication:**
- Pros: Simpler implementation, immediate revocation, smaller cookies
- Cons: Requires session storage (Redis/database), sticky sessions for load balancing, not SPA-friendly
- Rejected: Adds infrastructure complexity and limits scalability

**OAuth 2.0 with External Provider:**
- Pros: Offloads authentication, social login support
- Cons: External dependency, more complex, requires internet connectivity
- Rejected: Overkill for MVP, want to learn authentication implementation

**Opaque Tokens with Token Introspection:**
- Pros: Better revocation, smaller tokens
- Cons: Requires database lookup on every request, reduces scalability
- Rejected: Defeats purpose of stateless authentication

**Longer-Lived Access Tokens:**
- Pros: Fewer refresh requests, simpler client logic
- Cons: Larger security window if token stolen, harder to revoke
- Rejected: Security risk outweighs convenience
