# ADR 1: Authentication via Username/Password Instead of SSO

**Date:** 2025-24-04  
**Status:** Accepted  

## Summary  
We opted to implement a username/password authentication system rather than using a Single Sign-On (SSO) provider such as Google. This decision stemmed from several compounding factors including development time constraints, repeated integration issues with the Google SDK, and insufficient documentation that hindered troubleshooting. Although SSO typically provides a better user experience by allowing seamless login through existing accounts, we prioritised speed and reliability over advanced features to ensure the authentication layer was functional and stable for the MVP.

## Context  
User authentication is a critical component of our system, required to protect user data and restrict access to authenticated individuals. At the start of the project, the team evaluated SSO solutions to streamline login and improve security. Google’s SSO was considered a viable option given its widespread adoption and familiarity among users. However, attempts to implement it encountered significant roadblocks. These included SDK compatibility issues, inconsistent token behavior, and unclear documentation which slowed down development efforts. As authentication was on the project’s critical path, the team decided it was more pragmatic to switch to a known and proven approach using email and password credentials.

## Decision  
We decided to implement a basic username/password login flow using traditional form-based authentication. This involved creating secure login and registration endpoints on the backend, hashing passwords using industry-standard methods, and issuing JSON Web Tokens (JWTs) upon successful authentication. While this method lacks the user convenience and federated login capabilities of SSO, it is easy to test, well-documented, and can be implemented without external dependencies. We plan to revisit SSO integration in a future iteration once the MVP is complete and stable.

## Consequences  
**Advantages:**  
- Rapid implementation enabled us to stay on track with the MVP timeline.  
- Avoided complex SDK integration and reduced technical risk.  
- Full control over the login process, with no reliance on third-party availability.

**Disadvantages:**  
- Requires users to manage a separate set of credentials.  
- Provides slightly lower convenience and security compared to federated authentication.  
- Additional effort will be needed to retrofit SSO in the future.
