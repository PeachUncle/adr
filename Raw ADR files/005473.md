# ADR-029: Comprehensive Observability Strategy

**Status**: Accepted  
**Date**: 2025-10-16  
**Decision Makers**: Architecture Team, DevOps Team, Trading Operations  
**Related ADRs**: ADR-021 (GCP Operations), ADR-024 (Cost Management), ADR-016 (Cloud Run), ADR-026 (GCP Architecture)

## Context

The multi-agent options trading system requires comprehensive observability to ensure reliability, compliance, rapid incident response, and continuous optimization. The system operates with real capital at risk across multiple distributed agents, making visibility into system health, performance, and behavior critical for operational success.

### Business Requirements

1. **Financial Risk Management**: Real-time visibility into trading decisions, risk metrics, and portfolio positions
2. **Regulatory Compliance**: Audit trails for all trading actions, API calls, and data access
3. **Operational Reliability**: 99.5% uptime SLO requiring rapid incident detection and resolution
4. **Cost Optimization**: Monitoring of cloud resource consumption and trading costs
5. **Performance Optimization**: Sub-second latency for critical paths (market data, Greeks calculation, risk checks)

### Technical Challenges

1. **Distributed Architecture**: 11+ agents communicating asynchronously via Pub/Sub
2. **High Cardinality**: Metrics with multiple dimensions (agent, symbol, strategy, environment)
3. **Volume**: 100+ metrics per minute during market hours, 10K+ log entries/hour
4. **Correlation**: Need to correlate logs, metrics, and traces across agent boundaries
5. **Retention**: Balance between data retention needs (compliance, debugging) and storage costs

## Decision

We adopt a **unified observability strategy** using Google Cloud Operations Suite with structured logging, comprehensive metrics, distributed tracing, and automated alerting. The strategy emphasizes:

1. **Structured Logging** with Cloud Logging for all agent activities
2. **Metrics-Driven Monitoring** with Cloud Monitoring for performance and health
3. **Distributed Tracing** with Cloud Trace for request flow analysis
4. **Proactive Alerting** with Cloud Monitoring alert policies
5. **Unified Dashboards** for real-time operational visibility
6. **SLI/SLO Framework** for objective performance measurement

## Architecture

### 1. Logging Architecture

#### 1.1 Log Levels and Usage

| Level | Usage | Examples | Retention |
|-------|-------|----------|-----------|
| DEBUG | Development troubleshooting | Variable values, state transitions | 7 days |
| INFO | Normal operations | Task completion, API calls | 30 days |
| WARNING | Recoverable issues | Retry attempts, fallback usage | 90 days |
| ERROR | Failures requiring attention | API failures, validation errors | 1 year |
| CRITICAL | System-level failures | Agent crashes, data corruption | 2 years |

#### 1.2 Structured Log Format

All logs use JSON-structured format with standardized fields:

```json
{
  "timestamp": "2025-10-16T14:32:15.123456Z",
  "severity": "INFO",
  "agent_id": "portfolio_orchestrator",
  "agent_version": "1.2.3",
  "environment": "production",
  "trace_id": "a1b2c3d4e5f6",
  "span_id": "1234567890ab",
  "task_id": "task_20251016_143215",
  "message": "Stock selection task completed",
  "context": {
    "symbols_analyzed": 150,
    "symbols_selected": 8,
    "duration_ms": 1250
  },
  "labels": {
    "component": "stock_selection",
    "market_regime": "high_volatility"
  }
}
```

#### 1.3 Log Correlation

- **Trace ID**: Propagated through all agent communications for end-to-end request tracking
- **Task ID**: Unique identifier for logical trading operations
- **Session ID**: Links logs across multiple tasks in a trading session
- **Symbol**: Trading symbol for filtering/correlation

### 2. Metrics Architecture

#### 2.1 Agent-Level Metrics

**Task Execution Metrics**:
- `agent.task.duration` (histogram): Task execution time with p50, p95, p99 percentiles
- `agent.task.success_rate` (gauge): Success percentage over 1-minute windows
- `agent.task.failure_count` (counter): Failures by error type
- `agent.state_transitions` (counter): State machine transitions
- `agent.message_latency` (histogram): Inter-agent message processing time

**Resource Metrics**:
- `agent.cpu.utilization` (gauge): CPU usage percentage
- `agent.memory.usage` (gauge): Memory consumption in MB
- `agent.memory.peak` (gauge): Peak memory during task execution
- `agent.container.restart_count` (counter): Container restart events

#### 2.2 Trading Metrics

**Portfolio Metrics**:
- `portfolio.net_liquidation_value` (gauge): Total portfolio value
- `portfolio.total_pl` (gauge): Cumulative profit/loss
- `portfolio.buying_power` (gauge): Available capital
- `portfolio.margin_used` (gauge): Margin utilization
- `portfolio.open_positions` (gauge): Number of open positions

**Position Metrics**:
- `position.delta` (gauge): Portfolio delta by symbol
- `position.gamma` (gauge): Portfolio gamma by symbol
- `position.theta` (gauge): Portfolio theta by symbol
- `position.vega` (gauge): Portfolio vega by symbol
- `position.profit_loss` (gauge): P&L per position

**Trading Activity Metrics**:
- `trading.orders_placed` (counter): Orders submitted by type (open, close)
- `trading.orders_filled` (counter): Successfully executed orders
- `trading.orders_rejected` (counter): Rejected orders by reason
- `trading.execution_slippage` (histogram): Price slippage in basis points
- `trading.trade_commissions` (counter): Cumulative commission costs

#### 2.3 Risk Metrics

- `risk.check.duration` (histogram): Risk validation time
- `risk.violations` (counter): Risk limit breaches by type
- `risk.daily_loss` (gauge): Daily P&L loss
- `risk.portfolio_var` (gauge): Value at Risk calculation
- `risk.concentration_ratio` (gauge): Position concentration metrics

#### 2.4 External Dependency Metrics

**API Metrics**:
- `api.request.duration` (histogram): API response time by provider
- `api.request.count` (counter): API calls by endpoint and status code
- `api.request.errors` (counter): API failures by error type
- `api.rate_limit.remaining` (gauge): Remaining API quota
- `api.circuit_breaker.state` (gauge): Circuit breaker status (open/closed)

**BigQuery Metrics**:
- `bigquery.query.duration` (histogram): Query execution time
- `bigquery.query.bytes_processed` (counter): Data scanned per query
- `bigquery.query.slot_time` (histogram): Slot utilization
- `bigquery.write.rows` (counter): Rows written to tables

### 3. Tracing Architecture

#### 3.1 Trace Propagation

- Cloud Run automatically creates root spans for HTTP requests
- Pub/Sub messages include trace context in message attributes
- Agent SDK automatically propagates trace context across async calls
- Python OpenTelemetry instrumentation for third-party libraries

#### 3.2 Custom Span Creation

Critical operations instrumented with custom spans:
- Stock selection analysis (symbol filtering, scoring, ranking)
- Greeks calculation (per-symbol calculation, aggregation)
- Risk validation (pre-trade checks, portfolio limits)
- Strategy execution (option chain analysis, order generation)
- Portfolio hedging (delta calculation, hedge recommendation)

#### 3.3 Span Attributes

Standard attributes attached to all spans:
- `agent.id`: Agent identifier
- `agent.version`: Agent version
- `task.type`: Type of operation
- `symbol`: Trading symbol (if applicable)
- `strategy`: Strategy name (if applicable)
- `environment`: Deployment environment

### 4. Alerting Architecture

#### 4.1 Alert Categories

| Category | Severity | Response SLA | Escalation |
|----------|----------|--------------|------------|
| Critical Trading | Critical | 5 minutes | Immediate page |
| System Health | High | 15 minutes | Email + Slack |
| Performance Degradation | Medium | 1 hour | Slack notification |
| Cost Anomaly | Medium | 4 hours | Email notification |
| Informational | Low | Next business day | Daily digest |

#### 4.2 Trading Alert Policies

**Critical Alerts**:
- Daily loss exceeds 2% of portfolio value
- Portfolio delta exceeds ±100 per $100K capital
- Risk validation failures >5 in 5 minutes
- Order rejection rate >20% over 10 minutes
- API circuit breaker opens for >2 minutes

**High Priority Alerts**:
- Agent error rate >5% over 5 minutes
- Task duration p95 >30 seconds for critical agents
- Portfolio margin utilization >70%
- Greeks calculation failures >3 consecutive attempts
- Trading session state stuck for >10 minutes

**Performance Alerts**:
- Agent CPU utilization >80% sustained for 5 minutes
- Agent memory usage >90% of limit
- BigQuery query duration >10 seconds for standard queries
- API response time p95 >5 seconds

**Cost Alerts**:
- Daily GCP spend >$150 (exceeds $4,500 monthly budget)
- API usage exceeds 80% of daily quota
- BigQuery bytes processed >100GB in 24 hours
- Cloud Run instance count >20 concurrent instances

#### 4.3 Alert Notification Channels

- **PagerDuty**: Critical trading and system health alerts
- **Slack**: All alerts with severity-based channels
- **Email**: Daily digest and cost anomaly reports
- **Webhooks**: Integration with incident management system

### 6. SLI/SLO Framework

#### 6.1 Service Level Indicators

| SLI | Measurement | Target SLO |
|-----|-------------|-----------|
| **Availability** | % of successful health checks | 99.5% |
| **Latency** | p95 task duration <30s | 95% |
| **Error Rate** | % of failed tasks | <2% |
| **Throughput** | Completed tasks/minute | >20 during market hours |
| **Data Freshness** | Market data age <60s | 99% |

#### 6.2 SLO Monitoring

- **Error Budget**: 0.5% downtime = 3.6 hours/month
- **Burn Rate Alerts**: Alert if error budget consumed >10% in 1 hour
- **SLO Violations**: Automated incident creation for SLO breaches
- **Monthly Review**: SLO performance review and adjustment

### 7. Data Retention and Costs

#### 7.1 Retention Policies

| Data Type | Raw Retention | Aggregated Retention | Compliance Retention |
|-----------|--------------|---------------------|---------------------|
| Logs (DEBUG) | 7 days | N/A | N/A |
| Logs (INFO) | 30 days | N/A | N/A |
| Logs (WARNING) | 90 days | N/A | N/A |
| Logs (ERROR) | 1 year | N/A | N/A |
| Logs (CRITICAL) | 2 years | N/A | N/A |
| Metrics | 7 days raw | 90 days (1-min agg) | 2 years (1-hour agg) |
| Traces | 30 days | N/A | N/A |
| Trading Logs | 2 years | N/A | 7 years (compliance) |

#### 7.2 Cost Management

**Estimated Monthly Costs** (based on production load):
- Cloud Logging: $50-80 (10K log entries/hour, 30-day retention)
- Cloud Monitoring: $30-50 (100+ metrics, 7-day raw retention)
- Cloud Trace: $20-30 (5K traces/day)
- **Total**: ~$100-160/month

**Cost Optimization Strategies**:
- Use log exclusion filters for high-volume DEBUG logs
- Sample traces at 10% for non-critical paths
- Aggregate metrics to 1-minute resolution after 7 days
- Export compliance logs to Cloud Storage (cheaper long-term storage)

## Consequences

### Positive

1. **Operational Visibility**: Comprehensive real-time visibility into system health, performance, and trading activity
2. **Rapid Incident Response**: Proactive alerting and detailed debugging information reduce MTTR
3. **Compliance Assurance**: Audit trails for all trading decisions and system actions
4. **Cost Optimization**: Monitoring of cloud costs enables proactive optimization
5. **Performance Optimization**: Detailed metrics and tracing identify bottlenecks
6. **Unified Platform**: Single observability suite (GCP Operations) simplifies operations

### Negative

1. **Operational Overhead**: Managing 100+ metrics, alerts, and dashboards requires ongoing effort
2. **Cost**: ~$100-160/month for observability infrastructure
3. **Cardinality Management**: High-dimensional metrics require careful label design
4. **Storage Costs**: Long-term log retention for compliance increases storage costs
5. **Alert Fatigue**: Risk of too many alerts desensitizing operators

### Risks

1. **Log Volume**: Market hours may generate higher log volume than estimated, increasing costs
2. **Metric Cardinality**: Adding symbols/strategies could exceed cardinality limits
3. **Alert Tuning**: Initial alert thresholds may require adjustment based on production behavior
4. **Trace Sampling**: 10% sampling may miss critical traces during incident investigation

### Mitigation Strategies

1. **Gradual Rollout**: Deploy observability instrumentation incrementally with monitoring
2. **Cost Budgets**: Set up GCP budget alerts at $120/month with auto-escalation
3. **Regular Review**: Monthly review of alert effectiveness and threshold tuning
4. **Trace Strategy**: Use 100% sampling for critical paths, 10% for informational traces
5. **Documentation**: Maintain runbooks for common alert conditions and resolution steps
