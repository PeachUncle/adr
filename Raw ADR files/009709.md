# 002. HTTP Repository Pattern for Frontend

**Date:** 2024-11-20

**Status:** ✅ **Accepted**

## Context

The frontend needs to persist tasks to a backend API. We need a clean way to abstract HTTP calls so that:

1. Application use cases don't directly call `fetch()`
2. HTTP logic is centralized and testable
3. The Repository interface from the Domain layer can be implemented via HTTP

The challenge: The same `TaskRepository` interface exists in the Domain layer (for backend) and needs an HTTP adapter for the frontend.

## Decision

Create an `HttpTaskRepository` class in the frontend Infrastructure layer that implements the `TaskRepository` interface from the Domain layer.

**Location:** `apps/web/src/infrastructure/persistence/HttpTaskRepository.ts`

**Responsibilities:**
- Converts Domain models to/from HTTP DTOs
- Makes HTTP requests (GET, POST, PUT, DELETE)
- Handles HTTP errors and maps them to domain exceptions
- Implements smart POST/PUT detection:
  - Uses `HEAD /api/tasks/:id` to check if task exists
  - Sends `POST` for new tasks
  - Sends `PUT` for updates

## Rationale

### Why Repository Pattern?

- **Abstraction**: Use cases don't know about HTTP, databases, or external services
- **Testability**: Easy to mock in unit tests
- **Consistency**: Same interface for backend (SQLiteRepository) and frontend (HttpRepository)
- **Flexibility**: Can swap implementations without changing use case code

### Why Smart POST/PUT Detection?

- **Single endpoint for save()**: Frontend use cases call `save()` without knowing if it's create or update
- **Efficient**: Uses HEAD request (no body) to check existence before deciding on HTTP method
- **Resilient**: Falls back to POST if HEAD fails (network issues)

### Why DTO Mapping?

- **Contract separation**: Domain models ≠ API response format
- **Flexibility**: API can evolve independently from domain
- **Type safety**: DTOs define expected API shape with TypeScript types

## Alternatives Considered

1. **Direct fetch() in use cases**
   - ❌ Couples business logic to HTTP
   - ❌ Hard to test without mocking fetch globally
   - ❌ HTTP concerns leak into domain/application layers

2. **HTTP service separate from Repository**
   - ❌ Duplicates abstraction
   - ❌ Breaks consistency with backend repository pattern

3. **Always POST, then PUT based on response**
   - ❌ Less efficient; makes unnecessary POST requests
   - ❌ Requires server to handle POST gracefully on duplicates

## Consequences

### Positive

- ✅ Use cases remain framework-agnostic
- ✅ Easy to mock for testing
- ✅ HTTP concerns centralized in one place
- ✅ Consistent with backend repository pattern
- ✅ Efficient: detects new vs. existing before choosing HTTP method

### Negative

- ❌ Extra HTTP call (HEAD) to determine POST vs. PUT
  - **Mitigation**: HEAD is lightweight; caching layer can reduce calls
- ❌ Requires DTO mapping boilerplate
  - **Mitigation**: Mapper class reusable across endpoints
