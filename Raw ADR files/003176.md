# 11. Persisting Job Assignment in PITAS

Date: 2024-10-14

## Status  
Accepted

## Context  
In the PITAS system, the **pitas-scheduler** needs to assign jobs to workers based on job type and worker availability. 
Once a job is assigned, the assignment must be persisted so that it can be tracked for execution. 
There is a question about whether the **pitas-scheduler** should maintain its own database to store job-worker assignments or rely on existing services for persistence.

## Decision  
We have decided **not to introduce a separate database for the pitas-scheduler**. 
Instead, we will persist job-worker assignments in the **pitas-jobs** service using the `serviceProvider` field in the job record. 
This way, the **pitas-jobs** service holds the source of truth for job-worker assignments, eliminating the need for additional storage in **pitas-scheduler**.


### Implementation
For example, after a worker is assigned, the job document in **pitas-jobs** looks like this (**pitas-sheduler** updates the `serviceProvider` field using the `sendJobAssignedEventPort`):
```json
{
    "_id": "0c2a2ebf-9f05-4016-aa9f-22609bcfadac",
    "jobName": "job1",
    "jobStatus": "ASSIGNED",
    "serviceProvider": "internal-worker-d2e3f918-054d-4238-bf46-73ad9bfa0c0e",
    "inputData": "45-3",
    "outputData": "",
    "jobType": "calculator",
    "jobListName": "pitas-jobs-tutors"
}
```
### Why This Is Sufficient
- By storing the worker assignment directly in **pitas-jobs**, we keep all job-related data in a single service. 
- The **pitas-scheduler** does not need its own persistence layer since it can query **pitas-jobs** for assigned jobs and retrieve the worker ID from the `serviceProvider` field. 
- This approach simplifies the architecture while ensuring that the **pitas-scheduler** can recover job assignments by querying **pitas-jobs** for jobs with `jobStatus = "ASSIGNED"`.

### Reasoning
1. **Data Ownership and Responsibility**: The ownership of job data—including assignments—is naturally tied to **pitas-jobs**, which is responsible for tracking the entire lifecycle of a job. Duplicating this information in the **pitas-scheduler** would introduce potential inconsistencies and violate the principle of **data ownership**—i.e., only one service should own and be responsible for persisting data related to a domain entity (in this case, a job).
 
2. **Coupling and Modularity**: By avoiding a separate persistence layer in the **pitas-scheduler**, we maintain **low coupling** between the scheduler and the data storage concerns. This approach aligns with the principle of **modular architecture**, where each service is responsible for a clear, distinct set of responsibilities. In this case, **pitas-jobs** handles persistence, while **pitas-scheduler** manages job scheduling logic.

3. **Recovery Trade-offs**: One potential advantage of having a separate persistence layer in **pitas-scheduler** would be **self-recovery**. If the scheduler had its own database, it could recover its state (job-worker assignments) after a failure or restart. However, the **event-driven architecture** we currently employ already allows for system-wide recovery, as **pitas-jobs** holds the source of truth for job assignments. The scheduler can query **pitas-jobs** upon restart to retrieve any uncompleted assignments. This offers a recovery mechanism without introducing additional complexity.

4. **Simplicity and Performance**: Avoiding a dedicated database for the scheduler keeps the system **simpler** and reduces the performance overhead associated with maintaining an additional persistence layer. The current approach leverages the existing persistence of **pitas-jobs**, minimizing the risk of **data synchronization issues** and avoiding unnecessary redundancy.

### Alternatives Considered

- **Dedicated Database for `pitas-scheduler`**:  
  A separate database for **pitas-scheduler** would allow the scheduler to store job-worker assignments independently. However, this would introduce additional complexity and data duplication, and we would still need to sync data with **pitas-jobs**.

- **In-Memory Storage in Scheduler**:  
  Another alternative would be to store assignments temporarily in memory within **pitas-scheduler**. However, this would lack persistence across restarts and would require more complex recovery mechanisms.

### Trade-offs
- **Simplicity vs. Independence**: While not having a dedicated database keeps the system simpler, it makes the **pitas-scheduler** dependent on querying **pitas-jobs** for state recovery. This is a trade-off between simplicity and the ability to recover independently.
 
- **Performance vs. Persistence**: The current solution introduces some latency when **pitas-scheduler** queries **pitas-jobs** for job details and worker assignments, but it avoids the overhead of managing its own persistent state.

## Consequences

### Positive Consequences
- **Simplicity**: The solution avoids the complexity of maintaining a separate database in the **pitas-scheduler**. All assignment data is centralized in **pitas-jobs**, which already handles job data.
- **Consistency**: By persisting job-worker assignments in **pitas-jobs**, we ensure that there is a single source of truth for job status and assignments, reducing potential synchronization issues.
- **Recoverability**: The **pitas-scheduler** can recover its state by querying **pitas-jobs** for all assigned but incomplete jobs. This removes the need for the scheduler to store assignments independently.

### Negative Consequences
- **Service Dependency**: The **pitas-scheduler** is dependent on **pitas-jobs** to persist assignments and retrieve job information, meaning it cannot function without **pitas-jobs** being available.
