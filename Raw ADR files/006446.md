# ADR-004: Frontend Architecture (Next.js 16 App Router)

**Date**: 2025-11-01  
**Status**: Accepted  
**Related**: ADR-001 (Hexagonal Architecture), ADR-002 (Architecture Validation), ADR-003 (OpenAPI Generation)

---

## Context

The ATEKBase system requires two frontend applications:

1. **User-Facing Web App** (`apps/web`) - For end users to access the system
2. **Admin Dashboard** (`apps/admin`) - For administrators to manage users, view audit trails, and system oversight

Key requirements:

- **Performance**: Fast page loads with SSR/SSG
- **Security**: HttpOnly cookies for session management (not localStorage)
- **Type Safety**: End-to-end type safety from API to UI
- **Developer Experience**: Modern React patterns with minimal boilerplate
- **Compliance**: Audit trail integration, secure authentication
- **Separation of Concerns**: Admin functions separate from user app

---

## Decision

### Framework Choice: Next.js 16 with App Router

We will use **Next.js 16 App Router** (stable as of Next.js 13+) for both frontend applications.

**Why Next.js 16:**

- **React Server Components (RSC)**: Reduce client bundle size, improve performance
- **Server Actions**: Type-safe mutations without separate API routes
- **App Router**: File-based routing with layouts and nested routes
- **Built-in TypeScript support**: Zero configuration
- **Vercel/self-hosting ready**: Production deployment options

**Why App Router (not Pages Router):**

- Future-proof (Next.js 13+ default, recommended by Vercel)
- Server Components reduce JavaScript sent to client
- Simpler data fetching (no getServerSideProps/getStaticProps)
- Better layout composition with nested routes

### Authentication Strategy: Server Actions + HttpOnly Cookies

**Pattern:**

```typescript
// Server Action (apps/web/app/actions.ts)
'use server';

export async function loginAction(formData: FormData) {
  const result = await apiClient.post<LoginResponseDto>('/auth/login', {
    email: formData.get('email'),
    password: formData.get('password'),
  });

  if (result.success) {
    // Set HttpOnly cookie (secure, not accessible via JavaScript)
    cookies().set('session', result.data.token, {
      httpOnly: true,
      secure: process.env.NODE_ENV === 'production',
      sameSite: 'lax',
      maxAge: 60 * 60 * 1, // 1 hour
    });

    redirect('/');
  }

  return { error: 'Invalid credentials' };
}
```

**Why Server Actions:**

- ✅ **Security**: No API key/token exposed to client-side JavaScript
- ✅ **Type Safety**: TypeScript types shared between server and client
- ✅ **Simplicity**: No separate API routes needed for mutations
- ✅ **Progressive Enhancement**: Forms work without JavaScript

**Why HttpOnly Cookies (not localStorage):**

- ✅ **XSS Protection**: JavaScript cannot access HttpOnly cookies
- ✅ **CSRF Protection**: SameSite=Lax prevents cross-site requests
- ✅ **FDA Compliance**: More secure than client-side storage
- ✅ **Automatic Transmission**: Browser sends cookie with every request

### Session Management

**Pattern:**

```typescript
// middleware.ts
export async function middleware(request: NextRequest) {
  const session = await getSession(request.cookies);

  if (!session && !isPublicRoute(request.nextUrl.pathname)) {
    return NextResponse.redirect(new URL('/login', request.url));
  }

  return NextResponse.next();
}

export const config = {
  matcher: ['/((?!api|_next/static|_next/image|favicon.ico).*)'],
};
```

**Session Validation:**

- JWT tokens validated on every request via middleware
- Expired tokens automatically redirect to login
- Role-based access control enforced at route level

### API Client Integration

**Type-Safe API Calls with OpenAPI-Generated Types:**

```typescript
import type { components } from '@pkg/openapi-client';

type UserResponseDto = components['schemas']['UserResponseDto'];

async function getUser(id: string): Promise<UserResponseDto> {
  const response = await fetch(`${API_URL}/users/${id}`, {
    headers: {
      Authorization: `Bearer ${token}`,
    },
  });

  return response.json(); // TypeScript knows the exact shape!
}
```

**Benefits:**

- ✅ Single source of truth (OpenAPI spec)
- ✅ Compile-time type checking
- ✅ No manual type definitions
- ✅ Catches API changes immediately

### Separation of Concerns: Two Apps

**Why Separate Apps (`apps/web` and `apps/admin`):**

1. **Security Isolation**
   - Admin routes not exposed to regular users
   - Different authentication scopes
   - Separate deployment environments (optional)

2. **Role-Based UI**
   - Admin dashboard has different navigation, components
   - User app focuses on core functionality
   - No role-checking clutter in user app

3. **Performance**
   - User app bundle smaller (no admin code)
   - Admin app can use heavier libraries (charts, tables) without affecting user experience

4. **Deployment Flexibility**
   - Can deploy admin behind VPN/firewall
   - User app on public CDN
   - Independent scaling

**Shared Code:**

- Both apps use `@pkg/openapi-client` for API types
- Shared utilities in `lib/` directories (session parsing, validation)
- UI components could be shared via `packages/ui` (future enhancement)

### UI Framework: Tailwind CSS + Dark Theme

**Tailwind CSS v3:**

```typescript
// tailwind.config.ts
export default {
  darkMode: 'class',
  theme: {
    extend: {
      colors: {
        background: 'hsl(var(--background))',
        foreground: 'hsl(var(--foreground))',
      },
    },
  },
};
```

**Why Tailwind:**

- ✅ Utility-first (no CSS files to maintain)
- ✅ Responsive design built-in
- ✅ Dark mode support (class-based)
- ✅ Purge unused CSS in production

**Dark Theme Implementation:**

- Default dark mode for admin dashboard
- User preference stored in cookie
- No flash of unstyled content (FOUC)

### Form Validation: Zod Schemas

**Client + Server Validation:**

```typescript
// lib/schemas.ts
import { z } from 'zod';

export const loginSchema = z.object({
  email: z.string().email('Invalid email format'),
  password: z.string().min(8, 'Password must be at least 8 characters'),
});

export type LoginInput = z.infer<typeof loginSchema>;
```

**Server Action with Validation:**

```typescript
'use server';

export async function loginAction(input: LoginInput) {
  const validation = loginSchema.safeParse(input);

  if (!validation.success) {
    return { error: validation.error.flatten() };
  }

  // Proceed with login...
}
```

**Benefits:**

- ✅ Same schema client and server (single source of truth)
- ✅ Runtime validation (catches bad data)
- ✅ Type inference (TypeScript types from Zod schema)

## Consequences

### Positive

✅ **Performance**

- Server Components reduce client bundle by ~40%
- Faster initial page loads with SSR

✅ **Security**

- HttpOnly cookies prevent XSS attacks
- Server Actions eliminate API key exposure
- Role-based routing enforced at middleware level

✅ **Type Safety**

- End-to-end types from API to UI (OpenAPI → TypeScript)
- Zod schemas validate at runtime
- Compile-time errors for API changes

✅ **Developer Experience**

- File-based routing (no React Router config)
- Server Actions eliminate boilerplate
- Tailwind CSS (no CSS files to maintain)

✅ **Compliance**

- Secure authentication (CFR Part 11 §11.10(d))
- Audit trail integration (audit trail visible in admin dashboard)
- Role-based access control (CFR Part 11 §11.10(g))

### Negative

❌ **Learning Curve**

- Server Components are new (developers need training)
- App Router differs from Pages Router (migration path)

❌ **Complexity**

- Two separate apps (more infrastructure)
- Middleware logic can be tricky (route matching patterns)

❌ **Bundle Size**

- Next.js framework overhead (~200KB gzipped)
- Dark theme CSS adds ~10KB

### Mitigations

- **Training**: Add Server Components examples to `.cursor/rules.md`
- **Documentation**: Detailed setup guides in `apps/web/README.md` and `apps/admin/README.md`
- **Testing**: Comprehensive unit tests for schemas and session logic
- **Performance**: Lazy load heavy components, optimize images with Next.js Image

## Alternatives Considered

### Alternative 1: Single App with Role-Based UI

**Pattern:**

```typescript
// Single app with role checks
{user.hasRole('ADMIN') && <AdminPanel />}
{user.hasRole('VIEWER') && <ViewerPanel />}
```

**Rejected Because:**

- ❌ User app bundle includes admin code (larger bundle)
- ❌ Complex role-checking logic throughout UI
- ❌ Security risk (admin code exposed to users)
- ❌ Harder to deploy admin behind VPN

### Alternative 2: Pages Router (Next.js 12 style)

**Pattern:**

```typescript
// pages/index.tsx
export async function getServerSideProps(context) {
  const session = await getSession(context);
  return { props: { session } };
}
```

**Rejected Because:**

- ❌ Pages Router in maintenance mode (Next.js 13+ focuses on App Router)
- ❌ No Server Components (larger client bundles)
- ❌ More boilerplate (getServerSideProps, getStaticProps)
- ❌ Not future-proof

### Alternative 3: React SPA (Vite + React Router)

**Pattern:**

```typescript
// client-side routing only
import { BrowserRouter, Route } from 'react-router-dom';
```

**Rejected Because:**

- ❌ No SSR (slower initial load, worse SEO)
- ❌ Token management in localStorage (XSS risk)
- ❌ Larger client bundles (entire app in JavaScript)
- ❌ No Server Actions (need separate API routes)
