## Context

In a sophisticated multi-agent system, the session context is not merely a debugging utility but a core component of its operational fabric. It serves as the substrate for agent analysis, decision-making, and complex interactions. Storing this context is critical for:

-   **Multi-Agent Collaboration**: Enabling agents to share state, communicate intermediate results, and collaboratively build on each other's work.
-   **Complex Analysis**: Tracking the multi-step reasoning process, including the dynamic plans agents create and the data they gather.
-   **Decision and Action Auditing**: Recording the specific sequence of agent actions, tool calls, and decisions for traceability and compliance.
-   **System Resilience**: Recovering from transient failures in long-running, multi-agent workflows.

The session context must capture the entire lifecycle of a request, including dynamic plans, inter-agent messages, tool calls, intermediate conclusions, and final outputs.

## Decision

We will implement a **two-tiered agent session context storage strategy** leveraging Redis for in-flight sessions and BigQuery for permanent archival.

1.  **In-Flight Session Context (Operational Memory)**: The live, mutable context of an *active* agent analysis will be stored in **Redis**. This provides a high-speed, resilient checkpointing mechanism.
2.  **Archived Session Context (Permanent Memory)**: The final, immutable context of a *completed* agent analysis will be archived in **Google BigQuery**. This creates a permanent, auditable, and analyzable record of every agent decision.

## Rationale

This two-tiered approach is optimal because it addresses the distinct needs of operational resilience and long-term analytics without compromise.

1.  **Separation of Concerns**: Active sessions require low-latency reads and writes for state checkpointing, a workload for which Redis is the industry standard. Archived sessions require cost-effective storage and powerful querying for analytics, which is the core strength of BigQuery. A single database cannot perform both of these functions optimally.
2.  **Resilience and Performance**: Storing in-flight context in Redis allows a long-running agent task to be recovered quickly after a transient failure. Using BigQuery for this would be too slow. Archiving to BigQuery is done asynchronously upon completion, so it does not impact the perceived performance of the agent's execution.
3.  **Unified Analytics**: By archiving all session data to BigQuery, we create a single, powerful analytics environment (as established in ADR-004). This allows us to run complex queries that correlate agent behavior with market data and trade outcomes, which is invaluable for debugging, performance tuning, and strategy refinement.
4.  **Cost-Effectiveness**: The solution is highly cost-optimized. Redis provides cheap, high-performance operational storage, while BigQuery offers extremely low-cost long-term storage for the large volume of session data we expect to generate.

## Consequences

The consequences of this decision are broken down into a summary of outcomes and specific implementation requirements.

### Positive Outcomes

-   **Improved Resilience**: The system can recover from transient failures in long-running agent tasks.
-   **Enhanced Debuggability & Auditing**: A complete, immutable record of every agent's execution flow is available for analysis in BigQuery.
-   **Advanced Analytics**: BigQuery enables sophisticated analysis of agent performance, tool usage, and decision-making patterns.
-   **Unified Data Architecture**: This approach leverages and reinforces the existing data architecture decisions for Redis and BigQuery.

### Implementation Requirements

-   **Data Models**: A structured Pydantic model for the `AgentSessionContext` will be defined to ensure a consistent format for both Redis and BigQuery.
-   **Agent Logic**: The base agent class will be modified to include methods for saving context to Redis during execution and archiving the final context to BigQuery upon completion.
-   **Infrastructure**: The `trading.agent_session_archives` table must be created in BigQuery, and its schema managed via Terraform.
-   **Performance**: The latency of saving context to Redis must be monitored, and the archival process to BigQuery must be fully asynchronous to avoid blocking.

## Alternatives Considered

1.  **BigQuery Only**: Storing all session context, including in-flight data, directly in BigQuery.
    -   **Reason for Rejection**: BigQuery is an analytical data warehouse, not an operational database. It has relatively high write latency (seconds), making it unsuitable for the frequent checkpointing required for in-flight session management. This would severely degrade performance and responsiveness.

2.  **Redis Only**: Using Redis for both in-flight and long-term storage of session context.
    -   **Reason for Rejection**: Redis is not a cost-effective or practical solution for permanent, long-term archival of large datasets. Furthermore, its querying capabilities are limited and cannot compare to the powerful SQL analytics engine of BigQuery, which is a core requirement for analyzing agent performance.

3.  **Relational Database Only (e.g., Cloud SQL)**: Storing all session context in a traditional SQL database.
    -   **Reason for Rejection**: This approach is not ideal for either use case. It is less performant than Redis for high-speed operational checkpointing and less scalable and cost-effective than BigQuery for large-scale analytics. Additionally, the semi-structured nature of agent context (which is often like a nested JSON object) is difficult to model in a rigid relational schema.

## Implementation Strategy

### Phase 1: Data Model and Schema Design (Week 1)
**Deliverables**:
- Define Pydantic model for `AgentSessionContext` (session_id, agent_name, start_time, end_time, status, plan, messages, tool_calls, conclusions, final_output)
- Design Redis key structure (`session:{session_id}`, TTL: 24 hours)
- Define BigQuery table schema `trading.agent_session_archives` (partitioned by date, clustered by agent_name)
- Document session lifecycle states (ACTIVE, COMPLETED, FAILED, RECOVERED)
- Create session context versioning strategy for schema evolution

**Dependencies**: ADR-001 and ADR-004 acceptance, agreement on session context structure

### Phase 2: Redis Checkpointing Implementation (Week 1-2)
**Deliverables**:
- Implement `SessionContextManager` class for Redis operations (save, load, delete)
- Modify base agent class to checkpoint context at key decision points
- Implement automatic checkpointing on tool calls and inter-agent messages
- Add recovery logic to resume from last checkpoint after failure
- Unit tests for checkpointing and recovery mechanisms

**Dependencies**: Phase 1 data model, Redis infrastructure from ADR-001

### Phase 3: BigQuery Archival Implementation (Week 2-3)
**Deliverables**:
- Implement asynchronous archival service (background task or Cloud Function)
- Add archival trigger on agent task completion
- Implement batch archival for completed sessions (every 5 minutes)
- Create BigQuery materialized views for common analytics queries
- Integration tests for end-to-end session lifecycle (checkpoint → archive)

**Dependencies**: Phase 2 Redis implementation, BigQuery infrastructure from ADR-004

### Phase 4: Analytics and Monitoring (Week 3-4)
**Deliverables**:
- Create BigQuery queries for agent performance analysis (success rate, execution time, tool usage)
- Implement session context monitoring dashboard (Cloud Monitoring)
- Add alerting for checkpoint failures and archival delays
- Document query patterns for debugging and analysis
- Performance optimization (checkpoint frequency tuning, batch size optimization)

**Dependencies**: Phase 3 archival implementation, production-like workload for testing

## Cost Analysis

### Monthly Operational Costs

**Redis for In-Flight Sessions**:
- Session context size: ~10KB per session (JSON serialized)
- Peak concurrent sessions: 50 (multi-agent workflows)
- Total memory required: 500KB + overhead = 1MB
- Redis instance (shared with operational data): $0 incremental cost (already provisioned in ADR-001)
- **Subtotal**: $0 incremental (included in ADR-001 Redis allocation)

**BigQuery for Archived Sessions**:
- Average session context size: 15KB (includes full execution trace)
- Sessions per day: 1,000 (across all agents)
- Monthly data ingestion: 1,000 × 30 × 15KB = 450MB/month
- Annual storage: 450MB × 12 = 5.4GB/year
- Storage cost (active): 5.4GB × $0.020/GB = $0.11/month
- Streaming inserts: 30,000 rows × $0.05/million = $0.0015/month
- Query processing (100GB scanned/month): 100GB × $5/TB = $0.50/month
- **Subtotal**: $0.61/month

**Total Estimated Monthly Cost**: $0.61/month (negligible incremental cost)

### Cost Optimization Strategies

1. **Session Context Compression**:
   - Compress JSON before storing in Redis (gzip compression)
   - Reduces size by 60-70%: 15KB → 5KB
   - Lower memory usage in Redis, faster network transfer

2. **Aggressive TTL for Completed Sessions**:
   - Delete from Redis immediately after archival to BigQuery
   - Frees memory for active sessions
   - No cost savings but improves performance

3. **BigQuery Partition Pruning**:
   - Partition by date, cluster by agent_name
   - Queries filtering by date/agent scan <5% of data
   - Query cost reduction: 95% for filtered queries

4. **Session Sampling for Analytics**:
   - Archive all sessions for audit compliance
   - Sample 10% for detailed performance analytics (detailed tool trace)
   - Reduces query processing costs by 90% for analytics workload

### ROI Comparison

**vs No Checkpointing (Restart from Scratch)**:
- Average agent task duration: 30 seconds
- Failure rate without checkpointing: 5% (transient network/API errors)
- Wasted compute time: 1,000 tasks/day × 5% × 30s = 1,500 seconds/day = 12.5 hours/month
- At $0.10/hour compute cost: $1.25/month wasted
- **ROI**: $1.25 savings vs $0.61 cost = 2:1 ROI (plus improved reliability)

**vs File-Based Archival (Cloud Storage)**:
- Cloud Storage: $0.020/GB for standard storage = $0.11/month (storage only)
- Query processing: Requires loading full files, no query optimization
- BigQuery provides SQL analytics, partitioning, and indexing
- **Trade-off**: $0.50/month more expensive but 100x faster queries

## Risk Assessment

| Risk | Severity | Likelihood | Impact | Mitigation |
|------|----------|------------|--------|------------|
| Redis checkpoint failure | High | Low | Lost work, agent restart from beginning | Retry logic with exponential backoff, fallback to in-memory only mode, monitor checkpoint success rate |
| BigQuery archival delay | Medium | Medium | Incomplete audit trail, delayed analytics | Asynchronous archival with retry queue, alert on 1-hour delay, temporary buffering in Cloud Storage |
| Session context size explosion | Medium | Medium | Redis memory exhaustion, high BigQuery costs | Enforce size limits (100KB max), compress large contexts, sample verbose tool outputs |
| Checkpoint performance impact | Low | Medium | Slower agent execution, degraded UX | Asynchronous checkpointing, batch updates, monitor checkpoint latency (<50ms target) |
| Schema evolution breaking changes | High | Low | Archival failures, lost sessions | Schema versioning in context model, backward-compatible changes only, canary deployments |
| Session context PII leakage | High | Low | Compliance violations | Redact sensitive data before archival, access controls on BigQuery table, audit log access |
| Recovery logic bugs | High | Medium | Incorrect agent state, duplicate actions | Extensive testing of recovery scenarios, idempotent agent operations, recovery dry-run mode |
| Cross-agent session conflicts | Medium | Low | Session overwrite, lost context | Unique session IDs (UUID), optimistic locking in Redis, detect conflicts on save |
