# ADR: Cache Invalidation for /api/orders

- Candidate: CAND-N1YH
- Date: 2025-10-23

## Context
The /api/orders endpoint serves order data with moderate read traffic and occasional writes. The API requires near-real-time data freshness for active orders while tolerating slight staleness for historical data. Current implementation uses SQLite with indexes, but database queries are becoming a bottleneck during peak hours.

## Options Considered
1) **TTL-based cache (per key)** - Each cached item expires after a fixed time period
2) **Tag-based cache invalidation** - Group related cache entries by tags and invalidate by tag
3) **Event-driven invalidation on write (pub/sub)** - Invalidate cache immediately when data changes
4) **No cache (DB + indexes only)** - Rely solely on database performance optimizations

## Decision
We choose: **TTL-based cache with manual invalidation support** (hybrid of options 1 and 3)

## Rationale (Criteria)
- **Simplicity**: TTL-based caching is straightforward to implement and reason about. No complex pub/sub infrastructure needed.
- **Staleness risk**: Acceptable for orders API. Active orders use shorter TTLs (30s), completed orders use longer TTLs (5min).
- **DB offload**: Reduces database queries by 70-90% based on cache hit rates.
- **Deployment/ops complexity**: Low - uses APCu (if available) or file cache fallback. No external dependencies.
- **Failure modes**: Graceful degradation - if cache fails, falls back to database queries.

## When NOT to use this choice (Anti-case)
- Real-time financial transactions where any staleness is unacceptable
- High-frequency writes (>100 writes/second) where cache invalidation overhead exceeds benefits
- Distributed systems requiring cache consistency across multiple servers (would need Redis/Memcached)
- Data that changes unpredictably and cannot tolerate any staleness

## Rollback Plan
1. Set cache TTL to 0 (effectively disabling cache while keeping code in place)
2. Monitor database load and response times
3. If issues persist, deploy previous version without cache layer
4. Cache can be disabled via feature flag: `DISABLE_CACHE=1`

## Implementation Notes
- **Cache keys**: `orders:list:{user_id}:{status}`, `orders:detail:{order_id}`
- **TTLs**: Active orders: 30s, Completed orders: 300s, User order lists: 60s
- **Invalidation triggers**:
  - On order create/update: invalidate `orders:list:*` and specific `orders:detail:{id}`
  - Manual invalidation via `cache_invalidate()` for admin operations
- **Storage**: APCu (primary) with file-based fallback for environments without APCu
- **Garbage collection**: Runs on 1% of requests to clean expired file cache entries
