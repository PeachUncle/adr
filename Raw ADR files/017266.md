# ADR-001: Use DynamoDB as Primary Database

## Status
Accepted

## Context

Social Flow requires a database that can:
- Scale horizontally to handle millions of users
- Provide single-digit millisecond latency at scale
- Support flexible schema for evolving social features
- Handle high write throughput for posts, likes, comments
- Integrate well with AWS ecosystem
- Provide cost-effective scaling

We evaluated several options:
- Traditional RDBMS (PostgreSQL, MySQL)
- NoSQL document stores (MongoDB, DynamoDB)
- Graph databases (Neo4j)

## Decision

We will use **Amazon DynamoDB** as the primary database for Social Flow.

Key factors:
1. **Performance**: Single-digit millisecond latency at any scale
2. **Scalability**: Auto-scaling from zero to petabytes without downtime
3. **Availability**: 99.99% SLA with multi-AZ replication
4. **Serverless**: No infrastructure management required
5. **Cost Model**: Pay-per-request pricing aligns with usage
6. **AWS Integration**: Native integration with Lambda, AppSync, IAM

## Consequences

### Positive

- **Infinite scale**: Can handle viral posts and traffic spikes
- **Low latency**: Fast reads/writes critical for social media
- **No ops burden**: Fully managed service
- **Global tables**: Multi-region replication for low latency worldwide
- **Backup**: Point-in-time recovery and on-demand backups
- **Streams**: Native change data capture for event-driven architecture
- **Cost efficiency**: Pay only for what we use

### Negative

- **Query limitations**: No complex joins or aggregations
- **Learning curve**: Requires understanding of partition keys and access patterns
- **Schema design**: Must know access patterns upfront (single-table design)
- **No ACID across items**: Limited transactions (max 25 items)
- **Vendor lock-in**: Tightly coupled to AWS

### Risks

- **Cost at scale**: High read/write volumes could be expensive
  - *Mitigation*: Use caching (Redis), optimize access patterns
- **Schema changes**: Difficult to change partition/sort keys
  - *Mitigation*: Careful upfront design, use GSIs for flexibility
- **Complex queries**: Analytics queries challenging
  - *Mitigation*: Use ClickHouse for analytics, OpenSearch for search

## Alternatives Considered

### PostgreSQL (RDS/Aurora)

**Pros:**
- Mature, well-understood
- Rich query capabilities (joins, aggregations)
- ACID transactions
- Strong consistency

**Cons:**
- Vertical scaling limits
- Read replicas needed for scale
- More operational overhead
- Higher latency at scale

**Why not chosen:** Scaling limitations for social media workload. Would require sharding for millions of users.

### MongoDB (Atlas)

**Pros:**
- Flexible schema
- Rich query language
- Document model fits social data
- Good developer experience

**Cons:**
- Self-managed or Atlas costs
- Scaling complexity (sharding)
- Consistency trade-offs
- Not serverless

**Why not chosen:** DynamoDB better fits serverless architecture and AWS ecosystem.

### Neo4j (Graph Database)

**Pros:**
- Natural fit for social graph
- Efficient relationship queries
- Powerful query language (Cypher)

**Cons:**
- Scaling challenges
- Operational complexity
- Limited AWS integration
- High cost

**Why not chosen:** While great for social graph, not optimal for general-purpose storage. We'll use DynamoDB with adjacency lists.

## Implementation Notes

### Table Design

We use **single-table design** with the following structure:

```
PK                    SK                   GSI1-PK           GSI1-SK
-------------------------------------------------------------------
USER#<userId>         #METADATA            USERNAME#<name>   -
USER#<userId>         POST#<postId>        -                 -
POST#<postId>         #METADATA            USER#<userId>     CREATED#<time>
POST#<postId>         LIKE#<userId>        -                 -
POST#<postId>         COMMENT#<commentId>  -                 -
FOLLOW#<userId>       USER#<targetId>      USER#<targetId>   USER#<userId>
```

### Access Patterns

1. Get user by ID: `PK=USER#<id>, SK=#METADATA`
2. Get user by username: GSI1 query on `USERNAME#<name>`
3. Get user's posts: `PK=USER#<id>, SK begins_with POST#`
4. Get post with likes: `PK=POST#<id>`
5. Get user's feed: Query multiple users, sort by timestamp
6. Follow/unfollow: Single item write

### Capacity Planning

- **On-demand mode** initially for unpredictable traffic
- **Provisioned mode** for predictable, high-volume tables (analytics)
- **Auto-scaling** for tables with variable load

### Caching Strategy

- Redis for:
  - Hot user profiles
  - Feed cache (15 minutes)
  - Post cache (1 hour)
  - Trending content (5 minutes)
- Reduces DynamoDB reads by 80%+
