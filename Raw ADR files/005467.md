## Context

The multi-agent trading system consists of 15+ distinct agents and services running on Google Cloud Run, each requiring access to different GCP resources:

- Cloud SQL (transactional data)
- Memorystore Redis (operational state)
- BigQuery (analytics warehouse)
- Secret Manager (credentials)
- Pub/Sub (message streaming)
- Vertex AI (ML models)

Current security gaps:
- No documented service account per agent
- ADR-011 (line 448) mentions service accounts without specification
- ADR-022 (line 32) references "Secret Manager Secret Accessor" role without defining which agents need it
- No IAM role matrix exists for the agent hierarchy
- Risk of over-permissioning if default service accounts are used
- No audit trail linking agent actions to specific service accounts

Security requirements:
- Least privilege access (minimum permissions required)
- Separation of duties (no shared service accounts)
- Audit trail for all agent actions
- Defense in depth (limit blast radius of credential compromise)
- Compliance with financial data handling requirements

## Decision

Implement one dedicated service account per agent with minimum required IAM permissions. Service accounts will follow the naming convention: `{agent-name}@{project-id}.iam.gserviceaccount.com`.

## Rationale

1. **Least Privilege**: Each agent receives only the permissions required for its specific responsibilities.
2. **Audit Trail**: Cloud Audit Logs can trace all actions to specific service accounts, enabling precise security analysis.
3. **Blast Radius Limitation**: Credential compromise affects only one agent's permissions.
4. **Defense in Depth**: Multiple layers of access control (IAM + Secret Manager policies + application logic).
5. **Compliance**: Financial trading systems require clear audit trails and access controls.
6. **Separation of Duties**: Prevents privilege escalation by enforcing role boundaries at infrastructure level.

## Security Principles

### 1. Least Privilege

**Definition**: Each service account receives only the minimum permissions required to perform its specific function.

**Implementation**:
- Greeks Calculation Service has zero GCP IAM roles (stateless computation)
- Strategy Agents have Redis Editor but NOT Cloud SQL Client (cannot write trade records)
- Market Analysis Agent has BigQuery Viewer but NOT Editor (read-only analytics)
- Data Ingestion Service has Pub/Sub Subscriber but NOT Publisher (one-way data flow)

**Verification**:
```bash
# Audit service account permissions
gcloud projects get-iam-policy {project-id} \
  --flatten="bindings[].members" \
  --filter="bindings.members:serviceAccount:orchestrator-agent@*" \
  --format="table(bindings.role)"
```

### 2. No Shared Service Accounts

**Prohibition**: Never reuse service accounts across multiple agents.

**Rationale**: Shared accounts make audit trails ambiguous and increase blast radius of credential compromise.

**Exception**: None. Even similar agents (e.g., multiple strategy agents) must have dedicated service accounts.

### 3. No Default Compute Service Account Usage

**Prohibition**: Never use `{project-number}-compute@developer.gserviceaccount.com` for agents.

**Rationale**: Default service accounts have Editor role on the project, violating least privilege.

**Enforcement**: Terraform configuration explicitly assigns custom service accounts to all Cloud Run services.

### 4. Regular Audit and Review

**Frequency**: Quarterly IAM audit (January, April, July, October)

**Audit Checklist**:
- [ ] Verify each service account still aligns with agent's current responsibilities
- [ ] Remove unused service accounts
- [ ] Review Cloud Audit Logs for suspicious access patterns
- [ ] Verify MCP server authorization lists match current agent roster
- [ ] Check for over-permissioned roles (e.g., Editor, Owner)
- [ ] Validate Secret Manager access matches documented matrix

**Automation**:
```bash
# Generate IAM audit report
gcloud asset search-all-iam-policies \
  --scope=projects/{project-id} \
  --query="policy:serviceAccount" \
  --format=json > iam_audit_$(date +%Y%m%d).json
```

### 5. Workload Identity for GKE (Future)

**Condition**: If migrating from Cloud Run to GKE.

**Implementation**: Bind Kubernetes service accounts to Google Cloud service accounts using Workload Identity.

**Benefit**: Eliminates need to manage service account keys, uses short-lived tokens.

**Reference**: [GKE Workload Identity Documentation](https://cloud.google.com/kubernetes-engine/docs/how-to/workload-identity)

## Secret Access Patterns

### Secret-to-Agent Mapping

| Secret | Agents with Access | IAM Policy Enforcement |
|--------|-------------------|------------------------|
| `ib-gateway-api-key` | Orchestrator, IB Gateway, Trade Execution, MCP IB Gateway | Secret Manager IAM binding per agent |
| `cloud-sql-password` | Orchestrator, Risk Management, Trade Execution, Performance Analytics, MCP Database | Separate read-only and read-write users in Cloud SQL |
| `redis-connection-string` | All agents except Greeks Calculation | Secret Manager IAM binding per agent |
| `alpha-vantage-api-key` | Stock Selection, Market Analysis, MCP Market Analysis | Secret Manager IAM binding per agent |
| `finnhub-api-key` | Stock Selection, Market Analysis, MCP Market Analysis | Secret Manager IAM binding per agent |
| `ib-client-id` | IB Gateway, MCP IB Gateway | Secret Manager IAM binding |

### Secret Rotation Procedure

1. Create new secret version in Secret Manager
2. Update agent environment variables (Cloud Run revision deployment)
3. Graceful rolling update (zero-downtime)
4. Verify all agents using new secret version
5. Disable old secret version after 24-hour grace period
6. Monitor Cloud Audit Logs for failed authentication attempts

### Secret Manager IAM Best Practices

- Use Secret Manager Secret Accessor role, NOT Secret Manager Admin
- Grant access at secret level, NOT project level
- Use separate secrets for read-only vs read-write database credentials
- Enable Secret Manager audit logging for all access attempts
- Set secret expiration dates where applicable (API keys)

## Cross-Service Authentication

### Agent-to-MCP Server Authentication Flow

```
1. Agent requests service account token from metadata server
   GET http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token

2. Agent includes token in MCP request header
   Authorization: Bearer {token}

3. MCP server validates token
   - Verify token signature with Google public keys
   - Extract service account email from token claims
   - Check if service account in ALLOWED_SERVICE_ACCOUNTS list

4. MCP server authorizes tool access
   - If authorized: Execute tool, return result
   - If unauthorized: Return 403 Forbidden with error message
```

### Token Validation Implementation

```python
# src/mcp_servers/common/auth.py

from google.auth.transport import requests
from google.oauth2 import id_token

async def verify_service_account_token(token: str, allowed_accounts: List[str]) -> bool:
    """
    Verify Google Cloud service account token.

    Returns True if token valid and service account in allowed list.
    """
    try:
        request = requests.Request()
        id_info = id_token.verify_oauth2_token(token, request)

        # Extract service account email
        service_account = id_info.get('email')

        # Check authorization
        if service_account in allowed_accounts:
            logger.info(
                "mcp_auth_success",
                service_account=service_account,
                token_expiry=id_info.get('exp')
            )
            return True
        else:
            logger.warning(
                "mcp_auth_denied",
                service_account=service_account,
                reason="not_in_allowed_list"
            )
            return False

    except ValueError as e:
        logger.error("mcp_auth_failed", error=str(e))
        return False
```

### Token Caching and Refresh

```python
# Agent-side token management

from google.auth import default
from google.auth.transport.requests import Request
import time

class TokenManager:
    def __init__(self):
        self.credentials, _ = default()
        self.cached_token = None
        self.token_expiry = 0

    def get_token(self) -> str:
        """Get cached token or refresh if expired"""
        current_time = time.time()

        # Refresh if token expired or expiring soon (5min buffer)
        if current_time >= (self.token_expiry - 300):
            self.credentials.refresh(Request())
            self.cached_token = self.credentials.token
            self.token_expiry = self.credentials.expiry.timestamp()

            logger.info(
                "token_refreshed",
                service_account=self.credentials.service_account_email,
                expiry=self.token_expiry
            )

        return self.cached_token
```

## Risk Assessment

### Risk: Over-Permissioning

**Description**: Service accounts granted more permissions than required, violating least privilege.

**Likelihood**: Medium (common configuration error)

**Impact**: High (increases blast radius of credential compromise)

**Mitigation**:
- Quarterly IAM audits with checklist (see Security Principles section)
- Terraform-managed IAM policies (no manual console changes)
- Pre-commit hooks to validate IAM policy changes
- Policy Analyzer tool to identify over-permissioned accounts

### Risk: Credential Leakage

**Description**: Service account keys exposed in code, logs, or error messages.

**Likelihood**: Low (using Workload Identity eliminates key files)

**Impact**: Critical (full compromise of agent permissions)

**Mitigation**:
- Use Workload Identity (no key files on disk)
- Never log authentication tokens
- Secret scanning in CI/CD pipeline (ADR-018)
- Automated key rotation if keys must be used

### Risk: Privilege Escalation

**Description**: Compromised agent gains additional permissions through IAM role manipulation.

**Likelihood**: Very Low (requires IAM Admin role on compromised account)

**Impact**: Critical (full system compromise)

**Mitigation**:
- No agent service accounts have IAM Admin role
- Terraform-managed IAM policies prevent manual changes
- Cloud Audit Logs alert on IAM policy changes
- Separation of duties (DevOps team manages IAM, agents have zero IAM permissions)

### Risk: Insider Threat

**Description**: Malicious developer with Terraform access grants unauthorized permissions.

**Likelihood**: Very Low (requires multiple control failures)

**Impact**: High (unauthorized data access or trading actions)

**Mitigation**:
- Terraform state stored in GCS with versioning enabled
- Pull request reviews required for Terraform changes
- Cloud Audit Logs capture all IAM policy changes with identity
- Quarterly IAM audits review recent changes

### Risk: MCP Server Authorization Bypass

**Description**: Agent bypasses MCP server authorization by directly accessing backend services.

**Likelihood**: Low (requires VPC network access)

**Impact**: Medium (circumvents tool-level access control)

**Mitigation**:
- Backend services (Redis, Cloud SQL) use VPC Service Controls
- IAM policies prevent unauthorized direct access
- MCP servers deployed in separate VPC subnet
- Network policies restrict agent-to-service connectivity

## Monitoring and Success Criteria

### Cloud Audit Log Queries

**Query 1: Unauthorized Access Attempts**
```sql
-- BigQuery query for denied access attempts
SELECT
  timestamp,
  protoPayload.authenticationInfo.principalEmail as service_account,
  protoPayload.resourceName as resource,
  protoPayload.status.code as status_code,
  protoPayload.status.message as error_message
FROM
  `{project}.audit_logs.cloudaudit_googleapis_com_data_access`
WHERE
  protoPayload.status.code = 7  -- PERMISSION_DENIED
  AND protoPayload.authenticationInfo.principalEmail LIKE '%@{project}.iam.gserviceaccount.com'
ORDER BY
  timestamp DESC
LIMIT 100
```

**Query 2: IAM Policy Changes**
```sql
-- Audit all IAM policy changes
SELECT
  timestamp,
  protoPayload.authenticationInfo.principalEmail as actor,
  protoPayload.methodName as method,
  protoPayload.resourceName as resource,
  JSON_EXTRACT(protoPayload.request, '$.policy') as new_policy
FROM
  `{project}.audit_logs.cloudaudit_googleapis_com_activity`
WHERE
  protoPayload.methodName LIKE '%SetIamPolicy%'
ORDER BY
  timestamp DESC
```

**Query 3: Secret Manager Access Patterns**
```sql
-- Monitor secret access frequency by service account
SELECT
  protoPayload.authenticationInfo.principalEmail as service_account,
  protoPayload.resourceName as secret,
  COUNT(*) as access_count,
  MIN(timestamp) as first_access,
  MAX(timestamp) as last_access
FROM
  `{project}.audit_logs.cloudaudit_googleapis_com_data_access`
WHERE
  protoPayload.serviceName = 'secretmanager.googleapis.com'
  AND protoPayload.methodName = 'google.cloud.secretmanager.v1.SecretManagerService.AccessSecretVersion'
  AND DATE(timestamp) = CURRENT_DATE()
GROUP BY
  service_account, secret
ORDER BY
  access_count DESC
```

## Consequences

### Positive

1. **Security Posture**: Defense in depth with least privilege access control.
2. **Audit Trail**: Cloud Audit Logs provide immutable record of all agent actions.
3. **Compliance**: Financial system requirements for access control and audit trails met.
4. **Blast Radius Limitation**: Credential compromise affects only one agent's scope.
5. **Operational Visibility**: Clear mapping of actions to specific agents via service accounts.
6. **Scalability**: Pattern extends to new agents without architectural changes.

### Negative

1. **Operational Complexity**: 15+ service accounts to create and manage.
2. **Terraform Configuration**: Extensive IAM binding configuration required.
3. **Debugging Complexity**: Permission issues require checking multiple IAM policies.
4. **Initial Setup Time**: Service account creation and IAM binding for all agents (estimated 2-3 days).
5. **Audit Overhead**: Quarterly reviews add operational burden (estimated 4 hours per quarter).

### Mitigation for Negative Consequences

**Complexity**:
- Terraform modules for service account creation (reusable pattern)
- Automated IAM audit scripts reduce manual review time
- Documentation matrix (this ADR) serves as single source of truth

**Debugging**:
- Centralized IAM audit dashboard in Google Cloud Console
- CLI scripts to query service account permissions
- Structured logging includes service account in all log entries

## Alternatives Considered

### Alternative 1: Shared Service Accounts by Agent Level

**Approach**: One service account for all Level 3 Strategy Agents, one for all Service Agents, etc.

**Pros**:
- Simpler Terraform configuration (fewer service accounts)
- Easier initial setup

**Cons**:
- Ambiguous audit trails (cannot determine which specific agent performed action)
- Larger blast radius (compromise affects entire agent tier)
- Violates separation of duties principle

**Rejection Reason**: Audit trail clarity and blast radius limitation are critical security requirements for financial systems.

### Alternative 2: Default Compute Service Account

**Approach**: Use `{project-number}-compute@developer.gserviceaccount.com` for all agents.

**Pros**:
- Zero configuration required
- Simplest possible setup

**Cons**:
- Default service account has Editor role (massive over-permissioning)
- No audit trail differentiation (all agents appear identical in logs)
- Single point of failure (compromise affects entire system)
- Violates all security best practices

**Rejection Reason**: Unacceptable security risk for financial trading system.

### Alternative 3: Per-Service-Type Service Accounts

**Approach**: One service account for "data access agents", one for "execution agents", etc.

**Pros**:
- Moderate complexity (4-5 service accounts vs 15+)
- Simpler than per-agent approach

**Cons**:
- Still ambiguous audit trails within service type groups
- Blast radius larger than per-agent approach
- Requires defining and maintaining service type taxonomy

**Rejection Reason**: Marginal complexity reduction does not justify loss of audit clarity and increased blast radius.

### Alternative 4: IAM Conditions (Attribute-Based Access Control)

**Approach**: Use single service account with IAM conditions to restrict access based on agent metadata.

**Pros**:
- Single service account simplifies configuration
- Fine-grained access control through IAM conditions

**Cons**:
- IAM conditions limited to resource tags and time-based restrictions (cannot differentiate by calling agent)
- Complex condition syntax prone to misconfiguration
- Not supported for all GCP services (e.g., Memorystore Redis)
- Audit logs still show same service account for all agents

**Rejection Reason**: IAM conditions do not provide agent-level differentiation in audit trails.

## Service Account Naming Convention

**Format**: `{agent-name}@{project-id}.iam.gserviceaccount.com`

**Examples**:
- `orchestrator-agent@trading-prod-12345.iam.gserviceaccount.com`
- `iron-condor-agent@trading-prod-12345.iam.gserviceaccount.com`
- `mcp-ib-gateway@trading-prod-12345.iam.gserviceaccount.com`

**Rules**:
- Use lowercase with hyphens (not underscores or camelCase)
- Agent name matches Cloud Run service name
- MCP servers prefixed with "mcp-"
- Support services suffixed with "-service" or "-agent" as appropriate

**Account ID Constraints**:
- Length: 6-30 characters
- Characters: Lowercase letters, numbers, hyphens
- Must start with lowercase letter
- Must end with letter or number

## Appendix: Terraform Module Example

```hcl
# terraform/modules/agent_service_account/main.tf

variable "agent_name" {
  description = "Agent name (e.g., 'orchestrator-agent')"
  type        = string
}

variable "display_name" {
  description = "Human-readable display name"
  type        = string
}

variable "description" {
  description = "Service account description"
  type        = string
}

variable "project_id" {
  description = "GCP project ID"
  type        = string
}

variable "secrets" {
  description = "List of secret IDs this agent can access"
  type        = list(string)
  default     = []
}

variable "iam_roles" {
  description = "List of IAM roles to grant"
  type        = list(string)
  default     = []
}

resource "google_service_account" "agent" {
  account_id   = var.agent_name
  display_name = var.display_name
  description  = var.description
  project      = var.project_id
}

resource "google_secret_manager_secret_iam_member" "secret_access" {
  for_each = toset(var.secrets)

  secret_id = each.value
  role      = "roles/secretmanager.secretAccessor"
  member    = "serviceAccount:${google_service_account.agent.email}"
}

resource "google_project_iam_member" "role_binding" {
  for_each = toset(var.iam_roles)

  project = var.project_id
  role    = each.value
  member  = "serviceAccount:${google_service_account.agent.email}"
}

output "email" {
  description = "Service account email"
  value       = google_service_account.agent.email
}

output "name" {
  description = "Service account name"
  value       = google_service_account.agent.name
}
```
