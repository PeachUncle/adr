# ADR 002: Turborepo Monorepo Structure

**Status:** Accepted

**Date:** 2025-10-13

**Deciders:** Development Team

## Context

The Latera project consists of multiple related components:
- Desktop application (Electron + React)
- Landing page/marketing website (Next.js)
- Shared TypeScript types and utilities
- Potentially shared UI components

We need to decide on a code organization strategy that:
- Allows code sharing between desktop app and web
- Provides efficient build and development workflows
- Scales with potential future additions (browser extension, mobile companion)
- Remains simple enough for a single developer side project
- Supports independent deployment of desktop app and landing page

## Decision

We will use **Turborepo** to organize the project as a monorepo with the following structure:

```
latera/
├── apps/
│   ├── desktop/          # Electron application
│   └── web/              # Next.js landing page
├── packages/
│   ├── shared/           # Shared TypeScript utilities
│   ├── ui/               # Shared React components
│   └── tsconfig/         # Shared TypeScript configs
├── docs/                 # Documentation and ADRs
├── turbo.json           # Turborepo pipeline configuration
└── package.json         # Root workspace configuration
```

### Workspace Assignments:
- `@latera/desktop` - Main Electron application
- `@latera/web` - Landing page
- `@latera/shared` - Shared utilities, types, constants
- `@latera/ui` - Shared React components
- `@latera/tsconfig` - Shared TypeScript configurations

## Consequences

### Positive

- **Code Sharing**: Shared types, utilities, and components between desktop and web
- **Incremental Builds**: Turborepo's caching dramatically speeds up rebuilds
- **Task Orchestration**: Parallel task execution with dependency awareness
- **Type Safety**: Changes to shared packages immediately reflected in consumers
- **Single Command Development**: `turbo dev` runs all apps simultaneously
- **Consistent Tooling**: Shared ESLint, Prettier, TypeScript configs
- **Easier Refactoring**: Cross-package refactoring with IDE support
- **Scalable**: Easy to add browser extension or API server later
- **CI/CD Efficiency**: Only build affected packages on changes

### Negative

- **Initial Complexity**: More setup than single-package repo
- **Dependency Management**: Need to manage inter-package dependencies carefully
- **Build Tool Learning Curve**: Understanding Turborepo pipeline configuration
- **Potential Over-Engineering**: May be overkill for early stages
- **Versioning Complexity**: Coordinating versions across packages
- **Workspace Hoisting**: Occasional issues with dependency resolution

### Mitigation Strategies

- Start with minimal packages, add only when needed
- Use clear naming conventions for workspace packages
- Document package relationships and dependency graph
- Leverage Turborepo's remote caching once team grows
- Keep shared packages focused and small
- Use `pnpm` for efficient disk usage and strict dependencies

## Alternatives Considered

### Polyrepo (Separate Repositories)
- **Pros**: Simplest to start, independent versioning, clear boundaries
- **Cons**: Code duplication, type drift between projects, harder to refactor shared code, multiple repos to manage

### Nx Monorepo
- **Pros**: More features (code generators, affected graph visualization), excellent DX
- **Cons**: Heavier tooling, more configuration, steeper learning curve, potentially over-featured for side project

### Lerna
- **Pros**: Mature, well-known, good for library publishing
- **Cons**: Primarily for package publishing workflows, slower builds than Turborepo, less active development recently

### pnpm Workspaces Only
- **Pros**: Minimal tooling, fast, efficient disk usage
- **Cons**: No built-in task orchestration, no caching layer, manual build ordering, less sophisticated than Turborepo

### Rush
- **Pros**: Built for large-scale monorepos, robust dependency management
- **Cons**: Complex for small projects, enterprise-focused, steep learning curve, less community adoption

## Implementation Details

### Turborepo Pipeline Configuration

```json
{
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", ".next/**", "out/**"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    },
    "lint": {
      "dependsOn": ["^build"]
    },
    "test": {
      "dependsOn": ["^build"]
    }
  }
}
```

### Package Manager Choice

We will use **pnpm** with Turborepo because:
- Efficient disk usage (content-addressable storage)
- Fast installation times
- Strict dependency resolution prevents phantom dependencies
- First-class workspace support
- Better monorepo performance than npm/yarn

### Development Workflow

```bash
# Install all dependencies
pnpm install

# Run all apps in development mode
pnpm dev

# Build all packages
pnpm build

# Lint all packages
pnpm lint

# Run tests across workspace
pnpm test

# Work on specific package
pnpm --filter @latera/desktop dev
```

## Package Dependency Rules

1. **Apps can depend on packages**, but not other apps
2. **Packages can depend on other packages**, with clear hierarchy
3. **Avoid circular dependencies** between packages
4. **Shared package** should have no dependencies on app-specific logic
5. **UI package** can depend on shared package only

## Notes

- Start with `@latera/shared` package for types and utilities
- Add `@latera/ui` only when we have 3+ shared components
- Use Turborepo's `--filter` flag to work on specific packages during development
- Consider remote caching (Vercel) if CI builds become slow
- Document package purposes in each package.json `description` field

## Migration Path

1. **Phase 1** (Initial): Single desktop app + landing page, minimal shared code
2. **Phase 2** (Growth): Extract shared types and utilities to `@latera/shared`
3. **Phase 3** (Scaling): Add `@latera/ui` when component library emerges
4. **Phase 4** (Future): Add browser extension or API as new workspace packages
