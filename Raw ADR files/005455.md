## Context

The multi-agent trading system requires a dedicated relational database for transactional data with strict ACID compliance. The system handles:

1. **Trade Execution Records**: Final executed trades with complete order details, fills, and commission data
2. **Order Lifecycle Tracking**: Order creation, submission, fills, partial fills, cancellations, and rejections
3. **Audit Trails**: Regulatory compliance records for all trading activities and agent decisions
4. **Agent State Checkpoints**: Permanent snapshots of agent state for recovery and audit purposes

**Current State**:
- ADR-001 established hybrid memory architecture (Redis for operational, Cloud SQL for transactional, BigQuery for analytical)
- ADR-002 defined data boundary (Cloud SQL for `trades`, `orders`, `audit_trails`)
- ADR-010 specifies Google ADK agents connect to Cloud SQL for state persistence
- ADR-011 defines Docker containers with Cloud SQL Proxy sidecars for secure connectivity
- **Gap**: No dedicated ADR documenting Cloud SQL design decisions, instance sizing, cost analysis, or migration strategy

**Requirements**:
- ACID compliance for financial transaction integrity
- Low-latency writes (<50ms) for order lifecycle updates
- High availability (99.95% SLA minimum)
- Point-in-time recovery for regulatory compliance
- Secure connectivity from containerized agents on Cloud Run
- Cost-effective operation (<$200/month for transactional workload)
- Horizontal read scalability for audit queries

## Decision

**Adopt Google Cloud SQL for PostgreSQL** as the dedicated transactional database for all ACID-compliant financial records.

### Primary Decision Points

1. **Database Engine**: PostgreSQL 15.x (latest stable)
2. **Instance Type**: Serverless (Cloud SQL Autopilot) for development/staging, Always-On (Enterprise tier) for production
3. **Connection Method**: Cloud SQL Proxy sidecars in Cloud Run containers (per ADR-011)
4. **Schema Migration**: Alembic for version-controlled migrations
5. **Backup Strategy**: Automated daily backups with 30-day retention, point-in-time recovery enabled
6. **Replication**: Single-region with high availability (HA) configuration (primary + standby)

### Core Tables

**1. trades**
- Final executed trade records
- Fields: trade_id, symbol, strategy_type, entry_timestamp, exit_timestamp, premium_received, max_loss, profit_loss, state
- Primary key: trade_id (UUID)
- Indexes: symbol, entry_timestamp, state

**2. orders**
- Order lifecycle tracking
- Fields: order_id, trade_id, order_type, symbol, quantity, limit_price, status, submitted_at, filled_at, commission
- Primary key: order_id (UUID)
- Foreign key: trade_id → trades(trade_id)
- Indexes: trade_id, status, submitted_at

**3. audit_trails**
- Compliance and audit records
- Fields: audit_id, event_type, agent_name, event_timestamp, event_data (JSONB), trade_id, order_id
- Primary key: audit_id (UUID)
- Foreign keys: trade_id → trades(trade_id), order_id → orders(order_id)
- Indexes: event_type, agent_name, event_timestamp

**4. agent_state_checkpoints** (from ADR-001)
- Permanent agent state snapshots
- Fields: checkpoint_id, agent_id, checkpoint_timestamp, state_data (JSONB)
- Primary key: checkpoint_id (UUID)
- Indexes: agent_id, checkpoint_timestamp

## Rationale

### Why PostgreSQL Over Alternatives

| Aspect | PostgreSQL | MySQL | SQL Server | Firestore |
|--------|-----------|--------|------------|-----------|
| **ACID Compliance** | Full | Full | Full | Limited |
| **JSONB Support** | Excellent | Limited | Good | Native |
| **GCP Integration** | Native | Native | None | Native |
| **Transaction Isolation** | Serializable | Repeatable Read | Serializable | None |
| **Cost (Cloud SQL)** | $50-150/month | $50-150/month | N/A (Azure) | $100+/month |
| **Python Ecosystem** | Excellent (asyncpg) | Good (aiomysql) | Poor | Good |
| **Compliance Features** | Excellent | Good | Excellent | Limited |

**Decision Factors**:
1. **JSONB Support** (Weight: 30%): PostgreSQL's JSONB for agent state storage and audit event data
2. **ACID Guarantees** (Weight: 30%): Required for financial transaction integrity
3. **Python Integration** (Weight: 20%): asyncpg provides async/await support matching Google ADK patterns
4. **Cost** (Weight: 10%): Competitive pricing on Cloud SQL
5. **GCP Native** (Weight: 10%): First-class Cloud SQL support

**PostgreSQL Advantages**:
- Industry-standard for financial applications
- Superior JSON support for flexible agent state and audit data
- Strong data integrity and constraint enforcement
- Excellent Python async support (asyncpg library)
- Advanced indexing (B-tree, GIN for JSONB)
- Proven track record for compliance and auditing

### Why Cloud SQL Over Self-Hosted PostgreSQL

| Aspect | Cloud SQL | Self-Hosted EC2/GCE | Self-Hosted Kubernetes |
|--------|----------|---------------------|------------------------|
| **Operational Overhead** | Minimal | High | Very High |
| **High Availability** | Built-in | Manual setup | Manual setup |
| **Automated Backups** | Built-in | Manual config | Manual config |
| **Point-in-Time Recovery** | Built-in | Manual setup | Manual setup |
| **Security Patches** | Automatic | Manual | Manual |
| **Monitoring** | Integrated (Cloud Ops) | Manual setup | Manual setup |
| **Cost (production)** | $150-200/month | $100-150/month + labor | $200+/month + labor |

**Decision Factors**:
1. **Operational Overhead** (Weight: 40%): Managed service eliminates DB administration burden
2. **Reliability** (Weight: 30%): Built-in HA, automated failover, backup management
3. **Security** (Weight: 20%): Automatic security patches, integrated IAM, encryption at rest/in transit
4. **Cost** (Weight: 10%): Total cost of ownership (including labor) favors managed service

**Cloud SQL Advantages**:
- Zero database administration overhead
- Built-in high availability and automatic failover
- Automated backup and point-in-time recovery
- Automatic security patching and updates
- Integrated with Cloud Monitoring and Cloud Logging
- Cloud SQL Proxy for secure connectivity
- Scales vertically without downtime
- Aligns with serverless, managed-first architecture (ADR-011, ADR-016)

### Connection Pooling Strategy

**Connection Pool Sizing** (per agent container):
```python
# asyncpg connection pool configuration
pool_config = {
    "min_size": 2,           # Minimum idle connections
    "max_size": 10,          # Maximum connections per container
    "max_queries": 50000,    # Connection recycling threshold
    "max_inactive_connection_lifetime": 300,  # 5 minutes
    "timeout": 10,           # Connection acquisition timeout (seconds)
    "command_timeout": 30    # Query execution timeout (seconds)
}

# Total connection budget calculation
# Orchestrator: 1 instance × 10 connections = 10
# Stock Selection: 1 instance × 10 connections = 10
# Strategy Agents: 5 instances × 10 connections = 50
# Service Agents: 10 instances × 10 connections = 100
# Total: ~170 connections (well under PostgreSQL default 100-200 limit)
```

**Connection Pool Implementation**:
```python
import asyncpg
from google.cloud.sql.connector import Connector

class CloudSQLConnectionPool:
    """Cloud SQL connection pool with Cloud SQL Proxy"""

    def __init__(self, instance_connection_name: str, database: str):
        self.connector = Connector()
        self.instance_connection_name = instance_connection_name
        self.database = database
        self.pool = None

    async def init_pool(self):
        """Initialize connection pool"""
        self.pool = await asyncpg.create_pool(
            dsn=await self._get_connection_string(),
            min_size=2,
            max_size=10,
            max_queries=50000,
            max_inactive_connection_lifetime=300,
            timeout=10,
            command_timeout=30
        )

    async def _get_connection_string(self) -> str:
        """Get connection string via Cloud SQL Connector"""
        return await self.connector.connect_async(
            instance_connection_name=self.instance_connection_name,
            driver="asyncpg",
            db=self.database,
            enable_iam_auth=True  # IAM-based authentication
        )
```

### Schema Migration Approach

**Alembic Configuration**:
- Version-controlled migrations in `migrations/versions/`
- Automated migration checks in CI/CD pipeline (ADR-018)
- Staging environment migration testing before production
- Rollback procedures for failed migrations

**Migration Workflow**:
```bash
# 1. Generate migration from schema changes
alembic revision --autogenerate -m "Add trade_state_transitions table"

# 2. Review generated migration script
# 3. Test migration in local/dev environment
alembic upgrade head

# 4. CI/CD pipeline tests migration in staging
# 5. Manual approval required for production migration
# 6. Production migration during maintenance window
alembic -c production.ini upgrade head
```

**Schema Versioning**:
- `alembic_version` table tracks current schema version
- Each migration script includes upgrade and downgrade paths
- Breaking changes require major version increment
- Schema compatibility validated on agent startup

### Backup and Disaster Recovery Strategy

**Automated Backups**:
- Daily automated backups at 02:00 UTC (off-peak)
- 30-day retention for compliance requirements
- Point-in-time recovery (PITR) with 7-day window
- Backup storage cost: ~$2/month (50GB × $0.08/GB × 0.5 compression ratio)

**Disaster Recovery Procedures**:

**Recovery Time Objective (RTO)**: 1 hour
**Recovery Point Objective (RPO)**: 15 minutes (via PITR)

**Failure Scenarios**:

1. **Primary Instance Failure** (HA configuration handles automatically):
   - Automatic failover to standby instance (<60 seconds)
   - No manual intervention required
   - Application reconnects via Cloud SQL Proxy

2. **Data Corruption or Accidental Deletion**:
   - Restore from point-in-time recovery
   - Manual process: 30-60 minutes
   - Steps: Create new instance → Restore to timestamp → Update connection strings → Restart agents

3. **Region-Wide Outage** (catastrophic):
   - Restore from backup to new region
   - Manual process: 1-2 hours
   - Requires DNS/configuration updates

**Backup Validation**:
- Monthly automated backup restoration test
- Validation: Schema integrity, row counts, sample data queries
- Documented in runbook (operations manual)

## Consequences

### Positive

1. **ACID Compliance**: Full transactional integrity for financial records, regulatory compliance guaranteed
2. **Operational Simplicity**: Zero database administration overhead, automated backups, patching, and HA
3. **Cost-Effective**: $150-200/month for production workload vs $500+/month for self-hosted equivalent (including labor)
4. **Integration**: Native Cloud SQL Proxy support in Cloud Run (ADR-011), IAM authentication, VPC peering
5. **Reliability**: 99.95% SLA, automatic failover, point-in-time recovery for disaster scenarios
6. **Scalability**: Vertical scaling without downtime, read replica support for future growth
7. **Security**: Encrypted at rest/in transit, IAM-based access, Cloud Audit Logs integration
8. **Developer Experience**: Async Python support (asyncpg), Alembic migrations, standard PostgreSQL ecosystem

### Negative

1. **GCP Lock-In**: Cloud SQL proprietary features (IAM auth, Cloud SQL Proxy) create vendor dependency
2. **Connection Overhead**: Cloud SQL Proxy adds 1-2ms latency per query (acceptable for transactional workload)
3. **Scaling Limitations**: Vertical scaling only (no horizontal sharding), max instance size limits
4. **Cost at Scale**: Cloud SQL pricing increases significantly for very large instances (>16 vCPU)
5. **Network Dependency**: Requires VPC peering or Cloud SQL Proxy, adds network complexity
6. **Migration Downtime**: Major version upgrades (PostgreSQL 15 → 16) require maintenance window

### Mitigation Strategies

**Lock-In Mitigation**:
- Use standard PostgreSQL features (avoid Cloud SQL-specific extensions)
- Maintain compatibility with self-hosted PostgreSQL for migration path
- Use Terraform for infrastructure (ADR-019) to enable multi-cloud portability
- Document Cloud SQL-specific features (IAM auth, Cloud SQL Proxy) for future migration planning

**Performance Mitigation**:
- Connection pooling to amortize proxy overhead across multiple queries
- Caching layer (Redis) for read-heavy queries (per ADR-001)
- Query optimization and index tuning to minimize latency
- Monitor Cloud SQL Proxy metrics for bottleneck detection

**Scaling Mitigation**:
- Design schema for horizontal partitioning (sharding-ready architecture)
- Use BigQuery for analytical queries (per ADR-002, ADR-004) to offload Cloud SQL
- Implement read replicas if read load exceeds 1000 QPS
- Plan for multi-instance architecture if write load exceeds 10,000 TPS (unlikely for this workload)

## Alternatives Considered

### 1. MySQL on Cloud SQL

**Pros**:
- Lower cost (identical pricing to PostgreSQL)
- Simpler replication setup
- Broader hosting provider support

**Cons**:
- Limited JSON support (no native JSONB equivalent)
- Weaker transaction isolation guarantees
- Less robust for complex queries

**Verdict**: Rejected due to inferior JSONB support and transaction isolation. Agent state checkpoints and audit trails require flexible JSON storage.

### 2. Self-Hosted PostgreSQL on GCE

**Pros**:
- Maximum control over configuration
- Potentially lower compute costs ($100-150/month)
- No vendor lock-in to Cloud SQL

**Cons**:
- High operational overhead (patching, backups, HA setup)
- Manual failover configuration
- No built-in point-in-time recovery
- Requires dedicated DevOps resources

**Verdict**: Rejected due to operational overhead. Contradicts serverless, managed-first architecture principles (ADR-011, ADR-016).

### 3. NoSQL (Firestore, MongoDB)

**Pros**:
- Horizontal scalability
- Flexible schema for agent state
- Native JSON support

**Cons**:
- No ACID guarantees across documents
- Eventual consistency model unacceptable for financial transactions
- Complex query patterns for relational data (orders → trades)
- Higher cost for transactional workload

**Verdict**: Rejected due to lack of ACID compliance. Financial transaction integrity non-negotiable.

### 4. CockroachDB (Distributed SQL)

**Pros**:
- Horizontal scalability
- PostgreSQL wire protocol compatibility
- Multi-region deployment

**Cons**:
- Over-engineered for current workload (<1 TPS)
- Higher cost ($500+/month for managed service)
- Increased operational complexity
- No GCP-native integration

**Verdict**: Rejected due to unnecessary complexity and cost. Current workload does not require distributed SQL capabilities.

### 5. Cloud Spanner

**Pros**:
- Global consistency and high availability
- Horizontal scalability
- Strong ACID guarantees

**Cons**:
- Extremely high cost ($1000+/month minimum)
- Over-engineered for workload size
- Complex schema design requirements
- No PostgreSQL compatibility

**Verdict**: Rejected due to prohibitive cost and complexity. Designed for 10,000+ TPS workloads, not <10 TPS.

## Integration with Existing Architecture

### ADR-001: Agent Memory Architecture
- Cloud SQL serves as Permanent Memory Layer for transactional records
- Dual persistence: Redis (operational state, TTL 24h) + Cloud SQL (permanent checkpoints)
- Agent state checkpoints written to `agent_state_checkpoints` table for recovery

### ADR-002: Cost-Effective Permanent Memory
- Cloud SQL stores `trades`, `orders`, `audit_trails` per data boundary specification
- BigQuery stores analytical data (`agent_session_archives`, `market_sentiment_snapshots`)
- Clear separation: Cloud SQL = transactional OLTP, BigQuery = analytical OLAP

### ADR-004: BigQuery Analytics Architecture
- Trade records from Cloud SQL exported to BigQuery for historical analysis
- Nightly ETL job (Cloud Functions) transfers closed trades to BigQuery
- BigQuery queries historical trade performance, Cloud SQL handles active trades

### ADR-010: Google ADK Framework
- Google ADK agents use asyncpg to connect to Cloud SQL
- State persistence via Cloud SQL for permanent checkpoints
- Agent initialization loads state from Redis (fast) or Cloud SQL (fallback)

### ADR-011: Docker Containerization
- Cloud SQL Proxy runs as sidecar container in Cloud Run pods
- Connection string: `postgresql://user:pass@localhost:5432/trading_db` (proxy on localhost)
- IAM-based authentication (no password management required)

### ADR-018: GitHub Actions CI/CD
- Alembic migration testing in CI pipeline
- Automated schema validation before deployment
- Staging database migration before production promotion

### ADR-021: Observability with Google Cloud Operations
- Cloud SQL metrics integrated into Cloud Monitoring dashboards
- Query performance logs exported to Cloud Logging
- Automated alerting for database health issues

### ADR-022: Google Secret Manager
- Database credentials stored in Secret Manager (if not using IAM auth)
- Connection strings injected as environment variables
- Secret rotation automated via Terraform
