# ADR-015: Message Broker Technology Selection (RabbitMQ)

## Status
Accepted (October 7, 2025)

## Context

### Business Drivers
BahariWatch requires asynchronous, event-driven communication between microservices (per ADR-002: Event-Driven Choreography). The system must process community reports of illegal fishing activities and generate enforcement alerts in near real-time to enable rapid response while vessels remain in the area. The proposal explicitly requires:

1. **Real-time alert delivery**: <5 seconds (p95) from report submission to enforcement notification (ADR-006 Performance SLO)
2. **High availability**: 99.5% uptime for critical reporting workflow (proposal requirement)
3. **Audit trail**: Legal evidence admissibility requires immutable event logs for 7-year retention (ADR-008 compliance)
4. **Message durability**: Zero data loss guarantee for enforcement alerts (proposal legal requirement)
5. **Dead letter queue**: Failed message recovery for manual intervention (ADR-014 saga state management)

### Stakeholder Concerns
1. **Beach Management Units (BMUs)**: Fast alert delivery determines enforcement effectiveness (15-30 minute vessel response window)
2. **Enforcement Officers**: Reliable message delivery prevents escaped illegal fishing vessels (KSh 2.9B annual economic loss)
3. **Anonymous Reporters**: System resilience ensures safe participation without fear of message loss
4. **Research Team**: Budget constraint (KSh 59,500 total project cost) limits infrastructure choices
5. **Development Team**: Operational simplicity for 6-month pilot timeline (May-October 2025)

### Technical Constraints
1. **Architecture Style**: Event-driven choreography (ADR-002) requires pub-sub messaging with topic routing
2. **Workflow Pattern**: Anthology Saga (ADR-004) uses asynchronous events with eventual consistency (30-second p99 window per ADR-014)
3. **Deployment Platform**: DigitalOcean App Platform (ADR-012) PaaS limits infrastructure complexity
4. **Budget**: Message broker must fit within $25-40/month total infrastructure cost (ADR-012)
5. **Team Expertise**: Python/Django development team (6-month project timeline limits learning curve)

### Integration with Other ADRs
- **ADR-001 (Microservices)**: Six services communicate via message broker (Report, Matching, Alert, Notification, Geospatial, Analytics)
- **ADR-002 (Choreography)**: Message broker is central coordination mechanism for event-driven workflows
- **ADR-004 (Anthology Saga)**: Message broker provides eventual consistency guarantees for report→match→alert workflow
- **ADR-008 (Security)**: Message broker must support TLS encryption and RBAC for sensitive enforcement data
- **ADR-010 (Fitness Functions)**: Message broker metrics must feed Prometheus monitoring for SLO validation
- **ADR-011 (External Integration)**: Circuit breaker pattern requires message queue for AIS/VMS feed outages
- **ADR-012 (Deployment)**: Managed message broker service must integrate with DigitalOcean App Platform
- **ADR-014 (Consistency)**: Idempotent consumers, retry logic, dead letter queues depend on broker capabilities

## Decision

**We will use RabbitMQ as the message broker for all inter-service asynchronous communication in BahariWatch.**

### Specific Configuration
1. **Managed Service**: DigitalOcean Managed RabbitMQ cluster (3-node cluster for high availability)
2. **Messaging Pattern**: Topic exchanges with durable queues for pub-sub event choreography
3. **Message Durability**: Persistent messages with disk-backed durable queues (zero data loss)
4. **Dead Letter Exchange**: Automatic retry with exponential backoff (1min, 5min, 15min, 1hour) → DLQ (per ADR-014)
5. **Publisher Confirms**: Synchronous acknowledgments ensure message acceptance before API response
6. **Consumer Acknowledgments**: Manual acknowledgments with idempotent consumers (Redis deduplication per ADR-014)
7. **Event Versioning**: JSON Schema validation with semantic versioning (v1, v2) for backward compatibility
8. **TLS Encryption**: End-to-end encryption for all message broker connections (per ADR-008 security requirements)

## Rationale

### Alternatives Considered

#### **Alternative 1: Apache Kafka (Event Streaming Platform)**

**Advantages:**
- **Event replay capability**: Consumers can reprocess historical events from specific offsets (useful for analytics)
- **High throughput**: Handles 100,000+ messages/second with horizontal partitioning
- **Event sourcing**: Immutable log provides natural audit trail for compliance (7-year retention per ADR-008)
- **Consumer lag monitoring**: Built-in metrics for tracking consumer group processing delays
- **Exactly-once semantics**: Transactional producers/consumers prevent duplicate events

**Disadvantages:**
- **Operational complexity**: Requires ZooKeeper (Kafka <3.0) or KRaft controller quorum, partition management, consumer group coordination
- **Cost**: DigitalOcean Managed Kafka starts at $60/month (exceeds total budget of $25-40/month per ADR-012)
- **Over-engineered for use case**: BahariWatch expects <500 reports/day during pilot (0.35 messages/second average, 10 messages/second peak)
- **Learning curve**: Team unfamiliar with Kafka ecosystem (Confluent Schema Registry, Connect, Streams API) in 6-month timeline
- **Message routing limitations**: Kafka topics lack flexible routing patterns (requires consumer filtering or multiple topics)
- **Latency overhead**: Batch writes optimize throughput but increase latency (50-100ms vs RabbitMQ 5-20ms)

**Why Rejected:**
Kafka's strengths (high throughput, event replay, horizontal scalability) are unnecessary for BahariWatch's modest message volumes (<10 msg/sec). The **$60/month cost exceeds the entire infrastructure budget**, and operational complexity (ZooKeeper, partition management) introduces unnecessary risk for a 6-month pilot project. While event replay is valuable for analytics, ADR-013's saga state tracking provides equivalent audit trail via PostgreSQL saga log tables (simpler operational model).

---

#### **Alternative 2: AWS SNS/SQS (Managed Pub-Sub + Queueing)**

**Advantages:**
- **Fully managed**: Zero operational overhead (no broker configuration, patching, scaling)
- **Pay-per-use pricing**: $0.50 per million requests (cost-effective for low volumes)
- **Native AWS integration**: Seamless integration with Lambda, CloudWatch, EventBridge
- **Unlimited scalability**: Auto-scales to handle traffic spikes without provisioning
- **FIFO queues**: Guaranteed message ordering with exactly-once delivery (SQS FIFO)

**Disadvantages:**
- **Vendor lock-in**: AWS-specific API ties architecture to single cloud provider (contradicts ADR-012 DigitalOcean deployment)
- **Architecture complexity**: SNS + SQS requires separate services for pub-sub + queueing (operational overhead)
- **Limited routing**: SNS topic filters lack RabbitMQ's flexible routing key patterns (e.g., `report.*.v1` wildcards)
- **No dead letter exchange**: SQS DLQ requires manual configuration per queue (vs RabbitMQ centralized DLX)
- **Latency**: Cross-service SNS→SQS hops add 50-100ms vs RabbitMQ's in-process routing
- **Migration cost**: Moving infrastructure from DigitalOcean (ADR-012) to AWS invalidates existing deployment decisions

**Why Rejected:**
AWS SNS/SQS creates **vendor lock-in** that conflicts with ADR-012's DigitalOcean deployment strategy. The two-service architecture (SNS for pub-sub + SQS for queueing) increases operational complexity compared to RabbitMQ's unified broker model. Additionally, SNS topic filtering lacks the sophisticated routing key patterns required for choreography (e.g., matching service consumes `report.submitted.*` but ignores `report.updated.*`). While cost is attractive, the migration burden outweighs benefits for a 6-month pilot.

---

#### **Alternative 3: Redis Pub-Sub (In-Memory Messaging)**

**Advantages:**
- **Ultra-low latency**: Sub-millisecond message delivery (in-memory)
- **Simple deployment**: Redis already used for idempotent consumer cache (ADR-014), no additional infrastructure
- **Cost-effective**: $15/month managed Redis cluster (DigitalOcean) handles both caching + messaging
- **Developer familiarity**: Team already uses Redis for session management, rate limiting

**Disadvantages:**
- **No message durability**: Pub-sub messages lost if subscriber is offline (fire-and-forget model)
- **No message acknowledgments**: Cannot guarantee at-least-once delivery (critical for enforcement alerts)
- **No dead letter queue**: Failed messages silently dropped (no recovery mechanism)
- **No message replay**: Cannot reprocess historical events for debugging or analytics
- **Limited routing**: Simple channel-based routing lacks topic exchange flexibility (e.g., wildcard subscriptions)
- **Horizontal scaling limitations**: Single-node Redis Pub-Sub doesn't scale across multiple nodes (Redis Cluster requires client-side sharding)

**Why Rejected:**
Redis Pub-Sub's **fire-and-forget model violates zero data loss requirement** for enforcement alerts (proposal legal requirement). The lack of message acknowledgments means a crashed consumer loses in-flight messages, creating compliance risk for court-admissible evidence (ADR-008). Additionally, missing dead letter queue support contradicts ADR-014's saga recovery strategy (manual intervention for stuck workflows). While latency is excellent, **reliability trade-offs are unacceptable** for critical enforcement notifications.

---

#### **Alternative 4: No Message Broker (Synchronous HTTP API Calls)**

**Advantages:**
- **Simplicity**: Direct service-to-service HTTP calls (no middleware)
- **Request-response semantics**: Immediate failure notification if downstream service is unavailable
- **Zero infrastructure cost**: No message broker hosting fees
- **Debugging simplicity**: HTTP logs provide complete request/response traces

**Disadvantages:**
- **Tight temporal coupling**: Report Service must wait for Matching Service, Alert Service, Notification Service to complete (serialized processing)
- **Cascading failures**: If Notification Service is down, entire workflow fails (violates 99.5% availability SLO per ADR-006)
- **Poor scalability**: Synchronous calls block threads, limiting concurrent report submissions (ADR-006 requires 10,000+ users)
- **No retry mechanism**: Transient failures require application-level retry logic in every service (complex error handling)
- **Circuit breaker complexity**: Each service needs circuit breaker configuration for every downstream dependency (N² integration points)
- **Violates ADR-002**: Contradicts explicit decision for event-driven choreography (destroys service decoupling)

**Why Rejected:**
Synchronous HTTP calls **violate ADR-002's explicit decision for event-driven choreography**. This approach creates tight temporal coupling that contradicts the microservices architecture's decoupling goals (ADR-001). A single service failure (e.g., Notification Service SMS provider outage) would cascade to block all report submissions, **violating 99.5% availability SLO** (ADR-006). Additionally, synchronous processing increases latency (serialized vs parallel workflow stages), making sub-5-second alert delivery target (ADR-006) difficult to achieve. This alternative fundamentally undermines the chosen architecture style.

### Trade-Off Analysis

| Dimension | RabbitMQ | Kafka | AWS SNS/SQS | Redis Pub-Sub | Sync HTTP |
|-----------|----------|-------|-------------|---------------|-----------|
| **Latency** (lower is better) | ⭐⭐⭐⭐ 5-20ms | ⭐⭐⭐ 50-100ms | ⭐⭐⭐ 50-100ms | ⭐⭐⭐⭐⭐ <1ms | ⭐⭐ 100-500ms |

| **Throughput** (msg/sec) | ⭐⭐⭐⭐ 10,000+ | ⭐⭐⭐⭐⭐ 100,000+ | ⭐⭐⭐⭐⭐ Unlimited | ⭐⭐⭐⭐ 50,000+ | ⭐⭐ 1,000+ |

| **Team Familiarity** | ⭐⭐⭐⭐ Python kombu | ⭐⭐ Kafka ecosystem | ⭐⭐⭐ Boto3 SDK | ⭐⭐⭐⭐⭐ Redis-py | ⭐⭐⭐⭐⭐ Requests lib |

**Justification:**
RabbitMQ provides the **optimal balance** for BahariWatch's requirements:
1. **Low latency (5-20ms)** meets <5 second alert delivery SLO (ADR-006)
2. **Message durability** guarantees zero data loss for enforcement evidence (proposal requirement)
3. **Flexible routing** (topic exchanges) enables sophisticated choreography patterns (e.g., wildcard subscriptions for `report.*.v1`)
4. **Native dead letter exchange** simplifies ADR-014 saga recovery strategy
5. **Managed service** ($15/month) fits within $25-40/month budget (ADR-012)
6. **Python kombu library** aligns with Django development stack (minimal learning curve)

RabbitMQ sacrifices Kafka's event replay capability, but ADR-014's saga state log provides equivalent audit trail via PostgreSQL (simpler operational model for 6-month pilot).

## Consequences

### Positive

1. **Low Latency Delivery**: 5-20ms message routing enables <5 second alert delivery SLO (ADR-006 performance requirement)
2. **Zero Data Loss**: Durable queues + publisher confirms guarantee message persistence for legal evidence (ADR-008 compliance)
3. **Operational Simplicity**: DigitalOcean managed service eliminates broker maintenance overhead (compatible with 6-month pilot timeline)
4. **Budget Compliance**: $15/month cost fits within $25-40/month infrastructure budget (ADR-012 deployment constraints)
5. **Flexible Routing**: Topic exchanges support sophisticated choreography patterns (e.g., `report.*.v1` wildcard subscriptions)
6. **Dead Letter Queue**: Native DLX enables ADR-014 saga recovery strategy (automatic retry + manual intervention)
7. **Team Productivity**: Python kombu library aligns with Django stack (minimal learning curve)
8. **High Availability**: 99.95% SLA + 3-node cluster meets 99.5% availability SLO (ADR-006 requirement)
9. **Decoupling**: Asynchronous messaging eliminates temporal coupling between services (ADR-002 choreography)
10. **Idempotent Consumers**: Message acknowledgments enable Redis-backed deduplication (ADR-014 consistency guarantees)
11. **Event Versioning**: JSON Schema validation supports backward-compatible API evolution (ADR-005 versioning)
12. **Security Compliance**: TLS encryption + RBAC protect sensitive enforcement data (ADR-008 security requirements)

### Negative

1. **No Event Replay**: Cannot reprocess historical events from specific offsets (must rely on saga state log for audit trail)
2. **Manual Monitoring**: Requires custom Prometheus exporters for queue depth, consumer lag metrics (vs Kafka's built-in JMX)
3. **Horizontal Scaling Complexity**: Queue sharding requires manual partition design (vs Kafka's automatic partitioning)
4. **Limited Throughput**: 10,000 msg/sec ceiling may require migration if pilot scales beyond 10,000+ active users
5. **Single Cloud Vendor**: DigitalOcean managed service creates lock-in (though mitigated by AMQP protocol portability)
6. **Message Size Limit**: 128MB default max message size may limit future video evidence uploads (requires S3 presigned URLs)

### Neutral

1. **Technology Maturity**: RabbitMQ (15+ years) is battle-tested, but lacks Kafka's "modern event streaming" ecosystem
2. **Consumer Lag Tracking**: Requires manual implementation via Prometheus metrics (not built into protocol)
3. **Multi-Tenancy**: Supports virtual hosts for isolation, but lacks Kafka's fine-grained topic ACLs
4. **Message Ordering**: Guarantees order within single queue, but not across multiple consumers (acceptable for eventual consistency)

### Security Implications

1. **TLS Encryption**: All RabbitMQ connections use TLS 1.3 (per ADR-008 encryption requirements)
   - Message confidentiality: Enforcement alert data encrypted in transit
   - Certificate validation: Mutual TLS prevents man-in-the-middle attacks

2. **Access Control**: RabbitMQ virtual hosts + user permissions isolate service contexts
   - Report Service: Write-only to `report.submitted.*` topic
   - Matching Service: Read-only from `report.submitted.*`, write to `match.found.*`
   - Alert Service: Read-only from `match.found.*`, write to `alert.generated.*`
   - Admin vhost: Isolated from application traffic for management UI

3. **Message Signing**: HMAC-SHA256 signatures on critical events (alert.generated) prevent tampering
   - Signature verification in Notification Service ensures message authenticity
   - Invalid signatures trigger DLQ for security investigation

### Data Privacy Implications

1. **GDPR Right to Erasure**: RabbitMQ messages retain no PII after consumption
   - Durable queues contain only UUIDs referencing database records
   - User deletion (ADR-008) requires no message broker cleanup

2. **Anonymous Reporting**: Message payloads exclude user identifiers (per ADR-008 privacy)
   - `report.submitted` event contains only report_id, GPS, photo_url
   - Reporter identity never transmitted through message broker

3. **Data Residency**: DigitalOcean managed RabbitMQ cluster hosted in Frankfurt (EU GDPR compliance)
   - Cross-border data transfer limited to encrypted message payloads
   - Audit logs stored in Kenya region (per ADR-013 data retention)

## Implementation Notes

### Phase 1: RabbitMQ Cluster Provisioning (Week 1)

1. **Provision DigitalOcean Managed RabbitMQ**
   ```bash
   # DigitalOcean CLI
   doctl databases create bahariwatch-rabbitmq \
     --engine rabbitmq \
     --version 3.12 \
     --size db-s-2vcpu-4gb \
     --region fra1 \
     --num-nodes 3
   
   # Export connection details
   doctl databases connection bahariwatch-rabbitmq \
     --format URI > .env.rabbitmq
   ```

2. **Configure Virtual Hosts and Users**
   ```bash
   # Create virtual hosts for service isolation
   rabbitmqctl add_vhost /bahariwatch
   rabbitmqctl add_vhost /admin
   
   # Create service-specific users
   rabbitmqctl add_user report_service $(openssl rand -hex 32)
   rabbitmqctl set_permissions -p /bahariwatch report_service \
     "report\\..*" "report\\..*" ""  # Write to report.*, read nothing
   
   rabbitmqctl add_user matching_service $(openssl rand -hex 32)
   rabbitmqctl set_permissions -p /bahariwatch matching_service \
     "^$" "match\\..*" "report\\..*"  # Read report.*, write match.*
   
   rabbitmqctl add_user alert_service $(openssl rand -hex 32)
   rabbitmqctl set_permissions -p /bahariwatch alert_service \
     "^$" "alert\\..*" "match\\..*"  # Read match.*, write alert.*
   ```

3. **Configure TLS Encryption**
   ```bash
   # Generate TLS certificates (Let's Encrypt)
   certbot certonly --standalone \
     -d rabbitmq.bahariwatch.internal \
     --email admin@bahariwatch.ke \
     --agree-tos
   
   # Configure RabbitMQ TLS listeners
   cat >> /etc/rabbitmq/rabbitmq.conf <<EOF
   listeners.ssl.default = 5671
   ssl_options.cacertfile = /etc/letsencrypt/live/rabbitmq.bahariwatch.internal/chain.pem
   ssl_options.certfile   = /etc/letsencrypt/live/rabbitmq.bahariwatch.internal/cert.pem
   ```

### Phase 3: Producer Implementation (Week 2-3)

```python
# report_service/messaging/producer.py
import json
import logging
import uuid
from typing import Dict, Any
import pika
from django.conf import settings
import jsonschema

logger = logging.getLogger(__name__)

class EventPublisher:
    """Thread-safe event publisher with schema validation"""
    
    def __init__(self):
        self.connection = None
        self.channel = None
        self._connect()
        
    def _connect(self):
        """Establish connection with TLS and publisher confirms"""
        credentials = pika.PlainCredentials(
            settings.RABBITMQ_USER,
            settings.RABBITMQ_PASSWORD
        )
        
        ssl_options = pika.SSLOptions(
            context=self._get_ssl_context(),
            server_hostname=settings.RABBITMQ_HOST
        )
        
        parameters = pika.ConnectionParameters(
            host=settings.RABBITMQ_HOST,
            port=5671,
            virtual_host='/bahariwatch',
            credentials=credentials,
            ssl_options=ssl_options,
            heartbeat=600,
            blocked_connection_timeout=300
        )
        
        self.connection = pika.BlockingConnection(parameters)
        self.channel = self.connection.channel()
        
        # Enable publisher confirms (synchronous acknowledgment)
        self.channel.confirm_delivery()
        
        # Declare topic exchange (idempotent)
        self.channel.exchange_declare(
            exchange='bahariwatch.events',
            exchange_type='topic',
            durable=True
        )
        
    def _get_ssl_context(self):
        """Load TLS certificates for mutual authentication"""
        import ssl
        context = ssl.create_default_context(cafile=settings.RABBITMQ_CA_CERT)
        context.load_cert_chain(
            certfile=settings.RABBITMQ_CLIENT_CERT,
            keyfile=settings.RABBITMQ_CLIENT_KEY
        )
        return context
    
    def publish(self, routing_key: str, payload: Dict[str, Any], schema_path: str):
        """
        Publish event with schema validation and publisher confirms.
        
        Args:
            routing_key: Topic routing key (e.g., "report.submitted.v1")
            payload: Event payload dictionary
            schema_path: Path to JSON Schema file for validation
            
        Raises:
            jsonschema.ValidationError: If payload violates schema
            pika.exceptions.UnroutableError: If message not routed to any queue
        """
        # Generate idempotency key
        event_id = str(uuid.uuid4())
        
        # Build full event envelope
        event = {
            "event_id": event_id,
            "event_type": routing_key,
            "timestamp": datetime.utcnow().isoformat() + "Z",
            "payload": payload
        }
        
        # Validate against JSON Schema
        schema = json.load(open(schema_path))
        jsonschema.validate(instance=event, schema=schema)
        
        # Publish with mandatory flag (ensures routing)
        try:
            self.channel.basic_publish(
                exchange='bahariwatch.events',
                routing_key=routing_key,
                body=json.dumps(event),
                properties=pika.BasicProperties(
                    delivery_mode=2,  # Persistent (survives broker restart)
                    content_type='application/json',
                    content_encoding='utf-8',
                    message_id=event_id,
                    timestamp=int(datetime.utcnow().timestamp())
                ),
                mandatory=True  # Return message if not routed
            )
            
            logger.info(f"Published event {event_id} to {routing_key}")
            
        except pika.exceptions.UnroutableError:
            logger.error(f"Event {event_id} not routed to any queue")
            raise
            
        except Exception as e:
            logger.error(f"Failed to publish event {event_id}: {e}")
            raise
    
    def close(self):
        """Close connection gracefully"""
        if self.connection and not self.connection.is_closed:
            self.connection.close()
```

### Phase 4: Consumer Implementation (Week 3-4)

```python
# matching_service/messaging/consumer.py
import json
import logging
import time
import redis
from typing import Callable
import pika
from django.conf import settings

logger = logging.getLogger(__name__)

class EventConsumer:
    """Idempotent event consumer with Redis deduplication"""
    
    def __init__(self, queue_name: str, routing_keys: list[str], callback: Callable):
        self.queue_name = queue_name
        self.routing_keys = routing_keys
        self.callback = callback
        self.connection = None
        self.channel = None
        self.redis_client = redis.Redis(
            host=settings.REDIS_HOST,
            port=6379,
            db=1,  # Dedicated DB for idempotency cache
            decode_responses=True
        )
        
    def start(self):
        """Start consuming messages with automatic reconnection"""
        while True:
            try:
                self._connect()
                self._consume()
            except KeyboardInterrupt:
                logger.info("Stopping consumer")
                break
            except Exception as e:
                logger.error(f"Consumer error: {e}, reconnecting in 5s...")
                time.sleep(5)
    
    def _connect(self):
        """Establish connection with TLS"""
        credentials = pika.PlainCredentials(
            settings.RABBITMQ_USER,
            settings.RABBITMQ_PASSWORD
        )
        
        ssl_options = pika.SSLOptions(
            context=self._get_ssl_context(),
            server_hostname=settings.RABBITMQ_HOST
        )
        
        parameters = pika.ConnectionParameters(
            host=settings.RABBITMQ_HOST,
            port=5671,
            virtual_host='/bahariwatch',
            credentials=credentials,
            ssl_options=ssl_options,
            heartbeat=600,
            blocked_connection_timeout=300
        )
        
        self.connection = pika.BlockingConnection(parameters)
        self.channel = self.connection.channel()
        
        # Declare durable queue
        self.channel.queue_declare(queue=self.queue_name, durable=True)
        
        # Bind queue to routing keys
        for routing_key in self.routing_keys:
            self.channel.queue_bind(
                exchange='bahariwatch.events',
                queue=self.queue_name,
                routing_key=routing_key
            )
        
        # Configure QoS (prefetch 1 for fair dispatch)
        self.channel.basic_qos(prefetch_count=1)
        
    def _get_ssl_context(self):
        """Load TLS certificates"""
        import ssl
        context = ssl.create_default_context(cafile=settings.RABBITMQ_CA_CERT)
        context.load_cert_chain(
            certfile=settings.RABBITMQ_CLIENT_CERT,
            keyfile=settings.RABBITMQ_CLIENT_KEY
        )
        return context
    
    def _consume(self):
        """Consume messages with manual acknowledgments"""
        logger.info(f"Consuming messages from {self.queue_name}")
        
        for method, properties, body in self.channel.consume(self.queue_name):
            try:
                # Parse event
                event = json.loads(body)
                event_id = event['event_id']
                
                # Check idempotency cache (Redis)
                if self.redis_client.exists(f"processed:{event_id}"):
                    logger.warning(f"Duplicate event {event_id}, skipping")
                    self.channel.basic_ack(method.delivery_tag)
                    continue
                
                # Process event (business logic)
                self.callback(event)
                
                # Mark as processed (TTL 7 days per ADR-014)
                self.redis_client.setex(
                    f"processed:{event_id}",
                    60 * 60 * 24 * 7,  # 7 days
                    "1"
                )
                
                # Acknowledge message
                self.channel.basic_ack(method.delivery_tag)
                logger.info(f"Processed event {event_id}")
                
            except json.JSONDecodeError:
                logger.error(f"Invalid JSON in message, rejecting")
                self.channel.basic_reject(method.delivery_tag, requeue=False)
                
            except Exception as e:
                logger.error(f"Error processing event: {e}")
                # Reject and requeue for retry (triggers dead letter exchange)
                self.channel.basic_reject(method.delivery_tag, requeue=True)
```

```python
#!/bin/bash

# Declare dead letter exchange
rabbitmqadmin declare exchange \
  name=dead_letter_exchange \
  type=fanout \
  durable=true \
  vhost=/bahariwatch

# Declare dead letter queue
rabbitmqadmin declare queue \
  name=dead_letter_queue \
  durable=true \
  vhost=/bahariwatch \
  arguments='{"x-message-ttl":604800000}'  # 7 days TTL

# Bind dead letter queue to exchange
rabbitmqadmin declare binding \
  source=dead_letter_exchange \
  destination=dead_letter_queue \
  vhost=/bahariwatch

# Configure retry queues (exponential backoff per ADR-014)
for delay in 60 300 900 3600; do
  rabbitmqadmin declare queue \
    name="retry_queue_${delay}s" \
    durable=true \
    vhost=/bahariwatch \
    arguments="{
      \"x-message-ttl\":${delay}000,
      \"x-dead-letter-exchange\":\"bahariwatch.events\"
    }"
done

# Update existing queues to use DLX
rabbitmqadmin declare queue \
  name=matching_service_queue \
  durable=true \
  vhost=/bahariwatch \
  arguments='{
    "x-dead-letter-exchange":"dead_letter_exchange",
    "x-max-retries":4
```

```python
from django.core.management.base import BaseCommand
from matching_service.messaging.consumer import EventConsumer
import json

class Command(BaseCommand):
    help = 'Manually process dead letter queue messages'
    
    def handle(self, *args, **options):
        """Process DLQ messages one by one with admin approval"""
        # Connect to DLQ
        consumer = EventConsumer(
            queue_name='dead_letter_queue',
            routing_keys=[],  # DLQ bound to DLX, not topics
            callback=self.process_dlq_message
        )
        
        # Consume with manual acknowledgment
        consumer.start()
    
    def process_dlq_message(self, event: dict):
        """Prompt admin to retry or discard message"""
        print(f"\n--- Dead Letter Message ---")
        print(json.dumps(event, indent=2))
        
        action = input("Action (retry/discard/skip)? ").strip().lower()
        
        if action == 'retry':
            # Re-publish to original routing key
            from matching_service.messaging.producer import EventPublisher
            publisher = EventPublisher()
            publisher.publish(
                routing_key=event['event_type'],
                payload=event['payload'],
                schema_path=f"schemas/events/{event['event_type'].replace('.', '_')}.json"
            )
            publisher.close()
            print("✓ Message re-published")
            
        elif action == 'discard':
            print("✗ Message discarded")
            
        else:
            print("⊘ Skipped")
            raise Exception("Skip message (will remain in DLQ)")
```
