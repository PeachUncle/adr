## Context

The trading system requires a number of sensitive credentials ("secrets") to operate, including:
-   API keys for third-party data providers (Alpha Vantage, Finnhub).
-   Database credentials for Cloud SQL.
-   Service account keys for authenticating with GCP services.

Multiple ADRs (ADR-013, ADR-014, ADR-018) state that these secrets must be stored "securely." Storing them in plain text in configuration files, source code, or as simple environment variables is not a secure or manageable practice. We need a dedicated, secure, and auditable solution for managing the lifecycle of these secrets.

## Decision

We will use **Google Secret Manager** as the central, authoritative store for all application secrets. Agents and services running on Google Cloud Run will be granted fine-grained IAM permissions to access specific secrets at runtime.

## Rationale

1.  **Centralized and Secure Storage**: Secret Manager provides a single, secure place to store and manage all secrets. Secrets are encrypted at rest, and access is controlled by Google's robust IAM framework, providing a much higher level of security than environment variables or encrypted files.
2.  **Fine-Grained Access Control**: We can grant an agent's service account permission to access *only* the specific secrets it needs (principle of least privilege). For example, the `MarketAnalysisAgent` can be granted access to the Alpha Vantage API key, but not the database credentials.
3.  **Auditability**: All access to secrets is automatically logged in Google Cloud Audit Logs. This provides a clear and immutable audit trail, which is critical for security and compliance in a financial application.
4.  **Native GCP Integration**: Secret Manager integrates seamlessly with our chosen deployment platform, Google Cloud Run (ADR-016). Our application code can use the Google Cloud client libraries to fetch secrets at startup, without needing to manage credential files.
5.  **Cost-Effective**: The service has a generous free tier and very low costs for storage and access, making it a highly cost-effective solution.

## Consequences

-   **Implementation**:
    -   Application startup logic will be modified. Instead of reading secrets from environment variables, agents will fetch them from Secret Manager using the `google-cloud-secret-manager` Python library.
    -   Access to secrets will be granted to our Cloud Run services by assigning the "Secret Manager Secret Accessor" IAM role to their service accounts.
-   **Infrastructure as Code**: All secrets will be provisioned and their IAM policies managed via Terraform (ADR-019). The secret *values* themselves will not be stored in the Terraform state; they will be passed in securely during the deployment process.
-   **CI/CD**: The GitHub Actions pipeline (ADR-018) will require permission to manage secrets in Secret Manager during deployment.

## Alternatives Considered

-   **Environment Variables in Cloud Run**: This is simpler to implement but less secure. Secrets are visible in the Cloud Run service definition and are not as easily rotated or audited as they are in Secret Manager.
-   **HashiCorp Vault**: Vault is an extremely powerful, open-source secrets management tool. However, it requires self-hosting and management, which introduces significant operational overhead and cost. For our needs, the fully managed, native GCP solution is far more cost-effective and simpler to operate.
-   **Encrypted Files in Google Cloud Storage**: This would involve encrypting a file with credentials and storing it in a GCS bucket. While more secure than plain text, it lacks the fine-grained access control, versioning, and audit logging features of a dedicated secrets management service like Secret Manager.

## Implementation Strategy

### Phase 1: Secret Manager Setup (Week 1)
**Deliverables**:
- Enable Secret Manager API in GCP project
- Define secret naming convention (format: `{env}-{service}-{credential-type}`, e.g., `prod-market-analysis-api-key`)
- Create initial secrets via Terraform (without values, just placeholders)
- Configure secret versioning and rotation policies
- Set up IAM roles and service accounts for secret access

**Dependencies**: GCP project with billing enabled, Terraform configuration (ADR-019)

### Phase 2: IAM and Access Control (Week 1-2)
**Deliverables**:
- Create service account for each agent with least-privilege access
- Assign "Secret Manager Secret Accessor" role to service accounts for specific secrets only
- Document access control matrix (which agent accesses which secrets)
- Configure audit logging for all secret access operations
- Implement secret access testing for each service account

**Dependencies**: Phase 1 completion, Cloud Run services defined

### Phase 3: Application Integration (Week 2-3)
**Deliverables**:
- Integrate `google-cloud-secret-manager` Python library into agent codebase
- Implement secret loading function at application startup
- Add error handling and retry logic for secret access failures
- Implement secret caching with TTL to reduce API calls
- Update agent documentation with secret access patterns

**Dependencies**: Phase 2 completion, agent codebase structure

### Phase 4: CI/CD Integration (Week 3)
**Deliverables**:
- Configure GitHub Actions workflow to populate secret values during deployment
- Use GitHub Actions secrets as source for Secret Manager values
- Implement secret rotation workflow in CI/CD pipeline
- Add automated testing for secret access in deployment pipeline
- Document secret management procedures for developers

**Dependencies**: Phase 3 completion, ADR-018 (GitHub Actions CI/CD)

## Cost Analysis

### Monthly Operational Costs

| Component | Usage Pattern | Cost |
|-----------|---------------|------|
| Secret Storage (20 secrets) | Active secrets | $1.20/month ($0.06 per secret) |
| Secret Access Operations (100K/month) | Application startup and periodic refresh | $0.30/month ($0.03 per 10K operations) |
| Secret Versions (60 versions) | 3 versions per secret on average | Included in storage cost |
| Audit Logging (Cloud Logging) | Access audit trail | $0.10/month (minimal log volume) |
| **Total Monthly Cost** | | **$1.60/month** |

**Free Tier Coverage**:
- First 6 active secrets: Free
- First 10,000 access operations: Free
- Estimated actual cost: $0.50-1.00/month after free tier

### Cost Optimization Strategies

1. **Secret Caching**: Cache secrets in memory for 1-hour TTL. Reduces access operations from 1M/month to 100K/month (90% reduction).

2. **Minimize Secret Versions**: Maintain only 3 most recent versions per secret. Deletes old versions automatically via Terraform lifecycle policy.

3. **Batch Secret Loading**: Load all required secrets in single startup sequence instead of on-demand loading. Reduces API calls and improves startup performance.

4. **Consolidate Secrets**: Where appropriate, use single secret with JSON structure instead of multiple separate secrets (e.g., database config as single JSON secret).

5. **Audit Log Sampling**: Sample audit logs at 10% for non-critical secrets to reduce logging costs while maintaining security visibility.

### ROI Comparison vs Alternatives

| Approach | Setup Cost | Monthly Cost | Security | Auditability | Operational Overhead |
|----------|------------|--------------|----------|--------------|----------------------|
| Secret Manager | Low | $0.50-1.60 | Very High | Excellent | Very Low |
| Environment Variables | Very Low | $0 | Low | None | Low |
| HashiCorp Vault | Very High | $30-60 (self-hosted) | Very High | Excellent | High |
| Encrypted GCS Files | Medium | $0.10 | Medium | Poor | Medium |

**Verdict**: Secret Manager provides best security-to-cost ratio with minimal operational overhead.

## Risk Assessment

| Risk | Severity | Likelihood | Impact | Mitigation |
|------|----------|------------|--------|------------|
| Secret access failure at startup | High | Low | Agent fails to start, service outage | Implement retry logic with exponential backoff, maintain fallback to cached secrets, alerting on secret access failures |
| Overly permissive IAM roles | High | Medium | Agent accesses secrets it shouldn't, lateral movement in security breach | Implement least-privilege principle, regular IAM audit, automated policy validation in CI/CD |
| Secret rotation breaks application | Medium | Medium | Application uses old secret, authentication failures | Implement secret versioning, blue-green deployment during rotation, automated testing post-rotation |
| Secret Manager quota exceeded | Low | Very Low | Unable to create new secrets or access existing ones | Monitor quota usage, set alerts at 80% capacity, request quota increase proactively |
| Secrets leaked in logs or errors | High | Medium | Credential exposure in Cloud Logging | Implement log scrubbing, structured error messages that don't include secret values, regular log audits |
| Missing audit trail | Medium | Low | Security incident without visibility into secret access | Enable Cloud Audit Logs for Secret Manager, retain audit logs for 90 days minimum, regular audit log reviews |
| Secret Manager service outage | Medium | Very Low | Unable to start new agents or refresh secrets | Cache secrets with extended TTL during outage, implement circuit breaker pattern, maintain backup access method |

## Monitoring and Success Criteria

### Key Metrics

| Metric | Target | Measurement Method |
|--------|--------|-------------------|
| Secret Access Success Rate | >99.9% | Secret Manager API success rate |
| Secret Access Latency (p95) | <200ms | Secret Manager API latency monitoring |
| Secret Rotation Success Rate | 100% | Automated rotation workflow success |
| Unauthorized Access Attempts | 0 | Cloud Audit Logs for denied secret access |
| Secrets with Latest Version | 100% | Automated validation of secret freshness |

### Alerting Thresholds

**Critical**:
- Secret access failure for any production agent
- Unauthorized access attempt detected (IAM permission denied)
- Secret rotation failed for production secret
- Secret Manager quota at 90% capacity

**Warning**:
- Secret access latency >500ms for 5 minutes
- Secret not rotated in 90 days (approaching stale threshold)
- More than 3 versions exist for single secret (cleanup needed)
- Secret access from unexpected service account

**Info**:
- Secret successfully rotated
- New secret created
- Secret version deprecated
- IAM policy updated for secret

### Success Criteria

**Functional Requirements**:
- All sensitive credentials stored in Secret Manager (zero hardcoded secrets)
- Each agent service account has access only to required secrets
- All secret access operations logged in Cloud Audit Logs
- Secrets accessible via Python client library at application startup
- Secret rotation workflow defined and tested

**Performance Requirements**:
- Secret access completes within 200ms (p95)
- Application startup time increases <500ms due to secret loading
- Secret caching reduces access operations by >80%

**Cost Requirements**:
- Total secret management costs remain below $5/month
- Secret storage costs <$2/month
- Access operation costs <$1/month

**Operational Requirements**:
- All secrets defined and provisioned via Terraform (infrastructure as code)
- Secret rotation procedures documented for each secret type
- IAM access matrix documented and reviewed quarterly
- Developer onboarding includes secret management training

### Risk Factors

1. **Learning Curve**: Very low complexity - Secret Manager API is intuitive and well-documented. Python client library has simple interface. Risk: Minimal.

2. **IAM Misconfiguration**: Low complexity - Least-privilege access requires careful planning but IAM simulator helps validate policies. Risk: Overly permissive roles granted. Mitigation: Automated IAM policy validation, regular audits.

3. **Secret Rotation Coordination**: Low complexity - Requires versioning strategy and deployment coordination. Risk: Application breaks during rotation. Mitigation: Blue-green deployment, secret version overlap period.

4. **Dependency on GCP Service**: Very low complexity - Secret Manager is highly available managed service. Risk: Service outage prevents secret access. Mitigation: Secret caching with extended TTL, acceptable for rare outage scenarios.

5. **Cost Predictability**: Very low complexity - Costs are directly proportional to secret count and access operations, both easily predictable. Risk: Minimal, costs are very low even with generous estimates.
