# ADR 0002: Slots Pattern Adoption

**Date:** 2025-10-11  
**Status:** ✅ Accepted  
**Deciders:** Architecture Team  
**Related:** ADR 0001 (Component Classification)

---

## Context

After classifying 60 components into 4 tiers, we identified that **24 components (40%)** are Tier 3 (Complex) - components with multiple sub-elements that users frequently need to customize.

**Problem:**
Traditional `className` prop is insufficient for complex components:

```typescript
// ❌ Problem: Can't customize individual parts
<Dialog className="my-dialog">
  {/* How do I style the overlay? Header? Footer separately? */}
</Dialog>

// ❌ Workaround: CSS selectors (fragile)
.my-dialog > [data-overlay] { /* Breaks if structure changes */ }
```

**Components affected (24 total):**
- **Overlays:** Dialog, Modal, Drawer, Popover, DropdownMenu, ContextMenu, Toast
- **Forms:** Select, Combobox
- **Data:** Table
- **Navigation:** Tabs, Accordion, NavMenu, Pagination
- **Others:** Stepper, Menu, Breadcrumbs, Progress, Slider

**Research conducted:**
- HeroUI slots system (26.9k stars, production-proven)
- Material-UI's `sx` prop approach
- Vue's named slots concept
- Chakra UI's style props

---

## Decision

We adopt the **Slots Pattern** for Tier 3+ components.

### What is Slots Pattern?

Components expose **named style slots** for each customizable sub-element via `classNames` prop:

```typescript
<Dialog 
  classNames={{
    overlay: 'bg-blue-500/30',
    content: 'max-w-2xl shadow-2xl',
    header: 'bg-gradient-to-r from-blue-500',
    body: 'p-6',
    footer: 'justify-between',
    close: 'text-red-500',
  }}
>
  <DialogHeader>Title</DialogHeader>
  <DialogBody>Content</DialogBody>
  <DialogFooter>Actions</DialogFooter>
</Dialog>
```

### Type System

```typescript
// Shared utility type
export type ComponentSlots<T extends string> = Partial<Record<T, string>>;

export interface SlotsProps<T extends string> {
  classNames?: ComponentSlots<T>;
}

// Component-specific
export type DialogSlots = 
  | 'overlay'
  | 'content'
  | 'header'
  | 'title'
  | 'description'
  | 'body'
  | 'footer'
  | 'close';

export interface DialogProps extends SlotsProps<DialogSlots> {
  open?: boolean;
  onOpenChange?: (open: boolean) => void;
}
```

### Implementation Pattern

```typescript
const defaultStyles = {
  overlay: 'fixed inset-0 bg-black/50 z-50',
  content: 'fixed left-1/2 top-1/2 -translate-x-1/2 -translate-y-1/2 bg-white rounded-lg',
  header: 'px-6 py-4 border-b',
  body: 'px-6 py-4',
  footer: 'px-6 py-4 border-t',
};

export function Dialog({ classNames, children, ...props }: DialogProps) {
  return (
    <Root {...props}>
      <Overlay className={cn(defaultStyles.overlay, classNames?.overlay)} />
      <Content className={cn(defaultStyles.content, classNames?.content)}>
        {children}
      </Content>
    </Root>
  );
}
```

### Naming Conventions

Standardized slot names across all components:

| Slot | Usage | Components |
|------|-------|------------|
| **base** | Root element | All components |
| **trigger** | Interactive trigger | Dropdown, Tooltip, Dialog |
| **overlay** | Background overlay | Dialog, Modal, Drawer |
| **content** | Main content container | All overlays, Dropdown |
| **header** | Header section | Dialog, Card, Modal, Table |
| **title** | Title text | Dialog, Accordion, Card |
| **body** | Main content | Dialog, Card, Modal |
| **footer** | Footer section | Dialog, Card, Modal, Table |
| **item** | List item | Dropdown, Select, List |
| **close** | Close button | Dialog, Toast, Modal |

## Rationale

### Why Slots Pattern?

**Alternatives considered:**

#### 1. Single className Only
```typescript
<Dialog className="my-custom-dialog">
```
❌ **Rejected:**
- Can't customize individual parts
- Requires complex CSS selectors
- Breaks when structure changes
- Not discoverable (which parts can be styled?)

#### 2. Multiple className Props
```typescript
<Dialog 
  overlayClassName="..."
  contentClassName="..."
  headerClassName="..."
/>
```
⚠️ **Rejected:**
- Pollutes props interface (20+ props for complex components)
- Not scalable
- Not grouped logically
- Type inference issues

#### 3. Style Props (Chakra approach)
```typescript
<Dialog 
  overlayProps={{ bg: 'blue.500' }}
  contentProps={{ maxW: '2xl' }}
/>
```
❌ **Rejected:**
- Requires runtime CSS-in-JS
- Performance cost
- Not compatible with Tailwind v4
- Goes against our CSS-first principle

#### 4. Slots Pattern ✅ **Selected**
```typescript
<Dialog classNames={{ overlay: '...', content: '...' }}>
```
✅ **Advantages:**
- Granular customization
- Type-safe (autocomplete for slot names)
- Grouped logically
- Zero runtime cost
- Compatible with Tailwind
- Discoverable (TypeScript shows available slots)
- Flexible (only override what you need)

### Why 40% of Components?

**Distribution:**
- Tier 1-2 (Simple/Standard): 36 components (60%) - **className only**
- Tier 3-4 (Complex/Compound): 24 components (40%) - **Slots required**

**Reasoning:**
- Most components (60%) are simple enough for single className
- Only complex components (40%) benefit from slots
- Avoids over-engineering simple components
- Provides power when needed

## Consequences

### Positive

✅ **Granular Control**
- Users can customize any sub-element
- No need for complex CSS selectors
- Direct, explicit styling

✅ **Type Safety**
- TypeScript autocompletes slot names
- Compile-time errors for invalid slots
- Self-documenting API

✅ **Discoverability**
- Developers can see available slots via TypeScript
- Clear which parts can be customized
- IntelliSense shows options

✅ **Flexibility**
- Override only what you need
- Default styles always apply
- Can combine with component variants

✅ **Maintainability**
- Centralized default styles
- Easy to update defaults
- User customizations isolated

✅ **Performance**
- Zero runtime cost (compile-time only)
- No JavaScript execution
- Pure CSS classes

✅ **Consistent DX**
- Same pattern across all complex components
- Easy to learn once, apply everywhere
- Predictable API

### Negative / Trade-offs

⚠️ **Verbosity**
- More typing for customization
- Nested object syntax
- Mitigation: Only use when needed, TypeScript autocomplete helps

⚠️ **Learning Curve**
- Developers must learn slot concept
- Must know which slots are available
- Mitigation: Comprehensive docs, TypeScript hints, examples

⚠️ **Type Maintenance**
- Must define slots for each complex component
- Must keep slot names consistent
- Mitigation: Naming conventions, linting rules, code generation

### Risks

🟡 **Risk: Inconsistent Naming**
- Impact: Confusing API, hard to remember
- Mitigation: **Naming conventions** (overlay, content, header, body, footer)
- Validation: Code review, automated checks

🟡 **Risk: Over-use**
- Impact: Simple components unnecessarily complex
- Mitigation: **Only for Tier 3+**, guideline in CODE_STANDARD
- Validation: Architecture review

🟢 **Risk: Breaking Changes**
- Impact: Changing slot names breaks user code
- Mitigation: Document in ADR, versioning, migration guide
- Probability: Low (careful planning, user feedback)


```typescript
<Dialog 
  classNames={{

    content: 'max-w-4xl rounded-2xl shadow-2xl border-2 border-primary',
    header: 'bg-gradient-to-r from-blue-600 to-purple-600 text-white',
    title: 'text-2xl font-bold',
    body: 'p-8 text-lg',
    footer: 'bg-gray-50 justify-between',
    close: 'text-white hover:text-gray-200',
  }}
>
  <DialogHeader>
    <DialogTitle>Custom Dialog</DialogTitle>
  </DialogHeader>
  <DialogBody>
    Fully customized with slots!
  </DialogBody>
  <DialogFooter>
    <Button>Close</Button>
  </DialogFooter>
</Dialog>
```
