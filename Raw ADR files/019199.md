# ADR-002: Database-First Approach

## Status

Accepted

## Context

Entity Framework Core offers two primary approaches for managing database schema:

1. **Code-First**: Define entities in C#, generate migrations automatically, EF manages schema
2. **Database-First**: Write SQL migrations manually, use EF only for object mapping

For Trama, several factors influenced this decision:

1. **Schema Control**: Want full control over table structure, indexes, constraints, and performance optimizations
1. **Migration Conflicts**: With multiple modules, EF migrations can conflict and become difficult to manage
1. **Database Expertise**: Building SQL skills is valuable and transferable
1. **Transparency**: SQL migrations are explicit and reviewable, EF migrations can be opaque

The key tension is between the convenience of EF migrations versus the control of SQL.

## Decision

We will use a **Database-First approach** with the following characteristics:

1. **SQL Migrations**: All schema changes written as SQL scripts in `infrastructure/migrations/`
2. **Sequential Numbering**: Migrations numbered sequentially (001, 002, 003...) with descriptive names
3. **EF Core for Mapping Only**: Use EF Core configurations to map entities to existing schema
4. **Custom Migration Runner**: Built custom runner that executes SQL files and tracks history
5. **No EF Migrations**: Explicitly disable EF migrations via `NoMigrationsAssembly`
6. **Idempotent Scripts**: Use `IF NOT EXISTS` and similar patterns for safety
7. **Manual Application**: Migrations run automatically on startup


## Consequences

### Positive

- **Full PostgreSQL Control**: Can use any PostgreSQL feature including PostGIS, custom types, advanced indexes
- **Better Learning**: Forces understanding of SQL, database design, and performance optimization
- **Explicit Migrations**: SQL scripts are clear, reviewable, and version-controlled
- **No Migration Conflicts**: Multiple modules can have migrations without EF conflicts
- **Performance Optimization**: Can write optimized SQL, create specific indexes, use database features
- **Easier Debugging**: Can see exactly what SQL is executed, no hidden EF magic
- **Database Portability**: SQL scripts can be run independently of application
- **Better for PostGIS**: Geospatial features are first-class, not abstracted

### Negative

- **More Manual Work**: Must write SQL by hand, no automatic generation
- **Requires SQL Knowledge**: Team must be comfortable with SQL and PostgreSQL
- **Entity Sync Burden**: Must manually keep entities in sync with schema
- **No Automatic Rollback**: Must write down migrations manually
- **Testing Complexity**: Harder to use in-memory databases for testing
- **Tooling Gap**: Lose EF migration tooling (Add-Migration, Update-Database commands)
- **Documentation Burden**: Must document schema changes clearly in SQL

### Neutral

- **Migration History**: Custom tracking table (`__MigrationHistory`) instead of EF's `__EFMigrationsHistory`
- **Development Workflow**: Different workflow than standard EF, requires adjustment
- **Code Generation**: Could add tooling to generate entities from schema if needed

## Notes

This decision aligns with the "database-first" philosophy common in enterprise applications and aligns well with PostgreSQL's strengths. The approach is documented in detail in `docs/DATABASE-FIRST-APPROACH.md`.

Key practices to maintain:
- Always test migrations locally before applying to production
- Keep migrations small and focused
- Document complex changes with comments
- Use constraints and indexes for data integrity and performance
- Never modify applied migrations, always create new ones

This decision could be reconsidered if:
- Team lacks SQL expertise
- Need to support multiple database providers
- Schema becomes extremely complex and manual sync is error-prone
- EF Core adds better PostGIS support
