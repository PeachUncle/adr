# ADR 0004: Container Registry Strategy

**Status:** Accepted  
**Date:** 2025-09-10  
**Scope:** Container Management

## Context

We need to decide on container registry architecture for multiple environments (dev, staging, production). Options include environment-specific registries versus a shared registry with promotion workflows.

## Decision

We will implement a **Single Shared Azure Container Registry** with **environment-based tag promotion** rather than environment-specific registries.

### Registry Pattern

```text
Registry: sharedlearnacr.azurecr.io
├── api-service-1/
│   ├── v1.0.0-abc123      # Immutable build artifact
│   ├── dev-ready          # Environment promotion tag
│   ├── staging-ready      # Manual approval gate  
│   └── prod-ready         # Production readiness
├── api-service-2/
└── web-app/
```

### Promotion Workflow

1. **Build**: Create immutable artifact tagged with `v{version}-{commit-sha}`
2. **Dev Promotion**: Automatic promotion to `dev-ready` on main branch
3. **Staging Promotion**: Manual promotion to `staging-ready` with approval
4. **Production Promotion**: Manual promotion to `prod-ready` with validation

## Alternatives Considered

### Option 1: Environment-Specific Registries

- `dev-acr.azurecr.io`, `staging-acr.azurecr.io`, `prod-acr.azurecr.io`
- **Rejected**: 3x cost ($15/month vs $5), potential version drift, complex promotion

### Option 2: Multi-Registry with Replication

- Use ACR geo-replication and premium tier
- **Rejected**: Significantly higher cost (~$25/month), over-engineered for learning environment

### Option 3: External Registry (Docker Hub, GitHub Container Registry)

- **Rejected**: No Azure AD integration, additional auth complexity, security concerns

## Consequences

### Positive

- **Cost Optimization**: Single Basic ACR (~$5/month vs 3×$5)
- **Immutable Deployments**: Same binary artifact across all environments
- **Clear Audit Trail**: Production images traceable to exact commit
- **Simplified RBAC**: Centralized access control and permissions
- **Enterprise Compliance**: Proper promotion gates and approval workflows
- **Storage Efficiency**: No duplicate images across environments

### Negative

- **Single Point of Failure**: Registry downtime affects all environments
- **Tag Management Complexity**: Need to manage promotion tags carefully
- **Permission Complexity**: Same registry accessed by multiple environment teams
- **Promotion Dependencies**: All environments must use same registry

## Implementation

### 1. Registry Configuration

```hcl
resource "azurerm_container_registry" "shared" {
  name                = var.acr_name
  resource_group_name = azurerm_resource_group.shared.name
  location            = azurerm_resource_group.shared.location
  sku                 = "Basic"
  admin_enabled       = false  # Use managed identity
}
```

### 2. RBAC Pattern

- **Shared ACR**: Deployed in shared environment state
- **Environment AKS**: References ACR via remote state
- **Role Assignment**: AcrPull role assigned from environment to ACR

### 3. GitHub Actions Integration

```yaml
# Build immutable artifact
- name: Build
  run: docker build -t $ACR.azurecr.io/$SERVICE:v1.0.0-$COMMIT_SHA

# Promote to environment
- name: Promote to Dev
  run: |
    docker tag $ACR.azurecr.io/$SERVICE:v1.0.0-$COMMIT_SHA \
               $ACR.azurecr.io/$SERVICE:dev-ready
```

## Security Considerations

### Access Control

- AKS clusters have AcrPull permissions only
- GitHub Actions has AcrPush permissions for CI/CD
- No admin access enabled (managed identities only)

### Image Security

- Container vulnerability scanning in CI/CD
- Base image updates through automated PRs
- Signed images for production environments (future)
