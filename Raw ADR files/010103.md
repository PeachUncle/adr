# ADR-002: Service Communication Patterns

## Status
Accepted

## Context
The cryptocurrency trading bot architecture requires multiple services to communicate effectively while remaining decoupled. We need to determine the most appropriate communication patterns for different types of interactions between services.

## Options Considered

### 1. Request-Response (REST/HTTP or gRPC)
- **Pros**: Simple to understand, direct feedback, strong typing with gRPC
- **Cons**: Tight coupling, potential cascading failures, higher latency

### 2. Event-Driven (Pub/Sub)
- **Pros**: Loose coupling, resilience to service outages, scales well
- **Cons**: More complex to debug, eventual consistency challenges

### 3. Hybrid Approach
- **Pros**: Uses the best pattern for each interaction type
- **Cons**: Increased complexity in architecture understanding

## Decision
We've selected a hybrid communication approach:

1. **Event-Driven (NATS Pub/Sub)** for:
   - Market data streaming from Data Collection to ML Analysis
   - Trading signals from ML Analysis to Trade Execution
   - System events for logging and auditing
   - Asynchronous notifications across services

2. **Request-Response (REST/HTTP)** for:
   - Configuration updates that require immediate feedback
   - User-initiated commands through the API Gateway
   - Authentication and authorization checks

3. **Binary Protocol (gRPC)** for:
   - ML model checkpoint storage and retrieval
   - Performance-critical internal service communications

## Implementation Details
1. For event-driven communication, we'll use NATS subjects with a consistent naming structure:
   - `market.data.<pair>` for market data
   - `ml.prediction.<pair>` for trading signals
   - `trade.executed.<pair>` for executed trades
   - `system.log.<service>.<level>` for logging

2. For request-response, the API Gateway will handle routing and authentication.

3. Services will be designed to be resilient to communication failures with circuit breaking and retries where appropriate.

## Consequences
- **Positive**: Services can evolve independently
- **Positive**: System remains responsive even if some services are down
- **Positive**: High-performance communication where needed
- **Negative**: Debugging across services requires tracing infrastructure
- **Negative**: Developers need to understand multiple communication patterns
