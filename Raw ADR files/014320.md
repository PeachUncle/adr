# TASK-004: SQLite schema & migrations
> Source: tasks/tasks.md

## Context
- Goal: Create SQLite schema with tables for historical_prices, market_cache, user_logs, portfolio_positions, portfolio_tx, and provide migration scripts.
- Dependencies: TASK-001 (monorepo structure)
- Acceptance: `python db/init.py` creates DB; schema diagram in `/docs`.
- Constraints: Consider `sqlite3` + `alembic` (optional) for migrations.

## Options Considered
- Option A: Simple SQLite schema with basic CREATE TABLE statements
  - Pros: Quick implementation; meets basic requirements
  - Cons: Limited flexibility; no migration support
- Option B: Comprehensive schema with Alembic migrations
  - Pros: Professional migration system; version control for schema changes
  - Cons: Over-engineering for current scope; additional complexity
- Option C: Balanced approach with SQLite schema + simple migration script
  - Pros: Meets requirements; provides foundation for future Alembic adoption; aligns with technical.md architecture
  - Cons: Manual migration process initially

## Decision
- Choose Option C. Implement a comprehensive SQLite schema with proper relationships and indexes, plus a simple migration script. This provides a solid foundation that can be enhanced with Alembic later when needed.

## Impacts
- Performance: Proper indexes for query performance
- Complexity: Moderate - well-structured schema with relationships
- Security/Privacy: Data integrity through constraints and foreign keys
- Compatibility: Standard SQLite patterns; easy to extend
- Risks & Mitigations:
  - Risk: Schema changes require manual migration
  - Mitigation: Document schema changes; plan Alembic adoption for future
