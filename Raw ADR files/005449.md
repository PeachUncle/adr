## Context

The system's functional requirements (`docs/reqs/multi_agent_ai_requirements.md`) mandate that the `StockSelectionAgent` must perform a "veto check" on trade candidates by analyzing recent news and sentiment. This is a critical risk management step to avoid entering trades in companies facing adverse events.

The system needs a defined, modular, and efficient way to perform this analysis. Placing this logic directly within the `StockSelectionAgent` would violate the principle of separation of concerns, making the agent overly complex and preventing the reuse of sentiment analysis by other potential agents (e.g., the `PortfolioHedgingAgent`).

## Decision

We will delegate the entire sentiment analysis workflow to the **`MarketAnalysisAgent`**. This agent will act as a centralized service for all sentiment-related queries.

The workflow will be as follows:
1.  The `StockSelectionAgent` (or any other authorized agent) sends a request to the `MarketAnalysisAgent` for the sentiment of a specific stock ticker.
2.  The `MarketAnalysisAgent` receives the request and first checks its internal cache (in Redis) for a recent, valid sentiment score for that ticker.
3.  If a valid cached result exists, it is returned immediately.
4.  If there is no valid cached result, the `MarketAnalysisAgent` uses its configured external tools (e.g., the Alpha Vantage `NEWS_SENTIMENT` API) to fetch news articles and their corresponding sentiment scores.
5.  The agent processes these results into a standardized format (e.g., `Positive`, `Negative`, `Neutral` with a confidence score).
6.  The result is stored in the Redis cache with a defined Time-To-Live (TTL) to serve subsequent requests.
7.  The standardized result is returned to the requesting agent.

## Rationale

This decision aligns with our established hierarchical agent architecture for several key reasons:

1.  **Separation of Concerns**: It reinforces the designated roles of the agents. The `StockSelectionAgent` is responsible for the *what* and *when* of the selection process, while the `MarketAnalysisAgent` is the specialist for performing the *how* of complex market-related analysis.
2.  **Centralization and Caching**: By centralizing this function, we create a single point of logic for sentiment analysis. More importantly, this allows for effective caching. If multiple agents or processes require sentiment for the same stock in a short period, the analysis is only performed once, which significantly improves performance and reduces external API costs.
3.  **Abstraction**: The `StockSelectionAgent` does not need to know the specific implementation details of how sentiment is derived (e.g., whether it's from Alpha Vantage, NewsAPI + Google NLP, or another source). It simply requests a standardized sentiment object. This makes the system more modular and easier to maintain; the sentiment provider can be changed or upgraded within the `MarketAnalysisAgent` without affecting any other part of the system.
4.  **Consistency**: This pattern is consistent with how other complex analytics, such as correlation matrices, are handled by the `MarketAnalysisAgent`.

## Implementation Strategy

### Phase 1: MarketAnalysisAgent Enhancement (Weeks 1-2)
- Add `get_sentiment_for_ticker(symbol: str) -> SentimentResult` method to MarketAnalysisAgent
- Create Pydantic model for `SentimentResult` (sentiment: str, confidence: float, sources: list, timestamp: datetime)
- Implement Alpha Vantage NEWS_SENTIMENT API integration
- Create secure API key management using Google Secret Manager (per ADR-020)

### Phase 2: Caching Layer Implementation (Week 3)
- Design Redis cache schema for sentiment data (key: `sentiment:{ticker}`, TTL: 6 hours)
- Implement cache-first lookup logic in `get_sentiment_for_ticker`
- Add cache warming for watchlist tickers (pre-fetch during market hours)
- Create cache invalidation strategy for breaking news events

### Phase 3: StockSelectionAgent Integration (Week 4)
- Update `StockSelectionAgent` Deep Analysis phase to call sentiment method
- Implement veto logic: reject candidates with "Negative" sentiment + confidence >0.7
- Add sentiment score to candidate scoring model (weight: 10-15%)
- Create sentiment override mechanism for manual trade approval

### Phase 4: Testing and Monitoring (Week 5)
- Unit tests for sentiment parsing and cache logic
- Integration tests with Alpha Vantage API (sandbox environment)
- Performance testing: cache hit rate, API latency, veto accuracy
- Production deployment with alerting and monitoring

**Dependencies**:
- ADR-011 (Alpha Vantage): NEWS_SENTIMENT API integration
- ADR-001 (Memory): Redis caching infrastructure
- ADR-020 (GSM): Secure API key storage

## Cost Analysis

### API Costs
- **Alpha Vantage Tier**: Premium plan required for NEWS_SENTIMENT API
  - Cost: $50/month (125 API requests/day limit)
  - Usage: ~3-5 requests/day per trading day (20 requests/month typical)
  - Headroom: 100+ requests/day available for growth

### Infrastructure Costs
- **Redis Caching**: $5/month (Cloud Memorystore minimal instance)
  - Storage: <10MB for sentiment cache (negligible)
  - TTL: 6 hours (automatic expiration)
- **Secret Manager**: $0.06/month (1 secret: Alpha Vantage API key)

### Cost Savings (Caching ROI)
- **Without caching**: If multiple agents/processes request same ticker sentiment:
  - Scenario: 3 agents checking same 10 tickers = 30 API calls/day
  - Cost: $400/month (far exceeds tier limit, requires $200/month enterprise tier)
- **With 90% cache hit rate**: 3 API calls/day for new tickers
  - Cost: $50/month (stays within premium tier)
- **Monthly savings**: $350

### Total Monthly Cost
- Alpha Vantage API: $50
- Redis caching: $5
- Secret Manager: $0.06
- **Total**: $55/month

### ROI Analysis
- **Implementation cost**: $15,000 (one-time, 5 weeks development)
- **Monthly operational cost**: $55
- **Risk reduction value**: Non-negotiable risk management requirement
  - Prevents entry into positions facing negative catalysts
  - Expected to prevent 1-2 losing trades/month ($500-1000 saved)
- **Break-even**: 15-30 months (direct cost), but risk management value makes this required regardless

## Risk Assessment

| Risk | Severity | Likelihood | Impact | Mitigation |
|------|----------|------------|--------|------------|
| Alpha Vantage API outage | High | Low | No sentiment veto, potential bad trades | Cache extends to 24 hours during outage, fallback to manual review |
| API rate limit exceeded | Medium | Medium | Delayed sentiment checks | Cache warming, monitor usage, upgrade tier if needed |
| Inaccurate sentiment scoring | High | Medium | False vetoes or missed warnings | Confidence threshold tuning, human review for borderline cases |
| Cache staleness during breaking news | Critical | Low | Enter trade before negative catalyst | 6-hour TTL balances freshness vs cost, breaking news alerts trigger cache invalidation |
| API key compromise | Critical | Low | Unauthorized API usage, cost spike | GSM encryption, key rotation every 90 days, usage monitoring |
| Over-reliance on sentiment veto | Medium | Medium | Miss valid opportunities | Sentiment is one input (10-15% weight), not sole decision factor |
| Vendor lock-in to Alpha Vantage | Medium | Low | Migration cost if provider fails | Abstract sentiment interface, maintain provider flexibility |

## Monitoring and Success Criteria

### Key Metrics

1. **Sentiment API Uptime**: Target 99.5% availability
   - Metric: `(Successful API calls / Total API calls) × 100`
   - Alerting: <95% success rate over 24-hour window

2. **Cache Hit Rate**: Target 85-90% cache hits
   - Metric: `(Cache hits / Total sentiment requests) × 100`
   - Alerting: <75% cache hit rate (indicates cache TTL too short or high ticker diversity)

3. **Veto Accuracy**: Target 70-80% of vetoed candidates subsequently decline
   - Metric: Track underlying price 5 days after veto decision
   - Review: Monthly analysis of vetoed vs non-vetoed candidate performance

4. **API Cost Efficiency**: Target <$60/month total cost
   - Metric: Monthly Alpha Vantage invoice
   - Alerting: Usage approaching tier limits (>100 requests/day)

5. **Sentiment Processing Latency**: Target <2 seconds end-to-end
   - Metric: Time from `get_sentiment_for_ticker()` call to return
   - Breakdown: Cache lookup (<50ms), API call (<1.5s), parsing (<0.5s)

### Alerting Thresholds

- **Alpha Vantage API Error**: >5% API error rate over 1 hour
- **Cache Miss Spike**: Cache hit rate drops below 70%
- **Rate Limit Warning**: API usage exceeds 80% of daily limit
- **Sentiment Processing Timeout**: >5 seconds latency for sentiment check
- **API Key Rotation Due**: 80 days since last rotation (alert 10 days before)

### Success Criteria

- **Functional**: MarketAnalysisAgent provides sentiment for 100 consecutive requests without error
- **Performance**: 90%+ cache hit rate after first week of production use
- **Business Impact**: Sentiment veto prevents at least 1 bad trade/month (validated through post-veto analysis)
- **Cost Control**: Monthly API costs remain <$60 for first 6 months

## Consequences

-   **Implementation**:
    -   The `MarketAnalysisAgent` will be enhanced with a new public method, e.g., `get_sentiment_for_ticker(symbol: str) -> SentimentResult`.
    -   The `MarketAnalysisAgent` will require configuration for the chosen sentiment analysis API, including API keys which must be stored securely in Google Secret Manager.
    -   A Pydantic model for the `SentimentResult` will be created to ensure a standardized data contract between agents.
    -   The `StockSelectionAgent`'s workflow will be updated to call this new method during its "Deep Analysis" phase.
-   **Dependencies**: A new dependency on an external news/sentiment API provider (Alpha Vantage NEWS_SENTIMENT) will be introduced and must be managed.
-   **Performance**: The introduction of caching will significantly improve performance for repeated requests and reduce external API traffic.
-   **Risk Management**: Adds critical pre-trade risk filter to prevent entries during negative catalysts (earnings misses, regulatory issues, etc.)
-   **Cost Control**: Redis caching prevents API cost explosion by reducing redundant sentiment API calls by 85-90%
-   **Extensibility**: Abstracted sentiment interface allows future integration of additional sentiment providers (Finnhub, NewsAPI + Google NLP)

## Alternatives Considered

1.  **Sentiment Logic within `StockSelectionAgent`**: This was rejected because it would create a monolithic agent, violate the separation of concerns, and prevent caching and reuse of the sentiment analysis by other agents.
2.  **Create a new, dedicated `SentimentAgent`**: This was rejected as unnecessary agent sprawl. Sentiment analysis is a form of market analysis and fits squarely within the existing mandate of the `MarketAnalysisAgent`. Creating a new agent for every specific analytical task would lead to a fragmented and overly complex architecture.
3.  **Use free sentiment sources (Twitter, Reddit)**: Rejected due to data quality concerns, lack of structured APIs, and potential for manipulation. Professional-grade sentiment analysis requires curated news sources.
4.  **Build custom sentiment model**: Rejected due to high development cost ($50,000+), ongoing training requirements, and availability of high-quality commercial APIs at reasonable cost.

- **Infrastructure**: Redis cache (Cloud Memorystore), Alpha Vantage API subscription
- **Monthly Cost Estimate**: $55 (API $50 + Redis $5)

**Implementation Challenges**:
1. **Cache TTL Tuning**: Balancing freshness (detect breaking news) vs cost (reduce API calls)
2. **Veto Threshold Calibration**: Setting confidence threshold to minimize false positives (rejecting valid trades) and false negatives (missing bad news)
3. **Breaking News Detection**: Implementing mechanism to invalidate cache when major news breaks
4. **Sentiment Accuracy Validation**: Establishing ground truth for veto effectiveness (requires historical tracking)
