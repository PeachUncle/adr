# ADR 016: Redaction & De-redaction Pattern for Secure PII Handling

## Status
Accepted

## Context

The system must process, store, and retrieve documents that may contain personally identifiable information (PII) and other sensitive data. Regulatory, privacy, and business requirements dictate that:
- PII must be redacted for most users and downstream systems (e.g., LLMs, search, analytics).
- In rare, auditable cases, authorized users (e.g., compliance officers, claims adjusters) must be able to view the original PII values.
- All access to original PII must be strictly controlled, logged, and compliant with privacy regulations (GDPR, CCPA, etc.).

## Problem

The current redaction implementation only replaces PII with generic placeholders and does not support secure, auditable restoration (de-redaction) of original values for authorized users. There is no persistent, encrypted mapping between placeholders and original values, nor a mechanism for fine-grained access control and auditing.

## Decision

We will implement a **token vault-based redaction and de-redaction pattern** as follows:

- **Redaction:**
  - Replace each PII instance with a unique placeholder token (e.g., `***SSN_1***`).
  - Store a mapping record for each placeholder in a secure, encrypted vault (e.g., DynamoDB with KMS, or SQL with envelope encryption).
  - Each mapping record includes: `doc_id`, `placeholder_id`, `entity_type`, `original_value` (encrypted), `confidence`, `created_at`, `expires_at` (TTL).

- **De-redaction:**
  - A dedicated PII Resolver service/class will, upon authorized request, retrieve and decrypt original values for placeholders.
  - The resolver will enforce strict ABAC/RBAC checks and require a reason for access.
  - All de-redaction attempts (authorized or denied) will be logged in an immutable audit log.
  - Mappings will auto-expire after a configurable TTL.

- **API:**
  - Expose secure endpoints for redaction, de-redaction, and audit log retrieval.

- **Security:**
  - All original values are encrypted at rest.
  - Only the resolver service (with a specific IAM role) can decrypt values.
  - All access is logged and auditable.

For detailed implementation steps, see [redaction_de_redaction_design.md](../redaction_de_redaction_design.md).

## Consequences

- **Pros:**
  - Strong privacy and compliance guarantees.
  - Fine-grained, auditable access to PII for authorized users only.
  - Supports regulatory requirements (GDPR, CCPA, etc.).
  - Scalable and compatible with vector search, LLMs, and downstream analytics.

- **Cons:**
  - Increased implementation and operational complexity.
  - Requires secure, persistent storage and key management.
  - Slight performance overhead for de-redaction and auditing.
