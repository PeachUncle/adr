# TASK-003: API contract (OpenAPI) & request/response DTOs
> Source: tasks/tasks.md

## Context
- Goal: Define endpoints (POST /classify, POST /predict, POST /chat, GET /news, GET /price/{ticker}) with OpenAPI schema and example payloads.
- Dependencies: TASK-002 (backend bootstrap)
- Acceptance: OpenAPI JSON/YAML generated and committed under `/docs/api`.
- Constraints: Models: IntentRequest, IntentResponse, PredictRequest, PredictResponse, ChatRequest, ChatResponse.

## Options Considered
- Option A: Simple endpoint definitions with basic DTOs
  - Pros: Quick implementation; meets basic requirements
  - Cons: Limited validation; poor developer experience
- Option B: Comprehensive DTOs with validation, examples, and detailed OpenAPI metadata
  - Pros: Better API documentation; stronger validation; professional quality
  - Cons: More complex; may be overkill for current scope
- Option C: Balanced approach with proper DTOs, validation, and good OpenAPI documentation
  - Pros: Meets requirements; provides good foundation; aligns with technical.md architecture
  - Cons: Slightly more complex than minimal

## Decision
- Choose Option C. Implement comprehensive DTOs with proper validation, examples, and detailed OpenAPI metadata. This provides a professional API contract that will be valuable for frontend integration and future development.

## Impacts
- Performance: Minimal overhead from Pydantic validation
- Complexity: Moderate - well-structured DTOs with validation
- Security/Privacy: Input validation and sanitization
- Compatibility: Standard FastAPI/OpenAPI patterns
- Risks & Mitigations:
  - Risk: Over-engineering for current scope
  - Mitigation: Focus on requirements; defer complex business logic to future tasks
