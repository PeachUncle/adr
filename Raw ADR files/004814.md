# ADR-006: Use RabbitMQ over Kafka for Message Queuing

**Date**: 2022-04-18
**Status**: ✅ Accepted
**Author**: Marcus Chen
**Reviewers**: Sarah Chen, That consultant we hired for a week

## Context

We need asynchronous message processing for:
- Order processing pipeline
- Email/notification sending
- Inventory updates
- Payment retry logic
- Analytics events

Options considered:
1. **Apache Kafka**: The "enterprise" choice
2. **RabbitMQ**: Traditional message broker
3. **AWS SQS**: Managed service
4. **Redis Pub/Sub**: We already have Redis

## Decision

We will use **RabbitMQ** (via Amazon MQ) for all message queuing needs.

## Rationale

### Why RabbitMQ

1. **Right tool for the job**: Our message volume is ~50K/day. Kafka is designed for millions. We'd be using a sledgehammer to crack a nut (🥁).

2. **Flexible routing**: RabbitMQ's exchanges (direct, fanout, topic) match our needs perfectly.

3. **Dead letter exchanges**: Built-in support for failed message handling. Critical for payment retries.

4. **Team familiarity**: 2 engineers have RabbitMQ experience. 0 have Kafka experience.

5. **Operational simplicity**: Amazon MQ handles clustering, backups, updates.

### Why Not Kafka

Chester read an article about Kafka and wanted us to use it. Our response:

> "Kafka is awesome for:
> - Event sourcing at scale
> - Stream processing
> - When you have millions of events per second
> - When you have a dedicated platform team
>
> We have:
> - 50K messages per day
> - 6 engineers
> - Acorn delivery
>
> We're not LinkedIn."

Chester accepted this after we showed him the complexity of a Kafka cluster.

### Why Not AWS SQS

SQS was a close second:
- ✅ Fully managed
- ✅ Pay per use
- ❌ No message routing (each queue is independent)
- ❌ Limited retry strategies
- ❌ 256KB message limit is tight

### Why Not Redis Pub/Sub

- ❌ No persistence (messages lost if subscriber is down)
- ❌ No acknowledgments
- ❌ Fire-and-forget only

## Implementation

### Exchange Structure

```
┌─────────────────────────────────────────────────────────────┐
│                    acornio-exchange (topic)                  │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  order.created ──────► order-processing-queue               │
│  order.shipped ──────► notification-queue                   │
│  order.* ────────────► analytics-queue                      │
│                                                              │
│  payment.failed ─────► payment-retry-queue                  │
│  payment.* ──────────► analytics-queue                      │
│                                                              │
│  inventory.low ──────► reorder-alert-queue                  │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### Dead Letter Setup

```
Main Queue ──(failure)──► DLX ──► dead-letter-queue
                                       │
                                       ▼
                              (Manual review after 3 retries)
```

### Retry Strategy

```javascript
{
  exchange: 'acornio-exchange',
  queue: 'payment-retry-queue',
  options: {
    deadLetterExchange: 'acornio-dlx',
    messageTtl: 300000,  // 5 minutes
    maxRetries: 3,
    backoff: 'exponential'  // 1m, 2m, 4m
  }
}
```

## Consequences

### Positive

- Simple mental model for developers
- Easy debugging (RabbitMQ management UI is excellent)
- Reliable message delivery with acknowledgments
- Good monitoring via CloudWatch + RabbitMQ metrics

### Negative

- Another piece of infrastructure to monitor
- Amazon MQ isn't the cheapest (~$150/month for our setup)
- Some learning curve for developers new to message queues

### Trade-offs Accepted

- We won't be able to replay historical events (unlike Kafka)
- Message ordering is per-queue, not global
- We're locked into AWS for hosting

## Migration Path (If Needed)

If we somehow become LinkedIn-scale:
1. Our message publishing is abstracted behind a `MessagePublisher` interface
2. Consumers use a similar abstraction
3. Could migrate to Kafka by implementing new adapters
4. This will never happen but it makes Chester feel better

## Queue Reference

| Queue | Purpose | Consumer |
|-------|---------|----------|
| order-processing | New order workflow | acorn-api |
| notification | Email/push triggers | squirrel-mailer |
| payment-retry | Failed payment retry | billing-service |
| inventory-sync | Stock level updates | nutventory |
| analytics-ingest | Event tracking | (external Segment) |
| dead-letter | Failed messages | Manual review |
