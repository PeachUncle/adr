# ADR-0001: Use ADRs

## Status

🟢 Active

## Context

I am starting what I expect to be a long-running project.

I want to:
- make architecture decisions explicitly/consciously;
- make it possible to critique those decisions as I learn through the life of
  the project.
- document those decisions in a format that can be reasonably consumed by both
  humans and context-limited LLMs (read: concise, precise, and structured).

## Decision

Document key each decision in the form of an Architecture Decision Record (ADR).

https://adr.github.io/

### Format

- Each ADR is a seperate Markdown formatted text file.
- Each ADR file is named `<number>-<title>.adr.md`
  - `<number>` is a monotonically increasing number and prefixed with `0`s to ensure it is 4 digits long.
  - `<title>` is a kabab-case string that tersely describes the decision.
    - prefer the format `for-<need>-use-<solution>`.
- Each ADR has the following sections:
  - `Status`
    - Draft :: From idea through completely analyzed (with citations, etc.)
    - Active :: Decided and implemented
    - Abandoned :: Never got implemented (with a note about why)
    - Superseded :: Replaced by a subsequent solution (with a link to that ADR)
  - `Context` — Relevant operating realities at the time of the decision.
  - `Decision` — The decision that was made (succinct summary with as much detail as necessary to implement the decision).)
  - `Rationale` — The key factors that led to selecting this solution.
  - `Alternatives Considered` - at least two other viable alternatives to the selected solution (with notes about what was learned about each).
  - `Consequences` — The pros and cons of the selected solution.

## Rationale

- the format of ADRs work well as a prompt for critical thinking while keeping the effort scoped and results concise.
- by requiring context and alternatives, it's possible to review the logic behind the decision long after I have forgotten those details (or that they have changed over time).
- given that each ADR is a single file, it's easy to link to, add to LLMs context, and for a person to read in a short time.

## Alternatives Considered

### Organically Organized Design Documents

I could just start writing down ideas as I have them.

- this would be even more lightweight than ADRs.

However...

- this approach lacks the prompting to think critically about these decisions.


### Rational Unified Process (RUP) Style Design Documents

I could use the documentation scheme of a formal software development process like RUP.

https://en.wikipedia.org/wiki/Rational_Unified_Process

- I'm familiar with RUP and _could_ use that process for guiding the development of the project.
- Such frameworks embody a thoughtful capture of information about a software project at each stage.

However...
- I find that documentation requires more than what is technically necessary in most cases.
- The intent of that kind of documentation doesn't match my circumstances — I'm more interested in reaching high-quality decisions than I am about controlling a project.

## Consequences

### Expected Benefits

- I will make higher-quality decisions / avoid mistakes that can be circumnavigated by critical thinking.
- I will be able to mature the ways I meet the needs of the project through an explicit evolutionary process (i.e. turn information that I learn into design decisions more easily).
- I won't undo a change irresponsibly — avoiding undoing a thoughtfully considered decision because I forgot an important (if subtle) reason for the choice.

### Anticipated Tradeoffs

- I'm going to spend more time that I'd like in documenting decisions.

### Potential Risks

- I overinvest in this documentation and fail to make meaningful actual progress on the project (measured in working software).
