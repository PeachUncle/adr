# ADR-0005: UI/UX Implementation Principles

## Status
Accepted

## Date
2025-12-16

## Context
During development, several UI/UX decisions were made that establish patterns
for the rest of the application. These decisions prioritize clarity, simplicity,
and minimal dependencies.

## Decisions

### 1. Separate Create/Edit Forms Over Shared Partials

**Decision**: Create separate `create.blade.php` and `edit.blade.php` files
rather than a shared `_form.blade.php` partial.

**Rationale**:
- **Clarity over DRY**: Forms often diverge (different validation messages,
  conditional fields, different actions)
- **Easier debugging**: Each form is self-contained
- **No conditional logic**: Avoids `@if($editing)` scattered through templates
- **Explicit over implicit**: New developers understand each form immediately

**Pattern**:
```
resources/views/
  projects/
    create.blade.php  # Full form for creating
    edit.blade.php    # Full form for editing (uses old() with defaults)
    index.blade.php
    show.blade.php
```

### 2. Alpine.js for Client-Side Interactions, No Extra Plugins

**Decision**: Use vanilla Alpine.js without plugins like `@alpine/focus`.

**Rationale**:
- Native HTML handles most keyboard interactions (tab, escape in forms)
- Extra plugins add dependencies that can cause upgrade pain
- Alpine's core features (x-show, x-data, @click) cover 95% of needs
- Browser focus management is often sufficient

**Example** (delete confirmation):
```html
<div x-data="{ showDelete: false }">
    <button @click="showDelete = true">Delete</button>
    <div x-show="showDelete" x-cloak>
        <form method="POST">
            <button type="submit">Confirm</button>
            <button @click="showDelete = false" type="button">Cancel</button>
        </form>
    </div>
</div>
```

### 3. Inline Confirmations Over Modals

**Decision**: Use inline expanding confirmation UI rather than modal dialogs.

**Rationale**:
- Simpler implementation (no portal/teleport needed)
- Clearer context (confirmation appears next to the item)
- No focus trapping complexity
- Mobile-friendly (no overlay management)

### 4. x-cloak for Flash Prevention

**Decision**: Always use `x-cloak` on Alpine-toggled elements.

**Implementation**:
```html
<!-- In layout head -->
<style>[x-cloak] { display: none !important; }</style>

<!-- In components -->
<div x-show="isOpen" x-cloak>...</div>
```

**Rationale**: Prevents flash of unstyled content before Alpine initializes.

### 5. Status/Priority Badges with Semantic Colors

**Decision**: Use consistent color coding for statuses and priorities.

**Pattern**:
```
Priority:
- low: gray
- medium: blue
- high: orange
- urgent: red

Status:
- pending: gray
- in_progress: yellow
- done: green

Project Status:
- active: green
- archived: gray
- completed: blue
```

### 6. Error States with Recovery Actions

**Decision**: Error messages should always include a recovery action.

**Example**:
```html
<div class="bg-red-50 border border-red-200 rounded p-6">
    <h2>AI Unavailable</h2>
    <p>Could not connect to server (url, model)</p>
    <a href="...">Retry</a>
    <span>Fallback AI not configured</span>
</div>
```

**Rationale**: Users should never be stuck. Always provide a next step.

### 7. CDN for Development, Bundle Option for Production

**Decision**: Use CDN links for Tailwind and Alpine during development.

```html
<script src="https://cdn.tailwindcss.com"></script>
<script defer src="https://cdn.jsdelivr.net/npm/alpinejs@3.x.x/dist/cdn.min.js"></script>
```

**Rationale**:
- Zero build step during development
- Fast iteration
- Can switch to Vite bundling for production if needed
- Tailwind JIT via CDN handles custom classes

## Consequences
- Consistent patterns across all views
- Minimal JavaScript dependencies
- Clear, debuggable templates
- Accessible by default (semantic HTML)
- Easy onboarding for new developers
