# ADR-001: Database-Driven Device Management

## Status
**Accepted** - 2024-01-XX

## Context

The CosmicX IoT Hub currently uses Node-RED's global context (`global.get()` and `global.set()`) to store device registry, device states, and other critical system data. This approach has several critical limitations that prevent the system from meeting commercial-grade requirements:

### Problems with Current Approach
1. **Data Volatility**: All device data is lost on Node-RED restart, causing system amnesia
2. **No Persistence**: Device states, onboarding history, and control logs are not persisted
3. **Scalability Issues**: In-memory storage cannot handle large device counts (target: 25,000+ devices)
4. **No Audit Trail**: No logging of device control actions or state changes
5. **No Backup/Recovery**: Cannot backup or restore device configurations
6. **No Data Analytics**: Historical data is not available for analytics or debugging
7. **Concurrency Issues**: Global context is not thread-safe for concurrent operations
8. **No ACID Guarantees**: No transactional consistency for related operations

### Business Requirements
- **99.9% Availability**: System must survive restarts without data loss
- **25,000+ Devices**: Must scale to enterprise IoT deployments
- **Audit Compliance**: All device interactions must be logged for compliance
- **Point-in-Time Recovery**: Database must support backup and recovery (RPO ≤ 5 minutes)
- **Real-time Analytics**: Historical data needed for device health monitoring

## Decision

We will **replace Node-RED global context with PostgreSQL database storage** for all device-related data persistence.

### Implementation Strategy
1. **Database Schema**: Create comprehensive tables for devices, device states, device history, onboarding, and control logs
2. **Database Helper Module**: Create `lib/database-helpers.js` with functions that replace global context calls
3. **Gradual Migration**: Implement new database-driven flows alongside existing flows for safe transition
4. **Backward Compatibility**: Maintain existing API contracts while changing underlying storage
5. **Performance Optimization**: Use database indexes, connection pooling, and prepared statements

### Database Design Principles
- **UUID Primary Keys**: For distributed system compatibility
- **JSONB State Storage**: Flexible schema for diverse device types
- **Time-series History**: Separate table for historical state tracking
- **Audit Logging**: Complete audit trail for all device operations
- **Referential Integrity**: Foreign key constraints for data consistency

## Consequences

### Positive
- ✅ **Data Persistence**: Device data survives system restarts
- ✅ **Scalability**: PostgreSQL can handle 25,000+ devices efficiently
- ✅ **ACID Compliance**: Transactional consistency for critical operations
- ✅ **Audit Trail**: Complete logging of all device interactions
- ✅ **Backup/Recovery**: Standard database backup and recovery procedures
- ✅ **Analytics Ready**: Historical data available for analytics and monitoring
- ✅ **Performance**: Indexed queries much faster than in-memory searches at scale
- ✅ **Concurrent Access**: Database handles concurrent reads/writes safely
- ✅ **Data Integrity**: Constraints prevent invalid data states

### Negative
- ❌ **Complexity**: Additional database infrastructure to manage
- ❌ **Latency**: Database queries add ~1-5ms vs in-memory access
- ❌ **Dependencies**: System now depends on PostgreSQL availability
- ❌ **Migration Effort**: Significant refactoring of existing Node-RED flows

### Risks and Mitigations
| Risk | Impact | Mitigation |
|------|--------|------------|
| Database downtime | System unavailable | Database clustering, connection pooling with retries |
| Query performance | Slow API responses | Database indexing, query optimization, connection pooling |
| Data migration | Data loss during transition | Gradual rollout, extensive testing, backup procedures |
| Increased complexity | Harder to debug | Comprehensive logging, monitoring, health checks |

## Implementation Details

### Database Schema
```sql
-- Core device registry
CREATE TABLE devices (
    id UUID PRIMARY KEY,
    friendly_name VARCHAR(128) UNIQUE NOT NULL,
    ieee_address VARCHAR(64) UNIQUE,
    device_type VARCHAR(64) NOT NULL,
    protocol VARCHAR(32) NOT NULL,
    -- ... additional fields
);

-- Current device states
CREATE TABLE device_states (
    device_id UUID REFERENCES devices(id),
    state JSONB NOT NULL,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- Historical state changes
CREATE TABLE device_history (
    id UUID PRIMARY KEY,
    device_id UUID REFERENCES devices(id),
    state JSONB NOT NULL,
    event_type VARCHAR(64),
    recorded_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
```

### API Compatibility
```javascript
// Old: global.get('devices')
const devices = global.get('devices') || [];

// New: database query
const devices = await dbHelpers.getAllDevices();

// Old: global.set for device state
global.set(`device:${deviceId}:state`, newState);

// New: database update
await dbHelpers.updateDeviceState(deviceId, newState, 'api');
```

### Performance Considerations
- **Connection Pooling**: 20 concurrent connections with 2-second timeout
- **Prepared Statements**: All queries use parameterized statements
- **Indexes**: Optimized for device lookups and state queries
- **Batch Operations**: Bulk inserts for device discovery
