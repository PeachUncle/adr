# ADR-002: Use MediatR Library for Mediator Pattern Implementation

## Status
Accepted (Inferred from implementation)

## Context
With the decision to use CQRS pattern (see ADR-001), the system needed a way to:
- Decouple controllers from command/query handlers
- Support dependency injection for handlers
- Enable potential cross-cutting concerns (logging, validation, etc.)
- Avoid manual handler registration and discovery
- Maintain consistency with common .NET patterns

The team needed to choose between implementing a custom mediator or using an existing library.

## Decision
Use MediatR library (version 8.0) as the mediator implementation for both .NET Framework and .NET Core applications.

Key implementation details:
- All commands implement `IRequest` or `IRequest<TResponse>`
- All handlers implement `IRequestHandler<TRequest>` or `IRequestHandler<TRequest, TResponse>`
- Autofac integration for dependency injection
- Automatic handler discovery via assembly scanning

## Consequences

### Positive
- **Reduced Boilerplate**: No need to write custom mediator implementation
- **Community Support**: Well-maintained library with extensive documentation
- **Proven Solution**: Battle-tested in production environments
- **DI Integration**: Seamless integration with dependency injection containers
- **Pipeline Behaviors**: Support for cross-cutting concerns through pipeline behaviors
- **Async Support**: Built-in async/await support for handlers

### Negative
- **External Dependency**: Adds external dependency to the project
- **Version Compatibility**: Need to maintain compatible versions across projects
- **Learning Curve**: Developers need to understand MediatR concepts
- **Magic Registration**: Handler registration happens automatically, which can be opaque
- **Debugging Complexity**: Indirection can make debugging more difficult

### Risks
- **Library Abandonment**: Risk if MediatR stops being maintained
- **Breaking Changes**: Major version updates might require significant refactoring
- **Performance Overhead**: Additional abstraction layer adds minimal overhead
- **Over-abstraction**: Temptation to over-use mediator for simple operations

## Notes
Current implementation uses:
- MediatR 8.0.0 in both .NET Framework and .NET Core projects
- Autofac for dependency injection and handler registration
- Assembly scanning for automatic handler discovery
- No pipeline behaviors currently implemented (future enhancement opportunity)

## Alternatives Considered
1. **Custom Mediator Implementation**: More control but more code to maintain
2. **Direct Dependency Injection**: Simpler but tighter coupling
3. **Service Locator Pattern**: Anti-pattern, leads to hidden dependencies
4. **Command Bus Libraries**: Similar to MediatR but less popular in .NET ecosystem

## Recommendations
1. Consider implementing pipeline behaviors for:
   - Logging
   - Validation
   - Performance monitoring
   - Transaction handling
2. Upgrade to latest MediatR version (current implementation uses 8.0, latest is 12.x)
3. Add unit tests for mediator configuration and handler registration
