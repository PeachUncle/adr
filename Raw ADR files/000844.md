# ADR-013: Data Retention and Analytical Data Architecture

## Status
**Accepted** (October 7, 2025)

## Context

### Business Drivers
BahariWatch generates multiple categories of data with distinct retention and analytical requirements, serving both operational enforcement needs and long-term research objectives. The system must balance:

**Operational Data Needs (Real-Time Enforcement):**
- Community reports with GPS-stamped photos for immediate matching and alert generation
- AIS/VMS vessel tracking data for real-time correlation
- Alert delivery records for enforcement response tracking
- Sub-5-second alert delivery performance requirement

**Analytical Data Needs (Research & Policy):**
- Survey responses for research analysis by Kenya Marine and Fisheries Research Institute (KMFRI)
- Historical vessel tracking patterns for illegal fishing hotspot analysis
- Report history for enforcement evidence and legal proceedings
- Performance metrics for Beach Management Unit (BMU) evaluation
- Trend analysis for policy guidelines to scale participatory monitoring nationally

**Compliance and Legal Requirements:**
- **GDPR Right to be Forgotten:** User data must be deletable upon request (per ADR-008)
- **Enforcement Evidence:** Report history and GPS photos must be retained for legal proceedings (minimum 5 years per Kenyan law)
- **Anonymous Reporting Protection:** PII must not be accessible in analytical datasets (per ADR-008)
- **Data Sovereignty:** Consideration for data storage location (Kenya vs international cloud providers)

### Technical Constraints
Per ADR-003 (Database Architecture), BahariWatch uses a **monolithic PostgreSQL + PostGIS database** with logical separation by schema. This decision deferred database decomposition but acknowledged future needs for operational vs analytical data separation.

**Current Data Volume Projections (6-Month Pilot):**
- **Community Reports:** 500-1,000 reports/month × 6 months = 3,000-6,000 reports
- **GPS Photos:** Avg 2MB/photo × 5,000 photos = 10GB photo storage
- **Vessel Tracking (Cached GFW API):** 100 vessels × 30 days × 24 hourly positions = 72,000 position records/month
- **Survey Responses:** 200 surveys/month × 6 months = 1,200 survey entries
- **Alerts:** 50-100 alerts/month × 6 months = 300-600 alert records

**Post-Pilot Scaling (12-24 Months):**
- 10,000+ coastal users submitting reports
- 50,000-100,000 reports annually
- 100GB-500GB GPS photo storage
- Millions of vessel position records from continuous AIS/VMS ingestion

### Architecture Characteristics Affected
(Reference: Fundamentals of Software Architecture, Chapters 4-6)
- **Performance:** Analytical queries on large datasets must not degrade operational system performance
- **Scalability:** Data storage and query capacity must scale from pilot (5k reports) to national deployment (100k+ reports)
- **Data Integrity:** Historical data immutability for legal evidence and research reproducibility
- **Compliance:** GDPR data retention limits, anonymous reporting protection, audit trail requirements
- **Cost:** Budget-conscious storage strategy within KSh 59,500 project constraints

### Integration with Other ADRs
- **Depends on:** ADR-003 (Monolithic Database), ADR-008 (Security & Privacy Controls), ADR-012 (Deployment Infrastructure)
- **Related to:** ADR-001 (Microservices - potential Analytics Service), ADR-010 (Fitness Functions for data retention compliance)
- **Supports:** Research objectives in project proposal (trend analysis, policy guidelines, BMU evaluation)

## Decision

We will adopt a **hybrid operational-analytical data architecture** using **PostgreSQL logical separation with time-series partitioning** for operational data, **read replicas for analytical queries**, and **object storage lifecycle policies** for GPS photo archival. We defer full CQRS (Command Query Responsibility Segregation) and external data warehouse/lake implementation until post-pilot scaling requirements justify the complexity.

### Architecture Components:

#### 1. Operational Data Tier (Real-Time Enforcement)
- **PostgreSQL schemas:** `reports`, `vessels`, `alerts`, `users` (per ADR-003 logical separation)
- **Table partitioning:** Time-series partitioning on `created_at` column (monthly partitions)
- **Hot data window:** Last 90 days in active partitions (optimized indexes, frequent queries)
- **Write-optimized:** Normalized schemas for transactional integrity (ACID compliance)

#### 2. Analytical Data Tier (Research & Reporting)
- **PostgreSQL read replica:** Offload analytical queries to dedicated read replica (prevents operational degradation)
- **Materialized views:** Pre-computed aggregations for common analytical queries (hotspot maps, BMU performance metrics)
- **Analytical schema:** Denormalized `analytics` schema with fact/dimension tables for complex queries
- **Read-optimized:** Optimized for aggregations, joins, and full-table scans

#### 3. Archival Data Tier (Long-Term Storage)
- **Cold storage:** GPS photos older than 90 days moved to DigitalOcean Spaces with infrequent access tier
- **Database archival:** Reports/alerts older than 2 years archived to compressed JSONB format in `archive` schema
- **Legal retention:** Immutable audit logs for 5 years (enforcement evidence, compliance audits)

#### 4. Data Lifecycle Management
- **Retention Policies:**
  - **GPS Photos:** 5 years (legal evidence requirement), then soft-delete with 30-day recovery window
  - **Community Reports:** 5 years (legal evidence), then anonymize (remove user_id, retain spatial/temporal data for research)
  - **Vessel Tracking:** 3 years (pattern analysis), then aggregate to daily summaries, delete raw positions
  - **Survey Responses:** Indefinite (research data), anonymize PII after 1 year
  - **Alerts:** 5 years (enforcement accountability), then archive to compressed format
  - **User Accounts:** Delete on request (GDPR), cascade delete associated non-evidential data

- **Automated Archival:**
  - Weekly cron job partitions hot data (reports/alerts created >90 days ago) into cold partitions
  - Monthly job moves GPS photos to object storage cold tier (S3 Glacier-like pricing)
  - Yearly job anonymizes reports older than 5 years (GDPR compliance automation)

#### 5. Analytics Access Patterns
- **Business Intelligence Dashboards (Grafana):**
  - Query read replica for real-time metrics (report volume, alert latency, BMU activity)
  - Materialized views refreshed hourly (hotspot maps, vessel activity summaries)
  
- **Research Queries (KMFRI, Universities):**
  - Direct SQL access to read replica (anonymized datasets only)
  - Export API endpoint for CSV/JSON bulk downloads (rate-limited per ADR-011)
  
- **Enforcement Reports (Government Agencies):**
  - Secure API endpoints for legal evidence retrieval (authenticated access per ADR-008)
  - Audit log captures all evidence access (compliance requirement)

## Rationale

### Alternatives Considered

#### Alternative 1: Full CQRS with Separate Analytical Database (Rejected for Pilot)
**Pros:**
- Complete operational/analytical separation (zero query interference)
- Optimal schema design for each use case (normalized OLTP, denormalized OLAP)
- Independent scaling (scale read models without impacting write models)
- Supports event sourcing for full historical reconstruction

**Cons:**
- **Complexity overhead:** Separate database infrastructure (2x PostgreSQL clusters + event stream synchronization)
- **Development velocity:** Event sourcing patterns slow feature iteration during pilot phase
- **Cost:** Additional database hosting (~$30/month) exceeds pilot budget constraints
- **Synchronization lag:** Eventual consistency between write and read models complicates real-time dashboards
- **Over-engineering:** Pilot scale (5k reports, 10GB photos) doesn't justify architectural complexity

**Why Rejected:** CQRS is premature optimization for pilot scale. PostgreSQL read replicas provide 80% of CQRS benefits (query isolation, read scalability) with 20% of the complexity. Defer until post-pilot scaling (100k+ reports) justifies investment.

#### Alternative 2: External Data Warehouse (Snowflake, BigQuery, AWS Redshift) (Rejected)
**Pros:**
- Purpose-built for analytical workloads (columnar storage, massively parallel processing)
- Unlimited scalability for petabyte-scale datasets
- Advanced SQL analytics (window functions, statistical aggregations)
- Industry-standard for enterprise business intelligence

**Cons:**
- **Cost prohibitive:** $50-200/month minimum (exceeds entire project budget)
- **Integration complexity:** ETL pipelines from PostgreSQL to warehouse (additional tooling like Airbyte, Fivetran)
- **Vendor lock-in:** Proprietary SQL dialects (Snowflake vs BigQuery) complicate migration
- **Data latency:** Batch ETL processes introduce hours of staleness (conflicts with real-time enforcement requirements)
- **Over-engineering:** Pilot analytical needs (trend reports, survey analysis) satisfied by PostgreSQL + PostGIS spatial queries

**Why Rejected:** Data warehouse is overkill for pilot scale and budget. PostgreSQL with proper indexing and materialized views handles analytical queries for 6-month pilot. Re-evaluate if dataset exceeds 1TB or analytical query latency becomes unacceptable.

#### Alternative 3: Data Lake (AWS S3 + Athena, DigitalOcean Spaces + Presto) (Rejected)
**Pros:**
- Cost-effective storage for semi-structured data (GPS photos, vessel tracking JSON)
- Schema-on-read flexibility (no upfront schema design for analytical queries)
- Supports machine learning workflows (future predictive illegal fishing models)
- Decoupled from operational database (no schema change brittleness)

**Cons:**
- **Query performance:** S3 + Athena slower than PostgreSQL for structured relational queries
- **Lack of ACID guarantees:** Data lake append-only model complicates GDPR data deletion (Right to be Forgotten)
- **Development complexity:** Requires data engineers to manage Parquet/ORC file formats, partitioning strategies
- **Limited SQL support:** Athena/Presto SQL not full PostgreSQL feature parity (PostGIS spatial queries unsupported)
- **Cost creep:** Per-query pricing model unpredictable for research users running ad-hoc analytics

**Why Rejected:** Data lake deferred until machine learning use cases materialize (predictive IUU fishing models). Current analytical needs (survey analysis, hotspot mapping) better served by PostgreSQL spatial queries. Data lake appropriate for post-pilot if ML becomes priority.

#### Alternative 4: Single Database Without Read Replica (Rejected)
**Pros:**
- **Simplest architecture:** No replication lag, strong consistency guarantees
- **Zero additional cost:** No separate database instance
- **Unified schema:** No synchronization logic between operational and analytical schemas

**Cons:**
- **Performance degradation:** Analytical queries (full-table scans, aggregations) lock tables and slow operational writes
- **Availability risk:** Long-running analytical queries consume connection pool, block alert delivery
- **No scalability path:** Cannot independently scale read/write workloads
- **Violates ADR-010 fitness function:** Availability SLO (99.5% uptime) violated by analytical query interference

**Why Rejected:** Even at pilot scale, analytical queries risk operational performance. Read replica provides query isolation for negligible cost (~$15/month, already budgeted in ADR-012). This decision aligns with "Hard Parts" Chapter 14 guidance: "The formats and schemas of [operational data] don't necessarily fit (or even allow the use of) [analytical data]."

### Why Hybrid Operational-Analytical Architecture?

Per "Software Architecture: The Hard Parts" Chapter 14:
> "The split between operational and analytical data is hardly a new problem—the fundamental different uses of data have existed as long as data. As architecture styles have emerged and evolved, approaches for how to handle data have changed and evolved similarly."

**Our hybrid approach balances pilot pragmatism with post-pilot evolution:**

1. **Read Replica Isolation:** Offloads analytical queries to dedicated replica, protecting operational performance (99.5% availability SLO per ADR-010)
2. **Time-Series Partitioning:** PostgreSQL native partitioning optimizes hot data queries (last 90 days) while preserving historical data for legal retention
3. **Materialized Views:** Pre-computed aggregations (hotspot maps, BMU metrics) avoid expensive JOIN operations on read replica
4. **Object Storage Lifecycle:** GPS photos automatically tiered to cold storage (cost-effective archival while maintaining legal evidence accessibility)
5. **Clear Migration Path:** Read replica + partitioning sets foundation for CQRS if post-pilot scaling requires full operational/analytical separation

**Key Insight from "Hard Parts" Chapter 14:**
> "Modern architecture patterns favor domain partitioning, encapsulating technical implementation details. For example, the microservices architecture attempts to separate services by domain rather than technical capabilities, encapsulating domain knowledge, including data, inside the service boundary."

Our hybrid approach respects domain partitioning (per ADR-007 Data Ownership) while providing technical separation of operational vs analytical workloads. Unlike Data Warehouse (loses domain context in transformation) or Data Lake (dumps unstructured data), our read replica preserves PostgreSQL domain schemas while optimizing for analytical query patterns.

## Architecture Characteristics Impact

(Reference: Fundamentals of Software Architecture, Chapters 4-6)

### ↑ Positive Impact

- **Performance: ↑↑↑** (Analytical queries isolated to read replica, operational writes unaffected by long-running aggregations)
- **Scalability: ↑↑** (Read replica scales analytical query load independently from operational database)
- **Availability: ↑↑↑** (Query isolation protects 99.5% uptime SLO, analytical failures don't cascade to operational system)
- **Data Integrity: ↑↑** (Immutable archival for legal evidence, audit logs for compliance)
- **Cost: ↑↑↑** (Read replica $15/month + object storage $5/month = $20/month total, fits budget)
- **Maintainability: ↑↑** (PostgreSQL-native features reduce custom ETL logic, unified SQL interface for developers)
- **Compliance: ↑↑↑** (Automated retention policies enforce GDPR deletion, anonymization, audit trails)

### ↓ Negative Impact

- **Consistency: ↓** (Read replica lag 1-5 seconds, analytical dashboards may show slightly stale data; acceptable for research use cases)
- **Complexity: ↓** (Read replica replication logic, partitioning maintenance, materialized view refresh jobs add operational overhead)

### → Neutral Impact

- **Security: →** (Same encryption at rest/transit as operational database per ADR-008, read replica adds attack surface but mitigated by VPC isolation)
- **Testability: →** (Read replica testable via automated queries, partitioning requires time-based test data)

## Consequences

### Positive

1. **Operational Performance Protected:** Analytical queries (trend reports, hotspot map generation) run on read replica, zero impact on alert delivery latency (<5s SLO)
2. **Cost-Effective Scaling:** Read replica ($15/month) provides 80% of CQRS benefits at 20% of cost, fits within KSh 59,500 project budget
3. **Research Accessibility:** KMFRI and university researchers query anonymized datasets via read replica without operational access
4. **Legal Compliance:** 5-year retention for enforcement evidence, automated GDPR deletion after retention period
5. **Spatial Query Preservation:** PostGIS functions (ST_Within, ST_Distance) work natively on read replica for hotspot analysis
6. **Clear Evolution Path:** Read replica + partitioning foundation enables smooth migration to CQRS or data warehouse if post-pilot scaling requires
7. **Simplified Development:** Single PostgreSQL ecosystem (vs polyglot persistence) reduces learning curve for student developer
8. **Automated Data Lifecycle:** Cron jobs handle photo archival, report anonymization, partition maintenance without manual intervention
9. **Audit Trail Immutability:** Append-only audit logs in `audit` schema provide tamper-proof compliance records
10. **Survey Data Longevity:** Indefinite retention of anonymized survey responses supports long-term fisheries research

### Negative

1. **Replication Lag:** Read replica 1-5 seconds behind primary database, analytical dashboards show slightly stale data (acceptable for research, not real-time enforcement)
2. **Partition Maintenance Overhead:** Monthly partition creation and archival jobs require monitoring and error handling
3. **Materialized View Staleness:** Hourly refresh means hotspot maps lag by up to 1 hour (trade-off for query performance)
4. **Limited Advanced Analytics:** PostgreSQL window functions less powerful than specialized OLAP databases (Snowflake, BigQuery)
5. **No Machine Learning Pipeline:** Deferred ML workflows (predictive IUU models) until data lake infrastructure justified
6. **Storage Cost Growth:** Object storage costs increase linearly with GPS photo volume (mitigated by cold tier pricing)
7. **GDPR Deletion Complexity:** Cascading deletes across partitions, object storage, read replica require careful orchestration
8. **Read Replica Failover:** If read replica fails, analytical queries fallback to primary database (temporary operational performance impact)

### Neutral

1. **Replication Monitoring:** Prometheus metrics track replication lag, alert if exceeds 10 seconds (per ADR-010 fitness function)
2. **Schema Evolution:** Database migrations must apply to both primary and read replica (PostgreSQL replication handles automatically)
3. **Backup Strategy:** Read replica backups redundant with primary database backups (DigitalOcean Managed PostgreSQL per ADR-012)

import pytest
import psycopg2
from datetime import datetime

def test_read_replica_replication_lag():
    """Verify read replica lag is acceptable (<10 seconds)"""
    # Connect to primary database
    primary_conn = psycopg2.connect(os.environ['PRIMARY_DATABASE_URL'])
    primary_cursor = primary_conn.cursor()
    
    # Write timestamp to primary
    write_time = datetime.now()
    primary_cursor.execute("""
        INSERT INTO health_checks (check_name, check_time) 
        VALUES ('replication_lag_test', %s)
    """, (write_time,))
    primary_conn.commit()
    
    # Wait 2 seconds for replication
    time.sleep(2)
    
    # Read from replica
    replica_conn = psycopg2.connect(os.environ['REPLICA_DATABASE_URL'])
    replica_cursor = replica_conn.cursor()
    replica_cursor.execute("""
        SELECT check_time 
        FROM health_checks 
        WHERE check_name = 'replication_lag_test' 
        ORDER BY check_time DESC 
        LIMIT 1
    """)
    
    result = replica_cursor.fetchone()
    assert result is not None, "Replication failed: data not found on replica"
    
    replica_time = result[0]
    lag_seconds = (replica_time - write_time).total_seconds()
    
    # Fitness function: Replication lag must be <10 seconds
    assert lag_seconds < 10, \
        f"Replication lag {lag_seconds}s exceeds 10s threshold"
    
    print(f"✅ Read replica replication lag: {lag_seconds:.2f}s (<10s threshold)")
    
    # Cleanup
    primary_cursor.execute("DELETE FROM health_checks WHERE check_name = 'replication_lag_test'")
    primary_conn.commit()
```

# cron_jobs/verify_object_storage_lifecycle.py
import boto3
from datetime import datetime, timedelta
import prometheus_client

def verify_photo_archival_policy():
    """Runtime fitness function: Verify GPS photos archived after 90 days"""
    s3_client = boto3.client('s3',
        endpoint_url=os.environ['SPACES_ENDPOINT'],
        aws_access_key_id=os.environ['SPACES_ACCESS_KEY'],
        aws_secret_access_key=os.environ['SPACES_SECRET_KEY']
    )
    
    # Check for photos older than 90 days in hot storage
    cutoff_date = datetime.now() - timedelta(days=90)
    
    response = s3_client.list_objects_v2(
        Bucket=os.environ['SPACES_BUCKET_NAME'],
        Prefix='photos/hot/'
    )
    
    old_photos_count = 0
    if 'Contents' in response:
        for obj in response['Contents']:
            if obj['LastModified'].replace(tzinfo=None) < cutoff_date:
                old_photos_count += 1
    
    # Fitness function: <1% of photos in hot storage should be >90 days old
    total_photos = len(response.get('Contents', []))
    if total_photos > 0:
        old_photo_percentage = (old_photos_count / total_photos) * 100
        assert old_photo_percentage < 1, \
            f"{old_photo_percentage:.1f}% of photos in hot storage are >90 days old"
    
    # Export metric to Prometheus
    gauge = prometheus_client.Gauge(
        'photo_archival_policy_violations', 
        'Number of photos in hot storage older than 90 days'
    )
    gauge.set(old_photos_count)
    
    print(f"✅ Photo archival policy: {old_photos_count} violations (<1% threshold)")
```

### Security Implications

1. **Read Replica Access Control:**
   - Read replica VPC-isolated from public internet (DigitalOcean VPC per ADR-012)
   - Separate PostgreSQL user roles: `operational_writer`, `analytical_reader`, `admin`
   - `analytical_reader` role: SELECT-only on `analytics` schema (no PII access)
   - SSL/TLS required for all read replica connections

2. **Anonymization Logic:**
   - Automated cron job anonymizes reports after 5-year retention period
   - Anonymization: `user_id` → NULL, GPS coordinates rounded to 0.1° precision (11km grid)
   - Survey responses: Strip PII fields (name, phone) after 1 year, retain demographic aggregates

3. **Audit Log Immutability:**
   - Append-only `audit` schema with PostgreSQL trigger preventing UPDATEs/DELETEs
   - Audit logs track all evidence access (WHO accessed WHAT evidence WHEN)
   - Tamper detection: Cryptographic hash chain (each audit entry hashes previous entry)

4. **Object Storage Encryption:**
   - GPS photos encrypted at rest (AES-256) in DigitalOcean Spaces
   - Pre-signed URLs with 1-hour expiration for evidence retrieval (prevent URL sharing)
   - Server-side encryption keys rotated quarterly

### Data Privacy Implications

1. **GDPR Right to be Forgotten:**
   - User deletion API endpoint triggers cascading delete across partitions, read replica, object storage
   - Legal evidence exemption: Reports flagged as evidence retained despite deletion request (notify user)
   - Deletion verification fitness function: Query deleted user_id across all schemas/partitions (must return zero)

2. **Anonymous Reporting Protection:**
   - Analytical queries use `analytics` schema with user_id pre-anonymized
   - Research data exports (CSV/JSON) filtered through anonymization layer
   - PII leakage detection in analytical queries (per ADR-010 fitness function)

3. **Research Data Ethics:**
   - Survey responses anonymized before researcher access (no PII in analytical datasets)
   - Informed consent captured during survey submission (stored separately in `consent` table)
   - Data sharing agreements required for KMFRI/university access (signed MOU on file)

**Automated Partition Management:**
```python
# cron_jobs/hot_data_partition_manager.py
import psycopg2
from datetime import datetime, timedelta
from dateutil.relativedelta import relativedelta

def create_future_partitions(conn, months_ahead=3):
    """Create partitions for next N months"""
    cursor = conn.cursor()
    
    for i in range(1, months_ahead + 1):
        future_date = datetime.now() + relativedelta(months=i)
        partition_name = f"community_reports_{future_date.strftime('%Y_%m')}"
        start_date = future_date.replace(day=1)
        end_date = start_date + relativedelta(months=1)
        
        # Check if partition already exists
        cursor.execute("""
            SELECT tablename 
            FROM pg_tables 
            WHERE schemaname = 'reports' AND tablename = %s
        """, (partition_name,))
        
        if cursor.fetchone() is None:
            cursor.execute(f"""
                CREATE TABLE reports.{partition_name}
                PARTITION OF reports.community_reports
                FOR VALUES FROM ('{start_date.isoformat()}') TO ('{end_date.isoformat()}')
            """)
            conn.commit()
            print(f"✅ Created partition: {partition_name}")

def archive_cold_partitions(conn, cold_days=90):
    """Move partitions older than N days to archive schema"""
    cursor = conn.cursor()
    cutoff_date = datetime.now() - timedelta(days=cold_days)
    cutoff_month = cutoff_date.strftime('%Y_%m')
    
    cursor.execute("""
        SELECT tablename 
        FROM pg_tables 
        WHERE schemaname = 'reports' 
        AND tablename LIKE 'community_reports_____%%'
        AND tablename < 'community_reports_' || %s
    """, (cutoff_month,))
    
    for (partition_name,) in cursor.fetchall():
        # Move partition to archive schema (preserves data, changes namespace)
        cursor.execute(f"""
            ALTER TABLE reports.{partition_name} 
            SET SCHEMA archive
        """)
        conn.commit()
        print(f"📦 Archived partition: {partition_name} (older than {cold_days} days)")

if __name__ == '__main__':
    conn = psycopg2.connect(os.environ['DATABASE_URL'])
    create_future_partitions(conn, months_ahead=3)
    archive_cold_partitions(conn, cold_days=90)
    conn.close()
```

**Database Router Implementation:**
```python
# config/routers.py

class AnalyticalDatabaseRouter:
    """
    Route analytical queries to read replica, operational queries to primary
    """
    
    analytical_models = {
        'HotspotMapView',
        'BMUPerformanceReport',
        'SurveyResponse',
        'VesselTrackingHistory',
    }
    
    def db_for_read(self, model, **hints):
        """
        Analytical models read from replica, operational models from primary
        """
        if model.__name__ in self.analytical_models:
            return 'replica'
        return 'default'
    
    def db_for_write(self, model, **hints):
        """
        All writes go to primary database
        """
        return 'default'
    
    def allow_relation(self, obj1, obj2, **hints):
        """
        Allow relations between objects in same database
        """
        db_set = {'default', 'replica'}
        if obj1._state.db in db_set and obj2._state.db in db_set:
            return True
        return None
    
    def allow_migrate(self, db, app_label, model_name=None, **hints):
        """
        Migrations only run on primary database
        """
        return db == 'default'
```

-- migrations/003_create_analytical_materialized_views.sql

CREATE SCHEMA IF NOT EXISTS analytics;

-- Hotspot Map (Daily Aggregation)
CREATE MATERIALIZED VIEW analytics.hotspot_map_daily AS
SELECT 
    DATE(r.created_at) as report_date,
    ST_SnapToGrid(ST_Point(r.gps_longitude, r.gps_latitude), 0.01) as grid_cell,
    COUNT(*) as report_count,
    AVG(r.gps_latitude) as avg_latitude,
    AVG(r.gps_longitude) as avg_longitude
FROM reports.community_reports r
WHERE r.created_at >= CURRENT_DATE - INTERVAL '90 days'
GROUP BY report_date, grid_cell
HAVING COUNT(*) >= 3  -- At least 3 reports to qualify as hotspot
WITH DATA;

CREATE INDEX idx_hotspot_map_date ON analytics.hotspot_map_daily(report_date);
CREATE INDEX idx_hotspot_map_geom ON analytics.hotspot_map_daily USING GIST(grid_cell);

-- BMU Performance Metrics (Monthly Aggregation)
CREATE MATERIALIZED VIEW analytics.bmu_performance_monthly AS
SELECT 
    DATE_TRUNC('month', r.created_at) as report_month,
    u.bmu_name,
    COUNT(DISTINCT r.user_id) as active_reporters,
    COUNT(r.report_id) as total_reports,
    COUNT(CASE WHEN a.alert_id IS NOT NULL THEN 1 END) as reports_matched_to_alerts,
    AVG(EXTRACT(EPOCH FROM (a.created_at - r.created_at))) as avg_match_latency_seconds
FROM reports.community_reports r
JOIN users.users u ON r.user_id = u.user_id
LEFT JOIN alerts.alerts a ON r.report_id = a.report_id
WHERE r.created_at >= CURRENT_DATE - INTERVAL '12 months'
GROUP BY report_month, u.bmu_name
WITH DATA;

CREATE INDEX idx_bmu_performance_month ON analytics.bmu_performance_monthly(report_month);

-- Vessel Activity Summary (Weekly Aggregation)
CREATE MATERIALIZED VIEW analytics.vessel_activity_weekly AS
SELECT 
    DATE_TRUNC('week', v.timestamp) as activity_week,
    v.vessel_id,
    v.vessel_name,
    COUNT(*) as position_count,
    ST_Extent(ST_Point(v.longitude, v.latitude)) as activity_bounding_box,
    MIN(v.timestamp) as first_seen,
    MAX(v.timestamp) as last_seen
FROM vessels.vessel_positions v
WHERE v.timestamp >= CURRENT_DATE - INTERVAL '26 weeks'
GROUP BY activity_week, v.vessel_id, v.vessel_name
WITH DATA;

CREATE INDEX idx_vessel_activity_week ON analytics.vessel_activity_weekly(activity_week);

import boto3
from datetime import datetime
import hashlib

def upload_gps_photo(photo_file, report_id, gps_latitude, gps_longitude):
    """Upload GPS-stamped photo to object storage"""
    s3_client = boto3.client('s3',
        endpoint_url=os.environ['SPACES_ENDPOINT'],
        aws_access_key_id=os.environ['SPACES_ACCESS_KEY'],
        aws_secret_access_key=os.environ['SPACES_SECRET_KEY']
    )
    
    # Generate unique photo key
    upload_date = datetime.now().strftime('%Y/%m/%d')
    photo_hash = hashlib.sha256(photo_file.read()).hexdigest()[:16]
    photo_key = f"photos/{upload_date}/{report_id}_{photo_hash}.jpg"
    
    # Reset file pointer after hashing
    photo_file.seek(0)
    
    # Upload with metadata
    s3_client.put_object(
        Bucket=os.environ['SPACES_BUCKET_NAME'],
        Key=photo_key,
        Body=photo_file,
        ContentType='image/jpeg',
        Metadata={
            'report_id': str(report_id),
            'gps_latitude': str(gps_latitude),
            'gps_longitude': str(gps_longitude),
            'upload_timestamp': datetime.now().isoformat(),
            'retention_years': '5'  # Legal evidence retention
        },
        ServerSideEncryption='AES256'  # Encrypt at rest
    )
    
    # Generate presigned URL (1 hour expiration for evidence retrieval)
    photo_url = s3_client.generate_presigned_url(
        'get_object',
        Params={'Bucket': os.environ['SPACES_BUCKET_NAME'], 'Key': photo_key},
        ExpiresIn=3600
    )
    
    print(f"✅ Uploaded photo: {photo_key}")
    return photo_url

import psycopg2
from datetime import datetime, timedelta

def anonymize_reports_after_retention(conn, retention_years=5):
    """Anonymize reports older than retention period (GDPR compliance)"""
    cursor = conn.cursor()
    cutoff_date = datetime.now() - timedelta(days=retention_years*365)

            anonymized_at = NOW()

        AND user_id IS NOT NULL

# api/gdpr_endpoints.py
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework import status
from django.db import transaction

class GDPRUserDeletionView(APIView):
    """
    GDPR Right to be Forgotten: Delete user and associated data
    """
    
    @transaction.atomic
    def delete(self, request, user_id):
        # Check if user has reports flagged as legal evidence
        evidence_reports = Report.objects.filter(
            user_id=user_id,
            is_legal_evidence=True
        )
        
        if evidence_reports.exists():
            return Response({
                'status': 'partial_deletion',
                'message': f'{evidence_reports.count()} reports retained as legal evidence',
                'evidence_report_ids': list(evidence_reports.values_list('report_id', flat=True))
            }, status=status.HTTP_206_PARTIAL_CONTENT)
        
        # Cascading delete across all schemas
        with connection.cursor() as cursor:
            # Delete user data from all schemas
            cursor.execute("DELETE FROM users.users WHERE user_id = %s", [user_id])
            cursor.execute("DELETE FROM reports.community_reports WHERE user_id = %s", [user_id])
            cursor.execute("DELETE FROM surveys.survey_responses WHERE user_id = %s", [user_id])
            
            # Delete GPS photos from object storage
            photo_keys = Photo.objects.filter(user_id=user_id).values_list('photo_key', flat=True)
            for photo_key in photo_keys:
                delete_photo_from_storage(photo_key)
            
            # Log deletion in audit trail
            cursor.execute("""
                INSERT INTO audit.gdpr_deletion_log (
                    user_id, deletion_timestamp, initiator_ip, reports_deleted, photos_deleted
                ) VALUES (%s, NOW(), %s, %s, %s)
            """, [user_id, request.META.get('REMOTE_ADDR'), report_count, len(photo_keys)])
        
        return Response({
            'status': 'complete_deletion',
            'message': f'User {user_id} and all associated data deleted'
        }, status=status.HTTP_204_NO_CONTENT)
