# ADR-002: Use EncryptedSharedPreferences for Alarm State

Date: 2025-10-30

## Status
Accepted

## Context

AlarmScheduler needs to persist the next scheduled alarm time to handle system events (boot, time changes). This data must be:
- Quickly accessible (boot receiver has limited time)
- Persistent across app restarts and reboots
- Protected from tampering (user shouldn't modify alarm state)
- Small in size (only a few key-value pairs)

Storage options available:
1. **SharedPreferences** - Simple key-value storage, plaintext
2. **EncryptedSharedPreferences** - Encrypted key-value storage (Jetpack Security)
3. **Room Database** - Structured database, requires more setup
4. **DataStore** - Modern preference storage, async-first
5. **File storage** - Custom file-based persistence

## Decision

We will use **EncryptedSharedPreferences** from Jetpack Security for storing alarm-related state.

**Stored data:**
- `next_alarm_time`: Timestamp of next scheduled alarm
- `last_trigger_time`: Timestamp of last alarm trigger
- `alarm_request_code`: PendingIntent request code
- `last_backup_timestamp`: Timestamp of last Drive backup

**Implementation:**
```kotlin
class EncryptedPrefsManager(context: Context) {
    private val masterKey = MasterKey.Builder(context)
        .setKeyScheme(MasterKey.KeyScheme.AES256_GCM)
        .build()

    private val encryptedPrefs = EncryptedSharedPreferences.create(
        context,
        "stepdown_secure_prefs",
        masterKey,
        EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
        EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
    )

    fun saveNextAlarmTime(timestamp: Long) {
        encryptedPrefs.edit()
            .putLong("next_alarm_time", timestamp)
            .apply()
    }

    fun getNextAlarmTime(): Long {
        return encryptedPrefs.getLong("next_alarm_time", 0L)
    }
}
```

## Consequences

### Positive
1. **Security**: Data is encrypted at rest, prevents casual tampering
2. **Fast access**: Key-value access is instant, suitable for broadcast receivers
3. **Familiar API**: Same interface as SharedPreferences
4. **Small footprint**: No database overhead for simple data
5. **Android backup compatible**: Can be included in Auto Backup
6. **Jetpack supported**: Official library with ongoing maintenance

### Negative
1. **Limited query capability**: Can't query or index data
2. **Not for large data**: Inappropriate for event log (use Room for that)
3. **Synchronous I/O**: Blocks calling thread (mitigated by small data size)
4. **Key store dependency**: Requires Android Keystore (API 23+, we target 26+)
5. **Recovery complexity**: If keystore is wiped, data is lost

### Risks
1. **Keystore corruption**: Rare but possible, keystore can be reset
   - *Mitigation*: Detect corruption, delete prefs file, reschedule alarm from current time
   - *Impact*: User misses one alarm cycle, app recovers automatically

2. **Performance in tight loops**: Synchronous I/O in receiver
   - *Mitigation*: Only access once per alarm cycle, ~1ms overhead
   - *Acceptable*: Well within 10-second receiver limit

3. **Backup/restore challenges**: Encrypted data can't be restored across devices
   - *Mitigation*: Don't include in Auto Backup manifest
   - *Approach*: Treat as ephemeral, reschedule alarm on fresh install

## Alternatives Considered

### Alternative 1: Plain SharedPreferences
**Pros:**
- Simpler, no encryption overhead
- Slightly faster (no encryption)
- No keystore dependency

**Cons:**
- User can modify with root/ADB
- Not secure against tampering
- Doesn't follow security best practices

**Verdict:** Rejected due to lack of tamper protection

### Alternative 2: Room Database
**Pros:**
- More structured storage
- Can query and index
- Good for complex data

**Cons:**
- Overkill for 3-4 key-value pairs
- Slower initialization in receiver
- Requires async access (coroutines)
- More complex setup

**Verdict:** Rejected due to unnecessary complexity for simple data

### Alternative 3: Jetpack DataStore
**Pros:**
- Modern async API
- Type-safe with Proto DataStore
- Better for complex preferences

**Cons:**
- Async-first design incompatible with boot receiver
- Must use runBlocking() in receiver (anti-pattern)
- Slower than EncryptedSharedPreferences for simple use case
- More complexity for marginal benefit

**Verdict:** Rejected due to async requirement

### Alternative 4: Custom encrypted file
**Pros:**
- Full control over encryption
- Can optimize for specific use case

**Cons:**
- Reinventing the wheel
- Must handle encryption correctly (easy to get wrong)
- More code to maintain
- No advantage over EncryptedSharedPreferences

**Verdict:** Rejected due to unnecessary complexity

## Data Separation Strategy

**EncryptedSharedPreferences** (this ADR):
- Alarm state (next trigger time, last trigger)
- Backup timestamps
- Security-sensitive configuration

**Plain SharedPreferences** (separate file):
- User settings (theme, tone pack)
- Start allowance
- Days elapsed
- Non-sensitive configuration

**Room Database** (see ADR-005):
- Event log (all TRIGGER, SKIP, SNOOZE, LOG events)
- Historical data for export/backup

This separation ensures:
- Right tool for right data
- Fast boot receiver access (EncryptedSharedPreferences)
- Fast settings access (SharedPreferences)
- Complex queries for events (Room)
