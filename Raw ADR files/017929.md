# 7. Use localStorage for Todo Persistence

**Status:** Accepted

## Context

The todo application needs to persist user data so that todos survive page refreshes. Without persistence, users lose all their todos when they close or refresh the browser tab, which is unacceptable for a real todo application.

We need a client-side storage mechanism that:
- Persists data across browser sessions
- Is simple to implement and maintain
- Has adequate storage capacity for todo lists
- Works reliably across modern browsers
- Doesn't require server infrastructure

### Available Options

1. **localStorage**
   - Simple synchronous API
   - 5-10MB storage limit
   - Excellent browser support (all modern browsers)
   - String-only storage (requires JSON serialization)
   - Synchronous operations

2. **IndexedDB**
   - Asynchronous API (non-blocking)
   - Much larger storage capacity (50MB+)
   - Supports complex queries and indexes
   - More complex API, typically requires wrapper library
   - Better for large datasets

3. **sessionStorage**
   - Same API as localStorage
   - Only persists for current session (lost on tab close)
   - Not suitable for persistent todo storage

4. **Cache API / Service Workers**
   - Designed for caching HTTP responses
   - Requires service worker setup
   - Overkill for simple data persistence

## Decision

We will use **localStorage** for persisting todo data.

### Implementation Details

- **Storage key**: `storm-supply-todos`
- **Data format**: JSON array of todo objects
- **Save strategy**: Auto-save after every todo operation (add/toggle/delete)
- **Load strategy**: Load on store initialization
- **Error handling**: Gracefully handle parse errors and quota exceeded errors

### Storage Structure

```javascript
localStorage.setItem('storm-supply-todos', JSON.stringify([
  { id: 1, text: 'Example todo', completed: false },
  { id: 2, text: 'Another todo', completed: true }
]))
```

## Consequences

### Positive

- **Simple implementation**: Straightforward API, no external dependencies
- **Adequate capacity**: 5-10MB is far more than needed for todo lists (thousands of todos)
- **Synchronous**: Acceptable for small datasets, no async complexity
- **Universal support**: Works in all modern browsers
- **No server required**: Purely client-side solution
- **Instant saves**: Synchronous writes ensure data is saved immediately

### Negative

- **Browser-specific**: Data doesn't sync across devices or browsers
- **Limited capacity**: 5-10MB limit (not an issue for todos, but worth noting)
- **Synchronous blocking**: Can block UI thread (not noticeable with small data)
- **String-only storage**: Requires JSON serialization/deserialization
- **No encryption**: Data stored in plain text (not sensitive for todos)
- **User can clear**: Users can clear browser data and lose todos

### Mitigations

- **Size limit**: Monitor and warn if approaching storage limits
- **Parse errors**: Wrap all localStorage access in try-catch blocks
- **Quota exceeded**: Handle gracefully with user notification
- **Data loss**: Document that data is local-only, consider export feature in future
- **Migration path**: If we need IndexedDB later, we can migrate localStorage data

### Future Considerations

If the application grows to need:
- Cross-device synchronization → Add server-side storage
- Offline-first PWA → Migrate to IndexedDB + Service Workers
- Large datasets → Migrate to IndexedDB
- Encrypted storage → Add encryption layer or use encrypted storage API

## Alternatives Considered

**IndexedDB**: Rejected because it's unnecessarily complex for this use case. The async API and need for wrapper libraries (like Dexie.js) add complexity without meaningful benefit for a simple todo list.

**Server-side storage**: Not considered as this is a client-side-only application exercise. Could be added later if cross-device sync is needed.
