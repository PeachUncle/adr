# ADR-002: Three Deployment Modes Architecture

**Status**: Accepted

**Date**: 2024-11-15

**Decision Makers**: Architecture Team, Product Team

---

## Context

OpenAuction IQ serves diverse customer segments with varying requirements for **data sovereignty**, **privacy**, **operational complexity**, and **cost**. Different organizations have different needs:

1. **Small to medium publishers** want a **low-friction SaaS solution** with minimal operational overhead
2. **Large enterprises** require **data sovereignty** and **control over their ML infrastructure**
3. **Industry consortiums** need **collaborative learning** while preserving **competitive privacy** (can't share raw auction data with competitors)

A single deployment model cannot satisfy all these requirements. We needed to decide: **How many deployment modes should we support?**

Key constraints:
- **Code sharing**: All modes should share the same core codebase
- **Feature parity**: All modes should support the same ML capabilities
- **Privacy**: Some customers cannot share raw data (regulatory, competitive)
- **Operational simplicity**: Some customers want zero infrastructure management
- **Cost efficiency**: Different price/performance trade-offs for different scales

---

## Decision

We have chosen to support **three distinct deployment modes**:

### 1. CloudX Central (Multi-Tenant SaaS)

**Architecture**: Centralized multi-tenant deployment on CloudX infrastructure

**Characteristics**:
- Shared infrastructure across all customers
- Centralized model training with aggregated data
- Managed service (zero operational overhead for customers)
- Fastest model improvements (benefits from all customer data)
- Lowest per-customer cost

**Target Audience**: Small to medium publishers, quick evaluations

### 2. Single-User (Self-Hosted)

**Architecture**: Single-tenant deployment on customer infrastructure (Docker/Kubernetes)

**Characteristics**:
- Full data sovereignty (data never leaves customer infrastructure)
- Isolated model training per customer
- Customer-managed infrastructure
- Customizable deployment (on-prem, private cloud, VPC)
- Higher operational overhead

**Target Audience**: Large enterprises, regulated industries, high data sensitivity

### 3. Federated (Collaborative Privacy-Preserving)

**Architecture**: Multi-organization collaborative learning with privacy guarantees

**Characteristics**:
- Distributed training across multiple organizations
- No raw data sharing (only encrypted gradient updates)
- Differential privacy guarantees (ε, δ)-DP
- Secure aggregation (additive secret sharing)
- Benefits from collaborative learning without exposing sensitive data

**Target Audience**: Industry consortiums, competitors who want to collaborate, privacy-conscious organizations

---

## Consequences

### Positive

1. **Market Coverage**:
   - Addresses all customer segments (SMB → Enterprise → Consortiums)
   - No customer excluded due to deployment constraints
   - Can serve both cost-sensitive and privacy-sensitive customers

2. **Privacy Spectrum**:
   - CloudX Central: Maximum data sharing, fastest improvements
   - Single-User: Full data isolation, complete control
   - Federated: Collaborative learning + privacy preservation
   - Customers can choose their privacy/performance trade-off

3. **Competitive Advantage**:
   - Few ML platforms offer federated learning for ad tech
   - Privacy-preserving collaboration is unique differentiator
   - Can serve regulated industries (finance, healthcare) who can't use SaaS

4. **Code Reuse**:
   - Shared core codebase (90%+ code reuse)
   - Same ML models and algorithms across all modes
   - Consistent API and CLI across deployments
   - Reduces maintenance burden vs. separate products

5. **Revenue Model Flexibility**:
   - SaaS pricing for CloudX Central
   - Enterprise licensing for Single-User
   - Consortium pricing for Federated
   - Can optimize pricing per segment

### Negative

1. **Implementation Complexity**:
   - Must test all three deployment modes
   - Need separate CI/CD pipelines
   - Different security models per mode
   - Increased QA and testing burden

2. **Feature Development Overhead**:
   - Every new feature must work in all three modes
   - Need to consider federated constraints (no centralized data access)
   - Slower feature velocity vs. single-mode product

3. **Documentation & Support Burden**:
   - Need separate deployment guides for each mode
   - Different troubleshooting workflows
   - Higher support complexity (three different failure modes)
   - Customer confusion about which mode to choose

4. **Infrastructure Costs**:
   - CloudX Central requires multi-tenant architecture
   - Federated requires secure aggregation server infrastructure
   - Single-User requires packaging and distribution (Docker images, Helm charts)
   - Higher infrastructure maintenance costs

5. **Performance Variability**:
   - CloudX Central has best performance (most data)
   - Single-User has limited data (single organization)
   - Federated has communication overhead (slower training)
   - Need to set different performance expectations per mode

6. **Security Complexity**:
   - Different threat models per deployment
   - CloudX: Protect tenant isolation
   - Single-User: Protect customer infrastructure
   - Federated: Protect against malicious participants
   - Requires three separate security audits

## Alternatives Considered

### 1. Single Mode Only (CloudX Central SaaS)

**Pros**:
- ✅ Simplest implementation
- ✅ Fastest feature development
- ✅ Lowest maintenance cost
- ✅ Best model performance (centralized data)

**Cons**:
- ❌ **Excludes enterprise customers** (data sovereignty requirements)
- ❌ **Excludes regulated industries** (can't use SaaS for compliance)
- ❌ **No privacy-preserving collaboration** (competitors can't work together)
- ❌ **Smaller addressable market**

**Why Rejected**: Too limiting. Would exclude 40-50% of potential market (enterprises and regulated industries). Competitive disadvantage vs. self-hosted competitors.

---

### 2. Two Modes (CloudX Central + Single-User)

**Pros**:
- ✅ Covers most market segments
- ✅ Simpler than three modes
- ✅ Lower complexity than three modes
- ✅ Addresses data sovereignty concerns

**Cons**:
- ❌ **No collaborative learning** for competitors
- ❌ **Misses federated learning opportunity** (unique differentiator)
- ❌ **Single-User customers don't benefit from others' data**
- ❌ **Still 80% of three-mode complexity** (testing, docs, support)

**Why Rejected**: Marginal complexity savings (80% of three-mode cost) but misses significant market opportunity (industry consortiums, collaborative learning). Federated mode is key differentiator and only adds 20% incremental complexity.

---

### 3. Four+ Modes (Add Hybrid or Edge Modes)

**Pros**:
- ✅ Even more market coverage
- ✅ Could support edge deployments (CDN-hosted models)
- ✅ Hybrid mode (partial data sharing)

**Cons**:
- ❌ **Complexity explosion**: Testing, docs, support overhead
- ❌ **Marginal market value**: Diminishing returns per mode
- ❌ **Code fragmentation risk**: Hard to maintain feature parity
- ❌ **Customer confusion**: Too many choices

**Why Rejected**: Three modes are sufficient for 95%+ of market. Additional modes would add 50%+ complexity for <5% market coverage. Not worth the cost.

---

### 4. Unified Mode with Configuration Flags

**Pros**:
- ✅ Single codebase
- ✅ Customers can switch modes easily
- ✅ Less documentation burden

**Cons**:
- ❌ **Security risk**: Misconfiguration could leak data
- ❌ **Testing complexity**: Exponential combinations of flags
- ❌ **Performance overhead**: Need to support all modes in single binary
- ❌ **Unclear boundaries**: Hard to reason about deployment

**Why Rejected**: Security and testing complexity too high. Clear mode separation is safer and easier to reason about. Configuration flags make sense within a mode, not across modes.

## Deployment Mode Comparison

| Criterion | CloudX Central | Single-User | Federated |
|-----------|---------------|-------------|-----------|
| **Data Location** | CloudX (centralized) | Customer infrastructure | Distributed (each org) |
| **Privacy** | 🔴 Shared data | ✅ Full isolation | ✅ (ε,δ)-DP guarantees |
| **Model Performance** | ✅ Best (most data) | 🟡 Limited (single org) | 🟡 Good (collaborative) |
| **Operational Overhead** | ✅ Zero (managed) | 🔴 High (self-managed) | 🟡 Medium (managed server) |
| **Training Speed** | ✅ Fast (centralized) | ✅ Fast (local) | 🔴 Slow (communication) |
| **Infrastructure Cost** | ✅ Low (shared) | 🔴 High (dedicated) | 🟡 Medium (shared server) |
| **Data Sovereignty** | ❌ No | ✅ Full control | ✅ Local control |
| **Collaborative Learning** | ✅ Implicit (centralized) | ❌ No | ✅ Explicit (federated) |
| **Scalability** | ✅ Unlimited (cloud) | 🟡 Limited (customer infra) | 🟡 Medium (network bound) |
| **Compliance Friendly** | 🔴 Limited | ✅ Yes | ✅ Yes |

**Legend**: ✅ Excellent | 🟡 Acceptable | 🔴 Poor

## Use Case Mapping

### CloudX Central
- **Small publishers** (< 10M auctions/month)
- **Startups** evaluating ad tech ML
- **Quick POCs** and trials
- **Cost-sensitive** customers

### Single-User
- **Large publishers** (> 100M auctions/month)
- **Regulated industries** (finance, healthcare)
- **Data-sensitive** organizations (government, defense)
- **Custom infrastructure** requirements (on-prem, air-gapped)

### Federated
- **Industry consortiums** (e.g., multiple publishers forming alliance)
- **Competitors collaborating** (improve industry benchmarks without sharing data)
- **Privacy-first organizations** (want collaboration but can't share raw data)
- **Research institutions** (academic collaboration)

## Implementation Strategy

### Code Sharing (90%+)

**Shared Components**:
- Core ML models (PPO agent, neural networks)
- Training algorithms (RL, supervised learning)
- Data preprocessing and feature engineering
- API server and CLI
- Metrics and monitoring

**Mode-Specific Components** (10%):
- CloudX: Multi-tenancy isolation, tenant routing
- Single-User: Single-tenant configuration, local storage
- Federated: Gradient aggregation, secure aggregation, DP-SGD

### Deployment Separation

**Separate Artifacts**:
- `openauction-iq-cloudx` - CloudX multi-tenant image
- `openauction-iq-single` - Single-user Docker Compose / Helm chart
- `openauction-iq-federated-server` - Federated aggregation server
- `openauction-iq-federated-client` - Federated client node

**Shared Base Image**: All artifacts built from same base image with mode-specific entry points.

### Configuration Approach

**Mode Selection**: Environment variable `OPENAUCTION_IQ_MODE`
- `cloudx` - Multi-tenant SaaS mode
- `single` - Single-user self-hosted mode
- `federated-server` - Federated aggregation server
- `federated-client` - Federated client node

**Mode-Specific Config**: Separate config files per mode with validation at startup.

---

## Future Considerations

1. **Hybrid Mode**: Partial data sharing with differential privacy (e.g., share aggregated statistics but not raw auctions)
2. **Edge Mode**: Deploy models at CDN edge for ultra-low latency predictions
3. **Mobile Mode**: On-device training for mobile apps (federated learning on phones)
4. **Cross-Mode Migration**: Tools to migrate customers between modes (e.g., CloudX → Single-User for graduating startups)

---

## Monitoring and Success Metrics

**Per-Mode Metrics**:
- CloudX: Tenant count, multi-tenant model performance, tenant isolation incidents
- Single-User: Active deployments, customer infrastructure diversity, support ticket rate
- Federated: Active consortiums, gradient aggregation latency, privacy budget consumption

**Shared Metrics**:
- Model accuracy across all modes (should be within 5%)
- Feature parity (100% features available in all modes)
- Code reuse percentage (target: >90%)

**Alerts**:
- Feature parity drops below 95% → Flag for immediate fix
- Single-User support tickets > 2× CloudX → Documentation gap
- Federated training 3× slower than CloudX → Communication optimization needed
