# ADR-001: Hybrid Logical Clocks over TrueTime

**Status**: Accepted  
**Date**: 2025-10-31  
**Deciders**: Core Team

## Context

Distributed transactions require globally ordered timestamps to ensure consistency. Google Spanner uses TrueTime, which requires specialized hardware (GPS + atomic clocks). We need an alternative for open-source deployments.

## Decision

Use **Hybrid Logical Clocks (HLC)** instead of TrueTime.

## Rationale

### HLC Advantages
- **No special hardware**: Works with standard NTP
- **Open source friendly**: No proprietary requirements
- **Sufficient ordering**: Provides happened-before relationships
- **Clock drift tolerant**: Uses logical counters when physical time doesn't advance

### HLC Format
```rust
struct Timestamp {
    physical: u64,    // Wall clock milliseconds
    logical: u64,     // Logical counter
    node_id: u64,     // Node identifier (tie-breaker)
}
```

### Ordering Rules
1. Compare `physical` first
2. If equal, compare `logical`
3. If still equal, compare `node_id`

### Update Algorithm
```rust
fn update(received_ts: Timestamp) -> Timestamp {
    let wall_time = current_wall_time();
    let max_physical = max(wall_time, last_physical, received.physical);
    
    let logical = if max_physical > last_physical {
        0  // Physical time advanced, reset logical
    } else {
        last_logical + 1  // Same physical time, increment logical
    };
    
    Timestamp { physical: max_physical, logical, node_id: self.node_id }
}
```

## Consequences

### Positive
- ✅ No specialized hardware required
- ✅ Can deploy anywhere (cloud, on-prem, edge)
- ✅ Lower operational complexity
- ✅ Battle-tested in CockroachDB, YugabyteDB

### Negative
- ❌ No strict upper bound on clock drift (unlike TrueTime's ±7ms)
- ❌ May need to retry transactions on large clock skew
- ❌ Requires NTP for physical clock synchronization

### Mitigations
- Monitor clock drift across nodes
- Reject timestamps with excessive drift (e.g., >250ms)
- Use commit wait if strong consistency is critical (Phase 3+)

## Alternatives Considered

### 1. TrueTime (Rejected)
- **Pros**: Strict uncertainty bounds, proven at scale
- **Cons**: Requires GPS/atomic clocks, not open-source friendly

### 2. Lamport Timestamps (Rejected)
- **Pros**: No physical clocks needed
- **Cons**: Unbounded logical counters, no real-time ordering

### 3. Vector Clocks (Rejected)
- **Pros**: Full causality tracking
- **Cons**: Storage overhead (O(nodes)), not suitable for large clusters
