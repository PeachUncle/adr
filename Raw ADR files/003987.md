# ADR-001: Use setExactAndAllowWhileIdle() for Daily Alarms

Date: 2025-10-30

## Status
Accepted

## Context

StepDown requires daily notifications at a consistent time (5-6 PM) to remind users of their smoking schedule. Android provides several alarm scheduling mechanisms:

1. **AlarmManager.setRepeating()**: Inexact alarms, batched with others for battery efficiency
2. **AlarmManager.setExact()**: Exact alarms, but can be delayed by Doze mode
3. **AlarmManager.setExactAndAllowWhileIdle()**: Exact alarms that fire even in Doze mode
4. **WorkManager**: Job scheduling for deferrable background work
5. **Foreground Service**: Keeps process alive for continuous work

**Requirements:**
- Alarm must fire daily between 5-6 PM (exact window)
- Must work reliably even when device is idle (Doze mode)
- Must survive device reboots
- Must handle time/timezone changes
- No foreground service allowed (user experience and battery concerns)

**Constraints:**
- Target API 26-35 (Android 8.0 - 12.0)
- Battery efficiency is important but secondary to reliability
- User expects daily reminder at consistent time

## Decision

We will use **AlarmManager.setExactAndAllowWhileIdle()** for scheduling daily notifications.

**Implementation details:**
```kotlin
fun scheduleExactAlarm(triggerAtMillis: Long) {
    val intent = Intent(context, AlarmReceiver::class.java).apply {
        action = ACTION_DAILY_TRIGGER
    }

    val pendingIntent = PendingIntent.getBroadcast(
        context,
        ALARM_REQUEST_CODE,
        intent,
        PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
    )

    alarmManager.setExactAndAllowWhileIdle(
        AlarmManager.RTC_WAKEUP,
        triggerAtMillis,
        pendingIntent
    )
}
```

**Alarm time calculation:**
- Random time between 5:00 PM and 6:00 PM each day
- Prevents user from gaming the system by checking at a predictable time
- Provides 1-hour window for system to fire alarm reliably

**Persistence strategy:**
- Store next scheduled time in EncryptedSharedPreferences
- Re-schedule on BOOT_COMPLETED, TIME_CHANGED, TIMEZONE_CHANGED
- Each alarm trigger schedules the next day's alarm

## Consequences

### Positive
1. **Reliability**: Alarm fires even when device is in Doze mode
2. **Consistency**: User receives notification at predictable time daily
3. **Simplicity**: No need for foreground service or WorkManager complexity
4. **Battery conscious**: One alarm per day is acceptable battery impact
5. **System integration**: Leverages Android's built-in alarm infrastructure

### Negative
1. **Per-alarm scheduling**: Must re-schedule after each alarm (not a repeating alarm)
2. **API 26+ limitation**: Requires explicit user permission on API 31+ (SCHEDULE_EXACT_ALARM)
3. **System can defer**: In extreme battery saver, system may still defer the alarm
4. **Single shot**: If alarm is missed, it won't retry until next reboot/reschedule
5. **Wake lock required**: Uses RTC_WAKEUP which wakes device from sleep

### Risks
1. **Permission denial**: On API 31+, users can revoke SCHEDULE_EXACT_ALARM permission
   - *Mitigation*: Check permission before scheduling, show rationale to user
   - *Fallback*: Use setAndAllowWhileIdle() as inexact backup

2. **Alarm missed during battery saver**: Extreme battery saver can suppress alarms
   - *Mitigation*: Document behavior to user, alarm will fire on next wake/charge
   - *Acceptable*: User consciously chose battery over functionality

3. **Receiver time limit**: BroadcastReceiver has 10-second execution limit
   - *Mitigation*: Keep receiver logic minimal, delegate to WorkManager if needed
   - *Current approach*: Log event to Room (~50ms), schedule next alarm (~10ms), show notification (~20ms)

4. **Clock manipulation**: User changing system time could skip alarms
   - *Mitigation*: Listen for TIME_CHANGED and TIMEZONE_CHANGED broadcasts
   - *Re-schedule*: Recalculate next alarm based on new time

## Alternatives Considered

### Alternative 1: WorkManager with PeriodicWorkRequest
**Pros:**
- Handles reboots automatically
- Better battery optimization
- Guaranteed execution (eventually)

**Cons:**
- Cannot guarantee exact time (flex period is minimum 15 minutes)
- Jobs can be deferred significantly by JobScheduler
- Over-engineered for simple daily notification
- Less predictable for user experience

**Verdict:** Rejected due to inexact timing

### Alternative 2: Foreground Service
**Pros:**
- Complete control over timing
- Can maintain internal clock
- Never killed by system

**Cons:**
- Persistent notification annoys users
- Terrible battery impact
- Explicitly forbidden by product requirements
- Violates Android best practices for this use case

**Verdict:** Rejected due to battery and UX concerns

### Alternative 3: AlarmManager.setRepeating()
**Pros:**
- Simpler API (repeating automatically)
- Better battery efficiency (batched alarms)

**Cons:**
- Inexact timing (can drift by 30+ minutes)
- Not reliable for specific time window requirement
- Still requires manual rescheduling on boot

**Verdict:** Rejected due to unreliable timing

### Alternative 4: Cloud-based push notifications
**Pros:**
- Offloads scheduling to server
- Works across devices

**Cons:**
- Requires server infrastructure (cost, maintenance)
- Requires internet connection
- Violates privacy-first requirement
- Over-engineered for local-only feature

**Verdict:** Rejected due to privacy and complexity
