# ADR-001: Cross-Project AlloyDB Connectivity Strategy

## Status
Proposed

## Date
2025-10-27

## Context

We need to establish connectivity from a Flask application running on Cloud Run in **Project B** to an AlloyDB database with Private Service Access (PSA) in **Project A**.

### Current State
- **Project A** (Production): AlloyDB cluster with Private Service Access already configured and running in production
- **Project B**: Cloud Run services that need read/write access to the AlloyDB database
- **Constraint**: Cannot modify Project A's networking or recreate AlloyDB (no downtime acceptable)

### Problem Statement
AlloyDB uses Private Service Access, which creates a VPC peering connection to a Google-managed VPC. When we attempt to connect Cloud Run from Project B:

```
Cloud Run (Project B) →
VPC Connector (Project B) →
Project B VPC →
[VPC Peering to Project A] →
Project A VPC →
[CANNOT traverse to Google-managed VPC] ❌ →
AlloyDB (Google-managed VPC)
```

**Root cause**: GCP does not support transitive VPC peering. Traffic cannot traverse multiple peering connections.

### Options Available

1. **Direct VPC Peering** (Current attempt - Failed)
2. **Shared VPC**
3. **Private Service Connect (PSC)**
4. **AlloyDB Auth Proxy**
5. **TCP Proxy VM (Jump Host)**

## Decision

We will use a **TCP Proxy VM in Project A** as a forwarding layer to enable Cloud Run in Project B to access AlloyDB in Project A.

## Rationale

### Why NOT Other Options

#### 1. Direct VPC Peering (Attempted)
```
Status: ❌ FAILED
```

**What we tried:**
- Created VPC peering between Project A and Project B VPCs
- Enabled "Export custom routes" on Project A
- Enabled "Import custom routes" on Project B
- Verified peering status shows "Active" on both sides

**Why it failed:**
- VPC peering does not support transitive routing
- AlloyDB's Private Service Access creates a peering to a Google-managed VPC
- Traffic from Project B → Project A → Google-managed VPC is blocked
- Even with custom route export/import, the Google-managed VPC routes are not propagated

**Technical limitation:**
```
Project B VPC (peering 1) ↔ Project A VPC (peering 2) ↔ Google-managed VPC
                          [Cannot traverse both peerings]
```

#### 2. Shared VPC
```
Status: ❌ REJECTED - Requires downtime
```

**Why rejected:**
- Would require migrating AlloyDB to a Shared VPC network
- Migration requires AlloyDB instance recreation
- Unacceptable downtime for production database
- Complex organizational setup (host project, service projects)
- May not align with current project structure/permissions

#### 3. Private Service Connect (PSC)
```
Status: ❌ REJECTED - Requires AlloyDB recreation
```

**Why rejected:**
- AlloyDB currently uses Private Service Access (PSA), not PSC
- Switching from PSA to PSC requires recreating the AlloyDB instance
- No in-place migration path available
- Unacceptable downtime for production database

#### 4. AlloyDB Auth Proxy
```
Status: ❌ REJECTED - Changes authentication model
```

**Why rejected:**
- Forces IAM-based database authentication instead of traditional database users
- Requires managing database permissions through IAM instead of SQL GRANT statements
- Breaking change to existing database user management
- Example impact:
  ```sql
  -- Current approach (traditional DB users)
  CREATE USER app_user WITH PASSWORD 'secure_password';
  GRANT SELECT, INSERT ON table TO app_user;

  -- Auth Proxy approach (IAM users)
  GRANT SELECT, INSERT ON table TO "serviceaccount@project.iam";
  -- Loses granular user management
  ```
- Team preference for traditional PostgreSQL user management
- Would require refactoring existing authentication logic

### Why TCP Proxy VM (Selected)

#### Advantages

✅ **Zero downtime** - No changes to AlloyDB or Project A networking
✅ **Preserves authentication model** - Traditional PostgreSQL users continue to work
✅ **Simple and reliable** - Well-understood technology (HAProxy, nginx stream, or socat)
✅ **Transparent to applications** - Flask app connects as if it's a normal PostgreSQL server
✅ **No VPC migration** - Works with existing Private Service Access setup
✅ **Network isolation maintained** - Proxy controls which services can access AlloyDB
✅ **Easy to monitor** - Standard proxy metrics and health checks

#### How it works

```
Cloud Run (Project B) →
VPC Connector (Project B) →
Project B VPC →
[VPC Peering] →
Project A VPC →
Proxy VM (has PSA routes) ✓ →
AlloyDB (Google-managed VPC) ✓
```

**Key insight:** The Proxy VM lives inside Project A's VPC, so it has access to the Private Service Access routes that lead to the Google-managed VPC where AlloyDB resides.

## Consequences

### Positive
✅ Minimal infrastructure changes - only adds one VM
✅ No production downtime or disruption
✅ Maintains existing database authentication model
✅ Easy to understand and troubleshoot
✅ Can be deployed and tested independently
✅ Proxy can be hardened and monitored separately
✅ Firewall rules provide additional security layer

### Negative
❌ Introduces a single point of failure (SPOF)
❌ Small latency overhead (~1-5ms depending on region)
❌ Additional infrastructure component to maintain
❌ Proxy VM has operating system patching requirements
❌ Not a "serverless" solution (though VM can be small)

### Mitigation Strategies

1. **High Availability**
   - Use Managed Instance Group (MIG) with autoscaling (min 2 instances)
   - Regional distribution for better fault tolerance
   - Health checks for automatic failover
   - Example configuration:
     ```hcl
     resource "google_compute_region_instance_group_manager" "proxy" {
       base_instance_name = "alloydb-proxy"
       region             = var.region
       target_size        = 2

       named_port {
         name = "postgres"
         port = 5432
       }

       auto_healing_policies {
         health_check      = google_compute_health_check.postgres.id
         initial_delay_sec = 300
       }
     }
     ```

2. **Monitoring and Alerting**
   - Prometheus metrics on proxy throughput, latency, error rates
   - Cloud Monitoring alerts on VM health
   - Connection pool monitoring
   - Example alerts:
     - Proxy VM CPU > 80% for 5 minutes
     - Connection failures > 1% error rate
     - Proxy process down

3. **Performance Optimization**
   - Use same region as AlloyDB to minimize latency
   - Right-size VM based on connection count (start with e2-small)
   - Connection pooling if needed (though likely handled by application)
   - Regional Internal Load Balancer for distribution

4. **Security Hardening**
   - Minimal OS (Container-Optimized OS or minimal Debian)
   - Firewall rules limiting source IPs to Project B VPC CIDR
   - VPC Service Controls for additional boundary
   - Automated OS patching with COS or apt-unattended-upgrades

## Alternative Patterns Considered

### 1. SSH Tunnel
```bash
# From Cloud Run
ssh -L 5432:alloydb-ip:5432 jump-host
```
**Rejected because:**
- SSH key management complexity
- Not designed for high-throughput database traffic
- Connection stability issues
- Not transparent to applications

### 2. Cloud VPN
```
Project B VPC ↔ [Cloud VPN] ↔ Project A VPC
```
**Rejected because:**
- Still has transitive peering problem
- More complex than proxy VM
- Higher cost
- Doesn't solve the fundamental routing issue

### 3. Interconnect
```
Project B ↔ [Dedicated Interconnect] ↔ Project A
```
**Rejected because:**
- Massive overkill for single database connection
- High cost ($100s/month minimum)
- Long setup time
- Still doesn't solve transitive peering

## Implementation Example

### Proxy VM Setup (HAProxy)

**Terraform configuration:**
```hcl
resource "google_compute_instance" "alloydb_proxy" {
  project      = var.project_a_id
  name         = "alloydb-proxy"
  machine_type = "e2-small"
  zone         = "us-central1-a"

  boot_disk {
    initialize_params {
      image = "debian-cloud/debian-11"
    }
  }

  network_interface {
    network    = google_compute_network.project_a_vpc.id
    subnetwork = google_compute_subnetwork.project_a_subnet.id
    # No external IP - internal only
  }

  metadata_startup_script = <<-EOF
    #!/bin/bash
    apt-get update
    apt-get install -y haproxy

    cat > /etc/haproxy/haproxy.cfg <<'HAPROXY'
    global
        log /dev/log local0
        maxconn 1000

    defaults
        mode tcp
        timeout connect 5s
        timeout client  50s
        timeout server  50s
        log global

    frontend postgres_frontend
        bind *:5432
        default_backend alloydb_backend

    backend alloydb_backend
        server alloydb ${var.alloydb_private_ip}:5432 check
    HAPROXY

    systemctl enable haproxy
    systemctl restart haproxy
  EOF

  tags = ["alloydb-proxy"]
}

# Firewall rule allowing Project B to access proxy
resource "google_compute_firewall" "allow_project_b_to_proxy" {
  project = var.project_a_id
  name    = "allow-project-b-to-alloydb-proxy"
  network = google_compute_network.project_a_vpc.id

  allow {
    protocol = "tcp"
    ports    = ["5432"]
  }

  source_ranges = [var.project_b_vpc_cidr]  # e.g., "10.2.0.0/20"
  target_tags   = ["alloydb-proxy"]
}
```

### Alternative: Using nginx stream

**nginx.conf:**
```nginx
stream {
    upstream alloydb {
        server ALLOYDB_PRIVATE_IP:5432;
    }

    server {
        listen 5432;
        proxy_pass alloydb;
        proxy_connect_timeout 5s;
    }
}
```

### Alternative: Using socat (Lightest)

```bash
socat TCP-LISTEN:5432,fork TCP:ALLOYDB_PRIVATE_IP:5432
```

### Flask Application Configuration

**Project B - Cloud Run:**
```python
# No changes needed to application code
# Just point to proxy VM IP instead of AlloyDB IP

import psycopg2

conn = psycopg2.connect(
    host=os.getenv('DB_HOST'),  # Set to proxy VM internal IP
    port=5432,
    database='mydb',
    user='app_user',
    password=os.getenv('DB_PASSWORD')
)
```

**Environment variable:**
```bash
# Instead of:
DB_HOST=10.0.0.5  # AlloyDB IP (unreachable)

# Use:
DB_HOST=10.1.0.10  # Proxy VM IP (reachable via peering)
```

## Validation Plan

To validate this approach before implementing in production, we will create a **minimal test environment** with two GCP projects.

### Test Environment Setup

**Project A (Test):**
- VPC with Private Service Access configured
- AlloyDB instance (smallest tier for testing)
- e2-micro VM with HAProxy forwarding to AlloyDB
- Firewall rule allowing Project B VPC CIDR

**Project B (Test):**
- VPC with VPC peering to Project A
- Serverless VPC Connector
- Cloud Run service with simple Python script
- Script performs: `SELECT 1` and writes a test row

### Success Criteria
1. ✅ Cloud Run in Project B can connect to proxy VM
2. ✅ Proxy VM successfully forwards to AlloyDB
3. ✅ Read operations work (SELECT queries)
4. ✅ Write operations work (INSERT/UPDATE queries)
5. ✅ Connection pooling works correctly
6. ✅ Latency overhead is acceptable (<10ms added)
7. ✅ Firewall rules properly restrict access

### Test Script

```python
# test-alloydb-connection.py (deployed to Cloud Run)
import psycopg2
import os
import time

def test_connection():
    try:
        start = time.time()
        conn = psycopg2.connect(
            host=os.getenv('PROXY_VM_IP'),
            port=5432,
            database='postgres',
            user='test_user',
            password=os.getenv('DB_PASSWORD')
        )
        connect_time = time.time() - start

        # Test read
        cur = conn.cursor()
        cur.execute('SELECT 1')
        result = cur.fetchone()

        # Test write
        cur.execute('''
            CREATE TABLE IF NOT EXISTS test_table (
                id SERIAL PRIMARY KEY,
                timestamp TIMESTAMP DEFAULT NOW()
            )
        ''')
        cur.execute('INSERT INTO test_table DEFAULT VALUES RETURNING id')
        insert_id = cur.fetchone()[0]
        conn.commit()

        print(f"✅ Connection successful")
        print(f"✅ Connect time: {connect_time*1000:.2f}ms")
        print(f"✅ Read test passed: {result}")
        print(f"✅ Write test passed: inserted id={insert_id}")

        cur.close()
        conn.close()
        return True

    except Exception as e:
        print(f"❌ Connection failed: {e}")
        return False

if __name__ == '__main__':
    test_connection()
```

## Future Considerations

### If Requirements Change

1. **Need for higher availability:**
   - Migrate to Shared VPC (if downtime window becomes available)
   - Use Regional Internal Load Balancer with MIG for proxy VMs

2. **Need for lower latency:**
   - Consider recreating AlloyDB with PSC when major version upgrade is needed
   - Optimize proxy VM placement (same zone as AlloyDB)

3. **Need for better scalability:**
   - Transition to Private Service Connect when performing planned maintenance
   - Use this as bridge solution until scheduled maintenance window

4. **Alternative: Wait for AlloyDB Auth Proxy improvements**
   - Google may release improvements to Auth Proxy allowing traditional DB users
   - Monitor AlloyDB release notes for authentication features

## Summary (TL;DR)

We need Cloud Run (Project B) to access AlloyDB (Project A). Direct VPC peering **failed due to transitive peering limitations** - traffic cannot traverse from Project B VPC → Project A VPC → Google-managed VPC where AlloyDB lives.

**Decision:** Deploy a small TCP proxy VM in Project A that forwards PostgreSQL traffic to AlloyDB.

**Why this works:**
- Proxy VM lives in Project A VPC and has Private Service Access routes to AlloyDB
- Simple, reliable, transparent to applications
- Zero downtime, no database recreation needed
- Preserves traditional PostgreSQL authentication

**Trade-offs:**
- Adds one infrastructure component (can be made HA with MIG)
- Small latency overhead (~1-5ms)
- Preferred over alternatives that require downtime or change authentication models
