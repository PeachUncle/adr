# ADR 003: Single-Table Design for DynamoDB

**Status:** Accepted

**Date:** 2025-01-15

## Context

We chose DynamoDB for our database (see ADR 001). Now we needed to decide on the schema design strategy:

**Options Considered:**
1. **Single-table design** (Multiple entities in one table)
2. **Multi-table design** (Separate tables per entity)
3. **Hybrid approach** (Primary table + specialized tables)

## Decision

**We chose Single-Table Design.**

## Rationale

### Single-Table Benefits

**1. Query Efficiency**
- All related data fetched in single request
- Example: Get user + all birthdays in one round-trip
- Reduces application complexity

**2. Transaction Support**
- DynamoDB transactions work best within a single table
- Easier to implement consistency guarantees
- Atomic updates across user + birthdays

**3. Flexible Access Patterns**
- Easy to add new access patterns via GSI
- Query by reminder date, by user, by birthday - all efficient
- No cross-table joins needed

**4. Cost Efficiency**
- No duplicate data across tables
- Fewer provisioned RCU/WCU allocations
- Better use of on-demand billing

**5. Portfolio Value**
- Demonstrates advanced DynamoDB design skills
- Shows understanding of NoSQL best practices
- Impresses interviewers with sophisticated data modeling

### Our Access Patterns

The single-table design efficiently supports:

1. **Get user profile**
   - Query: `PK = USER#{user_id}`, `SK = PROFILE`
   - Result: 1 item (user record)

2. **Get all birthdays for user**
   - Query: `PK = USER#{user_id}`, `SK begins_with BDAY#`
   - Result: All birthday records for that user

3. **Get reminder queue for today**
   - Query: `GSI1PK = REMIND#{today}`, `SK begins_with USER#`
   - Result: All users with reminders due today
   - Used by scheduled reminder Lambda

4. **Get single birthday**
   - Query: `PK = USER#{user_id}`, `SK = BDAY#{birthday_id}`
   - Result: Single birthday record

## Schema Design

### Primary Keys

```
Partition Key (PK): Scopes items to user or system
Sort Key (SK): Distinguishes entity type and ID
```

**Entities:**

```
USER#{user_id} / PROFILE
├─ email
├─ phone_number
├─ timezone
├─ notification_time
└─ timestamps

USER#{user_id} / BDAY#{birthday_id}
├─ name
├─ date (YYYY-MM-DD)
├─ birth_year
├─ remind_days_before
├─ notes
├─ GSI1PK (reminder date)
├─ GSI1SK (user_id)
└─ timestamps
```

### Global Secondary Index 1 (GSI1)

**Purpose:** Query reminders by date

```
Partition Key: GSI1PK = REMIND#{MM-DD}
Sort Key: GSI1SK = USER#{user_id}
```

**Why this design:**
- `REMIND#{MM-DD}` is the reminder date (always MM-DD, no year)
- Year-agnostic querying (birthday on 03-15 annually)
- EventBridge scheduled job queries today's reminder date

**Example:**
- Birthday: 1965-03-15, remind 7 days before
- Reminder date: 03-08 (MM-DD format)
- `GSI1PK = REMIND#03-08`
- `GSI1SK = USER#abc-123`
- Query all reminders due on 03-08 across all users

## Data Denormalization

### Acceptable Denormalization

Some data is stored in multiple places for efficiency:

```
Birthday entity contains:
- user_id (to scope query)
- GSI1PK/GSI1SK (for reminder queries)
- calculated age (convenience)
```

**Why OK:**
- Data is calculated (age), not independently maintained
- Would be needed anyway (age at notification time)
- No consistency risk

### Avoided Denormalization

We do NOT denormalize:
- User's phone number in birthday record
- User's timezone in birthday record
- User's notification time in birthday record

**Why:**
- Would need to update multiple records if user changes settings
- Risk of stale data
- Instead: birthday record stores only FK (user_id), lookup when needed

## Trade-offs

### Advantages
- ✅ Efficient queries (no joins)
- ✅ Transaction support within table
- ✅ Lower costs (less storage, fewer RCU)
- ✅ Demonstrates advanced data modeling
- ✅ Easy to add new access patterns via GSI
- ✅ Simpler application code (fewer queries)

### Disadvantages
- ❌ Schema design must be planned upfront
- ❌ Harder to modify schema later (no ALTER TABLE)
- ❌ Requires understanding of DynamoDB concepts
- ❌ Less normalized (some denormalization required)

## Why Not Multi-Table?

**Separate tables (one per entity type):**

```
Tables:
- users-table
- birthdays-table
```

**Disadvantages:**
- Query across tables requires multiple round-trips
- Getting user + birthdays = 2 queries
- Transactions across tables (not supported efficiently)
- More complex application code
- Higher cost (more provisioned capacity)

**When multi-table makes sense:**
- 100K+ items per entity type
- Different access patterns don't benefit from same table
- Team inexperienced with DynamoDB

## Why Not Hybrid?

**Hybrid approach (multiple tables with relationships):**

```
Tables:
- users-table (user profiles)
- birthdays-table (all birthdays across users)
```

**Disadvantages:**
- Loses the single-query benefits
- Requires careful consistency management
- More operational overhead
- Doesn't align with serverless paradigm

## Capacity Planning

### DynamoDB On-Demand Billing

Since we use on-demand billing, capacity isn't something we provision. However, understanding capacity helps with cost estimation:

**Expected usage (100 users):**
- 100 user profiles × 1 KB = 100 KB
- 500 birthdays × 0.5 KB = 250 KB
- **Total storage:** ~400 KB (well under free tier 25 GB)

**Requests:**
- Read heavy: 1000 API requests/month
- Write heavy: 10 reminder SMS notifications/day = 300/month
- **Estimated cost:** <$0.10/month

## Future Extensions

### Potential new access patterns:

**Query birthdays by name (global search)**
- Add GSI2: `PK = BDAY_NAME#{first_3_chars}`, `SK = BDAY_ID`
- Enables autocomplete functionality

**Query birthdays by month (upcoming birthdays)**
- Add GSI3: `PK = MONTH#{MM}`, `SK = USER#{user_id}`
- Enables "birthdays this month" dashboard

**Audit log (who updated what)**
- Add separate items: `USER#{user_id} / AUDIT#{timestamp}`
- Enables audit trail

## Migration Path

If we ever need to move away from single-table:

1. **To RDS:** Export items to CSV → import to PostgreSQL
2. **To another DynamoDB table:** Use AWS DMS or custom Lambda migration
3. **To Elasticsearch:** Stream items via DynamoDB Streams

The application abstraction (db.py module) makes this easier.
