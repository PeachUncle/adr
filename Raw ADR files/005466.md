## Context

ADR-011 established that all agents and services within the system will be containerized using Docker. This decision necessitates a platform for storing, deploying, and managing these containers in a scalable and reliable production environment. The chosen platform must align with our goals of minimizing operational overhead and maintaining cost-effectiveness.

## Decision

1.  We will use **Google Cloud Run** as the primary platform for deploying and running all containerized agents and services.
2.  We will use **Google Artifact Registry** to store and manage our Docker container images.

## Rationale

1.  **Serverless and Fully Managed**: Cloud Run is a serverless platform. We are only responsible for the container image; Google manages the underlying servers, networking, and scaling. This drastically reduces operational complexity and aligns with our strategy of leveraging managed services.
2.  **Cost-Effectiveness (Scale to Zero)**: Cloud Run's primary advantage is its ability to scale down to zero instances when a service is not receiving requests. For many of our agents that operate intermittently (e.g., only on a trigger or a schedule), this is significantly more cost-effective than paying for an always-on virtual machine or Kubernetes node.
3.  **Simplicity over Complexity**: For the current needs of our system, a full-fledged Kubernetes cluster (like Google Kubernetes Engine - GKE) would be overly complex and expensive to manage. Cloud Run provides the right level of control (auto-scaling, revisions, networking) without the steep learning curve and operational burden of Kubernetes.
4.  **Seamless GCP Integration**: Cloud Run and Artifact Registry are core parts of the GCP ecosystem. They integrate natively with our other chosen services, including IAM for secure access, Cloud Logging/Monitoring for observability, and Pub/Sub for event-driven agent invocation.

## Consequences

-   **Stateless Service Design**: Agents deployed on Cloud Run must be designed as stateless web services. Any required state must be externalized to a service like Redis, which is already part of our architecture (ADR-001). This enforces a clean, robust design.
-   **Implementation**:
    -   Each agent's container must expose an HTTP server to receive requests (e.g., using a lightweight framework like FastAPI or Flask).
    -   Event-driven agents (like the `Data Ingestion Service`) will be configured to be triggered by events from Pub/Sub (ADR-015).
-   **Deployment**: Our CI/CD pipeline will be configured to:
    1.  Build the Docker image for an agent.
    2.  Push the image to Google Artifact Registry.
    3.  Deploy the new image as a revision to the corresponding Cloud Run service.
-   **Infrastructure**: Cloud Run services and Artifact Registry repositories will be defined and managed via our Infrastructure as Code (IaC) setup.

## Alternatives Considered

-   **Google Kubernetes Engine (GKE)**: GKE is an extremely powerful and flexible container orchestrator. However, it comes with significant operational overhead (managing nodes, clusters, networking policies, etc.) and higher baseline costs. It was deemed overkill for the current scale and needs of the project.
-   **Google Compute Engine (GCE) with Docker**: This would involve manually provisioning virtual machines and managing the Docker daemon, networking, scaling, and health checks ourselves. This approach provides maximum control but carries the highest operational burden and was rejected in favor of a managed, serverless solution.

## Implementation Strategy

### Phase 1: Artifact Registry Setup (Week 1)
**Deliverables**:
- Create Artifact Registry Docker repository: `trading-agents`
- Configure IAM permissions for CI/CD push and Cloud Run pull
- Set up vulnerability scanning for container images
- Configure image retention policy (keep last 10 versions)
- Terraform configuration for Artifact Registry
- Test manual docker push/pull to registry

**Dependencies**: GCP project setup, ADR-019 (Terraform)

### Phase 2: Base Service Template (Week 1-2)
**Deliverables**:
- Create base FastAPI service template for agents
- Implement health check endpoints (/health, /ready)
- Add structured logging configuration
- Create Dockerfile with multi-stage build
- Add Docker Compose for local development
- Unit tests for base service template
- Documentation for agent service development

**Dependencies**: Phase 1 complete

### Phase 3: Initial Service Deployment (Week 2-3)
**Deliverables**:
- Deploy first Cloud Run service (Data Ingestion Service)
- Configure service settings (CPU, memory, concurrency, timeout)
- Set up Pub/Sub push subscription trigger
- Configure IAM service accounts and permissions
- Implement blue-green deployment pattern
- Integration tests for deployed service
- Performance testing under load

**Dependencies**: Phase 2 complete, ADR-015 (Pub/Sub) implementation

### Phase 4: Multi-Service Rollout (Week 3-5)
**Deliverables**:
- Deploy remaining agent services (Market Analysis, Stock Selection, etc.)
- Configure VPC connector for private service communication
- Set up Cloud Run service-to-service authentication
- Implement request routing and load balancing
- Create service deployment templates
- End-to-end tests for multi-service workflows

**Dependencies**: Phase 3 complete, agent implementations

### Phase 5: Monitoring and Auto-Scaling (Week 5-6)
**Deliverables**:
- Configure Cloud Monitoring dashboards for all services
- Set up alerting for service errors, latency, cold starts
- Optimize auto-scaling settings (min/max instances, CPU targets)
- Implement custom metrics for business logic
- Performance tuning and optimization
- Operational runbooks

**Dependencies**: Phase 4 complete, ADR-021 (Observability)

## Cost Analysis

### Monthly Operational Costs

**Cloud Run Compute**:
- Request charges: First 2M requests free, then $0.40/M requests
- Estimated: 500K requests/month (agents running intermittently)
- Request cost: $0/month (within free tier)

**Cloud Run CPU Time**:
- First 180,000 vCPU-seconds free, then $0.00002400/vCPU-second
- Estimated: 50K vCPU-seconds/month (average 100ms per request)
- CPU cost: $0/month (within free tier)

**Cloud Run Memory**:
- First 360,000 GiB-seconds free, then $0.00000250/GiB-second
- Estimated: 100K GiB-seconds/month (512MB per container)
- Memory cost: $0/month (within free tier)

**Artifact Registry Storage**:
- Storage: $0.10/GB per month
- Estimated: 5GB (10 images × ~500MB each)
- Storage cost: $0.50/month

**Data Transfer**:
- Ingress: Free
- Egress within GCP region: Free
- Egress to internet: $0.12/GB (minimal for API responses)
- Transfer cost: $2-5/month

**Total Estimated Monthly Cost**: $2.50-5.50/month

### Cost Optimization Strategies

1. **Scale to Zero**:
   - Services scale to zero when idle
   - Only pay for actual request processing time
   - Estimated savings: $200-300/month vs always-on VMs

2. **Request Batching**:
   - Process multiple items per request where possible
   - Reduces request count and cold starts
   - Estimated savings: 40% reduction in request charges

3. **Minimum Instances Configuration**:
   - Critical services: min=1 to avoid cold starts
   - Non-critical services: min=0 for cost savings
   - Trade-off: $10-15/month for instant availability

4. **Container Image Optimization**:
   - Multi-stage Docker builds reduce image size by 60%
   - Smaller images = faster cold starts, lower storage costs
   - Estimated savings: $3-5/month on storage and egress

### ROI Comparison

**vs Google Kubernetes Engine (GKE)**:
- GKE cluster (3 nodes, n1-standard-1): $75/month
- Load balancer: $18/month
- Persistent storage: $10/month
- Operational overhead: 20% engineering time
- Cloud Run: $2.50-5.50/month, zero operational overhead
- **Cost Savings**: 95%+ reduction

**vs Google Compute Engine (GCE)**:
- 2 × n1-standard-1 instances: $50/month
- Load balancer: $18/month
- Manual scaling, patching, monitoring overhead
- Cloud Run: $2.50-5.50/month, fully managed
- **Cost Savings**: 90%+ reduction

**vs AWS Lambda (comparable serverless)**:
- Lambda compute: $0.20 per 1M requests
- API Gateway: $3.50 per 1M requests
- Data transfer: Similar costs
- Cloud Run generally 20-30% cheaper with simpler pricing

## Risk Assessment

| Risk | Severity | Likelihood | Impact | Mitigation |
|------|----------|------------|--------|------------|
| Cold start latency | Medium | High | Delayed agent responses (1-3s), slower trading decisions | Min instances=1 for critical services, container size optimization, keep-alive requests |
| Request timeout (60s max) | Medium | Low | Long-running processes fail | Break into smaller tasks, use async processing with Pub/Sub, status polling patterns |
| Memory limits (4GB max) | Low | Low | OOM errors for data-intensive processing | Memory-efficient algorithms, streaming processing, offload to BigQuery for large datasets |
| Concurrent request limits | Low | Medium | Request throttling during high load | Configure max instances, request queuing, horizontal scaling, load testing |
| Stateless design complexity | Medium | Medium | More complex state management | Use Redis for session state, Cloud SQL for persistent state, clear state boundaries |
| Service-to-service auth complexity | Low | Low | Authentication errors, security gaps | Use Cloud Run service identity, IAM policies, service-to-service tokens |
| Regional outage | High | Very Low | Complete system unavailable | Multi-region deployment option (adds cost), graceful degradation, manual failover procedures |

## Monitoring and Success Criteria

### Key Metrics

**Cloud Run Performance**:
1. Request latency: <500ms p95, <1s p99
2. Cold start frequency: <10% of requests
3. Cold start duration: <2 seconds
4. Request success rate: >99.9%

**Resource Utilization**:
1. CPU utilization: 40-70% under load
2. Memory utilization: <80% of allocated
3. Container instance count: Auto-scales 0-10
4. Request queue depth: <50 concurrent requests

**Availability and Reliability**:
1. Service uptime: >99.9%
2. Failed deployment rate: <1%
3. Rollback time: <5 minutes
4. Mean time to recovery: <10 minutes

### Alerting Thresholds

**Critical Alerts (PagerDuty)**:
- Service completely unavailable for >5 minutes
- Error rate >10% for >2 minutes
- All container instances failing health checks
- Request latency >5 seconds p95
- Service deployment failed

**Warning Alerts (Email)**:
- Error rate >5% for >5 minutes
- Request latency >2 seconds p95
- Cold start rate >30%
- Memory utilization >90%
- Container instance count at maximum

**Informational Alerts (Dashboard)**:
- Daily request volume trends
- Cold start patterns by time of day
- Resource utilization trends
- Deployment history and success rate

### Success Criteria

**Functional Requirements**:
- All agents successfully deployed and accessible
- Stateless operation with external state management
- Pub/Sub event triggers working correctly
- Service-to-service communication authenticated

**Performance Requirements**:
- 99.9% uptime for critical services
- Request latency <1 second p95
- Cold starts <10% of requests for active services
- Auto-scaling handles 10x traffic spikes

**Cost Requirements**:
- Monthly cost <$10 for typical operations
- Stay within free tier for first 6 months
- Cost per request <$0.001
- No unexpected cost spikes

**Operational Requirements**:
- Zero-downtime deployments
- Automated rollback on deployment failure
- Self-healing through auto-restart
- Minimal operational intervention required
