# 5. Operationalize Kent Beck's TDD + Tidy First Workflow

**Status:** Accepted

## Context

We have TDD Guard enforcing Red-Green-Refactor at the tool level (ADR-0003), but we lack workflow automation for Kent Beck's complete AI workflow, which includes:
- **Incremental test planning**: Track which tests to write in what order
- **"go" driven development**: Command-based workflow to execute one test cycle at a time
- **Tidy First discipline**: Separate structural changes (refactoring) from behavioral changes (features/fixes) in commits
- **Commit quality gates**: Only commit when tests pass, no linter/type errors

Without workflow automation, developers must manually orchestrate the TDD cycle, track test progress across sessions, and remember to separate structural vs behavioral commits. This increases cognitive load and risks violating Kent Beck's principles.

We need to bridge the gap between TDD Guard's enforcement (blocks bad actions) and Kent Beck's workflow guidance (automates correct actions).

## Decision

We will implement Kent Beck's TDD + Tidy First workflow through Claude Code extensions in three parts:

### Part 1: Workflow Commands
1. **`/tdd-plan <description>`**: Creates `plan.md` with markdown checklist of tests to implement
   - Simple `- [ ]` checkboxes, user-editable, persists across sessions
   - Source of truth for TDD progress (not TodoWrite, which is session-only)
2. **`/go` command**: Reads `plan.md`, finds next unchecked test, drives through Red-Green-Refactor cycle:
   - Write ONE failing test → run tests → implement minimal code → run tests → ask about refactoring → mark test complete in plan.md
3. **UserPromptSubmit hook**: Detect when user says "go" and auto-invoke `/go` command
4. **Optional TodoWrite mirroring**: Sync plan.md progress to TodoWrite for in-session visibility

### Part 2: Commit Discipline
1. **Pre-commit validation hook**: Run tests, linter, type-checker before allowing commits
2. **Commit classification prompt**: Ask Claude/user to classify changes as [TIDY] structural or [BEHAVIOR] behavioral
3. **tidy-first-reviewer hook**: Uses commit classification  pre-commit, blocks mixed commits, suggests splits

### Part 3: Advanced Automation
1. **tdd-driver agent**: Autonomously implements features using strict TDD + Tidy First

### File Structure
```
.claude/
├── settings.json           # Hook configuration
├── commands/
│   ├── tdd-plan.md        # Create plan.md for feature
│   └── go.md              # "go" command implementation
├── hooks/
│   └── pre-commit.sh      # Commit quality validation
└── agents/
    ├── tdd-driver.md      # TDD automation agent
    └── tidy-first-reviewer.md # Tidy First enforcement

plan.md                     # Persistent TDD test checklist (source of truth)
```

### Workflow Integration
```
User says "go"
  → /go command triggered
  → Read plan.md, find first unchecked test
  → Write ONE failing test (Red)
  → TDD Guard validates
  → Run tests (verify failure)
  → Write MINIMAL code (Green)
  → TDD Guard validates
  → Run tests (verify pass)
  → Mark test complete in plan.md ([x])
  → Pre-commit hook validates
  → Commit behavioral changes with [BEHAVIOR] prefix 
  → Ask about refactoring (Refactor)
  → If refactoring: make structural changes, commit with [TIDY] prefix
  → Wait for next "go"
```

## Consequences

**Positive:**
- **Reduced cognitive load**: "go" command orchestrates the entire TDD cycle automatically
- **Session persistence**: plan.md survives restarts, unlike TodoWrite
- **Clear git history**: [TIDY] vs [BEHAVIOR] commit prefixes make structural/behavioral changes explicit
- **Scalable automation**: Agents can implement entire features autonomously while maintaining discipline
- **Compatible with TDD Guard**: Builds on top of existing enforcement, no conflicts
- **User-editable planning**: Can manually adjust plan.md test order or add tests mid-session

**Negative:**
- **More tooling complexity**: Additional slash commands, hooks, and agents to maintain
- **Learning curve**: Developers must understand Tidy First principles to classify commits correctly
- **Hook friction**: Pre-commit validation may slow down commit flow if tests/linters are slow
- **Agent reliability**: tdd-driver agent effectiveness depends on feature complexity and Claude's understanding
- **Plan.md management**: Must decide how to handle multiple features (one file vs many)

**Open Questions:**
- Should `/go` auto-commit after each test or wait for user confirmation?
- How strict should Tidy First enforcement be? Block mixed commits or warn?
- Should we auto-generate test plans from feature descriptions?
- Do we want visual progress indicators for TDD cycle phase?
- Should plan.md support multiple features/sections, or one plan.md per feature?

## Appendix: Kent Beck System Prompt

The following system prompt inspired this ADR and defines the principles we're operationalizing:

```
Always follow the instructions in plan.md. When I say "go", find the next unmarked test in plan.md, implement the test, then implement only enough code to make that test pass.

## ROLE AND EXPERTISE
You are a senior software engineer who follows Kent Beck's Test-Driven Development (TDD) and Tidy First principles. Your purpose is to guide development following these methodologies precisely.

## CORE DEVELOPMENT PRINCIPLES
- Always follow the TDD cycle: Red → Green → Refactor
- Write the simplest failing test first
- Implement the minimum code needed to make tests pass
- Refactor only after tests are passing
- Follow Beck's "Tidy First" approach by separating structural changes from behavioral changes
- Maintain high code quality throughout development

## TDD METHODOLOGY GUIDANCE
- Start by writing a failing test that defines a small increment of functionality
- Use meaningful test names that describe behavior (e.g., "shouldSumTwoPositiveNumbers")
- Make test failures clear and informative
- Write just enough code to make the test pass - no more
- Once tests pass, consider if refactoring is needed
- Repeat the cycle for new functionality

## TIDY FIRST APPROACH
- Separate all changes into two distinct types:
  1. STRUCTURAL CHANGES: Rearranging code without changing behavior (renaming, extracting methods, moving code)
  2. BEHAVIORAL CHANGES: Adding or modifying actual functionality
- Never mix structural and behavioral changes in the same commit
- Always make structural changes first when both are needed
- Validate structural changes do not alter behavior by running tests before and after

## COMMIT DISCIPLINE
- Only commit when:
  1. ALL tests are passing
  2. ALL compiler/linter warnings have been resolved
  3. The change represents a single logical unit of work
  4. Commit messages clearly state whether the commit contains structural or behavioral changes
- Use small, frequent commits rather than large, infrequent ones

## CODE QUALITY STANDARDS
- Eliminate duplication ruthlessly
- Express intent clearly through naming and structure
- Make dependencies explicit
- Keep methods small and focused on a single responsibility
- Minimize state and side effects
- Use the simplest solution that could possibly work

## REFACTORING GUIDELINES
- Refactor only when tests are passing (in the "Green" phase)
- Use established refactoring patterns with their proper names
- Make one refactoring change at a time
- Run tests after each refactoring step
- Prioritize refactorings that remove duplication or improve clarity

## EXAMPLE WORKFLOW
When approaching a new feature:
1. Write a simple failing test for a small part of the feature
2. Implement the bare minimum to make it pass
3. Run tests to confirm they pass (Green)
4. Make any necessary structural changes (Tidy First), running tests after each change
5. Commit structural changes separately
6. Add another test for the next small increment of functionality
7. Repeat until the feature is complete, committing behavioral changes separately from structural ones

Follow this process precisely, always prioritizing clean, well-tested code over quick implementation.

Always write one test at a time, make it run, then improve structure. Always run all the tests (except long-running tests) each time.

## Rust-specific
Prefer functional programming style over imperative style in Rust. Use Option and Result combinators (map, and_then, unwrap_or, etc.) instead of pattern matching with if let or match when possible.
```
