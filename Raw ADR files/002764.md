# ADR-0001: Modular Monolith (Phase 1) vs Microservices

## Status
Accepted (2025-12-26)

## Context
We are a solo developer building a legally launchable V1. The platform requires:
- low-latency playback session minting and entitlement checks,
- asynchronous media processing (FFmpeg),
- payments/webhooks,
- moderation/DMCA workflows.

Distributed microservices would increase operational overhead (deployments, tracing, failure modes) and slow iteration. However, the system must be designed so future teams can scale without a rewrite.

## Decision
Build a **modular monolith** API (single deployable) in Kotlin + Spring Boot, with:
- strict module boundaries (bounded contexts),
- **schema-per-module** in Postgres,
- a transactional **outbox** for integration events,
- separate worker deployables for heavy async workloads (media pipeline, indexing).

## Options Considered
1) Modular monolith + workers (chosen)
2) Microservices from day 1 (per bounded context)
3) “Mini-services”: 2–3 coarse services (API + media + payments)

## Pros / Cons
### 1) Modular monolith + workers
Pros:
- Fast iteration and debugging; fewer production failure modes.
- One deployable for API; still allows independent scaling via workers.
- Clean seams (facades + outbox) make later extraction feasible.
Cons:
- Requires discipline to avoid cross-module coupling.
- Shared DB can encourage “just join it” shortcuts if not enforced.

### 2) Microservices from day 1
Pros:
- Strong isolation and independent scaling from the start.
- Natural team ownership boundaries later.
Cons:
- High ops overhead (service discovery, retries, distributed tracing, deployments).
- Harder to maintain consistent authorization, data integrity, and debugging as solo dev.

### 3) Coarse “mini-services”
Pros:
- Some isolation without full microservices overhead.
Cons:
- Easy to get the worst of both worlds (distributed complexity + poor boundaries).

## Consequences
- We must enforce module boundaries via build rules and code review.
- Cross-module communication is via facades (sync) and outbox events (async).
- Service extraction later becomes a transport change (in-process → HTTP/gRPC) with stable contracts.

## Rollback
If the modular monolith becomes a bottleneck or requires separate team ownership:
- Extract a bounded context into a service by:
  1) freezing its facade + event contracts,
  2) moving its schema to a new DB,
  3) replacing in-process calls with HTTP/gRPC,
  4) keeping event contracts stable while consumers migrate.
