# ADR-0001: Modular Monolith Architecture

**Status:** Accepted  
**Date:** October 2025  
**Deciders:** Development Team, Technical Lead  
**Related ADRs:** [ADR-0002: Tech Stack](./0002-tech-stack-nest-postgres-redis-s3.md)

## Context

We need to choose an architectural pattern for the Logistic marketplace platform that will:
- Support rapid MVP development and iteration
- Allow independent development of business domains (shipments, bids, payments, etc.)
- Scale to handle initial production load (estimated 1000-5000 requests/min)
- Minimize operational complexity for a small team (2-4 developers)
- Provide a clear migration path to distributed systems if needed

**Alternatives Considered:**
1. **Monolithic Architecture**: Single deployable unit with no module boundaries
2. **Modular Monolith**: Single deployable unit with strong internal module boundaries
3. **Microservices**: Multiple independently deployable services
4. **Serverless**: Function-as-a-Service with event-driven architecture

## Decision

We will implement a **Modular Monolith** architecture using NestJS modules as bounded contexts.

### What is a Modular Monolith?

A modular monolith is a single deployable application that is internally organized into loosely coupled, highly cohesive modules with explicit boundaries and well-defined interfaces. Each module represents a bounded context from Domain-Driven Design (DDD).

**Key Characteristics:**
```
┌─────────────────────────────────────────────────────────────────┐
│ Single Deployment Unit (apps/backend)                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐      │
│  │ Auth     │  │Shipments │  │ Bids     │  │ Payments │      │
│  │ Module   │  │ Module   │  │ Module   │  │ Module   │      │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘      │
│       │             │              │              │            │
│       └─────────────┴──────────────┴──────────────┘            │
│                          │                                      │
│                   ┌──────▼──────┐                              │
│                   │   Shared    │                              │
│                   │ Infrastructure│                            │
│                   │ (DB, Redis,  │                            │
│                   │  S3, Jobs)   │                            │
│                   └─────────────┘                              │
└─────────────────────────────────────────────────────────────────┘
```

### Module Structure

Each module follows a consistent structure:
```
modules/shipments/
├── shipments.module.ts       # NestJS module definition
├── shipments.controller.ts   # API endpoints
├── shipments.service.ts      # Business logic
├── shipments.repository.ts   # Data access (optional)
├── entities/                 # Domain entities
│   └── shipment.entity.ts
├── dto/                      # Data Transfer Objects
│   ├── create-shipment.dto.ts
│   └── update-shipment.dto.ts
└── interfaces/               # Public contracts
    └── shipments.service.interface.ts
```

### Module Communication Rules

1. **No Direct Database Access**: Modules cannot access another module's database tables directly
2. **Public Interfaces Only**: Cross-module communication happens through exported service interfaces
3. **Event-Driven Integration**: Asynchronous workflows use event emitters or job queues
4. **Shared Kernel**: Common utilities (config, logging, DTOs) live in `common/`

**Example: Bids Module depending on Shipments Module**
```typescript
// ✅ GOOD: Through public interface
import { ShipmentsService } from '../shipments/shipments.service';

@Injectable()
export class BidsService {
  constructor(private shipmentsService: ShipmentsService) {}
  
  async createBid(shipmentId: string, bidData: CreateBidDto) {
    // Use public interface
    const shipment = await this.shipmentsService.findById(shipmentId);
    // ...
  }
}

// ❌ BAD: Direct database access
import { Shipment } from '../shipments/entities/shipment.entity';
import { InjectRepository } from '@nestjs/typeorm';

@Injectable()
export class BidsService {
  constructor(
    @InjectRepository(Shipment) // Don't do this!
    private shipmentRepo: Repository<Shipment>
  ) {}
}
```

## Rationale

### Why Modular Monolith?

#### 1. **Development Velocity** ✅
- Single codebase reduces cognitive overhead
- Easier to refactor across modules
- Shared types and utilities reduce duplication
- Faster local development setup (one `docker compose up`)

#### 2. **Operational Simplicity** ✅
- Single deployment process (one Docker image)
- Simplified monitoring and logging (single log stream)
- Easier debugging (no distributed tracing needed initially)
- Lower infrastructure costs (1 server vs 10+ services)

#### 3. **Team Size** ✅
- Suitable for small teams (2-4 developers)
- No need for DevOps specialization initially
- Easier onboarding (single repository)

#### 4. **Migration Path** ✅
- Strong module boundaries enable future extraction
- Modules can be converted to microservices independently
- Shared infrastructure (DB, Redis) can be split later
- No architectural rewrite needed

#### 5. **Performance** ✅
- In-process communication (no network overhead)
- Shared database connections (connection pooling)
- Single transaction coordinator (ACID guarantees)

### Why Not Microservices?

| Concern | Microservices Challenge | Modular Monolith Advantage |
|---------|------------------------|----------------------------|
| **Team Size** | Requires multiple teams, ownership model | Single team can manage entire system |
| **Operational Overhead** | Service discovery, API gateways, distributed tracing | Single process, no network complexity |
| **Data Consistency** | Eventual consistency, saga patterns | ACID transactions, immediate consistency |
| **Development Speed** | API contracts, versioning, inter-service coordination | Direct function calls, TypeScript interfaces |
| **Debugging** | Distributed logs, request tracing across services | Single log file, stack traces |
| **Cost** | 10+ services = 10+ containers/VMs | 1 service = 1 container |

**When to Migrate to Microservices:**
- Team grows beyond 10 developers
- Individual modules need independent scaling (e.g., tracking module has 10x traffic)
- Modules have different technology requirements (e.g., ML service needs Python)
- Deployment independence becomes critical (deploy payments without affecting shipments)

### Why Not Serverless?

| Concern | Serverless Challenge | Modular Monolith Advantage |
|---------|---------------------|----------------------------|
| **Cold Starts** | 2-5 second latency for first request | Always warm |
| **Stateful Connections** | Database connection pooling is difficult | Persistent connection pool |
| **Local Development** | Complex local emulation | Native Docker Compose |
| **Cost Predictability** | Pay-per-invocation can be expensive | Fixed infrastructure cost |
| **Long-Running Jobs** | 15-minute timeout limit | No timeout (handled by BullMQ workers) |

## Consequences

### Positive Consequences ✅

1. **Faster Time to Market**: MVP can be deployed in weeks, not months
2. **Lower Infrastructure Costs**: Single server handles MVP load (~$100-200/month vs $500-1000+ for microservices)
3. **Simplified Monitoring**: Single health check, single log stream, single APM instance
4. **Strong Consistency**: ACID transactions across modules without distributed transaction complexity
5. **Easier Testing**: Integration tests can span multiple modules without network mocking

### Negative Consequences ⚠️

1. **Tight Deployment Coupling**: All modules deploy together (mitigated by CI/CD automation)
2. **Scaling Limitations**: Cannot scale individual modules independently (acceptable for MVP)
3. **Technology Lock-in**: All modules must use Node.js/TypeScript (acceptable for current team)
4. **Shared Fate**: A bug in one module can crash the entire application (mitigated by error boundaries)

### Mitigation Strategies

1. **Module Isolation**: Enforce boundaries through code reviews and linting
2. **Feature Flags**: Deploy features incrementally without code branching
3. **Horizontal Scaling**: Run multiple instances behind a load balancer when needed
4. **Circuit Breakers**: Implement error isolation (e.g., notifications failure doesn't affect payments)
5. **Caching**: Use Redis to reduce database load and improve performance

## Migration Strategy

### Phase 1: MVP (Current) - Modular Monolith
- All modules in `apps/backend`
- Single PostgreSQL database with schema-per-module
- Single Redis instance for caching and jobs
- Target load: 1000-5000 req/min

### Phase 2: Growth (6-12 months) - Optimized Monolith
- Add read replicas for reporting module
- Separate Redis clusters (cache vs jobs)
- Implement CDN for static assets
- Target load: 10,000-50,000 req/min

### Phase 3: Scale (12-24 months) - Hybrid Architecture
- Extract high-throughput modules (e.g., tracking) to separate services
- Keep transactional core as monolith (shipments, bids, contracts, payments)
- Shared event bus (Kafka/RabbitMQ) for inter-service communication
- Target load: 50,000-200,000 req/min

### Phase 4: Distributed (24+ months) - Microservices
- Full microservices architecture if needed
- Service mesh for observability
- Independent databases per service
- Target load: 200,000+ req/min

## Enforcement

### Architectural Rules (Enforced in Code Review)

1. **Module Exports**: Each module must export a public interface via `index.ts`
2. **Dependency Direction**: Dependencies flow from outer modules (controllers) to inner modules (services, repositories)
3. **No Circular Dependencies**: Use dependency injection and interfaces to break cycles
4. **Shared Database Schema**: Each module owns its database tables (prefix with module name, e.g., `shipments_*`, `bids_*`)
5. **Event-Driven Communication**: Cross-module async workflows use BullMQ jobs, not direct service calls
