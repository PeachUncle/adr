# 16. Comparison of WebSub and MQTT for Event-Based Communication in PITAS

Date: 2024-12-22

## Status
Accepted

## Context
The PITAS system required implementation of event-based communication for auction notifications between different groups' auction houses. As part of exploring different approaches to achieve this, we implemented both W3C WebSub and MQTT as alternative solutions for the same functionality. This implementation allowed us to compare these protocols in practice for distributing auction-related events such as new auctions and bid notifications.

## Decision
We implemented both WebSub and MQTT as alternative approaches for event-based communication in the auction system, with both protocols handling the same responsibilities:

### Implementation Details
0. **Integration with Pitas Systema and Http communication**:
   - We integrated the auction house within our system. We decided that the scheduler is the one responsible of recognizing if we have to launch an auction or not, based on if we have a worker for a certain job Type.
   - The scheduler though sends a notification to the auction house to launch an auction. 
   - We have then implemented all the http classes to handle the communication within the system (in /web folder) and the communication with the external auction houses. 
   - Given our worker and the workflow implemented before the split we had to implement a communication between the workers and the auction house, mainly for giving back results to other auction houses (/auctionhouse/adapter/out/messaging/http/ExternalAuctionHouseNotifier.java).
   - We also implemented a map in the auction house to keep of the JobId and the AuctionId to be able to give back the results to the correct auction house.
   - We then adapted all our endpoints and payloads to be coherent with the *task force* specifications. We think that some of the decisioins took in the task force are not the best ones, because a lot of times we had to heavily modify our code in order to have in a class some data that were not needed. These things could have be done in a smarter way, exploiting the information of each speicific class, but of course we all had different implementation. 
   
1. **WebSub Implementation**:
   - Utilized Google WebSub Hub and Switchboard as hub providers
   - Publishers (Auction Houses) expose auction feeds
   - Subscribers implement callback endpoints for auction notifications
   - Resource discovery through centralized directory
   - Used for publishing new auctions and receiving notifications about auctions from other groups

2. **MQTT Implementation**:
   - Utilized HiveMQ's public broker
   - Publishers and subscribers connect to the same MQTT broker
   - Topic structure for auctions and notifications
   - Used for the same functionality: publishing new auctions and receiving notifications

### Protocol Comparison From Implementation Experience

1. **WebSub Characteristics**:
   - Web-native protocol using HTTP
   - Requires public endpoints for callbacks
   - Higher initial setup complexity
   - Better suited for web-scale distribution
   - More complex subscription management
   - Difficult debugging.

2. **MQTT Characteristics**:
   - Lightweight protocol
   - Simpler implementation
   - Requires persistent broker connection
   - More immediate message delivery
   - Straightforward topic-based routing

## Consequences

### WebSub Consequences
**Positive**:
- Built on standard web technologies
- Natural integration with REST APIs
- Supports content negotiation
- Scales well for large deployments

**Negative**:
- Requires public endpoints for callbacks
- More complex subscription management
- Higher latency due to HTTP overhead
- More involved error handling
- The testing inter groups can be done only trhough the VM, in our case at the plug fest the VM was not working, so we could not test the interoperability.
 
### MQTT Consequences
**Positive**:
- Simpler implementation
- Lower latency
- Lightweight protocol
- Easier to debug and monitor

**Negative**:
- Requires maintaining broker connections
- Less web-native
- Potential single point of failure (broker)
- Limited built-in security features

## Trade-offs

1. **Protocol Characteristics**:
   - WebSub offers better integration with web infrastructure but has higher complexity
   - MQTT provides simpler implementation but requires dedicated broker infrastructure

2. **Operational Considerations**:
   - WebSub has higher latency but better scalability
   - MQTT has lower latency but requires connection management

3. **Development Experience**:
   - WebSub development requires more setup but aligns with web standards
   - MQTT development is simpler but requires different tooling and monitoring

## Recommendations Based on Implementation Experience

For similar auction notification systems:
- Choose WebSub when:
  - Web-scale distribution is required
  - Integration with existing web infrastructure is important
  - Public endpoints are already available
  - Content negotiation is needed

- Choose MQTT when:
  - Lower latency is priority
  - Simpler implementation is preferred
  - Maintaining broker connection is acceptable
  - Resource constraints exist
