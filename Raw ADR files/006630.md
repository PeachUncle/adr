# ADR 3.1: Context Orchestration Contract

- Status: Accepted (2025-10-29)
- Owners: Memory Systems Working Group
- Tags: context, user-profile, serialization, replay

## Context
- V3 agents must coordinate shared context while maintaining tenant isolation and reproducible state.
- Earlier designs allowed ad-hoc enrichment of agent prompts, leading to divergent states and untraceable personalization logic.
- The hardened blueprint requires deterministic serialization of user profiles, macro plans, and runtime notes so every sub-agent can replay the same history.

## Decision
- MasterState SHALL be the single canonical context document, persisted after every planner tick via the execution log defined in ADR 2.1.
- ResearchState, SynthesisState, and other sub-agent states SHALL derive from snapshot slices of MasterState plus explicit task directives issued by the Master_Planner.
- User profile data SHALL be stored in PostgreSQL for metadata, with vectorized preferences mirrored in Milvus `user_kb`. Retrieval SHALL occur through an MCP tool (`retrieve_user_profile`) that emits both the raw document pointer and the embedding reference.
- Context mutations (compression, reordering, enrichment) SHALL be performed by dedicated Context_Engineer routines that record input hash, operation type, and output hash in the log.
- Sub-agents SHALL reload the latest signed registry snapshot and MasterState hash before executing any task to guarantee tool parity and consistent personalization.

## Consequences
- Pros: deterministic personalization, simplified debugging, strong guardrails against prompt drift, auditable context lineage.
- Cons: additional serialization overhead, stricter coupling between planner loop and persistence, need for context schema migrations when fields evolve.
- Mitigation: versioned context schemas (`master_state_v3`), automated backward compatibility checks, and schema diff alerts in CI.

## Implementation Notes
- MasterState schema (compact JSON): `version`, `tenant_id`, `user_profile_pointer`, `macro_plan`, `research_queue`, `active_tools`, `context_hash`.
- Context_Engineer utilities SHALL live in `backend/python/app/context_vars.py` with pure functions supporting replay.
- Frontend components SHALL render context-driven panels (profile, tools, reports) exclusively from API responses sourced from MasterState, not from client-side caches.
