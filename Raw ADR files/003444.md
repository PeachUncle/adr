# ADR 3: Pivot from Monolithic to Microservices Architecture

**Date:** 2025-01-05  
**Status:** Accepted  

## Summary  
The project initially began with a monolithic architecture to enable rapid prototyping and reduce upfront complexity. However, as functional requirements expanded and team size grew, we made an early decision to re-architect the system using a domain-based microservices approach. This shift was motivated by the need for better scalability, maintainability, and parallel development efficiency.

## Context  
Monoliths are often the simplest and fastest way to get a prototype off the ground, which aligned well with our early-stage development goals. But as the application evolved, we started to encounter friction related to code coupling, deployment bottlenecks, and difficulty in scaling parts of the system independently. The growing number of features ranging from authentication to search, reservations, and notifications necessitated a structure that enabled parallel work across services without introducing merge conflicts or regression risks. A microservices architecture offered a way to logically isolate domains, align teams with features, and provide flexibility for future scaling needs.

## Decision  
We broke the monolith into several microservices, each dedicated to a specific domain such as Auth, Listings, Bookings, and Notifications. Each service was built as an independently deployable unit with its own database schema, container image, and HTTP API. Inter-service communication was implemented using RESTful interfaces, with authentication and shared data coordinated via internal API gateways and message queues (planned for future use). CI/CD pipelines were restructured to support independent deployment and versioning of services.

## Consequences  
**Advantages:**  
- Improved development velocity through parallel team workflows.  
- Increased system scalability and better fault isolation.  
- Easier to apply updates or adopt new tech stacks per service.

**Neutral:**  
- Requires setup of shared observability tools such as monitoring and tracing to manage complexity.

**Disadvantages:**  
- Significantly more complex DevOps overhead including service discovery, deployment, and health checks.  
- Debugging and local testing require additional tooling and environment management.
