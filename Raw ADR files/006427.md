# Architecture Alignment Decisions

This log captures concrete choices made while tailoring the GitLab deployment plan to a TypeScript-first GitHub Chat Mode pipeline. Each entry should be updated as new information surfaces.

## ADR-0001 – Pilot-First Conversion Strategy

- **Status:** Accepted
- **Context:** The original GitLab plan assumed simultaneous scaffold + conversion. To reduce risk and allow per-repo approval, we prioritise converting a single high-impact repository first.
- **Decision:** Stage one repository under `skills/pilot/`, implement a minimal converter (`tools/converter/src/pilot.ts`), and treat the resulting GitHub chat mode bundle as the gold standard for future automation.
- **Consequences:**
  - Early validation of strict TypeScript rules before scaling.
  - Enables smoke testing of CI without the full dataset.
  - Requires maintaining `docs/architecture/pilot-findings.md` as the canonical test report.

## ADR-0002 – Unified TypeScript Monorepo

- **Status:** Proposed
- **Context:** The GitLab plan separated tooling and site assets but did not prescribe language boundaries. We want zero JavaScript drift and centralised configuration.
- **Decision:** Manage all runtime and tooling code inside a pnpm-powered TypeScript monorepo with a root `tsconfig.base.json` and shared lint/format config. No package may disable strict rules.
- **Consequences:**
  - Simplifies dependency sharing (`packages/types`, `packages/config`).
  - Requires initial investment in project references and CI caching.
  - Forces third-party utilities lacking types to go through dedicated type definition shims instead of `any` casts.

## ADR-0003 – Validation via Zod (or Equivalent)

- **Status:** Proposed
- **Context:** Converting legacy Claude skill definitions to GitHub chat mode requires runtime validation. Manual assertion risks slipping `any` back in.
- **Decision:** Use a schema validation library (Zod, Valibot, or TypeBox) with full TypeScript inference to guarantee the shape of converted skills and search indices.
- **Consequences:**
  - Provides safe parsing boundaries for CLI tools and frontend consumption.
  - Adds runtime dependency; must be bundled carefully for the website.
  - Keeps validation logic centralised in `packages/validation` so CI can gate every conversion.

## ADR-0004 – GitLab Pages Deployment Target

- **Status:** Accepted
- **Context:** The GitLab deployment plan remains authoritative. Prior GitHub experiments helped unblock local development, but all production releases will publish via GitLab Pages.
- **Decision:** Optimise the monorepo for GitLab CI/CD. The static frontend (`frontend/`) will be built by `.gitlab-ci.yml`, with artefacts staged for GitLab Pages. Any GitHub automation stays experimental and must not block GitLab jobs.
- **Consequences:**
  - CI documentation can focus on GitLab-specific caching, environments, and approval gates.
  - Requires keeping `.gitlab-ci.yml` in sync with pnpm workspaces and Playwright/Vitest jobs.
  - The skills indexer must publish data to `frontend/src/data/skills.json` so the GitLab Pages site resolves at build time.
  - Optional GitHub workflows may exist but are non-blocking mirrors.

Update this document whenever additional deviations or confirmations arise. Each ADR must list status (`Proposed`, `Accepted`, `Superseded`) and trace back to code changes or documentation entries.
