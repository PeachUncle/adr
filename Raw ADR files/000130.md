# ADR-0009: SwiftLint for Code Quality Standards

**Date**: 2024-10-12
**Status**: Accepted

## Context

iOS projects need consistent code quality and style enforcement across contributors. Several options exist for Swift code linting and formatting:

1. **SwiftLint**: Linting tool with 200+ rules (realm/SwiftLint)
2. **SwiftFormat**: Code formatting tool focused on automatic fixes
3. **Xcode Built-in**: Xcode's native formatting and analyzer
4. **Manual Code Review**: Human-only enforcement
5. **Swift-Format**: Apple's official formatting tool (swift-format)

The choice affects:

- Code consistency across contributors
- Automated vs. manual enforcement
- Developer workflow integration
- Maintainability and configurability
- Industry standard alignment

As of 2024-2025, the iOS community has established clear preferences based on adoption, features, and ecosystem integration.

## Decision

**We will adopt SwiftLint as the primary code quality tool, with SwiftFormat available as an optional enhancement.**

The implementation includes:

- SwiftLint (required): Linting and code quality rules
- Configuration in `.swiftlint.yml`
- Integration with pre-commit hooks (runs automatically)
- Strict mode enabled (warnings treated as errors in hooks)
- SwiftFormat (optional): Available but not enforced by default

## Alternatives Considered

### 1. SwiftFormat Only

Using SwiftFormat for both formatting and linting.

**Why not chosen**:

- Primarily a formatter, not a comprehensive linter
- Fewer code quality rules (focuses on style, not patterns)
- Less configurable for quality checks
- Doesn't catch logical issues (force unwrapping, force casts, etc.)
- Better as complement to SwiftLint, not replacement

### 2. Swift-Format (Apple's Official Tool)

Using Apple's official `swift-format` tool.

**Why not chosen**:

- Less mature than SwiftLint (fewer years of development)
- Smaller community and ecosystem
- Fewer rules and less configuration
- Less IDE integration
- Not as widely adopted in iOS community
- SwiftLint has 18K+ GitHub stars vs. swift-format's 2K+

### 3. Xcode Built-in Only

Relying solely on Xcode's native formatting and static analyzer.

**Why not chosen**:

- Not automatable in pre-commit hooks
- Requires manual invocation
- Less comprehensive rule set
- No configuration file (can't version control settings)
- Doesn't integrate with CI/CD easily
- Inconsistent across team (different Xcode versions)

### 4. Manual Code Review Only

No automated linting, rely on human reviewers.

**Why not chosen**:

- Inconsistent enforcement
- Wastes reviewer time on style issues
- Can't catch all patterns reliably
- No immediate feedback for developers
- Slower development cycle

### 5. Multiple Tools (SwiftLint + SwiftFormat + Swift-Format)

Using all available tools simultaneously.

**Why not chosen**:

- Tool conflicts (different style preferences)
- Confusion about which tool to run
- Maintenance burden (multiple configurations)
- Slower hook execution
- Diminishing returns

## Consequences

### Positive

1. **Industry Standard**: SwiftLint is the most widely adopted Swift linting tool (18,000+ GitHub stars)
2. **Comprehensive Rules**: 200+ built-in rules covering style, quality, and patterns
3. **Highly Configurable**: `.swiftlint.yml` allows project-specific customization
4. **Active Development**: Regular updates and community support
5. **Xcode Integration**: Can run in Xcode build phases
6. **Auto-Fix**: Supports `--fix` for automatic corrections
7. **Fast Execution**: Written in Swift, optimized for performance (~2 seconds)
8. **CI/CD Compatible**: Easy to integrate in automated pipelines
9. **Well Documented**: Extensive documentation and examples
10. **Team Consistency**: Same results for all developers

### Negative

1. **External Dependency**: Requires installation via Homebrew
2. **Configuration Maintenance**: Rules need periodic review
3. **Learning Curve**: Team needs to learn rule names and behavior
4. **False Positives**: Some rules may need disabling for specific cases
5. **Not a Formatter**: Catches issues but doesn't auto-format (need SwiftFormat for that)

### Mitigation Strategies

- **Easy Installation**: Document in README and provide `make setup-hooks`
- **Pragmatic Configuration**: Start with reasonable defaults, adjust as needed
- **Inline Overrides**: Allow `// swiftlint:disable` for valid exceptions
- **Clear Documentation**: Explain rules and rationale in `.swiftlint.yml` comments
- **Optional SwiftFormat**: Provide SwiftFormat integration for auto-formatting

## Rationale

The decision prioritizes **community alignment, comprehensive quality checking, and proven reliability**.

Key factors:

1. **Overwhelming Adoption**: Used by Apple, Airbnb, LinkedIn, and thousands of iOS projects
2. **Battle-Tested**: In production use since 2015, mature and stable
3. **Comprehensive Coverage**: Best balance of style, quality, and pattern checking
4. **Performance**: Fast enough for pre-commit hooks (~2 seconds)
5. **Configurability**: Can tailor rules to project needs
6. **Ecosystem**: Integrates with all major iOS tools (Xcode, pre-commit, CI/CD)
7. **Active Maintenance**: Regular updates, security fixes, new Swift version support

SwiftLint's dominance in the iOS ecosystem makes it the obvious choice for a modern project.

## Implementation Notes

### Installation

```bash
# Via Homebrew (recommended)
brew install swiftlint

# Verify installation
swiftlint version
```

### Configuration File: `.swiftlint.yml`

```yaml
# Paths to exclude from linting
excluded:
  - Pods
  - .build
  - ThreeXThreeCubePuzzleSolver.xcodeproj
  - DerivedData

# Paths to include (override exclusions)
included:
  - ThreeXThreeCubePuzzleSolver
  - ThreeXThreeCubePuzzleSolverTests
  - ThreeXThreeCubePuzzleSolverUITests

# Opt-in rules (not enabled by default)
opt_in_rules:
  - empty_count
  - empty_string
  - explicit_init
  - first_where
  - force_unwrapping
  - sorted_imports

# Rule customization
line_length:
  warning: 120
  error: 150

force_unwrapping: warning
force_cast: warning

reporter: "xcode"  # Xcode-style output
```

### Pre-commit Hook Integration

```yaml
# .pre-commit-config.yaml
- repo: local
  hooks:
    - id: swiftlint
      name: SwiftLint
      entry: swiftlint lint --strict
      language: system
      types: [swift]
      files: '\.swift$'
```

**Note**: `--strict` treats warnings as errors in pre-commit context.

### Makefile Integration

```bash
make lint  # Run SwiftLint manually
```

### Xcode Integration (Optional)

Add build phase to Xcode:

```bash
if command -v swiftlint >/dev/null 2>&1; then
  swiftlint
else
  echo "warning: SwiftLint not installed"
fi
```

### Usage

```bash
# Lint all files
swiftlint

# Lint specific files
swiftlint lint --path ThreeXThreeCubePuzzleSolver/

# Auto-fix issues
swiftlint --fix

# Strict mode (warnings as errors)
swiftlint lint --strict

# Generate rule documentation
swiftlint rules
```

### Inline Overrides

For valid exceptions:

```swift
// Disable specific rule for next line
// swiftlint:disable:next force_cast
let view = superview as! CustomView

// Disable rule for block
// swiftlint:disable force_unwrapping
let value1 = optional1!
let value2 = optional2!
// swiftlint:enable force_unwrapping

// Disable rule for entire file
// swiftlint:disable file_length
```

## Rule Philosophy

### Enabled by Default

Rules that catch common issues:

- `force_unwrapping`: Encourage safe unwrapping
- `force_cast`: Encourage safe casting
- `line_length`: Maintain readability (120 characters)
- `trailing_whitespace`: Clean code
- `unused_declaration`: Remove dead code

### Opt-in Rules

Additional quality rules:

- `empty_count`: Use `.isEmpty` instead of `.count == 0`
- `first_where`: Use `.first(where:)` instead of `.filter().first`
- `sorted_imports`: Keep imports organized
- `explicit_init`: Be explicit with initializers

### Disabled/Lenient

Rules that may be too strict:

- `function_body_length`: Warning at 40 lines, error at 60
- `type_body_length`: Warning at 300 lines, error at 400
- `identifier_name`: Allow short names for common cases (x, y, z, id)

## Future Enhancements

### SwiftFormat Integration (Optional)

For automatic formatting:

```bash
# Install
brew install swiftformat

# Uncomment in .pre-commit-config.yaml
- id: swiftformat
  entry: swiftformat --lint
  language: system
  types: [swift]
```

### Custom Rules

Can add project-specific rules:

```yaml
custom_rules:
  no_print:
    name: "No Print Statements"
    regex: '\bprint\('
    message: "Use proper logging instead of print()"
    severity: warning
```

### CI Integration

Already integrated in GitHub Actions:

```yaml
# Runs via pre-commit framework
- name: Run CI pipeline
  run: make ci
```

## Maintenance

### Updating SwiftLint

```bash
# Update to latest version
brew upgrade swiftlint

# Update pre-commit hook versions
pre-commit autoupdate
```

### Adding New Rules

1. Review SwiftLint changelog for new rules
2. Test new rules: `swiftlint lint --enable-all-rules`
3. Add desired rules to `opt_in_rules` in `.swiftlint.yml`
4. Update documentation

### Rule Adjustments

Based on team feedback:

- Adjust severity (warning vs. error)
- Modify thresholds (line length, function length)
- Add exceptions (identifier names)
- Document rationale in `.swiftlint.yml` comments
