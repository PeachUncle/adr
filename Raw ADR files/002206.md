# ADR-002: External Secrets Operator Implementation

!!! info "ADR Metadata"
    **Status**: ✅ Accepted  
    **Date**: 2025-10-09  
    **Deciders**: Platform Team, DevOps Team  
    **Last Updated**: 2025-10-09

## Context

To implement our centralized secret management architecture (ADR-001), we need a solution to synchronize secrets from external systems (Azure Key Vault) into Kubernetes clusters. The following options were evaluated:

!!! abstract "Evaluated Options"
1. ⭐ **External Secrets Operator (ESO)**
2. ☁️ **Azure Key Vault Provider for Secrets Store CSI Driver**
3. 📝 **Custom solution using Azure CLI/PowerShell**
4. 📁 **Secrets Store CSI Driver with Azure provider**## Decision

!!! success "Selected Solution"
    We will use **External Secrets Operator (ESO)** version 0.9+ as our secret synchronization solution.

### Key Capabilities Used
!!! info "ESO Components"
- 🗄️ **SecretStore**: Defines connection to Azure Key Vault
- 🔄 **ExternalSecret**: Defines which secrets to sync and how to transform them
- ⬆️ **PushSecret**: For pushing generated secrets back to Azure Key Vault
- 🌍 **ClusterSecretStore**: For cluster-wide secret store definitions### Configuration Approach
```yaml title="ClusterSecretStore Configuration"
apiVersion: external-secrets.io/v1beta1
kind: ClusterSecretStore
metadata:
  name: azure-keyvault-store
spec:
  provider:
    azurekv:
      authType: WorkloadIdentity
      vaultUrl: "https://itl-secrets.vault.azure.net/"
      serviceAccountRef:
        name: external-secrets-operator
        namespace: external-secrets-system
```

## Rationale

!!! tip "Why External Secrets Operator"
1. 🌍 **Vendor Neutral**: Not tied to specific cloud provider
2. 🔍 **Rich Feature Set**: Supports both pull and push patterns
3. 📈 **Active Development**: Strong community and regular updates
4. ☸️ **Kubernetes Native**: Uses CRDs and follows Kubernetes patterns
5. ☁️ **Multi-Provider**: Can work with multiple secret backends
6. 🔄 **Transformation Support**: Built-in secret transformation capabilities!!! warning "Why Not Alternatives"
    - **CSI Driver**: Limited to mount-based access, no push capabilities
    - **Custom Solution**: High maintenance overhead, limited features
    - **Azure Provider Only**: Vendor lock-in, limited functionality

## Implementation Details

### Secret Sync Pattern
```yaml title="ExternalSecret Configuration"
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: app-secrets
  namespace: myapp
spec:
  refreshInterval: 5m
  secretStoreRef:
    name: azure-keyvault-store
    kind: ClusterSecretStore
  target:
    name: app-secrets
    type: Opaque
  data:
  - secretKey: database-password
    remoteRef:
      key: myapp-database-password
```

### Push Secret Pattern
```yaml title="PushSecret Configuration"
apiVersion: external-secrets.io/v1alpha1
kind: PushSecret
metadata:
  name: generated-secret-push
  namespace: myapp
spec:
  updatePolicy: Replace
  deletionPolicy: Delete
  refreshInterval: 10s
  secretStoreRefs:
  - name: azure-keyvault-store
    kind: ClusterSecretStore
  selector:
    secret:
      name: generated-secret
  data:
  - match:
      secretKey: password
      remoteRef:
        remoteKey: myapp-generated-password
```

## Consequences

!!! tip "Positive Outcomes"
- 🔄 **Automatic Synchronization**: Secrets stay in sync without manual intervention
- 📁 **Namespace Isolation**: Each namespace can have its own ExternalSecret definitions
- 🔍 **Audit Trail**: All secret operations are logged and traceable
- ⏱️ **Flexible Refresh**: Configurable refresh intervals per secret
- ⬆️ **Push Capabilities**: Can push generated secrets back to Azure Key Vault!!! warning "Negative Consequences"
    - 🧩 **Additional Complexity**: New CRDs and concepts to learn
    -  **Dependency**: Creates dependency on ESO operator health
    -  **Resource Overhead**: Additional pods and controllers in cluster

!!! danger "Risks and Mitigations"
    **Risk**: ESO operator failure stops secret sync  
    **Mitigation**: High availability deployment, monitoring, backup procedures
    
    **Risk**: Azure API rate limits  
    **Mitigation**: Appropriate refresh intervals, exponential backoff
    
    **Risk**: Secret sync delays  
    **Mitigation**: Monitoring and alerting on sync failures

## Monitoring and Operations

### Key Metrics to Monitor
!!! note "Essential Metrics"
    -  Secret sync success/failure rates
    -  Refresh interval performance
    -  ESO operator health and resource usage
    -  Azure Key Vault API call patterns

### Alerting Criteria
!!! warning "Alert Conditions"
    -  ExternalSecret sync failures > 5 minutes
    -  ESO operator pod restarts
    -  Azure Key Vault connection failures

## Configuration Standards

### Naming Conventions
!!! info "Naming Standards"
    - **SecretStore**: `{environment}-keyvault-store`
    - **ExternalSecret**: `{app-name}-secrets`
    - **Target Secret**: `{app-name}-secrets`

### Refresh Intervals
!!! tip "Environment-Specific Intervals"
    - **Production**: 5 minutes
    - **Development**: 1 minute
    - **Test**: 10 minutes
