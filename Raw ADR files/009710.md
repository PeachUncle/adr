# 003. Frontend DDD Architecture Implementation

**Date:** 2024-11-22

**Status:** ✅ **Accepted**

## Context

The backend API was built using Domain-Driven Design with clear layer separation. However, the React frontend remained coupled to HTTP services with business logic scattered across components and hooks.

When additional features were needed on the frontend, it became difficult to:
- Test business logic in isolation
- Reuse domain models from the backend
- Maintain consistency between frontend and backend architectures
- Scale the frontend codebase cleanly

## Decision

Implement the same 4-layer DDD architecture on the frontend as the backend:

1. **Domain Layer** (reused from `@tasklist/tasks-domain`)
   - Shared business models, entities, value objects
   - Same aggregates and domain logic as backend

2. **Application Layer** (`apps/web/src/application/`)
   - Frontend-specific use cases that orchestrate domain logic
   - Examples: `GetAllTasksUseCase`, `CreateTaskUseCase`, `CompleteTaskUseCase`
   - No HTTP calls; delegates to repository

3. **Infrastructure Layer** (`apps/web/src/infrastructure/`)
   - `HttpTaskRepository` implements the `TaskRepository` interface
   - Maps HTTP DTOs ↔ Domain models
   - `AppContainer` provides dependency injection (Service Locator pattern)

4. **Presentation Layer** (`apps/web/src/presentation/`)
   - React components (UI only)
   - Custom hooks for state management
   - ViewModels to transform domain models for React
   - No direct domain imports in components

## Rationale

### Why Replicate DDD on Frontend?

1. **Consistency**: Frontend and backend architectures match
   - Easier for developers to move between frontend/backend
   - Same business logic location and patterns
   
2. **Reusability**: Share domain models between frontend and backend
   - Package `@tasklist/tasks-domain` used by both
   - Frontend use cases for frontend-specific logic
   - No duplicate entity definitions

3. **Testability**: Isolate business logic from React
   - Use cases test in isolation without mocking React
   - HttpTaskRepository tested separately from components
   - Components focused only on UI, easier to test with React Testing Library

4. **Maintainability**: Clear separation of concerns
   - Frontend developers understand where logic lives
   - Adding features doesn't require understanding entire codebase
   - Easy to spot where a bug likely is

5. **Scalability**: Pattern supports growing complexity
   - Multiple features can use same use cases
   - New developers onboard faster
   - Code review focused on layers (domain, infrastructure, presentation)

### Tradeoffs

**Upside:**
- Cleaner, more maintainable frontend codebase
- Same patterns frontend and backend
- Better testability
- Easier feature additions

**Downside:**
- More files (use cases, view models, repositories)
- Frontend developers need DDD learning curve
- Can feel over-engineered for simple features
- Initial development slower than "quick and dirty"

## Alternatives Considered

1. **Keep simple service-based architecture**
   - ❌ Works for simple apps but doesn't scale
   - ❌ Different patterns between frontend/backend
   - ❌ Business logic scattered across components

2. **Use backend API as the "application layer"**
   - ❌ Can't implement frontend-specific workflows
   - ❌ Frontend still needs orchestration for complex UI flows
   - ❌ Backend becomes bottleneck for frontend logic

3. **Use Redux/MobX for state management instead**
   - ❌ Different from backend patterns (backend has use cases, not stores)
   - ❌ Redux doesn't prevent business logic in components
   - ❌ Doesn't leverage shared domain models

## Consequences

### Positive

- ✅ Frontend and backend use same architectural patterns
- ✅ Domain models reusable across full stack
- ✅ Use cases isolated and fully testable
- ✅ Clear dependency flow: UI → Use Cases → Domain → Repository → HTTP
- ✅ Easier to add new features
- ✅ Easier to teach new developers

### Negative

- ❌ More boilerplate code (use cases, view models, repositories)
- ❌ More files to navigate (but well-organized)
- ❌ Team needs DDD training
- ❌ Initial development takes longer
