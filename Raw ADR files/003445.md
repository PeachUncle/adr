# ADR 4: Use of Nginx Reverse Proxy for Local Development, AWS ALB for Production

**Date:** 2025-17-04  
**Status:** Accepted  

## Summary  
To support local and production routing across multiple services, we chose to use nginx as a reverse proxy for development environments and AWS Application Load Balancer (ALB) for production. This separation allowed us to simulate production-like routing during development without introducing the complexity of cloud services locally, while taking advantage of AWS's managed capabilities in deployment environments.

## Context  
The system architecture consists of multiple independently running containers that represent frontend and backend services. In development, we needed a quick and easily configurable way to route browser and API traffic to the correct containers. Nginx was selected because of its simplicity, community support, and compatibility with Docker Compose. For production, however, AWS ALB provided a managed solution with native ECS integration, health checks, automatic scaling, and security features such as SSL termination. Using ALB ensured we could manage traffic reliably and securely at scale without needing to maintain custom infrastructure.

## Decision  
During local development, we used nginx as a reverse proxy configured via nginx.conf and integrated with Docker Compose for easy service mapping. In production, we defined routing rules using AWS ALB via Terraform, allowing ECS services to register dynamically and route traffic based on URL paths. This hybrid setup balances local simplicity and production-grade robustness.

## Consequences  
**Advantages:**  
- Simple and effective setup for local development.  
- Leverages AWS ALB's managed features in production.  
- Avoids the need for manual load balancing infrastructure.

**Disadvantages:**  
- Developers must maintain separate routing configurations for nginx and ALB.  
- Slight behavioral differences between local and production environments can cause inconsistencies if not well-tested.
