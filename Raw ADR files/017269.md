# ADR-005: Multi-Environment CI/CD with GitHub Actions

## Status
Accepted

## Context

Social Flow requires a robust deployment pipeline that:
- Automates testing to catch bugs early
- Enables frequent, safe deployments
- Supports multiple environments (dev, staging, production)
- Provides rollback capabilities
- Maintains code quality standards
- Integrates security scanning
- Scales with team growth

Manual deployments are error-prone, slow, and don't scale. We need automated CI/CD that provides confidence in releases while maintaining velocity.

## Decision

We will implement **multi-environment CI/CD using GitHub Actions** with separate workflows for:
1. **Continuous Integration (CI)**: Code quality, testing, security scanning
2. **Continuous Deployment (CD)**: Automated deployment to staging and production
3. **Release Management**: Semantic versioning and changelog generation

### Pipeline Architecture

**CI Workflow** (runs on every push/PR):
- Code quality checks (TypeScript, ESLint, Prettier)
- Unit tests with coverage
- Integration tests with service containers
- E2E tests (Playwright, 4-shard parallel)
- Performance tests (k6)
- Security scanning (Trivy)
- Build and artifact creation

**CD Workflow** (environment-specific):
- **Staging**: Auto-deploy from `main` branch
- **Production**: Deploy from tags matching `v*.*.*`
- Includes: CDK deployment, migrations, cache invalidation, smoke tests

**Release Workflow**:
- Automated semantic versioning (release-please)
- Changelog generation
- npm package publishing
- GitHub release creation

## Consequences

### Positive

- **Faster deployments**: From hours to minutes
- **Higher confidence**: Comprehensive testing before deployment
- **Consistency**: Same process every time
- **Rollback capability**: Easy revert to previous versions
- **Audit trail**: All deployments tracked in GitHub
- **Team scalability**: New developers can deploy safely
- **Quality gates**: Enforce standards automatically
- **Security visibility**: Vulnerabilities caught early

### Negative

- **Initial setup time**: Complex workflow configuration
- **GitHub Actions costs**: Compute minutes charged (but free tier generous)
- **Lock-in**: Tightly coupled to GitHub
- **Debugging difficulty**: CI failures can be hard to debug locally
- **Secret management**: Requires careful handling of credentials

### Risks

- **Pipeline downtime**: GitHub Actions outage blocks deployments
  - *Mitigation*: Manual deployment scripts as backup
- **Secret exposure**: Misconfigured secrets could leak
  - *Mitigation*: Protected environments, secret scanning
- **Flaky tests**: Intermittent test failures block deployments
  - *Mitigation*: Test retry logic, quarantine flaky tests
- **Cost overrun**: High compute usage in large teams
  - *Mitigation*: Optimize workflows, use caching, monitor usage

## Implementation Details

### CI Workflow Structure

```yaml
name: CI

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main, develop]

jobs:
  code-quality:
    # TypeScript, ESLint, Prettier, npm audit
  
  unit-tests:
    # Jest with coverage, upload to Codecov
  
  integration-tests:
    # LocalStack, Redis, OpenSearch containers
  
  e2e-tests:
    strategy:
      matrix:
        shard: [1, 2, 3, 4]
    # Playwright parallel execution
  
  performance-tests:
    if: github.ref == 'refs/heads/main'
    # k6 load testing
  
  security-scan:
    # Trivy vulnerability scanning
  
  build:
    # TypeScript build, artifact upload
  
  coverage-report:
    # Aggregate coverage, PR comments
  
  notify:
    # Pipeline status notification
```

### CD Workflow Structure

```yaml
name: CD

on:
  push:
    branches: [main]
    tags: ['v*.*.*']
  workflow_dispatch:

jobs:
  deploy-staging:
    if: github.ref == 'refs/heads/main'
    environment: staging
    # CDK deploy, migrations, smoke tests
  
  deploy-production:
    if: startsWith(github.ref, 'refs/tags/v')
    environment: production
    # Backup, CDK deploy, migrations, monitoring
  
  rollback:
    if: github.event_name == 'workflow_dispatch'
    # Emergency rollback capability
```

### Environment Configuration

**Staging Environment:**
- No protection rules (auto-deploy)
- Secrets: AWS credentials, staging-specific configs
- Environment URL: staging-api.socialflow.example.com

**Production Environment:**
- Required reviewers: 2
- Only deploy from tags
- Secrets: AWS credentials, production configs
- Environment URL: api.socialflow.com

### Optimization Strategies

**1. Caching:**
```yaml
- uses: actions/cache@v3
  with:
    path: |
      ~/.pnpm-store
      node_modules
    key: ${{ runner.os }}-pnpm-${{ hashFiles('**/pnpm-lock.yaml') }}
```

**2. Parallel Execution:**
```yaml
strategy:
  matrix:
    node-version: [20]
    shard: [1, 2, 3, 4]
```

**3. Conditional Jobs:**
```yaml
if: github.event_name == 'push' && github.ref == 'refs/heads/main'
```

**4. Artifact Sharing:**
```yaml
- uses: actions/upload-artifact@v3
  with:
    name: build-artifacts
    retention-days: 7
```

### Security Measures

**Secret Scanning:**
```yaml
- name: Security Scan
  uses: aquasecurity/trivy-action@master
  with:
    scan-type: 'fs'
    severity: 'CRITICAL,HIGH'
```

**Protected Environments:**
- Production requires manual approval
- Environment secrets isolated
- Branch protection rules enforced

**SARIF Upload:**
```yaml
- uses: github/codeql-action/upload-sarif@v2
  with:
    sarif_file: 'trivy-results.sarif'
```

## Alternatives Considered

### Jenkins

**Pros:**
- Flexible, powerful
- Self-hosted (no vendor lock-in)
- Mature ecosystem
- Free

**Cons:**
- Infrastructure overhead
- Maintenance burden
- Security responsibility
- Slower than cloud CI

**Why not chosen:** GitHub Actions integrates better with our GitHub workflow, requires no infrastructure management.

### GitLab CI

**Pros:**
- Integrated with GitLab
- Good Docker support
- Auto DevOps features

**Cons:**
- Would require migrating from GitHub
- Learning curve
- Less community support

**Why not chosen:** Already using GitHub, would require repo migration.

### CircleCI

**Pros:**
- Fast, reliable
- Good Docker support
- Nice UI
- Free tier

**Cons:**
- Additional tool to manage
- Cost at scale
- Less GitHub integration
- Vendor lock-in

**Why not chosen:** GitHub Actions provides similar capabilities with better GitHub integration.

### AWS CodePipeline

**Pros:**
- Native AWS integration
- No vendor lock-in for CI
- Integrates with CodeBuild, CodeDeploy

**Cons:**
- More complex setup
- Limited free tier
- Less flexible than GitHub Actions
- Worse developer experience

**Why not chosen:** GitHub Actions provides better developer experience and is more familiar to team.

### Manual Deployment Scripts

**Pros:**
- Full control
- No external dependencies
- No cost

**Cons:**
- Error-prone
- Slow
- No testing automation
- Doesn't scale
- No audit trail

**Why not chosen:** Doesn't meet requirements for automated testing and safe deployments.

## Best Practices

### 1. Test Locally First

```bash
# Run same checks as CI
pnpm run type-check
pnpm run lint
pnpm test
pnpm run build
```

### 2. Keep Workflows DRY

Use reusable workflows and composite actions:

```yaml
# .github/workflows/deploy.yml (reusable)
on:
  workflow_call:
    inputs:
      environment:
        required: true
        type: string
```

### 3. Fast Feedback

- Run quick tests first (linting, type checking)
- Fail fast on errors
- Parallel execution where possible

### 4. Semantic Versioning

Use Conventional Commits:
- `feat:` → minor version bump
- `fix:` → patch version bump
- `BREAKING CHANGE:` → major version bump

### 5. Rollback Plan

Always have a rollback strategy:
- Tag previous versions
- Backup before deployment
- Smoke tests after deployment
- Rollback workflow ready
