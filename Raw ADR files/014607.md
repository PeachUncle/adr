# Quick Reference: Determinism Evaluation

**For:** Quick review before discussion  
**See Full Analysis:** DEC-0010_DETERMINISM_ENFORCEMENT_EVALUATION.md

---

## The Question

**Should we relax determinism enforcement during development/draft phases?**

---

## Current State (Strict Always)

```yaml
dependencies:
  - package: base
    version: "1.0.0"  # MUST be exact - no exceptions
```

**Pros:**
- ✅ Simple to understand and implement
- ✅ Guaranteed determinism forever
- ✅ No surprises

**Cons:**
- ⚠️ Manual version updates for every bug fix
- ⚠️ Can't auto-benefit from dependency improvements
- ⚠️ Iterative development friction

---

## Proposed Alternative (Draft Mode)

```yaml
# During development
metadata:
  version: "0.5.0-draft"  # -draft suffix = flexible mode

dependencies:
  - package: base
    version: "^1.0.0"  # Flexible constraint OK in draft
```

```yaml
# After finalization (remove -draft)
metadata:
  version: "0.5.0"  # Release mode = strict

dependencies:
  - package: base
    version: "^1.0.0"  # ERROR: Must be exact in release mode
    # Fix: Change to version: "1.0.0"
```

**Pros:**
- ✅ Better developer experience
- ✅ Auto-updates during development
- ✅ Strict guarantees for releases

**Cons:**
- ⚠️ Two validation modes to implement
- ⚠️ More complex to understand
- ⚠️ Authors must remember to finalize

---

## Key Insight: Patch Versions in Our Domain

In typical semver:
- Patch (1.0.0 → 1.0.1) = bug fixes, no API changes

In our domain:
- Typo fix: `"colour"` → `"color"` = **output changes** (intentional)
- Weight fix: `weight: 10` → `weight: 1` = **output changes** (intentional)
- Rule fix: condition logic → **output changes** (intentional)

**Implication:** Even "bug fixes" break determinism in prompt generation!

## Options Summary

| Option | Complexity | DX | Determinism | Recommendation |
|--------|------------|----|--------------|----------------|
| **A. Status Quo** | 🟢 Low | ⚠️ Acceptable | ✅ Perfect | **v1.0.0** ✅ |
| **B. Draft Mode** | ⚠️ Medium | ✅ Good | ✅ For releases | v1.1.0 (if needed) |
| **C. Semver Inference** | ⚠️ Medium | ✅ Good | ✅ For v1.0.0+ | v1.1.0 alternative |
| **D. Lock Files** | 🔴 High | ✅ Best | ✅ Perfect | v1.2.0+ |

---

## Recommendation

### For v1.0.0 (Now)
**Keep strict exact matching (Option A)**

Why?
- ✅ Simple to explain and implement
- ✅ Clear guarantees from day one
- ✅ Can add flexibility later (non-breaking)
- ✅ Gather real feedback before optimizing

### For v1.1.0 (Later, if needed)
**Consider draft mode (Option B) based on user feedback**

If users say: "Manual version management is painful!"
→ Add draft mode

If users say: "Exact versions are fine"
→ Keep as-is

### For M12 Marketplace (Future)
**Implement lock files (Option D) with marketplace**

This is the "proper" solution:
- Industry-standard pattern (npm, yarn, cargo)
- Flexible constraints + determinism guarantees
- Marketplace needs resolution anyway
- **Note:** M12 focuses on package registry and discovery, perfect timing for lock files

---

## Discussion Questions

1. **How important is DX friction vs. guarantees?**
   - Are we optimizing for authors or consumers?
   - Most packages consumed, few authored
   
2. **Can we gather early feedback?**
   - Test with internal packages first?
   - Beta testers before v1.0.0?
   
3. **Is draft mode worth the complexity?**
   - 2 validation modes to test
   - Authors must understand mode semantics
   
4. **Should we plan lock files from the start?**
   - Even if implementing in v1.2.0
   - Affects dependency design decisions now

## Decision Checklist

Before deciding, consider:

- [ ] **Simplicity:** Which option is easiest to explain?
- [ ] **Stability:** Which guarantees are non-negotiable?
- [ ] **Flexibility:** Can we change later without breaking v1.0.0?
- [ ] **Feedback:** Do we have real user needs or guessing?
- [ ] **Implementation:** How much work for each option?
- [ ] **Documentation:** How much to explain to users?

## Bottom Line

**The safe, simple choice:** Keep strict (Option A)
- Ship v1.0.0 with clear guarantees
- Iterate based on real feedback
- Add features in v1.1.0+ if needed

**The ambitious choice:** Implement draft mode (Option B)
- Better DX from day one
- More complex, more to test
- Risk: Complexity might not be needed

**Recommendation:** **Keep strict for v1.0.0** ✅
