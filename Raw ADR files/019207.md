# ADR-010: Adapter Pattern for Cross-Module Communication

## Status

Accepted

## Context

In a modular monolith architecture with per-module DbContexts, modules need to access data from other modules without violating module boundaries. The key challenges are:

1. **Module Isolation**: Modules should not directly reference each other's infrastructure or repositories
2. **Data Access**: Modules need read access to other modules' data (e.g., Users module needs artist names, Artists module needs user info)
3. **Avoid Circular Dependencies**: Direct module-to-module references create circular dependencies
4. **Type Safety**: Need compile-time type checking for cross-module calls
5. **Testability**: Should be able to mock cross-module dependencies in tests
6. **Performance**: Minimize overhead of cross-module communication
7. **Future Extraction**: Should support eventual extraction to microservices

Several approaches were considered:

**Option 1: Direct Module References**
- Modules directly reference other modules' Application layer
- Simple but creates tight coupling and circular dependencies

**Option 2: Shared DTOs in Shared Kernel**
- All DTOs in Shared.Application
- Violates module autonomy, creates god object problem

**Option 3: Event-Driven Only**
- All cross-module communication via events
- Too slow for synchronous read operations

**Option 4: Adapter Pattern**
- Each module defines interfaces for what it needs from other modules
- Separate adapter projects implement these interfaces
- Adapters translate between module-specific DTOs

## Decision

We will use the **Adapter Pattern** for synchronous cross-module data access:

**Architecture:**
```
Module A (Consumer)
    ↓ depends on
Interface (defined in Module A)
    ↑ implemented by
Adapter Project (separate)
    ↓ depends on
Module B (Provider)
```

**Structure:**
```
server/src/
├── Modules/
│   ├── Users/
│   │   └── Application/
│   │       └── Interfaces/
│   │           └── IArtistServiceAdapter.cs  # Users defines what it needs
│   └── Artists/
│       └── Application/
│           └── Services/
│               └── ArtistsAdapterSupportService.cs  # Artists exposes data
└── Adapters/
    └── Artists.Users.Adapter/
        └── ArtistServiceAdapter.cs  # Adapter implements interface
```

**Key Principles:**

1. **Consumer Defines Interface**: The module that needs data defines the interface
   ```csharp
   // In Users.Application
   public interface IArtistServiceAdapter
   {
       Task<ArtistWithPortfolioDto?> GetArtistByIdAsync(Guid artistId);
       Task<List<ArtworkDto>> GetArtworksByIdsAsync(IEnumerable<Guid> artworkIds);
   }
   ```

2. **Provider Exposes Support Service**: The module that owns data exposes an adapter support service
   ```csharp
   // In Artists.Application
   public class ArtistsAdapterSupportService
   {
       public async Task<ArtistProfileDto?> GetArtistByIdAsync(Guid artistId) { }
       public async Task<List<ArtworkDto>> GetActiveArtworksByIdsAsync(...) { }
   }
   ```

3. **Adapter Translates**: Separate adapter project implements interface using support service
   ```csharp
   // In Artists.Users.Adapter project
   public class ArtistServiceAdapter : IArtistServiceAdapter
   {
       private readonly ArtistsAdapterSupportService _adapterService;
       
       public async Task<ArtistWithPortfolioDto?> GetArtistByIdAsync(Guid artistId)
       {
           var artist = await _adapterService.GetArtistByIdAsync(artistId);
           return MapToAdapterDto(artist); // Translate DTOs
       }
   }
   ```

4. **Dependency Injection**: Adapters registered in adapters extension startup
   ```csharp
   // In Api/Extensions/AdaptersExtensions.cs
   services.AddScoped<IArtistServiceAdapter, ArtistServiceAdapter>();
   ```

**Naming Convention:**
- Interface: `I{Provider}ServiceAdapter` (e.g., `IArtistServiceAdapter`)
- Support Service: `{Provider}AdapterSupportService` (e.g., `ArtistsAdapterSupportService`)
- Adapter Project: `{Provider}.{Consumer}.Adapter` (e.g., `Artists.Users.Adapter`)
- Adapter Class: `{Provider}ServiceAdapter` (e.g., `ArtistServiceAdapter`)

## Consequences

### Positive

- **Module Independence**: Modules don't directly reference each other
- **No Circular Dependencies**: Adapter projects break circular dependency chains
- **Type Safety**: Compile-time checking of cross-module calls
- **Testability**: Easy to mock adapters in unit tests
- **Clear Contracts**: Interfaces document what each module needs from others
- **DTO Translation**: Each module uses its own DTOs, adapters translate
- **Future Microservices**: Adapters can be replaced with HTTP clients when extracting services
- **Explicit Dependencies**: Easy to see what data each module needs
- **Versioning**: Can version adapter interfaces independently

### Negative

- **Additional Projects**: Each adapter requires a separate project (more complexity)
- **DTO Duplication**: Similar DTOs exist in multiple modules (e.g., `UserDto` in Auth, Artists, Users)
- **Mapping Overhead**: Adapters must map between different DTO types
- **More Code**: Requires interface, support service, adapter, and DTO mapping
- **Learning Curve**: Team must understand adapter pattern and when to use it
- **Maintenance**: Changes to data structures require updating multiple DTOs and mappings
- **Performance Overhead**: Extra layer of indirection and DTO mapping

### Neutral

- **Adapter Projects Location**: Separate `Adapters/` directory at solution level
- **Support Services**: Each module exposes one support service for all adapters
- **DTO Ownership**: Each module owns its DTOs, adapters translate between them
- **Registration**: All adapters registered in API startup, not in modules

## Implementation Guidelines

### When to Use Adapters

**Use Adapters For:**
- ✅ Synchronous read operations (get user, get artist, get artwork)
- ✅ Data needed for display or validation
- ✅ Cross-module queries that need immediate response

**Don't Use Adapters For:**
- ❌ Write operations (use events instead)
- ❌ Complex business logic (keep in owning module)
- ❌ Data that can be denormalized (store locally)
- ❌ Async operations that can wait (use events)

### Performance Considerations

- **Batch Operations**: Prefer `GetByIdsAsync` over multiple `GetByIdAsync` calls
- **Caching**: Consider caching frequently accessed data (future)
- **Projection**: Support services should only fetch needed fields
- **Pagination**: Support pagination for list operations
- **Async All The Way**: All adapter methods should be async

## Alternatives Considered

**Direct Module References:**
- Pros: Simpler, no adapter projects, direct access
- Cons: Circular dependencies, tight coupling, hard to extract
- Rejected: Violates module independence

**Shared DTOs in Shared Kernel:**
- Pros: No DTO duplication, single source of truth
- Cons: God object problem, modules lose autonomy, tight coupling
- Rejected: Violates module ownership

**Event-Driven Only:**
- Pros: Complete decoupling, async by default
- Cons: Too slow for synchronous reads, eventual consistency issues
- Rejected: Not suitable for immediate data needs

**Mediator Pattern (MediatR):**
- Pros: Decoupled, in-process messaging
- Cons: Harder to discover dependencies, runtime errors, less type-safe
- Rejected: Prefer compile-time safety of interfaces

**Service Locator:**
- Pros: No explicit dependencies
- Cons: Anti-pattern, hides dependencies, runtime errors
- Rejected: Violates dependency inversion principle

## Migration to Microservices

When extracting a module to a microservice, adapters provide a clean migration path:

**Before (Monolith):**
```csharp
public class ArtistServiceAdapter : IArtistServiceAdapter
{
    private readonly ArtistsAdapterSupportService _service;
    
    public async Task<ArtistDto> GetArtistByIdAsync(Guid id)
    {
        return await _service.GetArtistByIdAsync(id);
    }
}
```

**After (Microservice):**
```csharp
public class ArtistServiceAdapter : IArtistServiceAdapter
{
    private readonly HttpClient _httpClient;
    
    public async Task<ArtistDto> GetArtistByIdAsync(Guid id)
    {
        return await _httpClient.GetFromJsonAsync<ArtistDto>($"/api/artists/{id}");
    }
}
```

Consumer code remains unchanged - only adapter implementation changes!
