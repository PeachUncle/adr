# CLI Does Not Deploy

## Context and Problem Statement

CAIRA is targeted at deploying into both "green field" (fresh) and "brown field" (existing) environments. In the initial phase, we’re targeting DevOps-aware professionals who are confortable with using Terraform for managing deployments (such as SDEs in an ISE crew).

How do we use our CLI to easily support both types of environments, given that both can have significant constraints and existing IT and security policies from the customer?

<!-- This is an optional element. Feel free to remove. -->
## Decision Drivers

* Output supports "green field" and "brown field" deployments
* Invoking the CLI, in and of itself, will not violate any customer constraints or security policies
* It should be easy to decouple errors in the CLI from errors in deployment

## Considered Options

* CLI Creates Deployment Configuration
* CLI Creates Deployment Configuration and Deploys to Environment

## Decision Outcome

Chosen option: "CLI Creates Deployment Configuration", because it allows for easy decoupling of the deployment configuration and deployment steps.

### Consequences

* Good, because it ensures easy debuggability of CLI errors vs. deployment errors
* Good, because it gives an opportunity for customer security review of any deployment before committing
* Good, because it allows any required modifications to fit into existing "brown field" environments
* Bad, because it requires end users of the CLI to understand how to deploy environment configuration scripts (e.g. Terraform) into their environment

## Pros and Cons of the Options

### CLI Creates Deployment Configuration and Deploys to Environment

In this case, the CLI would create the environment configuration and then deploy it into Azure.

* Good, because end users would not need any knowledge of how to deploy resources _in sunny-day scenarios_
* Bad, because it is more difficult to diagnose issues as stemming from CLI or deployment
* Bad, because customer policy/security review becomes challenging as they have bespoke requirements and access control for deployments
* Bad, because it makes it difficult to modify the deployment configuration to adhere to any customer-specific requirements (e.g. for "brown field" deployments)
* Bad, because any errors in deployment will require intervention from DevOps-aware users, negating the one "Good" aspect
* Bad, because users of CAIRA will expect CAIRA members to support/fix/troubleshoot any failures in deployment
* Bad, as it creates an expectation of backward compatibility, with users attempting to re-deploy a modified RA into the same environment in a single step
