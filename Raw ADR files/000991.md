# Different options for creating and maintaining different CAIRA modules and reference architectures

## Context and Problem Statement

Extension to [ADR 0003](./0003-options-for-creating-IaC.md)

As there's increasing adoption for Azure Verified Modules (AVMs) and CAIRA modules, we are revisiting the decision made in ADR 0003 to consider additional factors especially with emphasis on ongoing support, maintenance and large scale adoption. This decision also impacts our repository structure and direction when CAIRA goes public/open source.

## Key terminology

*Resource module:* A **Resource module** represents a single Azure service and contains the relevant AVM (Azure Verified Module) infrastructure as code (IaC) to deploy the service.

*Functional module:* A **Functional module** is a grouping of **Resource modules** that are typically deployed together. These form the main building blocks of a reference architecture.

*Reference Architecture:* A combination of pre-configured **Resource modules** grouped together in one or more **Functional modules** that are typically required to deliver a specific customer use case that conform to security best practices, amongst others.

*AVM pattern module*: A reusable IaC template or blueprint that adheres to Microsoft’s standards and best practices for deploying Azure resources. These modules encapsulate specific architectural patterns or solutions, ensuring consistency, reliability, and compliance across deployments.

## Decision Drivers

* Consistency in IaC templates across Microsoft
* Dependencies and layers of abstraction
* Adherence to Best Practices
* Long term sustainable Support and Maintenance
* Ease of Testing & Comprehensive Testing
* Development Velocity
* Ease of Adoption/Consumption for crews and any users
* Facilitate Contribution
* Extensibility/Flexibility to extend
* Broader availability to Microsoft customers

## Considered Options

* **Option 1**: Use AVM Resource modules to build out CAIRA owned Functional modules and Reference Architectures (current state).
* **Option 2**: Use AVM Resource modules, create new AVM Pattern modules for CAIRA functional modules and maintain reference architecture and capabilities in CAIRA repo. The reference architectures would demonstrate usage of AVM Resource and AVM Pattern modules for specific scenarios.
* **Option 3**: Use AVM Resource modules and create new AVM Pattern modules for CAIRA core & AI functional modules and for reference architectures. Keep guidance, ADRs, capabilities in ISE Playbook or Azure Docs that references the respective AVM pattern modules for different architectures/usecases.

## Decision Outcome

Option 2: Use AVM Resource modules, create new AVM Pattern modules for CAIRA's functional modules. Maintain the reference architecture and capabilities in the
CAIRA repository. The reference architectures will make use of AVM Resource and AVM Pattern modules for defined scenarios.

This option offers control and flexibility in extending and maintaining CAIRA's reference architectures while simplifying the IaC setup for both our crews and customers. It strikes a balanced approach, combining the benefits of AVM modules with the CAIRA repository (and our goal for MCSB compliant modules as baseline). This enables us to maintain control, test, and enhance AI reference architectures, while gradually adopting the structure of AVM pattern modules. By doing so, we can streamline the use of CAIRA reference architectures and continue improving the overall user experience. Adopting Azure Verified Pattern Modules also ensures alignment with best practices, enhanced security, and easier integration with Azure services, all of which drive efficiency and reliability in our deployments.

* We will designate a group of ISE members to own and maintain each AVM pattern module that we create.
* We will adhere to the [AVM support and maintenance model](https://azure.github.io/Azure-Verified-Modules/help-support/module-support/)
* We will continue to maintain Azure subscriptions to conduct comprehensive testing for the reference architectures and any pattern modules, as needed.
* On a case-by-case basis, an identified set of team members and the Product Owner will be responsible for reviewing and assisting in decisions regarding the creation of a pattern module versus a reference architecture

> NOTE:
>
> In some instances, the team may have the need for a resource for which there might not
> be an AVM module readily available.
> In those cases, the implementation can be done using a local module definition, but the need for the AVM module must be tracked with a task.

## Pros and Cons of the Options

### Option 1: Use AVM Resource modules to build out CAIRA owned modules and reference architectures (Current CAIRA)

#### Good (Current CAIRA)

* Complete control and flexibility in the modules we create and own
* Single place/repo for consumption for crews/users
* Single place/repo for contribution except when they need to add new AVM resource modules
* Flexibility in the level of integration testing and extensive tests we want to add for the reference architectures
* High Developer velocity as few dependencies on AVM team

#### Bad (Current CAIRA)

* Dedicated and deep investment needed for support and maintenance of repo especially when we go public.
* Requires regular and long-term maintenance of multiple Azure subscriptions for running tests and pipelines
* Requires separate/dedicated effort to make it easily discoverable beyond ISE. ISE is an internal Microsoft organization and should utilize existing Microsoft systems for contributions.
* Requires guidance/support for users/crews on how to mix/match different CAIRA owned modules to create their own reference architecture per project requirements
* For composability and ease of use, may require deep investment in UX tools or integration with existing Microsoft-wide developer cli tools like azd
* No catchers yet

### Option 2: Use AVM Resource modules and create new AVM Pattern modules for CAIRA functional modules and keep reference architecture (that use the AVM Resource + Pattern modules) capabilities in CAIRA repo

#### Good (AVM Resource + AVM Pattern + only RA in CAIRA)

* Leverage AVM long-term support model for all modules consistently (resource & pattern modules)
* Wider reach/adoption & discoverability for anybody who use AVM (and the adoption numbers for AVM is growing). The ISE investment in developing AVMs results in broader impact and utilizes a OneMicrosoft approach for contributing to existing systems.
* Baseline tests/pipelines for the pattern modules will be run and maintained by AVM core team in their subscriptions
* Fewer abstraction layers within CAIRA as reference architectures will take dependency on AVM resource & pattern modules
* Provides flexibility in reusing/extending available pattern modules in a reference architecture

#### Bad (AVM Resource + AVM Pattern + only RA in CAIRA)

* Creates ambiguity on when to create a CAIRA reference architecture versus an AVM pattern module. Can cause confusion. Requires clear guidance and possibly a review committee to decide when it should be an AVM pattern module versus a RA in CAIRA repository.
* Contribution from crews may need to be done across multiple repos if there is a pattern module change needed; Has a learning curve for stitching together AVM resource & AVM CAIRA Pattern Modules to create a new RA
* Effort needed to move CAIRA owned functional modules to AVM pattern modules. This would be a one-time cost to begin-with.
* Requires a dedicated subscription(s) and maintenance of the subscription for running RA tests & pipelines

### Option 3: Use AVM Resource modules + create new AVM Pattern modules for caira core, caira ai, etc. + create new AVM Pattern modules for reference architectures + keep guidance is ISE playbook or Azure Docs that references the respective AVM pattern modules for different architectures

#### Good (AVM all the way)

* Leverage AVM long-term support model for all modules consistently (resource & pattern modules)
* Wider reach/adoption & discoverability for anybody who use AVM (and the adoption numbers for AVM is growing).  The ISE investment in developing AVMs results in broader impact and utilizes a OneMicrosoft approach for contributing to existing systems.
* Baseline tests/pipelines for the pattern modules will be run and maintained by AVM core team in their subscriptions
* No ambiguity for contributors on when to create Pattern modules versus CAIRA reference architectures as everything will be a pattern module.
* Provides flexibility & composability in reusing/extending available pattern modules in a reference architecture. There are strong signals from the crews that this is the desired level of composability.

#### Bad (AVM all the way)

* Not easy/possible to mandate MCSB compliance across all pattern modules
* Requires learning curve for consumption by crews and for contributors especially since this option will create a dependency between pattern modules when creating a RA, as is the case for any contribution for other options too.
* Will need to rely on AVM's testing strategy for the pattern modules. To mitigate this, we can continue to maintain a dedicated subscription for any comprehensive tests that are not already included in the AVM run pipelines.
* Effort needed to move CAIRA modules to AVM pattern modules.
* Crew contributions will require collaboration with the AVM team (external to ISE) to triage requests and review changes with module owner(s), which may result in longer timelines.
