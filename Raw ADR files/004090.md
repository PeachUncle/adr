# ADR-001: Start with Monolith First (V1)

**Date:** 2025-12-13  
**Status:** Accepted  
**Author:** Samuel Erlangga  
**Context:** V1 - Initial Implementation

---

## Context

### Business Context

SynergySpace is a brain-surfing notes & publishing platform that allows creators to:

1. Take private notes with backlinks (Obsidian-style)
2. Publish notes with one click, preserving backlinks for audience exploration

This is a **learning project** focused on understanding distributed systems architecture through iterative evolution.

### Technical Context

- **Current state:** Empty repository, starting from scratch
- **Goal:** Build a working product that teaches distributed systems concepts
- **Constraint:** Solo developer learning journey (not a production launch)

### Forces at Play

- **Learning priority:** Need to understand fundamentals before complexity
- **Time:** Building incrementally over 16 weeks across 4 versions
- **Complexity:** Want to eventually learn microservices, but need foundation first
- **Risk:** Premature optimization could obscure learning

---

## Decision

**We will start with a monolithic ASP.NET Core MVC application for V1.**

### Implementation Approach

- Single ASP.NET Core MVC project
- Single SQLite database (file-based, zero setup)
- ASP.NET Identity for authentication
- Entity Framework Core for data access
- Razor views + JavaScript for UI

All features (notes, backlinks, publishing) in one codebase initially.

**Database Choice:** SQLite for V1 because:

- Zero configuration (no server setup)
- Perfect for learning (focus on app logic, not DB admin)
- Easy to reset/backup (just delete the .db file)
- Completely free
- Can migrate to PostgreSQL/SQL Server in V2+ for learning purposes

---

## Consequences

### Positive ✅

- **Fast iteration:** No service boundaries to cross, no network calls to debug
- **Simple deployment:** One application to deploy and run
- **Easy debugging:** Single process, step through entire request
- **Learn fundamentals:** MVC patterns, EF Core, authentication before distributed complexity
- **Clear baseline:** Establishes working product before architectural changes
- **Natural bottlenecks emerge:** Will experience real pain points that justify service split

### Negative ❌

- **No distributed systems practice yet:** Won't learn service-to-service auth, retries, etc. initially
- **Will require refactoring:** Moving to microservices (V2) requires code reorganization
- **Not resume-worthy alone:** Needs evolution to V2-V4 to demonstrate advanced skills

### Neutral ⚪

- This is **intentionally temporary** - V1 is foundation for V2-V4
- Trade-off: Short-term simplicity for long-term learning path

---

## Alternatives Considered

### Alternative 1: Start with Microservices from Day 1

**Description:** Build separate Auth API, Notes API, Publishing API immediately

**Pros:**

- Looks impressive on resume
- Forces learning distributed patterns early
- "Industry best practice" for SaaS

**Cons:**

- **Premature complexity:** Adding service boundaries before understanding domain
- **Slower learning:** Debugging network issues before mastering MVC basics
- **Unjustified architecture:** No performance data to justify split
- **Analysis paralysis:** Too many design decisions upfront

**Why Rejected:**
Following the principle "Start Simple, Justify Complexity" - we should split services when we can articulate **WHY** based on real problems (scaling, security isolation, team ownership), not because it's trendy.

---

### Alternative 2: Build as Separate Services but Deploy as Monolith

**Description:** Use modular monolith pattern with clear service boundaries, deploy as one

**Pros:**

- Cleaner internal architecture
- Easier migration to microservices later
- Enforces bounded contexts

**Cons:**

- **More abstraction than needed:** V1 is simple enough not to need this
- **Slower initial development:** More interfaces, more indirection
- **Doesn't teach distributed systems pain:** Still one process, no network calls

**Why Rejected:**
Good middle ground, but adds ceremony without adding learning value at this stage. Better to experience the pain of tight coupling first, then appreciate clean boundaries in V2.

---

### Alternative 3: Serverless (Azure Functions)

**Description:** Build as independent Azure Functions from start

**Pros:**

- Auto-scaling
- Pay per use
- No server management

**Cons:**

- **Wrong learning path:** Skips fundamentals (HTTP, state management, connection pooling)
- **Hidden complexity:** Cold starts, function chaining, durable functions
- **Local development harder:** Requires emulators

**Why Rejected:**
Serverless is an advanced pattern. Need to understand traditional web apps first.

## Implementation Notes

### Technical Details

**Project Structure:**

```
MainApp/
├── Controllers/       # MVC controllers
├── Models/           # Entity models (User, Note, Tag, Backlink)
├── Services/         # Business logic (BacklinkParser, NoteService)
├── Data/             # DbContext, migrations
├── Views/            # Razor views
└── wwwroot/          # Static files (CSS, JS)
```

**Key Dependencies:**

- `Microsoft.AspNetCore.Mvc` (ASP.NET Core MVC)
- `Microsoft.EntityFrameworkCore.SqlServer` (EF Core)
- `Microsoft.AspNetCore.Identity.EntityFrameworkCore` (Authentication)
- `Markdig` (Markdown parsing)

**Database Tables:**

- `Users` (from ASP.NET Identity)
- `Notes` (Id, UserId, Title, Body, IsPublished, Slug, CreatedAt, UpdatedAt)
- `Tags` (Id, UserId, Name)
- `NoteTags` (NoteId, TagId)
- `Backlinks` (Id, SourceNoteId, TargetNoteId, LinkText)

## Validation

**How will we know V1 was the right starting point?**

### Success Criteria

- ✅ **Working product in 4 weeks:** User can register, create notes, see backlinks, publish notes
- ✅ **Clear understanding of domain:** Data model and business logic are well-understood
- ✅ **Identified bottlenecks:** Can articulate specific reasons to split services in V2
- ✅ **Test coverage:** >70% code coverage with clear test structure

### Metrics to Track

- **Development velocity:** Features completed per week
- **Bug rate:** Issues found per feature
- **Learning milestones:** MVC patterns, EF Core migrations, authentication flows

### Review Date

**Schedule review on:** End of Week 4 (after V1 completion)

**Questions to ask at review:**

1. Do we understand the core domain well enough to split it?
2. What would be hard to change in this monolith?
3. Where would we draw service boundaries if we split today?
4. What performance bottlenecks emerged (if any)?

**Trigger for V2:**
When we can answer: "We should split Auth/License into separate service because [specific reason: security isolation, different scaling needs, team ownership]"
