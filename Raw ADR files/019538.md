# ADR-0005: Design Token Architecture with Hybrid Approach

**Status:** ✅ Accepted
**Date:** 2025-10-12
**Deciders:** Developer + Claude
**Impact:** 🔴 HIGH (Foundation for entire design system)
**Technical Story:** Design token system strategy decision

## Context

We need to establish a design token architecture for our UI library. This decision impacts:
- **Developer Experience:** How developers define and use design tokens
- **Performance:** Build-time vs runtime token processing
- **Maintainability:** How easy to add/modify tokens
- **Flexibility:** Theme customization capabilities
- **Future-proofing:** Alignment with modern tooling (Tailwind v4)
- **Bundle Size:** Dependencies and generated code

### Research Findings

**HeroUI (formerly NextUI) Analysis:**
- Uses Tailwind v4 (`tailwindcss: "4.1.11"`) but keeps v3-style plugin pattern
- Does NOT use `@theme` directive
- Plugin auto-generates CSS variables from JS config
- Runtime color manipulation (HSL conversion, foreground calculation)
- Dependencies: `color`, `color2k`, `deepmerge`, `flat`
- **Why they kept plugin:** Legacy compatibility, extensive theme API, enterprise stability

**Tailwind v4 Native Approach:**
- New `@theme` directive for CSS-first configuration
- Native CSS variables (no JS required)
- Direct utility generation from theme definitions
- Zero runtime cost, smaller bundle
- No built-in theme inheritance or color manipulation

### The Challenge

Both approaches have significant trade-offs:

**Pure Plugin Approach (HeroUI-style):**
- ✅ Theme inheritance (`extend: "dark"`)
- ✅ Auto foreground color calculation
- ✅ TypeScript type safety
- ✅ Developer-friendly JS API
- ❌ Runtime overhead (color parsing, HSL conversion)
- ❌ Heavy dependencies
- ❌ Doesn't leverage Tailwind v4 features
- ❌ Larger bundle size

**Pure @theme Approach (Tailwind v4 native):**
- ✅ Zero runtime cost
- ✅ No dependencies
- ✅ Smaller bundle
- ✅ Native Tailwind v4 integration
- ✅ Fast builds
- ❌ No theme inheritance
- ❌ Manual color scale definition
- ❌ Manual foreground calculation
- ❌ Verbose (must define all scales)

## Decision

We will use a **Hybrid Approach** that combines the best of both worlds:

```
@theme Directive (Tailwind v4 native)
         ↓
   Base Atomic Tokens (colors, spacing, etc.)
         ↓
Lightweight Plugin (semantic mappings only)
         ↓
   Semantic Tokens (primary, background, etc.)
         ↓
Components (tailwind-variants)
```

### Architecture Details

**Layer 1: Base Tokens (@theme)**
```css
/* packages/tokens/src/base.css */
@theme {
  /* Atomic color scales */
  --color-blue-50: oklch(0.95 0.05 250);
  --color-blue-500: oklch(0.6 0.2 250);
  --color-blue-900: oklch(0.2 0.15 250);

  /* Layout tokens */
  --radius-sm: 0.5rem;
  --radius-md: 0.75rem;
  --radius-lg: 1rem;

  /* Shadows */
  --shadow-sm: 0 1px 2px 0 oklch(0 0 0 / 0.05);
}
```

**Layer 2: Semantic Mappings (Lightweight Plugin)**
```typescript
/* packages/tokens/src/plugin.ts */
export const uiTokens = plugin(({ addBase }) => {
  addBase({
    ':root, [data-theme]': {
      '--color-primary': 'var(--color-blue-500)',
      '--color-primary-foreground': '#ffffff',
      '--color-background': '#ffffff',
      '--color-foreground': '#0a0a0a',
    },
    '.dark': {
      '--color-background': '#0a0a0a',
      '--color-foreground': '#fafafa',
    },
    '[data-theme="ocean"]': {
      '--color-primary': 'var(--color-cyan-500)',
    }
  });
});
```

**Layer 3: Component Usage**
```tsx
<Button className="bg-primary text-primary-foreground">
  Click me
</Button>
```

### Key Principles

1. **Atomic tokens in @theme:** Base color scales, spacing, radii (rarely change)
2. **Semantic tokens in plugin:** Role-based mappings (primary, background)
3. **No runtime processing:** All tokens are static CSS variables
4. **Zero heavy dependencies:** No color manipulation libraries
5. **Pre-calculated values:** Use tools for color scales, document ratios

## Consequences

### Positive

**Performance:**
- ✅ Zero runtime cost (all build-time)
- ✅ Smallest possible bundle size
- ✅ Fast builds (no complex processing)
- ✅ Leverages Tailwind v4 native features

**Developer Experience:**
- ✅ Semantic token API (`bg-primary`, `text-foreground`)
- ✅ Theme switching works (`[data-theme="custom"]`)
- ✅ Easy to override inline (`[--color-primary:#FF0000]`)
- ✅ Clean separation: atomic vs semantic
- ✅ TypeScript types can be generated

**Maintainability:**
- ✅ Simple plugin (~50 lines, just mappings)
- ✅ Single source of truth (`@theme` definitions)
- ✅ Easy to debug (pure CSS variables)
- ✅ No complex dependencies to maintain
- ✅ Future-proof (native Tailwind v4)

**Flexibility:**
- ✅ Custom themes via CSS (`[data-theme="custom"]`)
- ✅ Component-level overrides possible
- ✅ Can reference base tokens (`var(--color-blue-500)`)

### Negative

**Manual Work Required:**
- ❌ No auto color scale generation (use tools like Leonardo, Tailwind Palette Generator)
- ❌ No auto foreground calculation (pre-calculate with ColorHexa, document contrast)
- ❌ No theme "extend" syntax (use CSS var references instead)

**Impact:** Minimal - adds ~5-10 minutes to initial setup, but better DX long-term

### Neutral

**Trade-off Analysis:**
- 📊 Setup time: Medium (one-time cost)
- 📊 Runtime performance: Best possible (zero cost)
- 📊 Bundle size: Smallest (no deps)
- 📊 DX score: 9/10 (semantic + flexible)
- 📊 Maintenance: Easy (simple code)
- 📊 Future-proof: 10/10 (native Tailwind v4)

## Alternatives Considered

### Alternative 1: Pure HeroUI-Style Plugin

**Description:** Full plugin with runtime color processing, auto calculations

**Pros:**
- Auto foreground color calculation
- Theme inheritance API
- TypeScript config
- Familiar to HeroUI users

**Cons:**
- Runtime overhead (color parsing)
- Heavy dependencies (`color`, `color2k`, `deepmerge`)
- Larger bundle size
- Doesn't leverage Tailwind v4 features
- More complex maintenance

**Why not chosen:** Over-engineering for our use case. We're a greenfield project focused on learning best practices, not maintaining legacy compatibility.

### Alternative 2: Pure Tailwind v4 @theme

**Description:** Use only `@theme` directive, no plugin

**Pros:**
- Zero dependencies
- Smallest bundle
- Native Tailwind v4
- Fast builds

**Cons:**
- No semantic token abstraction
- Verbose theme definitions
- No theme inheritance
- Must manually calculate all values
- Less developer-friendly API

**Why not chosen:** Too low-level. Semantic tokens (`primary`, `background`) provide better DX than raw color references.

### Alternative 3: CSS Variables Only (No Tailwind)

**Description:** Pure CSS custom properties, manual utility classes

**Pros:**
- No build tools required
- Ultimate control
- Native browser features

**Cons:**
- No utility class generation
- Manual responsive design
- No purging
- Verbose code

**Why not chosen:** Tailwind utilities are too valuable to give up.

## Implementation Plan

### Phase 1: Foundation (Week 1)

**Task 1.1: Setup Package Structure**
```
packages/tokens/
├── src/
│   ├── base.css           # @theme definitions
│   ├── plugin.ts          # Semantic mappings
│   ├── themes/
│   │   ├── light.css      # Light overrides
│   │   ├── dark.css       # Dark overrides
│   │   └── presets.css    # Custom theme examples
│   └── index.ts           # Entry point
├── package.json
└── README.md
```

**Task 1.2: Define Color Scales**
- Use [Leonardo](https://leonardocolor.io/) or [Tailwind Palette Generator](https://tailwind-color-palette-generator.vercel.app/)
- Generate scales: blue, red, green, yellow, purple, cyan, zinc
- Document WCAG contrast ratios

**Task 1.3: Define Layout Tokens**
- Spacing scale (xs, sm, md, lg, xl)
- Border radius (sm, md, lg)
- Shadows (sm, md, lg)
- Font sizes (xs, sm, base, lg, xl)

**Task 1.4: Create Semantic Mappings Plugin**
- Map atomic tokens to semantic roles
- Support light/dark themes
- Support custom theme variants

### Phase 2: Integration (Week 2)

**Task 2.1: Update tooling/tailwind-config/**
```typescript
import { uiTokens } from '@xidoke/ui-tokens';

export default {
  plugins: [uiTokens],
};
```

**Task 2.2: Generate TypeScript Types**
```typescript
// Auto-generate from @theme definitions
export type ColorToken =
  | 'primary'
  | 'secondary'
  | 'background'
  | 'foreground';
```

**Task 2.3: Create Documentation**
- Token usage guide
- Theme customization guide
- Migration examples

### Phase 3: Validation (Week 2)

**Task 3.1: Test with Button Component**
```tsx
<Button className="bg-primary text-primary-foreground">
  Primary Button
</Button>
```

**Task 3.2: Test Theme Switching**
```tsx
<div data-theme="ocean">
  <Button>Ocean Theme</Button>
</div>
```

**Task 3.3: Performance Validation**
- Measure bundle size impact
- Verify zero runtime cost
- Test build times

### Success Metrics

- ✅ Token definitions in single file (<200 lines)
- ✅ Plugin code <100 lines
- ✅ Zero runtime dependencies
- ✅ Bundle size increase <5KB
- ✅ Theme switching works without rebuild

## Lessons Learned

**From HeroUI:**
- ✅ Semantic token API is valuable
- ✅ Theme switching is critical
- ✅ TypeScript support matters
- ❌ Full plugin is over-engineering for most projects
- ❌ Runtime color manipulation not needed

**From Tailwind v4:**
- ✅ CSS-first is the future
- ✅ `@theme` provides clean API
- ✅ Zero-config is desirable
- ⚠️ Need semantic layer on top

**Our Approach:**
- Take semantic API from HeroUI
- Take build-time approach from Tailwind v4
- Avoid over-engineering
- Keep it simple and maintainable
