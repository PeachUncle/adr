# TASK-001: Parse existing frontend & propose monorepo layout
> Source: tasks/tasks.md

## Context
- Goal: Scan current Vite/Tailwind/TS-React frontend and list routes, components, and API calls; propose monorepo structure.
- Acceptance: Provide a markdown report of the current frontend API surface + new filesystem map; create folders with boilerplate READMEs.
- Constraints: Keep frontend import aliases stable when moving; align with docs/architecture.mermaid and docs/technical.md.

### Frontend Scan (API surface and structure)
- Routes (react-router):
  - `/` → `src/pages/Index.tsx` → `src/components/FinancialDashboard.tsx`
  - `*` → `src/pages/NotFound.tsx`
- Key components:
  - `src/components/FinancialDashboard.tsx` (composes `ChatInterface`, `StockWidget`, `NewsWidget`)
  - `src/components/ChatInterface.tsx` (local state; simulated bot replies)
  - `src/components/StockWidget.tsx` (local state; simulated price updates)
  - `src/components/NewsWidget.tsx` (static list)
  - UI library components under `src/components/ui/*`
- API calls: None at present. No `fetch`/`axios` usage; data is simulated client-side.
- Build config:
  - Vite alias `@ → ./src` (must remain stable after any move).

### Proposed Monorepo Layout
```
/frontend           # existing UI (current root contents to be moved in a follow-up task)
/backend            # FastAPI service exposing /api/v1
/ml                 # Training & inference (LSTM + artifacts)
/llm                # Ollama DeepSeek prompts/tools
/data_fetchers      # Price/news fetchers and caching
/db                 # SQLite schema & migrations
/infra              # docker, compose, Makefile
/docs               # API contracts, diagrams, evals (existing)
```

## Options Considered
- Option A: Move the existing frontend into `/frontend` immediately.
  - Pros: Structure is finalized early; clearer boundaries.
  - Cons: Higher churn risk; breakage unless all paths, tooling, and deployment are updated; distracts from backend bootstrap.
- Option B: Scaffold monorepo directories now; move frontend in a later, coordinated task.
  - Pros: Non‑disruptive; unblocks backend/ML/LLM work; aligns with acceptance criteria.
  - Cons: Temporary mismatch where frontend still resides at root.
- Option C: Keep flat repo until backend is ready.
  - Pros: Zero work now.
  - Cons: Delays structure; increases future refactor cost.

## Decision
- Choose Option B. Create required top‑level directories with README placeholders now. Defer moving the existing UI into `/frontend` until the backend contract is ready, maintaining the `@` alias and minimizing risk.

## Impacts
- Performance: Neutral (structure only).
- Complexity: Reduced long‑term by clear boundaries; minimal short‑term overhead.
- Security/Privacy: Neutral.
- Compatibility: Frontend continues to run unchanged; alias `@` preserved.
- Risks & Mitigations:
  - Risk: Confusion with both root UI and `/frontend/` directory.
  - Mitigation: Document that `/frontend` will host the UI after the planned move; keep only README in `/frontend` until then.
