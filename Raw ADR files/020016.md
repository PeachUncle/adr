# ADR-0001: Single Container Architecture

**Status:** Accepted

**Date:** 2025-11-02

**Deciders:** Solo developer

---

## Context

vpn-hopper needs to package a WireGuard VPN client and SSH server together to enable remote network access and diagnostics. Several architectural approaches were considered:

### Option 1: Multi-Container (Microservices)
- Separate containers for WireGuard and SSH
- Requires shared network namespace or complex networking
- More overhead, orchestration complexity

### Option 2: Single Container (Monolithic)
- Both WireGuard and SSH in one container
- Simple deployment, single image
- Easier networking configuration

### Option 3: Sidecar Pattern
- SSH as main container, WireGuard as sidecar
- Kubernetes-native approach
- Overkill for simple use case

---

## Decision

**We will use a single container architecture** that packages both WireGuard client and SSH server into one Docker image.

The container runs:
1. **entrypoint.sh** - Initialization script
2. **WireGuard client** - wg-quick to establish tunnel
3. **SSH server** - sshd as the main process (PID 1 via exec)

---

## Rationale

### Advantages

1. **Simplicity**
   - Single `docker run` command
   - No orchestration required
   - Minimal configuration

2. **Deployment Ease**
   - Works on any Docker host
   - No Compose/Swarm/K8s required for basic usage
   - Straightforward port mapping

3. **Network Simplicity**
   - WireGuard and SSH naturally share the container's network namespace
   - No complex network sharing between containers
   - Traffic routing is straightforward

4. **Resource Efficiency**
   - Single base image layer
   - Minimal memory overhead
   - Faster startup (no orchestration delay)

5. **User Experience**
   - Clear mental model: one container = one jumpbox
   - Easy to reason about and troubleshoot
   - Straightforward logs in one place

### Disadvantages

1. **Less Modular**
   - Cannot independently scale SSH and WireGuard (not needed for this use case)
   - Harder to swap components (rare requirement)

2. **Violates Microservices Principles**
   - Two processes in one container
   - Not "one concern per container"
   - Counter-argument: This is one concern — "network jumpbox"

3. **Restart Coupling**
   - Restarting WireGuard also restarts SSH (acceptable trade-off)

---

## Consequences

### Positive

- Users can deploy with minimal Docker knowledge
- Works in constrained environments (single container budget)
- Image can be used as-is without additional tooling
- Documentation is simpler and more approachable

### Negative

- Kubernetes deployments lose some granularity
- Cannot use separate health checks per component easily
- Log aggregation slightly less granular (could add structured logging)

### Mitigations

- For Kubernetes users, we can later provide Helm charts with init containers if needed
- Health checks can still verify both components (script-based)
- Logs are still accessible via `docker logs` or K8s pod logs

---

## Alternatives Considered

### Alternative 1: Docker Compose Multi-Container

```yaml
services:
  wireguard:
    image: linuxserver/wireguard
    # ...
  
  ssh:
    image: custom-ssh
    network_mode: "service:wireguard"
```

**Rejected because:**
- Requires Compose knowledge
- More complex to deploy
- Harder to distribute as single artifact
- Network_mode dependency is fragile

### Alternative 2: Kubernetes Pod with Multiple Containers

```yaml
spec:
  containers:
  - name: wireguard
    # ...
  - name: ssh
    # ...
```

**Rejected because:**
- Forces Kubernetes dependency
- Overkill for the target use case (home labs, simple deployments)
- Adds barrier to entry

## Notes

This decision prioritizes **ease of use** over **architectural purity**. The target audience (network admins, home labbers) values simplicity and quick deployment over microservices best practices.

If Kubernetes or advanced orchestration is needed, the single-container design still works well in that context — it just becomes a single-container pod/deployment.

---

## Review

Should be reviewed if:
- WireGuard and SSH start requiring significantly different resource profiles
- Independent scaling becomes necessary
- Component reuse in other projects is desired
- Kubernetes becomes the primary deployment target
