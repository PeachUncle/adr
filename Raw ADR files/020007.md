# ADR-003: No Optimistic Updates - Rely on Real-Time Subscriptions

## Status

Accepted

## Context

The original requirements mentioned "optimistic updates" for instant message display. However, the existing codebase already has robust real-time subscriptions via Supabase that provide near-instant updates (~100-200ms). Implementing optimistic updates would add complexity and potential for duplicate messages.

## Decision

We will NOT implement optimistic updates. Instead, we rely solely on Supabase real-time subscriptions for message display updates.

## Rationale

### Chosen: Real-Time Subscriptions Only

- **Simplicity**: No temporary message IDs or deduplication logic needed
- **Reliability**: Single source of truth (database)
- **Existing Infrastructure**: Supabase subscriptions already work well
- **No Duplicates**: Impossible to have duplicate messages in UI
- **Consistent State**: All clients see identical message order and timing

### Rejected: Optimistic Updates

- ❌ **Complexity**: Need temporary IDs, deduplication, rollback logic
- ❌ **Race Conditions**: Subscription insert + optimistic add could create duplicates
- ❌ **State Management**: Complex logic to replace temp messages with real ones
- ❌ **Error Handling**: Need to remove optimistic messages on failure
- ❌ **Testing**: Much harder to test all edge cases

## Implementation Details

### Message Send Flow

```javascript
const handleSend = async () => {
  const messageText = value;
  setValue(""); // Clear input immediately
  setIsSending(true);

  try {
    await addMessage(messageText, channelId, user.id);
    // Real-time subscription will add message to UI
  } catch (error) {
    toast.error("Failed to send");
    setValue(messageText); // Restore on failure
  } finally {
    setIsSending(false);
  }
};
```

### User Experience

- Input clears immediately (feels responsive)
- Send button shows loading spinner
- Message appears via subscription (~100-200ms delay)
- On error: text restored to input, toast shown

## Consequences

### Positive

- **Simpler Code**: ~50% less complexity in MessageInput component
- **Fewer Bugs**: No race conditions or duplicate message issues
- **Easier Testing**: Only need to test send success/failure, not optimistic states (see [ADR-014: Testing Strategy](./adr-014-testing-strategy.md))
- **Consistent Behavior**: All users see messages at same time
- **Reliable State**: Database is always source of truth

### Negative

- **Perceived Latency**: ~100-200ms delay before message appears
- **Less "Snappy" Feel**: Not as instant as optimistic updates
- **Network Dependency**: Poor connections more noticeable

### Mitigation Strategies

- Clear input immediately (user can keep typing)
- Show loading spinner (clear feedback)
- Restore text on error (no data loss)
- Auto-scroll to new messages (smooth experience)

## Performance Impact

- **Reduced Bundle Size**: No optimistic update logic
- **Fewer Re-renders**: No temporary state changes
- **Network**: Same number of requests (just the addMessage call)
- **Memory**: No temporary message objects

## Alternative Considered: Hybrid Approach

We considered showing optimistic updates only for the current user's messages, but this would create inconsistent behavior and still require deduplication logic.

## Implementation

This decision is implemented in the [Shadcn Chat UI specification](../../.kiro/specs/shadcn-chat-ui/), which rebuilds the chat interface following this real-time subscription approach without optimistic updates.

## Future Considerations

If user feedback indicates the ~200ms delay is problematic, we can revisit optimistic updates in Phase 2. The component architecture documented in [ADR-006](./adr-006-component-architecture.md) supports adding this later without major refactoring.
