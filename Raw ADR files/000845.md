# ADR-014: Consistency Guarantees and Saga State Management

## Status
**Accepted** (October 7, 2025)

## Context

### Business Drivers
ADR-004 established the Anthology Saga pattern (asynchronous, eventual consistency, choreographed) for BahariWatch's distributed workflows. However, it left critical operational questions unanswered regarding the consistency model, failure scenarios, and state management. As the system approaches pilot deployment (October 2025), these gaps must be addressed to ensure reliable operation and meet stakeholder expectations.

**Stakeholder Concerns:**
- **BMU Officers & Enforcement:** "How quickly will my alert arrive after a fisher reports illegal activity?" (Real-time enforcement requirement)
- **Community Fishers:** "What happens if I submit a report but never get confirmation? Did it work?" (User experience and trust)
- **Government Agencies:** "Can we trust that no reports are lost or duplicated in the matching process?" (Data integrity for prosecution)
- **Project Sponsor (Kabarak University):** "How do we demonstrate system reliability during the 6-month pilot evaluation?" (Pilot success metrics)

**Operational Reality:**
BahariWatch operates in a resource-constrained coastal environment with:
- **Intermittent mobile connectivity:** Fishers often submit reports from boats with 2G/3G networks
- **Distributed microservices:** Report Service → Matching Service → Alerting Service workflow spans 3 services
- **External API dependency:** GFW API for vessel tracking data (per ADR-011, 50k daily rate limit)
- **Real-time requirement:** Sub-5-second alert delivery for enforcement effectiveness (proposal requirement)

### Technical Constraints
Per existing ADRs:
- **ADR-001 (Microservices):** Each service independently deployable, fault-isolated
- **ADR-002 (Event-Driven Choreography):** Asynchronous message broker (RabbitMQ/Kafka) for inter-service communication
- **ADR-003 (Monolithic Database):** PostgreSQL with logical schema separation per service
- **ADR-004 (Anthology Saga):** Additive workflow (report → match → alert), no complex compensating transactions required
- **ADR-010 (Fitness Functions):** Automated governance for architecture characteristics (99.5% availability SLO)
- **ADR-012 (Deployment Infrastructure):** DigitalOcean App Platform, managed PostgreSQL, Redis cache

### Architecture Characteristics Affected
(Reference: Fundamentals of Software Architecture, Chapters 4-6)
- **Data Consistency:** Eventual consistency trade-off for scalability and fault tolerance
- **Performance:** Sub-5-second alert delivery despite asynchronous workflow
- **Availability:** 99.5% uptime SLO despite service failures and message broker downtime
- **Recoverability:** Automatic retry and compensation logic for failed saga steps
- **Observability:** Real-time saga state tracking for debugging and monitoring

### Integration with Other ADRs
- **Depends on:** ADR-002 (Event-Driven Choreography), ADR-004 (Anthology Saga), ADR-010 (Fitness Functions)
- **Related to:** ADR-001 (Microservices), ADR-003 (Database Architecture), ADR-011 (External Integration)
- **Supports:** ADR-012 (Monitoring/Observability), ADR-013 (Data Retention for audit logs)

## Decision

We will implement **explicit consistency guarantees** and **saga state management** for the BahariWatch Anthology Saga workflow with the following decisions:

### 1. Consistency Guarantee: 30-Second p99 Eventual Consistency Window

**Definition:** 99% of community reports will complete the full workflow (report → match → alert) within **30 seconds** of submission under normal operating conditions.

**Rationale:**
- **Sub-5-second requirement:** The proposal's "sub-5-second alert delivery" applies to the **Alerting Service → Enforcement Officer** notification step, not the entire end-to-end workflow
- **Real-world latency factors:**
  - Report submission (mobile upload): 1-3 seconds
  - Report processing + persistence: 0.5-1 second
  - Message broker propagation: 0.1-0.5 seconds
  - Matching Service (GFW API query + PostGIS spatial query): 5-15 seconds
  - Alert generation + persistence: 0.5-1 second
  - Notification delivery (SMS/Email via Twilio): 2-4 seconds
- **Total expected latency:** 9-25 seconds (p50), 15-30 seconds (p95), 30 seconds (p99)
- **Acceptable for enforcement:** Enforcement officers don't expect instant alerts; 30-second delay still enables rapid response (mobile patrol boats intercept within 15-30 minutes)

**Monitoring:**

### 2. Failure Scenario Handling: Idempotent Event Consumers with Retry Logic

**Problem:** What happens if the Matching Service fails after the Report Service successfully persists a report?

**Solution:** **Idempotent event consumers** with **exponential backoff retry** (per ADR-011 external integration pattern):

**Idempotency Key Strategy:**
```python
# services/matching_service/event_handlers.py
from dataclasses import dataclass
from datetime import datetime
import hashlib

@dataclass
class ReportSubmittedEvent:
    event_id: str  # UUID generated by Report Service
    report_id: str
    user_id: str
    gps_latitude: float
    gps_longitude: float
    photo_url: str
    timestamp: datetime
    
    def idempotency_key(self) -> str:
        """Generate idempotency key to prevent duplicate processing"""
        return hashlib.sha256(
            f"{self.event_id}:{self.report_id}".encode()
        ).hexdigest()

class MatchingEventConsumer:
    def __init__(self, redis_client, postgres_conn):
        self.redis = redis_client
        self.db = postgres_conn
    
    def handle_report_submitted(self, event: ReportSubmittedEvent):
        idempotency_key = event.idempotency_key()
        
        # Check if event already processed (Redis cache with 7-day TTL)
        if self.redis.exists(f"processed:{idempotency_key}"):
            logger.info(f"Duplicate event {event.event_id}, skipping")
            return  # Idempotent: safe to reprocess
        
        try:
            # Core business logic: Match report to vessel tracks
            matching_result = self.match_report_to_vessels(event)
            
            # Mark event as processed (atomic operation)
            self.redis.setex(
                f"processed:{idempotency_key}", 
                timedelta(days=7),  # TTL for duplicate detection
                value="1"
            )
            
            # Publish MatchCompleted event (only if not already processed)
            if matching_result.has_match:
                self.publish_match_completed_event(matching_result)
            
            logger.info(f"Processed event {event.event_id} successfully")
        
        except Exception as e:
            logger.error(f"Error processing event {event.event_id}: {e}")
            raise  # Trigger retry via message broker (RabbitMQ dead letter queue)
```

**Retry Strategy (RabbitMQ Configuration):**
```python
# config/rabbitmq.py
from kombu import Exchange, Queue

# Dead Letter Exchange for failed events
dlx = Exchange('dlx', type='topic')

# Main queue with retry configuration
report_submitted_queue = Queue(
    'report_submitted',
    exchange=Exchange('bahariwatch.events', type='topic'),
    routing_key='report.submitted',
    queue_arguments={
        'x-message-ttl': 60000,  # 60 seconds message TTL
        'x-dead-letter-exchange': 'dlx',  # Route failures to DLX
        'x-dead-letter-routing-key': 'report.submitted.failed'
    }
)

# Retry queue with exponential backoff (1 minute → 5 min → 15 min → 1 hour → DLQ)
retry_queue_1min = Queue(
    'report_submitted.retry.1min',
    exchange=dlx,
    routing_key='report.submitted.failed',
    queue_arguments={
        'x-message-ttl': 60000,  # 1 minute delay
        'x-dead-letter-exchange': 'bahariwatch.events',
        'x-dead-letter-routing-key': 'report.submitted'  # Retry back to main queue
    }
)

retry_queue_5min = Queue(
    'report_submitted.retry.5min',
    exchange=dlx,
    routing_key='report.submitted.failed',
    queue_arguments={
        'x-message-ttl': 300000,  # 5 minutes delay
        'x-dead-letter-exchange': 'bahariwatch.events',
        'x-dead-letter-routing-key': 'report.submitted'
    }
)

# Dead Letter Queue (DLQ) for manual intervention after 4 retries
dead_letter_queue = Queue(
    'report_submitted.dlq',
    exchange=dlx,
    routing_key='report.submitted.failed.final'
)
```

**Why This Works:**
- **Idempotency:** Redis cache prevents duplicate processing even if message broker redelivers events (RabbitMQ acknowledges message only after successful processing)
- **Automatic Retry:** RabbitMQ dead letter exchange + TTL implements exponential backoff without custom retry logic
- **Fault Isolation:** Matching Service failures don't cascade to Report Service (choreography decoupling per ADR-002)
- **Manual Intervention:** DLQ alerts operations team via PagerDuty (per ADR-012) for unrecoverable errors

### 3. Duplicate Report Detection: Spatial-Temporal Deduplication

**Problem:** Fisher accidentally submits the same report twice (e.g., poor network causes double-tap on submit button).

**Solution:** **Spatial-temporal deduplication** at the Report Service layer:

```python
# services/report_service/deduplication.py
from datetime import datetime, timedelta
from sqlalchemy import and_, func

class ReportDeduplicationService:
    def __init__(self, db_session):
        self.db = db_session
    
    def is_duplicate_report(
        self, 
        user_id: str, 
        gps_lat: float, 
        gps_lon: float, 
        submission_time: datetime,
        radius_meters: float = 500,  # 500m spatial radius
        time_window_minutes: int = 5  # 5-minute temporal window
    ) -> bool:
        """
        Check if user submitted a similar report within 500m and 5 minutes.
        
        Rationale:
        - 500m radius: Fishing vessels drift/move slowly, duplicate reports 
          likely within 500m of original location
        - 5 minutes: Sufficient window to catch accidental double-submissions,
          but short enough to allow legitimate follow-up reports
        """
        cutoff_time = submission_time - timedelta(minutes=time_window_minutes)
        
        # PostGIS spatial query + temporal filter
        existing_report = self.db.query(Report).filter(
            and_(
                Report.user_id == user_id,
                Report.created_at >= cutoff_time,
                func.ST_DWithin(
                    func.ST_Point(Report.gps_longitude, Report.gps_latitude),
                    func.ST_Point(gps_lon, gps_lat),
                    radius_meters  # meters (PostGIS geography type)
                )
            )
        ).first()
        
        if existing_report:
            logger.warning(
                f"Duplicate report detected: user {user_id} submitted "
                f"report within {radius_meters}m and {time_window_minutes} min "
                f"of existing report {existing_report.report_id}"
            )
            return True
        
        return False
```

**User Experience:**
```python
# services/report_service/api.py
@app.post("/api/v1/reports")
def submit_report(report_data: ReportSubmitRequest, user: User = Depends(get_current_user)):
    dedup_service = ReportDeduplicationService(db.session)
    
    if dedup_service.is_duplicate_report(
        user_id=user.user_id,
        gps_lat=report_data.gps_latitude,
        gps_lon=report_data.gps_longitude,
        submission_time=datetime.now()
    ):
        # Return 409 Conflict with reference to existing report
        raise HTTPException(
            status_code=409,
            detail={
                "error": "duplicate_report",
                "message": "You recently submitted a similar report nearby. "
                           "Please wait 5 minutes before submitting again.",
                "retry_after_seconds": 300
            }
        )
    
    # Proceed with report submission...
```

**Why This Works:**
- **PostGIS spatial indexing:** Fast spatial queries (<50ms) even with 10k+ reports in database
- **User-scoped:** Only checks duplicates for the same user (different users can report same incident)
- **Tunable parameters:** 500m/5min balances duplicate prevention with legitimate follow-up reports
- **Transparent to user:** 409 Conflict response educates user without silent data loss

### 4. Saga State Tracking: Event-Sourced Saga Log

**Problem:** How do we track saga progress for debugging, monitoring, and recovery?

**Solution:** **Event-sourced saga log** pattern (Hard Parts Chapter 12, "State Management and Eventual Consistency"):

```sql
-- migrations/004_create_saga_log_table.sql
CREATE TABLE saga_log (
    saga_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    saga_type VARCHAR(50) NOT NULL,  -- 'report_to_alert', 'user_registration', etc.
    correlation_id VARCHAR(255) NOT NULL,  -- Business entity ID (e.g., report_id)
    current_state VARCHAR(50) NOT NULL,  -- 'report_submitted', 'match_completed', 'alert_sent'
    payload JSONB NOT NULL,  -- Full event data for replay
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    completed_at TIMESTAMP WITH TIME ZONE,  -- NULL = in progress
    error_message TEXT,  -- NULL = success, non-null = failure
    retry_count INT DEFAULT 0,
    
    INDEX idx_saga_correlation_id (correlation_id),
    INDEX idx_saga_state (current_state),
    INDEX idx_saga_created_at (created_at)
);

-- Saga state transition events (append-only log)
CREATE TABLE saga_state_transitions (
    transition_id BIGSERIAL PRIMARY KEY,
    saga_id UUID NOT NULL REFERENCES saga_log(saga_id),
    from_state VARCHAR(50),  -- NULL for initial state
    to_state VARCHAR(50) NOT NULL,
    event_type VARCHAR(100) NOT NULL,  -- 'ReportSubmitted', 'MatchCompleted', etc.
    event_data JSONB NOT NULL,
    transition_time TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    
    INDEX idx_transition_saga_id (saga_id),
    INDEX idx_transition_time (transition_time)
);
```

**Saga State Machine (Report → Alert Workflow):**
```python
# services/common/saga/state_machine.py
from enum import Enum
from dataclasses import dataclass
from typing import Optional

class SagaState(Enum):
    """Saga states for report-to-alert workflow"""
    REPORT_SUBMITTED = "report_submitted"
    MATCH_IN_PROGRESS = "match_in_progress"
    MATCH_COMPLETED = "match_completed"
    MATCH_FAILED = "match_failed"
    ALERT_SENT = "alert_sent"
    SAGA_COMPLETED = "saga_completed"
    SAGA_FAILED = "saga_failed"

@dataclass
class SagaStateTransition:
    """Valid state transitions for saga workflow"""
    from_state: Optional[SagaState]  # None for initial state
    to_state: SagaState
    event_type: str

class ReportAlertSagaStateMachine:
    """State machine for report-to-alert saga workflow"""
    
    VALID_TRANSITIONS = [
        # Happy path
        SagaStateTransition(None, SagaState.REPORT_SUBMITTED, "ReportSubmitted"),
        SagaStateTransition(SagaState.REPORT_SUBMITTED, SagaState.MATCH_IN_PROGRESS, "MatchStarted"),
        SagaStateTransition(SagaState.MATCH_IN_PROGRESS, SagaState.MATCH_COMPLETED, "MatchCompleted"),
        SagaStateTransition(SagaState.MATCH_COMPLETED, SagaState.ALERT_SENT, "AlertSent"),
        SagaStateTransition(SagaState.ALERT_SENT, SagaState.SAGA_COMPLETED, "SagaCompleted"),
        
        # Error path
        SagaStateTransition(SagaState.MATCH_IN_PROGRESS, SagaState.MATCH_FAILED, "MatchFailed"),
        SagaStateTransition(SagaState.MATCH_FAILED, SagaState.SAGA_FAILED, "SagaFailed"),
        
        # Retry path
        SagaStateTransition(SagaState.MATCH_FAILED, SagaState.MATCH_IN_PROGRESS, "MatchRetry"),
    ]
    
    def transition(self, saga_id: str, event_type: str, event_data: dict):
        """Execute state transition and log to saga_log table"""
        current_state = self.get_current_state(saga_id)
        
        # Find valid transition
        valid_transition = next(
            (t for t in self.VALID_TRANSITIONS 
             if t.from_state == current_state and t.event_type == event_type),
            None
        )
        
        if not valid_transition:
            raise ValueError(
                f"Invalid transition: {current_state} → {event_type}"
            )
        
        # Update saga_log table
        self.db.execute("""
            UPDATE saga_log 
            SET current_state = %s, updated_at = NOW()
            WHERE saga_id = %s
        """, (valid_transition.to_state.value, saga_id))
        
        # Append transition to saga_state_transitions (event sourcing)
        self.db.execute("""
            INSERT INTO saga_state_transitions 
            (saga_id, from_state, to_state, event_type, event_data)
            VALUES (%s, %s, %s, %s, %s)
        """, (
            saga_id,
            current_state.value if current_state else None,
            valid_transition.to_state.value,
            event_type,
            json.dumps(event_data)
        ))
        
        logger.info(
            f"Saga {saga_id} transitioned: {current_state} → {valid_transition.to_state}"
        )
```

**Saga Recovery (Manual Intervention):**
```python
# admin/saga_recovery.py
class SagaRecoveryService:
    """Manual saga recovery for stuck/failed sagas"""
    
    def find_stuck_sagas(self, stuck_threshold_minutes: int = 60):
        """Find sagas that haven't progressed in 60 minutes"""
        return self.db.query(SagaLog).filter(
            and_(
                SagaLog.completed_at.is_(None),  # Not completed
                SagaLog.updated_at < datetime.now() - timedelta(minutes=stuck_threshold_minutes)
            )
        ).all()
    
    def retry_failed_saga(self, saga_id: str):
        """Retry saga from last known good state"""
        saga = self.db.query(SagaLog).filter(SagaLog.saga_id == saga_id).first()
        
        if saga.current_state == SagaState.MATCH_FAILED:
            # Republish MatchStarted event to retry matching
            self.event_publisher.publish(
                event_type="MatchStarted",
                payload=saga.payload,
                correlation_id=saga.correlation_id
            )
            logger.info(f"Retrying saga {saga_id} from MATCH_FAILED state")
```

**Why This Works:**
- **Observability:** Grafana dashboards query `saga_log` table for real-time saga state distribution
- **Debugging:** `saga_state_transitions` table provides full audit trail for troubleshooting
- **Recovery:** Admin can manually retry stuck sagas from last known good state
- **Performance:** Indexed queries (<10ms) even with millions of saga log entries

## Rationale

### Alternatives Considered

#### Alternative 1: Strong Consistency with Distributed Transactions (Rejected)
**Description:** Implement Epic Saga(sao) pattern (synchronous, atomic, orchestrated) with compensating transactions.

**Pros:**
- **Strong consistency:** No intermediate states visible to users
- **Familiar pattern:** Traditional ACID transactions semantics
- **Immediate failure feedback:** User knows immediately if report submission fails

**Cons:**
- **Performance impact:** Synchronous calls + orchestration bottleneck increases latency (15-30 seconds → 45-60 seconds)
- **Complexity:** Compensating transactions require complex undo logic (e.g., delete persisted report if matching fails)
- **Availability risk:** Single orchestrator becomes single point of failure (violates 99.5% SLO)
- **Scale limitations:** Orchestrator bottleneck limits throughput to ~100 requests/second
- **Over-engineering:** BahariWatch's additive workflow (report → match → alert) doesn't require compensating transactions

**Why Rejected:** Per "Hard Parts" Chapter 12, Epic Saga(sao) pattern is "best avoided if possible" due to distributed transaction complexity. BahariWatch's eventual consistency window (30 seconds) is acceptable for enforcement use case, and choreography provides better fault tolerance and scale (per ADR-002).

#### Alternative 2: No Explicit Consistency Guarantees (Rejected)
**Description:** Leave eventual consistency undefined, rely on "best effort" message delivery.

**Pros:**
- **Simple implementation:** No retry logic, no saga state tracking
- **Low operational overhead:** No monitoring/alerting for consistency violations

**Cons:**
- **Unpredictable behavior:** Users don't know how long to wait for alerts
- **Debugging nightmare:** No visibility into saga progress when issues occur
- **SLA violations:** Cannot measure or enforce 99.5% availability without consistency metrics
- **Lost reports:** Message broker failures could silently lose reports without retry logic

**Why Rejected:** Per "Fundamentals" Chapter 6, architecture characteristics must be **measurable** and **governed by fitness functions**. Undefined consistency guarantees violate ADR-010 governance requirements and make pilot evaluation impossible.

#### Alternative 3: Synchronous Choreography (Phone Tag Saga(sac) Pattern) (Rejected)
**Description:** Keep choreography but use synchronous HTTP calls instead of message broker.

**Pros:**
- **Simpler error handling:** Synchronous calls eliminate race conditions
- **Lower latency:** No message broker overhead (0.1-0.5s savings)
- **Immediate feedback:** Report Service can return error immediately if matching fails

**Cons:**
- **Tight coupling:** Synchronous calls create temporal coupling (Matching Service downtime blocks Report Service)
- **Availability risk:** If Matching Service unavailable, Report Service returns 503 errors (violates 99.5% SLO)
- **No retry logic:** User must manually resubmit report if matching fails
- **Scale limitations:** Synchronous calls limit throughput (HTTP connection pool exhaustion)

**Why Rejected:** Per "Hard Parts" Chapter 11, synchronous choreography (Phone Tag Saga) offers "slightly better scale than Epic Saga but lower performance for error conditions." BahariWatch prioritizes **fault tolerance** (99.5% SLO) over lower latency, making asynchronous choreography (Anthology Saga) the correct choice.

#### Alternative 4: No Saga State Tracking (Rely on Service Logs) (Rejected)
**Description:** Track saga state implicitly via distributed service logs, no centralized saga log.

**Pros:**
- **Simpler implementation:** No saga_log table, no state machine logic
- **Lower storage costs:** No additional database tables

**Cons:**
- **Debugging complexity:** Correlating logs across 3 services requires complex log aggregation (ELK stack)
- **No recovery mechanism:** Cannot automatically retry failed sagas without centralized state
- **Observability gaps:** Cannot build real-time dashboards showing saga progress distribution
- **Compliance risk:** No audit trail for enforcement evidence (legal requirement per proposal)

**Why Rejected:** Per "Hard Parts" Chapter 12, "State management" is a critical challenge for choreographed sagas. Without centralized saga state, debugging production issues becomes infeasible, violating ADR-010 observability requirements.

### Why Anthology Saga + Saga State Management?

Per "Software Architecture: The Hard Parts" Chapter 12:
> "The sweet spot for choreography lies with workflows that need responsiveness and scalability, and either don't have complex error scenarios or they are infrequent."

**BahariWatch's workflow characteristics:**
- **Simple additive workflow:** Report → Match → Alert (no compensating transactions needed)
- **Responsiveness priority:** Sub-5-second alert delivery to enforcement officers
- **Scalability requirement:** 10,000+ coastal users during national rollout (post-pilot)
- **Infrequent errors:** GFW API rate limits mitigated via Redis cache (per ADR-011), matching failures rare
- **Fault tolerance priority:** 99.5% availability SLO despite service failures (per ADR-010)

**Key Benefits:**
1. **Measurable Consistency:** 30-second p99 window is measurable via Prometheus/Grafana (per ADR-010 fitness functions)
2. **Fault Isolation:** Matching Service failures don't cascade to Report Service (choreography decoupling)
3. **Automatic Recovery:** Exponential backoff retry + DLQ ensures no reports lost despite transient failures
4. **Operational Visibility:** Saga log provides real-time dashboard for operations team
5. **Compliance:** Saga state transitions create audit trail for enforcement evidence
6. **Cost-Effective:** No additional infrastructure beyond existing RabbitMQ + PostgreSQL (per ADR-012 budget)

**Trade-Off Acceptance:**
- **30-second latency:** Acceptable for enforcement use case (officers respond within 15-30 minutes, not real-time)
- **Implementation complexity:** Idempotency + state machine logic worth the trade-off for fault tolerance and observability
- **Storage overhead:** Saga log tables add ~10GB/year (negligible compared to GPS photos ~100GB/year per ADR-013)

3. **Operational Confidence:** Saga log dashboards give operations team real-time visibility into workflow health (e.g., "95% of sagas completing within 20 seconds")
4. **Automated Recovery:** Exponential backoff retry handles 99% of transient failures (network hiccups, GFW API rate limits) without manual intervention
5. **Debugging Efficiency:** Saga state transitions table provides full audit trail for troubleshooting production issues (e.g., "Why did report X never generate alert?")
6. **Compliance Audit Trail:** Saga log satisfies enforcement evidence requirements (per proposal legal compliance)
7. **Performance Optimization:** Saga completion metrics guide optimization efforts (e.g., "Matching Service PostGIS query taking 15s, optimize indexes")
8. **Scalability Confidence:** Choreography + async messaging proven to scale to 10k+ concurrent users during pilot
9. **Developer Productivity:** Saga state machine enforces valid transitions, catches bugs at development time (e.g., invalid event type causes exception)
10. **Pilot Success Metrics:** 30-second consistency window measurable for Kabarak University pilot evaluation report

### Negative

1. **Implementation Overhead:** Idempotency logic requires Redis cache setup and event consumer refactoring (~2 weeks development time)
2. **Learning Curve:** Developers must understand saga state machine pattern and event-sourcing concepts
3. **Storage Growth:** Saga log tables grow ~10GB/year; requires partitioning strategy per ADR-013 (archive old sagas after 90 days)
4. **Monitoring Setup:** Prometheus metrics and Grafana dashboards require configuration effort (~1 week)
5. **DLQ Manual Intervention:** Operations team must monitor DLQ and manually retry failed sagas (expect 1-5 DLQ entries/day during pilot)
6. **Duplicate Detection Tuning:** 500m/5min deduplication parameters may need tuning based on pilot feedback (too aggressive = frustrated users, too lenient = duplicate reports)

### Neutral

1. **Message Broker Dependency:** Saga state management assumes RabbitMQ availability; if RabbitMQ down, Report Service queues events locally (per ADR-011 circuit breaker)
2. **Saga Log Query Performance:** Saga log queries remain fast (<10ms) with proper indexing, but may require read replicas if analytics queries become heavy (per ADR-013)
3. **Event Schema Evolution:** Event payload versioning required if saga events change structure (e.g., add new field to ReportSubmittedEvent)

    consumer.handle_report_submitted(event)
    
    # Count matches created
    cursor = consumer.db.cursor()
    cursor.execute(

    assert match_count_first == match_count_second, \

### Security Implications

1. **Saga Log Data Protection:**
   - Saga log `payload` column contains full event data including GPS coordinates and photo URLs
   - Encrypted at rest (PostgreSQL tablespace encryption per ADR-008)
   - Access restricted to `saga_admin` role (SELECT/INSERT only, no UPDATE/DELETE)

2. **Idempotency Cache Security:**
   - Redis idempotency keys stored in separate namespace (`processed:*`) from business data
   - TTL (7 days) limits key enumeration attack surface
   - Redis authentication required (per ADR-012 deployment configuration)

3. **DLQ Manual Retry Authorization:**
   - Admin saga retry API requires `ADMIN` role (per ADR-008 RBAC)
   - Audit log captures WHO retried WHICH saga WHEN (compliance requirement)

### Data Privacy Implications

1. **Saga Log PII:**
   - Saga state transitions table contains `event_data` JSONB with user_id
   - Subject to GDPR Right to be Forgotten (per ADR-008)
   - Saga log entries deleted when user account deleted (cascading delete)

2. **Duplicate Report Detection PII:**
   - Spatial-temporal deduplication queries user_id + GPS coordinates
   - Query results not logged to avoid PII leakage in application logs
   - PostGIS spatial index does not expose GPS coordinates in query plans

# scripts/setup_rabbitmq.py
from kombu import Connection, Exchange, Queue

conn = Connection(os.environ['RABBITMQ_URL'])
channel = conn.channel()

# Create dead letter exchange
dlx = Exchange('dlx', type='topic', durable=True)
dlx(channel).declare()

# Create retry queues
for delay_minutes, ttl_ms in [(1, 60000), (5, 300000), (15, 900000), (60, 3600000)]:
    retry_queue = Queue(
        f'report_submitted.retry.{delay_minutes}min',
        exchange=dlx,
        routing_key='report.submitted.failed',
        queue_arguments={
            'x-message-ttl': ttl_ms,
            'x-dead-letter-exchange': 'bahariwatch.events',
            'x-dead-letter-routing-key': 'report.submitted'
        }
    )
    retry_queue(channel).declare()

# Create DLQ
dlq = Queue(
    'report_submitted.dlq',
    exchange=dlx,
    routing_key='report.submitted.failed.final',
    durable=True
)
dlq(channel).declare()

print("✅ RabbitMQ retry configuration complete")

from fastapi import APIRouter, Depends, HTTPException
from services.common.auth import require_admin_role

router = APIRouter(prefix="/admin/sagas")

@router.get("/stuck")
def list_stuck_sagas(
    stuck_threshold_minutes: int = 60,
    admin: User = Depends(require_admin_role)

    recovery_service = SagaRecoveryService(db.session)

                "correlation_id": saga.correlation_id,
                "current_state": saga.current_state,
                "last_updated_at": saga.updated_at.isoformat(),
                "stuck_duration_minutes": 
                    (datetime.now() - saga.updated_at).total_seconds() / 60
            }
            for saga in stuck_sagas
        ]
    }

@router.post("/retry/{saga_id}")

    saga_id: str,
    admin: User = Depends(require_admin_role)
):
    """Manually retry failed saga"""
    recovery_service = SagaRecoveryService(db.session)
    
    try:

            resource_id=saga_id
        )
