# ADR-0001: Phase II Technology Stack Selection

> **Scope**: Document decision clusters, not individual technology choices. Group related decisions that work together (e.g., "Frontend Stack" not separate ADRs for framework, styling, deployment).

- **Status:** Accepted
- **Date:** 2025-12-12
- **Feature:** 001-task-crud-auth
- **Context:** Phase II requires a full-stack web application with authentication, replacing the Phase I in-memory Python CLI. The stack must support server-side rendering, type safety, rapid development, scalability, and secure authentication. Constitutional requirements mandate specific technologies to ensure consistency across the Evolution of Todo project phases.

## Decision

**Frontend Stack:**
- **Framework:** Next.js 16+ with App Router (NOT Pages Router)
- **Language:** TypeScript 5.x (strict mode enabled)
- **Styling:** Tailwind CSS 4.x (utility-first, no CSS-in-JS)
- **Authentication:** Better Auth with JWT plugin
- **Rendering:** Server Components by default, Client Components only for interactivity

**Backend Stack:**
- **Framework:** FastAPI 0.115+
- **Language:** Python 3.13+
- **Package Manager:** UV (fast, modern Python package management)
- **ORM:** SQLModel 0.0.24+ (NOT raw SQLAlchemy)
- **Validation:** Pydantic v2 (fast validation, TypeScript compatibility)
- **Authentication:** JWT middleware with python-jose, bcrypt for password hashing

**Database:**
- **RDBMS:** PostgreSQL 16
- **Local Development:** Docker PostgreSQL container
- **Production:** Neon Serverless PostgreSQL
- **Migrations:** Alembic

**Development Tools:**
- **Containerization:** Docker 24+, Docker Compose 2.x
- **Testing:** pytest + pytest-asyncio (backend), Jest + React Testing Library (frontend), Playwright (E2E)

## Consequences

### Positive

- **Type Safety End-to-End:** TypeScript (frontend) + Pydantic (backend) + SQLModel (database) ensures type safety across the entire stack
- **Modern React Patterns:** Next.js 16+ App Router with Server Components reduces JavaScript bundle size and improves performance
- **Fast Backend Development:** FastAPI provides automatic OpenAPI documentation, async support, and excellent developer experience
- **Unified Data Models:** SQLModel combines SQLAlchemy ORM with Pydantic validation, reducing code duplication
- **Constitutional Compliance:** All choices align with Phase II requirements, ensuring consistency across project phases
- **Excellent Tooling:** Next.js dev server with Fast Refresh, FastAPI auto-reload, and OpenAPI Swagger UI accelerate development
- **Production Ready:** Neon serverless PostgreSQL provides automatic scaling, backups, and branching for database
- **Strong Ecosystem:** All technologies have large communities, extensive documentation, and active maintenance

### Negative

- **Learning Curve:** Developers must learn Next.js App Router patterns (Server vs Client Components), SQLModel ORM, and Better Auth
- **Framework Coupling:** Tight coupling to Next.js App Router and FastAPI means migration to alternatives would be significant effort
- **Newer Technologies:** Next.js 16+ App Router and SQLModel 0.0.24+ are relatively new, with evolving best practices
- **Better Auth Maturity:** Better Auth is less mature than NextAuth, with smaller community and fewer integrations
- **UV Package Manager:** UV is newer than pip/poetry, with potential compatibility issues in some environments
- **Neon Dependency:** Production database relies on third-party SaaS (vendor lock-in risk, though PostgreSQL itself is portable)
- **Complexity for Small Projects:** Stack may be over-engineered for very simple use cases (but appropriate for Phase II+ evolution)

## Alternatives Considered

**Alternative Stack A: Pages Router + Express.js + Prisma**
- Frontend: Next.js Pages Router, Express.js backend, Prisma ORM
- Why rejected: Pages Router is older architecture, Express.js lacks automatic OpenAPI docs, Prisma has different migration model than Alembic
- Tradeoffs: More mature ecosystem but less aligned with modern React patterns and constitutional requirements

**Alternative Stack B: Remix + Django + Django ORM**
- Frontend: Remix (React framework), Django (Python web framework), Django ORM
- Why rejected: Remix has different mental model than Next.js, Django is heavier framework with more opinions, Django ORM doesn't integrate with Pydantic
- Tradeoffs: Proven stability but heavier weight, less type safety, slower iteration

**Alternative Stack C: Vite + Flask + SQLAlchemy**
- Frontend: Vite + React, Flask backend, raw SQLAlchemy
- Why rejected: Requires manual SSR setup, Flask is synchronous (no async), raw SQLAlchemy violates constitutional requirement for SQLModel
- Tradeoffs: More flexibility but more boilerplate, less integrated, violates Phase II constitution

**Alternative Stack D: SvelteKit + FastAPI + Tortoise ORM**
- Frontend: SvelteKit (Svelte framework), FastAPI backend, Tortoise ORM (async Python ORM)
- Why rejected: SvelteKit has smaller ecosystem than React/Next.js, Tortoise ORM doesn't integrate with Pydantic like SQLModel does
- Tradeoffs: Svelte is simpler than React but less widely adopted, Tortoise lacks SQLModel's Pydantic integration

**Why Chosen Stack Wins:**
- Constitutional alignment: All Phase II requirements explicitly met
- Type safety: Unified type system from database to frontend (SQLModel → Pydantic → TypeScript)
- Developer experience: Excellent tooling, hot reload, automatic documentation
- Performance: Server Components reduce bundle size, async FastAPI handles concurrent requests
- Ecosystem maturity: Large communities, extensive resources, proven in production
- Future-proof: App Router is React's future, FastAPI is modern async Python standard
