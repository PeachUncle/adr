# ADR 0005: GitHub Actions CI/CD Pipeline Strategy

**Status:** Accepted  
**Date:** 2025-09-10  
**Scope:** CI/CD Architecture

## Context

We need to implement a CI/CD pipeline that supports multiple environments, promotes container images safely, and integrates with Azure services securely. The pipeline must balance automation with control gates for enterprise compliance.

## Decision

We will implement a **multi-stage GitHub Actions pipeline** with **environment-based promotion gates** and **Azure workload identity federation**.

### Pipeline Architecture

```text
┌─────────────┐    ┌──────────────┐    ┌─────────────────┐
│   Test      │────│    Build     │────│   Promote Dev   │
│   Security  │    │   Container  │    │   Auto Deploy   │
│   Audit     │    │   Image      │    │                 │
└─────────────┘    └──────────────┘    └─────────────────┘
                                                │
                          ┌─────────────────────┘
                          │
                          ▼
                   ┌─────────────────┐    ┌─────────────────┐
                   │ Promote Staging │────│ Promote Prod    │
                   │ Manual Approval │    │ Manual Approval │
                   │                 │    │ Extra Validation│
                   └─────────────────┘    └─────────────────┘
```

### Workflow Stages

1. **Test Stage**: Runs on all PRs and pushes
   - Unit tests with coverage reporting
   - ESLint security scanning
   - npm audit for vulnerabilities
   - No Azure resource access required

2. **Build Stage**: Creates immutable container artifacts
   - Build container with semantic versioning
   - Tag with commit SHA for traceability
   - Push to shared ACR
   - Generate metadata for promotion

3. **Promote Dev**: Automatic promotion for main branch
   - Retag image with `dev-ready`
   - Deploy to development AKS cluster
   - Run integration tests
   - Update deployment status

4. **Promote Staging**: Manual approval required
   - Manual trigger or approval workflow
   - Retag image with `staging-ready`
   - Deploy to staging environment
   - Run end-to-end tests

5. **Promote Prod**: Enhanced validation and approval
   - Multiple approver requirement
   - Security validation checks
   - Retag image with `prod-ready`
   - Blue-green deployment strategy

## Authentication Strategy

### Azure Workload Identity Federation

```yaml
# No long-lived secrets in GitHub
- name: Azure Login
  uses: azure/login@v1
  with:
    client-id: ${{ secrets.AZURE_CLIENT_ID }}
    tenant-id: ${{ secrets.AZURE_TENANT_ID }}
    subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
    # No client-secret required with federated identity
```

### Required GitHub Secrets

- `AZURE_CLIENT_ID`: Service principal application ID
- `AZURE_TENANT_ID`: Azure AD tenant ID  
- `AZURE_SUBSCRIPTION_ID`: Target Azure subscription
- No `AZURE_CLIENT_SECRET` stored (federated identity)

## Container Image Strategy

### Tagging Pattern

```text
Base Build: myacr.azurecr.io/api-service-1:v1.0.0-abc1234
Dev Ready:  myacr.azurecr.io/api-service-1:dev-ready
Staging:    myacr.azurecr.io/api-service-1:staging-ready
Production: myacr.azurecr.io/api-service-1:prod-ready
Latest:     myacr.azurecr.io/api-service-1:latest
```

### Promotion Mechanics

```bash
# Build immutable artifact
docker build -t $ACR/$SERVICE:v1.0.0-$COMMIT_SHA

# Environment promotion (no rebuild)
docker tag $ACR/$SERVICE:v1.0.0-$COMMIT_SHA $ACR/$SERVICE:dev-ready
docker push $ACR/$SERVICE:dev-ready
```

## Deployment Strategy

### Kubernetes Deployment

- Namespace isolation per service
- Resource limits and health checks
- Rolling updates with readiness probes
- Automatic rollback on failed health checks

### Infrastructure as Code

- Separate workflows for infrastructure changes
- Terraform plan on PR, apply on merge
- Environment-specific approval gates
- State management via Azure Storage

## Security Controls

### Pipeline Security

- Dependabot for dependency updates
- Container vulnerability scanning
- Secret scanning in code
- OIDC token-based Azure authentication

### Runtime Security

- Non-root container execution
- Read-only file systems where possible
- Network policies for pod-to-pod communication
- Managed identity for Azure service access

## Environment Configuration

### Development Environment

- Automatic deployment on main branch merge
- Lower resource limits for cost optimization
- Relaxed security policies for faster iteration
- Comprehensive logging for debugging

### Staging Environment

- Manual promotion approval required
- Production-like configuration
- Full security scanning and validation
- Performance testing integration

### Production Environment

- Multiple approver requirements
- Blue-green deployment strategy
- Enhanced monitoring and alerting
- Automatic rollback capabilities

## Consequences

### Positive

- **Immutable Artifacts**: Same container across all environments
- **Audit Trail**: Complete traceability from commit to deployment
- **Security**: No long-lived secrets, federated identity
- **Scalability**: Pipeline supports multiple services and environments
- **Cost Efficiency**: Shared container registry, optimized resource usage

### Negative

- **Complexity**: Multi-stage pipeline requires understanding
- **Approval Overhead**: Manual gates may slow feature delivery
- **Debugging Challenges**: Container promotion can obscure source of issues
- **Azure Dependency**: Tight coupling with Azure services

## Implementation Guidelines

### New Service Onboarding

1. Copy pipeline template for new service
2. Update service name and resource references
3. Configure environment-specific secrets
4. Test deployment to development environment

### Security Hardening

- Rotate service principal credentials quarterly
- Enable branch protection rules
- Require PR reviews for pipeline changes
- Monitor pipeline execution for anomalies
