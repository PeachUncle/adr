## Context

This is a 100% AI-generated codebase for a solo indie hacker who is NOT a developer. The code is written BY AI, maintained BY AI, and debugged BY AI. There will NEVER be a human developer reading this code to learn from it.

### Background

Traditional software development practices assume:
- Human developers will read and maintain the code
- Multiple environments with varying capabilities
- Need for backward compatibility
- Defensive programming for edge cases
- Documentation for human understanding

**None of these assumptions apply here.**

### Decision Drivers

- **AI-only maintenance**: No human will debug this code
- **Solo project**: No team collaboration needed
- **Modern stack only**: Can use latest features without concern
- **Fast iteration**: Need rapid development without defensive overhead
- **Clear failures**: AI needs obvious error messages to fix problems
- **Context window limits**: Smaller codebase fits better in AI context
- **Asset valuation metrics**: Speed to market drives organic traffic, waitlist growth, and MRR (PRD goals)

## Decision

**Adopt "Practical-Lean & Fail-Fast" as the CORE PHILOSOPHY for all code generation.**

This philosophy prioritizes:
1. **Directness** over abstraction
2. **Failing fast** over graceful degradation (for application errors)
3. **Latest features** over compatibility
4. **One way** over flexibility
5. **AI readability** over human readability

### Rationale

- **Minimal code surface** = fewer bugs
- **Clear failures** = easy AI debugging
- **Fast development** = no time wasted on "what ifs"
- **Small codebase** = fits in AI context window
- **No legacy burden** = always modern
- **Better asset valuation** = faster time to market increases organic traffic and MRR

### Implementation Approach

#### What Practical-Lean Means

**YES ✅**
- Direct, obvious code that fails immediately when something is wrong
- Latest stable versions only (PHP 8.4, PostgreSQL 18)
- One way to do things, not three
- Clear error messages that AI can fix
- Assume modern environment always
- PHP 8.4+ features (property hooks, asymmetric visibility)

**NO ❌**
- Backward compatibility checks
- Polyfills or fallbacks
- "What if X doesn't exist?" defensive code
- Multiple code paths for edge cases
- Comments explaining code to humans
- Abstract factories, design patterns for "flexibility"
- "Enterprise" patterns (repositories, services, DTOs)

## Consequences

### Positive Consequences

- **Minimal code surface**: Fewer places for bugs to hide
- **Clear failures**: AI sees exact error and can fix immediately
- **Fast development**: No time spent on defensive programming
- **Small codebase**: Entire project fits in AI context window
- **No legacy burden**: Always using latest, best features
- **Reduced complexity**: No abstraction layers to navigate
- **Faster execution**: No compatibility checks at runtime
- **Better asset valuation**: Speed to market drives traffic/MRR metrics

### Negative Consequences

- **Will break on older PHP/PostgreSQL** (intended!)
- **No graceful degradation for application errors** (intended!)
- **Requires PHP 8.4+ environment** (intended!)
- **Not "enterprise ready"** (not the goal!)
- **No human-friendly documentation** (not needed!)
- **Cannot run on shared hosting** (use modern hosting!)

### Risks and Mitigation

- **Risk**: Environment doesn't have PHP 8.4
  - **Mitigation**: Use Docker or modern hosting that supports it (Hetzner CPX21, €15/mo)

- **Risk**: Silent failures could go unnoticed
  - **Mitigation**: That's why we fail fast - problems surface immediately

## Alternatives Considered

### Option 1: Traditional Defensive Programming

- **Description**: Check for function existence, version compatibility, graceful fallbacks
- **Pros**: Works in more environments, handles edge cases
- **Cons**: 3x more code, harder to debug, slower development
- **Rejected because**: Unnecessary complexity for AI-maintained code

### Option 2: Enterprise Patterns

- **Description**: Repository pattern, service layers, DTOs, dependency injection
- **Pros**: "Best practices", testable, scalable
- **Cons**: Massive overhead, abstraction hell, doesn't fit in context window
- **Rejected because**: Solo project doesn't need enterprise complexity

### Option 3: Human-Oriented Code

- **Description**: Extensive comments, documentation, clean code principles
- **Pros**: Readable by humans, educational, maintainable by teams
- **Cons**: Wasted effort - no human will read this
- **Rejected because**: This is AI-to-AI code

## Implementation Details

### Code Examples

#### 1. FAIL FAST

```php
// ❌ WRONG - defensive programming
if (function_exists('uuidv7')) {
    $id = uuidv7();
} else {
    $id = uuid4(); // fallback
}

// ✅ RIGHT - assume it exists
$id = uuidv7(); // PHP will crash if missing - GOOD!
```

#### 2. NO BACKWARD COMPATIBILITY

```php
// ❌ WRONG - checking versions
if (PHP_VERSION_ID >= 80400) {
    // use property hooks
} else {
    // use getters/setters
}

// ✅ RIGHT - just use it
public string $email {
    set => filter_var($value, FILTER_VALIDATE_EMAIL) ?: throw new Exception();
}
```

#### 3. ONE OBVIOUS WAY

```php
// ❌ WRONG - multiple options
class UserRepository {
    public function find($id) {...}
    public function findById($id) {...}
    public function getUserById($id) {...}
}

// ✅ RIGHT - one way
Flight::db()->fetchRow('SELECT * FROM users WHERE id = ?', [$id]);
```

#### 4. NO HUMAN-ORIENTED CODE

```php
// ❌ WRONG - explaining to humans
/**
 * This method validates email according to RFC 5322
 * @param string $email The email to validate
 * @return bool True if valid
 */
public function validateEmail(string $email): bool {
    // Check if email matches pattern
    return filter_var($email, FILTER_VALIDATE_EMAIL);
}

// ✅ RIGHT - AI doesn't need comments
public string $email {
    set => filter_var($value, FILTER_VALIDATE_EMAIL) ?: throw new Exception();
}
```

### Two-Tier Error Handling Strategy

**Fail-fast applies to application errors, NOT operational errors.**

#### 1. Application Errors (Programming Bugs) → Fail-Fast
- Invalid types, null dereference, missing config
- **Action**: Throw immediately (NOT: error_log + continue)
- **Example**: Invalid user input to business logic

```php
// ✅ Fail-fast for bugs (NOT: degradation)
public string $email {
    set => filter_var($value, FILTER_VALIDATE_EMAIL)
        ?: throw new \InvalidArgumentException('Invalid email');
}
```

#### 2. Operational Errors (Infrastructure Failures) → Graceful Degradation
- Disk full, permission denied, network timeout
- **Action**: `error_log()` + continue (NOT: throw)
- **Example**: Log file write failures (see .strategic-claude-basic/product/ARCHITECTURE.md for operational error handling patterns)

```php
// ✅ Degrade gracefully for ops (NOT: throw)
$fp = fopen($logPath, 'a');
if ($fp === false) {
    error_log("Cannot open log file: $logPath");
    return; // Throwing would crash app - WRONG for ops
}
```

**Decision Rule**: Code bug → throw exception. Infrastructure limit → error_log + continue.

#### HTTP Status Code Mapping

Application errors must map to appropriate 4xx HTTP status codes in Controllers:

| Error Type | HTTP Status | Example | Action |
|------------|-------------|---------|--------|
| **Validation Failure** | 422 Unprocessable Entity | Invalid email format, missing required field | Throw `\InvalidArgumentException` in Model, catch in Controller → 422 |
| **Authentication Required** | 401 Unauthorized | No session token, expired token | Throw `\RuntimeException` in Middleware → 401 |
| **Authorization Failure** | 403 Forbidden | Insufficient trust level, not listing owner | Throw `\RuntimeException` in Controller → 403 |
| **Resource Not Found** | 404 Not Found | Tool slug doesn't exist, thread ID invalid | Return null from query, Controller uses `Flight::halt(404)` |
| **Rate Limit Exceeded** | 429 Too Many Requests | Exceeded posting limit, too many signups | Throw `\RuntimeException` in RateLimitMiddleware → 429 |

Operational errors must map to 5xx status codes with retry/backoff guidance:

| Error Type | HTTP Status | Example | Action |
|------------|-------------|---------|--------|
| **Database Timeout** | 503 Service Unavailable | Query exceeded 30s timeout | Catch `\PDOException`, log error, return 503 with `Retry-After: 60` |
| **External Service Failure** | 502 Bad Gateway | Email API (Postmark) down | Catch connection exception, log, queue for retry, return 502 |
| **Disk Full** | 507 Insufficient Storage | Cannot write upload to disk | Catch write error, log, return 507, alert ops team |

**Global Error Handler Pattern** (Recommended - DRY):
```php
// In app/config/error_handlers.php
Flight::map('error', function(\Throwable $e) {
    // Log all errors
    error_log("Unhandled error: " . $e->getMessage());

    // Operational errors → 5xx with graceful degradation
    if ($e instanceof \PDOException) {
        Flight::halt(503, 'Service temporarily unavailable');
    }

    // Application errors → 4xx fail-fast
    if ($e instanceof \InvalidArgumentException) {
        Flight::halt(422, $e->getMessage());
    }

    // Default: 500 for unexpected errors
    Flight::halt(500, 'An internal server error occurred');
});

// Controllers stay clean - just throw, don't catch
public function create(): void {
    $request = Flight::request();
    $email = $request->data->email;

    // Application error: fail-fast (throw)
    if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
        throw new \InvalidArgumentException('Invalid email format');
    }

    // Operational error handling: PDOException thrown by database
    // Global handler catches it → 503
    $db = Flight::db();
    $db->execute('INSERT INTO waitlist (email) VALUES (?)', [$email]);

    Flight::json(['success' => true], 201);
}
```

This is cleaner than try-catch in every controller (DRY principle).

**ALL components** in the codebase must follow this philosophy:

- Templates (Plates)

### Migration Strategy

For existing code that doesn't follow this philosophy:
1. Remove all defensive checks
2. Remove all backward compatibility
3. Remove all unnecessary abstractions
4. Remove all human-oriented comments
5. Let it fail if environment is wrong
