# ADR-009: Service Granularity Analysis

## Status

Accepted

## Context

The BahariWatch system requires a distributed architecture to monitor illegal, unreported, and unregulated (IUU) fishing along Kenya's coastline. While ADR-001 established microservices as the architectural style, it did not provide rigorous justification for *why* specific services exist as separate deployable units rather than being combined.

According to "Software Architecture: The Hard Parts" (Chapter 7), determining service granularity is one of the hardest decisions in distributed architecture. The wrong granularity leads to either:
- **Too Fine-Grained:** Excessive inter-service communication, operational complexity, deployment overhead, data consistency challenges
- **Too Coarse-Grained:** Lost benefits of independent deployability, scalability bottlenecks, fault isolation failures, team coupling

### Business Drivers

From the BahariWatch proposal:
- **Community Reporting:** Small-scale fishers and coastal residents submit GPS-stamped photographic evidence of suspected IUU fishing anonymously
- **Vessel Tracking Integration:** Correlate community reports with AIS/VMS/PDS vessel position data
- **Real-Time Alerting:** Generate alerts for law enforcement within sub-5-second latency when matches are detected
- **Analytics & Surveys:** Support research analysis, BMU performance evaluation, and pattern detection for hotspot mapping
- **Multi-Channel Notifications:** Deliver alerts via SMS, email, and in-app notifications
- **Enforcement Dashboard:** Provide government agencies with secure access to verified IUU evidence
- **Scalability Requirements:** Support 10,000+ coastal users with spike handling during peak reporting periods
- **High Availability:** 99.5% uptime SLO for critical reporting and alerting workflows

### Technical Constraints

- **Integration with other ADRs:**
  - ADR-001: Microservices architecture style chosen
  - ADR-002: Event-driven choreography for service communication
  - ADR-003: Monolithic database with logical schema separation
  - ADR-007: Data ownership boundaries defined per bounded context
  - ADR-008: Security requirements including anonymous reporting, RBAC, end-to-end encryption

### Architecture Characteristics Affected

- **Deployability:** Independent deployment frequency per service
- **Scalability:** Ability to scale specific functions independently
- **Fault Tolerance:** Isolation of failures to minimize blast radius
- **Maintainability:** Team autonomy and cognitive load management
- **Performance:** Response time for real-time alerting and hotspot generation
- **Security:** Principle of least privilege and attack surface reduction

### Framework: Granularity Disintegrators vs Integrators

"Hard Parts" Chapter 7 provides competing forces:

**Granularity Disintegrators** (forces pushing toward smaller services):
1. **Service Scope & Function:** Single responsibility principle
2. **Code Volatility:** Different change frequencies
3. **Scalability & Throughput:** Different load characteristics
4. **Fault Tolerance & Availability:** Isolation of critical vs non-critical functions
5. **Security:** Separation of sensitive operations
6. **Extensibility:** Ability to add features independently

**Granularity Integrators** (forces pushing toward larger services):
1. **Database Transactions:** Need for ACID consistency
2. **Workflow & Choreography:** Communication overhead between services
3. **Shared Code:** Duplication vs reuse trade-offs
4. **Data Relationships:** Foreign key constraints and referential integrity

## Decision

We establish the following service boundaries for BahariWatch, each justified by granularity disintegrators/integrators analysis:

### Core Services

1. **Report Management Service**
2. **Vessel Tracking Integration Service**
3. **Matching & Correlation Service**
4. **Alert Management Service**
5. **Notification Delivery Service**
6. **Geospatial Analysis Service**
7. **User & Identity Service**
8. **Analytics & Survey Service**

### Supporting Services

9. **API Gateway** (ADR-005)
10. **Audit & Compliance Service** (from ADR-007)

## Rationale

### Service 1: Report Management Service

**Responsibilities:**
- Accept GPS-stamped photo submissions from mobile/web clients
- Store report metadata (location, timestamp, description, device fingerprint)
- Manage report lifecycle (submitted → under review → verified/dismissed)
- Enforce anonymous reporting rules (no PII storage)
- Publish `ReportSubmitted` events

**Granularity Disintegrators (Favor Separation):**
- ✅ **Service Scope:** Single bounded context—"Report Submission & Lifecycle" (DDD)
- ✅ **Code Volatility:** HIGH—Community feedback may drive frequent UX/validation changes
- ✅ **Scalability:** HIGH LOAD—Primary entry point for 10,000+ users; needs independent horizontal scaling
- ✅ **Fault Tolerance:** CRITICAL—Must remain available even if matching/alerting fails (99.5% SLO)
- ✅ **Security:** Handles potentially sensitive photo evidence; requires strict access controls
- ✅ **Extensibility:** Future features like video uploads, multi-photo reports, offline queue

**Granularity Integrators (Favor Combining):**
- ⚠️ **Database Transactions:** Requires ACID for report metadata + photo storage reference (satisfied by ADR-003 schema: `report_management`)
- ⚠️ **Workflow:** Must immediately publish `ReportSubmitted` event (async, no strong coupling)
- ✅ **Shared Code:** Minimal overlap with other services (photo encryption is domain-specific)
- ✅ **Data Relationships:** Owns `reports` table; no foreign keys to other service schemas (ADR-007)

**Decision:** **SEPARATE SERVICE** ✅

**Justification:** High code volatility, critical availability requirement, and independent scalability needs outweigh integration forces. This service can be deployed/scaled without affecting matching or alerting.

### Service 2: Vessel Tracking Integration Service

**Responsibilities:**
- Ingest AIS/VMS/PDS feeds from external sources (polling or webhooks)
- Normalize vessel position data into canonical format
- Store historical vessel tracks in `vessel_tracking` schema
- Publish `VesselPositionUpdated` events
- Implement circuit breakers for unreliable external APIs

**Granularity Disintegrators (Favor Separation):**
- ✅ **Service Scope:** Single bounded context—"External Vessel Data Ingestion"
- ✅ **Code Volatility:** MEDIUM—External API changes (AIS/VMS providers may update contracts)
- ⚠️ **Scalability:** MODERATE—Batch ingestion of position data (not user-facing traffic)
- ✅ **Fault Tolerance:** ISOLATION NEEDED—External API failures should not cascade to other services
- ✅ **Security:** May handle government vessel data (sensitive); needs separate access controls
- ✅ **Extensibility:** Future integration with LRIT (Long Range Identification and Tracking), radar data, satellite imagery

**Granularity Integrators (Favor Combining):**
- ⚠️ **Database Transactions:** Simple writes to `vessel_tracking` schema (no cross-schema transactions)
- ⚠️ **Workflow:** Loosely coupled via events (Matching Service subscribes to `VesselPositionUpdated`)
- ✅ **Shared Code:** Minimal overlap (geospatial utilities shared via library, not service)
- ✅ **Data Relationships:** Owns `vessels` and `vessel_positions` tables independently

**Decision:** **SEPARATE SERVICE** ✅

**Justification:** Fault tolerance isolation is critical—unreliable external APIs (VMS downtime noted in proposal: "unpaid maintenance subscription of Sh16 million") must not block report submission or alerting. Circuit breaker and retry logic are domain-specific to this service.

### Service 3: Matching & Correlation Service

**Responsibilities:**
- Subscribe to `ReportSubmitted` and `VesselPositionUpdated` events
- Execute geospatial correlation algorithm (ST_DWithin query for vessels within 5 km of report location, ±30 min time window)
- Generate `MatchFound` or `NoMatchFound` events
- Store match results in `matching_service` schema
- Implement hotspot detection (cluster analysis of repeat matches)

**Granularity Disintegrators (Favor Separation):**
- ✅ **Service Scope:** Single bounded context—"Geospatial Correlation Logic"
- ✅ **Code Volatility:** MEDIUM—Algorithm tuning (distance thresholds, time windows) based on enforcement feedback
- ✅ **Scalability:** COMPUTE-INTENSIVE—PostGIS spatial queries are CPU-heavy; needs independent scaling
- ✅ **Fault Tolerance:** NON-CRITICAL—If matching fails, reports are still stored; can retry asynchronously
- ⚠️ **Security:** Reads from `report_management` and `vessel_tracking` schemas (read-only access via views, ADR-007)
- ✅ **Extensibility:** Future ML models for pattern recognition, anomaly detection

**Granularity Integrators (Favor Combining):**
- ⚠️ **Database Transactions:** Reads from multiple schemas (`report_management`, `vessel_tracking`) but writes only to `matching_service` schema—no distributed transaction needed (eventual consistency acceptable)
- ⚠️ **Workflow:** Central orchestrator of the saga (ADR-004: Anthology Saga pattern)
- ⚠️ **Shared Code:** Heavy use of PostGIS functions (but this is database-level, not application code duplication)
- ⚠️ **Data Relationships:** Stores foreign keys to `reports.id` and `vessels.id` (logical references, not enforced FKs per ADR-003)

**Why Not Combine with Report Service?**
- **Different scalability profile:** Matching is CPU-bound (geospatial queries), Report Service is I/O-bound (photo uploads)
- **Different fault tolerance needs:** Report submission must succeed even if matching is slow/down
- **Different deployment frequency:** Matching algorithm changes (tuning thresholds) should not require redeploying report submission logic

**Why Not Combine with Vessel Tracking Service?**
- **Separation of concerns:** Vessel Tracking is integration-focused (adapter pattern for external APIs), Matching is computation-focused (domain logic)
- **Independent extensibility:** Matching may evolve to ML-based predictions without affecting ingestion

**Decision:** **SEPARATE SERVICE** ✅

**Justification:** Compute-intensive geospatial correlation requires independent scaling. Fault isolation ensures report submission remains fast even when matching is under heavy load. This is the "heart" of the system's domain logic and warrants dedicated ownership.

### Service 4: Alert Management Service

**Responsibilities:**
- Subscribe to `MatchFound` events
- Apply alert rules (e.g., only alert on vessels >24m, or specific gear types)
- Store alert records in `alert_management` schema
- Publish `AlertCreated` events (consumed by Notification Service)
- Implement alert deduplication (prevent alert spam for same vessel within 1 hour)
- Provide alert acknowledgment API for enforcement officers

**Granularity Disintegrators (Favor Separation):**
- ✅ **Service Scope:** Single bounded context—"Alert Rules & Lifecycle"
- ✅ **Code Volatility:** HIGH—Enforcement agencies may frequently change alert criteria (gear types, vessel sizes, time windows)
- ⚠️ **Scalability:** LOW LOAD—Only processes matches (subset of reports); scales with match volume, not user submissions
- ✅ **Fault Tolerance:** CRITICAL—Must guarantee delivery to enforcement (99.5% SLO); needs retry logic and dead letter queue
- ✅ **Security:** Determines who receives alerts (RBAC enforcement); sensitive enforcement-only data
- ✅ **Extensibility:** Future features: escalation workflows, multi-agency routing (KWS, KFS, Navy), priority scoring

**Granularity Integrators (Favor Combining):**
- ⚠️ **Database Transactions:** Simple writes to `alert_management` schema (no cross-schema transactions)
- ⚠️ **Workflow:** Loosely coupled via events (subscribes to `MatchFound`, publishes `AlertCreated`)
- ✅ **Shared Code:** Minimal overlap with other services (rule engine is domain-specific)
- ✅ **Data Relationships:** Stores foreign key to `matching_service.matches.id` (logical reference only)

**Why Not Combine with Matching Service?**
- **Different volatility:** Alert rules change frequently (business logic), matching algorithms change infrequently (stable domain logic)
- **Different security context:** Alert Service enforces RBAC (who sees what alerts), Matching Service is computation-only
- **Deployment independence:** Rule changes (e.g., "alert only on vessels >30m") should not require redeploying geospatial correlation logic

**Why Not Combine with Notification Service?**
- **Separation of concerns:** Alert Management is policy enforcement (business rules), Notification is delivery mechanism (infrastructure)
- **Extensibility:** Alerts may route to multiple channels (SMS, email, dashboard) or external systems (government APIs)

**Decision:** **SEPARATE SERVICE** ✅

**Justification:** High code volatility (rule changes) and critical delivery guarantees warrant dedicated service. This isolates business logic from infrastructure concerns (notification delivery).

### Service 5: Notification Delivery Service

**Responsibilities:**
- Subscribe to `AlertCreated` events (and other notification triggers: `ReportVerified`, `SurveyInvitation`)
- Send SMS via Africa's Talking API
- Send emails via SendGrid API
- Send in-app push notifications via Firebase Cloud Messaging
- Implement retry logic with exponential backoff for failed deliveries
- Store delivery status (sent/failed) in `notification_delivery` schema

**Granularity Disintegrators (Favor Separation):**
- ✅ **Service Scope:** Single bounded context—"Multi-Channel Notification Delivery"
- ⚠️ **Code Volatility:** LOW—Infrastructure integration code is stable once implemented
- ⚠️ **Scalability:** MODERATE—Scales with alert volume + survey invitations (not as high as report submissions)
- ✅ **Fault Tolerance:** NON-CRITICAL—Failed notifications should not block alerts from being created; retries can be asynchronous
- ✅ **Security:** Handles PII (phone numbers, email addresses); separate from anonymous reporting services
- ✅ **Extensibility:** Future channels: WhatsApp Business API, Telegram bots, webhook integrations to government systems

**Granularity Integrators (Favor Combining):**
- ⚠️ **Database Transactions:** Simple writes to `notification_delivery` schema (no cross-schema transactions)
- ⚠️ **Workflow:** Loosely coupled via events (subscribes to `AlertCreated`, `ReportVerified`, etc.)
- ⚠️ **Shared Code:** SMS/Email client libraries could be shared (but different APIs: Africa's Talking vs SendGrid)
- ✅ **Data Relationships:** No foreign keys to other schemas (stores alert_id as logical reference)

**Why Not Combine with Alert Service?**
- **Separation of concerns:** Alert Management is domain logic (who gets what alert), Notification is infrastructure (how to deliver)
- **Fault isolation:** Third-party API failures (Africa's Talking downtime) should not prevent alerts from being created
- **Extensibility:** Adding new channels (WhatsApp) should not require changing alert rule logic

**Decision:** **SEPARATE SERVICE** ✅

**Justification:** Fault tolerance isolation for third-party API dependencies. This service can fail and retry without blocking alert creation. Clean separation between "what to notify" (Alert Service) and "how to deliver" (Notification Service).

### Service 6: Geospatial Analysis Service

**Responsibilities:**
- Generate hotspot maps (cluster analysis of high-density IUU reports)
- Compute risk scores for specific regions (based on report frequency, vessel patterns)
- Execute scheduled batch analytics (weekly/monthly reports)
- Provide geospatial query API for dashboard (e.g., "show all reports within 10 km of Malindi")
- Store analytical results in `analytics_reporting` schema (separate from operational data per ADR-013)

**Granularity Disintegrators (Favor Separation):**
- ✅ **Service Scope:** Single bounded context—"Geospatial Analytics & Hotspot Detection"
- ⚠️ **Code Volatility:** LOW—Statistical algorithms are stable; may add ML models over time
- ✅ **Scalability:** COMPUTE-INTENSIVE—Batch processing of large spatial datasets; needs dedicated CPU/memory resources
- ✅ **Fault Tolerance:** NON-CRITICAL—Analytics failures should not affect real-time reporting/alerting
- ⚠️ **Security:** Read-only access to historical data (no sensitive PII beyond what's already anonymized)
- ✅ **Extensibility:** Future ML models (predict IUU risk), integration with satellite imagery, oceanographic data (currents, SST)

**Granularity Integrators (Favor Combining):**
- ⚠️ **Database Transactions:** Reads from multiple schemas (`report_management`, `vessel_tracking`, `matching_service`) but writes only to `analytics_reporting` schema—CQRS pattern (ADR-013)
- ⚠️ **Workflow:** Asynchronous batch processing (scheduled jobs, not event-driven)
- ⚠️ **Shared Code:** Uses same PostGIS functions as Matching Service (but analytics queries are more complex: clustering algorithms like DBSCAN)
- ⚠️ **Data Relationships:** No write dependencies on operational schemas (read-only analytical queries)

**Why Not Combine with Matching Service?**
- **Different scalability profile:** Analytics runs batch jobs (hours-long processing), Matching runs real-time queries (seconds)
- **Resource isolation:** Heavy analytical queries should not starve real-time matching of CPU/memory
- **Deployment independence:** Adding ML models for risk prediction should not require redeploying real-time matching logic

**Decision:** **SEPARATE SERVICE** ✅

**Justification:** CQRS separation between operational (real-time) and analytical (batch) workloads. Compute-intensive hotspot generation requires dedicated resources and should not compete with real-time alerting.

### Service 7: User & Identity Service

**Responsibilities:**
- Manage user accounts (BMU officers, enforcement agents, admins, researchers)
- Authenticate API requests (JWT token issuance and validation)
- Enforce RBAC policies (role-based access control per ADR-008)
- Generate anonymous device fingerprints (SHA-256 hash for community reporters)
- Store user profiles in `user_management` schema (ADR-007)
- Provide OAuth2 authorization for government agency integrations (ADR-008)

**Granularity Disintegrators (Favor Separation):**
- ✅ **Service Scope:** Single bounded context—"Identity & Access Management"
- ⚠️ **Code Volatility:** LOW—IAM logic is stable; role definitions may change occasionally
- ✅ **Scalability:** HIGH LOAD—Every API request requires JWT validation (but caching reduces load)
- ✅ **Fault Tolerance:** CRITICAL—If auth fails, entire system is inaccessible (99.5% SLO); needs high availability
- ✅ **Security:** Handles most sensitive data (passwords, API keys, PII); must be isolated with strictest controls
- ✅ **Extensibility:** Future SSO integration (Google, Microsoft), biometric authentication, hardware tokens

**Granularity Integrators (Favor Combining):**
- ⚠️ **Database Transactions:** Simple writes to `user_management` schema (no cross-schema transactions)
- ⚠️ **Workflow:** Synchronous dependency for other services (all services call User Service for JWT validation)
- ⚠️ **Shared Code:** JWT libraries shared (but validation logic is centralized in this service)
- ✅ **Data Relationships:** No foreign keys from other schemas (other services store user_id as logical reference)

**Why Not Combine with Report Service?**
- **Security isolation:** IAM requires strictest controls; separating reduces attack surface
- **Reusability:** All services (Report, Alert, Analytics, etc.) need authentication; centralized service avoids duplication
- **Regulatory compliance:** GDPR/Kenya DPA require clear data ownership for PII (ADR-007)

**Decision:** **SEPARATE SERVICE** ✅

**Justification:** Security isolation and reusability. This is a cross-cutting concern consumed by all services, warranting dedicated ownership with highest security standards.

### Service 8: Analytics & Survey Service

**Responsibilities:**
- Manage survey campaigns (e.g., "BMU satisfaction survey," "IUU perception study")
- Collect survey responses from mobile/web clients
- Store responses in `analytics_reporting` schema
- Generate statistical reports (aggregate data, anonymized)
- Provide data export API for research institutions (KMFRI, universities)
- Enforce data retention policies (ADR-013: anonymize PII after 6 months)

**Granularity Disintegrators (Favor Separation):**
- ✅ **Service Scope:** Single bounded context—"Research Surveys & Data Export"
- ✅ **Code Volatility:** MEDIUM—Survey questions and formats change frequently per research needs
- ⚠️ **Scalability:** LOW LOAD—Surveys are periodic (not continuous like reporting)
- ⚠️ **Fault Tolerance:** NON-CRITICAL—Survey downtime does not affect core reporting/alerting workflows
- ⚠️ **Security:** Handles research data (less sensitive than enforcement data, but still subject to GDPR)
- ✅ **Extensibility:** Future integrations with external research platforms (Qualtrics, ODK)

**Granularity Integrators (Favor Combining):**
- ⚠️ **Database Transactions:** Simple writes to `analytics_reporting` schema (no cross-schema transactions)
- ⚠️ **Workflow:** Independent of operational workflows (not event-driven; standalone CRUD API)
- ⚠️ **Shared Code:** Minimal overlap with other services (survey logic is domain-specific)
- ⚠️ **Data Relationships:** May reference user_id from `user_management` schema for authenticated surveys (but anonymous surveys have no FK)

**Why Not Combine with Geospatial Analysis Service?**
- **Different volatility:** Survey formats change frequently (research requirements), geospatial algorithms are stable
- **Different user base:** Surveys target community users, geospatial analysis serves enforcement dashboards
- **Deployment independence:** Adding new survey questions should not require redeploying hotspot generation logic

**Why Not Combine with Report Service?**
- **Different bounded context:** Surveys are research-focused (non-operational), reports are enforcement-focused (operational)
- **Different lifecycle:** Survey campaigns have start/end dates; reports are continuous

**Decision:** **SEPARATE SERVICE** ✅

**Justification:** Different bounded context (research vs enforcement) and different volatility profile. Surveys are a distinct business capability mentioned in the proposal ("survey system for BMU evaluation").

## Trade-Off Analysis

### Quantitative Service Sizing Matrix

| Service | LOC Estimate | Deployment Freq | Scalability Need | Fault Tolerance | Team Size |
|---------|-------------|----------------|-----------------|-----------------|-----------|
| **Report Management** | 3,000 | Weekly | HIGH (horizontal) | CRITICAL (99.5%) | 2-3 devs |
| **Vessel Tracking Integration** | 2,500 | Monthly | MODERATE (batch) | ISOLATION NEEDED | 2 devs |
| **Matching & Correlation** | 4,000 | Bi-weekly | HIGH (CPU-bound) | NON-CRITICAL (async) | 3-4 devs |
| **Alert Management** | 2,000 | Weekly | MODERATE | CRITICAL (99.5%) | 2 devs |
| **Notification Delivery** | 1,500 | Monthly | MODERATE | NON-CRITICAL (retry) | 1-2 devs |
| **Geospatial Analysis** | 3,500 | Monthly | HIGH (batch) | NON-CRITICAL | 2-3 devs |
| **User & Identity** | 2,000 | Quarterly | HIGH (caching) | CRITICAL (99.9%) | 2 devs |
| **Analytics & Survey** | 2,500 | Bi-weekly | LOW | NON-CRITICAL | 2 devs |
| **API Gateway** | 1,000 | Quarterly | HIGH (gateway) | CRITICAL (99.9%) | 1-2 devs |
| **Audit & Compliance** | 1,500 | Quarterly | LOW (append-only) | CRITICAL (99.5%) | 1-2 devs |

**Total System Complexity:** ~23,500 LOC across 10 services (~2,350 LOC per service—within "Sweet Spot" range per Hard Parts p. 137)

### Inter-Service Communication Overhead

| Communication Path | Frequency | Latency Impact | Mitigation |
|-------------------|-----------|----------------|------------|
| Report → Matching | Per report submission | ~50ms event publish | Async (no blocking) |
| Matching → Alert | Per match found (~20% of reports) | ~50ms event publish | Async (no blocking) |
| Alert → Notification | Per alert created | ~100ms (external API) | Async with retry |
| API Gateway → User Service | Every authenticated request | ~10ms (JWT validation) | Redis cache (95% hit rate) |
| API Gateway → Report/Alert/Analytics | Per API call | ~20-50ms (internal network) | HTTP/2, connection pooling |
| Geospatial Analysis → All schemas (read) | Nightly batch | N/A (offline) | Read replicas (ADR-003) |

**Total Latency Budget:** Report submission → Alert delivery = ~210ms (well under 5-second SLO)

### Alternatives Considered

#### Alternative 1: Combine Matching + Alert into "Correlation & Alerting Service"

**Rationale for Rejection:**
- **Violates Single Responsibility Principle:** Matching is computation (geospatial correlation), Alert is policy enforcement (business rules)
- **Code volatility mismatch:** Alert rules change weekly (enforcement feedback), matching algorithm changes monthly
- **Deployment coupling:** Changing alert rules (e.g., "only alert vessels >30m") would require redeploying geospatial correlation logic (high risk)
- **Team autonomy:** Combining forces data science team (matching algorithms) and enforcement policy team (alert rules) to coordinate deployments

**Trade-Off:** Would reduce inter-service communication by 1 hop (~50ms saved), but loses deployment independence and team autonomy.

#### Alternative 2: Combine Report + Vessel Tracking into "Data Ingestion Service"

**Rationale for Rejection:**
- **Different fault tolerance profiles:** Community reports are user-facing (must stay up), vessel tracking is backend integration (can tolerate downtime)
- **Different scalability patterns:** Reports are high-volume user traffic (10,000+ users), vessel tracking is low-volume batch ingestion (3 external APIs)
- **Security isolation:** Reports handle anonymous user data, vessel tracking handles government-sensitive vessel positions (different threat models)
- **Extensibility:** Future integration with satellite imagery (for vessel tracking) should not affect report submission logic

**Trade-Off:** Would reduce operational complexity (9 services instead of 10), but loses fault isolation and security boundaries.

#### Alternative 3: Combine Geospatial Analysis + Analytics/Survey into "Analytics & Reporting Service"

**Rationale for Rejection:**
- **Different user bases:** Geospatial analysis serves enforcement dashboards (real-time queries), surveys serve researchers (batch export)
- **Different data models:** Geospatial uses PostGIS spatial types, surveys use flat relational tables
- **Resource contention:** Heavy geospatial queries (DBSCAN clustering) could starve survey API responses

**Trade-Off:** Would simplify service catalog, but loses clear separation between operational analytics (hotspots) and research analytics (surveys).

#### Alternative 4: Combine Notification + API Gateway (both are infrastructure)

**Rationale for Rejection:**
- **Different responsibilities:** API Gateway is synchronous request routing, Notification is asynchronous message delivery
- **Different scaling patterns:** Gateway scales with total API traffic (reads + writes), Notification scales with alert volume (writes only)
- **Deployment risk:** Gateway is critical path for all requests (99.9% SLO), Notification failures should not bring down entire system

**Trade-Off:** Would reduce service count, but increases blast radius of failures.

## Architecture Characteristics Impact

| Characteristic | Impact | Explanation |
|---------------|--------|-------------|
| **Scalability** | ↑ **Highly Positive** | Independent scaling: Report Service handles 10,000+ users, Matching Service scales CPU for geospatial queries, Geospatial Analysis scales memory for batch analytics |
| **Performance** | → **Neutral** | Inter-service latency (~210ms total) is well under 5-second SLO; Redis caching mitigates JWT validation overhead |
| **Fault Tolerance** | ↑ **Highly Positive** | Critical services (Report, Alert, User) isolated from non-critical (Notification, Analytics); external API failures (VMS downtime) do not cascade |
| **Maintainability** | ↑ **Positive** | Single Responsibility Principle per service; team autonomy (each service has 1-2 dedicated developers); reduced cognitive load |
| **Testability** | ↑ **Positive** | Services can be tested in isolation; contract testing via Pact (ADR-007); fitness functions enforce boundaries |
| **Deployability** | ↑ **Highly Positive** | Weekly deployments for high-volatility services (Report, Alert), quarterly for stable services (User, Gateway); no "big bang" releases |
| **Security** | ↑ **Positive** | Principle of least privilege: each service accesses only its schema (ADR-007); IAM isolation in User Service; attack surface reduction |
| **Operational Complexity** | ↓ **Negative** | 10 services vs 1 monolith: requires orchestration (Kubernetes), distributed tracing (Jaeger), centralized logging (ELK), service mesh (Istio?) |
| **Data Consistency** | ↓ **Moderate Negative** | Eventual consistency between services; saga compensation logic required (ADR-004); no ACID transactions across service boundaries |
| **Development Velocity** | → **Neutral Short-Term, ↑ Positive Long-Term** | Initial overhead of setting up 10 services, but teams can move faster independently once established |

## Consequences

### Positive

1. **Independent Scalability:**
   - Report Service can scale to 100 pods during peak submission hours without scaling Matching Service
   - Geospatial Analysis Service can provision GPU instances for ML models without affecting real-time services

2. **Team Autonomy:**
   - Data science team owns Matching + Geospatial Analysis (algorithm development)
   - Enforcement policy team owns Alert Management (rule configuration)
   - Integration team owns Vessel Tracking (external API adapters)
   - Each team can deploy independently without cross-team coordination

3. **Fault Isolation:**
   - VMS API downtime (noted in proposal) does not prevent report submissions
   - Third-party notification API failures (Africa's Talking) do not block alert creation
   - Heavy analytical queries do not starve real-time matching of CPU resources

4. **Deployment Flexibility:**
   - High-volatility services (Report, Alert) deploy weekly for rapid feedback
   - Low-volatility services (User, Gateway) deploy quarterly for stability
   - Canary deployments per service reduce risk of breaking changes

5. **Technology Diversity:**
   - Geospatial Analysis Service can use Python + scikit-learn for ML models
   - Real-time services use Go/Kotlin for low latency
   - Analytics Service uses R for statistical analysis
   - Each service chooses best-fit technology without global constraints

6. **Clear Ownership:**
   - Each bounded context (DDD) maps to exactly one service (ADR-007)
   - No ambiguity about "who owns alerts" or "who owns matching logic"
   - On-call rotation is per-service, not monolithic

### Negative

1. **Operational Complexity:**
   - 10 services require orchestration (Kubernetes with 10 Deployments)
   - Distributed tracing needed (Jaeger/Zipkin) to debug cross-service requests
   - Centralized logging (ELK Stack) with correlation IDs
   - Service mesh (Istio?) for traffic management, observability, security

2. **Data Consistency Challenges:**
   - Eventual consistency between Report → Matching → Alert (typically <1 second, but not guaranteed)
   - Saga compensation logic required if Matching Service fails after Report is submitted (ADR-004)
   - No foreign key constraints across service boundaries (logical references only per ADR-003)

3. **Inter-Service Latency:**
   - Report submission → Alert delivery requires 4 hops (Report → Matching → Alert → Notification)
   - Total latency ~210ms (acceptable for 5-second SLO, but overhead exists)
   - Network failures between services require retry logic

4. **Development Overhead:**
   - Boilerplate for each service: Dockerfile, Kubernetes manifests, CI/CD pipeline, monitoring dashboards
   - Contract testing required (Pact) to prevent breaking changes (ADR-007 fitness function)
   - Shared libraries for common code (geospatial utilities, JWT validation) require versioning strategy

5. **Transactional Boundaries:**
   - Cannot use database transactions across services (e.g., atomically create report + vessel match + alert)
   - Must rely on saga pattern (ADR-004) and idempotent event handlers
   - Debugging failed sagas requires correlation IDs and centralized logging

6. **Testing Complexity:**
   - End-to-end testing requires spinning up all 10 services (or mocking)
   - Contract testing (Pact) requires coordination between teams
   - Performance testing must simulate inter-service latency

### Neutral

1. **Service Catalog Size:**
   - 10 services is moderate complexity (not microservices "death star" of 100+ services, but not a monolith)
   - Within "Sweet Spot" range per Hard Parts (Chapter 7): 5-15 services for most organizations

2. **Database Schema Count:**
   - 10 logical schemas in monolithic database (ADR-003) vs 10 separate databases
   - Future migration path exists if data integrators weaken (ADR-003 review criteria)

3. **Event Volume:**
   - ~1000 events/hour during peak (ReportSubmitted, VesselPositionUpdated, MatchFound, AlertCreated)
   - Message broker (RabbitMQ/Kafka per ADR-002) handles this easily; not a bottleneck

#### FF-009-1: Service Size Boundary Check

**Objective:** Ensure no service exceeds 5,000 LOC (upper bound of "Sweet Spot" per Hard Parts p. 137)

**Implementation:**
```bash
#!/bin/bash
# File: scripts/fitness-functions/ff-009-1-service-size-check.sh

THRESHOLD=5000
VIOLATIONS=()

for service in services/*; do
  SERVICE_NAME=$(basename "$service")
  LOC=$(find "$service/src" -name "*.kt" -o -name "*.py" -o -name "*.go" | xargs wc -l | tail -n 1 | awk '{print $1}')
  
  if [ "$LOC" -gt "$THRESHOLD" ]; then
    VIOLATIONS+=("$SERVICE_NAME: $LOC LOC (exceeds $THRESHOLD)")
  fi
done

if [ ${#VIOLATIONS[@]} -gt 0 ]; then
  echo "❌ FF-009-1 FAILED: Services exceeding size threshold:"
  printf '%s\n' "${VIOLATIONS[@]}"
  exit 1
else
  echo "✅ FF-009-1 PASSED: All services within size threshold"
  exit 0
fi
```

**Cadence:** Run on every pull request (CI pipeline)

**Remediation:** If violated, split service into smaller services using component decomposition patterns (Hard Parts Chapter 5)

#### FF-009-2: Inter-Service Coupling Check

**Objective:** Prevent services from directly accessing other services' database schemas (enforce event-driven communication per ADR-002)

**Implementation:**
```python
# File: scripts/fitness-functions/ff-009-2-coupling-check.py
import re
import sys
from pathlib import Path

# Map service names to their owned schemas (from ADR-007)
SERVICE_SCHEMAS = {
    "report-management-service": ["report_management"],
    "vessel-tracking-service": ["vessel_tracking"],
    "matching-service": ["matching_service"],
    "alert-service": ["alert_management"],
    "notification-service": ["notification_delivery"],
    "geospatial-service": ["analytics_reporting"],
    "user-service": ["user_management"],
    "analytics-service": ["analytics_reporting"],
    "audit-service": ["audit_compliance"]
}

def check_schema_access_violations():
    violations = []
    
    for service_dir in Path("services").iterdir():
        if not service_dir.is_dir():
            continue
            
        service_name = service_dir.name
        allowed_schemas = SERVICE_SCHEMAS.get(service_name, [])
        
        # Search for SQL queries in service code
        for sql_file in service_dir.rglob("*.sql"):
            content = sql_file.read_text()
            
            # Extract schema references (e.g., "FROM vessel_tracking.vessels")
            schema_refs = re.findall(r'FROM\s+(\w+)\.\w+', content, re.IGNORECASE)
            schema_refs += re.findall(r'JOIN\s+(\w+)\.\w+', content, re.IGNORECASE)
            
            for schema in schema_refs:
                if schema not in allowed_schemas:
                    violations.append(
                        f"{service_name} accesses unauthorized schema '{schema}' in {sql_file}"
                    )
    
    return violations

if __name__ == "__main__":
    violations = check_schema_access_violations()
    
    if violations:
        print("❌ FF-009-2 FAILED: Unauthorized schema access detected:")
        for v in violations:
            print(f"  - {v}")
        sys.exit(1)
    else:
        print("✅ FF-009-2 PASSED: All services respect schema boundaries")
        sys.exit(0)
```

**Cadence:** Run on every pull request (CI pipeline)

**Remediation:** Replace direct schema access with event subscription or read-only view (ADR-007)

#### FF-009-4: Service Latency Budget

**Objective:** Ensure end-to-end latency from report submission → alert delivery stays under 5-second SLO

**Implementation:**
```python
# File: scripts/fitness-functions/ff-009-4-latency-budget.py
import requests
import time
import sys

LATENCY_SLO_MS = 5000  # 5 seconds

def test_end_to_end_latency():
    # Submit a test report
    start = time.time()
    
    report_response = requests.post(
        "https://api.staging.bahariwatch.ke/v1/reports",
        json={
            "latitude": -3.9869,
            "longitude": 39.7320,
            "description": "Test IUU report",
            "photo_url": "https://test.bucket/photo.jpg"
        },
        headers={"Authorization": "Bearer <test-token>"}
    )
    
    if report_response.status_code != 201:
        print(f"❌ Report submission failed: {report_response.status_code}")
        sys.exit(1)
    
    report_id = report_response.json()["id"]
    
    # Poll for alert creation (eventual consistency)
    alert_created = False
    for _ in range(50):  # Poll for up to 5 seconds
        time.sleep(0.1)
        
        alerts_response = requests.get(
            f"https://api.staging.bahariwatch.ke/v1/alerts?report_id={report_id}",
            headers={"Authorization": "Bearer <test-token>"}
        )
        
        if alerts_response.json()["alerts"]:
            alert_created = True
            break
    
    elapsed_ms = (time.time() - start) * 1000
    
    if not alert_created:
        print(f"❌ FF-009-4 FAILED: No alert created within {LATENCY_SLO_MS}ms")
        sys.exit(1)
    
    if elapsed_ms > LATENCY_SLO_MS:
        print(f"❌ FF-009-4 FAILED: Latency {elapsed_ms:.0f}ms exceeds SLO {LATENCY_SLO_MS}ms")
        sys.exit(1)
    
    print(f"✅ FF-009-4 PASSED: End-to-end latency {elapsed_ms:.0f}ms (under {LATENCY_SLO_MS}ms)")
    sys.exit(0)

if __name__ == "__main__":
    test_end_to_end_latency()
```

**Cadence:** Run every 15 minutes on staging (synthetic monitoring)

**Remediation:** Profile slow services with distributed tracing (Jaeger); optimize database queries or add caching

### Security Implications

- **Principle of Least Privilege:** Each service has read/write access only to its own schema (enforced by PostgreSQL roles per ADR-007)
- **Attack Surface Reduction:** Compromising one service (e.g., Notification Service via third-party API exploit) does not grant access to sensitive data in other services (e.g., Report Service photos)
- **Defense in Depth:** API Gateway enforces rate limiting and JWT validation before requests reach backend services
- **Audit Trail:** Each service publishes audit events (consumed by Audit Service per ADR-008)

### Data Privacy Implications

- **GDPR Article 25 (Data Protection by Design):** Service boundaries align with data ownership (ADR-007); deleting a user in User Service triggers cascade deletion events to other services
- **Right to Be Forgotten:** User Service publishes `UserDeleted` event; all services must implement handlers to purge user data within 30 days
- **Data Minimization:** Services only store data required for their bounded context (e.g., Notification Service does not store report photos)

## Implementation Notes

### For Developers

1. **Service Template:**
   Use the provided service template in `templates/microservice-kotlin/` (or Python/Go variant) for consistent project structure:
   ```
   service-name/
   ├── src/
   │   ├── main/
   │   │   ├── kotlin/
   │   │   │   ├── api/         # REST controllers
   │   │   │   ├── domain/      # Business logic
   │   │   │   ├── events/      # Event publishers/subscribers
   │   │   │   └── persistence/ # Database repositories
   │   │   └── resources/
   │   │       └── db/migrations/ # Flyway migrations
   │   └── test/
   ├── Dockerfile
   ├── build.gradle.kts
   └── k8s/
       ├── deployment.yaml
       └── service.yaml
   ```

2. **Event-Driven Communication:**
   - Use CloudEvents standard for event schema (JSON)
   - Include correlation ID in all events for distributed tracing
   - Implement idempotent event handlers (use event ID to detect duplicates)

3. **Database Access:**
   - Each service connects to PostgreSQL with role `<service_name>_role` (e.g., `report_management_role`)
   - Role has read/write only on owned schema (enforced by PostgreSQL grants)
   - Use Flyway for schema migrations (versioned SQL files)

4. **Error Handling:**
   - Publish `<ServiceName>Failed` events for saga compensation (ADR-004)
   - Log errors with structured logging (JSON format for ELK ingestion)
   - Implement exponential backoff for retry logic

5. **Testing:**
   - Unit tests: Mock external dependencies (message broker, database)
   - Integration tests: Use Testcontainers for PostgreSQL + RabbitMQ
   - Contract tests: Use Pact to verify event schemas between services

### For DevOps

1. **Kubernetes Deployment:**
   - Each service has separate Deployment and Service manifests
   - Use HorizontalPodAutoscaler (HPA) for auto-scaling:
     - Report Service: CPU >70%
     - Matching Service: CPU >80% (compute-intensive)
     - User Service: Memory >60% (caching)

2. **Resource Allocation:**
   ```yaml
   # Example for Matching Service (compute-intensive)
   resources:
     requests:
       cpu: "1000m"    # 1 vCPU
       memory: "2Gi"
     limits:
       cpu: "2000m"    # 2 vCPU
       memory: "4Gi"
   ```

3. **Health Checks:**
   - Liveness probe: `/health/live` (does service process respond?)
   - Readiness probe: `/health/ready` (can service handle traffic? Check DB connection, message broker)

4. **Monitoring:**
   - Prometheus metrics exposed at `/metrics`
   - Key metrics per service:
     - Request rate (req/sec)
     - Error rate (5xx responses)
     - Latency (p50, p95, p99)
     - Database connection pool utilization
     - Message queue depth

5. **Distributed Tracing:**
   - Inject Jaeger sidecar into each pod
   - Propagate trace context in HTTP headers (`X-B3-TraceId`, `X-B3-SpanId`)
   - Tag spans with service name, operation, and correlation ID

### For Product Team

1. **Feature Development Workflow:**
   - **Scenario:** Add new alert rule "Alert if vessel enters Marine Protected Area"
   - **Service Changed:** Alert Management Service only
   - **Other Services:** No changes required (matching logic unchanged, notification delivery unchanged)
   - **Deployment Risk:** LOW (isolated change)

2. **Prioritizing Service Improvements:**
   - **High Impact, Low Effort:** Optimize Matching Service geospatial query (affects 100% of reports)
   - **High Impact, High Effort:** Add ML-based IUU prediction to Geospatial Analysis Service (long-term value)
   - **Low Impact:** Add new survey question to Analytics Service (only affects research users)

3. **Understanding Service Boundaries:**
   - **"Why can't we add user authentication to Report Service?"** → Authentication is owned by User Service (DDD bounded context); Report Service delegates via JWT validation
   - **"Why is hotspot generation slow?"** → Geospatial Analysis Service runs batch jobs; consider moving to real-time streaming if needed
