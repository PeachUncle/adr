# ADR-0008: Pre-commit Hook Timing Strategy

**Date**: 2024-10-12
**Status**: Accepted

## Context

Git hooks can run at different stages: pre-commit, pre-push, prepare-commit-msg, etc. The timing of automated checks significantly impacts developer experience and workflow efficiency.

The key tension is between:

- **Fast feedback**: Running checks immediately on commit catches issues early
- **Workflow friction**: Slow checks block commits and frustrate developers
- **Comprehensive validation**: Thorough testing requires time
- **Local vs. remote**: What should run locally vs. in CI

iOS development presents unique challenges:

- Building iOS apps requires simulator boot time (~10-20 seconds)
- Running tests can take 1-2 minutes even for small test suites
- Developers commit frequently (every 5-15 minutes with TDD)
- Slow pre-commit hooks get disabled by developers

Research shows iOS teams have converged on a specific pattern: fast linting on commit, comprehensive testing on push or in CI.

## Decision

**We will implement a two-stage hook strategy that separates fast code quality checks (on commit) from slower comprehensive validation (on push).**

### Stage 1: Pre-Commit (Fast - 2-5 seconds)

**What runs:**

- SwiftLint code quality checks
- Trailing whitespace removal
- File ending validation
- YAML file validation
- Large file detection
- Merge conflict detection
- Private key detection

**Target time:** Under 5 seconds

### Stage 2: Pre-Push (Fast - <1 second) - Active

**What runs:**

- Trailing whitespace checks
- End of file validation
- Large file detection

**Target time:** Under 1 second
**Actual time:** 0.5 seconds
**Configuration:** Active by default

**Tests removed from local hooks:**
Based on empirical testing (October 2024), iOS simulator tests were found to be incompatible with git hook timing requirements:

- Unit tests alone: 45 seconds (simulator boot + build)
- Full coverage: 2+ minutes
- These timings are **fundamental iOS constraints**, not optimizable

Tests now run:

- **Manually**: `make test-unit` or `make test-coverage` when developer chooses
- **CI**: Automatically on every push (comprehensive validation)

### Stage 3: CI (Comprehensive - 2-5 minutes) - Required

**What runs:**

- Everything from Stage 1 and Stage 2
- Release build validation
- Test result reporting
- Coverage threshold enforcement

## Alternatives Considered

### 1. All Checks on Every Commit

Running full test suite + linting on every commit.

**Why not chosen**:

- Too slow (1-2 minutes per commit)
- Blocks TDD workflow (need fast commit cycles)
- Developers disable hooks to avoid friction
- Research shows this pattern leads to low hook adoption
- Not aligned with iOS community practices

### 2. All Checks on Push Only

No pre-commit hooks, run everything only on push.

**Why not chosen**:

- Delayed feedback on style issues (find out only when pushing)
- Wastes time running full test suite when linting fails
- Misses opportunity for fast validation
- Doesn't catch issues early in development

### 3. Linting on Commit, Tests Always on Push

Same as decision but with tests always enabled on push (not optional).

**Why not chosen**:

- Forces same workflow on all developers
- Some developers prefer running tests manually
- Can slow down experimental branches
- Better to recommend than require
- CI is the ultimate safety net

### 4. CI Only, No Local Hooks

Rely entirely on GitHub Actions for all validation.

**Why not chosen**:

- Very slow feedback loop (wait for CI)
- Wastes CI resources on preventable issues
- Frustrating developer experience
- Can't iterate locally
- Higher CI costs

### 5. Tests on Commit, Configurable Timeout

Run tests on commit but abort if they exceed a timeout.

**Why not chosen**:

- Unpredictable behavior (sometimes tests run, sometimes don't)
- Confusing for developers
- Still blocks workflow
- Timeout makes tests less reliable

## Consequences

### Positive

1. **Fast Commits**: 2-5 second checks don't block TDD workflow
2. **Immediate Style Feedback**: Catch formatting/linting issues instantly
3. **Developer Autonomy**: Can choose test timing (push hooks optional)
4. **Higher Adoption**: Fast hooks stay enabled (developers don't bypass)
5. **Appropriate Validation**: Style checks before commit, tests before sharing
6. **CI Safety Net**: Comprehensive validation still happens automatically
7. **Industry Alignment**: Matches patterns from professional iOS teams
8. **Flexibility**: Developers can run tests manually when they choose

### Negative

1. **Possible Style-Only Commits**: Tests might not run locally before push
2. **Optional Push Hooks**: Some developers may skip enabling them
3. **Split Configuration**: Need to manage both commit and push stages
4. **Documentation Burden**: Must explain when to enable push hooks

### Mitigation Strategies

- **CI as Safety Net**: GitHub Actions runs all checks automatically
- **Clear Documentation**: Explain when to enable push hooks (feature work vs. experimental)
- **Make It Easy**: Provide `make setup-hooks` for both stages
- **Recommendation Guidance**: Document best practices for different workflows

## Rationale

The decision prioritizes **developer experience and adoption** while maintaining code quality through CI.

Key factors:

1. **Research-Based**: iOS community has converged on fast commit, thorough push pattern
2. **Developer Psychology**: Slow hooks get disabled; fast hooks stay enabled
3. **TDD Compatibility**: 2-5 second commits allow rapid Red-Green-Refactor cycles
4. **Appropriate Timing**: Style issues caught immediately, functionality validated before sharing
5. **Real-World Usage**: Professional iOS teams use this exact pattern
6. **Fallback Safety**: CI catches everything, local hooks are optimization

The pattern acknowledges that:

- Developers commit more frequently than they push
- Style issues should be caught immediately
- Test failures are acceptable in local commits (part of TDD)
- Tests are most valuable before sharing code (push) or merging (CI)

## Implementation Notes

### Pre-Commit Configuration

```yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-added-large-files
      - id: check-merge-conflict
      - id: detect-private-key

  - repo: local
    hooks:
      - id: swiftlint
        entry: swiftlint lint --strict
        language: system
        types: [swift]
        # Runs on commit (default stage)
```

### Pre-Push Configuration (Optional)

```yaml
  - repo: local
    hooks:
      - id: swift-tests
        entry: make test-coverage
        language: system
        pass_filenames: false
        stages: [push]  # Only on push, not commit
```

### Installation

```bash
# Install commit hooks (fast checks)
pre-commit install

# Optionally install push hooks (thorough checks)
pre-commit install --hook-type pre-push
```

### Makefile Integration

```bash
make setup-hooks  # Installs both commit and push hooks
make pre-commit   # Run commit hooks manually
make pre-push     # Run push hooks manually
```

### Developer Workflows

**Workflow 1: Feature Development (Recommended)**

```bash
# Enable both stages
pre-commit install
pre-commit install --hook-type pre-push

# Work with confidence
git commit  # Fast linting (2-5s)
git push    # Tests run (1-2m), catches issues before sharing
```

**Workflow 2: Experimental Work**

```bash
# Enable only commit hooks
pre-commit install

# Fast iteration
git commit  # Fast linting (2-5s)
git push    # No local tests, CI validates later

# Run tests manually when ready
make test
```

**Workflow 3: Bypass When Needed**

```bash
# Skip hooks for specific commits
git commit --no-verify  # Skip commit hooks
git push --no-verify    # Skip push hooks
```

## Timing Benchmarks

Based on actual project measurements (October 12, 2024):

| Stage | Check | Time | Blocking |
|-------|-------|------|----------|
| Commit | SwiftLint | ~1.0s | Yes |
| Commit | File checks | ~0.2s | Yes |
| **Commit Total** | | **1.2s** | **Yes** |
| Push | File checks only | 0.5s | Yes |
| Manual | Unit tests | ~45s | No (opt-in) |
| Manual | Full coverage | ~2m | No (opt-in) |
| CI | Full pipeline | ~2-5m | No (async) |

**Actual measurements:**

```bash
make pre-commit  # 1.214 seconds total
make pre-push    # 0.496 seconds total
make test-unit   # 44.971 seconds total
```

**Target achieved:** Commit stage well under 5 seconds (actual: 1.2s) ✅

## Maintenance

### Adding Commit Checks

Only add checks that are:

- Very fast (< 2 seconds)
- No external dependencies (simulators, network)
- Deterministic (same result every time)
- Style/format related

Examples: SwiftFormat, import sorting, copyright headers

### Adding Push Checks

Can add checks that are:

- Slower (up to 2 minutes acceptable)
- Require simulators or builds
- Comprehensive validation
- Test related

Examples: Security scans, dependency audits, additional test suites

## iOS-Specific Findings (October 2024)

### Empirical Test Results

Actual measurements on this project revealed iOS-specific constraints:

**Unit Test Breakdown (45 seconds total):**

- Simulator boot/warmup: 20-30 seconds
- Incremental build: 10-15 seconds
- Actual test execution: <1 second
- CPU usage: 6% (mostly waiting on I/O)

**Key Insight:** The 45-second duration is **fundamental to iOS development**, not a code issue:

- Simulator must boot (unavoidable OS process)
- App must build (Swift compilation required)
- Test bundle must load (framework overhead)

### Why iOS is Slower than React Native

React Native developers experience 5-15 second test cycles because:

- Jest runs in Node.js (no simulator)
- JavaScript is interpreted (no compilation)
- Hot reload replaces modules instantly

Native iOS **cannot** achieve this:

- Swift must compile to machine code
- iOS Simulator is a full OS virtualization
- XCTest framework requires app context

This is industry-wide, not project-specific.

### Test Execution Strategy

Since tests were removed from git hooks, they run via:

**Manual execution:**

```bash
make test-unit       # Fast unit tests (~45s)
make test-coverage   # Full tests with coverage (~2m)
make ci              # Complete CI pipeline locally
```

**CI execution:**

- GitHub Actions runs on every push
- Full test suite with coverage
- Automatic validation before merge

Simulators are managed by xcodebuild automatically and shut down after test completion.

## Status

**Accepted** - Currently implemented and validated

**Final Implementation (October 12, 2024):**

- Pre-commit: 1.2 seconds (SwiftLint + file checks)
- Pre-push: 0.5 seconds (file checks only)
- Tests: CI-only (45+ seconds incompatible with git hooks)

This represents a **refinement** of the original decision after empirical testing revealed that even "fast" iOS simulator tests (45s) are too slow for pre-push hooks. The pattern now matches industry practice: instant linting on commit, comprehensive testing in CI.
