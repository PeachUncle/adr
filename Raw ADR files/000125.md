# ADR-0004: RealityKit for 3D Visualization

**Status**: Accepted
**Date**: October 12, 2025
**Deciders**: Architecture Team

## Context

The app requires high-quality 3D visualization of a 3x3 cube puzzle with:

- Interactive rotation and manipulation
- Smooth animations for moves (U, R, F, etc.)
- Responsive performance on target devices (targeting 60 FPS)
- Integration with SwiftUI views
- Educational overlays (highlighting specific pieces, showing move effects)
- Potential future AR features

Available options for 3D rendering on iOS:

1. **RealityKit**: Apple's modern 3D framework
2. **SceneKit**: Apple's high-level 3D framework
3. **Metal**: Low-level GPU programming API
4. **Unity**: Cross-platform game engine
5. **Custom OpenGL ES**: Legacy option

Key considerations:

- Integration with SwiftUI
- Future-proofing and long-term Apple support
- Modern rendering capabilities
- Potential AR feature integration
- Development ecosystem maturity

## Decision

**We will use RealityKit as the primary 3D rendering engine for cube visualization, leveraging its modern architecture and SwiftUI-first design.**

## Alternatives Considered

### SceneKit

**Pros**:

- Mature, stable framework (released 2014)
- Extensive documentation and community examples
- Well-understood patterns and best practices
- Proven track record

**Cons**:

- Older technology not receiving significant new features
- Less natural SwiftUI integration (requires UIViewRepresentable wrapper)
- Limited AR capabilities compared to RealityKit
- Not Apple's strategic direction for future 3D development
- Less modern rendering capabilities

**Why not chosen**: While SceneKit is mature and stable, RealityKit represents Apple's future direction for 3D graphics on iOS. RealityKit's native SwiftUI integration and modern architecture make it the better long-term choice.

### Metal (Direct GPU Programming)

**Pros**:

- Maximum performance and control
- Direct access to GPU features
- Optimal for custom rendering techniques

**Cons**:

- Very high development complexity
- Requires deep graphics programming expertise
- Must implement all scene management manually
- Longer development time
- Harder to maintain

**Why not chosen**: Overkill for cube visualization; SceneKit provides sufficient performance with much lower complexity.

### Unity

**Pros**:

- Powerful, mature 3D engine
- Rich asset ecosystem
- Cross-platform (iOS + Android)
- Visual editor for scene design

**Cons**:

- Significant app size overhead
- Poor integration with native iOS UI (SwiftUI)
- License costs for removing splash screen
- Heavyweight for simple cube visualization
- Not ideal for educational app (game engine association)

**Why not chosen**: Excessive overhead for relatively simple 3D requirements; poor SwiftUI integration.

### OpenGL ES

**Pros**:

- Mature, well-documented
- Cross-platform

**Cons**:

- Deprecated by Apple (since iOS 12)
- No future support
- Lower performance than Metal-backed frameworks
- Manual scene management complexity

**Why not chosen**: Deprecated technology with no future; SceneKit provides better performance and Apple support.

### Custom WebGL/Three.js in Web View

**Pros**:

- Cross-platform via web technologies
- Large ecosystem

**Cons**:

- Poor performance in web view
- Terrible integration with native UI
- Unable to meet responsive performance requirements

**Why not chosen**: Performance and integration issues make this infeasible.

## Consequences

### Positive

1. **Future-Proof**: Apple's strategic direction for 3D and AR development
2. **Native SwiftUI Integration**: `RealityView` designed specifically for SwiftUI ([RealityKit in SwiftUI](https://developer.apple.com/documentation/realitykit/realityview))
3. **Modern Architecture**: Entity-Component-System (ECS) provides clean separation of concerns
4. **Excellent Performance**: Modern Metal-backed rendering optimized for latest iOS devices
5. **AR-Ready**: Seamless ARKit integration if AR features are added later
6. **Photorealistic Rendering**: Physically-based rendering (PBR) with advanced lighting
7. **Active Development**: Regular updates and new features in iOS releases
8. **Small Footprint**: No external dependencies; framework included in iOS

### Negative

1. **Smaller Community**: Fewer code examples compared to SceneKit (introduced 2019)
2. **Learning Curve**: ECS architecture requires different mental model than traditional scene graphs
3. **Evolving API**: Some features still maturing; potential API changes in future releases
4. **iOS-Only**: No code reuse for Android (but this is acceptable per ADR-0001)
5. **Minimum iOS Version**: Requires iOS 15+ for basic features, iOS 16+ for advanced capabilities

### Neutral

1. **Documentation**: Good official documentation from Apple, but less third-party content than SceneKit
2. **Complexity**: ECS provides cleaner architecture but has steeper initial learning curve

## Rationale

The decision prioritizes **future-proofing and modern architecture** while meeting current and future requirements.

### Key Factors

#### Future-Proofing

- RealityKit is Apple's strategic direction for 3D graphics
- Active development with new features in each iOS release
- Built for modern iOS paradigms (SwiftUI, Combine, async/await)
- Better positioned for long-term support and optimization

#### Native SwiftUI Integration

```swift
// RealityKit's natural SwiftUI integration
struct CubeView: View {
    var body: some View {
        RealityView { content in
            let model = Entity()
            let mesh = MeshResource.generateBox(size: 0.1)
            let material = SimpleMaterial(color: .gray, isMetallic: true)
            model.components.set(ModelComponent(mesh: mesh, materials: [material]))
            content.add(model)
        }
    }
}
```

`RealityView` is purpose-built for SwiftUI, providing cleaner integration than SceneKit's UIViewRepresentable wrapper.

#### Modern Architecture Benefits

- **ECS Pattern**: Entity-Component-System provides better code organization
- **Composable**: Components can be mixed and matched for flexible behavior
- **Type-Safe**: Swift-first API with strong typing throughout
- **Reactive**: Works naturally with SwiftUI's state management

#### AR-Ready from Day One

If AR features are added (e.g., "see solution overlaid on real cube"):

- **Seamless ARKit Integration**: RealityKit designed to work with ARKit
- **No Migration Needed**: Same entities work in both virtual and AR contexts
- **Unified Codebase**: Single rendering pipeline for all 3D content

#### Performance

- Modern Metal-backed rendering optimized for current devices
- Designed for iOS 15+ hardware capabilities
- Continuous optimization in iOS updates

## Implementation Notes

### Entity Structure

```swift
class CubeModel {
    var rootEntity = Entity()
    var cubies: [Entity] = []

    init() {
        // Create 27 cubie entities (3×3×3)
        for x in 0..<3 {
            for y in 0..<3 {
                for z in 0..<3 {
                    let cubie = createCubie(x: x, y: y, z: z)
                    cubies.append(cubie)
                    rootEntity.addChild(cubie)
                }
            }
        }
    }

    func createCubie(x: Int, y: Int, z: Int) -> Entity {
        let entity = Entity()
        let mesh = MeshResource.generateBox(size: 0.1, cornerRadius: 0.005)
        let material = SimpleMaterial(color: .gray, roughness: 0.15, isMetallic: true)
        entity.components.set(ModelComponent(mesh: mesh, materials: [material]))
        entity.position = SIMD3<Float>(Float(x) * 0.11, Float(y) * 0.11, Float(z) * 0.11)
        return entity
    }
}
```

### Animation Approach

```swift
// Smooth move animations using RealityKit
func animateMove(_ move: Move, duration: TimeInterval) {
    let affectedCubies = cubiesForMove(move)
    
    // Create rotation transform
    let rotation = simd_quatf(angle: .pi / 2, axis: SIMD3<Float>(0, 1, 0))
    
    // Animate each affected cubie
    for cubie in affectedCubies {
        var transform = cubie.transform
        transform.rotation *= rotation
        cubie.move(to: transform, relativeTo: cubie.parent, duration: duration)
    }
}
```

### SwiftUI Integration

```swift
struct CubeVisualizationView: View {
    @StateObject var viewModel: CubeViewModel

    var body: some View {
        ZStack {
            // RealityKit view
            RealityView { content in
                content.add(viewModel.cubeModel.rootEntity)
                content.camera = .spatialTracking
            }

            // SwiftUI overlays
            VStack {
                // Educational annotations
                MoveIndicatorView(move: viewModel.currentMove)
                Spacer()
                ControlsView()
            }
        }
        .edgesIgnoringSafeArea(.all)
    }
}
```

### Performance Optimizations

- Use mesh instancing for identical cubie geometries
- Share materials across entities to reduce memory overhead
- Leverage RealityKit's automatic batching for draw calls
- Use component-based design for efficient updates
- Profile with Instruments (Metal System Trace) to identify bottlenecks

### Testing Considerations

- Test on iPhone 12 (minimum device) to measure and validate frame rate
- Validate animation smoothness during rapid moves
- Test gesture interactions (rotation, zoom) responsiveness
- Memory profiling for long sessions
- Establish performance baselines through profiling with Instruments
- Test on iOS 15+ to ensure compatibility
