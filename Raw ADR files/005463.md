## Context

A centralized, version-controlled repository is the foundational requirement for any software project, especially one involving automated CI/CD. The system needs a reliable, secure, and widely-supported platform to host the source code for all agents and services. The choice of this platform directly influences the selection and integration of other DevOps tools, particularly the CI/CD system.

## Decision

We will use **GitHub** as the exclusive platform for all source code management. All agent code, documentation, and configuration files will be stored in private GitHub repositories.

## Rationale

1.  **Cost-Effectiveness**: GitHub's free tier offers unlimited private repositories for individuals and teams, which completely covers the project's needs without any cost.
2.  **Seamless CI/CD Integration**: GitHub provides GitHub Actions, a powerful and tightly integrated CI/CD platform (see ADR-018). Choosing GitHub makes the adoption of GitHub Actions seamless, as workflows are defined in YAML files directly within the repository and are triggered automatically by repository events (e.g., pushes, pull requests).
3.  **Industry Standard and Ecosystem**: GitHub is the de facto standard for source control. This brings numerous advantages, including a massive community for support, extensive documentation, and the largest ecosystem of third-party integrations and tools (the GitHub Marketplace).
4.  **Developer Familiarity**: The development team is already highly familiar with GitHub's workflow (pull requests, code reviews, branching strategies), which reduces friction and accelerates the development process.

## Consequences

-   **Platform Dependency**: The project's CI/CD and source control will be tightly coupled to the GitHub ecosystem. This is considered an acceptable trade-off given the benefits of integration.
-   **Implementation**:
    -   A new private GitHub repository will be created for the project.
    -   A branching strategy (e.g., GitFlow or a simpler trunk-based model) will be defined and enforced.
    -   Branch protection rules will be configured for the `main` branch to require pull requests and status checks before merging.

## Alternatives Considered

-   **GitLab**: GitLab is a very strong, all-in-one competitor that provides source control, CI/CD, and a container registry in a single application. While its integrated nature is compelling, GitHub's larger ecosystem and more generous free tier for CI/CD minutes with GitHub Actions make it slightly more cost-effective and flexible for this project.
-   **Self-Hosted Git (e.g., Gitea)**: This would involve setting up and maintaining our own Git server. This was rejected due to the significant operational overhead (security, backups, maintenance) and the lack of a tightly integrated, managed CI/CD platform. The cost and effort of self-hosting far outweigh the benefits for a project of this scale.

## Implementation Strategy

### Phase 1: Repository Setup (Week 1)
**Deliverables**:
- Create private GitHub repository: `trading-system`
- Initialize with README, .gitignore, LICENSE
- Set up repository structure (agents/, docs/, infrastructure/, tests/)
- Configure repository settings (features, permissions, security)
- Add CODEOWNERS file for code review assignments
- Document repository conventions and guidelines

**Dependencies**: GitHub account with organization

### Phase 2: Branch Protection and Workflow (Week 1)
**Deliverables**:
- Configure main branch protection rules
- Require pull request reviews (minimum 1 reviewer)
- Require status checks before merge (tests, linting)
- Enable automatic deletion of merged branches
- Set up branch naming conventions (feature/, bugfix/, hotfix/)
- Create PR and issue templates
- Document Git workflow and branching strategy

**Dependencies**: Phase 1 complete

### Phase 3: Team Access and Permissions (Week 1)
**Deliverables**:
- Configure team access levels (admin, write, read)
- Set up deploy keys for CI/CD
- Configure personal access tokens for automation
- Enable two-factor authentication requirement
- Set up audit logging
- Document access management procedures

**Dependencies**: Phase 2 complete

### Phase 4: Integration and Automation (Week 2)
**Deliverables**:
- Enable GitHub Actions (ADR-018)
- Configure automated security scanning (Dependabot, CodeQL)
- Set up commit signing requirements
- Enable GitHub Pages for documentation (if needed)
- Configure webhooks for external integrations
- Integrate with project management tools

**Dependencies**: Phase 3 complete, ADR-018 (GitHub Actions)

## Cost Analysis

### Monthly Operational Costs

**GitHub Free Tier** (for private repositories):
- Unlimited private repositories: Free
- Unlimited collaborators: Free
- 2GB storage per repository: Free
- 500MB GitHub Packages storage: Free
- GitHub Actions: 2,000 minutes/month free

**Total Estimated Monthly Cost**: $0/month

### Cost Optimization Strategies

1. **Stay on Free Tier**:
   - Free tier sufficient for team size <3 developers
   - No paid features required for project scope
   - Estimated savings: $48-144/month vs Team plan

2. **Efficient Storage Management**:
   - Use Git LFS for large files sparingly
   - Archive old branches and releases
   - Keep binary artifacts in Artifact Registry, not Git

3. **GitHub Actions Optimization**:
   - Covered in ADR-018
   - Stay within 2,000 free minutes/month
   - Estimated savings: $8-16/month vs paid runner time

### Upgrade Considerations

**GitHub Team** ($4/user/month if needed):
- Required team size features: None currently
- Protected branches on private repos: Available on Free tier now
- CODEOWNERS: Available on Free tier
- **Upgrade trigger**: >5 developers or need advanced security features

**GitHub Enterprise** ($21/user/month):
- Advanced security features (SAML SSO, audit logs)
- Not required for current project scale
- **Upgrade trigger**: Regulatory compliance requirements

## Risk Assessment

| Risk | Severity | Likelihood | Impact | Mitigation |
|------|----------|------------|--------|------------|
| GitHub service outage | High | Low | Development blocked, CI/CD stopped | Local development continues, mirror repository to GitLab as backup, wait for service restoration |
| Accidental repository deletion | High | Very Low | Complete code loss | Branch protection prevents main deletion, automated daily backups to cloud storage, Terraform-managed repo |
| Unauthorized access | High | Low | Code theft, malicious commits | 2FA required, access audit logging, IP allowlisting, deploy key rotation |
| Large file bloat | Medium | Medium | Repository slow, storage exceeded | Git LFS for large files, pre-commit hooks to prevent large files, regular repository cleanup |
| Merge conflicts | Low | High | Development friction, delayed merges | Short-lived feature branches, frequent rebasing, clear branching strategy, automated conflict detection |
| Lost commit history | Medium | Low | Difficulty debugging, unclear changes | Protected main branch, signed commits, detailed commit messages, PR descriptions |
| API rate limiting | Low | Medium | CI/CD slowdowns, automation failures | Use GitHub Apps over personal tokens, implement backoff logic, cache API responses |

## Monitoring and Success Criteria

### Key Metrics

**Repository Health**:
1. Active contributors: 2-3 developers
2. Average PR merge time: <24 hours
3. Open PR count: <10 at any time
4. Branch count: <20 active branches

**Code Quality**:
1. PR review coverage: 100% of changes
2. Failing status checks: 0 before merge
3. Security alerts: Addressed within 7 days
4. Code review comments per PR: 2-5 average

**Development Velocity**:
1. Commits per week: 20-50
2. PR throughput: 5-10 per week
3. Issue close rate: >80%
4. Release frequency: Weekly or bi-weekly

### Alerting Thresholds

**Critical Alerts (Email)**:
- Main branch protection rules modified
- Repository made public accidentally
- Security vulnerability detected (high/critical)
- Failed backup to external storage
- Unauthorized access attempt

**Warning Alerts (Email)**:
- PR open for >3 days without review
- Repository size approaching limits
- Large file committed (>50MB)
- Unusual commit patterns
- Status checks failing on main

**Informational Alerts (Dashboard)**:
- Weekly commit summary
- PR review statistics
- Contributor activity trends
- Repository growth metrics

### Success Criteria

**Functional Requirements**:
- All code stored in version control
- Full commit history preserved
- Branch protection enforced on main
- Pull request workflow functioning

**Performance Requirements**:
- Git clone time <30 seconds
- PR status checks complete <5 minutes
- Repository size <2GB
- No lost commits or branches

**Cost Requirements**:
- Remain on GitHub Free tier indefinitely
- No paid features required
- Storage within free tier limits
- Actions minutes <2000/month

**Operational Requirements**:
- Zero data loss incidents
- 100% uptime (GitHub SLA)
- Daily automated backups
- Access auditing enabled
