# ADR-002: Real-time Messaging - NATS JetStream

## Status
**Accepted** - 2024-01-15

## Context
We need a real-time messaging system to handle:
- Event-driven architecture between microservices
- Real-time notifications to web/mobile clients
- Message persistence and replay capabilities
- High-throughput, low-latency messaging
- Clustering and high availability

## Decision
We will use **NATS JetStream** as our real-time messaging bus.

## Options Considered

### Option 1: NATS JetStream ✅ **CHOSEN**
**Pros:**
- Extremely low latency (sub-millisecond)
- Simple to deploy and operate
- Built-in persistence and replay
- Excellent clustering support
- Small resource footprint
- Built-in security features
- Support for multiple messaging patterns

**Cons:**
- Smaller ecosystem compared to Kafka
- Fewer third-party integrations
- Less mature tooling
- Newer technology (less battle-tested)

### Option 2: Apache Kafka
**Pros:**
- Mature, battle-tested
- Huge ecosystem and tooling
- Excellent for high-throughput scenarios
- Strong consistency guarantees
- Extensive monitoring tools

**Cons:**
- Complex to deploy and operate
- Higher latency than NATS
- Resource-intensive
- Steep learning curve
- Overkill for many use cases

### Option 3: Redis Streams
**Pros:**
- Simple to use
- Good performance
- Familiar Redis operations
- Built-in data structures

**Cons:**
- Limited clustering capabilities
- No built-in schema management
- Memory-only persistence
- Single point of failure

### Option 4: Amazon SQS/SNS
**Pros:**
- Fully managed
- Excellent AWS integration
- Highly available
- Pay-per-use pricing

**Cons:**
- Vendor lock-in
- Higher latency
- Limited messaging patterns
- Cost can be high at scale

## Consequences

### Positive
- Very low operational overhead
- Excellent performance characteristics
- Simple deployment and scaling
- Built-in security and monitoring
- Supports both pub/sub and request/reply patterns

### Negative
- Smaller community and ecosystem
- Fewer learning resources
- Limited third-party tool integration
- May need custom solutions for some use cases

### Neutral
- Standard messaging patterns apply
- Good documentation available
- Active development and community

## Implementation Notes
- Use JetStream for persistent messaging
- Implement proper error handling and retries
- Set up monitoring and alerting
- Use subject-based routing for message organization
- Implement proper authentication and authorization

## Migration Path
If NATS proves insufficient, migration to Kafka is straightforward:
1. Deploy Kafka cluster
2. Implement dual-write during transition
3. Migrate consumers incrementally
4. Switch producers after verification
