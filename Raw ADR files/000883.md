# ADR 002: Cognito vs Custom Auth

**Status:** Accepted

**Date:** 2025-01-15

## Context

We needed to implement user authentication for the Birthday Reminder Platform. The core requirements are:
- Users sign up with email/password
- Secure token-based authentication for API calls
- Password reset capability
- Optional MFA support
- Low operational complexity
- Minimal additional cost

**Options Considered:**
1. **AWS Cognito** (Managed service)
2. **Custom implementation** (Build our own auth)
3. **Third-party service** (Auth0, Firebase Auth)

## Decision

**We chose AWS Cognito.**

## Rationale

### Managed Service Benefits
- **Zero operational overhead:** AWS handles all authentication infrastructure
- **Security best practices:** Built-in protection against common attacks
- **Compliance ready:** Supports HIPAA, SOC 2, and other compliance standards
- **Scaling:** Automatically scales to millions of users

### Features Out of the Box
- ✅ User sign up and email verification
- ✅ Password reset flow
- ✅ Optional MFA (SMS, TOTP, email)
- ✅ Social login (Google, Facebook, etc.) for future
- ✅ Session management
- ✅ JWT token generation and validation

### Developer Experience
- **Hosted UI:** Can use Cognito's built-in login page (no custom UI required)
- **Standard OAuth 2.0/OpenID Connect:** Works with existing libraries (AWS Amplify, etc.)
- **API Gateway integration:** API Gateway has native Cognito authorizer
- **Lambda integration:** Easy to extract user claims in Lambda functions

### Cost Effectiveness
- **Free tier:** 50,000 monthly active users (MAU) free
- **Pay-per-user:** Only $0.015 per additional MAU after free tier
- **No infrastructure costs:** Fully managed

### Security
- **No password storage:** We never see or store passwords (Cognito handles it)
- **Industry-standard tokens:** JWT tokens with standard claims
- **Rate limiting:** Built-in protection against brute force attacks
- **HTTPS only:** All communication encrypted

## Trade-offs

### Advantages
- ✅ Enterprise-grade security
- ✅ Zero operational overhead
- ✅ Scales automatically
- ✅ Low cost (free up to 50K users)
- ✅ Standard OAuth 2.0 integration
- ✅ MFA support without extra implementation
- ✅ Good for portfolio (shows knowledge of managed identity services)

### Disadvantages
- ❌ Vendor lock-in (AWS-specific)
- ❌ Less customization than custom implementation
- ❌ Cognito UI styling limited compared to custom
- ❌ Debug issues require AWS documentation/support
- ❌ Learning curve for Terraform/IaC configuration

## Why Not Custom Auth?

**Building our own authentication system would require:**
- Secure password hashing (bcrypt, scrypt, etc.)
- Salt generation and management
- Token generation and validation (JWT)
- Refresh token rotation
- Password reset flow (email generation, verification codes)
- Rate limiting on login attempts
- CSRF protection
- Secure session management
- All this code must be security-audited

**Complexity & Risk:**
- ❌ High risk of security vulnerabilities
- ❌ Takes weeks to implement properly
- ❌ Ongoing maintenance and patching
- ❌ Doesn't demonstrate platform engineering skills better than using managed service

## Why Not Third-Party (Auth0)?

**Auth0 advantages:**
- More customization options
- Multi-tenant architecture

**Auth0 disadvantages:**
- Additional vendor dependency
- Separate pricing and account management
- Less integrated with AWS (extra API calls)
- Overkill for this project scope

## Consequences

### Positive
- Users can sign up immediately without custom auth code
- Secure by default (we don't handle passwords)
- Easy to add social login later
- Easy to add MFA for users who want it
- Demonstrates knowledge of AWS managed services
- Fully serverless architecture

### Negative
- Tied to AWS ecosystem
- Limited UI customization without extra work
- Less control over user experience

## Implementation Details

### Cognito Configuration
- **User Pool:** For storing user credentials
- **Hosted UI:** For signup/login/password reset
- **App Client:** For integration with frontend
- **Domain:** Custom domain for consistency

### Frontend Integration
- Use AWS Amplify Auth library
- Store ID token in memory (not localStorage for security)
- Send ID token in API requests
- Use automatic token refresh

### API Integration
- API Gateway Cognito Authorizer validates token
- Lambda extracts user_id from token claims
- All queries scoped to authenticated user

## Future Considerations

- **Multi-factor authentication:** Can enable SMS or TOTP MFA
- **Social sign-in:** Easy to add Google, Facebook, GitHub logins
- **Custom domain:** Use custom domain for hosted UI
- **Lambda triggers:** Use Lambda functions to customize auth flow (e.g., custom validation)
- **Fine-grained access control:** Could use groups/roles for authorization

## Security Checklist

- ✅ Passwords never stored or visible in our system
- ✅ All tokens validated before API access
- ✅ Tokens are JWT (standard format)
- ✅ HTTPS enforced for all communication
- ✅ Cognito handles rate limiting
- ✅ CORS properly configured for frontend domain
- ✅ User data scoped by authenticated user_id
