# ADR-001: Use SQLite for MVP Instead of ETS

## Status

Superseded by ADR-008 (PostgreSQL Migration)

## Context

The initial implementation used ETS (Erlang Term Storage) as the data layer for all Ash resources. While ETS provides excellent performance for in-memory operations, several constraints emerged:

1. **Data Persistence**: ETS is an in-memory storage system, meaning all data is lost when the application restarts
2. **Development Workflow**: Developers need to recreate test data after every restart
3. **Feature Limitations**: Many Ash features like migrations, complex queries, and relationships work better with SQL databases
4. **Testing Complexity**: ETS doesn't support database transactions, making test isolation difficult
5. **Production Readiness**: Even for MVP, users expect their financial data to persist

## Decision

We will migrate from ETS to SQLite for the MVP phase, using the AshSqlite.DataLayer for all Ash resources.

## Consequences

### Positive

- **Data Persistence**: All data survives application restarts
- **Better Testing**: SQLite supports transactions for test isolation via Ecto.Adapters.SQL.Sandbox
- **Migration Support**: Can generate and run database migrations with `mix ash_sqlite.generate_migrations`
- **SQL Features**: Access to indexes, constraints, and complex queries
- **Production Path**: Easier migration to PostgreSQL for production (both are SQL databases)
- **Developer Experience**: No need to recreate data after restarts during development

### Negative

- **Performance**: SQLite is slower than in-memory ETS for read operations
- **Concurrency**: SQLite has limited write concurrency (single writer at a time)
- **Money Type Issues**: AshMoney.Types.Money doesn't serialize properly with SQLite, requiring refactoring
- **Migration Overhead**: Need to generate and maintain database migrations

### Neutral

- **File-based Storage**: SQLite stores data in a single file, which is simple but requires backup strategies
- **Testing Setup**: Need to configure Ecto.Adapters.SQL.Sandbox for concurrent tests

## Implementation

1. Add `ash_sqlite` dependency to mix.exs
2. Configure SharedLedger.Repo with SQLite adapter
3. Update all resources to use `data_layer: AshSqlite.DataLayer`
4. Add `sqlite do` blocks with table names to each resource
5. Generate and run migrations with `mix ash_sqlite.generate_migrations`
6. Refactor Money type handling to work with SQLite serialization
