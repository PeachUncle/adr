# Design: Random Orthogonal Projection Matrix

## Context
RaBitQ quantization requires orthogonal transformations to rotate vectors before quantization. We need a function to generate random orthogonal projection matrices with arbitrary dimensions (m×n) that can be used in the quantization pipeline. The matrices must be reproducible (seeded) for consistent benchmarking and debugging.

## Goals / Non-Goals

### Goals
- Generate orthonormal matrices with configurable dimensions (m×n)
- Support reproducible generation via random seed
- Efficient memory usage with allocator-aware design
- Numerical stability for typical embedding dimensions (up to 2048)
- Simple, testable API

### Non-Goals
- Not optimizing for real-time generation (offline/setup phase is acceptable)
- Not supporting sparse or structured matrices (future work)
- Not implementing specialized SIMD optimizations initially
- Not providing matrix multiplication operations yet (separate future work)

## Decisions

### Algorithm: QR Decomposition via Modified Gram-Schmidt
**Decision**: Use Modified Gram-Schmidt orthogonalization on a random Gaussian matrix.

**Rationale**:
- **Simplicity**: Straightforward to implement in pure Zig without external dependencies
- **Numerical stability**: Modified Gram-Schmidt is more stable than classical GS
- **Correctness**: Produces truly orthonormal columns/rows
- **Educational**: Clear algorithm for research code

**Alternatives considered**:
1. **Householder reflections**: More stable but more complex to implement
2. **Givens rotations**: Even more complex, overkill for this use case
3. **Random rotations composition**: Fast but less uniform distribution over orthogonal matrices
4. **LAPACK/BLAS QR**: Would require C dependencies, against project constraints

### Memory Layout: Row-Major
**Decision**: Store matrix data in row-major order (C-style).

**Rationale**:
- Standard in systems programming
- Better cache locality for row operations
- Easier integration with vector operations (vectors as rows)
- Matches typical usage: multiply matrix by column vector

**Alternatives considered**:
- Column-major (Fortran-style): Better for some linear algebra operations, but less intuitive

### Data Structure
**Decision**: Use `@Vector` for SIMD-optimized operations with power-of-2 dimensions.

```zig
pub const Matrix = struct {
    allocator: Allocator,
    rows: usize,
    cols: usize,
    data: []f32,  // row-major storage, length = rows * cols
    // Internal: data organized to enable @Vector operations
    
    pub fn deinit(self: *Matrix) void;
};
```

**Key constraints**:
- Both `rows` and `cols` MUST be powers of 2 (enforced at creation time)
- This enables efficient SIMD operations using Zig's `@Vector` type
- Typical dimensions: 64, 128, 256, 512, 1024, 2048

**Rationale**:
- **SIMD performance**: Power-of-2 dimensions align perfectly with vector register sizes
- **Memory alignment**: Ensures optimal cache line usage
- **Typical use cases**: Image embeddings (SIFT: 128, ResNet: 256/512) are power-of-2
- **Zig @Vector**: Built-in SIMD support for arithmetic operations

### Random Number Generation
**Decision**: Use Zig's standard library RNG with explicit seeding.

**Rationale**:
- Built-in, no dependencies
- Sufficient quality for random matrix generation
- Explicit seed parameter ensures reproducibility

**Box-Muller Transform**: For Gaussian random numbers
- Simple to implement
- Produces high-quality normal distribution samples
- No lookup tables needed

### Orthogonalization Details

For m×n matrix where m ≥ n:
- Generate m×n Gaussian random matrix A
- Apply MGS to get Q (orthonormal columns)
- Result: Q^T * Q = I_n

For m×n matrix where m < n:
- Generate m×n Gaussian random matrix A
- Apply MGS on transposed view to get orthonormal rows
- Result: Q * Q^T = I_m

### Error Handling
```zig
pub const MatrixError = error{
    InvalidDimensions,      // Zero, negative, or non-power-of-2
    OutOfMemory,
};

pub fn createRandomOrthogonalProjection(
    allocator: Allocator,
    m: usize,              // Must be power-of-2
    n: usize,              // Must be power-of-2
    seed: u64,
) MatrixError!Matrix
```

**Validation**: Both `m` and `n` must be:
- Greater than 0
- Powers of 2 (checked via `(x & (x - 1)) == 0`)

## Risks / Trade-offs

### Risk: Numerical Precision
- **Issue**: Floating-point errors can accumulate during orthogonalization
- **Mitigation**: Use Modified Gram-Schmidt (more stable), test orthogonality with tolerance
- **Acceptable**: f32 precision sufficient for typical quantization use cases

### Risk: Performance for Large Dimensions
- **Issue**: O(n³) complexity for QR decomposition
- **Impact**: May be slow for dimensions > 2048
- **Mitigation**: This is a setup/initialization phase, not in the hot path
- **SIMD optimization**: Using `@Vector` significantly improves performance for inner loops
- **Future**: Can further optimize with blocked algorithms if needed

### Trade-off: Simplicity vs. Performance
- **Choice**: Using SIMD via `@Vector` while keeping algorithm straightforward
- **Justification**: Power-of-2 constraint and `@Vector` provide significant performance gains with minimal complexity increase
- **Balance**: Simple algorithm (Modified Gram-Schmidt) with SIMD-optimized arithmetic

### Trade-off: Power-of-2 Constraint
- **Choice**: Strict power-of-2 dimension requirement
- **Upside**: Optimal SIMD performance, simpler memory layout, matches typical use cases
- **Downside**: Cannot handle arbitrary dimensions (e.g., 768 dimensions not supported)
- **Justification**: Target use cases (SIFT, standard CNNs) use power-of-2 dimensions

### Trade-off: Memory Overhead
- **Issue**: Need temporary storage during QR decomposition
- **Impact**: 2x memory temporarily (input matrix + output matrix)
- **Acceptable**: One-time cost during initialization

## Open Questions
1. Should we support both f32 and f64 precision via generics?
   - **Leaning**: Start with f32 only, add f64 if needed
   
2. Should we return the Q matrix or also expose R from QR decomposition?
   - **Decision**: Only return Q (the orthogonal matrix), R not needed for this use case
   
3. Should we validate orthogonality after generation and return an error if tolerance exceeded?
   - **Leaning**: Yes in debug builds, optional validation function for testing

4. What vector length should we use for `@Vector` operations?
   - **Decision**: Use compile-time determined vector sizes based on dimension and target architecture
   - **Approach**: Process rows/columns in chunks that fit SIMD registers (e.g., @Vector(8, f32))
