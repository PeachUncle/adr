# ADR-002: Database Strategy

## Status
Accepted

## Context
Our microservices architecture requires a database strategy that supports service autonomy, data consistency, and scalability. We need to decide on database technologies, data ownership patterns, and consistency models.

## Decision
We will implement a "Database per Service" pattern with the following database technologies:

### Database Technologies
- **PostgreSQL**: Primary database for transactional services
  - User Service: User profiles, addresses, roles
  - Product Service: Products, categories, inventory
  - Order Service: Orders, order items, shipping information
  - Payment Service: Payment transactions, refunds

- **MongoDB**: Document database for flexible schema requirements
  - Notification Service: Notification templates, delivery logs, user preferences

- **Redis**: In-memory cache for performance optimization
  - Session storage
  - Frequently accessed data caching
  - Rate limiting counters

### Data Ownership
- Each service owns its data exclusively
- No direct database access between services
- Data sharing through well-defined APIs
- Event-driven updates for data synchronization

### Consistency Model
- **Strong Consistency**: Within service boundaries
- **Eventual Consistency**: Across service boundaries
- **Saga Pattern**: For distributed transactions

## Consequences

### Positive
- **Service Autonomy**: Teams can choose optimal database technology
- **Independent Scaling**: Databases can be scaled based on service needs
- **Fault Isolation**: Database issues don't cascade across services
- **Technology Optimization**: Use best database for specific use cases

### Negative
- **Data Duplication**: Some data may be replicated across services
- **Complex Queries**: Cross-service queries require multiple API calls
- **Eventual Consistency**: Temporary data inconsistencies possible
- **Operational Overhead**: Multiple databases to manage

### Mitigation Strategies
- **CQRS**: Separate read and write models where appropriate
- **Event Sourcing**: For audit trails and data reconstruction
- **Database Migrations**: Automated with Flyway
- **Backup Strategy**: Automated backups for all databases
- **Monitoring**: Database performance and health monitoring

## Database Schema Design

### User Service (PostgreSQL)
```sql
-- Users table with proper indexing
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    password VARCHAR(255) NOT NULL,
    first_name VARCHAR(255) NOT NULL,
    last_name VARCHAR(255) NOT NULL,
    status VARCHAR(20) DEFAULT 'ACTIVE',
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);

-- Addresses table
CREATE TABLE addresses (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT REFERENCES users(id),
    address_line_1 VARCHAR(255) NOT NULL,
    city VARCHAR(100) NOT NULL,
    country VARCHAR(100) NOT NULL,
    is_default BOOLEAN DEFAULT FALSE
);
```

### Product Service (PostgreSQL)
```sql
-- Categories table
CREATE TABLE categories (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(255) UNIQUE NOT NULL,
    parent_id BIGINT REFERENCES categories(id),
    is_active BOOLEAN DEFAULT TRUE
);

-- Products table
CREATE TABLE products (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    sku VARCHAR(100) UNIQUE NOT NULL,
    price DECIMAL(10,2) NOT NULL,
    stock_quantity INTEGER NOT NULL,
    category_id BIGINT REFERENCES categories(id),
    status VARCHAR(20) DEFAULT 'ACTIVE'
);
```

### Order Service (PostgreSQL)
```sql
-- Orders table
CREATE TABLE orders (
    id BIGSERIAL PRIMARY KEY,
    order_number VARCHAR(50) UNIQUE NOT NULL,
    user_id BIGINT NOT NULL,
    status VARCHAR(20) DEFAULT 'PENDING',
    total_amount DECIMAL(10,2) NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);

-- Order items table
CREATE TABLE order_items (
    id BIGSERIAL PRIMARY KEY,
    order_id BIGINT REFERENCES orders(id),
    product_id BIGINT NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(10,2) NOT NULL
);
```

## Data Synchronization Strategy

### Event-Driven Updates
- Services publish events when data changes
- Interested services subscribe to relevant events
- Use message queues (RabbitMQ) for reliable delivery

### Example Events
```json
{
  "eventType": "UserCreated",
  "userId": 123,
  "email": "user@example.com",
  "timestamp": "2024-01-20T10:30:00Z"
}

{
  "eventType": "ProductStockUpdated",
  "productId": 456,
  "newStock": 50,
  "timestamp": "2024-01-20T10:35:00Z"
}
```

### Data Consistency Patterns

#### Saga Pattern for Order Processing
1. Create Order (Order Service)
2. Reserve Inventory (Product Service)
3. Process Payment (Payment Service)
4. Send Confirmation (Notification Service)

If any step fails, compensating transactions are executed.

#### CQRS for Product Catalog
- Write Model: Normalized data in Product Service
- Read Model: Denormalized data optimized for queries
- Event sourcing for product changes

## Backup and Recovery Strategy

### Automated Backups
- Daily full backups for all databases
- Point-in-time recovery capability
- Cross-region backup replication

### Disaster Recovery
- RTO (Recovery Time Objective): 4 hours
- RPO (Recovery Point Objective): 1 hour
- Automated failover for critical services

## Performance Optimization

### Indexing Strategy
- Primary keys and foreign keys automatically indexed
- Additional indexes on frequently queried columns
- Composite indexes for complex queries

### Caching Strategy
- Redis for frequently accessed data
- Application-level caching with TTL
- Cache invalidation on data updates

### Connection Pooling
- HikariCP for PostgreSQL connections
- Optimized pool sizes based on service load
- Connection health monitoring

## Monitoring and Alerting

### Database Metrics
- Connection pool utilization
- Query performance and slow queries
- Database size and growth trends
- Replication lag (if applicable)

### Alerts
- High CPU/memory usage
- Slow query detection
- Connection pool exhaustion
- Backup failure notifications

## Migration Strategy

### Schema Migrations
- Flyway for automated schema migrations
- Version-controlled migration scripts
- Rollback capabilities for failed migrations

### Data Migrations
- Blue-green deployments for major changes
- Gradual data migration for large datasets
- Data validation and integrity checks

## Alternatives Considered

### Shared Database
- **Pros**: Simpler queries, ACID transactions
- **Cons**: Tight coupling, scaling bottlenecks
- **Rejected**: Violates microservices principles

### NoSQL Only
- **Pros**: Flexible schema, horizontal scaling
- **Cons**: Limited ACID guarantees, complex queries
- **Rejected**: Not suitable for all data types

### Event Sourcing Everywhere
- **Pros**: Complete audit trail, temporal queries
- **Cons**: Complexity, storage overhead
- **Rejected**: Overkill for simple CRUD operations
