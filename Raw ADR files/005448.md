## Context

The multi-asset trading system requires a robust memory solution to support its agents. The system needs to differentiate between long-term, durable memory for analysis and auditing, and short-term, high-speed operational memory for real-time state management and caching. The preference is for cloud-based, managed solutions to minimize operational overhead.

## Decision

We will implement a dual-layer memory architecture composed of a Permanent Memory Layer for long-term storage and an Operational Memory Layer for high-speed, temporary data access.

1.  **Permanent Memory Layer**: A hybrid of **Google Cloud SQL for PostgreSQL** for transactional records and **Google BigQuery** for all other analytical and semi-structured long-term data.
2.  **Operational Memory Layer**: **Google Memorystore for Redis** for in-memory caching and state management.

## Rationale

A dual-layer memory architecture provides a "best of both worlds" solution that is cost-effective, scalable, and resilient.

1.  **Separation of Concerns**: It acknowledges that operational and analytical data have fundamentally different requirements. Operational data needs low latency and high throughput for small transactions, while analytical data requires cost-effective storage for large volumes and powerful querying capabilities. Using a single database for both is inefficient and leads to compromises.
2.  **Optimized for Cost and Performance**: Each component is chosen for its strength in its specific domain.
    -   **Redis** provides sub-millisecond latency for the real-time operational data that the trading system depends on.
    -   **Cloud SQL** provides the transactional integrity (ACID compliance) required for critical financial records.
    -   **BigQuery** provides extremely low-cost, petabyte-scale storage for the vast amounts of market and agent data the system will archive, with an unparalleled analytics engine.
3.  **Reduced Operational Overhead**: By selecting fully managed GCP services, we eliminate the need to manage servers, replication, or scaling, allowing the team to focus on the application logic.

## Consequences

-   **New Dependencies**: The project will require new Python libraries for interacting with PostgreSQL (`asyncpg`), BigQuery (`google-cloud-bigquery`), and Redis (`redis-py`).
-   **Infrastructure**: New cloud resources (Google Cloud SQL, BigQuery datasets, and Google Memorystore) will need to be provisioned and configured.
-   **Implementation**:
    -   Client modules for all three data stores will be required.
    -   The `IBGatewayAgent` will stream data to BigQuery and Redis.
    -   The `Orchestrator` will use Redis for state management.
    -   Agents will query BigQuery for historical analysis and log their final decisions there.
-   **Configuration**: The application's configuration will need to be updated with connection details for all three data services.
-   **Cost**: This architecture introduces costs for three managed services, but it is highly optimized. Caching in Redis reduces API and compute costs, while BigQuery provides very cheap long-term storage.
-   **Resilience**: The system will be highly resilient, with operational state recoverable from Redis and a complete, auditable history of all market data and agent decisions stored in BigQuery and Cloud SQL.

## Alternatives Considered

1.  **Single Database (PostgreSQL Only)**: Using a single Cloud SQL for PostgreSQL database for all data (transactional, analytical, and caching).
    -   **Reason for Rejection**: This approach is not scalable or cost-effective. Relational databases are not designed for the high-volume, semi-structured data generated by agents, and their analytical performance does not scale as well as a dedicated data warehouse like BigQuery. Using it for caching would also be far less performant than an in-memory store like Redis.

2.  **NoSQL-First Approach (e.g., Firestore)**: Using a NoSQL database as the primary store for all data.
    -   **Reason for Rejection**: While flexible, most NoSQL databases lack the strict ACID compliance and transactional integrity required for core financial records like trades and orders. This would introduce unacceptable data integrity risks.

3.  **Using a Different In-Memory Store (e.g., Memcached)**: Using a simpler caching solution like Memcached instead of Redis.
    -   **Reason for Rejection**: Redis was chosen over Memcached because it offers a richer set of data structures (hashes, lists, sets) and has built-in persistence options. This makes it more versatile, allowing it to be used not just for simple caching but also for more complex tasks like state management and message queuing, which are requirements for the system.

## Implementation Strategy

### Phase 1: Infrastructure Provisioning (Week 1-2)
**Deliverables**:
- Provision Google Memorystore for Redis instance (4GB memory, standard tier)
- Provision Google Cloud SQL for PostgreSQL instance (db-custom-2-7680 configuration)
- Configure BigQuery dataset `trading` with partition tables
- Set up VPC network peering and IAM roles
- Configure backup policies (Redis RDB snapshots, Cloud SQL automated backups)

**Dependencies**: GCP project access, Terraform infrastructure-as-code setup

### Phase 2: Client Libraries and Abstractions (Week 2-3)
**Deliverables**:
- Implement Redis client module with connection pooling (`redis-py` with `asyncio` support)
- Implement Cloud SQL client module (`asyncpg` with connection pool)
- Implement BigQuery client module (`google-cloud-bigquery` with streaming inserts)
- Create abstraction layer for data access patterns (cache-aside, write-through)
- Unit tests for all client modules

**Dependencies**: Phase 1 infrastructure provisioned

### Phase 3: Agent Integration (Week 3-5)
**Deliverables**:
- Update `IBGatewayAgent` to dual-dispatch market data (Redis + BigQuery)
- Modify Portfolio Orchestrator Agent to use Redis for state management
- Implement session context checkpointing in base agent class (Redis)
- Add BigQuery archival for completed agent sessions (ADR-003)
- Integration tests for data flow across all three stores

**Dependencies**: Phase 2 client libraries, ADR-003 implementation

### Phase 4: Monitoring and Optimization (Week 5-6)
**Deliverables**:
- Configure Cloud Monitoring dashboards for Redis, Cloud SQL, BigQuery
- Set up alerting thresholds (memory usage, connection pool exhaustion, query costs)
- Implement cache warming strategy for frequently accessed data
- Performance testing and optimization (connection pool tuning, batch insert sizes)
- Documentation for operational runbooks

**Dependencies**: Phase 3 integration complete, ADR-025 (Observability) implementation

## Cost Analysis

### Monthly Operational Costs

**Redis Memorystore**:
- Standard tier (4GB instance): $35/month
- Data transfer (egress): $10-15/month
- **Subtotal**: $45-50/month

**Cloud SQL for PostgreSQL**:
- db-custom-2-7680 instance (2 vCPU, 7.68GB RAM): $120/month
- Storage (100GB SSD): $17/month
- Backup storage (100GB): $8/month
- Data transfer: $5-10/month
- **Subtotal**: $150-155/month (see ADR-025 for detailed breakdown)

**BigQuery**:
- Storage (1TB active, 5TB long-term): $20 + $10 = $30/month
- Query processing (500GB scanned/month): $2.50/month
- Streaming inserts (10M rows/month): $0.50/month
- Data transfer: $5-10/month
- **Subtotal**: $38-43/month (see ADR-004 for optimization strategies)

**Total Estimated Monthly Cost**: $233-248/month

### Cost Optimization Strategies

1. **Redis Caching Reduces API Calls**:
   - Without Redis: 1M IB Gateway API calls/month × $0.0005 = $500/month
   - With Redis (90% cache hit rate): 100K API calls/month × $0.0005 = $50/month
   - **Net Savings**: $450/month (Redis cost: $50, savings: $450, ROI: 9:1)

2. **BigQuery Partitioning**:
   - Without partitioning: 2.5TB scanned/month × $5/TB = $12.50/month
   - With date partitioning (20% of data scanned): 500GB × $5/TB = $2.50/month
   - **Savings**: $10/month (80% reduction)

3. **Cloud SQL Connection Pooling**:
   - Reduces connection overhead by 70%, enabling smaller instance size
   - Prevents need for 4 vCPU instance upgrade ($120/month avoided)

### ROI Comparison

**vs Single PostgreSQL Approach**:
- Single Cloud SQL for all workloads: db-custom-8-30720 (8 vCPU, 30GB RAM) = $480/month
- Current hybrid approach: $233-248/month
- **Cost Savings**: 48-52% reduction

**vs NoSQL-First Approach (Firestore)**:
- Firestore storage (1TB): $180/month
- Document reads (100M/month): $360/month
- Document writes (10M/month): $180/month
- Total: $720/month
- **Cost Savings**: 66-67% reduction

## Risk Assessment

| Risk | Severity | Likelihood | Impact | Mitigation |
|------|----------|------------|--------|------------|
| Redis data loss | High | Low | State recovery required, delayed order execution | RDB persistence enabled (hourly snapshots), AOF logging for critical state, fallback to Cloud SQL for state reconstruction |
| Cloud SQL connection exhaustion | Medium | Medium | Agent failures, blocked trades | Connection pooling (max 50 connections), circuit breaker pattern, connection monitoring alerts at 80% utilization |
| BigQuery streaming insert quota | Medium | Low | Data loss for analytics, incomplete audit trail | Batch inserts where latency acceptable, fallback to Cloud Storage + load jobs, quota monitoring and alerting |
| Redis memory exhaustion | High | Medium | Cache eviction, performance degradation | LRU eviction policy, memory monitoring at 80% threshold, auto-scaling to larger tier, TTL policies for ephemeral data |
| Network partition | High | Low | Complete system outage | VPC peering with redundant paths, retry logic with exponential backoff, regional replication for Redis (if critical) |
| BigQuery cost overrun | Low | Medium | Budget exceeded | Query cost monitoring, daily spending alerts at $20, partitioning enforcement, materialized views for frequent queries |
| Cloud SQL replication lag | Medium | Low | Stale data reads, incorrect risk calculations | Read replicas for analytics queries only, write to primary for operational data, replication lag monitoring (<5s threshold) |
| Schema evolution conflicts | Low | Medium | BigQuery insert failures | Schema auto-detect enabled, backward-compatible changes only, schema validation in client libraries |

## Monitoring and Success Criteria

### Key Metrics

**Redis Performance**:
1. Cache hit rate: >90% (Target: 95%)
2. Memory utilization: <80% of allocated capacity
3. Command latency: <1ms p95, <5ms p99
4. Eviction rate: <100 keys/minute

**Cloud SQL Performance**:
1. Query latency: <50ms p95, <100ms p99
2. Connection pool utilization: <80% of max connections
3. Transaction throughput: >500 TPS sustained
4. Replication lag: <5 seconds

**BigQuery Performance**:
1. Query cost: <$8/day (<$250/month)
2. Streaming insert latency: <10 seconds p95
3. Storage growth: <50GB/day
4. Query slot utilization: <500 slot-seconds/query p95

### Alerting Thresholds

**Critical Alerts (PagerDuty)**:
- Redis memory usage >90%
- Cloud SQL connections >90% of pool
- BigQuery daily cost >$20
- Redis unavailable for >30 seconds
- Cloud SQL primary unavailable

**Warning Alerts (Email)**:
- Redis cache hit rate <85%
- Cloud SQL query latency >100ms p95
- BigQuery storage >1TB (active tier)
- Connection pool utilization >70%
- Redis eviction rate >500 keys/minute

**Informational Alerts (Dashboard)**:
- Daily BigQuery cost summary
- Weekly storage growth trends
- Cache performance analytics
- Query pattern analysis

### Success Criteria

**Functional Requirements**:
- All operational state persists correctly across system restarts
- Zero data loss for transactional records (trades, orders)
- Complete audit trail for all agent decisions in BigQuery
- Agent session recovery <30 seconds after failure

**Performance Requirements**:
- 99.9% uptime for operational memory layer (Redis)
- <10ms p95 latency for operational data access (Redis GET)
- <100ms p95 latency for transactional data access (Cloud SQL SELECT)
- <5 second p95 latency for analytical queries (BigQuery)

**Cost Requirements**:
- Total monthly cost <$300 (within 10% tolerance)
- BigQuery query cost <$250/month
- No single query exceeding $5 cost
- ROI >5:1 vs single-database approach

**Operational Requirements**:
- Zero manual intervention required for normal operations
- Automated backups with <1 hour RPO (Recovery Point Objective)
- <15 minute RTO (Recovery Time Objective) for operational layer
- Self-healing connection pools and retry mechanisms
