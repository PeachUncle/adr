## Context and Problem Statement

In the previous version of the architecture, we decided to keep a monolithic application with Django and PostgreSQL, deployed in a simple environment, using a single server for the entire backend. However, the infrastructure has changed to integrate technologies such as containers, an API and an API Gateway, which are now customer-imposed requirements. 

## Decision Drivers

- **Customer requirements**: The introduction of containers and an API Gateway are mandatory customer requirements to facilitate API management and security.
- **Simplicity in deployment**: Containers will simplify the configuration and deployment of the system in different environments.
- **Security and access control**: The use of an API Gateway allows centralizing authentication, authorization and access logs to the API, which is essential for the security of the system.

## Considered Options

- **Monolithic application with containers for Django, PostgreSQL, API Gateway, and the API Gateway database.**
  * Using containers both Django server and PostgreSQL.
  * PostgreSQL with persistent volume for the database.
  * API accessible through the API Gateway.
  * API Gateway runs in its own container and has its own independent database.

## Decision Outcome

The chosen option is to keep the **monolithic application**, but with the following updates:
  * **Containerization**: Both Django and PostgreSQL run inside containers, making it easier to deploy and manage the environment.
  ** **Volume for PostgreSQL**: PostgreSQL has been configured to use a persistent volume, ensuring that data is preserved even if the container is stopped or restarted.
  **API and API Gateway**: An API has been implemented to allow clients to access both the web interface and the API. An API Gateway is used to handle authentication, authorization and logging of API accesses. The API Gateway runs in its own container and has its own independent database.

### Positive Consequences

- **Easier deployment**: Containerization allows deployment to be done consistently across different environments (development, production, etc.).
- **Improved security**: The API Gateway centralizes security management, making it easier to implement authentication and access control.
- **Guaranteed data persistence**: PostgreSQL remains persistent thanks to the volume, ensuring data integrity, while the API Gateway database is also persistent.
- **Flexible accessibility**: Clients can access both the web and the API, enhancing interaction with the application.

### Negative Consequences

- **Container management complexity**: The introduction of containers and the API Gateway adds some complexity to infrastructure management, especially if you do not have prior experience.
- **API Gateway dependency**: The introduction of the API Gateway creates a central point of failure, and its management must be robust to avoid availability issues.
- **Potential for resource overhead**: The use of containers, while flexible, could increase resource usage compared to a direct implementation if not properly managed.
