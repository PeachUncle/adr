# ADR-0003: AWS SQS for Message Queue

## Status
Accepted

## Context
We need a reliable message queue to handle communication between the producer and consumer services. The queue must handle high throughput, provide message persistence, and support retry mechanisms for failed message processing.

## Decision
We will use AWS Simple Queue Service (SQS) as our message queue with the following configuration:

- **Standard Queue**: For high throughput and at-least-once delivery
- **Dead Letter Queue (DLQ)**: For messages that fail processing after 5 attempts
- **Message Retention**: 4 days for main queue, 14 days for DLQ
- **Visibility Timeout**: 30 seconds
- **Server-side Encryption**: Enabled for security
- **Batch Processing**: Consumer processes messages in batches of 10

## Consequences
### Positive
- **Reliability**: SQS provides 99.9% availability SLA
- **Scalability**: Automatically scales with message volume
- **Durability**: Messages are stored redundantly across multiple AZs
- **Security**: Server-side encryption and IAM integration
- **Monitoring**: CloudWatch integration for metrics and alarms
- **Cost-effective**: Pay-per-use pricing model
- **Managed Service**: No operational overhead for queue management

### Negative
- **Vendor Lock-in**: Tied to AWS ecosystem
- **Latency**: Network calls to AWS SQS add latency
- **Message Ordering**: Standard queues don't guarantee FIFO ordering
- **Message Size Limit**: 256KB per message
- **Cost**: Per-message pricing for high volume scenarios

### Neutral
- **At-least-once Delivery**: Messages may be delivered more than once
- **Eventual Consistency**: Acceptable for financial transaction processing
- **Batch Processing**: Reduces API calls but increases processing complexity

## Implementation Notes
- Consumer uses Spring Cloud AWS SQS for integration
- Manual acknowledgment mode for better control over message processing
- Circuit breaker and retry patterns implemented in consumer
- Batch processing reduces API calls and improves throughput
- DLQ configuration ensures no messages are lost due to processing failures
