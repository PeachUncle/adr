## Context

The review of the system's documentation revealed that critical, portfolio-level risk parameters (such as VIX thresholds, position limits, and portfolio heat) were inconsistently defined across multiple documents. This creates ambiguity, increases the risk of misconfiguration, and makes the system difficult to manage and update. The core principle of the V5 architecture is to have a robust, unified, and easily maintainable system, which is undermined by scattered, hardcoded risk values.

## Decision

We will centralize all global risk management parameters into a single, machine-readable configuration file (e.g., `config/risk.yaml`). This file will serve as the definitive source of truth for the `Risk Management Agent` and will be respected by all other agents, particularly the `Portfolio Orchestrator Agent`.

This decision formalizes the parameters that were previously inconsistent into a single, authoritative specification.

## Rationale

Centralizing risk parameters in a dedicated configuration file is a critical design decision for ensuring the system is robust, maintainable, and safe.

1.  **Single Source of Truth**: It eliminates ambiguity and inconsistency. When risk parameters are scattered across documents or hardcoded in multiple agents, the risk of misconfiguration and error becomes extremely high. Centralization ensures that all components of the system operate with the exact same risk framework.
2.  **Maintainability and Agility**: Market conditions change, and risk parameters need to be tuned. Storing them in a configuration file allows for rapid updates without requiring code changes, testing, and redeployments. This makes the system more agile and easier to manage.
3.  **Reduced Risk**: By externalizing and centralizing these critical values, we reduce the risk of developers accidentally introducing incorrect values during implementation. It makes the risk policy explicit and transparent.

### Core Risk Parameters

The following parameters are now defined as the system-wide standard:

1.  **`max_portfolio_heat`**: `25%`
    -   **Definition**: The maximum percentage of account value that can be at risk across the entire portfolio (calculated as `Sum(Max Loss of all open positions) / Account Value`).
    -   **Rationale**: Caps the total systemic risk exposure at any given time. A value of 25% is standard for this strategy.

2.  **`max_options_positions`**: `12` (renamed from `max_open_positions` for clarity)
    -   **Definition**: The maximum number of concurrent multi-leg options positions (Iron Condors, Cash-Secured Puts, Covered Calls, Bear Call Spreads combined).
    -   **Excludes**: Stock-only positions from CSP assignment.
    -   **Rationale**: Prevents over-diversification and ensures each position can be monitored effectively. The value of 12 aligns with the V5 strategy's capacity.

3.  **`max_assigned_stock_positions`**: `3` (renamed from `max_stock_positions` for clarity)
    -   **Definition**: The maximum number of stock positions held as a result of Cash-Secured Put assignment (not including intentional stock purchases for Covered Calls).
    -   **Rationale**: Limits exposure to assignment risk and ensures adequate capital remains available for options trading. Stock positions consume significantly more capital than options positions and require different management protocols. The value of 3 provides adequate assignment capacity while maintaining primary focus on options strategies.
    -   **Related Limits**:
      - `max_stock_allocation`: 40% of portfolio value (ensures stock positions don't dominate the portfolio)
      - Assignment capacity formula: `(max_stock_positions - current_assignments) / max_stock_positions`
      - See `stock_selection_rules.md` Section 5.1 for assignment capacity calculations

4.  **`max_vix_for_new_trades`**: `35`
    -   **Definition**: The VIX level above which the `Portfolio Orchestrator Agent` will not initiate any new trades.
    -   **Rationale**: Acts as a primary filter to avoid entering new positions in extremely high-volatility environments where correlations spike and models become less reliable. The 35 level provides a buffer before the circuit breaker.

5.  **`circuit_breaker_vix`**: `40`
    -   **Definition**: The VIX level that triggers a "circuit breaker" event, halting all new trading activity and transitioning the system into a defensive, portfolio-preservation mode.
    -   **Rationale**: Represents an extreme market fear level where the primary goal must shift from profit generation to capital preservation.

6.  **`circuit_breaker_daily_loss`**: `2%`
    -   **Definition**: The portfolio-wide daily loss percentage that triggers a "circuit breaker" event, halting all new trading for the remainder of the day.
    -   **Rationale**: Provides a hard stop to prevent cascading losses from a single-day market event or system malfunction.

7.  **`circuit_breaker_correlation`**: `90%`
    -   **Definition**: The average pairwise correlation of all assets currently held in the portfolio. A value approaching 100% indicates a complete loss of diversification. This metric triggers a "circuit breaker" event, halting all new trading and commanding the system to exit all open positions to mitigate systemic risk.
    -   **Rationale**: An extremely high portfolio correlation indicates a loss of diversification, where all positions are likely to move in the same direction, dramatically increasing risk.

### Greeks Limits

The following Greeks thresholds are now centralized to resolve ambiguity between position-level and portfolio-level limits:

**Position-Level Greeks Limits** (per individual position):

8.  **`max_position_delta`**: `50`
    -   **Definition**: Maximum absolute delta for any single options position.
    -   **Rationale**: Controls directional exposure at the position level.

9.  **`max_position_gamma`**: `5`
    -   **Definition**: Maximum gamma for any single position.
    -   **Rationale**: Limits rate of delta change sensitivity per position.

10. **`max_position_vega`**: `100`
    -   **Definition**: Maximum vega for any single position.
    -   **Rationale**: Controls volatility risk per position.

**Portfolio-Level Greeks Limits** (aggregate across all positions):

11. **`max_portfolio_delta`**: `200` / **`min_portfolio_delta`**: `-200`
    -   **Definition**: Maximum absolute portfolio delta (sum of all position deltas).
    -   **Rationale**: Controls aggregate directional bias. Positive = bullish, Negative = bearish.
    -   **Reference**: See `delta_hedging.md` Section 2.2 for regime-based adjustments.

12. **`max_portfolio_gamma`**: `50`
    -   **Definition**: Maximum portfolio gamma (sum of all position gammas).
    -   **Rationale**: Controls aggregate rate of delta change across portfolio.

13. **`max_portfolio_vega`**: `500`
    -   **Definition**: Maximum portfolio vega (sum of all position vegas).
    -   **Rationale**: Limits total volatility exposure across all positions.

14. **`max_portfolio_theta`**: `-200`
    -   **Definition**: Maximum portfolio theta (sum of all position thetas, negative for short premium).
    -   **Rationale**: Controls aggregate time decay exposure.

## Configuration File Specification

The complete configuration schema is defined in `config/risk.yaml`:

**File Location**: `/opt/data/trading/config/risk.yaml`

**Schema Structure**:
```yaml
version: "1.0"
portfolio_limits:
  max_portfolio_heat: 0.25
  max_options_positions: 12
  max_assigned_stock_positions: 3
  max_stock_allocation: 0.40

vix_thresholds:
  max_vix_for_new_trades: 35
  circuit_breaker_vix: 40

circuit_breakers:
  daily_loss_pct: 0.02
  correlation_threshold: 0.90
  max_simultaneous_defense_positions: 3

position_greeks_limits:
  max_position_delta: 50
  max_position_gamma: 5
  max_position_vega: 100
  max_position_theta: -50

portfolio_greeks_limits:
  max_portfolio_delta: 200
  min_portfolio_delta: -200
  max_portfolio_gamma: 50
  max_portfolio_vega: 500
  max_portfolio_theta: -200

regime_based_greeks:
  stable_bull:
    portfolio_delta_range: [50, 150]
    monitoring_frequency_minutes: 15
  # ... other regimes

risk_budget:
  premium_multiplier: 1.5
  atr_multiplier: 2.0
  atr_period: 14
  alert_levels:
    level_1_monitor_closely: 0.40
    level_2_trigger_defense: 0.60
    level_3_immediate_action: 1.00

# Additional sections for assignment risk, position sizing,
# recovery mode, correlation management, delta hedging, monitoring
```

**Validation Rules**:
- All percentage values must be between 0.0 and 1.0
- Position limits must be positive integers
- Greeks limits must allow for realistic position construction
- VIX thresholds: `max_vix_for_new_trades` < `circuit_breaker_vix`

**Versioning Strategy**:
- Configuration version tracked in `version` field
- Breaking changes require major version increment
- Agents validate version compatibility on startup
- Version mismatch triggers startup failure (fail-safe)

## Consequences

-   **Consistency**: All agents and documentation will now refer to a single source of truth for risk, eliminating contradictions.
-   **Maintainability**: Risk parameters can be updated in one place without code changes.
-   **Implementation**:
    -   Configuration file (`config/risk.yaml`) created with complete schema.
    -   A `ConfigManager` service will be responsible for loading and providing these parameters to the relevant agents.
    -   The `Risk Management Agent` will be updated to consume these parameters.
-   **Reduced Risk**: Centralization reduces the chance of a critical misconfiguration.

## Alternatives Considered

1.  **Hardcoding Parameters in Agent Code**: This was the implicit status quo that led to this ADR.
    -   **Reason for Rejection**: This approach is brittle, error-prone, and unmaintainable. It requires a full software development and deployment cycle to change a simple risk threshold and inevitably leads to inconsistencies between different agents and documentation.

2.  **Using Environment Variables**: Storing each risk parameter as a separate environment variable for each agent.
    -   **Reason for Rejection**: While better than hardcoding, this approach makes it difficult to manage the *set* of risk parameters as a coherent whole. It increases operational complexity, as a large number of environment variables must be managed for each deployment, and it doesn't provide a single, easily readable file that defines the entire risk policy.

3.  **Storing Parameters in a Database**: Using a table in a database (e.g., Cloud SQL) to store the risk parameters.
    -   **Reason for Rejection**: This adds unnecessary complexity and a database dependency for what is essentially static application configuration. It introduces a potential point of failure and requires a separate process for updating and versioning the parameters. A version-controlled configuration file is a much simpler and more robust solution for this use case.
