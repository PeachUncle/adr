# ADR-002: Offline-First Sync Model

## Context
- Inspectors operate offline; current demos rely on localStorage/data-URLs, which will not scale for media or deterministic replay.
- The v3 market realities plan elevates offline as a product constraint; the final blueprint stubs sync but lacks the concrete contract.
- We need a contract the clients and server share so retries, conflicts, and idempotency are safe.

## Decision
- Represent client writes as a **workspace mutation log**, persisted locally (IndexedDB) and sent in **batches** to the server.
- Each mutation carries `mutation_id` (uuid), `idempotency_key`, optional `base_revision`, `type`, `payload`, `actor`, `device_id`, and `client_timestamp`.
- Server endpoint accepts a batch, applies idempotently, and returns a **sync receipt** with accepted/rejected mutations, new revision, and conflict reasons.
- Heavy blobs (photos/audio) are stored locally and uploaded via signed URLs; mutations refer to blob handles, not data URLs.
- Keep request/response + background jobs; do not adopt full event sourcing.

## Rationale
- Deterministic replay and idempotency protect against double publishes/uploads.
- Keeping the payload schema explicit unlocks golden tests for offline replay and conflict handling.
- Separation of blob upload prevents IndexedDB bloat and improves retry semantics.

## Consequences
- New contracts: `contracts/sync/workspace_mutation.v1.json` and `contracts/sync/mutation_receipt.v1.json`.
- Engine gets `engine.sync` to validate/apply mutation batches; Platform implements storage/persistence/adapters.
- Field and portal clients share the same mutation schema; background sync can run on either.
- Golden tests should include: apply batch twice → same state; conflict scenarios return stable reasons.

## Open Questions
- Conflict policy per field type (notes/cards merge vs last-write-wins).
- Offline ordering guarantees: do we require causal ordering or just dedupe?
- How to batch media uploads when offline for long durations (chunking/backpressure).
