# ADR-009: Billing Anchor Day for Subscriptions (The February Incident)

**Date**: 2023-05-22
**Status**: ✅ Accepted
**Author**: Sarah Chen
**Reviewers**: Marcus Chen, Finance Team (who were very upset)

## Context

On February 28, 2023, our subscription billing system attempted to bill customers on "day 31" of February. 

Results:
- 2,847 subscriptions failed to bill
- Error: "Invalid date: February 31"
- Revenue impact: ~$120K delayed
- Customer complaints: 47
- Slack messages in #incidents: 892
- Chester's blood pressure: Elevated

The billing system stored `billing_day` as an integer (1-31) representing the day of month to bill. Customers who signed up on the 31st expected to be billed on the 31st. February disagreed.

## Decision

1. **Billing anchor days are restricted to 1-28**
2. **Customers signing up on days 29-31 are assigned anchor day 28**
3. **Existing subscriptions on days 29-31 migrated to day 28**
4. **Database constraint enforces this**

## Rationale

### Options Considered

#### Option 1: Bill on last day of month
- Pro: Simple logic
- Con: Billing day varies (28th, 30th, 31st), confusing for customers
- Con: "Your next bill is on the last day" - which is when?

#### Option 2: Smart day mapping
- Bill on 31st, or 30th if month doesn't have 31, or 28th for Feb
- Pro: Maintains customer expectation
- Con: Complex logic
- Con: We tried this, it caused the incident

#### Option 3: Fixed anchor day (1-28) ✅ CHOSEN
- Pro: Every month has these days
- Pro: Simple, predictable
- Con: Customers who want day 31 can't have it
- Con: One-time migration needed

### Why Option 3

1. **Simplicity wins**: Date logic is a minefield. Simpler is safer.

2. **Customer impact minimal**: 4.2% of customers had anchor days 29-31. We emailed them explaining the change. 3 complained. We gave them a free month.

3. **Stripe compatibility**: Stripe's subscription billing uses similar logic.

4. **Finance approved**: Predictable billing dates make revenue forecasting easier.

## Implementation

### Database Change

```sql
-- Add constraint
ALTER TABLE subscriptions 
ADD CONSTRAINT valid_billing_anchor 
CHECK (billing_anchor_day BETWEEN 1 AND 28);

-- Migration (run before constraint)
UPDATE subscriptions 
SET billing_anchor_day = 28 
WHERE billing_anchor_day > 28;
```

### Code Change

```typescript
// subscription-service.ts
function calculateBillingAnchor(signupDate: Date): number {
  const dayOfMonth = signupDate.getDate();
  return Math.min(dayOfMonth, 28);  // Cap at 28
}

// UI messaging
function getBillingDayText(anchor: number): string {
  if (anchor === 28) {
    return "28th of each month (or last day for shorter months)";
  }
  return `${anchor}${getOrdinalSuffix(anchor)} of each month`;
}
```

### Customer Communication

Email sent to affected customers:

> Subject: Small change to your Acornio billing date
>
> Hi {name},
>
> We're making a tiny adjustment to your billing date. Instead of the 31st, 
> you'll now be billed on the 28th of each month. 
>
> Why? February doesn't have 31 days (we learned this the hard way 🐿️).
>
> As a thank you for your understanding, your next month is on us!

## Consequences

### Positive
- No more February billing failures
- Simpler billing logic
- Predictable revenue forecasting
- Stripe integration is cleaner

### Negative
- 4.2% of customers had billing date changed
- Minor revenue timing shift (some bills moved earlier by 1-3 days)
- We had to explain this in an all-hands (embarrassing)

## Monitoring

Added alerts for:
- Any billing attempt on days > 28 (should be impossible now)
- Subscription creation with invalid anchor (constraint will fail)
- Monthly check for subscriptions that somehow bypassed validation

## Prevention

1. **Code review checklist** now includes: "Does this touch date logic? Get Sarah to review."

2. **Test suite** includes edge cases:
   - January 31 signup
   - February billing
   - Leap year February
   - Time zones crossing date boundaries

3. **This ADR** serves as documentation for future engineers wondering "why only 1-28?"
