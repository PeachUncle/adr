# ADR-002: GraphQL for API Layer

## Status
Accepted

## Context

Social Flow needs an API that can:
- Efficiently fetch complex, nested data structures
- Support real-time updates for social features
- Provide flexibility for mobile and web clients
- Enable rapid frontend development
- Minimize over-fetching and under-fetching

Traditional REST APIs require multiple round trips for complex data and often return more data than needed.

## Decision

We will use **GraphQL** as the primary API layer for Social Flow, powered by AWS AppSync.

Key reasons:
1. **Flexible queries**: Clients request exactly what they need
2. **Single endpoint**: No need for multiple REST endpoints
3. **Type safety**: Schema-first development with TypeScript codegen
4. **Real-time**: Native WebSocket subscriptions
5. **AWS AppSync**: Managed GraphQL service with DynamoDB integration

## Consequences

### Positive

- **Developer experience**: Frontend teams can iterate quickly
- **Performance**: Reduced network round trips and payload sizes
- **Type safety**: Generated TypeScript types for frontend and backend
- **Real-time**: Built-in subscriptions for likes, comments, notifications
- **Schema documentation**: Self-documenting API via introspection
- **Versioning**: Evolution without breaking changes (additive)
- **Caching**: Normalized caching works well with GraphQL

### Negative

- **Learning curve**: Teams need to learn GraphQL concepts
- **Complexity**: Query complexity and depth limiting required
- **N+1 problem**: Need DataLoader pattern to batch requests
- **Caching challenges**: HTTP caching doesn't work the same way
- **File uploads**: Not native to GraphQL (need multipart)

### Risks

- **Query complexity attacks**: Malicious complex queries
  - *Mitigation*: Query depth limiting, complexity analysis, rate limiting
- **Over-fetching from backend**: Resolvers might fetch unnecessary data
  - *Mitigation*: Careful resolver implementation, DataLoader batching
- **Breaking changes**: Schema changes can break clients
  - *Mitigation*: Deprecation workflow, schema versioning

## Alternatives Considered

### REST API

**Pros:**
- Well-understood, mature
- HTTP caching works well
- Simple to implement
- Wide tooling support

**Cons:**
- Multiple endpoints needed
- Over-fetching/under-fetching
- Versioning complexity
- No native real-time support

**Why not chosen:** Too rigid for complex social data structures. Would need many endpoints and round trips.

### gRPC

**Pros:**
- High performance (binary protocol)
- Strong typing (Protocol Buffers)
- Bidirectional streaming
- Code generation

**Cons:**
- Not web-friendly (needs proxy)
- Limited browser support
- Less flexible than GraphQL
- Steeper learning curve

**Why not chosen:** Poor browser support makes it unsuitable for web/mobile clients.

### REST + WebSockets

**Pros:**
- Familiar REST patterns
- WebSockets for real-time
- HTTP caching works

**Cons:**
- Need to maintain two protocols
- Client complexity
- No query flexibility
- Multiple endpoints

**Why not chosen:** More complexity than GraphQL which provides both in one protocol.

## Implementation Notes

### Schema Structure

```graphql
type Query {
  me: User
  user(username: String!): User
  post(id: ID!): Post
  feed(algorithm: FeedAlgorithm, limit: Int): PostConnection
  searchUsers(query: String!): UserConnection
  searchPosts(query: String!): PostConnection
}

type Mutation {
  createPost(input: CreatePostInput!): Post
  likePost(postId: ID!): LikeResult
  followUser(userId: ID!): FollowResult
  updateProfile(input: UpdateProfileInput!): User
}

type Subscription {
  postCreated: Post
  postUpdated(postId: ID!): Post
  notificationReceived: Notification
}
```

### Resolvers

- **Lambda resolvers**: Custom business logic
- **Direct resolvers**: DynamoDB VTL templates for simple CRUD
- **Pipeline resolvers**: Multi-step operations

### DataLoader Pattern

Batch and cache data fetching within a single request:

```typescript
const userLoader = new DataLoader(async (userIds) => {
  const users = await batchGetUsers(userIds);
  return userIds.map(id => users[id]);
});
```

### Query Complexity

Limit query depth and complexity:

```typescript
{
  validationRules: [
    depthLimit(10),
    createComplexityLimitRule(1000)
  ]
}
```

### Caching

- **Response caching**: Cache entire query responses (5-60 seconds)
- **Normalized cache**: Apollo Client's InMemoryCache
- **CDN caching**: CloudFront for public queries

### Error Handling

Use GraphQL error extensions:

```json
{
  "errors": [{
    "message": "Post not found",
    "extensions": {
      "code": "NOT_FOUND",
      "postId": "123"
    }
  }]
}
```
