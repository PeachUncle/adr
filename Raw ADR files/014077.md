# ADR-002 - ORM Configuration Location

## Date
2025-08-01

## Status
Accepted

## Context
The ORM client interfaces (PlanOrmClient, TagOrmClient) were originally placed in `io.springboot.web.config.orm` package. This placement was questioned because:
- These interfaces are data layer components, not web layer components
- Other configuration classes are directly under `io.springboot.config`
- The `web` package typically contains controllers, filters, and other web-specific components

## Decision
Move ORM client interfaces from `io.springboot.web.config.orm` to `io.springboot.config.orm`.

## Consequences

### Positive
- **Consistency**: All configuration-related classes are now under the same parent package
- **Semantic accuracy**: ORM configuration is correctly placed outside the web layer
- **Simpler structure**: Removes unnecessary `web` layer, making the package structure flatter
- **Clearer intent**: Package structure now accurately reflects the architectural layers

### Negative
- **Breaking change**: Required updating import statements (minimal impact)

### Neutral
- ORM configuration remains in its own `orm` subdirectory for organization

## Alternatives Considered

### Option 1: Keep in web.config.orm
- **Description**: Maintain the original location
- **Pros**: No refactoring needed
- **Cons**: Semantically incorrect, confusing placement
- **Reason for rejection**: Violates architectural clarity

### Option 2: Move directly to io.springboot.config
- **Description**: Place ORM clients directly in config package without orm subdirectory
- **Pros**: Even flatter structure
- **Cons**: Mixes different types of configuration
- **Reason for rejection**: The orm subdirectory provides useful categorization

### Option 3: Create separate persistence package
- **Description**: Create `io.springboot.persistence.orm` or similar
- **Pros**: Clear separation of persistence concerns
- **Cons**: Splits configuration across multiple top-level packages
- **Reason for rejection**: Prefer keeping all Spring configuration together

## Notes
- This change aligns with Spring Boot conventions
- The refactoring was straightforward with only one file requiring import updates
- Future persistence-related configurations should follow this pattern
