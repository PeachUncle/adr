# ADR 3: Next.js with TypeScript for UI [Revised]

## Context
The project is a web application that must be responsive, accessible, and performant on desktop and mobile. We initially chose React with TypeScript due to its robust ecosystem and extensive documentation. However, the React team’s announcement of sunsetting Create React App as a recommended bootstrap tool [1] prompted a reassessment. The React Foundation recommended alternative starting points, such as building a React app from scratch or adopting other frameworks like Next.js, Vite, or Remix.

Given our small team size and the goal of minimizing development complexity, we prioritized solutions that provide routing, performance optimizations, and production-ready defaults out of the box. Next.js is a mature, actively maintained framework built on top of React, which meets these criteria. It continues to evolve with strong community and corporate backing, which provides confidence in its long-term support and relevance.

## Decision
Due to the official sunsetting of Create React App and our desire to adopt a mature, integrated, and future-proof framework that accelerates development with fewer custom configurations, we have decided to adopt Next.js with TypeScript for our frontend. This change was made early in the project lifecycle before significant development work began, minimizing lost effort. While the development team must now learn Next.js conventions, the benefits of a well-supported and actively maintained framework outweighs the initial learning curve.

## Status
Accepted

## Consequences
### Positive
- **Consistent development experience:** A frontend and backend built with TypeScript results in fewer context switching for the development team and better code reuse patterns.
- **Accelerated delivery:** Next.js’s opinionated framework and built-in routing, performance optimizations, and conventions enable faster development compared to custom React setups.
- **Mature, actively maintained framework:** Next.js’s strong community and corporate backing provide confidence in ongoing updates, security patches, and evolving best practices, future-proofing our frontend stack.

### Negative
- **Learning curve:** Team must learn React and Next.js concurrently, including Next.js-specific paradigms like file-based routing and server rendering.
- **Tighter framework coupling:** Higher dependence on Next.js conventions compared to a minimal React stack restricts some architectural flexibility.
- **Risk of Vendor Lockout:** The company that manages Next.js, Vercel, has been accused of vendor lock-in in regards to some of Next.js' cloud-related features [2] [3]. We do not need to utilize any of those features in this project but we have to be aware of the risk.
