# ADR-006: Adopt Typer for CLI Interface

## Status
**PROPOSED** – 2025-10-03

## Context
The CLI currently relies on a Click-based implementation (`src/aw_narrator/cli/click_main.py`) alongside a legacy manual parser (`src/aw_narrator/cli/main.py`). Recent feature work has increased CLI complexity (segmentation, checkpoint resume, async flows), and type annotations are duplicated across options and validation logic.

Typer builds directly on Click but uses standard Python type hints to declare parameters, automatically generating help text, validation, and completion scripts. By embracing Typer we can:
- Reduce boilerplate when adding options
- Align command definitions with our type-annotated domain layer
- Simplify testing via auto-generated CLIs that mirror function signatures
- Eliminate the manually parsed legacy CLI entry point

## Decision
Adopt Typer as the primary CLI framework for ActivityWatch Narrator.

Implementation outline:
1. Introduce a Typer app in `src/aw_narrator/cli/app.py` that exposes all commands currently provided by `click_main.py`.
2. Incrementally migrate option definitions, leveraging type annotations and default values for validation.
3. Wrap async workflows with Typer’s coroutine support (using `asyncio.run()` helpers) while maintaining existing business logic.
4. Update tests to target the Typer entry point, replacing subprocess calls to `aw_narrator.cli.main` or `click_main` with Typer-driven invocations.
5. Remove or deprecate the Click-based CLI and legacy manual parser once parity is verified.

## Consequences

### Positive
- **Consistency**: CLI arguments mirror function signatures, reducing drift between implementation and documentation.
- **Developer speed**: Adding flags requires fewer explicit `@click.option` decorators.
- **Type safety**: Native use of Python typings and optional Pydantic integration.
- **User experience**: Automatic help/usage text stays synchronized with code; shell completion scripts are generated automatically.
- **Maintenance**: Eliminates duplicate CLI implementations and simplifies future feature work.

### Negative
- **Migration effort**: Requires refactoring existing CLI modules, tests, and documentation.
- **Learning curve**: Team must become comfortable with Typer patterns.
- **Dependency overlap**: Typer still depends on Click internally; both packages remain in the dependency graph.

### Risks & Mitigations
- **Regression risk**: Mitigate with TDD—port one command/test at a time and keep Click CLI until Typer version passes the suite.
- **Async handling**: Ensure event loop management is centralized (Typer’s `asyncio.run` wrapper) and covered by tests.

## Alternatives Considered
1. **Remain on Click**: Maintain current approach; rejected due to increasing boilerplate and duplicated declarations.
2. **Custom minimal parser**: Not viable; would expand maintenance burden and lose Click/Typer ecosystem benefits.
3. **Argparse / Rich CLI**: Provides less ergonomic developer experience and would require more manual wiring than Typer.

## Implementation Plan
- Publish Typer app skeleton with parity commands.
- Migrate existing Click options to Typer annotations in small steps (per command), running targeted tests after each change.
- Update integration tests and documentation to reference the new CLI.
- Remove legacy `cli/main.py` and Click entry point after the Typer CLI reaches full coverage.
