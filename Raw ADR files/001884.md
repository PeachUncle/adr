# ADR-0005: PostgreSQL Database Dual Deployment Strategy

> **Scope**: Document decision clusters, not individual technology choices. Group related decisions that work together (e.g., "Frontend Stack" not separate ADRs for framework, styling, deployment).

- **Status:** Accepted
- **Date:** 2025-12-12
- **Feature:** 001-task-crud-auth
- **Context:** Phase II requires a relational database for storing users and tasks with foreign key relationships, ACID compliance, and efficient querying. We need to choose a database system that works well with SQLModel ORM, supports local development with Docker, and can scale to production workloads. Additionally, we need a deployment strategy that provides environment parity (same schema in development and production) while optimizing for developer experience and production scalability.

## Decision

**PostgreSQL 16** as the database engine with **dual deployment strategy**:

**Local Development:**
- **Engine:** PostgreSQL 16 Docker container
- **Orchestration:** Docker Compose service (`db`)
- **Persistence:** Docker volume (`postgres_data`)
- **Connection:** `DATABASE_URL=postgresql://postgres:postgres@db:5432/tasks_db`

**Production:**
- **Engine:** Neon Serverless PostgreSQL (PostgreSQL 16 compatible)
- **Features:** Automatic scaling, built-in backups, database branching
- **Connection:** `DATABASE_URL=postgresql://user:pass@neon-host.neon.tech/tasks_db?sslmode=require`

**Environment Parity:**
- Same PostgreSQL 16 version in both environments
- Identical schema (users, tasks tables with relationships)
- Same Alembic migrations applied in both environments
- Only `DATABASE_URL` changes between development and production

**ORM Integration:**
- **SQLModel** for all database models (User, Task)
- **Alembic** for database migrations (version controlled)
- **Indexes:** Foreign keys (user_id), frequently queried fields (completed)

## Consequences

### Positive

- **Environment Parity:** Same PostgreSQL 16 version ensures identical behavior in development and production
- **ACID Compliance:** PostgreSQL transactions ensure data integrity (user deletion cascades to tasks)
- **Relational Model:** Foreign keys enforce referential integrity (tasks.user_id references users.id)
- **SQLModel Integration:** Excellent ORM support with Pydantic validation (type-safe models)
- **Fast Local Development:** Docker container starts in <5 seconds, no remote database latency
- **Production Scalability:** Neon provides automatic scaling, connection pooling, and serverless architecture
- **Built-in Features:** PostgreSQL JSON support, full-text search, advanced indexing (B-tree, GiN)
- **Cost-Effective:** Neon free tier sufficient for Phase II, pay-as-you-go for production
- **Database Branching:** Neon allows database branches (test migrations before applying to main)
- **Automatic Backups:** Neon provides point-in-time recovery (no manual backup setup)

### Negative

- **Neon Vendor Lock-In:** Production database tied to Neon service (though PostgreSQL itself is portable)
- **Neon Dependency:** Neon outage affects production (mitigated by their SLA and redundancy)
- **Cold Start Latency:** Neon serverless may have cold start delays (<100ms typically)
- **Connection Limits:** Neon free tier has connection limits (fixed by connection pooling)
- **Cost Uncertainty:** Neon pricing scales with usage (though predictable based on metrics)
- **Docker Overhead:** Local PostgreSQL container consumes ~100MB RAM (minimal impact)
- **Migration Complexity:** Alembic migrations must be tested in both environments before production

## Alternatives Considered

**Alternative A: MySQL/MariaDB**
- Docker (local) + AWS RDS MySQL (production)
- Why rejected:
  - Less robust JSON support than PostgreSQL
  - SQLModel optimized for PostgreSQL (better feature support)
  - Different SQL dialects between MySQL and PostgreSQL (migration complexity)
  - PostgreSQL has better full-text search and advanced indexing
- Tradeoffs: MySQL more widely deployed, but PostgreSQL better fit for SQLModel and modern features

**Alternative B: MongoDB (NoSQL)**
- Docker MongoDB (local) + MongoDB Atlas (production)
- Why rejected:
  - NoSQL doesn't fit relational data model (users ↔ tasks relationship)
  - Loses referential integrity (no foreign key constraints)
  - SQLModel is SQL-based (Pydantic + SQLAlchemy), incompatible with MongoDB
  - Phase II constitution requires relational database
- Tradeoffs: Flexible schema, horizontal scaling, but poor fit for relational data

**Alternative C: Supabase (PostgreSQL + Features)**
- Supabase (local) + Supabase (production)
- Why rejected:
  - Adds features we don't need (real-time subscriptions, auto-generated APIs, auth)
  - More complex than Neon (additional configuration and concepts)
  - Vendor lock-in to Supabase-specific features
  - Neon focused on database only (simpler, less coupling)
- Tradeoffs: More features, but increased complexity and scope creep

**Alternative D: AWS RDS PostgreSQL**
- Docker PostgreSQL (local) + AWS RDS PostgreSQL (production)
- Why rejected:
  - More expensive than Neon (always-on instances vs serverless)
  - Manual scaling (resize instances vs automatic scaling)
  - No database branching (Neon feature for testing migrations)
  - More complex setup (VPC, security groups, backup configuration)
- Tradeoffs: AWS ecosystem integration, but higher cost and manual management

**Alternative E: Single Neon Database (No Local Docker)**
- Neon for both development and production
- Why rejected:
  - Requires internet connection for all development (productivity blocked by outages)
  - Slower iteration (network latency affects every query)
  - Cost: Each developer would need separate Neon database
  - Docker Compose provides instant local database (no remote dependency)
- Tradeoffs: True environment parity, but dependent on internet and slower

**Why PostgreSQL + Dual Deployment Wins:**
- **Environment parity:** Same PostgreSQL 16 version in development and production
- **Local speed:** Docker PostgreSQL instant startup, zero latency
- **Production scalability:** Neon serverless automatic scaling
- **Cost-effective:** Docker free locally, Neon free tier for development/staging
- **SQLModel optimized:** PostgreSQL is SQLModel's primary target database
- **Feature-rich:** JSON support, full-text search, advanced indexing
- **Simple migration:** Change DATABASE_URL only to switch environments
