# Program Architecture

## Context and Problem Statement

Previously, the web was deployed in a local environment. However, a customer-imposed requirement mandates migrating the deployment to Amazon Web Services (AWS). This migration involves moving our web to a cloud-based infrastructure, maintaining the same components (Django, Kong and PostgreSQL) but adapting them to AWS-managed services.

In addition, it was necessary to merge the Django database and the Kong database into one, avoiding the need to manage separate database servers.

## Decision Drivers

- **Customer requirement**: Mandatory migration from local deployment to AWS.
- **Continuity of existing architecture**: Preserve the structure of a Django application behind an API Gateway (Kong) with a PostgreSQL database.
- **Reuse of current components**: Minimize changes during migration.

## Considered Options

- **Migrate the existing container-based architecture to AWS using ECS, Load Balancers, and a RDS database**:
  - Deploy Django and Kong in separate ECS clusters.
  - Use an AWS RDS instance as a shared database for both Django and Kong.
  - Use AWS Load Balancers (external and internal) to handle access and routing.
  - Keep all services within the same VPC for internal communication.

## Decision Outcome

The selected option was to migrate the system to AWS with the following setup:

- **Two ECS clusters**:
  - One cluster hosting the **Django web application**.
  - One cluster hosting **Kong (API Gateway)**.
    
    Each ECS cluster runs **two service instances** to ensure high availability and facilitate updates and failover.
- An **AWS RDS instance** serves as the shared database for both Django and Kong, eliminating the need to manage separate database containers or servers.
- An **external load balancer** exposes:
  - Port `8000` for Django web access through path `/polls/*`.
  - Port `8001` for Kong Admin API through path `/`.
  - Port `8003` for Kong Proxy (API access) through path `/api/*`.
- An **internal load balancer** facilitates the routing from Kong to Django inside the VPC. Kong routes API requests from `/api/v1/` on port `8003` to `/api/v1/` on Django’s port `8000` through the internal load balancer.

## Positive Consequences

- **Compliance with customer requirements**: The system is now deployed in AWS as mandated.
- **Simplified database management**: By using AWS RDS, both Django and Kong share a database, reducing maintenance overhead.
- **Preservation of architecture**: The same application and API Gateway structure is retained with minimal changes.
- **AWS benefits**: Automatic backups, failover options, and monitoring.

## Negative Consequences

- **Increased infrastructure complexity**: compared to local deployment, requiring knowledge of AWS ECS, RDS, and Load Balancers.
- **Higher operational costs**: associated with AWS services.
- **Potential learning curve**: it is not easy for a team to learn how to use AWS tools, as they are complex and not very intuitive.


## Annex I: AWS Architecture Description

The system is deployed entirely within an **AWS Virtual Private Cloud (VPC)** to ensure controlled and secure internal communication.

### Main components:

- **ECS Clusters**:
  - **ECS Cluster 1**: Hosts the **Django web application** with **two ECS service instances** for availability and update flexibility.
  - **ECS Cluster 2**: Hosts **Kong (API Gateway)** with **two ECS service instances** to ensure continuous API routing.

- **AWS RDS**:
  - A single **AWS RDS instance** (PostgreSQL) is used as the shared database for both:
    - The Django web application.
    - The Kong API Gateway (for storing its configuration and operational data).
  - This centralization removes the need for separate databases or volumes per container.

- **Load Balancers**:
  - **External Load Balancer** exposes:
    - Path `/polls/*` → Django Port `8000` → Django web interface .
    - Path `/` → Kong Port `8001` → Kong Admin API.
    - Path `/api/*` → Kong Port `8003` → Kong Proxy for external API requests.
  - **Internal Load Balancer**:
    - Used by Kong to route `/api/v1/` requests on port `8003` to Django’s `/api/v1/` endpoint on port `8000`.
    - Ensures that this internal routing remains confined within the VPC.

All traffic from Kong to Django passes through the **internal load balancer**, while client requests reach the system via the **external load balancer**.

This architecture preserves the functional design of the system while adapting it to an AWS infrastructure, reducing maintenance responsibilities while complying with the client’s requirements.
