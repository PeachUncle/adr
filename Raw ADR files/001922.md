# Adopting GitHub Flow Over Git Flow

* Status: accepted
* Deciders: Oihana Elizagoyen, Xabier Mikel Gutierrez and Aimar Uriarte
* Date: 2025/03/03

Technical Story: [Create quality ADRs #7](https://github.com/oihanaelizagoyen/GTIO/issues/7)

## Context and problem statement

We already have a branching strategy in place, Git Flow, but we are considering adopting GitHub Flow as it is simpler and more suitable for our project.

## Decision drivers

* **Simplicity & Agility** – GitHub Flow is simpler and allows for a more flexible workflow.
* **Continuous Deployment** – Our project benefits from frequent releases rather than structured versioning.
* **Reduced Merge Conflicts** – By working in smaller, short-lived branches, we avoid large integration issues.
* **Industry Best Practices** – Many modern teams adopt GitHub Flow for its efficiency in fast-paced development.

## Considered options

* **Continue with Git Flow** – Stick to the current model with develop/main and multiple supporting branches.
* **Adopt GitHub Flow** – Switch to a simpler branching strategy with main and feature branches only.
* **Hybrid Approach** – Use GitHub Flow for daily development but retain a long-lived develop branch for releases.

## Decision outcome

Chosen option: **Adopt GitHub Flow**

### Justification:

GitHub Flow was chosen because it simplifies our workflow by eliminating unnecessary branches. It aligns well with our CI/CD pipeline for fast releases, encourages frequent integrations and better collaboration, and reduces overhead and maintenance complexity. Its better for small teams and projects that require continuous deployment.

### Positive consequences

* Faster deployments and reduced friction in merging changes.
* Encourages continuous integration and smaller, manageable changes.
* Enhances code quality due to enforced pull request reviews.
* Reduces the risk of long-lived branches causing integration headaches.

### Negative consequences

* Less structured release management compared to Git Flow.
* Requires discipline in maintaining well-defined feature branches.
* May not be ideal for projects that require strict versioning policies.

## Pros and Cons of the Options

### Continue with Git Flow

* Good, because it is well-structured for projects with planned releases.
* Good, because it supports hotfixes and long-term maintenance.
* Bad, because it is more complex and slower in fast-paced environments.
* Bad, because it adds extra overhead with maintaining multiple branches.

### Adopt GitHub Flow

* Good, because it is simple and effective for continuous integration.
* Good, because it encourages faster releases and better collaboration.
* Bad, because it requires discipline to manage direct commits to `main`.
* Bad, because it is less suited for teams with strict release cycles.

### Hybrid Approach

* Good, because it keeps some structure while enabling fast feature releases.
* Good, because it allows gradual transition from Git Flow to GitHub Flow.
* Bad, because it still adds some complexity compared to pure GitHub Flow.
* Bad, because it could cause confusion if not properly defined.
