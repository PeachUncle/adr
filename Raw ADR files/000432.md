# ADR-002: Cost-Aware Traffic Governance for LLM APIs

**Status**: Accepted
**Date**: December 2024
**Author**: Vincent
**Implementation**: [Atlas](https://github.com/BugVanquisher/Atlas) + [Hyperion](https://github.com/BugVanquisher/Hyperion)

---

## Context

LLM inference is expensive. At scale, uncontrolled API usage can result in:
- Runaway costs (single user exhausting GPU budget)
- Resource starvation (batch jobs blocking real-time users)
- Unfair resource allocation across tenants

### The Challenge

Traditional rate limiting (requests/second) doesn't work well for LLMs:
- A 10-token request costs ~$0.0001
- A 4000-token request costs ~$0.12 (1200x more)
- Both count as "1 request" in naive rate limiting

### Requirements

From Vertex AI Provisioned Throughput experience:
- Need token-level accounting, not just request counting
- Different users have different priority needs
- Burst capacity matters (batch jobs vs. real-time)
- Cost attribution for chargeback/showback

---

## Decision

**Implement a multi-dimensional quota system with priority-aware routing:**

```
┌────────────────────────────────────────────────────────────┐
│              ATLAS TRAFFIC GOVERNANCE                      │
├────────────────────────────────────────────────────────────┤
│  LAYER 1: Rate Limiting                                    │
│  ├── QPS limit (requests/second)                           │
│  ├── Burst allowance (token bucket)                        │
│  └── Per-IP limits (DDoS protection)                       │
├────────────────────────────────────────────────────────────┤
│  LAYER 2: Quota Management                                 │
│  ├── Daily token quota per API key                         │
│  ├── Monthly token quota                                   │
│  └── Priority-based reservation pools                      │
├────────────────────────────────────────────────────────────┤
│  LAYER 3: Intelligent Routing                              │
│  ├── Request complexity estimation                         │
│  ├── Model selection (small vs. large)                     │
│  └── Batch grouping by parameters                          │
└────────────────────────────────────────────────────────────┘
```

## Implementation in Atlas

### Token-Based Quota System

```python
# atlas/gateway/quota.py

class QuotaManager:
    """
    Token-based quota management with intelligent reservations.

    Design Decision: Pre-reserve tokens for streaming requests
    - Problem: Don't know final token count until stream ends
    - Solution: Reserve estimated tokens upfront, refund unused
    - Trade-off: May temporarily over-count, but never under-count
    """

    def __init__(self, redis_client):
        self.redis = redis_client

    async def check_and_reserve(
        self,
        api_key: str,
        estimated_tokens: int,
        priority: str = "normal"
    ) -> QuotaResult:
        """
        Check quota and reserve tokens atomically.

        Priority affects reservation pool:
        - critical: 30% of daily limit reserved
        - high: 20% reserved
        - normal: 10% reserved
        - low: 5% reserved (may be preempted)
        """
        async with self.redis.pipeline() as pipe:
            # Get current usage
            daily_key = f"quota:{api_key}:daily:{today()}"
            monthly_key = f"quota:{api_key}:monthly:{this_month()}"

            daily_used = await pipe.get(daily_key) or 0
            monthly_used = await pipe.get(monthly_key) or 0

            limits = await self._get_limits(api_key)

            # Check against priority-adjusted limits
            effective_daily = limits.daily * self._priority_factor(priority)
            effective_monthly = limits.monthly * self._priority_factor(priority)

            if daily_used + estimated_tokens > effective_daily:
                return QuotaResult(
                    allowed=False,
                    reason="daily_quota_exceeded",
                    current=daily_used,
                    limit=effective_daily
                )

            if monthly_used + estimated_tokens > effective_monthly:
                return QuotaResult(
                    allowed=False,
                    reason="monthly_quota_exceeded",
                    current=monthly_used,
                    limit=effective_monthly
                )

            # Reserve tokens
            await pipe.incrby(daily_key, estimated_tokens)
            await pipe.incrby(monthly_key, estimated_tokens)
            await pipe.execute()

            return QuotaResult(
                allowed=True,
                reserved=estimated_tokens,
                reservation_id=self._generate_reservation_id()
            )

    async def refund(self, api_key: str, reservation_id: str, actual_tokens: int):
        """
        Refund unused tokens after request completes.

        Called when:
        - Streaming request ends (refund reserved - actual)
        - Request fails (refund full reservation)
        - Request cancelled (refund full reservation)
        """
        reservation = await self._get_reservation(reservation_id)
        if not reservation:
            return

        refund_amount = reservation.reserved - actual_tokens
        if refund_amount > 0:
            await self.redis.decrby(f"quota:{api_key}:daily:{today()}", refund_amount)
            await self.redis.decrby(f"quota:{api_key}:monthly:{this_month()}", refund_amount)

            # Track refunds for analytics
            await self._record_refund(api_key, refund_amount, reservation.priority)
```

### Priority-Based Rate Limiting

```python
# atlas/gateway/rate_limiter.py

class PriorityRateLimiter:
    """
    Token bucket rate limiter with priority queues.

    Design Decision: Separate buckets per priority
    - critical: Always allowed (up to QPS limit)
    - high: 80% of burst capacity
    - normal: 50% of burst capacity
    - low: 20% of burst capacity, shed first under load
    """

    def __init__(self, qps: float, burst: int):
        self.qps = qps
        self.burst = burst
        self.buckets = {
            "critical": TokenBucket(qps, burst),
            "high": TokenBucket(qps * 0.8, int(burst * 0.8)),
            "normal": TokenBucket(qps * 0.5, int(burst * 0.5)),
            "low": TokenBucket(qps * 0.2, int(burst * 0.2)),
        }

    async def acquire(self, api_key: str, priority: str) -> RateLimitResult:
        bucket = self.buckets.get(priority, self.buckets["normal"])

        if bucket.try_acquire():
            return RateLimitResult(allowed=True)

        # Check if higher priority bucket has capacity (spillover)
        if priority in ["normal", "low"]:
            for higher in ["critical", "high"]:
                if self.buckets[higher].try_acquire():
                    return RateLimitResult(allowed=True, spillover=True)

        return RateLimitResult(
            allowed=False,
            retry_after=bucket.time_to_refill(),
            reason=f"rate_limited_{priority}"
        )
```

## Implementation in Hyperion

### Cost-Optimized Batching

```python
# hyperion/batching.py

class IntelligentBatcher:
    """
    Batch requests to maximize GPU utilization and minimize cost.

    Design Decision: Parameter-aware batching
    - Only batch requests with compatible parameters
    - Different max_tokens = different compute time
    - Different temperatures = incompatible generations

    Trade-off: Smaller batches vs. compatibility
    Observed: 2.8 requests/batch average (good balance)
    """

    def __init__(self, batch_size: int = 8, max_wait_ms: int = 50):
        self.batch_size = batch_size
        self.max_wait_ms = max_wait_ms
        self.queues: Dict[str, asyncio.Queue] = {}

    def _get_batch_key(self, request: InferenceRequest) -> str:
        """
        Group compatible requests together.

        Compatible = same model + similar max_tokens + same temperature
        """
        token_bucket = (request.max_tokens // 100) * 100  # Round to 100s
        return f"{request.model}:{token_bucket}:{request.temperature}"

    async def add_request(self, request: InferenceRequest) -> InferenceResponse:
        batch_key = self._get_batch_key(request)

        if batch_key not in self.queues:
            self.queues[batch_key] = asyncio.Queue()
            asyncio.create_task(self._process_batch(batch_key))

        future = asyncio.Future()
        await self.queues[batch_key].put((request, future))

        return await future

    async def _process_batch(self, batch_key: str):
        """
        Collect requests until batch_size or max_wait_ms.
        """
        queue = self.queues[batch_key]
        batch = []

        deadline = time.time() + (self.max_wait_ms / 1000)

        while len(batch) < self.batch_size:
            try:
                timeout = max(0, deadline - time.time())
                request, future = await asyncio.wait_for(
                    queue.get(),
                    timeout=timeout
                )
                batch.append((request, future))
            except asyncio.TimeoutError:
                break

        if batch:
            # Execute batch inference
            responses = await self._execute_batch([r for r, _ in batch])

            # Distribute responses
            for (request, future), response in zip(batch, responses):
                future.set_result(response)
```

### Model Selection Based on Complexity

```python
# hyperion/routing.py

class CostAwareRouter:
    """
    Route requests to appropriate model based on complexity.

    Design Decision: Estimate complexity, route to smallest capable model
    - Simple queries (< 50 words, simple intent): Small model
    - Medium queries: Medium model
    - Complex queries (multi-step reasoning): Large model

    Cost savings: 30-40% observed in production
    """

    def __init__(self):
        self.models = {
            "small": {"name": "llama-7b", "cost_per_1k": 0.001},
            "medium": {"name": "llama-13b", "cost_per_1k": 0.003},
            "large": {"name": "llama-70b", "cost_per_1k": 0.015},
        }
        self.complexity_classifier = self._load_classifier()

    def select_model(self, request: InferenceRequest) -> str:
        """
        Select model based on request complexity.
        """
        # User can override
        if request.model_hint:
            return request.model_hint

        # Estimate complexity
        complexity = self.complexity_classifier.predict(request.prompt)

        if complexity < 0.3:
            return "small"
        elif complexity < 0.7:
            return "medium"
        else:
            return "large"
```

## Traffic Forecasting (Atlas v0.2.5)

```python
# atlas/forecasting/predictor.py

class UsagePredictor:
    """
    Predict future usage for capacity planning.

    Why forecasting?
    - Proactive quota warnings before hitting limits
    - Capacity recommendations for scaling
    - Cost projections for budgeting
    """

    async def get_forecast(self, api_key: str, days_ahead: int = 7) -> Forecast:
        """
        Predict usage based on historical patterns.
        """
        history = await self._get_usage_history(api_key, days_back=30)

        # Detect patterns
        daily_pattern = self._detect_daily_pattern(history)
        weekly_pattern = self._detect_weekly_pattern(history)
        trend = self._detect_trend(history)

        # Project forward
        projections = []
        for day in range(days_ahead):
            base = history[-1].usage * (1 + trend * day)
            daily_factor = daily_pattern[day % 7]
            projected = base * daily_factor

            projections.append(DailyProjection(
                date=today() + timedelta(days=day),
                projected_usage=projected,
                confidence_interval=(projected * 0.8, projected * 1.2)
            ))

        return Forecast(
            projections=projections,
            peak_expected=max(p.projected_usage for p in projections),
            capacity_recommendation=self._recommend_capacity(projections)
        )
```

## Consequences

### Benefits

1. **Fair Resource Allocation**: Token-based quotas reflect actual cost
2. **Priority Handling**: Critical requests always get through
3. **Cost Reduction**: 30-40% savings from intelligent routing
4. **Predictability**: Users know their limits and can plan
5. **Observability**: Full visibility into usage patterns

### Trade-offs

1. **Complexity**: Token counting more complex than request counting
   - Mitigation: Abstract behind simple API
   - Benefit: More accurate cost attribution

2. **Reservation Overhead**: Pre-reserving may temporarily over-count
   - Mitigation: Prompt refunds, trailing average for estimates
   - Observed impact: <5% over-counting

3. **Batching Latency**: Waiting for batch adds 20-50ms
   - Mitigation: Configurable max_wait_ms
   - Trade-off: 3x throughput increase worth small latency

### Metrics from Production

| Metric | Value |
|--------|-------|
| Cost reduction (routing) | 34% |
| Throughput increase (batching) | 3.2x |
| Quota accuracy | 97% |
| P99 additional latency | 35ms |
| Reservation refund rate | 23% |

## Alternatives Considered

### 1. Request-Based Quotas Only

**Rejected because**:
- 100-token request = 4000-token request (unfair)
- No cost correlation
- Easy to game (many small requests)

### 2. No Priority System

**Rejected because**:
- Batch jobs could block real-time users
- No way to handle critical requests during overload
- All-or-nothing rate limiting

### 3. Static Model Assignment

**Rejected because**:
- Overprovisioning (always use large model)
- Underprovisioning (always use small model, quality issues)
- No cost optimization
