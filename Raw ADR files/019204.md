# ADR-007: PostgreSQL with PostGIS

## Status

Accepted

## Context

The Trama platform's core feature is **proximity-based artist search** - users need to find artists within a specific radius (e.g., "tattoo artists within 10km of my location"). This requires:

- **Geospatial Queries**: Calculate distances between coordinates, find points within radius
- **Performance**: Fast queries even with thousands of artists
- **Accuracy**: Proper handling of Earth's curvature (not flat plane calculations)
- **Indexing**: Efficient spatial indexes for large datasets
- **Standard Compliance**: Use industry-standard geospatial data types

## Decision

We will use **PostgreSQL 17 with PostGIS 3.5 extension** as our primary database:

**PostgreSQL 17:**
- Open-source relational database
- Strong ACID compliance
- Excellent performance and scalability
- Rich feature set (JSONB, full-text search, CTEs, window functions)
- Mature .NET support via Npgsql and EF Core

**PostGIS 3.5:**
- Industry-standard geospatial extension for PostgreSQL
- Implements OGC (Open Geospatial Consortium) standards
- Provides geometry and geography types
- Includes spatial functions (distance, within, intersects, etc.)
- Supports spatial indexes (GIST, BRIN)

**Why Geography Type:**
- Uses spherical calculations (accounts for Earth's curvature)
- Distances in meters (intuitive)
- Coordinates in longitude/latitude (WGS84 standard)
- More accurate for proximity search than geometry type

## Consequences

### Positive

- **Accurate Geospatial Queries**: PostGIS handles Earth's curvature correctly (not flat plane)
- **High Performance**: GIST indexes enable fast spatial queries even with large datasets
- **Standard Compliance**: Uses OGC standards, making data portable
- **Rich Spatial Functions**: Distance, within, intersects, buffer, and 100+ more functions
- **Proven Technology**: PostGIS is battle-tested in production systems worldwide
- **Learning Value**: Gain experience with geospatial databases and queries
- **PostgreSQL Features**: Access to JSONB, full-text search, CTEs, window functions
- **Strong .NET Support**: Npgsql and EF Core have excellent PostgreSQL/PostGIS integration
- **Open Source**: No licensing costs, active community support
- **Future Flexibility**: Can add more complex spatial features (polygons, routes, etc.)

### Negative

- **PostgreSQL-Specific**: Locks us into PostgreSQL (can't easily switch to MySQL/SQL Server)
- **Learning Curve**: Team must learn PostGIS functions and spatial concepts
- **Deployment Complexity**: Requires PostGIS extension installation (not just PostgreSQL)
- **Query Complexity**: Spatial queries are more complex than simple WHERE clauses
- **Index Maintenance**: GIST indexes require more maintenance than B-tree indexes
- **Data Migration**: Migrating spatial data between databases is more complex
- **Debugging Difficulty**: Spatial queries are harder to debug and visualize
- **Limited GUI Tools**: Fewer tools support PostGIS compared to standard SQL

### Neutral

- **Geography vs Geometry**: Using geography type (spherical) instead of geometry (planar)
- **SRID 4326**: Using WGS84 coordinate system (standard for GPS)
- **Distance Units**: All distances in meters (requires conversion for miles/km display)
- **Index Type**: GIST indexes are larger than B-tree but necessary for spatial queries
- **Query Performance**: Spatial queries are slower than simple equality checks but acceptable

## Implementation Notes

**Performance Considerations:**
- GIST indexes are essential for spatial queries (10-100x speedup)
- Use `ST_DWithin` instead of `ST_Distance < radius` (uses index)
- Geography type is slower than geometry but more accurate
- Consider geometry type for very large datasets (if accuracy trade-off acceptable)

## Alternatives Considered

**MySQL with Spatial Extensions:**
- Pros: Widely known, good performance, spatial support
- Cons: Less mature spatial features, fewer functions than PostGIS, weaker JSONB support
- Rejected: PostGIS is more feature-rich and better documented

**SQL Server with Spatial Types:**
- Pros: Enterprise support, good .NET integration, spatial types
- Cons: Licensing costs, less mature spatial features than PostGIS, Linux support limited
- Rejected: Prefer open-source solution

**MongoDB with Geospatial Indexes:**
- Pros: Native geospatial support, flexible schema, good performance
- Cons: No ACID transactions, weaker relational model, less mature for complex queries
- Rejected: Need strong relational model for user/artist/artwork relationships

**Elasticsearch with Geo Queries:**
- Pros: Excellent search performance, good geospatial support
- Cons: Not a primary database, eventual consistency, operational complexity
- Rejected: Overkill for MVP, can add later for search optimization

**Custom Distance Calculation (Haversine Formula):**
- Pros: No special database required, works with any SQL database
- Cons: Slow without spatial indexes, complex queries, reinventing the wheel
- Rejected: PostGIS provides better performance and more features

**SQLite with SpatiaLite:**
- Pros: Lightweight, no server required, spatial support
- Cons: Limited concurrency, not suitable for production, fewer features
- Rejected: Need production-grade database with better concurrency
