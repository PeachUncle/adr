# ADR 002: Microservices Boundaries

## Status
Accepted

## Context

The ASDEFCON platform requires decomposition into independently deployable services. We need to determine:
- How to split the system into services
- What each service's bounded context contains
- How services communicate
- How to maintain data consistency

Key requirements:
- Independent deployment to Railway
- Independent scaling based on load
- Team autonomy
- Clear ownership
- Minimal inter-service coupling

## Decision

We will implement **five independent microservices** based on bounded contexts:

### 1. Document Service

**Bounded Context**: Document management and AI analysis

**Responsibilities**:
- Upload and storage of source documents (FPS, OCD, specs, ILS plans)
- Document parsing and text extraction
- AI-powered requirement analysis
- Deliverable extraction
- Contract classification
- Document metadata management

**Domain Entities**:
- Document (aggregate root)
- Requirement
- Deliverable
- AnalysisResult
- DocumentMetadata

**External Dependencies**:
- Anthropic API (Claude)
- S3 storage
- Vector database (semantic search)

**API Endpoints**:
- `POST /api/v1/documents` - Upload document
- `GET /api/v1/documents/{id}` - Retrieve document
- `POST /api/v1/documents/{id}/analyze` - Trigger AI analysis
- `GET /api/v1/documents/{id}/requirements` - Get extracted requirements

### 2. Clause Service

**Bounded Context**: Clause library and recommendations

**Responsibilities**:
- Clause library management
- Clause search and filtering
- Dependency resolution
- AI-powered clause recommendations
- Template management (ASDEFCON versions)
- Clause categorization

**Domain Entities**:
- Clause (aggregate root)
- ClauseDependency
- Template
- Recommendation
- ClauseCategory

**External Dependencies**:
- Anthropic API (recommendations)
- Vector database (semantic search)

**API Endpoints**:
- `GET /api/v1/clauses` - List/search clauses
- `POST /api/v1/clauses` - Create clause
- `GET /api/v1/clauses/{id}/dependencies` - Get dependencies
- `POST /api/v1/clauses/recommend` - Get AI recommendations

### 3. Compliance Service

**Bounded Context**: Rules engine and validation

**Responsibilities**:
- Compliance rules management
- Contract validation
- Rule execution
- Audit trail recording
- Classification validation
- Threshold checks

**Domain Entities**:
- Rule (aggregate root)
- ValidationResult
- AuditTrail
- ComplianceCheck

**External Dependencies**:
- Document Service (read-only)
- Clause Service (read-only)

**API Endpoints**:
- `POST /api/v1/validate` - Validate contract
- `GET /api/v1/rules` - List rules
- `GET /api/v1/audit-trail/{contract_id}` - Get audit history

### 4. Collaboration Service

**Bounded Context**: Comments, reviews, and workflows

**Responsibilities**:
- Comment threads
- Review cycles
- Approval workflows
- User notifications
- Real-time updates
- Activity feed

**Domain Entities**:
- Comment (aggregate root)
- Review
- Workflow
- Notification

**External Dependencies**:
- RabbitMQ (event bus)
- Redis (real-time state)
- WebSocket (future)

**API Endpoints**:
- `POST /api/v1/comments` - Create comment
- `GET /api/v1/contracts/{id}/comments` - List comments
- `POST /api/v1/reviews` - Create review
- `GET /api/v1/workflows/{id}` - Get workflow status

### 5. Export Service

**Bounded Context**: Document generation

**Responsibilities**:
- Word document generation
- ASDEFCON template formatting
- PDF export
- Contract packaging
- Version control
- Export history

**Domain Entities**:
- ContractDocument (aggregate root)
- ExportJob
- Template
- ExportHistory

**External Dependencies**:
- S3 storage
- Document Service (read-only)
- Clause Service (read-only)
- python-docx library

**API Endpoints**:
- `POST /api/v1/exports` - Generate document
- `GET /api/v1/exports/{id}` - Download export
- `GET /api/v1/exports/{id}/status` - Check export status

## Service Communication

### Synchronous (REST)

- Frontend → All services
- Compliance Service → Document Service (read)
- Compliance Service → Clause Service (read)
- Export Service → Document Service (read)
- Export Service → Clause Service (read)

### Asynchronous (Message Bus)

- Document analyzed → Compliance Service
- Contract created → Collaboration Service
- Review completed → Export Service

### Data Ownership

Each service owns its data exclusively:
- No direct database access between services
- Communication via APIs only
- Eventual consistency acceptable
- Event-driven for cross-service updates

## Database Strategy

**Option 1**: Schemas per service (chosen)
- Single PostgreSQL database
- Schema per service (document_schema, clause_schema, etc.)
- Better for development
- Easier migrations
- Lower cost on Railway

**Option 2**: Database per service
- Complete isolation
- Independent scaling
- Higher operational complexity
- Higher cost

## Deployment

Each service:
- Independent Railway deployment
- Own environment variables
- Own health checks
- Own scaling configuration
- Independent CI/CD pipeline

## Consequences

### Positive

- **Independent Deployment**: Deploy document-service without touching others
- **Independent Scaling**: Scale export-service during heavy generation load
- **Team Autonomy**: Teams own entire service lifecycle
- **Fault Isolation**: Export service failure doesn't affect document analysis
- **Technology Flexibility**: Could use different tech for export if needed
- **Clear Ownership**: No ambiguity about who owns what

### Negative

- **Network Latency**: HTTP calls between services slower than in-process
- **Eventual Consistency**: Must handle async updates
- **Operational Complexity**: 5 services to monitor vs 1
- **Data Duplication**: Some data cached/replicated
- **Transaction Boundaries**: No distributed transactions
- **Development Overhead**: Must run multiple services locally

### Mitigations

- Docker Compose for local development
- Shared infrastructure components (logging, monitoring)
- Circuit breakers for resilience
- Comprehensive API contracts (OpenAPI)
- Local caching to reduce inter-service calls
- Event sourcing for audit requirements

## Alternative Considered

### Modular Monolith

**Rejected because**:
- Harder to scale specific components
- Deployment coupling
- Team coupling
- Railway's architecture optimized for microservices
- Future: different teams may own services

### More Fine-Grained Services

**Rejected because**:
- Too much operational overhead for team size
- Over-engineered for current requirements
- Can split later if needed

## Migration Path

If we need to merge services later:
1. Services already have clean boundaries
2. Move code between repos
3. Combine databases
4. Update API calls to in-process calls
5. Minimal business logic changes
