# ADR-003: Migrate from NutDB (MySQL) to PostgreSQL

**Date**: 2022-11-01 (Updated: 2024-10-01)
**Status**: ⚠️ In Progress (for 2 years)
**Author**: Marcus Chen
**Reviewers**: Sarah Chen, The entire engineering team at various points

## Context

We have two databases:
1. **PostgreSQL (Aurora)**: Primary database for new systems
2. **NutDB (MySQL 5.5)**: Legacy database from WordPress era

NutDB contains:
- Historical orders (2019-2022): ~450K records
- Historical users: ~89K records  
- Product data (synced bidirectionally): ~200 products
- Mystery tables nobody understands: ~23

NutDB is:
- Running on an m4.large EC2 instance
- Backed up "manually" (Chester's nephew does it monthly)
- Connected to by NutTracker, legacy-bridge, and 4 unknown IP addresses
- A security risk (MySQL 5.5 is EOL)

## Decision

We will migrate all data from NutDB to PostgreSQL and decommission NutDB.

## Migration Plan

### Phase 1: User Data ✅ COMPLETE (2023-04)
- Migrated users table
- Password rehashing during migration
- Dual-write period: 3 months

### Phase 2: Product Data ✅ COMPLETE (2023-07)
- Products fully in PostgreSQL
- legacy-bridge syncs back to NutDB for NutTracker

### Phase 3: Order Data ⚠️ IN PROGRESS
- Historical orders need migration
- Complex due to different schema structures
- Finance needs this data for audits

**Blockers**:
- NutDB `orders.status` is INTEGER, PostgreSQL is ENUM. Mapping is unclear.
- NutDB has orders with `user_id` referencing deleted users (orphans)
- Tax data format changed 3 times

### Phase 4: NutTracker Dependency 🚫 NOT STARTED
- Can't decommission NutDB until NutTracker is replaced
- See ADR-012

### Phase 5: Decommission 🚫 NOT STARTED
- Shut down NutDB
- Archive final backup
- Redirect all queries to PostgreSQL
- Party 🎉

## Consequences

### Why This Is Taking So Long

1. **NutTracker**: Every migration attempt breaks NutTracker. We can't break NutTracker (orders don't ship).

2. **Schema Archaeology**: Nobody documented the original schema. We're reverse-engineering from PHP code.

3. **Priority Shifts**: Every quarter, something else becomes more urgent.

4. **Data Quality**: NutDB has:
   - 847 orders with status "7" (what is 7?)
   - 23 products with negative prices
   - A user with email "test@test.test" who has 1,200 orders

### Risks

1. **Security**: MySQL 5.5 hasn't received security updates since 2020
2. **Compliance**: Auditors are starting to ask questions
3. **Cost**: Running two databases is expensive
4. **Complexity**: Every new feature needs to consider both DBs

## Current Workarounds

- `legacy-bridge` service handles dual-writes
- Nightly sync job copies PostgreSQL changes to NutDB
- Manual reconciliation monthly (Sarah does this, bless her)

## What We Need to Finish

1. [ ] Map all NutDB status codes to PostgreSQL enums
2. [ ] Handle orphaned orders (decision needed: delete or create placeholder users?)
3. [ ] Export final financial data for compliance
4. [ ] Replace NutTracker (ADR-012)
5. [ ] Actually turn off NutDB without Chester panicking

## Lessons Learned

- Don't let databases live beyond their usefulness
- Document EVERYTHING
- "We'll migrate later" means "We'll never migrate"
- Chester's nephew is not a backup strategy
