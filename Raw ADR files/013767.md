# ADR-0002: Use InboxItem as the Unified Brain Dump / Capture Model

## Status
Accepted

## Date
2025-12-17

## Context
The application introduces a "brain dump" feature that allows users to quickly
enter unstructured thoughts, reminders, ideas, or tasks without immediately
deciding where they belong.

Initially, the feature was conceived primarily for idea capture, with AI used
to suggest whether an entry should become a task or a new project. Further
consideration revealed that:

- Not all captured input is an "idea"
- Some entries are reminders or tasks
- Some entries may originate from multiple sources in the future
  (manual input, quick-add actions, automation, or AI suggestions)
- All such inputs share a common need: they must be **processed later**

This reframed the feature from "idea capture" to a **universal intake inbox**.

## Decision
We will create a model named **`InboxItem`** to represent any unprocessed user
input awaiting triage.

All "brain dumps," quick captures, and future intake mechanisms will create
`InboxItem` records, which are later processed into tasks, projects, or other
structured entities.

## Rationale
- `InboxItem` aligns with well-established GTD and inbox-based workflows
- It accurately represents the lifecycle: capture → process → organize
- It does not assume what the content is or what it will become
- It remains neutral across:
  - ideas
  - reminders
  - tasks
  - vague or incomplete thoughts
- It supports the realization that **tasks may also be added to the inbox**
  before being fully classified
- It provides a stable, first-class domain concept rather than an ephemeral
  funnel or UI-only construct

While names like `Idea` or `BrainDump` describe subsets of the data, `InboxItem`
truthfully represents the broader role this model plays in the system.

## Alternatives Considered

### Capture
Strongly considered.

Pros:
- Single-word model name
- GTD-aligned terminology (capture → process → organize)
- Neutral and flexible

Cons:
- Verb-derived noun is less immediately clear in code and queries
- Slightly more abstract than the concrete "inbox" mental model
- Less explicit about lifecycle state (unprocessed vs processed)

Ultimately, `InboxItem` was chosen for clarity and semantic precision.

### Idea
Rejected.
- Not all inbox entries are ideas
- Some entries are reminders or tasks
- Overly narrow for the expanded scope

### BrainDump
Rejected.
- Informal
- Better suited for UI language than a domain model
- Lacks clarity in analytics and APIs

## Consequences
- All unstructured user input enters the system as an `InboxItem`
- Inbox items may later be:
  - converted into tasks
  - used to create new projects
  - linked to existing projects
  - archived or discarded
- AI is used to **suggest** classification, not to perform irreversible actions
- The inbox becomes a durable staging area rather than an ephemeral funnel

This approach avoids premature specialization and supports future features such
as:
- reviewing unprocessed inbox items
- tracking conversion rates
- AI-assisted triage improvements
- additional intake sources

## Schema
```
inbox_items
- id
- content (text)
- status (pending, processed, archived)
- ai_suggestion (json, nullable)
- timestamps

projects.inbox_item_id (nullable FK) - traceability
tasks.inbox_item_id (nullable FK) - traceability
```

## Design Principle
Treat **raw human input as a first-class domain object** and delay classification
until sufficient context and user intent are available.
