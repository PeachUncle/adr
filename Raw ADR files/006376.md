# ADR-002: Use Supabase for Backend-as-a-Service

**Status**: Accepted

**Date**: 2024-09-20

**Deciders**: Development Team

**Tags**: backend, database, authentication, infrastructure

## Context

ParentLog requires several backend services:

1. **Database**: PostgreSQL for storing messages, user profiles, families
2. **Authentication**: User signup, login, session management
3. **Real-time updates**: Push message updates to connected clients
4. **File storage**: (Future) Store media attachments
5. **API layer**: RESTful API for database queries

As a solo developer building an MVP, we need to minimize infrastructure management while maintaining flexibility and avoiding vendor lock-in where possible.

## Decision

We will use **Supabase** (https://supabase.com) as our Backend-as-a-Service platform, providing PostgreSQL database, authentication, real-time subscriptions, and storage in a single platform.

## Alternatives Considered

### Option 1: Firebase
**Pros:**
- Generous free tier
- Excellent real-time database
- Simple authentication
- Google-backed reliability

**Cons:**
- NoSQL (Firestore) requires different data modeling
- Less flexible querying than SQL
- Vendor lock-in (proprietary database)
- No PostgreSQL experience transfer
- Complex offline/online sync

### Option 2: Supabase (Chosen)
**Pros:**
- PostgreSQL (standard SQL, no vendor lock-in)
- Row Level Security for data isolation
- Built-in authentication (email, OAuth, magic links)
- Real-time subscriptions via WebSocket
- PostgREST API (auto-generated from schema)
- Generous free tier (500MB database, 50K monthly active users)
- Open-source (can self-host if needed)
- TypeScript client with excellent DX

**Cons:**
- Relatively new platform (less mature than Firebase)
- Smaller ecosystem and community
- Real-time can be finicky with RLS policies
- Need to learn PostgreSQL RLS concepts

### Option 3: Custom Backend (Node.js + PostgreSQL + Auth0)
**Pros:**
- Full control over infrastructure
- No platform lock-in
- Can optimize exactly for our use case

**Cons:**
- Significant development time (weeks vs. hours)
- Must manage authentication security
- Real-time implementation complexity
- Database hosting and management
- Ops overhead (backups, scaling, monitoring)
- Higher costs (separate services for DB, auth, hosting)

### Option 4: AWS Amplify
**Pros:**
- Full AWS ecosystem integration
- GraphQL API generation
- Enterprise-grade infrastructure

**Cons:**
- Complex setup and configuration
- DynamoDB default (NoSQL)
- Expensive at scale
- Steeper learning curve
- Over-engineered for MVP

## Consequences

### Positive
- **Fast development**: Auth + DB + Realtime in one platform
- **Row Level Security**: Built-in multi-tenancy and data isolation
- **PostgreSQL**: Standard SQL, portable, can export data
- **TypeScript client**: Excellent IDE autocomplete and type safety
- **Free tier**: No costs during MVP phase
- **Dashboard**: Easy database inspection and management
- **Auto-generated API**: PostgREST creates REST API from schema
- **Real-time**: WebSocket subscriptions with minimal code
- **Open-source**: Can self-host if needed (exit strategy)

### Negative
- **RLS complexity**: Learning curve for Row Level Security policies
- **Platform dependency**: Some vendor lock-in (though mitigated by PostgreSQL)
- **Real-time limitations**: Some edge cases with RLS + real-time subscriptions
- **Community size**: Smaller community than Firebase for troubleshooting
- **Service role pattern**: Need to understand when to bypass RLS (admin operations)

### Neutral
- **PostgreSQL knowledge**: Transferable to other PostgreSQL hosting
- **Pricing**: Free tier sufficient for MVP, paid tier reasonable for growth
- **Documentation**: Good but still evolving

## Implementation Details

**Key Supabase Features Used:**

1. **PostgreSQL Database**
   - Custom schema with tables for families, messages, profiles
   - Indexes for performance
   - Foreign key constraints for data integrity

2. **Row Level Security (RLS)**
   - Family-based isolation (users see only their family's data)
   - Service role for admin operations (invitations)
   - Policy-based access control

3. **Supabase Auth**
   - Email/password authentication
   - Email verification
   - JWT tokens in httpOnly cookies
   - Automatic token refresh

4. **Real-time Subscriptions**
   - WebSocket subscriptions to message table
   - Filtered by family_account_id
   - Instant timeline updates

5. **PostgREST API**
   - Auto-generated REST API from schema
   - Filter, sort, pagination built-in
   - Works seamlessly with RLS

**Client Types:**

- **Browser Client**: RLS-enforced queries (user data only)
- **Server Client**: Server-side queries with user context
- **Service Role Client**: Admin queries bypassing RLS

## Notes

**Migration Path:**
If we outgrow Supabase or need to self-host:
1. Export PostgreSQL database (standard pg_dump)
2. Deploy PostgreSQL to any hosting provider
3. Replace Supabase Auth with alternative (Clerk, Auth0, custom)
4. Replace real-time with alternative (Pusher, custom WebSocket)

**Free Tier Limits:**
- 500MB database storage
- 50,000 monthly active users
- 2GB file storage
- 50GB bandwidth
