# ADR-003: Multi-Raft over Single-Raft

**Status**: Accepted  
**Date**: 2025-10-31  
**Deciders**: Core Team

## Context

Raft consensus ensures data replication and fault tolerance. Two architectures:
1. **Single Raft**: One Raft group for entire cluster
2. **Multi-Raft**: Multiple Raft groups, one per data range

## Decision

Use **Multi-Raft** (one Raft group per range).

## Rationale

### Multi-Raft Advantages

1. **Horizontal Scalability**
   - Each range is independent
   - Different ranges can have different leaders
   - Parallelizes consensus across ranges
   - Add nodes → add Raft groups

2. **Load Distribution**
   - Hot range → different leader than cold range
   - Avoids single leader bottleneck
   - Better CPU/network utilization

3. **Fault Isolation**
   - Leader failure in Range-1 doesn't affect Range-2
   - Elections are per-range (faster recovery)
   - Reduced blast radius

4. **Geo-Placement**
   - Different ranges can have different replica locations
   - EU data → EU replicas
   - US data → US replicas
   - Lower latency for regional workloads

### Single Raft Disadvantages
- ❌ Single leader bottleneck (all writes go through one node)
- ❌ Leader election affects entire cluster
- ❌ Cannot distribute load across nodes
- ❌ No geo-placement flexibility

## Architecture

### Range Definition
```rust
struct Range {
    id: RangeId,
    start_key: Key,
    end_key: Key,
    replicas: Vec<Replica>,
    leaseholder: NodeId,
}
```

### Raft Group per Range
- Range-1: Raft Group-1 (nodes: A, B, C)
- Range-2: Raft Group-2 (nodes: B, C, D)
- Range-3: Raft Group-3 (nodes: C, D, E)

### Split/Merge
- **Split**: When range grows too large (size or QPS)
  - Range-1 `[A, Z)` → Range-1 `[A, M)` + Range-2 `[M, Z)`
  - New Raft group created for Range-2
  
- **Merge**: When range shrinks
  - Range-1 `[A, M)` + Range-2 `[M, Z)` → Range-1 `[A, Z)`
  - Raft group for Range-2 disbanded

### Lease-Based Reads
- **Leaseholder**: One replica per range holds exclusive lease
- **Linearizable reads**: Go to leaseholder (no Raft round-trip)
- **Follower reads**: Stale but fast, at `safe_timestamp`

## Implementation Phases

### Phase 1: Single Range, Single Raft Group
- MVP: All data in one range
- One Raft group, 3 nodes
- Basic replication and failover

### Phase 2: Multi-Range, Multi-Raft
- Range splitting based on size/QPS
- Multiple Raft groups per node
- Lease management
- Range balancing

### Phase 3: Geo-Distributed Multi-Raft
- Cross-region replication
- Quorum reads/writes
- Follower reads for locality

## Consequences

### Positive
- ✅ Horizontal scalability (more ranges = more parallelism)
- ✅ Load distribution across nodes
- ✅ Fault isolation per range
- ✅ Geo-placement flexibility
- ✅ Proven architecture (CockroachDB, TiKV, etcd-multi-raft)

### Negative
- ❌ Complexity: Manage many Raft groups per node
- ❌ Split/merge overhead
- ❌ Coordination for cross-range transactions (Phase 2+)
- ❌ More metadata to track

### Mitigations
- **Complexity**: Use battle-tested Raft library (raft-rs)
- **Overhead**: Batch Raft messages, share transport
- **Cross-range txn**: 2PC coordinator handles multi-range writes
- **Metadata**: Centralized meta service (vega-meta)

## Comparison: Single vs Multi-Raft

| Aspect | Single Raft | Multi-Raft |
|--------|-------------|------------|
| Leader bottleneck | ❌ Yes | ✅ No |
| Scalability | ❌ Limited | ✅ Horizontal |
| Fault isolation | ❌ Low | ✅ High |
| Complexity | ✅ Simple | ❌ Complex |
| Geo-placement | ❌ No | ✅ Yes |
| Cross-range txn | ✅ Easy | ❌ Needs 2PC |

## Alternatives Considered

### 1. Single Raft (Rejected for production, used in Phase 1 MVP)
- **When**: Phase 1 MVP
- **Why**: Simpler to implement initially
- **Limitation**: Not scalable

### 2. Raft + Primary-Backup Hybrid (Rejected)
- **Idea**: Raft for metadata, primary-backup for data
- **Cons**: Weaker consistency, split-brain risk

### 3. Paxos (Rejected)
- **Pros**: More flexible than Raft
- **Cons**: Harder to implement correctly, fewer libraries
