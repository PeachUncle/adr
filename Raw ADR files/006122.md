# ADR 017: Repository pattern

 This pattern is frequently used in the domain and infrastructure layers to abstract the data access logic, making it easy to swap data sources or implement caching without affecting the rest of the application.

## Relevant data

Assumptions:

+ You want to access persistent data in SQL Server. 
+ Creation, migration, etc. of the database does not enter in this decision.
+ Only access for CRUD for database records.

## Background

Using Dappr as ORM, the repository pattern is necessary to abstract the data access logic, making it easy to swap data sources or implement caching without affecting the rest of the application.

```csharp
using System;
using System.Data;
using System.Data.SqlClient;
using Dapper;

public class DapperExample
{
    public void QueryUsingDapper()
    {
        string connectionString = "your_connection_string";
        
        using (IDbConnection connection = new SqlConnection(connectionString))
        {
            connection.Open();
            
            // Execute a query using Dapper
            string sql = "SELECT * FROM Customers"; //Alert! ·*· is anti-pattern, use explicit columns
            var customers = connection.Query<Customer>(sql);
            
            foreach (var customer in customers)
            {
                Console.WriteLine($"Customer: {customer.Name}, Email: {customer.Email}");
            }
        }
    }
}

public class Customer
{
    public int Id { get; set; }
    public string Name { get; set; }
    public string Email { get; set; }
}

```
Using Enity Framework Core (EF Core) as ORM, the repository pattern is not necessary, since EF Core already implements it. However, it is necessary to implement the Unit of Work pattern and Generic Repository.

```csharp	
using System;
using Microsoft.EntityFrameworkCore;

public class EFExample
{
    public void QueryUsingEntityFramework()
    {
        string connectionString = "your_connection_string";
        
        var options = new DbContextOptionsBuilder<MyDbContext>()
            .UseSqlServer(connectionString)
            .Options;
        
        using (var context = new MyDbContext(options))
        {
            // Execute a query using Entity Framework
            var customers = context.Customers.ToList();
            
            foreach (var customer in customers)
            {
                Console.WriteLine($"Customer: {customer.Name}, Email: {customer.Email}");
            }
        }
    }
}

public class MyDbContext : DbContext
{
    public DbSet<Customer> Customers { get; set; }
    
    public MyDbContext(DbContextOptions<MyDbContext> options) : base(options)
    {
    }
}

public class Customer
{
    public int Id { get; set; }
    public string Name { get; set; }
    public string Email { get; set; }
}
```

## Options considered

| | Dapper | Entity Framework |
|---|---|---|
| Advantages | - Efficient and fast performance. | - Higher abstraction and productivity. |
| | - Full control over SQL queries. | - Complete Object-Relational Mapping (ORM). |
| | - Lightweight and easy to learn. | - Support for multiple databases. |
| | - Can be more suitable for small or simple projects. | - Support for advanced features like migrations, caching, and transactions. |
| Disadvantages | - More manual code for result mapping. | - Higher overhead and complexity in small or simple projects. |
| | - Requires writing SQL queries manually. | - Slightly lower performance compared to Dapper. |
| | - Less abstraction and automation compared to Entity Framework. | - Steeper initial learning curve. |
