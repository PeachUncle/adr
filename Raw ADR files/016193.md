# ADR-002: Populator Service Placement and Architecture

**Status**: Proposed  
**Date**: 2025-09-18  
**Author**: Refactoring Analysis  

## Context

The populator service is currently located in `src/infrastructure/services/populator/` but represents a significant separate application within the main server. Key issues:

1. **Size and Complexity**: The populator has its own CLI, database layer, services, and models
2. **Logical Separation**: CVE/CPE population is a distinct concern from the vulnerability analysis API
3. **Infrastructure vs Domain Logic**: Population logic is not infrastructure - it's a separate domain
4. **Deployment Concerns**: Population might need different deployment patterns than the API server

## Decision

**Keep the populator integrated but move it to its own top-level module.** This balances your preference against having a separate crate while addressing architectural concerns.

### New Structure
```
src/
├── cli/              # CLI commands (existing)
├── domain/           # Core business domains (existing)
├── infrastructure/   # Infrastructure concerns (existing)  
├── populator/        # NEW: Population domain and services
│   ├── domain/       # Population-specific domain logic
│   │   ├── cpe/      # CPE analysis and processing
│   │   ├── cve/      # CVE analysis and processing
│   │   └── nvd/      # NVD API integration logic
│   ├── infrastructure/ # Population infrastructure
│   │   ├── database/ # Population-specific database operations
│   │   ├── nvd_client/ # NVD API client
│   │   └── config/   # Population configuration
│   └── services/     # Population service implementations
└── web/              # Web API layer (existing)
```

### Rationale

1. **Domain Separation**: Population is its own domain with distinct concerns
2. **Clear Boundaries**: Population logic separated from main API logic
3. **Maintainability**: Easier to understand and modify population vs API concerns
4. **Future Flexibility**: Could be extracted to separate crate later if needed
5. **Single Binary**: Maintains your preference for unified deployment

## Implementation Plan

### Phase 1: Create New Structure
1. Create `src/populator/` directory with proper domain structure
2. Move population services out of infrastructure
3. Reorganize population logic by domain concerns

### Phase 2: Update Dependencies
1. Update CLI handlers to use new populator module
2. Ensure clean separation between API and population concerns
3. Update imports and module structure

### Phase 3: Refine Architecture
1. Identify any leaked population logic in other domains
2. Ensure population has its own configuration management
3. Consider future extraction points if needed

## Consequences

### Positive
- Clear separation of concerns between API and population
- Population logic gets proper domain architecture
- Easier to maintain and understand each area
- Infrastructure module becomes cleaner
- Better preparation for potential future extraction

### Negative
- Some reorganization complexity
- Need to update imports and dependencies
- Temporary increase in module complexity during transition

### Alternative Considered: Extract to Separate Crate

**Rejected because:**
- You prefer single binary deployment
- Adds complexity of inter-crate dependencies
- Population is used by main application for data setup

### Alternative Considered: Keep in Infrastructure

**Rejected because:**
- Population is not infrastructure - it's domain logic
- Creates confusion about what belongs in infrastructure
- Makes infrastructure module too large and complex
- Mixes data processing logic with infrastructure concerns

## Migration Strategy

1. **Create new module structure** without moving files initially
2. **Move files incrementally** to ensure compilation at each step
3. **Update imports** as files are moved
4. **Test thoroughly** to ensure no functionality is lost
5. **Update documentation** to reflect new architecture

## Future Considerations

- Population could be extracted to separate binary if deployment needs change
- NVD integration could be extracted as shared library
- Population database operations could be optimized independently
- Different scaling strategies for API vs population workloads
