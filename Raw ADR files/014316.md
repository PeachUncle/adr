# Design: Drizzle ORM Migration

## Context
The database schema was recently refactored from raw SQL to Drizzle ORM with 21 separate table files following SOC principles. The schema includes:
- Auth tables (Better Auth): user, session, account, verification
- Subscription tables: subscription-plans, subscriptions, payments
- User data tables: user-profiles, user-preferences, push-subscriptions
- Decision tables: decisions, decision-tags, decision-taggings, decision-outcomes
- Gamification tables: daily-progress, user-streaks
- Analytics tables: decision-patterns, behavior-events, ai-usage-metrics, ai-cost-daily-rollups, admin-metrics

However, the application layer (routes and services) still uses a legacy `query()` function that was removed during the schema refactor. This creates a broken state where TypeScript compilation fails.

## Goals / Non-Goals

**Goals:**
- Migrate all database operations to use Drizzle ORM query builder
- Maintain type safety across all database operations
- Preserve existing API behavior and contracts (zero breaking changes)
- Improve developer experience with autocomplete and type inference
- Prepare codebase for future relational queries

**Non-Goals:**
- Changing API endpoints or response structures
- Adding new features or capabilities
- Performance optimization (though type safety may help)
- Database schema changes (already completed)
- Changing error handling patterns

## Decisions

### Decision 1: Use Drizzle Query Builder vs Drizzle Relational Queries
**Choice**: Start with query builder, migrate to relational queries in future iterations.

**Rationale**:
- Query builder syntax closely mirrors SQL, easier 1:1 migration
- Relational queries require defining all relations (already done in relations.ts)
- Can incrementally adopt relational queries for complex joins later
- Lower risk of semantic changes during initial migration

**Example transformation**:
```typescript
// Before (raw SQL)
const result = await query(
  'SELECT * FROM decisions WHERE user_id = $1 ORDER BY created_at DESC LIMIT $2',
  [userId, limit]
);

// After (Drizzle query builder)
const result = await db
  .select()
  .from(decisions)
  .where(eq(decisions.userId, userId))
  .orderBy(desc(decisions.createdAt))
  .limit(limit);
```

### Decision 2: Migration Order
**Choice**: Services first, then routes (core routes before supporting routes).

**Rationale**:
- Services have fewer dependencies, easier to test in isolation
- Core routes (decisions, user) have most complexity, tackle when services are stable
- Supporting routes (patterns, subscriptions) depend on core functionality
- Allows incremental testing and rollback if needed

### Decision 3: Handle JSONB Types
**Choice**: Use Drizzle's `.$type<T>()` for JSONB columns with explicit TypeScript types.

**Rationale**:
- Schema already defines types like `.$type<Record<string, unknown>>()`
- Maintains flexibility for evolving JSONB structures
- Type-safe access to nested properties
- Avoids runtime validation overhead

**Example**:
```typescript
// Schema definition
metadata: jsonb('metadata').$type<Record<string, unknown>>()

// Query usage
const decision = await db.select().from(decisions).where(eq(decisions.id, id));
// decision.metadata is typed as Record<string, unknown>
```

### Decision 4: Handle Upsert Operations
**Choice**: Use Drizzle's `.onConflictDoUpdate()` for upsert patterns.

**Rationale**:
- Existing code uses `ON CONFLICT DO UPDATE` in gamification
- Drizzle provides native support via `.onConflictDoUpdate()`
- Maintains atomic operations for daily progress and streaks
- Type-safe conflict resolution

**Example**:
```typescript
await db
  .insert(dailyProgress)
  .values({ userId, date, count: 1 })
  .onConflictDoUpdate({
    target: [dailyProgress.userId, dailyProgress.date],
    set: { count: sql`${dailyProgress.count} + 1` }
  });
```

## Risks / Trade-offs

### Risk: SQL Semantic Differences
**Description**: Drizzle query builder may generate slightly different SQL than hand-written queries.
**Impact**: Medium - Could affect query performance or results
**Mitigation**:
- Review generated SQL using `db.select().toSQL()`
- Test all endpoints thoroughly
- Compare query plans for critical queries
- Keep raw SQL as comments during migration for reference

### Risk: Type Mismatches
**Description**: TypeScript types may not match runtime PostgreSQL types exactly.
**Impact**: Low - Drizzle infers types from schema
**Mitigation**:
- Schema already has explicit types defined
- Use `.execute()` only when necessary
- Validate results in tests

### Risk: Breaking Existing Functionality
**Description**: Logic errors during migration could break API endpoints.
**Impact**: High - Could affect production users
**Mitigation**:
- Migrate incrementally (services → routes)
- Run TypeScript compiler after each file
- Test each endpoint after migration
- Keep git history for easy rollback
- Document any behavioral changes

### Trade-off: Bundle Size
**Description**: Drizzle ORM adds ~50KB to bundle size.
**Impact**: Low - Backend doesn't have strict size constraints
**Benefit**: Type safety, maintainability, developer experience

## Migration Plan

### Phase 1: Services (Low Risk)
1. `src/services/subscription.ts` - 4 queries
2. `src/services/gamification.ts` - 6 queries
3. Run TypeScript compiler, fix errors
4. Manual testing of affected endpoints

### Phase 2: Core Routes (Medium Risk)
1. `src/routes/decisions.ts` - 15 queries (most complex)
2. `src/routes/user.ts` - 8 queries
3. Run TypeScript compiler after each file
4. Integration testing for each route

### Phase 3: Supporting Routes (Low Risk)
1. `src/routes/subscriptions.ts` - 4 queries
2. `src/routes/patterns.ts` - 2 queries
3. Final TypeScript compilation
4. Full regression testing

### Rollback Strategy
- Git revert individual file changes if issues found
- Keep legacy SQL as comments until full validation
- Incremental deployment allows partial rollback

### Success Criteria
- Zero TypeScript compilation errors
- All API endpoints return same response structures
- All tests pass (once written)
- No regression in API response times
- Improved developer experience (autocomplete, type safety)

## Open Questions
None - schema is complete, query patterns are well-understood, migration path is clear.
