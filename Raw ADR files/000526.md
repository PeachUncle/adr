# ADR-005: Event-Driven Design

## Status
Accepted

## Context
For the Farm Management System, we needed an architecture that could handle:

- Real-time IoT sensor data processing
- Loose coupling between agricultural modules
- Complex business workflows and notifications
- Audit logging and compliance requirements
- Scalable processing of agricultural events
- Integration with external systems
- Asynchronous processing of resource-intensive tasks

## Decision
We chose an **Event-Driven Architecture** using domain events, message queues, and event sourcing patterns.

## Rationale

### 3. Complex Business Workflows

**Irrigation Workflow**
```typescript
// Workflow triggered by moisture sensor reading
class IrrigationWorkflow {
  @EventHandler('SENSOR_READING_RECEIVED')
  async handleLowSoilMoisture(event: SensorReadingEvent) {
    if (event.data.sensorType !== 'SOIL_MOISTURE') return;
    if (event.data.value > 30) return; // Moisture is adequate

    // Create irrigation task
    await this.eventBus.publish(new IrrigationNeededEvent({
      fieldId: event.metadata.fieldId,
      priority: this.calculatePriority(event.data.value),
      recommendedDuration: this.calculateIrrigationDuration(event.data.value),
    }));

    // Check weather forecast
    await this.eventBus.publish(new WeatherCheckRequestedEvent({
      fieldId: event.metadata.fieldId,
      reason: 'IRRIGATION_PLANNING',
    }));
  }
}
```

### 4. Audit & Compliance

**Event Sourcing**
```typescript
interface DomainEvent {
  id: string;
  type: string;
  data: any;
  metadata: {
    userId: string;
    tenantId: string;
    correlationId?: string;
    causationId?: string;
  };
  occurredAt: Date;
  version: number;
}

// Event store for audit trail
@Injectable()
export class EventStore {
  async saveEvent(event: DomainEvent): Promise<void> {
    await this.prisma.domainEvent.create({
      data: {
        id: event.id,
        type: event.type,
        data: event.data,
        metadata: event.metadata,
        occurredAt: event.occurredAt,
        version: event.version,
      },
    });
  }

  async getEventsForAggregate(
    aggregateId: string,
    fromVersion?: number
  ): Promise<DomainEvent[]> {
    return this.prisma.domainEvent.findMany({
      where: {
        'metadata.aggregateId': aggregateId,
        version: fromVersion ? { gte: fromVersion } : undefined,
      },
      orderBy: { version: 'asc' },
    });
  }
}
```

### 5. Scalability & Performance

**Asynchronous Processing**
- Non-blocking request handling
- Parallel event processing
- Load distribution across workers
- Backpressure handling

**Message Queue Benefits**
```typescript
// Redis-based message queue
@Injectable()
export class MessageQueue {
  async publish(event: DomainEvent): Promise<void> {
    await this.redis.xadd(
      `events:${event.type}`,
      '*',
      'id', event.id,
      'data', JSON.stringify(event.data),
      'metadata', JSON.stringify(event.metadata),
      'occurredAt', event.occurredAt.toISOString()
    );
  }

  async subscribe(
    eventType: string, 
    handler: EventHandler
  ): Promise<void> {
    const stream = `events:${eventType}`;
    
    while (true) {
      const results = await this.redis.xreadgroup(
        'GROUP', 'processors', this.workerId,
        'COUNT', '10', 'BLOCK', '1000',
        'STREAMS', stream, '>'
      );

      if (results && results.length > 0) {
        await this.processEvents(results[0][1], handler);
      }
    }
  }
}
```

## Architecture Components

### 1. Event Bus

**Core Event Bus Implementation**
```typescript
@Injectable()
export class EventBus {
  private handlers = new Map<string, EventHandler[]>();

  async publish(event: DomainEvent): Promise<void> {
    // Store event for audit
    await this.eventStore.saveEvent(event);
    
    // Get handlers for this event type
    const handlers = this.handlers.get(event.type) || [];
    
    // Execute handlers asynchronously
    const promises = handlers.map(handler => 
      this.executeHandler(handler, event)
    );
    
    await Promise.allSettled(promises);
  }

  register(eventType: string, handler: EventHandler): void {
    const handlers = this.handlers.get(eventType) || [];
    handlers.push(handler);
    this.handlers.set(eventType, handlers);
  }
}
```

### 2. Event Handlers

**Handler Patterns**
```typescript
// Simple handler
@Injectable()
export class AlertHandler implements EventHandler {
  constructor(private alertService: AlertService) {}

  @EventHandler('DEVICE_OFFLINE')
  async handle(event: DeviceOfflineEvent): Promise<void> {
    await this.alertService.create({
      type: 'DEVICE_OFFLINE',
      severity: 'HIGH',
      deviceId: event.data.deviceId,
      message: `Device ${event.data.deviceId} went offline`,
      metadata: {
        lastSeen: event.data.lastSeen,
        suspectedCause: event.data.suspectedCause,
      },
    });
  }
}

// Saga/Workflow handler
@Injectable()
export class CropManagementSaga implements EventHandler {
  @EventHandler('FIELD_PLANTED')
  async handle(event: FieldPlantedEvent): Promise<void> {
    // Schedule future tasks
    await this.scheduleIrrigationCheck(event.data.fieldId);
    await this.scheduleFertilizationReminder(event.data);
    await this.scheduleHarvestPlanning(event.data);
  }

  private async scheduleIrrigationCheck(fieldId: string): Promise<void> {
    // Schedule irrigation check in 7 days
    await this.scheduler.schedule({
      task: 'IRRIGATION_CHECK',
      fieldId,
      scheduledFor: addDays(new Date(), 7),
    });
  }
}
```

### 3. Event Store

**Event Persistence**
```typescript
@Injectable()
export class EventStore {
  constructor(private prisma: PrismaService) {}

  async saveEvents(events: DomainEvent[]): Promise<void> {
    await this.prisma.domainEvent.createMany({
      data: events.map(event => ({
        id: event.id,
        type: event.type,
        data: event.data,
        metadata: event.metadata,
        occurredAt: event.occurredAt,
        version: event.version,
      })),
    });
  }

  async getEventStream(
    aggregateId: string,
    fromVersion = 0
  ): Promise<DomainEvent[]> {
    const events = await this.prisma.domainEvent.findMany({
      where: {
        'metadata.aggregateId': aggregateId,
        version: { gte: fromVersion },
      },
      orderBy: { version: 'asc' },
    });

    return events.map(this.mapToDomainEvent);
  }
}
```

## Alternatives Considered

### Direct Service Calls

**Pros**:
- Simple to implement
- Immediate response
- Easy debugging
- No additional infrastructure

**Cons**:
- Tight coupling between services
- No audit trail
- Difficult to scale
- Single point of failure
- No asynchronous processing

### Shared Database

**Pros**:
- Simple data sharing
- Transactional consistency
- Easy to query

**Cons**:
- Tight coupling through shared schema
- Performance bottlenecks
- Difficult to scale independently
- No event history

### Message Queue Only

**Pros**:
- Asynchronous processing
- Load balancing
- Durability

**Cons**:
- No type safety
- Complex error handling
- Limited query capabilities
- No event sourcing

### CQRS Pattern

**Pros**:
- Read/write optimization
- Scalable reads
- Clear separation

**Cons**:
- Increased complexity
- Eventual consistency
- More infrastructure

## Consequences

### Positive
- **Loose Coupling**: Services can evolve independently
- **Scalability**: Asynchronous processing enables scaling
- **Audit Trail**: Complete event history for compliance
- **Flexibility**: Easy to add new event consumers
- **Resilience**: System can handle temporary failures

### Negative
- **Complexity**: More complex than direct calls
- **Debugging**: Asynchronous flows are harder to debug
- **Eventual Consistency**: Not immediately consistent
- **Learning Curve**: Team needs to learn event patterns

### Risks
- **Event Ordering**: Maintaining event order is challenging
- **Duplicate Processing**: Need idempotent handlers
- **Event Schema Evolution**: Managing event version changes
- **Performance**: High event volume can impact performance

## Performance Considerations

### Event Processing
- **Batch Processing**: Process events in batches
- **Parallel Processing**: Multiple worker processes
- **Prioritization**: Event priority queues
- **Backpressure**: Rate limiting and buffering

### Storage Optimization
- **Event Partitioning**: Partition events by tenant or type
- **Compression**: Compress event data
- **Retention Policies**: Archive old events
- **Indexing**: Efficient event querying

## Future Considerations

### Event Sourcing Evolution
- **Snapshot Strategy**: Periodic aggregate snapshots
- **Event Rebuild**: Efficient aggregate reconstruction
- **Migration Tools**: Event schema migration utilities

### Advanced Patterns
- **Process Managers**: Complex workflow coordination
- **Event Versioning**: Backward-compatible event evolution
- **Distributed Tracing**: End-to-end event flow tracking

## Conclusion

Event-driven architecture provides the ideal foundation for our agricultural management platform, enabling real-time IoT data processing, loose coupling between agricultural modules, and comprehensive audit capabilities. The asynchronous nature of events allows the system to handle high-volume sensor data while maintaining responsive user interfaces.

The event sourcing approach gives us a complete audit trail for compliance and regulatory requirements, while the message queue system provides the scalability and resilience needed for agricultural operations that often occur in remote or connectivity-challenged environments.
