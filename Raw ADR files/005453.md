## Context

The multi-agent options trading system requires comprehensive data analytics capabilities to support:

1. **Real-time correlation analysis** across multiple timeframes (30m, 1h, 4h, 1d, 3d, 1w)
2. **Historical price data management** with efficient querying and analysis
3. **News sentiment analysis** with impact scoring for trading decisions
4. **Implied volatility surface analysis** with IV rank calculations
5. **Multi-strategy support** for Iron Condor, Covered Call, and Cash-Secured Put strategies

### Current State Analysis

The existing system architecture includes:
- Multi-agent coordination via Portfolio Orchestrator Agent
- 6-state trading finite state machine
- Direct async communication between agents
- Basic price data handling through the `Market Analysis Agent`
- Limited historical analysis capabilities

### Requirements

1. **Performance**: Enable sub-second query response for real-time decisions by serving pre-calculated analytics (like correlation matrices) from a low-latency cache. BigQuery will serve as the powerful engine for performing these complex calculations.
2. **Scalability**: Handle 1000+ symbols with multi-timeframe analysis
3. **Cost Efficiency**: Maintain infrastructure costs under $500/month
4. **Integration**: Seamless integration with existing multi-agent architecture
5. **Data Types**: Support for historical prices, options data, news, and IV surfaces
6. **Analytics**: Advanced correlation analysis, sentiment scoring, and strategy signals

## Decision

**We will implement BigQuery as the primary analytics data warehouse** for the multi-agent trading system, responsible for both storing the raw historical market data and serving all analytical queries.

### Primary Decision Points

1. **BigQuery for All Analytics Data (OLAP)**
   - **Primary Ingestion Target**: Ingest and archive the real-time market data stream from the `IBGatewayAgent`.
   - **Analytical Engine**: Power historical price analysis, multi-timeframe correlation matrices, news sentiment scoring, IV surface analysis, and performance reporting.

2. **Data Ingestion Architecture**
   - The `IBGatewayAgent` will publish raw market data (ticks, quotes) to a real-time message stream.
   - A dedicated `Data Ingestion Service` will subscribe to this stream, handling the batching and streaming ingestion into BigQuery.
   - This decouples the real-time gateway from the analytics warehouse, improving resilience and preventing backpressure from affecting the operational data flow. This creates a high-fidelity, permanent archive of all market events, which serves as the foundational dataset for all subsequent analysis.

3. **Integration Architecture**
   - Analytical agents (`MarketAnalysisAgent`, `RiskManagementAgent`) will query BigQuery for historical context.
   - Real-time operational data will continue to be served from Redis to decouple analytics from the live trading loop.

4. **Cost-Optimized Design**
   - Partitioned tables by date for query performance and cost management.
   - Materialized views for frequently calculated aggregations (e.g., daily OHLC from raw ticks).
   - Intelligent caching in Redis for expensive or frequently requested query results.

## Rationale

### Why BigQuery Over Alternatives

| Aspect | BigQuery | PostgreSQL | Dataflow | Cloud SQL |
|--------|----------|------------|----------|-----------|
| **Analytics Performance** | Excellent | Limited | Good | Poor |
| **Correlation Calculations** | 10-50ms | 100-500ms | 100-200ms | 1000ms+ |
| **Large Dataset Handling** | Excellent | Limited | Good | Poor |
| **Cost for Analytics** | $70-250/month | $200+/month | $2000+/month | $500+/month |
| **Scalability** | Unlimited | Hardware limited | Good | Limited |
| **Integration Complexity** | Medium | Low | High | Low |

### Key Advantages

1. **Performance**: Native SQL correlation functions with columnar storage optimization
2. **Cost Efficiency**: Pay-per-query model scales with actual usage
3. **Scalability**: Handles petabyte-scale data without performance degradation
4. **Advanced Analytics**: Built-in statistical functions, window operations, and ML capabilities
5. **Maintenance**: Fully managed service with automatic optimization

## Implementation Strategy

### Phase 1: Core Infrastructure (Weeks 1-2)
- Set up BigQuery datasets and core tables, including the `raw_market_ticks` table.
- Implement the data streaming pipeline from the `IBGatewayAgent` to BigQuery.
- Create materialized views to generate `historical_prices` (OHLC) from the raw tick data.
- Integrate with existing `MarketAnalysisAgent` to query the new historical views.

### Phase 2: Advanced Analytics (Weeks 3-4)
- Implement multi-timeframe correlation analysis based on the historical data.
- Add news sentiment analysis and impact scoring.
- Create IV surface construction and analysis.
- Build strategy-specific signal generation.

### Phase 3: Integration & Optimization (Weeks 5-6)
- Integrate with `Strategy Execution Agents` for strategy decisions.
- Implement intelligent caching and cost optimization.
- Add performance monitoring and alerting.
- Refine materialized views for frequent queries.

### Phase 4: Production Hardening (Weeks 7-8)
- Load testing and performance validation.
- Cost optimization and query tuning.
- Documentation and training.
- Production deployment.

### Schema Design

#### Core Tables
1. **raw_market_ticks**: The primary ingestion target for the IB stream. Contains raw, high-fidelity tick data. Partitioned by timestamp, clustered by symbol.
2. **historical_prices**: A materialized view over `raw_market_ticks` that provides daily OHLCV data.
3. **correlation_matrices**: Multi-timeframe correlation data with intelligent caching.
4. **company_news**: Sentiment analysis with impact scoring.
5. **iv_surface**: Implied volatility surface with rank calculations.
6. **daily_signals**: Strategy-specific trading signals.

#### Key Features
- **Partitioning**: Time-based partitioning for query performance.
- **Clustering**: Symbol-based clustering for efficient filtering.
- **Materialized Views**: Pre-compute expensive calculations (e.g., OHLC from ticks).
- **Expiration Management**: Automatic cache invalidation.

## Alternatives Considered

### 1. Google Cloud Dataflow
- **Pros**: Real-time stream processing, advanced analytics
- **Cons**: High cost ($2,000+/month), complex setup, over-engineered
- **Decision**: Rejected due to cost and complexity

### 2. PostgreSQL with Extensions
- **Pros**: Lower cost, familiar SQL interface
- **Cons**: Limited scalability, poor analytics performance, requires significant optimization
- **Decision**: Rejected due to performance limitations

### 3. Redis + Custom Analytics
- **Pros**: Ultra-low latency, full control
- **Cons**: High development effort, limited analytics capabilities, expensive at scale
- **Decision**: Rejected due to development complexity

### 4. Hybrid Cloud SQL + BigQuery (Alternative Considered)
- **Pros**: Optimal for operational + analytics split
- **Cons**: Additional complexity, multiple data stores
- **Decision**: Viable but not needed for current analytics-focused requirements

## Implementation Details

### BigQuery Dataset Structure
```sql
-- Primary ingestion table for raw market data
CREATE TABLE `trading.raw_market_ticks` (
  timestamp TIMESTAMP NOT NULL,
  symbol STRING NOT NULL,
  price FLOAT64,
  volume INT64,
  -- other fields like bid, ask, etc.
) PARTITION BY DATE(timestamp) CLUSTER BY symbol;

-- Materialized view for daily OHLC data
CREATE MATERIALIZED VIEW `trading.historical_prices` AS
SELECT
  symbol,
  DATE(timestamp) as date,
  -- Logic to calculate OHLCV from ticks
FROM `trading.raw_market_ticks`
GROUP BY symbol, date;

CREATE TABLE `trading.correlation_matrices` (
  symbols ARRAY<STRING> NOT NULL,
  timeframe STRING NOT NULL,
  correlation_matrix JSON NOT NULL,
  expires_at TIMESTAMP NOT NULL
) PARTITION BY DATE(created_at) CLUSTER BY timeframe;
```
