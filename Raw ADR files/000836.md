# ADR-002: Service Communication Style - Event-Driven Choreography

**Date:** 2025-01-15  
**Status:** Accepted  
**Supersedes:** None  
**Related ADRs:** ADR-001 (Microservices), ADR-004 (Saga Pattern), ADR-014 (Consistency), ADR-015 (RabbitMQ)

---

## Context

### Business Drivers
BahariWatch requires **real-time alert delivery** to enforcement agents when community reports match suspicious vessel activity. The system must:
- Process **100 reports/hour** during peak fishing seasons (April-June, October-December)
- Deliver alerts within **<5 seconds p95 latency** (ADR-006)
- Maintain **99.5% availability** despite service failures (ADR-006)
- Support **asynchronous workflows** (report → vessel matching → alert generation → notification)
- Enable **independent service deployments** to accelerate iteration during 6-month pilot

### Technical Constraints
- **Budget:** KSh 59,500 limits infrastructure to ~$40/month (ADR-012)
- **Timeline:** 6-month pilot (May-October 2025) requires rapid development velocity
- **Connectivity:** Coastal regions have intermittent network (offline-first mobile app, async processing preferred)
- **External Dependencies:** AIS/VMS feeds have unpredictable latency (5-30 seconds), requiring loose coupling
- **Team Size:** Small team (3-4 developers) needs simple debugging and operational model

### Architecture Characteristics Affected
From ADR-006, the communication style directly impacts:
1. **Performance (8/10 priority):** <5s p95 alert delivery requires async processing
2. **Availability (9/10 priority):** Service failures must not cascade
3. **Fault Tolerance (7/10 priority):** External API timeouts require circuit breakers
4. **Scalability (7/10 priority):** Independent service scaling for matching engine (CPU-intensive)
5. **Testability (6/10 priority):** Decoupled services enable independent testing

### Integration with Other ADRs
- **ADR-001 (Microservices):** Defines 8 services requiring inter-service communication
- **ADR-004 (Anthology Saga):** Async choreography enables saga pattern for report workflows
- **ADR-011 (External Integration):** Circuit breakers and bulkheads require async communication
- **ADR-014 (Consistency):** 30-second p99 eventual consistency window assumes async messaging
- **ADR-015 (RabbitMQ Selection):** Message broker choice implements this communication pattern

## Decision

**Adopt event-driven choreography** using **RabbitMQ topic exchanges** for all inter-service communication in the BahariWatch report-to-alert workflow.

### Core Principles
1. **Services communicate exclusively via domain events** (no direct REST calls between services)
2. **RabbitMQ topic exchanges** enable flexible routing (e.g., `report.submitted.v1`, `vessel.matched.v1`)
3. **JSON Schema validation** enforces event contracts (semantic versioning: major.minor.patch)
4. **Idempotent consumers** with Redis deduplication prevent duplicate processing
5. **Dead Letter Exchange (DLX)** with exponential backoff retry (1min → 5min → 15min → 1hour → DLQ)
6. **Transactional Outbox pattern** ensures zero data loss during message broker downtime

### Message Broker Selection (ADR-015)
**RabbitMQ** chosen over Kafka, AWS SNS/SQS, Redis Pub/Sub:
- **Cost:** $15/month 3-node cluster (vs $60/month Kafka)
- **Latency:** 5-20ms publish-to-consume (meets <5s alert delivery SLO)
- **Reliability:** Persistent queues + publisher confirms = zero data loss
- **Operational Simplicity:** No ZooKeeper, fits small team capacity
- **Flexible Routing:** Topic exchanges support wildcard subscriptions (`report.*.v1`)

### Event Schema Management
- **Format:** JSON with JSON Schema validation (v7 draft)
- **Versioning:** Semantic versioning in event names (`report.submitted.v1`, `report.submitted.v2`)
- **Registry:** Git-based schema repository (`/schemas/events/`) with CI validation
- **Breaking Changes:** New major version events published in parallel (6-month migration window)
- **Evolution Rules:**
  - ✅ **Non-breaking:** Add optional fields, deprecate fields (mark with `"deprecated": true`)
  - ❌ **Breaking:** Remove fields, rename fields, change types, alter semantics

**Example Event Schema:**

### Idempotency Strategy
**Problem:** Network retries or consumer restarts may deliver same event multiple times.

**Solution:** Redis-backed idempotency cache (7-day TTL)
```python
# Consumer pseudocode
def handle_event(event):
    event_id = event['event_id']
    
    # Check if already processed
    if redis.exists(f"processed:event:{event_id}"):
        logger.info(f"Event {event_id} already processed, skipping")
        return  # Acknowledge without reprocessing
    
    try:
        # Process event
        process_business_logic(event)
        
        # Mark as processed (7-day TTL for audit trail)
        redis.setex(f"processed:event:{event_id}", 604800, "1")
        
        # Acknowledge message
        channel.basic_ack(delivery_tag=method.delivery_tag)
    except Exception as e:
        # Reject and requeue for retry
        channel.basic_nack(delivery_tag=method.delivery_tag, requeue=True)
```

**Key Design Points:**
- **7-day TTL** balances audit trail needs with Redis memory limits
- **Event ID uniqueness** enforced at producer (UUID v4)
- **Correlation IDs** link events in same saga for distributed tracing
- **Redis persistence** (RDB snapshots) survives Redis restarts

### Dead Letter Queue (DLQ) Strategy
**Problem:** Transient failures (network timeouts, rate limits) vs permanent failures (malformed events, business rule violations).

**Solution:** 4-tier exponential backoff retry → DLQ → manual intervention

**RabbitMQ Configuration:**
```python
# Primary queue with DLX routing
channel.queue_declare(
    queue='vessel.match.queue',
    durable=True,
    arguments={
        'x-dead-letter-exchange': 'vessel.match.dlx',
        'x-dead-letter-routing-key': 'retry.1min'
    }
)

# Retry queues with TTL
retry_queues = [
    {'name': 'retry.1min', 'ttl': 60000, 'next': 'retry.5min'},
    {'name': 'retry.5min', 'ttl': 300000, 'next': 'retry.15min'},
    {'name': 'retry.15min', 'ttl': 900000, 'next': 'retry.1hour'},
    {'name': 'retry.1hour', 'ttl': 3600000, 'next': 'dlq.final'}
]

for retry_config in retry_queues:
    channel.queue_declare(
        queue=retry_config['name'],
        durable=True,
        arguments={
            'x-message-ttl': retry_config['ttl'],
            'x-dead-letter-exchange': 'vessel.match.dlx',
            'x-dead-letter-routing-key': retry_config['next']
        }
    )

# Final DLQ (no TTL, manual processing)
channel.queue_declare(queue='dlq.final', durable=True)
```

**Retry Policy:**
| Attempt | Delay | Total Elapsed | Action |
|---------|-------|---------------|--------|
| 1st | 1 minute | 1 min | Retry (transient network error likely) |
| 2nd | 5 minutes | 6 min | Retry (external API rate limit recovery) |
| 3rd | 15 minutes | 21 min | Retry (GFW API maintenance window) |
| 4th | 1 hour | 1h 21min | Retry (last attempt before DLQ) |
| Failed | ∞ (manual) | Manual | PagerDuty alert, admin dashboard intervention |

**DLQ Monitoring:**
- **Prometheus Metric:** `rabbitmq_queue_messages{queue="dlq.final"}` → Alert if >10 messages
- **Admin Dashboard:** View DLQ messages with filters (error type, service, timestamp)
- **Replay Capability:** Admin can fix data and re-publish events to primary queue

**Permanent Failure Handling:**
- **Malformed Events:** Logged to ELK with full payload for debugging, not retried
- **Business Rule Violations:** Logged as warnings, saga marked as compensating (ADR-014)
- **External API 404s:** No retry, saga transitions to manual_review state

### Transactional Outbox Pattern
**Problem:** Message broker downtime (e.g., RabbitMQ cluster rebalancing) must not lose events.

**Solution:** Database-backed outbox table ensures at-least-once delivery

**Schema:**
```sql
CREATE TABLE outbox_events (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    event_type VARCHAR(100) NOT NULL,
    event_payload JSONB NOT NULL,
    created_at TIMESTAMP DEFAULT NOW(),
    published_at TIMESTAMP,
    retry_count INT DEFAULT 0,
    INDEX idx_unpublished (published_at) WHERE published_at IS NULL
);
```

**Publishing Flow:**
```python
@transaction.atomic  # PostgreSQL transaction
def create_report(request):
    # 1. Save business entity
    report = Report.objects.create(...)
    
    # 2. Save event to outbox (same transaction)
    OutboxEvent.objects.create(
        event_type='report.submitted.v1',
        event_payload={
            'event_id': str(uuid.uuid4()),
            'data': {'report_id': str(report.id), ...}
        }
    )
    
    # 3. Transaction commits atomically (both or neither)
    return JsonResponse({'report_id': str(report.id)})

# Background worker (separate process)
def publish_outbox_events():
    while True:
        unpublished = OutboxEvent.objects.filter(
            published_at__isnull=True,
            retry_count__lt=5
        ).order_by('created_at')[:100]
        
        for event in unpublished:
            try:
                # Publish to RabbitMQ
                channel.basic_publish(
                    exchange='bahariwatch.events',
                    routing_key=event.event_type,
                    body=json.dumps(event.event_payload),
                    properties=pika.BasicProperties(delivery_mode=2)  # Persistent
                )
                
                # Mark as published
                event.published_at = timezone.now()
                event.save()
            except pika.exceptions.AMQPConnectionError:
                # RabbitMQ down, will retry next loop iteration
                event.retry_count += 1
                event.save()
                logger.warning(f"RabbitMQ unavailable, event {event.id} retry {event.retry_count}")
        
        time.sleep(5)  # Poll every 5 seconds
```

**Key Benefits:**
- **Zero Data Loss:** Event persisted in database before publish attempt
- **At-Least-Once Delivery:** Background worker retries until success
- **RabbitMQ Downtime Tolerance:** Events queue in database, auto-publish when broker recovers
- **Observability:** Query outbox table for publishing lag, retry patterns

## Rationale

### Alternatives Considered

#### **Option A: Synchronous REST API Calls (Rejected)**
**Description:** Services call each other via HTTP REST APIs (e.g., Report Service → `POST /api/vessel/match`)

**Why Rejected:**
- ❌ **Cascading Failures:** Vessel Service downtime blocks Report Service (violates 99.5% availability SLO)
- ❌ **Tight Coupling:** Changes to Matching Service API require coordinated deployments (slows iteration)
- ❌ **Poor Scalability:** All services must scale together (expensive, inefficient)
- ❌ **Timeouts:** GFW API delays (5-30s) would block Report Service threads
- ❌ **No Replay:** Failed transactions lost, no audit trail

**Trade-Off Analysis:**
| Dimension | Sync REST | Event-Driven | Winner |
|-----------|-----------|--------------|--------|
| Latency | 200-500ms (single hop) | 5-20ms per hop, 3-5 hops = 15-100ms | REST (but violates async requirement) |
| Availability | 99.0% (coupled failures) | 99.5% (isolated failures) | ✅ Event-Driven |
| Scalability | Vertical (all services) | Horizontal (per service) | ✅ Event-Driven |
| Debuggability | ⭐⭐⭐⭐ (synchronous stacktraces) | ⭐⭐⭐ (distributed tracing required) | REST |
| Operational Complexity | ⭐⭐ (simple) | ⭐⭐⭐⭐ (message broker, DLQ, outbox) | REST |
| Cost | $25/month (no broker) | $40/month (+$15 RabbitMQ) | REST |

**Verdict:** REST is simpler but violates core requirements (availability, scalability, async workflows).

#### **Option B: Event-Driven Orchestration (Workflow Engine) (Rejected)**
**Description:** Central orchestrator (e.g., Temporal, Camunda) manages report-to-alert workflow

**Why Rejected:**
- ❌ **Single Point of Failure:** Orchestrator downtime blocks all workflows (violates availability SLO)
- ❌ **Expensive:** Temporal Cloud $50+/month exceeds budget
- ❌ **Over-Engineering:** Simple linear workflow (report → match → alert) doesn't justify complexity
- ❌ **Vendor Lock-In:** Temporal/Camunda proprietary APIs hard to migrate
- ❌ **Team Capacity:** Small team lacks expertise in workflow engines

**When Orchestration Would Be Better:**
- Complex branching workflows (BahariWatch has simple linear flow)
- Human-in-the-loop tasks (not applicable to pilot phase)
- Long-running transactions (>1 hour - our saga completes in <30 seconds)
- Budget >$100/month for managed service

#### **Option C: Kafka Event Streaming (Rejected)**
**Description:** Apache Kafka for event log with replay capability

**Why Rejected:**
- ❌ **Cost:** $60/month managed Kafka exceeds budget (vs $15/month RabbitMQ)
- ❌ **Operational Complexity:** ZooKeeper maintenance, partition rebalancing
- ❌ **Over-Engineering:** Replay capability not needed (write-once report data)
- ❌ **Latency:** 20-50ms typical (vs 5-20ms RabbitMQ for low volumes)
- ❌ **Resource Usage:** Min 3 brokers + 3 ZooKeeper nodes = 6 VMs

**When Kafka Would Be Better:**
- High throughput (>1000 msg/sec - BahariWatch is ~3 msg/sec)
- Event replay required (analytics reprocessing - not needed in pilot)
- Multiple consumers with different replay positions (not applicable)
- Budget >$100/month

**See ADR-015 for detailed RabbitMQ vs Kafka analysis**

#### **Option D: AWS Step Functions (Rejected)**
**Description:** Serverless workflow orchestration

**Why Rejected:**
- ❌ **Vendor Lock-In:** Conflicts with DigitalOcean deployment strategy (ADR-012)
- ❌ **Cost Unpredictability:** $25 per million state transitions (hard to forecast)
- ❌ **Regional Latency:** AWS Africa (Cape Town) adds 50-100ms vs DigitalOcean Amsterdam
- ❌ **Complexity:** JSON-based state machines hard to version control and test

## Architecture Characteristics Impact

### Performance (8/10 Priority)
**Impact:** ✅ **Positive (+2)** - Async processing enables <5s p95 alert delivery
- **Message Latency:** 5-20ms RabbitMQ publish-to-consume
- **Saga Completion:** 9-25s p50, 15-30s p95, 25-35s p99 (within 30s SLO from ADR-014)
- **Parallel Processing:** Notification Service sends SMS + Email concurrently (not sequential)

**Mitigation for Negative Impacts:**
- **Distributed Tracing:** Jaeger tracks end-to-end saga latency (identifies bottlenecks)
- **Performance Budget:** Each service must process events in <500ms p95

### Availability (9/10 Priority)
**Impact:** ✅ **Positive (+3)** - Service isolation prevents cascading failures
- **RabbitMQ SLA:** 99.95% (3-node cluster with automatic failover)
- **Bulkhead Pattern:** Matching Service failure doesn't crash Report Service
- **Graceful Degradation:** DLQ queues failed events for later processing (no data loss)

**Mitigation for Negative Impacts:**
- **Message Broker Monitoring:** Prometheus alerts if RabbitMQ queue depth >1000
- **Transactional Outbox:** Tolerates RabbitMQ downtime (events persist in database)

### Fault Tolerance (7/10 Priority)
**Impact:** ✅ **Positive (+2)** - Automatic retries and dead letter queue
- **Transient Failures:** 4-tier exponential backoff (1min → 5min → 15min → 1hour)
- **Permanent Failures:** DLQ with manual intervention (admin dashboard)
- **Zero Data Loss:** Outbox pattern + persistent queues + publisher confirms

### Scalability (7/10 Priority)
**Impact:** ✅ **Positive (+3)** - Independent horizontal scaling per service
- **CPU-Intensive Services:** Matching Service auto-scales 1-10 replicas (PostGIS queries)
- **I/O-Bound Services:** Notification Service scales 1-3 replicas (API rate limits)
- **Message Broker:** RabbitMQ 10k msg/sec capacity (pilot needs ~3 msg/sec)

### Testability (6/10 Priority)
**Impact:** ⚠️ **Negative (-1)** - Distributed testing more complex than monolith
- **Integration Tests:** Require Testcontainers for RabbitMQ (adds 30s to CI pipeline)
- **Contract Tests:** Pact for event schema validation between services
- **End-to-End Tests:** Selenium tests require synthetic event publishing

**Mitigation:**
- **Test Doubles:** In-memory fake message broker for unit tests (pytest fixtures)
- **Chaos Engineering:** Simulate RabbitMQ downtime in staging (ADR-010 fitness function)

### Maintainability (Implicit)
**Impact:** ⚠️ **Negative (-1)** - Event-driven systems harder to debug than synchronous
- **Distributed Tracing Required:** Jaeger for correlation IDs across services
- **Event Versioning Overhead:** Must maintain JSON Schema registry
- **Operational Burden:** RabbitMQ cluster management (mitigated by managed service)

**Mitigation:**
- **Centralized Logging:** ELK Stack with correlation IDs (ADR-012)
- **Admin Dashboard:** Visualize saga state machines, replay failed events
- **Developer Documentation:** Event catalog with examples, sequence diagrams

## Consequences

### Positive
1. ✅ **High Availability:** Service failures isolated (Report Service up even if Matching Service down)
2. ✅ **Independent Deployments:** Services can deploy without coordinating (accelerates iteration)
3. ✅ **Horizontal Scalability:** Matching Service scales to 10 replicas during peak seasons
4. ✅ **Async Processing:** GFW API timeouts (5-30s) don't block Report Service
5. ✅ **Zero Data Loss:** Transactional outbox + persistent queues + retries
6. ✅ **Audit Trail:** All events logged to ELK (7-year retention for compliance)
7. ✅ **Extensibility:** New consumers (e.g., Analytics Service) subscribe without modifying producers

### Negative
1. ⚠️ **Eventual Consistency:** 30-second p99 saga completion (vs immediate in synchronous)
2. ⚠️ **Operational Complexity:** RabbitMQ cluster management, DLQ monitoring, outbox worker
3. ⚠️ **Debugging Difficulty:** Distributed tracing required, no single stacktrace
4. ⚠️ **Cost Overhead:** +$15/month for RabbitMQ (40% increase vs synchronous)
5. ⚠️ **Schema Versioning:** JSON Schema registry maintenance, breaking change coordination
6. ⚠️ **Testing Overhead:** Testcontainers, Pact contracts, synthetic events for E2E tests

### Neutral
1. → **Learning Curve:** Team must learn RabbitMQ, event-driven patterns (offset by RabbitMQ's simplicity vs Kafka)
2. → **Message Ordering:** Not guaranteed (acceptable - report events are independent)
3. → **Duplicate Handling:** Requires idempotency (mitigated by Redis cache)

### Security Implications
- **TLS 1.3 Encryption:** All RabbitMQ connections use mutual TLS (ADR-008)
- **RBAC:** RabbitMQ vhosts per service (Report Service can't publish to `vessel.matched` exchange)
- **Message Signing:** HMAC-SHA256 signatures prevent event tampering (critical for enforcement evidence)
- **PII Protection:** GPS coordinates rounded to 100m in events (ADR-008 anonymization)

### Data Privacy Implications (GDPR/Kenya DPA)
- **7-Year Retention:** Outbox events archived to cold storage after 90 days (ADR-013)
- **Right to Erasure:** User deletion triggers cascading event tombstones (`user.deleted.v1` event)
- **Audit Trail:** All events logged to immutable ELK index (tamper-proof for legal compliance)
- **Cross-Border Transfer:** RabbitMQ cluster in EU (DigitalOcean Amsterdam) for GDPR compliance

### For Developers

#### **Publishing Events (Producer)**
```python
# report_service/events.py
import json
import pika
from django.db import transaction

def publish_report_submitted_event(report):
    event = {
        'event_id': str(uuid.uuid4()),
        'event_type': 'report.submitted.v1',
        'timestamp': timezone.now().isoformat(),
        'version': '1.0.0',
        'correlation_id': str(uuid.uuid4()),
        'data': {
            'report_id': str(report.id),
            'location': {
                'type': 'Point',
                'coordinates': [report.longitude, report.latitude]
            },
            'photo_url': report.photo.url,
            'timestamp': report.created_at.isoformat()
        }
    }
    
    # Validate against JSON Schema before publishing
    schema = load_schema('report.submitted.v1.json')
    jsonschema.validate(event, schema)
    
    # Use transactional outbox pattern
    with transaction.atomic():
        # Save to database first
        report.save()
        
        # Then save to outbox (same transaction)
        OutboxEvent.objects.create(
            event_type=event['event_type'],
            event_payload=event
        )
    
    # Background worker will publish to RabbitMQ
```

#### **Consuming Events (Consumer)**
```python
# vessel_service/consumers.py
import pika
import json
from redis import Redis

redis = Redis(host='redis', decode_responses=True)

def callback(ch, method, properties, body):
    event = json.loads(body)
    event_id = event['event_id']
    
    # Idempotency check
    if redis.exists(f"processed:event:{event_id}"):
        logger.info(f"Skipping duplicate event {event_id}")
        ch.basic_ack(delivery_tag=method.delivery_tag)
        return
    
    try:
        # Validate against JSON Schema
        schema = load_schema(event['event_type'] + '.json')
        jsonschema.validate(event, schema)
        
        # Business logic
        report_id = event['data']['report_id']
        location = event['data']['location']['coordinates']
        
        # Query GFW API for vessels near location
        vessels = query_gfw_vessels(location, radius_km=10)
        
        # Publish VesselMatched event
        if vessels:
            publish_vessel_matched_event(report_id, vessels)
        
        # Mark as processed (7-day TTL)
        redis.setex(f"processed:event:{event_id}", 604800, "1")
        
        # Acknowledge message
        ch.basic_ack(delivery_tag=method.delivery_tag)
        
    except Exception as e:
        logger.error(f"Error processing event {event_id}: {e}", exc_info=True)
        
        # Reject and requeue for retry (will go to DLX)
        ch.basic_nack(delivery_tag=method.delivery_tag, requeue=False)

# Start consuming
channel.basic_consume(queue='vessel.match.queue', on_message_callback=callback)
channel.start_consuming()
```

### For Product Team

#### **User Impact of Eventual Consistency**
- **Expected Behavior:** Fisher submits report → sees "Submitted successfully" → alert arrives 5-30 seconds later
- **User Education:** Onboarding flow explains "Alerts are sent within 30 seconds" (not "immediately")
- **Status Tracking:** Mobile app shows "Report submitted ✓" → "Vessels matched ✓" → "Alert sent ✓" (WebSocket updates)

#### **Error Messaging**
- **Transient Failures:** "Submitting report... (retrying)" → don't alarm user
- **Permanent Failures:** "Report saved locally. Will retry when online." → offline-first UX
