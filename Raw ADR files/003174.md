# 3. Granularity and Service Separation for PITAS Application
Date: 2024-09-25

## Status
Accepted

## Context

The PITAS application is responsible for managing jobInformation assignments, internal and external worker scheduling, as well as facilitating the bidding process for external workers via an auction house and credit system. This broad scope requires clear separation between components to ensure scalability, maintainability, and fault tolerance.

The goal is to decide how to structure the PITAS application into manageable services that can be developed, deployed, and maintained independently. 
We will use Granularity Integrators and Disintegrators to decide how to split the services.

We agreed upon following Bounded Contexts:
- Job List
- Worker List
- Sheduler
- Worker
- Auction House
- Credit System

## Decision
We separate the whole project into two dividable services on one hand we have the *Internal Job Assignment* and on the other hand we have the *external Work searcher*.

The *Internal Job Assignment* contains following modules:
- Job List
- Worker List
- Sheduler
- Worker

The *External Work Searcher* contains following modules:
- Auction House
- Credit System

### Disintegrators
- **Service Functionality:** We have separated the Auction House and the Credit System into a distinct, deployable unit called "External Work Searcher." These Services were split from the others because they are not directly related to the Job List, Scheduler, Worker List, or Worker Service. The Auction House and Credit System only need to work when an internal worker cannot be found. For this reason, we decided to implement both as a separate system under the name "External Work Searcher."
- **Code Volatility:** Since we cannot yet predict how frequently we will need to change code in our services, it is challenging to disintegrate them based on code volatility. However, we believe it makes sense to separate the credits and auction house functionalities, as services like Job List, Worker Service, and Scheduler do not depend on this code. Only the Worker List has a dependency, but that is not important enought to the service's functionality. Therefore, we have decided to keep it within the Internal Job Assignment service.
- **Scalability and Throughput:**  Scalability behaves differently for the auction house and credit system compared to the Job List, Scheduler, Worker List, or Worker Service. The key reason is that as the number of internal workers in our Worker List grows, we need to ensure the system scales efficiently. However, this approach doesn't apply to the auction house and credit system. We always prioritize internal workers, and only when we cannot find any,we start searching externally. Therefore, the scalability operates differently. Another important aspect is elasticity, which may play a significant role in the external worker search system. There can be times when no external workers are available, and other times when the system experiences a heavy load.
- **Fault tolerance:** For fault tolerance reasons, it makes sense to separate the auction house and credit service from the Worker List, Worker Service, Job List, and Scheduler Service. The reason behind this separation is that if any errors occur in the auction house or credit system, the internal jobInformation assignment system can continue working, making sure that the main service is still working.
- **Data Security:** As both System deal with the same kind of sensitive Data. We don’t think that this disintegrator plays a role in separating Systems.
- **Extensibility:** Separating these systems provides better extensibility. As new features or external systems (e.g., additional auction services or third-party worker databases) are introduced, they can be added to the External Work Searcher system without requiring changes to the internal jobInformation assignment process. This separation makes future development easier, as each part of the system can be extended independently.

### Integrators
- **Workflow and Choreography:** The Scheduler Service works closely with the Job List and Worker List services, and these services are in constant communication. Therefore, we put them into one system. In the External Worker Searcher system, the Auction House communicates with the Credits Service, so we combined them into a single service. Although the Auction House also interacts with the Worker List, the criteria set by the disintegrators are more important to us and are the reason to keep them separated
- **Shared Code:** The Workers List and the Worker Service will have the same Shared Library so it is important to put them together. The same goes for the credits and the auction System so we put these also together.
- **Data Relationships:** The Auction House relies on data from external workers, while the internal jobInformation assignment depends on data from the External Work Searcher and also maintains its own data. We aim to keep the data separate because we believe fault tolerance is more important than having one database for both systems.



## Consequences
### Positive Consequences:
- **Modular Extensibility:** By separating the two domains (internal jobInformation assignment and external worker search), each part of the system can evolve independently. New features related to external worker management, such as integrating additional auction houses or implementing different bidding mechanisms, can be developed and deployed without impacting the internal jobInformation assignment systems.
- **Targeted Scalability:** Internal and external systems can scale independently based on their specific load requirements. The internal system can handle many internal workers simultaneously, while the external system scales dynamically based on demand for external workers, leading to more efficient resource utilization.
- **Enhanced Fault Tolerance:** Failures in the external worker search system will not affect the internal jobInformation assignment system, ensuring core functionalities remain operational. If the Auction House or Credit System goes down, the internal workers continue to be assigned jobs without interruption.
- **Interoperability and Integration:** The separation encourages clear API-driven communication between systems, simplifying integration with third-party systems like external worker databases or additional auction systems.

### Negative Consequences:
- **Data Consistency Risks:** Maintaining data consistency between the Internal Job Assignment and External Work Searcher systems may require additional overhead. While APIs can manage data flows, ensuring consistent state across two separate systems could introduce complexity and potential latency issues.
- **Increased Complexity in Deployment:** Having two distinct systems may require more sophisticated deployment processes. Teams will need to manage separate deployments for Internal Job Assignment and External Work Searcher systems, potentially increasing the operational burden.
- **Coordination Challenges for Cross-System Changes:** Any changes that affect both systems (e.g., modifications in the Worker List that impact both internal and external workflows) will need careful coordination to avoid introducing bugs or downtime.
