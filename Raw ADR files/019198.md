# ADR-001: Modular Monolith Architecture

## Status

Accepted

## Context

Trama is a project focused on building a platform for discovering local artists. The project has several competing concerns:

1. **Team Size**: Single developer project, which makes managing multiple services and deployments challenging.

1. **Scalability Needs**: MVP targets 1,000 users and 1,000 artists. This scale doesn't require distributed architecture.

1. **Modularity Requirements**: The domain naturally divides into distinct modules (Auth, Users, Artists, Search) that should have clear boundaries.

1. **Future Flexibility**: While starting simple, we want the option to extract services later if needed.

1. **Deployment Complexity**: Managing multiple services, databases, and inter-service communication adds operational overhead that's unnecessary at MVP stage.

The key tension is between keeping things simple and development velocity versus building in modularity for future growth.

## Decision

We will use a **Modular Monolith** architecture with the following characteristics:

1. **Single Deployable Unit**: All modules compile into one API application
2. **Clear Module Boundaries**: Each module (Auth, Users, Artists, Search) has its own Domain, Application, and Infrastructure layers
3. **Shared Kernel**: Common base classes and interfaces in Shared.Domain, Shared.Application, and Shared.Infrastructure
4. **No Cross-Module Dependencies**: Modules communicate through shared interfaces and events, never direct references
5. **Per-Module DbContext**: Each module has its own DbContext, all connecting to the same PostgreSQL database
6. **Event-Driven Communication**: Modules communicate asynchronously via MassTransit events


## Consequences

### Positive

- **Simplified Deployment**: Single application to build, test, and deploy. No need for container orchestration or service mesh.
- **Easier Development**: Run entire application locally with one command. No need to manage multiple services during development.
- **Faster Iteration**: Changes across modules don't require coordinating deployments or API versioning.
- **Lower Operational Complexity**: One application to monitor, one set of logs, simpler troubleshooting.
- **Better Learning Focus**: Can focus on domain logic, database design, and frontend rather than distributed systems concerns.
- **Future Extraction Path**: Clear module boundaries make it possible to extract to microservices later if needed.

### Negative

- **Scaling Limitations**: Can only scale vertically (bigger server) not horizontally (more servers) without significant refactoring.
- **Deployment Coupling**: All modules deploy together. A bug in one module requires redeploying everything.
- **Technology Lock-in**: All modules must use the same technology stack (.NET 9).
- **Shared Database**: All modules share one database, creating a potential bottleneck and single point of failure.
- **Memory Footprint**: All modules loaded in memory even if some are rarely used.
- **Team Scaling**: Harder for multiple teams to work independently since they share a codebase.

### Neutral

- **Module Boundaries**: Require discipline to maintain. Without enforcement, modules can become tightly coupled.
- **Event-Driven Communication**: Adds complexity compared to direct method calls, but less than distributed messaging.
- **Testing Strategy**: Can test modules in isolation or together, providing flexibility.

## Notes

This decision aligns with the "start with a monolith" philosophy advocated by Martin Fowler and others. The modular structure provides an extraction path if we reach scale where microservices make sense (likely 10,000+ users, multiple teams).

Key indicators that would trigger reconsidering this decision:
- Individual modules becoming performance bottlenecks
- Need for independent scaling of specific modules
- Multiple teams working on the codebase
- Different technology requirements for different modules
