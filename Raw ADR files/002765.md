# ADR-0006: Persistence (JPA/Hibernate vs jOOQ vs Exposed)

## Status
Accepted (2025-12-26)

## Context
We need a persistence approach that supports:
- schema-per-module ownership and clear boundaries,
- auditability for money/event tables,
- predictable query performance (catalog/search feeds, admin views),
- Kotlin ergonomics and long-term maintainability.

Kotlin + JPA works, but can introduce proxy/lazy-loading pitfalls and accidental N+1 queries. A type-safe SQL approach can be more explicit and easier to reason about as the system grows.

## Decision
Use **Flyway** for migrations and **jOOQ** for data access in V1 (type-safe SQL), with Spring-managed transactions.

## Options Considered
1) JPA/Hibernate (Spring Data JPA)
2) jOOQ + Flyway (chosen)
3) Exposed (Kotlin SQL DSL)

## Pros / Cons
### 1) JPA/Hibernate
Pros:
- Familiar Spring ecosystem and fast CRUD scaffolding.
- Good for simple aggregates when used carefully.
Cons:
- Kotlin friction (open classes, proxies) and runtime surprises.
- Performance pitfalls (lazy loading, N+1) can become costly quickly.

### 2) jOOQ + Flyway
Pros:
- Explicit SQL, predictable performance, type-safe query construction.
- Clear separation between domain models and persistence records.
- Plays well with schema-per-module and complex reporting queries.
Cons:
- Code generation adds build complexity (requires DB schema for generation).
- More boilerplate than JPA for trivial CRUD.

### 3) Exposed
Pros:
- Kotlin-first DSL; pleasant for Kotlin-only teams.
Cons:
- Less common in Spring Boot production environments; ecosystem/tooling less mature than jOOQ.

## Consequences
- We must set up jOOQ codegen deterministically (local + CI).
- We should avoid “active record” style patterns; keep repositories per module.
- Domain invariants live in services, not in ORM mappings.

## Rollback
If jOOQ codegen becomes too heavy early:
- Use JPA for specific modules with very simple CRUD while keeping Flyway migrations,
- keep repository interfaces stable so swapping implementations later is contained.
