# ADR-0003: Dual Solver Strategy (Optimal + Speed)

**Status**: Accepted
**Date**: October 12, 2025
**Deciders**: Architecture Team

## Context

The app needs to provide solving algorithms for users at different skill levels and with different goals. We must decide:

- What type(s) of solving algorithms to implement
- How to balance computational efficiency with educational value
- How to serve both beginners and advanced speed cubers

Key considerations:

- **Beginners** want to understand how to solve the cube and learn standard methods
- **Speed cubers** want to learn efficient, practical algorithms used in competitions
- **Puzzle enthusiasts** are curious about computer-optimal solutions
- Educational value of showing different approaches

Algorithm types available:

1. **Optimal solvers**: Find minimal move solutions (e.g., Kociemba, IDA*)
2. **Speed-cubing methods**: Human-friendly algorithms (CFOP, Roux, ZZ)
3. **Beginner methods**: Layer-by-layer approaches with fewer algorithms to memorize

## Decision

**We will implement two distinct solving algorithms:**

1. **Optimal Solver**: Kociemba's algorithm (or similar two-phase solver) that finds near-optimal solutions (targeting solutions within God's Number of 20 moves)
2. **Speed Solver**: CFOP (Fridrich method) implementation using standard "sexy move" sequences and common algorithm sets (F2L, OLL, PLL)

Both solvers will be available to all users, with clear explanations of their differences and use cases.

## Alternatives Considered

### Single Optimal Solver Only

**Pros**:

- Simpler implementation (one algorithm to maintain)
- Always provides shortest solution
- Demonstrates computer solving efficiency

**Cons**:

- Optimal solutions use non-intuitive move sequences
- Does not teach practical speed-cubing techniques
- Not how humans actually solve cubes
- Less educational value for aspiring speed cubers

**Why not chosen**: Does not serve the "learn to speed-solve" use case; lacks educational value for human-practical techniques.

### Single Speed Method Only (CFOP)

**Pros**:

- Focus on practical, learnable techniques
- Aligns with competition standards
- Simpler implementation

**Cons**:

- Longer solutions compared to optimal solvers
- Users miss seeing optimal computer efficiency
- No comparison between approaches

**Why not chosen**: Missing opportunity to demonstrate computer efficiency and provide educational comparison.

### Multiple Speed Methods (CFOP + Roux + ZZ)

**Pros**:

- Accommodates different learning preferences
- Shows variety of solving approaches
- Appeals to method enthusiasts

**Cons**:

- Significantly more complex implementation
- Maintenance burden for multiple algorithms
- UI complexity in presenting choices
- Diminishing returns (CFOP is dominant)

**Why not chosen**: Added complexity not justified by user benefit; CFOP is the dominant method in competitive speed-cubing.

### God's Number Solver (Optimal in ≤20 moves)

**Pros**:

- Truly optimal solutions ([God's Number proven to be 20](https://www.cube20.org/))
- Theoretically interesting

**Cons**:

- Computationally prohibitive on mobile (requires massive lookup tables)
- Impractical for on-device implementation
- Does not improve educational value over Kociemba

**Why not chosen**: Computational and storage requirements make this infeasible for mobile devices.

## Consequences

### Positive

1. **Educational Comparison**: Users see difference between computer-optimal and human-practical approaches
2. **Serves Multiple Skill Levels**: Beginners learn practical methods; enthusiasts explore optimal solutions
3. **Flexibility**: Users choose algorithm based on context (learning vs. speed practice)
4. **Showcases App Sophistication**: Dual algorithms demonstrate technical depth
5. **Clear Differentiation**: "Optimal" vs "Speed" labels clearly communicate trade-offs
6. **Real-World Relevance**: CFOP teaches actual competition techniques

### Negative

1. **Increased Complexity**: Two algorithms to implement, test, and maintain
2. **More UI Surface Area**: Need interface for algorithm selection and explanation
3. **Performance Variance**: Optimal solver expected to be slower than speed solver; actual performance to be measured
4. **Potential Confusion**: Users might not understand which to use when
5. **Testing Burden**: Must validate both algorithms across all cube states

### Neutral

1. **Algorithm Maintenance**: Both algorithms well-established; unlikely to need changes
2. **Code Duplication**: Some shared logic (move representation), but largely separate implementations

## Rationale

The dual-solver approach maximizes **educational value and user choice** while remaining technically feasible.

### Key Factors

#### Different Use Cases Require Different Solutions

**Optimal Solver Use Cases**:

- "What's the most efficient solution to this cube?"
- "How does a computer solve it?"
- Curiosity and puzzle-solving interest
- Demonstrating minimum move count

**Speed Solver Use Cases**:

- "How would I solve this in competition?"
- Learning practical algorithms (F2L, OLL, PLL)
- Practicing look-ahead and efficiency
- Understanding standard "sexy move" patterns

#### Educational Philosophy

The app's mission is education. Showing both approaches teaches:

- How humans and computers approach problems differently
- Trade-offs between optimality and practicality
- Why speed cubers use specific patterns (recognition speed)

#### Technical Feasibility

- Both algorithms expected to run efficiently on-device
- Performance targets to be validated through implementation:
  - Kociemba: Responsive for one-time solution requests
  - CFOP: Real-time or near-real-time response
- Neither requires backend or excessive memory

#### Market Differentiation

Most 3x3 cube puzzle apps provide only one or the other. Providing both demonstrates sophistication and educational depth.

### Testing Requirements

- Validate both solvers produce valid solutions
- Performance testing on minimum device (iPhone 12)
- Correctness testing with randomized cube states
- Edge case testing (already-solved, one-move-away, etc.)
