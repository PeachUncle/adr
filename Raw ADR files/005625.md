# ADR-0001: Monorepo Consolidation - Flatten Directory Structure

**Date**: 2025-10-30
**Status**: Accepted
**Deciders**: Architecture Team
**Affects**: Project structure, all Python imports, deployment scripts

## Context

The project previously had a nested directory structure with the backend living in `chronos-forecasting/aimoto-backend/` while the frontend lived in `aimoto/frontend/`. This created:

1. **Confusion**: Unclear which is the "real" backend directory
2. **Long paths**: Complicated import statements and file references
3. **Dependency ambiguity**: `chronos-forecasting` is both a directory AND a package dependency
4. **Build complexity**: Docker and scripts had to navigate deep nesting
5. **Onboarding friction**: New developers confused by directory layout

## Decision

Flatten the directory structure by moving the backend from `chronos-forecasting/aimoto-backend/` directly to `aimoto-backend/` at the monorepo root.

**New Structure:**
```
/project-root/
├── aimoto/                 (frontend)
│   └── frontend/
├── aimoto-backend/         (backend - moved from nested structure)
├── data/                   (shared data)
├── docs/                   (documentation)
└── scripts/                (utilities)
```

## Rationale

1. **Clarity**: Clear distinction between `aimoto-backend` (directory) and `chronos-forecasting` (dependency package)
2. **Simplicity**: Shorter paths reduce cognitive load
3. **Alignment**: Directory structure matches project name (`aimoto`)
4. **Build efficiency**: Simpler Docker build contexts and script references
5. **Git history**: Renaming directory preserves commit history
6. **Developer experience**: Shorter working directory paths and import statements

### Trade-offs Made

- **One-time refactoring effort**: ~80 files needed import updates
- **Path calculation changes**: All `.parent` references in Path calculations needed adjustment
- **Breaking change**: External references to old directory structure would break (mitigated by no external dependencies)

## Alternatives Considered

### Alternative A: Keep Nested Structure
- **Pros**: No refactoring effort, existing scripts work as-is
- **Cons**: Continued confusion, complex paths, harder to scale

### Alternative B: Move Backend to Different Location
- **Pros**: Different approach
- **Cons**: Would still require refactoring, unclear if alternative is better

### Alternative C: Create Symlinks
- **Pros**: Avoids refactoring
- **Cons**: Fragile, masks underlying problem, creates maintenance burden

## Consequences

### Positive
- ✅ Clearer directory structure for all developers
- ✅ Simpler import statements (`from aimoto_backend import ...`)
- ✅ Cleaner Docker build contexts
- ✅ Easier to navigate project layout
- ✅ Better IDE support (shorter paths)
- ✅ Simplified CI/CD scripts

### Negative
- ⚠️ Required comprehensive refactoring of 80+ files
- ⚠️ All path calculations needed adjustment for `.parent` indices
- ⚠️ One-time effort to update all references

### Neutral
- Git history is preserved through git mv
- No functional changes to code behavior

## Implementation Notes

This decision was implemented as part of a larger architectural refactoring (ÉTAPE 14). The consolidation significantly improved code clarity and developer experience without affecting functionality.

Key learning: Path calculations in Python scripts need careful attention when moving source code directories. All `.parent` references must be adjusted for the new nesting depth.
