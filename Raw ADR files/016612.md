# ADR-013: Virtualized Scroll with LiveView Streams

## Status

Accepted

## Date

2025-10-04

## Context

The TransactionLive.Index page initially used traditional list-based pagination with an infinite scroll pattern. As the number of transactions grew, several issues emerged:

### Problems with Previous Approach

1. **Memory Growth**: All loaded transactions remained in memory (`assigns.transactions`)
2. **DOM Bloat**: Every loaded transaction added to the DOM, degrading performance
3. **Unreliable Viewport Detection**: Phoenix LiveView's `phx-viewport-top` and `phx-viewport-bottom` had inconsistent behavior with table elements
4. **Mobile UX Issues**: Nested scroll containers created poor mobile experience
5. **State Management Complexity**: Manual list manipulation for updates/deletes prone to bugs

### Requirements

- Support large transaction datasets (1000+ items)
- Maintain smooth scrolling performance
- Enable bidirectional pagination (forward and backward)
- Provide reliable infinite scroll on all devices
- Support real-time updates (PubSub integration)
- Export functionality for visible and all transactions

---

## Decision

Implement **virtualized scrolling** using Phoenix LiveView Streams combined with custom JavaScript IntersectionObserver hooks.

### Core Components

#### 1. LiveView Streams

Replace `assigns.transactions` list with stream-based rendering:

```elixir
# Before
socket |> assign(:transactions, transactions)

# After
socket |> stream(:transactions, transactions, at: -1, limit: page_size * 3)
```

**Benefits:**

- Automatic DOM virtualization (keeps max 3 pages in DOM)
- Built-in memory management
- Efficient updates via `stream_insert/3` and `stream_delete/3`

#### 2. Bidirectional Pagination

Track current page and load adjacent pages on demand:

```elixir
# Loader module handles pagination
def load_transactions(socket, new_page, reset? \\ false)
  # Prepend when going backward (new_page < current_page)
  # Append when going forward (new_page > current_page)
```

#### 3. JavaScript IntersectionObserver Hook

Custom `VirtualizedScroll` hook with sentinel-based detection:

```javascript
// Top sentinel triggers prev-page
this.topObserver = new IntersectionObserver(
  (entries) => {
    if (entry.isIntersecting && page > 1) {
      this.pushEvent("prev-page", {});
    }
  },
  { threshold: 0, rootMargin: "400px" },
);

// Bottom sentinel triggers next-page
this.bottomObserver = new IntersectionObserver(
  (entries) => {
    if (entry.isIntersecting && has_more) {
      this.pushEvent("next-page", {});
    }
  },
  { threshold: 0, rootMargin: "400px" },
);
```

#### 4. Sentinel Elements

Invisible markers for scroll detection:

```heex
<!-- Top sentinel -->
<tr id="top-sentinel" data-page={@page} style="height: 1px;">
  <td colspan="5"></td>
</tr>

<!-- Transaction rows -->
<tr :for={{dom_id, transaction} <- @streams.transactions} id={dom_id}>
  ...
</tr>

<!-- Bottom sentinel -->
<tr id="bottom-sentinel" data-has-more={to_string(@has_more)} style="height: 1px;">
  <td colspan="5"></td>
</tr>
```

### Implementation Details

**Module Structure:**

```
TransactionLive.Index (420 LOC)
├── State (127 LOC) - State initialization
├── Loader (96 LOC) - Data loading with streams
├── Calculations (152 LOC) - Financial calculations
└── VirtualizedScroll Hook (66 LOC) - Scroll detection
```

**Event Flow:**

1. User scrolls → Sentinel enters viewport
2. IntersectionObserver fires → `prev-page` or `next-page` event
3. LiveView handler → Calls `Loader.load_transactions(socket, new_page)`
4. Loader → Fetches page from database
5. Stream update → Adds new items, prunes old (keeps 3 pages max)
6. DOM updates → New transactions visible, old removed

**Real-time Updates:**

```elixir
def handle_info({:transaction_created, transaction}, socket) do
  # Increment counter, don't auto-add (user pulls to refresh)
  socket |> update(:new_transactions_count, &(&1 + 1))
end

def handle_info({:transaction_updated, transaction}, socket) do
  socket |> stream_insert(:transactions, transaction)
end

def handle_info({:transaction_deleted, transaction}, socket) do
  socket |> stream_delete(:transactions, transaction)
end
```

## Consequences

### Positive

1. **Performance**
   - DOM size capped at ~60 elements (3 pages × 20 items)
   - Memory usage constant regardless of scroll depth
   - Smooth scrolling even with 1000+ transactions

2. **Reliability**
   - IntersectionObserver works consistently across browsers
   - Sentinel-based detection more reliable than `phx-viewport-*`
   - No nested scroll containers (better mobile UX)

3. **Maintainability**
   - Stream operations simpler than manual list manipulation
   - Clear separation of concerns (State, Loader, Calculations)
   - Easier to test (no race conditions with list updates)

4. **User Experience**
   - Single scroll behavior (no nested scrollbars)
   - Bidirectional navigation (scroll up to see previous)
   - Real-time updates via streams
   - Fast initial load (only 20 items)

### Negative

1. **Complexity**
   - Custom JavaScript hook required
   - Learning curve for stream-based patterns
   - More files to maintain (4 modules vs 1)

2. **Export Limitations**
   - "Visible" scope exports current page only (not all loaded)
   - Need separate query for currently visible items

3. **Testing Changes**
   - Tests need to use `data-phx-stream` instead of list access
   - Hook interactions harder to test than simple events

### Neutral

1. **Migration**
   - All tests updated and passing (651 tests)
   - Backward compatible with existing data
   - No database schema changes required

---

## Alternatives Considered

### 1. Continue with `phx-viewport-*` Attributes

**Rejected:** Unreliable with table elements, inconsistent browser behavior

### 2. Manual Pagination Buttons

**Rejected:** Poor UX compared to infinite scroll, extra clicks required

### 3. Load More Button

**Rejected:** Less intuitive than automatic loading, requires user action

### 4. Server-Side Cursor Pagination

**Rejected:** More complex implementation, doesn't solve DOM bloat issue

### 5. Third-Party Virtual Scroll Libraries

**Rejected:** Adds dependencies, not optimized for LiveView, harder to customize

## Metrics

### Before

- File size: 726 LOC (monolithic)
- DOM elements: Unbounded (all loaded transactions)
- Memory usage: O(n) where n = transactions loaded
- Scroll performance: Degrades with >100 items

### After

- Main file: 420 LOC (42% reduction)
- Total: 795 LOC across 4 focused modules
- DOM elements: Max 60 (3 pages × 20 items)
- Memory usage: O(1) constant (virtualized)
- Scroll performance: Consistent regardless of dataset size
