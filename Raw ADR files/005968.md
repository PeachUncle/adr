# ADR-005: Transaction Confirmation Tracking

**Status**: Proposed  
**Date**: 2024-01-XX  
**Deciders**: Staff Engineer Candidate, Jacquin Mininger  

## Context

After transaction submission, must wait for blockchain inclusion and finality:

- **Latency Requirement**: Detect confirmation ASAP for user feedback
- **Finality Rules**: Different chains have different confirmation requirements
  - Ethereum: 12 confirmations (~2.5 minutes)
  - Arbitrum: 1 confirmation (~250ms)
  - Base/Optimism: 3-5 confirmations
- **Reorganizations**: Blocks can be reorganized, reverting transactions
- **Dropped Transactions**: Can be evicted from mempool without notification

## Decision

Implement a **hybrid tracker** with WebSocket subscriptions for real-time updates, falling back to adaptive polling when WebSockets are unavailable.

**Key Principles**:
1. **Real-Time Updates**: WebSocket subscriptions for instant confirmation detection
2. **Reliable Fallback**: Adaptive polling ensures confirmation even if WebSocket fails
3. **Adaptive Intervals**: Increase polling frequency after first confirmation
4. **Reorg Detection**: Track block reorganizations and affected transactions

## Trade-offs

**Chosen: Hybrid WebSocket + Polling**

*Advantages*:
- ✅ Low latency with WebSocket (real-time)
- ✅ Reliable fallback to polling
- ✅ Adaptive intervals save RPC resources
- ✅ Reorg detection built-in

*Disadvantages*:
- ⚠️ More complex than polling-only
- ⚠️ WebSocket connection management overhead
- ⚠️ Dual code paths to maintain

**Alternative: Polling Only** - Rejected

*Why Rejected*:
- ❌ Higher latency (3-12s intervals)
- ❌ More RPC load (constant polling)
- ✅ Simpler implementation (only benefit)

**Alternative: WebSocket Only** - Rejected

*Why Rejected*:
- ❌ Single point of failure
- ❌ Some RPC providers don't support WebSockets
- ❌ No fallback during connection issues

## Metrics & Monitoring

Key metrics:
- `confirmation_latency_seconds` - Time from submission to confirmation
- `pending_confirmations` - Current tracking count
- `confirmations_by_source` - WebSocket vs polling breakdown
- `dropped_txs_total` - Transactions lost from mempool
- `reorgs_total` - Block reorganization events

Alert conditions:
- `confirmation_latency_seconds` p99 > 60s → Slow confirmations
- `websocket_connected` = 0 for >5 min → WebSocket down, relying on polling
- `dropped_txs_total` > 5 in 1 hour → High mempool eviction rate

## Confirmation Requirements by Chain

| Chain | Required Confirmations | Average Time | Reasoning |
|-------|----------------------|--------------|-----------|
| Ethereum | 12 | ~2.5 min | Protect against deep reorgs |
| Arbitrum | 1 | ~250ms | L2 finality via L1 posting |
| Base | 3 | ~6s | L2 with fast finality |
| Optimism | 3 | ~6s | L2 with fast finality |
| BSC | 15 | ~45s | Higher reorg risk than Ethereum |
