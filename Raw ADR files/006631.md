# ADR 3.4: Error-As-Learning and Replay Semantics

- Status: Accepted (2025-10-29)
- Owners: Reliability & Observability Guild
- Tags: resilience, replay, telemetry, incident-response

## Context
- V3 must satisfy production-grade reliability with traceable recovery from tool outages, credential failures, and upstream data loss.
- Earlier releases treated tool errors as terminal events or logged them inconsistently, preventing effective RCA and automated improvement.
- The new blueprint mandates that every failure contribute to institutional knowledge while keeping user-facing commitments.

## Decision
- All tool invocations and agent actions SHALL record success or failure events in the execution log with structured error payloads (`error_code`, `retry_policy`, `root_cause_hint`).
- Master_Planner SHALL enforce an error-handling policy: attempt deterministic retries when safe, trigger REPLAN when alternate strategy exists, otherwise produce a user-facing diagnostic.
- Reflection_Critique nodes SHALL treat failure events as learning opportunities, appending remediation notes that feed post-run analytics and future planning heuristics.
- Replay jobs SHALL consume the same log segment to reproduce the failure, verify fixes, and certify that remediation steps resolve the incident without regressions.
- Incident alerts SHALL fire whenever retry budgets are exhausted or when specific error codes (auth, quota, schema mismatch) recur beyond thresholds.

## Consequences
- Pros: institutionalizes learning from failures, improves MTTR, supports compliance by proving controlled degradation, enables reproducible RCA.
- Cons: higher volume of telemetry data, need for robust alert routing, potential information overload without curated dashboards.
- Mitigation: aggregate failures by `tool_id` and `error_code`, surface actionable dashboards in Grafana, and rotate log archives to avoid storage bloat.

## Implementation Notes
- Error payload schema: `{ "tool_id": str, "error_code": str, "message": str, "attempt": int, "max_attempts": int, "retry_after": Optional[int] }`.
- Replay harness SHALL exist in `backend/python/tests/replay/` to run deterministic replays against stored logs.
- Frontend SHALL surface failure states in Tool Manager and Active Report components using real API data, never static placeholders.
