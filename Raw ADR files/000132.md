# ADR-0011: GitHub Actions CI/CD Configuration

**Date**: 2024-10-12
**Status**: Accepted

## Context

Continuous Integration and Deployment (CI/CD) is essential for maintaining code quality and catching issues early. For iOS projects hosted on GitHub, several CI/CD options exist:

1. **GitHub Actions**: Native GitHub CI/CD platform
2. **CircleCI**: Third-party CI service with iOS support
3. **Travis CI**: Traditional CI service
4. **Bitrise**: iOS-specialized CI platform
5. **Jenkins**: Self-hosted CI server
6. **Xcode Cloud**: Apple's native CI/CD (new in 2021)

The choice affects:

- Cost (free tier limits vs. paid plans)
- Performance (build times, concurrency)
- Integration with GitHub features
- Configuration complexity
- Team familiarity and maintenance

For open-source projects, cost-effectiveness and ease of setup are particularly important, while still maintaining professional quality standards.

## Decision

**We will use GitHub Actions as our CI/CD platform with a configuration that emphasizes script composition, efficiency, and clear reporting.**

Key implementation decisions:

1. **Platform**: GitHub Actions (not CircleCI, Bitrise, etc.)
2. **Runner**: `macos-15` with Xcode 16
3. **Xcode Selection**: Explicit version (`Xcode_16.0.app`)
4. **Concurrency**: Cancel in-progress runs on new pushes
5. **Script Reuse**: Call `scripts/run-ci-locally.sh` (DRY principle)
6. **Summary Reports**: Use GitHub Actions Summary for test results
7. **Artifact Upload**: Preserve test results and coverage reports
8. **Trigger Events**: Push to main/develop, PRs, manual dispatch

## Alternatives Considered

### 1. Xcode Cloud (Apple's Native CI)

Using Apple's first-party CI/CD service.

**Why not chosen**:

- Costs money after free tier (25 compute hours/month)
- Less flexible than GitHub Actions
- Newer service, less community knowledge
- Configuration in Xcode (not in repo)
- This is an open-source project (cost matters)
- Less integration with non-Apple services

### 2. CircleCI

Popular third-party CI service with good iOS support.

**Why not chosen**:

- Requires account with separate service
- Free tier limitations (500 credits/month)
- Additional configuration complexity
- Less tight integration with GitHub
- Good option but GitHub Actions is "good enough"
- Costs more for open source projects

### 3. Bitrise

iOS-specialized CI/CD platform.

**Why not chosen**:

- Specialized for iOS (good) but costs money
- Free tier very limited for open source
- Another external service to manage
- Configuration in UI (less version controlled)
- Overkill for straightforward build/test workflow
- More complex than needed

### 4. Self-Hosted Jenkins

Self-managed CI server with iOS agents.

**Why not chosen**:

- Requires infrastructure management
- Need to provision macOS machines
- High maintenance overhead
- Not cost-effective for small projects
- Complex setup for contributors
- Poor fit for open source

### 5. Travis CI

Traditional open-source CI service.

**Why not chosen**:

- Free tier eliminated for open source (2020)
- Lost popularity in iOS community
- Slower than GitHub Actions
- Less active development
- GitHub Actions is better integrated

## Consequences

### Positive

1. **Zero Cost**: Free for public GitHub repositories
2. **Native Integration**: Built into GitHub, no separate accounts
3. **Good Performance**: macOS runners with recent Xcode versions
4. **Version Controlled**: `.github/workflows/` in repository
5. **Rich Ecosystem**: Huge action marketplace
6. **Excellent Documentation**: Well-documented, large community
7. **Modern Features**: Concurrency control, job summaries, artifacts
8. **Flexible Triggers**: Push, PR, manual, scheduled
9. **Script Reuse**: Calls same scripts as local development (DRY)
10. **Easy Debugging**: Can run scripts locally (`./scripts/run-ci-locally.sh`)

### Negative

1. **GitHub Dependency**: Tied to GitHub platform
2. **Runner Constraints**: Limited macOS versions available
3. **Queue Times**: Shared runners may have wait times
4. **Less iOS-Specific**: Not specialized for iOS like Bitrise
5. **Minute Limits**: 2000 minutes/month for free tier (10x multiplier for macOS)

### Mitigation Strategies

- **Script Composition**: Keep CI logic in scripts, easy to migrate platforms
- **Local Testing**: `make ci` runs exact same workflow locally
- **Efficient Workflows**: Cancel in-progress runs to save minutes
- **Selective Triggers**: Only run on meaningful branches/events

## Rationale

The decision prioritizes **cost-effectiveness, simplicity, and maintainability** for an open-source project.

Key factors:

1. **Free for Open Source**: GitHub Actions is completely free for public repos
2. **Native Integration**: No external services, no separate logins
3. **Good Enough**: Meets all requirements without over-engineering
4. **Community Standard**: Most open-source projects use GitHub Actions now
5. **Easy Migration**: Script-based approach means platform changes are easy
6. **Modern Platform**: Active development, new features regularly

For a commercial project with higher throughput needs, Bitrise or Xcode Cloud might make sense. For open source, GitHub Actions is the pragmatic choice.

## Implementation Details

### Workflow File: `.github/workflows/ci.yml`

```yaml
name: CI

on:
  workflow_dispatch:  # Allow manual trigger
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main, develop ]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build-and-test:
    name: Build and Test
    runs-on: macos-15

    steps:
    - name: Checkout code
      uses: actions/checkout@v4

    - name: List runner info
      run: sw_vers && arch

    - name: Select Xcode version
      run: sudo xcode-select -s /Applications/Xcode_16.0.app/Contents/Developer

    - name: Show Xcode version
      run: xcodebuild -version

    - name: Run CI pipeline
      run: make ci

    - name: Generate GitHub Actions summary
      if: always()
      run: |
        # Parse test results and coverage
        # Output to $GITHUB_STEP_SUMMARY

    - name: Upload test results
      uses: actions/upload-artifact@v4
      if: always()
      with:
        name: test-results
        path: |
          ./TestResults.xcresult
          ./test-results.json
          ./coverage.json
          ./coverage-report.txt
```

### Key Configuration Choices

#### 1. Runner Selection: `macos-15`

**Why macos-15**:

- Latest stable macOS on GitHub Actions
- Supports Xcode 16
- Best performance for current iOS development
- Includes all necessary tools (xcrun, simctl, etc.)

**Alternatives considered**:

- `macos-14`: Older, but still supports Xcode 15
- `macos-latest`: Would auto-upgrade, potentially breaking changes

**Decision**: Explicit `macos-15` for stability, upgrade deliberately

#### 2. Xcode Selection: Explicit Version

```yaml
- name: Select Xcode version
  run: sudo xcode-select -s /Applications/Xcode_16.0.app/Contents/Developer
```

**Why explicit**:

- Reproducible builds (same Xcode version always)
- No surprises from runner Xcode upgrades
- Clear documentation of requirements

**Alternatives considered**:

- Accept default Xcode (changes over time)
- Use latest Xcode (unpredictable)

**Decision**: Explicit version, upgrade deliberately

#### 3. Concurrency Control

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

**Why concurrency control**:

- Saves CI minutes (cancel outdated runs)
- Faster feedback (don't wait for old runs)
- Typical workflow: push fixes, want latest results

**Benefit**: On rapid pushes, only latest commit runs (saves ~20 minutes per cancelled run)

#### 4. Script Composition

```yaml
- name: Run CI pipeline
  run: make ci
```

Which calls:

```bash
make ci → scripts/run-ci-locally.sh
  → scripts/build-release.sh
  → scripts/run-tests.sh
```

**Why script composition**:

- DRY: Logic in one place (scripts)
- Local Testing: `make ci` works identically
- Maintainability: Update scripts, not YAML
- Portability: Easy to migrate to other CI platforms

**Alternatives considered**:

- Inline xcodebuild commands in YAML (duplicates Makefile)
- GitHub Actions steps (less composable)

**Decision**: Delegate to scripts (see ADR0010)

#### 5. GitHub Actions Summary

```yaml
- name: Generate GitHub Actions summary
  if: always()
  run: |
    echo "## Test Summary" >> $GITHUB_STEP_SUMMARY
    echo "- **Total Tests:** $TESTS_RUN" >> $GITHUB_STEP_SUMMARY
    echo "- **Passed:** ✅ $TESTS_PASSED" >> $GITHUB_STEP_SUMMARY
```

**Why summary**:

- Quick visual feedback in GitHub UI
- No need to dig through logs
- Shows results even if run fails
- Professional presentation

**Example output**:

```markdown
## Test Summary
- **Total Tests:** 7
- **Passed:** ✅ 7
- **Failed:** ❌ 0

## Code Coverage
- **Overall Coverage:** 85.5%
```

#### 6. Artifact Upload

```yaml
- name: Upload test results
  uses: actions/upload-artifact@v4
  if: always()
  with:
    name: test-results
    path: |
      ./TestResults.xcresult
      ./coverage.json
```

**Why artifacts**:

- Preserve full test results
- Download for local analysis
- Runs even if tests fail (`if: always()`)
- Useful for debugging CI failures

**Retention**: 90 days default (configurable)

### Trigger Configuration

```yaml
on:
  workflow_dispatch:  # Manual trigger
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main, develop ]
```

**Why these triggers**:

- **Push to main/develop**: Validate main branches
- **Pull requests**: Validate before merge
- **Manual dispatch**: Debug or special runs
- **Not on all branches**: Save CI minutes

**Branch strategy**:

- `main`: Production-ready code
- `develop`: Integration branch
- Feature branches: Validated via PR

### Simulator Selection

Delegates to Makefile:

```yaml
run: make ci
```

Which auto-detects simulator (see ADR0006):

```makefile
DETECTED_SIM := $(shell xcrun simctl list devices available iPhone 2>/dev/null | ...)
SIMULATOR ?= platform=iOS Simulator,name=$(or $(DETECTED_SIM),iPhone 16)
```

**Why delegate**:

- Works on any developer machine
- Works in CI with any available simulators
- No hardcoded simulator names in CI config
- Consistent with local development

## Cost Analysis

### GitHub Actions Free Tier

**For public repositories**: Unlimited minutes ✅

**For private repositories**:

- 2000 minutes/month free
- macOS minutes count as 10x (1 macOS minute = 10 Linux minutes)
- Effective: 200 macOS minutes/month free

**This project (public)**: No cost ✅

### Estimated Usage

**Per CI run**:

- Build + test: ~2-3 minutes
- Typical PR: 1 run
- Typical push: 1 run

**Monthly estimate**:

- ~100 runs/month (active development)
- ~300 minutes total
- **Cost**: $0 (public repo)

### Comparison

| Platform | Free Tier | This Project |
|----------|-----------|--------------|
| **GitHub Actions** | Unlimited (public) | ✅ Free |
| CircleCI | 500 credits/month | ⚠️ Limited |
| Travis CI | No free tier | ❌ Costs money |
| Bitrise | 45 minutes/month | ❌ Not enough |
| Xcode Cloud | 25 hours/month | ✅ Free (but overkill) |

## Monitoring and Maintenance

### Regular Checks

- **Monthly**: Review failed runs, adjust workflows
- **Quarterly**: Update Xcode version
- **Annually**: Review platform choice

### Update Process

1. **Xcode updates**: Update runner image and xcode-select path
2. **Action updates**: `uses: actions/checkout@v4` → v5
3. **Script updates**: Modify `scripts/` (automatically used)
4. **Dependency updates**: SwiftLint, pre-commit versions

### Performance Optimization

**Current**: ~2-3 minutes per run

**Future optimizations**:

- Cache derived data (if needed)
- Parallel test execution (if test suite grows)
- Skip builds on doc-only changes

**Decision**: Keep simple until needed

## Migration Path

If we need to change platforms later:

**Easy migration because**:

1. CI logic is in scripts (`scripts/`)
2. Local testing is identical (`make ci`)
3. Minimal YAML-specific logic
4. Standard xcodebuild commands

**Steps to migrate**:

1. Create config for new platform
2. Call `./scripts/run-ci-locally.sh`
3. Adjust artifact handling (platform-specific)
4. Done!

**Estimated effort**: 1-2 hours
