# ADR-012: Ash Framework Preparation Modules Pattern

## Status

Accepted

## Date

2025-09-20

## Context

Ash Framework resources support preparations - functions that modify queries before execution. Initially, SharedLedger used inline preparations directly in resource action definitions:

```elixir
read :list_paginated do
  prepare fn query, _ ->
    # Inline logic here
    Ash.Query.sort(query, transaction_date: :desc)
  end
end
```

As preparation logic grew complex (date presets, sorting, filtering), inline definitions became:

- Hard to test
- Difficult to reuse
- Cluttered resource files
- Harder to understand

## Decision

We adopted the Ash Framework's recommended pattern of extracting preparations into dedicated modules:

1. **Create Preparation Modules**: Each logical preparation gets its own module
2. **Use Standard Interface**: Implement `Ash.Resource.Preparation` behaviour
3. **Organize by Resource**: Place under `ResourceName/Preparations/` directory
4. **Single Responsibility**: Each module handles one concern

## Consequences

### Positive

- **Testability**: Preparations can be unit tested in isolation
- **Reusability**: Same preparation can be used across multiple actions
- **Clarity**: Resource files focus on declaration, not implementation
- **Maintainability**: Logic is organized and easy to find
- **Documentation**: Each preparation can have proper moduledoc
- **Composability**: Preparations compose naturally in pipelines

### Negative

- **More Files**: Each preparation needs its own file
- **Indirection**: Must navigate to another file to see logic
- **Learning Curve**: Developers need to understand the pattern

### Neutral

- **Performance**: No runtime difference, same execution
- **Debugging**: Stack traces show module names instead of anonymous functions

## Implementation

### Structure

```
lib/shared_ledger/ledger/transaction/
├── preparations/
│   ├── default_sort.ex
│   ├── handle_date_preset.ex
│   └── with_limit.ex
└── transaction.ex
```

### Preparation Module Example

```elixir
defmodule SharedLedger.Ledger.Transaction.Preparations.DefaultSort do
  @moduledoc """
  Applies default sorting to transaction queries.
  Transactions are sorted by transaction_date (desc), then inserted_at (desc).
  """
  use Ash.Resource.Preparation

  @impl true
  def prepare(query, _opts, _context) do
    Ash.Query.sort(query, transaction_date: :desc, inserted_at: :desc)
  end
end
```

### Resource Usage

```elixir
defmodule SharedLedger.Ledger.Transaction do
  use Ash.Resource, domain: SharedLedger.Ledger, data_layer: AshPostgres.DataLayer

  alias SharedLedger.Ledger.Transaction.Preparations

  actions do
    read :list_paginated do
      prepare Preparations.DefaultSort
      prepare Preparations.HandleDatePreset
      prepare Preparations.WithLimit
    end
  end
end
```

### Testing

```elixir
defmodule SharedLedger.Ledger.Transaction.Preparations.DefaultSortTest do
  use SharedLedger.DataCase

  alias SharedLedger.Ledger.Transaction.Preparations.DefaultSort

  test "applies correct sorting" do
    query = Ash.Query.new(Transaction)
    prepared = DefaultSort.prepare(query, %{}, %{})

    assert prepared.sort == [
      {:transaction_date, :desc},
      {:inserted_at, :desc}
    ]
  end
end
```

## Pattern Guidelines

### When to Extract

- Logic > 5 lines
- Reused across actions
- Complex business logic
- Needs testing
- Multiple concerns mixed together

### When to Keep Inline

- Simple one-liners
- Action-specific logic
- Trivial transformations

### Naming Conventions

- Module: `ResourceName.Preparations.VerbNoun`
- Examples: `HandleDatePreset`, `ApplyDefaults`, `ValidatePermissions`

## Migration Path

1. **Identify Complex Preparations**: Find inline preparations > 5 lines
2. **Extract to Modules**: Create preparation modules with behaviour
3. **Update Resource**: Replace inline with module reference
4. **Add Tests**: Write unit tests for preparations
5. **Document**: Add moduledoc explaining purpose

## Alternatives Considered

1. **Keep Inline**
   - Pros: Everything in one file, less navigation
   - Cons: Poor testability, cluttered resources

2. **Shared Preparations Module**
   - Pros: Fewer files
   - Cons: Violates single responsibility, harder to test

3. **Mixin Modules**
   - Pros: Could share across resources
   - Cons: Complex, against Ash patterns
