# ADR-003: Single-Region Deployment for Data Residency Compliance

## Status
Accepted

## Context
User-uploaded images may contain personally identifiable content, and many
institutions require that data remain within their legal jurisdiction.
Waste-management guidance also varies by region, so inference and storage must
not cross national or provincial boundaries.

Options considered:
1. Global multi-region active-active deployment  
2. Cross-region replication (S3 + DynamoDB global tables)  
3. Single-region deployment for each jurisdiction  

## Decision
The Trash Sorter system is deployed as a **self-contained stack per region**
(e.g., `ca-central-1` for Canada).  
All components — API Gateway, Lambda, S3 buckets, DynamoDB tables, logs,
and the weekly aggregate-insights export job — operate **only** within that
region. No cross-region replication is enabled.

## Rationale
- Ensures clear compliance with regional data residency requirements  
- Simplifies auditing and red-bar testing (all resources exist in exactly one region)  
- Prevents accidental cross-border transfer of user images  
- Guarantees that **30-day retention** policies are enforced **per region**

## Consequences

**Positive**
- Strong residency and privacy guarantees  
- Easy to verify using automated tests (`test_data_residency_single_region`)  
- Each region has its own S3 bucket, lifecycle rules, EXIF stripping, and idempotent request-id storage  
- Predictable behavior for future multi-region deployments  

**Negative**
- No cross-region failover: if the region goes down, the service is unavailable  
- Higher cost when scaling internationally (separate buckets, logs, Lambda, export jobs per region)  
- Requires an explicit routing layer (DNS or client-side) to connect users to their allowed region  

## Future Work
Scaling beyond Canada would involve:
- Deploying the same stack independently in each permitted region  
- Routing users to the correct region based on jurisdiction  
- Ensuring every region maintains:  
  - its own S3 image bucket  
  - its own 30-day lifecycle policy  
  - its own DynamoDB prediction table  
  - its own weekly aggregate-insights export job  
- Running data residency tests per region to prevent silent drift
