# ADR 0003: Compound Components Pattern

**Date:** 2025-10-11  
**Status:** ✅ Accepted  
**Deciders:** Architecture Team  
**Related:** ADR 0001 (Component Classification), ADR 0002 (Slots Pattern)

---

## Context

After classifying 60 components, we identified **10 components (17%)** as Tier 4 (Compound) - components where multiple related sub-components need to share state.

**Problem:**
How do we handle components where multiple parts need to communicate and share state?

**Examples:**
- **Accordion:** Items need to know which item is open (single mode) or which items are open (multiple mode)
- **Tabs:** Tab triggers and content panels need to share active tab state
- **RadioGroup:** Radio items need to know which one is selected
- **DropdownMenu:** Trigger and content need to share open/close state

**Bad approaches:**

```typescript
// ❌ Props drilling nightmare
<Accordion activeItem="1" onItemChange={...}>
  <AccordionItem itemId="1" isActive={activeItem === "1"} onToggle={...}>
    {/* Props hell! */}
  </AccordionItem>
</Accordion>

// ❌ Monolithic configuration
<Accordion 
  items={[
    { title: "Item 1", content: "..." },
    { title: "Item 2", content: "..." },
  ]}
/>
// Not flexible, can't customize individual items
```

**Research conducted:**
- Radix UI compound primitives (industry standard)
- React Context best practices
- HeroUI composition patterns
- Headless UI approach

---

## Decision

We adopt the **Compound Components Pattern** with React Context for Tier 4 components.

### What is Compound Components Pattern?

Multiple related components work together, sharing state via Context:

```typescript
<Accordion type="single" collapsible>
  <AccordionItem value="1">
    <AccordionTrigger>What is React 19?</AccordionTrigger>
    <AccordionContent>
      React 19 introduces...
    </AccordionContent>
  </AccordionItem>
  
  <AccordionItem value="2">
    <AccordionTrigger>What is TypeScript 5.9?</AccordionTrigger>
    <AccordionContent>
      TypeScript 5.9 adds...
    </AccordionContent>
  </AccordionItem>
</Accordion>
```

### Architecture

**Three layers:**

1. **Context:** Shared state
2. **Root Component:** Provides context
3. **Sub-Components:** Consume context

### Implementation Pattern

**1. Context Layer:**
```typescript
// accordion-context.tsx
import { createContext, useContext } from 'react';

export interface AccordionContextValue {
  value?: string | string[];
  onValueChange?: (value: string | string[]) => void;
  type?: 'single' | 'multiple';
  disabled?: boolean;
}

export const AccordionContext = createContext<AccordionContextValue | null>(null);

export function useAccordionContext() {
  const context = useContext(AccordionContext);
  
  if (!context) {
    throw new Error(
      'useAccordionContext must be used within an Accordion component'
    );
  }
  
  return context;
}
```

**2. Root Component:**
```typescript
// accordion.tsx
import * as Radix from '@radix-ui/react-accordion';
import { AccordionContext } from './accordion-context';

export function Accordion({ 
  type, 
  value, 
  onValueChange, 
  disabled, 
  classNames, 
  children, 
  ...props 
}: AccordionProps) {
  const contextValue = { type, value, onValueChange, disabled };

  return (
    <AccordionContext.Provider value={contextValue}>
      <Radix.Root
        type={type}
        value={value}
        onValueChange={onValueChange}
        className={cn('accordion-root', classNames?.root)}
        {...props}
      >
        {children}
      </Radix.Root>
    </AccordionContext.Provider>
  );
}
```

**3. Sub-Components:**
```typescript
// accordion-item.tsx
export function AccordionItem({ value, disabled, classNames, children, ...props }: AccordionItemProps) {
  const context = useAccordionContext(); // Access shared state
  
  return (
    <Radix.Item
      value={value}
      disabled={disabled ?? context.disabled}
      className={cn('accordion-item', classNames?.item)}
      {...props}
    >
      {children}
    </Radix.Item>
  );
}

// accordion-trigger.tsx
export function AccordionTrigger({ classNames, children, ...props }: AccordionTriggerProps) {
  return (
    <Radix.Header>
      <Radix.Trigger className={cn('accordion-trigger', classNames?.trigger)} {...props}>
        {children}
        <ChevronDownIcon />
      </Radix.Trigger>
    </Radix.Header>
  );
}
```

### Export Strategy

**Option 1: Named Exports (Recommended)**
```typescript
export { Accordion } from './accordion';
export { AccordionItem } from './accordion-item';
export { AccordionTrigger } from './accordion-trigger';
export { AccordionContent } from './accordion-content';
export { useAccordionContext } from './accordion-context';

// Usage
import { Accordion, AccordionItem, AccordionTrigger, AccordionContent } from '@xidoke/ui-react';
```

**Why:** Better tree-shaking, clearer imports, TypeScript friendly

**Option 2: Compound Object (Alternative)**
```typescript
const Accordion = Object.assign(AccordionRoot, {
  Item: AccordionItem,
  Trigger: AccordionTrigger,
  Content: AccordionContent,
});

// Usage
<Accordion>
  <Accordion.Item>
    <Accordion.Trigger>...</Accordion.Trigger>
  </Accordion.Item>
</Accordion>
```

**Decision:** Use **Option 1 (Named Exports)** for better tree-shaking.

## Rationale

### Why Compound Pattern?

**Alternatives considered:**

#### 1. Props Drilling
```typescript
<Accordion activeItem={activeItem}>
  <AccordionItem id="1" isActive={activeItem === "1"} onToggle={handleToggle}>
```
❌ **Rejected:**
- Props hell (10+ props per item)
- Not scalable
- Tedious to use
- Error-prone

#### 2. Monolithic Configuration
```typescript
<Accordion items={[{ title: "...", content: "..." }]} />
```
❌ **Rejected:**
- Not flexible (can't customize individual items)
- Can't compose with other components
- Limited to predefined structure
- Not composable

#### 3. Render Props
```typescript
<Accordion>
  {({ activeItem, setActiveItem }) => (
    <AccordionItem active={activeItem === "1"}>
  )}
</Accordion>
```
⚠️ **Rejected:**
- More complex than Context
- Harder to type
- Less discoverable
- Not as flexible

#### 4. Compound Components with Context ✅ **Selected**
```typescript
<Accordion type="single">
  <AccordionItem value="1">
    <AccordionTrigger>...</AccordionTrigger>
    <AccordionContent>...</AccordionContent>
  </AccordionItem>
</Accordion>
```
✅ **Advantages:**
- Flexible composition
- Clean API
- Type-safe
- Follows React patterns
- Used by Radix UI (industry standard)
- Scalable
- Discoverable

### Why Only 10 Components (17%)?

**Components requiring compound pattern:**
1. Accordion
2. Tabs
3. RadioGroup
4. DropdownMenu
5. ContextMenu
6. NavigationMenu
7. Select
8. Collapsible (simple compound)
9. Stepper
10. Breadcrumbs (optional)

**Most components (83%) don't need shared state:**
- Simple components work independently
- Complex components only need slots
- Only use compound when state sharing is essential

## Consequences

### Positive

✅ **Flexible Composition**
- Users compose components freely
- Can customize any part
- Can add custom elements between sub-components

✅ **Clean API**
- No props drilling
- Each component focused on its responsibility
- Intuitive usage

✅ **Type Safety**
- TypeScript enforces correct usage
- Context hook throws error if used outside provider
- Autocomplete for sub-components

✅ **Scalability**
- Easy to add new sub-components
- State management centralized
- Clear separation of concerns

✅ **Follows React Patterns**
- Uses Context API (React standard)
- Hooks-based (modern React)
- Composable (React philosophy)

✅ **Integration with Radix UI**
- Wraps Radix primitives cleanly
- Adds our styling + slots
- Maintains accessibility

✅ **Testable**
- Can test context provider
- Can test sub-components independently
- Can test integration

### Negative / Trade-offs

⚠️ **Complexity**
- More files per component (9-10 files)
- Context setup required
- Hook for context access
- Mitigation: Templates via Plop, clear docs

⚠️ **Learning Curve**
- Developers must understand Context
- Must understand compound pattern
- Must understand when to use it
- Mitigation: Comprehensive docs, examples, training

⚠️ **Bundle Size**
- More code than simple components
- Context overhead (minimal)
- Mitigation: Tree-shaking, only 17% of components

⚠️ **Runtime Check**
- Context existence check on every render
- Mitigation: Negligible performance impact, better DX

### Risks

🟡 **Risk: Context Misuse**
- Impact: Using sub-component outside provider crashes
- Mitigation: **Error message in hook**, clear docs
- Example: `throw new Error('Must be used within Accordion')`

🟡 **Risk: Context Pollution**
- Impact: Too much in context, performance issues
- Mitigation: **Only essential state in context**
- Rule: Only shared state, not all state

🟢 **Risk: Over-use**
- Impact: Using compound for simple components
- Mitigation: **Clear guidelines** (only Tier 4)
- Validation: Architecture review

## Best Practices

### 1. Always Check Context
```typescript
export function useAccordionContext() {
  const context = useContext(AccordionContext);
  if (!context) {
    throw new Error('useAccordionContext must be used within Accordion');
  }
  return context;
}
```

### 2. Type Context Strictly
```typescript
// ✅ Explicit types
export interface AccordionContextValue {
  value?: string | string[];
  onValueChange?: (value: string | string[]) => void;
}

// ❌ Loose types
type AccordionContextValue = Record<string, any>;
```

### 3. Export Context Hook
```typescript
// Allow advanced users to access context
export { useAccordionContext } from './accordion-context';
```

### 4. Document Compound Usage
Include usage examples in component README showing composition.
