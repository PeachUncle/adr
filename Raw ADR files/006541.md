# Decision: Sentence-Level Granularity for Stage 1 Narrative Assembly

Date: 2025-11-09

## Context

The two-stage pipeline (ADR-0004) required deciding on the granularity of clips for LLM processing. Word-level data provides maximum precision but comes with a significant token cost. Sentence-level data is more compact but potentially limits editing flexibility.

Token cost analysis revealed:
- **Word-level format:** ~28,000-33,000 tokens for 1000 words (compact array format)
- **Sentence-level format:** ~6,000-8,000 tokens for 1000 words (~67 sentences)
- **Savings:** 75-80% token reduction with sentence-level

Additionally, the existing storyboard.py system already preferred sentence boundaries, with the semantic validator marking mid-sentence cuts as errors.

## Options Considered

- **Option A: Word-Level Throughout**
  - Use word-level data for both Stage 1 (narrative assembly) and Stage 2 (length optimization)
  - Pros: Maximum precision, can make mid-sentence cuts, can trim individual filler words
  - Cons: High token cost (~28k-33k tokens), slower LLM processing, more validation errors from incomplete thoughts

- **Option B: Sentence-Level Throughout**
  - Use sentence-level data for both stages
  - Pros: 75-80% token savings, guaranteed coherence, faster LLM processing
  - Cons: Cannot make mid-sentence cuts, cannot trim filler within sentences, coarser granularity

- **Option C: Hybrid (Sentence for Stage 1, Word for Stage 2)**
  - Stage 1: Sentence-level for narrative assembly
  - Stage 2: Word-level for length optimization (when implemented)
  - Pros: Token savings for Stage 1, precision available in Stage 2 when needed, best of both
  - Cons: Need to maintain both formats, slightly more complex data flow

## Decision

Chose **Option C (Hybrid)** - Sentence-level for Stage 1, with option for word-level in future Stage 2.

**Rationale:**

1. **Stage 1 goal is narrative assembly, not precision trimming**
   - Sentence is the natural unit for story structure
   - Hook, setup, core value, proof are all sentence-level concepts
   - Complete thoughts are more important than word-precise cuts at this stage

2. **75% token savings = cheaper experiments and production**
   - Lower cost per project
   - More iterations during development
   - Faster LLM processing (smaller context)

3. **Filler handling is already algorithmic**
   - `clip_analyzer.py` can filter sentences with >60% filler ratio before LLM sees them
   - Heavy-filler sentences get dropped in preprocessing

4. **Current system already prefers sentence boundaries**
   - Existing prompt instructs: "Prefer ending segments at sentence boundaries (where is_sentence_end = 1)"
   - Semantic validator marks mid-sentence cuts as errors
   - In practice, LLM already selects sentence-aligned ranges most of the time

5. **Stage 2 can use word-level when implemented**
   - When implementing length optimization (future work)
   - Can trim filler words from selected sentences
   - Precision cuts when hitting target duration

**Clip granularity:** Sentence-level as base unit
- Cleaner cuts (respects thought boundaries)
- Easier for LLM to reason about semantic intent
- Can still reference word-level metrics (energy, pitch) for sentence scoring
- Matches existing `sentence_id` and `is_sentence_end` flags from word_metrics.py

**Sentence-level format:**
```json
{
  "sentence_id": 0,
  "text": "Complete sentence text here.",
  "start": 0.0,
  "end": 3.5,
  "duration": 3.5,
  "word_count": 8,
  "avg_energy": 0.25,
  "max_energy": 0.45,
  "avg_pitch": 120.5,
  "pitch_variance": 0.15,
  "filler_ratio": 0.0,
  "engagement_score": 0.85
}
```

## Consequences

**Positive:**
- 75-80% reduction in LLM token cost for Stage 1
- Faster LLM processing (6k-8k tokens vs 28k-33k)
- Guaranteed semantic coherence (complete thoughts)
- Fewer validation errors (no incomplete sentences)
- Easier for LLM to reason about narrative structure
- Can still achieve precision in Stage 2 if needed

**Negative:**
- Cannot make mid-sentence cuts in Stage 1
- Cannot trim individual filler words within sentences (must drop whole sentence)
- Need to maintain both sentence-level and word-level formats
- Slightly more complex data flow between stages

**Affected Areas:**
- `clip_analyzer.py` (new service): Groups words by sentence_id, computes sentence-level scores
- `narrative_assembler.py` (new service): Works with sentence-level clips
- `length_optimizer.py` (future): May use word-level for precision trimming
- LLM prompt design: Simpler prompts (reasoning about sentences vs word ranges)
- Token budget: Can process ~4x more content in same context window

**Hybrid benefit:**
This approach gives us BOTH advantages:
- **Stage 1:** Token savings + guaranteed coherence (sentence-level)
- **Stage 2:** Precision trimming when needed (word-level)

**Fallback plan:**
If testing reveals that sentence-level narrative quality is insufficient, can revert Stage 1 to word-level with minimal refactoring (data transformation layer already in place).

**Example comparison:**
- **Current System (Word-Level):** LLM receives 1000 words × 11 fields = ~28k tokens, selects arbitrary word ranges
- **Stage 1 (Sentence-Level):** LLM receives 67 sentences × ~100 tokens = ~6k tokens, selects complete thoughts
- **Token Savings:** 22,000 tokens (~$0.04 per project at Claude pricing)
