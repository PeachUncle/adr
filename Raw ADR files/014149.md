# P-SRE-001: Data Access Through EF Core Only

## Status
Accepted

## Date
2025-10-02

## Context

The Platform SRE microservice requires a consistent and maintainable approach to data access. As the microservice grows in complexity, it becomes critical to establish clear boundaries and standards for how data is accessed and manipulated within the application.

Currently, the microservice uses Entity Framework Core (EF Core) as the primary Object-Relational Mapping (ORM) framework, as evidenced by the existing infrastructure components like `EfRepository.cs` and `EfErrorBudgetWindowConfiguration.cs`. However, without explicit architectural constraints, developers might be tempted to:

- Use raw SQL queries directly against the database
- Implement alternative data access patterns (e.g., ADO.NET, Dapper)
- Bypass the repository pattern and domain models
- Access the database through different ORMs or micro-ORMs

This lack of standardization could lead to:
- Inconsistent data access patterns across the codebase
- Difficulty in maintaining data integrity and business rules
- Challenges in testing and mocking data access layers
- Potential security vulnerabilities through uncontrolled SQL execution
- Loss of benefits from EF Core's features (change tracking, migrations, LINQ, etc.)

## Decision

**All data access within the Platform SRE microservice MUST be performed exclusively through Entity Framework Core (EF Core). Any other method of data access is strictly forbidden.**

This decision encompasses the following constraints:

1. **No Raw SQL**: Direct SQL queries, stored procedure calls, or any raw database commands are prohibited
2. **No Alternative ORMs**: Usage of other ORMs (Dapper, NHibernate, etc.) or micro-ORMs is not allowed
3. **No Direct Database Connections**: Direct ADO.NET connections or any database-specific drivers are forbidden
4. **Repository Pattern Enforcement**: All data access must go through the established repository pattern using `IRepository<T>` and `EfRepository<T>`
5. **Domain Model Consistency**: All database entities must be represented as proper domain models accessible through EF Core's DbContext

### Approved Data Access Methods:
- EF Core LINQ queries through repositories
- EF Core change tracking and SaveChanges operations
- EF Core migrations for schema changes
- EF Core configurations for entity mappings
- Repository pattern implementations extending `EfRepository<T>`

### Exceptions:
- Database migrations and schema management through EF Core tools
- Read-only reporting queries may use EF Core with `AsNoTracking()` for performance optimization
- Integration tests may use EF Core In-Memory provider for testing purposes

## Consequences

### Positive:
- **Consistency**: Uniform data access patterns across the entire microservice
- **Maintainability**: Single point of responsibility for data access concerns
- **Type Safety**: Strong typing and compile-time checking through LINQ
- **Change Tracking**: Automatic change detection and transaction management
- **Migration Support**: Automated schema versioning and deployment
- **Testing**: Easier unit testing with in-memory providers and mocking
- **Performance**: Built-in query optimization and caching mechanisms
- **Security**: Protection against SQL injection through parameterized queries

### Negative:
- **Performance Limitations**: Some complex queries might be less efficient than raw SQL
- **Learning Curve**: Developers must be proficient in EF Core and LINQ
- **Framework Dependency**: Strong coupling to Microsoft's EF Core ecosystem
- **Query Limitations**: Certain advanced database features might not be accessible

### Mitigation Strategies:
- Provide comprehensive EF Core training for the development team
- Establish performance monitoring to identify and optimize slow queries
- Create reusable query extensions and specifications for complex scenarios
- Document best practices for EF Core usage within the microservice

## Compliance and Enforcement

- Code reviews must verify adherence to this decision
- Static analysis tools should be configured to detect violations
- CI/CD pipelines should include automated checks for non-EF Core data access
- Any exceptions to this rule must be explicitly approved by the architecture team and documented as a separate ADR
