# ADR 001: Why Nx Monorepo

## Status

Accepted

## Context

The RACR (Resource Allocation and Conflict Resolution) system requires a robust, scalable architecture that can support multiple applications (web frontend, API backend, worker services) while maintaining code reusability, consistent tooling, and efficient development workflows. We needed to decide between a monorepo approach versus multiple separate repositories.

## Decision

We will use an Nx monorepo to house all RACR system components, including:

- `apps/web` - Next.js PWA frontend
- `apps/api` - NestJS GraphQL API
- `apps/workers/*` - Various NestJS worker services
- `libs/*` - Shared libraries for types, utilities, UI components, etc.

## Rationale

### Benefits of Monorepo Approach

1. **Shared Code and Types**: Common interfaces, types, and utilities can be shared across all applications without publishing to npm or maintaining version compatibility.

2. **Atomic Commits**: Changes that span multiple applications (e.g., API schema changes and frontend updates) can be committed atomically, ensuring consistency.

3. **Single Build Pipeline**: One CI/CD pipeline can build, test, and deploy all components together, reducing complexity and ensuring integration.

4. **Developer Experience**: Nx provides powerful tooling for code generation, dependency management, and caching, improving development velocity.

5. **Refactoring Safety**: Large-scale refactoring across the entire codebase is safer and easier to manage.

### Alternatives Considered

#### Multiple Repositories

- **Pros**: Clear boundaries, independent deployment, smaller codebase per repo
- **Cons**: Code duplication, version drift between shared libraries, complex release coordination, harder to maintain consistency

#### Single Repository (non-monorepo)

- **Pros**: Simple structure
- **Cons**: No tooling for managing dependencies between apps, harder to scale, poor developer experience

## Consequences

### Positive

- Faster development cycles due to shared tooling and code
- Reduced bugs from version mismatches
- Easier refactoring and architectural changes
- Better code reuse and consistency

### Negative

- Larger repository size
- All developers need access to entire codebase
- Potential for tighter coupling between teams

## Implementation Notes

- Use Nx's `libs/` structure for shared code
- Maintain clear boundaries between applications using Nx project tags
- Use Nx's dependency graph to enforce architectural rules
- Leverage Nx caching for faster CI builds
