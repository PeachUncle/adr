# ADR-004: Use In-Memory Storage for Initial Implementation

## Status
Accepted (Inferred from implementation - likely temporary)

## Context
The system needed a data storage mechanism for the product catalog. As this appears to be a reference implementation or proof of concept for .NET Framework to Core migration, the team needed to decide on the initial storage approach.

Considerations:
- Simplicity for demonstration purposes
- Focus on architecture patterns rather than infrastructure
- Quick setup without external dependencies
- Easy to understand for developers learning the pattern

## Decision
Implement in-memory storage using a simple singleton `List<ProductDto>` in the `Products` class.

Implementation details:
- Products stored in a `List<ProductDto>` field
- Singleton lifetime via Autofac DI registration
- No persistence between application restarts
- No database setup required
- No external dependencies for storage

## Consequences

### Positive
- **Zero Configuration**: No database setup or connection strings needed
- **Fast Development**: No time spent on database design or migrations
- **Simple to Understand**: Clear and straightforward implementation
- **Fast Performance**: No network latency or disk I/O
- **Easy Testing**: No need for test database or mocking
- **Focus on Patterns**: Allows focus on CQRS and migration patterns
- **Portable**: Runs anywhere without external dependencies

### Negative
- **Data Loss**: All data lost when application restarts
- **Not Production Ready**: Cannot be used in production environment
- **No Concurrency Control**: Potential race conditions with concurrent modifications
- **Limited Scalability**: Cannot scale beyond single instance
- **No Query Capabilities**: Cannot perform complex queries efficiently
- **Memory Limitations**: Data limited by available RAM
- **No Transaction Support**: Cannot rollback failed operations
- **No Data Validation**: No database-level constraints

### Risks
- **False Simplicity**: Might give wrong impression about production complexity
- **Migration Debt**: Switching to real database requires significant refactoring
- **Concurrency Issues**: Thread-safety not properly handled
- **Memory Leaks**: Unbounded growth if products are never removed
- **Testing Gap**: Tests don't cover real database scenarios

## Notes
Current implementation issues:
- Not thread-safe (no locking mechanism)
- No interface abstraction for the repository
- Singleton pattern means shared state across all requests
- No cleanup or memory management

## Alternatives Considered

1. **Entity Framework Core with SQL Server**
   - Pro: Production-ready, full ACID compliance
   - Con: Requires SQL Server setup, more complex

2. **SQLite Database**
   - Pro: File-based, no server required, still uses EF Core
   - Con: Additional configuration, migration management

3. **NoSQL (MongoDB/RavenDB)**
   - Pro: Document-oriented fits DTOs well
   - Con: External dependency, different query paradigm

4. **Redis Cache**
   - Pro: Fast, supports persistence
   - Con: External service requirement

5. **File-Based JSON Storage**
   - Pro: Simple, persistent, human-readable
   - Con: Poor performance, concurrency issues

## Migration Path

To migrate to production storage:

### Phase 1: Add Repository Interface
```csharp
public interface IProductRepository
{
    Task AddAsync(ProductDto product);
    Task<List<ProductDto>> GetAllAsync();
}
```

### Phase 2: Implement Entity Framework Core
1. Add EF Core packages
2. Create `ProductEntity` and `DbContext`
3. Implement `IProductRepository` with EF Core
4. Add database migrations
5. Configure connection strings

### Phase 3: Update Handlers
1. Make handlers async
2. Inject `IProductRepository` instead of `Products`
3. Add transaction support
4. Implement error handling

## Recommendations

### Immediate (for learning/demo purposes)
1. Add thread-safety with `ConcurrentBag` or locking
2. Create `IProductRepository` interface
3. Add memory limit checks
4. Implement basic cleanup mechanism

### Before Production
1. **Must** implement proper database storage
2. Add transaction support
3. Implement concurrency control
4. Add data validation and constraints
5. Design proper domain models separate from DTOs
6. Implement repository and unit of work patterns
7. Add integration tests with real database
8. Consider using EF Core with code-first approach
9. Implement audit logging for data changes
10. Add backup and recovery procedures

## Decision Review
This decision is appropriate for a proof of concept or learning exercise but must be revisited before any production use. The in-memory implementation successfully demonstrates the CQRS pattern and .NET migration approach without the complexity of database setup.
