# ADR-002: LSM Tree over B-Tree for Storage Engine

**Status**: Accepted  
**Date**: 2025-10-31  
**Deciders**: Core Team

## Context

VEGA requires a storage engine optimized for:
- High write throughput (distributed log replication)
- MVCC with multiple versions per key
- Range scans
- Disk efficiency

Two main approaches: **LSM-tree** (Log-Structured Merge-tree) vs **B-tree**.

## Decision

Use **LSM-tree** as the storage engine.

## Rationale

### LSM-Tree Characteristics
- **Write-optimized**: Sequential writes to WAL + memtable, batched flushes
- **Append-only**: No in-place updates, perfect for MVCC
- **Compaction**: Merges SSTables in background, amortizes cost
- **Read amplification**: May need to check multiple SSTables

### B-Tree Characteristics
- **Read-optimized**: Single tree lookup, O(log n)
- **Random writes**: In-place updates require disk seeks
- **Write amplification**: Tree rebalancing, page splits
- **MVCC complexity**: Versioning requires additional structures

### Why LSM for VEGA?

1. **Write-Heavy Workload**
   - Raft log replication → many writes per transaction
   - Multi-version writes (MVCC) → more write volume
   - LSM handles this better with sequential I/O

2. **MVCC Natural Fit**
   - Append-only SSTables → versions never overwritten
   - Tombstones for deletes
   - Compaction cleans up old versions

3. **Proven in Similar Systems**
   - CockroachDB: Uses RocksDB (LSM)
   - TiDB: Uses RocksDB (LSM)
   - Cassandra: LSM-based
   - LevelDB/RocksDB: Battle-tested

4. **Range Scan Efficiency**
   - SSTables are sorted → efficient range iteration
   - Block-based index for skip-ahead

## Implementation Strategy

### Phase 0-1: MVP
- WAL: Simple append-log with fsync
- Memtable: BTreeMap (Rust stdlib) → good enough for MVP
- SSTable: Custom format with [Entries][Index][Footer]
- Compaction: Manual/triggered, size-tiered

### Phase 2+: Production
- Memtable: Skiplist for better concurrency
- Compaction: Leveled + size-tiered hybrid
- Bloom filters: Reduce read amplification
- Block cache: LRU cache for hot SSTables

### LSM Workflow
```
Write → WAL (fsync) → Memtable (in-memory, sorted)
                         ↓ (when full)
                      Flush to SSTable (immutable, on-disk)
                         ↓ (background)
                      Compaction (merge SSTables, GC old versions)
```

## Consequences

### Positive
- ✅ High write throughput (sequential I/O)
- ✅ Natural MVCC support
- ✅ Good compression (compacted SSTables)
- ✅ Can use RocksDB as fallback (Phase 2)

### Negative
- ❌ Read amplification (check multiple SSTables)
- ❌ Write amplification (compaction rewrites data)
- ❌ Compaction overhead (CPU, I/O)
- ❌ Space amplification (old versions until compaction)

### Mitigations
- **Read amplification**: Bloom filters, block cache, compaction
- **Write amplification**: Tuned compaction triggers, leveled strategy
- **Compaction overhead**: Background threads, I/O scheduling
- **Space amplification**: Aggressive tombstone/version GC

## Alternatives Considered

### 1. B-Tree (Rejected)
- **Pros**: Lower read amplification, simpler
- **Cons**: Write amplification, MVCC complexity

### 2. RocksDB (Deferred to Phase 2)
- **Pros**: Production-ready, tuned LSM, C++ performance
- **Cons**: FFI overhead, less control, harder to customize
- **Decision**: Start with custom LSM for learning/control, migrate to RocksDB if needed

### 3. LMDB (Rejected)
- **Pros**: B-tree with MVCC built-in, zero-copy reads
- **Cons**: Write-ahead log required, copy-on-write overhead

## Performance Expectations

| Operation | Target Latency | Notes |
|-----------|----------------|-------|
| Point write | < 5ms (p50) | WAL fsync + memtable insert |
| Point read | < 3ms (p50) | Memtable + 1-2 SSTables |
| Range scan | < 50ms (1000 rows) | Sequential SSTable reads |
| Compaction | Background | <10% CPU target |
