# 3. Use Amazon Bedrock AgentCore Gateway for Unified MCP Server Architecture

Date: 2025-11-16

## Status

Accepted

## Context

Kiro Forge needs to expose multiple backend services (steering storage, search, analytics, synchronization) to various AI development environments including kiro, VSCode, Amazon Q Developer, and Q CLI. The system must provide:

- Unified access point for multiple backend services
- Secure authentication and authorization
- Tool discovery capabilities for AI agents
- Compatibility with Model Context Protocol (MCP)
- Scalability and managed infrastructure

Traditional approaches would require:
- Managing multiple MCP server endpoints
- Implementing custom authentication for each service
- Building tool discovery mechanisms from scratch
- Maintaining infrastructure for each service endpoint


## Decision

We will use Amazon Bedrock AgentCore Gateway as the unified MCP server endpoint for Kiro Forge, implementing a single Gateway with multiple Targets architecture.

### Architecture Pattern
```
Single AgentCore Gateway (MCP Server)
    ├── Target 1: Lambda - Steering CRUD Operations
    ├── Target 2: Lambda - Search & Discovery
    ├── Target 3: Lambda - Analytics Service (optional)
    └── Target 4: Lambda - Compliance Rules Endpoint (optional)
```

### Implementation Approach
- Create one AgentCore Gateway with OAuth authentication (Cognito)
- Enable semantic search for tool discovery
- Add each backend service as a separate Gateway Target
- Use Lambda targets for custom business logic
- Use OpenAPI targets for REST-based services
- Leverage Gateway's built-in IAM role for service-to-service authentication


## Consequences

### Positive
- **Single Endpoint**: Clients connect once to `gateway-id.gateway.bedrock-agentcore.region.amazonaws.com/mcp`
- **Unified Authentication**: OAuth tokens managed centrally through Cognito
- **Tool Discovery**: Semantic search enables agents to find relevant tools automatically
- **Managed Service**: No infrastructure provisioning or scaling concerns
- **Security**: Comprehensive ingress and egress authentication built-in
- **Flexibility**: Easy to add new services as additional targets without client changes
- **Cost Efficiency**: Pay only for actual usage, no idle infrastructure costs
- **Multi-Environment Support**: Same endpoint works across VSCode, Q Developer, and Q CLI
- **Easy Client Installation**: Standard MCP protocol means clients only need to add Gateway URL and OAuth credentials to their MCP configuration - no custom SDKs or complex setup required

### Negative
- **OAuth Requirement**: All clients must implement OAuth token flow

### Neutral
- **Target Limits**: Need to monitor number of targets per Gateway (can create multiple Gateways if needed)
- **Cold Start**: Lambda targets may experience cold start latency (mitigated by provisioned concurrency if needed)

## Alternatives Considered

### Alternative 1: Multiple Standalone MCP Servers
- Each service runs its own MCP server
- **Rejected**: Increases client complexity, requires managing multiple connections and authentication mechanisms

### Alternative 2: Custom API Gateway + Lambda
- Build custom MCP server implementation
- **Rejected**: Requires significant development effort, lacks built-in tool discovery and semantic search

### Alternative 3: Direct Lambda Function URLs
- Expose Lambda functions directly with function URLs
- **Rejected**: No MCP protocol support, lacks unified authentication and tool discovery
