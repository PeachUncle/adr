# ADR-003: Use Shared Contracts Library for Cross-Platform Compatibility

## Status
Accepted (Inferred from implementation)

## Context
The system consists of:
- A legacy .NET Framework 4.7.2 console application (client)
- A modern .NET Core 3.1 Web API (server)

These components need to share:
- Command and Query definitions
- Data Transfer Objects (DTOs)
- Interface definitions
- Common constants

The challenge was to maintain a single source of truth for these contracts while ensuring compatibility between .NET Framework and .NET Core.

## Decision
Create a shared contracts library (`NETCore.App.Contracts`) targeting .NET Standard 2.0, which is compatible with both:
- .NET Framework 4.7.2
- .NET Core 3.1

The contracts library contains:
- Command interfaces and implementations (`ICommand`, `AddProductCommand`)
- Query interfaces and implementations (`IQuery`, `GetProductsQuery`)
- DTOs (`ProductDto`, `RequestDto`)
- Shared constants (`HttpHeaderKeys`)

## Consequences

### Positive
- **Single Source of Truth**: Contract changes only need to be made in one place
- **Type Safety**: Compile-time checking of contract compatibility
- **Cross-Platform Compatibility**: .NET Standard 2.0 works with both platforms
- **Clean Separation**: Clear boundary between contracts and implementation
- **Refactoring Safety**: IDE refactoring tools work across all projects
- **Version Alignment**: Ensures client and server use same contract versions

### Negative
- **Deployment Coupling**: All components must be deployed with compatible contract versions
- **Limited to .NET Standard 2.0**: Cannot use latest C# features in contracts
- **Circular Dependency Risk**: Must be careful to keep contracts pure (no implementation logic)
- **Build Complexity**: Additional project in solution increases build time
- **Versioning Challenges**: Breaking changes affect all consumers

### Risks
- **Contract Pollution**: Tendency to add implementation details to contracts
- **Backward Compatibility**: Breaking changes require coordinated deployment
- **Over-sharing**: Risk of sharing too much, creating tight coupling

## Notes
Current implementation:
- Uses .NET Standard 2.0 for maximum compatibility
- References MediatR for `IRequest` interfaces
- Contains only interfaces, DTOs, and simple POCOs
- No business logic or implementation details

## Alternatives Considered

1. **Code Generation**: Generate contracts from OpenAPI/Swagger spec
   - Pro: Language agnostic
   - Con: Loss of type safety, more complex build process

2. **Duplicate Contracts**: Maintain separate contract definitions
   - Pro: Independent evolution
   - Con: Synchronization nightmare, drift over time

3. **REST without Shared Types**: Use only HTTP/JSON without shared .NET types
   - Pro: Maximum decoupling
   - Con: Loss of compile-time safety, more runtime errors

4. **Proto Contracts (gRPC)**: Use Protocol Buffers for contract definition
   - Pro: Language agnostic, efficient serialization
   - Con: More complex, overkill for simple HTTP/JSON

## Recommendations

1. **Keep Contracts Pure**: Never add implementation logic to contracts
2. **Version Carefully**: Use semantic versioning for contract changes
3. **Document Changes**: Maintain changelog for contract modifications
4. **Consider Contract Tests**: Add tests to verify contract compatibility
5. **Plan for Evolution**: Design contracts with future extensibility in mind
6. **Upgrade to .NET Standard 2.1**: When .NET Framework support is dropped
