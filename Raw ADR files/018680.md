# ADR-001: Programming Language Choice

## Status
Accepted

## Context
termctrl is a terminal automation tool that controls existing terminals (not a terminal emulator). Key requirements:

- **Fast startup**: CLI tool used frequently, cannot afford initialization delays
- **Small binary size**: Lightweight distribution for easy installation and storage efficiency
- **Cross-platform**: Support macOS, Linux, Windows with single codebase
- **Complex integrations**: iTerm2 Python API, AppleScript, tmux CLI, system APIs
- **Easy contribution**: Clear architecture and tooling to lower contributor barriers
- **Reliability**: Automation failures cascade to user workflows
- **Zero dependencies**: Single binary deployment for easy distribution

## Decision
**Go** with external process integration strategy.

*Revised from initial Rust decision based on contribution ease analysis.*

## Rationale

### Terminal Automation Challenges
Terminal automation presents unique technical challenges that drive language choice:

**Integration Complexity**
- iTerm2: Websocket communication with Python API + AppleScript fallback
- tmux: Command-line interface parsing and session management
- System APIs: Window focus control via platform-specific APIs

**Error Handling Requirements**
- Graceful degradation when terminals/APIs unavailable
- Clear diagnostics for complex automation failures
- Retry logic for unreliable external processes

**Performance Constraints**
- Sub-100ms startup for responsive CLI experience
- Concurrent operations across multiple terminal sessions
- Minimal resource usage when running alongside AI agents

### Language Evaluation

**Go: Chosen**
- ✅ **Significantly easier contribution**: Simple syntax, no ownership/lifetimes, faster compile times
- ✅ **Zero startup overhead**: Compiled binary with no runtime initialization
- ✅ **Compact binaries**: ~5-10MB statically linked binaries (acceptable vs. 2-5MB Rust)
- ✅ **Battery included standard library**: Rich stdlib for integration tasks (HTTP, JSON, exec, OS APIs)
- ✅ **Simple external processes**: `exec.Command` more straightforward than Rust subprocess handling
- ✅ **Effortless concurrency**: Goroutines much simpler than Rust async for terminal operations
- ✅ **Easy JSON/string parsing**: No ownership complexity when parsing terminal output
- ✅ **Cross-compilation**: Single pipeline produces all platform binaries
- ✅ **Readable error handling**: Explicit `if err != nil` easier for contributors
- ✅ **Integration-focused design**: Language optimized for I/O, networking, system integration
- ❌ **GC pauses**: Negligible impact for I/O-bound terminal automation
- ❌ **Less memory safety**: Acceptable trade-off for contribution ease

**Rust: Rejected**
- ✅ **Computational performance**: Excellent for CPU-intensive, algorithmic work
- ✅ **Maximum memory safety**: Zero-cost abstractions and compile-time guarantees
- ✅ **Smaller binaries**: ~2-5MB vs. Go's 5-10MB
- ✅ **Excellent tooling**: `cargo`, `rustfmt`, `clippy` create consistent development experience
- ✅ **Strong error types**: `Result<T,E>` provides robust error handling
- ❌ **High contribution barrier**: Ownership, lifetimes, borrow checker complexity
- ❌ **Integration overhead**: More verbose for I/O, JSON parsing, external processes
- ❌ **Computational focus mismatch**: Optimized for computation, not integration tasks
- ❌ **Overkill for use case**: Memory safety benefits less critical for terminal automation

**Python: Rejected**
- ✅ **Native iTerm2 integration**: Direct websocket API access
- ✅ **Low contributor barrier**: Widely known language, rapid iteration
- ✅ **Rapid prototyping**: Quick implementation of automation logic
- ❌ **Startup latency**: 50-200ms interpreter initialization unacceptable
- ❌ **Large distribution**: 50-100MB with bundled runtime vs. 2-5MB native binary
- ❌ **Distribution complexity**: Requires Python runtime management
- ❌ **Security concerns**: Bundling Python interpreter increases attack surface

### Integration Strategy

**iTerm2 Integration**
- Spawn Python subprocess for iTerm2 API communication using `exec.Command`
- AppleScript fallback via `osascript` execution
- WebSocket connection management using Go's `gorilla/websocket`

**Error Handling Approach**
- Capability detection before operations with explicit `if err != nil` checks
- Custom error types for each integration point
- User-friendly error messages with suggested fixes

**Security Model**
- Minimal external process privileges using `exec.CommandContext`
- Input validation for all external commands
- No shell injection vectors through parameterized commands

## Consequences

### Trade-offs Accepted
- **Slightly larger binaries**: 5-10MB vs. 2-5MB Rust (acceptable for contribution benefits)
- **GC overhead**: Minimal impact for I/O-bound terminal automation workload
- **Less memory safety**: Runtime panics possible but rare in terminal automation context
- **Ecosystem gaps**: Some terminal-specific libraries may need custom implementation

### Integration vs Computation Focus
termctrl is fundamentally an **integration application**, not a computational one:

**Integration Workload Characteristics**
- **I/O-bound operations**: 90% of time spent waiting for external processes (tmux, osascript, iTerm2 API)
- **Text processing**: Parsing terminal output, JSON responses, simple string manipulation
- **System API calls**: Window focus, notifications, environment variable access
- **External process orchestration**: Spawning subprocesses, managing communication channels

**Why Go Excels for Integration**
- **Battery-included stdlib**: `os/exec`, `encoding/json`, `net/http`, `os` packages handle common integration tasks
- **Simple concurrency**: Goroutines ideal for coordinating multiple external processes
- **Minimal boilerplate**: Less code to write and maintain for I/O operations
- **Integration-first design**: Language optimized for network services, system tools, I/O processing

**Why Rust's Strengths Don't Apply**
- **Computational performance**: Irrelevant when bottlenecked by external process latency (10-50ms)
- **Memory safety**: Less critical for short-lived CLI operations with trusted inputs
- **Zero-cost abstractions**: No performance-critical algorithms to optimize

### Risk Mitigation
- **Runtime reliability**: Comprehensive testing, panic recovery for critical paths
- **Performance monitoring**: Benchmark external process latency, not language overhead
- **Testing strategy**: Cross-platform CI with real terminal environments
- **Gradual rollout**: Start with iTerm2/tmux, expand terminal support iteratively

### Long-term Implications
- **Contributor growth**: Low barrier enables more terminal backend implementations
- **Maintainability**: Simple, readable code easier to debug and extend across integrations
- **Performance**: Goroutines handle hundreds of concurrent terminal sessions efficiently
- **Extensibility**: Interface-based architecture allows new terminal backends without core changes
- **Rapid iteration**: Fast compile times accelerate feature development and testing
