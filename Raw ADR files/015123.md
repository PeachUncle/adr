# Design: Vector I/O from Disk

## Context
RaBitQ quantization research requires loading benchmark vector datasets (SIFT-1M, GIST-1M, etc.) from disk. These datasets are commonly distributed in binary formats like fvecs. We need a simple, efficient reader that integrates with our existing Matrix structure.

## Goals / Non-Goals

### Goals
- Read fvecs format files (standard for SIFT/GIST datasets)
- Load N vectors (user-specified or all)
- Validate dimension consistency
- Return Matrix structure for seamless integration
- Design for future format extensibility

### Non-Goals
- Not supporting compressed formats (gzip, etc.) initially
- Not implementing streaming/iterator pattern yet (batch load only)
- Not writing vectors to disk (read-only for now)
- Not supporting non-power-of-2 dimensions (current Matrix constraint)

## Decisions

### fvecs Format Specification
**Format Structure:**
```
[dimension: u32][vector_1: f32 × dimension][dimension: u32][vector_2: f32 × dimension]...
```

**Key Properties:**
- Little-endian byte order
- Dimension prefix repeated for each vector
- Contiguous f32 values per vector
- Common in benchmark datasets (SIFT: 128D, GIST: 960D)

**Reference:** Standard format used by INRIA, Yandex SIFT-1M, ANN benchmarks

### API Design

```zig
pub const VectorIOError = error{
    FileNotFound,
    InvalidFormat,
    DimensionMismatch,
    InvalidDimension,  // Not power-of-2
    UnexpectedEOF,
    OutOfMemory,
};

pub fn loadVectorsFromFile(
    allocator: Allocator,
    path: []const u8,
    max_vectors: ?usize,
) VectorIOError!Matrix
```

**Parameters:**
- `allocator`: Memory allocator for Matrix
- `path`: File path to fvecs file
- `max_vectors`: Optional limit (null = load all)

**Returns:**
- `Matrix` with rows = vectors, cols = dimension
- Error if file invalid or dimension inconsistent

### Implementation Strategy

**Reading Algorithm:**
1. Open file and read first dimension (4 bytes)
2. Validate dimension is power-of-2
3. Calculate vector count (file_size / (4 + dimension * 4))
4. Determine N = min(max_vectors ?? ∞, vector_count)
5. Allocate Matrix(N, dimension)
6. Loop: Read dimension (validate match), read vector data
7. Populate Matrix row-by-row

**Memory Efficiency:**
- Single Matrix allocation upfront
- Sequential file reading (no buffering needed)
- Direct copy from file to Matrix data

### Error Handling

**Validation Points:**
1. File existence and readability
2. Minimum file size (at least one vector)
3. Dimension value is power-of-2
4. Dimension consistency across all vectors
5. File size matches expected format
6. Successful reads for all vectors

**Error Messages:**
- "File not found: {path}"
- "Invalid fvecs format: dimension {d} is not power-of-2"
- "Dimension mismatch: expected {d1}, got {d2} at vector {n}"
- "Unexpected EOF while reading vector {n}"

### Integration with Matrix

**Matrix Compatibility:**
- Matrix already requires power-of-2 dimensions ✓
- SIFT vectors are 128D (2^7) ✓
- Matrix uses row-major storage (matches fvecs row iteration)
- Matrix.init() handles allocation

**Usage Pattern:**
```zig
const matrix = @import("matrix.zig");
const vector_io = @import("vector_io.zig");

var vectors = try vector_io.loadVectorsFromFile(
    allocator,
    "sift_base.fvecs",
    1000,  // Load first 1000 vectors
);
defer vectors.deinit();

// vectors is now a Matrix(1000, 128)
// Can be used with orthogonal projections, quantization, etc.
```

### Extensibility Pattern

**Future Format Support:**
Design allows adding new formats without breaking API:

```zig
// Future: Format detection
pub const VectorFormat = enum {
    fvecs,
    bvecs,
    ivecs,
    hdf5,
};

// Future: Format-agnostic loader
pub fn loadVectors(
    allocator: Allocator,
    path: []const u8,
    format: ?VectorFormat,  // null = auto-detect
    max_vectors: ?usize,
) !Matrix
```

**Current Implementation:**
- Focus on fvecs only
- Internal structure allows format dispatch pattern
- File parsing logic isolated for easy extension

## Risks / Trade-offs

### Risk: Large Files
- **Issue**: SIFT-1M is ~500MB, loading all at once uses significant memory
- **Mitigation**: `max_vectors` parameter allows partial loading
- **Future**: Could add streaming/iterator API

### Risk: Non-Standard fvecs Variants
- **Issue**: Some datasets may have format variations
- **Mitigation**: Strict validation with clear error messages
- **Acceptable**: Start with standard format, extend if needed

### Trade-off: Batch vs Streaming
- **Choice**: Batch loading into Matrix
- **Upside**: Simple API, easy integration, supports SIMD operations
- **Downside**: Memory usage for large datasets
- **Justification**: Research use case typically works with subsets

### Trade-off: Format Validation
- **Choice**: Strict validation (dimension consistency, power-of-2)
- **Upside**: Early error detection, clear failure modes
- **Downside**: Can't load malformed files
- **Justification**: Benchmark datasets are well-formed

## Migration Plan
N/A - This is a new feature with no existing code to migrate.

## Open Questions
1. Should we support memory-mapped I/O for very large files?
   - **Leaning**: No initially, add if performance profiling shows benefit

2. Should we provide utility to inspect fvecs files (count, dimension)?
   - **Leaning**: Yes, add simple `inspectFvecsFile()` helper

3. Error handling: Continue on dimension mismatch or fail fast?
   - **Decision**: Fail fast - data integrity is critical
