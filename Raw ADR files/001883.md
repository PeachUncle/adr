# ADR-0004: Better Auth JWT Authentication Strategy

> **Scope**: Document decision clusters, not individual technology choices. Group related decisions that work together (e.g., "Frontend Stack" not separate ADRs for framework, styling, deployment).

- **Status:** Accepted
- **Date:** 2025-12-12
- **Feature:** 001-task-crud-auth
- **Context:** Phase II requires secure user authentication and authorization for the full-stack application. Users must be able to register accounts, log in with credentials, and maintain authenticated sessions. The backend must validate all requests and enforce user data isolation. We need to choose an authentication strategy that balances security, developer experience, type safety, and integration with Next.js + FastAPI.

## Decision

**Better Auth** on frontend with **JWT plugin**, **python-jose** for backend JWT validation, **shared secret** (`BETTER_AUTH_SECRET`) for token signing/verification.

**Authentication Flow Components:**

**Frontend (Better Auth + JWT):**
- **Library:** Better Auth with JWT plugin
- **Token Storage:** HttpOnly cookie (XSS protection)
- **Token Expiration:** 7 days (configurable)
- **Registration:** Email + password (bcrypt hashing before transmission)
- **Login:** Email + password validation, JWT issued on success

**Backend (FastAPI + python-jose):**
- **JWT Library:** python-jose (HS256 algorithm)
- **Password Hashing:** bcrypt (cost factor 12)
- **Middleware:** JWT validation on protected endpoints
- **User Extraction:** Extract `user_id` from validated JWT claims
- **Authorization:** Verify `user_id` in URL matches authenticated user (return 404 if mismatch)

**Shared Configuration:**
- **Secret:** `BETTER_AUTH_SECRET` environment variable (min 32 characters)
- **Algorithm:** HS256 (HMAC SHA-256)
- **Token Claims:** `sub` (user_id), `exp` (expiration timestamp)

**Security Requirements:**
- **User Data Isolation:** ALL database queries filter by authenticated `user_id`
- **Password Security:** bcrypt hashing (NEVER store plaintext)
- **XSS Protection:** HttpOnly cookies prevent JavaScript access to tokens
- **Information Leakage Prevention:** Return 404 (not 403) for unauthorized access attempts

## Consequences

### Positive

- **Type Safety:** Better Auth provides TypeScript types for authentication state (user, session, loading)
- **Next.js Optimized:** Better Auth designed specifically for Next.js App Router (Server/Client Components)
- **Simple Integration:** Frontend and backend share same secret (single configuration point)
- **Stateless Authentication:** JWT tokens allow horizontal scaling (no session database required)
- **HttpOnly Cookie Security:** Automatic XSS protection (JavaScript cannot access token)
- **7-Day Token Expiration:** Balance between security and user experience (no frequent re-logins)
- **bcrypt Password Hashing:** Industry-standard password security (cost factor 12)
- **User Data Isolation:** JWT contains `user_id` for all authorization checks (enforced at middleware level)

### Negative

- **Better Auth Maturity:** Smaller community than NextAuth, fewer integrations, less battle-tested
- **No Token Refresh:** 7-day token expires without automatic refresh (Phase II scope - refresh in Phase III+)
- **Shared Secret Management:** `BETTER_AUTH_SECRET` must be identical in frontend and backend (configuration coupling)
- **JWT Revocation Difficulty:** Cannot invalidate tokens before expiration (logout only clears cookie client-side)
- **Token Size:** JWT tokens larger than session IDs (base64-encoded JSON with signature)
- **Manual User Extraction:** Backend must manually extract and validate `user_id` from JWT claims
- **No Social Auth:** Better Auth supports OAuth but Phase II scope is email/password only

## Alternatives Considered

**Alternative A: NextAuth with Database Sessions**
- Frontend: NextAuth library, Backend: Database-backed session storage
- Why rejected:
  - Requires session table and database queries on every request (slower than stateless JWT)
  - Less type-safe than Better Auth (more runtime configuration)
  - Database session storage adds complexity (session cleanup, TTL management)
  - Not aligned with Phase II constitution preference for Better Auth
- Tradeoffs: Token revocation easier (delete session row), but slower and more complex

**Alternative B: Auth0 (Third-Party SaaS)**
- Frontend: Auth0 SDK, Backend: Auth0 JWT validation
- Why rejected:
  - Vendor lock-in: Dependent on Auth0 service availability and pricing
  - Cost: Auth0 charges per active user (monthly recurring cost)
  - External dependency: Auth0 outage blocks all authentication
  - Overkill: Auth0's features (SSO, MFA, RBAC) exceed Phase II scope
- Tradeoffs: Zero maintenance, enterprise features, but vendor lock-in and ongoing cost

**Alternative C: Custom JWT Implementation**
- Frontend: Manual JWT handling with fetch, Backend: Custom JWT validation
- Why rejected:
  - Security risk: Easy to implement JWT incorrectly (algorithm confusion, timing attacks)
  - Reinventing the wheel: Better Auth and python-jose are battle-tested
  - More code: Custom implementation requires more maintenance
  - No TypeScript types: Lose type safety for authentication state
- Tradeoffs: Full control, but security risks and maintenance burden

**Alternative D: Clerk (Third-Party SaaS, React-Focused)**
- Frontend: Clerk SDK, Backend: Clerk JWT validation
- Why rejected:
  - Similar vendor lock-in issues as Auth0
  - Cost: Clerk charges per active user
  - Less FastAPI integration: Clerk optimized for Next.js + Vercel
  - Not aligned with Phase II constitution preference for Better Auth
- Tradeoffs: Excellent UX, prebuilt UI components, but vendor lock-in and cost

**Why Better Auth + JWT Wins:**
- **Constitutional alignment:** Better Auth specified in Phase II requirements
- **Type safety:** TypeScript types for authentication state
- **Next.js optimized:** Designed for App Router (Server/Client Components)
- **Stateless:** JWT enables horizontal scaling (no session database)
- **Simple integration:** Shared secret between frontend and backend
- **Security:** HttpOnly cookies, bcrypt password hashing, 7-day expiration
- **Cost:** Zero ongoing costs (self-hosted authentication)
