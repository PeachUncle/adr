## Context

BillingCore is built on a microservices architecture deployed on Azure Kubernetes Service (AKS). As the system grows, we face several cross-cutting concerns that need to be addressed consistently across all services:

1. **Service-to-Service Communication**: Services need reliable, discoverable communication without hardcoding endpoints
2. **State Management**: Distributed state needs to be managed consistently across services
3. **Pub/Sub Messaging**: Event-driven communication requires integration with Azure Service Bus
4. **Secrets Management**: Secrets need to be accessed securely from Azure Key Vault
5. **Observability**: Distributed tracing needs to work seamlessly across service boundaries

Building these capabilities from scratch in each service would lead to:
- Duplicated code and inconsistent implementations
- Tight coupling to specific infrastructure (Azure-specific SDKs everywhere)
- Complex testing scenarios
- Increased maintenance burden

We need an abstraction layer that provides these capabilities as building blocks while maintaining portability and simplicity.

## Decision

**We will adopt Dapr (Distributed Application Runtime) as our service mesh and distributed systems building blocks provider.**

Dapr will be deployed as a sidecar container alongside each microservice in AKS, providing:

- **Service Invocation**: Service-to-service calls via Dapr sidecar with automatic mTLS, retries, and service discovery
- **State Stores**: Abstracted state management using Azure Redis Cache
- **Pub/Sub**: Event publishing/subscribing via Azure Service Bus
- **Secrets**: Unified secrets API backed by Azure Key Vault
- **Bindings**: Input/output bindings for external system integration
- **Observability**: Automatic distributed tracing with OpenTelemetry

## Options Considered

### Option 1: Direct Azure SDK Integration

| Aspect | Details |
|--------|---------|
| **Description** | Use Azure SDKs directly in each service for Service Bus, Redis, Key Vault, etc. |
| **Pros** | Full control, native Azure features, no additional runtime |
| **Cons** | Tight coupling to Azure, duplicated boilerplate, complex testing, no service mesh benefits |

### Option 2: Istio Service Mesh

| Aspect | Details |
|--------|---------|
| **Description** | Deploy Istio as a full-featured service mesh for traffic management and security |
| **Pros** | Mature ecosystem, powerful traffic management, strong mTLS |
| **Cons** | High complexity, steep learning curve, resource overhead, no building blocks (state, pub/sub) |

### Option 3: Dapr (Selected)

| Aspect | Details |
|--------|---------|
| **Description** | Deploy Dapr sidecars with building blocks for distributed systems patterns |
| **Pros** | Simple API, portable across clouds, built-in building blocks, low overhead, great .NET integration |
| **Cons** | Sidecar adds some latency (~1ms), relatively newer project (CNCF graduated) |

### Option 4: Custom Service Mesh + Libraries

| Aspect | Details |
|--------|---------|
| **Description** | Build custom shared libraries for each concern |
| **Pros** | Full control, tailored to our needs |
| **Cons** | High development effort, maintenance burden, reinventing the wheel |

## Consequences

### Positive

- **Simplified Development**: Services interact with Dapr's simple HTTP/gRPC API instead of complex SDKs
- **Cloud Portability**: Can migrate to other clouds by swapping Dapr components (no code changes)
- **Consistent Patterns**: All services use the same patterns for state, pub/sub, secrets
- **Built-in Resilience**: Automatic retries, circuit breakers, and timeouts via Dapr
- **Excellent .NET Support**: First-class Dapr SDK for .NET with dependency injection support
- **Simplified Testing**: Can test services without real infrastructure using Dapr's component abstraction
- **Observability**: Automatic distributed tracing propagation across service boundaries

### Negative / Risks

- **Sidecar Latency**: Adds ~1-2ms per service call (mitigated: acceptable for our SLAs)
- **Additional Component**: Another component to monitor and maintain (mitigated: AKS has Dapr extension support)
- **Team Learning**: Team needs to learn Dapr concepts (mitigated: excellent documentation, simple APIs)
- **Version Management**: Need to manage Dapr runtime versions across services (mitigated: use AKS Dapr extension for managed updates)

### Neutral

- Memory footprint of ~20-50MB per sidecar is acceptable for our cluster sizing
- Dapr is now a CNCF Graduated project, indicating maturity and community support

## Implementation Notes

### Dapr Components Configuration

```yaml
# State Store (Azure Redis)
apiVersion: dapr.io/v1alpha1
kind: Component
metadata:
  name: statestore
spec:
  type: state.redis
  version: v1
  metadata:
  - name: redisHost
    value: billing-redis.redis.cache.windows.net:6380
  - name: redisPassword
    secretKeyRef:
      name: redis-secret
      key: redis-password
  - name: enableTLS
    value: "true"
```

```yaml
# Pub/Sub (Azure Service Bus)
apiVersion: dapr.io/v1alpha1
kind: Component
metadata:
  name: pubsub
spec:
  type: pubsub.azure.servicebus.topics
  version: v1
  metadata:
  - name: connectionString
    secretKeyRef:
      name: servicebus-secret
      key: connection-string
```

```yaml
# Secrets (Azure Key Vault)
apiVersion: dapr.io/v1alpha1
kind: Component
metadata:
  name: azurekeyvault
spec:
  type: secretstores.azure.keyvault
  version: v1
  metadata:
  - name: vaultName
    value: billing-keyvault
  - name: azureClientId
    value: <managed-identity-client-id>
```

### Service Integration Pattern

```csharp
// Program.cs - Register Dapr client
builder.Services.AddDaprClient();

// Service invocation
public class InvoiceService
{
    private readonly DaprClient _daprClient;
    
    public async Task<Customer> GetCustomerAsync(Guid customerId)
    {
        // Service invocation via Dapr sidecar
        return await _daprClient.InvokeMethodAsync<Customer>(
            HttpMethod.Get,
            "customer-service",
            $"api/customers/{customerId}");
    }
    
    public async Task PublishInvoiceCreatedAsync(Invoice invoice)
    {
        // Pub/Sub via Dapr
        await _daprClient.PublishEventAsync(
            "pubsub",
            "invoice-created",
            new InvoiceCreatedEvent(invoice));
    }
}
```

### Rollout Plan

1. **Phase 1 (Week 1-2)**: Install Dapr on AKS DEV cluster, configure components
2. **Phase 2 (Week 3-4)**: Migrate Invoice Service to use Dapr for pub/sub
3. **Phase 3 (Week 5-6)**: Migrate remaining services
4. **Phase 4 (Week 7)**: Deploy to UAT with full integration testing
5. **Phase 5 (Week 8)**: Production rollout with canary deployment

### Rollback Plan

- Dapr sidecar injection can be disabled per deployment via annotation
- Services can fall back to direct SDK calls if needed
- Component configurations are stored in Git for version control
