# ADR-0004: DynamoDB for Transaction Storage

## Status
Accepted

## Context
We need a database to store processed financial transactions with high availability, scalability, and performance. The database must handle high write throughput, provide data durability, and support efficient querying of transaction data.

## Decision
We will use Amazon DynamoDB as our primary database with the following configuration:

- **Table Name**: `processed_transactions`
- **Primary Key**: Composite key with PK (partition key) and SK (sort key)
- **Billing Mode**: Pay-per-request (on-demand)
- **Encryption**: Server-side encryption enabled
- **Point-in-time Recovery**: Enabled for data protection
- **Natural Indexing**: Leveraging PK/SK for efficient queries without additional indexes
- **Single Table Design**: Using single table pattern for future extensibility
- **Data Model**:
  - PK: `ITEM_TYPE#processed_transactions#ACCOUNT_ID#{account_id}`
  - SK: `{transaction_timestamp}`

## Consequences
### Positive
- **Scalability**: Automatically scales with data volume and request rate
- **Performance**: Single-digit millisecond latency for most operations
- **Availability**: 99.99% availability SLA with multi-AZ replication
- **Durability**: 99.999999999% (11 9's) durability
- **Security**: Server-side encryption and IAM integration
- **Managed Service**: No operational overhead for database management
- **Cost-effective**: Pay-per-request pricing for variable workloads
- **Backup**: Point-in-time recovery for data protection
- **Natural Indexing**: PK/SK provides automatic sorting and efficient queries by account and timestamp
- **Query Efficiency**: No additional indexes needed for account-based queries and time-range scans
- **Single Table Benefits**: Simplified data model and future extensibility for additional entities

### Negative
- **Vendor Lock-in**: Tied to AWS ecosystem
- **Query Limitations**: Limited query flexibility compared to SQL databases
- **Cost**: Can be expensive for high read/write scenarios
- **Learning Curve**: Different data modeling approach required
- **No Joins**: Cannot perform complex joins across tables

### Neutral
- **Eventual Consistency**: Default consistency model (strong consistency available for reads)
- **NoSQL**: Schema flexibility but requires careful data modeling
- **Partition Strategy**: Requires careful design of partition keys for even distribution

## Alternatives Considered
- **Amazon RDS (PostgreSQL/MySQL)**: Rejected due to operational overhead and scaling limitations
- **Amazon Aurora**: Rejected due to higher cost and complexity for this use case
- **MongoDB**: Rejected due to need for self-management and lower reliability
- **Redis**: Rejected due to lack of persistence and limited query capabilities

## Implementation Notes
- Uses AWS SDK v2 for DynamoDB Enhanced Client
- Composite key design allows efficient querying by account and time range
- PK/SK design provides natural sorting by timestamp within each account partition
- HTTP queries can efficiently retrieve transactions by account with optional time range filtering
- Single table design pattern allows for future addition of related entities (accounts, balances, etc.)
- Batch write operations for improved performance
- IAM roles for secure access control
- LocalStack integration for development environment
