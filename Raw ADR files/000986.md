# Decision on Pipeline Execution for CAIRA Project

## Context and Problem Statement

The [CAIRA](https://github.com/microsoft/CAIRA) project currently uses an end-to-end pipeline that tests the base case, but additional pipelines are needed for comprehensive nightly builds. Deploying real infrastructure on Azure is time-consuming, with some configurations taking up to an hour for deployment and teardown.
If we run all reference implementations on every pull request, we risk slowing down development significantly.

We need to decide how to structure pipeline execution to balance thorough testing and developer efficiency.

## Decision Drivers

* **Pipeline execution time**: Long deployments (up to one hour) impact developer productivity if triggered for every pull request.
* **Real Azure infrastructure**: Full deployments are critical to ensure the stability of the project, but should be balanced against deployment time and resource costs.
* **Quick feedback on pull requests**: Developers need timely feedback on changes without long wait times.
* **Coverage of reference implementations**: Ensuring that all reference implementations are tested regularly to maintain system integrity.
* **Cost management**: Running full infrastructure builds on Azure can incur significant costs.
* **Dependency Change Detection**: Ability to detect issues arising from dependency updates independently of code changes.
* **Code Integrity in Main Branch**: Ensuring that the `main` branch always contains buildable and stable code.

## Considered Options

* Run all builds on every pull request.
* Run an integration pipeline on pull requests (covering a subset of critical tests and deployments checks), and then run the full set of tests and deployments as part of a nightly/periodic build.
* Run only nightly builds.
* Utilize GitHub Merge Queues with additional build triggers and maintain nightly builds.

## Decision Outcome

**Chosen Option**: **Utilize GitHub Merge Queues with critical builds on pull requests and maintain nightly builds for full coverage**.

This approach was selected after further evaluation revealed that GitHub Merge Queues provide a more efficient and reliable mechanism for managing pull requests and ensuring pipeline integrity. The final strategy includes:

1. **GitHub Merge Queues**:
    * **Sequential PR Merging**: Merge queues allow building a sequence of PRs that are merged into the `main` branch in an orderly fashion.
    * **Pre-Merge Builds**: Specific builds are executed just before a PR is merged to `main`. If these tests fail, the PR is reverted to a state where developers can address the issues.
    * **Merge Group Trigger**: Introduces an additional build triggered by `merge_group`, which performs a matrix build covering all reference implementations.
    * **Code Integrity Assurance**: Ensures that only code that successfully builds across all reference implementations is merged into `main`, preventing broken code from entering the primary branch.

2. **Nightly Builds**:
    * **Dependency Change Detection**: Nightly builds remain in place to detect changes in dependencies that may not be triggered by PRs. This ensures that any indirect changes affecting the builds are identified and addressed promptly.
    * **Avoiding Silent Failures**: By running nightly builds independently, the team can avoid situations where a build fails due to dependency updates without any corresponding PR, ensuring greater reliability.

3. **Tag-Based Builds**:
    * **Release Automation**: Builds are triggered upon the creation of a version tag in the repository. These builds generate releases containing a zip file for each reference implementation.
    * **Future Enhancements**: The contents and format of the zip files will be detailed in a separate ADR, allowing for focused discussions and decisions.

### Updated Definition of Critical Builds

Critical builds now encompass both pre-merge checks via GitHub Merge Queues and the existing criteria:

* **Pre-Merge Critical Builds**: Executed as part of the merge queue process to ensure that each PR meets the necessary standards before being merged.
* **Matrix Builds on Merge Group**: Triggered by the `merge_group` event to validate all reference implementations collectively, ensuring comprehensive coverage.

### Mitigating Risks from Nightly Builds

* **Priority Handling**: Failed nightly builds continue to be prioritized for prompt review and resolution.
* **Automatic Issue Creation**: Issues are automatically created in the repository for any failed nightly builds to ensure visibility and tracking.

### Handling Consistent Nightly Build Failures

* **Process and Communication**: Persistent nightly build failures are discussed in daily standups to prioritize their resolution.
* **Potential Automation**: The team may consider automating responses to repeated failures, such as blocking new PRs, based on ongoing evaluations.

### Queue Management with GitHub Merge Queues

* **No Additional Coverage with Merge Queues Alone**: Initial consideration revealed that GitHub merge queues do not provide additional test coverage beyond what is already executed during the PR phase.
* **Integration with Critical Builds**: However, when combined with pre-merge and matrix builds, merge queues enhance the overall pipeline strategy by ensuring ordered and reliable merges.

### Consequences

* **Good**:
  * Provides structured and reliable merging of pull requests with comprehensive pre-merge checks.
  * Maintains fast feedback for critical changes while ensuring full infrastructure coverage through nightly builds.
  * Reduces Azure resource costs by limiting full deployments to overnight runs.
  * Facilitates quicker turnaround times for developers, enabling faster merging of pull requests.
  * Detects dependency-related issues independently of code changes.
  * **Ensures `main` Branch Integrity**: Guarantees that only code that successfully builds across all reference implementations is merged into `main`, preventing broken code from entering the primary branch.
  * If nightly builds fail consistently, it would block PR merges for extended periods.

* **Bad**:
  * Adds complexity to the pipeline management with merge queues and multiple build triggers.
  * Potential delays in PR merges if nightly builds fail consistently.
  * Requires a mechanism to handle failed nightly builds (e.g., automatic issue creation and updates).

## Pros and Cons of the Options

### Option 1: Run all builds on every pull request

* **Good**:
  * Ensures complete testing coverage with every pull request, reducing the risk of undetected issues.
  * Immediate detection of problems across all reference implementations.

* **Bad**:
  * Extremely slow pipeline execution times (up to one hour) delay pull request merges.
  * High Azure resource costs due to repeated deployments.
  * Creates bottlenecks in developer workflows, particularly for frequent pull requests.

### Option 2: Run critical builds on pull requests, with nightly builds

* **Good**:
  * Balances speed and thoroughness, providing immediate feedback for critical infrastructure changes and full coverage via nightly builds.
  * Reduces costs and pipeline congestion by limiting full deployments to overnight builds.
  
* **Neutral**:
  * Nightly builds ensure full coverage, but some issues may not be caught immediately after changes.

* **Bad**:
  * Allows Broken Code in `main`: Potentially permits code that breaks some reference implementations to be merged into `main` until the nightly build catches the issue.
  * Requires handling of nightly build failures (e.g., through automated issue creation and updates).

### Option 3: Run only nightly builds

* **Good**:
  * Completely avoids blocking developers during the day with long pipelines.
  * Lowest Azure resource costs, as full deployments are only triggered once per day.

* **Bad**:
  * No immediate feedback on pull requests, allowing potential issues to go unnoticed until the nightly build.
  * Increases the likelihood of breaking changes being merged without immediate testing.

### Option 4: Utilize GitHub Merge Queues with critical builds on pull requests and maintain nightly builds

* **Good**:
  * Provides structured and reliable merging of pull requests with comprehensive pre-merge checks.
  * Balances fast feedback for critical changes and thorough testing through nightly builds.
  * Detects dependency-related issues independently of code changes.
  * Reduces Azure resource costs by optimizing build triggers.
  * Ensures `main` Branch Integrity: Prevents broken code from being merged into `main`, maintaining a stable and buildable primary branch.

* **Bad**:
  * Adds complexity to the pipeline management with merge queues and multiple build triggers.
  * Potential delays in PR merges if nightly builds fail consistently.
  * Requires a mechanism to handle failed nightly builds (e.g., automatic issue creation and updates).

## More Information

To track the progress of implementing the additional pipelines for nightly builds and merge queues, tasks will be created in the backlog.
The current end-to-end pipeline, which tests the base case, will remain in place, with enhancements added to cover the full range of reference implementations in nightly builds and pre-merge checks via merge queues. Documentation regarding the new pipeline strategies will be updated in the repository.

Additionally, for the tag-based builds that create releases with zip files for each reference implementation, a separate ADR will be created to discuss and define the contents and format of these zip files in detail.
