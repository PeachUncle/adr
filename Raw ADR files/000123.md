# ADR-0002: On-Device Processing Only

**Status**: Accepted
**Date**: October 12, 2025
**Deciders**: Architecture Team

## Context

We need to decide where computation happens for the app's core features:

- Cube scanning and state recognition
- Solving algorithms (optimal and speed methods)
- 3D visualization and animation

Options include:

1. On-device processing only
2. Cloud-based processing (backend API)
3. Hybrid approach (some features on-device, some cloud)

Key considerations:

- User privacy concerns with camera data
- Network latency impact on user experience
- Infrastructure costs and complexity
- Offline functionality requirements
- Computational feasibility on modern mobile devices

## Decision

**All cube scanning, state recognition, and solving algorithms will run entirely on-device. No backend services or cloud processing will be used.**

## Alternatives Considered

### Cloud-Based Processing

**Pros**:

- Unlimited computational resources
- Algorithm updates without app updates
- Centralized monitoring and analytics
- Easier A/B testing of algorithms

**Cons**:

- Network latency degrades user experience
- Requires always-on internet connection
- Privacy concerns: camera images sent to servers
- Infrastructure costs (compute, storage, networking)
- Backend maintenance and operations overhead
- GDPR/privacy compliance complexity
- Single point of failure

**Why not chosen**: Privacy concerns and network dependency make this approach unacceptable for educational app experience.

### Hybrid Approach

**Pros**:

- On-device for latency-sensitive operations (scanning)
- Cloud for computationally intensive operations (optimal solving)
- Balanced privacy and performance

**Cons**:

- Complex architecture with multiple failure modes
- Still requires network connectivity for full functionality
- Privacy concerns remain for any cloud data
- Backend infrastructure still needed
- Inconsistent user experience (some features offline, some require network)

**Why not chosen**: Adds complexity without sufficient benefit; target devices are expected to handle required computations adequately.

## Consequences

### Positive

1. **Privacy by Design**: Camera images never leave device; zero data collection or transmission
2. **Zero Latency**: No network round-trips; instant feedback to users
3. **Works Offline**: Full functionality without internet connection (flights, remote areas, data plans)
4. **No Infrastructure Costs**: No servers, databases, or networking costs
5. **No Backend Maintenance**: No operations overhead, scaling concerns, or downtime risk
6. **Simplified Architecture**: Single codebase, no client/server coordination
7. **App Store Approval**: Privacy-first approach aligns with Apple's requirements
8. **User Trust**: No telemetry or "phone home" behavior builds user confidence

### Negative

1. **Device Limitations**: Constrained by device CPU/GPU capabilities
2. **Algorithm Updates**: Require app updates (App Store review process)
3. **Larger App Size**: All ML models and algorithm code bundled in app (actual size to be determined)
4. **Battery Impact**: Heavy computation on-device consumes more battery
5. **Testing Complexity**: Must test across multiple device generations and iOS versions
6. **No Centralized Analytics**: Cannot easily gather usage metrics or performance data
7. **Feature Limitations**: Cannot implement features requiring server-side coordination (leaderboards, sharing)

### Neutral

1. **Device Requirements**: Must target iPhone 12+ (A14 Bionic) for acceptable performance
2. **Optimization Critical**: Performance profiling and optimization essential
3. **User Support**: Harder to debug user-reported issues without server-side logging

## Rationale

The decision prioritizes **user privacy and experience** over operational flexibility.

Key factors:

### Privacy is Paramount

- Camera-based apps face scrutiny regarding data collection
- Educational app users (including parents) highly value privacy
- No legitimate business need for user data collection
- Privacy violations can destroy app reputation instantly

### Performance is Feasible

- Target iPhones (A14 Bionic and newer) provide documented capabilities:
  - Neural Engine for ML acceleration ([Apple A14 Bionic specifications](https://en.wikipedia.org/wiki/Apple_A14))
  - Metal for GPU acceleration ([Metal documentation](https://developer.apple.com/metal/))
  - Multi-core CPU for parallel computation
- Performance targets to be validated through implementation:
  - Optimal solving: Responsive for educational use
  - Speed solving: Real-time or near-real-time response
  - Vision processing: Per-face scanning within seconds
  - 3D rendering: Target 60 FPS sustained

### Offline is Essential

- Educational apps often used in varied environments (classrooms without WiFi, travel)
- Network dependency creates friction and frustration
- Competitive advantage: "Works anywhere, anytime"

### Simplicity Wins

- No backend means faster development and lower operational risk
- Single team can build and maintain entire app
- No distributed system debugging complexity

The app's core value proposition—helping users learn and solve 3x3 cube puzzles—does not require cloud processing. On-device processing delivers superior privacy and user experience with acceptable performance on target hardware.

## Implementation Notes

### Performance Optimization Strategies

- Use Swift concurrency (actors) to offload heavy computation
- Leverage CoreML and Neural Engine for ML inference
- Profile with Instruments to identify bottlenecks
- Cache computed results where appropriate
- Optimize algorithms using efficient data structures

### Testing Requirements

- Test on minimum supported device (iPhone 12) to ensure acceptable performance
- Profile battery impact during extended use
- Memory profiling to prevent leaks during long sessions
- Stress testing with worst-case cube states

### Future Considerations

If future features require server-side components (e.g., online leaderboards):

- Keep core functionality (scanning, solving, learning) on-device
- Optional online features only for non-essential social elements
- Never transmit camera images or cube states without explicit user consent
