# ADR 001: Service Communication Pattern

## Status

Accepted

## Context

As the RentIO-Server grows in complexity, we need a standardized approach for inter-service communication that maintains clear service boundaries while enabling robust, type-safe interactions between services. Previous implementations had services directly importing entities and classes from other services, creating tight coupling that made changes difficult and error-prone.

## Decision

We will implement service decoupling using the following approach:

1. **Contract-First Development**:
   - Define service contracts in a shared `contracts` library
   - Use Typia with Nestia for type-safe API definitions
   - Generate client SDKs automatically from interface definitions

2. **Type-Safe Communication**:
   - All data transfer objects (DTOs) are defined in the shared contracts library
   - Runtime validation ensures data integrity across service boundaries
   - Automated SDK generation keeps clients in sync with API changes

3. **Dual Communication Modes**:
   - HTTP REST: For synchronous request/response communication
   - NATS Messaging: For asynchronous event-driven communication
   - Service client factory to support both modes with the same interface

4. **Service Boundaries**:
   - No direct imports between service modules
   - Communication exclusively through defined interfaces
   - Clear separation between internal implementation and public API

## Implementation

1. Created a shared contracts library structure
2. Defined shared DTOs with Nestia-compatible type definitions
3. Created Nestia API interface definitions for services
4. Added Nestia configuration for SDK generation
5. Implemented the API interfaces in service controllers
6. Created type-safe service clients in consuming services

## Benefits

1. **Reduced Coupling**: Services are now isolated, with communication only through well-defined interfaces
2. **Type Safety**: Compile-time and runtime type checking prevents integration errors
3. **Automatic Documentation**: OpenAPI specs are automatically generated from interfaces
4. **Better Developer Experience**: Type-safe SDKs make consuming services simpler
5. **Adaptability**: Communication mode can be switched without changing code

## Consequences

1. **Added Complexity**: Additional abstraction layer requires more initial development
2. **Build-Time Dependencies**: SDK generation must be part of the build process
3. **Learning Curve**: Developers need to understand the contract-first approach
4. **Serialization Overhead**: Data must be serialized/deserialized at service boundaries

## Related Decisions

- API versioning strategy will be addressed in a future ADR
- Error handling across service boundaries will be standardized in a future ADR

## Notes

While this approach adds some complexity, the benefits of loose coupling and type safety outweigh the costs, especially as the system grows. The contracts library will be the source of truth for all service interactions, ensuring consistency and maintainability.
