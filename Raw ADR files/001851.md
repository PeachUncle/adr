# ADR-3: Queue-based scheduler and device state management

**Status**: Accepted

## Context
We are migrating from a bare-metal loop to FreeRTOS. Multiple tasks must update and read device state without race conditions. The system needs deterministic behavior, and a simple testable structure with low memory overhead.

Options considered:
- Shared globals + mutexes (low overhead, higher coupling, deadlock risk, error-prone).
- Polling with global state (wastes CPU, latency spikes).
- Direct cross-task calls/notifications (couples tasks, hard to evolve).
- FreeRTOS queues or stream/message buffers (bounded, typed messages, back-pressure, decoupling).

## Decision
Use FreeRTOS queues as the exclusive inter-task communication mechanism and adopt a single-writer “Device State Manager” task:
- All tasks writing to the device state post commands via a single command queue; no shared globals or direct cross-task calls.
- All readers obtain consistent views via a snapshot request/response queue pair to protect against race conditions (copy of device state at the time of request).
- Fixed-size message struct (type enum + union payload) to keep allocations static and predictable.
- The manager task is the sole mutator of device state; derived values (e.g., distance) are updated there.

## Task rates and justification
- updateStepLogic_Task ≈ 200 Hz
  - Matches accelerometer processing needs (low-latency step edge detect); ≤5 ms detection latency target while staying well under CPU budget.
- userInputUpdateState_Task ≈ 75 Hz
  - Human I/O and debounce friendly (~13 ms period); <50 ms UI response target with low CPU overhead.
- pollClientCommunication_Task ≈ 100 Hz
  - Keeps up with 9600 baud UART line buffering and provides <20 ms typical command handling latency.
- displayUpdate_Task ≈ 5 Hz
  - Human-readable update with maximum 200ms delay.
- deviceStateManager_Task
  - Event-driven (runs when queues have data); no fixed rate to keep mutation serialized and responsive.

## Consequences
Pros:
- Deterministic, thread-safe state updates; clear ownership (single writer).
- Decoupled modules, simpler testing and evolution.

Cons/Risks:
- Additional RAM for queues and messages.
- Potential latency if queues fill; requires sizing and monitoring.
- Need to handle queue-full cases consistently.
- Safe reads in the form of snapshots at cost of potential latency in reading up to date information
