# ADR 002: Why GraphQL and gRPC (Dual Contract Architecture)

## Status

Accepted

## Context

The RACR system requires efficient communication between multiple components: web frontend, API backend, and various worker services. We needed to choose communication protocols that balance flexibility for client needs with performance for internal service communication, while maintaining clear API contracts.

## Decision

We will implement a "Dual Contract" architecture using:

1. **GraphQL** for client-server communication (web frontend ↔ API backend)
2. **gRPC** for service-service communication (API backend ↔ worker services)

## Rationale

### GraphQL for Client-Server Communication

**Benefits:**

- **Flexible Queries**: Clients can request exactly the data they need, reducing over/under-fetching
- **Single Endpoint**: One `/graphql` endpoint replaces multiple REST endpoints
- **Strong Typing**: Schema-first approach with automatic type generation
- **Introspection**: Built-in API documentation and tooling
- **Real-time Support**: Subscriptions for live updates (future scalability)

**Why not REST:**

- Multiple endpoints to maintain and version
- Over/under-fetching common with complex UIs
- Less efficient for mobile and low-bandwidth clients

### gRPC for Service-Service Communication

**Benefits:**

- **High Performance**: Binary protocol with efficient serialization (Protocol Buffers)
- **Low Latency**: Optimized for internal network communication
- **Strong Typing**: Generated client/server code from .proto files
- **Streaming Support**: Bidirectional streaming for real-time data processing
- **Multi-language**: Official support for 10+ programming languages

**Why not HTTP/JSON:**

- Text-based protocols are slower to parse
- No built-in streaming or bidirectional communication
- Less efficient for high-frequency internal service calls

### Dual Contract Benefits

1. **Clear Separation of Concerns**: Public API (GraphQL) vs Internal API (gRPC)
2. **Performance Optimization**: Fast internal communication, flexible external API
3. **Evolutionary Architecture**: Can evolve internal services without breaking clients
4. **Developer Experience**: Best tool for each use case

## Alternatives Considered

### Single Protocol Approaches

#### REST for Everything

- **Pros**: Simple, familiar, no additional tooling
- **Cons**: Performance bottlenecks, over-fetching, complex API versioning

#### GraphQL for Everything

- **Pros**: Unified API, flexible queries
- **Cons**: Internal service communication overhead, complexity for simple service calls

#### gRPC for Everything

- **Pros**: High performance, strong typing
- **Cons**: Complex for web clients, overkill for public APIs

### Other Protocol Combinations

#### REST + gRPC

- **Pros**: Familiar public API
- **Cons**: Still have REST maintenance overhead

#### GraphQL + REST

- **Pros**: Flexible queries externally
- **Cons**: REST still has performance limitations internally

## Consequences

### Positive

- Optimal performance for each communication pattern
- Clear API boundaries and contracts
- Future-proof architecture for scaling
- Best developer experience for each use case

### Negative

- Additional complexity in maintaining two protocols
- Learning curve for developers new to GraphQL/gRPC
- More tooling and build steps required

## Implementation Notes

- **GraphQL Schema**: Defined in `libs/shared/graphql-schema/`
- **gRPC Protobufs**: Defined in `libs/shared/protos/`
- **Code Generation**: Use Nx generators for consistent schema handling
- **API Versioning**: Semantic versioning for both contracts
- **Monitoring**: Separate metrics for GraphQL and gRPC performance
