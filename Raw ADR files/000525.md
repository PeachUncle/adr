# ADR-004: Multi-Tenant Architecture

## Status
Accepted

## Context
For the Farm Management System, we needed to support multiple agricultural organizations with:

- Complete data isolation between tenants
- Shared infrastructure for cost efficiency
- Customizable features per tenant
- Scalable architecture for growth
- Secure data access patterns
- Efficient resource utilization
- Tenant-specific configurations

## Decision
We chose a **Row-Level Security (RLS) based multi-tenant architecture** with shared database and application instances.

## Rationale

### 1. Cost Efficiency

**Shared Infrastructure**
- Single database instance reduces operational costs
- Shared application servers for better resource utilization
- Centralized maintenance and updates
- Economies of scale for cloud resources

**Resource Optimization**
- Database connection pooling across tenants
- Shared caching layer
- Efficient hardware utilization
- Reduced backup and maintenance overhead

### 2. Data Security & Isolation

**Row-Level Security**
- Database-level tenant isolation
- Automatic filtering of tenant data
- Prevention of cross-tenant data leakage
- Security enforced at the lowest level

**Implementation Example**
```sql
-- Enable RLS on all tenant tables
ALTER TABLE farms ENABLE ROW LEVEL SECURITY;
ALTER TABLE fields ENABLE ROW LEVEL SECURITY;
ALTER TABLE devices ENABLE ROW LEVEL SECURITY;

-- Create tenant isolation policy
CREATE POLICY tenant_isolation ON farms
  FOR ALL TO authenticated_users
  USING (tenant_id = current_setting('app.current_tenant_id')::uuid);
```

### 3. Scalability

**Horizontal Scaling**
- Application servers can be scaled independently
- Database read replicas for query performance
- Load balancing across application instances
- Tenant-specific caching strategies

**Vertical Scaling**
- Resource allocation based on tenant needs
- Performance isolation between tenants
- Tiered service levels
- Resource usage monitoring

### 4. Maintenance & Operations

**Centralized Updates**
- Single codebase to maintain
- Simpler deployment processes
- Consistent feature rollout
- Centralized monitoring and logging

**Backup & Recovery**
- Single backup strategy
- Point-in-time recovery for all tenants
- Efficient storage utilization
- Simplified disaster recovery

### 5. Agricultural Domain Benefits

**Data Sharing Patterns**
- Regional agricultural data sharing
- Benchmarking across farms
- Collaborative farming insights
- Industry-wide analytics

## Architecture Design

### 1. Tenant Identification

**Multi-Tenant Resolution**
```typescript
// Tenant resolution middleware
@Injectable()
export class TenantMiddleware implements NestMiddleware {
  async use(req: Request, res: Response, next: NextFunction) {
    const tenantId = await this.resolveTenant(req);
    if (!tenantId) {
      throw new UnauthorizedException('Tenant not found');
    }
    
    // Set tenant context for request
    req.tenantId = tenantId;
    
    // Set PostgreSQL session variable for RLS
    await this.prisma.$executeRaw`SET app.current_tenant_id = ${tenantId}`;
    
    next();
  }

  private async resolveTenant(req: Request): Promise<string> {
    // Priority order for tenant resolution
    // 1. Subdomain (tenant.farm-system.com)
    // 2. Custom domain
    // 3. JWT token claim
    // 4. Header-based identification
  }
}
```

### 2. Database Design

**Tenant-Aware Schema**
```sql
-- All tables include tenant_id
CREATE TABLE farms (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  name TEXT NOT NULL,
  location GEOGRAPHY(POINT, 4326),
  size_hectares DECIMAL(10, 2),
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- Composite indexes for tenant isolation
CREATE INDEX idx_farms_tenant_name ON farms(tenant_id, name);
CREATE INDEX idx_farms_tenant_location ON farms(tenant_id, location);

-- Partitioning by tenant for large tables
CREATE TABLE sensor_readings (
  time TIMESTAMPTZ NOT NULL,
  tenant_id UUID NOT NULL,
  device_id TEXT NOT NULL,
  value DOUBLE PRECISION NOT NULL,
  metadata JSONB
) PARTITION BY HASH (tenant_id);
```

### 3. Service Layer Design

**Tenant-Aware Services**
```typescript
@Injectable()
export class FarmsService {
  constructor(
    private prisma: PrismaService,
    private tenantContext: TenantContextService,
  ) {}

  async create(data: CreateFarmDto): Promise<Farm> {
    // Automatically add tenant context
    const farmData = {
      ...data,
      tenantId: this.tenantContext.getCurrentTenantId(),
    };

    return this.prisma.farm.create({
      data: farmData,
      include: {
        fields: true,
        devices: true,
      },
    });
  }

  async findByTenant(
    tenantId: string,
    options?: FindManyOptions
  ): Promise<Farm[]> {
    // RLS automatically filters by tenant_id
    return this.prisma.farm.findMany({
      where: {
        // tenant_id filter handled by RLS
        ...options?.where,
      },
      include: options?.include,
      orderBy: options?.orderBy,
    });
  }
}
```

### 4. API Design

**Tenant-Scoped Endpoints**
```typescript
@Controller('farms')
@UseGuards(TenantGuard)
export class FarmsController {
  constructor(private farmsService: FarmsService) {}

  @Post()
  async create(
    @Body() createFarmDto: CreateFarmDto,
    @Tenant() tenant: TenantContext,
  ): Promise<FarmDto> {
    // Tenant automatically injected from context
    return this.farmsService.create(createFarmDto);
  }

  @Get()
  async findAll(
    @Query() query: FindFarmsQuery,
    @Tenant() tenant: TenantContext,
  ): Promise<PaginatedResponse<FarmDto>> {
    return this.farmsService.findByTenant(
      tenant.id,
      query
    );
  }
}
```

## Alternatives Considered

### Database-per-Tenant

**Pros**:
- Complete data isolation
- Independent scaling per tenant
- Custom database configurations
- Easier data migration

**Cons**:
- High operational overhead
- Complex backup/restore procedures
- Inefficient resource utilization
- Higher costs at scale

### Schema-per-Tenant

**Pros**:
- Logical data separation
- Shared database instance
- Independent schema versions

**Cons**:
- Complex migration management
- Limited scalability
- Cross-tenant analytics complexity
- Higher maintenance overhead

### Application-per-Tenant

**Pros**:
- Complete isolation
- Independent deployments
- Custom configurations per tenant

**Cons**:
- Very high operational costs
- Complex deployment pipelines
- Resource waste
- Maintenance nightmare

### Hybrid Approach

**Pros**:
- Flexibility for different tenant sizes
- Optimized resource allocation
- Tiered service levels

**Cons**:
- Increased complexity
- Multiple deployment patterns
- Migration challenges
- Operational overhead

## Implementation Details

### 1. Tenant Management

**Tenant Lifecycle**
```typescript
@Injectable()
export class TenantsService {
  async createTenant(data: CreateTenantDto): Promise<Tenant> {
    // Create tenant record
    const tenant = await this.prisma.tenant.create({
      data: {
        ...data,
        status: 'ACTIVE',
        createdAt: new Date(),
      },
    });

    // Initialize tenant data
    await this.initializeTenantData(tenant.id);

    // Set up tenant-specific configurations
    await this.configureTenant(tenant.id, data.settings);

    return tenant;
  }

  private async initializeTenantData(tenantId: string): Promise<void> {
    // Create default data structures
    await this.createDefaultUsers(tenantId);
    await this.createDefaultRoles(tenantId);
    await this.setupDefaultPermissions(tenantId);
  }
}
```

### 2. Resource Management

**Tenant Limits and Quotas**
```typescript
interface ResourceLimits {
  maxFarms: number;
  maxFields: number;
  maxDevices: number;
  maxUsers: number;
  maxApiCalls: number; // per month
  storageQuota: number; // in GB
  aiFeatures: {
    maxPredictions: number;
    maxImageAnalysis: number;
  };
}

@Injectable()
export class ResourceLimitService {
  async checkResourceLimit(
    tenantId: string,
    resourceType: string,
    currentCount: number
  ): Promise<boolean> {
    const limits = await this.getTenantLimits(tenantId);
    
    switch (resourceType) {
      case 'farms':
        return currentCount < limits.maxFarms;
      case 'devices':
        return currentCount < limits.maxDevices;
      // ... other resource types
    }
  }
}
```

### 3. Performance Optimization

**Tenant-Aware Caching**
```typescript
@Injectable()
export class CacheService {
  async get<T>(key: string, tenantId: string): Promise<T | null> {
    const tenantKey = `tenant:${tenantId}:${key}`;
    return this.redis.get(tenantKey);
  }

  async set<T>(
    key: string, 
    value: T, 
    tenantId: string,
    ttl?: number
  ): Promise<void> {
    const tenantKey = `tenant:${tenantId}:${key}`;
    await this.redis.set(tenantKey, JSON.stringify(value), ttl);
  }
}
```

### 4. Monitoring & Analytics

**Tenant-Specific Metrics**

@Injectable()
export class TenantMetricsService {

    await this.metrics.increment('api.calls', {

## Consequences

### Positive
- **Cost Efficiency**: Shared infrastructure reduces costs
- **Security**: Database-level isolation ensures data security
- **Scalability**: Horizontal scaling for application layer
- **Maintenance**: Centralized updates and monitoring
- **Resource Optimization**: Efficient resource utilization

### Negative
- **Complexity**: More complex than single-tenant architecture
- **Performance**: Potential performance impact from RLS
- **Debugging**: More complex debugging across tenants
- **Migration**: Cross-tenant data migrations are complex

### Risks
- **Noisy Neighbor**: One tenant affecting others
- **Data Leakage**: Security vulnerabilities in RLS policies
- **Performance**: Database contention at high scale
- **Complexity**: Operational complexity increases

## Performance Considerations

### Database Optimization
- **Connection Pooling**: Per-tenant connection pools
- **Indexing Strategy**: Tenant-aware indexing
- **Query Optimization**: RLS query plan optimization
- **Partitioning**: Large tables partitioned by tenant

### Application Optimization
- **Caching**: Tenant-aware caching strategies
- **Rate Limiting**: Per-tenant rate limiting
- **Resource Allocation**: Fair resource distribution
- **Monitoring**: Tenant-specific performance metrics

## Conclusion

The row-level security based multi-tenant architecture provides the optimal balance of security, cost efficiency, and scalability for our agricultural management platform. The database-level isolation ensures data security while the shared infrastructure keeps operational costs manageable.

This approach allows us to serve farms of all sizes, from small family farms to large agricultural enterprises, while maintaining the security and performance requirements of each tenant type. The architecture is designed to scale efficiently as we grow our customer base.
