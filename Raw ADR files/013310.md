# 4. Use AWS CodePipeline and CodeBuild for Continuous Deployment in a single account

Date: 2025-11-16

## Status

Accepted

## Context

Kiro Forge requires an automated continuous deployment (CD) pipeline to deploy infrastructure and application updates reliably and consistently. The system needs to:

- Automatically deploy changes when code is pushed to the repository
- Build and deploy Lambda functions for Gateway targets
- Deploy infrastructure changes (AgentCore Gateway, Cognito, IAM roles)
- Provide visibility into deployment status and failures
- Support rollback capabilities
- Maintain deployment history and audit trails

Given the small size of the project and team, we need a solution that:
- Minimizes operational overhead
- Reduces infrastructure complexity
- Keeps costs low
- Provides sufficient automation without over-engineering

## Decision

We will use AWS CodePipeline with AWS CodeBuild for continuous deployment of Kiro Forge, running in the same AWS account as the application infrastructure.

### Implementation Approach
- Single AWS account deployment (no cross-account complexity)
- CodePipeline orchestrates the deployment workflow
- CodeBuild handles build, test, and packaging
- AWS CDK for infrastructure as code
- CDK deploy command used in pipeline for infrastructure deployment
- S3 bucket for artifact storage
- CloudWatch Logs for build and deployment logs


## Consequences


### Positive
- **Fully Managed**: No servers to maintain, AWS handles scaling and availability
- **Native Integration**: Seamless integration with GitHub, S3, CloudFormation, and Lambda
- **Simple Architecture**: Single account deployment reduces complexity and IAM overhead
- **Cost Effective**: Pay only for build minutes and pipeline executions (minimal cost for small projects)
- **Built-in Audit**: CloudTrail automatically logs all pipeline activities
- **Visibility**: Console UI shows pipeline status, build logs, and deployment history
- **Low Maintenance**: Minimal configuration and operational overhead

### Negative
- **Single Account Risk**: No environment isolation (mitigated by small project scope)
- **Cold Start**: CodeBuild containers have startup time on each execution

## Alternatives Considered

### Alternative 1: GitHub Actions
- Native GitHub integration, free for public repos
- **Rejected**: Requires AWS credentials management in GitHub, less native AWS integration, additional complexity for CloudFormation deployments

### Alternative 2: Multi-Account Pipeline
- Separate accounts for dev, staging, production
- **Rejected**: Unnecessary complexity for small project size, increased IAM and cross-account setup overhead

## Future Considerations

### When to Migrate to Multi-Account
**For production use, the pipeline should be migrated to a standalone AWS account separate from the application infrastructure.** This provides:
- Isolation of deployment infrastructure from application workloads
- Enhanced security through separation of concerns
- Protection against accidental resource deletion
- Clearer cost allocation and billing
- Better compliance with AWS Well-Architected Framework

Consider multi-account architecture when:
- Moving to production deployment
- Implementation of features after the hackathon
