# ADR-0003: Environment-Based Configuration

**Status:** Accepted

**Date:** 2025-11-02

**Deciders:** Solo developer

---

## Context

vpn-hopper needs a configuration mechanism that allows users to customize:
- SSH authentication (keys, users, passwords)
- WireGuard connection details (keys, endpoints, allowed IPs)
- Network interface settings

Several configuration approaches exist for containers:

### Option 1: Environment Variables Only
- Configuration via `-e` flags or env files
- Simple, Docker-native
- Limited flexibility for complex configs

### Option 2: Mounted Configuration Files Only
- Mount `wg0.conf` and `sshd_config`
- Full flexibility
- Requires file management

### Option 3: Hybrid (Env Vars + Optional File Mounts)
- Environment variables for simple cases
- File mounts for advanced cases
- Best of both worlds

### Option 4: Runtime API/Configuration Server
- HTTP API or config server inside container
- Dynamic reconfiguration
- Significant complexity

---

## Decision

**vpn-hopper will use a hybrid configuration approach:**

1. **Primary**: Environment variables for common use cases
2. **Override**: Mounted configuration files for advanced scenarios
3. **Priority**: Mounted files take precedence over env vars

---

## Rationale

### Advantages

1. **Ease of Use for Simple Cases**
   ```bash
   docker run -e SSH_USER=admin -e WG_ENDPOINT=vpn.example.com:51820 ...
   ```
   - No file management needed
   - Quick prototyping and testing
   - Copy-paste friendly documentation

2. **Power User Support**
   ```bash
   docker run -v ./wg0.conf:/etc/wireguard/wg0.conf:ro ...
   ```
   - Full WireGuard configuration options
   - Multi-peer setups
   - Custom SSH hardening

3. **Docker-Native**
   - Uses standard Docker patterns
   - Works with Docker Compose env_file
   - Compatible with Docker Swarm secrets
   - Kubernetes ConfigMap/Secret friendly

4. **Security Flexibility**
   - Secrets can stay out of images
   - Environment variables for CI/CD
   - File mounts for production (with proper permissions)
   - Supports both workflows

5. **Backward Compatibility**
   - Can add new env vars without breaking existing deployments
   - File-based configs remain stable

### Disadvantages

1. **Configuration Complexity**
   - Two ways to configure = potential confusion
   - Need clear documentation on precedence

2. **Environment Variable Limits**
   - Size limits on env vars (typically 128KB)
   - Not suitable for very large configs
   - Multi-line handling can be awkward

3. **Secret Exposure Risk**
   - Env vars visible in `docker inspect`
   - Not ideal for sensitive data (mitigated by file mounts)

## Implementation Details

### Configuration Precedence

```
1. Mounted files (highest priority)
   ├─ /etc/wireguard/wg0.conf
   └─ /authorized_keys/authorized_keys

2. Environment variables
   ├─ WG_ADDRESS, WG_PRIVKEY, WG_PEER_PUBKEY, ...
   └─ SSH_USER, SSH_AUTH_KEY, ...

3. Defaults (lowest priority)
   ├─ SSH_USER=vpn
   ├─ WG_IFACE=wg0
   └─ WG_ALLOWED_IPS=0.0.0.0/0
```

### Environment Variables Supported

**SSH Configuration:**
```bash
SSH_USER=vpnadmin          # SSH username (default: wghopper)
SSH_PASSWORD=plaintext     # Plaintext password (required)
SSH_PASSWORD_HASH="$6$..." # Hashed password (preferred, overrides SSH_PASSWORD)
```

**WireGuard Configuration:**
```bash
WG_IFACE=wg0              # Interface name
WG_ADDRESS=10.13.13.5/32  # Client IP
WG_PRIVKEY=secret         # Private key
WG_PEER_PUBKEY=pubkey     # Server public key
WG_ENDPOINT=vpn.com:51820 # Server endpoint
WG_ALLOWED_IPS=0.0.0.0/0  # Routing
WG_DNS=10.13.13.1         # Optional DNS
WG_KEEPALIVE=25           # Keepalive interval
WG_PRESHARED_KEY=psk      # Optional PSK
```

### File Mount Locations

**WireGuard Config:**
```
/etc/wireguard/wg0.conf
```

### Configuration Generation

The entrypoint script follows this logic:

```bash
# WireGuard
if [ -f /etc/wireguard/wg0.conf ]; then
    # Use mounted config file
    echo "Using mounted config"
else
    # Generate from env vars
    if [ -n "$WG_PRIVKEY" ] && [ -n "$WG_PEER_PUBKEY" ]; then
        echo "Generating config from env"
        cat > /etc/wireguard/wg0.conf <<EOF
[Interface]
Address = $WG_ADDRESS
PrivateKey = $WG_PRIVKEY
...
EOF
    fi
fi

# SSH - Password required
if [ -n "$SSH_PASSWORD_HASH" ]; then
    usermod -p "$SSH_PASSWORD_HASH" "$SSH_USER"
elif [ -n "$SSH_PASSWORD" ]; then
    echo "$SSH_USER:$SSH_PASSWORD" | chpasswd
else
    echo "Error: SSH_PASSWORD or SSH_PASSWORD_HASH required"
    exit 1
fi
```

## Consequences

### Positive

- **Flexibility**: Supports both simple and complex deployments
- **Discoverability**: Users can start simple, graduate to files when needed
- **Ecosystem Fit**: Works with standard Docker tooling
- **Documentation**: Can show progressive examples (simple → advanced)

### Negative

- **Testing Surface**: Must test both env var and file-based configs
- **Error Handling**: Need clear errors when configs conflict or are incomplete
- **Documentation Burden**: Must explain both approaches and precedence

### Mitigations

- Document configuration precedence clearly in setup guide
- Provide example `.env` file for common env var scenarios
- Provide example `wg0.conf` for complex scenarios
- Log which configuration method was used at container startup

## Use Case Examples

### Use Case 1: Quick Testing (Env Vars)
```bash
docker run -d \
  -e SSH_USER=test \
  -e SSH_PASSWORD=test123 \
  -e WG_ADDRESS=10.13.13.5/32 \
  -e WG_PRIVKEY=$WG_KEY \
  -e WG_ENDPOINT=vpn.example.com:51820 \
  vpn-hopper:latest
```

### Use Case 2: Production (Mounted Files + Hashed Password)
```bash
docker run -d \
  -e SSH_USER=vpnadmin \
  -e SSH_PASSWORD_HASH="$6$rounds=656000$..." \
  -v /secure/wg0.conf:/etc/wireguard/wg0.conf:ro \
  vpn-hopper:latest
```

### Use Case 3: Hybrid (Env Password + File WG)
```bash
docker run -d \
  -e SSH_PASSWORD=secure-password \
  -v ./multi-peer-wg0.conf:/etc/wireguard/wg0.conf:ro \
  vpn-hopper:latest
```

### Use Case 4: Docker Compose
```yaml
services:
  vpn-hopper:
    image: vpn-hopper:latest
    env_file:
      - .env
    volumes:
      - ./wg0.conf:/etc/wireguard/wg0.conf:ro
```

## Alternatives Considered

### Alternative 1: Config File Only (No Env Vars)

**Example:**
```bash
docker run -v ./config:/config vpn-hopper:latest
```

**Rejected because:**
- Higher barrier to entry for new users
- Requires external file management for simple use cases
- Less portable across environments
- Harder to demo in documentation

### Alternative 2: Baked-In Config (Build-Time)

**Example:**
```dockerfile
FROM vpn-hopper:latest
COPY wg0.conf /etc/wireguard/
COPY authorized_keys /authorized_keys/
```

**Rejected because:**
- Secrets in image layers (security risk)
- New build required for config changes
- Not portable between environments
- Violates 12-factor app principles

### Alternative 3: Runtime API Configuration

**Example:**
```bash
curl -X POST http://localhost:8080/config \
  -d '{"wg_endpoint": "vpn.example.com:51820"}'
```

**Rejected because:**
- Significant complexity (web server, API, validation)
- Security concerns (auth, TLS, injection)
- Not aligned with container best practices
- Overkill for the use case

## Security Considerations

### Environment Variables
- ⚠️ Visible in `docker inspect`
- ⚠️ Plaintext passwords may appear in process listings
- ✅ Easier to inject from CI/CD secrets
- ✅ Can use Docker secrets (Swarm) or K8s secrets
- ✅ `SSH_PASSWORD_HASH` mitigates plaintext exposure

### Mounted Files
- ✅ Can use host filesystem permissions (600)
- ✅ Not visible in container inspect output
- ✅ Easier to rotate (just replace file)
- ⚠️ Need to manage file permissions carefully

### Recommendation
**For production:**
- Use `SSH_PASSWORD_HASH` instead of `SSH_PASSWORD`
- Mount WireGuard config files with restricted permissions (600)
- Or use Docker/K8s secret mechanisms
- Never commit passwords to version control

## Review

Should be reviewed if:

---

## Notes

This hybrid approach follows the principle of **progressive disclosure**: simple things should be simple, complex things should be possible.

It also aligns with the **12-factor app** methodology while acknowledging that not all containers are web apps.
