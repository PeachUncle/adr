# ADR 005: Integration Testing Over Unit Testing

## Status

Accepted (December 2024)

## Context

We need a testing strategy that catches bugs while remaining maintainable as the codebase evolves. The question is: **What should we test, and how?**

### Option 1: Comprehensive unit tests (test everything in isolation)

```typescript
// Test component in isolation with all dependencies mocked
describe("CampaignCard", () => {
  it("renders campaign name", () => {
    const mockCampaign = { id: "1", name: "Test" };
    const { getByText } = shallow(<CampaignCard campaign={mockCampaign} />);
    expect(getByText("Test")).toBeInTheDocument();
  });

  it("calls onDelete when delete clicked", () => {
    const mockOnDelete = jest.fn();
    const wrapper = shallow(<CampaignCard onDelete={mockOnDelete} />);
    wrapper.find(".delete-button").simulate("click");
    expect(mockOnDelete).toHaveBeenCalled();
  });
});
```

**Pros:**

- Fast (no DOM rendering)
- Isolates component behavior
- High coverage numbers

**Cons:**

- **Breaks on refactors**: Rename CSS class → test fails
- **False confidence**: Component works in isolation but fails when integrated
- **Doesn't test real user behavior**: Mocks everything, never calls actual hooks/services
- **Maintenance burden**: Refactor component → update 20 tests
- **Snapshot hell**: Snapshots break on every CSS/layout change

### Option 2: E2E tests (test entire application flow)

```typescript
// Test with Playwright/Cypress
test("user can create campaign", async ({ page }) => {
  await page.goto("http://localhost:5173");
  await page.click("text=Login");
  await page.fill("input[name=email]", "test@example.com");
  await page.fill("input[name=password]", "password");
  await page.click("button[type=submit]");

  await page.click("text=New Campaign");
  await page.fill("input[name=name]", "My Campaign");
  await page.click("text=Create");

  await expect(page.locator("text=My Campaign")).toBeVisible();
});
```

**Pros:**

- Tests real user flows
- Catches integration bugs
- High confidence (if E2E passes, feature works)

**Cons:**

- **Slow**: 10+ seconds per test (start browser, navigate, interact)
- **Flaky**: Network timing issues, race conditions
- **Hard to debug**: When test fails, unclear which part broke
- **Expensive to maintain**: Backend changes → update all E2E tests
- **Requires running backend**: Cannot test frontend in isolation

### Option 3: Integration tests with mocked backend (our approach)

```typescript
// Test component with real hooks, mocked service calls
import { render, screen, waitFor } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { vi } from "vitest";
import * as campaignService from "../services/campaignService";

describe("CampaignList", () => {
  it("creates campaign when form submitted", async () => {
    // Mock service layer (not hooks, not components)
    const createSpy = vi
      .spyOn(campaignService, "createCampaign")
      .mockResolvedValue({ status: "OK", code: 200 });

    // Render real component tree (hooks, context, everything)
    render(<CampaignList />);

    // Simulate real user interaction
    await userEvent.click(
      screen.getByRole("button", { name: /new campaign/i })
    );
    await userEvent.type(screen.getByLabelText(/name/i), "Welcome Campaign");
    await userEvent.click(screen.getByRole("button", { name: /create/i }));

    // Verify service was called with correct data
    await waitFor(() => {
      expect(createSpy).toHaveBeenCalledWith(
        expect.objectContaining({ name: "Welcome Campaign" })
      );
    });
  });
});
```

**Pros:**

- **Tests real behavior**: User clicks → hook calls service → UI updates
- **Fast**: No browser, no backend (service mocked)
- **Refactor-safe**: Change implementation → tests still pass (if behavior unchanged)
- **Easy to debug**: Clear what broke (service not called, wrong data, etc.)
- **Catches integration bugs**: Hook + component + context all tested together

**Cons:**

- Not true E2E (backend mocked)
- Requires good mock strategy (MSW or manual spies)
- Doesn't catch backend contract changes (if backend changes response shape, tests still pass)

## Decision

**We will focus on integration tests that render full component trees with real hooks and mocked service calls. Unit tests only for pure utility functions. E2E tests deferred until backend API stabilizes.**

### Testing Pyramid (Our Distribution):

```
     /\
    /E2E\         ← 0% (deferred)
   /------\
  /Integration\   ← 70% (focus here)
 /------------\
/Unit Tests    \  ← 30% (only pure functions)
----------------
```

### What We Test:

#### ✅ 1. Permission Gating (Business Rules)

```typescript
it("hides delete button when user lacks permission", () => {
  const authValue = {
    hasPermission: (resource: string, action: string) => {
      if (resource === "campaigns" && action === "delete") return false;
      return true;
    },
  };

  render(
    <AuthContext.Provider value={authValue}>
      <CampaignCard campaign={mockCampaign} />
    </AuthContext.Provider>
  );

  expect(
    screen.queryByRole("button", { name: /delete/i })
  ).not.toBeInTheDocument();
});
```

**Why**: Permission checks are business logic. If they break, users see features they can't use.

#### ✅ 2. Component Integration (User Flows)

```typescript
it("creates agent when form is valid", async () => {
  const createSpy = vi
    .spyOn(agentService, "createAgent")
    .mockResolvedValue({ status: "OK" });

  render(<AddAgentModal open={true} onOpenChange={() => {}} />);

  await userEvent.type(screen.getByPlaceholderText("Agent Name"), "My Agent");
  await userEvent.type(screen.getByPlaceholderText("Agent ID"), "AGENT-1");
  await userEvent.click(screen.getByRole("button", { name: /create/i }));

  await waitFor(() => expect(createSpy).toHaveBeenCalled());
});
```

**Why**: This is how users interact. If this breaks, feature is broken.

#### ✅ 3. Edge Cases (Pagination, Infinite Scroll, Error States)

```typescript
it("loads next page when scrolling to bottom", async () => {
  const mockFetch = vi
    .fn()
    .mockResolvedValueOnce({
      info: [
        /* page 1 */
      ],
      currentPage: 1,
      totalPages: 3,
    })
    .mockResolvedValueOnce({
      info: [
        /* page 2 */
      ],
      currentPage: 2,
      totalPages: 3,
    });

  vi.spyOn(conversationService, "getThreads").mockImplementation(mockFetch);

  render(<ConversationList />);

  // Wait for first page
  await screen.findByText("Thread 1");

  // Scroll to bottom
  const lastItem = screen.getByTestId("thread-list-end");
  fireEvent.scroll(lastItem); // Triggers intersection observer

  // Verify second page loaded
  await waitFor(() => expect(mockFetch).toHaveBeenCalledTimes(2));
});
```

**Why**: Infinite scroll has complex state. Easy to double-fetch or skip pages.

#### ✅ 4. Pure Functions (Utility Logic)

```typescript
// utils/permissions.test.ts
describe("parseRolePermissions", () => {
  it("parses JSON string permissions", () => {
    const input = '{"campaigns": {"view": true, "create": false}}';
    const result = parseRolePermissions(input);
    expect(result).toEqual({ campaigns: { view: true, create: false } });
  });

  it("returns empty object for invalid JSON", () => {
    const result = parseRolePermissions("invalid json");
    expect(result).toEqual({});
  });
});
```

**Why**: Pure functions are easy to test. No mocking needed.

### What We DON'T Test:

#### ❌ 1. Styled Components (Snapshot Tests)

```typescript
// Anti-pattern we avoid
it("matches snapshot", () => {
  const tree = renderer.create(<CampaignCard campaign={mock} />).toJSON();
  expect(tree).toMatchSnapshot();
});
```

**Why NOT**:

- Breaks on every CSS change
- Doesn't prove behavior
- Snapshot diffs are unreadable

#### ❌ 2. Shallow Rendering

```typescript
// Anti-pattern we avoid
it("renders correctly", () => {
  const wrapper = shallow(<CampaignList />);
  expect(wrapper.find(".campaign-item")).toHaveLength(3);
});
```

**Why NOT**:

- Doesn't test hooks (SWR, useAuth)
- Doesn't test context integration
- False confidence (component works in shallow render, fails in real app)

#### ❌ 3. SWR/React Query Internals

```typescript
// Anti-pattern we avoid
it("calls useSWR with correct key", () => {
  const swrSpy = vi.spyOn(SWR, "default");
  render(<CampaignList />);
  expect(swrSpy).toHaveBeenCalledWith(
    ["/campaigns", 1, 10],
    expect.any(Function)
  );
});
```

**Why NOT**:

- Tests implementation, not behavior
- If we swap SWR for React Query, test breaks (but behavior unchanged)
- User doesn't care how data is fetched, only that it appears

#### ❌ 4. Third-Party Libraries

```typescript
// Anti-pattern we avoid
it("axios is called with correct URL", () => {
  const axiosSpy = vi.spyOn(axios, "get");
  // ...
});
```

**Why NOT**:

- We trust axios works (it has its own tests)
- We test our service layer, which uses axios
- If axios breaks, their tests will catch it

## Consequences

### Positive

1. **Refactor-Safe Tests**:

   - Changed campaign card from `<Card>` to `<div>` → tests still pass
   - Swapped useState for useReducer → tests still pass
   - Renamed CSS classes → tests still pass

   **What makes test fail**: User-facing behavior changes (button doesn't call service, wrong data sent)

2. **Fast Feedback Loop**:

   - ~2 seconds to run all tests (11 test suites)
   - No browser startup, no backend
   - Can run on every save (Vitest watch mode)

3. **Clear Failure Messages**:

   ```
   ✕ creates campaign when form submitted (25 ms)

   Expected spy to have been called with:
     [{ name: 'Welcome Campaign', agentId: 'AGENT-1' }]
   Received:
     [{ name: 'Welcome Campaign' }]

   → Missing agentId in service call
   ```

   Clear what broke, easy to fix.

4. **Onboarding**:
   - New developer reads test: "Oh, this component calls campaignService.createCampaign"
   - Tests document expected behavior
   - Tests show how to use components (render with providers, user interactions)

### Negative

1. **Not True E2E**:

   - Backend could change response shape → tests still pass
   - Network errors not caught
   - OAuth flow not tested end-to-end

   **Mitigation**: Will add E2E tests when backend stabilizes (ADR noted in "When to revisit")

2. **Mocking Overhead**:

   - Every test must mock services
   - If service signature changes, must update mocks

   **Mitigation**: Centralized test utilities:

   ```typescript
   // __tests__/test-utils.tsx
   export function mockCampaignService() {
     vi.spyOn(campaignService, "getCampaigns").mockResolvedValue(mockData);
     vi.spyOn(campaignService, "createCampaign").mockResolvedValue({
       status: "OK",
     });
   }
   ```

3. **Context Boilerplate**:

   - Must wrap every component with providers (Auth, Toast, Router)

   **Mitigation**: Custom render helper:

   ```typescript
   export function renderWithProviders(
     ui: ReactElement,
     { auth = defaultAuth } = {}
   ) {
     return render(
       <AuthContext.Provider value={auth}>
         <ToastProvider>
           <MemoryRouter>{ui}</MemoryRouter>
         </ToastProvider>
       </AuthContext.Provider>
     );
   }
   ```

## Implementation

### Test File Structure

```
src/
  __tests__/
    agents.test.tsx           # Integration tests for agent features
    campaigns.test.tsx        # Integration tests for campaign features
    conversations.test.tsx    # Infinite scroll, threading tests
    test-utils.tsx           # Shared test helpers
  utils/
    __tests__/
      permissions.test.ts    # Unit tests for pure functions
      format.test.ts         # Unit tests for formatters
```

### Test Utilities (test-utils.tsx)

```typescript
import { ReactElement } from "react";
import { render, RenderOptions } from "@testing-library/react";
import { AuthContext } from "../contexts/AuthContext";
import { ToastProvider } from "../components/ui/toast";
import { MemoryRouter } from "react-router-dom";

// Default auth value for tests
export function makeAuth(permissions: string = "all") {
  const allPermissions = {
    campaigns: { view: true, create: true, edit: true, delete: true },
    agents: { view: true, create: true, edit: true, delete: true },
  };

  const viewOnly = {
    campaigns: { view: true, create: false, edit: false, delete: false },
    agents: { view: true, create: false, edit: false, delete: false },
  };

  return {
    user: { id: "1", email: "test@example.com", role: "admin" },
    isAuthenticated: true,
    permissions: permissions === "all" ? allPermissions : viewOnly,
    hasPermission: (resource: string, action: string) => {
      const perms = permissions === "all" ? allPermissions : viewOnly;
      return perms[resource]?.[action] ?? false;
    },
  };
}

export function renderWithProviders(
  ui: ReactElement,
  { route = "/", auth = makeAuth() }: { route?: string; auth?: any } = {}
) {
  return render(
    <AuthContext.Provider value={auth}>
      <ToastProvider>
        <MemoryRouter initialEntries={[route]}>{ui}</MemoryRouter>
      </ToastProvider>
    </AuthContext.Provider>
  );
}
```

### Example Test (campaigns.test.tsx)

```typescript
import { describe, it, expect, vi, beforeEach } from "vitest";
import { screen, waitFor } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { renderWithProviders, makeAuth } from "./test-utils";
import * as campaignService from "../services/campaignService";
import { CampaignList } from "../pages/Campaigns";

describe("Campaign Management", () => {
  beforeEach(() => {
    vi.clearAllMocks();
  });

  it("fetches and displays campaigns", async () => {
    const mockData = {
      info: [
        { id: "1", name: "Campaign 1", status: 1 },
        { id: "2", name: "Campaign 2", status: 1 },
      ],
      currentPage: 1,
      totalPages: 1,
    };

    vi.spyOn(campaignService, "getCampaigns").mockResolvedValue(mockData);

    renderWithProviders(<CampaignList />);

    await waitFor(() => {
      expect(screen.getByText("Campaign 1")).toBeInTheDocument();
      expect(screen.getByText("Campaign 2")).toBeInTheDocument();
    });
  });

  it("hides create button when user lacks permission", () => {
    renderWithProviders(<CampaignList />, { auth: makeAuth("view") });

    expect(
      screen.queryByRole("button", { name: /new campaign/i })
    ).not.toBeInTheDocument();
  });

  it("creates campaign when form submitted", async () => {
    const createSpy = vi
      .spyOn(campaignService, "createCampaign")
      .mockResolvedValue({ status: "OK", code: 200 });

    renderWithProviders(<CampaignList />);

    await userEvent.click(
      screen.getByRole("button", { name: /new campaign/i })
    );
    await userEvent.type(screen.getByLabelText(/name/i), "Welcome Campaign");
    await userEvent.click(screen.getByRole("button", { name: /create/i }));

    await waitFor(() => {
      expect(createSpy).toHaveBeenCalledWith(
        expect.objectContaining({ name: "Welcome Campaign" })
      );
    });
  });
});
```

## Compliance

### How to verify we follow this decision:

```bash
# No shallow rendering
grep -r "shallow(" src/__tests__/
# Expected: 0 results

# No snapshot tests of components
grep -r "toMatchSnapshot" src/__tests__/
# Expected: 0 results (only allow for test-utils or pure data structures)

# Integration tests use renderWithProviders
grep -r "renderWithProviders" src/__tests__/ | wc -l
# Expected: 20+ (most tests use this helper)

# Services are spied, not mocked entirely
grep -r "vi.spyOn.*Service" src/__tests__/ | wc -l
# Expected: 30+ (spy on specific methods, not whole module)
```

### Coverage Targets:

- **Services**: 80%+ (unit tests, no React needed)
- **Hooks**: 60%+ (integration tests with components)
- **Components**: 50%+ (critical paths only, not every render variation)
- **Utils**: 90%+ (pure functions, easy to test)

**We don't chase 100% coverage.** We test what matters.

### When to revisit:

- If tests become slow (> 10 seconds) → investigate mocking strategy
- If tests break on every refactor → we're testing implementation, not behavior
- When backend API stabilizes → add E2E tests with Playwright
- If integration tests miss too many bugs → increase coverage or add E2E

## Real-World Results

### Metrics (After 6 Months):

- **Test count**: 47 integration tests, 18 unit tests
- **Test runtime**: ~2 seconds (all tests)
- **Bugs caught by tests**: 12 (mostly permission checks, edge cases)
- **Bugs missed by tests**: 3 (backend contract changes)
- **Flaky tests**: 0 (no network, no browser = stable)
- **Tests updated due to refactor**: 2 (both were legitimate behavior changes)

### Developer Feedback:

> "I refactored the campaign card from a table to a grid layout. Zero tests broke. That's when I knew our testing strategy was right."
> – Developer 1

> "Integration tests are documentation. When I need to add a feature, I read the test to see how to use the component."
> – Developer 2

## Philosophy: Tests Should Fail When Behavior Changes

**Good test failure** (behavior changed):

```
✕ creates campaign when form submitted

Expected spy to have been called, but it was not called.

→ Form no longer calls createCampaign. This is a bug.
```

**Bad test failure** (implementation changed):

```
✕ renders correctly

Snapshot mismatch:
  - <div className="campaign-card">
  + <article className="campaign-card">

→ Changed HTML tag from div to article. Behavior unchanged, but test broke.
```

Our strategy: **Only the first type of failure is valuable.**
