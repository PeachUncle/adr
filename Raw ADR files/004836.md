# ADR-005: Checkpoint-Based Retry System for Segmented Narratives

## Status
**ACCEPTED** - 2025-10-03

## Context
When generating segmented narratives over long time periods (days/weeks), LLM providers occasionally timeout due to:
- Network latency issues
- Model processing delays
- Server load variations
- Long-running inference on complex segments

Previously, a timeout on any segment meant:
- Loss of all successfully generated segments
- Need to regenerate the entire narrative from scratch
- Wasted time and API calls
- Poor user experience for multi-hour generation runs

The user requested a solution where failed segments can be regenerated without losing completed work.

## Decision
Implement **Option 4: Segment Checkpoint Files with Resume Capability** from the proposed solutions:

### Architecture Components

1. **Checkpoint Domain Models** (`domain/checkpoints.py`):
   - `SegmentStatus` enum: PENDING, SUCCESS, TIMEOUT, ERROR
   - `SegmentCheckpoint`: Stores segment metadata, status, narrative, and errors
   - `CheckpointMetadata`: Run-level metadata (run_id, time_range, total_segments)
   - `CheckpointManager`: Handles checkpoint persistence and retrieval

2. **Checkpoint Storage**:
   - Location: `~/.aw-narrator-checkpoints/{run_id}/`
   - Files per run:
     - `metadata.json`: Run metadata
     - `segment_NNN.json`: Checkpoint for each segment
     - `segment_NNN_activities.json`: Activities for segment regeneration
   - Run ID format: `{timestamp}_{hash}` for uniqueness

3. **CLI Integration**:
   - `--resume RUN_ID`: Resume from checkpoint, regenerate only failed segments
   - `--list-checkpoints`: Show all available checkpoint runs with status
   - `--no-checkpoints`: Disable checkpoint saving (not recommended)
   - Checkpoints enabled by default for segmented narratives

4. **Error Handling**:
   - Timeout errors caught and saved with TIMEOUT status
   - Generic errors caught and saved with ERROR status
   - Placeholder narratives inserted for failed segments
   - Clear CLI output showing failed segment numbers
   - Instructions provided for retry command

### Resume Workflow

```bash
# Initial run with timeout on segment 3
aw-narrator --yesterday --segment-hours 1 --llm-provider lmstudio
# Output: ⚠️ 1 segment(s) failed: [3]
#         To retry failed segments, run: aw-narrator --resume 20251003_105959_a1b2c3d4e5f6

# Resume to regenerate only failed segments
aw-narrator --resume 20251003_105959_a1b2c3d4e5f6
# Loads existing successful segments from cache
# Regenerates only segment 3
# Combines all segments into final narrative
```

## Consequences

### Positive
- **Never lose completed work**: Successful segments are preserved
- **Efficient retries**: Only regenerate failed segments
- **Crash recovery**: Can resume after application crashes, not just timeouts
- **Debugging capability**: Inspect individual segment checkpoints
- **Future-ready**: Architecture supports parallel processing enhancement
- **User control**: Clear visibility into what failed and how to retry
- **Minimal overhead**: Checkpoint I/O is negligible compared to LLM generation time

### Negative
- **Disk usage**: Checkpoints consume disk space (~1-5MB per run)
- **Cleanup required**: Users may need to manually clean old checkpoints
- **Complexity**: Additional code paths for checkpoint management
- **State management**: Need to handle checkpoint versioning if data models change

### Implementation Details

**Checkpoint Manager Features**:
- Automatic run ID generation based on time range and activity count
- JSON serialization for human-readable checkpoints
- Activity reconstruction from saved data
- Failed segment identification and filtering
- Run cleanup utilities

**Segmented Narrative Integration**:
- Checkpoints saved after each segment generation
- Try-catch blocks around LLM calls to capture timeouts/errors
- Return tuple: `(Narrative, run_id | None)` for checkpoint tracking
- Progress indicators show checkpoint status

**Resume Function**:
- Validates run_id exists
- Loads all checkpoints and identifies failed segments
- Reuses successful segments from cache
- Regenerates failed segments with same LLM provider
- Combines all segments into cohesive narrative

### Future Enhancements
- Automatic checkpoint cleanup (age-based or count-based)
- Checkpoint compression for large runs
- Parallel segment regeneration
- Checkpoint migration tools for model changes
- Web UI for checkpoint management

## Alternatives Considered

1. **Inline Retry Loop with Exponential Backoff**: Simpler but less flexible, can't resume across sessions
2. **State Cache with Retry Command**: Similar but less granular than checkpoint files
3. **Two-Phase Generation with Placeholders**: Requires output parsing, more complex
4. **Interactive Retry Prompts**: Poor UX for automated workflows, interrupts generation

Option 4 (Checkpoints) chosen for robustness, flexibility, and future extensibility.
