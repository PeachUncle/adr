# ADR 001: Domain-Driven Design Architecture

## Status
Accepted

## Context

The ASDEFCON platform deals with a complex domain:
- Contract assembly with multiple document types (FPS, OCD, specifications)
- Clause dependencies and conflict resolution
- Multi-layered compliance rules
- Collaborative workflows with approvals
- Security classifications
- Multi-tenancy requirements

The codebase must be:
- Maintainable by multiple teams
- Testable at all layers
- Adaptable to changing requirements
- Secure and auditable
- Scalable

## Decision

We will adopt **Domain-Driven Design (DDD)** with **Clean Architecture** as our core architectural pattern.

### Structure

Each service follows this layered architecture:

```
┌─────────────────────────────────┐
│  Presentation Layer             │  FastAPI routes, middleware, schemas
├─────────────────────────────────┤
│  Application Layer              │  Use cases, DTOs, orchestration
├─────────────────────────────────┤
│  Domain Layer                   │  Entities, value objects, domain services
├─────────────────────────────────┤
│  Infrastructure Layer           │  Database, AI, storage, message bus
└─────────────────────────────────┘
```

### Layer Responsibilities

**Domain Layer**:
- Pure Python, minimal external dependencies
- Business logic and rules
- Entities and value objects
- Domain services
- Repository interfaces (protocols)
- Domain exceptions

**Application Layer**:
- Use case implementations
- Application services
- DTOs for layer boundaries
- Port interfaces for infrastructure
- Orchestration of domain logic

**Infrastructure Layer**:
- Database implementations
- AI service clients
- Storage adapters
- Message bus implementations
- External API clients
- Concrete repository implementations

**Presentation Layer**:
- FastAPI routes and middleware
- Request/response schemas (Pydantic)
- Authentication and authorization
- Input validation
- Error handling

### Key Principles

1. **Dependency Rule**: Dependencies point inward. Domain never depends on outer layers.

2. **Entities**: Rich domain models with behavior, not anemic data containers.

3. **Value Objects**: Immutable objects representing domain concepts.

4. **Repositories**: Abstract data access, implemented in infrastructure.

5. **Domain Services**: Business logic that doesn't belong to a single entity.

6. **Use Cases**: Application-specific business rules.

## Consequences

### Positive

- **Testability**: Domain logic can be tested without infrastructure
- **Maintainability**: Clear separation of concerns
- **Flexibility**: Easy to swap infrastructure implementations
- **Team Scalability**: Teams can work independently on different layers
- **Business Alignment**: Code structure reflects business concepts
- **Onboarding**: New developers can understand structure quickly

### Negative

- **Initial Complexity**: More files and abstractions than simple layered architecture
- **Boilerplate**: More code for interfaces and DTOs
- **Learning Curve**: Team must understand DDD principles
- **Over-engineering Risk**: Small features might feel over-architected

### Mitigations

- Comprehensive documentation and examples
- Code generation for boilerplate (e.g., repository templates)
- Regular architecture reviews
- Team training on DDD patterns

## Example Structure

```python
# Domain Layer
# domain/models/document.py
from __future__ import annotations
from dataclasses import dataclass
from typing import Protocol

@dataclass(frozen=True)
class DocumentId:
    """Value object representing a document identifier."""
    value: str

class Document:
    """Aggregate root for document entity."""
    def __init__(self, id: DocumentId, content: str):
        self._id = id
        self._content = content
        self._analyzed = False

    def mark_analyzed(self) -> None:
        """Domain method for state transition."""
        self._analyzed = True

# domain/repositories/document_repository.py
class DocumentRepository(Protocol):
    """Abstract repository interface."""
    async def save(self, document: Document) -> None: ...
    async def find_by_id(self, id: DocumentId) -> Document | None: ...

# Application Layer
# application/use_cases/analyze_document.py
class AnalyzeDocumentUseCase:
    """Use case for analyzing a document."""
    def __init__(
        self,
        document_repo: DocumentRepository,
        ai_service: AIService,
    ):
        self._document_repo = document_repo
        self._ai_service = ai_service

    async def execute(self, document_id: str) -> AnalysisResult:
        doc = await self._document_repo.find_by_id(DocumentId(document_id))
        analysis = await self._ai_service.analyze(doc.content)
        doc.mark_analyzed()
        await self._document_repo.save(doc)
        return analysis

# Infrastructure Layer
# infrastructure/persistence/postgres/document_repository.py
class PostgresDocumentRepository(DocumentRepository):
    """Concrete implementation of document repository."""
    async def save(self, document: Document) -> None:
        # Database-specific implementation
        pass

# Presentation Layer
# presentation/api/v1/routes/documents.py
@router.post("/documents/{document_id}/analyze")
async def analyze_document(
    document_id: str,
    use_case: AnalyzeDocumentUseCase = Depends(get_use_case),
):
    result = await use_case.execute(document_id)
    return AnalysisResponse.from_domain(result)
```
