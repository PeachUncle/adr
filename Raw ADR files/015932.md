# ADR-001: Use Axum as the Web Framework

## Status

Accepted

## Context

RustDrop needs a web framework to handle HTTP requests for file uploads, downloads, and administrative functions. The Rust ecosystem offers several mature web frameworks, each with different design philosophies and tradeoffs:

- **Actix-web**: High-performance, actor-based framework with the largest ecosystem
- **Axum**: Modern, tower-based framework from the Tokio team with excellent type safety
- **Rocket**: Developer-friendly framework with macro-based routing
- **Warp**: Filter-based, composable framework
- **Tide**: Async-std based framework with Express.js-like API

Key requirements for RustDrop:
1. Strong async support for handling concurrent file uploads/downloads
2. Good multipart form handling for file uploads
3. Easy integration with the Tokio ecosystem
4. Type-safe routing and request handling
5. Middleware support for logging, CORS, and static file serving
6. Active maintenance and community support

## Decision

We chose **Axum 0.7** as the web framework for RustDrop.

### Justification

1. **Tokio Native Integration**: Axum is built by the Tokio team and integrates seamlessly with the Tokio async runtime, which we already need for async file I/O. This eliminates runtime compatibility issues.

2. **Tower Middleware Ecosystem**: Axum is built on Tower, providing access to a rich ecosystem of middleware including:
   - `tower-http` for static file serving, CORS, and request tracing
   - Composable layers that can be applied at router or handler level
   - Battle-tested middleware from production systems

3. **Type-Safe Extractors**: Axum's extractor pattern provides compile-time safety for request handling:
   ```rust
   async fn upload(
       State(state): State<Arc<AppState>>,
       multipart: Multipart,
   ) -> Result<impl IntoResponse, AppError>
   ```
   This catches errors at compile time rather than runtime.

4. **Excellent Multipart Support**: The `axum::extract::Multipart` extractor provides streaming multipart handling, crucial for large file uploads without buffering entire files in memory.

5. **No Macros Required**: Unlike Rocket, Axum doesn't require procedural macros for routing, leading to faster compile times and easier debugging.

6. **Ergonomic Shared State**: The `State` extractor with `Arc<T>` provides a clean pattern for sharing application state across handlers.

## Consequences

### Positive

- **Compile-time safety**: Type errors in route handlers are caught during compilation
- **Performance**: Minimal abstraction overhead, efficient async handling
- **Ecosystem compatibility**: Easy integration with other Tokio-based crates
- **Maintainability**: Clear, explicit code without magic macros
- **Future-proof**: Active development and strong backing from the Tokio team

### Negative

- **Learning curve**: Developers familiar with Express.js or Flask may find the type-heavy approach initially challenging
- **Boilerplate**: Some patterns require more explicit code compared to macro-heavy frameworks
- **Newer framework**: Smaller ecosystem of Axum-specific tutorials and examples compared to Actix-web

### Neutral

- **Performance vs Actix-web**: While Actix-web sometimes benchmarks higher, the difference is negligible for RustDrop's use case (file I/O bound, not compute bound)

## Alternatives Considered

### Actix-web

**Pros:**
- Highest raw performance in benchmarks
- Largest ecosystem and community
- Mature and battle-tested

**Cons:**
- Actor model adds complexity not needed for this use case
- Historical stability concerns (though now resolved)
- Different async runtime (actix-rt) requires care with Tokio interop

**Why not chosen:** The added complexity of the actor model doesn't benefit a straightforward file-sharing service, and the Tokio-native integration of Axum was preferred.

### Rocket

**Pros:**
- Very developer-friendly API
- Excellent documentation
- Request guards provide elegant authorization

**Cons:**
- Heavy use of procedural macros increases compile times
- Historically slow to adopt async (now supported in 0.5+)
- Less flexibility in middleware composition

**Why not chosen:** The macro-heavy approach made debugging harder, and compile times were noticeably longer.

### Warp

**Pros:**
- Composable filter-based design
- Also built on Tower/Tokio
- Functional programming style

**Cons:**
- Filter composition can lead to complex type signatures
- Less intuitive for developers from other web frameworks
- Smaller community than Axum

**Why not chosen:** The filter-based API, while powerful, made the code harder to read and maintain for a team with varied Rust experience.
