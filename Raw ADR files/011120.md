# ADR-001: Programming Language Selection

**Status**: DECIDED  
**Date**: 2025-12-18  
**Updated**: 2025-12-18  
**Context**: Foundation setup

## Decision

**Dual-layer architecture:**
- **Lean 4** — Computation layer (all proofs and mathematical logic)
- **Rust** — Visualization layer (rendering, pixel output, hardware interaction)

## Rationale

No single language satisfies all requirements. The solution is architectural separation:

```
┌─────────────────────────────────────────────────────────┐
│                  VISUALIZATION LAYER                    │
│                       (Rust)                            │
│   • Real-time rendering (60+ FPS)                       │
│   • GPU/shader interaction                              │
│   • Framebuffer/pixel manipulation                      │
│   • Hardware-accelerated graphics                       │
│   • "Dumb renderer" — displays what Lean computes       │
└─────────────────────────────────────────────────────────┘
                           ▲
                           │ FFI / Data serialization
                           │ (proven computation results)
                           │
┌─────────────────────────────────────────────────────────┐
│                   COMPUTATION LAYER                     │
│                       (Lean 4)                          │
│   • All mathematical proofs                             │
│   • Physics simulation                                  │
│   • Matrix/vector operations                            │
│   • Coordinate transformations                          │
│   • Geometry and spatial logic                          │
│   • Proofs embedded in code (dependent types)           │
└─────────────────────────────────────────────────────────┘
```

## Original Question

Which programming language best serves the project's core principles?

## Requirements

### Computation Layer Requirements
1. **Functional paradigm support** — First-class functions, immutability, pure functions
2. **Mathematical precision** — Arbitrary precision arithmetic or reliable numerics
3. **Type safety** — Strong typing to catch errors at compile time
4. **Theorem proving** — Ability to formally verify code
5. **Practicality** — Reasonable tooling and ecosystem

### Visualization Layer Requirements
1. **Real-time performance** — 60+ FPS rendering capability
2. **Hardware access** — GPU, framebuffer, display interaction
3. **Memory safety** — No crashes or undefined behavior
4. **FFI capability** — Interop with computation layer
5. **Graphics ecosystem** — Libraries for rendering

## Analysis: Computation Layer

### For Maximum Rigor: Lean 4
- Dependent types allow proofs within the code
- Growing mathlib ecosystem
- Better performance than older proof assistants
- Active development and community

### For Practical Rigor: Haskell
- Mature functional language
- Strong type system (with extensions)
- Can use QuickCheck for property-based testing
- Good numeric libraries
- LiquidHaskell for refinement types (optional verification)

## Analysis: Visualization Layer

### For Safety + Performance: Rust
- Zero-cost abstractions
- Memory safety without garbage collection
- Excellent graphics ecosystem (wgpu, vulkano, pixels, minifb)
- Good FFI capabilities
- Growing Lean 4 interop tooling

### For Maximum Control: C
- Universal FFI (easiest Lean interop)
- Maximum hardware control
- Mature graphics libraries
- Manual memory management (risk)

### For Simplicity: Zig
- Simple, readable systems language
- Easy C interop
- Growing but smaller ecosystem

## Recommendation

Given the dual-layer architecture, we select the best language for each layer:

### Computation Layer: Lean 4
**Rationale**: The goal is "proof-first development" — proofs must exist BEFORE code is written. Lean 4 uniquely satisfies this by making proofs and code the same artifact. Code cannot compile without a valid proof.

### Visualization Layer: Rust
**Rationale**: Visualization requires real-time performance and hardware access that proof-oriented languages cannot provide. Rust offers memory safety comparable to proof guarantees, excellent graphics ecosystem, and good FFI for Lean interop.

## Final Decision

### Computation Layer: Lean 4
- Proofs and code are unified — code cannot compile without valid proof
- Dependent types provide maximum mathematical rigor
- Growing mathlib ecosystem for mathematical foundations
- Better performance than older proof assistants
- Active development and community

### Visualization Layer: Rust  
- Zero-cost abstractions for real-time performance
- Memory safety without garbage collection
- Minimal framebuffer libraries (minifb, pixels)
- Good FFI capabilities for Lean interop
- **Note**: After ADR-002, Rust does ZERO computation — only buffer copy

## Consequences

### Positive
- Maximum mathematical rigor in computation (Lean 4)
- Entire computation stack is proven (including rasterization)
- Rust layer is trivially simple (~100 lines)
- Clear proof boundary: Lean proves, Rust copies

### Negative
- Two languages to maintain (though Rust is minimal)
- FFI boundary adds some complexity
- Smaller talent pool for Lean 4
- Learning curve for dependent types

### Mitigations
- Rust layer is so small it's human-verifiable
- Well-defined byte-buffer interface
- Lean 4 documentation and onboarding materials
- Incremental complexity introduction
