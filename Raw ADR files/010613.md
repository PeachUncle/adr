# ADR-003: Blackboard Pattern in workflows4s

**Status**: Proposed

## Question

What's the workflows4s equivalent of the blackboard pattern?

## Context

Embabel (Tripper's framework) uses a blackboard pattern where:
- Actions read/write domain objects to a shared knowledge repository
- Framework determines execution order based on dependencies
- Type-safe composition ensures correct data flow
- Automatic dependency resolution

We need to understand how workflows4s achieves similar state management and action composition.

## Decision

The **workflows4s State** serves as the blackboard equivalent. workflows4s uses an **event-sourced state model** where:
- **State is the blackboard**: A single, immutable data structure that flows through the workflow
- **Events are write operations**: All state changes happen through events
- **Type parameters enforce dependencies**: Input/output types ensure correct data flow
- **Event sourcing provides persistence**: State can be reconstructed from events

### Comparison: Embabel vs. workflows4s

| Aspect | Embabel (Tripper) | workflows4s |
|--------|-------------------|-------------|
| **Knowledge Repository** | Blackboard with named entries | Single State type |
| **Read Operation** | `read[T](key)` | State as input: `WIO[In, _, _]` |
| **Write Operation** | `write[T](key, value)` | Event + handler: `handleEvent` |
| **Dependency Management** | Explicit `@Reads`, `@Writes` | Type-driven: `WIO[-In, +Err, +Out]` |
| **Execution Order** | Framework analyzes dependencies | Sequential composition via `>>>` |
| **Type Safety** | Compile-time checking | Compile-time via type parameters |
| **Persistence** | Optional | Built-in (event sourcing) |

### workflows4s State Model

The core abstraction:

```scala
// Define your workflow context
object TripperWorkflowCtx extends WorkflowContext {
  // This is the "blackboard" - contains all workflow knowledge
  case class State(
    travelBrief: TravelBrief,
    travelers: Travelers,
    pointsOfInterest: List[PointOfInterest] = List.empty,
    researchedPOIs: List[ResearchedPointOfInterest] = List.empty,
    proposedPlan: Option[ProposedTravelPlan] = None,
    accommodations: List[Stay] = List.empty,
    finalPlan: Option[TravelPlan] = None,
    userConfirmed: Boolean = false
  )
  
  // Events represent state changes (write operations)
  sealed trait Event
  case class POIsFound(pois: List[PointOfInterest]) extends Event
  case class POIsResearched(researched: List[ResearchedPointOfInterest]) extends Event
  case class PlanGenerated(plan: ProposedTravelPlan) extends Event
  case class AccommodationsFound(stays: List[Stay]) extends Event
  case class PlanFinalized(plan: TravelPlan) extends Event
}
```

### Reading from State (Blackboard Read)

Each workflow step declares what state it needs via input type:

```scala
import TripperWorkflowCtx._

// This step "reads" travelBrief and travelers from state
val findPointsOfInterest: WIO[State, Nothing, State] = WIO
  .runIO[State] { state =>
    // Access state fields (implicit read from blackboard)
    val brief: TravelBrief = state.travelBrief
    val travelers: Travelers = state.travelers
    
    // Call LLM to find POIs
    findPOIsWithLLM(brief, travelers).map(pois => POIsFound(pois))
  }
  .handleEvent { (state, event) =>
    // Write to blackboard via state transformation
    state.copy(pointsOfInterest = event.pois)
  }
  .named("Find Points of Interest")
```

### Writing to State (Blackboard Write)

State changes happen through **events** and **event handlers**:

```scala
// Step produces an event (write operation)
val researchPOIs: WIO[State, Nothing, State] = WIO
  .runIO[State] { state =>
    // Read from blackboard
    val pois: List[PointOfInterest] = state.pointsOfInterest
    
    // Parallel research (like Tripper)
    researchPOIsInParallel(pois).map(researched => POIsResearched(researched))
  }
  .handleEvent { (state, event) =>
    // Write to blackboard
    state.copy(researchedPOIs = event.researched)
  }
  .named("Research POIs")
```

### Type-Safe Dependencies

workflows4s enforces dependencies through types:

```scala
// This step REQUIRES researchedPOIs to be populated
// Type system ensures it can only run after researchPOIs
val generatePlan: WIO[State, Nothing, State] = WIO
  .runIO[State] { state =>
    // Compiler ensures these fields exist and have correct types
    require(state.researchedPOIs.nonEmpty, "POIs must be researched first")
    
    generateTravelPlan(
      state.travelBrief,
      state.travelers,
      state.researchedPOIs
    ).map(plan => PlanGenerated(plan))
  }
  .handleEvent { (state, event) =>
    state.copy(proposedPlan = Some(event.plan))
  }
  .named("Generate Travel Plan")
```

### Composing Steps (Execution Order)

Unlike Embabel's automatic ordering, workflows4s uses explicit composition:

```scala
// Explicit sequential composition (replaces Embabel's dependency analysis)
val travelPlanningWorkflow: WIO.Initial = 
  confirmOperation >>>              // Step 1: User confirmation
  findPointsOfInterest >>>          // Step 2: Find POIs (reads travelBrief, travelers)
  researchPOIs >>>                  // Step 3: Research (reads pointsOfInterest)
  generatePlan >>>                  // Step 4: Generate (reads researchedPOIs)
  findAccommodations >>>            // Step 5: Find stays (reads proposedPlan)
  finalizePlan                      // Step 6: Finalize (reads everything)
```

**Benefits**:
- Explicit control flow (no hidden magic)
- Clear execution order
- Type-safe: Won't compile if data dependencies are wrong

### Alternative: Parallel Execution

For independent steps (like Tripper's parallel POI research):

```scala
val researchPOIsParallel: WIO[State, Nothing, State] = WIO
  .forEach { (state: State) => state.pointsOfInterest.toSet }
  .apply { (poi: PointOfInterest) =>
    WIO.runIO[PointOfInterest] { poi =>
      researchSinglePOI(poi).map(research => POIResearched(poi, research))
    }
    .handleEvent { (_, event) => event.research }
    .done
  }
  .buildOutput { (state, results: Map[PointOfInterest, ResearchedPOI]) =>
    state.copy(researchedPOIs = results.values.toList)
  }
  .named("Research All POIs")
```

### Event Sourcing Benefits

Unlike Embabel, workflows4s automatically persists all state changes:

```scala
// All events are persisted
case class POIsFound(pois: List[PointOfInterest]) extends Event

// On recovery, events replay to rebuild state
val recovered = events.foldLeft(initialState) { (state, event) =>
  event match {
    case POIsFound(pois) => state.copy(pointsOfInterest = pois)
    case POIsResearched(researched) => state.copy(researchedPOIs = researched)
    // ... other cases
  }
}
```

**Benefits**:
- Audit trail (every state change recorded)
- Recovery (rebuild state from events)
- Debugging (replay to any point)
- Testing (deterministic replay)

## Consequences

### Positive

1. **Type-safe data flow**: Compiler ensures correct dependencies
2. **Event sourcing**: Built-in persistence and audit trail
3. **Explicit composition**: Clear execution order, no hidden dependencies
4. **Immutability**: State never mutated, always copied
5. **Testability**: Can replay events for testing
6. **Recovery**: Automatic state reconstruction from events
7. **Single state model**: Simpler than multiple blackboard entries

### Negative

1. **Explicit ordering**: Must manually compose steps (vs. automatic in Embabel)
2. **State must be comprehensive**: All data must be in State type
3. **Event boilerplate**: Must define events for all state changes
4. **Large state types**: State can become large with many fields
5. **No automatic dependency resolution**: Manual composition required

### Trade-offs

- **Embabel**: Automatic dependency resolution, implicit execution order
- **workflows4s**: Explicit composition, type-driven dependencies

For llm4s-tripper:
- ✅ Use explicit composition (clearer control flow)
- ✅ Leverage event sourcing (audit trail, recovery)
- ✅ Single State type (simpler than multiple blackboard entries)
- ⚠️ Must carefully design State to include all workflow knowledge

## Implementation Guidelines

### 1. Design Comprehensive State

Include all workflow data:

```scala
case class TravelPlanningState(
  // Input (never changes)
  travelBrief: TravelBrief,
  travelers: Travelers,
  
  // Intermediate results
  pointsOfInterest: List[PointOfInterest] = List.empty,
  researchedPOIs: List[ResearchedPointOfInterest] = List.empty,
  proposedPlan: Option[ProposedTravelPlan] = None,
  accommodations: List[Stay] = List.empty,
  
  // Final output
  finalPlan: Option[TravelPlan] = None,
  
  // Metadata
  userConfirmed: Boolean = false,
  confirmationTimestamp: Option[Long] = None,
  error: Option[String] = None
)
```

### 2. Define Events for State Transitions

One event per state change:

```scala
sealed trait TravelPlanningEvent
case class POIsFound(pois: List[PointOfInterest]) extends TravelPlanningEvent
case class POIsResearched(researched: List[ResearchedPointOfInterest]) extends TravelPlanningEvent
case class PlanGenerated(plan: ProposedTravelPlan) extends TravelPlanningEvent
case class AccommodationsFound(stays: List[Stay]) extends TravelPlanningEvent
case class PlanFinalized(plan: TravelPlan) extends TravelPlanningEvent
case class ErrorOccurred(message: String) extends TravelPlanningEvent
```

### 3. Create Workflow Steps

Each step reads and writes state:

```scala
def createStep(name: String)(
  read: State => A,                          // Read from blackboard
  process: A => IO[Event],                   // Process
  write: (State, Event) => State             // Write to blackboard
): WIO[State, Nothing, State] = WIO
  .runIO[State] { state => process(read(state)) }
  .handleEvent(write)
  .named(name)
```

### 4. Compose Workflow

Explicit composition replaces dependency analysis:

```scala
val workflow: WIO.Initial = 
  step1 >>> step2 >>> step3 >>> step4
  
// Or with branching
val workflowWithBranching = 
  confirmOperation.flatMap { state =>
    if (state.userConfirmed) {
      findPOIs >>> researchPOIs >>> generatePlan
    } else {
      cancelWorkflow
    }
  }
```

### 5. Test Event Replay

Verify deterministic state reconstruction:

```scala
val events = List(
  POIsFound(pois),
  POIsResearched(researched),
  PlanGenerated(plan)
)

val state1 = events.foldLeft(initialState)(applyEvent)
val state2 = events.foldLeft(initialState)(applyEvent)

assert(state1 == state2)  // Must be identical
```

## Pattern Comparison Table

| Pattern | Embabel (Tripper) | workflows4s | llm4s-tripper Choice |
|---------|-------------------|-------------|---------------------|
| **State Container** | Blackboard | State type | ✅ State type |
| **Read Operation** | `@Reads[T]` | Input type | ✅ Input type |
| **Write Operation** | `@Writes[T]` | Event handler | ✅ Event handler |
| **Dependency** | Annotations | Type params | ✅ Type params |
| **Execution Order** | Auto-computed | Manual composition | ✅ Manual (clearer) |
| **Persistence** | Optional | Event sourcing | ✅ Event sourcing |
