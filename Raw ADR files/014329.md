# TASK-015: Frontend ↔ Backend contract map and insertion points
> Source: tasks/tasks.md

## Context
- Parse the frontend codebase to locate components that render chat, news, watchlist, portfolio, and portfolio stats
- Create mapping table: endpoint → component → props expected → state slice
- Define a typed API client (SDK) with base URL from env and shared error shape
- Document the data flow per component and the route_hint mapping from /chat

## Options Considered
- **Option A**: Create separate API clients for each component (Pros: Component isolation; Cons: Code duplication, inconsistent error handling)
- **Option B**: Single typed API client with shared error handling (Pros: Consistent interface, DRY principle; Cons: Larger bundle size)
- **Option C**: Use React Query for API management (Pros: Built-in caching, loading states; Cons: Additional dependency, complexity)

## Decision
- **Chosen approach**: Single typed API client (Option B) with React Query integration
- **Rationale**: Provides consistent interface across all components while leveraging React Query for caching and state management

## Impacts
- **Performance**: Minimal impact - API client is lightweight, React Query provides efficient caching
- **Complexity**: Moderate - Centralized API management reduces component complexity
- **Security/Privacy**: Improved - Consistent error handling and request/response validation
- **Compatibility**: High - Works with existing React/TypeScript setup
- **Risks & Mitigations**: 
  - Risk: API client becomes too large; Mitigation: Modular exports, tree-shaking
  - Risk: Route hint parsing fails; Mitigation: Robust parsing with fallbacks
