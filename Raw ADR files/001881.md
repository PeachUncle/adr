# ADR-0002: Monorepo Structure for Phase II

> **Scope**: Document decision clusters, not individual technology choices. Group related decisions that work together (e.g., "Frontend Stack" not separate ADRs for framework, styling, deployment).

- **Status:** Accepted
- **Date:** 2025-12-12
- **Feature:** 001-task-crud-auth
- **Context:** Phase II introduces a full-stack application with separate frontend (Next.js) and backend (FastAPI) components. We need to decide how to organize the codebase: single monorepo with both components, or separate repositories. This decision affects developer workflow, versioning, deployment, CI/CD pipelines, and long-term maintainability.

## Decision

**Monorepo structure** with `frontend/` and `backend/` directories in a single repository.

**Directory Structure:**
```
Full-Stack-Web-Application/
├── frontend/                 # Next.js 16+ App Router
│   ├── app/                  # App Router pages
│   ├── components/           # UI components
│   ├── lib/                  # API client, utilities
│   ├── package.json
│   ├── tsconfig.json
│   ├── Dockerfile.dev
│   └── CLAUDE.md             # Frontend-specific agent instructions
├── backend/                  # FastAPI
│   ├── src/
│   │   ├── models/           # SQLModel
│   │   ├── schemas/          # Pydantic
│   │   ├── routers/          # API endpoints
│   │   └── middleware/       # JWT auth
│   ├── tests/
│   ├── alembic/              # Database migrations
│   ├── pyproject.toml
│   ├── Dockerfile.dev
│   └── CLAUDE.md             # Backend-specific agent instructions
├── specs/                    # Feature specifications (shared)
├── history/                  # ADRs and PHRs (shared)
├── .specify/                 # SpecKit Plus (shared)
├── docker-compose.yml        # Orchestration
├── .gitignore
├── CLAUDE.md                 # Root agent instructions
└── README.md
```

**Key Principles:**
- **Workspace Isolation:** Frontend and backend have separate dependency management (package.json vs pyproject.toml)
- **Shared Documentation:** Specifications, ADRs, PHRs, and constitution live at repository root
- **Workspace-Specific Instructions:** Each workspace has its own CLAUDE.md for agent context
- **Single Version Control:** One Git repository, one version history
- **Independent Deployment:** Frontend and backend can be deployed separately despite sharing repository

## Consequences

### Positive

- **Atomic Changes Across Stack:** Frontend and backend changes in same feature can be committed together (single PR, single review)
- **Simplified Dependency Management:** Shared tooling (Docker Compose, linting configs) defined once at root
- **Single Source of Truth:** Specifications, API contracts, and ADRs accessible to both frontend and backend developers
- **Easier Refactoring:** Renaming API endpoints requires coordinated changes visible in single PR diff
- **Shared CI/CD Pipeline:** One GitHub Actions workflow can build, test, and deploy both components
- **Better Developer Onboarding:** Single `git clone`, single repository to understand
- **Consistent Versioning:** Frontend and backend versions stay in sync (e.g., v1.2.0 includes both)
- **Reduced Context Switching:** Developers work in one repository, not switching between multiple repos

### Negative

- **Larger Repository Size:** Single repo grows larger over time (though Phase II scope is bounded)
- **Coupling Risk:** Teams might become less disciplined about API contracts if both sides in same repo
- **Build Complexity:** CI/CD must determine which workspace changed to optimize builds
- **Access Control Limitations:** Cannot grant frontend-only or backend-only repository access (though workspaces have separate CLAUDE.md files)
- **Merge Conflicts:** Higher chance of conflicts if multiple developers work on frontend and backend simultaneously
- **Deployment Coupling:** Temptation to deploy both together even when only one changed (mitigated by separate Docker containers)

## Alternatives Considered

**Alternative A: Separate Repositories (frontend-repo, backend-repo)**
- Separate Git repositories for frontend and backend
- Why rejected:
  - API contract changes require coordinated PRs across two repos (complex workflow)
  - Specifications and ADRs duplicated or split between repos
  - Version drift: frontend v1.2.0 might work with backend v1.1.5 or v1.3.0 (unclear compatibility)
  - Developers must clone two repos, maintain two sets of credentials
- Tradeoffs: Better access control and independent scaling, but worse developer experience and coordination overhead

**Alternative B: Micro-Frontends with Separate Repos**
- Separate repositories for each micro-frontend module + backend
- Why rejected:
  - Over-engineering for Phase II scope (single SPA sufficient)
  - Adds complexity: module federation, cross-app routing, shared state management
  - Increases deployment complexity
- Tradeoffs: Better for large teams with independent feature ownership, but unnecessary for current scope

**Alternative C: Monorepo with Workspaces (npm/yarn workspaces, Python multi-package)**
- Single repo with package manager workspaces for shared libraries
- Why rejected:
  - Frontend (npm) and backend (UV/Python) have incompatible workspace tools
  - Adds complexity without clear benefit for Phase II
  - Shared libraries not needed (API contracts are the interface)
- Tradeoffs: Useful for shared component libraries, but adds tooling complexity

**Why Monorepo Wins:**
- **Atomic changes:** API contract updates visible in single PR
- **Single source of truth:** Specifications accessible to all developers
- **Simpler workflow:** One clone, one branch, one PR review
- **Phase II scope:** Current scale doesn't require separate repos
- **Spec-Driven Development:** Monorepo aligns with SDD workflow (specs before implementation, contracts as interface)
