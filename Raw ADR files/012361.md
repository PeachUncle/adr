# ADR 0001 — CLI & TUI share a single Core in one repo (spec‑first)

- **Status:** Accepted  
- **Date:** 2025-10-10  
- **Owner:** next-ai-presets maintainers  
- **Decision type:** Architecture

## Context

We’re building **next-ai-presets**: AI-applied, capability-driven presets that safely **swap Next-Forge defaults** (DB/ORM, Auth, Payments, Docs, Storage/Uploads, Flags, Analytics, Security, Collaboration). We also plan to:

- Offer both a **CLI** (non-interactive) and a **TUI** (interactive) UX.
- Keep a **spec-first** approach (recipes + schemas) so AIs/humans can apply changes deterministically.
- Support **monthly prebuilt template branches** (e.g., `template-2025-10-01`) that users can scaffold from.
- Leave a path to a future **SaaS registry** without locking the OSS repo.

We need an approach that avoids duplicated logic between CLI and TUI, protects the spec repo from being overwritten during generation, and scales to more templates/providers later.

## Decision

1. **Monorepo with a shared Core**
   - Create `@next-ai-presets/core` containing **all business logic**:
     - Schema validation (JSON Schema + Zod), spec/recipe loading, planning, idempotent execution (ops/codemods), and an **event stream** for rendering diffs/progress.
   - Keep template knowledge in a **template adapter** (first: `adapter-next-forge`) that maps repo shape and file paths.
   - Store machine-readable **specs/recipes** and **schemas** in the repo; the core reads them at runtime.

2. **CLI and TUI are thin runners**
   - `@next-ai-presets/cli` (Commander) and `@next-ai-presets/tui` (Ink) call the same `planAndApply()` API from Core and **render** its event stream.  
   - No business logic is implemented in the UI layers.

3. **Spec-first contract**
   - Recipes are defined in a **DSL** (YAML/JSON) under `specs/templates/<template>/<version>/recipes/...` and validated by a `recipe-dsl.schema.json`.
   - Config is validated by `preset-config.schema.json` (JSON Schema) and `presetConfig.zod.ts` (Zod) with conditional rules (e.g., Supabase sub-capabilities only valid when `db="supabase"`).

4. **Safe generation outputs**
   - Generation **never writes** to repo root. The CLI/TUI require `--cwd <target>` or use a clean OUT directory (e.g., `.artifacts/templates/<stamp>`).  
   - Scheduled builds publish an **orphan branch** (e.g., `template-YYYY-MM-DD`) whose root is the generated template.

5. **Monthly templates & conformance**
   - A GitHub Action runs monthly: init latest Next-Forge → apply chosen presets → build → push **orphan branch** `template-<date>` → tag.  
   - Conformance CI validates that specs remain compatible with the latest Next-Forge (dry-run + build/tests + optional Playwright/axe smoke).

6. **SaaS-ready, opt-in**
   - A `packages/cloud` client (optional) can fetch a registry/auth in future; injected into Core via options. No cloud calls unless flags are provided.

## Rationale

- **Single source of truth:** All planning/execution lives in Core, so CLI/TUI/agents/SaaS reuse the same engine.
- **Spec-first & future-proof:** Recipes + schemas are reviewable and versioned; new adapters (e.g., CRA/Astro/SvelteKit) can reuse presets.
- **Safety & trust:** OUT dir rule + orphan branches prevent root clobbering; idempotent ops and diffs build confidence.
- **DX:** Users choose non-interactive CLI or TUI without changing behavior; both stream the same progress/diff events.
- **SaaS path without lock-in:** Cloud features are additive and optional.

## Options considered

1. **Spec-only repo + separate runner repo**  
   - **Pros:** very clean separation.  
   - **Cons:** splits discoverability and increases coordination.  
   - **Reason rejected:** We want one repo that “just works” while still being spec-first.

2. **Single CLI only (no TUI)**  
   - **Pros:** simpler.  
   - **Cons:** worse onboarding; interactive selection is valuable for discovery.  
   - **Reason rejected:** We can add TUI cheaply if Core owns logic.

3. **Bake logic directly in CLI/TUI**  
   - **Pros:** quickest initial POC.  
   - **Cons:** duplication, hard to test, brittle.  
   - **Reason rejected:** We expect many providers/adapters; centralizing logic scales better.

## Consequences

- **Positive**
  - Minimal duplication; any new capability/provider benefits all UIs.
  - Easy to add more renderers (Desktop, VS Code extension) by consuming Core.
  - Safer automation via idempotent recipes and OUT/branch guardrails.
- **Negative / Costs**
  - Monorepo & workspace management overhead.
  - Need to maintain adapter mappings as Next-Forge evolves.
  - Building and testing the ops engine and codemods requires discipline.

## Implementation sketch

**Repo layout**
```
schemas/
  preset-config.schema.json
  recipe-dsl.schema.json

specs/
  index.json
  templates/
    next-forge/
      vX.Y/
        capabilities.json
        recipes/...

packages/
  core/                    # parser, planner, ops engine, zod/json-schema, event bus
  adapter-next-forge/      # path maps, detection
  cli/                     # commander wrapper (bin: next-ai-presets)
  tui/                     # ink wrapper (bin: next-ai-presets-tui)
  cloud/                   # (optional) registry/auth client
codemods/                  # AST transforms referenced by recipes
```

**Core API (excerpt)**
```ts
type ApplyOptions = {
  cwd: string; template: string; specPathOrUrl: string;
  config: unknown; dryRun?: boolean; onEvent?: (e: CoreEvent) => void;
};
type CoreEvent =
  | { type: "info"; msg: string }
  | { type: "step"; id: string; title: string }
  | { type: "diff"; file: string; patch: string };

async function planAndApply(opts: ApplyOptions): Promise<void>;
```

**Monthly template workflow (high-level)**
1) Compute `STAMP = YYYY-MM-DD`  
2) Generate into `.artifacts/templates/$STAMP`  
3) Apply presets (no root writes)  
4) Build & test  
5) Push **orphan branch** `template-$STAMP` and tag `template-$STAMP`

## Security & safety notes

- **Secrets:** Never write service-role keys to client env; server-only access.  
- **Idempotence:** Re-applying same preset choices results in no changes.  
- **Branding:** Use vendor names descriptively; no endorsement implied.  
- **Repo safety:** CI and local scripts refuse when working tree is dirty (or auto-stash with notice).

## Test strategy

- **Schema lint:** Validate all `preset.config.json` and recipe files in CI.  
- **Conformance:** Run “init latest Next-Forge → apply → build/test” on PRs touching specs/recipes.  
- **A11y smoke (optional):** Playwright + axe for main flows when corresponding features are enabled.  
- **Golden tests for codemods:** Input/expected pairs per transform.

## Rollback plan

If this approach proves too heavy, we can:
- Keep **specs/schemas** as the stable core,
- Strip down CLI/TUI to a single runner,
- Or pivot to a spec-only repo plus an external runner (without breaking spec consumers).
