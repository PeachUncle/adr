# ADR-011: Dual-Context Transaction Routing Pattern

## Status

Accepted

## Date

2025-09-20

## Context

SharedLedger allows users to view and manage transactions in two contexts:

1. **Global context**: All transactions across all accounts
2. **Account context**: Transactions for a specific account

This raised questions about URL structure and routing patterns. Should transactions only be accessible under accounts? Should we duplicate the logic? How do we handle navigation between contexts?

## Decision

We implemented a dual-context routing pattern where transactions are accessible via two distinct URL patterns:

1. **Root-level routes** (`/transactions`):
   - Shows all transactions across all accounts
   - Used for global financial overview
   - Quick access from main navigation

2. **Nested routes** (`/accounts/:account_id/transactions`):
   - Shows transactions filtered to specific account
   - Maintains account context for navigation
   - Natural hierarchy for account-specific operations

Both routes use the same LiveView component (`TransactionLive.Index`) with context detection based on route parameters.

## Consequences

### Positive

- **User Flexibility**: Users can choose their preferred navigation pattern
- **Context Preservation**: Account context maintained when drilling down
- **Global Overview**: Easy access to all transactions without account selection
- **Code Reuse**: Single LiveView handles both contexts
- **Natural Navigation**: Follows RESTful patterns users expect

### Negative

- **URL Duplication**: Same resource accessible via multiple URLs
- **Potential Confusion**: Developers might wonder why there are two routes
- **SEO Considerations**: Multiple URLs for similar content
- **Testing Overhead**: Need to test both routing patterns

### Neutral

- **Breadcrumb Complexity**: Different breadcrumb trails for each context
- **State Management**: Must handle both with/without account_id

## Implementation

### Router Configuration

```elixir
# Global context
live "/transactions", TransactionLive.Index, :index

# Account context
live "/accounts/:account_id/transactions", TransactionLive.Index, :account_transactions
```

### Context Detection in LiveView

```elixir
def mount(params, _session, socket) do
  socket =
    case params do
      %{"account_id" => account_id} ->
        # Account context - filter by account
        socket
        |> assign(:account_id, account_id)
        |> assign(:context, :account)
        |> load_account_transactions(account_id)

      _ ->
        # Global context - show all
        socket
        |> assign(:account_id, nil)
        |> assign(:context, :global)
        |> load_all_transactions()
    end

  {:ok, socket}
end
```

### Navigation Patterns

```elixir
# From dashboard
<.link navigate="/transactions">View All Transactions</.link>

# From account page
<.link navigate={~p"/accounts/#{@account.id}/transactions"}>
  View Account Transactions
</.link>

# Add transaction with context
<%= if @account_id do %>
  <.link navigate={~p"/accounts/#{@account_id}/transactions/new"}>
    Add Transaction
  </.link>
<% else %>
  <.link navigate="/transactions/new">Add Transaction</.link>
<% end %>
```

## Use Cases

### Global Context Use Cases

- Financial overview across all accounts
- Monthly spending analysis
- Tax preparation
- Quick transaction entry without account selection

### Account Context Use Cases

- Account reconciliation
- Account-specific reporting
- Reviewing shared account activity
- Account member transaction review

## Alternatives Considered

1. **Single Route Only (`/transactions`)**
   - Pros: Simpler, no duplication
   - Cons: Always requires filter selection, poor UX

2. **Nested Only (`/accounts/:id/transactions`)**
   - Pros: Clear hierarchy
   - Cons: No global view, requires account selection first

3. **Query Parameters (`/transactions?account_id=123`)**
   - Pros: Single route, filterable
   - Cons: Less RESTful, poor URLs for sharing

4. **Separate LiveViews**
   - Pros: Clear separation of concerns
   - Cons: Code duplication, maintenance burden

## Related Patterns

This pattern is commonly seen in:

- **GitHub**: `/issues` (all) vs `/owner/repo/issues` (scoped)
- **Jira**: `/issues` (all) vs `/projects/KEY/issues` (project)
- **Banking Apps**: All transactions vs account transactions
