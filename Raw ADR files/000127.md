# ADR-0006: Makefile Simulator Auto-Detection

**Date**: 2024-10-12
**Status**: Accepted

## Context

The iOS development workflow requires building and testing the app against specific iOS simulators. Each developer machine may have different iPhone simulators installed, and manually configuring simulator selection across different development environments creates friction and maintenance overhead.

The project needs a consistent way to:

- Build and test on any developer machine without manual configuration
- Work out-of-the-box for 90% of developers
- Allow easy override when specific simulators are needed
- Follow iOS development best practices (not C/C++ conventions like autoconf)
- Support CI/CD environments with different available simulators

iOS development differs from traditional C/C++ projects where autoconf is common. The iOS community has different conventions that should be respected.

## Decision

**We will implement automatic simulator detection in the Makefile that automatically selects the first available iPhone simulator, with easy override capabilities.**

The implementation uses:

```bash
DETECTED_SIM := $(shell xcrun simctl list devices available iPhone 2>/dev/null | \
    grep -m 1 "iPhone" | \
    awk -F'[()]' '{print $1}' | \
    xargs)
SIMULATOR ?= platform=iOS Simulator,name=$(or $(DETECTED_SIM),iPhone 16)
```

This provides:

1. **Auto-detection**: Finds first available iPhone simulator at Makefile parse time
2. **Fallback**: Uses "iPhone 16" if no simulators detected
3. **Override support**: Via command line args, environment variables, or inline variables
4. **Zero configuration**: Works immediately on developer machines with Xcode installed

## Alternatives Considered

### 1. Autoconf Configuration System

Using traditional autoconf with `./configure && make` pattern.

**Why not chosen**:

- Not standard for iOS/Xcode projects
- Overkill for simple simulator selection
- Not idiomatic for iOS development community
- Adds unnecessary complexity with M4 macros and templates

### 2. Manual Configuration Files

Requiring developers to create local configuration files with simulator preferences.

**Why not chosen**:

- Creates setup friction for new developers
- Configuration files need to be gitignored
- Easy to forget or misconfigure
- Doesn't solve CI/CD environment differences

### 3. Fixed Simulator Name

Hardcoding a specific simulator name in the Makefile.

**Why not chosen**:

- Breaks when simulator not available on developer machine
- Different iOS versions have different simulator names
- No flexibility for testing across simulator versions
- Fails in CI environments with different simulators

### 4. No Makefile (Xcode Only)

Relying entirely on Xcode GUI for building and testing.

**Why not chosen**:

- Prevents command-line CI/CD workflows
- No scriptable build process
- Harder to integrate with automated workflows
- Reduces development velocity for command-line users

## Consequences

### Positive

1. **Zero Configuration**: 90% of developers can run `make test` immediately after clone
2. **Flexible Override**: Easy customization when specific simulators needed
3. **CI/CD Compatible**: Works in automated environments with explicit simulator specification
4. **iOS Idiomatic**: Follows iOS community conventions, not C/C++ patterns
5. **Troubleshooting Support**: `make list-simulators` and `make show-config` help debugging
6. **Consistent**: Works across macOS versions and Xcode installations

### Negative

1. **iOS-Specific**: Solution only works for iOS development (acceptable trade-off)
2. **Xcode Dependency**: Requires xcrun/simctl tools (already required for iOS dev)
3. **Parse-Time Detection**: Simulator detection happens at Makefile parse, not runtime
4. **Shell Command Overhead**: Small performance cost for detection command

### Mitigation Strategies

- Provide clear error messages when no simulators detected
- Document override methods for specific use cases
- Include troubleshooting guide for common issues
- Regular testing on different macOS/Xcode versions

## Rationale

The decision prioritizes **developer experience and iOS community alignment** over cross-platform consistency.

Key factors:

1. **Community Standards**: iOS developers expect environment variables with smart defaults, not autoconf
2. **Friction Reduction**: New team members can build immediately without setup steps
3. **Operational Simplicity**: CI/CD can specify exact simulators while development "just works"
4. **Maintainability**: Simple shell detection is easier to understand and debug than autoconf

The approach aligns with how other iOS development tools handle configuration: smart defaults with easy overrides.

## Implementation Notes

### Override Methods

```bash
# Method 1: Command-line argument
make test SIMULATOR="platform=iOS Simulator,name=iPhone 15"

# Method 2: Environment variable
export SIMULATOR="platform=iOS Simulator,name=iPhone 17"
make test

# Method 3: Inline environment variable
SIMULATOR="platform=iOS Simulator,name=iPhone Air" make test
```

### Troubleshooting Commands

```bash
make show-config      # Display current configuration
make list-simulators  # Show all available simulators
```

### CI/CD Usage

Always specify explicit simulators in CI environments:

```yaml
- name: Run Tests
  run: make test SIMULATOR="platform=iOS Simulator,name=iPhone 15"
```
