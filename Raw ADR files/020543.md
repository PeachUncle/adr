# Workflow for version controlled diagrams

**Related Ticket:** 102  
**Date:** 2025-07-21  
**Status:** Proposed

![A diagram showing the proposed docs-as-code workflow for diagrams.](../assets/diagrams/adr-SCRUM-102-diagram-workflow.excalidraw.svg)

## Context

Our project requires architectural and workflow diagrams to be included in our in-repository documentation. We need a method to manage these diagrams that is scalable, maintainable, and aligned with our "Docs as Code" philosophy. Storing traditional binary image files (like PNGs) in Git is problematic as it leads to repository bloat and lacks meaningful version history. Furthermore, a lack of a standardized process can lead to inconsistent diagrams created with different tools, making maintenance difficult and diffs meaningless.

## Decision

We will adopt a standardized workflow for creating, storing, and reviewing diagrams within our Git repository.

1.  **File Format:** **SVG** will be our official format for all diagrams. As a text-based format, it can be efficiently stored and versioned by Git, preventing repository bloat.

2.  **Creation Tool:** **Excalidraw** will be our official diagramming tool. **This tool is free, open-source, and permanent.** This means we can use it forever without cost and are not locked into a proprietary company's ecosystem.
    * *Note: This decision pertains to the core Excalidraw tool, not the separate, paid Excalidraw+ cloud service.*

3.  **Storage Workflow & Naming Convention:** To ensure diagrams are organized, discoverable, and reusable, we will follow a specific folder structure and naming convention.
    * **Folder Structure:** All diagram files will be stored in a central `docs/assets/diagrams/` folder. This provides a single, predictable location for all visual assets.
    * **File Storage:** For each diagram, we will commit a **single `.excalidraw.svg` file**. This special file is both a viewable SVG image and contains the embedded, editable Excalidraw scene data.
        * This single file serves as **both** the editable source of truth and the viewable artifact, preventing any sync issues.
    * **Naming Convention:** To keep the `diagrams/` folder organized and link diagrams to their documents, filenames will be prefixed with the context and unique identifier of the document they primarily support.
        * **Example:** For an ADR named `2025-07-21-SCRUM-95-adopt-workflow.md`, a related diagram would be named `adr-2025-07-21-SCRUM-95-<shortDescriptor>.svg`. This makes assets easy to find and their context immediately clear.

4.  **Review Process:** The primary method for reviewing diagram changes in a pull request will be the **visual diff**. Reviewers will use the rendering capabilities of GitHub or VS Code extensions (like GitLens) to compare the "before" and "after" images, rather than scrutinizing the potentially noisy XML code diff of the SVG file.

## Consequences

* **Positive:**
    * We will have a single source of truth for all diagrams, versioned alongside the code they describe.
    * The workflow is clear, consistent, and easy for all team members to follow.
    * The use of SVG avoids repository bloat associated with binary image files.
    * Diagrams will be easily accessible to all stakeholders directly within the GitHub UI.

* **Negative:**
    * **It's immediately obvious that an `.excalidraw.svg` file is editable, but that assumes the dev read the guides as they should** This requires team discipline and awareness to avoid corrupting the file with a non-Excalidraw editor or an erroneous manual export.
    * The workflow requires team awareness to not corrupt the editable SVG files even with Excalidraw editor. The script and workflow guide makes this braindead easy to avoid, but ultimately, the onus is on the developer to put effort on that.

* **Follow-ups:**
    * Create tickets to migrate any high-value, existing diagrams to the new Excalidraw standard.
