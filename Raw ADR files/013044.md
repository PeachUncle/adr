# ADR-003: PostgreSQL as Primary Database

**Status**: Accepted

**Date**: 2024-11-15

**Decision Makers**: Architecture Team, Data Team

---

## Context

OpenAuction IQ requires a robust database system to store:

1. **Auction Data**: Billions of auction records with complex relationships
   - Bid requests, responses, wins/losses
   - Advertiser metadata, publisher metadata
   - Contextual features (device, geo, time, etc.)
   - High write throughput (millions of auctions/day)

2. **Model Metadata**: ML model lifecycle management
   - Model versions, hyperparameters, training configs
   - Model performance metrics over time
   - Model registry (dev/staging/production promotion)
   - A/B test configurations and results

3. **Time-Series Metrics**: Training and inference metrics
   - Real-time model performance (reward, accuracy, latency)
   - Training progress (loss curves, gradient norms)
   - System metrics (CPU, memory, GPU utilization)
   - Prometheus integration for monitoring

4. **Multi-Tenancy** (CloudX mode): Tenant isolation and management
   - Tenant metadata (quotas, access control)
   - Row-level security for tenant data isolation
   - Tenant-specific model configurations

5. **Relational Integrity**: Complex data relationships
   - Auctions → Bid Requests → Advertisers → Campaigns
   - Models → Training Runs → Checkpoints → Evaluations
   - Users → Tenants → Organizations
   - Foreign key constraints and transactions

**Key Requirements**:
- ✅ **ACID transactions** (auction data must be consistent)
- ✅ **Complex queries** (JOIN-heavy analytics queries)
- ✅ **Time-series support** (efficient timestamp-based queries)
- ✅ **JSON support** (store flexible auction metadata)
- ✅ **High write throughput** (millions of inserts/day)
- ✅ **Read scalability** (analytics queries on billions of rows)
- ✅ **Multi-tenancy** (row-level security for CloudX mode)
- ✅ **Strong ecosystem** (ORMs, migration tools, monitoring)

---

## Decision

We have chosen **PostgreSQL 16+** as the primary database for OpenAuction IQ.

**Specific Configuration**:
- **Version**: PostgreSQL 16+ (for parallel query improvements)
- **Extensions**:
  - `pg_stat_statements` - Query performance monitoring
  - `pgvector` - Vector similarity search for embeddings (future)
  - `timescaledb` - Time-series optimization (optional extension)
- **Connection Pooling**: PgBouncer for connection management
- **Replication**: Streaming replication for high availability
- **Backup**: pg_basebackup + WAL archiving (point-in-time recovery)

**Deployment**:
- CloudX Central: Managed PostgreSQL (AWS RDS / GCP Cloud SQL)
- Single-User: Docker PostgreSQL container
- Federated: Local PostgreSQL per client + central metadata DB

---

## Consequences

### Positive

1. **ACID Guarantees**:
   - Strong consistency for auction data
   - Transactions prevent data corruption
   - Foreign key constraints ensure referential integrity
   - No eventual consistency issues (vs. NoSQL)

2. **Rich Query Capabilities**:
   - Complex JOINs for analytics (e.g., "auction win rate by advertiser")
   - Window functions for time-series analysis
   - CTEs (Common Table Expressions) for readable complex queries
   - Full-text search for log analysis

3. **JSON Support**:
   - Native JSONB type for flexible auction metadata
   - Indexable JSON fields (GIN indexes)
   - Mix structured and unstructured data in same table
   - No need for separate document store

4. **Time-Series Optimization**:
   - Efficient timestamp indexing (BRIN indexes)
   - Partitioning by time ranges (monthly/weekly partitions)
   - TimescaleDB extension for even better time-series performance
   - Automatic partition management

5. **Multi-Tenancy Support**:
   - Row-Level Security (RLS) for tenant isolation
   - Schema-based multi-tenancy (one schema per tenant)
   - Declarative security policies
   - No application-level filtering needed

6. **Strong Ecosystem**:
   - Excellent ORM support (SQLAlchemy, Django ORM)
   - Robust migration tools (Alembic, Flyway)
   - Mature monitoring tools (pg_stat_monitor, pgAdmin)
   - Large community and documentation

7. **Performance**:
   - Parallel query execution (PostgreSQL 16+)
   - Advanced indexing (B-tree, GIN, GiST, BRIN, Bloom)
   - Query planner optimizations
   - Materialized views for pre-computed aggregations

8. **Operational Maturity**:
   - 30+ years of production use
   - Well-understood failure modes
   - Clear upgrade paths (pg_upgrade)
   - Managed offerings from all major clouds

### Negative

1. **Write Scalability Limits**:
   - Single-master architecture (writes don't horizontally scale)
   - Vertical scaling required for high write throughput
   - Need sharding for >1M writes/sec (complex to implement)
   - Not as write-scalable as Cassandra or MongoDB

2. **Operational Complexity** (Self-Hosted):
   - Requires PostgreSQL expertise for tuning
   - Manual replication setup for HA
   - Vacuum and autovacuum tuning needed
   - Connection pooling (PgBouncer) adds another component

3. **Not Optimized for Analytics** (Compared to Columnar DBs):
   - Row-oriented storage inefficient for wide table scans
   - Slower than ClickHouse/Redshift for OLAP queries
   - Need separate analytics DB for complex reporting
   - Materialized views are static (not real-time)

4. **Time-Series Limitations** (Without TimescaleDB):
   - Manual partition management can be complex
   - Retention policies require custom scripts
   - Not as efficient as purpose-built time-series DBs (InfluxDB, Prometheus)
   - Query performance degrades with billions of time-series points

5. **JSON Performance**:
   - JSONB queries slower than native columns
   - GIN indexes can be large (storage overhead)
   - No schema enforcement for JSON fields
   - Harder to optimize JSON queries vs. structured columns

6. **Licensing**:
   - PostgreSQL (open-source, permissive license) ✅
   - TimescaleDB (Apache 2.0 for community edition, commercial for enterprise features) 🟡
   - Managed PostgreSQL services have vendor lock-in risk

## Alternatives Considered

### 1. MySQL / MariaDB

**Pros**:
- ✅ Similar feature set to PostgreSQL
- ✅ Slightly better write performance (in some benchmarks)
- ✅ Mature ecosystem
- ✅ InnoDB storage engine with ACID support

**Cons**:
- ❌ **Weaker JSON support**: JSON type less mature than JSONB
- ❌ **Limited window functions**: Not as full-featured as PostgreSQL
- ❌ **Row-Level Security**: Not native (need triggers or application logic)
- ❌ **Replication complexity**: More complex than PostgreSQL streaming replication
- ❌ **Query optimizer**: Generally weaker than PostgreSQL

**Why Rejected**: PostgreSQL's superior JSON support, window functions, and row-level security are critical for our multi-tenant architecture. MySQL's advantages (write performance) don't outweigh these disadvantages.

---

### 2. MongoDB (Document Store)

**Pros**:
- ✅ Flexible schema (JSON-native)
- ✅ Horizontal write scalability (sharding)
- ✅ Good for unstructured auction metadata
- ✅ Built-in replication and sharding

**Cons**:
- ❌ **No ACID transactions** (until v4.0, and still limited)
- ❌ **Weak relational support**: JOIN-like operations ($lookup) are slow
- ❌ **No foreign key constraints**: Application must enforce integrity
- ❌ **Query complexity**: Aggregation pipeline harder than SQL
- ❌ **Storage overhead**: BSON encoding less efficient than PostgreSQL JSONB

**Why Rejected**: Our data is highly relational (auctions → advertisers → campaigns). MongoDB's lack of foreign keys and weak JOIN support make it a poor fit. We'd need to duplicate data or make multiple queries for basic operations.

---

### 3. Apache Cassandra (Wide-Column Store)

**Pros**:
- ✅ Massive write scalability (linear scaling)
- ✅ Tunable consistency (eventual → strong)
- ✅ Multi-datacenter replication
- ✅ High availability (no single point of failure)

**Cons**:
- ❌ **No JOINs**: Must denormalize data extensively
- ❌ **No foreign keys**: No referential integrity
- ❌ **No transactions**: Eventually consistent by default
- ❌ **Complex data modeling**: Need deep Cassandra expertise
- ❌ **Query limitations**: Must query by partition key (inflexible)

**Why Rejected**: Cassandra is optimized for write-heavy, eventually-consistent workloads with simple query patterns. Our use case requires complex JOINs, ACID transactions, and ad-hoc analytics queries. Cassandra would force us to denormalize heavily and give up consistency guarantees we need.

---

### 4. ClickHouse (Columnar OLAP Database)

**Pros**:
- ✅ Extremely fast analytics queries (100× faster than PostgreSQL)
- ✅ Excellent compression (10:1 typical)
- ✅ Built-in time-series support
- ✅ Horizontal scalability
- ✅ SQL interface

**Cons**:
- ❌ **Not OLTP-friendly**: Poor random write performance
- ❌ **No UPDATE/DELETE**: Immutable data model (updates via INSERT + merge)
- ❌ **No transactions**: No ACID guarantees
- ❌ **Weaker ecosystem**: Fewer ORMs and tools vs. PostgreSQL
- ❌ **Operational complexity**: Requires ClickHouse expertise

**Why Rejected**: ClickHouse excels at analytics but is poor at OLTP (transactional writes). We need both transactional auction recording AND analytics queries. Solution: Use PostgreSQL for OLTP, replicate to ClickHouse for analytics (future consideration).

---

### 5. TimescaleDB (PostgreSQL Extension)

**Pros**:
- ✅ Built on PostgreSQL (inherits all PostgreSQL features)
- ✅ Automatic time-based partitioning
- ✅ Optimized time-series queries (10-100× faster)
- ✅ Continuous aggregations (materialized views with auto-refresh)
- ✅ SQL interface (compatible with PostgreSQL tools)

**Cons**:
- ❌ **Not a separate choice**: TimescaleDB is a PostgreSQL extension
- ❌ **Enterprise features**: Some features require commercial license
- ❌ **Learning curve**: Need to learn TimescaleDB-specific concepts (hypertables, chunks)
- ❌ **Operational overhead**: Another extension to manage

**Why Not Rejected**: TimescaleDB is an **extension to PostgreSQL**, not an alternative. We can optionally enable it for time-series tables. Decision: **Use TimescaleDB for time-series tables** (metrics, training logs) but not required for core functionality.

---

### 6. Amazon DynamoDB (NoSQL Key-Value Store)

**Pros**:
- ✅ Fully managed (zero operational overhead)
- ✅ Massive scalability (auto-scaling)
- ✅ Single-digit millisecond latency
- ✅ Global replication (multi-region)

**Cons**:
- ❌ **Vendor lock-in**: AWS-only
- ❌ **No SQL**: Custom query language (PartiQL)
- ❌ **No JOINs**: Must denormalize or make multiple queries
- ❌ **Query limitations**: Must query by partition key
- ❌ **Cost**: Expensive at scale (per-request pricing)

**Why Rejected**: DynamoDB's vendor lock-in and query limitations make it unsuitable for our multi-cloud, analytics-heavy use case. We need SQL, JOINs, and ad-hoc queries that DynamoDB can't support.

## Implementation Details

### Schema Design Principles

1. **Normalized Relations**: Auction data is normalized (auctions, advertisers, publishers in separate tables with foreign keys)
2. **Partitioning**: Time-series tables partitioned by month (auctions_2024_01, auctions_2024_02, etc.)
3. **Indexes**: B-tree for foreign keys, GIN for JSONB, BRIN for timestamps
4. **Multi-Tenancy**: Row-Level Security policies for CloudX mode

### Example Schema (Simplified)

```sql
-- Auctions table (partitioned by month)
CREATE TABLE auctions (
    id BIGSERIAL PRIMARY KEY,
    tenant_id UUID NOT NULL,  -- Multi-tenancy
    timestamp TIMESTAMPTZ NOT NULL,
    advertiser_id BIGINT REFERENCES advertisers(id),
    publisher_id BIGINT REFERENCES publishers(id),
    bid_price DECIMAL(10, 4),
    floor_price DECIMAL(10, 4),
    win BOOLEAN,
    metadata JSONB,  -- Flexible auction metadata
    created_at TIMESTAMPTZ DEFAULT NOW()
) PARTITION BY RANGE (timestamp);

-- Row-Level Security for multi-tenancy
ALTER TABLE auctions ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON auctions
    FOR ALL
    USING (tenant_id = current_setting('app.current_tenant')::UUID);

-- Time-series partition (monthly)
CREATE TABLE auctions_2024_12 PARTITION OF auctions
    FOR VALUES FROM ('2024-12-01') TO ('2025-01-01');

-- Indexes
CREATE INDEX idx_auctions_timestamp ON auctions_2024_12 USING BRIN (timestamp);
CREATE INDEX idx_auctions_tenant ON auctions_2024_12 (tenant_id);
CREATE INDEX idx_auctions_metadata ON auctions_2024_12 USING GIN (metadata);
```

### Connection Pooling (PgBouncer)

```ini
# pgbouncer.ini
[databases]
openauction_iq = host=postgres port=5432 dbname=openauction_iq

[pgbouncer]
pool_mode = transaction  # Transaction-level pooling
max_client_conn = 1000   # Max client connections
default_pool_size = 25   # Connections per user/database
```

### Backup Strategy

1. **Continuous Archiving**: WAL (Write-Ahead Log) archiving to S3/GCS
2. **Base Backups**: Daily pg_basebackup snapshots
3. **Point-in-Time Recovery (PITR)**: Restore to any point in time (within WAL retention)
4. **Retention**: 30 days for WAL, 90 days for base backups

## Performance Considerations

### Write Throughput

**Estimated Load**:
- 1M auctions/day = ~12 inserts/sec (light load)
- 100M auctions/day = ~1,200 inserts/sec (medium load)
- 1B auctions/day = ~12,000 inserts/sec (heavy load)

**PostgreSQL Capacity**:
- Single instance: 10,000-50,000 inserts/sec (depending on hardware)
- With batching: 100,000+ inserts/sec
- **Conclusion**: PostgreSQL can handle expected load with proper tuning

**Optimization**:
- Batch inserts (INSERT with 1000 rows at a time)
- Disable synchronous_commit for non-critical data
- Increase shared_buffers and work_mem
- Use UNLOGGED tables for temporary data

### Read Performance

**Query Types**:
1. **OLTP**: Point lookups (auction by ID) → B-tree indexes → <1ms
2. **Time-series**: Recent auctions (last 24h) → BRIN indexes → <100ms
3. **Analytics**: Aggregations (win rate by advertiser) → Materialized views → <1s

**Optimization**:
- Materialized views for pre-computed aggregations (refreshed hourly)
- Covering indexes for common queries (INCLUDE clause)
- Parallel query execution (parallel_workers = 4)
- pg_stat_statements for query optimization

## Monitoring and Alerts

**Key Metrics**:
1. **Connection Pool**: Active connections, connection wait time (PgBouncer)
2. **Query Performance**: Slow queries (>1s), query plan cache hit rate
3. **Replication Lag**: Standby lag (should be <10s)
4. **Vacuum**: Last vacuum time, dead tuples percentage
5. **Disk Usage**: Database size, WAL disk usage

**Alerts**:
- Replication lag > 60s → Failover risk
- Connection pool saturation > 90% → Increase pool size
- Slow query count > 10/min → Query optimization needed
- Disk usage > 80% → Cleanup or scaling needed

**Tools**:
- `pg_stat_statements` - Query performance tracking
- `pgAdmin` - GUI for database management
- `pg_stat_monitor` - Enhanced monitoring (Percona)
- Prometheus + postgres_exporter - Metrics collection

## Migration Strategy

**Phase 1: Initial Setup** (Week 1)
- Deploy PostgreSQL 16
- Create base schema with Alembic migrations
- Set up replication and backups
- Configure PgBouncer connection pooling

**Phase 2: Data Loading** (Week 2-3)
- Bulk load historical auction data (if available)
- Create indexes and partitions
- Test query performance
- Optimize slow queries

**Phase 3: Application Integration** (Week 4)
- Integrate with API server (SQLAlchemy ORM)
- Implement connection pooling in application
- Test multi-tenancy (row-level security)
- Load testing (simulate production traffic)

**Phase 4: Production Cutover** (Week 5)
- Enable monitoring and alerting
- Set up automated backups
- Deploy to production
- Monitor performance for 2 weeks

## Future Considerations

1. **Read Replicas**: Add read replicas for analytics queries (offload from primary)
2. **Sharding**: If write load exceeds 100K inserts/sec, shard by tenant_id (Citus extension)
3. **ClickHouse Replication**: Replicate auction data to ClickHouse for faster analytics
4. **TimescaleDB Migration**: Migrate time-series tables to TimescaleDB for better performance
5. **pgvector Extension**: Add vector similarity search for ad targeting (embeddings)
