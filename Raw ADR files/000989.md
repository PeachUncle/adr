# Repository structure

## Context and Problem Statement

CAIRA repository structure needs to allow for ease of development, maintenance. Also support ease of delivery of the Reference Architectures to users.

## Decision Drivers

- must be modular to allow for ease of readability and maintenance
- must be easy to follow for contributors to create/extend reference architectures
- must not allow for any dead code generation
- core's[^1] integrity needs to be maintained and repo structure must provide a way to allow enforcement of Core-by-default[^2] for all RAs
- must be flexible for future enhancements based on new features/capabilities

[^1]: Core is defined as resources necessary to ensure the RA abides by CAIRA's [principles](./../../README.md) e.g. compliant to MCSB;
[^2]: core-by default - all RAs pull in all of Core resources

## Considered Options

1. [Current State] Single Repo, folders separated by ai, data, applications, common; Reference Architecture (RA) folder contains IaC files for the resources used in that RA.
2. Single Repo, with one folder per azure resource which contains its IaC scripts (eg. main.tf, variables.tf); RA folders only have resources for that specific RA.
3. Single Repo, segregated CAIRA-core and separate folders for each Azure product area (ai, data, app, citizen-dev); RA folders will have resources for that specific RA.
4. Single Repo, segregated CAIRA-core and all resources stored in a folder; RAs will have an immutable core and resource files.
5. Two Repos, One for external end-users (CAIRA-External) and one for internal developers (CAIRA-Internal). CAIRA-External contains only RAs and their resource files. CAIRA-Internal is not exposed to customer and contains core, resources etc.

## Decision Proposal

Chosen option: "**Option 4.** Single Repo, segregated CAIRA-core and all resources stored in a folder; RAs will have an immutable core and the resource files specific to the RA, documentation, tests and pipeline scripts.", because it allows for easy development, packaging and maintenance of RAs.

### Consequences

- Good, everything needed for a RA is contained within one folder (dependencies, usage docs, resources, test, etc.)
- Good, easy to bring in support for new RAs
- Good, removing segregated folders for ai, data, app, etc. to avoids confusion for contributors on which folder to add their contribution to. Instead helps focus on the RA and any resources needed for the RA
- Good, provides ability to enforce core-by-default for all RAs[^2]
- Good, no duplication of scripts within the resources folder
- Good, only those resources needed by RA will be part of the RA folder. No unused or unnecessary resources will be part of the RA
- Bad, may have duplicated resource files across RAs i.e., if Azure AI Search is used in RA1 and RA2, then the file will reside in both RA1 and RA2. So, if the underlying Azure AI Search terraform resource module property gets changed, then will have to ensure that all RAs that use this property gets updated. NOTE: this problem will manifest in different ways regardless of which option we settle in. We will look for ways to address this problem when encountered.

## Pros and Cons of the Options

### Option 1: Single Repo, folders separated by ai, data, app, common; Reference Architecture (RA) folder contains IaC files for the resources used in that RA

This the current state of the repository where we have separate folders for each module (ai, data, app) and common for any cross-cutting concerns such as security, identity, networking and observability. Reference Architecture folder has IaC files (.tf for terraform) and use flags to enable or disable resources needed by the RA

- Good, directly provides RA specific IaC scripts that can be used to setup environments; No additional iac-generation step required
- Bad, makes it hard for RA contribution. Requires prior knowledge of what goes in ai, data, app folders and possibly discussion on where to create vs reuse one of these folders when developing a RA
- Bad, can lead to dead code generation i.e., generating resource files which are not needed by the RA
- Bad, leads to duplication of IaC scripts across the different folders (ai, data, app) and across RAs. Difficult to test and maintain
- Bad, difficult to enforce core across RAs and hence hard to abide by CAIRA's principles[^1]

```text
caira/.
├── docs/
│   └── adrs
├── media
└── infrastructure/
    └── terraform/
        ├── modules/
        │   ├── ai/
        │   ├── app/
        │   ├── common/
        │   └── data/
        └── reference_architectures/
            └── ra1/
                ├── src
                ├── tests
                ├── main.tf
                └── variables.tf
```

### Option 2: Single Repo, with one folder per azure resource which contains its IaC scripts

This proposal flattens the entire repository to have Reference Architectures and Infrastructure Modules (i.e. azure resource modules). The RAs will contain default config and documents. The Infrastructure folder contains the one folder per azure resource; mimics the structure of terraform provider. Needs a separate config generator script to generate the configs per RA based on the user input.

- Good, RAs are self-contained with all necessary resources
- Good, provides flexibility on composing any combination of RA
- Good, developers can easily add and remove resources needed
- Bad, difficult to enforce the concept of core and hence difficult to ensure the principles of CAIRA around security, observability etc.
- Bad, too granular to maintain one folder per every resource; complicates the usage of the resource within RAs
- Bad, difficult to do impact analysis when core changes. Hence testing RAs will be cumbersome
- Bad, with the flexibility that this option offers, comes a problem of too many varied scenarios and moves away from providing opinionated RAs that is testable and verifiable.
- Bad, violates the opinionated principles of CAIRA by being too flexible

### Option 3: Single Repo, segregated CAIRA-core and separate folders for each Azure product area (ai, data, app, citizen-dev)

- Good, RAs are self-contained with all necessary resources, tests, docs, etc
- Good, provides a way to enforce core in every RA
- Bad, makes it hard for RA contribution. Requires prior knowledge of what goes in ai, data, app, citizen-dev modules and possibly discussion on where to create vs reuse one of these modules when developing a RA
- Bad, if a particular Azure resource does not fall under any of the chosen product areas, will lead to confusion on when to create a new module or extend an existing module making contributions difficult in those scenarios
- Bad, leads to duplication of IaC code and scripts across RAs when specific requirements are needed

```text
.
├── docs/
│   └── adrs
├── media
├── pipelines
├── tests
├── infrastructure/
│   ├── core/
│   ├── ai/
│   ├── app/
│   ├── citizen-dev/
│   └── data/
└── reference_architectures/
    ├── ra1/
    │   ├── README
    │   ├── tests
    │   ├── pipelines
    │   └── resources
    └── ra2/
        ├── README
        ├── tests
        ├── pipelines
        └── resources
```

### Option 5: Two Repos, One for external end-users (CAIRA-External) and one for internal developers (CAIRA-Internal)

- Neutral, may make it easier for end-users to only see the RAs and their resources. For ISE crews who are usually savvy in IaC providers such as terraform or bicep, they would want access to CAIRA-Internal as well. Defeats the purpose of maintaining two separate repos
- Bad, additional overhead in build and release management to maintain two different repositories
- Bad, can lead to code inconsistencies if the dependency management across two repositories and pull-request are not well-sequenced
- Bad, difficult to enforce core unless we add core resources with external repository as well. This means you will have to maintain two cores (one within each repo) and keep them consistent
- Bad, packaging the test suites and pipelines scripts for each RA can become cumbersome
- Bad, would require a CLI in order to use the repositories as there will be no way to just clone and use a Reference Architecture
- Bad, crews would require to put some effort to convert their IaC code from engagement to match the two repos.

```text
.
└── caira-external/
    ├── reference-architectures/
    │   ├── core/
    │   ├── ra1/
    │   └── ra2/
    └── cli

.
└── caira-internal/
    ├── reference-architectures/
    │   ├── ra1/
    │   └── ra2/
    ├── core/
    ├── resources/
    ├── tests
    ├── scripts
    └── pipelines
```
