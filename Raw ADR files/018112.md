# ADR-0004: WCAG AAA as Accessibility Standard

**Status:** Accepted
**Date:** 2025-10-22
**Deciders:** Project maintainers

## Context

The super-claude project needs to establish an accessibility standard for all UI components and patterns generated by skills.

Requirements:

- Clear, measurable accessibility criteria
- Industry-recognized standards
- Applicable to modern web applications
- Enforceable through tooling and code review
- Balances accessibility with development practicality

The accessibility standard affects:

- Component generation (component-generator)
- Design system patterns (design-system-orchestrator)
- Testing strategies (accessibility validation)
- Code review guidelines
- User expectations

## Decision

**Adopt WCAG AAA (Web Content Accessibility Guidelines Level AAA) as the target accessibility standard for all generated components and patterns.**

All component-related skills will:

- Generate components targeting WCAG AAA compliance
- Include accessibility attributes (ARIA, semantic HTML)
- Provide keyboard navigation support
- Ensure color contrast meets AAA standards (7:1 for normal text, 4.5:1 for large text)
- Document accessibility features and requirements

**Pragmatic approach:**

- **Target AAA** where practical and achievable
- **Minimum AA** where AAA is impractical (note exceptions)
- **Document trade-offs** when AAA cannot be met

## Alternatives Considered

### Option 1: WCAG A (Minimal Compliance)

**Description:**
Most basic level of web accessibility.

**Pros:**

- Easiest to achieve
- Least restrictive
- Faster development

**Cons:**

- Insufficient for many users with disabilities
- Not competitive with modern standards
- Poor user experience for accessibility needs
- Minimal legal protection

**Decision:** ❌ Rejected

**Rationale:** Level A is too minimal for modern applications and doesn't provide adequate accessibility for users with disabilities.

### Option 2: WCAG AA (Standard Compliance)

**Description:**
Middle tier of WCAG, most common legal requirement.

**Pros:**

- Industry standard for most organizations
- Meets most legal requirements (ADA, Section 508)
- Achievable for most applications
- Good balance of accessibility and practicality
- Color contrast 4.5:1 (normal text), 3:1 (large text)

**Cons:**

- Not the highest standard available
- May exclude some users with severe disabilities
- Less competitive as "accessibility leader"
- Contrast requirements may be insufficient for some users

**Decision:** ❌ Rejected (as primary target)

**Rationale:** While AA is good, we want to target the highest reasonable standard. AA will be our fallback when AAA is impractical.

### Option 3: WCAG AAA (Highest Compliance)

**Description:**
Highest level of web accessibility, strictest requirements.

**Pros:**

- Best possible accessibility for users
- Demonstrates commitment to inclusion
- Future-proof (regulations trend toward higher standards)
- Competitive advantage
- Color contrast 7:1 (normal text), 4.5:1 (large text)
- Superior keyboard navigation requirements
- Better for users with severe disabilities

**Cons:**

- Harder to achieve (more strict requirements)
- May require more development time
- Some requirements impractical for certain content types
- Can limit design flexibility

**Decision:** ✅ Selected

**Rationale:** AAA represents our commitment to maximum accessibility. The stricter requirements push us to create better, more inclusive patterns. We'll be pragmatic and document when AA is acceptable, but AAA is our target.

### Option 4: No Specific Standard

**Description:**
No formal accessibility standard, rely on best practices.

**Pros:**

- Maximum flexibility
- No compliance burden
- Faster development

**Cons:**

- No clear criteria for success
- Inconsistent accessibility
- Legal risk
- Poor experience for users with disabilities
- No competitive advantage

**Decision:** ❌ Rejected

**Rationale:** Without a standard, accessibility becomes inconsistent and unmeasurable. A clear standard is essential for quality and consistency.

## Consequences

### Positive

- **Superior accessibility**: Best possible experience for users with disabilities
- **Competitive advantage**: Few projects target AAA
- **Future-proof**: Ahead of regulatory trends
- **Clear criteria**: Measurable success criteria for components
- **Better patterns**: Stricter requirements lead to better design
- **Inclusive by default**: Generated components work for everyone

### Negative

- **Development time**: AAA requirements take more time to implement
- **Design constraints**: Color contrast and other requirements may limit design options
- **Documentation burden**: Need to document accessibility features thoroughly
- **Testing complexity**: Validating AAA compliance requires more comprehensive testing
- **Pragmatic exceptions**: Need to document when AA is acceptable

### Neutral

- **Learning curve**: Developers need to understand AAA requirements
- **Tooling**: Need accessibility validation tools in skills
- **Review process**: Code review must check accessibility compliance

## Implementation Notes

**How will this be enforced?**

- component-generator includes AAA-compliant patterns
- design-system-orchestrator validates color contrast (7:1)
- Accessibility linting in generated code
- Documentation includes accessibility notes
- Code review checklist includes WCAG AAA criteria

**Validation tools:**

- axe-core for automated testing
- Manual keyboard navigation testing
- Color contrast checkers (minimum 7:1 for normal text)
- Screen reader testing recommendations

**When does this take effect?**

- Immediately for all new component generation
- Existing examples should be updated or noted as pre-AAA

**What needs to change to comply?**

- Component templates include ARIA attributes
- Color palettes meet AAA contrast requirements
- Keyboard navigation is default in all interactive components
- Focus indicators meet AAA visibility requirements
- Documentation includes accessibility usage notes

**Pragmatic exceptions (where AA is acceptable):**

- Decorative elements (non-functional)
- Complex data visualizations (where AAA contrast impairs readability)
- Third-party integrations (if vendor doesn't support AAA)
- **Document all exceptions explicitly**

## Notes

**AAA is a target, not a requirement:**

We target AAA but accept AA where AAA is impractical. The key is:

1. **Default to AAA** in all generated patterns
2. **Document exceptions** when AA is acceptable
3. **Provide guidance** on when to use AA vs AAA
4. **Never go below AA** (A is insufficient)

**Color contrast quick reference:**

- **AAA:** 7:1 for normal text, 4.5:1 for large text (18pt+)
- **AA (fallback):** 4.5:1 for normal text, 3:1 for large text

**Keyboard navigation requirements:**

- All interactive elements must be keyboard accessible
- Focus indicators must be clearly visible
- Tab order must be logical
- No keyboard traps

**ARIA usage:**

- Use semantic HTML first (button, nav, main, etc.)
- Add ARIA when semantic HTML is insufficient
- Always test with screen readers

This decision reflects our commitment to building inclusive applications by default.
