# 8. Enforce Test Coverage on Changed Code

**Status:** Accepted

**Date:** 2025-10-13

## Context

Our project uses TDD (ADR-0003, ADR-0005) and micro-commits (ADR-0006) to ensure high code quality. While TDD-guard enforces test-first development, we lack visibility into whether our tests actually cover the code we write.

### The Problem

Traditional coverage tools measure **total codebase coverage**, which has limitations:

- **Legacy code drag**: Untested old code lowers overall percentage, obscuring new code quality
- **False confidence**: 80% total coverage may hide 0% coverage on recent changes
- **Poor feedback loop**: Developers don't know if their specific changes are tested
- **Irrelevant metrics**: Coverage on unchanged code doesn't matter for current work

### What We Need

**Diff-based coverage** answers the right question: "Are the lines I just changed/added covered by tests?"

This aligns with our workflow:
- **Micro-commits**: Each commit changes a small number of lines
- **TDD cycles**: We write tests for new functionality
- **Refactoring safety**: We need to verify that refactored code remains tested

### Technical Requirements

- Parse Vitest coverage output (lcov format)
- Compare against git diff
- Calculate coverage percentage on changed lines only
- Enforce configurable threshold
- Fast execution (< 2 seconds)
- Clear reporting of uncovered lines with exact line numbers
- Easy to run locally and in CI/CD

## Evaluation Process

We conducted a comprehensive evaluation of three solutions:

1. **diff-cover (Python tool)** - Active open-source project, 905K weekly downloads
2. **@atakama/cover-diff (Node.js package)** - Unmaintained but secure npm package
3. **Custom Node.js script** - Purpose-built solution with full control

Each solution was:
- Implemented in separate git worktrees
- Tested with real code changes
- Evaluated by independent AI agents using a 27-criterion scorecard
- Scored across 10 categories (installation, performance, accuracy, output quality, DX, maintenance, security, cost, features, use cases)

### Evaluation Results

| Solution | Overall Score | Key Strength | Key Weakness |
|----------|--------------|--------------|--------------|
| **diff-cover** | 9.37/10 | Best overall quality, active maintenance | Python dependency |
| **Custom Script** | 8.51/10 | Complete control, best detail | Team maintenance burden |
| **@atakama/cover-diff** | 8.23/10 | Zero vulnerabilities, simplest setup | Poor output quality, unmaintained |

## Decision

We will use a **custom Node.js script** to enforce test coverage on changed code.

### Rationale

While diff-cover scored highest overall (9.37/10), we chose the custom script (8.51/10) for these reasons:

**Why Custom Script:**
1. **Complete control**: We own the logic and can customize behavior for our specific workflow
2. **Best output detail**: Shows every uncovered line with per-file breakdowns (perfect for micro-commits)
3. **Maximum privacy**: All data stays local, ideal for compliance requirements
4. **No external dependencies**: Only 2 minimal npm packages (parse-lcov, parse-diff) with zero vulnerabilities
5. **Fastest execution**: 0.22 seconds (vs 0.36s for diff-cover)
6. **Excellent documentation**: 448 lines of well-commented code, comprehensive setup guide
7. **JavaScript ecosystem**: Aligns with our Node.js/TypeScript stack
8. **Easy to extend**: Can add features as needed (HTML reports, JSON output, etc.)

**Why Not diff-cover:**
- Python dependency adds complexity to development environment
- Less control over behavior and output format
- External dependency for core development workflow
- Though actively maintained, we still depend on external project decisions

**Why Not @atakama/cover-diff:**
- Poor output quality (no line numbers, raw LCOV format)
- Unmaintained for 5 years (though it works)
- Limited features and configurability
- Poor developer experience

### Implementation

**Script Location:**
```
scripts/check-coverage-on-changes.js
```

**Dependencies:**
```bash
npm install --save-dev parse-lcov parse-diff
```

**Vitest Configuration:**
```typescript
// vitest.config.ts
export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',
      reporter: ['text', 'lcov', 'html'],
      reportsDirectory: './coverage',
      include: ['src/**/*.ts', 'src/**/*.vue'],
    }
  }
})
```

**Package.json Scripts:**
```json
{
  "scripts": {
    "test:coverage": "vitest run --coverage",
    "check-coverage": "node scripts/check-coverage-on-changes.js",
    "check-coverage:verbose": "node scripts/check-coverage-on-changes.js --verbose",
    "check-coverage:full": "npm run test:coverage && npm run check-coverage"
  }
}
```

### Workflow Integration

**During development:**
```bash
npm run check-coverage:full
```

This will:
1. Run all tests with coverage enabled
2. Generate `coverage/lcov.info`
3. Analyze coverage on changed lines (vs main branch)
4. Report coverage % with exact line numbers
5. Exit with error if below 80% threshold

**Custom thresholds:**
```bash
node scripts/check-coverage-on-changes.js --threshold 90
```

**Different base branch:**
```bash
node scripts/check-coverage-on-changes.js --base feature-branch
```

**Verbose output:**
```bash
node scripts/check-coverage-on-changes.js --verbose
```

### Coverage Thresholds

- **Changed-line coverage**: 80% minimum (configurable)
- **Total coverage**: Not enforced (legacy code may be untested)

Rationale: We care about the quality of new code, not the sins of the past.

### When to Check Diff Coverage

**Required:**
- Before creating a pull request
- After completing a feature (all tests in plan.md checked)
- After refactoring sessions

**Recommended:**
- Before each micro-commit (fast feedback loop)
- During TDD cycles for immediate validation

**Optional:**
- Automated via pre-commit hook (see consequences)

### CI Integration

```yaml
# .github/workflows/test.yml
- name: Generate coverage
  run: npm run test:coverage

- name: Check diff coverage
  run: node scripts/check-coverage-on-changes.js --base origin/${{ github.base_ref }} --threshold 80
```

This fails the PR build if changed lines are under 80% covered.

## Consequences

### Positive

- **Maximum control**: Can customize logic, thresholds, output format, and behavior
- **Best output quality**: Most detailed feedback with every uncovered line listed
- **Fast feedback**: 0.22 second execution time, perfect for frequent checks
- **Complete privacy**: All processing local, no external services or data transmission
- **Minimal dependencies**: Only 2 small, stable npm packages (zero vulnerabilities)
- **JavaScript-native**: Aligns with project tech stack
- **No legacy drag**: Old untested code doesn't affect metrics
- **Complements TDD-guard**: TDD-guard enforces test-first, this verifies coverage
- **Works with micro-commits**: Small diffs = quick, detailed coverage checks
- **Extensible**: Easy to add features (HTML reports, JSON output, Slack notifications)
- **Transparent**: Open-source implementation in our repo, fully auditable
- **Free**: No licensing costs or usage limits

### Negative

- **Maintenance burden**: Team owns the code (~0-2 hours/year estimated)
- **Initial learning curve**: Developers need to understand custom tool
- **Low bus factor**: Initially one person understands the implementation
- **No vendor support**: Can't contact support for issues
- **Limited features**: No built-in dashboards, trends, or historical tracking
- **Testing gap**: Script itself has no automated tests
- **Documentation requirement**: Must maintain setup and usage documentation

### Mitigations

- **Comprehensive documentation**: Detailed inline comments, setup guide, troubleshooting section
- **Simple architecture**: 448 lines of clean, modular code with single-responsibility functions
- **Knowledge sharing**: Code review sessions, pair programming on any modifications
- **Low maintenance frequency**: Rarely needs changes once working (~1-2 updates per year)
- **Clear error messages**: Script provides helpful guidance when issues occur
- **Fallback option**: Can switch to diff-cover if maintenance becomes burdensome
- **Version control**: All changes tracked in git history

### Trade-offs Considered

**Why not diff-cover (9.37/10)?**
- **Pros**: Highest score, actively maintained, multiple output formats, HTML reports
- **Cons**: Python dependency, less control, external dependency for core workflow
- **Verdict**: Excellent tool, but we value control and JavaScript alignment more

**Why not @atakama/cover-diff (8.23/10)?**
- **Pros**: Zero vulnerabilities, simplest setup, no Python, fastest execution
- **Cons**: Poor output quality (no line numbers), unmaintained 5 years, limited features
- **Verdict**: Security is good, but output quality too poor for productive development

**Why custom script despite maintenance burden?**
- Maintenance burden is **low** (0-2 hrs/year) due to:
  - Simple, well-defined task (parse coverage + diff)
  - Stable dependencies (parse-lcov, parse-diff unchanged for years)
  - Comprehensive documentation mitigates knowledge transfer
  - Code is modular and well-commented
- Benefits of control and customization outweigh minimal maintenance cost

**Why 80% threshold?**
- Balances quality with pragmatism
- Some structural code may not need tests (type guards, simple getters, comments)
- Refactorings may move code without adding tests
- Can be adjusted per-project if too strict/lenient
- Configurable via CLI flag for different contexts

### Performance Comparison

| Solution | Execution Time | Notes |
|----------|----------------|-------|
| Custom Script | 0.22s | Fastest, perfect for pre-commit hooks |
| @atakama/cover-diff | 0.05-0.10s | Technically fastest, but poor UX |
| diff-cover | 0.36s | Still excellent, sub-second |

All three are fast enough for:
- ✅ Pre-commit hooks
- ✅ CI/CD pipelines
- ✅ Local development iterations
- ✅ Code review workflows
