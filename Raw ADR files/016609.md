# ADR-010: Phoenix 1.8+ Function Component Architecture

## Status

Accepted

## Date

2025-09-20

## Context

SharedLedger was initially built with Phoenix patterns that included:

- Separate template files (app.html.heex, live.html.heex)
- Template-based layouts
- Mixed approaches to component definition
- Separate layouts for LiveView and regular views

Phoenix 1.7+ and especially 1.8+ introduced a new paradigm favoring function components over template files, promoting better code organization and reusability.

## Decision

We adopted Phoenix 1.8+ conventions throughout the application:

1. **Function Components Over Templates**:
   - Consolidated app.html.heex and live.html.heex into a single `app/1` function
   - Created specialized layout functions (landing/1) as needed
   - Defined all layouts as function components with attributes

2. **Unified Layout System**:
   - Single layout system for both regular and LiveView pages
   - Router configuration uses consistent layout specification
   - Removed `layout: {SharedLedgerWeb.Layouts, :live}` in favor of unified `:app`

3. **Component Architecture**:
   - Heavy use of declarative attributes with `attr` and `slot`
   - Embraced HEEx shorthand syntax (`:if`, `:for`)
   - CoreComponents for consistent UI elements

## Consequences

### Positive

- **Consistency**: Single pattern for all components and layouts
- **Maintainability**: Layouts defined in one place as functions
- **Type Safety**: Attributes provide better documentation and validation
- **Modern Patterns**: Aligned with Phoenix ecosystem evolution
- **Reduced Files**: Fewer template files to manage
- **Better Composition**: Function components compose naturally

### Negative

- **Breaking Change**: Existing code required refactoring
- **Learning Curve**: Developers familiar with older patterns need adjustment
- **Documentation**: Many tutorials still show old patterns

### Neutral

- **Performance**: No significant performance impact
- **Testing**: Test patterns remain largely the same

## Implementation Example

### Before (Template-based)

```heex
<!-- lib/shared_ledger_web/templates/layout/app.html.heex -->
<main class="container">
  <%= @inner_content %>
</main>

<!-- lib/shared_ledger_web/templates/layout/live.html.heex -->
<main class="container">
  <%= @inner_content %>
</main>
```

### After (Function Component)

```elixir
# lib/shared_ledger_web/components/layouts.ex
def app(assigns) do
  ~H"""
  <%= if assigns[:current_user] do %>
    <div class="min-h-screen bg-base-200">
      <.navbar current_user={@current_user} />
      <main class="relative">
        {@inner_content}
      </main>
    </div>
  <% else %>
    <main class="relative">
      <.flash_group flash={@flash} />
      {@inner_content}
    </main>
  <% end %>
  """
end
```

### Router Configuration

```elixir
# Before
layout: {SharedLedgerWeb.Layouts, :live}

# After
layout: {SharedLedgerWeb.Layouts, :app}
```

## Migration Path

1. **Phase 1**: Create function components alongside templates
2. **Phase 2**: Update router configuration
3. **Phase 3**: Migrate LiveViews to use new layouts
4. **Phase 4**: Remove old template files
5. **Phase 5**: Update tests for new structure

## Alternatives Considered

1. **Keep Template Files**
   - Pros: No migration needed, familiar pattern
   - Cons: Against framework direction, harder to maintain

2. **Gradual Migration**
   - Pros: Less risk, can revert easily
   - Cons: Inconsistency during transition

3. **Custom Abstraction Layer**
   - Pros: Could hide implementation details
   - Cons: Additional complexity, fights framework
