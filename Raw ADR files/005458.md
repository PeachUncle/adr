## Context

Following the decision in ADR-001 to use separate long-term and operational memory stores, a deeper analysis is required for the long-term permanent memory solution. The primary drivers for this decision are **cost-effectiveness** and **flexibility**, especially to support the evolving data needs of an AI agent-based trading system. The system will need to store both highly structured transactional data (trades, orders) and semi-structured or unstructured data that agents produce (analysis artifacts, logs, market sentiment data).

This ADR compares managed SQL and NoSQL cloud database offerings from GCP and Azure and recommends a hybrid approach using native GCP services.

## Decision

We will adopt a **hybrid data storage model** for permanent memory, leveraging two powerful, serverless GCP services that are purpose-built for their respective tasks:

1.  **Primary Store for Agent-Generated Data (Analytics)**: **Google BigQuery** will be used for storing the large volume of semi-structured and evolving data generated by AI agents, such as analysis results, decision logs, and market sentiment.
2.  **Transactional Store for Core Data (SQL)**: **Google Cloud SQL for PostgreSQL** will be used for core, highly structured, relational data like trade execution records and audit trails, where transactional integrity is paramount.

## Rationale

A hybrid model using BigQuery and Cloud SQL is the most cost-effective, flexible, and scalable solution that meets all of the system's data storage requirements.

1.  **Purpose-Built Services**: The solution uses the best tool for each job. Cloud SQL provides the strict ACID compliance and relational integrity needed for critical financial transactions. BigQuery provides unparalleled scalability, flexibility for semi-structured data, and a powerful analytical engine for the massive datasets generated by the agents.
2.  **Unified Analytics Ecosystem**: By designating BigQuery as the primary store for all agent-generated and analytical data (as established in ADR-004), we prevent data silos. This allows for powerful, efficient queries that can join agent decision logs with market data and trade outcomes, all within a single, optimized environment.
3.  **Cost-Effectiveness**: This model is highly optimized for cost. BigQuery's storage is extremely inexpensive for the large volumes of analytical data we anticipate, and its pay-per-query model is ideal for our analytical workload. Cloud SQL's serverless option provides a cost-effective solution for the lower-volume transactional workload.
4.  **GCP Native Integration**: Using native GCP services ensures seamless integration with the rest of our stack, including IAM for security, Cloud Monitoring for observability, and the ADK framework.

## Consequences

-   **Increased Complexity**: The development team will need to manage and interact with two different database systems. A clear data governance strategy is required to define the boundary between transactional and analytical data.
-   **Data Modeling**: A clear data boundary is critical.
    -   **Cloud SQL**: `trades`, `orders`, `audit_trails`.
    -   **BigQuery**: `agent_session_archives`, `market_sentiment_snapshots`, `backtesting_results`.
-   **Tooling**: The project will require SDKs for both BigQuery (`google-cloud-bigquery`) and Cloud SQL (`asyncpg`).
-   **Flexibility**: The system can easily adapt as agents evolve and produce new types of data, as BigQuery's support for schema evolution allows for new fields to be added without complex migrations.

## Alternatives Considered

1.  **BigQuery Only**: Using BigQuery for both analytical and transactional data.
    -   **Reason for Rejection**: BigQuery is an Online Analytical Processing (OLAP) system, not an Online Transaction Processing (OLTP) database. Its write latency is too high for the frequent, small updates required for transactional records, and it does not enforce the same level of relational integrity as a true SQL database.

2.  **Cloud SQL Only**: Using a single PostgreSQL database for all data.
    -   **Reason for Rejection**: This is not a cost-effective or scalable solution for the analytical workload. Storing petabytes of semi-structured agent data in a relational database would be prohibitively expensive, and the performance of complex analytical queries would be poor compared to a columnar store like BigQuery.

3.  **Pure NoSQL Solution (e.g., Firestore)**: Using a NoSQL database for all data.
    -   **Reason for Rejection**: While highly flexible, this approach was rejected because most NoSQL databases lack the strict ACID compliance and transactional guarantees required for core financial records. This would introduce an unacceptable risk to data integrity.

4.  **Using another Cloud Provider (e.g., Azure SQL + Azure Synapse)**:
    -   **Reason for Rejection**: While other providers offer a similar set of services, this was rejected to maintain a consistent, single-cloud architecture on GCP. This avoids multi-cloud complexity and leverages the deep integration between native GCP services.

## Implementation Strategy

### Phase 1: Data Governance and Schema Design (Week 1-2)
**Deliverables**:
- Document data boundary between Cloud SQL and BigQuery
- Define Cloud SQL schema for `trades`, `orders`, `audit_trails` tables
- Define BigQuery schema for `agent_session_archives`, `market_sentiment_snapshots`, `backtesting_results`
- Create data classification matrix (transactional vs analytical)
- Document schema evolution policies for both systems

**Dependencies**: ADR-001 acceptance, stakeholder agreement on data boundaries

### Phase 2: Infrastructure and Tooling (Week 2-3)
**Deliverables**:
- Provision Cloud SQL instance (db-custom-2-7680) with automated backups
- Configure BigQuery dataset with partitioned tables (partition by date)
- Implement Python SDK wrappers for `asyncpg` and `google-cloud-bigquery`
- Create data access abstraction layer for transactional vs analytical queries
- Set up Terraform configurations for infrastructure-as-code

**Dependencies**: Phase 1 schema definitions, GCP project provisioning

### Phase 3: Data Migration and Integration (Week 3-5)
**Deliverables**:
- Implement dual-write pattern in `IBGatewayAgent` (Cloud SQL for trades, BigQuery for market data)
- Migrate historical data from archived sources to BigQuery
- Implement ETL pipeline for Cloud SQL to BigQuery analytics (daily batch)
- Create data validation tests for consistency across both stores
- Integration tests for agent data access patterns

**Dependencies**: Phase 2 infrastructure, ADR-006 (IB Gateway) implementation

### Phase 4: Analytics and Optimization (Week 5-6)
**Deliverables**:
- Create BigQuery materialized views for common agent queries
- Implement query cost monitoring and alerting
- Optimize BigQuery table clustering and partitioning strategies
- Document query patterns and best practices for developers
- Performance benchmarking and tuning

**Dependencies**: Phase 3 data migration complete, production-like data volume

## Cost Analysis

### Monthly Operational Costs

**Cloud SQL for PostgreSQL**:
- db-custom-2-7680 instance (2 vCPU, 7.68GB RAM): $120/month
- Storage (100GB SSD at $0.17/GB): $17/month
- Backup storage (100GB at $0.08/GB): $8/month
- High availability (if enabled): +$120/month (optional)
- Data transfer (egress to internet): $5-10/month
- **Subtotal**: $150-155/month (standard) or $270-275/month (HA)

**BigQuery**:
- Active storage (1TB at $0.020/GB): $20/month
- Long-term storage (5TB at $0.010/GB): $50/month
- Query processing (500GB scanned/month at $5/TB): $2.50/month
- Streaming inserts (10M rows at $0.05/million): $0.50/month
- Batch load operations: Free
- Data transfer (same region): Free
- **Subtotal**: $73/month

**Total Estimated Monthly Cost**: $223-228/month (standard) or $343-348/month (HA)

### Cost Optimization Strategies

1. **BigQuery Partitioning and Clustering**:
   - Without optimization: 2.5TB scanned/month × $5/TB = $12.50/month
   - With date partitioning + symbol clustering: 400GB scanned/month × $5/TB = $2/month
   - **Savings**: $10.50/month (84% reduction in query costs)

2. **Long-Term Storage Migration**:
   - BigQuery automatically moves tables not modified in 90 days to long-term storage
   - Cost reduction: $0.020/GB → $0.010/GB (50% savings)
   - Estimated 5TB eligible for long-term storage: $50/month savings annually

3. **Batch Loading vs Streaming**:
   - Streaming inserts: $0.05 per million rows
   - Batch loading: Free
   - Use batch loading for non-time-critical data (backtesting results, historical analysis)
   - **Savings**: $3-5/month

4. **Cloud SQL Rightsizing**:
   - Monitor actual CPU and memory usage
   - Downsize to db-custom-1-3840 if usage <50%: $60/month savings
   - Use Cloud SQL Insights to identify inefficient queries

5. **Query Result Caching**:
   - BigQuery caches query results for 24 hours
   - Repeated queries by multiple agents: No additional cost
   - Estimated 30% of queries benefit from caching

### ROI Comparison

**vs Cloud SQL Only Approach**:
- Single Cloud SQL for all data: db-custom-8-30720 (8 vCPU, 30GB RAM) = $480/month
- Storage (10TB SSD): $1,700/month
- Backup storage (10TB): $800/month
- **Total**: $2,980/month
- Current hybrid approach: $223-228/month
- **Cost Savings**: 92% reduction ($2,750/month saved)

**vs BigQuery Only Approach**:
- Active storage (1TB): $20/month
- Query processing for transactional queries (5TB scanned/month): $25/month
- Streaming inserts (100M rows/month): $5/month
- **Total**: $50/month for storage, but unacceptable latency for transactional writes (5-10 seconds vs <50ms)
- **Trade-off**: Hybrid approach costs $173/month more but provides 100x better transactional performance

**vs NoSQL Approach (Firestore)**:
- Document storage (1TB): $180/month
- Document reads (100M operations): $360/month
- Document writes (10M operations): $180/month
- **Total**: $720/month
- **Cost Savings**: 69% reduction ($497/month saved)

## Risk Assessment

| Risk | Severity | Likelihood | Impact | Mitigation |
|------|----------|------------|--------|------------|
| Data boundary violations | High | Medium | Wrong data in wrong store, compliance issues | Strict data governance policy, code reviews, data validation layer in abstraction library |
| Cloud SQL storage exhaustion | Medium | Medium | Write failures, system outage | Storage monitoring at 70% threshold, auto-scaling storage enabled, partition old data to BigQuery |
| BigQuery cost overrun | Medium | Medium | Budget exceeded | Query cost monitoring, require cost estimates for new queries, enforce partitioning, slot reservations for predictable pricing |
| Schema evolution conflicts | Medium | High | Application failures, data corruption | Schema versioning strategy, backward-compatible changes only, canary deployments for schema changes |
| Cross-store consistency | High | Low | Audit failures, incorrect analytics | Transaction boundaries clearly defined, eventual consistency acceptable for analytics, reconciliation jobs |
| Cloud SQL connection pool exhaustion | Medium | Medium | Application failures | Connection pooling (max 50 connections), connection timeout monitoring, circuit breaker pattern |
| BigQuery partition skew | Low | Medium | Query performance degradation, higher costs | Monitor partition sizes, implement sub-partitioning by symbol, clustering for frequently filtered columns |
| Data migration failures | High | Low | Data loss, incomplete historical records | Validation checks, dry-run migrations, maintain source data until verification complete |

## Monitoring and Success Criteria

### Key Metrics

**Cloud SQL Metrics**:
1. Query latency: <50ms p95 for transactional queries
2. Connection pool utilization: <80% of max connections (40/50)
3. Storage utilization: <70% of provisioned capacity
4. Transaction throughput: >500 TPS sustained
5. Backup success rate: 100%

**BigQuery Metrics**:
1. Daily query cost: <$8/day (<$250/month)
2. Query latency: <5 seconds p95 for analytical queries
3. Streaming insert latency: <10 seconds p95
4. Storage growth rate: <50GB/day
5. Partition pruning efficiency: >80% of queries use partition filters

**Data Quality Metrics**:
1. Schema validation failures: <0.1% of inserts
2. Cross-store reconciliation errors: <10 per month
3. Data freshness: BigQuery analytics data <1 hour behind operational data
4. Backup verification success: 100%

### Alerting Thresholds

**Critical Alerts (PagerDuty)**:
- Cloud SQL primary instance unavailable
- Cloud SQL storage >90% full
- BigQuery daily cost >$20
- Cloud SQL backup failure
- Schema validation failure rate >1%

**Warning Alerts (Email)**:
- Cloud SQL storage >70% full
- BigQuery daily cost >$10
- Cloud SQL connection pool >80% utilized
- Query latency >100ms p95 (Cloud SQL)
- BigQuery insert failures >100/hour

**Informational Alerts (Dashboard)**:
- Daily BigQuery cost summary
- Weekly storage growth trends
- Query pattern analysis
- Most expensive BigQuery queries (top 10)
- Schema evolution events

### Success Criteria

**Functional Requirements**:
- Zero data loss for transactional records (trades, orders, audit trails)
- 100% of agent-generated data successfully archived to BigQuery
- Schema evolution completed without downtime
- Cross-store queries execute successfully (join Cloud SQL and BigQuery)

**Performance Requirements**:
- Transactional writes (Cloud SQL): <50ms p95 latency
- Transactional reads (Cloud SQL): <100ms p95 latency
- Analytical queries (BigQuery): <5 seconds p95 latency
- Data freshness: BigQuery analytics <1 hour behind operational data

**Cost Requirements**:
- Total monthly cost <$300 (including HA configuration)
- BigQuery query cost <$250/month
- No single BigQuery query exceeding $5 cost
- 90%+ cost reduction vs single Cloud SQL approach

**Operational Requirements**:
- Automated backups with <1 hour RPO (Recovery Point Objective)
- <1 hour RTO (Recovery Time Objective) for Cloud SQL
- Zero manual intervention for schema migrations
- Self-service query capabilities for developers (BigQuery console)
