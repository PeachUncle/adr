# ADR-003: Use Single JSON File for Metadata

## Status

Accepted

## Context

RustDrop needs to persist metadata about uploaded files, including:
- File information (name, size, MIME type)
- Access control (share IDs, passwords, expiration)
- Usage tracking (download counts, view counts)
- Gallery features (public visibility, reactions)

Storage options for this metadata include:
1. **Single JSON file**: All metadata in one file
2. **Individual JSON files**: One metadata file per upload
3. **SQLite database**: Embedded SQL database
4. **PostgreSQL/MySQL**: Full relational database
5. **Key-value store**: Redis, RocksDB, etc.

Key requirements:
- Simple deployment (single binary ideal)
- Human-readable format for debugging
- Atomic updates to prevent corruption
- Fast lookups by share ID
- No additional infrastructure

## Decision

We chose a **single JSON file** (`files.json`) for all metadata, with an in-memory cache for fast access.

### Implementation Details

```rust
pub struct Storage {
    upload_dir: PathBuf,
    metadata_file: PathBuf,
    files: RwLock<HashMap<String, FileInfo>>,  // In-memory cache
}

// Metadata structure (from models.rs)
pub struct FileInfo {
    pub id: Uuid,
    pub original_name: String,
    pub stored_name: String,
    pub share_id: String,  // 8-char short ID for URLs
    pub size: u64,
    pub mime_type: String,
    pub uploaded_at: DateTime<Utc>,
    pub expires_at: Option<DateTime<Utc>>,
    pub max_downloads: u32,
    pub download_count: u32,
    pub password_hash: Option<String>,
    pub is_archive: bool,
    pub archived_files: Vec<ArchivedFileInfo>,
    pub is_public: bool,
    pub view_count: u32,
    pub reactions: HashMap<String, u32>,
}
```

The file is loaded into memory at startup and written back after each modification.

## Consequences

### Positive

1. **Zero Dependencies**: No database driver, no connection pooling, no migrations
2. **Human Readable**: Can inspect/edit metadata with any text editor
3. **Simple Backup**: Just copy one file alongside the uploads directory
4. **Debuggability**: `cat files.json | jq .` instantly shows all metadata
5. **Portability**: JSON is universally supported; easy to migrate to other systems
6. **Single Binary**: Supports the goal of a single deployable artifact
7. **Fast Reads**: In-memory HashMap provides O(1) lookups by share ID
8. **Atomic Writes**: Full file write ensures consistency

### Negative

1. **Write Amplification**: Every update rewrites the entire file
2. **Memory Usage**: All metadata must fit in memory (not an issue for typical scale)
3. **Concurrent Write Limits**: RwLock serializes writes (acceptable for typical load)
4. **No Query Capability**: Can't do complex queries like "files larger than 1GB uploaded last week"
5. **Scale Ceiling**: Thousands of files work fine; millions would need a different approach

### Neutral

1. **No Schema Migrations**: New fields can be added with `#[serde(default)]`; removed fields are ignored

## Alternatives Considered

### Individual JSON Files Per Upload

**Approach:** Store each FileInfo as `uploads/87b77d35.json` alongside the actual file.

**Pros:**
- No write amplification
- Scales to more files
- Natural pairing with uploaded files

**Cons:**
- Expensive to list all files (directory scan + parse each file)
- Gallery/admin views become slow
- More complex cleanup (two files per upload)
- Harder to backup atomically

**Why not chosen:** The need to frequently list all files (admin dashboard, gallery, expiry cleanup) makes per-file metadata expensive.

### SQLite Database

**Pros:**
- SQL query capabilities
- Proven reliability
- Still file-based, no server needed
- Handles concurrent access well

**Cons:**
- Adds dependency (though Rust bindings are mature)
- Binary format not human-readable
- Requires schema migrations for changes
- Slightly more complex deployment

**Why not chosen:** For the current scale and requirements, SQLite adds complexity without proportional benefit. The JSON approach is simpler to understand, debug, and maintain. SQLite would be the natural upgrade path if query capabilities become necessary.

### PostgreSQL/MySQL

**Pros:**
- Full SQL capabilities
- Excellent concurrent access
- Rich ecosystem of tools

**Cons:**
- Requires separate server deployment
- Connection management complexity
- Overkill for single-instance deployment

**Why not chosen:** Violates the single-binary, minimal-infrastructure design goal.

### Key-Value Store (Redis, RocksDB)

**Pros:**
- Fast read/write operations
- Good concurrent access
- Redis offers expiration natively

**Cons:**
- Redis requires separate server
- RocksDB adds significant complexity
- Neither is human-readable

**Why not chosen:** The infrastructure overhead (Redis) or implementation complexity (RocksDB) isn't justified for the expected scale.

## Design Decisions

### In-Memory Cache with Write-Through

```rust
pub async fn save_file(&self, file_info: FileInfo) -> Result<(), StorageError> {
    let mut files = self.files.write().await;
    files.insert(file_info.share_id.clone(), file_info);
    self.persist_metadata(&files).await
}
```

**Rationale:**
- Reads are O(1) from HashMap, important for download requests
- Writes persist immediately, ensuring durability
- RwLock allows concurrent reads with exclusive writes

### Short Share IDs as Primary Key

Files are indexed by 8-character share IDs (e.g., `Kx7mN2pQ`) rather than UUIDs:

**Rationale:**
- Share IDs are used in URLs and API calls
- More compact than 36-character UUIDs
- Human-memorable for verbal sharing

### Pretty-Printed JSON

```rust
let json = serde_json::to_string_pretty(&files_vec)?;
tokio::fs::write(&self.metadata_file, json).await?;
```

**Rationale:**
- Minimal size increase (bytes vs kilobytes)
- Dramatically easier to read and debug
- Diffs are meaningful in version control

## Scale Considerations

The current approach works well for:
- Hundreds to low thousands of files
- Single-instance deployments
- Moderate concurrent access

Warning signs that would indicate need for SQLite migration:
- `files.json` exceeding several megabytes
- Write latency becoming noticeable
- Need for complex queries (e.g., "most downloaded files this month")

## Future Considerations

1. **Optional SQLite Backend**: Could add a storage backend abstraction
2. **Write Batching**: Could buffer rapid successive writes
3. **Compressed Storage**: Could gzip the JSON file if size becomes an issue
4. **Incremental Backup**: Could implement append-only log for easier backup
