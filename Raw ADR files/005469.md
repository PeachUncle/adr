## 1.0 Context

The multi-agent trading system requires continuous, reliable access to market data for opportunity identification, position monitoring, and risk management. ADR-006 established Interactive Brokers Gateway as the primary data source, while ADR-013 and ADR-014 introduced Alpha Vantage and Finnhub for news, sentiment, and fundamental data. However, these ADRs did not specify:

1. **Failover conditions**: When to switch between data providers
2. **Failback procedures**: How to restore primary source after recovery
3. **Health check specifications**: How to validate data provider availability
4. **Circuit breaker integration**: When to halt trading due to data unavailability
5. **Cost implications**: Financial impact of using backup providers

Market data unavailability creates critical operational risks:
- Lost trading opportunities during market scanning
- Inability to monitor active positions during defense states
- Risk management blind spots from stale data
- Potential regulatory violations from trading on inaccurate quotes

A resilient, well-defined failover strategy is essential for system reliability and regulatory compliance.

## 2.0 Decision

We will implement a **three-tier hierarchical failover strategy** for market data access, managed by the `MarketAnalysisAgent`:

### 2.1 Provider Hierarchy

**Tier 1 (Primary)**: Interactive Brokers Gateway
- Real-time market data for equities and options
- Live options chains with Greeks
- Sub-second quote updates during market hours
- No additional cost for active trading accounts

**Tier 2 (Secondary)**: Alpha Vantage
- 15-minute delayed quotes (free tier)
- Real-time quotes (paid tier: $50/month)
- Options data endpoint (limited coverage)
- 500 API calls/day (free tier)

**Tier 3 (Tertiary)**: Finnhub
- 15-minute delayed quotes (free tier)
- Real-time quotes (paid tier: $25/month)
- Options data (limited availability)
- 60 API calls/minute (free tier)

**Failover Logic**: Automatic sequential cascade from Tier 1 → Tier 2 → Tier 3 based on defined triggers. All three providers unavailable triggers trading halt circuit breaker.

### 2.2 Failover Triggers

The `MarketAnalysisAgent` will monitor primary data source health and trigger failover based on these conditions:

**Tier 1 → Tier 2 Failover Triggers**:
1. **Connection Loss**: IB Gateway TCP connection down >30 seconds
2. **Quote Staleness**: No market data updates received for >60 seconds during market hours
3. **API Error Rate**: >5 consecutive API errors or >20% error rate over 5 minutes
4. **Latency Degradation**: Quote latency exceeds 5 seconds for >2 minutes
5. **Manual Override**: Orchestrator command to switch providers

**Tier 2 → Tier 3 Failover Triggers**:
1. **API Unavailability**: Alpha Vantage HTTP 503/500 errors for >90 seconds
2. **Timeout**: Request timeout (>10 seconds) for 3 consecutive calls
3. **Rate Limit**: HTTP 429 response (exceeded API quota)
4. **Data Quality**: Missing required fields in >50% of responses over 5 minutes

**All Providers Failed → Circuit Breaker**:
1. All three tiers unavailable simultaneously
2. Orchestrator immediately transitions to emergency defensive state
3. New trade initiation halted (circuit breaker activated)
4. Active positions monitored using last known cached data
5. Manual intervention required to resume trading

### 2.3 Failback Strategy

**Automatic Failback Conditions**:
- **Tier 2 → Tier 1**: 5 consecutive successful health checks from IB Gateway (30 seconds total)
- **Tier 3 → Tier 2**: 5 consecutive successful health checks from Alpha Vantage (30 seconds total)
- **Tier 3 → Tier 1**: IB Gateway health restored, automatic preference for primary

**Manual Override**: Orchestrator can force failback via command interface at any time.

**Health Check Specification**:
```
Health Check Protocol (every 6 seconds):
1. Connection Check: TCP socket alive (IB) or HTTPS reachable (APIs)
2. Test Quote Request: Fetch SPY quote (standard market benchmark)
3. Latency Validation: Round-trip time <2 seconds
4. Data Quality Check: Required fields present (price, volume, timestamp)
5. Result: PASS (all checks succeed) or FAIL (any check fails)

Success Criteria for Failback:
- 5 consecutive PASS results (30 seconds of stable connectivity)
- No circuit breaker conditions active
- Current provider operational (no degraded failback)
```

**Failback Hysteresis**: 30-second confirmation window prevents oscillation between providers during intermittent connectivity issues.

## 3.0 Rationale

### 3.1 Why This Specific Hierarchy

**IB Gateway as Primary**:
- Zero marginal cost for active accounts (no additional data fees)
- Highest data quality: real-time, tick-by-tick updates
- Complete options chain data with calculated Greeks
- Direct integration with execution platform (data-execution consistency)
- Lowest latency (<50ms) for time-sensitive decisions

**Alpha Vantage as Secondary**:
- Established provider with proven reliability
- Free tier sufficient for emergency failover scenarios
- Structured JSON API (easy integration)
- News and sentiment endpoints complement market data
- Paid tier ($50/month) available if real-time backup required

**Finnhub as Tertiary**:
- Cost-effective backup (free tier: 60 calls/min)
- Redundancy from different infrastructure provider
- Covers both market data and fundamental data gaps
- Already integrated per ADR-014

**Tier Ordering Logic**: Prioritizes data quality and latency, with cost efficiency as secondary factor. Free-tier backup providers minimize operational costs while maintaining resilience.

### 3.2 Why 30-Second Thresholds

**Failover Timing**:
- 30 seconds balances rapid response with false positive prevention
- Market conditions can change significantly in <30 seconds during high volatility
- Prevents premature failover from transient network glitches
- Sufficient time for IB Gateway auto-reconnection attempts

**Failback Timing**:
- 30-second health confirmation (5 × 6-second checks) provides high confidence
- Prevents rapid oscillation between providers (hysteresis effect)
- Allows sufficient validation that primary source is stable
- Documented in system monitoring as "connection stability window"

### 3.3 Why Circuit Breaker on Total Failure

When all data providers fail simultaneously:
- **Risk Management Blind**: Cannot validate position Greeks or portfolio exposure
- **Regulatory Compliance**: Trading on stale data violates best execution requirements
- **Operational Safety**: Manual oversight required when automation loses visibility
- **Capital Preservation**: Halting new trades protects capital during infrastructure failure

Circuit breaker integrates with ADR-008 risk parameters: `circuit_breaker_data_loss: true` triggers same defensive state as VIX or correlation breakers.

## 4.0 Implementation Strategy

### 4.1 MarketAnalysisAgent Architecture Enhancement

The `MarketAnalysisAgent` will be enhanced with a new `DataProviderManager` module:

**Module Components**:

1. **Provider Registry**:
   - Configuration for all three data providers
   - API credentials, endpoints, rate limits
   - Health check intervals and timeout values

2. **Health Monitor Service**:
   - Background loop executing health checks every 6 seconds
   - Maintains provider status: `HEALTHY`, `DEGRADED`, `FAILED`
   - Publishes status updates to Redis for system visibility

3. **Failover Controller**:
   - Evaluates failover triggers based on health metrics
   - Executes provider switch with zero-downtime cutover
   - Logs all failover events to Cloud SQL for audit trail

4. **Failback Orchestrator**:
   - Tracks health recovery of higher-tier providers
   - Implements 5-check confirmation logic
   - Executes automatic failback when conditions met

5. **Circuit Breaker Interface**:
   - Communicates with Portfolio Orchestrator on total failure
   - Triggers `circuit_breaker_data_loss` event
   - Provides last-known-good data cache for defensive monitoring

**Data Flow**:
```
Health Monitor (6s loop) → Status Assessment → Failover Decision
                                                       ↓
                                    Provider Switch → Update Redis Cache
                                                       ↓
                                    Notify Orchestrator → Log to Cloud SQL
```

### 4.2 Integration with Existing Agents

**Portfolio Orchestrator Agent**:
- Subscribes to data provider status events from Redis
- Receives circuit breaker notifications on total data loss
- Commands manual failover/failback via `MarketAnalysisAgent` API

**Risk Management Agent**:
- Validates data source before risk calculations
- Applies degraded-mode risk limits when using backup providers
- Rejects new trades if data source is Tier 3 (delayed quotes)

**Strategy Execution Agents**:
- Query `MarketAnalysisAgent` for current data provider status
- Adjust monitoring frequency based on data tier (Tier 2/3: wider update intervals)
- Use cached Greeks from last Tier 1 data when on backup providers

### 4.3 Configuration Integration

Add to `config/risk.yaml` (per ADR-008):

```yaml
market_data_failover:
  tier1_provider: "interactive_brokers"
  tier2_provider: "alpha_vantage"
  tier3_provider: "finnhub"

  failover_triggers:
    connection_timeout_seconds: 30
    quote_staleness_seconds: 60
    api_error_rate_threshold: 0.20
    latency_threshold_seconds: 5
    consecutive_errors_threshold: 5

  failback_settings:
    health_check_interval_seconds: 6
    consecutive_success_required: 5
    total_confirmation_window_seconds: 30
    enable_auto_failback: true

  circuit_breaker:
    halt_trading_on_total_failure: true
    max_stale_data_minutes: 5
    alert_on_tier2_failover: true
    alert_on_tier3_failover: true

  health_check:
    test_symbol: "SPY"
    required_fields: ["price", "volume", "timestamp", "bid", "ask"]
    max_latency_ms: 2000
```

## 5.0 Cost Analysis

### 5.1 Baseline Costs (Current State)

**Interactive Brokers** (ADR-006):
- Account: $0 (no monthly minimum for active trading)
- Market data: $0 (included with active trading)
- Options data: $0 (included)
- **Total**: $0/month

### 5.2 Failover Costs (Backup Providers)

**Alpha Vantage** (Tier 2):
- **Free Tier**: 500 API calls/day, 15-min delayed quotes
- **Paid Tier** (if real-time backup needed): $50/month
- **Projected Usage**: 5-10 hours/month during IB outages
- **Estimated Cost**: $0-50/month (depends on tier selection)

**Finnhub** (Tier 3):
- **Free Tier**: 60 API calls/min, 15-min delayed quotes
- **Paid Tier** (if real-time needed): $25/month
- **Projected Usage**: 1-3 hours/month during dual failure
- **Estimated Cost**: $0-25/month

### 5.3 Cost Scenarios

| Scenario | Duration/Month | IB Cost | Alpha Vantage | Finnhub | Total |
|----------|---------------|---------|---------------|---------|-------|
| **Normal Operations** | 99% uptime | $0 | $0 (free tier) | $0 (free tier) | **$0** |
| **IB Outages** (Tier 2) | 1% (7 hours) | $0 | $0-50 | $0 | **$0-50** |
| **Dual Failure** (Tier 3) | 0.1% (40 min) | $0 | $0-50 | $0-25 | **$0-75** |

**Recommendation**: Start with free tiers for both backup providers. Upgrade to paid tiers only if:
1. IB outages exceed 10 hours/month
2. Real-time backup data becomes regulatory requirement
3. Trading strategy requires sub-minute quote precision during failover

**Annual Cost Estimate**: $0-600 (worst case with both paid tiers)

### 5.4 Cost-Benefit Analysis

**Costs**:
- Development: 2 engineers × 4 weeks = $20,000 (one-time)
- Infrastructure: $0-600/year (backup API subscriptions)
- Maintenance: 4 hours/quarter review = $2,000/year
- **Total Year 1**: $22,000-22,600

**Benefits**:
- **Prevented Losses**: Single 1% drawdown on $100k account = $1,000 saved per incident
- **Uptime Improvement**: 99% → 99.9% reliability (10× reduction in downtime)
- **Opportunity Cost**: Capture 95% of trading opportunities vs 85% without failover
- **Regulatory Risk**: Avoid potential trading halt penalties
- **ROI**: Breaks even after preventing 22 market data outage incidents

**Expected Incidents/Year**: Based on IB historical uptime (99.5%), expect ~43 hours downtime annually. Failover strategy reduces impact of 95% of these incidents.

## 6.0 Risk Assessment

### 6.1 Technical Risks

| Risk | Severity | Likelihood | Impact | Mitigation |
|------|----------|------------|--------|------------|
| **Cascading Failure**: All providers fail simultaneously | Critical | Very Low | Trading halt, position monitoring blind spot | Circuit breaker activates, cached data used, manual oversight |
| **Failover Loop**: Rapid oscillation between providers | Medium | Low | Performance degradation, increased latency | 30-second hysteresis window, rate limiting |
| **Data Inconsistency**: Quote discrepancies between providers | High | Medium | Suboptimal trade decisions | Provider validation on failback, staleness checks |
| **Latency Spike**: Backup provider slower than primary | Medium | High | Delayed position updates | Degraded-mode monitoring (wider intervals) |
| **Rate Limit Breach**: Exceed backup provider API quotas | High | Medium | Failover to Tier 3 or circuit breaker | Request batching, cache optimization |

### 6.2 Operational Risks

| Risk | Severity | Likelihood | Impact | Mitigation |
|------|----------|------------|--------|------------|
| **False Positive Failover**: Premature provider switch | Low | Medium | Unnecessary complexity, potential cost | 30-second confirmation, multi-criteria triggers |
| **Missed Failback**: Stay on backup provider unnecessarily | Low | Low | Higher costs, degraded data quality | Automatic health monitoring, failback automation |
| **Configuration Error**: Incorrect failover thresholds | High | Low | Delayed failover or false positives | Schema validation, integration testing |
| **API Key Expiration**: Backup provider credentials invalid | Medium | Low | Failover failure | Automated credential validation, rotation alerts |

### 6.3 Financial Risks

| Risk | Severity | Likelihood | Impact | Mitigation |
|------|----------|------------|--------|------------|
| **Cost Overrun**: Excessive backup API usage | Medium | Low | Unplanned $600/year expense | Free tier monitoring, usage alerts, budget caps |
| **Opportunity Loss**: Delayed data during failover | Medium | Medium | Missed trades, suboptimal entries | Maintain quote cache, fast failover (<30s) |
| **Slippage Increase**: Stale quotes cause wider spreads | Low | High | 0.1-0.3% additional slippage | Validate quote freshness, reject stale data |

## 7.0 Monitoring and Success Criteria

### 7.1 Key Metrics

**Availability Metrics**:
1. **Data Source Uptime**: % of time primary provider available
   - Target: >99.5% (IB Gateway availability)
   - Alert: <99% over rolling 7-day window

2. **Failover Frequency**: Number of provider switches per month
   - Target: <10 failovers/month
   - Alert: >20 failovers/month (indicates instability)

3. **Failback Success Rate**: % of automatic failbacks completed
   - Target: >95%
   - Alert: <90% (indicates primary source instability)

**Performance Metrics**:
4. **Failover Latency**: Time from trigger to active backup provider
   - Target: <30 seconds
   - Alert: >60 seconds

5. **Data Staleness**: Age of quotes during backup operation
   - Target: <60 seconds (Tier 2/3 with paid subscriptions)
   - Alert: >300 seconds (5 minutes)

6. **Quote Discrepancy**: Price difference between providers
   - Target: <0.1% variance
   - Alert: >0.5% variance (indicates data quality issue)

**Cost Metrics**:
7. **Backup API Usage**: Calls/month to Tier 2 and Tier 3 providers
   - Target: <1000 calls/month (stay within free tiers)
   - Alert: Approaching rate limits (80% of quota)

8. **Failover Duration**: Total time on backup providers per month
   - Target: <10 hours/month
   - Alert: >20 hours/month (consider paid subscriptions)

### 7.2 Alerting Thresholds

**Critical Alerts** (immediate response):
- All data providers failed (circuit breaker activated)
- Primary provider down >5 minutes during market hours
- Data staleness >5 minutes with active positions

**Warning Alerts** (15-minute response):
- Failover to Tier 2 provider
- Failback failed after 3 attempts
- Quote discrepancy >0.5% detected

**Info Alerts** (logged for review):
- Successful failover to backup provider
- Automatic failback to primary completed
- Backup provider rate limit approaching (>80%)

### 7.3 Success Criteria

**Functional Requirements**:
- Zero missed trading opportunities due to data unavailability
- All active positions monitored during provider failovers
- Circuit breaker activates within 60 seconds of total data loss
- Health checks execute every 6 seconds with <1% failure rate

**Performance Requirements**:
- Failover completed in <30 seconds (95th percentile)
- Failback completed in <60 seconds (95th percentile)
- Quote staleness <60 seconds during backup operation
- System uptime >99.9% (including failover capability)

**Business Impact**:
- Maintain 99% of trading performance during provider outages
- Reduce market data downtime from 43 hours/year to <4 hours/year
- Prevent >$10,000 in opportunity losses annually
- Zero regulatory violations from trading on stale data

## 8.0 Consequences

### 8.1 Positive Consequences

**Resilience**:
- 10× improvement in data availability (99% → 99.9%)
- Continuous position monitoring during infrastructure failures
- Graceful degradation instead of hard failures

**Risk Management**:
- Circuit breaker protection against blind trading
- Cached data fallback for defensive monitoring
- Audit trail for all failover events

**Cost Efficiency**:
- Zero marginal cost for normal operations (free-tier backups)
- Avoided opportunity losses far exceed implementation costs
- Flexible upgrade path to paid tiers if needed

### 8.2 Negative Consequences

**Complexity**:
- `MarketAnalysisAgent` becomes more complex (multi-provider logic)
- Additional configuration surface area in `config/risk.yaml`
- Integration testing requires simulating provider failures

**Operational Overhead**:
- Monitoring three data provider relationships
- API key rotation for multiple services
- Quarterly review of failover strategy effectiveness

**Data Quality Trade-offs**:
- Tier 2/3 providers deliver delayed quotes (15-min on free tier)
- Potential quote discrepancies between providers
- Greeks calculations less accurate with stale underlying data

### 8.3 Migration Impact

**No Breaking Changes**:
- Existing `MarketAnalysisAgent` interface unchanged
- Other agents continue querying for market data normally
- Failover logic transparent to downstream consumers

**Configuration Migration**:
- Add `market_data_failover` section to `config/risk.yaml`
- Provide Alpha Vantage and Finnhub API keys via Google Secret Manager
- Update monitoring dashboards for new health metrics

**Backward Compatibility**:
- Failover disabled by default (`enable_auto_failover: false` in config)
- Manual activation after production validation
- Rollback via configuration change (no code deployment required)

## 9.0 Alternatives Considered

### 9.1 Single Provider Only (Status Quo)

**Description**: Continue relying exclusively on Interactive Brokers Gateway with no failover capability.

**Pros**:
- Simplest implementation (no additional code)
- Zero integration complexity
- No backup provider costs

**Cons**:
- Single point of failure for critical market data
- Trading halt during IB Gateway outages (historical: ~43 hours/year)
- Regulatory risk from trading on stale/unavailable data
- Lost opportunity cost: 15% of potential trades missed

**Reason for Rejection**: Unacceptable operational risk. Market data availability is critical infrastructure that requires redundancy.

### 9.2 Peer-to-Peer Data Sharing

**Description**: Deploy multiple IB Gateway instances across different network paths and share data between them via Redis.

**Pros**:
- Consistent data source (all IB quotes)
- No third-party provider dependencies
- Maintains real-time data quality

**Cons**:
- Requires multiple IB accounts (capital duplication)
- IB-wide outages affect all instances simultaneously
- Complex network topology and failover logic
- Limited redundancy (single provider infrastructure)

**Reason for Rejection**: High complexity with limited benefit. Does not protect against IB-wide service disruptions, which are the primary failure mode.

### 9.3 Premium Multi-Provider Aggregator (e.g., Bloomberg, Refinitiv)

**Description**: Use enterprise-grade market data aggregator with built-in redundancy.

**Pros**:
- Institutional-quality data reliability
- Built-in failover and data validation
- Comprehensive asset coverage

**Cons**:
- Prohibitive cost: $2,000-10,000/month
- Overkill for current trading volume
- Complex integration requirements
- Vendor lock-in

**Reason for Rejection**: Cost/benefit ratio unfavorable for system scale. Current three-tier strategy delivers 90% of reliability at <5% of cost.

### 9.4 WebSocket-Based Real-Time Backups

**Description**: Implement WebSocket connections to real-time providers (e.g., Polygon.io, Alpaca) as backup.

**Pros**:
- True real-time backup data (no delays)
- WebSocket efficiency for streaming quotes
- Modern API architecture

**Cons**:
- Requires paid subscriptions ($200-500/month)
- Additional WebSocket infrastructure complexity
- Increased operational monitoring surface
- Still requires three-tier cascade logic

**Reason for Rejection**: Current free-tier strategy adequate for failover scenarios. Can be reconsidered if IB outages exceed 20 hours/month, making paid backup subscriptions cost-effective.
