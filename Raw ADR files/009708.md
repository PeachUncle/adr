# 001. Use Domain-Driven Design (DDD) Architecture

**Date:** 2024-11-15

**Status:** ✅ **Accepted**

## Context

The TaskList application started as a monolithic CRUD app with business logic scattered throughout React components and Express handlers.
As complexity grew, adding features became error-prone and difficult to test.
We needed clear separation of concerns and a scalable architecture that could accommodate growing complexity.

## Decision

Adopt Domain-Driven Design with a four-layer architecture:

1. **Domain Layer** (`packages/tasks/domain/`) – Pure business logic, entities, aggregates, value objects
2. **Application Layer** (`packages/tasks/application/`) – Use cases, orchestration, DTOs, mappers
3. **Infrastructure Layer** (`packages/tasks/infrastructure/`) – Database, repositories, external services
4. **Presentation Layer** (`apps/web/src/presentation/`, `apps/api/src/`) – UI components, API controllers, views

### Layer Dependencies

```
Presentation → Application → Domain
Presentation → Infrastructure
Infrastructure → Domain
Application → Domain, Infrastructure
```

**Key Rules:**
- Domain layer has **zero** external dependencies (pure business logic)
- Infrastructure layer can depend on Domain and Application
- Presentation layer orchestrates through Application layer (use cases)
- No business logic in Presentation or Infrastructure layers

## Rationale

### Why DDD?

- **Testability**: Domain logic has zero external dependencies, making it trivial to test
- **Maintainability**: Clear boundaries between layers prevent logic from leaking
- **Reusability**: Domain and Application layers can be shared between frontend and backend
- **Scalability**: Adding new features doesn't require understanding the entire codebase
- **Knowledge**: Team members can work on specific layers independently
- **Onboarding**: New developers can understand specific areas in isolation

### Trade-offs

- **Upside**: Better architecture, clearer code, easier testing
- **Downside**: More boilerplate (use cases, mappers, DTOs), initial learning curve

## Alternatives Considered

1. **Feature-based structure**: Organize code by features (e.g., `/tasks`, `/users`)
   - ❌ Doesn't scale; business logic becomes mixed with infrastructure
   
2. **Layered by technology**: Organize by technology (e.g., `/components`, `/api`, `/database`)
   - ❌ High cognitive load; business logic scattered across layers
   
3. **No architecture**: Keep current ad-hoc structure with minimal organization
   - ❌ Becomes unmaintainable as codebase grows

## Consequences

### Positive

- ✅ Domain logic is isolated and fully testable
- ✅ Clear dependency graph visible in directory structure
- ✅ Easier to extend features without breaking existing logic
- ✅ New team members can understand layers in isolation
- ✅ Reduced coupling between components
- ✅ Business rules documented in entity/aggregate methods

### Negative

- ❌ More boilerplate code (use cases, mappers, value objects)
- ❌ Initial learning curve for team unfamiliar with DDD
- ❌ More files to navigate (but clearer organization)
- ❌ Requires discipline to maintain layer boundaries
