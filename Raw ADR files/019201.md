# ADR-004: MassTransit for Event-Driven Communication

## Status

Accepted

## Context

With per-module DbContexts (ADR-003), modules cannot directly query each other's data. We need a mechanism for cross-module communication and data synchronization. Several options exist:

1. **Direct Method Calls**: Modules call each other's services directly
2. **In-Memory Event Bus**: Simple pub/sub within the application
3. **Message Queue**: External message broker (RabbitMQ, Azure Service Bus)
4. **Database as Queue**: Use database tables for messaging
5. **MassTransit with SQL Transport**: Messaging framework using PostgreSQL as transport

Key requirements:
1. **Eventual Consistency**: User profile changes must sync to Artist module
2. **Reliability**: Messages must not be lost
3. **Simplicity**: Don't want to manage external message brokers
4. **Observability**: Need to track message flow and failures
5. **Future Flexibility**: May want to switch to RabbitMQ or Azure Service Bus later
6. **Learning Value**: Want to learn event-driven architecture patterns

The key tension is between simplicity (in-memory events) versus reliability and future flexibility (external message broker).

## Decision

We will use **MassTransit with PostgreSQL SQL Transport**:

1. **MassTransit Framework**: Industry-standard .NET messaging framework
2. **PostgreSQL Transport**: Uses existing PostgreSQL database as message transport
3. **Integration Events**: Define events in Shared.Domain for cross-module communication
4. **Event Consumers**: Each module implements consumers for events it cares about
5. **Automatic Retry**: MassTransit handles retries and error queues
6. **Fault Handling**: Custom fault consumers send email alerts on failures
7. **Observability**: Built-in OpenTelemetry integration for tracing

Example event flow:
```
User updates profile → UserProfileUpdatedEvent published
→ MassTransit stores in PostgreSQL
→ ArtistModule consumer receives event
→ Updates denormalized user data in Artist entity
```

## Consequences

### Positive

- **Reliable Messaging**: Messages persisted in database, not lost on application restart
- **No External Dependencies**: Uses existing PostgreSQL, no RabbitMQ or Azure Service Bus needed
- **Automatic Retries**: MassTransit handles retry logic with exponential backoff
- **Error Handling**: Dead letter queues and fault consumers for failed messages
- **Observability**: Built-in metrics, tracing, and logging
- **Future Flexibility**: Can switch to RabbitMQ or Azure Service Bus by changing configuration
- **Industry Standard**: MassTransit is widely used, good documentation and community
- **Eventual Consistency**: Enables proper event-driven architecture patterns
- **Module Decoupling**: Modules don't need direct references to each other

### Negative

- **Complexity**: More complex than simple method calls or in-memory events
- **Learning Curve**: Need to understand messaging patterns, consumers, sagas
- **Eventual Consistency**: Data may be temporarily out of sync
- **Debugging Difficulty**: Harder to trace message flow compared to synchronous calls
- **Database Load**: Message tables add load to PostgreSQL
- **Message Schema Evolution**: Need to handle event schema changes carefully
- **Testing Complexity**: Need to test async message handling

### Neutral

- **Performance**: Async messaging adds latency but improves throughput
- **Transaction Boundaries**: Messages published after transaction commits (outbox pattern)
- **Message Ordering**: Not guaranteed unless explicitly configured

## Notes

MassTransit with SQL Transport provides a good balance: reliable messaging without operational complexity of external brokers. The PostgreSQL transport is production-ready and used by many companies.

Key patterns implemented:
- **Integration Events**: Events that cross module boundaries
- **Event Consumers**: Handlers that process events
- **Fault Consumers**: Handle failed message processing
- **Outbox Pattern**: Ensures messages published reliably with database transactions

Example consumer:
```csharp
public class UserProfileUpdatedConsumer : IConsumer<UserProfileUpdatedEvent>
{
    public async Task Consume(ConsumeContext<UserProfileUpdatedEvent> context)
    {
        var evt = context.Message;
        // Update artist entity with new user data
    }
}
```

This decision could be reconsidered if:
- PostgreSQL becomes a bottleneck for messaging
- Need advanced messaging features (priority queues, delayed messages)
- Want to separate message storage from application database
- Scale requires dedicated message broker
