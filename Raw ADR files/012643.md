# ADR-2: API Structure for Recipe Management

## Status
Accepted

## Date
2025-03-16

## Context
The Recipe Management System deals with a complex domain model consisting of multiple related entities:

- Recipe (core entity with basic information)
- RecipeIngredient (ingredients with amounts and measurements)
- RecipeStep (cooking instructions)
- RecipeTag (categorization tags)
- NutritionalValue (nutritional information)
- RecipeImage (photos of the recipe)
- MealPlan (collection of recipes for meal planning)

A key architectural challenge is determining the appropriate API structure that balances:
- Frontend requirements for efficient data loading
- Backend maintainability and performance
- Support for multiple creation/update patterns
- Caching and optimization opportunities
- Future extensibility

The recipe domain is particularly challenging because a single "recipe" from a user perspective is composed of multiple database entities, but users expect to interact with it as a cohesive whole.

## Decision
We will implement a hybrid API approach with three complementary patterns:

1. **Entity-Based REST Endpoints** - Standard CRUD operations for individual entities
2. **Composite Endpoints** - Aggregated data for common UI scenarios
3. **Draft-Based Creation Flow** - Multi-step creation with persistent state

### 1. Entity-Based REST Endpoints

Standard REST endpoints mapping directly to domain entities:

```
GET /api/recipes                    # List recipes
GET /api/recipes/{id}               # Get basic recipe info
POST /api/recipes                   # Create recipe (basic info)
PUT /api/recipes/{id}               # Update recipe (basic info)
DELETE /api/recipes/{id}            # Delete recipe

GET /api/recipes/{id}/ingredients   # Get ingredients for recipe
POST /api/recipes/{id}/ingredients  # Add ingredients
PUT /api/recipes/{id}/ingredients/{ing_id} # Update specific ingredient
DELETE /api/recipes/{id}/ingredients/{ing_id} # Remove ingredient

# Similar patterns for steps, tags, etc.
```

### 2. Composite Endpoints

Additional endpoints that aggregate data for common UI scenarios:

```
GET /api/recipes/{id}/full          # Get recipe with all related data
GET /api/recipes/{id}/cooking-view  # Get data optimized for cooking mode
GET /api/recipes/search             # Advanced search with related data
```

### 3. Draft-Based Creation Flow

Support for multi-step creation with server-side state:

```
POST /api/recipes/drafts            # Create draft recipe
GET /api/recipes/drafts/{id}        # Get draft recipe
PUT /api/recipes/drafts/{id}        # Update draft recipe basic info

PUT /api/recipes/drafts/{id}/ingredients # Update draft ingredients
PUT /api/recipes/drafts/{id}/steps  # Update draft steps

POST /api/recipes/drafts/{id}/finalize # Finalize draft to create actual recipe
DELETE /api/recipes/drafts/{id}     # Discard draft
```

## Alternatives Considered

### 1. Pure Entity-Based API

A strictly RESTful approach mapping directly to database entities.

**Pros:**
- Simple, one-to-one mapping with database structure
- Clear separation of concerns
- Fine-grained control over data fetching
- Easy to implement CRUD operations
- Better cache control for individual entities

**Cons:**
- Requires multiple requests to load a complete recipe
- Higher network overhead
- Frontend needs to stitch data together
- More complex state management on the frontend
- Potential for race conditions

### 2. Pure Composite API

All endpoints return fully composed data structures.

**Pros:**
- Single request loads all data needed for a page
- Simplified frontend state management
- Reduced network overhead
- Frontend doesn't need to coordinate multiple requests

**Cons:**
- Less granular caching
- Over-fetching data for simple operations
- Backend complexity in aggregating data
- Potentially longer response times
- Less RESTful

### 3. GraphQL API

Implement a GraphQL server for flexible data fetching.

**Pros:**
- Clients can request exactly what they need
- Single request with flexible data selection
- Reduces over-fetching and under-fetching
- Self-documenting API schema
- Built-in tooling for introspection

**Cons:**
- More complex to implement on the backend
- Learning curve for teams new to GraphQL
- Requires additional tooling
- Potentially more difficult to optimize specific queries
- Caching more complex than REST

### 4. CQRS Pattern

Separate read and write models completely.

**Pros:**
- Read models optimized for specific views
- Write models focus on data integrity
- Better performance for frequently accessed data
- Clear separation between reads and writes

**Cons:**
- More complex architecture
- Potential data consistency challenges
- More endpoints to maintain
- Increased development complexity
- Steeper learning curve

### 5. BFF Pattern (Backend for Frontend)

Create specialized API layers for different frontend clients.

**Pros:**
- Tailored to specific frontend needs
- Reduces data transformation on the client
- Can aggregate data from multiple services
- Better performance for specific clients

**Cons:**
- Duplicated logic across BFFs
- More backend services to maintain
- Potential for inconsistency between clients
- Higher maintenance cost

## Rationale

The hybrid approach we've chosen combines the strengths of multiple patterns while mitigating their weaknesses:

1. **Entity-based endpoints** provide the foundation for fine-grained operations and clear separation of concerns. They align well with database structure and enable efficient caching of individual entities.

2. **Composite endpoints** address the common UI scenario of loading a complete recipe with all its components in a single request, improving frontend performance and simplifying state management.

3. **Draft-based creation** solves the multi-step form problem by maintaining server-side state during the creation process, enabling users to save progress and continue later.

This approach balances several key considerations:

- **Performance**: Composite endpoints reduce network overhead for common scenarios
- **Flexibility**: Entity endpoints enable fine-grained updates when needed
- **User Experience**: Draft pattern supports multi-step creation with persistence
- **Maintainability**: Clear separation between entity operations and aggregated views
- **Future-proofing**: The architecture can evolve to include more specialized endpoints as needed

The decision specifically avoids the complexity of GraphQL or CQRS while still addressing the key requirements. It also avoids the duplication inherent in the BFF pattern while still providing optimized data access for the primary frontend.

## Consequences

### Positive
- Better user experience with fewer network requests for common scenarios
- Efficient handling of multi-step forms with server-side state
- Clear API structure that maps well to both database and UI needs
- Good caching opportunities at multiple levels
- Scalable approach as the application grows

### Negative
- More endpoints to maintain compared to a pure REST or GraphQL approach
- Some duplication between entity endpoints and composite endpoints
- Additional complexity in backend implementation
- Potential for data inconsistency if not carefully managed

### Neutral
- Need for client-side logic to choose appropriate endpoints
- Backend must manage draft state cleanup
- Documentation must clearly explain the different endpoint types

## Implementation Plan

1. **Phase 1**: Implement core entity-based REST endpoints
   - Recipe CRUD
   - Recipe component operations (ingredients, steps, etc.)
   - Basic filtering and pagination

2. **Phase 2**: Add composite endpoints
   - Full recipe view
   - Cooking mode view
   - Advanced search capabilities

3. **Phase 3**: Implement draft pattern
   - Draft creation and management
   - Multi-step saving
   - Finalization process

4. **Phase 4**: Optimization
   - Caching strategy
   - Performance improvements
   - Additional specialized endpoints based on usage patterns
