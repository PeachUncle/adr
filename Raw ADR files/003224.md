# Debounced Supabase Realtime Invalidation

**Status:** Accepted
**Date:** 2025-12-07
**Deciders:** Development Team
**Technical Story:** Fix for modal double-click close issue caused by rapid Supabase realtime updates

---

## Context

When using Supabase Realtime with React Query, database changes trigger immediate cache invalidation and data refetching. In high-frequency update scenarios (e.g., multiple users making changes, batch operations), this caused:

1. **UI Flickering**: Constant re-renders from rapid state updates
2. **Modal Race Conditions**: When closing a modal, realtime updates would overwrite the "closed" state before React finished processing, requiring users to click the close button twice
3. **Excessive Network Requests**: Each realtime event triggered a full refetch

## Decision

We implemented **300ms debouncing** in the `useRealtimeInvalidation()` hook:

```typescript
// DEBOUNCE: Coalesce multiple rapid updates into a single invalidation
let debounceTimer: NodeJS.Timeout | null = null;
let pendingRequestIds: Set<string> = new Set();

const debouncedInvalidate = () => {
  if (debounceTimer) clearTimeout(debounceTimer);
  
  debounceTimer = setTimeout(() => {
    queryClient.invalidateQueries({ queryKey: ['requests'], exact: false });
    pendingRequestIds.forEach(requestId => {
      queryClient.invalidateQueries({ queryKey: ['request', requestId] });
    });
    pendingRequestIds = new Set();
  }, 300);
};
```

## Consequences

### Positive
- **Eliminates flickering**: Multiple rapid events are coalesced into one update
- **Fixes modal race condition**: 300ms gap prevents state overwrites during close animations
- **Reduces network traffic**: Fewer refetch requests during batch operations
- **Maintains realtime feel**: 300ms delay is imperceptible for most users

### Negative
- **Slight delay**: Updates appear 300ms after database change (acceptable trade-off)
- **Complexity**: Requires cleanup of debounce timer on unmount

### Risks
- **Critical updates delayed**: For truly time-sensitive data, the 300ms delay might be noticeable
- **Timer leaks**: Must ensure proper cleanup in useEffect return function

### Implementation Location
- `packages/frontend/src/hooks/useSupabaseRealtimeV3.ts` - `useRealtimeInvalidation()` debounce
- `packages/frontend/src/features/requests/components/Dashboard.tsx` - `handleCloseModal()` hash-only

### Complete Solution

The full fix required **two changes**:

1. **Debounced realtime invalidation** (300ms) - prevents rapid re-renders
2. **Hash-only close handler** - `handleCloseModal` now only sets `window.location.hash = '#/dashboard'`. The `hashchange` event listener in `useEffect` handles the React state update (`setSelectedRequest(null)`), mirroring native anchor link behavior.

```typescript
// packages/frontend/src/features/requests/components/Dashboard.tsx

// ❌ BEFORE: Direct state update + hash change caused race conditions
const handleCloseModal = () => {
  setSelectedRequest(null);  // Gets overwritten by realtime before React finishes
  window.location.hash = '#/dashboard';
};

// ✅ AFTER: Only change hash, let hashchange listener update state
const handleCloseModal = () => {
  window.location.hash = '#/dashboard';
  // The useEffect hashchange listener calls setSelectedRequest(null)
};

// The hashchange listener in useEffect handles state updates
useEffect(() => {
  const checkHash = () => {
    const hash = window.location.hash || '';
    if (hash.startsWith('#/requests/')) {
      // Open modal for the request ID in hash
      const id = hash.split('/')[2];
      const found = allRequestsRef.current.find(r => r.id === id);
      if (found) setSelectedRequest(found);
    } else {
      // Hash is not a request hash - close modal
      setSelectedRequest(null);
    }
  };
  
  window.addEventListener('hashchange', checkHash);
  return () => window.removeEventListener('hashchange', checkHash);
}, []);
```

This pattern ensures consistent behavior between programmatic close and native navigation.
