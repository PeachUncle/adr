# ADR 0010: Minimal High Availability for POC

## Status
Accepted

## Date
2025-09-10

## Context
The enterprise architecture specifies comprehensive high availability design including:

- **Multi-Availability Zone Deployment**: AKS node pools distributed across 3 availability zones
- **Auto-scaling**: Horizontal Pod Autoscaler (HPA), Vertical Pod Autoscaler (VPA), and Cluster Autoscaler
- **Load Balancing**: Azure Load Balancer Standard with zone redundancy
- **Database High Availability**: Azure SQL Database with zone-redundant configuration
- **Storage Redundancy**: Zone-redundant storage (ZRS) for persistent volumes
- **Application Gateway**: Zone-redundant Application Gateway for traffic distribution
- **Backup Strategy**: Automated backup with geo-redundant storage

This enterprise HA configuration provides 99.95%+ availability but increases costs significantly (~40-60%) and adds operational complexity.

## Decision
We will implement **minimal high availability** that provides reasonable resilience for a POC environment while optimizing for cost and simplicity.

### POC High Availability Implementation:

| Component | Enterprise HA | POC HA | Cost Impact | Availability Impact |
|-----------|---------------|--------|-------------|-------------------|
| AKS Nodes | 3-AZ, multi-node pools | Single zone, 2 nodes | -60% cost | 99.5% vs 99.95% |
| Database | Zone-redundant SQL | Basic SQL with backup | -80% cost | 99.5% vs 99.99% |
| Storage | Zone-redundant storage | Locally redundant storage | -50% cost | 99.9% vs 99.99% |
| Load Balancer | Standard LB zone-redundant | Basic LB single zone | -70% cost | 99.9% vs 99.99% |
| Auto-scaling | HPA + VPA + CA | HPA only | No cost difference | Manual scaling required |

**Estimated Availability: 99.5% (4.5 hours downtime/month) vs Enterprise: 99.95% (22 minutes/month)**

## Consequences

### Positive
- **Cost Optimization**: 50-70% reduction in infrastructure costs
- **Simplified Operations**: Reduced complexity for learning environment
- **Adequate Resilience**: Sufficient availability for development and testing
- **Learning Focus**: Emphasis on AKS patterns rather than HA complexity

### Negative
- **Single Point of Failure**: Availability zone failure affects entire environment
- **Manual Recovery**: Increased manual intervention for certain failure scenarios
- **Limited Auto-scaling**: Manual intervention required for capacity management
- **Extended Downtime**: Longer recovery times for certain failure modes

### Neutral
- **HA Patterns Preserved**: Core availability patterns maintained for future scaling
- **Architecture Consistency**: HA design principles applicable to enterprise scale

## Rationale
For a POC environment used for learning and development, occasional downtime is acceptable. The focus is on understanding AKS availability patterns and implementing basic resilience measures that can scale to enterprise requirements.

## Implementation Details

### AKS Cluster Configuration
```yaml
# Single availability zone deployment
node_pools:
  system_pool:
    vm_size: "Standard_B2s"
    node_count: 2
    availability_zones: ["1"]  # Single zone to reduce cost
    
  user_pool:
    vm_size: "Standard_B2s"
    node_count: 1
    min_count: 1
    max_count: 3
    availability_zones: ["1"]
```

### Application Resilience
```yaml
# Pod-level resilience configuration
deployment:
  replicas: 2  # Minimum for basic redundancy
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1
      
  resources:
    requests:
      cpu: 100m
      memory: 128Mi
    limits:
      cpu: 500m
      memory: 512Mi
      
  readinessProbe:
    httpGet:
      path: /health
      port: 3000
    initialDelaySeconds: 10
    periodSeconds: 5
    
  livenessProbe:
    httpGet:
      path: /health
      port: 3000
    initialDelaySeconds: 30
    periodSeconds: 10
```

### Auto-scaling Configuration
```yaml
# Horizontal Pod Autoscaler only
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-service
  minReplicas: 2
  maxReplicas: 5
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```

### Database Resilience
- **Azure SQL Basic**: Single database instance with automated backup
- **Backup Schedule**: Daily automated backup with 7-day retention
- **Recovery Strategy**: Point-in-time recovery within backup retention window
- **Monitoring**: Basic availability monitoring with alerts

### Storage Strategy
- **Persistent Volumes**: Locally redundant storage (LRS) for cost optimization
- **Backup Strategy**: Application-level backup for critical data
- **Recovery Process**: Manual recovery from backup if storage failure occurs

## Accepted Risks
The following availability risks are explicitly accepted for the POC:

1. **Availability Zone Failure**: 4-6 hour recovery time if AZ-1 fails
2. **Node Failure**: Temporary service interruption during node replacement
3. **Storage Failure**: Data recovery required from backup
4. **Manual Scaling**: Manual intervention required for capacity issues
5. **Extended Maintenance**: Longer maintenance windows due to single-zone deployment

These risks are acceptable for a non-production learning environment.

## Monitoring and Alerting
```yaml
# Basic availability monitoring
alerts:
  - name: "Pod Unavailable"
    condition: "available_replicas < desired_replicas"
    duration: "5m"
    
  - name: "Node Not Ready"
    condition: "node_status != Ready"
    duration: "2m"
    
  - name: "Database Connection Failed"
    condition: "database_connection_failure"
    duration: "1m"
    
  - name: "Service Endpoint Down"
    condition: "http_probe_success != 1"
    duration: "3m"
```

## Upgrade Strategy
When transitioning to staging/production:

1. **Phase 1**: Multi-availability zone node pools
2. **Phase 2**: Zone-redundant database configuration
3. **Phase 3**: Cluster Autoscaler and VPA implementation
4. **Phase 4**: Advanced load balancing and traffic management

## Alternative Options Considered
1. **Single Node Deployment**: Rejected due to no redundancy
2. **Full Enterprise HA**: Rejected due to cost and complexity
3. **Minimal HA**: Selected option balancing availability and cost
