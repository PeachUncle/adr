# Decision: Workflow Refinements - Dev Docs System and Build Checking Hooks

Date: 2025-11-17

## Context

After implementing ADR 0009's Claude Code native workflow (skills, backlog, reassess commands), we analyzed a production workflow from a developer who successfully rewrote 300k LOC solo over 6 months using Claude Code. Their approach, detailed in a Reddit post (https://www.reddit.com/r/ClaudeAI/comments/1oivjvm/claude_code_is_a_beast_tips_from_6_months_of/), revealed several critical gaps in our implementation:

**Problems with our current implementation:**
1. **TodoWrite is ephemeral** - Disappears on context compaction, causing "lost plot" issues on long tasks
2. **No build verification** - Claude can leave TypeScript errors undetected for hours
3. **Skills don't reliably auto-activate** - Depends on Claude's judgment rather than guaranteed triggers
4. **No persistent task context** - After context reset, all task knowledge is lost
5. **Hooks are cosmetic** - Current `.sh` hook just warns, doesn't enforce quality

**What the Reddit workflow achieved:**
- 300k+ LOC rewritten solo in 6 months
- Zero errors left behind (#NoMessLeftBehind philosophy)
- Consistent code quality across massive codebase
- Tasks survived context compactions without losing direction
- Skills actually activated when needed

## Approach

### Phase 1: Dev Docs System (Highest Priority)

Replace ephemeral TodoWrite with persistent dev docs filesystem:

```
~/dev/active/[task-name]/
├── [task-name]-plan.md      # The approved plan from planning phase
├── [task-name]-context.md   # Key files, decisions, integration points
└── [task-name]-tasks.md     # Checklist of implementation tasks
```

**Integration with existing workflow:**

1. **Planning Phase** (existing `/backlog select N`):
   - Runs strategic-plan-architect or uses Plan Mode
   - Creates dev docs directory automatically
   - Generates all three files with comprehensive details

2. **During Implementation**:
   - Claude references dev docs for current task context
   - Updates `tasks.md` as work progresses (checkboxes)
   - Updates `context.md` when discovering important details
   - Updates `Last Updated` timestamps

3. **Before Context Compaction**:
   - New slash command: `/update-dev-docs`
   - Claude reviews progress, updates all three files
   - Notes next steps in context.md
   - After compaction, just say "continue" - Claude reads dev docs and resumes

4. **Task Completion**:
   - Move directory to `~/dev/completed/[task-name]/`
   - Archive for future reference

**New Slash Commands:**
- `/create-dev-docs` - Convert approved plan to dev docs files (called automatically by backlog)
- `/update-dev-docs` - Update dev docs before compaction with current progress
- `/resume-task [task-name]` - Read dev docs and continue work after break

### Phase 2: Build Checking Hook (Error Prevention)

Replace cosmetic warning hook with functional build checker:

**Hook: Stop Event (runs when Claude finishes responding)**

TypeScript/JavaScript implementation that:

1. **Tracks File Edits:**
   - Monitors which files were modified during response
   - Identifies which repo/package each file belongs to
   - Maintains edit log with timestamps

2. **Runs Build Scripts:**
   - After Claude finishes, runs build/typecheck on affected repos
   - Uses appropriate script: `pnpm build`, `pnpm typecheck`, `npm run build`
   - Configurable per-repo in `.claude/build-config.json`

3. **Error Reporting:**
   - If < 5 errors: Shows errors to Claude immediately
   - If ≥ 5 errors: Recommends launching auto-error-resolver agent
   - Logs all errors for debugging
   - Claude fixes errors before moving to next task

4. **Configuration:**
```json
{
  "api": {
    "buildCommand": "pnpm build",
    "errorThreshold": 5
  },
  "web": {
    "buildCommand": "pnpm typecheck",
    "errorThreshold": 5
  }
}
```

**Remove:**
- Current `.claude/hooks/pre-edit-approval.sh` (redundant warning)
- PreToolUse hook registration in settings.local.json

### Phase 3: Skills Auto-Activation System (Future Enhancement)

**Not implementing immediately** due to complexity, but documented for future:

The Reddit user's approach uses TypeScript hooks with `skill-rules.json`:

**UserPromptSubmit Hook** (runs BEFORE Claude sees prompt):
- Analyzes user prompt for keywords, intent patterns, file paths
- Checks `skill-rules.json` for matching triggers
- Injects skill activation reminder into Claude's context
- Example: "🎯 SKILL ACTIVATION CHECK - Use backend-dev-guidelines skill"

**Stop Event Hook** (runs AFTER Claude responds):
- Analyzes edited files for risky patterns (try-catch, database ops, async)
- Shows gentle self-check reminder
- "Did you add error handling? Are Prisma operations using repository pattern?"
- Non-blocking awareness nudges

**skill-rules.json Example:**
```json
{
  "backend-dev-guidelines": {
    "type": "domain",
    "priority": "high",
    "promptTriggers": {
      "keywords": ["backend", "controller", "service", "API"],
      "intentPatterns": ["(create|add).*?(route|endpoint|controller)"]
    },
    "fileTriggers": {
      "pathPatterns": ["backend/src/**/*.ts"],
      "contentPatterns": ["router\\.", "export.*Controller"]
    }
  }
}
```

**Why defer this:**
- Requires TypeScript hooks (more complex than bash)
- Need to validate Phase 1 & 2 provide sufficient value first
- Can add later if skill activation remains unreliable

## Options Considered

### Option A: Full Adoption of Reddit Workflow
- Implement all three phases immediately
- Dev docs + build hooks + skills auto-activation
- Most comprehensive but highest complexity
- Risk: Over-engineering before validating need

### Option B: Hybrid Approach (CHOSEN)
- Phase 1: Dev docs system (addresses biggest pain point)
- Phase 2: Build checking hooks (addresses quality issues)
- Phase 3: Defer skills auto-activation (current approach may be sufficient)
- Balanced pragmatism - add proven patterns, defer speculative ones

### Option C: Minimal Changes
- Keep current implementation unchanged
- Only document Reddit workflow for future reference
- Rejected: Current gaps (ephemeral TodoWrite, no error checking) are real problems

## Decision Rationale

**Why Hybrid Approach:**

1. **Dev Docs System is Critical:**
   - TodoWrite's ephemerality causes real "lost plot" issues
   - Persistent filesystem survives context compactions
   - Proven pattern from 300k LOC rewrite
   - Solves actual pain point we'd encounter

2. **Build Hooks Prevent Quality Regression:**
   - "No mess left behind" philosophy is compelling
   - TypeScript errors accumulating silently is dangerous
   - Automatic verification removes cognitive load
   - Stop hook is non-invasive (runs after response)

3. **Skills Auto-Activation Can Wait:**
   - Our current skill descriptions may activate reliably enough
   - UserPromptSubmit hook complexity is significant
   - Want to validate Phases 1 & 2 work well first
   - Can add if activation proves unreliable in practice

4. **Incremental Validation:**
   - Implement highest-value changes first
   - Validate they work in our context
   - Avoid over-engineering based on different project needs

## Trade-offs

**Benefits:**
- Persistent task context survives context resets
- Zero TypeScript errors left undetected
- Quality enforcement without friction
- Proven patterns from production usage
- Incremental implementation reduces risk

**Costs:**
- More setup complexity than current simple skill approach
- Filesystem-based dev docs require discipline to update
- Build hooks add overhead to every response (small delay)
- Need to create/maintain build-config.json
- More moving parts to understand and debug

**Impact:**
- Development workflow: Significantly more robust for long tasks
- Code quality: Automated verification catches errors immediately
- Context management: Persistent docs enable seamless task resumption
- Team onboarding: More concepts to learn (dev docs system, hooks)
- Extends ADR 0009's implementation with battle-tested refinements
- Related ADRs: Builds on ADR 0008 (adaptive workflow) and ADR 0009 (native features)

## Implementation Priority

**Immediate (Phase 1 & 2):**
1. Remove current ineffective `.sh` hook
2. Create dev docs directory structure
3. Update `/backlog` command to create dev docs automatically
4. Add `/update-dev-docs` and `/resume-task` commands
5. Implement Stop event hook for build checking
6. Create `.claude/build-config.json` template

**Future (Phase 3, if needed):**
- Evaluate skill activation reliability after 2-4 weeks
- If skills don't activate consistently, implement UserPromptSubmit hook
- Create `skill-rules.json` configuration system
- Add TypeScript hook for automated skill injection
