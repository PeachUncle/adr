# ADR-003: Per-Module DbContext

## Status

Accepted

## Context

In a modular monolith with Entity Framework Core, there are several approaches to organizing database access:

1. **Single Shared DbContext**: One DbContext with all entities from all modules
2. **Per-Module DbContext**: Each module has its own DbContext
3. **Per-Module Database**: Each module has its own physical database

For Trama, we need to balance:

1. **Module Isolation**: Modules should be independent and not directly access each other's data
2. **Shared Database**: Want to use database features like foreign keys and joins across modules
3. **Transaction Boundaries**: Need transactions within modules, but avoid distributed transactions
4. **Future Extraction**: Want the option to extract modules to separate services later
5. **Development Simplicity**: Don't want to manage multiple databases in development
6. **Query Performance**: Need efficient queries

The key tension is between strict module isolation versus practical database usage and performance.

## Decision

We will use **Per-Module DbContext with Shared Database**:

1. **One DbContext Per Module**: Each module (Users, Artists, Search) has its own DbContext class
2. **Shared PostgreSQL Database**: All DbContexts connect to the same database instance
3. **Module-Specific Tables**: Each DbContext only maps tables relevant to its module
4. **No Cross-Module Queries**: Modules cannot query other modules' tables directly through their DbContext
5. **Shared Interfaces for Cross-Module Access**: Use adapter pattern with shared interfaces for cross-module data needs
6. **BaseDbContext**: Common base class that disables EF migrations
7. **Independent Configurations**: Each module configures its own entity mappings

Example structure:
```
UsersDbContext → PostgreSQL (users, refresh_tokens tables)
ArtistsDbContext → PostgreSQL (artists, artworks, tags tables)
```

## Consequences

### Positive

- **Clear Module Boundaries**: Each module owns its data access, enforcing encapsulation
- **Independent Evolution**: Modules can evolve their data access patterns independently
- **Easier Testing**: Can mock or replace individual DbContexts for testing
- **Future Extraction Path**: Clear separation makes it easier to move to separate databases later
- **Focused Configurations**: Each module only configures entities it cares about
- **Reduced Coupling**: Modules can't accidentally query each other's tables
- **Better Organization**: Code organization mirrors domain boundaries

### Negative

- **No Direct Cross-Module Joins**: Can't write queries that join across module boundaries in EF
- **Adapter Pattern Overhead**: Need adapter classes to access data from other modules
- **Potential N+1 Queries**: Cross-module data access may require multiple queries
- **Shared Database Coupling**: Still coupled at database level (foreign keys, transactions)
- **Configuration Duplication**: Some configuration (connection strings, conventions) duplicated
- **Performance Trade-offs**: May need to denormalize data or use events to avoid cross-module queries

### Neutral

- **Transaction Boundaries**: Transactions work within a module, cross-module requires careful design
- **Migration Coordination**: Migrations from different modules must be coordinated
- **Connection Pooling**: All DbContexts share the same connection pool

## Notes

This approach provides a middle ground between a single shared DbContext (too coupled) and separate databases. It enforces module boundaries at the application level while keeping operational simplicity.

Key patterns used:
- **Adapter Pattern**: For cross-module data access (e.g., `IUserServiceAdapter` in Artists module)
- **Domain Events**: For cross-module communication (e.g., `UserProfileUpdatedEvent`)
- **Denormalization**: Store frequently accessed cross-module data locally (e.g., username in Artist entity)

Example of cross-module access:
```csharp
// Artists module needs user data
public interface IUserServiceAdapter
{
    Task<UserDto> GetUserAsync(Guid userId);
}

// Implemented in Users module
public class UserServiceAdapter : IUserServiceAdapter
{
    private readonly UsersDbContext _context;
    // Implementation uses UsersDbContext
}
```

This decision could be reconsidered if:
- Performance issues from lack of joins become severe
- Need to scale modules independently (move to separate databases)
- Adapter pattern overhead becomes too burdensome
