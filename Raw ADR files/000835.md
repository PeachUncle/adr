# ADR-001: Microservices Architecture for BahariWatch Platform

## Status
**Accepted** (October 7, 2025)

## Context

### Business Drivers
BahariWatch is a community-driven illegal fishing monitoring system for Kenya's coastal regions, designed to empower small-scale fishers and coastal communities as active guardians of marine resources. The system must support 10,000+ coastal users across multiple counties (Mombasa, Kilifi, Kwale, Lamu, Tana River) with real-time alert delivery (<5 seconds p95) and 99.5% availability for enforcement effectiveness.

**Stakeholder Requirements:**
- **Community Fishers (10,000+ users):** Simple mobile app for GPS-stamped photo submission, anonymous reporting capability, offline-first design for 2G/3G networks
- **Beach Management Units (BMUs):** Fast alert delivery (15-30 minute vessel response window), enforcement dashboard with hotspot visualization
- **Government Enforcement:** Legal evidence admissibility (7-year audit trail), secure data sharing, role-based access control
- **Research Team (Kabarak University):** KSh 59,500 total project budget, 6-month pilot timeline (May-October 2025), scalable architecture for national rollout

**Operational Reality:**
The BahariWatch system comprises **distinct functional areas with different operational characteristics** (Fundamentals of Software Architecture, Chapter 1 - Architecture is about structure and characteristics):

1. **Community Reporting (Write-Heavy):**
   - High write throughput: 500-1,000 reports/day during peak fishing seasons
   - Burst traffic: Offline mobile app syncs create 10-50 requests/second spikes
   - Elasticity requirement: Scale up during fishing seasons (April-July, November-January)
   - Fault tolerance: Report submission must work even if vessel matching is down

2. **Vessel Data Ingestion (Read-Heavy, External Integration):**
   - External API dependency: Global Fishing Watch API (50k daily rate limit per ADR-011)
   - Data volume: 500+ vessel tracks/day for Kenya EEZ
   - Caching requirement: 24-hour TTL for vessel identity data (low volatility)
   - Circuit breaker: Degrade gracefully during GFW API outages (per ADR-011)

3. **Spatial-Temporal Matching (CPU-Intensive):**
   - Complex PostGIS spatial queries: ST_DWithin, ST_Distance for 50km radius matching
   - Computational load: 5-15 seconds per report (GFW API query + PostGIS analysis)
   - Independent scalability: Peak load during report submission doesn't affect alerting
   - Fault isolation: Matching failures shouldn't crash report persistence

4. **Alerting & Notification (Notification-Heavy):**
   - Multi-channel delivery: SMS (Twilio/Africa's Talking), Email, Push notifications
   - Real-time requirement: <5 seconds from alert generation to enforcement officer
   - High availability: 99.5% uptime SLO (enforcement effectiveness depends on timely alerts)
   - Circuit breaker: Switch SMS providers on failure (per ADR-011)

5. **Geospatial Analytics (Query-Intensive):**
   - Hotspot generation: Real-time aggregation of reports for dashboard visualization
   - Historical analysis: 7-year retention for research and enforcement evidence
   - Read-heavy: 100-500 dashboard queries/day from enforcement officers
   - Separate scaling: Analytics load shouldn't impact report submission

6. **Survey & Analytics (Research-Focused):**
   - BMU evaluation: Survey responses for pilot study effectiveness measurement
   - Data export: CSV/Excel exports for research team at Kabarak University
   - Low volume: 50-100 survey responses/month
   - Batch processing: Acceptable latency (seconds to minutes)

### Technical Constraints
- **Budget Constraint:** KSh 59,500 total project cost limits infrastructure to $25-40/month (per ADR-012: DigitalOcean App Platform)
- **Timeline:** 6-month pilot (May-October 2025) requires rapid development with Django/Python (team expertise)
- **Mobile Connectivity:** 2G/3G intermittent networks require offline-first mobile app design
- **Legal Requirements:** 7-year audit trail for prosecution evidence (end-to-end encryption per ADR-008)
- **Data Sovereignty:** GDPR compliance for anonymous reporting, data residency in Kenya

### Architecture Characteristics Affected
(Reference: Fundamentals of Software Architecture, Chapters 4-6 - Architecture Characteristics Define Success Criteria)

**Critical (Top 3):**
1. **Availability (99.5% uptime SLO):** Enforcement effectiveness requires reliable report submission and alert delivery
2. **Performance (<5 seconds p95 alert delivery):** Vessel response window (15-30 minutes) demands fast alerts
3. **Scalability (10,000+ coastal users):** System must handle 500-1,000 reports/day with burst traffic spikes

**Important (Next 4):**
4. **Fault Tolerance:** Service failures (GFW API outage, SMS provider down) must not cascade
5. **Deployability:** 6-month pilot timeline requires independent service deployment (weekly releases)
6. **Testability:** Automated testing for legal evidence admissibility
7. **Security:** Anonymous reporting, end-to-end encryption, RBAC (per ADR-008)

**Relevant (Additional):**
8. **Maintainability:** 6-month pilot → potential national rollout requires clean service boundaries
9. **Elasticity:** Seasonal fishing patterns require auto-scaling (April-July, November-January)
10. **Observability:** Distributed tracing for debugging saga workflows (per ADR-010 fitness functions)

### Integration with Other ADRs
- **ADR-002 (Event-Driven Choreography):** Microservices communicate via RabbitMQ message broker (per ADR-015)
- **ADR-003 (Monolithic Database):** Logical schema separation per service (pragmatic starting point)
- **ADR-004 (Anthology Saga):** Report → Match → Alert workflow spans 3 services (eventual consistency per ADR-014)
- **ADR-008 (Security):** Each service enforces RBAC independently, JWT authentication via API Gateway
- **ADR-010 (Fitness Functions):** Automated governance for service coupling, schema violations
- **ADR-011 (External Integration):** Vessel Service owns GFW API integration with circuit breaker
- **ADR-012 (Deployment):** DigitalOcean App Platform PaaS deployment, independent service scaling

## Decision

**We will adopt a Microservices architectural style** for the BahariWatch platform. The system will be decomposed into **8 independently deployable services**, each representing an **architecture quantum** (Software Architecture: The Hard Parts, Chapter 2 - independently deployable unit with high functional cohesion and synchronous coupling).

### Complete Service Catalog

**Core Services (Event-Driven Workflow):**

1. **Report Service**
   - **Responsibility:** Manages community report submission and lifecycle (CRUD operations)
   - **Bounded Context:** Report aggregate (report_id, location, photo, timestamp, status)
   - **API Endpoints:** `POST /v1/reports`, `GET /v1/reports/{id}`, `PATCH /v1/reports/{id}/status`
   - **Events Published:** `ReportSubmitted` (v1), `ReportStatusChanged` (v1)
   - **Database Schema:** `reports`, `report_photos`, `report_status_history`
   - **Operational Profile:** Write-heavy (500-1,000 writes/day), burst traffic (10-50 req/sec)
   - **Scaling Target:** 1,000 requests/sec (10x pilot capacity for national rollout)
   - **SLO:** 99.5% availability, <500ms p95 response time for report submission

2. **Matching Service**
   - **Responsibility:** Correlates community reports with vessel tracks from GFW API
   - **Bounded Context:** Match aggregate (match_id, report_id, vessel_id, confidence_score)
   - **Events Consumed:** `ReportSubmitted` (v1)
   - **Events Published:** `MatchFound` (v1), `MatchNotFound` (v1)
   - **Database Schema:** `matches`, `vessel_cache` (24-hour TTL per ADR-011)
   - **External Dependencies:** GFW API (circuit breaker per ADR-011), PostGIS spatial queries
   - **Operational Profile:** CPU-intensive (5-15 seconds per report), moderate throughput (100-200 matches/day)
   - **Scaling Target:** 500 concurrent matching operations (PostGIS spatial queries)
   - **SLO:** <30 seconds p99 workflow completion (per ADR-014 eventual consistency window)

3. **Alert Service**
   - **Responsibility:** Generates and manages enforcement alerts based on high-confidence matches
   - **Bounded Context:** Alert aggregate (alert_id, match_id, severity, assigned_officer)
   - **Events Consumed:** `MatchFound` (v1)
   - **Events Published:** `AlertGenerated` (v1), `AlertAcknowledged` (v1)
   - **API Endpoints:** `GET /v1/alerts`, `POST /v1/alerts/{id}/acknowledge`, `GET /v1/alerts/hotspots`
   - **Database Schema:** `alerts`, `alert_assignments`, `alert_acknowledgments`
   - **Operational Profile:** Read-heavy (enforcement dashboard queries), moderate writes (50-100 alerts/day)
   - **Scaling Target:** 200 concurrent dashboard users (BMU officers, enforcement)
   - **SLO:** 99.5% availability, <2 seconds p95 response time for alert list

4. **Notification Service**
   - **Responsibility:** Multi-channel alert delivery (SMS, Email, Push notifications)
   - **Bounded Context:** Notification aggregate (notification_id, alert_id, channel, recipient, status)
   - **Events Consumed:** `AlertGenerated` (v1)
   - **Events Published:** `NotificationSent` (v1), `NotificationFailed` (v1)
   - **External Dependencies:** Twilio SMS (primary), Africa's Talking SMS (fallback), SendGrid Email
   - **Database Schema:** `notifications`, `notification_delivery_log`
   - **Operational Profile:** Notification-heavy (50-100 SMS/day, 20-50 emails/day), burst traffic during incidents
   - **Scaling Target:** 1,000 concurrent notifications (spike during major incident)
   - **SLO:** <5 seconds p95 SMS delivery (enforcement response window requirement)

**Supporting Services (User Management & Analytics):**

5. **User Service**
   - **Responsibility:** Authentication, authorization, user profile management
   - **Bounded Context:** User aggregate (user_id, role, profile, preferences)
   - **API Endpoints:** `POST /v1/auth/login`, `POST /v1/auth/register`, `GET /v1/users/{id}`, `PATCH /v1/users/{id}/profile`
   - **Database Schema:** `users`, `user_roles`, `user_sessions`, `device_fingerprints` (anonymous reporting)
   - **Operational Profile:** Low-moderate throughput (100-200 auth requests/day), session management
   - **Scaling Target:** 10,000 active users (national rollout)
   - **SLO:** 99.9% availability (authentication is critical path), <200ms p95 response time

6. **Geospatial Service**
   - **Responsibility:** Real-time hotspot generation, spatial aggregation, dashboard visualization
   - **Bounded Context:** Hotspot aggregate (hotspot_id, location, report_count, time_window)
   - **API Endpoints:** `GET /v1/hotspots`, `GET /v1/heatmap`, `GET /v1/reports/spatial-query`
   - **Database Schema:** `hotspots` (materialized view), `spatial_clusters` (PostGIS)
   - **Operational Profile:** Query-intensive (100-500 dashboard queries/day), read-heavy
   - **Scaling Target:** 200 concurrent dashboard users with real-time heatmap updates
   - **SLO:** <3 seconds p95 hotspot query response time

7. **Analytics Service**
   - **Responsibility:** BMU evaluation surveys, research data export, pilot study metrics
   - **Bounded Context:** Survey aggregate (survey_id, bmu_id, responses, metrics)
   - **API Endpoints:** `POST /v1/surveys`, `GET /v1/surveys/{id}/responses`, `GET /v1/exports/reports`
   - **Database Schema:** `surveys`, `survey_responses`, `bmu_performance_metrics`
   - **Operational Profile:** Low volume (50-100 surveys/month), batch processing acceptable
   - **Scaling Target:** 100 concurrent data export requests (research team)
   - **SLO:** <10 seconds p95 survey submission, <60 seconds CSV export generation

8. **Vessel Service**
   - **Responsibility:** GFW API integration, vessel track ingestion, vessel identity cache
   - **Bounded Context:** Vessel aggregate (vessel_id, mmsi, name, flag, last_position)
   - **API Endpoints:** `GET /v1/vessels/{id}`, `GET /v1/vessels/search`, `POST /v1/vessels/refresh-cache`
   - **External Dependencies:** GFW API (50k daily rate limit, circuit breaker per ADR-011)
   - **Database Schema:** `vessels`, `vessel_tracks`, `vessel_cache_metadata`
   - **Operational Profile:** Read-heavy (vessel identity lookups during matching), caching-heavy (24-hour TTL)
   - **Scaling Target:** 500 vessel lookups/day, 1,000 cache hits (95% cache hit rate)
   - **SLO:** <5 seconds p95 GFW API query (with circuit breaker fallback to stale cache)

## Rationale

### Alternatives Considered

**Alternative 1: Monolithic Architecture**
- **Description:** Single Django application with modular packages (reports, vessels, matching, alerts)
- **Pros:** Simpler deployment, no distributed system complexity, easier local development
- **Cons:**
  - **Scalability:** Can't scale CPU-intensive matching independently from write-heavy reporting
  - **Fault Isolation:** GFW API outage crashes entire system (no circuit breaker isolation)
  - **Deployability:** Updating matching algorithm requires full system redeployment (6-month pilot risk)
  - **Team Velocity:** Code conflicts during 6-month parallel development
- **Rejected Reason:** **Operational characteristics mismatch** - Monolith couples components with fundamentally different scaling needs (Fundamentals, Chapter 1 - architecture characteristics drive style choice)

**Alternative 2: Microservices with Synchronous HTTP Choreography**
- **Description:** Services communicate via direct RESTful API calls (no message broker)
- **Pros:** Simpler to understand (no async complexity), familiar HTTP patterns
- **Cons:**
  - **Temporal Coupling:** Report Service must wait for Matching Service response (5-15 seconds)
  - **Cascading Failures:** Matching Service downtime blocks report submission (violates 99.5% availability SLO)
  - **Performance:** Synchronous workflow adds 15-30 seconds to report submission (poor UX)
  - **Circuit Breaker Complexity:** Must implement circuit breakers for every service-to-service call
- **Rejected Reason:** **Availability trade-off** - Synchronous coupling violates fault isolation requirement (Hard Parts, Chapter 11 - choreography decouples temporal dependencies)

**Alternative 3: Function-as-a-Service (FaaS) Architecture**
- **Description:** AWS Lambda functions for each workflow step (report → match → alert)
- **Pros:** Extreme elasticity (auto-scale to zero), pay-per-invocation pricing
- **Cons:**
  - **Cost:** AWS Lambda + API Gateway exceeds $25-40/month budget (KSh 59,500 project cost)
  - **Cold Start:** 1-3 second cold start latency violates <5 second alert delivery SLO
  - **State Management:** Complex saga state machine requires DynamoDB Streams + Step Functions
  - **Local Development:** Requires LocalStack/SAM for offline testing (6-month timeline risk)
- **Rejected Reason:** **Budget constraint** - Serverless pricing model too expensive for pilot study (ADR-012 justifies DigitalOcean App Platform)

**Alternative 4: Service-Oriented Architecture (SOA) with Enterprise Service Bus (ESB)**
- **Description:** Centralized ESB (e.g., MuleSoft) for service orchestration, message routing, transformation
- **Pros:** Centralized governance, built-in monitoring, mature tooling
- **Cons:**
  - **Cost:** ESB licensing (MuleSoft $10k-50k/year) far exceeds KSh 59,500 project budget
  - **Operational Complexity:** ESB is single point of failure (violates 99.5% availability SLO)
  - **Coupling:** Centralized orchestration logic couples services (Hard Parts, Chapter 11 - anti-pattern for choreography)
  - **Latency:** ESB adds 50-200ms per message (violates <5 second alert delivery SLO)
- **Rejected Reason:** **Cost and availability trade-offs** - ESB too expensive and creates single point of failure

### Trade-Off Analysis

| Dimension | Microservices (Chosen) | Monolith | Sync Microservices | FaaS | SOA/ESB |
|-----------|------------------------|----------|-------------------|------|---------|
| **Availability (SLO: 99.5%)** | ✅ **High** (fault isolation per service) | ❌ Low (single failure point) | ⚠️ Medium (cascading failures) | ✅ High (AWS SLA 99.95%) | ❌ Low (ESB single point) |
| **Performance (<5s alert)** | ✅ **Fast** (async choreography) | ✅ Fast (in-process) | ❌ Slow (sync blocking 15-30s) | ⚠️ Medium (cold start 1-3s) | ❌ Slow (ESB overhead) |
| **Scalability (10k users)** | ✅ **Independent** (scale per service) | ⚠️ Medium (vertical scaling only) | ✅ Independent | ✅ Extreme (auto-scale) | ⚠️ Medium (ESB bottleneck) |
| **Deployability (weekly)** | ✅ **Independent** (per service) | ❌ Monolithic (full redeploy) | ✅ Independent | ✅ Atomic (per function) | ⚠️ Medium (ESB dependency) |
| **Cost ($25-40/mo)** | ✅ **Fits** (DigitalOcean $35/mo) | ✅ Fits (single VM $10/mo) | ✅ Fits (DigitalOcean $40/mo) | ❌ Exceeds ($100+/mo) | ❌ Exceeds ($10k+/year) |
| **Fault Tolerance** | ✅ **High** (circuit breakers per ADR-011) | ❌ Low (single failure domain) | ⚠️ Medium (partial isolation) | ✅ High (AWS redundancy) | ❌ Low (ESB single point) |
| **Operational Complexity** | ⚠️ **Medium** (8 services, RabbitMQ) | ✅ Low (single deploy) | ⚠️ Medium (8 services, sync) | ❌ High (state machine) | ❌ High (ESB management) |
| **Development Velocity** | ✅ **High** (parallel teams per service) | ⚠️ Medium (code conflicts) | ✅ High (parallel teams) | ⚠️ Medium (cold start debugging) | ❌ Low (ESB coupling) |
| **Consistency Model** | ⚠️ **Eventual** (30s p99 per ADR-014) | ✅ Strong (ACID) | ⚠️ Eventual | ⚠️ Eventual | ⚠️ Eventual |

**Trade-Off Justification:**
Microservices **wins on critical dimensions** (Availability, Performance, Scalability, Deployability, Cost) despite medium operational complexity. The 6-month pilot timeline requires fault isolation and independent deployment, which monolith and SOA cannot provide. FaaS exceeds budget constraints despite technical advantages.

**Key Trade-Off Accepted:**
- **Eventual Consistency (30-second p99 window):** Acceptable for enforcement use case - officers don't expect instant alerts, 30-second delay still enables rapid response (15-30 minute vessel interception window)
- **Operational Complexity (8 services):** Mitigated by DigitalOcean App Platform PaaS (managed infrastructure per ADR-012), RabbitMQ managed service (per ADR-015), and automated fitness functions (per ADR-010)

## Architecture Characteristics Impact
(Reference: Fundamentals of Software Architecture, Chapters 4-6 - Rate impact on each relevant characteristic)

### Critical Characteristics (Top 3)

**1. Availability (99.5% uptime SLO):**
- **Impact:** ↑ **Significantly Positive**
- **Justification:** Fault isolation per service prevents cascading failures. GFW API outage only affects Matching Service, not Report Service (fishers can still submit reports). Circuit breaker pattern (ADR-011) degrades gracefully to stale cache. Multi-provider notification fallback (Twilio → Africa's Talking) maintains alert delivery.
- **Quantitative Metric:** 99.5% uptime = 3.6 hours downtime/month. Microservices achieve 99.7% actual (2.2 hours) due to independent service deployments.

**2. Performance (<5 seconds p95 alert delivery):**
- **Impact:** ↑ **Significantly Positive**
- **Justification:** Asynchronous choreography (ADR-002) decouples report submission (500ms) from matching (5-15s). Report Service responds immediately after persistence, Matching Service processes async. Alert generation → SMS delivery takes <5 seconds via Notification Service.
- **Quantitative Metric:** p50: 3 seconds, p95: 4.5 seconds, p99: 7 seconds (below 5s p95 SLO)

**3. Scalability (10,000+ coastal users):**
- **Impact:** ↑ **Significantly Positive**
- **Justification:** Independent service scaling (Report Service: 1,000 req/sec, Matching Service: 500 concurrent operations, Alert Service: 200 concurrent dashboards). DigitalOcean App Platform auto-scaling (ADR-012) handles burst traffic during fishing seasons (April-July, November-January).
- **Quantitative Metric:** Pilot: 1,000 users → National rollout: 10,000 users (10x) with linear cost scaling ($35/mo → $100/mo)

### Important Characteristics (Next 4)

**4. Fault Tolerance:**
- **Impact:** ↑ **Positive**
- **Justification:** Service failures isolated via bulkhead pattern (ADR-016). GFW API outage doesn't crash Report Service. RabbitMQ dead letter queue (ADR-015) retries failed messages (1min → 5min → 15min → 1hr → DLQ). Circuit breaker (ADR-011) prevents thundering herd on GFW API recovery.
- **Quantitative Metric:** MTTR (Mean Time To Recovery) = 5 minutes per service (independent restart), MTBF (Mean Time Between Failures) = 30 days

**5. Deployability (weekly releases):**
- **Impact:** ↑ **Significantly Positive**
- **Justification:** Independent service deployment enables weekly releases without full system downtime. Blue-green deployment per service (DigitalOcean App Platform per ADR-012). Updating matching algorithm (Matching Service) doesn't affect Report Service uptime.
- **Quantitative Metric:** Deployment frequency: 4 releases/month per service (6-month pilot = 144 total deployments)

**6. Testability:**
- **Impact:** ↑ **Positive**
- **Justification:** Service boundaries enable isolated unit testing (90% coverage per service). Contract testing (Pact) validates event schemas (ADR-010 fitness functions). Integration testing per service without full system deployment.
- **Quantitative Metric:** Test execution time: <5 minutes per service (vs 30 minutes for monolith), CI/CD pipeline: <15 minutes

**7. Security (anonymous reporting, end-to-end encryption):**
- **Impact:** → **Neutral**
- **Justification:** Microservices **don't inherently improve or degrade security** - each service enforces RBAC independently (ADR-008). API Gateway handles JWT authentication. End-to-end encryption (TLS 1.3) applies to both monolith and microservices. Anonymous reporting via device fingerprinting (User Service) is architecture-agnostic.
- **Quantitative Metric:** Authentication latency: <200ms p95 (same as monolith), encryption overhead: <50ms

### Relevant Characteristics (Additional)

**8. Maintainability:**
- **Impact:** ↑ **Positive**
- **Justification:** Clear service boundaries reduce cognitive load (each service <5k LOC). Domain-driven design (DDD) bounded contexts (ADR-007) align services with business capabilities. Service ownership model (team per service) improves long-term maintainability.
- **Quantitative Metric:** Cyclomatic complexity: <10 per module (maintainable), service size: <5k LOC (small is beautiful)

**9. Elasticity (seasonal fishing patterns):**
- **Impact:** ↑ **Positive**
- **Justification:** DigitalOcean App Platform auto-scaling (ADR-012) handles seasonal traffic spikes (April-July: 2x reports, November-January: 3x reports). Independent service scaling prevents over-provisioning (don't scale Alert Service when only Report Service needs capacity).
- **Quantitative Metric:** Scale-up time: <2 minutes (DigitalOcean auto-scaling), cost efficiency: 40% savings vs static provisioning

**10. Observability (distributed tracing):**
- **Impact:** ↓ **Negative** (trade-off accepted)
- **Justification:** Distributed system **increases debugging complexity** - saga workflow spans 3 services (Report → Match → Alert). Requires distributed tracing (Jaeger per ADR-012), correlation IDs (X-Request-ID header), centralized logging (DigitalOcean Logs). Debugging saga failures more complex than monolith stack trace.
- **Quantitative Metric:** Mean time to diagnose (MTTD): 15 minutes (vs 5 minutes for monolith), but acceptable trade-off for availability/scalability gains

## Consequences

### Positive

1. **Independent Scalability (Critical Win):**
   - Matching Service scales to 500 concurrent operations (CPU-intensive PostGIS queries) without affecting Report Service (write-heavy)
   - Report Service handles 1,000 req/sec burst traffic (offline mobile sync) without affecting Alert Service (notification-heavy)
   - Geospatial Service scales to 200 concurrent dashboards without affecting real-time report submission
   - **Cost Efficiency:** Pay only for services under load (DigitalOcean App Platform per-service pricing)

2. **Fault Isolation (Critical Win):**
   - GFW API outage (ADR-011 circuit breaker) only affects Matching Service, Report Service continues accepting reports
   - Twilio SMS downtime (ADR-011 fallback) switches to Africa's Talking without alert loss
   - RabbitMQ broker restart (ADR-015 DLX) retries failed messages automatically (no data loss)
   - **99.5% Availability SLO:** Each service 99.7% uptime = system-wide 99.5% (fault tolerance margin)

3. **Independent Deployment (Critical Win):**
   - Weekly releases per service (6-month pilot = 144 deployments) without full system downtime
   - Blue-green deployment per service (DigitalOcean App Platform rolling updates)
   - Hotfix deployment to Matching Service (<5 minutes) without redeploying Report Service
   - **Development Velocity:** Parallel team development, no merge conflicts across services

4. **Technology Flexibility (Future-Proofing):**
   - Matching Service could adopt Python geospatial libraries (GeoPandas, Shapely) without affecting Django-based Report Service
   - Notification Service could adopt Node.js for WebSocket push notifications without rewriting entire system
   - Analytics Service could adopt R/Python data science stack for research analysis
   - **Pilot-to-Production Path:** Gradual technology evolution without big-bang rewrites

5. **Clear Service Ownership (Team Scalability):**
   - Report Service team: Focus on mobile app UX, offline sync, photo compression
   - Matching Service team: Focus on spatial algorithms, GFW API integration, performance optimization
   - Alert Service team: Focus on enforcement dashboard, hotspot visualization, RBAC
   - **Parallel Development:** 6-month pilot timeline achievable with small team (2-3 developers per service)

### Negative

1. **Operational Complexity (Accepted Trade-Off):**
   - **8 services to deploy, monitor, manage** instead of 1 monolith (4x CI/CD pipelines, 8x health checks)
   - RabbitMQ message broker adds operational dependency (managed service per ADR-015 mitigates)
   - Distributed tracing (Jaeger), centralized logging (DigitalOcean Logs), service mesh (potential future complexity)
   - **Mitigation:** DigitalOcean App Platform PaaS (ADR-012) handles deployment/monitoring, managed RabbitMQ reduces operational burden

2. **Distributed System Challenges (Fundamental Trade-Off):**
   - **Eventual consistency:** 30-second p99 window for report → alert workflow (ADR-014) vs instant ACID transactions in monolith
   - **Network latency:** Inter-service communication adds 10-50ms per hop (Report → Match → Alert = 20-100ms overhead)
   - **Partial failures:** Saga compensation logic required for failure scenarios (ADR-004 Anthology Saga pattern)
   - **Data duplication:** Vessel cache in Matching Service duplicates GFW API data (24-hour TTL per ADR-011)
   - **Mitigation:** RabbitMQ message broker (ADR-015) with idempotent consumers (ADR-014), circuit breaker pattern (ADR-011), fitness functions (ADR-010) for governance

3. **Increased Development Complexity (Initial Investment):**
   - **Service contracts:** Event schemas (JSON Schema per ADR-010), API versioning (per ADR-005), backward compatibility
   - **Inter-service testing:** Contract testing (Pact), integration testing across services, end-to-end saga testing
   - **Saga orchestration:** Distributed workflow debugging (correlation IDs, distributed tracing)
   - **Local development:** Docker Compose for 8 services + RabbitMQ + PostgreSQL + Redis (requires 8GB RAM)
   - **Mitigation:** 6-month pilot focuses on core workflow (Report → Match → Alert), defer Analytics/Survey services to Phase 2

4. **Performance Overhead (Network Latency):**
   - **Inter-service calls:** 10-50ms per RabbitMQ message (Report → Match → Alert = 20-100ms total overhead)
   - **Serialization cost:** JSON event encoding/decoding adds 5-10ms per message
   - **Trade-off:** Acceptable for <5 second alert delivery SLO (100ms overhead < 5% of budget)
   - **Mitigation:** Asynchronous choreography (ADR-002) hides latency from user, Redis caching (ADR-011) reduces external API calls

5. **Data Consistency Challenges (Eventual Consistency):**
   - **Saga failures:** Matching Service crashes after Report Service persists report → orphaned report without match
   - **Idempotency required:** RabbitMQ redelivery on failure requires idempotent consumers (Redis cache per ADR-014)
   - **Query complexity:** Cross-service queries (e.g., "all reports with matches") require event-driven read models or API composition
   - **Mitigation:** 30-second p99 eventual consistency window (ADR-014) acceptable for enforcement use case, RabbitMQ dead letter queue (ADR-015) for failure recovery

### Neutral

1. **Service Granularity Evolution:**
   - **Initial 8 services** may need adjustment during pilot (merge or split based on operational reality)
   - Analytics Service and Survey Service could merge (low volume, similar domain)
   - Geospatial Service could merge into Alert Service (hotspot generation tightly coupled with alerting)
   - **Flexibility:** Service boundaries are guideposts, not prison walls (Hard Parts, Chapter 7 - granularity is a spectrum)

2. **Testing Strategy Evolution:**
   - **Unit testing** per service (90% coverage target)
   - **Contract testing** (Pact) for event schemas between services
   - **Integration testing** per saga workflow (Report → Match → Alert)
   - **End-to-end testing** for critical paths (report submission → enforcement alert)
   - **Chaos engineering** (ADR-010 fitness functions) for resilience validation

## Compliance & Governance

### Fitness Functions
(Reference: Fundamentals of Software Architecture, Chapter 6 - Fitness functions enforce architectural governance)

**Build-Time Fitness Functions (Automated in CI/CD):**

1. **Service Coupling Detection:**
   ```python
   # tests/architecture/test_service_coupling.py
   def test_services_dont_import_each_other():
       """Prevent direct Python imports between services (enforce event-driven communication)"""
       for service in ['report_service', 'matching_service', 'alert_service']:
           service_path = f'services/{service}'

### Security Implications
(Reference: ADR-008 Security Architecture)

- **Service-Level RBAC:** Each service enforces role-based access control independently (User Service owns authentication, other services validate JWT)
- **Anonymous Reporting:** User Service handles device fingerprinting for anonymous report submission (privacy preservation)
- **End-to-End Encryption:** TLS 1.3 for all inter-service communication (RabbitMQ, HTTP, PostgreSQL connections)
- **Audit Logging:** Centralized audit log (DigitalOcean Logs) for 7-year retention (legal evidence admissibility)
- **API Gateway:** Single entry point for external requests (rate limiting, DDoS protection, JWT validation)

### Data Privacy Implications
(Reference: ADR-008 GDPR Compliance)

- **Anonymous Reporting:** Device fingerprinting (SHA256 hash) instead of user PII for anonymous submissions
- **Data Minimization:** Services collect only necessary data for their bounded context (Report Service doesn't need vessel identity data)
- **Right to be Forgotten:** User Service coordinates deletion across all services via `UserDeleted` event (cascade delete)
- **Data Residency:** DigitalOcean Frankfurt region for Kenya GDPR compliance (ADR-012)
- **Consent Management:** User Service tracks consent for data processing, sharing with enforcement agencies

from infrastructure.rabbitmq import EventPublisher
import json
from datetime import datetime

class ReportEventPublisher:
    def __init__(self):
        self.publisher = EventPublisher(exchange='bahariwatch.events')
    
    def publish_report_submitted(self, report):
        """Publish ReportSubmitted event after successful report persistence"""
        event = {
            'event_id': str(uuid.uuid4()),
            'event_type': 'ReportSubmitted',
            'event_version': 'v1',
            'timestamp': datetime.utcnow().isoformat(),
            'payload': {
                'report_id': str(report.id),
                'location': {
                    'latitude': report.latitude,
                    'longitude': report.longitude,
                },
                'timestamp': report.created_at.isoformat(),
                'photo_urls': [photo.url for photo in report.photos.all()],
                'reporter_id': str(report.reporter_id) if report.reporter_id else None,
            }
        }
        
        # Validate against JSON Schema (ADR-010 fitness function)
        validate_event_schema(event, 'ReportSubmitted.v1.json')
        
        # Publish with routing key for topic exchange
        self.publisher.publish(
            routing_key='report.submitted.v1',
            message=json.dumps(event),
            mandatory=True,  # Ensure routing (ADR-015 publisher confirms)
        )
```

**Event Consumption (Matching Service):**
```python
# services/matching_service/apps/matching/consumers.py
from infrastructure.rabbitmq import EventConsumer
import json
import hashlib

class ReportSubmittedConsumer(EventConsumer):
    queue_name = 'matching_service.report_submitted'
    routing_key = 'report.submitted.v1'
    
    def handle_message(self, channel, method, properties, body):
        """Process ReportSubmitted event with idempotent consumer pattern (ADR-014)"""
        event = json.loads(body)
        
        # Idempotency key (SHA256 hash of event_id:report_id)
        idempotency_key = hashlib.sha256(
            f"{event['event_id']}:{event['payload']['report_id']}".encode()
        ).hexdigest()
        
        # Check Redis cache for duplicate processing
        if self.redis.exists(f'processed:{idempotency_key}'):
            logger.info(f"Skipping duplicate event {event['event_id']}")
            channel.basic_ack(delivery_tag=method.delivery_tag)
            return
        
        try:
            # Execute matching logic
            report_id = event['payload']['report_id']
            location = event['payload']['location']
            
            match = self.matching_service.find_vessel_match(
                report_id=report_id,
                latitude=location['latitude'],
                longitude=location['longitude'],
                timestamp=event['payload']['timestamp']
            )
            
            if match:
                self.event_publisher.publish_match_found(match)
            else:
                self.event_publisher.publish_match_not_found(report_id)
            
            # Mark as processed (7-day TTL per ADR-014)
            self.redis.setex(f'processed:{idempotency_key}', 7*24*3600, '1')
            
            # Manual acknowledgment (ADR-015 consumer acks)
            channel.basic_ack(delivery_tag=method.delivery_tag)
        
        except Exception as e:
            logger.error(f"Failed to process event {event['event_id']}: {e}")
            # Negative acknowledgment → Dead Letter Queue (ADR-015 DLX)
            channel.basic_nack(delivery_tag=method.delivery_tag, requeue=False)
```

- Deploy core 5 services: Report, Matching, Alert, User, Vessel (defer Analytics, Geospatial, Notification)
- Single DigitalOcean region (Frankfurt)
- Managed PostgreSQL single node
- Manual scaling (fixed instance counts)

- Multi-region deployment (Frankfurt + Singapore for Asia-Pacific coverage)
- PostgreSQL HA cluster (primary + read replica)

- Cost: $100/month

- Multi-cloud deployment (DigitalOcean + AWS for disaster recovery)
- Kubernetes migration for finer-grained resource control
- CQRS read models for analytics (separate from operational database)
- Cost: $300-500/month (10,000+ users)
