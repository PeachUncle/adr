## Context

The V5 trading strategy (`integrated_strategy_algo_v5.md`) introduces a machine learning model for market regime classification. This creates a requirement for a managed, reliable, and cost-effective infrastructure to support the entire machine learning lifecycle (MLOps), including data preparation, model training, versioning, deployment (serving), and monitoring.

## Decision

We will adopt a serverless, GCP-native MLOps stack using a combination of **Vertex AI** and **Google Cloud Run**.

1.  **Data & Feature Engineering**: **Google BigQuery** will be used as the single source for training data and for performing feature engineering via scheduled SQL queries, as established in ADR-004.

2.  **Model Training**: **Vertex AI Training** will be used to run our model training jobs. The training process will be containerized and submitted as a "Custom Training Job." This provides a serverless environment where we only pay for the compute resources used during the training run.

3.  **Model Storage & Versioning**: **Vertex AI Model Registry** will be the central, version-controlled repository for all trained model artifacts. Each quarterly or event-driven retraining will produce a new, versioned model in the registry, allowing for easy tracking and rollbacks.

4.  **Model Serving (Inference)**: **Google Cloud Run** will be used to deploy the trained model as a simple, stateless API endpoint. This aligns with our primary deployment strategy (ADR-016) and provides the most cost-effective solution for serving.

## Rationale

This decision creates a cohesive, serverless MLOps pipeline that aligns perfectly with our established architectural principles.

1.  **Cost-Effectiveness**: This is the primary driver.
    *   **Vertex AI Training** is serverless, meaning we are not paying for an idle, dedicated training server.
    *   **Google Cloud Run** for serving is exceptionally cost-effective due to its "scale-to-zero" capability. Since the model is only queried when the `StockSelectionAgent` is active, the model serving endpoint will incur near-zero cost during nights, weekends, and market holidays.
2.  **Minimized Operational Overhead**: The entire stack is fully managed. Vertex AI and Cloud Run handle all the underlying infrastructure, scaling, and security, allowing the team to focus on the model and agent logic, not on managing servers.
3.  **Architectural Consistency**: Using Cloud Run for model serving means we use the exact same deployment pattern, CI/CD pipeline (GitHub Actions), and IaC definitions (Terraform) for our ML model as we do for all our other agents and services. This drastically simplifies our DevOps processes.
4.  **Scalability and Reliability**: This stack is built on Google's enterprise-grade infrastructure. Both Vertex AI and Cloud Run can scale to handle any future needs, and the Model Registry provides the versioning and rollback capabilities essential for maintaining a reliable production system.

## Consequences

-   **Implementation**:
    *   The model training code must be containerized.
    *   A simple API service (e.g., using FastAPI) must be created to load the model from the registry and expose a prediction endpoint. This service will be deployed to Cloud Run.
    *   Our GitHub Actions CI/CD pipeline will be extended to include steps for:
        1.  Triggering a Vertex AI Training job.
        2.  Registering the new model in the Vertex AI Model Registry.
        3.  Deploying the new model version to the Cloud Run serving endpoint.
-   **Dependencies**: The project will require the `google-cloud-aiplatform` Python library to interact with the Vertex AI services.
-   **Infrastructure**: New Vertex AI and Cloud Run resources will be defined in our Terraform (ADR-019) configuration.

## Alternatives Considered

-   **Vertex AI Endpoints for Serving**: Vertex AI has its own managed service for deploying models called "Endpoints." While powerful, it is designed for always-on, high-throughput scenarios and does not scale to zero. For our intermittent workload, it would be significantly more expensive than Cloud Run.
-   **Self-Hosted ML on a GCE VM**: This would involve manually setting up a virtual machine, installing the necessary libraries, and managing the entire environment. This was rejected as it creates significant operational overhead and is less cost-effective than the serverless approach.

## Implementation Strategy

### Phase 1: Data Pipeline and Feature Engineering (Week 1-2)
**Deliverables**:
- Create BigQuery scheduled queries for feature extraction (VIX, term structure, breadth indicators)
- Define feature engineering transformations in SQL for market regime inputs
- Create materialized view or table for training dataset with 3+ years historical data
- Implement data validation checks for feature quality and completeness

**Dependencies**: ADR-004 (BigQuery Analytics), historical market data ingestion complete

### Phase 2: Model Training Infrastructure (Week 2-4)
**Deliverables**:
- Containerize model training code (Gradient Boosting classifier) using Docker
- Define Vertex AI Custom Training Job configuration
- Create training script that reads from BigQuery, trains model, validates performance
- Implement hyperparameter tuning with Vertex AI Hyperparameter Tuning service
- Configure model evaluation metrics (accuracy, precision, recall for 5 regime classes)

**Dependencies**: Phase 1 completion, scikit-learn or XGBoost model code developed

### Phase 3: Model Registry and Versioning (Week 4-5)
**Deliverables**:
- Configure Vertex AI Model Registry for model artifact storage
- Implement model versioning strategy (semantic versioning: major.minor.patch)
- Create model metadata schema (training date, performance metrics, feature list)
- Define model promotion workflow (dev -> staging -> prod)
- Implement A/B testing framework for comparing model versions

**Dependencies**: Phase 2 completion, trained model artifacts generated

### Phase 4: Model Serving on Cloud Run (Week 5-6)
**Deliverables**:
- Create FastAPI service for model inference with `/predict` endpoint
- Implement model loading from Vertex AI Model Registry at startup
- Add input validation and error handling for prediction requests
- Define Cloud Run service configuration (memory, CPU, concurrency limits)
- Create health check and readiness probe endpoints

**Dependencies**: Phase 3 completion, ADR-016 (Cloud Run deployment patterns)

### Phase 5: CI/CD and Monitoring (Week 6-7)
**Deliverables**:
- Extend GitHub Actions workflow to trigger Vertex AI training on schedule or manual trigger
- Automate model registration in Model Registry post-training
- Automate Cloud Run deployment of new model versions
- Implement model performance monitoring (prediction latency, error rate)
- Create alerting for model drift and performance degradation

**Dependencies**: Phase 4 completion, ADR-018 (GitHub Actions CI/CD), ADR-021 (Observability)

## Cost Analysis

### Monthly Operational Costs

| Component | Usage Pattern | Cost |
|-----------|---------------|------|
| Vertex AI Training (n1-standard-4, 2 hours/quarter) | Quarterly retraining | $1.60/training run ($0.53/month) |
| Vertex AI Model Registry (< 1GB storage) | Continuous | $0.10/month |
| Cloud Run Model Serving (256MB, 0.5 vCPU) | Scale-to-zero, ~100 requests/day during market hours | $5-15/month |
| BigQuery Feature Queries (10GB scanned/day) | Daily scheduled queries | $15/month |
| Container Registry Storage (Docker images) | Continuous | $0.50/month |
| **Total Monthly Cost** | | **$21-31/month** |

**Cost Sensitivity Analysis**:
- Training frequency: Quarterly ($0.53/month) vs Monthly ($1.60/month)
- Serving traffic: 100 req/day ($8/month) vs 1000 req/day ($25/month)
- Feature computation: 10GB/day ($15/month) vs 50GB/day ($75/month)

### Cost Optimization Strategies

1. **Quarterly Retraining Schedule**: Market regime models have low drift. Quarterly retraining (vs monthly) reduces training costs by 66% with minimal accuracy impact.

2. **Cloud Run Scale-to-Zero**: Model serving only active during market scanning hours (9:30 AM - 4:00 PM ET, weekdays). Zero cost during nights, weekends, holidays. Estimated 35% utilization vs always-on Vertex AI Endpoint.

3. **BigQuery Partitioning and Clustering**: Partition feature tables by date, cluster by symbol. Reduces query costs by 70-90% through scan reduction.

4. **Preemptible VMs for Training**: Use Vertex AI Training with preemptible instances for 60-80% cost reduction. Acceptable for non-time-sensitive quarterly training.

5. **Model Caching**: Implement Redis caching of regime predictions for 5-minute TTL. Reduces Cloud Run invocations by 90% during active scanning periods.

### ROI Comparison vs Alternatives

| Approach | Monthly Cost | Setup Complexity | Scalability | Operational Overhead |
|----------|--------------|------------------|-------------|----------------------|
| Vertex AI + Cloud Run | $21-31 | Medium (4/5) | High | Low |
| Vertex AI Endpoints | $120-200 | Low (2/5) | Very High | Very Low |
| Self-Hosted GCE VM | $30-50 | High (5/5) | Medium | High |
| SageMaker (AWS) | $40-80 | Medium (4/5) | High | Medium |

**Verdict**: Vertex AI + Cloud Run provides best cost-to-performance ratio for intermittent ML workloads.

## Risk Assessment

| Risk | Severity | Likelihood | Impact | Mitigation |
|------|----------|------------|--------|------------|
| Model performance degradation (drift) | High | Medium | Incorrect regime classification leads to suboptimal strategy selection | Implement automated model monitoring, quarterly retraining schedule, A/B testing framework for new models, fallback to rule-based regime detection |
| Training pipeline failure | Medium | Low | Delayed model updates, reliance on outdated model | Automated alerting on training job failures, maintain previous model version in registry, implement retry logic with exponential backoff |
| Prediction endpoint unavailability | High | Low | Stock selection agent cannot determine market regime, blocks new trades | Deploy model to multiple Cloud Run regions, implement circuit breaker pattern, cache last known regime for 1-hour fallback |
| Cold start latency on Cloud Run | Medium | Medium | First prediction after idle period takes 3-5 seconds, delays trade analysis | Implement Cloud Run minimum instances (1) during market hours, use async prediction pattern, pre-warm endpoint at market open |
| Feature engineering pipeline failure | High | Low | Incomplete or incorrect training data, model trained on bad features | Implement data validation checks (Great Expectations), alerting on feature anomalies, maintain feature schema versioning |
| Overfitting to historical data | Medium | Medium | Model performs well in backtest but fails in live trading | Use walk-forward validation, maintain holdout test set from recent data, implement ensemble model approach, monitor live prediction accuracy |
| Version mismatch (training vs serving) | Medium | Low | Serving endpoint uses different feature schema than training, prediction errors | Implement feature schema versioning, automated testing of serving endpoint post-deployment, model metadata includes feature list |

## Monitoring and Success Criteria

### Key Metrics

| Metric | Target | Measurement Method |
|--------|--------|-------------------|
| Model Training Success Rate | >95% | Vertex AI Training job completion status |
| Model Accuracy (5-class regime classification) | >70% | Validation set performance from training job |
| Prediction Latency (p95) | <500ms | Cloud Run request duration monitoring |
| Prediction Endpoint Availability | >99.5% | Cloud Run uptime monitoring |
| Model Drift Detection Latency | <7 days | Time between performance degradation and alert |

### Alerting Thresholds

**Critical**:
- Vertex AI training job failed
- Cloud Run prediction endpoint down >5 minutes
- Model accuracy on recent data <60% (significant drift)
- Prediction error rate >5%

**Warning**:
- Training job duration >4 hours (expected: 1-2 hours)
- Prediction latency p95 >1 second
- Model accuracy degraded 5-10% from baseline
- Feature pipeline missed scheduled execution

**Info**:
- New model training initiated
- Model registered to Model Registry
- New model version deployed to Cloud Run
- A/B test results available for review

### Success Criteria

**Functional Requirements**:
- Model successfully classifies market into 5 regimes with >70% accuracy
- Prediction endpoint responds to requests within 500ms (p95)
- Model retraining completes successfully on quarterly schedule
- Model Registry maintains at least 3 most recent model versions
- A/B testing framework compares new model against current production model

**Performance Requirements**:
- Training job completes within 3 hours for 3-year dataset
- Cloud Run scales to handle 100 concurrent prediction requests
- Cold start time <3 seconds
- Feature engineering pipeline completes within 1 hour daily

**Cost Requirements**:
- Total MLOps costs remain below $35/month
- Training costs <$2/month (quarterly schedule)
- Serving costs <$20/month (scale-to-zero pattern)

**Operational Requirements**:
- Automated CI/CD pipeline deploys new models without manual intervention
- Model performance monitoring dashboard available in Cloud Monitoring
- Documentation maintained for model architecture, features, and retraining procedures
- Rollback to previous model version completes within 5 minutes

### Risk Factors

1. **Model Complexity vs Explainability**: High complexity - Gradient Boosting models provide high accuracy but limited interpretability. Risk: Difficult to debug why model makes specific regime predictions. Mitigation: Implement SHAP values for feature importance, maintain rule-based fallback.

2. **Data Quality and Availability**: Medium complexity - Model performance depends on quality of VIX, breadth, and credit spread data. Risk: Missing or delayed data prevents training or predictions. Mitigation: Implement data validation, maintain cached features, design model to handle missing values.

3. **Integration with Trading System**: High complexity - Regime predictions must integrate seamlessly with Stock Selection Agent. Risk: Latency or errors in predictions block trading workflow. Mitigation: Implement async prediction pattern, cache results, design graceful degradation.

4. **Operational Maturity**: Very high complexity - Production ML requires monitoring, retraining, A/B testing, and rollback capabilities. Risk: System lacks operational rigor for production ML. Mitigation: Phased rollout starting with shadow mode (predictions logged but not used), gradual promotion to decision-making role.

5. **Cost Overruns**: Low complexity - Training and serving costs are predictable but could increase with higher traffic or more frequent retraining. Risk: Costs exceed budget. Mitigation: Implement cost monitoring alerts, use preemptible instances for training, aggressive caching for serving.
