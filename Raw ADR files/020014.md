# ADR-017: Error Handling & User Feedback Strategy

## Status

Accepted

## Context

The application currently has inconsistent error handling patterns across different layers that create production risks and poor user experience:

1. **Dual Toast Systems**: Both Sonner and Shadcn toast components are installed, creating inconsistent user feedback
2. **Inconsistent Logging**: Mix of `console.log("error")` and `console.error()` patterns throughout codebase
3. **Generic Error Messages**: Most catch blocks show generic "error occurred" messages without actionable guidance
4. **No Component Protection**: React component crashes can break entire application sections
5. **Naive Retry Logic**: No retry mechanisms for transient failures, causing unnecessary user friction

**Production Blockers Identified:**
- **Component Crashes**: No Error Boundaries to catch React crashes, entire app sections fail
- **Error Notification Spam**: Multiple simultaneous errors can flood users with toast notifications
- **Server Overload Risk**: No exponential backoff for retries, failed requests can hammer servers
- **Poor User Experience**: Vague error messages leave users confused about next steps

## Decision

We will implement a **minimal error handling infrastructure** that covers 90% of production error scenarios while maintaining development velocity.

**Core Components:**
1. **React Error Boundaries** - Catch component crashes and show fallback UI
2. **Single Toast System** - Standardize on Shadcn UI toast components only
3. **Error Classification** - Five core error types with actionable user messages
4. **Smart Retry Logic** - Exponential backoff for transient network failures
5. **Toast Rate Limiting** - Prevent notification spam during error cascades

## Rationale

### Chosen: Minimal Viable Error Handling

**Error Boundaries Benefits:**
- ✅ **App Stability**: Component crashes don't break entire application
- ✅ **User Recovery**: Fallback UI with retry options keeps users productive
- ✅ **Development Debugging**: Error details available in development mode
- ✅ **Simple Implementation**: Single component wraps critical sections

**Single Toast System Benefits:**
- ✅ **Consistency**: Unified user feedback across entire application
- ✅ **Bundle Size**: Remove unused Sonner dependency (~12KB savings)
- ✅ **Maintenance**: Single system to maintain and update
- ✅ **Accessibility**: Shadcn components include built-in ARIA support

**Smart Retry Benefits:**
- ✅ **Resilience**: Automatic recovery from transient network issues
- ✅ **Server Protection**: Exponential backoff prevents server overload
- ✅ **User Experience**: Reduces manual retry attempts by users
- ✅ **Configurable**: Easy to adjust retry parameters per operation type

### Rejected Alternatives

**Complex Error Management Systems**
- ❌ **Over-Engineering**: Circuit breakers and offline queues add complexity without clear MVP benefit
- ❌ **Development Time**: Would require 5+ days vs 2 days for minimal approach
- ❌ **Maintenance Overhead**: More sophisticated systems require ongoing maintenance

**Multiple Toast Systems (Current State)**
- ❌ **Inconsistency**: Different APIs and styling create confusing user experience
- ❌ **Bundle Bloat**: Unnecessary Sonner dependency increases bundle size
- ❌ **Developer Confusion**: Team must remember which system to use when

**No Error Handling (Status Quo)**
- ❌ **Production Risk**: Component crashes break user workflows
- ❌ **Poor UX**: Generic error messages provide no actionable guidance
- ❌ **Support Burden**: Users contact support for recoverable errors

### Explicitly Deferred to Future Phases

**Circuit Breaker Pattern** - Complex implementation, rarely needed at MVP scale. Add when we have 10k+ DAU and observe repeated cascade failures.

**Offline Operation Queue** - Over-engineered for current needs. Simple `navigator.onLine` checks sufficient until mobile users report data loss.

**Comprehensive Error Dictionaries** - 50+ predefined error messages premature. Start with 5 core types, expand based on actual support ticket patterns.

## Implementation Details

### 1. Error Boundaries (P0 - Prevents App Crashes)

```javascript
// components/ErrorBoundary.jsx
import React from 'react';
import { Button } from "~/components/ui/button";
import { Card } from "~/components/ui/card";

export class ErrorBoundary extends React.Component {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error, errorInfo) {
    console.error('[ErrorBoundary]', error, errorInfo.componentStack);
  }

  render() {
    if (this.state.hasError) {
      return (
        <Card className="p-6 m-4 max-w-md mx-auto">
          <h2 className="text-lg font-semibold mb-2">Something went wrong</h2>
          <p className="text-sm text-muted-foreground mb-4">
            This section couldn't load properly
          </p>
          <div className="flex gap-2">
            <Button onClick={() => this.setState({ hasError: false })} size="sm">
              Try Again
            </Button>
            <Button onClick={() => window.location.reload()} variant="outline" size="sm">
              Reload Page
            </Button>
          </div>
        </Card>
      );
    }
    return this.props.children;
  }
}

// Wrap in _app.jsx
<ErrorBoundary>
  <Component {...pageProps} />
</ErrorBoundary>
```

### 2. Error Classification (P0 - Actionable User Messages)

```javascript
// lib/errors.js
export const getErrorMessage = (error, context = '') => {
  // Auth errors
  if (error.status === 401 || error.message?.includes('JWT')) {
    return {
      title: "Session Expired",
      description: "Sign in again to continue"
    };
  }

  // Permission errors
  if (error.status === 403) {
    return {
      title: "Access Denied",
      description: "You don't have permission for this action"
    };
  }

  // Network errors
  if (!navigator.onLine || error.message?.includes('fetch')) {
    return {
      title: "Connection Failed",
      description: "Check your internet and try again"
    };
  }

  // Validation errors
  if (error.status === 400) {
    return {
      title: "Invalid Input",
      description: error.message || "Check your input and try again"
    };
  }

  // Server errors
  if (error.status >= 500) {
    return {
      title: "Server Error",
      description: "Try again in a moment"
    };
  }

  // Generic fallback
  return {
    title: `${context} Failed`,
    description: "Something went wrong. Please try again"
  };
};
```

### 3. Smart Retry (P0 - Handles Transient Failures)

```javascript
// lib/errors.js
export const withRetry = async (operation, maxRetries = 3) => {
  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      return await operation();
    } catch (error) {
      // Don't retry client errors
      if (error.status === 401 || error.status === 403 || error.status === 400) {
        throw error;
      }

      // Last attempt, give up
      if (attempt === maxRetries) throw error;

      // Exponential backoff: 1s, 2s, 4s
      const delay = 1000 * Math.pow(2, attempt - 1);
      await new Promise(resolve => setTimeout(resolve, delay));
    }
  }
};
```

### 4. Toast Rate Limiting (P0 - Prevents Spam)

```javascript
// lib/errors.js
const recentToasts = new Map();
const COOLDOWN = 5000; // 5 seconds

export const shouldShowToast = (errorTitle) => {
  const now = Date.now();
  const lastShown = recentToasts.get(errorTitle);
  
  if (!lastShown || now - lastShown > COOLDOWN) {
    recentToasts.set(errorTitle, now);
    return true;
  }
  return false;
};

// hooks/use-error-toast.js
import { useToast } from "~/hooks/use-toast";
import { getErrorMessage, shouldShowToast } from "~/lib/errors";

export const useErrorToast = () => {
  const { toast } = useToast();

  const showError = (error, context = '') => {
    const { title, description } = getErrorMessage(error, context);
    
    if (!shouldShowToast(title)) {
      console.warn('[Toast suppressed - duplicate]', title);
      return;
    }

    toast({
      variant: "destructive",
      title,
      description
    });
  };

  return { showError };
};
```

### 5. Standard Usage Pattern

```javascript
// Component example
import { useErrorToast } from "~/hooks/use-error-toast";
import { withRetry } from "~/lib/errors";

const MessageInput = () => {
  const { showError } = useErrorToast();

  const handleSend = async () => {
    try {
      await withRetry(() => 
        addMessage(messageText, channelId, user.id)
      );
      // Success handling
    } catch (error) {
      showError(error, 'Send Message');
      setValue(messageText); // Restore on failure
    }
  };

  return <form onSubmit={handleSend}>...</form>;
};
```

## Migration Plan

**Day 1: Core Infrastructure (4 hours)**
1. Create `ErrorBoundary.jsx` component
2. Create `lib/errors.js` with classification + retry
3. Create `hooks/use-error-toast.js`
4. Wrap app in ErrorBoundary

**Day 2: Component Migration (4 hours)**
1. Remove Sonner: `npm uninstall sonner`
2. Replace error handling in 5 critical paths:
   - Auth flow
   - Message sending
   - Channel operations
   - Real-time subscriptions
   - Data loading
3. Test error scenarios

## Success Metrics

**Before Migration:**
- 0 error boundaries (app crashes kill UI)
- 2 toast systems (Sonner + Shadcn)
- ~30 generic "error occurred" messages
- No retry logic

**After Migration:**
- 1 app-level error boundary
- 1 toast system (Shadcn)
- 5 error categories with actionable messages
- Exponential backoff retry on all API calls
- Toast rate limiting (max 1 toast per error type per 5s)

**Production Readiness:**
- ✅ Component crashes don't break app
- ✅ Users get specific, actionable error messages
- ✅ Transient failures auto-retry
- ✅ Multiple errors don't spam UI
- ✅ Bundle size reduced by 12KB

## What We're NOT Doing (Deferred to P1)

**Circuit Breaker** - Complex pattern, rarely needed at MVP scale. Add when we have 10k+ DAU and see repeated cascade failures.

**Offline Queue** - Over-engineered. Use simple `navigator.onLine` checks and show "You're offline" message. Queue can wait until we see actual user pain.

**Error Dictionaries** - 50+ predefined error messages is premature. Start with 5 core types, expand based on actual support tickets.

**Per-Operation Customization** - Don't need 30 different "failed to X" messages. Generic "X Failed" + description is fine for MVP.

## Testing Strategy

```javascript
/**
 * @adr ADR-017
 * @requirement Error handling and user feedback
 */
describe('Error Handling Infrastructure', () => {
  test('Error boundary catches component crashes', () => {
    const CrashingComponent = () => { throw new Error('Component crashed'); };
    const { getByText } = render(
      <ErrorBoundary>
        <CrashingComponent />
      </ErrorBoundary>
    );
    
    expect(getByText('Something went wrong')).toBeInTheDocument();
    expect(getByText('Try Again')).toBeInTheDocument();
  });

  test('Retry mechanism uses exponential backoff', async () => {
    const mockOperation = jest.fn()
      .mockRejectedValueOnce(new Error('Network failure'))
      .mockResolvedValueOnce('success');
    
    const startTime = Date.now();
    const result = await withRetry(mockOperation, 3);
    const duration = Date.now() - startTime;
    
    expect(result).toBe('success');
    expect(mockOperation).toHaveBeenCalledTimes(2);
    expect(duration).toBeGreaterThan(1000); // Should have exponential delay
  });

  test('Toast rate limiting prevents notification spam', () => {
    expect(shouldShowToast('Network Error')).toBe(true);
    expect(shouldShowToast('Network Error')).toBe(false); // Rate limited
    
    // Different error types not rate limited
    expect(shouldShowToast('Auth Error')).toBe(true);
  });

  test('Error classification provides actionable messages', () => {
    const authError = { status: 401, message: 'JWT expired' };
    const result = getErrorMessage(authError, 'Send Message');
    
    expect(result.title).toBe('Session Expired');
    expect(result.description).toBe('Sign in again to continue');
  });
});
```

## Future Considerations

### Phase 2 Enhancements (When Scale Demands)

**Circuit Breaker Implementation**
- Add when we observe cascade failures in production (typically >10k DAU)
- Will leverage existing retry infrastructure and error classification
- Prevents repeated failures from overwhelming system resources

**Comprehensive Offline Support**
- Implement operation queuing when mobile users report data loss
- Build on current `navigator.onLine` detection foundation
- Queue critical operations (messages, channel creation) for later sync

**Advanced Error Monitoring**
- Sentry integration planned for production error tracking and alerting
- Current structured logging patterns designed to be Sentry-compatible
- Error context and classification will map directly to Sentry error grouping

### Expansion Triggers

**Error Dictionary Growth**
- Add specific error messages when support sees same error >10 times/week
- Current generic fallbacks provide foundation for targeted improvements
- User feedback will drive priority of message improvements

**Performance Monitoring Integration**
- Add error rate and retry success metrics when monitoring budget available
- Current error logging provides foundation for performance dashboards
- Will help identify patterns requiring circuit breaker implementation

### Architecture Evolution

The minimal error handling infrastructure established in this ADR provides the foundation for sophisticated error management patterns. The error classification system, retry mechanisms, and structured logging are designed to support future enhancements without requiring architectural changes.

## Consequences

### Positive

- **Fast Implementation**: Ships in 2 days instead of 5+ days for complex error management
- **Production Coverage**: Addresses 90% of critical error scenarios for MVP scale
- **Bundle Optimization**: Removes 12KB unused Sonner dependency
- **User Experience**: Consistent, actionable error messages replace generic failures
- **App Stability**: Error boundaries prevent component crashes from breaking entire app
- **Developer Experience**: Single error handling pattern reduces cognitive load
- **Future-Ready**: Architecture supports adding sophisticated patterns when needed

### Negative

- **Limited Offline Support**: Basic `navigator.onLine` checks instead of operation queuing
- **No Circuit Breaking**: Repeated failures not automatically prevented (acceptable for <10k DAU)
- **Generic Fallbacks**: Some error messages remain generic until patterns emerge from usage
- **Manual Expansion**: Error types must be added manually as new scenarios are discovered

### Technical Implications

- **Bundle Size**: Net reduction of ~10KB (remove Sonner, add error utilities)
- **Performance**: Minimal overhead from error boundaries and retry logic
- **Monitoring**: Structured error logging prepares for future Sentry integration
- **Maintenance**: Single error handling system reduces maintenance complexity

### Migration Risk Mitigation

- **Incremental Rollout**: Error boundaries can be added component-by-component
- **Backward Compatibility**: Existing error handling continues working during migration
- **Testing Strategy**: Comprehensive error scenario testing prevents regressions
- **Rollback Plan**: Changes are isolated and easily reversible if issues arise
