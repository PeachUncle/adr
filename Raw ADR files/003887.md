# ADR-003: Model Provider Strategy

**Status:** Proposed

**Date:** 2026-01-09

**Deciders:** [You]

## Context

We need to choose LLM providers for different operations. The original plan assumed Claude API for everything, but:
- Different operations have different quality/cost trade-offs
- Tagging is high-volume, low-complexity (cheap model works)
- Chat/RAG needs better reasoning (quality matters)
- Embeddings require a separate provider (Claude doesn't offer embeddings)

Using multiple providers optimizes cost while maintaining quality where it matters.

## Decision Drivers

* **Cost:** Personal project with budget constraints
* **Quality:** Chat responses need to be good; tagging can be "good enough"
* **Learning goal:** Multi-provider orchestration is a production skill
* **Simplicity:** Don't over-engineer for Phase 1

## Considered Options

1. **Single provider (Claude only)** — Use Claude for everything except embeddings
2. **Cost-optimized multi-provider** — Cheap models for tagging, quality models for chat
3. **Single cheap provider** — Use GPT-4.1 nano for everything

Assuming ~500 tokens per note for tagging:

| Provider | Cost per 1000 notes |
|----------|---------------------|
| GPT-4.1 nano | ~$0.05 |
| Grok 4 Fast | ~$0.10 |
| Claude Haiku 4.5 | ~$0.50 |
| Claude Sonnet 4.5 | ~$1.50 |

**GPT-4.1 nano is 30x cheaper than Claude Sonnet for tagging.**

## Decision Outcome

Chosen option: **"Cost-optimized multi-provider"**

### Provider Assignment

| Operation | Provider | Model | Rationale |
|-----------|----------|-------|-----------|
| **Tagging** | OpenAI | `gpt-4.1-nano` | Cheapest, structured output works well |
| **Embeddings** | OpenAI | `text-embedding-3-small` | Good quality, can reduce dimensions |
| **Chat/RAG** | Anthropic | `claude-sonnet-4-5` | Best reasoning for knowledge synthesis |
| **Simple queries** | xAI | `grok-4-1-fast-non-reasoning` | Optional, for cost reduction |

### Consequences

**Good:**
* 10-30x cost reduction for high-volume tagging
* Best-in-class quality for chat (where it matters)
* Learns production pattern (model arbitrage)
* Abstraction layer already planned in ARCHITECTURE.md

**Bad:**
* Multiple API keys to manage
* More complex error handling (different APIs)
* Potential consistency issues between providers

**Neutral:**
* Need to implement provider abstraction (was already planned)

## Implementation

### Router Pattern

```python
# services/model_router.py
from enum import Enum

class Operation(Enum):
    TAGGING = "tagging"
    EMBEDDING = "embedding"
    CHAT = "chat"
    SIMPLE_QUERY = "simple_query"

class ModelRouter:
    ROUTING_TABLE = {
        Operation.TAGGING: {
            "provider": "openai",
            "model": "gpt-4.1-nano",
            "fallback": "gpt-4.1-mini"
        },
        Operation.EMBEDDING: {
            "provider": "openai",
            "model": "text-embedding-3-small",
            "dimensions": 512  # Reduced for storage
        },
        Operation.CHAT: {
            "provider": "anthropic",
            "model": "claude-sonnet-4-5",
            "fallback": "claude-haiku-4-5"
        },
        Operation.SIMPLE_QUERY: {
            "provider": "xai",
            "model": "grok-4-1-fast-non-reasoning",
            "fallback": "gpt-4.1-nano"
        }
    }

    def get_config(self, operation: Operation) -> dict:
        return self.ROUTING_TABLE[operation]
```
