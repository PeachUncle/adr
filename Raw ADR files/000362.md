# ADR 004: Multi-Tenancy Strategy

## Status
Accepted

## Context

The ASDEFCON platform will serve multiple Defence organizations:
- Different branches (Army, Navy, Air Force)
- Different units within branches
- Different security clearances
- Potential future: Allied nations

Requirements:
- Complete data isolation between tenants
- Shared infrastructure for efficiency
- Tenant context in all operations
- Audit trail per tenant
- Security classification per tenant
- Performance isolation

## Decision

We will implement **Row-Level Multi-Tenancy** with tenant context propagation through JWT tokens.

### Architecture

**Tenant Identification**:
- Tenant ID in JWT claims
- Middleware extracts tenant from token
- All operations scoped to tenant
- No cross-tenant queries allowed

**Data Isolation**:
- `tenant_id` column in all domain tables
- Database queries automatically filtered by tenant
- Repository layer enforces tenant isolation
- Foreign keys include tenant_id
- Unique constraints include tenant_id

**Authentication Flow**:
```
1. User logs in → Auth service
2. Auth service verifies credentials
3. JWT issued with tenant_id claim
4. Every API request includes JWT
5. Middleware extracts tenant_id
6. Request context includes tenant_id
7. All queries filtered by tenant_id
```

### Implementation

**Database Schema**:
```sql
-- Every table has tenant_id
CREATE TABLE documents (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    title TEXT NOT NULL,
    content TEXT,
    created_at TIMESTAMPTZ NOT NULL,
    CONSTRAINT fk_tenant FOREIGN KEY (tenant_id) REFERENCES tenants(id)
);

-- Composite indexes for performance
CREATE INDEX idx_documents_tenant ON documents(tenant_id, created_at);

-- Unique constraints include tenant_id
CREATE UNIQUE CONSTRAINT uq_document_ref
    ON documents(tenant_id, reference_number);

-- Row-level security (optional additional layer)
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON documents
    USING (tenant_id = current_setting('app.current_tenant_id')::UUID);
```

**Domain Model**:
```python
from __future__ import annotations
from dataclasses import dataclass
from uuid import UUID

@dataclass(frozen=True)
class TenantId:
    """Value object for tenant identifier."""
    value: UUID

class Document:
    """All entities have tenant_id."""
    def __init__(
        self,
        id: UUID,
        tenant_id: TenantId,
        title: str,
        content: str,
    ):
        self._id = id
        self._tenant_id = tenant_id
        self._title = title
        self._content = content

    @property
    def tenant_id(self) -> TenantId:
        return self._tenant_id
```

**Repository Layer**:
```python
class DocumentRepository(Protocol):
    """All repository methods implicitly scoped to tenant."""

    async def find_by_id(
        self,
        id: UUID,
        tenant_id: TenantId,
    ) -> Document | None:
        """Find document by ID within tenant scope."""
        ...

    async def find_all(
        self,
        tenant_id: TenantId,
        filters: Filters,
    ) -> list[Document]:
        """Find all documents for tenant."""
        ...

class PostgresDocumentRepository:
    """Implementation enforces tenant filtering."""

    async def find_by_id(
        self,
        id: UUID,
        tenant_id: TenantId,
    ) -> Document | None:
        query = (
            select(DocumentModel)
            .where(DocumentModel.id == id)
            .where(DocumentModel.tenant_id == tenant_id.value)
        )
        result = await self.session.execute(query)
        return self._to_domain(result.scalar_one_or_none())
```

**Middleware**:
```python
from fastapi import Request, HTTPException
from jose import jwt, JWTError

class TenantMiddleware:
    """Extract tenant from JWT and inject into request state."""

    async def __call__(self, request: Request, call_next):
        # Extract JWT
        auth_header = request.headers.get("Authorization")
        if not auth_header:
            raise HTTPException(401, "Missing authorization")

        token = auth_header.replace("Bearer ", "")

        try:
            # Decode and verify JWT
            payload = jwt.decode(
                token,
                settings.JWT_SECRET,
                algorithms=["HS256"],
            )

            # Extract tenant
            tenant_id = payload.get("tenant_id")
            if not tenant_id:
                raise HTTPException(401, "Missing tenant in token")

            # Inject into request state
            request.state.tenant_id = TenantId(UUID(tenant_id))
            request.state.user_id = UUID(payload["sub"])

        except JWTError:
            raise HTTPException(401, "Invalid token")

        response = await call_next(request)
        return response
```

**Dependency Injection**:
```python
from fastapi import Depends, Request

def get_tenant_id(request: Request) -> TenantId:
    """Extract tenant from request state."""
    return request.state.tenant_id

def get_document_repository(
    tenant_id: TenantId = Depends(get_tenant_id),
) -> DocumentRepository:
    """Inject repository with tenant context."""
    return PostgresDocumentRepository(
        session=get_session(),
        tenant_id=tenant_id,
    )

# Usage in route
@router.get("/documents/{id}")
async def get_document(
    id: UUID,
    tenant_id: TenantId = Depends(get_tenant_id),
    repo: DocumentRepository = Depends(get_document_repository),
):
    doc = await repo.find_by_id(id, tenant_id)
    if not doc:
        raise HTTPException(404)
    return doc
```

## Alternatives Considered

### 1. Database per Tenant

**Pros**:
- Complete isolation
- Independent backups
- Easier to migrate away

**Cons**:
- Operational complexity (many databases)
- Higher cost
- Schema migration complexity
- Connection pool overhead

**Rejected**: Too complex for our needs, over-engineered.

### 2. Schema per Tenant

**Pros**:
- Good isolation
- Single database

**Cons**:
- PostgreSQL schema overhead
- Migration complexity
- Query complexity

**Rejected**: Row-level simpler, performs well.

### 3. No Multi-Tenancy

**Rejected**: Business requirement, needed from day 1.

## Consequences

### Positive

- **Security**: Tenant data completely isolated
- **Performance**: Single database, good query performance with indexes
- **Cost Efficient**: Shared infrastructure
- **Simple Operations**: One database to backup/maintain
- **Flexible**: Easy to add new tenants
- **Scalable**: Proven pattern, scales to millions of tenants

### Negative

- **Query Complexity**: Every query needs tenant_id filter
- **Developer Burden**: Must remember tenant_id everywhere
- **Migration Risk**: Forgetting tenant_id in query = data leak
- **Schema Changes**: Must update all tables
- **Testing**: Need multi-tenant test scenarios

### Mitigations

- **Code Generation**: Repository templates include tenant filtering
- **Type Safety**: TenantId value object prevents mistakes
- **Middleware**: Automatic tenant injection
- **Tests**: Unit tests verify tenant isolation
- **Database Constraints**: Foreign keys enforce relationships
- **Optional RLS**: Row-level security as additional safety layer
- **Code Review**: Checklist includes tenant verification

## Security Considerations

**Prevent Cross-Tenant Access**:
1. Always filter by tenant_id
2. Verify tenant in JWT is valid
3. Audit log all tenant switches (if allowed)
4. Rate limit per tenant
5. Monitor for suspicious cross-tenant attempts

**Data Leakage Prevention**:
1. No global queries without tenant filter
2. Repository layer enforces tenant
3. Integration tests verify isolation
4. Automated security scanning

**Audit Trail**:
```python
# Every mutation logged with tenant context
audit_log.record(
    tenant_id=tenant_id,
    user_id=user_id,
    action="document.created",
    resource_id=document.id,
    details={"title": document.title},
)
```

## Performance Optimization

**Indexes**:
- Composite indexes: `(tenant_id, created_at)`
- Most queries start with tenant_id filter
- Very efficient B-tree lookups

**Partitioning** (future):
```sql
-- If needed for very large datasets
CREATE TABLE documents (
    ...
) PARTITION BY HASH (tenant_id);
```

**Caching**:
- Redis cache includes tenant_id in key
- Format: `tenant:{tenant_id}:resource:{id}`

**Connection Pooling**:
- Shared pool across tenants
- Consider tenant-specific pools for VIP tenants

## Testing Strategy

**Unit Tests**:
```python
@pytest.mark.asyncio
async def test_cannot_access_other_tenant_document():
    tenant1 = TenantId(uuid4())
    tenant2 = TenantId(uuid4())

    # Create document for tenant1
    doc = await repo.save(
        Document(id=uuid4(), tenant_id=tenant1, ...),
        tenant_id=tenant1,
    )

    # Try to access with tenant2
    result = await repo.find_by_id(doc.id, tenant_id=tenant2)

    assert result is None  # Isolated!
```

## Migration Path

If we need database-per-tenant later:
1. Export each tenant's data
2. Create separate databases
3. Import tenant data
4. Update connection logic
5. Minimal application changes (repository interface unchanged)
