## Context

The system architecture, particularly in ADR-004 (BigQuery Analytics) and ADR-006 (IB Gateway), specifies that the `IBGatewayAgent` must publish a high-throughput stream of raw market data. This data is then consumed by the `Data Ingestion Service` for archival into BigQuery.

This architectural pattern requires a message broker or stream service to act as an intermediary. This service is critical for decoupling the real-time operational components from the analytical/archival components, ensuring that a slowdown or failure in the data ingestion process does not impact the performance or availability of the live trading gateway.

## Decision

We will use **Google Cloud Pub/Sub** as the message stream service for all asynchronous, event-driven communication between decoupled services, with the primary initial use case being the market data stream.

## Rationale

1.  **GCP Native Integration**: As our project is standardized on Google Cloud Platform, Pub/Sub offers seamless, out-of-the-box integration with our other key services, including IAM for security, Cloud Monitoring for observability, and BigQuery for direct data ingestion if needed later.
2.  **Serverless and Fully Managed**: Pub/Sub is a serverless offering, which aligns with our goal of minimizing operational overhead. It automatically handles scaling, partitioning, and replication without requiring any manual infrastructure management.
3.  **Extreme Scalability and Performance**: Pub/Sub is designed to handle millions of messages per second with low latency. This ensures it can easily manage extreme spikes in market data volume during periods of high volatility without becoming a bottleneck.
4.  **Reliability**: It provides at-least-once delivery guarantees and message durability. This is critical for ensuring that no market data is lost between the gateway and the archival service, which is essential for the integrity of our historical dataset.
5.  **Cost-Effectiveness**: The pay-per-use pricing model (based on data volume) is highly cost-effective for this workload, as we only pay for the data that flows through the system.

## Consequences

-   **New Dependency**: The project will require the `google-cloud-pubsub` Python library.
-   **Implementation**:
    -   The `IBGatewayAgent` will be updated to include a Pub/Sub publisher client to publish messages to a designated "market-data" topic.
    -   The `Data Ingestion Service` will be implemented as a Pub/Sub subscriber that pulls messages from the corresponding subscription.
-   **Infrastructure**: A new Pub/Sub topic and subscription will need to be defined and managed via our Infrastructure as Code (IaC) setup.
-   **Local Development**: For local testing, we will use the Pub/Sub emulator, which is part of the Google Cloud CLI.

## Alternatives Considered

-   **Self-Hosted RabbitMQ/Kafka**: These are powerful open-source message brokers. However, they would require us to provision, manage, and scale our own virtual machines, which directly contradicts our preference for using managed services to reduce operational burden.
-   **Direct HTTP Calls**: The gateway could call an API endpoint on the ingestion service directly. This was rejected as it is a brittle, tightly-coupled approach that offers no durability. A failure in the ingestion service would cause the gateway to either block or lose data.

## Implementation Strategy

### Phase 1: Infrastructure Setup (Week 1)
**Deliverables**:
- Create Pub/Sub topic: `market-data-stream`
- Create subscription: `bigquery-ingestion-sub` (pull subscription)
- Configure IAM permissions for publishers and subscribers
- Set up message retention (7 days) and acknowledgment deadlines (60s)
- Terraform configuration for all Pub/Sub resources
- Enable dead-letter topic for failed messages

**Dependencies**: GCP project setup, ADR-019 (Terraform) infrastructure

### Phase 2: Publisher Integration (Week 1-2)
**Deliverables**:
- Install `google-cloud-pubsub` Python library
- Implement publisher client in `IBGatewayAgent`
- Add message batching (100 messages or 1MB, whichever first)
- Implement error handling and retry logic
- Add message attributes (timestamp, symbol, data_type)
- Unit tests for publisher with emulator
- Performance testing for message throughput

**Dependencies**: Phase 1 complete, ADR-006 (IB Gateway) implementation

### Phase 3: Subscriber Implementation (Week 2-3)
**Deliverables**:
- Create `Data Ingestion Service` as Cloud Run service
- Implement Pub/Sub pull subscriber
- Add message parsing and validation
- Implement BigQuery streaming insert batching
- Add dead-letter queue handling
- Integration tests with Pub/Sub emulator
- End-to-end tests with test topic

**Dependencies**: Phase 2 complete, ADR-004 (BigQuery) setup, ADR-016 (Cloud Run)

### Phase 4: Monitoring and Optimization (Week 3-4)
**Deliverables**:
- Configure Cloud Monitoring for Pub/Sub metrics
- Set up alerting for unacknowledged messages, publish errors, subscription lag
- Implement message flow rate monitoring
- Performance optimization (batch sizes, concurrent pull)
- Documentation for operational procedures
- Load testing with simulated market data volume

**Dependencies**: Phase 3 complete, ADR-021 (Observability) implementation

## Cost Analysis

### Monthly Operational Costs

**Pub/Sub Message Costs**:
- Message ingestion: First 10GB free, then $0.06/GB
- Estimated volume: 2GB/day = 60GB/month
- Message cost: (60GB - 10GB) × $0.06 = $3.00/month
- Message delivery: Same as ingestion = $3.00/month
- **Subtotal**: $6.00/month

**Message Storage**:
- Snapshot storage (7-day retention): 14GB average × $0.27/GB = $3.78/month
- Seek/replay operations: Minimal (<$0.50/month)
- **Subtotal**: $4.28/month

**Data Transfer**:
- Egress within same region (to Cloud Run): Free
- Egress to BigQuery: Free (GCP internal)
- **Subtotal**: $0/month

**Total Estimated Monthly Cost**: $10.28/month

### Cost Optimization Strategies

1. **Message Batching**:
   - Batch up to 100 messages per publish call
   - Reduces API overhead by 95%
   - Estimated savings: $15-20/month vs individual publishes

2. **Same-Region Deployment**:
   - All services (Pub/Sub, Cloud Run, BigQuery) in us-central1
   - Zero data transfer costs between services
   - Estimated savings: $30-50/month vs cross-region

3. **Message Compression**:
   - Compress message payload before publishing
   - Reduces data volume by 60-70%
   - Estimated savings: $4-5/month on message costs

4. **Optimized Retention**:
   - 7-day retention vs default 31 days
   - Reduces storage costs by 75%
   - Estimated savings: $10-12/month

### ROI Comparison

**vs Self-Hosted RabbitMQ**:
- GCE instance (n1-standard-2): $50/month
- Storage (100GB SSD): $17/month
- Maintenance overhead: 10% engineering time
- Pub/Sub managed: $10.28/month
- **Cost Savings**: 80% reduction + zero operational overhead

**vs Self-Hosted Kafka**:
- GCE instance (n1-standard-4): $100/month
- Storage (500GB SSD): $85/month
- Zookeeper instance: $50/month
- Maintenance overhead: 20% engineering time
- Pub/Sub managed: $10.28/month
- **Cost Savings**: 95%+ reduction + zero operational overhead

## Risk Assessment

| Risk | Severity | Likelihood | Impact | Mitigation |
|------|----------|------------|--------|------------|
| Message loss during publish | High | Low | Data gaps in BigQuery, incomplete audit trail | At-least-once delivery guarantee, publisher retry logic, message acknowledgment tracking |
| Subscription lag/backlog | Medium | Medium | Delayed data ingestion, stale analytics | Auto-scaling subscribers, backlog monitoring, alerting at 10K unacked messages |
| Message ordering violations | Low | Medium | Incorrect time-series reconstruction | Message timestamps, client-side ordering, ordered delivery keys for critical streams |
| Pub/Sub service outage | High | Very Low | Complete data pipeline failure | Regional redundancy option, local buffering in gateway, replay from snapshot after recovery |
| Dead-letter queue overflow | Medium | Low | Lost error messages | DLQ monitoring, automated investigation triggers, manual review processes |
| Cost overrun from high volume | Low | Medium | Budget exceeded | Daily volume monitoring, alerting at $15/day, message compression, retention tuning |
| Subscriber processing failures | Medium | Medium | Message redelivery, duplicate inserts | Idempotent BigQuery inserts, deduplication logic, exponential backoff on errors |

## Monitoring and Success Criteria

### Key Metrics

**Pub/Sub Publisher Performance**:
1. Publish success rate: >99.9%
2. Publish latency: <100ms p95, <500ms p99
3. Message throughput: 500-1000 messages/second sustained
4. Batch efficiency: >90% of publishes use full batch size

**Pub/Sub Subscriber Performance**:
1. Message processing latency: <5 seconds p95
2. Acknowledgment rate: >99.5%
3. Subscriber lag: <1 minute under normal load
4. Dead-letter queue size: <100 messages

**System Health**:
1. Unacknowledged message count: <5000 (backlog indicator)
2. Oldest unacknowledged message age: <5 minutes
3. End-to-end latency (publish to BigQuery): <10 seconds p95
4. Message loss rate: 0%

### Alerting Thresholds

**Critical Alerts (PagerDuty)**:
- Pub/Sub topic unavailable for >5 minutes
- Subscription lag >10 minutes
- Dead-letter queue >1000 messages
- Publish error rate >5%
- Subscriber completely stopped

**Warning Alerts (Email)**:
- Unacknowledged messages >10,000
- Publish latency >1 second p95
- Subscriber lag >5 minutes
- Dead-letter queue >100 messages
- Daily message volume >150% of baseline

**Informational Alerts (Dashboard)**:
- Hourly message volume trends
- Batch size distribution
- Publish/subscribe latency percentiles
- Cost trending (daily)

### Success Criteria

**Functional Requirements**:
- At-least-once delivery guarantee maintained
- Zero message loss during normal operations
- Subscriber can replay messages from any point in 7-day window
- Dead-letter queue captures all processing failures

**Performance Requirements**:
- End-to-end latency <10 seconds p95
- Support 1000 messages/second sustained throughput
- Subscriber lag <1 minute under normal load
- System recovers from backlog within 15 minutes

**Cost Requirements**:
- Monthly cost <$15 for typical trading volumes
- Cost per million messages <$2.50
- No single day exceeding $2 in Pub/Sub costs
- Storage costs <$5/month with 7-day retention

**Operational Requirements**:
- Zero manual intervention for normal operations
- Automated backlog clearing through auto-scaling
- Self-healing subscriber with exponential backoff
- Quarterly load testing to validate capacity
