# ADR 0001: Lite3 Reference Implementation Layout (bit-level + pseudocode)

Status: Draft

## Context

TRON needs a language-agnostic description of the reference implementation prototype from `https://github.com/fastserial/lite3`. The goal of this ADR is to capture the wire/memory layout and the key algorithms at the bit level, without tying the narrative to C or any specific runtime. The Lite3 design notes at `https://lite3.io/design_and_limitations.html` are used to confirm the byte layout and documented limitations.

## Decision

Adopt the Lite3 reference implementation's data layout and core algorithms as the prototype baseline for TRON. This ADR documents the observable layout and operations as implemented, focusing on:

- B-tree node layout and bit-level fields.
- key/value entry encoding.
- Lookup and insertion pseudocode.
- Generation-based invalidation semantics.

### Constants (fixed configuration)

The reference implementation bakes several constants into the format. These defaults are part of the on-the-wire contract for interoperability, and metadata is packed into two u32 fields (`GenType` and `EntriesNodeSize`).

#### Byte-sized fields

| Constant             | Value / definition | Rationale                                                                                 |
| -------------------- | ------------------ | ----------------------------------------------------------------------------------------- |
| RelPtrSize         | 4 bytes            | Size of relative node and entry offsets (u32).                                            |
| NodeAlignment       | 4 bytes            | Fixed to the largest field size (u32) in the node structure to keep native reads aligned. |
| TypeTag             | 1 byte             | Tagged union discriminator for schemaless decoding.                                       |
| LenPrefixMinBytes | 1 byte             | Minimum length prefix size for bytes/string payloads.                                     |
| LenPrefixMaxBytes | 4 bytes            | Maximum length prefix size for bytes/string payloads; size encoded in the `TypeTag`.       |

#### Bitfield widths and masks

| Constant      | Value / definition | Rationale                                                                                 |
| ------------- | ------------------ | ----------------------------------------------------------------------------------------- |
| EntriesBits  | 28                 | Bit width of `Entries` stored in `EntriesNodeSize`.                                      |
| NodeSizeBits | 3                  | Bit width of `NodeSize` stored in `EntriesNodeSize` (`NodeSize = N - 2`).                |
| KeyCountBits | 9                  | Bit width of `KeyCount` stored in `GenType`.                                             |
| GenCountBits | 15                 | Bit width of the generation counter stored in `GenType`.                                 |
| TypeTagBits  | 8                  | Bit width of the value type tag stored in `GenType` (low byte).                           |

#### Limits and defaults

| Constant         | Value / definition | Rationale                                                                                      |
| ---------------- | ------------------ | ---------------------------------------------------------------------------------------------- |
| DefaultMaxKeys | 7                  | Default max keys per node for non-canonical construction (corresponds to N=3, 96-byte nodes).  |
| HashProbeMax   | 16                 | Upper bound for quadratic probing to resolve hash collisions.                                  |

Derived constants and formulas are based on $K = 2^{N} - 1$ (`MaxKeys`), where $N \ge 2$ (so $K = 3, 7, 15, \dots$). $N$ is stored per node in `EntriesNodeSize` as a 3-bit code (`NodeSize = N - 2`).

$$\mathrm{MaxChildren} = K + 1 = 2^{N}$$

$$\mathrm{NodeSize} = 4 \cdot (1 + K + 1 + K + (K + 1)) = 4(3K + 3)\,\mathrm{bytes}$$

$$\mathrm{MinKeys} = 2^{N-1} - 1$$
Minimum keys per non-root node.

### Derived per-node/per-config values

These are computed per-node from $N$ and are not standalone constants.

| Value          | Definition                                              | Notes                                                       |
| -------------- | ------------------------------------------------------- | ----------------------------------------------------------- |
| MaxChildren   | $K + 1 = 2^{N}$                                         | Derived from MaxKeys.                                      |
| NodeSize      | $4(3K + 3)$ bytes                                       | Derived from MaxKeys (includes `EntriesNodeSize`).         |
| EntriesOffset | $4 (K + 1)$ bytes                                       | Offset of `EntriesNodeSize` within the node layout.        |
| ContainerMax  | $2^{28} - 1$ entries                                    | Max entries per object/array given a 28-bit entries field. |
| TreeHeightMax | $\lceil \log_{t}((\mathrm{ContainerMax}+1)/2) \rceil$   | Upper bound on tree height for a given N.                 |

$$\mathrm{ContainerMax} = 2^{28} - 1\,\mathrm{entries}$$

$$t = 2^{N-1}$$
Minimum degree for $N \ge 2$.

$$\mathrm{TreeHeightMax} \ge \left\lceil \log_{t} \left(\frac{\mathrm{ContainerMax} + 1}{2}\right) \right\rceil$$

With `RelPtrSize = 4` bytes for offsets and a contiguous buffer, `NodeSize` must fit within $2^{32}$ bytes. The 3-bit `NodeSize` field constrains $N$ to 2-9 (so $K \le 511$). Values outside this range are invalid.

The table below lists derived values for all valid $N$ (2-9). `ContainerMax` is constant at $2^{28} - 1$ entries because `Entries` is 28 bits, so it is omitted from the table. `TreeHeightMax` uses the formula above.

| N   | MaxKeys (K) | NodeSize (bytes) | EntriesOffset (bytes) | TreeHeightMax (upper bound) |
| --- | ------------ | ----------------- | ---------------------- | ----------------------------- |
| 2   | 3            | 48                | 16                     | 27                            |
| 3   | 7            | 96                | 32                     | 14                            |
| 4   | 15           | 192               | 64                     | 9                             |
| 5   | 31           | 384               | 128                    | 7                             |
| 6   | 63           | 768               | 256                    | 6                             |
| 7   | 127          | 1536              | 512                    | 5                             |
| 8   | 255          | 3072              | 1024                   | 4                             |
| 9   | 511          | 6144              | 2048                   | 4                             |

### Buffer overview (contiguous)

The buffer is a single contiguous byte array. The root container is stored at offset `0` as a B-tree node. All offsets in nodes are 32-bit unsigned integers measured from the start of the buffer, and new nodes/entries are appended to the end of the buffer as the structure grows.

| Segment 1                | Segment 2                | Segment 3       |
| ------------------------ | ------------------------ | --------------- |
| Root node (object/array) | key/value entries + data | child nodes ... |

### Node layout (fixed size, aligned)

Each node is a fixed-size record aligned to `NodeAlignment` bytes (fixed at 4). `NodeSize` is derived from $N$ stored in `EntriesNodeSize`. The default configuration uses `DefaultMaxKeys = 7` (N=3, 96-byte nodes). All nodes within the same object/array must use the same $N$.

| GenType | Hashes[MaxKeys] | EntriesNodeSize | KvOfs[MaxKeys] | ChildOfs[MaxKeys+1] |
| -------- | ---------------- | ---------------- | ---------------- | --------------------- |
| u32      | u32[]            | u32              | u32[]            | u32[]                 |

#### GenType (u32)

Lower 8 bits store the value type. The next 15 bits store the generation counter. The upper 9 bits store `KeyCount`.

| bits 31..23   | bits 22..8    | bits 7..0 |
| ------------- | ------------ | --------- |
| KeyCount (9b) | GenCount (15b) | TypeTag (8b) |

#### EntriesNodeSize (u32)

Lower 28 bits store `Entries` (entry count). The next 3 bits store `NodeSize`, which encodes the node order $N$ (where $K = 2^{N} - 1$). The encoding is `NodeSize = N - 2`, so $N = \mathrm{NodeSize} + 2$. The top bit is reserved and must be zero.

| bit 31 | bits 30..28  | bits 27..0    |
| ------ | ------------ | ------------- |
| 0      | NodeSize (3b) | Entries (28b) |

#### Entries (28b)

Entry count (number of entries in this object/array). Maximum value is $2^{28} - 1$.

#### KeyCount (9b)

Number of keys stored in this node (stored in `GenType`). Must be <= `MaxKeys` (where $K = 2^{N} - 1$).

### Key entry layout (objects)

Object entries store a variable-size `KeyTag` followed by a null-terminated key string. Array entries omit the key entirely (index is derived from the hash). The `KeyTag` is variable-length to keep small keys compact: 1 byte for `KeySize` <= 63 bytes, up to 4 bytes for larger keys.

| KeyTag (1..4 bytes) | Key bytes (includes 0x00) |
| -------------------- | ------------------------- |
| KeyTag bytes        | KeySize bytes            |

`KeyTag` is a little-endian integer stored in 1, 2, or 4 bytes (the reference computation never emits 3).

| high bits     | low 2 bits                |
| ------------- | ------------------------- |
| KeySize bits | TagSizeMinus1 (2 bits) |

`TagSize` = `TagSizeMinus1` + 1 (range: 1..4)
`KeySize` = number of key bytes, including the null terminator.

### Value entry layout

All values begin with a 1-byte `TypeTag`. Scalar payloads are written immediately after the tag; `bool` encodes its value in the tag and has no payload. For `bytes` and `string`, the payload begins with a 1..4 byte little-endian length; the length size is encoded in the `TypeTag`. For `object` and `array`, the value entry is a full node; the `TypeTag` is the low byte of `Node.GenType`.

Alignment padding inserted before object/array values is reserved and must be zero.

| Type   | Payload (size depends on type) |
| ------ | ------------------------------ |
| 1 byte | type-specific bytes            |

| Type   | Len (1..4 bytes) | bytes...  |
| ------ | ---------------- | --------- |
| 1 byte | LenBytes bytes  | Len bytes |

| Node (NodeSize bytes total) |
| ---------------------------- |
| object/array value           |

#### Value TypeTag table

`TypeTag` byte values are a bitfield. Only one category bit may be set at a time (or none for `null`), bit 0 is the subtype/value selector for that category, and bits 6..5 encode the length prefix size for length-prefixed types.

| Mask | Name         | Meaning                                                                                         |
| ---- | ------------ | ----------------------------------------------------------------------------------------------- |
| 0x02 | IsBool      | Bool tag; bit 0 is the value (0 = false, 1 = true).                                             |
| 0x04 | IsNumber    | Numeric tag; bit 0 selects i64 (0) vs f64 (1).                                                  |
| 0x08 | IsVarLen   | Var-len tag; bit 0 selects bytes (0) vs string (1).                                             |
| 0x10 | IsContainer | Container tag; bit 0 selects object (0) vs array (1).                                           |
| 0x60 | LenSize     | For bytes/string only: LenBytes = 1 + ((Type >> 5) & 0x03). Must be zero for other categories. |

Derived tag constants (common combinations):

| Value | Name      | Meaning                                   |
| ----- | --------- | ----------------------------------------- |
| 0x02  | IsFalse  | Bool false tag.                           |
| 0x03  | IsTrue   | Bool true tag.                            |
| 0x04  | IsInt    | i64 tag.                                  |
| 0x05  | IsFloat  | f64 tag.                                  |
| 0x08  | IsBytes  | bytes tag base (LenCode may be `OR`ed).  |
| 0x09  | IsString | string tag base (LenCode may be `OR`ed). |
| 0x10  | IsObject | object tag.                               |
| 0x11  | IsArray  | array tag.                                |

| Type byte                     | Name         | Follow bytes    | Details                                                                                                        |
| ----------------------------- | ------------ | --------------- | -------------------------------------------------------------------------------------------------------------- |
| 0x00                          | null         | 0               | No payload.                                                                                                    |
| 0x02 / 0x03                   | bool         | 0               | 0x02 = false, 0x03 = true (payload in tag).                                                                    |
| 0x04 / 0x05                   | number       | 8               | 0x04 = i64, 0x05 = f64.                                                                                        |
| 0x08 / 0x09 + (LenCode << 5) | bytes/string | LenBytes + Len | LenCode in 0..3 selects LenBytes = 1..4; base 0x08 = bytes, 0x09 = string (length includes null terminator). |
| 0x10 / 0x11                   | object/array | NodeSize - 1   | 0x10 = object, 0x11 = array; `TypeTag` is low byte of `Node.GenType`.                                         |

TypeTag bit diagrams (bit 7 is MSB, bit 0 is LSB):

```text
null:      0 0 0 0 0 0 0 0
bool:      0 0 0 0 0 0 1 V    (V: 0 = false, 1 = true)
number:    0 0 0 0 0 1 0 T    (T: 0 = i64, 1 = f64)
bytes:     0 L L 0 1 0 0 T    (L: LenCode 0..3 -> LenBytes 1..4; T: 0 = bytes, 1 = string)
container: 0 0 0 1 0 0 0 T    (T: 0 = object, 1 = array)
```

Only the combinations above are valid; for non-bytes categories, LenSize bits must be zero.

### Hashing and indexing

Objects use a 32-bit hash of the key string. The reference implementation uses DJB2 (including compile-time hashing for string literals). For TRON, FNV-1 is selected; see [appendix-hash-probing.md](appendix-hash-probing.md) for the probe analysis. Arrays use the numeric index directly as the hash. To resolve hash collisions, TRON uses quadratic probing with a fixed probe limit (default 16). The original Lite3 implementation failed on collisions (no probing).

```
ProbeHash = BaseHash + Attempt * Attempt
```

Each object has its own key space; collisions only occur within that object.

### Pseudocode (language-agnostic)

#### KeyTag size

```text
function KeyTagSize(KeySize):
    if KeySize == 0:
        return 0
    SizeGe26  = (KeySize >> 6)  != 0
    SizeGe214 = (KeySize >> 14) != 0
    return (SizeGe214 ? 2 : 0) + (SizeGe26 ? 1 : 0) + 1
```

#### Encode KeyTag

```text
function EncodeKeyTag(KeySize, TagSize):
    # little-endian integer, low 2 bits hold TagSize - 1
    TagValue = (KeySize << 2) | (TagSize - 1)
    WriteLeBytes(TagValue, TagSize)
```

#### Verify key entry

```text
function VerifyKey(Buf, BufLen, Ofs, ExpectedKeyBytesOrNull):
    TagSize = (Buf[Ofs] & 0b11) + 1
    TagValue = ReadLeBytes(Buf, Ofs, TagSize)
    KeySize = TagValue >> 2
    Ofs += TagSize
    if Ofs + KeySize > BufLen:
        Error("key out of bounds")
    if ExpectedKeyBytesOrNull is not null:
        if Buf[Ofs : Ofs + KeySize] != ExpectedKeyBytesOrNull:
            return "hash collision"
    return "ok", Ofs + KeySize
```

#### Verify value entry

```text
function VerifyVal(Buf, BufLen, Ofs):
    if Ofs + 1 > BufLen:
        Error("value out of bounds")
    Type = Buf[Ofs]
    Ofs += 1
    PayloadSize = TypeSize(Type)
    if Type == IsBytes or Type == IsString:
        if Ofs + 4 > BufLen:
            Error("value out of bounds")
        Len = ReadLeU32(Buf, Ofs)
        PayloadSize += Len
    if Ofs + PayloadSize > BufLen:
        Error("value out of bounds")
    return "ok", Ofs + PayloadSize
```

#### B-tree lookup (Get)

```text
function Get(Buf, BufLen, RootOfs, Key, KeyHash, KeySize):
    TagSize = KeyTagSize(KeySize)
    for Attempt in 0 .. HashProbeMax-1:
        Hash = KeyHash + Attempt * Attempt
        Node = ReadNode(Buf, RootOfs)
        while true:
            i = LowerBound(Node.Hashes, Node.KeyCount, Hash)
            if i < Node.KeyCount and Node.Hashes[i] == Hash:
                KvOfs = Node.KvOfs[i]
                if Key is not null:
                    Status, AfterKey = VerifyKey(Buf, BufLen, KvOfs, Key)
                    if Status == "hash collision":
                        break  # try next probe
                Status, Ignored = VerifyVal(Buf, BufLen, KvOfs)
                if Status == "ok":
                    return KvOfs
            if Node.ChildOfs[0] == 0:
                Error("not found")
            Node = ReadNode(Buf, Node.ChildOfs[i])
    Error("probe limit reached")
```

#### B-tree insertion (Set)

```text
function Set(Buf, BufLen, RootOfs, KeyOrNull, KeyHash, KeySize, ValLen):
    TagSize = KeyTagSize(KeySize)
    EntrySize = TagSize + KeySize + 1 + ValLen
    Root = ReadNode(Buf, RootOfs)
    Root.Gen += 1  # invalidate outstanding references
    for Attempt in 0 .. HashProbeMax-1:
        Hash = KeyHash + Attempt * Attempt
        Node = Root
        Parent = null
        while true:
            if Node.KeyCount == Node.MaxKeys:
                SplitNode(Buf, Node, Parent, RootOfs)
                # continue with updated Node/Parent
            i = LowerBound(Node.Hashes, Node.KeyCount, Hash)
            if i < Node.KeyCount and Node.Hashes[i] == Hash:
                KvOfs = Node.KvOfs[i]
                if KeyOrNull is not null:
                    Status, AfterKey = VerifyKey(Buf, BufLen, KvOfs, KeyOrNull)
                    if Status == "hash collision":
                        break  # try next probe
                # overwrite in place or append if size grows
                return KvOfs
            if Node.ChildOfs[0] != 0:
                Parent = Node
                Node = ReadNode(Buf, Node.ChildOfs[i])
            else:
                # insert new kv entry (and key if object)
                InsertIntoNode(Buf, Node, i, Hash, EntrySize)
                KvOfs = AppendEntry(Buf, KeyOrNull, TagSize, KeySize, ValLen)
                return KvOfs
    Error("probe limit reached")
```

### Mutation semantics (reference implementation behavior)

- New nodes and key/value entries are appended to the end of the buffer; index updates are done in-place, so buffer growth is append-only.
- When updating an existing key/index:
  - If the new encoded value length is smaller than the existing entry length, the value is overwritten in place (and the old value bytes are zeroed when deleted-bytes zeroing is enabled). Fixed-size scalars (`null`, `bool`, `i64`, `f64`) always fit in place; `bytes`/`string` fit only when the new length is <= the old length.
  - If the new encoded value length is equal to or larger than the existing entry length, a new entry is appended and the node's `KvOfs` is updated to point to the new entry. The old entry bytes are zeroed when deleted-bytes zeroing is enabled.
- Object/array values are full nodes and are aligned to `NodeAlignment`.
- Zeroing extra node slots makes the buffer deterministic; it is required for canonicalization and recommended for compression.
- Disabling deleted-bytes zeroing leaves deleted data in the buffer until overwritten.
- Alignment padding bytes (added before object/array values) are reserved and must be zeroed; canonical encodings require them to be zero.

### Canonical encoding and rewrite

Canonical encoding is defined over the logical data model, not the original byte layout. Any TRON buffer can be rewritten into canonical form by decoding the logical structure and re-encoding with the rules below.

- Object keys are inserted in lexicographic order; array elements are inserted in ascending index order; nested containers are emitted depth-first.
- Node order is chosen deterministically from total key count for the container: $N = \max(2, \lceil \log_{2}(\mathrm{KeyCount} + 1) \rceil)$, yielding $K = 2^{N} - 1$ and `NodeSize = 4(3K + 3)` bytes.
- All nodes in the same object/array use the chosen $N$.
- Reserved bytes (alignment padding and extra node slots) are zeroed.

### Generation-based invalidation

The generation counter is stored in the 15-bit `GenCount` field of `GenType` (range 0..32,767). Every mutation increments this counter at the container root and wraps modulo $2^{15}$. Pointers returned by lookup routines store the generation at the time of lookup; consumers must check that their reference generation matches the current buffer generation before dereferencing.

### Interop constraints (as implemented)

- Multi-byte fields (`u32` values in nodes, entries, and lengths) are written in little-endian order. Encoders and decoders must use little-endian.
- Node order $N$ is encoded in `EntriesNodeSize`; decoders must support $N$ in the valid range (2-9).
- Nodes are aligned to `NodeAlignment` (fixed at 4). Object/array values are padded to preserve alignment.
- Buffer size is limited to $2^{8 \cdot \mathrm{RelPtrSize}}$ bytes (4 GiB with 4-byte offsets). Container size is limited to $2^{28} - 1$ entries by the 28-bit entries field (practical limits may be lower due to buffer size and node/data overhead).

## Consequences

- B-tree indexing enables `O(log n)` lookup, insertion, and mutation directly in the buffer.
- The layout is compact and avoids extra indirection, but it ties interoperability to fixed `NodeSize` and alignment and a fixed little-endian encoding.
- Objects and arrays share the same physical representation, with arrays omitting key storage and using index hashes.
- Generation-based invalidation makes zero-copy reads safe but requires callers to revalidate references after mutation.
- Deletions can leave holes in the buffer; the reference implementation zeros deleted bytes by default and documents defragmentation as planned work.

## Design and limitations (non-normative background)

Differences from the Lite3 original:

- Hashing: this spec selects FNV-1 for object key hashing; the Lite3 reference implementation uses DJB2 (including compile-time hashing for literals). See [appendix-hash-probing.md](appendix-hash-probing.md) for the probe analysis.
- Quadratic probing: this spec sets `HashProbeMax = 16`; the original Lite3 implementation failed on collisions (no probing).
- Explicit spec: this repository provides a normative, language-agnostic specification that fixes constants and layout rules; Lite3 is primarily an implementation and design document.
- Canonical rewrite: this spec defines a deterministic canonical re-encoding process, including `NodeSize` selection via a formula from key counts (no fixed menu).

See [appendix-design-limitations.md](appendix-design-limitations.md).
