# P-SRE-002: Aggregate Access Through IRepository<> Only

## Status
Accepted

## Date
2025-10-03

## Context

The Platform SRE microservice follows Domain-Driven Design (DDD) principles with aggregates as the primary unit of consistency and transactional boundaries. The current implementation uses the Repository pattern through `IRepository<T>` interface to provide a consistent abstraction for aggregate persistence and retrieval.

As evidenced by the existing codebase structure, aggregates like `ErrorBudgetWindow` are accessed through the repository pattern in command handlers such as `CloseErrorBudgetWindowHandler`. However, without explicit architectural constraints, developers might be tempted to:

- Access aggregates directly through EF Core's `DbContext` or `DbSet<T>`
- Bypass the repository abstraction for "simple" operations
- Create custom data access methods that circumvent the repository pattern
- Use Entity Framework's direct querying capabilities on aggregate entities
- Access aggregate data through raw SQL or other data access mechanisms

This inconsistency could lead to:
- Violation of DDD principles and aggregate boundaries
- Inconsistent business rule enforcement across the application
- Difficulty in implementing cross-cutting concerns (auditing, caching, security)
- Challenges in testing and mocking aggregate operations
- Loss of encapsulation and proper aggregate lifecycle management
- Potential data integrity issues when aggregate invariants are bypassed

## Decision

**All access to aggregates within the Platform SRE microservice MUST be performed exclusively through the IRepository<T> interface. Any other method of aggregate access is strictly forbidden.**

This decision encompasses the following constraints:

1. **No Direct DbContext Access**: Aggregates cannot be accessed directly through EF Core's `DbContext` or `DbSet<T>` properties
2. **No Custom Data Access**: Custom queries, stored procedures, or alternative data access methods for aggregates are prohibited
3. **Repository Pattern Enforcement**: All aggregate operations (Create, Read, Update, Delete) must go through `IRepository<T>` implementations
4. **Consistent Abstraction**: The repository serves as the single point of access for all aggregate-related data operations
5. **Domain Model Protection**: Repository pattern ensures proper aggregate lifecycle management and business rule enforcement

### Approved Aggregate Access Methods:
- `IRepository<T>.FindAsync(id)` for retrieving aggregates by identifier
- `IRepository<T>.CreateAsync(aggregate)` for persisting new aggregates
- `IRepository<T>.UpdateAsync(aggregate)` for updating existing aggregates
- `IRepository<T>.DeleteAsync(aggregate)` for removing aggregates
- Custom repository methods that extend `IRepository<T>` for domain-specific queries

### Strictly Forbidden:
- Direct access to `DbSet<ErrorBudgetWindow>` or similar aggregate DbSets
- Using `AppContext` (DbContext) directly to query aggregate entities
- Creating custom data access classes that bypass the repository pattern
- Using EF Core LINQ queries directly on aggregate entities outside of repository implementations
- Any form of aggregate manipulation that doesn't go through the repository abstraction

### Exceptions:
- Repository implementations themselves (e.g., `EfRepository<T>`) may use DbContext internally
- Read-only projections for reporting purposes may access aggregate data directly, but NOT the aggregate entities themselves
- Database migrations and schema management operations
- Integration tests may use alternative repository implementations for testing purposes

## Consequences

### Positive:
- **Domain Integrity**: Ensures proper aggregate boundary enforcement and business rule application
- **Consistency**: Uniform access pattern for all aggregate operations across the microservice
- **Testability**: Simplified unit testing through repository interface mocking
- **Encapsulation**: Proper separation between domain logic and data access concerns
- **Maintainability**: Single point of responsibility for aggregate persistence logic
- **Cross-cutting Concerns**: Easier implementation of auditing, caching, and security at the repository level
- **DDD Compliance**: Maintains Domain-Driven Design principles and aggregate design patterns
- **Change Management**: Repository abstraction allows for future changes in persistence strategy without affecting domain logic

### Negative:
- **Performance Considerations**: Additional abstraction layer may introduce minimal overhead
- **Development Constraints**: Developers must work within repository interface limitations
- **Learning Curve**: Team must understand and consistently apply repository pattern principles
- **Flexibility Reduction**: Some complex queries might require extending repository interfaces

### Mitigation Strategies:
- Provide comprehensive training on repository pattern and DDD principles
- Create clear guidelines for extending repository interfaces for domain-specific needs
- Establish performance monitoring to ensure repository abstraction doesn't impact system performance
- Document best practices for repository usage and aggregate design
- Implement code analysis rules to detect violations of this architectural decision

## Compliance and Enforcement

- **Code Reviews**: All code changes must be reviewed to ensure compliance with repository-only access
- **Static Analysis**: Configure analyzers to detect direct DbContext usage on aggregate entities
- **Architecture Tests**: Implement automated tests that verify aggregate access patterns
- **CI/CD Integration**: Include checks in the build pipeline to prevent repository pattern violations
- **Team Guidelines**: Establish clear coding standards and architectural guidelines
- **Exception Process**: Any exceptions to this rule must be explicitly approved by the architecture team and documented

## Implementation Examples

### ✅ Correct Usage:
```csharp
public class CloseErrorBudgetWindowHandler(IRepository<ErrorBudgetWindow> repository, AppContext appContext)
    : ICommandHandler<CloseErrorBudgetWindow>
{
    public async Task HandleAsync(CloseErrorBudgetWindow command, CancellationToken cancellationToken)
    {
        var aggregate = await repository.FindAsync(command.Id);
        if (aggregate is null)
            throw Exception.NotFound(command.Id);
        
        aggregate.Close();
        await repository.UpdateAsync(aggregate);
        await appContext.SaveChangesAsync(cancellationToken);
    }
}
```

### ❌ Forbidden Usage:
```csharp
// Direct DbContext access - FORBIDDEN
var window = await appContext.ErrorBudgetWindows.FindAsync(command.Id);

// Direct DbSet querying - FORBIDDEN
var windows = await appContext.ErrorBudgetWindows.Where(w => w.State == WindowState.Open).ToListAsync();

// Custom data access bypassing repository - FORBIDDEN
var customDataAccess = new ErrorBudgetWindowDataAccess(connectionString);
var window = await customDataAccess.GetById(command.Id);
```
