# ADR-0007: Pre-commit Framework Adoption for Git Hooks

**Date**: 2024-10-12
**Status**: Accepted

## Context

The project needed a way to enforce code quality standards before code is committed and pushed. Several options exist for managing Git hooks:

1. **Native Git hooks**: Custom bash scripts in `.git/hooks/` directory
2. **Pre-commit framework**: Python-based hook management system
3. **Manual enforcement**: Rely on developers to run checks manually
4. **CI-only enforcement**: Only check code quality in CI/CD pipeline

The choice affects:

- Developer experience and workflow friction
- Team consistency and ease of onboarding
- Maintainability of hook configurations
- Integration with industry-standard tools

iOS projects in 2024-2025 have converged on specific patterns, as evidenced by research from Quality Coding, ColinChSwift, and industry blog posts showing widespread adoption of pre-commit framework with SwiftLint.

## Decision

**We will adopt the pre-commit framework (<https://pre-commit.com>) as the standard Git hook management system for this project.**

The implementation includes:

- Pre-commit framework for hook management (via Homebrew or pip)
- Configuration in `.pre-commit-config.yaml` (version-controlled)
- Integration with Makefile (`make setup-hooks`)
- SwiftLint as the primary linting tool
- Standard pre-commit hooks for file validation

## Alternatives Considered

### 1. Native Git Hooks with Custom Scripts

Using custom bash scripts in `scripts/` directory with manual installation via `scripts/install-git-hooks.sh`.

**Why not chosen**:

- Manual hook updates required (no automatic versioning)
- No ecosystem of pre-built hooks to leverage
- Custom scripts need more maintenance
- Less portable across different projects
- No automatic update mechanism (`pre-commit autoupdate`)
- Harder to add new checks (requires bash scripting)

### 2. Husky (Node.js-based)

Using Husky, which is popular in JavaScript/TypeScript projects.

**Why not chosen**:

- Requires Node.js ecosystem (not standard for Swift/iOS)
- Not idiomatic for iOS development
- Less common in iOS community
- Pre-commit framework is language-agnostic and more suitable

### 3. CI-Only Enforcement

Relying solely on GitHub Actions CI to enforce code quality.

**Why not chosen**:

- Slow feedback loop (wait for CI to complete)
- Wastes CI resources on preventable issues
- Frustrating developer experience (fix → push → wait → fail → repeat)
- No local validation before sharing code
- Higher CI costs

### 4. Manual Checks

Expecting developers to run linting and tests manually before committing.

**Why not chosen**:

- Inconsistent enforcement (human error)
- Easy to forget checks
- No standardization across team
- Code quality issues slip through

## Consequences

### Positive

1. **Industry Standard**: Pre-commit framework is widely adopted (12,000+ GitHub stars, used by major projects)
2. **Automatic Updates**: `pre-commit autoupdate` keeps hooks current
3. **Version Control**: Configuration file (`.pre-commit-config.yaml`) is tracked in Git
4. **Ecosystem**: Access to 100+ pre-built hooks (trailing whitespace, YAML validation, etc.)
5. **Language-Agnostic**: Works across Swift, Python, Shell, and other languages
6. **Team Consistency**: Everyone gets identical hook configuration
7. **Easy Installation**: Single command (`pre-commit install`) sets up all hooks
8. **Selective Execution**: Can run specific hooks or skip with `--no-verify`
9. **Integration**: Works seamlessly with SwiftLint and other iOS tools
10. **Documentation**: Well-documented with large community support

### Negative

1. **External Dependency**: Requires Python and pre-commit framework installation
2. **Learning Curve**: Team needs to understand pre-commit concepts
3. **Initial Setup**: Requires `brew install pre-commit` (one-time overhead)
4. **Framework Overhead**: Slightly slower than native hooks (minimal impact)

### Mitigation Strategies

- **Dependency Management**: Document installation in `README.md` and `docs/QUICK_START.md`
- **Easy Setup**: Provide `make setup-hooks` command for automated installation
- **Clear Documentation**: Create `docs/PRE_COMMIT_HOOKS.md` with comprehensive guide
- **Onboarding**: Include setup instructions in contributor guidelines

## Rationale

The decision prioritizes **developer experience, industry alignment, and maintainability** over minimal dependencies.

Key factors:

1. **iOS Community Standard**: Pre-commit + SwiftLint is the established pattern for modern iOS projects (2024-2025)
2. **Professional Projects**: Used by major iOS teams and open-source projects
3. **Lower Maintenance**: Framework handles hook installation, updates, and execution
4. **Better UX**: Fast checks on commit (2-5s) don't block developer flow
5. **Scalability**: Easy to add more checks as project grows (SwiftFormat, custom rules)
6. **Reliability**: Battle-tested framework with active maintenance

The slight overhead of the Python dependency is offset by significant gains in maintainability and developer experience.

## Implementation Notes

### Installation

```bash
# Install framework and linter
brew install pre-commit swiftlint

# Setup hooks (or use: make setup-hooks)
pre-commit install
pre-commit install --hook-type pre-push
```

### Configuration File

`.pre-commit-config.yaml` defines:

- Standard hooks (trailing whitespace, YAML validation, etc.)
- SwiftLint integration (local hook)
- Optional SwiftFormat integration (commented out)
- Stage configuration (commit vs push)

### Makefile Integration

```bash
make setup-hooks  # Install pre-commit framework hooks
make pre-commit   # Run commit hooks manually
make pre-push     # Run push hooks manually
```

### What Runs When

- **On commit** (2-5 seconds): SwiftLint + file checks
- **On push** (optional, 1-2 minutes): Full test suite
- **Manual**: `pre-commit run --all-files`

### Override When Needed

```bash
# Skip commit hooks
git commit --no-verify

# Skip push hooks
git push --no-verify
```
