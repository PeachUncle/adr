Abstract:: 
Production Spec enables safe extensibility and documentation, but extension is laborious; as PS grows, consistency checks become impractical and parallel EPs complicate change management. Propose: move PS and EPs into Repo, define workflow and prompts for EP lifecycle from concept to Completed.

## Motivation

> Section purpose:<!-- IMPORTANT, DO NOT DELETE -->
> To describe of the goals achieved by this Enhancement Proposal and argument
> that this is the minimal alteration of the Production Spec that would achieve
> those goals. From PEP 1: "It should clearly explain why the existing language
> specification is inadequate to address the problem that the PEP solves."



The Production Spec (PS) and Enhancement Proposal (EP) system is already
providing acountability and sustainability to the project, but has weighed down
the update process. Moreover, as the PS grows, checking Properties and Contracts
agaisnt new EPs for consistency will become unmanageable. Finally, the current
system for manual merging EPs into the PS is highly error prone and must be done
in parellel with the Repo Branch merge.

Centralizing the PS and EPs within the repository solves these scalability
problems through version control and integration with IDE-based LLM tools. Here
we propose such a move for the design docs and other documentation, as well as a
new Workflow for developing EPs.

## Rationale

> Section purpose:<!-- IMPORTANT, DO NOT DELETE -->
> To explain major design decisions, including comparison to alternative designs
> and related work, e.g. how the problem is solved in other software or systems.


Relocating design documents to the repository directly links version control
with the Production Spec, and quite trivially provides easier workflow
automation through LLMs tools. While some projects (e.g., Python PEPs) use
databases and comment systems for proposal management, our EPs are smaller and
developed primarily by single contributors. See [[EP 005]] for consideration of
how to represent Repo structure in the PS.

Design considerations remain however in the Workflow for developing an accurate
EP. A prompt-driven workflow provides standardized, easy-to-follow processes and
grounds the process in specific, structured steps like consistency checks. Given
the limitations of LLMs in maintaining context and planning, the proposed
Workflow emphasizes frequent use of small prompts, e.g. for reviewing milestone
progress or presenting planned points for drafting, as well as incremental
planning in a scratch file interleaved with occasional approval to edit the EP.

Not considered:
- Automated review of repo changes against proposal descriptions was out of
  scope for this EP, but could be part of a revised Workflow for EP integration.

## Spec Changes

> Section purpose:<!-- IMPORTANT, DO NOT DELETE -->
> Alterations to Objects, Contracts or Workflows that will achieve the goal of
> the EP.


##### Repo
Add the following properties:
- *Design directory.* Containing Production Spec, EPs, and Workflow guides.
- *Docs directory.* Containing user-facing documentation such as the Docs
  Overview Page.
- *Development scratch.* Directory containing implementation plans.

##### Scope of Master Branch
Add the following requirement:
- Development scratch directory does not enter the Master Branch on merge.

##### Workflow
Add the following properties:
- *Milestones.* The steps (and outcome) of the workflow.
- *Guide.* A detailed outline of what should be achieved in each Milestone, and
  description of any tools or procedures for interacting with the system to
  achieve them.

##### Workflows > Develop an Enhancement Proposal
Add new a new Workflow, "Enhancement Proposal Development".
Milestones:

1. *Conceptualization.* Identify problem and opportunity for improvement.

2. *Scoping.* Draft initial EP with a preamble, Motivation (perhaps lacking
   specificity about exact solution), and a high-level candidate solution in the
   Rationale.

3. *Lateral Review.* Consider alternative solutions, discuss merits, and select
   the best approach. Update the Rationale and Motivation to reflect this
   decision, noting any limitations or future EP opportunities.

4. *Change-Drafting.* Analyze the Production Spec for required changes and
   document them in the Spec Changes section. Do not edit the Production Spec at
   this stage.

5. *Compatibility Review.* Assess the EP against Production Spec Contracts.
   Draft the Risk and Reference Implementation based on identified Properties
   and Contracts at risk and requirements the solution must satisfy to maintain
   consistency of the system.


##### Workflows > Integrate a Completed EP
Replace the informal steps in the current PS with:
Milestones:
1. *Merge.* Create a pull request for the reference implementation branch and
   squash-merge into the Master Branch.


## Contracts at Risk

> Section purpose:<!-- IMPORTANT, DO NOT DELETE -->
> Description of how consistency of the system is maintained under the solution
> proposed. Confirmation that any affected Spec Objects maintain their
> Properties and obey any Contracts they are bound by, highlighting features of
> the proposed solution, and reference implementation that allow this, or Spec
> Changes that were necessary to maintain consistency.



- *ProductionSpec.* PS will reside in Design directory, update process formalized by new
  workflow. Neither change conflicts with PS properties (Schemas,
  Contracts, Workflows sections, and Consistency).
- *EP.* Location moved to Design directory; development process now governed
  by new Workflow. No properties to be invalidated.
- *Workflow.* New workflow object and properties (Milestones, Guide) added;
  Existing workflows updated to match.
- *Repo.* New properties (Design, Docs, Dev scratch) added to PS; reference
  implementation matches.
- *Master Branch.* Existing properties unaffected, but see SOC 2.
- *SOC 2 (Scope of Master Branch).* Contract updated to require Dev scratch
  exclusion; Reference Implementation includes mechanism for merging without
  dev notes.
- *Docs Overview Page.* Updated with short discussion of Workflows for
  developing and integrating EPs.
- *Integrate a Complete EP.* Required update to respect changes to SOC 2;
  separate requirements of merging Production Spec and reference implementation
  not required.
- *Develop an EP.* Product must respect Complete EP properties: Preamble,
  Motivation, Rationale, Contracts at Risk, Spec Changes, Reference
  Implementation. Milestones written specifically to develop these sections in
  accordance with their definition in the PS.
