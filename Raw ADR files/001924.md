# CI/CD

* Status: accepted  
* Date: 2025/03/19

## Context and Problem Statement

The team needs to choose a tool to implement a CI/CD pipeline on the project. They are looking for a solution that is easy to integrate with existing tools, and that is also understandable and accessible to the team, whose knowledge of CI/CD is limited.

## Decision Drivers

* Version control tool already implemented: GitHub.
* Simplicity and ease of integration.

## Considered Options

* GitHub Actions
* Jenkins
* GitLab CI
* CircleCI

## Decision Outcome

Chosen option: GitHub Actions. GitHub Actions was chosen as it integrates seamlessly with GitHub, the version control tool used in the project. In addition, it is an option that fits the learning curve of the team, as they are already familiar with GitHub, albeit with limited CI/CD knowledge.

### Positive Consequences

* **Direct integration with GitHub**: No need to configure an external tool, which facilitates version and deployment management.
* **Team familiarity**: Although CI/CD knowledge is limited, the team already has experience with GitHub, which lowers the barrier to entry.
* **Simplicity of configuration**: GitHub Actions allows CI/CD pipelines to be created directly from the repository without the need for external tools.

### Negative Consequences

* **Limited knowledge in the team**: Although the team has increased familiarity with GitHub, knowledge about GitHub Actions and CI/CD is still limited, which may require time to learn and adapt.
* **GitHub dependency**: By choosing GitHub Actions, we become dependent on the GitHub ecosystem for code management and deployments, which can be a limitation if you want to switch platforms in the future.

## Annex I: Actual workflows

1. The main GitHub Actions workflow is triggered by a **push** to the repository. It consists of the following steps:

   1. **Local deployment**: The web application is deployed locally in a controlled environment.

   2. **Test execution**: The project's test suite is executed to ensure that the changes have not introduced any errors.

   This workflow guarantees that every change is automatically tested, allowing for early detection of bugs before deployment and contributing to the project's stability and quality.

2. **Automatic Pull Request Creation**: This workflow automatically generates pull requests to streamline collaboration and code reviews, reducing the need for manual intervention. It is triggered only when explicitly indicated in the commit message.

3. **Test Re-execution and Docker Image Upload**: This workflow is triggered after a **merge** into the main branch. It reruns the tests to verify that no issues were introduced during the merge. Additionally, the resulting Docker image is uploaded to the **GitHub Container Registry (GHCR)**, ensuring that the latest image is always available for deployment.

In addition, work is being done to protect the `main` branch to prevent changes from being uploaded directly without going through a pull request. Although the rules were configured using the **rulesets** for the `main` branch on GitHub, we are currently experiencing an issue. GitHub displays the following message:  
   _“Your rulesets won't be enforced on this private repository until you move to GitHub Team organization account”_.

   This means that, in order for the rulesets to be enforced correctly, the repository needs to be inside a GitHub Team organization account, which is currently not the case. We are investigating solutions to implement this protection effectively in the future.
