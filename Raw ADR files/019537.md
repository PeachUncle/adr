# ADR 0004: Code Generation with Plop

**Date:** 2025-10-11  
**Status:** ✅ Accepted  
**Deciders:** Architecture Team  
**Related:** ADR 0001 (Component Classification), ADR 0002 (Slots), ADR 0003 (Compound)

---

## Context

We plan to build **60 components** across 4 tiers. Each component requires:
- Component implementation
- TypeScript types
- Unit tests (Vitest + Testing Library)
- Storybook stories
- Component README
- index.ts exports

**Without code generation:**
- ❌ Inconsistent file structure
- ❌ Missing files (forgot tests? forgot README?)
- ❌ Inconsistent naming conventions
- ❌ 10-30 minutes of boilerplate per component
- ❌ Copy-paste errors
- ❌ Onboarding friction (where do files go?)

**With 60 components:**
- Simple boilerplate: 10 mins × 36 components = **6 hours wasted**
- Complex boilerplate: 20 mins × 14 components = **4.7 hours wasted**
- Compound boilerplate: 30 mins × 10 components = **5 hours wasted**
- **Total: ~16 hours of repetitive work**

**Research conducted:**
- HeroUI uses Plop (proven at scale, 210+ components)
- React Native uses custom generators
- Next.js community best practices
- Evaluated alternatives (Hygen, Yeoman, custom scripts)

---

## Decision

We adopt **Plop.js** for code generation with **3 tier-specific templates**.

### What is Plop?

Plop is a micro-generator framework that creates files from templates:

```bash
pnpm plop component
? Component name: Button
? Component type: Simple
? Include tests? Yes
? Include stories? Yes
? Category: basics

✔ Component created at packages/react/src/button/
```

### Architecture

**Three templates matching our tiers:**

1. **Simple Template** (Tier 1-2)
   - 6 files: component, types (optional), test, stories, index, README
   - Pattern: Object + cn()
   - Examples: Button, Input, Badge

2. **Complex Template** (Tier 3)
   - 7-8 files: main, sub-components, types with slots, test, stories, index, README
   - Pattern: Slots
   - Examples: Dialog, Select, Table

3. **Compound Template** (Tier 4)
   - 9-10 files: root, sub-components, context, types, test, stories, index, README
   - Pattern: Context + sub-components + (optional slots)
   - Examples: Accordion, Tabs, DropdownMenu

### Template Features

**All templates include:**
- ✅ React 19 patterns (no forwardRef)
- ✅ TypeScript types
- ✅ CODE_STANDARD compliant
- ✅ Accessibility tests (vitest-axe)
- ✅ Storybook stories with variants
- ✅ Component README with usage examples
- ✅ Proper exports in index.ts
- ✅ JSDoc comments

**Simple template:**
```typescript
// Generated button.tsx
export interface ButtonProps extends React.ComponentPropsWithoutRef<'button'> {
  variant?: 'solid' | 'outline' | 'ghost';
  size?: 'sm' | 'md' | 'lg';
}

export function Button({ variant = 'solid', size = 'md', className, ...props }: ButtonProps) {
  return (
    <button className={cn('button-base', variants.variant[variant], variants.size[size], className)} {...props} />
  );
}

Button.displayName = 'Button';
```

**Complex template:**
```typescript
// Generated dialog.tsx with slots
export type DialogSlots = 'overlay' | 'content' | 'header' | 'body' | 'footer';

export interface DialogProps extends SlotsProps<DialogSlots> {
  open?: boolean;
  onOpenChange?: (open: boolean) => void;
}

const defaultStyles = {
  overlay: 'fixed inset-0 bg-black/50',
  content: 'fixed bg-white rounded-lg',
  // ...
};

export function Dialog({ classNames, children, ...props }: DialogProps) {
  return (
    <Root {...props}>
      <Overlay className={cn(defaultStyles.overlay, classNames?.overlay)} />
      <Content className={cn(defaultStyles.content, classNames?.content)}>
        {children}
      </Content>
    </Root>
  );
}
```

**Compound template:**
```typescript
// Generated accordion-context.tsx
export const AccordionContext = createContext<AccordionContextValue | null>(null);

export function useAccordionContext() {
  const context = useContext(AccordionContext);
  if (!context) throw new Error('Must be used within Accordion');
  return context;
}

// Generated accordion.tsx
export function Accordion({ type, value, onValueChange, children, ...props }: AccordionProps) {
  return (
    <AccordionContext.Provider value={{ type, value, onValueChange }}>
      <Root {...props}>{children}</Root>
    </AccordionContext.Provider>
  );
}
```

## Rationale

### Why Code Generation?

**Benefits:**

✅ **Consistency**
- All 60 components follow exact same structure
- Same file naming
- Same patterns
- Zero drift

✅ **Speed**
- 10-30 minutes → 30 seconds
- 16 hours saved across 60 components
- Focus on logic, not boilerplate

✅ **Quality**
- Tests always included
- Stories always included
- README always included
- Accessibility tests always included

✅ **Onboarding**
- New developers get correct structure immediately
- No need to reference examples
- Self-documenting templates

✅ **Standards Enforcement**
- Templates enforce CODE_STANDARD
- No debates about structure
- Automatic compliance

✅ **Scalability**
- Easy to add component #61, #62, #100
- Same process for all
- No fatigue from repetition

### Why Plop?

**Alternatives considered:**

#### 1. Manual Creation
❌ **Rejected:**
- Inconsistent
- Time-consuming
- Error-prone
- Not scalable to 60 components

#### 2. Copy-Paste from Examples
❌ **Rejected:**
- Inconsistent (which example to copy?)
- Easy to forget to update names
- Still time-consuming
- Drift over time

#### 3. Custom Scripts
⚠️ **Considered:**
- Full control
- No dependencies
- **Problem:** Need to build and maintain
- **Problem:** More work than Plop

#### 4. Hygen
⚠️ **Considered:**
- Similar to Plop
- **Problem:** Less popular (28k downloads/week vs 133k for Plop)
- **Problem:** Different template syntax

#### 5. Yeoman
❌ **Rejected:**
- Overkill for our use case
- Heavy, slower
- Outdated (last major update 2016)

#### 6. Plop.js ✅ **Selected**
- ✅ Lightweight (+4kb)
- ✅ Popular (133k downloads/week)
- ✅ Used by HeroUI (proven at scale)
- ✅ Simple Handlebars templates
- ✅ Interactive prompts
- ✅ Easy to maintain
- ✅ Fast
- ✅ Well-documented

## Consequences

### Positive

✅ **16 Hours Saved**
- Direct time savings across 60 components
- Can spend time on quality, not boilerplate

✅ **Zero Drift**
- All components start identical
- Updates to templates propagate
- Consistency guaranteed

✅ **Better Testing**
- Tests always included
- Accessibility tests always included
- Higher coverage

✅ **Better Documentation**
- README always included
- Storybook stories always included
- Consistent docs structure

✅ **Easier Refactoring**
- All components follow same pattern
- Easy to update all at once
- Can generate migration scripts

✅ **Lower Cognitive Load**
- Don't think about structure
- Don't think about naming
- Focus on component logic

✅ **Better Onboarding**
- New developers run one command
- Get perfect structure
- No guesswork

### Negative / Trade-offs

⚠️ **Setup Time**
- Initial: 2-4 hours to create templates
- Maintenance: ~15 mins per template update
- **Worth it:** Saved 16 hours, ongoing savings

⚠️ **Template Maintenance**
- Must keep templates updated
- Changes to CODE_STANDARD → Update templates
- **Mitigation:** Templates are version controlled, review process

⚠️ **Dependency**
- Adds Plop dependency (~4kb)
- **Acceptable:** Dev dependency only, well-maintained

⚠️ **Learning Curve**
- Developers must learn Plop command
- Must know which template to use
- **Mitigation:** Simple CLI, clear docs, only 3 templates

### Risks

🟢 **Risk: Template Bugs**
- Impact: Generated components have bugs
- Mitigation: Test templates, code review first generated components
- Probability: Low (templates are simple)

🟢 **Risk: Template Drift**
- Impact: Templates don't match CODE_STANDARD
- Mitigation: **Update templates when CODE_STANDARD changes**
- Validation: Automated checks, code review

🟢 **Risk: Over-Reliance**
- Impact: Developers don't understand component structure
- Mitigation: Document templates, require understanding
- Probability: Very Low (templates are educational)
