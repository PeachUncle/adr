# Use Azure Verified Modules (AVM) with no avm-pattern module for creating Infrastructure as Code (IaC)

## Context and Problem Statement

Choosing the right infrastructure development framework or provider among the varied choices such as Terraform, Bicep, ARM, CAF, AVM, etc. poses quite a challenge for our customers. The dev framework dictates how easy and maintainable the solution would be when it comes to setting up complex network requirements and security policies. The record here uses different factors to analyze popular infra dev framework choices.

## Decision Drivers

* The approach must be flexible and allow for complex IaC scenarios
* The approach must support best practices
* The approach must be consistent with IaC code across Microsoft and customers to facilitate contribution and longer term support
* The approach must support what our customers are adopting predominantly
* The approach must allow for reduction of complexity of IaC
* The upgrade options of the approach must be sustainable
* The approach must allow for velocity of development

## Considered Options

* Standard IaC Providers (Terraform)
* Azure Verified Modules (AVM) with Terraform and/or Bicep
* Azure Verified Modules with hybrid non-AVM packages
* Azure Verified Modules consuming only AVM resource modules - no pattern module

## Decision Outcome

Azure Verified Modules consuming only AVM resource modules and not the pattern module.

> NOTE:
>
> In some instances, the team may have the need for a resource for which there might not
> be an AVM module readily available.
> In those cases, the implementation can be done using a local module definition, but the need for the AVM module must be tracked with a task.

## Pros and Cons of the Options

### Standard IaC

This approach would use default/standard Terraform providers with no layers of abstraction.

#### Good (Standard IaC)

* full control of the IaC code - its release, how it is tested, its structure, management and ownership
* fewer external dependencies; could help with development velocity

#### Bad (Standard IaC)

* not easy to maintain; when new updates are released, need to ensure the security and networking standards of CAIRA are met for all reference implementations.
* Note: This approach would compete with other similar Terraform solutions and would have no means to differentiate itself initially in terms of best practice and standards, unless an alternate existing approach could be identified and adopted/conformed to, such as the [Azure Landing Zone Accelerators](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/landing-zone/#azure-landing-zone-acce).

### Azure Verified Modules (AVM) with Terraform and/or Bicep

Adopt AVM with Terraform as it provides the best cloud coverage and our customers are typically already using and are skilled in Terraform for multi-cloud deployment support. To begin-with, Terraform is prioritized over Bicep. But subsequent iterations and releases of CAIRA there are plans to support Bicep.

#### Good (AVM with Terraform/Bicep)

* AVM is a Microsoft internal initiative to consolidate and set the standards for what best practice Infrastructure-as-Code module looks like.
* Project structure is consistent and governed, contributed to and supported by both Microsoft internal and external communities.
* Modules are kept in sync with product roadmaps for the services they represent. See [AVM Module Indexes](https://github.com/Azure/Azure-Verified-Modules/blob/main/docs/static/module-indexes/TerraformResourceModules.csv)
* Modules will align to the [Well Architected Framework](https://learn.microsoft.com/azure/well-architected/what-is-well-architected-framework) (WAF), [Reliability Hub](https://learn.microsoft.com/azure/reliability/overview-reliability-guidance), [Azure ProActive Resiliency Library](https://aka.ms/aprl) (APRL), [Microsoft Cloud Security Benchmark](https://learn.microsoft.com/security/benchmark/azure/introduction) (MCSB) and the [Microsoft Defender for Cloud](https://learn.microsoft.com/en-us/azure/defender-for-cloud/recommendations-reference) (MDFC) frameworks and resources for high priority recommendations.
* Modules will provide clear documentation alongside examples to promote self-service consumption.
* Modules will be tested to ensure they comply with the specifications for AVM and their examples deploy as intended.
* The AVM process has a central CI/CD pipeline that introduces consistent testing of modules and patterns and provides a consistent linting process for all documentation.
* An AVM pattern module can be registered directly in the Terrform Hashicorp directory, allowing for significantly reduced code complexity and the ability to download the pattern module directly from the aforementioned registry without needing to clone a Github repository.

#### Bad (AVM with Terraform/Bicep)

* Dependency on module owners that need to respond to an issue within 3 days which could significantly delay the development process. Mitigation is to escalate the process or take ownership of a module. For modules that need to have the AVM core team or Product Groups do not step in due to the module owners/contributors not responding, the AVM module will become [orphaned](https://azure.github.io/Azure-Verified-Modules/help-support/module-support/) Providing longer term support for the underlying modules for which we take ownership will need to be factored in. However, this will be an expectation for any option we select.
* As AVM introduces a level of abstraction on top of Terraform, version management across the modules and patterns can become complex. This can be mitigated by both an internal CI/CD pipeline with pinned versions and the AVM CI/CD process.
* If an AVM module is not available or not possible to create for an underlying service, then it cannot be used at this stage in the solution. We are blocked on developing any functionality for that service until it is created, if we want to remain compliant with AVM.
* A pattern module is another versioned codebase that we would need to support, particularly if we need to make it open source.

### Azure Verified Modules with hybrid non-AVM packages

A hybrid approach of using AVM pattern modules with a combination of both AVM resource and non-AVM pure Terraform modules could be implemented.

#### Good (AVM with hybrid non-AVM packages)

* This would remove delays from AVM resource owners that are not responsive to issues being raised.
* The project would have more control on the management of the underlying IaC.

#### Bad (AVM with hybrid non-AVM packages)

* Using this hybrid approach would eliminate many of the benefits of the AVM process and it would not represent a "verified" solution officially, even if the project were to conform to the same standards of the AVM initiative. Verified here means it is compliant with the Well Architected Framework (WAF), Reliability Hub, Azure ProActive Resiliency Library (APRL), Microsoft Cloud Security Benchmark (MCSB) and the Microsoft Defender for Cloud (MDFC) frameworks
* At this stage it is not possible to bypass the AVM linting process during build for non-AVM modules, this is likely by design.

### Azure Verified Modules consuming only AVM resource modules - no pattern module

Adopt only AVM resource modules with Terraform initially as it provides the best cloud coverage and our customers are typically already using and are skilled in Terraform for multi-cloud deployment support.
Forego the AVM pattern module and use only the underlying AVM resource modules.

#### Good

* It provides us with full control on the complex scenarios we need to support. We want the solution to support both greenfield and brownfield customers, and by moving away from a pattern module we can control this complexity ourselves via a UX.
* By allowing for more complexity, for example like complex network configurations, naming conventions, tags and other custom requirements, we adhere more closely to the first principles of CAIRA programme.
* By abstracting away the pattern layer, and indeed not exposing it to the customer - all interaction would be via a UX, we can remove our liability in supporting various upgrade paths as we further extend the solution and/or the underlying services change. The plan would be to provide the customer with pre-configured and structured terraform files that the customer incorporates into their environment. For greenfield customers, little amendment would be required, for brownfield, the onus is on the customer to integrate the terraform files into their environment. We thus provide a snapshot of the selected configuration as terraform files, there are no versions or repos, thus reducing our upgrade, backward compatibility and support liability.
* This is a validated usage of AVM and does not invalidate the underlying AVM principles or goal
* By using only AVM resource modules, which are well understood, we get the benefits of AVM but retain flexibility and control for our complex requirements.
* We reduce our dependency on AVM Pattern Modules, should it not be adopted and thus minimise our risk. We can take the approach of taking signal from customers to help us determine on whether a pattern module is a good approach in the long run.
* We can still register our custom pattern module within the terraform registry for simplified usage, but as stated, we will aim to reduce complexity via the UX.
* We de-couple ourselves from the AVM linting and test process for pattern modules, allowing us to specify and create our own.

#### Bad

NOTE: Same **Cons** as the Option 2 (AVM) applies here. In addition:

* By deviating from the pattern module, we accept a level of technical debt if in the future AVM mandates the usage of AVM pattern modules, but this seems unlikely as pattern modules are not currently mandated in the AVM process and not using a pattern module is a core AVM design principle.
* We lose the consistent document formatting and linting as provided by AVM, but we can mitigate this by adopting the parts of AVM we find useful.
