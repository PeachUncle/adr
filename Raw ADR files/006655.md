# ADR 0003: Remote State Management Strategy

**Status:** Accepted  
**Date:** 2025-09-10  
**Scope:** Infrastructure as Code

## Context

We need to manage Terraform state across multiple environments while enabling team autonomy and preventing state conflicts. The challenge is balancing shared resource dependencies with independent environment management.

## Decision

We will implement **environment-isolated remote state** with **cross-environment references** using the following pattern:

### State File Structure

- `shared.terraform.tfstate` - Platform team managed shared resources (ACR, monitoring)
- `dev.terraform.tfstate` - Development team managed dev environment
- `staging.terraform.tfstate` - Future staging environment state
- `prod.terraform.tfstate` - Future production environment state

### Cross-Environment References

Use `terraform_remote_state` data sources instead of `azurerm` data sources to avoid hard dependencies:

```hcl
# Instead of this (creates hard dependency):
data "azurerm_container_registry" "shared" {
  name                = "sharedacr"
  resource_group_name = "shared-rg"
}

# Use this (loose coupling via state):
data "terraform_remote_state" "shared" {
  backend = "azurerm"
  config = {
    resource_group_name  = "tfstate-rg"
    storage_account_name = "tfstate..."
    container_name       = "tfstate"
    key                 = "shared.terraform.tfstate"
  }
}

locals {
  shared_acr_id = data.terraform_remote_state.shared.outputs.acr_id
}
```

### Backend Configuration

- Centralized state storage in Azure Storage Account
- Container-based state file isolation
- State locking enabled via Azure Storage
- Encryption at rest and in transit

## Consequences

### Positive

- **Team Autonomy**: Dev teams can deploy without affecting other environments
- **Loose Coupling**: Environments reference shared resources via outputs, not direct data sources
- **Independent Lifecycle**: Environments can be destroyed/rebuilt independently
- **Clear Dependencies**: Shared resource contracts defined via outputs
- **Parallel Development**: Teams can work on different environments simultaneously

### Negative

- **Complexity**: Requires understanding of remote state references
- **Deployment Order**: Shared resources must be deployed before dependent environments
- **State Drift Risk**: Manual changes can cause state/reality divergence
- **Troubleshooting**: Cross-state references can complicate debugging

## Implementation

### 1. Backend Storage Setup

```bash
# Centralized state storage
az storage account create \
  --name "tfstate..." \
  --resource-group "tfstate-rg" \
  --sku Standard_LRS \
  --encryption-services blob
```

### 2. Environment Backend Configuration

```hcl
# Each environment has isolated backend config
terraform {
  backend "azurerm" {
    resource_group_name  = "tfstate-rg"
    storage_account_name = "tfstate..."
    container_name       = "tfstate"
    key                 = "{environment}.terraform.tfstate"
  }
}
```

### 3. Cross-Environment Pattern

- Shared environment exposes outputs for ACR, networking, monitoring
- Dependent environments import via `terraform_remote_state`
- Role assignments and integrations in dependent environments

## Team Responsibilities

### Platform Team (Shared State)

- Deploy and manage shared resources (ACR, monitoring infrastructure)
- Maintain shared state outputs contract
- Coordinate changes that affect multiple environments

### Development Teams (Environment State)

- Manage environment-specific resources (AKS, networking, security)
- Reference shared resources via remote state
- Independent deployment and lifecycle management
