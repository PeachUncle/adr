# ADR 001: Service Layer Separation from React Components

## Status
Accepted (November 2024)

## Context

When building a React application that communicates with backend APIs, we need to decide where HTTP communication logic lives. Several patterns exist:

### Option 1: Direct API calls in components
```typescript
// Inside component
const handleSubmit = async () => {
  const response = await axios.post('/api/campaigns', formData);
  setData(response.data);
};
```

**Pros:**
- Simple, no abstraction
- Fast to prototype

**Cons:**
- Every component knows about axios, endpoints, response shapes
- Impossible to change API structure without touching 50+ files
- Cannot test business logic without mounting React components
- Duplicated error handling across components

### Option 2: Redux with thunks/sagas
```typescript
// Action creator
export const createCampaign = (data) => async (dispatch) => {
  dispatch({ type: 'CAMPAIGN_CREATE_REQUEST' });
  const response = await api.post('/campaigns', data);
  dispatch({ type: 'CAMPAIGN_CREATE_SUCCESS', payload: response.data });
};
```

**Pros:**
- Centralized state management
- Time-travel debugging

**Cons:**
- 200+ lines of boilerplate for simple CRUD
- Server state mixed with UI state
- Tight coupling between API calls and Redux actions
- Overkill for our use case (we're not building a collaborative editor)

### Option 3: Service layer + SWR/React Query
```typescript
// services/campaignService.ts
export async function getCampaigns(page = 1, limit = 10): Promise<PaginatedResponse> {
  const resp = await api.get(`/campaigns?page=${page}&limit=${limit}`);
  return normalizeResponse(resp);
}

// hooks/useCampaigns.ts
export function useCampaigns(page = 1) {
  const { data, error, mutate } = useSWR(
    ['/campaigns', page],
    () => campaignService.getCampaigns(page)
  );
  return { campaigns: data?.info || [], error, mutate };
}

// Component
function CampaignsPage() {
  const { campaigns, error } = useCampaigns(page);
  // Just render
}
```

**Pros:**
- Clear separation: services handle HTTP, hooks coordinate state, components render
- Services testable without React
- SWR handles caching, revalidation, deduplication automatically
- Can swap React for Vue by only changing UI layer
- Backend changes isolated to service files

**Cons:**
- Extra abstraction layer (services + hooks)
- Requires discipline to not import axios in components

## Decision

**We will use a service layer to encapsulate all HTTP communication, coordinated through custom hooks that integrate with SWR.**

### Architecture:

```
┌─────────────────────────────────────────┐
│  UI Layer (React Components)            │
│  - Renders data, handles events          │
│  - Does NOT import axios or know URLs   │
└─────────────────────────────────────────┘
                  ↓
┌─────────────────────────────────────────┐
│  State Coordination (Custom Hooks)       │
│  - useCampaigns, useAgents, etc.        │
│  - Integrates SWR with services         │
│  - Handles auth checks before fetch     │
└─────────────────────────────────────────┘
                  ↓
┌─────────────────────────────────────────┐
│  Business Logic (Services)               │
│  - campaignService, agentService, etc.  │
│  - Pure TypeScript, no React imports    │
│  - Normalizes backend responses         │
└─────────────────────────────────────────┘
                  ↓
┌─────────────────────────────────────────┐
│  Infrastructure (lib/axios)              │
│  - Token injection, error interceptors  │
│  - Does NOT know about domains          │
└─────────────────────────────────────────┘
```

### Invariants enforced:

1. **Components never import axios** - Violation caught in code review
2. **Services never import React** - Ensures testability
3. **Hooks coordinate, don't compute** - Business logic stays in services
4. **Types flow downward** - Services define contracts, components consume

## Consequences

### Positive

1. **Testability**: Can test `getCampaigns()` without mounting React
   ```typescript
   // __tests__/services/campaignService.test.ts
   it('normalizes paginated response', async () => {
     mock.onGet('/campaigns').reply(200, { data: { info: [...] } });
     const result = await getCampaigns(1, 10);
     expect(result.info).toHaveLength(10);
   });
   ```

2. **Changeability**: Backend changes pagination structure? Update one function in `campaignService.ts`. Components unaffected.

3. **Replaceability**: Could swap React for Vue/Svelte by only rewriting UI layer. Services remain unchanged.

4. **Onboarding**: New developers read service contracts to understand API:
   ```typescript
   export async function getCampaigns(
     page = 1, 
     limit = 10
   ): Promise<PaginatedCampaignsResponse>
   ```
   Return type is documentation.

5. **Parallel work**: Two developers can work on different features (emails vs campaigns) without merge conflicts in logic layer.

### Negative

1. **Extra layer**: Services + Hooks = more files than "just use Redux"
   - **Mitigation**: Clear conventions (one service per domain) prevent chaos

2. **Learning curve**: Junior devs might try to import axios in components
   - **Mitigation**: ESLint rule to ban axios imports outside `/services` and `/lib`

3. **Hook complexity**: Some hooks become coordinators for multiple services
   - **Example**: `useConversations` needs `conversationService` + `customerService`
   - **Mitigation**: Keep hooks focused on one primary service, compose in components if needed

## Compliance

### How to verify we follow this decision:

```bash
# No axios imports in components or pages
grep -r "import.*axios" src/pages/ src/components/
# Expected: 0 results

# No React imports in services
grep -r "import.*react" src/services/
# Expected: 0 results (except test files)

# Services export async functions with typed returns
grep -r "export async function" src/services/ | wc -l
# Expected: ~50+ (one per CRUD operation per domain)
```

### When to revisit:

- If we add 10+ more domains and services become unwieldy → consider service generator or code generation
- If backend moves to GraphQL → services layer still valid, just swap REST calls for GraphQL queries
- If we need client-side cache invalidation logic → may need event bus, but keep it in hooks layer

## Implementation Examples

### Service File Structure
```typescript
// services/campaignService.ts

// 1. Types (contract)
export interface Campaign {
  id: string;
  name: string;
  status: number;
}

export interface PaginatedCampaignsResponse {
  info: Campaign[];
  currentPage: number;
  totalPages: number;
  totalCount: number;
}

// 2. Base constants
const BASE = '/api/v1/secure/campaign';

// 3. CRUD operations
export async function getCampaigns(page = 1, limit = 10): Promise<PaginatedCampaignsResponse> {
  const resp = await api.get(`${BASE}?page=${page}&limit=${limit}`);
  return normalizeResponse(resp);
}

export async function createCampaign(body: Partial<Campaign>) {
  const resp = await api.post(BASE, body);
  return resp?.data ?? resp;
}

// 4. Helper functions (private)
function normalizeResponse(resp: any): PaginatedCampaignsResponse {
  const data = resp?.data?.data ?? resp?.data ?? { info: [] };
  return {
    info: data.info ?? [],
    currentPage: data.currentPage ?? 1,
    totalPages: data.totalPages ?? 1,
    totalCount: data.totalCount ?? 0,
  };
}
```

### Hook Structure
```typescript
// hooks/useCampaigns.ts
import useSWR from 'swr';
import { useAuth } from '../contexts/AuthContext';
import * as campaignService from '../services/campaignService';

export function useCampaigns(page = 1, limit = 10) {
  const { isAuthenticated, tokens } = useAuth();
  
  // Don't fetch if not authenticated
  const shouldFetch = Boolean(isAuthenticated && tokens?.accessToken);
  const key = shouldFetch ? ['/campaigns', page, limit] : null;
  
  const { data, error, isLoading, mutate } = useSWR(
    key,
    () => campaignService.getCampaigns(page, limit)
  );

  return {
    campaigns: data?.info ?? [],
    meta: {
      currentPage: data?.currentPage,
      totalPages: data?.totalPages,
      totalCount: data?.totalCount,
    },
    isLoading,
    error,
    mutate, // For optimistic updates
  };
}
```

### Component Usage
```typescript
// pages/Campaigns.tsx
function CampaignsPage() {
  const [page, setPage] = useState(1);
  const { campaigns, meta, isLoading, error, mutate } = useCampaigns(page);

  const handleDelete = async (id: string) => {
    await campaignService.deleteCampaign(id);
    mutate(); // Revalidate
  };

  if (isLoading) return <Spinner />;
  if (error) return <Error message={error.message} />;

  return (
    <div>
      {campaigns.map(c => <CampaignCard key={c.id} campaign={c} onDelete={handleDelete} />)}
      <Pagination page={page} total={meta.totalPages} onPageChange={setPage} />
    </div>
  );
}
```

## Lessons Learned (6 months later)

✅ **What worked:**
- Services stayed pure (no React imports crept in)
- New feature (email management) added without touching campaign code
- Junior dev onboarded in 2 hours by reading service contracts

⚠️ **What we had to adjust:**
- Some services needed helper functions (e.g., `generateAgentId()`)
- Added `api.ts` wrapper to standardize error handling across services
- SWR cache keys needed standardization (now always `[endpoint, ...params]`)

❌ **What we'd do differently:**
- Should have added service tests from day 1 (we added them later)
- Some hooks became too complex (e.g., `useConversations` handles pagination + infinite scroll). Consider splitting into `useConversationsPaginated` and `useConversationsInfinite`.
