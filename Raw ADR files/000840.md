# ADR-007: Data Ownership and Bounded Contexts

## Status
Accepted

## Context

BahariWatch is a distributed system with multiple microservices handling different aspects of IUU fishing monitoring. According to "Software Architecture: The Hard Parts" (Chapter 9, p. 175-200), one of the most critical decisions in distributed architectures is establishing clear data ownership to prevent coupling, maintain data integrity, and enable independent service evolution.

### Business Drivers
1. **Data Integrity**: Reports, vessel matches, and alerts must remain consistent across services
2. **Regulatory Compliance**: GDPR Article 30 requires clear documentation of data processing responsibilities
3. **Service Autonomy**: Services must evolve independently without breaking other services
4. **Performance**: use this guides #file:proposoal.md

5. **Audit Trail**: 7-year retention requires clear ownership of audit logs

### Technical Constraints
- **Monolithic Database**: ADR-003 establishes a single PostgreSQL instance with logical schemas
- **Event-Driven Architecture**: ADR-002 uses async messaging, requiring eventual consistency
- **External Data Sources**: AIS/VMS/PDS data owned by external agencies
- **Anonymous Reporting**: Some data (device IDs) must be anonymized before storage

### Data Entities in BahariWatch System

Based on the proposal (Section 3.4.5) and Container Diagram:

**Core Operational Data:**
- Community reports (photos, GPS, timestamps, status)
- Vessel tracking data (AIS/VMS/PDS positions, vessel metadata)
- User profiles (BMU officers, enforcement, admins, researchers)
- Vessel matches (report-to-vessel correlations, confidence scores)
- Alerts (severity, enforcement agency, escalation status)
- Notifications (SMS/Email delivery status)

**Analytical Data:**
- Survey responses (usability, privacy perceptions)
- Hotspot analysis (geospatial clustering)
- Performance metrics (response times, enforcement outcomes)
- Vessel behavior patterns (historical movement analysis)

**Compliance Data:**
- Audit logs (all data access, modifications)
- Encryption keys (data encryption keys, key rotation history)
- User consent records (privacy policy acceptance)

### Architecture Characteristics Affected
- **Data Integrity** (High): Single source of truth per entity prevents conflicting updates
- **Service Autonomy** (High): Clear ownership enables independent deployment
- **Performance** (High): Services own their data, reducing inter-service latency
- **Availability** (High): Service failures don't cascade via database coupling
- **Maintainability** (Medium): Bounded contexts reduce cognitive load for developers

### Integration with Other ADRs
- **ADR-001 (Microservices)**: Requires clear service boundaries aligned with data ownership
- **ADR-002 (Event-Driven)**: Services communicate via events, not direct data access
- **ADR-003 (Monolithic Database)**: Logical schemas enforce data ownership boundaries
- **ADR-004 (Saga Pattern)**: Data changes coordinated via events, not distributed transactions
- **ADR-006 (Architecture Characteristics)**: Security and auditability require clear data stewardship

## Decision

We establish **data ownership based on Domain-Driven Design (DDD) bounded contexts**, with each microservice owning its operational data and publishing domain events for cross-context communication. Data ownership is enforced through:

1. **Database Schemas**: Each service has a dedicated PostgreSQL schema (enforced by ADR-003)
2. **Service Interfaces**: Services expose data only via REST APIs and domain events
3. **Read Models**: Services maintain their own read-optimized views of external data
4. **Foreign Keys**: No cross-schema foreign keys (loose coupling via IDs only)

### Data Ownership Map

| **Bounded Context** | **Owning Service** | **Owned Entities** | **Database Schema** |
|---------------------|-------------------|-------------------|---------------------|
| **Report Management** | Report Service | Reports, Photos, Evidence | `report_schema` |
| **User Management** | User Service | Users, Profiles, Roles, Permissions | `user_schema` |
| **Vessel Tracking** | Vessel Matching Service | Vessels, Tracks, Positions, Matches | `vessel_schema` |
| **Alert Management** | Alerting Service | Alerts, Escalations, Rules | `alert_schema` |
| **Notification Delivery** | Notification Service | Notifications, Templates, Delivery Status | `notification_schema` |
| **Analytics & Reporting** | Analytics Service | Surveys, Hotspots, Metrics, Dashboards | `analytics_schema` |
| **Audit & Compliance** | (Shared Infrastructure) | Audit Logs, Encryption Keys, Consent Records | `audit_schema` |

## Rationale

### Alternatives Considered

#### Option A: Shared Database with Cross-Schema Foreign Keys
**Description**: Allow foreign keys between schemas for referential integrity.

**Rejected Because**:
- Tight coupling between services (schema changes cascade)
- Violates microservices principle of loose coupling
- Prevents independent service deployment
- "Hard Parts" Chapter 9 (p. 180): "Cross-service database constraints create operational coupling"

#### Option B: Database-Per-Service (Fully Distributed)
**Description**: Each service has its own PostgreSQL instance.

**Rejected Because**:
- Violates ADR-003 (monolithic database decision)
- Higher operational complexity (7 databases to manage)
- Increased cost (7x storage, 7x backups)
- No clear trigger for decomposition (premature optimization)
- "Hard Parts" Chapter 6 (p. 148): "Start with a shared database, decompose when data disintegrators outweigh integrators"

#### Option C: Single Schema with Table Prefixes
**Description**: All tables in `public` schema with naming convention (e.g., `report_reports`, `user_users`).

**Rejected Because**:
- Weak enforcement (developers can bypass conventions)
- No schema-level access control
- Difficult to track data ownership in code reviews
- Violates ADR-003 preference for logical separation via schemas

### Trade-Off Analysis

| Dimension | Option Chosen (Schema-Based Ownership) | Alternative (Database-Per-Service) | Justification |
|-----------|----------------------------------------|------------------------------------|---------------|
| **Service Coupling** | Low (no cross-schema FKs) | Very Low (complete isolation) | Sufficient decoupling for current scale |
| **Operational Complexity** | Low (1 database) | High (7 databases) | Reduces DevOps burden, aligns with ADR-003 |
| **Data Consistency** | Medium (eventual via events) | Low (distributed transactions) | Acceptable for use case (30-second delay OK) |
| **Query Performance** | High (local joins within schema) | Medium (cross-service API calls) | Better for analytics queries |
| **Cost** | Low (1 instance) | High (7 instances + networking) | Budget constraint (KSh 59,500 initial) |
| **Testability** | High (single DB for integration tests) | Medium (7 DBs to mock) | Faster test execution |

## Architecture Characteristics Impact

### Service Autonomy (Priority: High)
**Rating: ↑ High Positive Impact**

- Each service evolves its schema independently (no breaking changes to other services)
- Example: Report Service can add `vessel_sighting_quality` field without coordination
- Deployment independence: Report Service can deploy without Alerting Service downtime

### Data Integrity (Priority: High)
**Rating: ↑ High Positive Impact**

- Single source of truth per entity (no duplicate or conflicting data)
- Example: Vessel master data (MMSI, IMO) only in `vessel_schema`, never duplicated
- Foreign key integrity within bounded contexts prevents orphaned records

### Performance (Priority: High)
**Rating: ↑ Positive Impact**

- Services query their own data without network latency (local PostgreSQL queries)
- Example: Report Service retrieves report status in <10ms (no cross-service API call)
- Read models in Analytics Service cache frequently accessed data (hotspots, metrics)

### Availability (Priority: Critical)
**Rating: ↑ Positive Impact**

- Service failures don't cascade via database coupling
- Example: If Alerting Service crashes, Report Service continues accepting reports
- Circuit breakers protect against slow external queries (AIS/VMS feeds)

### Maintainability (Priority: Medium)
**Rating: ↑ Positive Impact**

- Developers understand bounded contexts (cognitive load reduced)
- Example: "Report Service owns reports" is clear, no ambiguity about data location
- Schema migrations scoped to single service (reduced coordination)

### Testability (Priority: Medium)
**Rating: ↑ Positive Impact**

- Integration tests use Testcontainers with single PostgreSQL instance
- Example: Test Report Service CRUD without mocking User Service database
- Contract tests verify event schemas between producers/consumers (Pact)

### Security (Priority: Critical)
**Rating: ↑ Positive Impact**

- Schema-level permissions enforce least privilege (Report Service can't query `user_schema`)
- Example: PostgreSQL role `report_service_role` granted only to `report_schema`
- Audit logs track which service accessed which data (compliance)

## Consequences

### Positive

1. **Clear Ownership**: Every entity has a single owning service, reducing confusion
2. **Independent Deployment**: Services deploy without coordinating schema migrations
3. **Event-Driven Communication**: Services communicate via domain events, not database queries
4. **GDPR Compliance**: Clear data stewardship enables GDPR Article 30 documentation
5. **Performance**: Services avoid chatty inter-service calls for operational data
6. **Testability**: Single database simplifies integration testing
7. **Cost-Effective**: Monolithic database reduces infrastructure costs vs database-per-service

### Negative

1. **Eventual Consistency**: Cross-context data (e.g., report_id in alerts) may be temporarily stale
2. **No Referential Integrity**: Foreign key constraints can't span schemas (enforced via events)
3. **Data Duplication**: Read models in Analytics Service duplicate operational data
4. **Query Complexity**: Cross-context queries require API calls or event replays
5. **Migration Risk**: Future database decomposition (ADR-003) requires data migration

### Neutral

1. **Schema Proliferation**: 7 schemas to manage (vs 1), but still simpler than 7 databases
2. **Event Complexity**: Services must publish events for all state changes (boilerplate code)
3. **Learning Curve**: Team must learn DDD bounded contexts and event-driven patterns

## Compliance & Governance

### Fitness Functions

#### FF-001: No Cross-Schema Foreign Keys
```sql
-- PostgreSQL query to detect cross-schema FKs
SELECT
  tc.constraint_name,
  tc.table_schema AS source_schema,
  tc.table_name AS source_table,
  ccu.table_schema AS target_schema,
  ccu.table_name AS target_table
FROM information_schema.table_constraints tc
JOIN information_schema.constraint_column_usage ccu
  ON tc.constraint_name = ccu.constraint_name
WHERE tc.constraint_type = 'FOREIGN KEY'
  AND tc.table_schema != ccu.table_schema;
```

**Trigger**: Run on every database migration (Flyway/Liquibase pre-deployment check)  
**Failure Action**: Block migration if cross-schema FKs detected

#### FF-002: Service Database Access Enforcement
```python
# pytest test suite

    cursor = conn.cursor()
    
    # Attempt to query user_schema (should fail)
    with pytest.raises(psycopg2.ProgrammingError) as exc_info:
        cursor.execute("SELECT * FROM user_schema.users LIMIT 1")
    
    assert "permission denied" in str(exc_info.value).lower()
```

### Security Implications

1. **Schema-Level Permissions**: PostgreSQL roles enforce least privilege
   ```sql
   -- Report Service role (read/write to report_schema only)
   CREATE ROLE report_service_role;
   GRANT CONNECT ON DATABASE bahariwatch TO report_service_role;
   GRANT USAGE ON SCHEMA report_schema TO report_service_role;
   GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA report_schema TO report_service_role;
   REVOKE ALL ON SCHEMA user_schema FROM report_service_role;
   ```

2. **Audit Logging**: All cross-context data access logged to `audit_schema`
   ```python
   # Middleware to log API calls
   @app.middleware("http")
   async def audit_middleware(request: Request, call_next):
       response = await call_next(request)
       await audit_log.write({
           "service": "report-service",
           "user_id": request.state.user_id,
           "action": f"{request.method} {request.url.path}",
           "timestamp": datetime.utcnow()
       })
       return response
   ```

3. **Encryption at Rest**: Sensitive columns encrypted via Transparent Data Encryption (TDE)
   - `reports.location` (GPS coordinates)
   - `user_profiles.phone_number` (PII)
   - `report_photos.photo_url` (S3 URLs contain object keys)

### Data Privacy Implications

1. **GDPR Article 30 (Records of Processing)**:

2. **GDPR Article 17 (Right to Erasure)**:

3. **Kenya Data Protection Act 2019 Section 25**:

## Implementation Notes

### For Developers

1. **Never Query Other Service Schemas**: Always use REST API or subscribe to events
   ```python
   # ❌ BAD: Direct database query
   user = db.query("SELECT * FROM user_schema.users WHERE id = ?", user_id)
   
   # ✅ GOOD: REST API call
   user = user_service_client.get_user(user_id)
   ```

2. **Publish Events on State Changes**: Other services may need to react
   ```python
   # After updating report status
   report.status = "Verified"
   db.save(report)
   
   # Publish event
   event_publisher.publish(ReportVerified(
       report_id=report.id,
       verification_level=report.verification_level
   ))
   ```

3. **Use UUIDs for Cross-Context References**: Never foreign keys
   ```python
   # ✅ GOOD: Store UUID, no FK constraint
   class Alert(Base):
       __tablename__ = "alerts"
       id = Column(UUID, primary_key=True)
       report_id = Column(UUID, nullable=False)  # No FK!
   ```

4. **Idempotent Event Handlers**: Events may be replayed
   ```python
   @event_handler(ReportSubmitted)
   def handle_report_submitted(event):
       # Check if already processed
       if analytics_db.exists(report_id=event.report_id):
           logger.info(f"Event {event.event_id} already processed, skipping")
           return
       
       # Process event
       analytics_db.create_report_metric(event)
   ```

### For Database Administrators

1. **Schema Ownership**: Each schema owned by specific PostgreSQL role
   ```sql
   CREATE SCHEMA report_schema AUTHORIZATION report_service_role;
   ```

2. **Connection Pooling**: Each service uses dedicated connection pool
   ```yaml
   # report-service/config.yaml
   database:
     url: postgresql://report_service_role:password@postgres:5432/bahariwatch
     pool_size: 20
     max_overflow: 10
     search_path: report_schema
   ```

3. **Schema Migrations**: Use Flyway/Liquibase with service-specific migration folders
   ```
   migrations/
   ├── report_schema/
   │   ├── V001__create_reports_table.sql
   │   └── V002__add_vessel_description.sql
   ├── user_schema/
   │   └── V001__create_users_table.sql
   └── vessel_schema/
       └── V001__create_vessels_table.sql
   ```

4. **Read Replicas**: Analytics Service uses read replica for heavy queries
   ```yaml
   # analytics-service/config.yaml
   database:
     primary_url: postgresql://postgres:5432/bahariwatch
     replica_url: postgresql://postgres-replica:5432/bahariwatch
   ```

### For Product Team

1. **Eventual Consistency Delays**: Users may see temporary inconsistencies
   - Example: Report shows "Submitted" for 5 seconds before showing "Matched" after vessel matching completes
   - Mitigation: Display loading indicators ("Matching in progress...")

2. **Data Ownership Requests**: New features must respect bounded contexts
   - Example: "Show reporter name on alert" → NOT possible (reports are anonymous)
   - Alternative: "Show BMU region of report" → Possible via report location

3. **Cross-Context Queries**: May require multiple API calls or eventual consistency
   - Example: "Dashboard showing reports with vessel names" → Report Service API + Vessel Service API
   - Performance: Cache vessel names in Report Service read model (eventual consistency)
