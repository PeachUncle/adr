# ADR-011: Observability Stack (Prometheus, Grafana, Jaeger, Seq)

## Status

Accepted

## Context

The Trama platform is a modular monolith with multiple modules (Auth, Artists, Users, Search) that communicate via HTTP endpoints and asynchronous events. As the application grows, we need comprehensive observability to:

- **Monitor System Health**: Track application performance, resource usage, and availability
- **Debug Production Issues**: Trace requests across modules and identify bottlenecks
- **Analyze Logs**: Search and analyze structured logs for errors and patterns
- **Track Business Metrics**: Monitor user activity, feature usage, and system behavior
- **Alert on Problems**: Proactively detect and respond to issues before users are affected
- **Optimize Performance**: Identify slow queries, high-latency endpoints, and resource constraints

We need an observability stack that provides:
- **Metrics**: Time-series data for system and business metrics
- **Logs**: Structured, searchable logs with correlation
- **Traces**: Distributed tracing across modules and external services
- **Visualization**: Unified dashboards for monitoring and analysis

The solution must be:
- Open-source and self-hosted (no vendor lock-in)
- .NET-native integration (minimal configuration)
- Docker-compatible (easy local development)
- Production-ready (scalable and reliable)

## Decision

We will use a **four-pillar observability stack**:

**Architecture:**
```
Application (Gateway + API)
    ↓
OpenTelemetry SDK
    ↓
┌─────────────┬──────────────┬──────────────┐
│  Prometheus │    Jaeger    │     Seq      │
│  (Metrics)  │   (Traces)   │    (Logs)    │
│      ↓      │      ↓       │      ↓       │
│   Grafana   │  Jaeger UI   │   Seq UI     │
└─────────────┴──────────────┴──────────────┘
```

### 1. Prometheus (Metrics Collection)

**Purpose:** Collect and store time-series metrics

**Version:** 3.1.0

**What We Collect:**
- ASP.NET Core metrics (HTTP requests, response times, error rates)
- Runtime metrics (GC, thread pool, memory usage)
- HTTP client metrics (outbound requests)
- MassTransit metrics (message processing, queue depth)
- Custom business metrics (user registrations, artwork uploads)

**Configuration:**
- Scrape interval: 15 seconds
- Retention: 90 days (configurable)
- Targets: Gateway (port 8080/5000), API (port 8080/7134)
- Metrics endpoint: `/metrics` (Prometheus format)

**Why Prometheus:**
- Industry standard for metrics collection
- Pull-based model (no agent required)
- Powerful query language (PromQL)
- Native Grafana integration
- Efficient time-series storage

### 2. Grafana (Metrics Visualization)

**Purpose:** Visualize Prometheus metrics with dashboards

**Version:** 11.4.0

**Dashboards:**
- System Overview (CPU, memory, disk, network)
- API Performance (request rate, latency, errors)
- Database Metrics (connections, query time, locks)
- Business Metrics (user activity, feature usage)

**Data Sources:**
- Prometheus (metrics only)

**Access:**
- Development: http://localhost:3000
- Production: https://[domain]/grafana (via Gateway)

**Why Grafana:**
- Best-in-class metrics visualization
- Native Prometheus integration
- Rich dashboard ecosystem
- Alerting capabilities
- Active community and plugins

**Note:** Grafana is used exclusively for metrics visualization. Traces and logs are viewed through their respective native UIs (Jaeger UI and Seq UI).

### 3. Jaeger (Distributed Tracing)

**Purpose:** Trace requests across modules and services

**Version:** 2.3.0

**What We Trace:**
- HTTP requests (Gateway → API)
- Database queries (Entity Framework Core)
- HTTP client calls (external APIs)
- MassTransit messages (event publishing/consuming)

**Configuration:**
- Protocol: OTLP (OpenTelemetry Protocol)
- Endpoint: http://jaeger:4317 (gRPC)
- Storage: Badger (embedded database)
- Sampling: 100% in development, configurable in production

**Trace Context:**
- Trace ID: Unique identifier for entire request flow
- Span ID: Unique identifier for each operation
- Parent Span ID: Links spans into a trace tree
- Tags: Custom metadata (user ID, endpoint, status code)

**Access:**
- Development: http://localhost:16686
- Production: https://[domain]/jaeger (via Gateway)

**Why Jaeger:**
- Native OpenTelemetry support
- Lightweight and fast
- No external dependencies (Badger storage)
- Excellent built-in UI for trace visualization
- CNCF graduated project

### 4. Seq (Structured Logging)

**Purpose:** Centralized structured log aggregation and search

**Version:** 2025.2

**What We Log:**
- Application logs (Info, Warning, Error, Fatal)
- HTTP request/response logs
- Database query logs (slow queries)
- Exception details with stack traces
- User context (user ID, correlation ID)

**Configuration:**
- Minimum level: Warning (production)
- Enrichers: Machine name, environment, correlation ID, user context
- API Key: Required for ingestion
- Retention: Configurable (default 30 days)

**Access:**
- Development: http://localhost:5341
- Production: https://[domain]/seq (via Gateway)

**Why Seq:**
- Purpose-built for structured logs
- Powerful query language
- Excellent .NET integration (Serilog)
- Built-in UI for log search and analysis
- Signal-based alerting
- Free for single-user (development)

### OpenTelemetry Integration

**Purpose:** Unified instrumentation SDK for metrics and traces

**Why OpenTelemetry:**
- Vendor-neutral standard (CNCF)
- Single SDK for metrics and traces
- Automatic instrumentation for ASP.NET Core, EF Core, HTTP clients
- Future-proof (industry standard)
- Reduces vendor lock-in

## Consequences

### Positive

- **Comprehensive Visibility**: Full observability across metrics, logs, and traces
- **Purpose-Built UIs**: Each tool has its own specialized UI optimized for its data type
- **Open Standards**: OpenTelemetry ensures vendor neutrality and future flexibility
- **Developer Friendly**: Automatic instrumentation requires minimal code changes
- **Production Ready**: All tools are battle-tested and widely adopted
- **Cost Effective**: All tools are open-source and self-hosted
- **Correlation**: Logs, metrics, and traces can be correlated via trace/correlation IDs
- **Performance**: Minimal overhead (<5% CPU, <100MB memory per service)
- **Debugging**: Distributed tracing makes debugging cross-module issues trivial
- **Best-in-Class Tools**: Each tool excels at its specific domain (Grafana for metrics, Jaeger for traces, Seq for logs)

### Negative

- **Operational Complexity**: Four additional services to deploy and maintain
- **Resource Usage**: Observability stack requires ~2GB RAM and 10GB disk
- **Learning Curve**: Team must learn Prometheus, Grafana, Jaeger, and Seq
- **Configuration Management**: Multiple configuration files to maintain
- **Data Retention**: Need to manage retention policies to control disk usage
- **Alert Fatigue**: Poorly configured alerts can overwhelm the team
- **Network Overhead**: Metrics scraping and trace export add network traffic
- **Storage Growth**: Metrics and traces grow linearly with traffic

### Neutral

- **Docker Compose**: All services run in Docker for local development
- **Port Management**: Grafana (3000), Prometheus (9090), Jaeger (16686), Seq (5341)
- **Multiple UIs**: Three separate UIs to access (Grafana, Jaeger UI, Seq UI) rather than a single pane of glass
- **Data Persistence**: All services use Docker volumes for data persistence
- **Sampling**: Traces sampled at 100% in development, configurable in production
- **Retention**: Prometheus (90 days), Jaeger (7 days), Seq (30 days)

### Correlation Strategy

**Correlation ID:**
- Generated by Gateway middleware
- Propagated via `X-Correlation-Id` header
- Included in all logs, metrics, and traces
- Enables end-to-end request tracking

**User Context:**
- Extracted from JWT token
- Enriched in logs and traces
- Enables user-specific debugging
- Privacy-aware (no PII in traces)

### Health Checks

All observability services have health checks:
- Prometheus: `http://prometheus:9090/-/healthy`
- Grafana: `http://grafana:3000/api/health`
- Jaeger: Configured in API health checks
- Seq: `http://seq:80/api/health`

### Performance Considerations

**Metrics:**
- Prometheus scraping: ~1-2ms per scrape
- Exporter overhead: <1% CPU
- Memory: ~50MB per service

**Traces:**
- OTLP export: Async, non-blocking
- Sampling reduces overhead (1.0 = 100%, 0.1 = 10%)
- Network: ~1KB per trace span

**Logs:**
- Serilog buffering: Async, non-blocking
- Seq ingestion: Batched for efficiency
- Minimum level filtering reduces volume

## Alternatives Considered

**ELK Stack (Elasticsearch, Logstash, Kibana):**
- Pros: Powerful log search, widely adopted, rich ecosystem
- Cons: Heavy resource usage (>4GB RAM), complex setup, overkill for MVP
- Rejected: Too resource-intensive for MVP, Seq provides better .NET integration

**Application Insights (Azure):**
- Pros: Fully managed, excellent .NET integration, automatic instrumentation
- Cons: Vendor lock-in, cost scales with usage, requires Azure account
- Rejected: Prefer self-hosted solution to avoid vendor lock-in

**Datadog:**
- Pros: All-in-one solution, excellent UX, powerful alerting
- Cons: Expensive ($15-31/host/month), vendor lock-in, SaaS only
- Rejected: Cost prohibitive for MVP, prefer self-hosted

**Zipkin (instead of Jaeger):**
- Pros: Lightweight, simple setup, OpenTelemetry compatible
- Cons: Less feature-rich than Jaeger, smaller community
- Rejected: Jaeger has better UI and more active development

**Loki (instead of Seq):**
- Pros: Grafana-native, label-based indexing, cost-effective
- Cons: Less powerful query language, no structured log support
- Rejected: Seq provides better structured logging and .NET integration

**InfluxDB (instead of Prometheus):**
- Pros: Purpose-built time-series database, better compression
- Cons: Less Grafana integration, smaller ecosystem
- Rejected: Prometheus is industry standard with better tooling
