# 004. ViewModel Pattern for Frontend UI Transformation

**Date:** 2024-11-22

**Status:** ✅ **Accepted**

## Context

When implementing DDD on the frontend, we needed a way to transform domain models for React components.

**The Problem:**
- Domain models (`Task`) contain value objects (`TaskId`, `TaskTitle`, `TaskDescription`)
- React components expect simple, flat data structures
- Components shouldn't import domain classes (couples UI to domain)
- Need to extract values (e.g., `task.id.value`) in components (spreads UI logic)
- Tests would need to mock entire domain class hierarchy

**Example of the Problem:**
```typescript
// ❌ Component importing and using domain model directly
import { Task } from '@tasklist/tasks-domain';

export const TaskItem: FC<{ task: Task }> = ({ task }) => {
  return (
    <div>
      {task.id.value}  {/* Extracting values in component */}
      {task.title.value}
      {task.status.valueOf() === 'COMPLETED' && <span>✓</span>}
    </div>
  );
};

// ❌ Component depends on domain structure
// ❌ Test needs to mock Task, TaskId, TaskTitle
// ❌ Tight coupling between UI and domain
```

## Decision

Create **ViewModels** that transform domain models into UI-friendly data structures.

A ViewModel:
1. Accepts a domain model in constructor
2. Extracts values from value objects
3. Provides computed properties for UI
4. Provides static factory methods
5. Is a simple, serializable data structure

### ViewModel Implementation Pattern

```typescript
// apps/web/src/presentation/viewmodels/TaskViewModel.ts
export class TaskViewModel {
  readonly id: string;
  readonly title: string;
  readonly description: string;
  readonly status: 'PENDING' | 'IN_PROGRESS' | 'COMPLETED';
  readonly createdAt: Date;
  readonly updatedAt: Date;
  readonly completedAt?: Date;

  constructor(task: Task) {
    this.id = task.id.value;
    this.title = task.title.value;
    this.description = task.description.value;
    this.status = task.status.valueOf();
    this.createdAt = task.createdAt;
    this.updatedAt = task.updatedAt;
    this.completedAt = task.completedAt;
  }

  // ✅ Computed properties for UI
  get isCompleted(): boolean {
    return this.status === 'COMPLETED';
  }

  get isPending(): boolean {
    return this.status === 'PENDING';
  }

  get isInProgress(): boolean {
    return this.status === 'IN_PROGRESS';
  }

  // ✅ Static factories
  static fromDomain(task: Task): TaskViewModel {
    return new TaskViewModel(task);
  }

  static fromDomainList(tasks: Task[]): TaskViewModel[] {
    return tasks.map(task => new TaskViewModel(task));
  }
}
```

### Component Using ViewModel

```typescript
// ✅ Component only knows about ViewModel
// ✅ No domain imports
// ✅ Easy to test (just pass plain object)
export const TaskItem: FC<{ task: TaskViewModel }> = ({ task }) => {
  return (
    <div>
      {task.id}
      {task.title}
      {task.isCompleted && <span>✓</span>}
    </div>
  );
};
```

### Hook Layer Handles Transformation

```typescript
// apps/web/src/presentation/hooks/useTasks.ts
const loadTasks = useCallback(async () => {
  try {
    const getAllTasksUseCase = appContainer.getGetAllTasksUseCase();
    const domainTasks = await getAllTasksUseCase.execute();
    
    // Transform domain → ViewModel
    const viewModels = TaskViewModel.fromDomainList(domainTasks);
    
    // State holds ViewModels, not domain models
    setTasks(viewModels);
  } catch (err) {
    setError(err.message);
  }
}, []);
```

## Rationale

### Why ViewModels?

1. **Decoupling**: Components don't import domain classes
   - Components depend on ViewModels, not Domain
   - Domain can change without affecting UI

2. **Simplicity**: ViewModels are plain data structures
   - Easy to understand for UI developers
   - No need to know about value objects or aggregates
   - Simple to test (no domain class mocking needed)

3. **Flexibility**: UI-specific computed properties
   - `isCompleted` helper for conditional rendering
   - Format dates specially for UI
   - Add color mappings without touching domain

4. **Type Safety**: Full TypeScript benefits
   - Compiler catches mistakes
   - IDE autocomplete for ViewModel properties
   - No implicit `any` types

5. **Testing**: Components test in isolation
   ```typescript
   describe('TaskItem', () => {
     it('shows checkmark when completed', () => {
       const taskVM: TaskViewModel = {
         id: '123',
         title: 'Test',
         status: 'COMPLETED',
         // ... other properties
       };
       
       const { getByText } = render(<TaskItem task={taskVM} />);
       expect(getByText('✓')).toBeInTheDocument();
     });
   });
   ```

### Trade-offs

**Upside:**
- Clean separation: Domain ≠ UI
- Easy component testing
- UI developers don't need DDD knowledge
- Can customize UI without touching domain

**Downside:**
- Extra transformation layer (ViewModel)
- More code to maintain
- Must keep ViewModel synchronized with domain changes

## Alternatives Considered

1. **Components import and use domain models directly**
   - ❌ Couples UI to domain structure
   - ❌ Hard to test (need to mock entire domain hierarchy)
   - ❌ UI developers must understand value objects

2. **Use Mapper functions instead of ViewModel class**
   - ❌ Less type-safe (functions can be called inconsistently)
   - ❌ Harder to add computed properties
   - ❌ No static factory methods

3. **Transform at component level**
   - ❌ Spreads transformation logic across many components
   - ❌ Inconsistent transformations
   - ❌ Hard to maintain if domain changes

4. **Use plain DTO objects returned from HTTP**
   - ❌ No computed properties (isCompleted, etc.)
   - ❌ Less type-safe
   - ❌ DTO structure must match UI needs exactly

## Consequences

### Positive

- ✅ Clean separation between domain and presentation
- ✅ Components are simple and testable
- ✅ Easy to add UI-specific computed properties
- ✅ No domain imports in components
- ✅ Domain changes isolated from presentation

### Negative

- ❌ Extra transformation step (ViewModel creation)
- ❌ More files to maintain
- ❌ Must remember to update ViewModel when domain changes
- ❌ Small performance cost (creating ViewModel instances)

## Testing Strategy

### Component Tests (No domain mocking needed)

```typescript
describe('TaskItem', () => {
  it('renders task with correct title', () => {
    const task: TaskViewModel = {
      id: '1',
      title: 'Buy groceries',
      status: 'PENDING',
      // ... minimal properties
    };
    
    const { getByText } = render(<TaskItem task={task} />);
    expect(getByText('Buy groceries')).toBeInTheDocument();
  });
});
```

### Hook Tests (Test transformation)

```typescript
describe('useTasks', () => {
  it('transforms domain models to ViewModels', async () => {
    const { result } = renderHook(() => useTasks());
    
    await waitFor(() => {
      expect(result.current.tasks).toHaveLength(1);
      expect(result.current.tasks[0]).toHaveProperty('id');
      expect(result.current.tasks[0]).toHaveProperty('isCompleted');
    });
  });
});
```
