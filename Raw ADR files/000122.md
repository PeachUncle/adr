# ADR-0001: Native iOS with Swift and SwiftUI

**Status**: Accepted
**Date**: October 12, 2025
**Deciders**: Architecture Team

## Context

We need to decide the primary technology stack for building the 3x3 Cube Puzzle Solver educational app. The app requires:

- High-performance 3D rendering for cube visualization
- Camera integration for real-world cube scanning
- Complex algorithms running efficiently
- Intuitive, responsive UI that feels native to iOS users
- Access to advanced iOS frameworks (ARKit, Vision, CoreML)

Options available include:

1. Native iOS with Swift and SwiftUI
2. Cross-platform frameworks (React Native, Flutter)
3. Hybrid approach (native + web views)

The app is initially targeted at iOS users only, with potential future expansion to other platforms.

## Decision

**We will build the app as a native iOS application using Swift 5.9+ and SwiftUI as the primary UI framework, with UIKit interop where needed.**

## Alternatives Considered

### React Native

**Pros**:

- Cross-platform code reuse (iOS/Android)
- Large developer community
- Fast iteration with hot reload

**Cons**:

- Performance overhead for 3D rendering and vision processing
- Bridge latency for camera/ML operations
- More difficult integration with ARKit, Vision, and CoreML
- Additional abstraction layer complicates debugging
- Limited access to latest iOS features

**Why not chosen**: Performance requirements and deep iOS framework integration needs make native development essential.

### Flutter

**Pros**:

- Cross-platform with good performance
- Modern UI framework
- Growing ecosystem

**Cons**:

- Limited access to iOS-specific frameworks without platform channels
- 3D rendering requires custom platform integrations
- Larger app size
- Less mature iOS framework integrations compared to Swift

**Why not chosen**: Similar limitations to React Native regarding iOS framework access, plus increased complexity for 3D and ML features.

### Hybrid (Ionic/Cordova)

**Pros**:

- Web technologies familiar to many developers
- Cross-platform

**Cons**:

- Poor performance for 3D and camera operations
- WebView overhead
- Limited native API access

**Why not chosen**: Performance requirements make this approach infeasible.

## Consequences

### Positive

1. **Maximum Performance**: Direct access to Metal for 3D rendering, no bridge overhead
2. **Best User Experience**: Native UI components provide familiar, responsive interactions
3. **Framework Access**: Full, immediate access to ARKit, Vision, CoreML, SceneKit
4. **Type Safety**: Swift's strong type system and compiler checks prevent many bugs
5. **Modern Concurrency**: Swift's async/await and actor model simplify complex asynchronous code
6. **Tool Support**: Xcode provides best-in-class debugging, profiling, and testing tools
7. **Future-Proof**: Direct access to new iOS features as Apple releases them
8. **Battery Efficiency**: Native code optimizes power consumption

### Negative

1. **Platform Lock-In**: Code cannot be reused for Android version
2. **Development Cost**: Building Android version requires separate implementation
3. **Team Expertise**: Requires iOS development skills and Swift knowledge
4. **Single Platform**: Cannot quickly deploy to other platforms for market validation

### Neutral

1. **SwiftUI/UIKit Mix**: SwiftUI is primary framework, but UIKit used where SwiftUI lacks features (e.g., complex camera controls)
2. **Learning Curve**: Developers new to Swift/SwiftUI require onboarding time
3. **Rapid Evolution**: SwiftUI evolves quickly; may need updates for new iOS versions

## Rationale

The decision prioritizes **user experience and technical feasibility** over cross-platform reach.

Key factors:

- **Performance is Critical**: Responsive 3D rendering and real-time camera processing require native performance and direct hardware access
- **iOS-First Strategy**: Initial market validation focuses on iOS users; Android expansion is a future consideration
- **Framework Dependencies**: ARKit and Vision framework capabilities ([Vision Framework](https://developer.apple.com/documentation/vision), [ARKit](https://developer.apple.com/documentation/arkit)) are essential for scanning features
- **Quality over Speed**: Native development produces higher quality app, even if initial development takes longer
- **Long-Term Maintainability**: Swift's type safety and modern features reduce long-term maintenance burden

The app's success depends on providing a smooth, intuitive learning experience. Native iOS development is the only approach that meets all technical requirements while delivering exceptional UX.

## Implementation Notes

- **Target iOS 16.0+** to leverage mature SwiftUI features ([SwiftUI releases](https://developer.apple.com/documentation/swiftui)) and modern Swift concurrency
- **Use SwiftUI** for all new views; UIKit only for platform limitations
- **Follow Apple's Human Interface Guidelines** ([HIG](https://developer.apple.com/design/human-interface-guidelines/)) for consistency with iOS ecosystem
- **Adopt Swift concurrency** ([Swift Concurrency](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/concurrency/)) (async/await, actors) instead of legacy GCD patterns
- **Structure for testability** using MVVM pattern with protocol-oriented design
