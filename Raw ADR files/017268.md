# ADR-003: AWS Cloud Infrastructure with CDK

## Status
Accepted

## Context

Social Flow requires cloud infrastructure that:
- Scales automatically based on demand
- Provides high availability and reliability
- Minimizes operational overhead
- Enables infrastructure as code (IaC)
- Integrates well with our serverless architecture

We need to choose both a cloud provider and an IaC tool.

## Decision

We will use **Amazon Web Services (AWS)** as our cloud provider and **AWS Cloud Development Kit (CDK)** for infrastructure as code.

Key reasons:
1. **Comprehensive services**: 200+ services covering all our needs
2. **Serverless ecosystem**: Lambda, AppSync, DynamoDB, etc.
3. **Global infrastructure**: 30+ regions for low latency worldwide
4. **CDK benefits**: Type-safe infrastructure with TypeScript
5. **Mature platform**: Battle-tested at massive scale

## Consequences

### Positive

- **Serverless-first**: Lambda, DynamoDB, AppSync reduce operational burden
- **Type safety**: CDK with TypeScript catches errors at compile time
- **Reusable constructs**: High-level abstractions for common patterns
- **Testing**: Can unit test infrastructure code
- **AWS integration**: Native service integration (IAM, CloudWatch, etc.)
- **CloudFormation**: CDK synthesizes to CloudFormation for safety
- **Developer experience**: Use familiar programming language (TypeScript)

### Negative

- **Vendor lock-in**: Tightly coupled to AWS
- **CDK learning curve**: Requires understanding both AWS and CDK
- **CloudFormation limits**: Stack limits, slow updates
- **Cost tracking**: Complex pricing across many services
- **AWS complexity**: Overwhelming number of services and options

### Risks

- **Lock-in**: Difficult to migrate to another cloud
  - *Mitigation*: Abstract business logic, use open standards where possible
- **Cost surprises**: Complex pricing can lead to unexpected bills
  - *Mitigation*: Cost monitoring, budgets, alerts
- **Region outages**: AWS region failures impact all services
  - *Mitigation*: Multi-region deployment for critical components

## Alternatives Considered

### Google Cloud Platform (GCP)

**Pros:**
- Strong ML/AI services
- Good BigQuery for analytics
- Competitive pricing
- Kubernetes expertise (GKE)

**Cons:**
- Smaller service catalog
- Less mature serverless
- Fewer regions
- Smaller community

**Why not chosen:** AWS has more comprehensive serverless ecosystem and larger market share.

### Azure

**Pros:**
- Good for enterprises
- Strong integration with Microsoft tools
- Azure Functions (serverless)
- Competitive pricing

**Cons:**
- Less mature serverless
- Smaller service catalog than AWS
- Less community support

**Why not chosen:** AWS has better serverless offerings and more comprehensive documentation.

### Terraform for IaC

**Pros:**
- Cloud-agnostic
- Mature, stable
- Large community
- State management

**Cons:**
- HASHICORP Configuration Language (not programming language)
- Limited AWS service support compared to CDK
- No compile-time type checking
- Less ergonomic than CDK

**Why not chosen:** CDK provides better developer experience with TypeScript, type safety, and faster AWS service updates.

### AWS CloudFormation (without CDK)

**Pros:**
- Native AWS tool
- No abstraction layer
- Mature and stable

**Cons:**
- Verbose YAML/JSON
- No type checking
- Hard to reuse code
- Poor developer experience

**Why not chosen:** CDK provides much better developer experience while still using CloudFormation under the hood.

## Implementation Notes

### CDK Project Structure

```
infrastructure/
├── bin/
│   └── app.ts              # CDK app entry point
├── stacks/
│   ├── api-stack.ts        # GraphQL API (AppSync)
│   ├── database-stack.ts   # DynamoDB tables
│   ├── compute-stack.ts    # Lambda functions
│   ├── storage-stack.ts    # S3 buckets
│   ├── media-stack.ts      # MediaConvert, CloudFront
│   ├── search-stack.ts     # OpenSearch domain
│   └── analytics-stack.ts  # ClickHouse, monitoring
├── constructs/
│   ├── api-construct.ts    # Reusable API construct
│   └── lambda-construct.ts # Reusable Lambda construct
└── test/
    └── stacks.test.ts      # Infrastructure tests
```

### Multi-Environment Strategy

```typescript
const app = new cdk.App();

// Development
new SocialFlowStack(app, 'SocialFlow-Dev', {
  env: { account: 'XXX', region: 'us-east-1' },
  stage: 'dev'
});

// Staging
new SocialFlowStack(app, 'SocialFlow-Staging', {
  env: { account: 'XXX', region: 'us-east-1' },
  stage: 'staging'
});

// Production (multi-region)
new SocialFlowStack(app, 'SocialFlow-Prod-US', {
  env: { account: 'XXX', region: 'us-east-1' },
  stage: 'prod'
});

new SocialFlowStack(app, 'SocialFlow-Prod-EU', {
  env: { account: 'XXX', region: 'eu-west-1' },
  stage: 'prod'
});
```

### Infrastructure Testing

```typescript
test('API stack creates AppSync API', () => {
  const app = new cdk.App();
  const stack = new ApiStack(app, 'TestStack');
  
  const template = Template.fromStack(stack);
  template.resourceCountIs('AWS::AppSync::GraphQLApi', 1);
});
```

### Deployment

```bash
# Bootstrap CDK (once per account/region)
cdk bootstrap

# Synthesize CloudFormation
cdk synth

# Deploy to dev
cdk deploy SocialFlow-Dev

# Deploy all stacks
cdk deploy --all

# Destroy dev environment
cdk destroy SocialFlow-Dev
```

### Cost Management

- **Tagging**: Tag all resources with environment, project, cost-center
- **Budgets**: Set up AWS Budgets with alerts
- **Cost Explorer**: Regular cost analysis
- **Right-sizing**: Monitor and optimize resource sizes
