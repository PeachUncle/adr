## Context

The multi-agent trading system requires:
- Independent agent lifecycle management
- Resource isolation per agent type
- Horizontal scaling for strategy execution agents
- Rapid deployment and rollback capabilities
- Consistent runtime environments across development/production
- Integration with Google Cloud Run serverless platform

Current deployment approach (virtual environments, process managers) lacks:
- Reproducible builds across environments
- Resource limits enforcement
- Automatic restart and health checking
- Version management for agent binaries
- Network isolation between agent tiers

## Decision

Adopt Docker containerization for all agent deployments with container-per-agent-type architecture on Google Cloud Run.

### Container Architecture

**Container Types**:
1. **Level 1 Container**: Portfolio Orchestrator Agent (singleton)
2. **Level 2 Container**: Stock Selection Agent (singleton)
3. **Level 3 Containers**: Strategy Execution Agents (horizontal scaling)
4. **Service Containers**: Support agents (Greeks, Risk, Execution)

**Base Image Strategy**:
```dockerfile
# Base image for all agents
FROM python:3.11-slim as base

# Security hardening
RUN useradd -m -u 1000 agent && \
    apt-get update && \
    apt-get install -y --no-install-recommends \
        ca-certificates \
        && rm -rf /var/lib/apt/lists/*

WORKDIR /app
USER agent
```

## Architecture

### Level 1 Container: Portfolio Orchestrator

**Dockerfile**: `docker/orchestrator/Dockerfile`

```dockerfile
FROM python:3.11-slim as base

RUN useradd -m -u 1000 agent
WORKDIR /app

# Install dependencies
COPY requirements/orchestrator.txt .
RUN pip install --no-cache-dir -r orchestrator.txt

# Copy application code
COPY src/agents/orchestrator/ ./orchestrator/
COPY src/common/ ./common/

# Environment configuration
ENV PYTHONUNBUFFERED=1 \
    AGENT_TYPE=orchestrator \
    AGENT_LEVEL=1 \
    MAX_POSITIONS=12 \
    MAX_PORTFOLIO_HEAT=0.25

USER agent
EXPOSE 8080
```

## Security Configuration

**Image Security**:
```dockerfile
# Multi-stage build for minimal attack surface
FROM python:3.11-slim as builder
WORKDIR /build
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

FROM python:3.11-slim
COPY --from=builder /root/.local /root/.local

# Non-root user
RUN useradd -m -u 1000 agent && \
    chown -R agent:agent /app
USER agent

# Read-only filesystem
VOLUME ["/tmp"]
ENV TMPDIR=/tmp
```

**Runtime Security**:
```yaml
security:
  # Cloud Run security settings
```

```yaml
      - '.'
    id: build-orchestrator

  - name: 'gcr.io/cloud-builders/docker'
    args:
      - 'build'
      - '-t'
      - 'us-central1-docker.pkg.dev/$PROJECT_ID/agents/stock-selection:$SHORT_SHA'
      - '-f'
      - 'docker/stock_selection/Dockerfile'
      - '.'
    id: build-stock-selection

  - name: 'gcr.io/cloud-builders/docker'
    args:
      - 'build'
      - '-t'
      - 'us-central1-docker.pkg.dev/$PROJECT_ID/agents/strategy:$SHORT_SHA'
      - '-f'
      - 'docker/strategy_agents/Dockerfile'
      - '.'
    id: build-strategy

  # Security scanning
  - name: 'aquasec/trivy'
    args:
      - 'image'
      - '--severity'
      - 'HIGH,CRITICAL'
      - 'us-central1-docker.pkg.dev/$PROJECT_ID/agents/orchestrator:$SHORT_SHA'
    id: scan-orchestrator

  # Push images
  - name: 'gcr.io/cloud-builders/docker'
    args: ['push', 'us-central1-docker.pkg.dev/$PROJECT_ID/agents/orchestrator:$SHORT_SHA']
    id: push-orchestrator

  # Deploy to Cloud Run
  - name: 'gcr.io/google.com/cloudsdktool/cloud-sdk'
    entrypoint: gcloud
    args:
      - 'run'
      - 'deploy'
      - 'portfolio-orchestrator'
      - '--image=us-central1-docker.pkg.dev/$PROJECT_ID/agents/orchestrator:$SHORT_SHA'
      - '--region=us-central1'
      - '--platform=managed'
    id: deploy-orchestrator

images:
  - 'us-central1-docker.pkg.dev/$PROJECT_ID/agents/orchestrator:$SHORT_SHA'
  - 'us-central1-docker.pkg.dev/$PROJECT_ID/agents/stock-selection:$SHORT_SHA'
  - 'us-central1-docker.pkg.dev/$PROJECT_ID/agents/strategy:$SHORT_SHA'

options:
  machineType: 'E2_HIGHCPU_8'
```

## Integration with Existing Architecture

**ADR-010 (Google ADK) Integration**:
- Each container runs Google ADK agent runtime
- State persistence via Redis (operational) and Cloud SQL (permanent)
- MCP tool servers accessible via internal networking (ADR-012)
- Agent-to-agent communication via Redis Pub/Sub

**ADR-006 (IB Gateway) Integration**:
- IB Gateway MCP server runs in dedicated container
- All agents connect via VPC internal networking
- Service account authentication for MCP calls
- Rate limiting enforced at gateway container

**ADR-002/003 (Memory Architecture) Integration**:
- Redis Memorystore accessed via Serverless VPC Access
- Cloud SQL connection via Cloud SQL Proxy sidecar
- Session context stored in Redis (TTL 24h)
- Permanent memory in Cloud SQL (agent decisions, trade history)

## Implementation Complexity

**Complexity Rating**: 3/5

**Factors**:
- Standard Docker containerization: Low complexity
- Cloud Run deployment: Medium complexity (managed service)
- Multi-container orchestration: Medium complexity (separate services)
- Security hardening: Medium complexity (IAM, secrets, scanning)

- Development: 2 DevOps engineers, 2 weeks
- Infrastructure: Cloud Run, Artifact Registry, Cloud Build
- Ongoing: Minimal operational overhead (serverless)

## Consequences

### Positive

1. **Resource Isolation**: Each agent type has dedicated resources and limits
2. **Independent Scaling**: Strategy agents scale horizontally based on load
3. **Rapid Deployment**: Container builds deploy in <5 minutes
4. **Version Management**: Immutable container tags for rollback capability
5. **Security**: Non-root containers, secret management, vulnerability scanning
6. **Cost Efficiency**: Cloud Run scales to zero for unused strategy agents
7. **Reproducible Builds**: Identical runtime across dev/staging/production
8. **Health Monitoring**: Built-in health checks and auto-restart

### Negative

1. **Cold Start Latency**: Cloud Run instances may have 1-3s cold start (mitigated by min_scale)
2. **Container Size**: ML models increase image size (stock selection: ~500MB)
3. **Network Overhead**: Container-to-container calls add latency vs in-process
4. **Build Complexity**: Multi-stage Dockerfiles require maintenance
5. **Resource Overhead**: Container runtime uses ~100MB memory baseline per instance

### Mitigation Strategies

**Cold Start**:
- Set `minScale: 1` for critical agents (Orchestrator, Stock Selection, Risk Service)
- Use `minScale: 0` only for Strategy Execution agents (acceptable latency)
- Pre-warm containers during market open (0930 ET)

**Image Size**:
- Multi-stage builds to exclude build dependencies
- Shared base image for common dependencies
- Model artifacts loaded from Cloud Storage (not baked into image)

**Network Latency**:
- VPC Connector with low-latency subnet
- HTTP/2 for multiplexing
- Connection pooling for Redis and MCP servers
- Regional deployment (all services in same region)
