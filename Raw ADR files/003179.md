# 14. Crawler Implementation for Auction Feed Discovery

**Date**: 2024-12-01

## Status

Accepted

## Context

In the PITAS ecosystem, auction feeds need to be discovered dynamically to support the decentralized architecture. The initial design required a discovery service capable of crawling other auction houses to build a network of auction feeds, subscribing to WebSub hubs, and filtering auction feeds based on application areas.

To fulfill these requirements, we decided to implement a crawler that interacts with the hypermedia overlay and retrieves auction feed links dynamically. This design choice allows for flexibility and scalability as new auction houses or hubs are added to the ecosystem.

## Decision

We implemented a crawler service that:
1. **Traverses the Hypermedia Overlay**: The crawler uses a breadth-first search (BFS) algorithm to explore the network of auction houses.
2. **Discovers Auction Feeds Dynamically**: By sending HTTP HEAD requests to the `/auctions` endpoints of known auction houses, the crawler retrieves `Link` headers containing references to hubs and other auction houses.
3. **Subscribes to Relevant Hubs**: The crawler identifies WebSub hubs via `rel="hub"` links and dynamically subscribes to them if they are relevant to the specified application areas.
4. **Filters by Application Areas**: The crawler parses `rel="<type>+auctionhouse"` annotations to filter auction feeds based on their application areas.
5. **Recursively Discovers Auction Houses**: Regardless of whether it subscribes to an auction feed, the crawler continues to explore other auction houses linked in the `Link` headers.

## Why a Crawler?

- **Dynamic Discovery**: A crawler is well-suited for the decentralized PITAS ecosystem, where new auction houses or hubs can be introduced without requiring centralized updates.
- **Hypermedia-Driven**: The crawler adheres to hypermedia principles, dynamically interpreting `Link` headers to discover and traverse the ecosystem.
- **Flexibility**: The design supports evolving requirements, such as new application areas or auction house topologies.

## How the Crawler Works

- **Initialization**: The user provides a seed URL to start the crawl. If no URL is provided, the system defaults to a predefined entry point.
- **Traversal**: The crawler performs BFS to traverse the network. HTTP HEAD requests are used to minimize payload size while retrieving `Link` headers.
- **Filtering and Subscribing**: The crawler subscribes to feeds only if they match the specified application areas. Hubs are dynamically subscribed to as needed.
- **Recursive Crawling**: Links to other auction houses are followed recursively, expanding the discovered network.

## Consequences

- **Loose Coupling**: The crawler operates independently of any specific auction house implementation, relying only on standard HTTP `Link` headers.
- **Scalability**: The BFS traversal ensures the crawler can scale to large networks of auction houses and hubs.
- **Flexibility**: The current implementation supports hardcoded application areas, but future iterations can incorporate dynamic configurations.
- **Extensibility**: The design allows for additional features, such as caching discovered auction houses or integrating more sophisticated filtering mechanisms.

## Comparison to Alternative Approaches

- **Centralized Discovery Service**: A centralized service would contradict the decentralized nature of the PITAS ecosystem and introduce a single point of failure.
- **Hardcoded Topology**: Hardcoding auction house links or hubs would reduce flexibility and require frequent updates to accommodate changes in the network.

## Trade-offs

- **Performance vs. Completeness**: Using BFS ensures all reachable auction houses are discovered, but it may be less efficient than a targeted traversal in dense networks.
- **Dynamic Subscriptions**: Subscribing dynamically introduces runtime overhead but eliminates the need for predefined hub lists.

## Future Improvements

- **Dynamic Filtering**: Replace hardcoded application areas with user-configurable filters.
- **Caching**: Implement a caching mechanism to avoid redundant requests to previously discovered auction houses.
- **Error Handling**: Enhance error handling for edge cases, such as unreachable auction houses or invalid `Link` headers.
