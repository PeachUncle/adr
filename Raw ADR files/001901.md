# ADR-003: Unified Report Generation Architecture

**Status:** Proposed  
**Date:** 2024-01-16  
**Author:** Development Team  

## Context

The current implementation has two different report generation systems that work in fundamentally different ways:

### Current Problems

1. **Classic Reports** (`back.ts`):
   - Direct API call that blocks until completion (30-120 seconds)
   - No progress tracking or intermediate states
   - Poor user experience with long loading times
   - No database record until completion

2. **Smart Agent Reports** (`smart-agent.ts`):
   - Async pattern with polling for status updates
   - Better UX with progress tracking
   - Complex state management and polling logic
   - Requires different UI flows and components

3. **Inconsistent User Experience**:
   - Different URL patterns and navigation flows
   - Complex conditional logic in components
   - Separate hooks and state management
   - Hard to maintain and extend

4. **Code Complexity**:
   - `page.tsx` has complex conditional rendering
   - Different error handling patterns
   - Duplicate loading states and UI logic
   - Hard to debug and test

## Decision

We will implement a **Unified Report Architecture** with the following principles:

### 1. Unified Data Flow
```
User clicks "Generate" → Create Report Record → Redirect to /report?reportId={id} → Unified Processing
```

### 2. Consistent State Machine
All reports (Classic and Smart) will follow the same state progression:
- `PENDING` → `IN_PROGRESS` → `COMPLETED`/`FAILED`

### 3. Single Source of Truth
- Always create a database record first (with `PENDING` status)
- All report data stored in the same `Report` table
- Unified metadata structure for both types

### 4. Unified Hook Pattern
A single `useReport(reportId)` hook handles both report types automatically.

## Architecture Design

### Database Schema Enhancement

```typescript
// Enhanced Report model
model Report {
  id        String    @id @default(cuid())
  type      ReportType // CLASSIC | SMART_AGENT
  status    ReportStatus // PENDING | IN_PROGRESS | COMPLETED | FAILED
  url       String
  userId    String
  
  // Unified report data (JSON)
  report    Json?
  
  // Unified metadata
  metadata  Json? // { progress?, currentStep?, estimatedTime?, analysisId?, etc. }
  error     Json? // Unified error structure
  
  startedAt    DateTime?
  completedAt  DateTime?
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt
}
```

### Unified Report Processing

#### 1. Report Creation (Server Action)
```typescript
// Single server action for both types
async function createReport(url: string, type: ReportType): Promise<{reportId: string}> {
  const report = await db.report.create({
```

```typescript
async function processReport(reportId: string) {

    currentStep: "Анализ сайта..."
  });
  
  // Make API call (with timeout and retry logic)
```

### Unified Frontend Hook

#### Super Smart `useReport` Hook

```typescript
// src/hooks/useReport.ts
export interface ReportState {
  status: ReportStatus;
  progress?: number;
  currentStep?: string;
  estimatedTimeRemaining?: number;
  message?: string;
  report?: SmartAgentResponse | WebsiteUXCRO;
  error?: ReportError;
  type?: ReportType;
  url?: string;
  createdAt?: Date;
}

export function useReport(reportId: string | null) {
  const [state, setState] = useState<ReportState>({ 
    status: ReportStatus.PENDING 
  });

  useEffect(() => {
    if (!reportId) return;

    let pollInterval: NodeJS.Timeout;

    const pollStatus = async () => {
      try {
        // Single endpoint that works for both types
        const result = await getReportStatus(reportId);
        
        setState({
          status: result.status,
          progress: result.metadata?.progress,
          currentStep: result.metadata?.currentStep,
          estimatedTimeRemaining: result.metadata?.estimatedTimeRemaining,
          message: result.metadata?.message,
          report: result.report,
          error: result.error,
          type: result.type,
          url: result.url,
          createdAt: result.createdAt
        });
        
        // Stop polling when complete
        if (result.status === ReportStatus.COMPLETED || result.status === ReportStatus.FAILED) {
          if (pollInterval) clearInterval(pollInterval);
        }
      } catch (error) {
        setState(prev => ({
          ...prev,
          status: ReportStatus.FAILED,
          error: { code: "FETCH_ERROR", message: error.message }
        }));
        if (pollInterval) clearInterval(pollInterval);
      }
    };

    // Start polling
    void pollStatus();
    pollInterval = setInterval(pollStatus, 2000);

    return () => {
      if (pollInterval) clearInterval(pollInterval);
    };
  }, [reportId]);

  return {
    ...state,
    isLoading: state.status === ReportStatus.PENDING || state.status === ReportStatus.IN_PROGRESS,
    isComplete: state.status === ReportStatus.COMPLETED,
    hasError: state.status === ReportStatus.FAILED,
    retryAnalysis: () => {/* retry logic */}
  };
}
```

### Simplified Page Structure

#### New Report Page (`src/app/report/page.tsx`)

```typescript
export default async function ReportPage({ searchParams }) {
  const { reportId, url } = await searchParams;
  
  // Authentication check
  const session = await auth();
  if (!session?.user) {
    redirect(`/login?callbackUrl=${encodeURIComponent(getCallbackUrl(searchParams))}`);
  }

  // If no reportId but have URL, show form to select report type
  if (!reportId && url) {
    return <ReportTypeSelector url={url} />;
  }
  
  // If no URL and no reportId, show URL input form
  if (!reportId && !url) {
    return <EnterUrlForm />;
  }

  // Main case: we have reportId - show unified report viewer
  return <UnifiedReportViewer reportId={reportId} />;
}
```

#### Unified Report Viewer Component

```typescript
function UnifiedReportViewer({ reportId }: { reportId: string }) {
  const reportState = useReport(reportId);
  
  if (reportState.isLoading) {
    return (
      <ReportLoadingState 
        progress={reportState.progress}
        currentStep={reportState.currentStep}
        estimatedTime={reportState.estimatedTimeRemaining}
      />
    );
  }
  
  if (reportState.hasError) {
    return (
      <ReportErrorState 
        error={reportState.error}
        onRetry={reportState.retryAnalysis}
      />
    );
  }
  
  if (reportState.isComplete && reportState.report) {
    // Render the appropriate report component based on type
    return reportState.type === ReportType.SMART_AGENT ? (
      <SmartAgentReport report={reportState.report} url={reportState.url} />
    ) : (
      <ClassicReport report={reportState.report} url={reportState.url} />
    );
  }
  
  return <div>No report data available</div>;
}
```

### Migration Strategy

#### Phase 1: Database and Backend
1. Update database schema to support unified structure
2. Create unified DAL methods for report management
3. Implement background job processing for classic reports
4. Add unified server actions

#### Phase 2: Frontend Unification
1. Create the unified `useReport` hook
2. Simplify page.tsx with new architecture
3. Create unified loading and error components
4. Update forms to always redirect to `/report?reportId={id}`

1. Convert classic reports to async processing
2. Add progress tracking for classic reports
3. Improve error handling and retry logic
4. Optimize API timeouts and reliability

## Benefits

### User Experience
- **Consistent Flow**: Same experience regardless of report type
- **Better Progress Tracking**: All reports show progress and status
- **Faster Perceived Performance**: Immediate redirect after clicking generate
- **Unified Error Handling**: Consistent error messages and retry options

### Developer Experience
- **Single Hook**: One `useReport` hook handles all cases
- **Simplified Components**: No more complex conditional logic
- **Easier Testing**: Unified patterns are easier to test
- **Better Maintainability**: Changes apply to both report types

### Technical Benefits
- **Reliability**: Background processing with retry logic
- **Scalability**: Can handle more concurrent reports
- **Consistency**: Same data patterns and state management
- **Extensibility**: Easy to add new report types

## Consequences

### Positive
- Dramatically simplified codebase
- Better user experience across all report types
- Easier to add new report types in the future
- More reliable report generation
- Consistent error handling and retry logic

### Negative
- **Migration Effort**: Significant refactoring required
- **Database Changes**: Need to migrate existing data
- **Temporary Complexity**: During migration, both systems may coexist
- **Testing Overhead**: Need to test migration and new unified flows

### Risks
- **Data Migration**: Risk of data loss during schema changes
- **Downtime**: May require brief service interruption
- **Performance**: Background processing may initially be slower
- **User Confusion**: URL patterns will change
