# Architecture Decision Record: PostgreSQL with Async SQLAlchemy

## Status
Accepted

## Date
2024-01-15

## Context
We needed to choose a database system for the AIVO Platform that can:

- Store student IEPs, learning progress, and analytics data
- Handle complex educational data relationships
- Support ACID transactions for compliance (FERPA/COPPA)
- Scale to 100,000+ students across multiple districts
- Enable fast analytics queries with JOINs and aggregations
- Integrate with async Python (FastAPI)
- Provide robust backup and recovery

### Alternatives Considered

1. **MySQL**
   - Pros: Popular, good tooling, wide support
   - Cons: Weaker JSON support, licensing concerns (Oracle), slower async drivers

2. **MongoDB**
   - Pros: Flexible schema, horizontal scaling, good for JSON
   - Cons: No JOINs, weaker ACID guarantees, poor for analytics, compliance concerns

3. **PostgreSQL**
   - Pros: ACID compliant, advanced JSON support, powerful analytics, strong async driver
   - Cons: More complex than MySQL, horizontal scaling requires extensions

4. **Amazon Aurora PostgreSQL**
   - Pros: Auto-scaling, high availability, managed service
   - Cons: Vendor lock-in, higher cost, less control

5. **CockroachDB**
   - Pros: Distributed SQL, auto-scaling, PostgreSQL compatible
   - Cons: More complex, higher cost, newer technology

## Decision
We have chosen **PostgreSQL 15+** with **asyncpg** driver and **SQLAlchemy 2.0** (async ORM).

## Rationale

### 1. ACID Compliance for Education Data
- Strong transaction guarantees required for:
  - IEP modifications (multiple related records)
  - Compliance audits (FERPA requires 7-year audit logs)
  - Grade and progress tracking
  - Parent consent management (COPPA)

Example transaction:
```python
async with db.transaction():
    # Update IEP
    await db.execute(update_iep_query)
    
    # Log change for FERPA audit
    await db.execute(insert_audit_log)
    
    # Notify stakeholders
    await db.execute(create_notification)
    
    # All or nothing - critical for compliance
```

### 2. Advanced JSON Support
- Education data has flexible, evolving structure
- IEP accommodations vary by student
- Learning analytics contain nested data structures

```sql
-- Query JSON data efficiently
SELECT student_id, 
       jsonb_path_query(accommodations, '$.visual[*]') as visual_aids
FROM ieps
WHERE accommodations @> '{"visual": [{"type": "text_to_speech"}]}'::jsonb;
```

### 3. Analytics Performance
- Complex queries with JOINs across students, IEPs, sessions, progress
- Window functions for time-series analytics
- CTEs (Common Table Expressions) for readable complex queries
- Materialized views for dashboard performance

```sql
-- K-anonymity aggregation (privacy-preserving analytics)
SELECT 
    district_id,
    grade_level,
    COUNT(*) as student_count,
    AVG(engagement_score) as avg_engagement,
    AVG(progress_rate) as avg_progress
FROM students s
JOIN learning_sessions ls ON ls.student_id = s.id
WHERE ls.created_at > NOW() - INTERVAL '30 days'
GROUP BY district_id, grade_level
HAVING COUNT(*) >= 5  -- k-anonymity (k=5)
```

### 4. Async Driver Performance
- **asyncpg** is the fastest PostgreSQL driver for Python
- 3-5x faster than psycopg2 (sync driver)
- Non-blocking I/O essential for 10,000+ concurrent users
- Benchmark: 60,000 queries/second vs 15,000 for sync driver

```python
# Async query
async with engine.begin() as conn:
    result = await conn.execute(
        select(Student).where(Student.district_id == district_id)
    )
    students = result.scalars().all()
```

### 5. Full-Text Search
- Search student names, IEP goals, accommodations
- Built-in `tsvector` and `tsquery` types
- GIN indexes for fast text search
- No need for external search engine (Elasticsearch) initially

```sql
CREATE INDEX idx_iep_goals_fts ON iep_goals 
USING GIN (to_tsvector('english', goal_description));

-- Fast full-text search
SELECT * FROM iep_goals
WHERE to_tsvector('english', goal_description) @@ 
      to_tsquery('english', 'reading & comprehension');
```

### 6. Data Integrity Features
- Check constraints for data validation
- Foreign keys with CASCADE options
- Exclusion constraints for preventing conflicts
- Row-level security for multi-tenancy

```sql
-- Check constraint for k-anonymity
ALTER TABLE performance_aggregates
ADD CONSTRAINT check_k_anonymity
CHECK (student_count >= k_anonymity_threshold);

-- Row-level security for district isolation
CREATE POLICY district_isolation ON students
FOR ALL
USING (district_id = current_setting('app.district_id')::uuid);
```

### 7. Extensions for Education
- **pg_stat_statements**: Query performance monitoring
- **pg_trgm**: Fuzzy string matching for name search
- **uuid-ossp**: UUID generation for student IDs
- **pg_cron**: Scheduled jobs for report generation
- **timescaledb** (optional): Time-series optimization for analytics

## Consequences

### Positive
- ✅ ACID guarantees ensure compliance data integrity
- ✅ Advanced JSON support handles flexible IEP data
- ✅ Fast analytics with complex JOINs and aggregations
- ✅ asyncpg provides high-performance async queries
- ✅ Full-text search built-in (no external dependency)
- ✅ Strong community and enterprise support
- ✅ Open source with permissive license

### Negative
- ⚠️ Horizontal scaling requires Citus or manual sharding (mitigated by vertical scaling initially)
- ⚠️ More complex than MySQL (mitigated by team training)
- ⚠️ Backup strategy requires planning (mitigated by pg_dump and WAL archiving)

### Neutral
- Need to learn PostgreSQL-specific features (JSONB, CTEs, window functions)
- Requires proper index management for performance
- Connection pooling required for scalability (using asyncpg pool)

## Implementation Notes

### Dependencies
```
sqlalchemy[asyncio]==2.0.23
asyncpg==0.29.0
alembic==1.13.0  # Database migrations
```

### Configuration
```python
# app/core/database.py
DATABASE_URL = "postgresql+asyncpg://user:password@localhost:5432/aivo_db"

engine = create_async_engine(
    DATABASE_URL,
    echo=False,
    pool_size=20,           # Connections per instance
    max_overflow=10,        # Extra connections under load
    pool_pre_ping=True,     # Check connections before use
    pool_recycle=3600,      # Recycle connections hourly
)

async_session = sessionmaker(
    engine,
    class_=AsyncSession,
    expire_on_commit=False
)
```

### Connection Pool Sizing
```
# Formula: (workers * 2) + spare
# Example: 4 workers * 2 + 2 = 10 connections per instance
# With 3 instances: 30 total connections

MIN_POOL_SIZE = 10
MAX_POOL_SIZE = 100  # Adjusted based on load testing
```

### Migration Strategy
```bash
# Create migration
alembic revision --autogenerate -m "Add analytics tables"

# Apply migration
alembic upgrade head

# Rollback if needed
alembic downgrade -1
```

### Backup Strategy
1. **Continuous WAL Archiving**: Point-in-time recovery
2. **Daily pg_dump**: Full logical backups
3. **Weekly pg_basebackup**: Physical backups
4. **Replicas**: Read replicas for analytics queries

### Performance Optimizations

1. **Indexes**:
```sql
-- Composite indexes for common queries
CREATE INDEX idx_learning_sessions_student_date 
ON learning_sessions(student_id, created_at DESC);

-- Partial indexes for filtered queries
CREATE INDEX idx_open_violations 
ON compliance_violations(severity, created_at)
WHERE status = 'open';

-- GIN indexes for JSONB
CREATE INDEX idx_ieps_accommodations 
ON ieps USING GIN (accommodations);
```

2. **Materialized Views**:
```sql
-- Pre-computed analytics
CREATE MATERIALIZED VIEW district_performance AS
SELECT 
    district_id,
    DATE_TRUNC('week', session_date) as week,
    AVG(engagement_score) as avg_engagement,
    COUNT(DISTINCT student_id) as active_students
FROM learning_sessions
GROUP BY district_id, DATE_TRUNC('week', session_date);

-- Refresh daily via pg_cron
CREATE EXTENSION pg_cron;
SELECT cron.schedule('refresh-district-perf', '0 2 * * *',
    'REFRESH MATERIALIZED VIEW CONCURRENTLY district_performance');
```

3. **Query Optimization**:
```python
# Eager loading to avoid N+1 queries
result = await session.execute(
    select(Student)
    .options(
        selectinload(Student.ieps),
        selectinload(Student.learning_sessions)
    )
    .where(Student.district_id == district_id)
)
```

## Monitoring & Metrics

Track these PostgreSQL metrics:
- Connection pool utilization
- Query latency (P50, P95, P99)
- Cache hit ratio (should be > 99%)
- Index usage (pg_stat_user_indexes)
- Table bloat (autovacuum effectiveness)
- Replication lag (for read replicas)

### Key Queries
```sql
-- Connection pool stats
SELECT count(*), state FROM pg_stat_activity GROUP BY state;

-- Slow queries
SELECT query, mean_exec_time, calls 
FROM pg_stat_statements 
ORDER BY mean_exec_time DESC LIMIT 10;

-- Cache hit ratio
SELECT 
    sum(heap_blks_hit) / (sum(heap_blks_hit) + sum(heap_blks_read)) as cache_hit_ratio
FROM pg_statio_user_tables;
```

## Scaling Strategy

### Vertical Scaling (Current)
- Start with db.m5.xlarge (4 vCPU, 16GB RAM)
- Scale up to db.m5.4xlarge (16 vCPU, 64GB RAM)
- 70% capacity: 50,000 students, 10,000 concurrent users

### Horizontal Scaling (Future)
When vertical scaling insufficient:
1. **Read Replicas**: Analytics queries on replicas
2. **Citus**: Distributed PostgreSQL for sharding
3. **Manual Sharding**: By district_id (each district isolated)

## Security

1. **Encryption**: At-rest (AES-256) and in-transit (SSL/TLS)
2. **Row-Level Security**: District data isolation
3. **Audit Logging**: pg_audit extension for FERPA compliance
4. **Principle of Least Privilege**: Application user has limited grants

```sql
-- Application user permissions
CREATE USER aivo_app WITH PASSWORD 'secure_password';
GRANT CONNECT ON DATABASE aivo_db TO aivo_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO aivo_app;
REVOKE DROP, TRUNCATE ON ALL TABLES IN SCHEMA public FROM aivo_app;
```
