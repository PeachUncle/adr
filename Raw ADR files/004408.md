# ADR 1: Monolithic Architecture with Docker

## Context
This project is built to run in a university setting with a centralized web application that's simple to deploy and maintain by a small local systems team. We're specifically designing it for the University of Victoria, not as a solution for multiple institutions.  big constraint is the need to integrate with existing university systems using Docker. The development team also prefers an environment where the backend, frontend, and databases are bundled into one cohesive package, aiming for a setup process that can be launched with just a single docker compose command.

## Decision 
We will adopt a monolithic, Dockerized architecture. The entire stack (backend, frontend, and database) will be containerized and orchestrated using Docker Compose. This is intended to simplify setup, streamline local development and deployment on local university servers. The monolithic structure will allow for easier configuration and maintenance by a small team with limited resources, while using Docker falls in line with our constraints for the operating enviornment.

## Status
Accepted

## Consequences
### Positive
- **Simplified deployment and maintenance:** With all components containerized, teams can deploy the application with minimal configuration.
- **Uniform environment:** Using Docker makes development enviornments congruent, reducing “it works on my machine” issues.
- **Faster onboarding:** The monolithic design in a single docker-compose command enables quick setup for new developers and administrators.

### Negative
- **Limited scalability:** As the application grows, the monolithic nature might make it challenging to scale individual components.
- **Potential for tight coupling:** Changes in one component could have unforeseen effects on others if the boundaries are not carefully managed. 
- **Future migration issues:** Transitioning to a distributed or microservices architecture if needed might require significant refactoring.

# ADR 2: Authentication via Auth.js for UVic Microsoft 365 Accounts

## Context
The project requires a robust authentication system to restrict access to certain University members (including staff, faculty, administrators, etc. but not students). The University has widely adopted Microsoft 365 authentication for various kinds of authentication, making it a trusted third-party identity provider. Therefore, integrating with Microsoft 365 offloads much of the verification and security concerns. Additionally, a solution that officially integerates with our NestJS backend would make implementation simpler. 

## Decision 
We will integrate Auth.js as our authentication framework. Auth.js offers native support for Microsoft 365 and integrates well with NestJS. It will streamline the authentication process, by allowing us to rely on a trusted third-party mechanisms to handle user verification, session management, and security concerns. This allows us to concentrate more development effort on building the core application functionality.

## Status
Accepted

## Consequences
### Positive
- **Reduced overhead:** Offloading authentication duties to a tried-and-tested system reduces the internal development burden.
- **Security benefits:** Leveraging Microsoft 365’s security features adheres to university policies and best practices.
- **Seamless integration:** Auth.js integrates smoothly with NestJS, which helps maintain consistency in our technology stack.

### Negative
- **Dependency on a third-party service:** Relying on external authentication means that any issues, API changes, or outages on Microsoft's or Auth.js' side could impact access.
- **Limited customization:** The use of a standardized M365-based authentication flow may restrict the flexibility to implement custom or additional authentication features.

# ADR 3: React with TypeScript for UI

## Context
The project is a web application that must be responsive, accessible, and performant on both desktop and mobile. We need a framework that supports responsive, light-weight, accessible and flexible UI, ideally with avaliable templates to minimize front-end work. In addition, a frontend framework built for use with Typescript would conform with our NestJS backend and make fullstack developement easier on the small team and reduce context-switching time sinks. A modern and widely supported frontend framework is required to meet these needs.

## Decision 
For our frontend, we will use React alongside TypeScript. React is a well-established framework with solid community backing, built-in accessibility practices, and excellent performance on both mobile and desktop platforms. It also offers a robust ecosystem, plenty of templates, and it has a proven track record in delivering fast, high-performance user interfaces. Pairing it with TypeScript will aligns our frontend with the NestJS backend which helps with the developer experience.

## Status
Accepted

## Consequences
### Positive
- **Consistent development experience:** Sharing TypeScript between frontend and backend results in fewer context switches and better code reuse patterns.
- **Rich ecosystem:** React offers a wide range of libraries and resources that can accelerate development, especially for mobile-responsive and accessible UIs.
- **Enhanced maintainability:** TypeScript’s static typing helps catch errors early and improves long-term maintainability.

### Negative
[Mostly compared to Next.js as it's our only other option]: #
- **Additional configuration overhead:** Unlike more structured frameworks like Angular that offer a more prescriptive structure out of the box, React’s open-ended nature requires teams to make additional choices about tooling and architectural patterns. This can make protyping take long and further archietcural desicions on how to configure the frontend crucial. 
- **Performance optimization responsibility:** Next.js comes with automatic performance optimizations such as code splitting, static generation, and even image optimization. In a standard React setup, we would be responsible for ensuring these optimizations, which can lead to inefficiencies if we do not manage it carefully.
- **Routing and structure:** Other framewors like Next.js and Vue offer an opinionated, file-based routing system that reduces boilerplate and potential routing errors. With React, we need to integrate routing solutions like React Router, which adds an extra step in development and can introduce variability in how navigation is managed across the project.
