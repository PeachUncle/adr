# Hypermedia APIs and the Constrained Web of Things
**Date**: 2024-12-15

## Status
Accepted
## Context
In this version, the PITAS application expanded its capabilities implementing the use of semantic hypermedia—and in particular,
the W3C Web of Things (WoT) Thing Description (TD)1—to decouple workers that offer physical
services from the concrete Web-enabled devices they use.

## Decision

We decided to create two different new workers for the new decouple workers: 
- **pitas-worker-robot**: We deiced to create a separate worker to handle the physical services of the robot. The worker when is initialized, performa SPARQL queries to the WoT Thing Directory to discover the TD of the robot. Once the TD is discovered, the worker will be able to interact with the robot using the TD. At the moment in the 
query we filter for the *cherryrobot* in order to get the td of the physical robot and see it in action. After retrieving the TD the robot worker service is called and we register a new operator to the robot. After that the robot movement can start, we only move the robot setting a new target, with a fixed movement and hard coded coordinates.
We also decided to remove our self as operator at the end of our job, in order to leave the robot free to be used by other operators. This is what we thought also all other groups would do, so we would not need to remove an operator before registering. 

- **pitas-worker-mirocard**: We created a separate worker also for the mirocard, which is based on the worker robot. The only difference is that here after we performed the query to the search engine and we retrieved the TD of the mirocard, we interact with the TD trhough *COAP* protocol. The, in the worker service, we set the "coap connection" and then perform a GET request to get the humidity value of the room. 
### Alternatives Considered
We considered to have only one worker for both the robot and the mirocard, but we decided to have two different workers in order to have a more modular and scalable system. Moreover, since we use different protocols to interact with the physical devices, we thought it was more coherent to have them separate. 

## Consequences
The consequences are that now the PITAS application has 2 new decoupled workers that offers physical
services from the concrete Web-enabled devices they use. Their URIs are not hard coded but are retrieved at runtime. 

## Trade-offs
We had to deal with the following trade offs:
- **Hard Coding the inputs of the jobs**: We decided, for both workers, to have hard coded performances of the jobs. This means that the movement of the robot is fixed and also the GET for the the mirocard is fixed to get the *humidity* of the room. We decided to opt for this solution because we wanted to focus on the interaction with the physical devices and not on the job itself. Having specific input for the job would not be complicated and could be a future improvement.

## Future Improvements
- **Dynamic Job Inputs**: As mentioned in the trade-offs, we could have dynamic inputs for the jobs. This would make the system more flexible and scalable. For example making possible to choose between humidity and temperature for the mirocard or setting a different target for the robot.
- We supposed that the robot is always free, we already have a primitive version of a solution that removes any operator from the robot and register our self to perform the Job, but it need to be tested.  This is a good solution in order to avoid problems because someone did not remove the operator from the robot.
