# ADR 004: Permission System as First-Class Concern

## Status

Accepted (November 2024)

## Context

Our application is multi-tenant with role-based access control (RBAC). Different users have different permissions (view, create, edit, delete) for different resources (campaigns, agents, customers). We need to decide how to enforce authorization in the UI.

### The Core Question:

> "Where and how do we check if a user is allowed to perform an action?"

### Option 1: Component-level role checks

```typescript
// Check user role in every component
function CampaignList() {
  const { user } = useAuth();
  const isAdmin = user.role === "admin";
  const isManager = user.role === "manager";

  return (
    <div>
      {(isAdmin || isManager) && <Button>Create Campaign</Button>}
      {isAdmin && <Button>Delete Campaign</Button>}
    </div>
  );
}
```

**Pros:**

- Simple to understand
- No abstraction

**Cons:**

- Permission logic scattered across components
- Hard to change (if roles change, update 50+ components)
- Doesn't handle granular permissions (what if managers can create but not delete?)
- Testing requires mocking entire user object
- No single source of truth for "what can this role do?"

### Option 2: Higher-Order Component (HOC) guards

```typescript
// Wrap components with permission checks
const withPermission = (Component, requiredRole) => (props) => {
  const { user } = useAuth();
  if (user.role !== requiredRole) return null;
  return <Component {...props} />;
};

const AdminCampaignList = withPermission(CampaignList, "admin");
```

**Pros:**

- Permission checks centralized in HOC
- Reusable pattern

**Cons:**

- Creates wrapper hell (multiple HOCs = `withAuth(withPermission(withLayout(Component)))`)
- Obscures component dependencies (what permissions does this need?)
- Hard to conditionally show UI elements (button visible only for admins)
- Performance: Unnecessary re-renders when wrapping entire components

### Option 3: Permission service with resource-action checks

```typescript
// Parse backend permissions into resource-action map
// utils/permissions.ts
export type PermissionsMap = Record<string, Record<string, boolean>>;
// Example: { "campaigns": { "create": true, "delete": false } }

export function parseRolePermissions(raw?: string): PermissionsMap {
  // Backend sends JSON string of permissions
  // Parse and normalize to typed structure
}

// contexts/AuthContext.tsx
const hasPermission = (resource: string, action: string) => {
  return permissions?.[resource]?.[action] ?? false;
};

// Component usage
function CampaignList() {
  const { hasPermission } = useAuth();

  const canCreate = hasPermission("campaigns", "create");
  const canDelete = hasPermission("campaigns", "delete");

  return (
    <div>
      {canCreate && <Button>Create Campaign</Button>}
      {canDelete && <Button>Delete Campaign</Button>}
    </div>
  );
}
```

**Pros:**

- Resource-action model matches backend RBAC
- Granular permissions (create ≠ delete ≠ view)
- Easy to test (mock `hasPermission` function)
- Explicit in components (clear what permissions are checked)
- Single source of truth (permissions from backend)
- Flexible (can add compound checks: `canCreate || canManage`)

**Cons:**

- Requires backend to send structured permissions
- Components must know resource names ("campaigns", "agents")
- Manual checks in every component (not automatic)

## Decision

**We will use a permission service with resource-action checks. Authorization is a first-class concern, explicitly checked before rendering actions.**

### Architecture:

```typescript
// Backend sends permissions in JWT or user profile
{
  "role": "manager",
  "permissions": {
    "campaigns": { "view": true, "create": true, "edit": true, "delete": false },
    "agents": { "view": true, "create": false, "edit": false, "delete": false },
    "customers": { "view": true, "create": false, "edit": false, "delete": false }
  }
}

// Client parses and provides hasPermission() helper
const { hasPermission } = useAuth();

// Components check explicitly
const canDelete = hasPermission("campaigns", "delete");
{canDelete && <DeleteButton />}
```

### Implementation:

```typescript
// utils/permissions.ts
export type PermissionsMap = Record<string, Record<string, boolean>>;

export function parseRolePermissions(raw?: string | unknown): PermissionsMap {
  if (!raw) return {};

  try {
    // Backend might send as string or already parsed
    const parsed = typeof raw === "string" ? JSON.parse(raw) : raw;

    // Normalize to our expected structure
    if (typeof parsed === "object" && parsed !== null) {
      return parsed as PermissionsMap;
    }
  } catch (error) {
    console.error("Failed to parse permissions:", error);
  }

  return {};
}

// contexts/AuthContext.tsx
export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const [permissions, setPermissions] = useState<PermissionsMap>({});

  useEffect(() => {
    // On login, parse permissions
    const userData = AuthService.getUser();
    if (userData) {
      setUser(userData);
      setPermissions(parseRolePermissions(userData.permissions));
    }
  }, []);

  const hasPermission = (resource: string, action: string): boolean => {
    return permissions?.[resource]?.[action] ?? false;
  };

  const hasAnyPermission = (resource: string, actions: string[]): boolean => {
    return actions.some((action) => hasPermission(resource, action));
  };

  return (
    <AuthContext.Provider
      value={{ user, permissions, hasPermission, hasAnyPermission }}
    >
      {children}
    </AuthContext.Provider>
  );
}
```

### Convention:

1. **Resource names** match backend entities:

   - `"campaigns"` (not `"campaign"` or `"Campaign"`)
   - `"agents"`, `"customers"`, `"prompts"`, etc.

2. **Action names** follow CRUD:

   - `"view"` (read/list)
   - `"create"` (insert)
   - `"edit"` (update)
   - `"delete"` (remove)
   - `"manage"` (superuser, all actions)

3. **Compound permissions** use helpers:

   ```typescript
   const canModify =
     hasPermission("campaigns", "edit") || hasPermission("campaigns", "manage");
   ```

4. **Fallback to false**: If permission not defined, assume no access.

## Consequences

### Positive

1. **Explicit Authorization**:

   ```typescript
   // Clear what this component requires
   const canCreate = hasPermission("campaigns", "create");
   const canDelete = hasPermission("campaigns", "delete");

   // Later in JSX
   {
     canCreate && <CreateButton />;
   }
   {
     canDelete && <DeleteButton />;
   }
   ```

   Reading this code, you immediately know: "This component needs create and delete permissions."

2. **Testability**:

   ```typescript
   // Test: User without delete permission shouldn't see delete button
   it("hides delete button when user lacks permission", () => {
     const authValue = {
       hasPermission: (resource: string, action: string) => {
         if (resource === "campaigns" && action === "delete") return false;
         return true;
       },
     };

     render(
       <AuthContext.Provider value={authValue}>
         <CampaignList />
       </AuthContext.Provider>
     );

     expect(screen.queryByText(/delete/i)).not.toBeInTheDocument();
   });
   ```

3. **Backend Alignment**:

   - Backend defines permissions in Keycloak/database
   - Client just consumes them
   - No client-side "business logic" for roles

4. **Granularity**:

   - Different actions for same resource
   - Manager can create campaigns but not delete
   - Support can view customers but not edit

5. **Audit Trail**:
   - Easy to log permission checks
   - Can track which features users attempt to access

### Negative

1. **Repetitive Checks**:

   ```typescript
   // Every component that shows "Create" must check
   const canCreate = hasPermission("campaigns", "create");
   {
     canCreate && <Button>Create</Button>;
   }
   ```

   **Mitigation**: Extract to custom hooks:

   ```typescript
   function useCampaignPermissions() {
     const { hasPermission } = useAuth();
     return {
       canView: hasPermission("campaigns", "view"),
       canCreate: hasPermission("campaigns", "create"),
       canEdit: hasPermission("campaigns", "edit"),
       canDelete: hasPermission("campaigns", "delete"),
     };
   }
   ```

2. **Client-Side Only (Not Secure)**:

   - These checks are for UX, not security
   - Backend MUST also enforce permissions
   - Attacker can bypass by calling API directly

   **Mitigation**: Document this clearly:

   ```typescript
   // SECURITY NOTE: This is UX-only. Backend must enforce.
   const canDelete = hasPermission("campaigns", "delete");
   ```

3. **String-Based API (Typo-Prone)**:

   ```typescript
   hasPermission("campains", "create"); // Typo: "campains"
   // Returns false, looks like permission issue
   ```

   **Mitigation**: Use constants:

   ```typescript
   // utils/permissions.ts
   export const RESOURCES = {
     CAMPAIGNS: "campaigns",
     AGENTS: "agents",
     CUSTOMERS: "customers",
   } as const;

   export const ACTIONS = {
     VIEW: "view",
     CREATE: "create",
     EDIT: "edit",
     DELETE: "delete",
   } as const;

   // Usage
   hasPermission(RESOURCES.CAMPAIGNS, ACTIONS.CREATE);
   ```

### Tradeoffs Accepted

| HOC Guards                             | Permission Service (Our Choice)         |
| -------------------------------------- | --------------------------------------- |
| ✅ No manual checks in components      | ❌ Must call hasPermission() explicitly |
| ❌ Wrapper hell                        | ✅ No wrappers                          |
| ❌ Hard to conditionally show elements | ✅ Easy to conditionally render         |
| ❌ Obscures dependencies               | ✅ Explicit what's required             |

**Conclusion**: We accept manual permission checks in exchange for explicitness and testability.

## Implementation Examples

### Page-Level Permission Check

```typescript
// pages/Campaigns.tsx
function CampaignsPage() {
  const { hasPermission } = useAuth();

  const canView = hasPermission("campaigns", "view");
  const canCreate = hasPermission("campaigns", "create");
  const canDelete = hasPermission("campaigns", "delete");

  if (!canView) {
    return (
      <AccessDenied message="You don't have permission to view campaigns" />
    );
  }

  return (
    <div>
      <PageHeader>
        <h1>Campaigns</h1>
        {canCreate && <Button onClick={openCreateDialog}>New Campaign</Button>}
      </PageHeader>

      <CampaignList onDelete={canDelete ? handleDelete : undefined} />
    </div>
  );
}
```

### Component-Level Permission Check

```typescript
// components/CampaignCard.tsx
function CampaignCard({ campaign }: { campaign: Campaign }) {
  const { hasPermission } = useAuth();

  const canEdit = hasPermission("campaigns", "edit");
  const canDelete = hasPermission("campaigns", "delete");

  return (
    <Card>
      <CardHeader>{campaign.name}</CardHeader>
      <CardContent>{campaign.description}</CardContent>
      <CardFooter>
        {canEdit && (
          <Button onClick={() => editCampaign(campaign.id)}>Edit</Button>
        )}
        {canDelete && <Button variant="destructive">Delete</Button>}
      </CardFooter>
    </Card>
  );
}
```

### Modal Permission Check

```typescript
// components/CreateCampaignDialog.tsx
function CreateCampaignDialog({ open, onOpenChange }: DialogProps) {
  const { hasPermission } = useAuth();

  const canCreate = hasPermission("campaigns", "create");

  // Don't render modal if user can't create
  if (!canCreate) return null;

  return (
    <Dialog open={open} onOpenChange={onOpenChange}>
      <DialogContent>
        <DialogHeader>Create Campaign</DialogHeader>
        <CampaignForm onSubmit={handleCreate} />
      </DialogContent>
    </Dialog>
  );
}
```

### Compound Permissions

```typescript
// Check multiple actions (OR logic)
const canModify =
  hasPermission("campaigns", "edit") || hasPermission("campaigns", "manage");

// Check multiple actions (AND logic)
const canFullAccess =
  hasPermission("campaigns", "view") &&
  hasPermission("campaigns", "create") &&
  hasPermission("campaigns", "edit") &&
  hasPermission("campaigns", "delete");

// Helper for OR logic
const { hasAnyPermission } = useAuth();
const canModify = hasAnyPermission("campaigns", ["edit", "manage"]);
```

## Compliance

### How to verify we follow this decision:

```bash
# All permission checks use hasPermission()
grep -r "hasPermission" src/pages/ src/components/ | wc -l
# Expected: 30+ calls (one per protected action)

# No direct role checks
grep -r "user.role ===" src/pages/ src/components/
# Expected: 0 results (use hasPermission instead)

# All tests mock hasPermission
grep -r "hasPermission.*mockImplementation\|hasPermission.*vi.fn" src/__tests__/
# Expected: 10+ (tests verify permission gating)
```

### When to revisit:

- If permission checks become too repetitive (> 5 calls per component) → consider custom hooks
- If backend changes permission structure (nested resources, hierarchical permissions)
- If we need attribute-based access control (ABAC) instead of RBAC
- If we add row-level permissions (user owns specific campaign, not all campaigns)

## Backend Contract

Our client expects backend to provide permissions in this format:

```json
// POST /auth/login response
{
  "user": {
    "id": "123",
    "email": "user@example.com",
    "role": "manager"
  },
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "permissions": {
    "campaigns": {
      "view": true,
      "create": true,
      "edit": true,
      "delete": false,
      "manage": false
    },
    "agents": {
      "view": true,
      "create": false,
      "edit": false,
      "delete": false,
      "manage": false
    }
  }
}
```

Alternatively, permissions can be embedded in JWT claims:

```json
// JWT payload
{
  "sub": "123",
  "email": "user@example.com",
  "role": "manager",
  "permissions": {
    "campaigns": { "view": true, "create": true, ... }
  }
}
```

**Client responsibility**: Parse and store permissions  
**Backend responsibility**: Define and enforce permissions

## Real-World Results

### Before (Role-based checks):

```typescript
// Old pattern (scattered role checks)
{
  user.role === "admin" && <DeleteButton />;
}
{
  (user.role === "admin" || user.role === "manager") && <EditButton />;
}
```

**Problems**:

- Added "supervisor" role → had to update 40+ components
- No way to give managers delete permission without changing role
- Tests mocked entire user object for one permission

### After (Permission-based checks):

```typescript
// New pattern
{
  hasPermission("campaigns", "delete") && <DeleteButton />;
}
{
  hasPermission("campaigns", "edit") && <EditButton />;
}
```

**Results**:

- Added "supervisor" role → backend defined permissions, client unchanged
- Gave managers delete permission → backend config change, zero client code changes
- Tests mock single function: `hasPermission = vi.fn()`

### Metrics:

- **Permission changes**: 5 in 6 months
- **Client code changes**: 0 (all handled by backend)
- **Permission-related bugs**: 1 (typo in resource name, fixed with constants)
- **Test coverage of permission gating**: 85%

## Security Considerations

### ⚠️ CRITICAL: Client-Side Permissions Are NOT Security

**These permission checks are for USER EXPERIENCE only.**

```typescript
// This prevents user from seeing "Delete" button
{
  hasPermission("campaigns", "delete") && <DeleteButton />;
}

// But attacker can still call API:
fetch("/api/campaigns/123", { method: "DELETE" });
```

**Backend MUST enforce permissions**:

```typescript
// Backend (example)
app.delete("/api/campaigns/:id", authenticate, async (req, res) => {
  // Check permission server-side
  if (!hasPermission(req.user, "campaigns", "delete")) {
    return res.status(403).json({ error: "Forbidden" });
  }

  await deleteCampaign(req.params.id);
  res.json({ success: true });
});
```

**Our approach**:

- Client permissions hide UI elements (better UX)
- Backend permissions block unauthorized actions (actual security)
- Both use same resource-action model (consistency)

### Permission Tampering:

**Attack**: User modifies permissions in browser console:

```javascript
// Attacker tries to grant themselves permissions
localStorage.setItem(
  "permissions",
  JSON.stringify({ campaigns: { delete: true } })
);
```

**Defense**:

- Permissions come from backend on every login
- Access token contains permissions (signed by backend)
- Backend validates token on every request
- Client permissions are ephemeral (reload → re-fetch from server)

**Conclusion**: Client tampering only affects their own UI. Backend blocks unauthorized actions.
