# ADR-0003: Docker Compose Local Development Strategy

> **Scope**: Document decision clusters, not individual technology choices. Group related decisions that work together (e.g., "Frontend Stack" not separate ADRs for framework, styling, deployment).

- **Status:** Accepted
- **Date:** 2025-12-12
- **Feature:** 001-task-crud-auth
- **Context:** Phase II requires a local development environment that supports frontend (Next.js), backend (FastAPI), and database (PostgreSQL) simultaneously. Developers need rapid iteration with hot reload, reproducible environments across machines, and minimal setup complexity. The development environment must match production architecture while remaining fast and accessible.

## Decision

**Docker Compose** for local development with 3 orchestrated services:

**Services:**
- **`db`**: PostgreSQL 16 container with persistent volume
- **`backend`**: FastAPI container with hot reload (Uvicorn --reload)
- **`frontend`**: Next.js container with Fast Refresh

**Key Features:**
- **Single-Command Startup:** `docker-compose up` starts all services
- **Hot Reload:** Code changes reflected in <3 seconds (volume mounts for source code)
- **Environment Parity:** Same Docker images used in development and production (different config only)
- **Persistent Data:** Database volume survives container restarts
- **Service Discovery:** Services communicate via Docker network (backend → db, frontend → backend)
- **Environment Variables:** `.env` files for configuration (DATABASE_URL, BETTER_AUTH_SECRET, etc.)

**Production Strategy:**
- **Development:** Docker Compose with PostgreSQL container
- **Production:** Container orchestration (Cloud Run, ECS) with Neon Serverless PostgreSQL
- **Same Schema:** Change only `DATABASE_URL` to switch environments

## Consequences

### Positive

- **Reproducible Environment:** "Works on my machine" eliminated - same Docker setup for all developers
- **Fast Onboarding:** New developers run `docker-compose up` (no local installations of Node, Python, PostgreSQL)
- **Hot Reload Speed:** <3 seconds for code changes (Next.js Fast Refresh, Uvicorn auto-reload)
- **Environment Parity:** Development containers match production architecture (same Dockerfiles)
- **Persistent Data:** Database volume persists across container restarts (no data loss during development)
- **Service Isolation:** Services run in separate containers with network isolation
- **Cross-Platform:** Works identically on Windows, macOS, Linux (Docker abstraction layer)
- **Easy Cleanup:** `docker-compose down` removes all containers cleanly

### Negative

- **Docker Dependency:** All developers must install Docker Desktop (licensing cost for large enterprises)
- **Resource Overhead:** Docker containers consume more RAM than native processes (~1GB for 3 services)
- **Slower First Build:** Initial `docker-compose up --build` takes 2-5 minutes (caching improves subsequent builds)
- **Volume Performance:** File watching on macOS/Windows can be slower than Linux (Docker volume sync overhead)
- **Learning Curve:** Developers unfamiliar with Docker must learn container concepts, Dockerfiles, docker-compose.yml
- **Debugging Complexity:** Debugging inside containers requires additional setup (remote debuggers, port forwarding)
- **Network Quirks:** Localhost vs container hostnames can confuse developers (frontend → http://backend:8000, not localhost:8000)

## Alternatives Considered

**Alternative A: Local Installations (npm, Python, PostgreSQL)**
- Install Node.js, Python, PostgreSQL directly on developer machines
- Why rejected:
  - Environment inconsistency: Different versions across developer machines ("works on my machine")
  - Complex setup: Developers manage npm, UV, PostgreSQL installation manually
  - Version conflicts: Global Python packages conflict between projects
  - Platform differences: Windows, macOS, Linux have different installation procedures
- Tradeoffs: Slightly faster execution (no Docker overhead), but environment inconsistency and setup complexity

**Alternative B: Cloud-Only Development (GitHub Codespaces, Gitpod)**
- All development in cloud-based environments (browser-based IDEs)
- Why rejected:
  - Requires constant internet connection (productivity blocked by outages)
  - Slower iteration: Network latency affects every keystroke and hot reload
  - Cost: Cloud environments charge per hour (monthly costs add up)
  - Limited IDE features: Browser-based IDEs lack full VS Code/PyCharm functionality
- Tradeoffs: Zero local setup, but dependent on internet, slower iteration, ongoing costs

**Alternative C: Kubernetes (Minikube, Kind, K3s) for Local Development**
- Run full Kubernetes cluster locally with Helm charts
- Why rejected:
  - Over-engineering: Kubernetes complexity unnecessary for 3-service application
  - Slow iteration: Kubernetes deployment cycles slower than Docker Compose
  - Resource intensive: Kubernetes control plane consumes significant RAM
  - Steep learning curve: Developers must learn Kubernetes concepts (pods, services, ingress)
- Tradeoffs: Matches production Kubernetes exactly, but excessive complexity for development

**Alternative D: Hybrid (Docker for DB only, native Node/Python)**
- Run only PostgreSQL in Docker, Node and Python natively
- Why rejected:
  - Partial solution: Doesn't solve Node/Python version consistency
  - Mixed complexity: Developers manage both Docker and native installations
  - Environment drift: Development environment still differs from production
- Tradeoffs: Lower resource usage than full Docker Compose, but incomplete solution

**Why Docker Compose Wins:**
- **Reproducibility:** Guaranteed identical environment across all developer machines
- **Single-command startup:** `docker-compose up` vs manual start of 3 services
- **Environment parity:** Same containers in development and production
- **Hot reload:** Fast enough for productive development (<3 seconds)
- **Proven pattern:** Industry standard for local multi-service development
