# 003: Initial Monolithic Database with Logical Separation

## Status
Accepted

## Context
A pure microservices architecture often calls for a "database-per-service" pattern to ensure loose coupling. However, our system's core functionality—the MatchingEngine—requires complex, performant spatial-temporal queries that join data from the Reports and Vessels domains. Implementing these joins across separate databases in a distributed environment would be complex, inefficient, and introduce significant challenges with data consistency and referential integrity. As "Software Architecture: The Hard Parts" (Chapter 6) notes, data relationships are a strong integrator force.

## Decision
We will begin with a monolithic database pattern (a single PostgreSQL instance with PostGIS) to serve all services. This is a pragmatic trade-off that prioritizes initial development speed and query performance. To mitigate the risks of coupling, we will enforce logical separation and clear data ownership:

- **Schema per Service**: Each service will have its own database schema (e.g., reports, vessels, alerts).
- **Data Ownership**: A service is forbidden from directly writing to another service's schema. All cross-service data modifications must happen via API calls or events. Read-only access to other schemas is permissible but should be minimized.
- **Future Decomposition**: This logical separation prepares us for a future evolution towards a "database-per-service" model if scalability becomes a major concern.

## Consequences

### Positive

- **Simplified Development**: Avoids the complexity of distributed transactions and cross-database joins from day one.
- **High Performance for Queries**: The MatchingService can leverage the full power of PostgreSQL and PostGIS for efficient, atomic queries across report and vessel data.
- **Transactional Integrity**: Guarantees ACID compliance for operations within the single database.

### Negative

- **Architectural Coupling**: The services are not fully independent; they are coupled at the database layer. A change to the database schema for one service could potentially impact another.
- **Scalability Bottleneck**: The single database could become a performance bottleneck for the entire system, although this is a manageable risk at our initial scale.
