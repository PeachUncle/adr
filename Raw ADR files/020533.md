# ADR-002: Use FPP REST API Over Direct Protocol

## Status
**Accepted** (2025-12-23)

## Context
Need to send test patterns to FPP controllers. Two main approaches:
1. **FPP REST API**: HTTP POST to `/api/command`
2. **Direct Protocol**: Send DDP/E1.31/ArtNet packets directly

Key factors:
- Simplicity vs. performance
- FPP API documentation availability
- Latency requirements (< 1s acceptable)
- Fallback options if API insufficient

## Decision
**Use FPP REST API as primary method, with direct protocol as fallback**

## Consequences

### Positive
- **Simple implementation**: Standard HTTP POST with JSON
- **Documented**: FPP API well-documented at `/api/help`
- **Error handling**: Structured JSON responses
- **Future-proof**: API less likely to change than binary protocols
- **Authentication-ready**: If FPP adds auth, API will support it
- **No protocol complexity**: Don't need to understand DDP/E1.31 packet format
- **Cross-browser**: Fetch API works everywhere

### Negative
- **Latency**: HTTP overhead (~50-100ms) vs. direct UDP (~5-10ms)
- **Dependency**: Relies on FPP web server being operational
- **Limited patterns**: May not support custom effects (can fallback)

### Risks & Mitigations
| Risk | Mitigation |
|------|------------|
| API doesn't support test patterns | Research early, implement direct DDP fallback |
| HTTP latency > 1s | Acceptable for field testing use case |
| FPP web server crashes | Direct protocol fallback or controller reboot docs |

## Alternatives Considered

### Alternative 1: Direct DDP Protocol
**Pros:**
- Lower latency (~10ms vs. ~100ms)
- Works even if FPP web server down
- No dependency on API stability
- More control over pixel data

**Cons:**
- Must implement DDP packet format (header + channel data)
- Must calculate universe/channel offsets
- Must handle multi-packet spanning for large props
- Binary protocol is harder to debug
- Browser UDP support limited (WebRTC/WebTransport needed)

**Why rejected as primary:** Unnecessary complexity for < 1s latency requirement. Keep as fallback option.

### Alternative 2: E1.31 (sACN)
**Pros:**
- Industry standard DMX-over-Ethernet
- Well-documented protocol
- Low latency

**Cons:**
- More complex than DDP (multicast, priority, sequence numbers)
- Requires universe math (512 channels per universe)
- Browser UDP limitations
- Not all FPP configs use E1.31

**Why rejected:** Same browser limitations as DDP, more complexity.

### Alternative 3: ArtNet
**Pros:**
- Older, well-established protocol
- Low latency

**Cons:**
- Deprecated in favor of sACN/DDP
- Universe size limits (512 channels)
- Not as common in FPP setups

**Why rejected:** Less common, no advantages over DDP.

## Implementation Notes

### FPP API Endpoint Research Needed
Before Phase 7 (implementation), verify:
- [ ] Exact API endpoint for test patterns: `POST /api/command`
- [ ] Available commands: `Set Channel Output`, `Test Pattern`, etc.
- [ ] Command payload format
- [ ] Response codes and error handling

Example hypothesis (to be validated):
```json
POST /api/command
{
  "command": "Set Channel Output",
  "args": {
    "channel": 1,
    "value": 255,
    "count": 150
  }
}
```

### Fallback to Direct DDP (If Needed)
If FPP API insufficient:
1. Implement DDP packet builder
2. Send via HTTP POST to `/api/channel/output/raw` (if available)
3. Or use WebSocket for real-time control
