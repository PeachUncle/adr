# NATS and GraphQL Pattern Integration

## Status
Proposed

## Context
Our core services follow a GraphQL-like query pattern with complex filtering, relations, and pagination. We need to determine how this pattern can effectively work with NATS while building our Process Orchestrator.

## Problem
NATS and GraphQL-like patterns have different characteristics that need to be reconciled:

1. **NATS Characteristics**
   - Message-based communication
   - Limited payload size (default 1MB)
   - Request-reply pattern support
   - Subject-based routing
   - Pub/sub capabilities

2. **GraphQL Pattern Requirements**
   - Complex nested queries
   - Field selection
   - Query batching
   - Real-time subscriptions
   - Type system

## Analysis

### Challenges

1. **Message Size Limitations**
```typescript
// Complex query example that could exceed NATS limits
interface ComplexQuery {
  fields: string[];
  relations: {
    name: string;
    fields: string[];
    nested: {
      name: string;
      fields: string[];
    }[];
  }[];
  filters: {
    expressions: string;
    parameters: Record<string, any>;
  };
  pagination: {
    offset: number;
    limit: number;
  };
}
```

2. **Performance Implications**
- Multiple round trips for nested data
- Network overhead for large result sets
- Connection pooling complexity
- Message size optimization needs

3. **Technical Constraints**
- Limited streaming capabilities
- Complex error handling for nested operations
- Schema distribution challenges
- Type system synchronization

## Decision

We will implement a hybrid approach that leverages the strengths of both NATS and direct HTTP/gRPC communication:

### 1. NATS Usage
- Process orchestration and management
- Event notifications
- Simple queries and commands
- State management
- Service discovery

### 2. Direct Communication
- Complex data fetching
- Large result sets
- Nested queries
- File transfers
- Streaming operations

### Implementation Strategy

1. **Process Orchestration via NATS**
```typescript
interface ProcessMessage {
  processId: string;
  stepId: string;
  action: 'START' | 'COMPLETE' | 'FAIL' | 'COMPENSATE';
  payload: {
    data?: Record<string, any>;
    error?: string;
  };
}
```

2. **Data Fetching via HTTP/gRPC**
```typescript
interface DataFetchStep {
  type: 'DATA_FETCH';
  service: string;
  endpoint: string;
  method: 'GET' | 'POST';
  query: {
    fields: string[];
    relations: string[];
    filters: Record<string, any>;
  };
}
```

3. **Hybrid Process Definition**
```typescript
interface ProcessDefinition {
  id: string;
  name: string;
  steps: Array<{
    id: string;
    type: 'NATS' | 'HTTP' | 'GRPC';
    service: string;
    action: string;
    compensation?: string;
    timeout: number;
    // For HTTP/gRPC steps
    query?: {
      fields?: string[];
      relations?: string[];
      filters?: Record<string, any>;
    };
  }>;
}
```

### Example Process Flow
```typescript
const hostRegistrationProcess: ProcessDefinition = {
  id: 'host-registration',
  name: 'Host Registration Process',
  steps: [
    {
      id: 'fetch-user',
      type: 'HTTP',
      service: 'user-service',
      action: 'GET /users/{userId}',
      timeout: 5000,
      query: {
        fields: ['id', 'email', 'status'],
        relations: ['profile', 'verification']
      }
    },
    {
      id: 'create-host',
      type: 'NATS',
      service: 'user-service',
      action: 'host.create',
      timeout: 5000,
      compensation: 'host.delete'
    },
    {
      id: 'verify-documents',
      type: 'GRPC',
      service: 'verification-service',
      action: 'VerificationService/VerifyDocuments',
      timeout: 10000
    }
  ]
};
```

## Consequences

### Positive
1. **Optimized Communication**
   - Best tool for each operation type
   - Better performance for complex queries
   - Reduced network overhead

2. **Improved Reliability**
   - No payload size issues
   - Better error handling
   - Appropriate protocols for each operation

3. **Enhanced Flexibility**
   - Multiple communication options
   - Protocol-specific optimizations
   - Better scaling options

### Negative
1. **Increased Complexity**
   - Multiple protocols to manage
   - More complex deployment
   - Additional configuration needed

2. **Operation Overhead**
   - Protocol switching logic
   - Multiple client libraries
   - Additional monitoring needed
