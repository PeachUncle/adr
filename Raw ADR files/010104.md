# ADR-003: Microservices Decoupling Strategy

## Status
Accepted

## Context
For our cryptocurrency trading bot to be maintainable, scalable, and resilient, we need to ensure proper decoupling between services. This involves determining strategies for service boundaries, contracts, and deployment.

## Decision
We will implement the following strategies for service decoupling:

### 1. Contract-First Design
- Each service will define and publish a clear contract (API specification or event schema)
- Contracts will be versioned and backward compatible where possible
- We will use JSON Schema for event payloads to allow for schema validation

### 2. Domain-Driven Service Boundaries
- Services are defined along domain boundaries (data collection, ML analysis, trade execution)
- Each service owns its data and exposes it only through its defined contracts
- Cross-domain references use identifiers rather than direct object references

### 3. Independent Deployability
- Services will be packaged as independent containers
- Each service has its own release cycle and versioning
- Deployment can occur without coordinating with other services

### 4. Asynchronous Communication
- Primary mode of communication is asynchronous via NATS
- Services should not rely on immediate responses from other services
- Services should be resilient to other services being temporarily unavailable

### 5. Statelessness Where Possible
- Core business logic services will be stateless where possible
- State will be externalized to dedicated data stores or managed via NATS JetStream
- This enables easier scaling and failover

## Specific Implementation
1. **Event Schemas**: 
   - All NATS messages will conform to published schemas
   - Schemas will be stored in a shared repository
   - Schema evolution follows clear compatibility rules

2. **API Documentation**:
   - REST APIs will be documented using OpenAPI
   - gRPC services will use Protocol Buffers with clear documentation

3. **Service Discovery**:
   - Services will locate each other through DNS-based discovery
   - The API Gateway will handle external API routing

4. **Authentication**:
   - Token-based authentication will be managed by the Security Service
   - Internal service-to-service communication will use mTLS

## Consequences
- **Positive**: Services can be developed, tested, and deployed independently
- **Positive**: System is more resilient to partial failures
- **Positive**: Easier to scale individual components based on load
- **Negative**: More complex initial setup
- **Negative**: More complex testing of end-to-end flows
- **Negative**: Requires discipline in following decoupling practices
