# ADR-0002: WireGuard Client-Only Design

**Status:** Accepted

**Date:** 2025-11-02

**Deciders:** Solo developer

---

## Context

vpn-hopper needs WireGuard functionality to connect to remote networks. There are several approaches to implementing WireGuard support:

### Option 1: Client + Server (Full VPN Solution)
- Container acts as both WireGuard server and client
- Can accept peer connections and initiate connections
- More complex configuration

### Option 2: Client-Only
- Container only initiates connections to existing WireGuard servers
- Simpler, single responsibility
- Requires external WireGuard server

### Option 3: Mesh Network Support
- Container participates in peer-to-peer mesh
- Complex routing and discovery
- Requires additional tooling

---

## Decision

**vpn-hopper will be a WireGuard client only**, not a server.

The container will:
- Connect to one or more existing WireGuard servers (peers)
- Support multiple peer configurations via `wg0.conf`
- Not accept incoming WireGuard connections from other peers
- Focus exclusively on "jump into an existing network" use case

---

## Rationale

### Advantages

1. **Clear Responsibility**
   - Single purpose: access remote networks
   - Not trying to be a full VPN solution
   - Easier to understand and document

2. **Simpler Configuration**
   - Users only need client keys and server info
   - No need to manage peer public keys on the container
   - Fewer configuration mistakes

3. **Security**
   - Smaller attack surface (no listening WireGuard port)
   - Only outbound connections initiated
   - Easier to firewall and harden

4. **Complements Existing Infrastructure**
   - Assumes users already have WireGuard servers
   - Doesn't compete with existing VPN solutions
   - Fills the "troubleshooting client" niche

5. **Resource Efficiency**
   - No need to track multiple peer states
   - Less memory and CPU overhead
   - Simpler networking rules

### Disadvantages

1. **Requires External Server**
   - Users must set up their own WireGuard server
   - Cannot be used standalone as VPN infrastructure
   - Additional prerequisite

2. **No Site-to-Site VPN**
   - Cannot connect two networks directly
   - Not suitable for mesh VPN scenarios

3. **Limited Peer-to-Peer**
   - Cannot accept connections from other clients
   - All traffic must route through server(s)

---

## Consequences

### Positive

- Documentation can focus on "connecting to your existing VPN"
- Smaller image size (fewer tools and configs needed)
- Clearer use case positioning
- Lower support burden (fewer configuration permutations)

### Negative

- Users wanting a full VPN solution must look elsewhere
- Cannot replace traditional VPN server software
- Requires infrastructure setup before using vpn-hopper

### Mitigations

- Clearly document in README that external WireGuard server is required
- Provide links to WireGuard server setup guides
- Suggest existing WireGuard server solutions (pivpn, wg-easy, etc.)

---

## Use Cases Supported

✅ **Supported:**
- Access home network from remote location
- Troubleshoot office network via VPN
- Debug IoT devices on remote network
- Multiple WireGuard servers (multi-peer config)
- Network diagnostics on remote networks

❌ **Not Supported:**
- Creating a VPN server for others to connect to
- Site-to-site VPN without separate server
- Mesh VPN participation
- Dynamic peer discovery and routing

---

## Alternatives Considered

### Alternative 1: Full Server + Client

**Example config:**
```ini
[Interface]
Address = 10.13.13.1/24
ListenPort = 51820  # Accept incoming connections
PrivateKey = ...

[Peer]
PublicKey = ...  # Peer 1
AllowedIPs = 10.13.13.2/32

[Peer]
PublicKey = ...  # Peer 2
AllowedIPs = 10.13.13.3/32
```

**Rejected because:**
- Significantly more complex
- Requires port forwarding and NAT traversal
- Higher security risk
- Not aligned with "troubleshooting jumpbox" use case
- Would need peer management UI/API

### Alternative 2: WireGuard Mesh (wireguard-p2p)

**Rejected because:**
- Adds dependency on external mesh tools
- Requires peer discovery mechanism
- Overcomplicated for the target audience
- Most users have simple client-server setups

---

## Implementation Details

### Multi-Peer Support

While client-only, we **do** support multiple peers in one config:

```ini
[Interface]
Address = 10.13.13.5/32
PrivateKey = CLIENT_PRIVATE_KEY

[Peer]
PublicKey = OFFICE_SERVER_PUBLIC_KEY
Endpoint = office.example.com:51820
AllowedIPs = 10.13.13.0/24

[Peer]
PublicKey = LAB_SERVER_PUBLIC_KEY
Endpoint = lab.example.com:51820
AllowedIPs = 10.42.0.0/16
```

This allows accessing multiple networks simultaneously, all routing through respective servers.

## Documentation Requirements

Due to this decision, documentation must:
- Clearly state "WireGuard client only" in feature list
- Provide prerequisites section mentioning WireGuard server requirement
- Link to external WireGuard server setup guides
- Show multi-peer examples for connecting to multiple networks

---

## Review

Should be reviewed if:
- User requests for server functionality become overwhelming
- Mesh VPN becomes a common use case for the tool
- WireGuard server setup becomes too complex for target users
- Container security posture changes

---

## Notes

This decision aligns with the Unix philosophy: "Do one thing and do it well."

vpn-hopper is a **tool for accessing networks**, not a tool for **creating networks**.
