# 5. Splitting PITAS Architecture into 5 Services for Modularity and Scalability

Date: 2024-09-30

## Status

Accepted

## Context

PITAS is managing job assignments, workers, scheduling, external worker auctions, and a credit system. We initially split this into two services (_Internal Job Assignment_, _External Work Searcher_). However, as the project evolves, we see the need for a more modular service-based architecture to support scalability, fault tolerance, and manageability.

The architecture must prioritize clear workflows, fault tolerance, and scalability while maintaining data consistency across systems.

## Decision

Split the PITAS architecture into five independent services:
- **Job List** (pitas-jobs): Handles job creation and persistence.
- **Worker Management** (pitas-workers): Manages worker list and worker-related data. It also contains the workers itself which are added to the list on startup of the service.
- **Scheduler** (pitas-scheduler): Assigns jobs to available workers.
- **Auction House** (pitas-aution-house): Manages external worker bidding and selection.
- **Credit System** (pitas-credits): Handles credits and payments for external workers.

This decision is based on the revision of the integrators and disintegrators and also our bounded context map.

### Disintegrators
- **Service Functionality:** We could furher split the Job List, Worker Management, and Scheduler services, as they have distinct responsibilities. The Auction House and Credit System could be seperated too, as they have different responsibilites. One is handling the bidding process and the other the payment process.
- **Code Volatility:** Separating the Worker Management and Scheduler services makes sense since worker availability logic might change more frequently than job assignment logic. Credit System and Auction House are also separated because changes in financial systems (like credits) do not often align with changes in auction systems.
- **Scalability and Throughput:** Job List and Scheduler have different scalability needs. Scheduler could face more load when assigning jobs, whereas Job List mainly handles data persistence. Worker Management scales with the number of workers added and removed, while Credit System scales with the number of transactions.
- **Fault Tolerance:** Scheduler and Worker Management are critical for internal functionality, so keeping them separate ensures that worker updates don’t crash the scheduling process. Credit System should be independent to avoid issues with financial transactions affecting external auctions.
- **Extensibility:** Each service can be extended independently. For example, you could add more complex worker matching to Scheduler or support for more auction platforms to Auction House without affecting the other services.

### Integrators:
- **Workflow and Choreography:** Job List works closely with Scheduler, but it is not required to be in the same service. They can communicate via APIs. Worker Management needs to work with Scheduler to provide available workers, but again, API-driven communication suffices. Auction House communicates with Credit System, but they can remain separate, linked through well-defined workflows.
- **Shared Code:** Worker Management and Scheduler might share some code for worker status updates, but separating them is still a valid decision. Auction House and Credit System might share some common transaction-related code, but separating them is still a valid decision.
- **Data Relationships:** Each service manages its own data, ensuring minimal overlap. Worker Management handles worker data, Scheduler only assigns jobs, and Credit System handles financial records, so data separation supports the architecture.

## Consequences
We will be closer to a microservices architecture, which has both positive and negative consequences. 

### Positive
- **Modularity**: Each service is independently scalable and extensible.
- **Fault Tolerance**: Failures in one service (e.g., Auction House) do not impact others (e.g., Job Assignment).
- **Targeted Testing**: Each service can be tested in isolation, simplifying the testing process.

### Negative
- **Increased Communication Overhead**: More services mean more API interactions, which could lead to latency and potential communication failures.
- **Higher Resource Utilization**: Running multiple independent services will consume more computational resources.
