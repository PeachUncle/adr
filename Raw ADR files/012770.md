## Context

Phase 1 requires establishing CI infrastructure for automated SSOT checks, determinism validation, and gate enforcement. The CI platform must support:

- Multi-OS builds (Linux + macOS per ADR-001)
- Automated gate execution (8 required gates from QUALITY_GATES.md)
- Evidence artifact retention
- Secret scanning and security checks
- Deterministic, reproducible builds

### Open Question Addressed

- **OQ-003:** "What is the minimal CI environment assumed (GitHub Actions, GitLab CI, self-hosted)?" (from `sot_index.json`)
- **PREREQ-002:** Select CI platform for automated SSOT checks

### Constraints from SoT

From DOC-14 Operating Model and QUALITY_GATES.md:

1. **Required CI Checks (PR level):**
   - G-SSOT-CONFLICT (SoT contradictions)
   - G-TRACEABILITY (REQ/ADR/CR linkage)
   - G-SECRETS (secret scanning)
   - G-CI-READY (lint/build/test)

2. **Required Release Checks (all gates):**
   - All 8 gates must PASS for release
   - Evidence artifacts stored with stable links
   - Retention ≥12 months (REQ-NFR-003)

3. **Determinism requirements:**
   - Stable environment (pinned tool versions)
   - Reproducible builds
   - Consistent ordering in all outputs

4. **Security requirements:**
   - No-egress default enforced in CI
   - Secret scanning mandatory
   - Audit logs for all pipeline runs

## Decision

### Primary CI Platform: **GitHub Actions**

**Rationale:**

1. **Zero infrastructure overhead:**
   - Hosted runners (no self-hosting required for Phase 1-3)
   - Automatic scaling
   - Free tier sufficient for MVP (2,000 minutes/month)

2. **Multi-OS support:**
   - Native Linux (ubuntu-latest) and macOS (macos-latest, macos-14 for ARM64) runners
   - Consistent environment across OSes
   - Matrix builds trivial to configure

3. **Integration with repository:**
   - Code and CI in same platform (if using GitHub for hosting)
   - Native PR checks and status reporting
   - Branch protection rules integration

4. **Ecosystem maturity:**
   - Massive GitHub Actions marketplace for reusable workflows
   - Well-documented, widely adopted
   - Strong security scanning integrations (CodeQL, dependency review)

5. **Evidence retention:**
   - Artifacts API with configurable retention (90 days default, configurable up to 400 days)
   - Stable artifact URLs for evidence linkage
   - Workflow run logs retained indefinitely (or per org policy)

6. **Determinism support:**
   - Pinnable action versions (`actions/checkout@v4`)
   - Pinnable runner images (`ubuntu-22.04` vs `ubuntu-latest`)
   - Hermetic builds possible with Docker or Nix

7. **Security:**
   - OIDC token support for keyless authentication
   - Secret scanning built-in
   - Environment protection rules for releases
   - Audit log API

**Deployment model:**
- **Phase 1-4:** GitHub-hosted runners (standard)
- **Phase 5+:** Evaluate self-hosted runners if needed for:
  - Longer retention requirements
  - Proprietary tooling
  - Network isolation requirements

## Alternatives Considered

### Alternative 1: GitLab CI

**Pros:**
- Excellent CI/CD capabilities (arguably more powerful than GitHub Actions)
- Built-in container registry
- Better support for complex DAG pipelines
- Self-hosted option from day 1

**Cons:**
- Additional platform if repository hosted on GitHub
- Free tier limited (400 minutes/month on GitLab.com)
- Larger learning curve for teams familiar with GitHub
- Less marketplace ecosystem vs GitHub Actions

**Verdict:** Strong runner-up; consider if migrating to GitLab for repository hosting

### Alternative 2: Self-Hosted (Jenkins / Drone / Buildkite)

**Pros:**
- Full control over environment
- No external dependency for CI
- Unlimited build minutes
- Custom runner configurations

**Cons:**
- Infrastructure overhead (maintenance, security patches, scaling)
- Requires dedicated ops resources
- Delayed Phase 1 timeline (weeks to set up)
- Higher complexity for multi-OS builds

**Verdict:** Deferred to Phase 5+ if GitHub Actions proves insufficient

### Alternative 3: Circle CI / Travis CI

**Pros:**
- Mature CI platforms
- Good multi-OS support

**Cons:**
- Additional vendor dependency
- Free tier limited
- Less GitHub integration vs Actions
- Travis CI reliability concerns (historical issues)

**Verdict:** Rejected; no clear advantage over GitHub Actions for this use case

## Consequences

### Positive

1. **Fast setup:** Workflows can be committed alongside code; no separate provisioning
2. **Multi-OS ready:** Linux + macOS builds in same workflow file
3. **PR automation:** Automated gate checks on every PR
4. **Marketplace leverage:** Reuse community actions for linting, testing, security scanning
5. **Evidence retention:** Artifacts API provides stable URLs for audit trails

### Negative

1. **Vendor lock-in:** Workflows not portable to other CI platforms without rewrite
2. **Free tier limits:** 2,000 minutes/month may be insufficient if Phase 6+ has heavy builds
3. **Network access:** Hosted runners have internet access by default (mitigation required for no-egress tests)
4. **Retention limits:** Default 90-day artifact retention may not meet ≥12 month requirement for releases

### Neutral / Mitigations

1. **Retention:** Configure org-level artifact retention to 400 days (max); archive critical evidence to S3/git-lfs if needed
2. **No-egress testing:** Use Docker containers with `--network none` for indexing tests
3. **Reproducibility:** Pin runner images (`ubuntu-22.04`) and action versions (`@v4` not `@main`)
4. **Cost monitoring:** Set up billing alerts if approaching free tier limits

---

## Security & Privacy Implications

1. **Secret management:** Use GitHub Secrets with environment scoping; never log secrets
2. **Network isolation:** No-egress tests run in Docker with `--network none`
3. **Audit logging:** GitHub audit log API captures all workflow runs and secret access
4. **OIDC tokens:** Use keyless authentication for artifact uploads (no long-lived credentials)
5. **Branch protection:** Require G-SECRETS gate to pass before merge

## Verification & Validation Plan

### Phase 1 CI Stub Implementation

1. **Minimal workflow:** `.github/workflows/pr-checks.yml` with:
   - Checkout code
   - Run preflight checks (`./scripts/preflight.sh`)
   - Run SSOT lint (`./scripts/check_ssot_consistency.sh`)
   - Run secret scan (`./scripts/check_no_secrets.sh`)
   - Upload evidence artifacts

2. **Multi-OS matrix:** Test on `ubuntu-22.04` and `macos-14` (ARM64)

3. **Evidence retention:** Verify artifacts accessible via API for ≥90 days

### Acceptance Criteria

- [ ] PR checks run automatically on every push
- [ ] CI passes on both Linux and macOS
- [ ] Secret scan gate blocks PRs with leaked secrets
- [ ] Evidence artifacts uploaded and accessible via stable URLs
- [ ] Workflow execution time ≤5 minutes for preflight + SSOT checks

### Evidence Location

- CI workflow file: `.github/workflows/pr-checks.yml`
- Example run artifacts: `https://github.com/<org>/<repo>/actions/runs/<run_id>`
- CI audit log: `/ssot/evidence/<date>/ADR-002/ci_audit_log.json`
