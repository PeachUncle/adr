# ADR-005: Workload Identity for External Secrets Operator

!!! info "ADR Metadata"
    **Status**:  Accepted  
    **Date**: 2025-10-09  
    **Deciders**: Platform Team, Security Team  
    **Last Updated**: 2025-10-09

## Context

External Secrets Operator (ESO) needs secure authentication to Azure Key Vault to perform secret synchronization operations. The following authentication methods were evaluated:

!!! abstract "Authentication Options"
    1. ⭐ **Workload Identity** - Azure AD Workload Identity for Kubernetes
    2.  **Service Principal with Client Secret** - Traditional client secret authentication
    3.  **Service Principal with Certificate** - Certificate-based authentication
    4.  **Managed Identity** - Azure Managed Identity (AKS only)

## Decision

!!! success "Selected Authentication Method"
    We will use **Azure AD Workload Identity** for authenticating External Secrets Operator to Azure Key Vault.

### Implementation Approach
!!! info "Key Components"
    -  **Federated Identity Credentials** between Kubernetes Service Account and Azure AD Application
    -  **OIDC Issuer** configured on AKS/Kubernetes cluster
    -  **Token Exchange** for short-lived access tokens
    -  **Least Privilege** access to specific Key Vault secrets

## Rationale

!!! tip "Why Workload Identity"
    
    **1. Security Benefits**
    
    -  No long-lived secrets in cluster
    -  Short-lived tokens (1 hour default)
    -  Strong cryptographic binding to service account
    -  Built-in token rotation

    **2. Operational Excellence**
    
    -  No secret rotation required
    -  Automatic token refresh
- ☸️ Native Kubernetes integration
- ⚡ Reduced operational overhead    **3. Compliance**
    
    -  Zero standing credentials
    -  Audit trail through Azure AD
    -  Conditional access policy support
    -  Identity governance integration

    **4. Azure Native**
    
    -  First-party Microsoft solution
    - 🛡️ Integrated with Azure RBAC
    -  Support for multiple Azure services
    -  Future-proof authentication method

!!! warning "Why Not Alternatives"
    - **Service Principal with Secret**: Long-lived credentials, rotation overhead, secret sprawl
    - **Certificate Authentication**: Complex certificate management, rotation complexity
    - **Managed Identity**: Limited to AKS, not portable to other Kubernetes distributions

## Implementation Architecture

!!! example "Components Overview"
    ```mermaid title="Workload Identity Architecture"
    graph TD
        A[Kubernetes Service Account] --> B[Workload Identity]
        B --> C[Azure AD Application]
        C --> D[Federated Identity Credential]
        D --> E[Azure Key Vault Access Policy]
        
        F[ESO Pod] --> A
        F --> G[Projected Service Account Token]
        G --> H[Token Exchange]
        H --> I[Azure AD Access Token]
        I --> J[Azure Key Vault API]
    ```

### Implementation Steps

!!! note "Setup Process"
    **1. Azure AD Application Setup**
    ```bash title="Create Azure AD Application"
    # Create Azure AD Application
    az ad app create \
      --display-name "external-secrets-operator" \
      --sign-in-audience AzureADMyOrg
    
    APP_ID=$(az ad app list --display-name "external-secrets-operator" --query "[0].appId" -o tsv)
    ```

    **2. Federated Identity Credential**
    ```bash title="Configure Federation"
    az ad app federated-credential create \
      --id $OBJECT_ID \
      --parameters '{
        "name": "eso-kubernetes-credential",
        "issuer": "https://aks-cluster-oidc-issuer-url/",
        "subject": "system:serviceaccount:external-secrets-system:external-secrets-operator",
        "audiences": ["api://AzureADTokenExchange"]
      }'
    ```

    **3. Kubernetes Service Account**
    ```yaml title="Service Account Configuration"
    apiVersion: v1
    kind: ServiceAccount
    metadata:
      name: external-secrets-operator
      namespace: external-secrets-system
      annotations:
        azure.workload.identity/client-id: "${APP_ID}"
      labels:
        azure.workload.identity/use: "true"
    ```

    **4. ClusterSecretStore Configuration**
    ```yaml title="Secret Store Setup"
    apiVersion: external-secrets.io/v1beta1
    kind: ClusterSecretStore
    metadata:
      name: azure-keyvault-store
    spec:
      provider:
        azurekv:
          authType: WorkloadIdentity
          vaultUrl: "https://itl-secrets.vault.azure.net/"
          serviceAccountRef:
            name: external-secrets-operator
            namespace: external-secrets-system
    ```

## Consequences

!!! tip "Positive Outcomes"
    -  **Enhanced Security**: No long-lived credentials in cluster
    - ⚡ **Reduced Operational Overhead**: No secret rotation required
    -  **Better Audit Trail**: Azure AD provides comprehensive logging
    -  **Compliance**: Meets zero standing privileges requirements
    -  **Future-Proof**: Microsoft's recommended authentication method

!!! warning "Negative Consequences"
    -  **Setup Complexity**: More initial configuration required
    -  **Dependency**: Requires Azure AD and properly configured OIDC
    -  **Troubleshooting**: More complex authentication flow to debug
    -  **Azure Lock-in**: Specific to Azure ecosystem

!!! danger "Risks and Mitigations"
    **Risk**: OIDC issuer misconfiguration breaks authentication  
    **Mitigation**: Validate configuration in dev/test first, backup service principal for emergencies
    
    **Risk**: Azure AD service disruption  
    **Mitigation**: Monitor Azure service health, implement fallback procedures
    
    **Risk**: Token refresh failures  
    **Mitigation**: ESO automatic retry, monitoring and alerting
