# ADR-006: Architecture Characteristics Requirements

## Status
Accepted

## Context

The BahariWatch system is designed to monitor illegal, unreported, and unregulated (IUU) fishing along Kenya's coastal regions through community-driven reporting. According to "Fundamentals of Software Architecture" (Chapter 4-6), architecture characteristics (also called non-functional requirements or quality attributes) define the success criteria for a system beyond its functional capabilities.

### Business Drivers
1. **Community Safety & Trust**: Fishers must feel safe reporting anonymously without fear of retaliation (KSh 2.9B annual losses from IUU fishing create dangerous incentives)
2. **Enforcement Effectiveness**: Real-time alerts enable rapid response to prevent fish stock depletion (146,500 MT annual production at risk)
3. **National Security**: Integration with government systems (VMS/AIS) requires high security standards
4. **Research Value**: Academic and policy analysis requires reliable, long-term data retention
5. **Blue Economy Goals**: Kenya Vision 2030 requires sustainable marine resource management

### Technical Constraints
- Mobile network reliability varies across coastal regions (2G/3G in remote areas)
- Limited computational resources on fisher mobile devices (Android 8+ target)
- Integration with legacy government systems (VMS/AIS feeds)
- Budget constraints for cloud infrastructure (~KSh 59,500 initial budget)
- Compliance with Kenya Data Protection Act 2019, GDPR, POPIA

### Architecture Characteristics Affected
Based on "Fundamentals" Chapter 5 (Extracting Architecture Characteristics from Domain Concerns), the following characteristics are critical for BahariWatch:

**Explicit Requirements from Proposal:**
- Security & Privacy (end-to-end encryption, anonymous reporting)
- Availability (99.5% uptime for community reporting)
- Performance (real-time hotspot generation, <5 second alert delivery)
- Scalability (10,000+ coastal users, spike load handling)

**Implicit Requirements** (derived from domain analysis):
- Fault Tolerance (system must continue operating despite AIS/VMS feed outages)
- Auditability (7-year data retention for legal compliance)
- Testability (automated testing for privacy controls)
- Observability (distributed tracing for debugging saga failures)

### Integration with Other ADRs
- **ADR-001 (Microservices)**: Enables independent scaling per characteristic (matching service can scale separately for performance)
- **ADR-002 (Event-Driven)**: Supports fault tolerance through async messaging and retry logic
- **ADR-003 (Monolithic DB)**: Trade-off: Simplifies consistency but may limit scalability
- **ADR-004 (Saga Pattern)**: Affects reliability through eventual consistency model
- **ADR-005 (REST API)**: Simplifies client integration but may limit real-time performance

## Decision

We establish **seven primary architecture characteristics** for BahariWatch, ranked by priority using the "Fundamentals" principle of selecting no more than 7 characteristics (Chapter 5, p. 71):

### Priority 1: Top-3 Driving Characteristics

1. **Security** (Score: 10/10 - Critical)
2. **Availability** (Score: 9/10 - Critical)
3. **Performance** (Score: 8/10 - High)

### Priority 2: Supporting Characteristics

4. **Scalability** (Score: 7/10 - High)
5. **Fault Tolerance** (Score: 7/10 - High)
6. **Auditability** (Score: 6/10 - Medium)
7. **Testability** (Score: 6/10 - Medium)

**Explicitly Excluded Characteristics:**
- **Portability**: Not required (cloud-native, single deployment target)
- **Installability**: Not applicable (SaaS model)
- **Configurability**: Limited need (single tenant, government deployment)

## Rationale

### Alternatives Considered

#### Option A: Performance as Top Priority
**Rejected** because security breaches (e.g., exposed reporter identities) would completely undermine community trust and system adoption. A 2-second vs 5-second alert delay is acceptable; a data breach is not.

#### Option B: Include 10+ Characteristics
**Rejected** based on "Fundamentals" guidance (Chapter 5, p. 71): "The more characteristics an architecture tries to support, the more complex and expensive the solution becomes. Architects should focus on the fewest characteristics that meet the business requirements."

#### Option C: Prioritize Scalability Over Availability
**Rejected** because a system that's offline can't receive reports during IUU incidents, even if it could theoretically handle millions of users. 99.5% availability for 1,000 users is more valuable than 95% availability for 100,000 users.

### Trade-Off Analysis

| Characteristic | BahariWatch Priority | Justification | Trade-Off Accepted |
|----------------|----------------------|---------------|-------------------|
| **Security** | 10/10 (Critical) | Anonymous reporting is core value proposition. Data breach = system failure. | May reduce performance (encryption overhead) |
| **Availability** | 9/10 (Critical) | IUU incidents happen 24/7. Downtime = missed reports and lost evidence. | Higher infrastructure costs (redundancy) |
| **Performance** | 8/10 (High) | Real-time alerts enable enforcement response while vessels are in area. | May limit feature complexity |
| **Scalability** | 7/10 (High) | Must support 10,000+ users across 6 coastal counties. | Acceptable: Start with vertical scaling, horizontal as needed |
| **Fault Tolerance** | 7/10 (High) | External system failures (AIS/VMS) shouldn't block report submission. | Eventual consistency (30-second delay acceptable) |
| **Auditability** | 6/10 (Medium) | Legal evidence requires immutable audit trail (7-year retention). | Storage costs increase over time |
| **Testability** | 6/10 (Medium) | Privacy controls must be verified automatically (GDPR compliance). | May slow development velocity initially |

**Key Trade-Off Decision**: We accept **eventual consistency** (ADR-004) to achieve high availability and fault tolerance. A 30-second delay in vessel matching is acceptable; a system that goes down during a report submission is not.

## Architecture Characteristics Impact

### 1. Security (Priority: Critical)
**Rating: ↑ High Positive Impact**

**Definition**: "The ability to protect data and functionality from unauthorized access and ensure data privacy" (Fundamentals, Chapter 4, p. 60)

**Quantitative Targets:**
- **Authentication**: JWT tokens with HS256, 1-hour expiry, 30-day refresh
- **Encryption at Rest**: AES-256-GCM for all sensitive data (photos, GPS coordinates)
- **Encryption in Transit**: TLS 1.3 for all HTTP communication (minimum)
- **Key Management**: Azure Key Vault with 90-day automatic rotation
- **Access Control**: RBAC with principle of least privilege (5 roles: Fisher, BMU Officer, Enforcement, Admin, Researcher)
- **Privacy**: Zero PII storage for anonymous reporters (hashed device IDs only)
- **Compliance**: GDPR Article 17 (Right to Erasure), Kenya Data Protection Act 2019 Section 25

**Measurement Methods:**
- **Penetration Testing**: Quarterly OWASP ZAP scans, <5 high-severity vulnerabilities
- **Vulnerability Scanning**: Daily dependency CVE checks (Snyk/Dependabot)
- **Audit Logs**: 100% of data access logged to ELK Stack (7-year retention)
- **Privacy Tests**: Automated EXIF stripping validation (pytest suite)

**Implementation:**
- All services authenticate via API Gateway (Kong) with JWT validation
- Photo uploads stripped of EXIF metadata (PIL/Pillow library)
- Device IDs hashed with SHA-256 + per-user salt (never stored in plaintext)
- Database connections encrypted with TLS (PostgreSQL SSL mode: require)
- Secrets managed via environment variables, never committed to Git

---

### 2. Availability (Priority: Critical)
**Rating: ↑ High Positive Impact**

**Definition**: "The percentage of time a system is operational and accessible" (Fundamentals, Chapter 4, p. 58)

**Quantitative Targets:**
- **Uptime SLA**: 99.5% availability (43.8 hours downtime per year)
- **Service Degradation**: Report submission available even if matching/alerting fails
- **Regional Resilience**: Multi-AZ deployment (at least 2 availability zones)
- **Database**: PostgreSQL with streaming replication (RPO: 1 minute, RTO: 5 minutes)
- **Message Broker**: Kafka with 3-broker cluster (min.insync.replicas=2)
- **API Gateway**: Kong with health checks (every 10 seconds, 3 failures = circuit open)

**Measurement Methods:**
- **Uptime Monitoring**: Pingdom/UptimeRobot with 1-minute checks from 3 locations
- **Synthetic Transactions**: Every 5 minutes, submit test report and verify in dashboard
- **Error Budget**: 0.5% allows ~22 hours downtime per year (tracked monthly)
- **Alerting**: PagerDuty escalation if availability drops below 99.5% in rolling 30-day window

**Implementation:**
- **Kubernetes Deployment**: 3 replicas per service (horizontal pod autoscaling)
- **Health Checks**: Liveness probes (HTTP /health endpoint), readiness probes (DB connectivity)
- **Circuit Breakers**: Hystrix/Resilience4j for external calls (5 failures → open for 30s)
- **Graceful Degradation**: Report submission stores metadata locally if S3 upload fails, retries via background job
- **Database Failover**: PostgreSQL with Patroni for automatic failover (<30 seconds)

---

### 3. Performance (Priority: High)
**Rating: ↑ High Positive Impact**

**Definition**: "The speed and efficiency with which a system responds to requests and processes data" (Fundamentals, Chapter 4, p. 59)

**Quantitative Targets:**
- **Report Submission Latency**: <5 seconds (p95), <10 seconds (p99)
- **API Response Time**: <500ms (p95) for GET /api/reports/, <200ms (p50)
- **Dashboard Load Time**: <3 seconds (p95) for initial page load
- **Vessel Matching Latency**: <15 seconds (p95) from report submission to match result
- **Alert Delivery**: <30 seconds (p95) end-to-end (report → enforcement notification)
- **Photo Upload**: <3 seconds for 5MB photo (p95)

**Measurement Methods:**
- **Application Performance Monitoring**: New Relic/Datadog with distributed tracing
- **Prometheus Metrics**: Histogram metrics for all endpoints (p50, p95, p99 latencies)
- **Load Testing**: Locust tests with 1000 concurrent users, sustained 100 req/sec
- **Real User Monitoring**: Track actual mobile app performance via Firebase Performance

**Implementation:**
- **Redis Caching**: Hot data cached with 1-hour TTL (report summaries, vessel metadata)
- **Database Indexes**: GIST index on location columns (PostGIS), B-tree on timestamp, status
- **Query Optimization**: SELECT only required fields, use EXPLAIN ANALYZE for slow queries (>100ms)
- **Async Processing**: Event-driven saga for matching/alerting (non-blocking report submission)
- **CDN**: CloudFlare for static assets (web dashboard, mobile app download)
- **Connection Pooling**: PgBouncer with 100 max connections per service

---

### 4. Scalability (Priority: High)
**Rating: ↑ High Positive Impact**

**Definition**: "The ability to handle increased load by adding resources" (Fundamentals, Chapter 4, p. 59)

**Quantitative Targets:**
- **Concurrent Users**: Support 10,000 active users across 6 coastal counties
- **Report Throughput**: 100 reports/hour sustained, 500 reports/hour peak (spike during fishing season)
- **Data Growth**: 50GB per year (photos), 5GB per year (structured data)
- **Geographic Distribution**: Serve users from Lamu to Kwale counties (<200ms latency variance)
- **Service Scaling**: Independent horizontal scaling per service (Report: 3-10 pods, Matching: 2-8 pods)

**Measurement Methods:**
- **Load Testing**: Weekly load tests with 2x current peak load (future-proofing)
- **Capacity Planning**: Monthly review of resource utilization (CPU >70% = scale trigger)
- **Kafka Lag Monitoring**: Consumer lag <100 messages per partition (if higher, scale consumers)
- **Database Size Monitoring**: Alert if growth exceeds 10GB/month (investigate data retention)

**Implementation:**
- **Horizontal Scaling**: Kubernetes HPA (CPU >70% or memory >80% → add pod)
- **Stateless Services**: No local state in service instances (enables easy scaling)
- **Database Read Replicas**: 2 read replicas for analytical queries (offload from primary)
- **Kafka Partitioning**: 10 partitions per topic (report-events, match-events, alert-events)
- **S3 Storage**: Unlimited scalability for photo storage (no capacity planning needed)
- **Rate Limiting**: API Gateway enforces 10 reports/day/user (prevents abuse, ensures fair resource allocation)

---

### 5. Fault Tolerance (Priority: High)
**Rating: ↑ High Positive Impact**

**Definition**: "The ability to continue operating correctly despite failures in components" (Fundamentals, Chapter 4, p. 60)

**Quantitative Targets:**
- **Service Failure**: System continues operating if 1 service instance fails (no data loss)
- **External System Failure**: Report submission succeeds even if AIS/VMS feeds are down
- **Database Failure**: Automatic failover within 30 seconds, zero data loss (synchronous replication)
- **Message Broker Failure**: Messages persisted to disk, replayed after recovery (no lost events)
- **Network Partition**: Services continue operating in degraded mode (eventual consistency)

**Measurement Methods:**
- **Chaos Engineering**: Monthly Chaos Monkey tests (randomly kill pods, verify recovery)
- **Failure Injection**: Quarterly tests of S3 outage, Kafka downtime, PostgreSQL failover
- **MTTR (Mean Time to Recovery)**: Target <5 minutes for service restart, <30 seconds for pod restart
- **Data Loss Prevention**: Zero data loss in last 12 months (verified via audit logs)

**Implementation:**
- **Service Redundancy**: Minimum 3 replicas per critical service (Report, Matching, Alerting)
- **Circuit Breakers**: Resilience4j with 5-failure threshold, 30-second open state, 5-second half-open
- **Bulkhead Pattern**: Separate thread pools for critical vs non-critical operations (prevent cascade failures)
- **Retry Logic**: Exponential backoff with jitter (1s, 2s, 4s, 8s max retry delay)
- **Dead Letter Queue**: Failed messages move to DLQ after 3 retries (manual intervention required)
- **Transactional Outbox**: Events stored in database before publishing (prevents dual-write problem)
- **Health Checks**: Liveness probe (is pod alive?), Readiness probe (is pod ready to serve traffic?)

---

### 6. Auditability (Priority: Medium)
**Rating: ↑ Positive Impact**

**Definition**: "The ability to track and verify all actions within the system for compliance and forensic analysis"

**Quantitative Targets:**
- **Log Retention**: 7 years for all audit logs (legal requirement for evidence)
- **Completeness**: 100% of data access, modifications, and deletions logged
- **Immutability**: Logs stored in append-only format (Elasticsearch with no delete permissions)
- **Search Performance**: <2 seconds to search 1TB of logs (Elasticsearch query)
- **Compliance**: Kenya Data Protection Act 2019, GDPR Article 30 (Records of Processing Activities)

**Measurement Methods:**
- **Audit Coverage**: Automated tests verify all endpoints log access attempts
- **Log Volume**: Track daily log ingestion rate (expected: ~5GB/day at 10,000 users)
- **Completeness Tests**: Quarterly validation that all CRUD operations are logged
- **Retention Verification**: Annual test that logs from 7 years ago are still accessible

**Implementation:**
- **ELK Stack**: Elasticsearch (storage), Logstash (ingestion), Kibana (visualization)
- **Structured Logging**: JSON format with correlation IDs (trace requests across services)
- **Log Schema**: timestamp, user_id (hashed), action, resource, IP address, result (success/failure)
- **Context Propagation**: Correlation IDs passed via HTTP headers (X-Correlation-ID)
- **Sensitive Data Masking**: GPS coordinates logged in truncated form (lat/lon to 2 decimal places)
- **Alerting**: Alert if log volume drops >50% (indicates logging failure, not reduced activity)

---

### 7. Testability (Priority: Medium)
**Rating: ↑ Positive Impact**

**Definition**: "The ease with which software can be tested for correctness and quality"

**Quantitative Targets:**
- **Code Coverage**: >80% for all services (unit + integration tests)
- **Test Execution Time**: <5 minutes for unit tests, <15 minutes for integration tests
- **Contract Tests**: 100% of event schemas validated (Pact for consumer-driven contracts)
- **Privacy Tests**: Automated validation of EXIF stripping, device ID hashing
- **Security Tests**: Weekly OWASP ZAP scans, <5 high-severity vulnerabilities

**Measurement Methods:**
- **Coverage Reports**: SonarQube tracks coverage per service, fails CI if <80%
- **Test Pyramid**: 70% unit tests, 20% integration tests, 10% E2E tests (fast feedback)
- **Flaky Test Tracking**: Tests that fail intermittently are flagged and fixed within 1 sprint
- **Test Data Management**: Testcontainers for integration tests (real PostgreSQL, Kafka)

**Implementation:**
- **Unit Tests**: pytest with mocked dependencies (report_service, matching_service, etc.)
- **Integration Tests**: Testcontainers spin up PostgreSQL, Kafka, Redis for realistic tests
- **Contract Tests**: Pact verifies event schemas between producers and consumers
- **E2E Tests**: Selenium/Playwright tests critical user journeys (submit report → receive alert)
- **Performance Tests**: Locust load tests run nightly against staging environment
- **Chaos Tests**: Chaos Monkey randomly kills pods in staging (verify graceful degradation)
- **CI/CD Pipeline**: GitHub Actions runs all tests on every commit (fail fast)

## Consequences

### Positive

1. **Clear Priorities**: Development team knows which characteristics to optimize for (security > availability > performance)
2. **Measurable Targets**: Quantitative SLAs enable objective validation ("Is 99.5% availability achieved?")
3. **Informed Trade-Offs**: When performance conflicts with security, security wins (encryption overhead accepted)
4. **Architecture Alignment**: ADR-001 (microservices) directly supports independent scaling for performance
5. **Stakeholder Confidence**: Explicit security guarantees increase fisher trust in anonymous reporting
6. **Compliance by Design**: GDPR/Kenya Data Protection Act requirements built into architecture

### Negative

1. **Complexity Cost**: Achieving 99.5% availability requires redundancy (3 replicas, multi-AZ) → higher infrastructure costs
2. **Performance Overhead**: AES-256 encryption adds ~10-20ms latency per request (acceptable trade-off)
3. **Development Velocity**: 80% test coverage requirement may slow feature development initially
4. **Operational Burden**: Monitoring 7 characteristics requires robust observability stack (ELK, Prometheus, Grafana)
5. **Over-Engineering Risk**: If user adoption is slow, we may have over-provisioned (mitigation: start with 3 replicas, scale as needed)

### Neutral

1. **Eventual Consistency**: 30-second delay in vessel matching is acceptable for use case (not real-time trading)
2. **Storage Costs**: 7-year audit log retention increases costs over time (budgeted, legally required)
3. **Learning Curve**: Team must learn distributed systems patterns (circuit breakers, sagas) → invest in training

#### FF-005: Fault Tolerance - Circuit Breaker Test
```python
# Integration test
def test_circuit_breaker_opens_on_s3_failure():
    """Verify circuit breaker opens after 5 consecutive S3 failures"""
    mock_s3 = Mock(side_effect=S3Exception("Service Unavailable"))
    
    for i in range(5):
        with pytest.raises(S3Exception):
            photo_storage_service.upload(photo, report_id)
    
    # 6th call should fail fast (circuit open)
    start = time.time()
    with pytest.raises(CircuitBreakerOpenException):
        photo_storage_service.upload(photo, report_id)
    duration = time.time() - start
    
    assert duration < 0.1, "Circuit breaker should fail fast (<100ms)"
```

**Trigger**: Run on every commit, weekly chaos test in staging  
**Failure Action**: Block deployment if test fails

### Security Implications

1. **Encryption Key Rotation**: Azure Key Vault rotates keys every 90 days (automated, zero-downtime)
2. **JWT Token Expiry**: Access tokens expire after 1 hour (reduce window for token theft)
3. **Rate Limiting**: 10 reports/day/user prevents abuse (DDoS mitigation)
4. **SQL Injection Prevention**: Django ORM parameterizes queries (no raw SQL in production)
5. **XSS Prevention**: Django REST Framework auto-escapes responses (Content-Security-Policy headers)

### Data Privacy Implications

1. **GDPR Article 17 (Right to Erasure)**: Anonymous reporters cannot be identified → cannot exercise right (disclosed in privacy policy)
2. **GDPR Article 30 (Records of Processing)**: Audit logs track all data processing activities (7-year retention)
3. **Kenya Data Protection Act 2019 Section 25**: Data minimization principle → only collect essential data (GPS, photo, timestamp)
4. **POPIA Section 11 (Processing Limitation)**: Data processed only for IUU monitoring (no secondary use without consent)

## Implementation Notes

### For Developers

1. **Security First**: When in doubt, prioritize security over performance. Example: Always hash device IDs, even if it adds 5ms latency.
2. **Measure, Don't Guess**: Use Prometheus metrics to validate performance targets. If p95 latency exceeds target, profile and optimize.
3. **Fail Fast**: Use circuit breakers for all external calls (AIS/VMS, S3, SMS gateway). Don't let one slow dependency block critical paths.
4. **Write Tests First**: Achieve 80% coverage by writing unit tests alongside code (TDD where possible).
5. **Monitor Everything**: Add Prometheus metrics for every new endpoint. Include business metrics (reports/hour) alongside technical metrics (latency).

### For DevOps

1. **Automate Fitness Functions**: All fitness functions should run automatically (CI/CD, Prometheus alerts).
2. **Capacity Planning**: Review resource utilization monthly. Scale before hitting limits (don't wait for outage).
3. **Chaos Testing**: Run Chaos Monkey weekly in staging, quarterly in production (during low-traffic hours).
4. **Backup Verification**: Test PostgreSQL restore monthly (verify RPO/RTO targets).
5. **Log Retention**: Archive Elasticsearch indices monthly to S3 (reduce storage costs, maintain 7-year retention).

### For Product Team

1. **Manage Expectations**: 30-second eventual consistency means alerts aren't instant (educate enforcement officers).
2. **Graceful Degradation**: Report submission works even if matching fails (prioritize availability over completeness).
3. **Privacy Trade-Offs**: Anonymous reporting means we can't send reporters updates (document in user guide).
4. **Performance Budgets**: New features cannot exceed 5-second p95 latency budget (requires performance testing before launch).
