## Summary

### Preamble

The user need appeared to have CPU monitoring dashboard with the `cpu_usage` metrics visualized.

### Status

**Approved**

### Decision drivers

`docker_stats` was selected due to lack of experience of using any OTEL receiver, so to explore anything in reasonable slot window (up to 4 days).
This receiver brought possibility to add additional attributes and labels and filter them in the pipeline which is interesting advantage.

### Prospects

Use only `docker_stats` receiver:
* ✅ Cheap to implement for the docker/docker swarm environment
* ✅ We have container containers & compose details in this context
* ❌ Limited only to the docker/docker swarm environment
* ❌ Limited numbers of available metrics
* ❌ Docker socket must be exposed to the container - security risk
* ❌ Stability of all provided metrics: Development
* ❌ Lack of throttling per core, throttling package, load average, CPU frequency metrics
  * ➡️ Can be used with read only mount inside sidecar
* Available data sources:
  * container_blockio_io_service_bytes_recursive_total
  * container_cpu_limit [scalar]
  * container_cpu_shares_ratio
  * container_cpu_throttling_data_periods_total
  * container_cpu_throttling_data_throttled_periods_total
  * container_cpu_throttling_data_throttled_time_nanoseconds_total
  * container_cpu_usage_kernelmode_nanoseconds_total
  * container_cpu_usage_nanoseconds_total
  * container_cpu_usage_system_nanoseconds_total
  * container_cpu_usage_usermode_nanoseconds_total
  * container_cpu_utilization_ratio [scalar]

Use `hostmetrics` and `ebpf`
* ✅ Can be used also inside k8s, vm and in the other places.
* ✅ Provides huge number of data sources = more interesting metrics
* ❌ We need to expose host details to the container
* ❌ Requires additional capabilities and even access to the host fs.
* Available data sources:
  * system.cpu.utilization
  * system.cpu.time
