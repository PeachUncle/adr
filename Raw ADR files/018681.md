# ADR-002: Terminal Backend Architecture

## Status
Accepted

## Context
termctrl needs to support multiple terminal emulators and terminal multiplexers with varying capabilities. Each terminal has different APIs, feature sets, and integration methods. We need an architecture that:

- Supports multiple terminals (iTerm2, tmux, generic terminals)
- Handles nested scenarios (tmux inside iTerm2)
- Allows graceful degradation when features are unavailable
- Enables easy addition of new terminal backends
- Provides a unified interface for all operations

## Decision
We will implement a **plugin-based backend architecture** with automatic terminal detection and capability discovery.

## Architecture Overview

```go
type TerminalBackend interface {
    Detect() (*TerminalInfo, error)
    Capabilities() TerminalCapabilities
    Focus(target *FocusTarget) error
    Notify(notification *Notification) error
    ListSessions() ([]*SessionInfo, error)
    PeekContent(sessionID string) (string, error)
}
```

### Core Components

**Terminal Detector**
- Runs detection methods for each registered backend
- Returns ordered list of detected terminals (innermost to outermost)
- Provides capability matrix for detected terminals

**Backend Registry**
- Maintains list of available backends
- Handles backend initialization and lifecycle
- Routes operations to appropriate backends

**Command Dispatcher**
- Implements operation fallback chain
- Coordinates multi-backend operations for nested terminals
- Provides unified error handling and response formatting

## Backend Implementations

### iTerm2 Backend
**Detection Method**: Check for `$TERM_PROGRAM=iTerm.app` and iTerm2 process
**Capabilities**: Full window/tab/session management, native notifications, content access, split pane support
**Integration**: 
- **Primary**: iTerm2 Python API via websocket/protobuf communication
- **Fallback**: AppleScript commands via `osascript` for legacy compatibility

```go
func (b *ITerm2Backend) Detect() (*TerminalInfo, error) {
    if os.Getenv("TERM_PROGRAM") == "iTerm.app" {
        return &TerminalInfo{
            ID:   "iterm2",
            Name: "iTerm2",
        }, nil
    }
    return nil, nil
}
```

### tmux Backend
**Detection Method**: Check for `$TMUX` environment variable
**Capabilities**: Session management, pane operations, content capture
**Integration**: tmux command-line interface

```go
func (b *TmuxBackend) Detect() (*TerminalInfo, error) {
    if _, exists := os.LookupEnv("TMUX"); exists {
        return &TerminalInfo{
            ID:   "tmux",
            Name: "tmux",
        }, nil
    }
    return nil, nil
}
```

### Generic Backend
**Detection Method**: Always available as fallback
**Capabilities**: Basic system notifications, limited focus control
**Integration**: Cross-platform system APIs

## Nested Terminal Handling

When multiple terminals are detected (e.g., tmux inside iTerm2):

1. **Layer Detection**: Identify all terminal layers from innermost to outermost
2. **Capability Aggregation**: Combine capabilities from all layers
3. **Operation Routing**: Choose the most appropriate layer for each operation
4. **Fallback Strategy**: Try multiple layers if primary operation fails

Example for focus operation in nested scenario:
1. Try tmux pane focus (most specific)
2. Fall back to iTerm2 tab focus (broader scope)
3. Fall back to system window focus (broadest scope)

## Operation Implementation Strategy

### Focus Operations
- **tmux**: `tmux select-pane`, `tmux select-window`
- **iTerm2**: Python API window/tab/session activation with AppleScript fallback
- **Generic**: System window focus APIs (X11, Win32, Cocoa)

### Notification Operations
- **iTerm2**: Native notification system via Python API with AppleScript fallback
- **tmux**: Terminal bell or external notification
- **Generic**: System notification APIs (`notify-rust`)

### Discovery Operations
- **tmux**: Parse `tmux list-sessions`, `tmux list-panes`
- **iTerm2**: Python API queries for windows/tabs/sessions with AppleScript fallback
- **Generic**: Limited to current terminal session

### Content Access
- **tmux**: `tmux capture-pane` command
- **iTerm2**: Python API content access with AppleScript fallback
- **Generic**: Not available (graceful degradation)

## Error Handling and Fallbacks

### Capability-Based Operations
```go
func (d *Dispatcher) Focus(target *FocusTarget) error {
    backends := d.getCapableBackends(CapabilityFocus)
    for _, backend := range backends {
        if err := backend.Focus(target); err != nil {
            if isRecoverable(err) {
                continue
            }
            return err
        }
        return nil
    }
    return ErrNoCapableBackend
}
```

### Graceful Degradation Examples
- Focus operation unavailable → Log warning, continue
- Notification unavailable → Fall back to terminal bell
- Content access unavailable → Return error with helpful message

## Future Extension Points

### New Backend Integration
1. Implement `TerminalBackend` trait
2. Add detection logic for terminal identification
3. Register backend with the backend registry
4. Add platform-specific dependencies if needed

### New Operation Types
1. Add method to `TerminalBackend` trait
2. Implement in each backend (or return `NotSupported`)
3. Add capability flag for feature detection
4. Update command dispatcher routing logic

## Consequences

### Positive
- **Extensibility**: Easy to add new terminals and operations
- **Robustness**: Graceful degradation when features unavailable
- **Flexibility**: Handles complex nested terminal scenarios
- **Maintainability**: Clear separation of concerns between backends

### Negative
- **Complexity**: More complex than single-backend approach
- **Testing**: Requires testing across multiple terminal combinations
- **Performance**: Overhead from capability detection and routing

### Mitigation Strategies
- **Caching**: Cache detection results for performance
- **Testing Matrix**: Automated testing across terminal combinations
- **Documentation**: Clear backend development guidelines
- **Capability Discovery**: Runtime capability reporting for users

## Alternative Considered
A single backend approach was considered but rejected due to the need to support multiple terminals with different capabilities and the requirement for nested terminal scenarios.
