# CLI Input and Output

## Context and Problem Statement

There are numerous choices users of the CLI need to make in order to configure an environment. How best can a user know what choices exist and the options for each choice? How can we ensure that a pro user can quickly create an environment configuration using the CLI in a repeatable way? How can we ensure that the choices made for a given environment are tracked and versioned?

<!-- This is an optional element. Feel free to remove. -->
## Decision Drivers

* Beginner users can quickly create a "default" deployment without significant effort in understanding all possible choices
* Pro users can quickly create a custom environment suited for their needs
* Environment creation with the same options is an easily repeatable process
* Choices for environment creation can be tracked and versioned
* Each reference architecture can easily specify their list of environment choices and options, as well as sensible defaults
* Multiple defaults for each reference architecture are supported, allowing e.g. "dev" vs. "pre-prod" vs. "prod" environments

## Considered Options

* CLI Q&A
* CLI Config File Driven
* CLI UX Driven

## Decision Outcome

Chosen option: "CLI Config File Driven", because it is easiest to implement, meets our needs, and is adaptable to the other two (e.g. in the future Q&A could create a config file, which would drive this implementation).

### Consequences

* Good, because beginner users can choose a sensible default configuration file from the reference architecture
* Good, because pro users can easily tune a default configuration or the baseline template to meet their needs, and have those changes reviewed and approved by others
* Good, because configuration files can be easily checked into source control, achieving tracking and versioning
* Good, because multiple configuration defaults can easily be created
* Bad, because the wall of options in a configuration file can be daunting to new users

## Pros and Cons of the Options

### CLI Q&A

The CLI, driven by a configuration file in the reference architecture, surfaces a series of questions (with options and defaults) which, when answered, output a configuration file.

* Good, because users can slowly acclimate to the options for a given architecture
* Good, because the order of the questions can convey semantics (e.g. earlier questions can be more pivotal, or groups of questions can all be focused on a particular aspect)
* Neutral, because configurations cannot easily be tracked and versioned, only the output. Can be mitigated by having the CLI output both the final configuration and the decision record for all Q&A pairs.
* Bad, because it only supports one set of defaults (can be mitigated by having multiple question configuration files for an architecture)
* Bad, because pro users will find it difficult to quickly create (and re-create) a custom environment configuration

Note: There is some contention here as to whether the lack of reproducibility/trackability of inputs is an issue. Some on CAIRA believe that users will never come back to the CLI to re-create an already created environment configuration. The decision makers (see header) believe that hedging to accommodate reproducibility is worthwhile.

### CLI UX Driven

Similar to Q&A, only driven by a UX instead of console-based Q&A

All Pros/Cons same as `CLI Q&A`, with the addition of:

* Good, because UX has real estate to include documentation and links to documentation easily
* Good, because UX can make it easier for non-DevOps-aware users to consume (NOTE: This is _not_ our target audience)
* Bad, because coupling the UX to the CLI can make revising/enhancing/maintaining each more difficult (e.g. people may need to rev their CLI because of a UX bug)
* Bad, because it increases the size and attack surface of the CLI

## More Information

One option for the CLI using configuration files is that it could take a config file containing a reference to a defaults config file and any overrides, making the actual configuration file quite small and allowing custom environments to be specified concisely. One consequence of this is that changes to the defaults in a reference architecture would propagate to the custom configuration without the explicit choice of the user, the next time they invoked the CLI, which would hamper repeatability.

Configuration files should allow for the specification of existing resources (e.g. for users deploying into an existing VNet). Whether configuration files should support the pass-through of arbitrary terraform code (e.g. for users who want to deploy additional resources beyond what is configured) is beyond the scope of this ADR and left to the implementors.
